## What it is

Every running program has three default streams: standard input (stdin, number 0) where it reads, standard output (stdout, 1) where it writes normal results, and standard error (stderr, 2) where it writes error messages. Redirection changes where a stream points, usually to a file, using operators like `>`, `>>`, `<` and `2>`. A pipe, written `|`, connects the stdout of one command to the stdin of the next, so data flows between programs without a temporary file.

## Why it exists

By default a command reads from the keyboard and writes to the screen. That is useless for automation: you want output saved to a log, errors kept separately, and the result of one tool fed into another. Redirection lets you capture or supply those streams with files. Pipes let you build a small chain of simple tools, each doing one job, instead of one giant command. Together they are how the shell glues programs into pipelines.

## How it works

<Compare id="redirect-vs-pipe" />

1. The shell sets up the streams before the command runs. `> file` points stdout at `file`, creating or truncating it; `>>` points it at the file but keeps the contents and appends.
2. `< file` points stdin at a file, so the command reads it as if typed.
3. `2> file` points stderr at a file. `2>&1` makes stderr point wherever stdout currently points.
4. A pipe runs both commands at once and connects the first command's stdout to the second's stdin.
5. Because the shell reads redirections left to right, `> out 2>&1` sends both to `out`, but `2>&1 > out` sends only stdout to `out` and leaves errors on the terminal.

## Example

Run a command, capture normal output to a file and merge errors into it, then filter a log with a pipe:

```bash
java -jar app.jar > app.log 2>&1
cat app.log | grep -i error
```

```text output
2026-11-02 10:02 ERROR failed to connect to db
2026-11-02 10:05 error: retrying
```

What to notice:

- `> app.log` captures stdout; `2>&1` then points stderr at the same file, so both normal and error lines land in `app.log`.
- `2>&1` comes *after* `> app.log`. If it came first, errors would still go to the terminal.
- The pipe `cat app.log | grep -i error` sends the file's text straight into grep, with no second file on disk.

## Rules and defaults

| Operator | Effect |
|---|---|
| `> file` | stdout to file, overwrite |
| `>> file` | stdout to file, append |
| `< file` | stdin from file |
| `2> file` | stderr to file |
| `2>> file` | stderr to file, append |
| `2>&1` | stderr to wherever stdout points now |
| `cmd1 \| cmd2` | cmd1 stdout to cmd2 stdin |

- `>` silently overwrites an existing file. Use `>>` when you want to keep the old content.
- Redirections are applied left to right, so the position of `2>&1` matters.
- A pipe connects only stdout by default; add `2>&1` or `|&` to also pipe stderr.

## Common mistakes

- **Expecting > to capture errors.** `>` only redirects stdout; errors still show on screen until you add `2>&1`.
- **Wrong order of 2>&1.** It copies the *current* stdout target, so it must come after `> file`.
- **Using > on a file you meant to keep.** `>` truncates it first. Reach for `>>` to append.

## Interview Qs

### What are stdin, stdout and stderr?

They are the three default streams of every process: stdin (file descriptor 0) is its input, stdout (1) is its normal output, and stderr (2) is its error output. Keeping errors on their own stream lets you log or hide them separately from normal output.

### How do you send both normal output and errors to one file?

`cmd > file 2>&1`. `> file` points stdout at the file, then `2>&1` points stderr at the same place as stdout. The order matters: `2>&1` must come after `> file`, or errors still go to the terminal.

### What is the difference between a pipe and redirection?

Redirection (`>`, `>>`, `<`) connects a stream to a file on disk. A pipe (`|`) connects one command's stdout to the next command's stdin, with no file in between. Redirect to save output; pipe to pass it straight into another command.
