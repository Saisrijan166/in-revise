## What it is

Beyond the nine [read, write and execute bits](card:file-permissions), a file carries three special bits. setuid ("set user ID") and setgid ("set group ID") change which identity a program runs as. The sticky bit changes who may delete files in a directory. They are set with a fourth, leading octal digit in [chmod](card:chmod) and shown as `s` or `t` in `ls -l`.

## Why it exists

Some everyday tasks need power the user does not have. Changing your password means writing to the root-only `/etc/shadow`; setuid lets the trusted `passwd` program do that briefly as root. Shared directories need safety too: `/tmp` must let every user create files, but one user must not be able to wipe another's. The sticky bit gives exactly that, so a world-writable folder stays usable.

## How it works

| Bit | Octal | On a file | On a directory | ls -l |
|---|---|---|---|---|
| setuid | 4 | run as the file's owner | (no standard effect) | `s` in owner x slot |
| setgid | 2 | run as the file's group | new files inherit the group | `s` in group x slot |
| sticky | 1 | (no modern effect) | only a file's owner may delete it | `t` in others x slot |

1. Add the bit as a leading digit: `chmod 4755 prog` (setuid), `2755` (setgid), `1777` (sticky).
2. In `ls -l`, the special bit replaces the matching execute letter: `s` if execute is also set, uppercase `S` if not; the sticky bit shows as `t` (or `T`).
3. When a setuid program starts, the kernel gives the process the file owner's privileges instead of the caller's.

## Example

```bash
ls -l /usr/bin/passwd
ls -ld /tmp
```

```text output
-rwsr-xr-x 1 root root 68208 /usr/bin/passwd
drwxrwxrwt 10 root root  4096 /tmp
```

What to notice:

- `passwd` shows `rws` for the owner: the `s` is setuid, so it runs as root (its owner) and can update `/etc/shadow` for any user.
- `/tmp` ends in `t`: it is world-writable (`rwxrwxrwx`) but sticky, so each user can delete only the files they own.

## Rules and defaults

- **setuid is ignored on scripts** on Linux; it works on compiled binaries only, for safety.
- **setgid on a directory** makes new files and subfolders take the directory's group, which keeps a shared project consistent.
- **Sticky only matters on directories** today; its old meaning for files (keep in swap) is obsolete.
- **Security risk:** a setuid-root program with a bug can hand out root. Keep these programs few, small and patched; audit them with `find / -perm -4000`.

## Common mistakes

- **Reading the sticky bit as "admin only".** It restricts deletion to each file's owner (plus the directory owner and root), not to root alone.
- **Expecting setuid to work on a shell script.** Linux ignores setuid on interpreted scripts; use a compiled helper or sudo instead.
- **Confusing `s` and `t` positions.** `s` appears in the owner or group execute slot (setuid/setgid); `t` appears in the others execute slot (sticky).

## Interview Qs

### What does the setuid bit do, and give an example?

setuid makes an executable run with its owner's privileges rather than the caller's. The classic example is `/usr/bin/passwd`, owned by root with setuid set: any user can run it to change their own password, which requires writing to the root-only `/etc/shadow`.

### What is the sticky bit used for?

On a shared, world-writable directory like `/tmp`, the sticky bit restricts deletion so a user can remove only files they own (plus the directory owner and root). It stops users from deleting each other's temporary files.

### How are special permissions shown in ls -l and set with chmod?

They replace the execute letters: `s` in the owner slot is setuid, `s` in the group slot is setgid, `t` in the others slot is sticky. Set them with a leading octal digit: `chmod 4755` (setuid), `2755` (setgid), `1777` (sticky).
