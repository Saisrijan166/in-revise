## What it is

[SSH](term:ssh) (Secure Shell) logs you in to another machine and gives you a shell there, over an encrypted connection on port 22. You run `ssh user@host`. `scp` copies files between machines over that same SSH connection, so the files are encrypted in transit. Together they are how you reach and manage remote servers from your own terminal, safely over an open network.

## Why it exists

Servers usually have no screen or keyboard; you work on them from your own machine across the internet. That link must be private, or anyone between could read your commands and passwords. SSH encrypts the whole session and proves the server's identity, replacing old tools like telnet that sent everything in clear text. `scp` adds file copying over the same secure channel, so deploying a build does not need a separate, unprotected transfer.

## How it works

<Steps>
<Step title="Make a key pair">
`ssh-keygen` creates a private key (kept secret on your machine) and a public key.
</Step>
<Step title="Install the public key">
Put the public key in the server's `~/.ssh/authorized_keys` (one line per allowed key).
</Step>
<Step title="Connect">
`ssh user@host` authenticates with the key, with no password prompt; `scp` reuses the same login.
</Step>
</Steps>

1. The private key never leaves your machine; the server only ever holds the matching public key.
2. On connect, SSH proves you hold the private key without sending it, then opens the encrypted shell.
3. `scp file user@host:/path` runs the same login and streams the file over the encrypted link.

## Example

```bash
scp app.jar deploy@10.0.0.5:/opt/app/
```

```text output
app.jar                       100%   48MB   22.4MB/s   00:02
```

What to notice: the file is copied to `/opt/app/` on the remote host `10.0.0.5` as user `deploy`, over SSH, so the transfer is encrypted. The progress line shows percent, size and speed. To copy the other way, swap the order: `scp deploy@10.0.0.5:/opt/app/app.jar .`.

## Rules and defaults

- **Default port 22:** override with `ssh -p 2222 user@host` and `scp -P 2222 ...` (note the capital `P` for scp).
- **Key auth is preferred:** keys are stronger than passwords and work in scripts; the private key stays on your machine.
- **scp direction:** the remote side is written `user@host:/path`; the local side is a plain path. Order is source then destination.
- **scp uses SFTP under SSH since OpenSSH 9.0;** behaviour is the same for everyday copies.

## Not to be confused with

`scp` copies a file each time, resending everything. `rsync` compares both sides and transfers only the changed parts, and can resume. Rule: a one-off copy, use scp; a large or repeated sync, use rsync (it also runs over SSH).

## Common mistakes

- **Thinking key login is less secure than a password.** It is stronger: the private key never leaves your machine and cannot be phished like a typed password.
- **Getting scp order or case wrong.** It is source then destination, and the port flag is `-P` (capital) for scp but `-p` for ssh.

## Interview Qs

### What is SSH and what port does it use?

SSH (Secure Shell) is a protocol and command for logging in to a remote machine over an encrypted connection, so commands and credentials are not sent in clear text. You run `ssh user@host`. The default port is 22.

### How does key-based authentication work, and why prefer it?

`ssh-keygen` makes a private and a public key. The public key goes in the server's `~/.ssh/authorized_keys`; the private key stays with you. SSH proves you hold the private key without sending it. It is safer than passwords and works without a prompt, so it suits scripts.

### What is the difference between scp and rsync?

Both copy files over SSH. `scp` re-sends the whole set each time. `rsync` compares source and destination and transfers only the changed parts, and can resume an interrupted copy, so it is far faster for large or repeated transfers.
