## What it is

Linux is organised in layers. At the bottom is the hardware: CPU, memory, disk and network. The [kernel](card:kernel-and-userspace) sits directly above it and is the only layer that controls the hardware. Above the kernel are the shell and system libraries, and on top are user applications such as a Java program or a web browser. Each layer uses the one directly below it.

## Why it exists

If every program drove the hardware itself, two programs could fight over the same memory or disk and crash the machine. Layering puts the kernel in charge of the hardware, so it can share the CPU and memory safely and stop one program from harming another. Libraries add a second benefit: apps reuse tested code instead of rewriting it.

1. You run an application; it calls a system library such as the C library.
2. The library asks the kernel to do the real work: read a file, send network data or get memory.
3. The kernel drives the hardware and returns the result back up the stack.

## Rules and defaults

- Applications never address hardware directly; the kernel does it on their behalf.
- The shell is itself an application in the top layer, not part of the kernel.
- Replacing the shell or libraries does not change the kernel below.

## Not to be confused with

The [kernel and user space](card:kernel-and-userspace) split is about privilege, who may touch hardware; the layer stack is about who calls whom. Rule: layers describe the call path, while the kernel and user-space line describes the privilege boundary.

## Common mistakes

- Thinking the shell is part of the kernel; it is an ordinary program in the top layer.
- Believing apps reach the disk or network directly; they always go through the kernel.

## Interview Qs

### What are the layers of a Linux system?

From bottom to top: hardware, the kernel, the shell and system libraries, and user applications. The kernel is the only layer that controls hardware; applications reach it through libraries, and each layer uses the one directly below it.

### Where does the shell sit in this stack?

The shell is a user application in the top layer, like any other program. It reads your commands and asks the kernel, through libraries, to run them. It is not part of the kernel.

### Why do applications not access hardware directly?

So the kernel can share hardware safely and keep programs isolated. If apps drove the hardware, two programs could corrupt each other's memory or data. The kernel acts as the single gatekeeper for CPU, memory, disk and network.
