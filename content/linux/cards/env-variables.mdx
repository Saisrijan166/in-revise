## What it is

An environment variable is a `name=value` setting that a process keeps and passes on to the programs it starts. The shell holds many of them. [PATH](term:path-variable) is a colon-separated list of directories the shell searches for commands; `HOME` is your home directory; `USER` is your login name; `PWD` is the current working directory. You read any of them with `$NAME`, as in `echo $HOME`.

## Why it exists

A program often needs a setting from outside its own code: where Java lives, which database to use, what region to run in. Hard-coding these would mean editing and rebuilding the program for every machine. Environment variables let the shell pass such settings in by name, so the same program behaves correctly on your laptop, a test box and production without any change to its code.

## How it works

| Step | Command | What it is |
|---|---|---|
| Set | `NAME=value` | a shell variable, visible only in this shell |
| Pass on | `export NAME` | now an environment variable child processes inherit |
| Read | `echo $NAME` | prints the current value |
| Remove | `unset NAME` | deletes it from the shell |

1. `NAME=value` creates a shell variable. This shell can read it, but programs it starts cannot.
2. `export NAME` (or `export NAME=value`) marks it so every child process gets a copy in its environment.
3. A child process receives a copy at start; changing it later does not flow back to the parent.

## Example

```bash
GREETING=hello          # shell variable only
bash -c 'echo [$GREETING]'   # child does not see it
export GREETING
bash -c 'echo [$GREETING]'   # now it does
```

```text output
[]
[hello]
```

What to notice: the first child shell prints empty brackets because `GREETING` was never exported. After `export GREETING`, the second child inherits it and prints `hello`. The value lives only in this session; to have it in every new shell, add the `export` line to `~/.bashrc`.

## Rules and defaults

- **`$` reads, not sets:** use `$NAME` to read a value and `NAME=value` to set one. No spaces around `=`.
- **Inherited, not shared:** a child gets a copy at launch. It cannot change the parent's environment, and later changes in the parent do not reach an already-running child.
- **Set by login:** `HOME`, `USER` and `PATH` are set for you when you log in; you rarely set them by hand.
- **Persistence is manual:** nothing set at the prompt survives a new shell. Put `export` lines in `~/.bashrc` (interactive shells) or `~/.profile` (login shells).

## Not to be confused with

A shell variable (`NAME=value`) is private to the current shell; an environment variable (after `export`) is handed to child processes too. Rule: if a program you launch must read it, it has to be exported.

## Common mistakes

- **Expecting a non-exported variable to reach a program.** Without `export`, only the shell itself sees it.
- **Putting spaces around `=`.** `NAME = value` makes the shell run `NAME` as a command. Write `NAME=value`.
- **Thinking a prompt setting is permanent.** It lasts only for that shell; persist it in `~/.bashrc` or `~/.profile`.

## Interview Qs

### What is the difference between a shell variable and an environment variable?

A shell variable (`NAME=value`) is visible only in the current shell. An environment variable is one that has been `export`ed, so the shell passes a copy to every child process it starts. Only exported variables reach the programs you launch.

### How do you make an environment variable permanent?

A variable set at the prompt lasts only for that shell. Add the `export NAME=value` line to a startup file such as `~/.bashrc` or `~/.profile`, which the shell reads each time it starts, so new shells get the variable again.

### What does PATH contain and why does it matter?

`PATH` is a colon-separated list of directories the shell searches, in order, to find the program for a command you type. If a command's directory is not on `PATH`, you get "command not found" even though the program exists; you then run it by full path or add its directory to `PATH`.
