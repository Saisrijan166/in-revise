## What it is

Amazon SNS (Simple Notification Service) is a managed publish/subscribe service. A publisher sends one message to a topic, which is a named channel. Each subscription on the topic names one endpoint, such as an [SQS queue](card:sqs), a Lambda function, an HTTPS URL, an email address or a phone number, and SNS pushes its own copy to each one. Where SQS holds a job for one worker, SNS tells everyone at once.

## Why it exists

When a ₹500 payment succeeds, the receipt worker, the ledger and the customer alert all need to know. If the payment API called each one, it would need code for every consumer, and one slow or broken consumer would delay or fail the payment. With SNS the API publishes once and does not know who listens. A new consumer is one new subscription, and the payment API does not change.

## How it works

1. You create the topic and subscribe each endpoint. A queue also needs an access policy that lets this topic call sqs:SendMessage on it.
2. The payment API calls Publish with the message body and optional message attributes, such as method = UPI.
3. SNS checks each subscription's filter policy. A subscription without one gets every message.
4. SNS pushes a copy to each matching subscription. A copy sent to a queue waits there until that service reads it.
5. If a delivery fails with a server-side error, SNS retries it. If retries run out, or the error is client-side (for example, the endpoint was deleted), the copy is dropped unless the subscription has a dead-letter queue.

## Example

The payment API publishes once, with the payment method as a message attribute:

```java
sns.publish(b -> b
    .topicArn("arn:aws:sns:ap-south-1:111122223333:payment-succeeded")
    .message("{\"paymentId\":\"pay_123\",\"amount\":500}")
    .messageAttributes(Map.of("method", MessageAttributeValue.builder()
        .dataType("String").stringValue("UPI").build())));
```

The fraud-check queue's subscription has this filter policy:

```json
{ "method": ["UPI"] }
```

What to notice:

- The publisher has no list of consumers; receipts, ledger and fraud check are only subscriptions on the topic.
- The filter policy reads message attributes by default. Set the subscription's FilterPolicyScope to MessageBody to filter on the JSON body instead.
- The receipts and ledger subscriptions have no filter policy, so they get every payment. The fraud check gets only UPI payments.
- By default a queue receives a JSON envelope (Type, MessageId, TopicArn, Message and more), and the worker reads the payment from Message. Turn on RawMessageDelivery to get the body exactly as published.

## Rules and defaults

- **Retries (at the time of writing):** to SQS and Lambda endpoints, up to 100,015 times over 23 days; to email, SMS and mobile push, 50 times over 6 hours; HTTP/S endpoints take a retry policy you set.
- **Subscription dead-letter queue:** an SQS queue set on a subscription, not on the topic, in the same account and Region.
- **Larger messages:** above 1 MiB, the SNS Extended Client Library stores the payload in S3, up to 2 GB.
- **FIFO topics:** keep order per message group, remove duplicates, and can archive and replay messages. SQS queues can subscribe to them; most other destinations support only standard topics.
- **Limits:** a standard topic allows up to 12,500,000 subscriptions and 200 filter policies.

## Not to be confused with

- **SQS:** stores a job until one worker pulls it and deletes it.
- **SNS:** pushes a copy of each message to every subscription and keeps nothing on a standard topic.

Rule: SNS tells everyone now; SQS holds work for one worker. Used together, SNS to one queue per service is the fan-out pattern. [EventBridge](card:eventbridge), next, also pushes to many targets but routes by event content.

## Interview Qs

### SQS or SNS: when do you use each?

SQS when a job must be done once, by any worker, at the worker's pace: it is pull-based and keeps the message until deleted. SNS when many systems must react to the same event: it pushes a copy to each subscriber. Often you use both, with SNS fanning out to one SQS queue per consumer.

### Why put an SQS queue behind SNS instead of subscribing a service's HTTPS endpoint?

The queue holds messages while the service is down or slow, so nothing depends on SNS retries. Each service reads at its own pace, scales on its own, and gets the queue's visibility timeout, retries and dead-letter queue.

### How does a subscriber get only some messages?

Give its subscription a filter policy: a small JSON object of allowed values, matched against message attributes by default or against the body. SNS sends the message only if every condition matches. Without a policy, the subscriber receives everything.
