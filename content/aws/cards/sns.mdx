## Why it exists

Receipts, the ledger and customer alerts all need to know a ₹500 payment succeeded. Without SNS the payment API would call each one and fail when any one is down.

## How it works

<Mermaid
  alt="The payment API publishes PaymentSucceeded once to an SNS topic. The topic pushes one copy to the receipts SQS queue, read by the receipt worker; one copy to the ledger SQS queue, read by the ledger service; and one copy to a notification Lambda function."
  chart={`flowchart LR
  API[Payment API] --> T((PaymentSucceeded topic))
  T --> Q1[[Receipts queue]] --> W[Receipt worker]
  T --> Q2[[Ledger queue]] --> L[Ledger service]
  T --> F[Notify Lambda]`}
/>

- Each queue keeps its own copy, so a slow ledger never delays receipts.
- A new consumer is one new subscription; the payment API does not change.

## Defaults

| What | Default | Where |

| Max message size | 256 KiB; up to 1 MiB with the topic's MaximumMessageSize | SNS quotas, 20-10-2026 |
| Retries to SQS or Lambda | Up to 100,015 times over 23 days | SNS DLQ docs, 20-10-2026 |

## Interview Qs

### SQS or SNS: when do you use each?

SQS when workers must each take a job and finish it at their own pace ([pull](card:sqs)). SNS when many systems must react to one event (push, fan-out). Often both: SNS fans out to SQS queues.

### Why put SQS queues behind SNS instead of subscribing services directly?

The queue holds messages while a service is down or slow, adds retries and a DLQ, and lets each service scale on its own.
