## Why it exists

Some apps need a whole server: their own OS, long-running processes and root access. EC2 gives one in minutes, no hardware to buy.

## How it works

| First letter of the type | Optimised for | Example |
|---|---|---|
| M, T | General purpose | A Spring Boot API |
| C | Compute | CPU-heavy batch jobs |
| R, X | Memory | Large in-memory data |
| I, D | Storage | Fast local disks |
| P, G | Accelerated (GPU) | Graphics, machine learning |

- The root disk is usually an [EBS volume](card:ebs-and-efs), so it survives stop and start.
- The app gets AWS credentials from an instance profile role, never stored keys: [temporary credentials](card:sts-and-temporary-credentials).
- Paying for it: [pricing models](card:aws-pricing-models).

## Example

```bash
#!/bin/bash
# EC2 user data on Amazon Linux 2023: runs once, as root, at first boot
yum install -y java-25-amazon-corretto-headless
aws s3 cp s3://payments-artifacts/payment-service.jar /opt/app.jar
nohup java -jar /opt/app.jar --server.port=8080 > /var/log/payments.log 2>&1 &
```

## Interview Qs

### What is the difference between stopping and terminating an instance?

Stop: you can restart it; EBS volumes stay and you pay for them and Elastic IPs, not the instance. Terminate deletes the instance for good; its root EBS volume is deleted too by default.

### How does code on EC2 read its instance ID or role credentials?

From the instance metadata service at 169.254.169.254. With IMDSv2 the code first gets a session token with a PUT request, then sends it with every GET; this adds defence against SSRF.
