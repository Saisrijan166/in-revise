## What it is

Amazon Aurora is a relational database engine built by AWS and run through RDS. It is compatible with MySQL and with PostgreSQL, so your existing SQL, drivers and tools keep working. What makes it different is storage: instead of each instance holding its own disk, an Aurora cluster has one cluster volume, a distributed storage layer that every instance in the cluster reads and writes. That volume keeps six copies of the data spread across three Availability Zones.

## Why it exists

A classic [RDS](card:rds) read replica keeps its own full copy of the data and replays every change onto it. Under heavy writes the replica falls behind, and a failover is slow because the new primary must catch up and warm its disk. Aurora splits the database into compute instances on top of one shared, self-growing storage layer. Because every instance reads the same volume, replicas barely lag and one can take over in seconds.

## How it works

<Compare id="rds-vs-aurora" />

1. You create a cluster with a writer instance. Writes go to it and are stored six times across three AZs in the cluster volume.
2. You add up to 15 Aurora Replicas. Each one reads the same shared volume, so it sees new data almost at once without copying it.
3. The app sends writes to the cluster endpoint, which always points at the current writer, and reads to the reader endpoint, which spreads them across the replicas.
4. If the writer fails and the cluster has replicas, Aurora promotes one, usually in under 60 seconds and often under 30. The cluster endpoint now points at it.
5. If the cluster has no replicas, Aurora rebuilds the primary instead, which can take several minutes.

So the key is: shared storage makes replicas cheap, nearly current, and quick to promote.

## Example

The payment service uses two URLs: the cluster endpoint for writes and the reader endpoint for read-only queries.

```properties
# Writes: the cluster endpoint always follows the current writer, even after a failover
payments.writer.url=jdbc:postgresql://payments.cluster-abc123example.ap-south-1.rds.amazonaws.com:5432/payments
# Reads: the reader endpoint balances connections across the Aurora Replicas
payments.reader.url=jdbc:postgresql://payments.cluster-ro-abc123example.ap-south-1.rds.amazonaws.com:5432/payments
```

What to notice:

- The two host names differ only by `cluster-` and `cluster-ro-`. The `-ro-` one is read-only and spreads load across replicas.
- Sending a write to the reader endpoint fails, because a replica cannot accept writes. Keep reports and lookups there, and the ledger writes on the cluster endpoint.
- After a failover the names do not change: the cluster endpoint simply resolves to the new writer, so the app keeps working.
- A report on the reader endpoint may see data a few milliseconds old, which is fine for a summary but not for confirming a payment just written.

## Rules and defaults

- **Storage:** one cluster volume, six copies across three AZs, grows by itself up to 128 TiB (256 TiB on some engine versions); you never provision its size.
- **Replicas:** up to 15 Aurora Replicas per cluster, each promotable; you can set a promotion priority (0 highest).
- **Serverless:** Aurora Serverless v2 scales capacity in ACUs (about 2 GiB of memory each) as load changes, and recent engine versions can scale down to 0.
- **Global Database:** adds read-only copies in other Regions with typical lag under a second, for low-latency global reads and Region-level disaster recovery.
- **Failover needs a replica:** keep at least one replica in another AZ, or a failure means a slow rebuild of the primary.

## Not to be confused with

RDS (the non-Aurora engines) gives each instance its own storage and replicas that each keep a separate copy. Aurora gives all instances one shared volume that replicas read directly. Rule: RDS replica = its own copy that can lag; Aurora replica = reads the shared volume, so it barely lags.

## Interview Qs

### How is Aurora different from RDS PostgreSQL?

Same SQL and drivers, different storage. Aurora keeps six copies of the data across three AZs in one shared volume that grows by itself. Replicas read that volume instead of their own copy, so they lag milliseconds, not seconds, and one is promoted faster on failover. RDS PostgreSQL gives each instance its own disk and copy.

### Why keep at least one Aurora Replica?

With a replica, failover promotes it in seconds. With no replica, Aurora must recreate the primary instance, which can take minutes of downtime. A replica in another AZ also keeps reads working if one AZ fails.

### When would you pick Aurora Serverless?

When load is spiky or hard to predict, or for dev and test databases that sit idle. Capacity follows demand in small steps and recent versions scale to zero, so you do not size an instance for the peak. For steady, predictable load a provisioned instance can be cheaper.
