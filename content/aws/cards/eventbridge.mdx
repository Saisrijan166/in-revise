## Why it exists

The fraud check wants only UPI payments; the ledger wants all of them. Hard-coding who gets what in the payment API couples every team to it.

## How it works

<Mermaid
  alt="The payment service puts a PaymentSucceeded event on a Custom Event Bus - Classic. Rule 1 matches every PaymentSucceeded event and sends it to the ledger SQS queue. Rule 2 matches only UPI payments and sends them to a fraud-check Lambda function. Events that match no rule go nowhere."
  chart={`flowchart LR
  P[Payment service] --> B{{payments bus}}
  B -- "Rule 1: all PaymentSucceeded" --> Q[[Ledger queue]]
  B -- "Rule 2: method = UPI" --> F[Fraud-check Lambda]`}
/>

- An event can match many rules; if it matches none, nothing happens.
- Values in a pattern's array mean "any of these".

## Example

```json
{
  "source": ["com.shop.payments"],
  "detail-type": ["PaymentSucceeded"],
  "detail": { "method": ["UPI"] }
}
```

Rule 2's pattern: only UPI payments from the payment service match.

## Interview Qs

### SNS or EventBridge for PaymentSucceeded?

EventBridge when consumers want different events by content, or you need AWS or SaaS events and replay. [SNS](card:sns) for plain fan-out of every message to many subscribers.

### How do you run a reconciliation job every night at 2 am?

Use EventBridge Scheduler with a cron expression (it also does one-time schedules). AWS calls scheduled rules legacy and recommends Scheduler.
