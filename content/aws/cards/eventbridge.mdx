## What it is

Amazon EventBridge is a serverless event bus. An event is a small JSON message that says something happened, such as a payment succeeding. Producers put events on a bus, and EventBridge delivers each event to the consumers whose filter matches it. Unlike [SNS](card:sns), which copies every message to every subscription, EventBridge decides where each event goes by looking inside its JSON. Every account also has a default bus that AWS services use for their own events, such as an EC2 instance changing state.

## Why it exists

Different teams want different events. The fraud check wants only UPI payments; the ledger wants all of them; an analytics team wants payments over ₹10,000. If the payment API called each consumer, or even published to fixed SNS topics, it would carry the knowledge of who wants what, and every new rule would change the API. EventBridge moves that choice to the consumer: each one writes a filter, and the producer just publishes events.

## How it works

The example uses the rules model of the Custom Event Bus - Classic, which most interviews still ask about:

  P[Payment service] -- "PutEvents" --> B{{payments bus}}

1. The payment service calls PutEvents with an event that has a source, a detail-type and a detail object holding the payment.
2. The bus checks the event against every rule's event pattern. A pattern lists only the fields that must match; EventBridge ignores the rest.
3. Each rule whose pattern matches sends the event to its targets, such as a queue or a Lambda function. One event can match several rules.
4. An event that matches no rule is dropped; nothing happens and no error is raised.
5. If a target delivery fails, EventBridge retries for up to 24 hours. Events that still fail are dropped unless the target has a dead-letter queue.

So EventBridge routes by what is inside the event, not by a fixed subscriber list.

## Example

Rule 2's event pattern matches only UPI payments from the payment service:

```json
{
  "source": ["com.shop.payments"],
  "detail-type": ["PaymentSucceeded"],
  "detail": { "method": ["UPI"] }
}
```

What to notice:

- Each value is a JSON array. A match needs any one value in the array, so `"method": ["UPI", "WALLET"]` would match either.
- All three fields must match for the pattern to match, so this rule catches only UPI payments from this one source.
- Any field not in the pattern is ignored, so the amount and payment ID do not affect matching.
- String matching is exact and case-sensitive: `"UPI"` does not match `"upi"`.

## Rules and defaults

- **Default bus:** every account has one; AWS services send their events to it. Create a Custom Event Bus for your application's own events.
- **Custom Event Bus - Classic:** the rules model. A rule has one event pattern and up to 5 targets; an event can match many rules. It keeps no events unless you add an archive.
- **Custom Event Bus (launched in 2026):** AWS's choice for new applications. It retains every event for 1 to 365 days, so a subscriber can replay or resume. Each subscriber has one filter and one target, and FIFO delivery is available per event group.
- **Retries:** to a Classic target, up to 24 hours and 185 attempts, then dropped unless a dead-letter queue is set. A new-bus subscriber retries 5 times within 300 seconds by default.
- **PutEvents:** up to 10 events per call, total under 1 MiB. Check FailedEntryCount in the response and resend the failed entries.
- **Scheduling:** to run a job on a cron or rate schedule, use EventBridge Scheduler; AWS calls the old scheduled rules legacy.

## Not to be confused with

- **SNS:** pushes a copy of every message to each subscription; the only filtering is a simple filter policy.
- **EventBridge:** a router that matches each event's full JSON against filters, ingests AWS and SaaS events, and can retain and replay.

Rule: SNS for plain fan-out of every message; EventBridge when consumers need different events by content, AWS or SaaS events, or replay.

## Interview Qs

### SNS or EventBridge for PaymentSucceeded?

SNS for plain fan-out: every subscriber gets every message, at very high throughput and low latency. EventBridge when consumers want different events chosen by content, when you must react to AWS service or SaaS events, or when you need to retain and replay events. EventBridge adds a little latency for that routing.

### An event matches no rule. What happens?

Nothing. EventBridge silently drops it, with no error to the producer. So a consumer that gets no events usually has a filter that matches nothing, often because of an exact-match or case mismatch. Test a pattern against a real event before relying on it.

### How do you run a reconciliation job every night at 2 am?

Use EventBridge Scheduler with a cron expression; it can also run one-time schedules and rate schedules. AWS now calls the older scheduled rules legacy and recommends Scheduler, which supports many targets and built-in retries.
