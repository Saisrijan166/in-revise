## What it is

Policy evaluation is the fixed order of checks AWS runs to turn every policy that applies to one request into a single answer: Allow or Deny. One request can meet several policies: the caller's own policy (an identity-based policy, as in [IAM basics](card:iam-basics)), a policy on the resource itself, such as an [S3](card:s3) bucket policy (a resource-based policy), and limits set for the whole organisation. Evaluation decides who wins when they disagree.

## Why it exists

The payment service's role may allow reading receipts, while the bucket policy refuses plain-HTTP requests and the company blocks some services for the whole account. Without one fixed rule you could not predict the result, or explain an AccessDenied error. AWS applies the same order to every request, so you can work out the answer from the policies alone, and a single Deny becomes a lock that no Allow can open.

## How it works

1. AWS authenticates the request: it checks the signature to learn the principal, the user or role session making the call.
2. It gathers every policy that applies and looks for a matching `Deny` statement. One explicit deny ends evaluation: the request is denied.
3. If the account belongs to AWS Organizations, its service control policies (SCPs, limits on the account's principals) and resource control policies (RCPs, limits on its resources) must allow the action.
4. A policy must then grant it: an identity-based policy on the caller, or a resource-based policy that names the caller. If none does, the answer is implicit deny.
5. Last, if the role or user has a permissions boundary, or the session was started with a session policy, those must allow the action too.

So the key is: Deny beats Allow, and "not mentioned" means denied.

## Example

The payment role's policy allows `s3:GetObject` on the receipts bucket. The bucket also carries this statement, which AWS documents as a way to allow only HTTPS:

```json
{
  "Sid": "RestrictToTLSRequestsOnly",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::payments-receipts", "arn:aws:s3:::payments-receipts/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

What to notice:

- Over HTTPS, `aws:SecureTransport` is true, so the condition does not match, the Deny does not apply, and the role's Allow lets the read through.
- Over plain HTTP the Deny matches and the request is denied, even though the role allows it, because step 2 runs before any Allow is looked at.
- `"Principal": "*"` means the Deny applies to everyone, admins included.
- Delete the `Condition` and the bucket denies every request from everyone; fixing a bucket policy that denies all principals is one of the tasks that needs the root user.

## Rules and defaults

- **Default:** every request starts as implicit deny. Only the root user is not limited by it.
- **Explicit deny wins:** a matching Deny in any policy type overrides any number of Allows.
- **Guardrails grant nothing:** SCPs, RCPs, permissions boundaries and session policies only cap access; the request still needs an identity-based or resource-based Allow.
- **Same account:** for most services an Allow in either the identity-based policy or the resource-based policy is enough. Role trust policies and KMS key policies are exceptions: they must allow the principal themselves.
- **Cross-account:** the caller's account must allow the call in an identity-based policy, and the resource's account must allow it in a resource-based policy. Both sides are needed.

## Not to be confused with

An identity-based policy sits on a user, group or role and says what that identity may do; it has no `Principal` element, because the identity it is attached to is the principal. A resource-based policy sits on a resource, such as a bucket or queue, and names which principals may use it. Rule: identity policy = what I may do; resource policy = who may use me.

## Interview Qs

### What is the difference between authentication and authorisation in AWS?

Authentication proves who the principal is, from the signed credentials on the request. Authorisation then evaluates the policies to decide whether that principal may perform this action on this resource. A request with a valid signature can still be denied by authorisation.

### A role's policy allows s3:GetObject, but the call is denied. What do you check?

Look for an explicit deny in the bucket policy, an SCP or RCP, a permissions boundary or a session policy. Cross-account, check that the bucket policy also allows the role. For objects encrypted with SSE-KMS, the role also needs decrypt permission on the [KMS key](card:kms-and-encryption). IAM Access Analyzer and CloudTrail help find the policy that blocked it.

### Why does an SCP not grant any permission?

An SCP only sets the maximum that principals in member accounts can do. It is a filter, not a grant. Access still needs an identity-based or resource-based policy that allows the action, inside that maximum.
