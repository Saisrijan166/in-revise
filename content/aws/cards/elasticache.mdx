## Why it exists

The payment service reads the same merchant config on every request. Reading it from memory is faster and takes that load off RDS.

## How it works

<Compare id="redis-vs-memcached" />

- AWS calls cache-aside "lazy loading". In Spring, `@Cacheable` does the read side: it runs the method only on a miss.
- Serverless caches use a VPC endpoint, or a public one (Valkey 9.0+, IAM auth and TLS 1.3 required).

## Interview Qs

### Valkey/Redis OSS or Memcached?

Valkey or Redis OSS when you need rich data types, replicas with automatic failover, backups or pub/sub. Memcached for the simplest multithreaded key-value cache that you can afford to lose.

### How do you keep cached merchant config from going stale?

Give every key a TTL, and evict the key when the config changes in the database (`@CacheEvict` in Spring). The next read misses and loads the fresh value.

### Serverless or node-based?

Serverless when load is unknown or spiky: no capacity planning, and data is stored across three AZs. Node-based when you need control over node type, shard count and placement.
