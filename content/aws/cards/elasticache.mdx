## What it is

Amazon ElastiCache is a managed in-memory data store: it runs Valkey, Redis OSS or Memcached for you. These keep data in RAM, so reads return in well under a millisecond, far faster than a disk-backed database. You put a cache in front of a database and keep the data that is read again and again, such as a merchant's fee config, so most reads are served from memory. Valkey is an open-source fork of Redis; Redis OSS is Redis itself.

## Why it exists

The payment service reads the same merchant config on nearly every request. Each read hits [RDS](card:rds), using CPU and connections that the real work needs. A database is tuned for correctness and durability, not for serving the same small value a million times. ElastiCache holds that value in RAM beside the app: after the first read, the rest come from memory, and RDS is left for writes and queries that genuinely need it.

## How it works

<Compare id="redis-vs-memcached" />

The common pattern is cache-aside (AWS calls it lazy loading):

1. The service needs the config for merchant `m-42` and asks the cache for key `merchant:m-42`.
2. On a hit, the cache returns the value from RAM and the database is untouched.
3. On a miss, the service reads the config from RDS, stores it in the cache with a TTL, and returns it. Later reads now hit.
4. When the config changes in RDS, the service deletes (evicts) that key, so the next read misses and reloads the fresh value.
5. The TTL is a safety net: even with no eviction, the key expires after its time and is reloaded.

So the key is: the cache speeds up reads, the database stays correct, and a TTL plus eviction keep the two from drifting apart.

## Example

In Spring, `@Cacheable` does the read side of cache-aside and `@CacheEvict` removes a stale key:

```java
@Cacheable(cacheNames = "merchantConfig", key = "#merchantId")   // hit: method is skipped
public MerchantConfig find(String merchantId) {
    return repository.findById(merchantId).orElseThrow();       // runs only on a miss
}

@CacheEvict(cacheNames = "merchantConfig", key = "#merchantId")  // delete the cached copy
public void changeFee(String merchantId, BigDecimal feePercent) {
    repository.updateFee(merchantId, feePercent);
}
```

What to notice:

- With `@Cacheable`, Spring checks the cache first and runs the method body only on a miss, then stores the result. The database read happens once per key until it expires.
- `@CacheEvict` deletes the key after the fee changes, so the next `find` misses and reloads. Remove this line and callers keep seeing the old fee until the TTL ends.
- The cache name maps to an ElastiCache instance through Spring's Redis configuration; the TTL is set there, not in these annotations.
- If ElastiCache is down, the method still runs against RDS, so the app keeps working, only slower.

## Rules and defaults

- **Engines:** Valkey, Redis OSS and Memcached (at the time of writing). Valkey and Redis OSS offer rich types, replicas and backups; Memcached is a plain multithreaded key-value cache.
- **Serverless:** no nodes to size; it scales itself, stores data across three AZs, and always uses encryption in transit (TLS).
- **Node-based:** you choose the node type, the number of nodes and their AZ placement, and you can turn on cluster mode to shard data.
- **Public endpoint:** available on serverless Valkey 9.0+; it requires IAM authentication and TLS 1.3. Otherwise the cache lives in your VPC and its security group must allow the client on port 6379.
- **Durability:** plain caches are not durable. For zero-loss in-memory data use MemoryDB, or node-based Valkey 9.0+ with durability enabled.

## Not to be confused with

Valkey and Redis OSS are the same kind of engine: rich data types, replicas with failover, backups and pub/sub. Memcached is a simpler, multithreaded key-value cache with none of those. Rule: Valkey/Redis OSS = features and high availability; Memcached = the plainest cache you can afford to lose.

## Interview Qs

### Valkey or Redis OSS versus Memcached?

Choose Valkey or Redis OSS when you need rich data types, replicas with automatic failover, backups or pub/sub. Choose Memcached for the simplest multithreaded key-value cache where losing the data is fine. Most new caches use Valkey, the open-source fork AWS now leads with.

### How do you keep cached merchant config from going stale?

Give every key a TTL so it refreshes on its own, and evict the key the moment the config changes in the database (`@CacheEvict` in Spring). The next read misses and loads the current value. TTL alone bounds staleness; eviction removes it at once.

### Serverless or node-based ElastiCache?

Serverless when load is unknown or spiky: no capacity planning, it scales itself and stores data across three AZs. Node-based when you want control over node type, shard count and placement, or need features such as durability on Valkey 9.0+.
