## What it is

AWS does not have one database. It offers purpose-built stores, each strong at one kind of access: relational databases for SQL and joins, DynamoDB for key lookups, ElastiCache for in-memory reads, Redshift for analytics, and more. Choosing a database on AWS means reading how each piece of data is written and read, then picking the store that fits, often using several in one system. Interviewers ask this to see whether you match data to a store on purpose.

## Why it exists

No single database is best at every access pattern. A relational database gives joins, constraints and transactions but grows costly when one key is read at massive scale. A key-value store is fast and huge but cannot join or report easily. Forcing everything into one leads to slow reports on a key-value store, or a relational server strained by one hot lookup. Picking per pattern keeps each part simple and fast.

## How it works

Match the access pattern to the store:

| Access pattern | Pick |
|---|---|
| Joins, constraints, multi-row SQL transactions | [RDS](card:rds) or [Aurora](card:aurora) |
| Key lookups at huge or spiky volume | [DynamoDB](card:dynamodb) |
| The same hot data read again and again | [ElastiCache](card:elasticache) |
| JSON documents queried on many fields | [DocumentDB](card:amazon-documentdb-node) |
| Highly connected data: fraud rings, recommendations | [Neptune](card:amazon-neptune-node) |
| Existing Apache Cassandra workloads | [Keyspaces](card:amazon-keyspaces-node) |
| Full-text search, log analytics | [OpenSearch Service](card:amazon-opensearch-node) |
| Large reporting queries over history (OLAP) | [Redshift](card:amazon-redshift-node) |

So the key is: start from the query, not the product, and accept that one system may hold data in two or three of these.

What to notice:

- RDS holds the payments and refunds, because they need transactions, joins and month-end reports. It is the source of truth.
- ElastiCache holds merchant config, read on every request, so RDS is not asked for the same value repeatedly.
- [S3](card:s3) holds the receipt PDFs, and only their keys live in the payment row, keeping the database small.
- Replace RDS with DynamoDB here and the refund-and-report logic becomes much harder, which is why the ledger stays relational.

## Rules and defaults

- **Default to relational:** when in doubt and the data is modest in scale with rich queries, RDS or Aurora is the safe choice.
- **DynamoDB when it is key access at scale:** such as idempotency keys or status-by-id at very high volume.
- **Cache, do not replace:** ElastiCache sits in front of a database; MemoryDB is the option when the in-memory data must be durable.
- **Analytics is separate:** Redshift answers big reporting queries; do not point live payment traffic at it.
- **Mix freely:** one service commonly uses two or three stores, each for the job it fits.

## Interview Qs

### Where does each piece of the payment system live?

Payments and refunds in RDS or Aurora, because they need transactions and reports. Merchant config cached in ElastiCache. Receipt PDFs in S3, with only their keys in the database. If idempotency checks run at very high volume, those keys fit DynamoDB. Each store matches how that data is read.

### When would you add DynamoDB next to RDS, rather than instead of it?

For one high-volume, key-based job, such as idempotency keys or payment-status-by-id, where DynamoDB's scale and steady latency shine. The ledger, refunds and reports stay in RDS, because they need joins and transactions. The two coexist, each doing what it is best at.

### Why not run reports on DynamoDB?

A report scans and aggregates across many items on fields that are not the key, which DynamoDB does with full-table Scans or many indexes, slowly and expensively. Redshift or a relational database answers such OLAP queries directly. DynamoDB is built for fast, targeted key reads instead.
