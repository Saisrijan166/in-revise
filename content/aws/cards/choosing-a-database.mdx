## Why it exists

No single database is best at every access pattern. AWS offers purpose-built stores, and interviewers ask you to match each piece of data to one.

## How it works

| Access pattern | Pick |
|---|---|
| Joins, constraints, SQL transactions | [RDS](card:rds) or [Aurora](card:aurora) |
| Key lookups with huge or spiky traffic | [DynamoDB](card:dynamodb) |
| Hot data read again and again | [ElastiCache](card:elasticache) |
| JSON documents queried on many fields | [DocumentDB](card:amazon-documentdb-node) |
| Highly connected data: fraud rings, recommendations | [Neptune](card:amazon-neptune-node) |
| Existing Cassandra workloads | [Keyspaces](card:amazon-keyspaces-node) |
| Time series such as IoT readings | [Timestream](card:amazon-timestream-node) |
| Full-text search, log analytics | [OpenSearch Service](card:amazon-opensearch-node) |
| Reports over large history (OLAP) | [Redshift](card:amazon-redshift-node) |

## Interview Qs

### Where does each piece of the payment system live?

Payments and refunds in RDS PostgreSQL, because they need transactions and reports. Merchant config cached in ElastiCache. Receipt PDFs in [S3](card:s3), with only their keys in the database.

### When would you add DynamoDB next to RDS?

For one high-volume, key-based job, such as idempotency keys or payment status by id. Keep the ledger and reports in RDS.
