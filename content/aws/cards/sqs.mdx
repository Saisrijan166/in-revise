## What it is

Amazon SQS (Simple Queue Service) is a managed message queue. A queue is a waiting line for messages: a producer, here the payment API, sends a message such as "build the receipt for pay_123", and a consumer, the receipt worker, takes it later. AWS runs the queue for you; a standard queue keeps copies of each message in several [Availability Zones](card:regions-and-azs). Your code only sends, receives and deletes.

## Why it exists

Building a receipt PDF and saving it to S3 takes seconds. If the payment API did it inside the request, every customer would wait, a burst of payments would overload the API, and a crash halfway would lose the job. With a queue, the API sends a small message and answers at once. Workers take jobs at their own pace, and a job survives a worker crash because SQS keeps it until a worker deletes it.

## How it works

1. The payment API calls SendMessage with the payment ID, and SQS stores the message.
2. A worker calls ReceiveMessage. With long polling, the call waits up to 20 seconds for a message instead of returning empty.
3. SQS hands over the message with a receipt handle and starts the visibility timeout. The message stays in the queue, but no other worker can see it.
4. The worker builds the PDF, saves it to S3, then calls DeleteMessage with the receipt handle. Only now is the message gone.
5. If the worker crashes or throws, it never deletes. When the visibility timeout ends, the message is visible again and another worker retries it.
6. When a message reaches the redrive policy's maxReceiveCount, SQS moves it to the dead-letter queue instead of retrying it forever.

So a message leaves the queue only when a worker deletes it.

## Example

The receipt queue is created with settings that fit the job, using the Java SDK ([Calling AWS from Java](card:aws-sdk-for-java) covers it later; the send, receive and delete calls are in [AWS Code Templates](card:aws-code-templates)):

```java
String dlqArn = "arn:aws:sqs:ap-south-1:111122223333:receipt-jobs-dlq";
sqs.createQueue(b -> b.queueName("receipt-jobs").attributes(Map.of(
    QueueAttributeName.VISIBILITY_TIMEOUT, "180",                // 3 min; a receipt takes ~90 s
    QueueAttributeName.RECEIVE_MESSAGE_WAIT_TIME_SECONDS, "20",  // long polling
    QueueAttributeName.REDRIVE_POLICY,
        "{\"deadLetterTargetArn\":\"" + dlqArn + "\",\"maxReceiveCount\":\"5\"}")));
```

What to notice:

- A visibility timeout of 180 seconds is longer than one receipt takes, so a worker deletes the message before anyone else can see it. With the default 30 seconds, slow receipts would be built twice.
- A queue-level wait time of 20 seconds turns on long polling for every receive that does not set its own. With the default of 0, idle workers pay for many empty responses.
- The redrive policy names a dead-letter queue that you create first. After 5 receives without a delete, a "poison" message that always fails moves there.

## Rules and defaults

- **Visibility timeout:** 30 seconds by default, 0 seconds to 12 hours (SQS quotas, at the time of writing). The 12 hours count from the first receive; extending with ChangeMessageVisibility does not reset them.
- **Retention:** a message nobody deletes is kept 4 days by default (1 minute to 14 days), then SQS deletes it.
- **Message size:** up to 1 MiB, raised from 256 KiB on 04-08-2025. For more, put the payload in S3 and send its key; the SQS Extended Client Library for Java does this, up to 2 GB. One call can send, receive or delete up to 10 messages.
- **Short polling is the default:** a receive with WaitTimeSeconds 0 checks only some servers, so it can return empty while messages exist.
- **Dead-letter queue:** same account, Region and type as the source queue (FIFO for FIFO). On a standard queue the message keeps its first enqueue time, so give the dead-letter queue a longer retention.
- **Lambda as the worker:** an [event source mapping](card:lambda) polls the queue and calls a function for you.

## Not to be confused with

- **Standard queue:** the default type. Throughput is nearly unlimited, but order is best effort and a message can arrive twice.
- **FIFO queue:** its name ends in .fifo. It keeps order within each message group and drops duplicates sent within 5 minutes, at lower throughput.

Rule: standard queue plus an idempotent worker by default; FIFO only when order per key matters.

## Common mistakes

- **"Delete first, then work, so it never runs twice."** A crash after the delete loses the job. Delete only after the work succeeds.
- **"Within the visibility timeout, nobody else can get the message."** SQS does not promise that; a standard queue delivers at least once, so make the worker idempotent.

## Interview Qs

### A worker crashes while building a receipt. Is the job lost?

No. The worker never deleted the message, so it becomes visible again when the visibility timeout ends and another worker retries it. So the timeout must exceed the normal processing time, and a dead-letter queue catches messages that keep failing.

### How do you handle duplicate messages?

Make the consumer idempotent: processing a message twice leaves the same result as once. For receipts, store the payment ID with a unique constraint and skip IDs already done. FIFO deduplication helps only when you also need order, and it limits throughput.

### Short polling or long polling?

Short polling, the default, answers at once and checks only some servers, so it often returns empty. Long polling waits up to 20 seconds, checks all servers and returns as soon as a message arrives: fewer empty, billed calls. Use long polling almost always.
