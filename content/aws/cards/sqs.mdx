## Why it exists

Making a receipt PDF takes seconds. If the payment API did it inline, every ₹500 payment would wait, and a worker crash would lose the job.

## How it works

<Steps label="Life of one SQS message">
  <Step title="Send">The payment API sends a job with the payment ID.</Step>
  <Step title="Receive">A worker gets it; other workers no longer see it.</Step>
  <Step title="Delete">Done in time: the worker deletes it.</Step>
  <Step title="Reappear">Not deleted within the visibility timeout: visible again.</Step>
  <Step title="Dead-letter">Received maxReceiveCount times: moved to the DLQ.</Step>
</Steps>

## Interview Qs

### A worker crashes while making a receipt. Is the job lost?

No. It was never deleted, so it reappears after the visibility timeout and another worker retries. Set the timeout above the normal processing time.

### How do you handle duplicate messages?

Make the consumer idempotent: record the payment ID with a unique constraint and skip IDs already done.

### The payload is bigger than 1 MiB. What now?

Store it in S3 and send its key; the SQS Extended Client Library for Java does this, up to 2 GB.
