## What it is

AWS CloudTrail is the audit log of your AWS account. Almost everything in AWS happens through an API call, whether you click in the console, run the CLI, or a service acts for you. CloudTrail records each of those calls as an event. An event names the caller (`userIdentity`), the action (`eventName`), the time, the Region and the source IP address. So CloudTrail answers questions of the form "who did this, and when?".

## Why it exists

When a security group suddenly opens to the whole internet, or a bucket policy disappears, metrics and logs cannot tell you who changed it or when. You need a trustworthy record of the control actions themselves. CloudTrail keeps that record automatically for every account, so during an incident or an audit you can trace a change back to a user, a role, a time and an IP, instead of guessing.

## How it works

<Compare id="cloudwatch-vs-cloudtrail" />

1. Any API call in the account, from the console, CLI, an SDK or another AWS service, is captured by CloudTrail as an event.
2. Management events (calls that change setup, like `AttachRolePolicy` or `DeleteBucketPolicy`) are recorded automatically; they land in event history within about 5 minutes.
3. Event history lets you search the last 90 days, in one Region, filtering on a single attribute such as `EventName`.
4. For a longer record you create a [trail](card:ct-trail), which delivers every event to an S3 bucket you own; a multi-Region trail captures all Regions.
5. [Data events](card:ct-data-events), such as individual S3 object reads, are high volume, so they are off until you turn them on for the specific buckets you want audited.

So the key is: the control actions are audited for free for 90 days; a trail is what you add for retention beyond that and for object-level data events.

## Example

To find who deleted a bucket policy, search event history for that one event name.

```bash
# Who deleted the receipts bucket policy, and from where?
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=DeleteBucketPolicy \
  --start-time 2026-10-22T00:00:00Z --end-time 2026-10-23T00:00:00Z
```

What to notice:

- `lookup-events` reads the free 90-day event history, so this works with no trail set up.
- Event history lets you filter on only one attribute at a time; here it is `EventName`. Each returned event carries `userIdentity`, `eventTime` and `sourceIPAddress`, which answer who, when and from where.
- To search across many attributes or Regions at once, or to query years of history, you would use a CloudTrail Lake event data store instead, not event history.

## Rules and defaults

- **Event history:** on from account creation, free, keeps 90 days of management events, scoped to one Region and one attribute filter per search (CloudTrail, at the time of writing).
- **Delivery time:** CloudTrail delivers events on average within about 5 minutes of the call; this is not guaranteed in real time.
- **Trails:** all trails created in the console are multi-Region by default; one copy of ongoing management events to S3 is free (you still pay S3 storage); data events and Insights events cost extra.
- **Data events:** off by default; turn them on per resource (for example a specific S3 bucket or Lambda function).
- **Not for configuration state:** CloudTrail records the calls, not what a resource looks like over time; that is [AWS Config](card:aws-config-recorder).

## Not to be confused with

CloudTrail records the API calls that were made. [AWS Config](card:aws-config-recorder) records how each resource's configuration looked over time and checks it against rules. Rule: CloudTrail = who called what; Config = what the resource's settings were, and whether they are compliant.

## Common mistakes

- **"CloudTrail logs every read of my S3 objects."** No. Object-level reads and writes are data events, which are off by default. Turn them on for the buckets you need to audit, and expect the cost that comes with the volume.
- **Relying on event history for long-term audit.** It only keeps 90 days. For compliance you need a trail delivering to S3 (and log file validation to prove nothing was altered).

## Interview Qs

### Someone deleted a bucket policy in production. How do you find out who?

Search CloudTrail event history (or your trail in S3) for the `DeleteBucketPolicy` event around that time. The event's `userIdentity` shows the user or role, `eventTime` shows when, and `sourceIPAddress` shows where from. Event history is on by default and covers the last 90 days, so no prior setup is needed.

### CloudWatch vs CloudTrail?

CloudWatch tells you how the system is behaving: metrics, logs and alarms for health and alerting. CloudTrail tells you who did what in the account: a record of every API call. They work together; you can even send trail events to CloudWatch Logs and alarm on risky calls like disabling encryption.

### Why are S3 data events off by default?

Object-level calls like `GetObject` can run millions of times, so logging them all is expensive and noisy. CloudTrail logs management events (which change setup) for free by default, and lets you enable data events only on the specific buckets where object-level audit is worth the cost.
