## What it is

A load balancer is a single network entry point that receives client requests and forwards each one to one of several backend targets. Elastic Load Balancing is the AWS service that runs it for you. It comes in three types: the Application Load Balancer (ALB) for HTTP and HTTPS, the Network Load Balancer (NLB) for raw TCP and UDP, and the Gateway Load Balancer (GWLB) for routing traffic through network appliances. It constantly checks each target's health and sends requests only to the healthy ones.

## Why it exists

Behind an [Auto Scaling group](card:auto-scaling-groups) the instances come and go: they start, stop and sometimes fail, each with a different IP. Clients cannot be asked to track that, and a single server would be one point of failure. The load balancer gives clients one stable DNS name and hides the fleet behind it. It spreads load so no instance is overwhelmed, stops sending to an instance the moment it fails a health check, and spans AZs so one AZ failing does not take the service down.

## How it works

<Compare id="alb-vs-nlb-vs-gwlb" />

A request travels through four things in order, so follow one through an ALB:

1. The client resolves the balancer's DNS name and connects to a listener, for example the HTTPS listener on port 443.
2. The listener ends TLS with its ACM certificate, then checks its rules in priority order for a match.
3. The matching rule points to a target group, for example the one for /payments.
4. The balancer picks a healthy target from that group and forwards the request; it never sends to a target that is failing its health check.
5. Meanwhile each target group keeps checking its targets, so a bad instance is dropped and a recovered one added back.

So the chain is listener, rule, target group, healthy target; an ALB needs subnets in at least two AZs.

## Example

A target group for the payment service, and the rule that finishes draining a removed instance gracefully:

```bash
aws elbv2 create-target-group --name payment-tg \
  --protocol HTTP --port 8080 --vpc-id vpc-0abc1234 \
  --health-check-path /actuator/health --matcher HttpCode=200

aws elbv2 modify-target-group-attributes --target-group-arn "$TG_ARN" \
  --attributes Key=deregistration_delay.timeout_seconds,Value=30
```

What to notice:

- The health check hits `/actuator/health` and treats HTTP 200 as healthy; a target must pass it before it ever receives traffic.
- The deregistration delay here is 30 seconds instead of the default 300: when an instance is removed, the balancer stops new requests but waits up to 30 s for in-flight ones to finish.
- If the app shuts down before that window ends, in-flight clients get 500-level errors, so the app should stop gracefully inside the delay.

## Rules and defaults

- **Subnets:** an ALB needs subnets in at least two AZs; cross-zone load balancing is always on for an ALB (a target group can turn it off).
- **Default health check (ALB target, instance/ip):** every 30 s, 5 s timeout, path `/`, success code 200, 5 passes to become healthy, 2 failures to become unhealthy.
- **Fail open:** if all targets in a group are unhealthy, the ALB routes to all of them regardless, rather than returning nothing.
- **Deregistration delay:** 300 s by default for ALB and NLB target groups; a draining target with no in-flight requests completes at once.
- **Sticky sessions:** optional; a cookie (`AWSALB` for duration-based) keeps one client on one target, and the client must accept cookies.

## Not to be confused with

An ALB works at layer 7, so it can read the HTTP request and route by path, host or header, end HTTPS, and target Lambda. An NLB works at layer 4: it forwards TCP and UDP connections very fast and can hand out a static IP per AZ, but it cannot read a URL. [API Gateway](card:api-gateway) is a different thing again, a managed API front door with auth and throttling. Rule: ALB for HTTP routing, NLB for raw speed and fixed IPs, GWLB only to insert security appliances.

## Common mistakes

- **"Sticky sessions make my app scalable."** They pin a client to one target, so a new instance gets little traffic until new sessions arrive, and losing that target loses the session. Prefer a stateless app with session state in [ElastiCache](card:elasticache); use stickiness only when the app truly keeps state in memory.

## Interview Qs

### ALB or NLB for a Spring Boot REST API?

ALB. It works at layer 7, so it can route /payments and /refunds to different target groups, end HTTPS with an ACM certificate, and health-check an HTTP path. Choose NLB for non-HTTP traffic, for extreme throughput, or when you need a fixed IP address per AZ.

### A target is stuck as unhealthy though the app runs fine. How do you debug it?

The check runs from the load balancer. Confirm the target's security group allows the balancer on the health check port, that the path exists and returns the success code, and that the app answers within the timeout. Check the target health reason code: Target.Timeout points to networking or a slow path, Target.ResponseCodeMismatch to a wrong status code.

### What happens to requests in flight when an instance is removed?

The balancer stops sending new requests and the target enters draining. It waits the deregistration delay, 300 s by default, for in-flight requests to finish before completing removal. If the app terminates its connections before the delay elapses, those clients receive 500-level errors, so shut down gracefully within the window.
