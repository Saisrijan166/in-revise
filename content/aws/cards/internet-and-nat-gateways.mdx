## What it is

An internet gateway (IGW) is a component you attach to a [VPC](card:vpc-and-subnets) to let its resources talk to the internet in both directions. A NAT gateway (Network Address Translation) is a managed service that lets resources in a private subnet start connections out to the internet, while stopping anyone outside from starting a connection in. Both are the pieces that carry traffic between your private network and the outside world, each for a different direction.

## Why it exists

A new VPC has no path to the internet at all. But a load balancer must be reachable from outside, and app servers in private subnets must still fetch OS patches and call payment partners, without being exposed. The internet gateway gives public-facing resources their two-way path. The NAT gateway gives private resources an outbound-only path, so they can reach out without ever being reachable.

## How it works

<Compare id="internet-gateway-vs-nat-gateway" />

1. You attach one internet gateway to the VPC and give the public subnet's route table a `0.0.0.0/0` route to it.
2. The ALB in the public subnet gets a public IP, so clients on the internet can reach it through the IGW.
3. For the private subnets, you create a NAT gateway in a public subnet and give each private route table a `0.0.0.0/0` route to the NAT gateway.
4. When a private task calls out, the NAT gateway swaps the task's private IP for its own Elastic IP and sends the traffic through the IGW; the reply comes back the same way.

So the IGW is the only door to the internet, and the NAT gateway is how private subnets borrow it for outbound traffic.

## Example

These two route tables put a public subnet and a private subnet on the same VPC. Only the targets differ.

```text
Public subnet route table        Private subnet-a route table
10.0.0.0/16  local               10.0.0.0/16  local
0.0.0.0/0    igw-0abc            0.0.0.0/0    nat-0aaa   (NAT gateway in public subnet a)
```

What to notice:

- The `local` route is the same in both and cannot be removed; it keeps the subnets able to reach each other inside the VPC.
- The public subnet's `0.0.0.0/0` points at the internet gateway (`igw-`), which is what makes it public.
- The private subnet's `0.0.0.0/0` points at the NAT gateway (`nat-`), so its traffic goes out but cannot be reached from outside.
- Change the private subnet's `0.0.0.0/0` target to the IGW and you have made it public, which is usually a mistake for app and database tiers.

## Rules and defaults

- **Internet gateway:** no charge for the gateway itself; you pay only for data transfer (Amazon VPC). It is horizontally scaled and highly available, so there is no AZ to choose.
- **NAT gateway connectivity type:** `public` by default, which needs a public subnet and an Elastic IP; a `private` NAT gateway has no Elastic IP and reaches other VPCs or on-premises, not the internet (Amazon VPC).
- **Bandwidth:** a NAT gateway starts at 5 Gbps and scales automatically up to 100 Gbps (Amazon VPC).
- **No security group on a NAT gateway:** you cannot attach one; control its traffic with the subnet's security groups and NACL.
- **Avoiding the NAT fee:** traffic to S3 or DynamoDB can skip the per-GB NAT charge through a [gateway endpoint](card:vpc-endpoints-privatelink).

## Interview Qs

### How do you make outbound internet access highly available for private subnets?

Create one zonal NAT gateway in each AZ and point each private subnet at the NAT gateway in its own AZ, or use a single regional NAT gateway that spans AZs automatically. A single zonal NAT gateway shared across AZs is a single point of failure.

### Can internet users reach a server through a NAT gateway?

No. A NAT gateway only allows connections that start inside the VPC; replies return, but no outsider can open a new connection. To accept inbound traffic, put a load balancer in the public subnets instead.

### Why prefer a gateway endpoint over NAT for S3 traffic?

A NAT gateway charges per GB processed, and S3 transfers can be large. A gateway endpoint sends that traffic to S3 over a private AWS path at no extra charge, cutting both the NAT data cost and the need for an internet route.
