## What it is

AWS KMS (Key Management Service) creates encryption keys, keeps them inside AWS, and controls who may use them. It protects data at rest: stored data, such as an [S3](card:s3) object, a disk or an [RDS](card:rds) database, stays unreadable without the key. A KMS key never leaves KMS unencrypted; KMS hands out data keys, small keys that do the actual encrypting. Data in transit, moving over the network, is protected separately by TLS.

## Why it exists

If someone copies a disk, a snapshot or a backup, they could read every payment record on it. Encryption fixes that, but then the key becomes the secret: kept in a config file, it leaks just like a password. KMS keeps the key in one place, a key policy decides who may decrypt, and CloudTrail logs every use. Taking the data is no longer enough; an attacker also needs permission on the key.

## How it works

1. The app or AWS service calls `GenerateDataKey` and names a KMS key.
2. KMS returns the same data key twice: once in plaintext and once encrypted under the KMS key.
3. The caller encrypts the data locally with the plaintext key, then removes that key from memory.
4. It stores the encrypted data key next to the encrypted data.
5. To read the data, the caller sends the encrypted data key to KMS `Decrypt`. KMS checks the key policy and returns the plaintext key only if this caller may decrypt.

So the key is: only the small data key travels to KMS, and the key policy is the one gate for reading the data. This pattern is called envelope encryption.

## Example

The payment service stores a receipt with SSE-KMS under its own key, so S3 runs the steps above:

```java
s3.putObject(PutObjectRequest.builder()
        .bucket("payments-receipts")
        .key("receipts/pay_123.pdf")
        .serverSideEncryption(ServerSideEncryption.AWS_KMS)
        .ssekmsKeyId("alias/receipts")        // customer managed key
        .bucketKeyEnabled(true)               // S3 Bucket Key: fewer KMS calls
        .build(),
    RequestBody.fromBytes(pdfBytes));
```

What to notice:

- `AWS_KMS` asks S3 for SSE-KMS; S3 does the envelope encryption, and the code never sees a data key.
- `alias/receipts` names a customer managed key, whose key policy you control. Leave the line out and S3 uses the AWS managed key `aws/s3`, which cannot be shared with another account.
- `bucketKeyEnabled(true)` lets S3 make data keys from a short-lived bucket-level key, which AWS says can cut KMS request costs by up to 99 per cent.
- The upload needs `kms:GenerateDataKey` on the key; a later download needs `kms:Decrypt` as well as `s3:GetObject`.

## Rules and defaults

- **Encrypt limit:** KMS `Encrypt` with a symmetric key takes at most 4,096 bytes of plaintext; anything bigger uses a data key.
- **Key policy:** every KMS key has exactly one. IAM policies can grant use of the key only if the key policy allows that; the default key policy does.
- **Rotation:** optional for customer managed keys; when on, every 365 days by default (90 to 2,560 allowed), and on demand. AWS managed keys rotate every year. KMS keeps the old key material, so old data still decrypts (AWS KMS, at the time of writing, 21-10-2026).
- **Key types:** AWS owned keys are a free default that you cannot manage; AWS managed keys (`aws/<service>`) live in your account; customer managed keys let you control the policy, rotation and deletion, for a monthly fee.
- **S3:** new objects get SSE-S3 (keys managed by S3) by default since 05-01-2023. SSE-C, where you send the key with every request, is disabled on new buckets since April 2026.
- **RDS:** encryption is chosen when the instance is created and cannot be turned off later; to encrypt an existing database, restore from an encrypted snapshot copy or use a blue/green deployment.
- **Regional:** a KMS key and its key policy belong to one Region; S3 needs the key in the bucket's Region.

## Interview Qs

### What is envelope encryption, and why use it?

A data key encrypts the data, and a KMS key encrypts the data key. Only the small data key goes to KMS, so large files are encrypted quickly and locally, and decrypt rights stay in one place, the key policy. KMS `Encrypt` alone accepts only 4 KB anyway.

### Does rotating a KMS key re-encrypt existing data?

No. Rotation creates new key material for new encryptions. KMS keeps the old material and picks the right one to decrypt, so old data works without code changes. Data keys are not rotated either, so rotation does not help if a data key itself leaks.

### What is the difference between SSE-S3 and SSE-KMS?

With SSE-S3, S3 owns and manages the keys; it is the default and needs no KMS calls. With SSE-KMS, a KMS key you choose wraps the data keys: its key policy controls who can decrypt, CloudTrail logs each use, and KMS requests add cost, which S3 Bucket Keys reduce.
