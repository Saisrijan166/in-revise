## Why it exists

Stolen disks, snapshots or backups must be unreadable, and decrypt rights belong in one controlled place, not in config files.

## How it works

<Steps label="Envelope encryption">
  <Step title="Ask">The app or service calls GenerateDataKey with a KMS key.</Step>
  <Step title="Receive">KMS returns the data key in plaintext and encrypted.</Step>
  <Step title="Encrypt">The plaintext key encrypts the data locally, then is wiped from memory.</Step>
  <Step title="Store">The encrypted key is stored next to the encrypted data.</Step>
  <Step title="Decrypt">KMS decrypts the data key, if the key policy allows the caller.</Step>
</Steps>

- S3 offers SSE-S3 (the [S3](card:s3) default), SSE-KMS with your KMS key, or SSE-C with a key you send.
- EBS volumes and RDS databases use KMS keys too, and their snapshots stay encrypted.
- TLS certificates for load balancers and CloudFront: [ACM](card:edge-security).

## Example

Store a receipt with SSE-KMS under a customer managed key.

```java
s3.putObject(PutObjectRequest.builder()
        .bucket("payments-receipts")
        .key("receipts/2026/10/pay_123.pdf")
        .serverSideEncryption(ServerSideEncryption.AWS_KMS)
        .ssekmsKeyId("alias/receipts")        // customer managed key
        .build(),
    RequestBody.fromBytes(pdfBytes));
```

## Interview Qs

### What is envelope encryption, and why use it?

A data key encrypts the data; a KMS key encrypts the data key. Only the small data key goes to KMS, and decrypt rights stay in one place: the key policy.

### Does rotating a KMS key re-encrypt existing data?

No. KMS keeps the old key material and picks the right one to decrypt, so old data works without code changes. Data keys are not rotated either.
