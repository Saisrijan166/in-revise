## Why it exists

A private subnet is only a routing choice. Something must still decide which ports and sources may reach the load balancer, the app and the database.

## How it works

<Compare id="security-group-vs-nacl" />

- AWS advises security groups as the main control; NACLs as subnet guard rails, such as denying one bad IP range.
- An AccessDenied error is IAM, not the network: [policy evaluation](card:iam-policy-evaluation).

## Example

```text
alb-sg   inbound 443   from 0.0.0.0/0
app-sg   inbound 8080  from alb-sg    (Spring Boot tasks)
db-sg    inbound 5432  from app-sg    (RDS PostgreSQL)
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| New security group | no inbound, all outbound | Amazon VPC, 20-10-2026 |
| Default NACL | allows all in and out | Amazon VPC, 20-10-2026 |
| New custom NACL | denies all until you add rules | Amazon VPC, 20-10-2026 |

## Interview Qs

### How do you let only the app reach the database?

On the database's security group, allow port 5432 with the app's security group as the source. New app tasks get access by joining that group; there are no IPs to keep up to date.

### When would you use a NACL at all?

To deny traffic, which security groups cannot do, for example a known bad CIDR, or as a subnet-wide safety net if someone launches a resource with the wrong security group.
