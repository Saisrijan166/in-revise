## What it is

A security group is a virtual firewall you attach to a resource, such as an EC2 instance or an ECS task, holding allow rules for the traffic that may reach it. A network ACL (NACL) is a filter attached to a whole [subnet](card:vpc-and-subnets), holding both allow and deny rules. The key difference is one word: a security group is stateful, so it remembers a connection and lets the reply back automatically; a NACL is stateless, so it treats every packet on its own.

## Why it exists

A private subnet is only a routing choice; by itself it decides nothing about who may connect. Something still has to say the load balancer accepts port 443, the app accepts 8080 only from the load balancer, and the database accepts 5432 only from the app. Security groups do this per resource, which is precise and easy to chain. NACLs add a coarser, subnet-wide layer, useful for blocking a bad IP range that security groups, being allow-only, cannot deny.

## How it works

<Compare id="security-group-vs-nacl" />

1. You create one security group per tier: `alb-sg`, `app-sg`, `db-sg`.
2. On `alb-sg` you allow inbound 443 from `0.0.0.0/0`, so the internet can reach the load balancer.
3. On `app-sg` you allow inbound 8080 with the source set to `alb-sg`, so only the load balancer's tasks can reach the app.
4. On `db-sg` you allow inbound 5432 with the source set to `app-sg`, so only the app can reach the database.

So each tier references the one in front of it, and no rule mentions an IP address. Return traffic needs no rules, because security groups are stateful.

## Example

This is the full set of inbound rules for the three-tier chain. Each source is a security group, not a CIDR.

```text
alb-sg   inbound 443    source 0.0.0.0/0    (the internet reaches the load balancer)
app-sg   inbound 8080   source alb-sg       (only the ALB reaches the Spring Boot tasks)
db-sg    inbound 5432   source app-sg       (only the app reaches RDS PostgreSQL)
```

What to notice:

- `app-sg` names `alb-sg` as its source, so every task in `app-sg` accepts traffic from any member of `alb-sg`, with no IPs to track as tasks come and go.
- There are no outbound reply rules anywhere, because security groups are stateful and allow the response automatically.
- Replace `source app-sg` on `db-sg` with `0.0.0.0/0` and the database becomes reachable from anywhere the network routing allows, a common and serious mistake.

## Rules and defaults

- **New security group:** no inbound rules (nothing allowed in) and one outbound rule allowing all traffic out (Amazon VPC).
- **Default NACL:** allows all inbound and outbound traffic. A new custom NACL denies all until you add rules (Amazon VPC).
- **NACL evaluation:** rules are numbered 1 to 32766 and evaluated lowest first; the first match applies and no later rule is checked. An unremovable `*` rule denies anything unmatched.
- **One NACL per subnet:** a subnet has exactly one NACL at a time, but one NACL can cover many subnets.
- **Not a substitute for IAM:** these rules decide which packets arrive; IAM decides which AWS API calls are allowed. An `AccessDenied` error is an [IAM](card:iam-policy-evaluation) problem, not a network one.

## Not to be confused with

A security group controls traffic at the resource and is stateful, so return traffic is automatic. A NACL controls traffic at the subnet boundary and is stateless, so you write rules for both directions. Rule: reach for security groups first as the main control; add NACL rules only to deny a range or as a subnet-wide guard rail.

## Common mistakes

- **"NACLs replace security groups."** They do not. AWS advises security groups as the primary control and NACLs only as a secondary, coarse layer.
- **"A security group can block a specific IP."** It cannot; it has allow rules only. To deny one bad CIDR, use a NACL deny rule with a low number.

## Interview Qs

### What is the difference between stateful and stateless filtering here?

A security group is stateful: once it allows a connection, the reply is allowed automatically, so you write one rule. A NACL is stateless: it checks each packet alone, so an inbound allow needs a matching outbound rule for the reply, usually on ephemeral ports 1024-65535.

### When would you use a NACL at all?

To deny traffic, which security groups cannot do, for example a known bad CIDR range, or as a subnet-wide safety net in case a resource is ever launched with the wrong security group. For normal allow rules, security groups are simpler and more precise.

### How do you lock the database down to just the app?

Put the app and database in separate security groups. On the database group, allow its port only from the app's security group as the source. New app tasks get access by joining that group; there are no IP addresses to maintain.
