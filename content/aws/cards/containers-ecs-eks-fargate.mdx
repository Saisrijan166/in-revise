## What it is

A container image is a package that holds your app plus everything it needs to run, so it behaves the same on any machine. You store the image in ECR (Elastic Container Registry), AWS's private image store. To actually run images, keep them healthy and scale them, you need an orchestrator. AWS gives you two: ECS (Elastic Container Service), its own simpler orchestrator, and EKS (Elastic Kubernetes Service), managed Kubernetes. Either one can run your containers on Fargate (no servers for you) or on EC2 instances you own.

## Why it exists

An image runs the same everywhere, which solves "it worked on my machine". But running one container is not enough: in production you need many copies for load, a restart when one crashes, a rolling update to a new version, and placement across AZs. Doing that by hand on [EC2](card:ec2) is error-prone. An orchestrator does it for you: you declare "run four copies of this image and keep them healthy", and ECS or EKS makes it so and keeps it so.

## How it works

<Compare id="ecs-vs-eks" />

Following the ECS path for the payment service:

1. You build the Docker image and push it to an ECR repository.
2. You write a task definition: which image, how much CPU and memory, which ports, and the IAM roles. A task is one running set of containers from that definition.
3. You create an ECS service that says "keep 4 tasks of this definition running" and attach it to an [ALB](card:elastic-load-balancing) target group.
4. ECS launches the tasks on Fargate. With awsvpc networking each task gets its own network interface, private IP and security groups.
5. If a task stops or fails its health check, the service launches a replacement, so the count stays at 4.

So the task definition is the recipe, the task is one running copy, and the service keeps the right number alive.

## Example

A Fargate task definition for the payment service, with both IAM roles:

```json
{
  "family": "payment-service",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "512",
  "memory": "1024",
  "executionRoleArn": "arn:aws:iam::123456789012:role/ecsTaskExecutionRole",
  "taskRoleArn": "arn:aws:iam::123456789012:role/paymentServiceTaskRole",
  "containerDefinitions": [{
    "name": "app",
    "image": "123456789012.dkr.ecr.ap-south-1.amazonaws.com/payment-service:1.4.0",
    "portMappings": [{ "containerPort": 8080 }]
  }]
}
```

What to notice:

- `cpu` 512 with `memory` 1024 is a valid Fargate pair; many combinations are rejected, so the numbers are not free to choose.
- `executionRoleArn` lets the ECS agent pull the image and write logs; `taskRoleArn` is what the app's own AWS calls use. Mixing them up is the most common ECS mistake, covered in [task role vs execution role](compare:task-role-vs-task-execution-role).
- `networkMode` must be `awsvpc` on Fargate, which is why each task has its own ENI and security groups.

## Rules and defaults

- **Fargate CPU/memory:** only fixed pairs are valid, for example 256 CPU with 512 MiB–2 GB, 512 CPU with 1–4 GB, 1024 CPU with 2–8 GB.
- **Networking:** Fargate requires `awsvpc`; each task gets one elastic network interface with a private IP.
- **Capacity options:** Fargate (no servers), your own EC2 instances in the cluster, or ECS Managed Instances (EC2 types you choose, run by AWS).
- **EKS fee:** EKS charges per cluster per hour for the control plane; ECS has no orchestration charge, you pay only for compute.
- **Image pull:** a Fargate task in a private subnet needs a NAT gateway or an ECR VPC endpoint to pull its image.

## Not to be confused with

ECR, ECS and EKS sound alike but do different jobs. ECR stores images. ECS and EKS run them. Fargate is not an orchestrator at all; it is a way to run ECS tasks or EKS pods without managing servers. Rule: ECR = store, ECS/EKS = orchestrate, Fargate = run without servers.

## Common mistakes

- **"EKS is just a better ECS."** EKS is real Kubernetes, with more power and more to operate, plus a per-cluster fee. If you are not using Kubernetes features or skills, ECS does the same job with less to run and no control-plane charge.

## Interview Qs

### ECS or EKS: which would you pick?

ECS for AWS-only teams: AWS's own API, no control-plane fee, fewer parts to learn. EKS when the team already uses Kubernetes or needs its ecosystem of tools and plugins, accepting a per-cluster hourly fee and more operational work. Both can run on Fargate, so the choice is about the orchestrator, not the servers.

### What is the difference between a task and a service in ECS?

A task is one running copy of a task definition; it can do a job and stop. A service keeps a desired number of tasks running, replaces any that fail, and registers them with a load balancer. Use a task for a one-off job and a service for a long-running API.

### What does Fargate actually remove, and what stays your job?

Fargate removes the servers: AWS provisions, patches and scales the hosts, and you no longer manage EC2 instances. What stays yours is the container image, the CPU and memory you set per task, the IAM roles, and the app itself. You pay for the vCPU and memory each task uses.
