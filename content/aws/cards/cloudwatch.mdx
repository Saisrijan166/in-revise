## What it is

Amazon CloudWatch is the AWS monitoring service. It holds two kinds of data: metrics, which are numbers measured over time, and logs, which are text lines your app and AWS services write. A metric is a named series of numbers in a namespace, such as the load balancer's 5xx count in `AWS/ApplicationELB`; dimensions like the load balancer's name tell one series apart from another. On top of that data you create alarms, which watch a metric and act when it crosses a line.

## Why it exists

When the payment service starts failing, you need to know before customers call. Without monitoring you would be logging in to each instance to tail files and guess. CloudWatch gathers the numbers and logs from every instance and service in one place, so you can see the whole system, search all logs at once, and have an alarm page the on-call engineer the moment errors rise, instead of finding out hours later.

1. Each AWS service pushes its metrics to CloudWatch on its own, for example the load balancer's per-minute 5xx count.
2. Your app writes log lines to a log group. A [metric filter](card:cw-metric-filter) can count lines that match a pattern, like `PAYMENT_FAILED`, and publish that count as a metric.
3. You create an alarm on a metric, with a threshold, a period and how many periods must breach.
4. CloudWatch evaluates the alarm each minute over the chosen window. When enough periods breach, the alarm moves to ALARM and runs its actions; when the metric recovers, it moves back to OK.

So the key is: the alarm acts only on a state change, so a brief spike that recovers does not page anyone.

## Example

This CloudFormation alarm pages the on-call team when the payment load balancer returns too many server errors.

```yaml
Payment5xxAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: AWS/ApplicationELB
    MetricName: HTTPCode_Target_5XX_Count
    Dimensions:
      - { Name: LoadBalancer, Value: !GetAtt PaymentAlb.LoadBalancerFullName }
    Statistic: Sum
    Period: 60                     # one data point per minute
    EvaluationPeriods: 5           # look at the last 5 minutes
    DatapointsToAlarm: 3           # 3 of those 5 breaching = ALARM
    Threshold: 10
    ComparisonOperator: GreaterThanThreshold
    AlarmActions: [!Ref OnCallTopic]
```

What to notice:

- `Statistic: Sum` adds up the 5xx responses in each one-minute period; `HTTPCode_Target_5XX_Count` counts errors from the targets, not from the load balancer itself.
- `DatapointsToAlarm: 3` with `EvaluationPeriods: 5` makes this a "3 out of 5" alarm, so one noisy minute does not page anyone, but a sustained problem does. Remove `DatapointsToAlarm` and it needs all 5 minutes breaching.
- `AlarmActions` points at an SNS topic; subscribers to that topic (email, SMS, a chat webhook) get the notification when the state turns to ALARM.

## Rules and defaults

- **Metric retention:** one-minute data is kept 15 days, five-minute data 63 days, one-hour data 455 days, then it ages out; you cannot delete a metric yourself (CloudWatch, at the time of writing).
- **Log retention:** a new log group keeps its logs forever by default; set a retention period (one day to ten years) per log group (CloudWatch Logs, at the time of writing).
- **EC2 monitoring:** basic monitoring (free) reports metrics every 5 minutes; detailed monitoring (paid) reports every minute. Match the alarm period to the resolution.
- **Missing data:** by default a period with no data is treated as `missing`; if the whole window is missing the alarm goes to INSUFFICIENT_DATA, not ALARM (CloudWatch, at the time of writing).
- **In-guest metrics:** memory, swap and disk-space use need the CloudWatch agent; they are not in the default EC2 metric set.

## Not to be confused with

CloudWatch answers "how is the system behaving?" with metrics, logs and alarms. [CloudTrail](card:cloudtrail) answers "who did what in the account?" with a record of every AWS API call. Rule: CloudWatch = health and alerting; CloudTrail = audit of API calls.

## Common mistakes

- **"The alarm will fire the moment the metric crosses the threshold once."** It fires only when enough periods in the window breach and the state actually changes. A one-minute spike that recovers usually stays OK.
- **Alarming on `Average` latency only.** A high p99 can hide behind a healthy average. Alarm on a percentile like p99 of `TargetResponseTime` for user-facing latency.

## Interview Qs

### How would you get alerted when the payment API starts failing?

Create a CloudWatch alarm on the load balancer's `HTTPCode_Target_5XX_Count` and on `TargetResponseTime` (a high percentile), over a few one-minute periods with an "M out of N" setting, and set the alarm action to an SNS topic the on-call team subscribes to. Add a dashboard, and a metric filter on the app logs for app-level errors.

### Why can't you see your EC2 instance's memory usage in CloudWatch?

Memory lives inside the guest operating system, which AWS cannot read from outside the instance. The default EC2 metrics cover CPU, network and disk I/O only. Install the CloudWatch agent on the instance; it collects in-guest metrics such as memory and disk-space use, plus logs, and publishes them as custom metrics.

### What does an alarm's INSUFFICIENT_DATA state mean?

The alarm does not have enough recent data points to decide OK or ALARM, for example just after creation, or when the metric has stopped reporting. By default missing data is treated as `missing`, so a metric that only reports when something happens can sit in INSUFFICIENT_DATA; you can change how missing data is treated per alarm.
