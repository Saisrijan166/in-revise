## Why it exists

You cannot fix what you cannot see. Every service needs numbers to watch, logs to search and a way to wake someone up when payments start failing.

## How it works

<Mermaid
  alt="AWS services such as the load balancer send metrics to CloudWatch. The payment service writes logs to a log group; a metric filter turns matching lines into a metric. An alarm watches a metric and, in the ALARM state, notifies an SNS topic or runs an Auto Scaling action."
  chart={`flowchart LR
  ALB[Load balancer] -- metrics --> M[Metric]
  App[Payment service] -- logs --> LG[Log group]
  LG -- metric filter --> M
  M --> A{Alarm}
  A -- ALARM --> SNS[SNS topic: on-call]
  A -- ALARM --> AS[Auto Scaling action]`}
/>

- Search logs with [Logs Insights](card:cw-logs-insights); a [metric filter](card:cw-metric-filter) counts lines like `PAYMENT_FAILED`.
- Traces across services: [X-Ray and OpenTelemetry](card:x-ray-and-tracing).

## Example

```yaml
Payment5xxAlarm:                       # CloudFormation
  Type: AWS::CloudWatch::Alarm
  Properties:
    Namespace: AWS/ApplicationELB
    MetricName: HTTPCode_Target_5XX_Count
    Dimensions: [{ Name: LoadBalancer, Value: !GetAtt PaymentAlb.LoadBalancerFullName }]
    Statistic: Sum
    Period: 60
    EvaluationPeriods: 5
    Threshold: 10
    ComparisonOperator: GreaterThanThreshold
    AlarmActions: [!Ref OnCallTopic]
```

## Interview Qs

### How would you get alerted when the payment API starts failing?

Alarm on the load balancer's target 5xx count and on latency, over a few one-minute periods, with an SNS topic as the action. Add a dashboard and, for app errors, a metric filter on the logs.

### Why can't you see your EC2 instance's memory use?

The default EC2 metrics do not include memory. Install the CloudWatch agent, which collects in-guest metrics such as memory and disk use, and logs.
