## What it is

AWS Lambda runs a single function in response to an event, such as an HTTP call, a new file in S3, or a message on a queue. You upload the function; AWS provides the server, the runtime and the scaling. To serve more events at once, Lambda runs more copies of your function side by side, each in its own execution environment, a small isolated micro-VM. You are charged only for the requests and the running time, not for idle servers.

## Why it exists

Some work does not justify a server that runs all day. A payment webhook fires a few times an hour; a receipt worker runs when a payment completes. On [EC2](card:ec2) you would keep an instance up and pay for it around the clock just for those bursts, and you would patch and scale it yourself. Lambda runs the code only when an event arrives and nothing when it is idle, and it scales from zero to many copies and back on its own, so there is no server to size or keep alive.

## How it works

1. An event arrives from a caller or an AWS service.
2. Lambda needs an execution environment. If a free warm one exists, it reuses it; otherwise it creates a new one, which is the cold start.
3. A new environment loads your code, starts the runtime (for Java, the JVM) and runs your init code (static fields, SDK clients). This happens once per environment.
4. Lambda calls your handler with the event. The handler gets its AWS permissions from the function's execution role: short-lived [temporary credentials](card:sts-and-temporary-credentials).
5. The environment stays warm for a while, so the next event skips init and runs the handler straight away.

So init runs once per environment and the handler runs once per event: anything expensive belongs in init.

## Example

A handler that writes each SQS message to S3, creating the S3 client in init so warm calls reuse it:

```java
public class ReceiptHandler implements RequestHandler<SQSEvent, Void> {
    private static final S3Client S3 = S3Client.create();   // init: once per environment

    @Override
    public Void handleRequest(SQSEvent event, Context context) {   // handler: once per batch
        for (SQSEvent.SQSMessage msg : event.getRecords()) {
            S3.putObject(b -> b.bucket("payment-receipts").key(msg.getMessageId() + ".json"),
                    RequestBody.fromString(msg.getBody()));
        }
        return null;
    }
}
```

What to notice:

- `S3` is a `static` field built outside the handler, so it is created during init and reused by every warm invocation, along with its connection pool.
- Moving `S3Client.create()` inside `handleRequest` would rebuild the client on every event, adding latency and wasting connections.
- The method returns after the batch; it must finish within the function's timeout (3 s by default, 900 s at most), or Lambda stops it.

## Rules and defaults

- **Timeout:** 3 s by default, 900 s (15 minutes) maximum per invocation.
- **Memory and CPU:** 128 MB to 10,240 MB; CPU scales with memory, and 1,769 MB gives one vCPU.
- **Concurrency:** 1,000 concurrent executions per Region by default (a soft limit); new accounts start lower and AWS raises it with use.
- **Payload:** 6 MB for a synchronous request and response; 1 MB for an asynchronous event.
- **SnapStart (Java 11+):** works only on published versions, not `$LATEST`; cannot be combined with provisioned concurrency; free on Java runtimes.
- **Credentials:** the function assumes its execution role; never put access keys in the code.

## Not to be confused with

Reserved and provisioned concurrency sound alike but differ. Reserved concurrency sets aside, and caps, one function's share of the Region's 1,000, and is free; it protects or limits a function. Provisioned concurrency keeps a number of environments initialised and warm so there is no cold start, and it costs extra. Rule: reserved = how many can run; provisioned = how many are kept warm.

## Common mistakes

- **"Provisioned concurrency and SnapStart together give the fastest Java."** They cannot be combined. Use SnapStart to cut JVM cold starts for free, and switch to provisioned concurrency only when you need double-digit-millisecond starts that SnapStart cannot guarantee.

## Interview Qs

### What is a cold start, and how do you reduce it for Java?

A cold start is the time to create a new execution environment: load the code, start the JVM and run static init, before the handler runs. Reduce it by keeping init light, using SnapStart to resume from a published snapshot, and reusing SDK clients across invocations. For strict latency, provisioned concurrency keeps environments warm.

### Why create SDK clients outside the handler?

Init code runs once per execution environment, but the handler runs on every event. A client built outside the handler is created during init and reused by all warm invocations, so you build the client and its connection pool once instead of per request. Building it inside the handler repeats that cost every time.

### When is Lambda the wrong choice?

When one run can exceed 15 minutes, when you need full control of the OS or special hardware, or for a steady, high-throughput API where always-warm containers are cheaper and avoid cold starts entirely. Lambda fits short, event-driven, spiky work like webhooks and file triggers.
