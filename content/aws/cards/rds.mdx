## What it is

Amazon RDS (Relational Database Service) is a managed service that runs a relational database engine for you: PostgreSQL, MySQL, MariaDB, Oracle, SQL Server or Db2. You create a DB instance, which is the database server, choose its size and storage, and place it in [private subnets](card:vpc-and-subnets) of your VPC. The app connects to its endpoint, a DNS name, with the normal JDBC driver. AWS runs the operating system and the engine underneath.

## Why it exists

Running PostgreSQL yourself on EC2 means installing it, patching the operating system and the engine, scheduling backups, testing restores and building failover to another AZ. Each job is easy to get wrong, and one mistake can lose payments. RDS takes over these jobs: you choose a backup retention period and a maintenance window and turn on Multi-AZ. Your time goes to the schema and the queries instead.

## How it works

  chart={`flowchart LR

  P -- "daily backup + logs" --> B[(S3, managed by RDS)]`}
/>

1. The payment service connects to the endpoint, such as `payments-db.abc123example.ap-south-1.rds.amazonaws.com`. DNS resolves it to the primary instance in AZ a.
2. Every write is copied synchronously to the standby in AZ b before it counts as done, so the standby holds every committed transaction.
3. RDS also takes a daily backup and uploads the transaction logs to S3 every five minutes. Together they allow a restore to any moment in the retention period.
4. If the primary or its AZ fails, RDS promotes the standby and points the endpoint's DNS record at it, typically within 60 to 120 seconds.
5. Open connections break. The connection pool opens new ones, and once the JVM looks the name up again, they reach the new primary.

So the app never needs a new address: the same endpoint name always leads to the current primary.

## Example

The payment service on ECS connects through the endpoint name, sizes its pool, and makes the JVM refresh DNS so it follows a failover:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://payments-db.abc123example.ap-south-1.rds.amazonaws.com:5432/payments
    hikari:
      maximum-pool-size: 10   # 6 tasks x 10 = 60 connections in total
```

```java
// At startup, before any connection is opened: look DNS names up again after 60 s
java.security.Security.setProperty("networkaddress.cache.ttl", "60");
```

What to notice:

- The URL names the endpoint, never an IP address. After a failover the same name points at the new primary.
- The pool size is per task. If Auto Scaling adds tasks, the total grows, so compare it with `max_connections`, which RDS sets from the instance's memory by default.
- On some Java setups the JVM caches DNS answers until it restarts, so the pool would keep dialling the old primary. AWS advises a JVM DNS TTL of 60 seconds or less.
- The password is not here. You will load it from [Secrets Manager](card:secrets-and-parameters) later.

## Rules and defaults

- **Backups:** automated backups are kept 7 days by default from the console and 1 day from the CLI or API; you can choose 0 to 35, and 0 turns them off.
- **Point-in-time restore:** always creates a new DB instance. You then switch the app to it, or copy the lost rows back.
- **Read replicas:** you create them yourself (RDS does not add them automatically), in the same or another Region, up to 15 per source instance (quota at the time of writing). A replica can be promoted to a standalone database.
- **Multi-AZ DB cluster:** a different option with a writer and two readable standbys in three AZs; its failover is usually under 35 seconds.
- **Many short-lived clients:** functions such as [Lambda](card:lambda) should connect through RDS Proxy, which pools and reuses database connections.
- **Test failover:** AWS advises testing a failover to learn how long it takes for you and to prove the app reconnects.

## Not to be confused with

A Multi-AZ standby is a hidden, synchronous copy that exists only to take over when the primary fails. A read replica is a visible, asynchronous copy with its own endpoint that serves read-only queries, so it can be slightly behind. Rule: Multi-AZ = survive a failure; read replica = serve more reads.

## Common mistakes

- **"A read replica is my backup."** A replica copies every change within seconds, including a mistaken DELETE. Use automated backups and point-in-time restore to go back in time.

## Interview Qs

### What happens to the app during a Multi-AZ failover?

RDS promotes the standby and moves the endpoint's DNS record to it, typically within one to two minutes. Open connections drop, so the pool must reconnect, and the JVM must not cache the old IP for long. Writes in flight fail and should be retried safely.

### Rows were deleted by mistake at 10:42. How do you recover?

Restore the database to a time just before 10:42 from automated backups. RDS creates a new DB instance at that point; you copy the missing rows back or switch the app to it. A read replica would not help, because it copied the delete too.

### Would you run PostgreSQL on EC2 or on RDS?

RDS by default: AWS recommends it for most relational workloads, because it does the patching, backups and failover for you. EC2 makes sense only when you need something RDS does not allow, such as full control of the operating system, and then you run backups and failover yourself.
