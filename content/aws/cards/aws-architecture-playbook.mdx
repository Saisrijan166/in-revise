## What it is

This is the closing concept: a method for answering AWS scenario questions, and a map from a need to the service that meets it. A scenario question gives you a situation ("design a backend that handles spikes and stores receipts") and expects you to pick services and justify them. The playbook is the order to answer in, and the need-to-service table is the shortcut for picking. It pulls together every concept in this tech into one answer.

## Why it exists

Scenario rounds reward structure, not trivia. Candidates who recite services sound broad but unfocused; candidates who start from requirements and match one service per need, with a reason, sound like engineers. Having a fixed order to walk through means you never freeze, never forget the boring-but-critical parts (access, observability, cost), and can defend each choice. The table turns "which service?" into a quick, confident lookup.

## How it works

Match the need to the service, and say why. Each row links the concept that explains it:

| Need | Pick |
|---|---|
| Traffic spikes | [Auto Scaling](card:auto-scaling-groups) behind a [load balancer](card:elastic-load-balancing) |
| Survive an AZ failure | Every layer in two or more [AZs](card:regions-and-azs) |
| Run the service; code on an event | [ECS, EKS or EC2](card:compute-choice); [Lambda](card:lambda) |
| Images and PDFs; static files near users | [S3](card:s3); [CloudFront](card:cloudfront) |
| Relational data or key lookups | [RDS, Aurora or DynamoDB](card:choosing-a-database) |
| Fast short-lived lookups | [ElastiCache](card:elasticache) |
| Background work; one event to many | [SQS, SNS or EventBridge](compare:sqs-vs-sns-vs-eventbridge-vs-kinesis) |
| A multi-step workflow | [Step Functions](card:step-functions) |
| Secrets; encryption keys | [Secrets Manager](card:secrets-and-parameters); [KMS](card:kms-and-encryption) |
| Reach AWS APIs from private subnets | [VPC endpoints](card:vpc-endpoints-privatelink) |
| Health and alarms; API audit | [CloudWatch](card:cloudwatch); [CloudTrail](card:cloudtrail) |
| Survive losing a Region | [A DR strategy](card:disaster-recovery) |

What to notice, phrased as the corrections interviewers listen for:

| Not that | Say this |
|---|---|
| Access keys in config | An IAM role: [temporary credentials](card:sts-and-temporary-credentials) |
| A read replica for failover | [Multi-AZ for failover, replicas for reads](compare:multi-az-vs-read-replicas) |
| A private subnet is secure by itself | It still needs tight [security groups](compare:security-group-vs-nacl) |

- The flow follows the answer order: traffic enters through Route 53 and the ALB (network), hits Fargate (compute), reads and writes RDS and ElastiCache (data), and offloads slow receipt work to SQS (async).
- Each box has a reason: RDS is Multi-AZ so an AZ failure does not lose the database; the queue exists so a slow receipt step does not block the payment response.
- The corrections table is where candidates lose points: naming an IAM role over access keys, and Multi-AZ over a read replica for failover, shows you understand why, not just what.

## Rules and defaults

- **Numbers first:** ask for traffic, data size, RTO and RPO before naming a single service.
- **One reason per service:** state why it fits and the alternative you rejected.
- **Cover the unglamorous needs:** access (IAM roles, Secrets Manager), observability (CloudWatch, X-Ray) and cost are part of a complete answer.
- **Close on the pillars:** finish by checking the design against the Well-Architected pillars, especially security, reliability and cost.
- **Default to managed:** prefer managed services (Fargate, RDS, SQS) over self-run ones unless a requirement forces otherwise.

## Interview Qs

### Traffic jumps tenfold during a sale. What do you do?

Scale ECS tasks on request-count-per-target behind the ALB, cache merchant config in ElastiCache to spare the database, move slow work like receipt generation to SQS so it does not block responses, and watch database connections and 5xx alarms. The point is elasticity plus shedding load off the hot path, not just "add servers".

### Which services would you use for a serverless payment API?

[API Gateway](card:api-gateway) in front of [Lambda](card:lambda) for the API, [DynamoDB](card:dynamodb) for payments looked up by id, SQS for receipt jobs, [Step Functions](card:step-functions) for multi-step flows like refunds, and CloudWatch with X-Ray to watch it. Everything scales to zero and per-request, which suits spiky, event-driven workloads.

### How do you structure a design answer so you don't miss anything?

Walk a fixed order: clarify the numbers, then compute, data, networking, access, async work, observability, deployment, and cost. Match one service to each need and justify it, then close by checking the Well-Architected pillars. The order stops you freezing and stops you forgetting access, observability and cost, which candidates often skip.
