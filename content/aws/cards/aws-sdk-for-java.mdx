## What it is

The AWS SDK for Java is the library your application uses to call AWS services from code: put an object in S3, send a message to SQS, read a secret. You use version 2.x (the `software.amazon.awssdk` packages). For each service you build a client, like `S3Client`, which signs every request, retries failures, pools HTTP connections, and finds your credentials. In Spring Boot, Spring Cloud AWS builds those clients for you and adds higher-level helpers on top.

## Why it exists

The payment service must put receipt PDFs in S3 and send "payment completed" messages to SQS. Doing that by hand would mean signing each HTTPS request with the AWS signature algorithm, retrying throttled calls, managing a connection pool, and somehow supplying credentials, a large amount of fiddly, security-sensitive code. The SDK does all of it, and crucially it finds credentials from the environment, so the running code never holds an access key.

## How it works

The SDK finds credentials by walking a fixed list and using the first source that has them, so the same code works on your laptop, in ECS and on EC2 without change.

<Steps label="Default credentials chain: the first source that has credentials wins">
  <Step title="Java system properties">aws.accessKeyId and aws.secretAccessKey</Step>
  <Step title="Environment variables">AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY</Step>
  <Step title="Web identity token">Assumes a role from a token file, as on EKS</Step>
  <Step title="Profile files">~/.aws/credentials and ~/.aws/config, including SSO</Step>
  <Step title="Container credentials">The ECS task role, via the ECS credentials endpoint</Step>
  <Step title="Instance profile">The EC2 instance role, from the instance metadata service</Step>
</Steps>

On ECS or EC2 the chain falls through to the task or instance role, so you attach an IAM role and store no keys. Which role each compute type gets is covered in [temporary credentials](card:sts-and-temporary-credentials).

## Example

Build the client once with explicit timeouts, then reuse it everywhere; credentials come from the chain, not from code.

```java
S3Client s3 = S3Client.builder()                        // build once, reuse everywhere
    .region(Region.AP_SOUTH_1)
    .overrideConfiguration(o -> o
        .apiCallTimeout(Duration.ofSeconds(10))         // whole call, across all retries
        .apiCallAttemptTimeout(Duration.ofSeconds(3)))  // one HTTP attempt
    .build();                                           // credentials: default chain
```

What to notice:

- There is no credentials provider on the builder, so the SDK uses the default chain; on ECS that resolves to the task role, which is why no keys appear here.
- `apiCallAttemptTimeout` caps one HTTP attempt and `apiCallTimeout` caps the whole call including retries. Remove them and there is no default, so a stuck call can hang the thread for minutes.
- This `S3Client` is thread-safe and holds a connection pool, so you build it once (a Spring bean, or a static field) and share it; you do not create one per request.

## Rules and defaults

- **Use 2.x:** SDK 1.x (the `com.amazonaws` packages) reached end of support on 31-12-2025; new code uses `software.amazon.awssdk`.
- **Reuse clients:** clients are thread-safe and pool connections; share one per service and call `close()` only at shutdown.
- **Timeouts:** the SDK sets connection and socket timeouts but no `apiCallTimeout` or `apiCallAttemptTimeout`; set those yourself.
- **Retries:** on by default; the SDK retries throttling and transient errors a few times with exponential backoff, and a token bucket stops retry storms.
- **Testing:** run LocalStack in Testcontainers to test AWS calls with no real account; Spring Cloud AWS can point its clients at it.

## Not to be confused with

The SDK client is a low-level, per-service object you build and configure. The Spring Cloud AWS [templates](card:aws-code-templates) (`S3Template`, `SqsTemplate`) and `@SqsListener` are higher-level helpers that wrap the client and are auto-configured as beans. Rule: SDK client = the raw, portable API; Spring Cloud AWS = the Spring-friendly layer over it.

## Interview Qs

### How does the app get AWS credentials on ECS without access keys?

The default credentials chain falls through to the container credentials provider. ECS sets the `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` environment variable, and the SDK fetches the task role's temporary credentials from that endpoint. You attach an IAM task role to the task definition; no keys live in the image, the config, or the code.

### Why build one SDK client and reuse it?

Each client is thread-safe and holds its own HTTP connection pool and threads, which are expensive to set up. Creating a client per request wastes those resources and can exhaust connections, slowing every call. Build one client per service at startup, share it across all requests, and close it only when the app shuts down.

### How do you test AWS code without a real account?

Run LocalStack, a fake AWS, in Testcontainers, and point the SDK clients at its endpoint. With Spring Cloud AWS, the Testcontainers module wires the clients to LocalStack through `@ServiceConnection`, so tests exercise real SDK calls against a local service instead of production AWS.
