## What it is

Distributed tracing follows a single request as it moves through many services. Each service records its own piece of work, with a start and end time, as a span (X-Ray calls a service's top-level span a segment, and a span for one downstream call inside it a subsegment). All the spans from one request share a trace ID, so a tool can gather them and draw one timeline. AWS X-Ray is the AWS service that stores traces and draws that timeline and a service map.

## Why it exists

One payment touches the load balancer, the payment service, the database, a queue and a worker. When it is slow, logs show each service on its own, so you cannot tell which hop ate the time, and you certainly cannot see the end-to-end path. A trace joins the pieces: it shows every hop in order, with its duration, so the slow or failing step is obvious. That is the one thing metrics and logs cannot give you.

1. The first service that handles the request gets or creates a trace ID and puts it in a header: `X-Amzn-Trace-Id` for X-Ray, or the W3C `traceparent` header with OpenTelemetry.
2. Each service records a span for its own work, and subsegments for the downstream calls it makes, such as a database query or a queue send.
3. When one service calls another, it passes the same trace ID along, so the next service's spans join the same trace.
4. Sampling decides which requests to trace: by default X-Ray records the first request each second and 5% of the rest, to keep cost and overhead down.
5. The spans are sent to X-Ray, which joins all spans with the same ID into one trace timeline and draws a service map of the services and their connections.

So the key is: one ID, passed in a header from hop to hop, is what turns scattered per-service records into a single picture.

## Example

The OpenTelemetry Java agent instruments the Spring Boot jar with no code changes; you attach it at startup.

```bash
# Zero-code tracing of the payment service with the OpenTelemetry Java agent
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=payment-service \
     -jar payment-service.jar
# Spans go over OTLP (http/protobuf, default localhost:4318) to the
# CloudWatch agent or an OpenTelemetry Collector, which forwards them to X-Ray
```

What to notice:

- `-javaagent:opentelemetry-javaagent.jar` attaches the agent, which auto-instruments common libraries (the web server, the JDBC driver, the AWS SDK) so each incoming request and downstream call becomes a span without touching your code.
- `otel.service.name` sets the name this service shows up as on the trace map; without it the service appears as "unknown_service".
- The agent exports over OTLP by default; it does not talk to X-Ray directly. A CloudWatch agent or OpenTelemetry Collector receives the spans and sends them on to X-Ray, which is why you stop the old X-Ray daemon when you switch.

## Rules and defaults

- **Instrumentation:** use OpenTelemetry; the X-Ray SDKs and daemon are in maintenance mode (security fixes only) since 25-02-2026 (X-Ray, at the time of writing).
- **Propagation:** OpenTelemetry defaults to the W3C `traceparent` header; you can add the X-Ray propagator to pass context to AWS services that read `X-Amzn-Trace-Id`.
- **Default sampling:** first request each second, then 5% of the rest; add rules to trace more of the paths you care about and less of health checks.
- **Retention:** X-Ray keeps trace and service-graph data for 30 days (X-Ray, at the time of writing).
- **Annotations vs metadata:** annotations are indexed and searchable (X-Ray indexes up to 50 per trace); metadata is stored but not indexed.

## Interview Qs

### A payment takes four seconds. How do you find the slow hop?

Open its trace in X-Ray. The timeline shows each segment and subsegment with its own duration, so the slow call, such as a database query, stands out. You can filter traces by an indexed annotation like the merchant id to find the affected requests, and compare them against fast ones.

### Why sample instead of tracing every request?

Tracing every request adds cost and overhead and produces far more data than you need to spot problems. X-Ray's default rule records the first request each second plus 5% of the rest, which is enough to see patterns; you add rules to trace all of a critical path, like payments, and little of noisy traffic like health checks.

### How is a trace tied together across services?

By a trace ID carried in a header. The first service creates the ID and puts it in the request; each service passes the same ID to its downstream calls and records spans tagged with it. The tracing backend gathers all spans with that ID into one trace, which is why context propagation (W3C `traceparent` or `X-Amzn-Trace-Id`) must flow through every hop.
