## Why it exists

A payment touches the load balancer, the service, RDS, SQS and a worker. Logs show each piece alone; a trace shows the whole path and where the time went.

## How it works

<Mermaid
  alt="One trace ID flows from the load balancer to the payment service, which records subsegments for RDS and SQS calls. The receipt worker continues the trace and writes to S3. X-Ray joins all parts into one trace."
  chart={`flowchart LR
  ALB[Load balancer] -- trace ID --> SVC[Payment service]
  SVC -- subsegment --> RDS[(RDS)]
  SVC -- subsegment --> Q[SQS queue]
  Q -- trace ID --> W[Receipt worker]
  W --> S3[(S3)]
  SVC -.-> XR[X-Ray: trace and trace map]
  W -.-> XR`}
/>

- Metrics say something is wrong, logs say what one service did, a trace says where in the chain.
- [Application Signals](card:cw-application-signals) adds latency and fault dashboards and SLOs on top of traces.

## Example

```bash
# Zero-code instrumentation of the Spring Boot jar (OpenTelemetry Java agent)
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=payment-service \
     -jar payment-service.jar
# Spans go over OTLP to the CloudWatch agent or an OpenTelemetry Collector, then to X-Ray
```

## Interview Qs

### A payment takes four seconds. How do you find the slow hop?

Open its trace. The timeline shows each segment and subsegment with its duration, so the slow call, say a database query, stands out. Filter traces by an indexed annotation such as the merchant id.

### Why sample instead of tracing every request?

Tracing everything costs money and overhead. X-Ray's default rule records the first request each second and 5% of the rest; add rules to keep more of the paths you care about.
