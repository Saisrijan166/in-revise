## What it is

AWS Step Functions runs a workflow as a state machine: a list of named steps, written in JSON, where each step says what to do and which step comes next. A step, called a state, can run a task (a [Lambda](card:lambda) function or an AWS API call), choose a branch, run steps in parallel, or wait. Step Functions moves the data from one step to the next, retries steps that fail, and records every step of every run so you can see exactly what happened.

## Why it exists

A payment flow is several steps: charge the card, save the receipt, notify the customer. If step two fails after step one, someone must refund the charge. Writing that retry and rollback logic by hand, spread across services, is fragile and hard to see into: when a payment gets stuck, nobody knows which step failed. Step Functions makes the steps, their retries and their rollback a single JSON definition, and keeps a full history of each run, so the flow is both reliable and visible.

## How it works

  S([Start]) --> C[Charge payment]
  C --> R[Save receipt to S3]

  R -. "Catch after retries" .-> RF[Refund payment] --> F([Fail])`}

1. You write the workflow in Amazon States Language: each state names its type, what it does, and the next state.
2. You start an execution with some input JSON. Step Functions enters the first state and passes the input to it.
3. A Task state does its work. If it throws an error listed in its Retry, Step Functions waits and tries again, up to the attempts you set.
4. If the retries are used up, a Catch sends the run to another state instead of failing, for example a RefundPayment step that undoes the charge.
5. Step Functions carries each state's output into the next state, and records the whole path, until the run reaches a Succeed or Fail state.

So retries and rollback are configuration in the state machine, not code in your services.

## Example

The SaveReceipt state retries twice, then on any remaining failure catches to a refund:

```json
"SaveReceipt": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": { "FunctionName": "save-receipt", "Payload.$": "$" },
  "Retry": [{ "ErrorEquals": ["States.TaskFailed"], "MaxAttempts": 2 }],
  "Catch": [{ "ErrorEquals": ["States.ALL"], "Next": "RefundPayment" }],
  "Next": "NotifyCustomer"
}
```

What to notice:

- `Retry` on `States.TaskFailed` retries any Lambda error twice; with no Retry, the first error would fail the whole execution.
- `Catch` on `States.ALL` runs only after the retries are used up, sending the run to RefundPayment instead of failing, which is the rollback step of the saga.
- `Payload.$: "$"` passes this state's whole input to the Lambda; the `.$` means the value comes from the run's data, not a literal string.
- Remove the Catch and a receipt that keeps failing leaves the card charged with no refund, so the Catch is what makes the flow self-correcting.

## Rules and defaults

- **Retry defaults:** when you give only `ErrorEquals`, Step Functions waits 1 second, retries up to 3 times, and doubles the interval each time (BackoffRate 2.0). You can add MaxDelaySeconds and jitter.
- **Retry and Catch states:** available on Task, Parallel and Map states, not on Pass or Wait, and not on a top-level execution failure.
- **Standard:** up to 1 year per run, exactly-once, full history kept 90 days; billed per state transition. Use it for payments and approvals.
- **Express:** up to 5 minutes; asynchronous runs are at-least-once and synchronous runs are at-most-once; billed per run, duration and memory. Use it for high-volume idempotent work.
- **Payload limit:** 256 KiB per state input or output. For larger data, store it in S3 and pass the key through the workflow.
- **Service integrations:** optimized integrations for common services, plus AWS SDK integrations that call over 200 AWS services. The .sync (run a job) and callback patterns are Standard only.

## Interview Qs

### Standard or Express workflows?

Standard runs up to a year and is exactly-once, so it suits non-idempotent, auditable flows like payments and approvals; it keeps 90 days of history and is billed per state transition. Express runs up to 5 minutes, is at-least-once when asynchronous, and is billed per run and duration, so it suits high-volume, idempotent event processing.

### How do you roll back a payment that spans several services?

Model a saga. Each step has a Catch that, on failure, jumps to a compensating step that undoes the earlier work, such as a refund, in reverse order. Step Functions drives this, but because retries can repeat a step, every step must be idempotent so a repeat does not double-charge or double-refund.

### Why use Step Functions instead of chaining Lambdas yourself?

Chained Lambdas hide the flow: retries, timeouts and rollback become ad-hoc code, and a stuck run is hard to trace. Step Functions makes the steps, retries and error paths a single JSON definition and records every run's exact path, so the workflow is visible, retried consistently, and easy to change without redeploying code.
