## Why it exists

Charge ₹500, save the receipt, notify the customer: if step two fails after step one, someone must refund. Hand-written retry and rollback code across services is fragile.

## How it works

<Mermaid
  alt="A payment state machine. Charge payment, then save the receipt to S3, then notify the customer, then succeed. If saving the receipt still fails after retries, a Catch sends the run to Refund payment, which ends in a Fail state."
  chart={`flowchart LR
  S([Start]) --> C[Charge payment]
  C --> R[Save receipt to S3]
  R --> N[Notify customer] --> OK([Succeed])
  R -. "Catch after retries" .-> RF[Refund payment] --> F([Fail])`}
/>

- Each box is a Task state; Choice, Parallel, Map and Wait states shape the flow.
- A Standard workflow keeps each run's history for 90 days, showing the exact path taken.

## Example

```json
"SaveReceipt": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": { "FunctionName": "save-receipt", "Payload.$": "$" },
  "Retry": [{ "ErrorEquals": ["States.TaskFailed"], "MaxAttempts": 2 }],
  "Catch": [{ "ErrorEquals": ["States.ALL"], "Next": "RefundPayment" }],
  "Next": "NotifyCustomer"
}
```

## Interview Qs

### Standard or Express?

Standard: up to 1 year, exactly-once; for payments and approvals. Express: up to 5 minutes, at-least-once (async) or at-most-once (sync), priced per run and duration; for high-volume, idempotent event processing.

### How do you roll back a payment that spans services?

Model a saga. Each step has a Catch that jumps to compensating steps, such as a refund, in reverse order. Retries can repeat a step, so every step must be idempotent.
