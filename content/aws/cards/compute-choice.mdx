## What it is

This concept is the decision itself: given a workload, which AWS compute service should run it. The choices you have met are [EC2](card:ec2) (a whole virtual server), [Lambda](card:lambda) (a function per event), and [containers on ECS or EKS](card:containers-ecs-eks-fargate) (images run by an orchestrator, on Fargate or EC2). Each trades control for less operational work, and interviewers often ask you to pick one and defend it.

## Why it exists

There is no single best compute service; there is a best fit for a given workload. A webhook that fires occasionally, a REST API that runs all day, and a job that needs a GPU each want something different. Picking wrongly costs money or latency: Lambda for a constantly busy API means endless cold starts, while EC2 for a tiny webhook means paying for an idle server. Knowing how to choose, and saying why, is the real interview skill.

## How it works

<Compare id="ec2-vs-lambda-vs-fargate" />

Work through four questions about the workload, in order:

1. How long does one run take? Over 15 minutes rules out Lambda.
2. How does traffic arrive? Rare or spiky events favour Lambda; steady load favours an always-on container.
3. How much of the machine must you control? Full OS control or special hardware points to EC2.
4. What does the team know? A Kubernetes team may choose EKS; otherwise ECS on Fargate is simpler.

Then match: short events to Lambda, a steady service to ECS on Fargate, a Kubernetes shop to EKS, deep control to EC2.

So you start from the workload, not from a favourite service.

## Example

A good default answer for "deploy this Spring Boot backend on AWS":

- Build a Docker image and push it to ECR.
- Run it as an ECS service on Fargate across two AZs, behind an ALB with health checks.
- Scale the task count on CPU or requests per target.

What to notice:

- This fits most steady web backends: no servers to patch, it spans AZs, and it scales with load.
- It is one good answer, not the only one; name the alternatives (Lambda for events, EC2 for control) to show you chose deliberately.
- If you want the least setup, ECS Express Mode takes an image and two IAM roles and builds the Fargate service, ALB, HTTPS and auto scaling for you.

## Rules and defaults

- **ECS service auto scaling:** scales the task count on a CloudWatch metric, the container equivalent of an Auto Scaling group.
- **ECS Express Mode:** give it a container image, a task execution role and an infrastructure role; it provisions a Fargate service, an ALB with HTTPS, auto scaling and a URL.
- **Elastic Beanstalk:** deploys your app onto EC2 or EKS and manages the load balancer and scaling for you; good when you want a platform to handle the plumbing.
- **App Runner:** closed to new customers; AWS points new users to ECS Express Mode.

## Not to be confused with

Fargate is not a fourth kind of compute to weigh against ECS and EKS; it is how you run them without servers. The real orchestrator choice is ECS versus EKS, and the capacity choice is Fargate versus EC2. Rule: decide the orchestrator first (ECS or EKS), then the capacity (Fargate or your EC2).

## Common mistakes

- **"I will put everything on Lambda to be fully serverless."** A long job hits the 15-minute limit, and a busy API pays cold starts and can cost more than a warm container. Match each workload to its fit instead of forcing one service everywhere.

## Interview Qs

### How would you deploy a Spring Boot backend on AWS?

Build a Docker image, push it to ECR, and run it as an ECS service on Fargate across two AZs behind an ALB with health checks, scaling the task count on CPU or requests per target. It needs no server management and spans AZs. I would add that Lambda suits events and EC2 suits deep control, so this is a deliberate default, not the only option.

### When would you choose Lambda over containers?

For short, event-driven or spiky work: a payment webhook, a file-upload trigger, a nightly job under 15 minutes. Lambda scales to zero when idle and needs no server. A steady API with many endpoints and constant traffic usually fits a container service better, because it stays warm and avoids repeated cold starts.

### When is EC2 still the right choice?

When you need control of the operating system, special instance types such as GPUs, or software that must be installed and tuned on the host itself. Containers and Lambda deliberately hide the host, so when you specifically need the host, EC2 is the fit.
