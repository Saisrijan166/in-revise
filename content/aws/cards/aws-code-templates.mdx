## What it is

This concept is a small set of code patterns for calling AWS from Java in an interview coding round. The idea behind all of them is one shape: build the service client, build a request object, call one method with that request. S3, SQS, DynamoDB and the rest all follow it, so you do not memorise thousands of methods, you learn the shape and the one or two fields each service needs. RDS is the exception that proves the point: it has no data-access SDK call at all.

## Why it exists

"Upload a file to S3" or "send a message to SQS" are common whiteboard questions, and candidates freeze trying to recall exact method names. The SDK has thousands of methods, but they are built on the same builder-then-call pattern, so once you see it, you can write any of them. Knowing that RDS data is plain JDBC, not an SDK call, is a distinction interviewers specifically listen for.

## How it works

The patterns below are the common ones. The rest live with the service that owns them, so each is written once:

| Task | Template |
|---|---|
| Log in to RDS with no password | [IAM database authentication](term:iam-database-authentication): the SDK or the JDBC wrapper makes a token |
| Share a private file | [pre-signed URL](card:s3) |
| Write only if absent | [conditional putItem](card:dynamodb) |
| Encrypt with your key | [SSE-KMS upload](card:kms-and-encryption) |
| Run on a queue message | [Lambda handler](card:lambda) |
| Timeouts and credentials | [client setup](card:aws-sdk-for-java) |

## Example

The same shape, three times: S3 put and get, SQS send-receive-delete, then the shorter Spring Cloud AWS way, and RDS as plain configuration.

```java
S3Client s3 = S3Client.builder().region(Region.AP_SOUTH_1).build();     // 1. client, once

PutObjectRequest put = PutObjectRequest.builder()                       // 2. request
        .bucket("payment-receipts").key("receipts/pay_123.txt").build();
s3.putObject(put, RequestBody.fromString("Paid INR 500 for pay_123"));  // 3. call

GetObjectRequest get = GetObjectRequest.builder()
        .bucket("payment-receipts").key("receipts/pay_123.txt").build();
System.out.println(s3.getObjectAsBytes(get).asUtf8String());
```

```text output
Paid INR 500 for pay_123
```

```java
SqsClient sqs = SqsClient.builder().region(Region.AP_SOUTH_1).build();
String url = sqs.getQueueUrl(b -> b.queueName("receipt-jobs")).queueUrl();

sqs.sendMessage(b -> b.queueUrl(url).messageBody("pay_123"));          // producer

ReceiveMessageRequest receive = ReceiveMessageRequest.builder().queueUrl(url)
        .waitTimeSeconds(20).maxNumberOfMessages(10).build();         // long polling
for (Message m : sqs.receiveMessage(receive).messages()) {
    System.out.println("Making receipt for " + m.body());             // keep it idempotent
    sqs.deleteMessage(b -> b.queueUrl(url).receiptHandle(m.receiptHandle()));
}
```

```text output
Making receipt for pay_123
```

```java
@Service
class ReceiptService {
    private final S3Template s3;
    private final SqsTemplate sqs;
    ReceiptService(S3Template s3, SqsTemplate sqs) { this.s3 = s3; this.sqs = sqs; }

    void save(String paymentId, InputStream pdf) {
        s3.upload("payment-receipts", "receipts/" + paymentId + ".pdf", pdf);
        sqs.send("receipt-jobs", paymentId);                  // queue name or URL
    }
    @SqsListener("receipt-jobs")                              // deleted only on success
    void onJob(String paymentId) { /* make the receipt */ }
}
```

```properties
# RDS is plain PostgreSQL: the normal driver, pointed at the RDS endpoint
spring.datasource.url=jdbc:postgresql://payments-db.abc123.ap-south-1.rds.amazonaws.com:5432/payments
# with spring-cloud-aws-starter-secrets-manager, the secret's JSON keys become properties
spring.config.import=aws-secretsmanager:/payments/db
spring.datasource.username=${username}
spring.datasource.password=${password}
```

What to notice:

- Every SDK block is the same three steps: `builder()` the client, `builder()` the request, call the method. The only differences are the field names (`bucket`/`key` for S3, `queueUrl`/`messageBody` for SQS).
- For SQS you must fetch the queue URL first, and you delete a message with the receipt handle from this receive, not the message id; deleting only after processing is what makes delivery at-least-once.
- The Spring block does the same work with far less code, and `@SqsListener` deletes the message only when `onJob` returns normally (ON_SUCCESS).
- The RDS block has no SDK call: it is ordinary JDBC configuration, with the password loaded from Secrets Manager rather than hardcoded.

## Rules and defaults

- **Call shape:** `ServiceClient.builder()` then `XxxRequest.builder()` then `client.xxx(request)`, for every service.
- **SQS deletion:** a received message is hidden for the visibility timeout; it is removed only when you call `deleteMessage` with its receipt handle after successful processing.
- **@SqsListener acknowledgement:** `ON_SUCCESS` by default, so a thrown exception leaves the message to reappear and be retried (Spring Cloud AWS, at the time of writing).
- **RDS data:** use the JDBC driver and JPA; never reach for the RDS SDK client to read or write rows.
- **No hardcoded secrets:** load the DB password from Secrets Manager via `spring.config.import`, or use IAM database authentication for no password at all.

## Interview Qs

### How do you upload a file to S3 from Spring Boot?

Inject one shared `S3Client`, build a `PutObjectRequest` with the bucket and key, and call `putObject` with a `RequestBody`; or inject `S3Template` and call `upload`. No keys in code: the default credentials chain finds the role. The same three-step shape, client then request then call, covers any S3 operation.

### Do you need the AWS SDK to use RDS from Java?

No, not for data. The application talks to the database over JDBC and JPA like any PostgreSQL or MySQL, pointed at the RDS endpoint. The RDS SDK only manages the instance itself, creating it, taking snapshots, failing over, or fetching its secret or IAM auth token. Mixing these up is a common interview slip.

### When does @SqsListener delete a message?

Its default acknowledgement mode is ON_SUCCESS: after the method returns without throwing, the message is acknowledged, which in SQS means deleted. If the method throws, the message is not deleted; it reappears after the visibility timeout for another attempt. That is why the handler must be idempotent.
