## What it is

AWS STS (Security Token Service) is the AWS service that issues temporary credentials when someone assumes an [IAM role](card:iam-basics). Temporary credentials are three values, an access key ID, a secret access key and a session token, plus an expiry time. They sign calls like normal keys until they expire. On AWS compute, AWS assumes the role for you, hands the keys to your code and replaces them before they run out.

## Why it exists

The payment service must upload receipts to S3. With an IAM user's access keys, you would put permanent keys in a config file or an image. From there they leak through Git, logs or a copied container, and keep working until someone notices. With a role nothing secret is stored: the keys come from STS, last about an hour and are renewed automatically, so a leaked copy soon stops working.

1. You create the role with two policies: a trust policy that says who may assume it (for ECS tasks, the service `ecs-tasks.amazonaws.com`) and a permissions policy that says what it may do.
2. You attach the role to the compute: an instance profile on [EC2](card:ec2), the task role on [ECS](card:containers-ecs-eks-fargate), the execution role on Lambda, or a role linked to a Kubernetes service account on EKS.
3. AWS assumes the role through STS and delivers the keys to the code: on EC2 through the instance metadata service, on ECS through a credentials endpoint inside the task.
4. The AWS SDK finds the keys through its default credentials chain, signs each call with them, and fetches new keys before the old ones expire.
5. Each call is then checked against the role's permissions, as in [policy evaluation](card:iam-policy-evaluation).

## Example

The payment service on ECS uploads a receipt. The code holds no keys:

```java
S3Client s3 = S3Client.builder()
        .region(Region.AP_SOUTH_1)   // no credentials here: the SDK finds the task role
        .build();                    // build once, reuse for every upload

s3.putObject(PutObjectRequest.builder()
        .bucket("payments-receipts")
        .key("receipts/pay_123.pdf")
        .contentType("application/pdf")
        .build(),
    RequestBody.fromBytes(pdfBytes));
```

What to notice:

- The builder sets only the Region. The default chain finds the task role's keys from the ECS credentials endpoint; you will see the whole chain in [the AWS SDK for Java](card:aws-sdk-for-java).
- The same code runs unchanged on EC2 or Lambda; only the source of the keys changes.
- The upload works only if the task role allows `s3:PutObject` on `payments-receipts/receipts/*`. Remove the task role on Fargate and the SDK finds no credentials at all.

## Rules and defaults

- **Session length:** AssumeRole lasts 3,600 seconds (1 hour) by default. You can ask for 15 minutes up to the role's maximum session duration, which is set between 1 and 12 hours (AWS STS, at the time of writing, 21-10-2026).
- **Role chaining:** a session gained by assuming a role from another role session lasts at most 1 hour.
- **Renewal on EC2:** new credentials appear in instance metadata at least five minutes before the old ones expire; the SDK switches by itself.
- **ECS:** when a task role is set, the SDK in the container uses only its credentials, never the instance's.
- **EKS:** Pod Identity links a role to a service account without an OIDC provider, but not for pods on Fargate; IRSA needs an OIDC provider per cluster.
- **Session policy:** a caller may pass one to AssumeRole; the session then gets only what both the role and the session policy allow.

## Not to be confused with

The ECS task role holds the permissions for your app's own AWS calls, such as writing receipts to S3. The task execution role is used by ECS itself to pull the image, send logs and fetch secrets before your code starts. Rule: my code calls AWS → task role; ECS cannot start the task → execution role.

## Interview Qs

### How does an app on EC2 get AWS credentials without access keys?

Attach an instance profile that holds a role. The SDK reads temporary keys for that role from the instance metadata service, and AWS rotates them, making new ones available before the old ones expire. No keys sit on disk or in code.

### How do you let a service in account A read a bucket in account B?

Either a role in B trusts account A, A's service assumes it and reads the bucket as that role, or B's bucket policy names A's role directly. In both cases A's own policy must also allow the call (`sts:AssumeRole` or `s3:GetObject`), because cross-account access needs both sides.

### Why are temporary credentials safer than access keys?

They expire, usually after an hour, so a leaked copy soon stops working. AWS renews them automatically, so nobody has to rotate or store them. Each session is logged in CloudTrail under the role, which shows who used it.
