## What it is

An AWS Region is a separate geographic area where AWS runs its services, such as `ap-south-1` in Mumbai. Each Region holds at least three Availability Zones (AZs). An AZ is one or more data centres with their own power and network, in buildings far enough apart that a fire or flood hits only one, yet linked to the other AZs by fast private fibre. You choose a Region for everything you create; some resources, such as a server, also sit in one AZ that you choose.

## Why it exists

Any single data centre can lose power, its network or the building itself. If the whole payment service runs in one, one incident stops every payment. AZs give you several places that fail independently but sit close together, so a database can copy each write to a second AZ before it confirms the write (synchronous replication) without slowing down much. Regions go further: separate copies of AWS in different parts of the world, for users nearby, local data laws and disaster recovery.

1. You choose one Region for the payment service, close to its users and allowed by data rules: `ap-south-1`.
2. You run app instances in two AZs, and a [load balancer](card:elastic-load-balancing), placed in both AZs, that sends each request only to an instance passing its health check.
3. The database runs as a primary in one AZ with a standby in another, and every write is copied to the standby before it is confirmed. You will see this in [RDS](card:rds).
4. AZ `ap-south-1a` loses power. The load balancer stops sending requests there, and the instance in `ap-south-1b` takes the load.
5. The database fails over: the standby becomes the primary, typically within 60 to 120 seconds on RDS.

So the key is: no layer may live in only one AZ.

## Example

In the AWS SDK for Java, each client is built for one Region, and every call it makes goes there.

```java
Region mumbai = Region.AP_SOUTH_1;                       // where the payment service runs
System.out.println(mumbai.id());
System.out.println(mumbai.metadata().description());

// Every call made with this client goes to ap-south-1 and nowhere else.
S3Client s3 = S3Client.builder().region(mumbai).build();

System.out.println(Region.AP_SOUTH_2.metadata().description()); // another Region
```

```text output
ap-south-1
Asia Pacific (Mumbai)
Asia Pacific (Hyderabad)
```

What to notice:

- `ap-south-1` is the Region code AWS uses everywhere: in the console, the command line and the SDK.
- A receipt bucket created through this client lives in Mumbai. Hyderabad (`ap-south-2`) is a separate Region and gets no copy unless you configure one.
- Building the client makes no call to AWS; the Region only decides where later calls go. Point it at the wrong Region and calls fail, because the resources you ask for live in another Region.

## Rules and defaults

- **At least three AZs per Region:** all within 100 km of each other (AWS Global Infrastructure, at the time of writing).
- **No automatic copies between Regions:** a regional resource stays in its Region; any copy in another Region is something you configure.
- **Opt-in Regions:** a Region launched after 20-03-2019, such as Hyderabad, is disabled until you enable it for your account; Mumbai is enabled by default.
- **AZ names and AZ IDs:** in accounts created before November 2025, in the oldest Regions, a name such as `us-east-1a` can point to a different physical AZ in each account. The AZ ID, such as `use1-az1`, is the same place in every account.
- **Beyond Regions:** edge locations serve cached content close to users, which you will see in [CloudFront](card:cloudfront); Local Zones put compute near large cities.

## Not to be confused with

Multi-AZ spreads one deployment over AZs inside one Region and protects you against a data centre failing; copies between AZs can be synchronous. Multi-Region runs a second copy in another Region and protects you against a whole Region failing; a database copy there, such as an RDS cross-Region read replica, is asynchronous and can lag. That is [disaster recovery](card:disaster-recovery). Rule: Multi-AZ for high availability; another Region for disaster recovery.

On RDS, AWS's managed database service, a Multi-AZ standby is a hidden copy that only takes over on failure, while a read replica is a readable copy that takes read traffic. Rule: standby = availability; read replica = more reads.

## Interview Qs

### What is the difference between a Region and an Availability Zone?

A Region is a geographic area, such as Mumbai (`ap-south-1`), isolated from other Regions. An AZ is one or more data centres inside a Region with separate power and networking. AZs fail independently but are close enough for low-latency synchronous replication, so you spread one application over AZs and use other Regions for disaster recovery.

### How do you choose a Region?

Compliance first: data residency rules can decide it on their own. Then latency to most users, price, which differs by Region, and whether the services and features you need exist there. Newer services often reach the larger Regions first.

### The payment API must survive the loss of one AZ. What do you check?

That no part lives in only one AZ: instances in at least two AZs with enough capacity if one is lost, the load balancer in those AZs, the database Multi-AZ, no session state kept on one instance, and the [network paths](card:internet-and-nat-gateways) out of each AZ.
