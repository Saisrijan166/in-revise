## What it is

Infrastructure as code (IaC) means you describe your cloud resources, the networks, servers, databases and permissions, in a file, and a tool creates them for you. With AWS CloudFormation, that file is a template, in YAML or JSON. When CloudFormation provisions the resources a template describes, the set of live resources it manages is called a stack. The CDK (Cloud Development Kit) lets you write the same thing in a real programming language like Java, which it then turns into a CloudFormation template.

## Why it exists

Building a system by clicking through the console cannot be reviewed, repeated, or rebuilt after a disaster; only the person who clicked knows what they did. Code can. A template is checked into git, reviewed in a pull request, and applied again to make an identical copy in another account or Region. So a new environment is one command, every environment matches, and recovery after a Region loss is replaying the templates rather than remembering hundreds of console clicks.

## How it works

<Compare id="cloudformation-vs-cdk-vs-terraform" />

1. You write a template describing the resources you want, or you write CDK code and run `cdk synth`, which generates the template.
2. You give the template to CloudFormation to create a stack; CloudFormation calls the underlying AWS APIs in order and tracks every resource it made.
3. To change the stack, you edit the template and create a change set, which lists what will be added, changed, or replaced, without touching anything yet.
4. You review the change set (especially any resource it would replace, like a database) and then execute it; CloudFormation applies only the differences.
5. If a create or update fails partway, CloudFormation rolls back: a failed create deletes what it made, and a failed update returns the stack to its last working state.

So the key is: you never issue the AWS calls yourself; you describe the end state, and CloudFormation works out and applies the steps.

## Example

This CDK stack, in Java, defines an S3 bucket for payment receipts with safe defaults; `cdk synth` turns it into a CloudFormation template.

```java
public class ReceiptsStack extends Stack {
    public ReceiptsStack(Construct scope, String id) {
        super(scope, id);
        Bucket.Builder.create(this, "Receipts")        // an L2 construct
            .versioned(true)                            // keep old versions
            .encryption(BucketEncryption.S3_MANAGED)    // encrypt at rest
            .blockPublicAccess(BlockPublicAccess.BLOCK_ALL)
            .enforceSSL(true)                           // reject plaintext access
            .removalPolicy(RemovalPolicy.RETAIN)        // keep receipts if the stack is deleted
            .build();
    }
}
```

What to notice:

- `Bucket.Builder` is an [L2 construct](card:cdk-constructs): a few lines of Java expand into a full `AWS::S3::Bucket` resource plus its policy in the generated template, with secure defaults filled in.
- `removalPolicy(RETAIN)` tells CloudFormation to keep the bucket if the stack is ever deleted; without it the default is to delete the bucket, which would throw away the receipts.
- You deploy this with `cdk deploy`, which synthesises the template and hands it to CloudFormation; the stack, change sets and rollback all work exactly as if you had written the YAML by hand.

## Rules and defaults

- **Deletion policy:** by default CloudFormation deletes a resource when its stack is deleted; `Retain` keeps it, `Snapshot` snapshots first. Exception: RDS DB instances and clusters default to `Snapshot` (CloudFormation, at the time of writing).
- **Update behaviour:** a property change is one of no interruption, some interruption, or replacement (new physical id, old resource deleted); the resource reference docs state which, and change sets show it.
- **Drift detection:** finds resources changed outside CloudFormation but does not correct them; you reconcile by updating the template or re-importing.
- **CDK bootstrap:** run `cdk bootstrap` once per account and Region to create the resources (an S3 bucket, an ECR repo, IAM roles) the CDK needs to deploy.
- **CDK languages:** TypeScript, JavaScript, Python, Java, C# and Go (AWS CDK v2, at the time of writing).

## Not to be confused with

A [change set](card:cfn-change-set) is a preview of an update you have not run yet. [Drift](card:cfn-drift-detection) is a difference that already exists because someone changed a resource outside CloudFormation. Rule: change set = what my next deploy will do; drift = what someone already did behind CloudFormation's back.

## Common mistakes

- **"IaC guarantees my live resources match the template."** Only if nobody edits them by hand. Console changes create drift, which CloudFormation does not notice until you run drift detection.
- **Ignoring a replacement in a change set.** Renaming or changing certain properties recreates the resource. For a stateful resource like a database, that means data loss unless you snapshot and plan the cutover first.

## Interview Qs

### What is infrastructure as code, and why use it?

Defining your servers, networks, databases and permissions in versioned files that a tool applies, instead of clicking in the console. You get code review on infrastructure changes, identical environments every time, fast rebuilds after a failure, and a clear history of what changed. On AWS the tool is CloudFormation (or CDK, which generates CloudFormation).

### Why create a change set before updating a stack?

It previews the update without applying it, including any resource CloudFormation would delete or replace, such as the payments database. That lets you catch a dangerous change, snapshot data, and plan a cutover before anything happens. Nothing changes until you execute the change set.

### What is drift, and can CloudFormation fix it automatically?

Drift is when a resource's live configuration no longer matches the template, usually because someone changed it in the console. Drift detection reports which resources and properties differ, but it does not fix them. You reconcile by updating the template to the intended state and deploying, so code and reality agree again.
