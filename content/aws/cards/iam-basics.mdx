## What it is

IAM (Identity and Access Management) is the AWS service that decides who may call which AWS API, on which resource. Everything you do in AWS, from uploading a receipt to S3 to starting a server, is an API call, and IAM checks each one. An identity is who is calling: a person, or an app such as the payment service. A policy is a JSON document attached to an identity that lists what it may do.

## Why it exists

Without IAM, everyone would share one all-powerful login: any person or app holding it could delete the database or read every receipt, and one leaked password would expose the whole account. IAM gives each person and each app its own identity with only the permissions its task needs. A leaked key or a buggy service can then damage only that small part.

## How it works

1. A new account has one root user: the email login that created it. It has full power, so you protect it with MFA and use it only for the few tasks that need it.
2. You create identities for everything else. People sign in through IAM Identity Center or another identity provider and get temporary access. Apps get an IAM role. An IAM user, with a long-term password or access keys, is kept for cases where a role cannot work.
3. You attach policies to those identities. Each statement has `Effect` (Allow or Deny), `Action` (such as `s3:PutObject`), `Resource` (an ARN, the unique name of a resource) and an optional `Condition`.
4. When a call arrives, AWS checks its signature to learn who is calling, then evaluates the policies to decide Allow or Deny. The exact order is the next concept, [policy evaluation](card:iam-policy-evaluation).

So the key is: identities say **who**, policies say **what**.

## Example

The payment service needs to save receipt PDFs in S3 and nothing else. This least-privilege policy goes on its role:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::payments-receipts/receipts/*"
  }]
}
```

What to notice:

- `"Version": "2012-10-17"` is the version of the policy language, not a date you update.
- The only action is `s3:PutObject`, so the service can write receipts but cannot read, list or delete them.
- The resource ends in `receipts/*`, so it covers only objects under that prefix of that bucket. Change it to `"*"` and the service could write into every bucket in the account.
- The policy is attached to a role, not to a user with keys; how an app uses a role is in [temporary credentials](card:sts-and-temporary-credentials).

## Rules and defaults

- **Nothing by default:** a new IAM user or role has no permissions. A request that no policy allows is denied (the root user is the one exception).
- **Root user:** some tasks need it, such as restoring permissions when the only admin locked themselves out, or closing a standalone account. Otherwise do not use it.
- **Three kinds of policy:** AWS managed policies are written and updated by AWS; customer managed policies are yours and can be attached to many identities; an inline policy belongs to one identity and is deleted with it. Start with AWS managed policies, then tighten with your own.
- **User groups:** a group gives the same policies to many users. It holds only users, cannot be nested, and cannot be named as a `Principal` in a policy.
- **IAM is global:** users, roles and policies are not tied to one Region.

## Not to be confused with

An IAM user is a fixed identity for one person or app, with a password or access keys that last until someone changes them. An IAM role has no long-term credentials: a trusted user, service or app assumes it and receives keys that expire. Rule: a user carries permanent keys that can leak; a role lends keys that expire.

IAM also differs from [security groups](card:security-groups-and-nacls): IAM decides AWS API calls, security groups decide which network packets reach a server.

## Interview Qs

### What is the difference between an IAM user, group and role?

A user is one identity with long-term credentials, a password or access keys. A group is a set of users that share the same policies; it is not an identity itself. A role has no long-term credentials: trusted users, services or federated people assume it and get temporary ones. AWS recommends roles for both apps and people.

### How do you apply least privilege in IAM?

Allow only the actions and resources a task needs, and narrow further with conditions. Start from AWS managed policies, then replace them with your own tighter policies. IAM Access Analyzer can generate a policy from the actions a role really used, as recorded in CloudTrail, and remove unused permissions after a review.

### Why should you not use the root user for daily work?

The root user has complete access to the account, and an implicit deny does not stop it the way it stops users and roles. If its password or keys leak, everything is exposed. Protect it with MFA, do not create access keys for it, and use it only for the tasks that require it.
