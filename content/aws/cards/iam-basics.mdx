## Why it exists

Every AWS API call is signed and checked. IAM lets you state exactly who may do what, so one leaked key or buggy service cannot touch everything.

## How it works

<Compare id="iam-user-vs-role" />

- Each policy statement has `Effect`, `Action`, `Resource` and an optional `Condition`; ARNs name the resources.
- Start from AWS managed policies, then tighten with customer managed ones; an inline policy belongs to one identity.
- When several policies meet, see [policy evaluation](card:iam-policy-evaluation); for assuming roles, see [STS](card:sts-and-temporary-credentials).

## Example

Least privilege for the receipt worker: it may only write PDFs under one prefix.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::payments-receipts/receipts/*"
  }]
}
```

## Interview Qs

### What is the difference between an IAM user, group and role?

A user is one person or app with long-term credentials. A group is a set of users that share policies. A role has no long-term credentials: trusted users, services or federated people assume it and get temporary ones.

### How do you apply least privilege in IAM?

Allow only the actions and resources a task needs, narrow further with conditions, and review it. IAM Access Analyzer can generate a policy from the actions a role really used, as logged in CloudTrail.

### Can you add a role to an IAM group?

No. A group holds only users, cannot be nested, and cannot be named as a Principal. Attach the policy to the role itself.
