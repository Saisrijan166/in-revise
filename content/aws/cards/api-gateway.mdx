## What it is

Amazon API Gateway is a managed service that sits in front of your API and handles the work every API needs before and after your code runs: checking who the caller is, limiting how fast they can call, picking the right stage, and forwarding the request to a backend. The backend can be a Lambda function, a public HTTP service, or a private load balancer in your [VPC](card:vpc-and-subnets). Because the gateway does this, a Lambda-based API needs no web server of its own.

## Why it exists

Every API has to authenticate callers, rate-limit them, version itself, and route requests. Writing and running that yourself means a server you have to scale and patch. API Gateway runs all of it as a managed service that scales on its own and charges per request, so you add authentication, throttling and routing by configuration, and you pay nothing while the API is idle.

## How it works

<Compare id="rest-api-vs-http-api" />

1. A request arrives at the API's URL and hits the stage you deployed, such as `prod`.
2. The authorizer runs first: it checks the token or signature and rejects the call if it is not allowed.
3. Throttling is applied: if the request rate is over the limit, the gateway returns `429` instead of calling the backend.
4. The integration forwards the request; a Lambda proxy integration passes the whole request to the function, which returns the response.

So the gateway does auth, throttling and routing in order, and your code only sees requests that passed.

## Example

This is the path of one payment call through a REST API with a Lambda proxy integration.

```text
POST /prod/payments   {"amount": 500, "currency": "INR", "method": "UPI"}
  1. authorizer checks the bearer token      -> fail: 401 Unauthorized
  2. throttling: over the account limit?      -> yes: 429 Too Many Requests
  3. Lambda proxy integration passes the whole request to the handler
<- 201 Created   {"paymentId": "pay_123", "status": "PENDING"}
```

What to notice:

- The authorizer and throttling run before the integration, so a bad token or a flood never reaches your Lambda function.
- A `429` here is throttling, not a client error in your code; the fix is retry-with-backoff or a higher quota.
- With a Lambda proxy integration, the function receives the entire request (headers, path, body) and must return a shape with `statusCode`, `headers` and `body`.

## Rules and defaults

- **Throttle quota:** 10,000 requests per second per account per Region across all API types, with a 5,000-request burst, by default; some Regions start lower (Amazon API Gateway).
- **Integration timeout:** REST APIs default to 29 s (raisable above 29 s on Regional and private APIs, which may lower your throttle quota); HTTP APIs are capped at 30 s and cannot be raised.
- **Payload size:** 10 MB maximum for both REST and HTTP APIs.
- **API keys are not authentication:** AWS advises against using API keys to control access; use IAM, a Lambda authorizer or Cognito, and keys only to identify clients for usage plans.
- **Throttling is best-effort:** do not rely on it to control cost or block access; use AWS Budgets and WAF for that.

## Not to be confused with

API Gateway publishes and protects APIs, with auth, throttling, keys and stages. An [Application Load Balancer](card:elastic-load-balancing) spreads steady HTTP traffic across targets and has no API-management features. Rule: Lambda or keyed partner APIs go behind API Gateway; busy container services sit behind an ALB; put API Gateway in front of a private ALB via a VPC link when you want both.

## Interview Qs

### When would you choose a REST API over an HTTP API?

Choose a REST API when you need API keys and usage plans, AWS WAF, response caching, request validation, or a private endpoint. Otherwise choose an HTTP API: it is cheaper and simpler, and it has built-in JWT authorizers.

### Clients are getting 429 errors. What does that mean and what do you do?

They are being throttled: the request rate passed the account-, stage-, method- or usage-plan limit. Retry with exponential backoff, request a higher quota, or reduce calls with caching. Throttling is best-effort, so do not rely on it for cost control.

### How do you handle a request whose backend takes minutes?

Do not keep the connection open past the integration timeout (29 or 30 s). Accept the request, put the work on a queue, and return `202 Accepted` with a URL the client can poll for the result. The slow work then runs asynchronously.
