## What it is

Amazon S3 (Simple Storage Service) is object storage: you store whole files, called objects, and read them back over HTTPS through an API. An object is the file's bytes plus metadata, such as its content type. Each object lives in a bucket, a container you create in one Region, and is found by its key, its full name inside that bucket. Unlike a disk, S3 is attached to no server: every app with permission calls the same API.

## Why it exists

The payment service must keep a PDF receipt for every payment. On a task's own disk, receipts vanish when the task is replaced, and two tasks see different files. Inside the database, large files bloat the tables and backups. S3 keeps files apart: every task reads the same bucket, storage grows with no size to plan, and AWS keeps copies across at least three AZs.

## How it works

1. The payment service calls PutObject with the bucket name, the key `receipts/2026/10/pay_123.pdf` and the PDF bytes. S3 stores the object across several AZs, encrypts it by default, and returns success.
2. The service writes that key into the payment row. The row stays the record of the payment; S3 only holds the file.
3. When the customer asks for the receipt, the service checks that the payment is theirs and creates a pre-signed URL for that key, valid for 10 minutes.
4. The customer's browser downloads the file straight from S3 with that URL. The bucket stays private, and the app never streams the bytes.

So the key is: S3 holds the bytes, the database holds the facts, and a key links them.

## Example

The payment service creates a 10-minute download link for one private receipt (AWS SDK for Java 2.x):

```java
try (S3Presigner presigner = S3Presigner.create()) {
    GetObjectRequest get = GetObjectRequest.builder()
            .bucket("payments-receipts")
            .key("receipts/2026/10/pay_123.pdf")
            .build();
    GetObjectPresignRequest request = GetObjectPresignRequest.builder()
            .signatureDuration(Duration.ofMinutes(10))      // the link expires in 10 minutes
            .getObjectRequest(get)
            .build();
    return presigner.presignGetObject(request).url().toString();
}
```

What to notice:

- The URL is signed with the credentials the SDK finds, on ECS the task role's. It can do only what that role may do: if the role cannot read the key, the link returns Access Denied.
- `signatureDuration` sets the lifetime. With temporary credentials, such as a task role's, the link also stops working when those credentials expire, even if that is earlier.
- Anyone who holds the URL can download the file until it expires, so keep it short and send it only to the owner.
- No setting in the code makes anything public: the bucket stays private, and only this one signed request is allowed.

## Rules and defaults

- **Versioning:** off by default. Once on, you can only suspend it, not remove it. A plain DELETE then adds a delete marker and the older versions stay.
- **Lifecycle rules:** after a number of days, a rule moves objects to a cheaper storage class or expires (deletes) them.
- **Event notifications:** S3 can tell SQS, SNS, Lambda or EventBridge when an object is created or deleted; you will meet these services in the integration topic.
- **Encryption:** since 05-01-2023 every new object is encrypted at rest with SSE-S3 by default; [KMS](card:kms-and-encryption) covers other options.
- **Large files:** a single PUT takes at most 5 GB. Multipart upload sends up to 10,000 parts in parallel (advised from 100 MB), and an object can reach 48.8 TiB (at the time of writing).
- **Pre-signed URL lifetime:** at most 7 days when signed with the SDK or CLI, and 12 hours from the console (at the time of writing).

## Not to be confused with

A bucket policy is attached to the bucket and says who may use it, for example another AWS account. An IAM policy is attached to a user or role and says what that identity may do, for example "the payment task role may write to `receipts/`". You will meet both in [IAM basics](card:iam-basics). Rule: IAM policy = what this caller may do; bucket policy = who may use this bucket.

## Common mistakes

- **"Making the bucket public is the easy way to share receipts."** Then anyone who guesses a key can read any receipt. Keep Block Public Access on, and share single files with pre-signed URLs or through [CloudFront](card:cloudfront).
- **"An upload that never finished costs nothing."** The parts of an unfinished multipart upload are stored and billed until you complete or abort it. Add a lifecycle rule that aborts incomplete multipart uploads.

## Interview Qs

### What are the S3 storage classes, and how do you choose one?

S3 Standard, the default, is for files read often. Intelligent-Tiering suits unknown access, moving objects between tiers by use. Standard-IA and One Zone-IA are for files read about monthly, with a retrieval fee and a 30-day minimum. The Glacier classes are archives. For receipts: Standard, then a lifecycle rule to a cheaper class.

### How do you upload a file larger than 5 GB?

With multipart upload: split the file into up to 10,000 parts, send them in parallel, then complete the upload so S3 joins them. If one part fails, you resend only that part. AWS advises it from 100 MB.

### Why not store receipts in the database as BLOBs?

Large files make rows, backups and replicas heavy, and every download passes through the app and database. In S3 the files sit apart, every task reads them, and customers download them directly through pre-signed URLs. The database keeps only the key.
