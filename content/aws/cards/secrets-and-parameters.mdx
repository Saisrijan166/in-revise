## What it is

AWS Secrets Manager is a managed store for secrets such as database passwords and API keys. It encrypts each secret with a [KMS key](card:kms-and-encryption), keeps its versions, and can rotate it on a schedule; rotation means replacing the password in both the secret and the database. Systems Manager Parameter Store is a simpler store for configuration values, such as endpoints and feature flags. The app reads both at runtime through its [IAM role](card:sts-and-temporary-credentials).

## Why it exists

The payment service needs the [RDS](card:rds) password. Written in `application.properties` or baked into the image, it is readable by anyone with the repo or the image, and it never changes, because changing it means a new build and a redeploy. Even a plain `environment` value in the ECS task definition is visible to anyone allowed to describe it. A managed store keeps the password out of all of these, lets IAM decide who may read it, and rotates it without code changes.

## How it works

  RDS[(RDS PostgreSQL)] -- "1. creates and rotates the password" --> SM[Secrets Manager]

  ECS -- "3. env var DB_PASSWORD" --> APP[Spring Boot]
  APP -- "4. JDBC with the password" --> RDS`}
/>

1. You let RDS manage the master password: it generates the password, stores it in Secrets Manager and rotates it, every seven days by default.
2. The secret is a JSON value with keys such as `username` and `password`, encrypted with a KMS key.
3. When a task starts, ECS reads the secret with the task execution role and puts the chosen JSON key into an environment variable in the container.
4. Spring Boot reads that variable into `spring.datasource.password` and connects to the database.
5. After a rotation, running tasks still hold the old value; only a task started later gets the new one.

## Example

The payment service's container definition asks ECS for one key of the secret, and Spring Boot reads it:

```json
"secrets": [{
  "name": "DB_PASSWORD",
  "valueFrom": "arn:aws:secretsmanager:ap-south-1:111122223333:secret:payments/db-AbCdEf:password::"
}]
```

```properties
spring.datasource.url=jdbc:postgresql://${DB_HOST}:5432/payments
spring.datasource.password=${DB_PASSWORD}
```

What to notice:

- `:password::` at the end of the ARN picks the `password` key from the secret's JSON; the two empty fields mean "the current version" (label `AWSCURRENT`). Without a key, the whole JSON lands in the variable.
- ECS fetches the value with the task execution role, which needs `secretsmanager:GetSecretValue` on this secret, plus `kms:Decrypt` if a customer managed key encrypts it. The app's task role needs nothing for this.
- `${DB_PASSWORD}` is resolved from the environment, so the password never appears in the repo or the image.
- Loading the secret directly with Spring Cloud AWS instead is shown in [AWS Code Templates](card:aws-code-templates).

## Rules and defaults

- **Size:** a secret value can be up to 65,536 bytes (64 KB). A Parameter Store value can be 4 KB in the standard tier and 8 KB in the advanced tier.
- **Rotation:** RDS, Aurora, Redshift and DocumentDB offer managed rotation for their master users, with no Lambda function. Other secrets rotate through a Lambda function. A schedule can be as frequent as every four hours.
- **Versions:** the current value has the label `AWSCURRENT`; after a rotation the old one becomes `AWSPREVIOUS`.
- **ECS injection:** happens only at container start. To pick up a rotated value, start new tasks, for example with a forced new deployment.
- **Caching:** the AWS Java caching client keeps secrets in memory and refreshes each one every hour by default.
- **Parameter Store tiers:** standard holds up to 10,000 parameters at no extra charge; advanced holds up to 100,000, is paid, and adds parameter policies and sharing.
- **Credentials:** Parameter Store has no built-in rotation, and AWS points credentials to Secrets Manager.

## Not to be confused with

Secrets Manager is built for credentials: it rotates them, keeps versions and can share them with other accounts. Parameter Store is built for configuration, with a free standard tier; a SecureString parameter is encrypted but never rotated. Rule: a password that should change → Secrets Manager; a setting → Parameter Store.

## Interview Qs

### Secrets Manager or Parameter Store for a database password?

Secrets Manager. It rotates the password on a schedule, with managed rotation for RDS and Aurora, and keeps versions so a rotation can be traced. A SecureString parameter can hold a password, but nothing rotates it, so keep Parameter Store for configuration.

### How does a Spring Boot app on ECS get its database password?

Either the task definition's `secrets` field injects it as an environment variable at container start, or Spring Cloud AWS loads it at startup with `spring.config.import=aws-secretsmanager:...`. In the first case the execution role needs `secretsmanager:GetSecretValue`; in the second, the task role does.

### Why not just put the password in the task definition's environment block?

Plain `environment` values are stored in the task definition as clear text, so every user or role allowed to describe it can read them, and they also show up in container tools such as `docker inspect`. The `secrets` field keeps only the secret's ARN in the task definition.
