## Why it exists

A public payment API attracts injection attempts, bots and floods. Blocking them at the edge keeps that traffic away from the app, and TLS needs certificates that never silently expire.

## How it works

| Service | Works at | Stops or gives | Price |
|---|---|---|---|
| AWS WAF | HTTP(S) requests | Injection, bad inputs, per-IP floods | Per web ACL, rule and request |
| Shield Standard | Network and transport layers | Common DDoS attacks | No extra charge, automatic |
| Shield Advanced | Those, plus the application layer | Larger DDoS, cost protection | Paid, 1-year commitment |
| ACM | TLS | Public certificates, renewed for you | Free on integrated services |

- The ALB or CloudFront ends TLS with the ACM certificate: see [load balancers](card:elastic-load-balancing) and [CloudFront](card:cloudfront).
- On your own servers, such as EC2, use ACM's ACME support or an exportable certificate ($7 per domain, as of 20-10-2026).

## Interview Qs

### What is the difference between AWS WAF and AWS Shield?

WAF checks HTTP(S) requests against your rules: SQL injection, bad inputs, per-IP rate limits. Shield fights DDoS: Standard covers common network and transport attacks for free; Advanced adds application-layer mitigation, DDoS cost protection and the Shield Response Team.

### How do you stop one client from flooding the payment API?

Add a rate-based rule to an AWS WAF web ACL on the ALB, CloudFront or API Gateway stage. It counts each IP's requests over a time window and blocks those above the limit. [API Gateway throttling](card:api-gateway) adds another limit.
