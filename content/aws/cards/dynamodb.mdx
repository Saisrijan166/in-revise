## What it is

Amazon DynamoDB is a managed NoSQL database. It stores items, which are like rows but can each hold any attributes, grouped into tables. Every item is found by its primary key: either a partition key alone, or a partition key plus a sort key. The partition key's value is hashed to decide which partition, a piece of the table's storage, holds the item. Unlike [RDS](card:rds), there is no join and no general WHERE: you read by key, so you shape the keys around the queries you need.

## Why it exists

Some data is read by key at a scale and speed that a single relational server struggles with: a payment's status by its id, millions of times a second, with steady low latency. A relational database would need bigger and bigger instances. DynamoDB spreads items across many partitions by hashing the partition key, so it stays fast as traffic grows. The cost is that you must know your access patterns up front, because only key-based reads are fast.

## How it works

The table below is a payments table keyed on `merchantId` (partition key) and `paymentId` (sort key). Items with the same merchant sit together, ordered by payment id.

| merchantId (partition key) | paymentId (sort key) | amountInr | status |
|---|---|---|---|
| m-42 | p-1001 | 500 | SUCCEEDED |
| m-42 | p-1002 | 500 | FAILED |
| m-77 | p-1003 | 500 | SUCCEEDED |

1. A write hashes `merchantId` to choose a partition and stores the item there, ordered by `paymentId`.
2. A Query gives one `merchantId` and optionally a `paymentId` range: "all payments of m-42", read straight from one partition.
3. A query the table key cannot serve, such as "all FAILED payments", needs a global secondary index (GSI) whose key is `status`.
4. By default a read is eventually consistent, so it may miss the newest write by a fraction of a second; you can ask for a strongly consistent read on the table.

So the key is: pick the partition key for even spread, and add a GSI for every query the main key cannot answer.

## Example

To store a payment only once, even if the request is retried, write it with a condition that the key does not already exist (AWS SDK for Java 2.x):

```java
PutItemRequest put = PutItemRequest.builder()
        .tableName("payments")
        .item(Map.of(
                "merchantId", AttributeValue.fromS("m-42"),
                "paymentId", AttributeValue.fromS(paymentId),
                "amountInr", AttributeValue.fromN("500")))
        .conditionExpression("attribute_not_exists(paymentId)")  // only if no such item yet
        .build();
try {
    dynamo.putItem(put);
} catch (ConditionalCheckFailedException e) {
    // the item already exists: this was a retry, so do nothing
}
```

What to notice:

- `attribute_not_exists(paymentId)` makes the write happen only when no item with that key exists. The check and the write are one atomic step.
- A retry of the same payment hits the condition and throws `ConditionalCheckFailedException`, so the payment is never stored twice. This is how you get idempotency.
- Without the condition, a retry would overwrite the item silently, which could hide a double charge.
- Numbers are sent as strings (`fromN("500")`): DynamoDB has one Number type, and the SDK carries it as text.

## Rules and defaults

- **Secondary indexes:** a GSI can use any attributes as its key, be added at any time, has its own capacity, and is eventually consistent. A local secondary index (LSI) keeps the table's partition key, must be created with the table, and allows strongly consistent reads.
- **Capacity mode:** on-demand is the default and recommended mode, billed per request with no capacity to plan. Provisioned mode, where you set read and write units, suits steady, predictable load.
- **Consistency:** reads are eventually consistent unless you set a strongly consistent read, which costs more and is not available on a GSI.
- **Item size:** 400 KB maximum per item, including attribute names. Keep large blobs in [S3](card:s3) and store the key.
- **Scan:** reads every item and charges for all of them; a filter is applied after the read and does not cut the cost. Use Query, not Scan, for anything routine.

## Not to be confused with

A Query reads items under one partition key quickly, using the key. A Scan reads the whole table or index item by item and then optionally filters. Rule: Query = targeted read by key, cheap; Scan = read everything, slow and costly, to avoid in hot paths.

## Interview Qs

### GSI or LSI?

A GSI can use any attribute as its partition and sort key, can be added after the table exists, has its own capacity, but its reads are only eventually consistent. An LSI keeps the table's partition key, with a different sort key, must be created with the table, and allows strongly consistent reads. Reach for a GSI for a new access pattern.

### How do you stop a retried payment from being stored twice?

Write with a condition expression, `attribute_not_exists` on the key. If an item with that key already exists, DynamoDB rejects the write with `ConditionalCheckFailedException`, so the retry changes nothing. This gives an idempotent write without a separate lock.

### Why avoid Scan on a large table?

A Scan reads every item, 1 MB per page, and consumes read capacity for all of them even when a filter returns few. On a hot table it can use up the throughput other requests need. Design a key or a GSI so the query reads only the items you want.
