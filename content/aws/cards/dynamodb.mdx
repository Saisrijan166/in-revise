## Why it exists

Some data is only ever read by key, at very high volume. DynamoDB hashes each partition key to spread items over many partitions.

## How it works

| merchantId (partition key) | paymentId (sort key) | amountInr | status |
|---|---|---|---|
| m-42 | p-1001 | 500 | SUCCEEDED |
| m-42 | p-1002 | 500 | FAILED |
| m-77 | p-1003 | 500 | SUCCEEDED |

- A Query reads one partition key, optionally a sort key range: "all payments of m-42".
- A GSI gives a second key, such as status, for queries the table key cannot serve.

## Example

```java
var put = PutItemRequest.builder().tableName("payments")
        .item(Map.of(
                "merchantId", AttributeValue.fromS("m-42"),
                "paymentId", AttributeValue.fromS(paymentId),
                "amountInr", AttributeValue.fromN("500")))
        .conditionExpression("attribute_not_exists(paymentId)")
        .build();
try {
    dynamo.putItem(put);
} catch (ConditionalCheckFailedException e) {
    // already stored: this is a retry, so do nothing
}
```

## Interview Qs

### GSI or LSI?

A GSI can use any partition and sort key, can be added later and has its own capacity, but its reads are only eventually consistent. An LSI keeps the table's partition key, must exist at creation, and allows strong reads.

### How do you stop a retried payment from being stored twice?

Write with a condition, attribute_not_exists on the key. If the item exists, DynamoDB rejects the write with ConditionalCheckFailedException, so the retry changes nothing.

### A payment written a moment ago is missing from a GSI query. Why?

Queries on a GSI are only eventually consistent, so a fresh write can appear a moment later. Read the item by its table key with a strongly consistent read, or accept the short delay.
