## Why it exists

Replacing every server at once turns one bad build into a full outage. Moving traffic in steps, with health checks and alarms, limits the damage and makes rollback fast.

## How it works

<Compare id="rolling-vs-blue-green-vs-canary" />

- New tasks get traffic only after passing [load balancer health checks](card:elastic-load-balancing).

## Example

<Steps label="CI/CD for the payment service">
  <Step title="Commit">A merge to main starts the pipeline.</Step>
  <Step title="Build and test">CodeBuild or GitHub Actions runs the tests and builds the image.</Step>
  <Step title="Push">The image goes to Amazon ECR, tagged with the commit.</Step>
  <Step title="Deploy">ECS shifts traffic to the new revision: rolling, canary or blue/green.</Step>
  <Step title="Watch">Alarms on 5xx and latency; on ALARM, roll back.</Step>
</Steps>

## Interview Qs

### How does GitHub Actions deploy to AWS without stored access keys?

Register GitHub as an OIDC identity provider in IAM and let the workflow assume a role through it. Each run gets short-lived credentials, so no long-term keys are kept in GitHub.

### Rolling update, blue-green or canary for a payment API?

Canary: send about 10% of traffic to the new version, watch the alarms, then move the rest. A bad release reaches few users and rolls back quickly.
