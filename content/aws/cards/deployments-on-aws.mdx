## What it is

A deployment strategy is how a new version of your service replaces the old one, and how user traffic moves onto it. The main choices are rolling (replace tasks a batch at a time), blue/green (run a full new copy, then switch), and canary (send a small slice first, then the rest). CI/CD is the pipeline that gets you there: it builds and tests the code on every commit, packages it as a container image, and triggers one of those deployment strategies.

## Why it exists

Replacing every running server at once turns one bad build into a full outage, with no easy way back. Moving traffic in controlled steps, behind health checks and alarms, limits the blast radius: if the new version is bad, only a fraction of requests hit it, and you can switch back quickly. Automating the build, test and deploy also removes the manual, error-prone steps between "merged" and "running in production".

## Example

A typical CI/CD flow for the payment service, from a merge to production traffic.

<Steps label="CI/CD for the payment service">
  <Step title="Commit">A merge to main starts the pipeline.</Step>
  <Step title="Build and test">CodeBuild or GitHub Actions runs the tests and builds the container image.</Step>
  <Step title="Push">The image goes to Amazon ECR, tagged with the commit SHA.</Step>
  <Step title="Deploy">ECS shifts traffic to the new service revision: rolling, canary or blue/green.</Step>
  <Step title="Watch">CloudWatch alarms on 5xx and latency; on ALARM during the bake time, ECS rolls back.</Step>
</Steps>

What to notice:

- The image is tagged with the commit SHA, so every deployment maps to an exact commit, and a rollback is redeploying a known earlier image rather than rebuilding.
- The deploy step and the watch step are linked: with alarm-based rollback, ECS does not mark the deployment complete until it has shifted traffic and watched the alarms stay quiet for the bake time.
- If GitHub Actions is the runner, it authenticates to AWS by assuming an IAM role through OIDC, so no AWS access keys are stored in the repo.

## Rules and defaults

- **Rolling defaults (ECS replica service):** `minimumHealthyPercent` 100% and `maximumPercent` 200%, so ECS can start the new tasks before stopping the old ones (ECS, at the time of writing).
- **Circuit breaker:** available for the rolling (`ECS`) deployment type; it fails a deployment whose tasks never reach a steady state, and can roll back.
- **Alarm rollback:** supported for the rolling deployment type; link CloudWatch alarm names, enable rollback, and ECS fails and reverts the deployment if an alarm fires. A rolling deployment has no bake time by default; set `bakeTimeInMinutes` if you want ECS to keep watching the alarms after the new tasks are healthy.
- **Built-in strategies:** ECS supports `ROLLING`, `BLUE_GREEN`, `LINEAR` and `CANARY` natively; blue/green, linear and canary default to a 15-minute deployment bake time, and the canary phase defaults to a 10-minute canary bake time.
- **No stored keys:** register GitHub (or another CI) as an OIDC identity provider in IAM so each run assumes a role for short-lived credentials.

## Common mistakes

- **"A blue/green or canary deployment needs CodeDeploy."** Not any more. ECS has built-in blue/green (since 17-07-2025) and linear and canary (since 30-10-2025); CodeDeploy is one option, not a requirement.
- **No bake time, no alarms.** Shifting all traffic and declaring success immediately means a slow memory leak or a spike under load goes unnoticed until customers complain. Keep a bake time and auto-rollback on alarms.

## Interview Qs

### How does GitHub Actions deploy to AWS without stored access keys?

Register GitHub as an OIDC identity provider in IAM and let the workflow assume an IAM role through it. Each workflow run receives short-lived credentials scoped to that role, so there are no long-term AWS keys sitting in GitHub secrets to leak or rotate.

### Rolling update, blue-green or canary for a payment API?

Canary. Shift about 5-10% of traffic to the new version, watch 5xx and latency alarms during the canary bake time, then shift the rest. A bad release reaches only a few users and rolls back quickly. Blue/green is the alternative when you want one clean switch and an instant switch-back; rolling is for routine, low-risk changes.

### What does it mean that a deployment "completed", and why is that not the same as healthy?

Completed means the new tasks are running and traffic has moved to them. It does not prove the release is good under real load, where a memory leak or a slow dependency may only show up after some minutes. That is why you keep a bake time with CloudWatch alarms that trigger an automatic rollback.
