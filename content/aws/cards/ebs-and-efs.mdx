## What it is

Amazon EBS (Elastic Block Store) gives an [EC2](card:ec2) instance a volume: a disk that lives on the network, not inside the host. It is block storage: the operating system sees a blank disk, formats it with a file system and reads it in small blocks. Amazon EFS (Elastic File System) is file storage instead: a ready-made shared folder, reached over the NFS protocol, that many Linux servers mount at once. Both differ from [S3](card:s3), where code reads whole objects through an API.

## Why it exists

An EC2 instance needs a disk for its operating system and for software that writes files, such as a database you run yourself. The host's own disk, instance store, loses its data when the instance stops, so lasting data needs a disk that lives apart. Some software also expects one folder that every server sees, such as a document tool whose uploads must appear on all servers. EBS solves the first need; EFS solves the second.

## How it works

<Compare id="s3-vs-ebs-vs-efs" />

1. You create an EBS volume in one AZ, choosing its type (gp3 for most workloads) and size, and attach it to an instance in that same AZ.
2. The operating system formats and mounts it. Because the volume is separate from the host, its data survives a stop and start of the instance.
3. To back it up, you take a snapshot. It saves only the blocks changed since the last snapshot, and AWS stores it in S3, copied across all AZs of the Region.
4. To get the data into another AZ, you create a new volume from the snapshot there. The volume itself never moves.
5. For a shared folder, you create an EFS file system and one mount target in each AZ. Every instance mounts it over NFS on port 2049 and sees the same files at once.

## Example

A reporting job keeps its data on an EBS volume in `ap-south-1a`, and it must now run in `ap-south-1b`. The AWS CLI moves the data through a snapshot:

```bash
# 1. Snapshot the volume in ap-south-1a, and wait until it completes
aws ec2 create-snapshot --volume-id vol-0abc1234example \
    --description "reports data before the AZ move"
aws ec2 wait snapshot-completed --snapshot-ids snap-0def5678example
# 2. Create a gp3 volume from the snapshot in ap-south-1b
aws ec2 create-volume --snapshot-id snap-0def5678example \
    --availability-zone ap-south-1b --volume-type gp3
# 3. Attach it to the instance in ap-south-1b
aws ec2 attach-volume --volume-id vol-0new9999example \
    --instance-id i-0123456789example --device /dev/sdf
```

What to notice:

- Nothing moves the original volume. The snapshot is stored Regionally, so `create-volume` can build a copy in any AZ you name.
- `attach-volume` works only because the new volume and the instance are in the same AZ. With a volume in `1a` and an instance in `1b`, the call fails.
- The new volume loads its blocks from S3 as they are first read, so early reads are slower. Fast snapshot restore, or reading every block once, removes that delay.
- For another Region, you first copy the snapshot there with `copy-snapshot`.

## Rules and defaults

- **One AZ:** a volume attaches only to instances in its own AZ.
- **Default type:** gp3 when you create a volume in the console; some other paths still default to gp2 (at the time of writing).
- **Multi-Attach:** only io1 and io2 volumes, on up to 16 Nitro instances in one AZ, and the software must use a cluster-aware file system.
- **Backups are your job:** AWS does not back up EBS volumes for you. Schedule snapshots with Data Lifecycle Manager or AWS Backup.
- **EFS types:** a Regional file system stores data across several AZs and can have one mount target per AZ. A One Zone file system lives in one AZ and has a single mount target.
- **EFS network:** the mount target's security group must allow inbound TCP 2049 from the clients' security group, or the instances cannot mount it.
- **EFS throughput:** Elastic is the default mode; storage grows and shrinks with the files, and you pay for what is stored.
- **Windows file shares:** use the Amazon FSx family, because EFS does not support Windows.

## Not to be confused with

Instance store is a disk physically on the host of an EC2 instance: fast and with no extra charge, but its data is lost on stop, hibernate or terminate. An EBS volume lives on the network, survives stop and start, and can be snapshotted. Rule: instance store = scratch space you can lose; EBS = data you must keep.

## Interview Qs

### Can two EC2 instances share one EBS volume?

Normally no: a volume attaches to one instance. Multi-Attach lets one io1 or io2 volume attach to up to 16 Nitro instances in the same AZ, but the software must coordinate writes with a cluster-aware file system. For a plain shared folder, use EFS.

### When would you choose EFS over S3?

When software needs a real shared file system: many Linux servers reading and writing one folder through file paths, with POSIX permissions and file locks. Files that your own code handles by key through the SDK, such as receipts, fit S3 better.

### gp2 or gp3?

gp3 for new volumes. A gp2 volume's IOPS grow with its size, 3 IOPS per GiB, so teams bought large disks only for speed. gp3 includes 3,000 IOPS and 125 MiB/s at any size, and you raise IOPS or throughput separately, without buying a bigger disk.
