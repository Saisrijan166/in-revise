## Why it exists

A server needs a disk that outlives the instance, and some apps need one folder that many servers read and write.

## How it works

<Compare id="s3-vs-ebs-vs-efs" />

- Multi-Attach: one io1 or io2 volume on up to 16 Nitro instances in one AZ; it needs a cluster-aware file system.
- AWS does not back up EBS by itself: schedule snapshots with Data Lifecycle Manager or AWS Backup.
- Windows shares or HPC file systems: the Amazon FSx family.

## Defaults

| What | Default | Where |
|---|---|---|
| Volume type when created in the console | gp3 (gp2 on some other paths) | EBS, as of 20-10-2026 |
| EFS throughput mode | Elastic | EFS, as of 20-10-2026 |

## Interview Qs

### What is the difference between instance store and EBS?

Instance store is a disk on the host of an [EC2](card:ec2) instance: fast and free, but its data is lost on stop, hibernate or terminate (a reboot keeps it). EBS is a network volume that persists on its own and can be snapshotted.

### How do you move an EBS volume to another AZ?

Take a snapshot; it is stored across the Region's AZs. Create a new volume from it in the target AZ. For another Region, copy the snapshot there first.

### When would you choose EFS over S3?

When software needs a real shared file system: many Linux servers reading and writing one folder with POSIX permissions and file locks. Files the app handles by key through the SDK, such as receipts, fit S3.
