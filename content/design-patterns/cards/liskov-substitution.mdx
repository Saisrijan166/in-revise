## What it is

The Liskov Substitution Principle is the L in SOLID, named after Barbara Liskov. It says a subtype must be usable wherever its base type is expected, without the caller noticing. "Subtype" means any implementation of a type, whether made with `extends` or by implementing an interface. The point is behaviour, not just method names: the subtype must honour the promises the base type made, which Liskov and Wing (1994) call the base type's contract.

## Why it exists

Polymorphism only works if callers can trust the base type. If a method accepts a `PaymentStrategy` and calls `pay()`, it assumes every strategy behaves like the contract says. A subtype that behaves differently, by rejecting valid inputs or throwing an unexpected error, breaks code that never even mentions it by name. LSP spells out the rules a subtype must follow so that substitution stays safe and callers never need to know which subtype they got.

## How it works

The subtype must keep four parts of the base type's contract.

| Rule | The subtype must | Payment example |
|---|---|---|
| Preconditions | not demand more from the caller | CardPayment cannot reject amounts the interface allows |
| Postconditions | promise at least as much | when pay() returns, the money is taken |
| Invariants | keep what is always true | a paid amount is never negative |
| Exceptions | throw no new kinds | refund() does not throw UnsupportedOperationException if the base never does |

1. Write down what the base type promises callers: inputs it accepts, results it guarantees, errors it can throw.
2. For each subtype, check it accepts at least those inputs and promises at least those results.
3. Check it introduces no new error that callers of the base type are not prepared for.
4. If a subtype cannot keep the contract, it is the wrong subtype: split the interface or compose instead.

So the key is: a subtype may do more, but never less and never differently, than the base type promised.

## Example

A gift card that cannot be refunded breaks the refundable contract.

```java
interface RefundablePayment extends PaymentStrategy { void refund(BigDecimal amount); }

class GiftCardPayment implements RefundablePayment {
    public void pay(BigDecimal amount) { /* debit the gift card */ }
    public void refund(BigDecimal amount) {                 // breaks the contract
        throw new UnsupportedOperationException("gift cards cannot be refunded");
    }
}
// A refund job looping over RefundablePayment now fails at run time on a gift card.
// Fix: GiftCardPayment implements only PaymentStrategy, not RefundablePayment.
```

What to notice:

- `GiftCardPayment` compiles, because the signature of `refund` matches, but it violates LSP by throwing an error no caller of `RefundablePayment` expects.
- Any code that treats all `RefundablePayment` values the same breaks the moment a gift card reaches it.
- The fix is structural: a gift card is not a refundable payment, so it should not be that subtype. [ISP](card:interface-segregation) (splitting the interface) is the usual remedy.

## Rules and defaults

- **Subtyping is behavioural:** the JVM enforces only signatures; keeping the contract is the author's job.
- **JDK example:** `List.of(...)` returns an unmodifiable list, and `Collection` documents `add` as an optional operation that may throw `UnsupportedOperationException` (since Java 9). Code that must add cannot assume every `List` allows it, so this is within the documented contract, not an LSP break.
- **Fix a broken hierarchy** by splitting the interface ([ISP](card:interface-segregation)) or by [composition](card:composition-over-inheritance), not by adding `instanceof` checks in callers.

## Interview Qs

### Why is Square extends Rectangle the classic LSP violation?

Rectangle's `setWidth` promises the height stays the same. A Square must change both sides together, so code that sets width 5 and height 4 expects area 20 but gets 16. The Square weakened Rectangle's postcondition, so it is not substitutable, even though it compiles and "a square is a rectangle" in mathematics.

### List.of(...).add(x) throws an exception. Does that break LSP?

No. `Collection` documents `add` as an optional operation that may throw `UnsupportedOperationException`, and `List.of` (Java 9) documents its lists as unmodifiable. The contract always allowed this, so a caller must not assume every `List` is mutable. The behaviour is within the promise, so substitution is still honoured.

### How do you spot an LSP violation in code?

Look for callers that use `instanceof` or type checks to treat one subtype specially, or subtype methods that throw new exceptions or silently do nothing. These mean the subtype does not keep the base type's contract, so callers have to know which subtype they hold.
