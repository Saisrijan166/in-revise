## Why it exists

Polymorphism works only if callers can trust the base type. A subtype that behaves differently breaks code that never even mentions it.

## How it works

| Rule | The subtype must | Payment example |
|---|---|---|
| Preconditions | not demand more | CardPayment cannot reject amounts the interface allows |
| Postconditions | promise at least as much | when pay() returns, the money is taken |
| Invariants | keep them true | a paid amount is never negative |
| Exceptions | throw no new kinds | no UnsupportedOperationException from refund() |

- Named after Barbara Liskov (Data Abstraction and Hierarchy, 1988); Liskov and Wing made it formal in 1994.
- Fix a broken subtype by splitting the interface ([ISP](card:interface-segregation)) or by [composition](card:composition-over-inheritance).

## Example

```java
interface RefundablePayment extends PaymentStrategy { void refund(BigDecimal amount); }

class GiftCardPayment implements RefundablePayment {
    public void pay(BigDecimal amount) { /* debit the gift card */ }
    public void refund(BigDecimal amount) {                // breaks the contract
        throw new UnsupportedOperationException("gift cards cannot be refunded");
    }
}
// A refund job that loops over RefundablePayment now fails at runtime.
// Fix: GiftCardPayment implements only PaymentStrategy.
```

## Interview Qs

### Why is Square extends Rectangle the classic LSP violation?

Rectangle's setWidth promises the height stays the same. Square must change both, so code that sets width 5 and height 4 expects area 20 and gets 16. Square's postcondition is weaker.

### List.of(...).add(x) throws. Does that break LSP?

No. Collection marks add as an optional operation that may throw UnsupportedOperationException, and List.of (Java 9) documents its lists as unmodifiable. Code that must add cannot assume every List allows it.
