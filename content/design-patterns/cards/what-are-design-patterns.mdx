## What it is

A design pattern is a named, proven shape of a solution for a design problem that comes up again and again. It is not code you copy; it is a description of how the classes and objects are arranged to solve that kind of problem, with its trade-offs. The best-known collection is the "Gang of Four" (GoF) book, which describes 23 patterns. The GoF are its four authors: Gamma, Helm, Johnson and Vlissides.

## Why it exists

The same design problems return in project after project: how to let an object vary its behaviour, how to wrap a library that does not fit, how to notify many parts when something happens. Without a shared vocabulary, you re-invent and re-explain the same solution each time. A pattern name such as Strategy or Adapter replaces a long explanation with one word and a structure your teammates already know.

## How it works

The GoF book sorts its 23 patterns into three families by what they organise.

| Family | What it organises | The GoF patterns |
|---|---|---|
| Creational (5) | How objects are made | [Singleton](card:singleton), [Factory Method](card:factory-method), [Abstract Factory](card:abstract-factory), [Builder](card:builder), [Prototype](card:prototype) |
| Structural (7) | How classes and objects fit together | [Adapter](card:adapter), [Bridge](card:bridge), [Composite](card:composite), [Decorator](card:decorator), [Facade](card:facade), [Flyweight](card:flyweight), [Proxy](card:proxy) |
| Behavioural (11) | How objects share work and talk | [Chain of Responsibility](card:chain-of-responsibility), [Command](card:command), [Interpreter](card:interpreter), [Iterator](card:iterator), [Mediator](card:mediator), [Memento](card:memento), [Observer](card:observer), [State](card:state), [Strategy](card:strategy), [Template Method](card:template-method), [Visitor](card:visitor) |

1. You notice a problem that fits a pattern's description, such as "I have many payment methods that each run a different algorithm".
2. You pick the pattern whose shape solves it, here [Strategy](card:strategy), and arrange your classes that way.
3. You weigh its trade-offs: a pattern adds classes and indirection, so you use one only when it pays for itself.

So the key is that a pattern is a shared name for a tested arrangement, not a rule you must follow.

## Example

The payment system in this tech is the running example. It supports UPI, card and wallet, and each applies the [Strategy](card:strategy) pattern.

```java
interface PaymentStrategy { void pay(BigDecimal amount); }        // the role
class UpiPayment  implements PaymentStrategy { public void pay(BigDecimal a) { } }
class CardPayment implements PaymentStrategy { public void pay(BigDecimal a) { } }

class PaymentService {
    private final PaymentStrategy strategy;                       // holds one method
    PaymentService(PaymentStrategy strategy) { this.strategy = strategy; }
    void checkout(BigDecimal amount) { strategy.pay(amount); }
}
```

What to notice:

- `PaymentStrategy` is the pattern's shared shape: an interface that every payment method implements.
- `PaymentService` works with the interface, so adding a new method means a new class, not an edit here.
- The word "Strategy" tells a reader the whole arrangement at once; that naming is the value of patterns.

## Not to be confused with

A **pattern** is a concrete solution shape for a recurring problem. A **principle** is a general rule for good design, such as [SOLID](card:single-responsibility) or DRY, that explains why patterns help. An **idiom** is one language's small habit, like Java's try-with-resources. Rule: a principle guides, a pattern solves, an idiom is a language trick.

## Common mistakes

- **"Repository, dependency injection and MVC are GoF patterns."** They are widely used patterns, but they are not among the 23 in the GoF book; they came from other authors.
- **"More patterns means better design."** A pattern used where plain code would do just adds classes to read. Patterns are tools for real problems, not a mark of quality.

## Interview Qs

### What are the three types of design patterns?

Creational, structural and behavioural. Creational patterns control how objects are made, such as Builder and Factory Method. Structural patterns assemble objects into larger structures, such as Adapter and Decorator. Behavioural patterns share responsibilities and communication between objects, such as Strategy and Observer. The GoF book has 5, 7 and 11 of them.

### Are design patterns still useful with lambdas and modern Java?

Yes. The ideas stay; the code gets shorter. A [Strategy](card:strategy) can be a lambda instead of a class, a [Singleton](card:singleton) can be an enum, and pattern matching for switch (Java 21) over sealed types often replaces a [Visitor](card:visitor). You still name the pattern to explain the intent.

### When should you not use a pattern?

When a simple solution already fits. Adding a pattern to a problem that does not need it creates extra classes and indirection for no gain, which is overengineering. Use a pattern only when the problem it targets actually appears.
