## Why it exists

Every edit to working code can break it. If new features arrive as new code, the old code stays tested and does not need rebuilding or redeploying.

## How it works

| Adding a wallet payment | if-else design | OCP design |
|---|---|---|
| Code you write | a new branch inside PaymentService | a new WalletPayment class |
| Old code | edited, retested, redeployed | untouched |
| Risk | a typo can break UPI and card too | limited to the new class |

- The service depends on an abstraction that stays fixed; each new implementation extends what it can do.
- Closure is strategic: guess the most likely changes and close against those.
- [Strategy](card:strategy) is the usual way to get there; [DIP](card:dependency-inversion) makes the arrows point the right way.

## Example

```java
// Before: every new method edits this working switch
void pay(PaymentMethod method, BigDecimal amount) {
    switch (method) {
        case UPI    -> upiSdk.call(amount);
        case CARD   -> cardSdk.call(amount);
        case WALLET -> walletSdk.call(amount);     // added by editing old code
    }
}
// After: the service calls PaymentStrategy; a new method is a new class
class WalletPayment implements PaymentStrategy {
    public void pay(BigDecimal amount) { System.out.println("Wallet paid ₹" + amount); }
}
```

## Interview Qs

### Which real systems show OCP best?

Plugin architectures, Martin says: IDEs and editors gain features as plugins while their core stays unchanged, because plugins depend on the core and not the other way round.

### Is OCP still relevant with small microservices?

Yes. Martin (2020): when requirements change, only part of the code is wrong. OCP keeps you from editing the code that is still right just to fix the part that is wrong.
