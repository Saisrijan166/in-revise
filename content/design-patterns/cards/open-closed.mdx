## What it is

The Open/Closed Principle is the O in SOLID. A module should be open for extension (you can add new behaviour) but closed for modification (you do not edit the code that is already there). You achieve both at once by making the code depend on a stable interface: new behaviour arrives as a new class that implements that interface, while the existing code stays as it is.

## Why it exists

Every edit to working code risks breaking it, and forces a rebuild, a retest and a redeploy of the parts you touched. Without OCP, each new payment method means another branch inside `PaymentService`, so the one class that already handles UPI and card is edited again and again, and a mistake there can break methods that were working. If new features instead arrive as new code, the old code stays tested and untouched.

## How it works

The same new feature, added two ways.

| Adding a wallet payment | if-else design | OCP design |
|---|---|---|
| Code you write | a new branch inside PaymentService | a new WalletPayment class |
| Old code | edited, retested, redeployed | untouched |
| Risk | a typo can break UPI and card too | limited to the new class |

1. Put the behaviour that varies behind a fixed interface, here `PaymentStrategy`.
2. Make the caller depend only on that interface, never on the concrete methods.
3. For a new behaviour, write a new class that implements the interface.
4. Wire the new class in where objects are created; the caller's code never changes.

So the key is: the interface stays closed, and new classes keep extending what the system can do.

## Example

Before, every method edits a working switch. After, a new method is a new class and the service is closed.

```java
// Before: adding WALLET means editing this tested method
void pay(PaymentMethod method, BigDecimal amount) {
    switch (method) {
        case UPI    -> upiSdk.call(amount);
        case CARD   -> cardSdk.call(amount);
        case WALLET -> walletSdk.call(amount);     // added by editing old code
    }
}
// After: the service calls PaymentStrategy; a new method is just a new class
class WalletPayment implements PaymentStrategy {
    public void pay(BigDecimal amount) { System.out.println("Wallet paid " + amount); }
}
```

What to notice:

- In the "before" code, each new method reopens and retests a method that already handled UPI and card.
- In the "after" code, `PaymentService` depends on `PaymentStrategy` and never changes; `WalletPayment` is new and isolated.
- A bug in `WalletPayment` cannot reach UPI or card, because they live in different closed classes.

## Rules and defaults

- **Closure is strategic:** you cannot close code against every possible change, so predict the likely one (new payment methods) and close against that.
- **The usual tool is [Strategy](card:strategy):** an interface plus interchangeable implementations is the common way to satisfy OCP.
- **[DIP](card:dependency-inversion) makes it work:** OCP needs the dependency arrows to point at the stable abstraction, which is what dependency inversion arranges.

## Common mistakes

- **"Closed means I can never touch this file again."** Closure is against a predicted kind of change. Other edits still happen; OCP only aims to avoid editing working code to add the expected new behaviour.
- **"Abstract everything just in case."** Guessing wrong adds interfaces you never extend. Close against changes you actually expect, in line with [YAGNI](card:design-principles).

## Interview Qs

### How do you make a class open for extension but closed for modification?

Depend on a fixed abstraction and add behaviour as new implementations of it. In the payment service, `PaymentService` calls the `PaymentStrategy` interface; a new method is a new class implementing it, so the service is extended without being edited. This is usually the [Strategy](card:strategy) pattern.

### Which real systems show OCP best?

Plugin architectures, Martin says. An IDE or editor gains features as plugins while its core stays unchanged, because each plugin depends on the stable core and the core knows nothing about any plugin. The dependency arrows point inward, so new features never force edits to the core.

### Is OCP still relevant with small microservices?

Yes. When requirements change, only part of the code is wrong (Martin, 2020). OCP keeps you from editing the part that is still right just to add the part that is new, which limits the blast radius of each change even in a small service.
