## What it is

An anti-pattern is a common solution that looks reasonable but causes more harm than good over time. It has a recognisable name so a team can point at it in review and agree to avoid it. Overengineering is one family of anti-pattern: adding abstractions, layers or patterns that the real problem never needed. The names below are the ones interviewers expect you to recognise.

## Why it exists

Patterns help only when they fit a real problem. If you do not know the common bad answers, you can reach for them without noticing: splitting one class into a dozen tiny ones, or wrapping a single-version rule in a Strategy "for later". Knowing the named anti-patterns lets you spot them in a code review and argue for the simpler design, instead of adding complexity that makes the code harder to read and test.

## How it works

Each anti-pattern below is a tempting move, its cost in a payment app, and the simpler fix.

| Anti-pattern | In a payment app | Fix |
|---|---|---|
| God object | `PaymentManager` validates, charges, writes SQL, renders receipts and sends SMS | split by reason to change: [SRP](card:single-responsibility) |
| Golden hammer | every rule becomes a Strategy, even one that never varies | start from the problem: [choosing a pattern](card:choosing-a-pattern) |
| Singleton abuse | `PaymentConfig.getInstance()` read and changed from everywhere | let the container hold one and [inject it](card:dependency-injection) |
| Speculative generality | a provider factory hierarchy for the one provider you have | wait for the second case: [YAGNI](card:design-principles) |
| Anemic domain model | `Payment` has only setters; `PaymentService` holds every refund rule | move the rule onto the entity: `payment.refund()` |

So the test is always the same: does this structure remove a real, present pain? If not, it is cost without benefit.

## Common mistakes

- **"A singleton is just a tidy way to share config."** It becomes global mutable state: any class can read or change it, the dependency is hidden, and tests cannot reset it. Keep one instance in the container and inject it.
- **"An anemic model is always wrong."** A service layer over entities that keep their own rules is fine. It is only an anti-pattern when entities are pure data bags and services hold every rule; for very simple logic a rich model may not pay off.

## Interview Qs

### What is a god object, and how do you fix it?

A class that controls far too much, like a `PaymentManager` that validates, charges, stores and notifies. It changes for many unrelated reasons, so any edit risks the rest. Split it by reason to change (SRP); if callers still want one entry point, put a [facade](card:facade) in front of the smaller classes.

### When does a singleton become an anti-pattern?

When it is global mutable state. Any class can read or change it, so the dependency is hidden from the method signatures and tests cannot reset it between runs. Keep a single instance in the container and inject it, which keeps one copy without the global access.

### How do you decide a design is overengineered?

Ask whether each abstraction removes a real, present problem. A Strategy for a rule with one version, or a factory for one provider, is speculative generality: cost now for flexibility nobody needs. Follow YAGNI and add the structure when the second case actually arrives.
