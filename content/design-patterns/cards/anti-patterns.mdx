## Why it exists

Patterns help only when they fit. Knowing the common bad answers lets you spot them in a code review and defend the simpler design.

## How it works

| Anti-pattern | In a payment app | Fix |
|---|---|---|
| God object | `PaymentManager` validates, charges, writes SQL, renders receipts, sends SMS | Split by reason to change: [SRP](card:single-responsibility) |
| Golden hammer | Every rule becomes a Strategy, even one that never varies | Start from the problem: [choosing a pattern](card:choosing-a-pattern) |
| Singleton abuse | `PaymentConfig.getInstance()` read and changed everywhere | Let the container hold one and [inject it](card:dependency-injection) |
| Speculative generality | A provider factory hierarchy for the one provider you have | Wait for the second case: [YAGNI](card:design-principles) |
| Anemic domain model | `Payment` has only setters; `PaymentService` holds every refund rule | Move the rule into the entity: `payment.refund()` |


## Interview Qs

### What is a god object, and how do you fix it?

A class that controls too much, like the PaymentManager above. Split it by reason to change; put a [facade](card:facade) in front if callers want one entry point.

### Is an anemic domain model always wrong?

It is an anti-pattern when entities are bags of getters and setters and services hold every rule. A service layer over entities that keep their own rules is fine; for simple logic a rich model may not pay off.

### When does a singleton become an anti-pattern?

When it is global mutable state: any class can read or change it, the dependency is hidden, and tests struggle to reset it. Keep one instance in the container and inject it instead.
