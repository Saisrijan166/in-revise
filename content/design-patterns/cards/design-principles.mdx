## What it is

Design principles are general rules for good object-oriented design. Patterns are concrete answers to specific problems; principles are the reasons behind them, and they let you judge any design even when no pattern fits. The ones interviewers ask about most are: program to an interface, encapsulate what varies, keep coupling low and cohesion high, and the short slogans DRY, KISS, YAGNI and the Law of Demeter.

## Why it exists

You cannot memorise a pattern for every situation. Principles give you a smaller set of ideas that explain why one design is easier to change than another. "Program to an interface" and "encapsulate what varies" are, in the GoF authors' words, the heart of their whole catalogue: almost every pattern is one of these two applied to a specific problem.

## How it works

Each principle, seen in the payment system.

| Principle | In the payment system |
|---|---|
| Program to an interface | `PaymentService` holds a `PaymentStrategy`, never a concrete `UpiPayment` |
| Encapsulate what varies | Payment methods change, so each sits behind `PaymentStrategy` |
| Loose coupling | A new `WalletPayment` needs no edit in `PaymentService` |
| High cohesion | `PaymentService` only takes payments; receipts live in another class |
| DRY | The refund-limit rule lives in one method, not copied into three strategies |
| KISS | Two fixed fee rules need one `if`, not a class hierarchy |
| YAGNI | No crypto-payment class until someone actually asks for it |
| Law of Demeter | `order.pay()`, not `order.getCustomer().getWallet().debit()` |

1. Find the part of the design that is likely to change, here the payment method.
2. Put that part behind an interface, so the rest of the code depends on the role, not the detail.
3. Keep each class to one job (high cohesion) and give it as few collaborators as possible (low coupling).
4. Resist extra structure until a real need appears (KISS, YAGNI), and keep each rule in one place (DRY).

So the key is: hide what varies, depend on roles, and stay as simple as the problem allows.

## Example

The Law of Demeter in one line: reach your direct friend, not your friend's parts.

```java
// Breaks the Law of Demeter: Order digs through Customer and Wallet
customer.getWallet().debit(amount);

// Follows it: Order asks its direct friend to do the job
order.pay(amount);     // Order talks to Customer/Wallet internally, callers do not
```

What to notice:

- The first line couples the caller to `Customer`, `Wallet` and `debit`; a change to any of them can break it.
- The second line depends only on `order`, so the chain of objects behind it can change freely.
- This is loose coupling made concrete: fewer things a caller must know means fewer things that can break it.

## Not to be confused with

Two ways to express a role-interface differ. An **interface** is a pure role: methods with no instance state, and a class may implement many. An **[abstract class](card:interface-vs-abstract-class)** is a partial parent: it can hold state and shared code, but a class extends only one. Rule: start with an interface for the role, and reach for an abstract class only when implementations share state or code.

## Interview Qs

### What is the difference between coupling and cohesion?

Coupling is how much one class depends on others; cohesion is how well the code inside one class belongs together. Good design aims for low coupling (few, loose links between classes) and high cohesion (each class focused on one job), so a change stays local.

### Why program to an interface?

Callers depend on the role, not the implementation, so a UPI gateway, a card gateway or a test mock can be swapped without editing them. The everyday form is `List<String> ids = new ArrayList<>()`: the variable is the role `List`, the implementation `ArrayList` can change.

### Does YAGNI forbid refactoring?

No. YAGNI forbids features built for a guessed future, not work that keeps the code easy to change. Fowler is explicit that refactoring is still encouraged; YAGNI targets speculative functionality, not good housekeeping.
