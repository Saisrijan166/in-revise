## Why it exists

Patterns are concrete answers; principles are the reasons behind them. They let you judge any design, even when no pattern fits.

## How it works

| Principle | In the payment system |
|---|---|
| Program to an interface | `PaymentService` holds a `PaymentStrategy`, never a `UpiPayment` |
| Encapsulate what varies | Payment methods change, so each sits behind `PaymentStrategy` |
| Loose coupling | A new `WalletPayment` needs no edit in `PaymentService` |
| High cohesion | `PaymentService` only takes payments; receipts have their own class |
| DRY | The refund-limit rule lives in one method, not in three strategies |
| KISS | Two fixed fee rules need one `if`, not a class hierarchy |
| YAGNI | No crypto payment class until someone asks for it |
| Law of Demeter | `order.pay()`, not `order.getCustomer().getWallet().debit()` |

- SOLID builds on these ([single responsibility](card:single-responsibility), [dependency inversion](card:dependency-inversion)); so does [composition over inheritance](card:composition-over-inheritance).

## Interview Qs

### What is the difference between coupling and cohesion?

Coupling is how much a class depends on others; cohesion is how well the code inside one class belongs together. Aim low on coupling, high on cohesion.

### Why program to an interface?

Callers depend on the role, so the implementation (UPI, card, a test mock) can change without editing them. Everyday form: `List<String> ids = new ArrayList<>()`.

### Does YAGNI forbid refactoring?

No. It forbids features built for a guessed future, not work that keeps code easy to change, such as refactoring (Fowler).
