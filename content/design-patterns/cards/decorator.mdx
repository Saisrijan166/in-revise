## What it is

Decorator is a class that wraps another object and implements the same interface as that object. When a method is called, the decorator does something extra, such as logging, then calls the same method on the object it wraps. Because it shares the interface, a caller cannot tell a wrapped object from a plain one. And because each decorator holds some object of that interface, a decorator can wrap another decorator, stacking features. Like [Adapter](card:adapter), it wraps and delegates; unlike Adapter, it keeps the interface unchanged.

## Why it exists

Features like logging, metrics and retries are optional and combine freely. If you add them by subclassing, every combination needs its own subclass: logging-only, metrics-only, logging-and-metrics, and so on, which explodes as features grow and is fixed at compile time. Decorator lets you write one small class per feature and wrap an object in exactly the features you want, decided at runtime for each object.

## How it works

  chart={`flowchart LR
  C[Caller] -- "charge(500)" --> L[LoggingGateway]
  L -- delegates --> M[MetricsGateway]
  M -- delegates --> U[UpiGateway: real charge]`}

1. Each decorator implements `PaymentGateway` and holds a `PaymentGateway`, which may be the real one or another decorator.
2. The caller holds the outermost decorator and calls `charge`, thinking it is a plain gateway.
3. That decorator does its extra work, then calls `charge` on the gateway it wraps.
4. The call travels inward through each layer until it reaches the real gateway, which does the actual charge.

So the key is that the outermost layer runs first and the innermost does the real work.

## Example

This stacks two decorators around a real gateway and runs the chain.

```java
class LoggingGateway implements PaymentGateway {            // same interface as what it wraps
    private final PaymentGateway inner;
    LoggingGateway(PaymentGateway inner) { this.inner = inner; }
    public void charge(BigDecimal amount) { System.out.println("charging " + amount); inner.charge(amount); }
}
class MetricsGateway implements PaymentGateway {            // a second, independent decorator
    private final PaymentGateway inner;
    MetricsGateway(PaymentGateway inner) { this.inner = inner; }
    public void charge(BigDecimal amount) { System.out.println("metric +1"); inner.charge(amount); }
}
PaymentGateway upi = amount -> System.out.println("UPI charged " + amount);   // the real one
new LoggingGateway(new MetricsGateway(upi)).charge(BigDecimal.valueOf(500));
```

```text output
charging 500
metric +1
UPI charged 500
```

What to notice:

- Both decorators implement `PaymentGateway` and hold a `PaymentGateway`, so each can wrap the real gateway or another decorator.
- Each `charge` does its own work first, then calls `inner.charge`, passing the call inward. The real gateway is the lambda at the bottom.
- The output order follows the nesting: logging is outermost, so it prints first; the real charge is innermost, so it prints last.
- Swap the nesting to `new MetricsGateway(new LoggingGateway(upi))` and `metric +1` prints before `charging 500`. No class changes; only the wrapping order does.

## Rules and defaults

- **Same interface:** a decorator must implement the exact interface it wraps, or callers could tell it apart and it would not be a drop-in.
- **Delegate inward:** a decorator should call the wrapped object; a decorator that stops the call is doing something else.
- **In the JDK:** `java.io` streams are decorators. `FilterInputStream` wraps another `InputStream`; `BufferedInputStream` extends it to add a buffer, as in `new BufferedInputStream(new FileInputStream(file))`.

## Not to be confused with

A [proxy](card:proxy) has the same structure but a different goal: it controls access to one object, such as deferring its creation or checking a permission, rather than adding features the caller chose. Rule: if the caller nests the wrappers to add behaviour, it is Decorator; if a wrapper guards or stands in for the real object, it is Proxy.

## Common mistakes

- **"A decorator can change the interface a bit."** Then callers can no longer treat it as the wrapped type, and stacking breaks. Changing the interface is [Adapter](card:adapter), not Decorator.

## Interview Qs

### Where does the JDK use Decorator?

In `java.io`. `FilterInputStream` wraps another `InputStream` and passes calls through to it; subclasses such as `BufferedInputStream` add features. `new BufferedInputStream(new FileInputStream(file))` adds buffering to a file stream without changing how you read it.

### Why use Decorator instead of inheritance for optional features?

With inheritance, every mix of features needs its own subclass, and the mix is fixed at compile time. Decorators are separate objects you combine at runtime, one small class per feature, so three features give three classes, not eight subclasses for every combination.

### Does the order of decorators matter?

Yes. The outermost decorator runs first. Logging wrapped around metrics logs before the metric is recorded; swap the nesting and the order flips. So the order you wrap them in is the order their behaviour runs.
