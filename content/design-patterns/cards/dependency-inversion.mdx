## What it is

The Dependency Inversion Principle is the D in SOLID. "High-level modules" hold the business policy, such as `PaymentService` deciding how a payment is taken. "Low-level modules" hold the details, such as the UPI SDK call or the SQL. DIP says neither should depend on the other directly. Both depend on an abstraction, and crucially the high-level side owns that abstraction: it defines the interface that the details must fit.

## Why it exists

In a plain layered design, business rules call SDKs and databases directly, so the most important code depends on the most changeable code. Every time an SDK's method or constructor changes, the ripple reaches up into the rules that matter most, and adding a new provider means editing the policy class. DIP flips the dependency: the policy defines an interface, the detail implements it, so the detail now depends on the policy, and the policy no longer changes when a detail does.

## How it works

1. The high-level `PaymentService` defines the `PaymentStrategy` interface it needs, in its own module.
2. Each detail, such as `UpiPayment`, implements that interface, so the detail depends on the policy's abstraction.
3. At run time the call still flows from `PaymentService` down into `UpiPayment`.
4. But in the source code, `UpiPayment` points up at `PaymentStrategy`; the dependency is inverted against the call.

So the key is: the call goes down, the source dependency points up, and the policy owns the interface.

## Example

How the modules are arranged: the core owns the interface, each detail depends on the core.

```text
payment/core   PaymentService, PaymentStrategy      policy; owns the interface
payment/upi    UpiPayment implements PaymentStrategy, calls the UPI SDK
payment/card   CardPayment implements PaymentStrategy
core imports nothing from upi or card; upi and card import core
```

What to notice:

- `core` has no import of `upi` or `card`, so it compiles and is tested without any SDK present.
- Each provider module depends on `core`, never the other way, which is the inverted dependency.
- Adding `payment/wallet` touches no existing module; this is how DIP delivers [OCP](card:open-closed).

## Rules and defaults

- **Policy owns the abstraction:** the interface lives with the high-level code that needs it, not with the detail that implements it.
- **Stable concretes are allowed:** Martin notes depending directly on a stable, non-volatile class such as `String` is fine; DIP targets volatile details.
- **Creating the object still needs the concrete class:** something must pick `UpiPayment`. Martin's answer was an [abstract factory](card:abstract-factory); today it is usually [dependency injection](card:dependency-injection).

## Interview Qs

### Why is it called "inversion"?

In traditional structured design, high-level modules depend on (call and import) low-level ones. In a good object-oriented design that source dependency is inverted: the detail depends on an abstraction the high-level side defines. The call still goes from high to low, but the compile-time dependency now points from low to high.

### How does DIP relate to the Open/Closed Principle?

DIP is the mechanism that delivers [OCP](card:open-closed). Martin (2000) says if OCP is the goal, DIP is the primary mechanism: by making policy depend on an abstraction, you can add new implementations (extension) without editing the policy (no modification).

### Can you follow DIP without a DI framework?

Yes. Pass the implementation into a constructor by hand in `main`, or create it in a factory. DIP is about which way dependencies point in the source code; a framework such as Spring only automates the wiring, it is not required by the principle.
