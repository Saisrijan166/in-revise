## Why it exists

In a classic layered design, business rules depend on SDKs and databases, so every change in a detail ripples up into the rules that matter most.

## How it works

<Mermaid
  alt="Before: PaymentService depends directly on UpiSdkClient. After: PaymentService depends on the PaymentStrategy interface, and UpiPayment also depends on PaymentStrategy by implementing it. The arrow from the detail now points up to the abstraction."
  chart={`flowchart LR
  subgraph Before
    PS1[PaymentService] --> U1[UpiSdkClient]
  end
  subgraph After
    PS2[PaymentService] --> I[[PaymentStrategy]]
    U2[UpiPayment] -. implements .-> I
  end`}
/>

- At runtime the call still goes from PaymentService to UpiPayment; only the source-code dependency flips.
- Creating the object still needs a concrete class: Martin's answer was an [abstract factory](card:abstract-factory); today it is usually [dependency injection](card:dependency-injection).
- Martin (2000): if OCP is the goal, DIP is the main mechanism.

## Example

```text
payment/core   PaymentService, PaymentStrategy     policy; owns the interface
payment/upi    UpiPayment implements PaymentStrategy, calls the UPI SDK
payment/card   CardPayment implements PaymentStrategy
core imports nothing from upi or card; upi and card import core
```

## Interview Qs

### Why is it called "inversion"?

Structured design made high-level modules depend on low-level ones. In a good object-oriented design that arrow is inverted: details depend on abstractions that the high-level side defines.

### Can you follow DIP without a DI framework?

Yes. Pass the implementation through a constructor by hand in main, or create it in a factory. Spring only automates the wiring.
