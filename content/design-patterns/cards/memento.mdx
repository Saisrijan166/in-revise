## What it is

Memento is a pattern for saving and restoring an object's state without breaking its encapsulation. The object whose state is saved is the **originator**. It produces a **memento**: a snapshot that holds a copy of its state, which only the originator can read back. A **caretaker** holds these snapshots, often on a stack, but never looks inside them. So you can roll the originator back to an earlier state, and its private fields never leave the object.

## Why it exists

A customer fills a payment form, switches from UPI to card, then wants to go back. To undo, something must remember the earlier amount and method. If outside code read and wrote the form's private fields directly to save and restore them, every piece of that code would depend on the form's internals, and the form could not change them safely. Memento lets the form hand out a sealed snapshot instead, so the state is saved without exposing a single field.

## How it works

1. The caretaker asks the originator to `save()`. The originator copies its state into a new memento and returns it.
2. The caretaker pushes the memento onto its stack. It treats the memento as an opaque token and does not read it.
3. The originator's state changes, for example the user switches to card.
4. To undo, the caretaker pops the last memento and passes it to the originator's `restore()`, which copies the state back into its own fields.

So the key is that the originator creates and reads the memento, while the caretaker only decides when to save and restore.

## Example

The `PaymentForm` is the originator; `PaymentDraft` is the memento; the `Deque` is the caretaker. Undo restores the earlier method.

```java
record PaymentDraft(BigDecimal amount, PaymentMethod method) { }    // the memento
class PaymentForm {                                                  // the originator
    private BigDecimal amount = BigDecimal.valueOf(500);
    private PaymentMethod method = PaymentMethod.UPI;
    PaymentDraft save() { return new PaymentDraft(amount, method); }
    void restore(PaymentDraft d) { amount = d.amount(); method = d.method(); }
    void choose(PaymentMethod m) { method = m; }
}
var form = new PaymentForm();
Deque<PaymentDraft> history = new ArrayDeque<>();                    // the caretaker
history.push(form.save());                                          // snapshot before the change
form.choose(PaymentMethod.CARD);                                   // user switches method
form.restore(history.pop());                                       // undo
System.out.println(form.save());                                   // state after undo
```

```text output
PaymentDraft[amount=500, method=UPI]
```

What to notice:

- `save()` and `restore()` are the only code that touches the form's private `amount` and `method`; the caretaker `history` just stores the `PaymentDraft` it is handed.
- `PaymentDraft` is a record, so its fields are final: a pushed snapshot can never be altered while it sits on the stack.
- The output is the state from before `choose(CARD)`, because `restore` copied the popped snapshot back. Remove the `history.push` line and there would be nothing to pop, so undo could not work.

## Rules and defaults

- **Only the originator reads the memento:** keep the memento's contents accessible to the originator alone (a nested or package-private type), so no other class depends on them.
- **Immutable snapshot:** a Java record (Java 16) makes the memento's fields final, so a saved state cannot change after capture.
- **Caretaker stays blind:** the caretaker stores and orders snapshots (usually a stack for undo) but never inspects or edits them.
- **Watch memory:** each snapshot is a full copy of the saved state, so frequent snapshots of large objects can use a lot of memory.

## Not to be confused with

A [command](card:command) is an action object: it knows how to do (and sometimes undo) one operation. A memento is captured state: a picture of how the object looked at a moment. Rule: Command = what to do; Memento = what it looked like before. Undo systems commonly use both, taking a memento before each command runs.

## Interview Qs

### How would you build undo for the payment form?

Before each change, push the form's memento (from `save()`) onto a history stack. To undo, pop the last memento and pass it to `restore()`. For undo paired with an action, wrap each change in a [command](card:command) and snapshot the form with a memento before the command runs, so undo restores the prior state.

### How does Memento preserve encapsulation if it exposes the object's state?

The originator creates the memento itself, because only it can see its private fields, and only it reads the memento back in `restore()`. The caretaker holds the snapshot as an opaque token. Making the memento an immutable, nested or package-private type keeps its contents hidden from every other class.

### What is the main cost of Memento?

Memory. Each memento is a full copy of the saved state, so taking many snapshots of large objects can consume a lot of memory. Mitigations include storing only the fields that changed, limiting how many snapshots you keep, or snapshotting less often.
