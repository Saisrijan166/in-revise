## What it is

Mediator is a pattern where a group of objects do not refer to each other directly. Instead each one, called a **colleague**, holds a reference only to one central **mediator** object and reports its changes to it. The mediator holds the rules about how the colleagues affect one another and calls the right ones in response. So the web of links between many objects collapses into one link per object, pointing at the mediator.

## Why it exists

On a checkout screen, the cart, the coupon box, the wallet balance and the Pay button each affect the others: a coupon changes the total, the total decides whether the wallet has enough, and that decides whether Pay is enabled. If each control calls the others directly, you get a tangle of references that nobody can change safely. Mediator moves all that logic into one object, so each control only says "I changed" and the rules live in a single place.

## How it works

1. Each colleague is given the mediator when it is created, and keeps no reference to the other colleagues.
2. When a colleague changes, it calls one method on the mediator and passes what happened.
3. The mediator applies its rules, for example "total is ₹500 and the wallet holds ₹300, so disable wallet pay".
4. The mediator calls back the colleagues that need to update, such as enabling or disabling the Pay button.

So the key is that no colleague ever talks to another colleague; all coordination passes through the mediator.

## Analogy

<Analogy title="Air traffic control" limit="A real control tower also handles safety and scheduling; a software mediator only wires objects together, so do not load it with unrelated work.">
Pilots do not radio each other to avoid collisions. Each one talks only to the control tower, and the tower tells each plane what to do. Remove the tower and every pilot would need to track every other plane.
</Analogy>

## Example

A tiny `CheckoutMediator` enables Pay only when there is a total and the wallet can cover it. The controls call the mediator; they never call each other.

```java
class CheckoutMediator {
    private BigDecimal total = BigDecimal.ZERO;
    private BigDecimal wallet = BigDecimal.ZERO;
    private boolean payEnabled;

    void cartChanged(BigDecimal newTotal) { total = newTotal; recompute(); }
    void walletChanged(BigDecimal balance) { wallet = balance; recompute(); }

    private void recompute() {                              // the one place with the rules
        payEnabled = total.signum() > 0 && wallet.compareTo(total) >= 0;
    }
    boolean isPayEnabled() { return payEnabled; }
}
```

What to notice:

- `cartChanged` and `walletChanged` are called by the controls; the controls hold no reference to each other, only to the mediator.
- `recompute` is the single place that decides whether Pay is enabled. A new rule (say, a minimum amount) changes this one method, not every control.
- If you deleted the mediator and let the cart enable the Pay button itself, the cart would need to know the wallet balance too, pulling every control into every other.

## Rules and defaults

- **One link each:** a colleague references only the mediator, which is what cuts the many-to-many coupling.
- **Rules live in the mediator:** put the coordination logic there, not in the colleagues, so colleagues stay reusable.
- **Keep it focused:** a mediator should coordinate one screen or flow. Piling unrelated logic into it creates a god object that is as hard to change as the tangle it replaced.

## Not to be confused with

A [facade](card:facade) gives outside callers one simple entry into a subsystem; the subsystem does not know the facade exists and its parts may still call each other. A mediator sits among peers that all know it and only talk through it. [Observer](card:observer) sets up one-way notifications from one subject to many observers, while a mediator handles two-way coordination among equals. Rule: Facade simplifies access from outside, Observer broadcasts one change, Mediator coordinates a group.

## Interview Qs

### How is Mediator different from Facade?

A facade is a simpler front door to a subsystem for outside callers; the subsystem does not know about it, and its parts may still call each other directly. A mediator sits among a set of peer objects that all know it, and they talk only through it in both directions. Facade simplifies access; Mediator removes peer-to-peer coupling.

### How is Mediator different from Observer?

Observer is one subject broadcasting a change to many observers, one way. Mediator is many colleagues coordinating through a central object, both ways, with the rules held in that object. They often combine: the mediator can publish events and colleagues subscribe as observers.

### What is the main risk with Mediator, and how do you avoid it?

The mediator can become a god object, because every coordination rule of the screen collects inside it. Avoid it by keeping one mediator per screen or flow, and moving reactions that do not depend on several colleagues out to separate observers so the mediator only holds true cross-colleague rules.
