## Why it exists

When one class mixes rules that different people own, a change asked for by one team can break a feature another team depends on.

## How it works

<Mermaid
  alt="Three groups ask for changes, each to its own class. The finance team changes PaymentService, which holds payment rules. The support team changes ReceiptService, which renders receipts. The ops team changes NotificationService, which sends SMS."
  chart={`flowchart LR
  F([Finance team]) --> PS[PaymentService: payment rules]
  S([Support team]) --> RS[ReceiptService: receipt layout]
  O([Ops team]) --> NS[NotificationService: SMS]`}
/>

- Martin traces SRP to Parnas (1972): split modules by the decisions likely to change.
- He calls it another way to state high cohesion and low coupling ([design principles](card:design-principles)).
- One class that does everything is the [god object](card:anti-patterns) anti-pattern.

## Example

```java
class PaymentService {                    // payment rules: asked for by finance
    void pay(BigDecimal amount) { /* charge through a PaymentStrategy */ }
}
class ReceiptService {                    // receipt layout: asked for by support
    String render(String paymentId, BigDecimal amount) {
        return "Receipt " + paymentId + ": paid ₹" + amount;
    }
}
class NotificationService {               // SMS text and channel: asked for by ops
    void sendSms(String phone, String text) { }
}
```

## Interview Qs

### What does "one reason to change" mean?

Reasons are people. Martin's example is an Employee class with pay calculation (the CFO's rules), an hours report (the COO's) and save (the CTO's). That is three reasons to change, so split it.

### Is a bug fix a reason to change?

No. Martin says bug fixes and refactoring are the programmer's job, not a responsibility of the code. A reason to change is a business function that asks for different behaviour.
