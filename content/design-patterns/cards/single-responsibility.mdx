## What it is

The Single Responsibility Principle is the S in [SOLID](card:open-closed), five design rules named by Robert C. Martin. It says a class (or module) should have one, and only one, reason to change. Martin is precise about what "reason" means: it is an actor, a group of people or a business function that asks for the behaviour. Two actors sharing one class is the problem the principle guards against.

## Why it exists

When one class mixes rules that different people own, a change asked for by one group can break a feature another group depends on. Picture a `PaymentService` that charges cards, formats receipts and sends SMS. Finance asks to change a fee, and the edit accidentally breaks the receipt that support relies on, because both live in the same class. Giving each actor its own class keeps a change where it belongs.

## How it works

1. For each class, ask who asks for its changes: which business function or team.
2. If more than one actor would ask, the class has more than one reason to change.
3. Split it so each class answers to one actor, gathering that actor's rules together.
4. Different actors' code now sits in different classes, so a change stays inside one of them.

So the key is: group what changes for the same reason, and separate what changes for different reasons.

## Example

The payment flow split by who owns each part. Finance owns charging, support owns the receipt, ops owns the SMS.

```java
class PaymentService {                    // charging rules: owned by finance
    void pay(String id, BigDecimal amount) { /* charge through a PaymentStrategy */ }
}
class ReceiptService {                     // receipt layout: owned by support
    String render(String id, BigDecimal amount) { return "Receipt " + id + ": paid " + amount; }
}
class NotificationService {                // SMS wording and channel: owned by ops
    void sendSms(String phone, String text) { }
}
```

What to notice:

- Each class changes for one reason: a fee change touches only `PaymentService`, a wording change only `NotificationService`.
- If these were one class, a receipt edit would force the payment code to be retested too.
- The split follows the actors, not the number of methods: `PaymentService` can grow many charging methods and still obey SRP.

## Rules and defaults

- **Reason = actor:** count reasons to change by the groups of people who ask, not by tasks or methods.
- **Bug fixes do not count:** Martin says the code is not responsible for bug fixes or refactoring; those are the programmer's job, not a business reason to change.
- **A heuristic, not a law:** Martin calls the SOLID principles heuristics, not rules or laws, so apply SRP with judgement rather than splitting every class on sight.

## Common mistakes

- **"Split until every class has one method."** That scatters related code and raises coupling. Split by actor, and keep one actor's rules together even if that is several methods.
- **"A bug fix is a reason to change, so it breaks SRP."** No. A reason to change is a business function asking for different behaviour; fixing a defect is not a new responsibility.

## Interview Qs

### What does "one reason to change" mean?

A reason is an actor: a group of people or a business function that asks for the behaviour. Martin's example is an Employee class with pay calculation (finance), an hours report (operations) and save (the technology team). That is three actors, so three reasons to change, so the class should be split.

### Is a bug fix a reason to change?

No. Martin says the code is not responsible for bug fixes or refactoring; those are the programmer's job. A reason to change is a business function that asks for different behaviour, such as finance changing how a fee is computed.

### How is SRP related to cohesion?

SRP is another way to state high cohesion. Gathering the code that one actor changes keeps closely related things together (high cohesion) and separates unrelated things (low coupling between actors' code), which is exactly what the general [design principles](card:design-principles) aim for.
