## What it is

Dependency injection (DI) is a way to give an object the other objects it needs instead of letting it build them. A dependency is just another object a class needs to do its work: `PaymentService` needs a `PaymentRepository` to save payments. With DI the class only declares what it needs, usually as constructor parameters, and something outside, called the container, creates those objects and passes them in. DI follows [the Dependency Inversion Principle](card:dependency-inversion): the class depends on an interface, not on a concrete class.

## Why it exists

If `PaymentService` calls `new UpiPayment()` itself, it is welded to that one class. You cannot swap UPI for card payments without editing the service, and a unit test cannot hand it a fake, so every test needs the real UPI code. With DI, `PaymentService` asks for "some `PaymentStrategy`" and does not care which class arrives. The app passes the real one; a test passes a stub.

## How it works

The wider idea is inversion of control (IoC): the framework creates your objects and calls into your code, instead of your code creating and calling everything. DI is the specific form of IoC that deals with dependencies.

1. Each class declares what it needs as constructor parameters; `PaymentService` lists a `PaymentRepository` and a `PaymentStrategy`.
2. At startup the container reads those parameters and creates the beans in dependency order, making the repository and the strategy first.
3. The container calls `new PaymentService(repository, strategy)` with the objects it already built.
4. A unit test skips the container and calls the same constructor with fakes.

So you write constructors, never the wiring code.

## Example

`PaymentService` declares its two dependencies in the constructor, and a test builds it with no Spring at all.

```java
@Service
public class PaymentService {
    private final PaymentRepository repository;
    private final PaymentStrategy strategy;

    public PaymentService(PaymentRepository repository, PaymentStrategy strategy) {
        this.repository = repository;        // no @Autowired: only one constructor
        this.strategy = strategy;
    }
}

// Unit test, no Spring:
var service = new PaymentService(fakeRepository, amount -> { /* pretend to pay */ });
```

What to notice:

- `private final` means each field is set once, in the constructor, and can never be null or reassigned later.
- The class has exactly one constructor, so Spring uses it without `@Autowired`. Add a second constructor and you must mark the one Spring should use.
- The parameter types are interfaces, so the app and the test each pass a different implementation.
- The test line builds the service with `new` and fakes: no container, no database, a fast test.

## Rules and defaults

- **Single constructor:** Spring uses it automatically; `@Autowired` is optional (Spring Framework 7).
- **Several constructors:** mark the one to use with `@Autowired`, or Spring falls back to a default (often no-argument) constructor and the dependencies stay null (Spring Framework 7).
- **Required vs optional:** constructor injection for required dependencies; setter injection for optional ones that have a default.
- **Field injection:** possible, but the field cannot be `final`, and a plain test must set it with reflection (`ReflectionTestUtils`), so prefer constructors in application code.

## Not to be confused with

A [factory](card:factory-method) is something the class still calls to get an object, so the class chooses to fetch it. With DI the class asks for nothing and receives its dependencies through the constructor. A [service locator](card:service-locator) is the middle case: the class asks a registry, so it depends on that registry; DI removes even that dependency.

## Common mistakes

- **"IoC and DI mean the same thing."** IoC is the broad idea that the framework runs the flow and calls your code. DI is the narrow form that supplies dependencies. Events and lifecycle callbacks are IoC too, but not DI.
- **"Creating a dependency with new inside a bean is fine."** That object is not managed by the container, nothing is injected into it, and the class is tied to one implementation, so a test cannot swap it.

## Interview Qs

### What is the difference between IoC and DI?

IoC is the broad principle: the framework, not your code, controls object creation and the flow, and calls into your code. DI is one specific form of IoC: the container supplies each object's dependencies from outside instead of the object creating or fetching them itself.

### Why is constructor injection preferred over field injection?

Dependencies are visible in one signature, fields can be `final`, and the object is never half-built, so a unit test just calls `new` with fakes. Field injection sets fields by reflection after construction, so `new` leaves them null, the field cannot be final, and the real number of dependencies is hidden.

### How is DI different from a service locator?

With a service locator the class asks a registry for each dependency, so it depends on the registry and the lookup is hidden inside the class. With DI the class asks for nothing; the dependencies arrive through the constructor, visible to anyone reading the signature.
