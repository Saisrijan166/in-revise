## Why it exists

If PaymentService calls `new UpiPayment()` itself, it is welded to that class: you cannot swap it or test with a fake.

## How it works

<Mermaid
  alt="In the app, the ApplicationContext creates a JPA PaymentRepository and a UpiPayment and passes both into the PaymentService constructor. A unit test passes fakes into the same constructor, with no container."
  chart={`flowchart LR
  AC[ApplicationContext] -- creates --> R[JPA PaymentRepository]
  AC -- creates --> U[UpiPayment]
  R --> PS[PaymentService]
  U --> PS
  T([Unit test]) -. "fakes, via new" .-> PS`}
/>

- Fowler's 2004 article named it DI, as "inversion of control" was too broad.
- Spring's docs call a long constructor a code smell: see [Single Responsibility](card:single-responsibility).

## Example

```java
@Service
public class PaymentService {
    private final PaymentRepository repository;
    private final PaymentStrategy strategy;
    public PaymentService(PaymentRepository repository, PaymentStrategy strategy) {
        this.repository = repository;          // no @Autowired: only one constructor
        this.strategy = strategy;
    }
}

// unit test: no Spring
var service = new PaymentService(fakeRepository, amount -> { });
```

## Interview Qs

### What is the difference between IoC and DI?

IoC is the broad idea: the framework, not your code, controls creation and flow. DI is one specific form: the container passes in each object's dependencies instead of the object finding them.

### Why is constructor injection preferred over field injection?

Dependencies are visible in one signature, fields can be final, and the object is never half-built, so a test just calls `new`. Field injection needs the container or reflection and hides how many dependencies there are.

### How is DI different from a service locator?

With a [service locator](card:service-locator) the class asks a registry, so it depends on that registry. With DI it asks for nothing: the dependency arrives through the constructor.
