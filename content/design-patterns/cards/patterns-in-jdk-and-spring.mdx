## What it is

This concept is a map, not a new pattern. It points at real classes in the JDK and in Spring and names the design pattern each one uses. The point is recognition: once you can say "`java.io` streams are Decorators" or "Spring's container is a Factory of beans", you show that you understand the pattern in working code, not just as a definition. Each row links to the concept that explains that pattern in full.

## Why it exists

Interviewers rarely ask you to recite a pattern's definition. They ask "where have you actually seen this one?". If you can only define Decorator, it sounds learned by rote; if you can say `BufferedInputStream` wraps `FileInputStream`, it is clear you have used it. This concept collects the examples that come up most, so you have a concrete class ready for each pattern.

## Example

A tiny program that proves two of the rows. `Runtime.getRuntime()` is a Singleton, and `List.of(...)` is a factory that hides the concrete class.

```java
// Singleton: the same instance every time
System.out.println(Runtime.getRuntime() == Runtime.getRuntime());
// Factory: List.of hides which concrete List class you get
List<Integer> nums = List.of(1, 2, 3);
System.out.println(nums.getClass().getSimpleName());
```

```text output
true
ListN
```

What to notice:

- `==` is `true`, so both calls returned the exact same `Runtime` object: one instance, the Singleton pattern.
- `List.of` returns a class named `ListN`, an internal immutable list you never name yourself. The factory decides the type, so your code depends only on `List`.
- You can name either class in an interview as a JDK example of its pattern.

## Interview Qs

### Which design patterns does Spring use?

Factory (`BeanFactory`, `FactoryBean`), Singleton (the default bean scope), Proxy (AOP and `@Transactional`), Observer (application events), Front Controller (`DispatcherServlet`), Adapter (`HandlerAdapter`), Strategy (`HandlerExceptionResolver`) and Builder (`RestClient.builder()`).

### Which patterns can you point to in the JDK?

Iterator (`java.util.Iterator`), Decorator (`java.io` streams such as `BufferedInputStream`), Adapter (`InputStreamReader`), Strategy (`Comparator`), Proxy (`java.lang.reflect.Proxy`), Builder (`HttpRequest.newBuilder()`) and Singleton (`Runtime.getRuntime()`).

### Why does calling a @Bean method from another @Bean method still give one object?

Because Spring replaces the `@Configuration` class with a CGLIB subclass by default (`proxyBeanMethods = true`). The subclass intercepts each `@Bean` call and returns the one container-managed bean instead of running the method again. Set `proxyBeanMethods = false` and it becomes a plain call that builds a new object.
