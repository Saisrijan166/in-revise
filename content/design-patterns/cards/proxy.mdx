## What it is

A proxy is an object that stands in for the real object and shares its interface, so callers use it as if it were the real thing. On each call the proxy can act before, after or instead of the real object: create it lazily, check a permission, call it over the network, or return a cached result. In structure it is like a [decorator](card:decorator), a wrapper with the same interface; the difference is intent. A decorator adds behaviour the caller chose, while a proxy controls access.

## Why it exists

Concerns such as access checks, lazy loading and starting a transaction do not belong inside the class doing the real work, and you often cannot change that class or its callers. A stand-in with the same interface lets you add these concerns around a call without touching either side. This is how Spring applies `@Transactional` and other AOP advice: it wraps your bean in a proxy, so the transaction logic lives outside your method.

## How it works

<Mermaid
  alt="The controller calls pay on the Spring proxy, which begins a transaction, calls the real PaymentService, then commits. The service's own call to this.audit skips the proxy."
  chart={`sequenceDiagram
  participant C as Controller

  participant S as PaymentService

  S->>S: this.audit() skips the proxy
  P->>P: commit`}
/>

1. Spring creates a proxy that implements the same interface as `PaymentService` and hands that proxy to callers.
2. The controller calls `pay` on the proxy, not on the real service.
3. The proxy runs the advice, here beginning a transaction, then calls `pay` on the real service.
4. Inside `pay`, a call to `this.audit()` goes straight to the real object and never passes the proxy, so no advice runs for it.
5. When `pay` returns, the proxy commits the transaction.

So the key is that only calls entering through the proxy get the advice.

## Example

A JDK dynamic proxy adds a line before and after every call, without a wrapper class.

```java
PaymentGateway real = amount -> System.out.println("UPI charged " + amount);
PaymentGateway proxy = (PaymentGateway) Proxy.newProxyInstance(
        PaymentGateway.class.getClassLoader(),
        new Class<?>[] { PaymentGateway.class },          // interfaces only
        (p, method, args) -> {                            // InvocationHandler
            System.out.println("before " + method.getName());
            Object result = method.invoke(real, args);    // call the real object
            System.out.println("after " + method.getName());
            return result;
        });
proxy.charge(BigDecimal.valueOf(500));
```

```text output
before charge
UPI charged 500
after charge
```

What to notice:

- `Proxy.newProxyInstance` builds the proxy at runtime from a list of interfaces; there is no hand-written proxy class.
- The `InvocationHandler` lambda runs for every method called on the proxy; `method.invoke(real, args)` forwards the call to the real object.
- Because a JDK proxy is built from interfaces, `PaymentGateway` must be an interface. A concrete class with no interface needs a CGLIB proxy instead.
- Remove `method.invoke(real, args)` and the real charge never happens; the proxy fully controls whether the real call runs.

## Rules and defaults

- **Proxy type in Spring Boot:** CGLIB subclass by default; `spring.aop.proxy-target-class` defaults to `true` in Spring Boot 4.1.1.
- **Proxy type in plain Spring Framework 7.0:** a JDK dynamic proxy when the bean has an interface, otherwise a CGLIB subclass.
- **CGLIB limits:** it subclasses the target, so a `final` class cannot be proxied, and `final` or `private` methods cannot be advised.
- **Per-bean override:** `@Proxyable` (new in Spring Framework 7.0) suggests the proxy type for one bean, overriding the global default, but only when the bean is actually being proxied.
- **Self-invocation:** a call through `this` never reaches the proxy, so its advice is skipped.

## Not to be confused with

A [facade](card:facade) also sits in front, but it offers a new, simpler interface over many classes, while a proxy keeps the exact interface of one object. Rule: same interface, one object, controlled access means Proxy; a new, simpler interface over a whole subsystem means Facade.

## Interview Qs

### JDK dynamic proxy or CGLIB, and what is the trade-off?

A JDK dynamic proxy implements the target's interfaces, so it can only proxy methods declared on an interface. CGLIB generates a subclass, so it needs no interface, but it cannot proxy a `final` class or `final` and `private` methods. Spring Boot uses CGLIB by default.

### Why is my @Transactional method ignored, and how do you fix it?

Usually self-invocation: another method of the same bean calls it through `this`, so the call never passes the proxy that holds the advice. Move the method to a separate bean and call it through that bean, or switch to AspectJ mode, which weaves the advice into bytecode instead of using a proxy. Also check the method is not `private` or `final`.

### What kinds of proxy are there?

A virtual proxy creates an expensive object only when first used; a protection proxy checks access rights; a remote proxy stands in for an object on another machine; a caching proxy returns a stored result. All share the real object's interface and add control around it.
