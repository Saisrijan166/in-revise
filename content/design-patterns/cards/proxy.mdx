## Why it exists

Checks, lazy loading and transactions belong around a call, not inside the class. A stand-in with the same interface adds them without changing the class or callers.

## How it works

<Mermaid
  alt="The controller calls pay on the Spring proxy, which begins a transaction, calls the real PaymentService, then commits. The service's own call to this.audit skips the proxy."
  chart={`sequenceDiagram
  participant C as Controller
  participant P as Spring proxy
  participant S as PaymentService
  C->>P: pay(₹500)
  P->>P: begin transaction
  P->>S: pay(₹500)
  S->>S: this.audit() skips the proxy
  P->>P: commit`}
/>

- Only calls that come in through the proxy get advice.
- `@Proxyable` (new in Spring Framework 7.0) sets the proxy type for one bean.

## Example

```java
PaymentGateway real = amount -> System.out.println("UPI charged " + amount);
PaymentGateway proxy = (PaymentGateway) Proxy.newProxyInstance(
        PaymentGateway.class.getClassLoader(),
        new Class<?>[] { PaymentGateway.class },          // interfaces only
        (p, method, args) -> {                            // InvocationHandler
            System.out.println("before " + method.getName());
            Object result = method.invoke(real, args);    // call the real object
            System.out.println("after " + method.getName());
            return result;
        });
proxy.charge(BigDecimal.valueOf(500));
```

```text output
before charge
UPI charged 500
after charge
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Proxy type | CGLIB subclass (`spring.aop.proxy-target-class=true`) | Spring Boot 4.1.1 |
| Proxy type without Boot | JDK proxy if the bean has an interface, else CGLIB | Spring Framework 7.0 |

## Interview Qs

### JDK dynamic proxy or CGLIB?

A JDK proxy implements the target's interfaces, so only their methods are proxied. CGLIB builds a subclass: no interface needed, but final classes and final or private methods cannot be advised.

### Why is my @Transactional method ignored, and how do you fix it?

Usually self-invocation: a method of the same bean calls it through this. Move it to another bean, or use AspectJ mode, which weaves bytecode instead of using a proxy. Also check it is not private or final.
