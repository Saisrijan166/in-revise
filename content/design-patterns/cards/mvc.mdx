## What it is

MVC (Model-View-Controller) splits a screen into three parts, each with one job. The model is the data and the rules behind it, and knows nothing about how it is shown. The view shows the model to the user, as an HTML page or as JSON for a REST API. The controller takes the user's input, calls the model, and picks the view. The front controller is a related pattern: one entry point that receives every request, runs the shared steps, then passes each request to the right controller.

## Why it exists

If input handling, business rules and HTML all sit in one place, each is hard to change without touching the others, and you cannot reuse the rules behind a different screen. Shared steps such as logging or security also get copied into every page. MVC separates the three concerns so each changes on its own, and a front controller puts the shared steps in one place that every request passes through.

1. An HTTP request arrives and the DispatcherServlet, the front controller, receives it first.
2. It asks a HandlerMapping which controller method handles this URL, then invokes that method through a HandlerAdapter.
3. The controller calls the model (`PaymentService`) to do the work.
4. A `@Controller` returns a view name; the DispatcherServlet asks a ViewResolver to turn it into an HTML page. A `@RestController` returns an object, which is written to the body as JSON with no view.

## Example

A REST controller in the payment app. It receives input, calls the model, and its return value becomes JSON.

```java
@RestController
@RequestMapping("/payments")
public class PaymentController {
    private final PaymentService service;

    public PaymentController(PaymentService service) { this.service = service; }

    @PostMapping
    public PaymentResponse pay(@RequestBody PaymentRequest request) {
        return service.pay(request);           // written as JSON, no view
    }
}
```

What to notice:

- The controller holds no business logic; it reads the request and calls `service.pay`, the model.
- `@RestController` is `@Controller` plus `@ResponseBody`, so the returned `PaymentResponse` is converted to JSON instead of being treated as a view name.
- `service` is injected through the constructor, so the controller depends on the interface, not on how the service is built.

## Rules and defaults

- **One DispatcherServlet:** by default it handles every request under the app's root path and delegates to the handler beans.
- **@RestController:** every method gets `@ResponseBody`, so return values go to the body; use plain `@Controller` when you render templates.
- **Handler beans:** HandlerMapping chooses the handler, HandlerAdapter invokes it, ViewResolver turns a view name into a view; Spring Boot auto-configures sensible defaults.
- **Shared steps:** filters and `HandlerInterceptor`s run around the controller, so cross-cutting work happens once in the front controller layer.

## Not to be confused with

The front controller is one entry point that handles every request; the MVC controller is the per-screen class that handles one action. In Spring the DispatcherServlet is the front controller and your `@Controller` is the MVC controller. Rule: one front controller for the whole app, many controllers, one per set of actions.

## Interview Qs

### What is the front controller in Spring MVC?

The DispatcherServlet. Every request reaches it first. It finds the handler through a HandlerMapping, invokes it through a HandlerAdapter, resolves exceptions, and renders the view if there is one. Shared concerns such as logging live here, so they run once for all requests.

### What is the difference between @Controller and @RestController?

A `@Controller` method usually returns a view name that a template engine renders into HTML. `@RestController` adds `@ResponseBody` to every method, so the return value is converted, typically to JSON, and written straight to the response body with no view step.

### Where does the model's business logic belong in MVC?

In the model layer, not the controller. The controller only reads input, calls the model and picks the view, so it stays thin. Keeping rules in the model lets you reuse them behind a different controller or a non-web caller.
