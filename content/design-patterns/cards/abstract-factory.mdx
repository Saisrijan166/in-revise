## What it is

Abstract Factory is a pattern for creating a **family** of related objects through one factory object. A family is a group of objects that are meant to work together, like a payment client and a refund client that both talk to the same provider. You define a factory interface with one creating method per product, and one concrete factory per variant. Each concrete factory makes only objects of its own variant. It builds on the [factory](card:factory-method) idea: instead of one creating method, you group several that must stay consistent.

## Why it exists

Some objects only make sense together. The test payment client and the test refund client belong to the sandbox; the live ones belong to production. If every object is created on its own with its own `new` or its own factory call, it is easy to build a live charge client and a test refund client in the same flow, which charges real money but logs a fake refund. Abstract Factory removes that risk: you pick one factory, and it is incapable of producing a mismatched set.

## How it works

1. Define a factory interface, `ProviderFactory`, with one method per product: `paymentClient()` and `refundClient()`.
2. Write one concrete factory per variant. `SandboxProviderFactory` returns test clients; `LiveProviderFactory` returns live ones.
3. At startup, choose a single concrete factory from configuration and pass it to the code that needs clients.
4. That code calls the factory's methods and gets back interfaces. Every object comes from the one factory, so the whole set is the same variant.

## Example

The checkout code is given a `ProviderFactory` and does not know which variant it holds.

```java
interface ProviderFactory {                       // one method per product in the family
    PaymentClient paymentClient();
    RefundClient refundClient();
}
class SandboxProviderFactory implements ProviderFactory {
    public PaymentClient paymentClient() { return amount -> System.out.println("test charge " + amount); }
    public RefundClient refundClient() { return id -> System.out.println("test refund " + id); }
}

ProviderFactory factory = new SandboxProviderFactory();   // chosen once, from config
factory.paymentClient().charge(BigDecimal.valueOf(500));
factory.refundClient().refund("pay_42");
```

```text output
test charge 500
test refund pay_42
```

What to notice:

- `ProviderFactory` has one method per product, so both clients always come from the same factory.
- Swap `new SandboxProviderFactory()` for `new LiveProviderFactory()` and both clients become live together, with no other change to the checkout code.
- You cannot end up with a test charge client and a live refund client, because a single factory makes the whole set.

## Rules and defaults

- **One method per product:** the factory interface declares a creating method for each product in the family.
- **A non-abstract factory must implement every method:** Java requires a concrete class to implement all of the interface's methods, so a factory cannot forget a product.
- **Adding a variant is cheap, adding a product is not:** a new variant is one new factory; a new product type changes the interface and every existing factory.
- **Choose the factory once:** usually at startup, from configuration, so the rest of the app stays unaware of the variant.

## Not to be confused with

[Factory Method](card:factory-method) creates **one** product, and a subclass decides its class. Abstract Factory creates a **family** of products that must match, and is often built from several factory methods. Rule: one product whose class varies, Factory Method; a matching set of products, Abstract Factory.

## Interview Qs

### When should you prefer Abstract Factory over Factory Method?

When several products must be created together and must belong to the same variant. Factory Method decides one product. Abstract Factory guarantees that the whole set, such as a provider's payment and refund clients, comes from one factory, so a test object and a live object can never be mixed.

### What is the main drawback of Abstract Factory?

Adding a new product type changes the factory interface, so every concrete factory must be updated to create it. It also multiplies small interfaces and classes. It pays off only when the "matching family" problem is real; otherwise it is overengineering.

### How is Abstract Factory related to Factory Method?

Abstract Factory is usually implemented using Factory Methods: each creating method on the factory interface is itself a factory method for one product. The difference is intent: Factory Method varies one product by subclass; Abstract Factory groups several products that must stay consistent.
