## What it is

Strategy is a pattern that puts each way of doing one job behind a shared interface, so the caller can choose which way to use. The object that does the job is called the context. It holds the interface and calls it, without knowing which concrete class it was given. This is [composition over inheritance](card:composition-over-inheritance) in action: the context has-a strategy instead of being a subclass for each case.

## Why it exists

Without the pattern, one method branches on the payment type: if UPI do this, else if card do that, else if wallet do that. Every new payment method edits that one method, and a careless edit can break the others. Strategy moves each branch into its own class behind a common interface. Now the service never changes, and a new method is just a new class, which keeps the service [open for extension but closed for modification](card:open-closed).

## How it works

1. You define one interface with the single method the job needs, here `pay(amount)`.
2. You write one class per way of doing it; each implements that interface.
3. The client, a [factory](card:factory-method) or Spring picks one strategy object and hands it to the context.
4. The context stores the interface and calls `pay`, never knowing which class it holds.
5. To add a way, you write a new class; the context and the other strategies are not touched.

So the key is that the context depends only on the interface, and the choice of class is made once, somewhere else.

## Example

The context holds `PaymentStrategy` and delegates. Because the interface has one method, a lambda can also be a strategy.

```java
interface PaymentStrategy { void pay(BigDecimal amount); }   // one method

class UpiPayment implements PaymentStrategy {
    public void pay(BigDecimal amount) { System.out.println("UPI " + amount); }
}
class PaymentService {                                        // the context
    private final PaymentStrategy strategy;
    PaymentService(PaymentStrategy strategy) { this.strategy = strategy; }
    void checkout(BigDecimal amount) { strategy.pay(amount); }
}
new PaymentService(new UpiPayment()).checkout(BigDecimal.valueOf(500));
new PaymentService(a -> System.out.println("Wallet " + a)).checkout(BigDecimal.TEN);
```

```text output
UPI 500
Wallet 10
```

What to notice:

- `PaymentService` names only the `PaymentStrategy` interface, so it works with any implementation and has no `if` on the payment type.
- The strategy is passed into the constructor, so you can swap it per instance, even at runtime.
- The last line passes a lambda, because `PaymentStrategy` has a single method. A new payment way need not always be a full class.
- Add `CardPayment` and `PaymentService` does not change; only the caller that creates the strategy learns the new option.

## Rules and defaults

- **One job per interface:** the strategy interface holds the single varying operation, so every concrete strategy is interchangeable.
- **The choice lives outside:** the context must not pick its own strategy with a switch, or the branching returns. Use a factory, a `Map<String, PaymentStrategy>` of beans, or dependency injection.
- **Lambda form (Java 8+):** if the interface has exactly one abstract method, a lambda or method reference can stand in for a class.
- **Stateless strategies are shareable:** a strategy with no fields can be one shared instance; one that keeps per-call data needs a fresh object.

## Not to be confused with

Strategy shares its shape with several patterns but differs in intent. A [factory](card:factory-method) creates an object; Strategy uses one already created, and the two often work together (a factory picks the strategy). [State](card:state) also delegates to a helper, but there the object swaps itself as events arrive, while a Strategy is chosen by the caller. [Template Method](card:template-method) varies steps through subclassing; Strategy varies the whole algorithm through composition. [Command](card:command) packs a single requested action to run later, while a Strategy is one of several ways to do a job now.

## Interview Qs

### What is the role of the context in Strategy?

The context, here `PaymentService`, holds the strategy interface and delegates the work to it. It does not know which concrete strategy it holds, so strategies can change without changing the context. Keeping the choice out of the context is what gives the pattern its value.

### How does Strategy support the Open/Closed Principle?

Adding `WalletPayment` means one new class that implements `PaymentStrategy`. `PaymentService` and the other strategies stay closed to modification. Only the one place that chooses the strategy, such as a factory or configuration, learns the new option, so the risk of breaking existing behaviour is small.

### Where does the JDK use Strategy?

`Comparator`. Passing a different comparator to `Collections.sort` or `list.sort` changes the ordering without changing the sort code. `Comparator` has one abstract method, so a lambda such as `(a, b) -> a.age() - b.age()` is a strategy too.
