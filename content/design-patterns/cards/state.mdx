## What it is

State is a pattern for an object whose behaviour depends on its status. Each status, such as PENDING or SUCCESS for a payment, becomes its own object that holds what is allowed in that status and which status comes next. The main object, the context, keeps a reference to its current state and forwards every event to it. It looks like [Strategy](card:strategy) (the context delegates to a helper), but here the states swap themselves as events happen.

## Why it exists

A payment's status decides what `confirm()` or `refund()` may do. Without the pattern, every one of these methods starts with the same switch on the status, and the rules are spread across many methods. Adding a new status means editing all of them, and it is easy to forget one check, so an illegal move like refunding a failed payment slips through. State puts each status's rules in one place, so a method has no switch and an illegal move is rejected by the state itself.

1. You list the allowed moves: the diagram above is the state machine.
2. Each state holds only the moves it allows; CREATED allows `submit`, SUCCESS allows `refund`, FAILED allows nothing.
3. The context keeps its current state and forwards each event to it, without a switch of its own.
4. The state does the work and returns the next state, which the context stores.
5. An event a state does not allow is rejected there, so the illegal move never happens.

So the key is that the rules for one status live in one place, and the context only passes events along.

## Example

Each state is an enum constant with its own method body. A constant overrides only the move it allows; the default body rejects the rest.

```java
enum PaymentState {
    CREATED { PaymentState submit()  { return PENDING; } },
    PENDING { PaymentState confirm() { return SUCCESS; } },
    SUCCESS { PaymentState refund()  { return REFUND_PENDING; } },
    FAILED, REFUND_PENDING, REFUNDED;
    PaymentState submit()  { throw new IllegalStateException(this + ": cannot submit"); }
    PaymentState confirm() { throw new IllegalStateException(this + ": cannot confirm"); }
    PaymentState refund()  { throw new IllegalStateException(this + ": cannot refund"); }
}
class Payment {                                        // the context
    private PaymentState state = PaymentState.CREATED;
    void refund() { state = state.refund(); }          // FAILED.refund() throws
}
```

What to notice:

- Each constant overrides only its allowed move, so `CREATED` has `submit`, `SUCCESS` has `refund`, and so on.
- The three default bodies throw, so any move a state does not override is rejected: `FAILED.refund()` throws "FAILED: cannot refund".
- `Payment.refund()` has no switch on the status; it just forwards to the current state and stores what comes back.
- This is the pattern because behaviour lives per state. A plain enum with just the names `CREATED, PENDING, ...` and no bodies would not be.

## Rules and defaults

- **Behaviour per state:** the pattern needs each state to carry its own behaviour; naming the states alone is not enough.
- **Reject by default:** give the default (non-overridden) move a clear failure, so an illegal transition throws instead of silently doing nothing.
- **The state decides the next state:** unlike Strategy, a state may know and return other states, which drives the lifecycle forward.
- **Enum vs classes (Java):** enum constants with class bodies suit a small, fixed set of states; separate state classes suit states that need their own fields or are added often.

## Not to be confused with

[Strategy](card:strategy) and State have the same shape: a context delegating to a helper object. The difference is intent. A Strategy is chosen once by the caller and the strategies do not know each other. A state is chosen by the lifecycle: the states can know each other and move the context to the next one as events arrive. Rule: many ways to do one job is Strategy; one object whose allowed actions change through a lifecycle is State.

## Interview Qs

### How is State different from Strategy?

Both delegate to a helper object, so they look the same in code. In Strategy the client picks the algorithm and the strategies never know each other. In State the states can know each other and move the context to the next state as events arrive. See [Strategy vs State](compare:strategy-vs-state).

### When is the State pattern overkill?

When there are only a few states that rarely change. A simple switch or a status field is clearer then, and the extra classes add no value. Use State when many methods depend on the status and new statuses or rules keep arriving.

### Why is a plain enum of statuses not the State pattern?

A plain enum only names the states; the behaviour still lives in switches elsewhere, which is exactly what the pattern removes. It becomes State only when each state carries its own behaviour, for example enum constants with their own method bodies, so the rules for a status sit in one place.
