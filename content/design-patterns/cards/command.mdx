## What it is

Command is a pattern that turns a request into an object. The object, the command, carries the target it should act on (the receiver) and the data it needs, and exposes a single `execute()` method. Three roles take part: the client builds the command, the invoker calls `execute()`, and the receiver holds the real logic. Because the request is now an object, you can store it, pass it, delay it or keep a history of it.

## Why it exists

Code that asks for a refund should not have to run the refund now, or know how refunds work. If it calls `refundService.refund(id)` directly, the refund happens inline, on the same thread, straight away. Packing the request as a `RefundCommand` object lets a job runner hold it, queue it, and run it later on a background worker. The caller is decoupled from when, where and by whom the action runs.

## How it works

1. The client builds a command, putting the receiver and the data inside it.
2. The client hands the command to the invoker, for example by adding it to a queue.
3. The invoker holds commands and knows only one method, `execute()`.
4. Later the invoker calls `execute()` on a command.
5. The command calls the receiver, which does the real work.

So the key is that the invoker triggers the action without knowing what it is, and the client decided the action without running it.

## Example

The command holds the receiver and the id; the job runner stores commands and runs them later, knowing only `execute()`.

```java
interface PaymentCommand { void execute(); }

class RefundCommand implements PaymentCommand {
    private final RefundService service; private final String paymentId;
    RefundCommand(RefundService s, String id) { service = s; paymentId = id; }
    public void execute() { service.refund(paymentId); }       // the receiver does the work
}
class JobRunner {                                              // the invoker
    private final Queue<PaymentCommand> queue = new ArrayDeque<>();
    void submit(PaymentCommand c) { queue.add(c); }
    void runAll() { while (!queue.isEmpty()) queue.poll().execute(); }
}
```

What to notice:

- `RefundCommand` stores the receiver and the data, so the whole request is one object that can sit on a queue.
- `JobRunner` depends only on `PaymentCommand.execute()`, so the same runner can handle refunds, payouts and reminders without knowing any of them.
- `submit` and `runAll` are separate, which is the point: the request is captured now and run later, maybe on another thread.
- To add undo, give the command an `undo()` and keep run commands on a stack; the runner code does not change.

## Rules and defaults

- **The command carries its context:** it holds the receiver and the data, so the invoker needs nothing but `execute()`.
- **Invoker stays ignorant:** the invoker must not depend on concrete commands, or it loses the ability to run any command.
- **Undo is optional:** add an `undo()` and a history stack only when you need reversible actions; many commands only ever run forward.
- **Runnable is the JDK form (Java):** a `Runnable` or `Callable` given to an `ExecutorService` is a command; the executor is the invoker and decides when and on which thread it runs.

## Not to be confused with

[Strategy](card:strategy) and Command both wrap behaviour in an object, so they look alike. A Strategy is one of several interchangeable ways to do a job, chosen and called by a context. A Command is a single requested action, with its data, meant to be run later by an invoker. Rule: choosing among ways to do one task is Strategy; capturing a request to queue, delay or undo is Command.

## Interview Qs

### A refund must run later from a queue. Command or Strategy?

Command. A refund is one requested action with its own data (the payment id), captured now and run later by a job runner that does not know the refund logic. Strategy fits a different need: when one job, such as paying, has several interchangeable ways. See [Command vs Strategy](compare:command-vs-strategy).

### How does Command support undo and redo?

Each command also implements an `undo()` that reverses its effect. Executed commands go on a history stack. Undo pops the last command and calls its `undo()`; redo runs its `execute()` again. Because each command knows how to reverse itself, the undo/redo machinery stays generic and does not grow with new actions.

### Where does the JDK use Command?

`Runnable` and `Callable`. You submit a task object to an `ExecutorService`, which decides when and on which thread it runs, so the executor is the invoker. Both are functional interfaces, so a lambda can be the command.
