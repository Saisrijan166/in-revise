## Why it exists

A fat interface forces implementers to stub methods they cannot support, and can force clients to rebuild when methods they never call change.

## How it works

  alt="Each client depends on one small interface: CheckoutService on Chargeable, RefundJob on Refundable, PayoutJob on Payouts. WalletAdapter implements Chargeable and Refundable only. BankAdapter implements all three."
  chart={`flowchart LR
  C[CheckoutService] --> CH[[Chargeable]]
  R[RefundJob] --> RF[[Refundable]]

  W[WalletAdapter] -.-> CH
  W -.-> RF
  B[BankAdapter] -.-> CH
  B -.-> RF
  B -.-> PO`}
/>

- Before: one PaymentGateway with charge, refund, payout and fetchSettlementReport; every adapter had to implement all four.
- Stubbing a method to throw is the [LSP](card:liskov-substitution) side of the same problem.
- Martin (2020): in Java, a client may need recompiling when a method it never calls changes.

## Example

```java
interface Chargeable { void charge(BigDecimal amount); }
interface Refundable { void refund(String paymentId, BigDecimal amount); }
interface Payouts    { void payout(String merchantId, BigDecimal amount); }

class WalletAdapter implements Chargeable, Refundable {   // no payouts, nothing to stub
    public void charge(BigDecimal amount) { }
    public void refund(String paymentId, BigDecimal amount) { }
}
class CheckoutService {
    CheckoutService(Chargeable gateway) { }                 // sees only charge()
}
```

## Interview Qs

### How is ISP different from SRP?

SRP is about why a class changes: one group of people. ISP is about what a client sees: only the methods it needs. One class may still implement several small interfaces.

### A third-party SDK has a huge interface. How do you apply ISP?

Define the small interface your code needs and wrap the SDK in an [adapter](card:adapter) that implements it. Your services then depend only on that small interface.
