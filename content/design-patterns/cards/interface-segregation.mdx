## What it is

The Interface Segregation Principle is the I in SOLID. It says no client should be forced to depend on methods it does not use. Instead of one large interface that serves every caller (a fat interface), you write several small interfaces, each holding the methods one kind of client needs. Fowler calls these role interfaces: each names a role a client plays, such as something that can be charged.

## Why it exists

A fat interface hurts in two ways. A class that implements it must provide every method, even ones it cannot support, so it stubs them to throw or do nothing, which is itself an [LSP](card:liskov-substitution) violation. And because every client depends on the whole interface, a change to a method only one client uses can force the others to recompile and redeploy (Martin, in Java). Splitting the interface by client need removes both problems: each client sees only what it uses.

1. Look at each kind of client and list only the methods it actually calls.
2. Make one interface per kind of client, holding just those methods.
3. Each supplier class implements the interfaces for the roles it can play, and no others.
4. Each client depends on its small interface, so a change elsewhere does not touch it.

So the key is: the interface follows the client's needs, and a supplier implements only the roles it truly supports.

## Example

The fat `PaymentGateway` (charge, refund, payout, fetchSettlementReport) split into roles. A wallet implements only two.

```java
interface Chargeable { void charge(BigDecimal amount); }
interface Refundable { void refund(String paymentId, BigDecimal amount); }
interface Payouts    { void payout(String merchantId, BigDecimal amount); }

class WalletAdapter implements Chargeable, Refundable {   // no payouts: nothing to stub
    public void charge(BigDecimal amount) { }
    public void refund(String paymentId, BigDecimal amount) { }
}
class CheckoutService {
    CheckoutService(Chargeable gateway) { }                // sees only charge()
}
```

What to notice:

- `WalletAdapter` implements two interfaces and has no empty `payout` method to stub, so no [LSP](card:liskov-substitution) trap.
- `CheckoutService` depends on `Chargeable` only, so adding a method to `Payouts` cannot affect it.
- A bank that does everything just implements all three interfaces; splitting never blocks a class that supports every role.

## Rules and defaults

- **Group by client, not by method:** a role interface may have several methods; the unit is a client's needs, not one method.
- **Shared methods may repeat:** if two client roles both need `charge`, it can appear in both interfaces; that is not duplication of knowledge.
- **Java makes it cheap:** a class can list many interfaces in its `implements` clause, so there is no cost to splitting a fat interface into roles.

## Common mistakes

- **"One method per interface."** That fragments related methods and gives each client a pile of tiny interfaces to assemble. Split by the kind of client, keeping a client's methods together.
- **"Just stub the methods you cannot support."** A stub that throws or returns nothing breaks substitutability for callers that expect it to work. Split the interface instead, so the class never has to stub.

## Interview Qs

### How is ISP different from SRP?

[SRP](card:single-responsibility) is about why a class changes: it should answer to one actor. ISP is about what a client sees: it should depend only on the methods it uses. A single class may still implement several small interfaces, so one class can serve several client roles while keeping each client's view minimal.

### A third-party SDK has a huge interface. How do you apply ISP?

Define the small interface your own code needs, and wrap the SDK in an [adapter](card:adapter) that implements it. Your services then depend only on that small interface, not on the SDK's full surface, so changes to methods you never call cannot reach you.

### Why can a fat interface force a client to recompile?

In a statically linked language, a client that depends on an interface depends on all of it. When a method the client never calls changes its signature, the interface changes, so everything depending on it, including that client, may need recompiling and redeploying (Martin). Small role interfaces limit this to the clients that really use the changed method.
