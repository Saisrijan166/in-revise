## Why it exists

After a payment succeeds, receipts, loyalty points and analytics all need to know. Calling each one from PaymentService ties it to every new feature.

## How it works

<Mermaid
  alt="PaymentService, the subject, publishes PaymentSucceeded. It loops over its observer list and calls ReceiptService and LoyaltyService. Neither observer is known to the subject by class, only by the observer interface."
  chart={`flowchart LR
  P[PaymentService: subject] -- PaymentSucceeded --> L{{observer list}}
  L --> R[ReceiptService]
  L --> Y[LoyaltyService]`}
/>

- Observers register with the subject; the subject only knows the observer interface.
- [Push model](card:push-model) sends the data; [pull model](card:pull-model) sends a signal and observers ask.
- Do not rely on notification order; in Spring set it with `@Order` if it matters.

## Example

```java
record PaymentSucceeded(String paymentId) { }

@Service
class PaymentService {
    private final ApplicationEventPublisher events;
    PaymentService(ApplicationEventPublisher events) { this.events = events; }
    void complete(String id) { events.publishEvent(new PaymentSucceeded(id)); }
}

@Component
class ReceiptService {
    @EventListener void on(PaymentSucceeded e) { /* send the receipt */ }
}
```

## Interview Qs

### Do Spring event listeners run in a separate thread?

No. By default publishEvent() waits until every listener finishes, in the caller's thread. Add @Async to a listener, or a custom ApplicationEventMulticaster, for asynchronous handling.

### Why is java.util.Observable deprecated?

Since Java 9. Its event model is limited: notification order is unspecified, and changes do not map one-to-one to notifications. Javadoc points to java.beans, java.util.concurrent or the Flow API instead.

### How do you send the receipt only after the payment commits?

Use @TransactionalEventListener: it runs after commit by default. If no transaction is active, the event is dropped unless fallbackExecution is true.
