## What it is

Observer is a pattern where one object, the **subject**, keeps a list of other objects, the **observers**, and calls a method on each of them whenever its own state changes. The subject knows the observers only through a small interface, not by their real class. So one change in the subject fans out to many reactions, and the subject does not need to know what those reactions are.

## Why it exists

After a payment succeeds, a receipt must go out, loyalty points must be added and analytics must be updated. If `PaymentService` calls each of these directly, it depends on all of them, and every new reaction means editing and re-testing `PaymentService`. With Observer, `PaymentService` only announces "a payment succeeded" to its observer list. Each reaction is a separate observer that registers itself, so new reactions are added without touching `PaymentService`.

## How it works

1. Each observer registers with the subject, so the subject's list fills up with objects it knows only by the observer interface.
2. The subject's state changes, for example a payment is marked succeeded.
3. The subject loops over its list and calls the same interface method on every observer.
4. Each observer runs its own reaction; the subject never learns what any of them did.

So the key is that the subject depends only on the interface, so observers come and go freely.

## Example

In Spring you rarely write the list by hand: `ApplicationEventPublisher` is the subject and `@EventListener` methods are the observers. This publishes one event and one observer reacts.

```java
record PaymentSucceeded(String paymentId) { }

@Service
class PaymentService {
    private final ApplicationEventPublisher events;
    PaymentService(ApplicationEventPublisher events) { this.events = events; }
    void complete(String id) { events.publishEvent(new PaymentSucceeded(id)); }
}

@Component
class ReceiptService {
    @EventListener void on(PaymentSucceeded e) { /* send the receipt */ }
}
```

What to notice:

- `PaymentService` names no receipt, loyalty or analytics class. It only publishes the event, so it is the subject and stays unchanged as reactions are added.
- `ReceiptService` is an observer: Spring finds the `@EventListener` method by the event type and calls it. Adding `LoyaltyService` with its own `@EventListener` needs no change to `PaymentService`.
- `publishEvent` runs the listener in the same thread by default, so `complete` does not return until the receipt code finishes. Add `@Async` to the listener to run it separately.

## Rules and defaults

- **Spring listeners are synchronous:** `@EventListener` methods run in the publisher's thread; the publisher waits for them (Spring Framework 7.0). Add `@Async` (with async enabled) to run on another thread.
- **Notification order is not guaranteed:** if order matters between listeners, set it with `@Order`.
- **@TransactionalEventListener:** runs after the surrounding database transaction commits by default. If no transaction is active, the event is dropped unless `fallbackExecution` is true.
- **java.util.Observer / Observable:** deprecated since Java 9 (not removed). Use Spring events, your own interface, or the `Flow` API instead.

## Not to be confused with

Observer and [publish/subscribe](compare:observer-vs-pub-sub) look alike, but Observer has the subject call its observers directly inside one process, while pub/sub puts a broker between publisher and subscribers so neither side knows the other and the event can be delivered across services. Rule: Observer for reactions inside one app, pub/sub for reactions in other services.

## Common mistakes

- **"Spring events run on a background thread, so publishing is fire-and-forget."** By default the listener runs in the publisher's thread, so a slow or failing listener slows or breaks the publisher. You must add `@Async` for a background thread.

## Interview Qs

### Do Spring event listeners run in a separate thread?

No. By default `publishEvent()` waits until every listener finishes, in the caller's thread. To run a listener separately, add `@Async` to it (with async enabled), or configure a custom `ApplicationEventMulticaster` with an executor.

### Why is java.util.Observable deprecated?

It has been deprecated since Java 9. Its model is weak: notification order is unspecified, and state changes do not map cleanly to notifications. The Javadoc points you to `java.beans`, the `java.util.concurrent` classes, or the `Flow` API for richer, safer event handling.

### How do you send the receipt only after the payment is committed to the database?

Use `@TransactionalEventListener`, which runs after the transaction commits by default. This avoids sending a receipt for a payment that later rolls back. If the listener runs with no active transaction, the event is discarded unless you set `fallbackExecution = true`.
