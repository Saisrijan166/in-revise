## What it is

Chain of Responsibility is a pattern that passes a request along a line of handlers. Each handler is a small object that does one check or step, then either passes the request to the next handler or stops it. The sender does not pick which handler deals with the request; it just gives it to the first one, and the request travels down the chain. This is how Servlet filters and Spring Security's filter chain are built.

## Why it exists

One method that does authentication, then permission, then amount and fraud checks grows into a long block of nested `if` statements. Adding or reordering a check means editing that block and risking the others. Chain of Responsibility makes each check its own handler linked to the next. Each handler stays small, and you add, remove or reorder a check by changing the links, not by rewriting one big method.

## How it works

<Steps label="Paying ₹500: the request passes each handler in order">
  <Step title="Authentication">Is the user logged in? If not, stop here.</Step>
  <Step title="Permission">May this user pay from this account? If not, stop.</Step>
  <Step title="Amount validation">Is ₹500 above zero and within the limit?</Step>
  <Step title="Fraud check">Does it look unusual? Hold or stop it.</Step>
  <Step title="Payment processing">The last link charges the payment.</Step>
</Steps>

1. You write one handler per check, each holding a reference to the next handler.
2. You link the handlers in the order the checks must run.
3. The sender gives the request to the first handler.
4. Each handler does its check, then either calls the next handler or stops the request there.
5. The request ends when a handler stops it, or when it reaches the last handler.

So the key is that each handler knows only its own job and the next link, so the chain is easy to extend and reorder.

## Example

A Servlet filter is a real handler in a chain. It either calls `chain.doFilter()` to pass the request on, or returns without calling it to block.

```java
public class AuthFilter implements Filter {               // jakarta.servlet.Filter
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        if (((HttpServletRequest) req).getHeader("Authorization") == null) {
            ((HttpServletResponse) res).sendError(HttpServletResponse.SC_UNAUTHORIZED);
            return;                                        // stop: do not pass it on
        }
        chain.doFilter(req, res);                          // pass to the next filter
    }
}
```

What to notice:

- `chain.doFilter(req, res)` is the pass-on step: it hands the request to the next handler in the chain.
- The early `return` without calling `doFilter` is how a handler stops the request; nothing after it runs.
- `AuthFilter` knows nothing about the later filters, only that a next link exists, so you can add or reorder filters without editing it.
- The container links the filters, so this is the real pattern, not an analogy.

## Rules and defaults

- **Each handler holds the next:** a handler knows only its own check and a reference to the next link, not the whole chain.
- **First-handler vs pipeline form:** in the classic form the first handler that can deal with the request stops; in a pipeline (filters) every handler runs unless one blocks.
- **Order is part of the design:** place handlers so prerequisites run first, such as authentication before authorisation.
- **End the chain:** without a final handler a request can fall off the end unhandled; add a default last handler or make the last link reject with a clear error.

## Not to be confused with

[Decorator](card:decorator) also wraps calls in a line, each wrapper adding behaviour and then calling the next, so the code looks similar. The difference is that a decorator always passes the call through to add behaviour around it, while a handler in a chain may stop the request and refuse to pass it on. Rule: wrapping to add behaviour to every call is Decorator; passing a request along until one handler stops it is Chain of Responsibility.

## Interview Qs

### What problem does Chain of Responsibility solve?

It replaces one large block of checks with small handlers linked in order. Each handler does one job and passes the request on or stops it. Checks can then be added, removed or reordered by changing the links, without touching the other handlers, which keeps each check small and testable.

### How do Servlet filters and Spring Security use it?

Each Servlet filter does its work and calls `chain.doFilter()` to pass the request on, or returns without it to block. Spring Security's `FilterChainProxy` picks the first `SecurityFilterChain` whose pattern matches the request and runs its ordered filters, such as authentication before authorisation. Both are real chains, not just an analogy.

### What happens if no handler deals with the request?

It falls off the end of the chain unhandled, which can silently allow or drop the request. End the chain with a default handler that handles or rejects anything left, or make the last link reject the request with a clear error, so nothing passes through unchecked.
