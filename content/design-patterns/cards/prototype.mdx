## Why it exists

Some objects take many settings to configure. When you need another one almost the same, copying a configured object is simpler than repeating every step.

## How it works

| | [Shallow copy](card:shallow-copy) | [Deep copy](card:deep-copy) |
|---|---|---|
| Copies | Each field value as it is | Also the mutable objects inside |
| Shared after the copy | Lists and other mutable fields | Nothing mutable |
| In Java | `Object.clone()` by default | A copy constructor that copies lists |
| Risk | Editing one changes the other | More code |

- Immutable fields, like `BigDecimal` or `LocalDate`, are safe to share.

## Example

```java
class RecurringPayment {
    BigDecimal amount; PaymentMethod method; LocalDate dueDate; List<String> tags;

    RecurringPayment(RecurringPayment src) {             // copy constructor
        amount = src.amount; method = src.method;         // immutable: share
        dueDate = src.dueDate;
        tags = new ArrayList<>(src.tags);                 // mutable: copy
    }
}
RecurringPayment next = new RecurringPayment(template);   // ₹500 by UPI, as last month
next.dueDate = template.dueDate.plusMonths(1);            // change only the date
```

## Interview Qs

### How does Prototype differ from clone() in Java?

Prototype is the idea: copy a configured object. `clone()` is one Java way to do it, with pitfalls: it is protected, shallow, and throws CloneNotSupportedException unless the class implements Cloneable. A copy constructor is clearer.

### What happens when a prototype bean is injected into a singleton?

Spring creates it once, when the singleton is created. The singleton keeps that one instance; it does not get a new one per use.
