## What it is

Prototype is a pattern where you create a new object by **copying an existing one** rather than constructing it from scratch. The object you copy is the prototype: a configured template. The copy keeps all of its settings, and you change only the few that differ. This matters most when an object takes many steps to set up. A copy can be **shallow** (the new object shares the inner objects of the original) or **deep** (the inner objects are copied too).

## Why it exists

Some objects take many settings to build: a recurring payment with an amount, a method, a schedule and a list of tags. When you need another one that is almost the same, repeating every setup step is tedious and easy to get subtly wrong. Copying a configured object reuses all of that setup in one step, and you adjust only what is different, such as the next due date. The caller does not even need to know the object's exact class or how it was configured.

## How it works

The decision that matters is shallow versus deep copy.

| | Shallow copy | Deep copy |
|---|---|---|
| Copies | Each field value as it is | Also copies the mutable objects inside |
| After the copy | Lists and other mutable fields are shared | Nothing mutable is shared |
| In Java | `Object.clone()` by default | A copy constructor that copies the lists |
| Risk | Editing one object changes the other | A little more code |

1. Start from a configured object, the template.
2. Copy it. A copy constructor takes the same type and copies its fields.
3. For each field, decide: an immutable value like `BigDecimal` or `LocalDate` is safe to share, so copy the reference. A mutable object like a `List` must be copied, or both objects share it.
4. Change only the fields that differ on the new object. So the key is to deep-copy the mutable fields; everything else can be shared.

## Example

A recurring payment is copied each month with a copy constructor. The mutable list is deep-copied; the immutable values are shared.

```java
class RecurringPayment {
    BigDecimal amount; PaymentMethod method; LocalDate dueDate; List<String> tags;

    RecurringPayment(RecurringPayment src) {              // copy constructor
        amount = src.amount; method = src.method;          // immutable: safe to share
        dueDate = src.dueDate;
        tags = new ArrayList<>(src.tags);                  // mutable list: copy it
    }
}
RecurringPayment next = new RecurringPayment(template);    // reuse last month's setup
next.dueDate = template.dueDate.plusMonths(1);             // change only the date
```

What to notice:

- `tags = new ArrayList<>(src.tags)` makes an independent list. Adding a tag to `next` does not touch `template`.
- `amount`, `method` and `dueDate` are immutable, so sharing the reference is safe; nothing can mutate them through the copy.
- Change `tags = new ArrayList<>(src.tags)` to `tags = src.tags` and the two payments share one list: a tag added to either appears on both. That is the shallow-copy bug.

## Rules and defaults

- **clone() is shallow and awkward:** `Object.clone()` is `protected`, makes a field-by-field shallow copy, and throws `CloneNotSupportedException` unless the class implements `Cloneable`.
- **Cloneable is an empty marker:** it declares no `clone()` method; it only signals that `Object.clone()` is allowed.
- **Prefer a copy constructor:** it is public, easy to read, and lets you deep-copy exactly the fields that need it.
- **Spring prototype scope is unrelated:** it creates a new bean instance on every request and copies nothing; do not confuse the two despite the shared name.

## Common mistakes

- **"A shallow copy is a real, independent copy."** It is not: mutable fields stay shared, so changing one object changes the other. Deep-copy the mutable fields.
- **"A prototype-scoped bean injected into a singleton gives a fresh instance each use."** No. Spring injects it once, when the singleton is created, so the singleton keeps that single instance for its whole life.

## Interview Qs

### How does the Prototype pattern differ from Java's clone()?

Prototype is the idea: create an object by copying a configured one. `clone()` is one Java mechanism for it, with pitfalls: it is protected, makes a shallow copy, and throws unless the class implements `Cloneable`. A copy constructor is a clearer way to implement the same idea and lets you control which fields are deep-copied.

### What is the difference between a shallow and a deep copy?

A shallow copy copies each field value as-is, so the copy and original share the same mutable objects inside, like a list. A deep copy also copies those inner objects, so nothing mutable is shared. Immutable fields can always be shared safely; only mutable ones need deep copying.

### What happens when a prototype-scoped bean is injected into a singleton bean?

Spring resolves the dependency once, when it creates the singleton, and injects one prototype instance. The singleton keeps that same instance for its lifetime; it does not receive a new one per use. To get a fresh instance each time, inject an `ObjectProvider` and call `getObject()`.
