## What it is

Template Method is a pattern where a base class fixes the order of steps of an algorithm in one method, and leaves some steps for subclasses to fill in. That method is called the template method; it calls the steps in order. Some steps are abstract, so every subclass must supply them; some are hooks, with an empty default that a subclass may override. Unlike [Strategy](card:strategy), which passes in an object, Template Method varies the steps through inheritance.

## Why it exists

Several payment processors run the same flow: validate the amount, charge it, then record the result. If each processor writes that flow itself, the copies drift apart and someone may reorder or skip a step. Template Method keeps the flow in one place, in the base class, and lets a subclass change only the step that genuinely differs, here the charge step. The shared steps and the order are written once and cannot be broken by a subclass.

## How it works

<Steps label="process(amount): the order is fixed in the base class">
  <Step title="validate(amount)">Shared step in the base class: reject a zero or negative amount.</Step>
  <Step title="executePayment(amount)">Abstract step: each subclass, UPI or card, must implement it.</Step>
  <Step title="afterPayment()">Hook: empty by default; a subclass may override it to send a receipt.</Step>
</Steps>

1. The base class writes the template method and marks it `final`, so no subclass can change the order.
2. It implements the steps that are the same for everyone, such as `validate`.
3. It declares the varying steps as abstract, so each subclass is forced to supply them.
4. It adds hooks for optional steps, with an empty body the base class calls anyway.
5. The base class calls the subclass's steps, not the other way round. That is the Hollywood principle: "don't call us, we'll call you".

## Example

The base class owns the order; the subclass fills in only the charge step. The amount is validated for everyone.

```java
abstract class PaymentProcessor {
    public final void process(BigDecimal amount) {             // the template method
        if (amount.signum() <= 0) throw new IllegalArgumentException("amount");
        executePayment(amount);                                // varies per subclass
        afterPayment();                                        // hook
    }
    protected abstract void executePayment(BigDecimal amount);
    protected void afterPayment() { }                          // empty by default
}
class UpiProcessor extends PaymentProcessor {
    protected void executePayment(BigDecimal amount) { System.out.println("UPI " + amount); }
}
new UpiProcessor().process(BigDecimal.valueOf(500));
```

```text output
UPI 500
```

What to notice:

- `process` is `final`, so `UpiProcessor` cannot reorder the steps or skip `validate`; it only fills `executePayment`.
- `validate` runs for every subclass, so the amount check is written once and cannot be forgotten.
- `afterPayment` is a hook: `UpiProcessor` leaves it empty, so nothing prints after the charge. A subclass that overrides it would send a receipt there.
- The base class calls the subclass's `executePayment`; the subclass never calls the base flow. That inversion is the pattern's core.

## Rules and defaults

- **Template method is final:** mark it `final` so no subclass can override it and change the fixed order ([JLS 8.4.3.3](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.4.3.3)).
- **Abstract step vs hook:** an abstract step forces every subclass to implement it; a hook has a default body and is optional.
- **Fixed at class-choice time:** the varying step is decided when you pick the subclass, so it cannot change per call; that is the trade-off versus Strategy.
- **Inheritance coupling:** a subclass is tied to the base class's steps and protected methods, so changes to the base can ripple into subclasses.

## Not to be confused with

[Strategy](card:strategy) and Template Method both let one part of an algorithm vary, but by different means. Strategy passes in an object (composition), so the behaviour can change at runtime and even be a lambda. Template Method uses a subclass (inheritance), so the step is fixed once the class is chosen. Rule: fixed order with one or two varying steps is Template Method; the whole algorithm varies or must change at runtime is Strategy.

## Common mistakes

- **"JdbcTemplate is Template Method because of the name."** JdbcTemplate fixes the JDBC workflow (open connection, run, map rows, close) but takes your code as a callback such as a `RowMapper` lambda. You never subclass it, so it is composition, closer to Strategy than Template Method.
- **Leaving the template method overridable.** If it is not `final`, a subclass can override the whole thing and lose the fixed order, which defeats the pattern.

## Interview Qs

### Template Method or Strategy?

Template Method varies steps through subclasses, fixed once the class is chosen. Strategy passes in an object, so the behaviour can change at runtime. Fixed order with one varying step points to Template Method; the whole algorithm varying, or needing to change per call, points to Strategy. See [Strategy vs Template Method](compare:strategy-vs-template-method).

### Where does the JDK use Template Method?

`java.util.AbstractList`. Extend it and implement `get(int)` and `size()`, and its `iterator` and other methods are built on those two, giving a working read-only list. To allow `set`, override `set(int, E)`; to grow or shrink, also add `add(int, E)` and `remove(int)`. The fixed logic lives in the base class; you supply only the varying steps.

### What is a hook method?

A hook is an optional step with an empty or default body that the template method calls. A subclass overrides it only when it needs to, for example sending a receipt after payment. An abstract step, by contrast, must be implemented by every subclass.
