## Why it exists

A million payments that each carry their own copy of the same currency data waste memory. Most of that data is identical, so it can be shared.

## How it works

| Part | Where it lives | Payment example |
| --- | --- | --- |
| Intrinsic state | Inside one shared, immutable object | `Currency` INR: code, symbol, decimals |
| Extrinsic state | Outside, passed in on each use | The amount, the payer |
| Flyweight factory | Hands out the shared instance | `Currency.getInstance("INR")` |

- Shared objects must be immutable, or one user's change leaks to all.
- String literals work the same way: equal literals refer to one interned `String` (JLS 3.10.5).

## Example

```java
Currency inr = Currency.getInstance("INR");
System.out.println(inr == Currency.getInstance("INR"));   // true: one shared instance

Integer a = 127, b = 127, c = 128, d = 128;               // autoboxing (JLS 5.1.7)
System.out.println(a == b);         // true: -128 to 127 are always cached
System.out.println(c == d);         // not guaranteed: do not rely on it
System.out.println(c.equals(d));    // true: compare values with equals
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Integer cache range | -128 to 127 always; more values may be cached | Java SE 25 `Integer.valueOf` |

## Interview Qs

### When is Flyweight worth it?

When an app holds a huge number of similar objects and memory is the problem. Split each into shared intrinsic state and per-use extrinsic state; otherwise the extra complexity is not worth it.

### Where does the JDK use Flyweight?

`Integer.valueOf` and boxing reuse cached objects for -128 to 127, string literals are interned, and `Currency` keeps one instance per currency.
