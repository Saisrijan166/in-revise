## What it is

Flyweight holds many similar objects cheaply by sharing their common part. The data is split in two. The **intrinsic state** is the same across many objects and never changes, so it is kept in one shared, immutable object. The **extrinsic state** differs for each use, so the caller passes it in on each call instead of storing a copy. A factory hands out the shared instance rather than making a new one, so one object stands where thousands of copies would have been.

## Why it exists

Imagine a million payments that each store their own copy of the INR currency details: code, symbol, decimal places. That data is identical for every INR payment, so a million copies waste memory for no benefit. Flyweight keeps one shared `Currency` object and lets every payment reference it, while the amount, which really does differ, stays on each payment. Memory drops from a million copies to one.

## How it works

| Part | Where it lives | Payment example |
| --- | --- | --- |
| Intrinsic state | Inside one shared, immutable object | `Currency` INR: code, symbol, decimal places |
| Extrinsic state | Outside, passed in on each use | The amount, the payer |
| Flyweight factory | Hands out the shared instance | `Currency.getInstance("INR")` |

1. The caller asks the factory for the shared object, for example `Currency.getInstance("INR")`.
2. The factory returns the one existing instance, creating it only the first time.
3. The caller stores just a reference to it, not a copy, so every INR payment points at the same object.
4. The caller passes the changing part, the amount, into each operation instead of storing it in the shared object.

So the key is that the shared object must be immutable, or one caller's change would leak to all.

## Example

The currency object is shared; boxed integers show the same sharing, with its limit.

```java
Currency inr = Currency.getInstance("INR");
System.out.println(inr == Currency.getInstance("INR"));   // one shared instance

Integer a = 127, b = 127, c = 128, d = 128;               // autoboxing (JLS 5.1.7)
System.out.println(a == b);         // -128 to 127 are always cached
System.out.println(c == d);         // 128 is not guaranteed: do not rely on it
System.out.println(c.equals(d));    // compare values with equals
```

```text output
true
true
false
true
```

What to notice:

- `Currency.getInstance("INR")` returns the same object both times, so `==` is `true`; it is a flyweight factory keeping one instance per currency.
- `a == b` is `true` because 127 is inside the guaranteed cache; `c == d` is `false` because 128 may be two objects.
- `c.equals(d)` is `true`: `equals` compares the values, which is why you compare boxed numbers with `equals`, not `==`.
- The amount being paid is never stored in the shared `Currency`; it is passed in per payment, which is the extrinsic state.

## Rules and defaults

- **Immutable shared state:** the shared object must be immutable, or one user's change would affect every user of it.
- **Integer cache range:** `Integer.valueOf` always caches -128 to 127 and may cache more; outside that range it may return new objects, so compare with `equals`. (Java SE 25)
- **String literals:** equal string literals refer to one interned `String` (JLS 3.10.5), the same sharing idea built into the language.
- **Worth it only at scale:** Flyweight pays off only with a large number of similar objects; otherwise the split adds complexity for little gain.

## Interview Qs

### When is Flyweight worth using?

When an application holds a very large number of similar objects and memory is the bottleneck. Split each object into shared intrinsic state and per-use extrinsic state so the common part exists once. With few objects, the extra complexity is not worth it.

### Where does the JDK use Flyweight?

`Integer.valueOf` and autoboxing reuse cached objects for -128 to 127; equal string literals are interned to one `String`; and `Currency` keeps a single instance per currency code. Each shares an immutable object rather than making copies.

### Why can you not compare Integer objects with ==?

`==` compares references. Only -128 to 127 are guaranteed to come from the cache, so two larger equal values such as 1000 may be different objects and `==` returns `false`. Use `equals`, which compares the numeric values.
