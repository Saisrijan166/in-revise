## What it is

This is a design guideline, not a pattern: when you want to reuse behaviour, prefer giving a class another object as a field (composition, a has-a relationship) over making it a subclass of a parent (inheritance, an is-a relationship). The held object does the work, and the holder forwards the call to it, which is called delegation. It is the GoF book's second principle and the idea behind patterns such as [Strategy](card:strategy) and [Decorator](card:decorator).

## Why it exists

Inheritance is the obvious way to reuse code, but a subclass can see and depend on the parent's internals. A later, safe-looking change inside the parent can then break every subclass, a problem named the fragile base class. Inheritance also fixes the choice at compile time: `UpiCheckout extends Checkout` is UPI forever. Composition reuses code through a small interface instead, so each part can change on its own and you can swap it while the program runs.

## How it works

<Compare id="inheritance-vs-composition" />

1. Decide whether the new class truly **is a** kind of the other, or merely **needs** what it does.
2. For a true is-a that can stand in for the parent everywhere, inheritance is fine.
3. Otherwise, hold the other object in a field (compose it) and expose only the interface you need.
4. When a call comes in, forward it to that field (delegate), so the holder stays thin and the part stays swappable.

So the key is: inherit to be a kind of something, compose to use something.

## Example

The same payment need, written both ways. The subclass version grows one class per method; the composed version keeps one class and swaps a part.

```java
// is-a: a new subclass for every payment method
class UpiCheckout extends Checkout {
    @Override void pay(BigDecimal amount) { /* UPI steps */ }
}

// has-a: one class; the strategy is a part you can swap
class PaymentService {
    private final PaymentStrategy strategy;
    PaymentService(PaymentStrategy strategy) { this.strategy = strategy; }
    void checkout(BigDecimal amount) { strategy.pay(amount); }   // delegation
}
```

What to notice:

- The `extends` version ties `UpiCheckout` to `Checkout`'s code; a change in `Checkout.pay` can alter every method's behaviour.
- `PaymentService` depends only on the `PaymentStrategy` interface, so a test can pass a fake and production can pass any method.
- Swapping the behaviour is a different constructor argument, not a new subclass; that is the run-time flexibility the slogan is about.

## Common mistakes

- **"Inheritance is always bad."** A real is-a with a base class designed for extension (documented, stable) is a correct use. The guideline says prefer composition, not forbid inheritance.
- **"Extending a convenient JDK class is fine."** `Stack` extends `Vector`, so it inherits insert-anywhere methods that break stack rules; its own Javadoc recommends `Deque` (for example `ArrayDeque`). Reuse by holding, not by extending for convenience.

## Interview Qs

### Why favour composition over inheritance?

A subclass depends on its parent's internals, so a parent change can break it (the fragile base class problem), and the choice is fixed at compile time. A composed part is reached only through its interface, so it can be tested alone, swapped at run time, and changed without touching the holder.

### When is inheritance the right choice?

When the subclass genuinely is a kind of the parent and can stand in for it anywhere (see [Liskov substitution](card:liskov-substitution)), and the base class was designed and documented for extension. Effective Java (3rd edition, Item 18) gives the same advice.

### Is composition the same as delegation?

No. Composition is the structure: one object holds another in a field. Delegation is the call: the holder forwards work to that part. You normally compose first and then delegate to the held object.
