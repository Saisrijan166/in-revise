## Why it exists

Inheritance reuses code but exposes the parent's insides to every subclass. Composition reuses code through a small interface, so each part can change on its own.

## How it works

<Compare id="inheritance-vs-composition" />

- It is the GoF book's second principle; Effective Java (3rd edition) Item 18 says the same.
- JDK lesson: `Stack` extends `Vector`, so it inherits insert-anywhere methods; its Javadoc recommends `Deque`.
- [Strategy](card:strategy) and [Decorator](card:decorator) are composition at work.

## Example

```java
// is-a: a new subclass for every payment method
class UpiCheckout extends Checkout {
    @Override void pay(BigDecimal amount) { /* UPI steps */ }
}

// has-a: one class; the strategy is a part you can swap
class PaymentService {
    private final PaymentStrategy strategy;
    PaymentService(PaymentStrategy strategy) { this.strategy = strategy; }
    void checkout(BigDecimal amount) { strategy.pay(amount); }
}
```

## Interview Qs

### Why favour composition over inheritance?

A subclass depends on its parent's internals, so a parent change can break it, and the choice is fixed at compile time. A composed part is reached only through its interface, so it can be tested alone and swapped.

### When is inheritance the right choice?

When the subclass truly is a kind of the parent and can stand in for it anywhere (see [Liskov substitution](card:liskov-substitution)), and the base class was designed for extension.

### Is composition the same as delegation?

No. Composition is the structure: one object holds another. Delegation is the call: the holder forwards work to that part.
