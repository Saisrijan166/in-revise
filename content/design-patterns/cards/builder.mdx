## What it is

Builder is a pattern for creating an object through a series of named steps instead of one big constructor call. You start a builder, set the fields you care about by name in any order, and call `build()` to get the finished object. It is most useful when an object has many fields, especially optional ones. A "telescoping constructor" is the problem it replaces: a chain of overloaded constructors, each taking a few more parameters, which grows unreadable as fields are added.

## Why it exists

A constructor like `new PaymentRequest(amount, "INR", UPI, null, null, key)` is easy to get wrong. Same-typed arguments can be swapped without the compiler noticing, the two nulls carry no meaning at the call site, and every optional field forces either a new constructor overload or a null. A builder gives each value a name, lets you leave optional fields out entirely, and checks the result in one place, so the call reads clearly and the object is validated once.

## How it works

1. Call `builder()` to get a fresh builder object that holds the fields, all unset.
2. Call a named setter for each field you want; each returns the builder, so calls chain in one statement.
3. Skip any optional field; it keeps its default, usually null.
4. Call `build()`. It checks the required fields are present and returns the finished object, or throws if one is missing. So the key is that `build()` is the single checkpoint.

## Example

The `PaymentRequest` has two required fields and one optional note. The record's compact constructor does the checking, and the builder provides the named steps.

```java
record PaymentRequest(BigDecimal amount, PaymentMethod method, String note) {
    PaymentRequest {                                 // runs on every new, so on build() too
        Objects.requireNonNull(amount, "amount"); Objects.requireNonNull(method, "method");
    }
    static Builder builder() { return new Builder(); }
    static final class Builder {
        private BigDecimal amount; private PaymentMethod method; private String note;
        Builder amount(BigDecimal v) { amount = v; return this; }    // return this: calls chain
        Builder method(PaymentMethod v) { method = v; return this; }
        Builder note(String v) { note = v; return this; }           // optional
        PaymentRequest build() { return new PaymentRequest(amount, method, note); }
    }
}
PaymentRequest.builder().amount(BigDecimal.valueOf(500)).method(PaymentMethod.UPI).build();
```

What to notice:

- Each setter returns `this`, which is why the calls chain in one line; this chaining is the readable part.
- `note` is simply left out, so an optional field needs no null at the call site.
- The checks live in the record's compact constructor, which `build()` calls. Remove the `requireNonNull` lines and a request with no amount would be built silently. The builder provides the names; the constructor provides the validation.

## Rules and defaults

- **Validation is yours to write:** put the `requireNonNull` and range checks in `build()` or the constructor. A builder does not add them for you.
- **Immutability is yours to design:** make the fields `final` and drop setters on the product. A record (Java 16) does this automatically.
- **JDK example:** `HttpRequest.newBuilder()` returns a builder whose `build()` returns a new immutable `HttpRequest` and throws `IllegalStateException` if no URI was set (Java 11).
- **Few required fields:** reach for a plain constructor or a record first; a builder earns its keep mainly when there are several optional fields.

## Not to be confused with

Builder assembles **one** complex object step by step and returns it at the end. [Abstract Factory](card:abstract-factory) returns each product of a matching **family** at once, usually fully formed. Rule: many optional fields on one object, Builder; a matching set of related objects, Abstract Factory.

## Interview Qs

### What problem does Builder solve that constructors cannot?

Long parameter lists with optional values. Overloaded constructors multiply, and same-typed arguments are easy to swap without the compiler noticing. A builder names each value at the call site, lets you omit optional ones, and checks the result once in `build()`, so construction is both readable and validated.

### Does using a builder make the object immutable?

No. A builder only controls how the object is constructed. If the product still has setters and non-final fields, anyone can change it after `build()`. Immutability comes from final fields and no setters, which a record provides automatically; the builder just supplies the named construction steps.

### When would you not use a builder?

When the object has only a few fields and they are all required. Then a plain constructor or a record is shorter and just as clear. A builder adds a whole extra class, so it is worth it mainly when several fields are optional and call sites would otherwise be confusing.
