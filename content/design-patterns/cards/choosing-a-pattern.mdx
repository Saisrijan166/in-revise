## What it is

Choosing a pattern is a small method for interview and design questions. The interviewer describes a problem, such as a payment method that keeps changing, and expects you to pick a [design pattern](card:what-are-design-patterns) that fits and explain why. This concept gives you two tools: a way to turn the problem you hear into a pattern, and a fixed order for explaining that pattern so your answer stays clear.

## Why it exists

Interviewers almost never say "use the Observer pattern". They say "we must notify email and SMS after a payment succeeds", and you have to recognise the pattern behind the words. Without a method, you either blank, or you name a pattern and then ramble through its class diagram. A fixed order keeps your answer short, shows you understand the problem, and stops you from over-engineering a solution nothing yet needs.

## How it works

Match the problem you heard to a pattern using this picker, then explain the pattern in five beats.

| You hear | Reach for |
| --- | --- |
| **Create:** one shared instance across the app | [Singleton](card:singleton) |
| Pick the right implementation at runtime | [Factory](card:factory-method) |
| A matching family of objects | [Abstract Factory](card:abstract-factory) |
| An object with many optional fields | [Builder](card:builder) |
| Copy an already configured object | [Prototype](card:prototype) |
| **Wrap:** an SDK with a different interface | [Adapter](card:adapter) |
| Add logging or retry around calls | [Decorator](card:decorator) |
| Intercept calls for security or caching | [Proxy](card:proxy) |
| One simple entry over many classes | [Facade](card:facade) |
| Treat one object and a group alike | [Composite](card:composite) |
| Two dimensions that vary independently | [Bridge](card:bridge) |
| Many similar objects eating memory | [Flyweight](card:flyweight) |
| **Behave:** one job done many ways | [Strategy](card:strategy) |
| Fixed steps where one part varies | [Template Method](card:template-method) |
| Behaviour that follows an object's status | [State](card:state) |
| An action to queue, log or undo | [Command](card:command) |
| Ordered checks where any can stop | [Chain of Responsibility](card:chain-of-responsibility) |
| Notify many listeners after an event | [Observer](card:observer) |
| Tangled calls between many objects | [Mediator](card:mediator) |
| Walk a collection without exposing it | [Iterator](card:iterator) |
| Snapshot and restore for undo | [Memento](card:memento) |
| A new operation over fixed types | [Visitor](card:visitor) |
| **App:** keep SQL out of business logic | [Repository](card:repository-and-dao) |
| Hand a class the objects it needs | [Dependency injection](card:dependency-injection) |

1. Listen for the pain in the question, such as "the method grows with every new case", and find its row above.
2. State the problem in one sentence, so the interviewer sees you understood it.
3. Give the idea: the one sentence that makes it that pattern.
4. Show one small example, then name where else the pattern is used, and finish with its trade-off.

So the key is to lead with the problem, not the pattern name. If two patterns seem to fit, [split them by intent](card:pattern-confusions-map).

## Example

Here is the five-beat answer for Strategy, in about 20 seconds.

<Steps label="Explaining Strategy in five beats">
  <Step title="Problem">An if-else over UPI, card and wallet grows every time a new payment method is added.</Step>
  <Step title="Idea">Each method implements one `PaymentStrategy` interface, and `PaymentService` calls the chosen one.</Step>
  <Step title="Example">Paying ₹500 by UPI runs `UpiPayment`; adding a wallet is just one new class, no edit to the service.</Step>
  <Step title="Elsewhere">`Comparator` passed to `List.sort` is the same idea: swappable behaviour handed in.</Step>
  <Step title="Trade-off">More classes, and overkill for two methods that rarely change.</Step>
</Steps>

## Common mistakes

- **"Listing every pattern I know shows breadth."** It shows you cannot choose. Pick the one the requirement needs and defend it; mention alternatives only if asked.
- **"A pattern always makes the design better."** Only when there is a real, present need. Applied too early it adds classes and indirection for no gain, which is [over-engineering](card:anti-patterns).

## Interview Qs

### How do you decide whether to use a pattern at all?

Use one only for a problem you have now, such as a second payment method arriving. If there is no such need, write plain code and refactor to a pattern later, when the need is real. Reaching for a pattern early is [over-engineering](card:anti-patterns) and follows the YAGNI rule: you are not going to need it yet.

### Which patterns commonly fit a payment system?

[Strategy](card:strategy) for the payment methods, [Adapter](card:adapter) for a third-party gateway SDK, [State](card:state) for the PENDING to PAID lifecycle, [Chain of Responsibility](card:chain-of-responsibility) for fraud and limit checks, and [Observer](card:observer) to notify after success. [Repository](card:repository-and-dao) keeps data access out of the logic, and all of it is wired by [dependency injection](card:dependency-injection).

### Any tip for a machine coding or LLD round?

State the problem, then the pattern and why, before writing code. Keep the code working and modular so a new requirement, like another payment method, needs a new class rather than edits across the codebase. Interviewers score extensibility and clarity more than the number of patterns you use.
