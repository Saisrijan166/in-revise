## Why it exists

Interviewers describe a problem, not a pattern. Map it, then explain in a fixed order.

## How it works

| You hear | Use |
| --- | --- |
| **Create:** one shared instance | [Singleton](card:singleton) |
| Pick the right implementation | [Factory](card:factory-method) |
| Matching object family | [Abstract Factory](card:abstract-factory) |
| Many optional fields | [Builder](card:builder) |
| Copy a configured object | [Prototype](card:prototype) |
| **Wrap:** SDK has another interface | [Adapter](card:adapter) |
| Add logging around calls | [Decorator](card:decorator) |
| Intercept calls: security, transactions | [Proxy](card:proxy) |
| One entry over many classes | [Facade](card:facade) |
| Treat one and many alike | [Composite](card:composite) |
| Two dimensions vary independently | [Bridge](card:bridge) |
| Many similar objects eat RAM | [Flyweight](card:flyweight) |
| **Behave:** one job, many ways | [Strategy](card:strategy) |
| Fixed steps, one varies | [Template Method](card:template-method) |
| Behaviour follows payment status | [State](card:state) |
| Queue or undo a refund | [Command](card:command) |
| Ordered checks, any can stop | [Chain of Responsibility](card:chain-of-responsibility) |
| Notify many after success | [Observer](card:observer) |
| Tangled calls between objects | [Mediator](card:mediator) |
| Walk a collection | [Iterator](card:iterator) |
| Snapshot, restore on undo | [Memento](card:memento) |
| New operations, fixed types | [Visitor](card:visitor) |
| **App:** SQL out of business logic | [Repository](card:repository-and-dao) |
| Dependencies handed in | [Dependency injection](card:dependency-injection) |

- Two fit? [Split them by intent](card:pattern-confusions-map).

## Example

<Steps label="The 20-second answer, on Strategy">
  <Step title="Problem">An if-else over UPI, card and wallet grows with each method.</Step>
  <Step title="Idea">Each method implements `PaymentStrategy`; `PaymentService` calls it.</Step>
  <Step title="Example">₹500 by UPI runs `UpiPayment`; wallet is one new class.</Step>
  <Step title="Elsewhere">`Comparator` in `List.sort`.</Step>
  <Step title="Trade-off">More classes; overkill for two that rarely change.</Step>
</Steps>

## Interview Qs

### How do you decide whether to use a pattern at all?

Only for a problem you have now, like a second payment method. Otherwise plain code; refactor later ([overengineering](card:anti-patterns)).

### Which patterns fit a payment system?

[Strategy](card:strategy), [Adapter](card:adapter), [State](card:state), [Chain of Responsibility](card:chain-of-responsibility), [Observer](card:observer), [Repository](card:repository-and-dao), wired by [DI](card:dependency-injection).

### Any tip for a machine coding round?

Name the problem, then the pattern and why. Keep code working and modular, so new requirements need few changes.
