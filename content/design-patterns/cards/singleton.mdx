## What it is

Singleton is a pattern that lets a class have only one object, and gives all callers that same object. The class makes its constructor private, so no other code can call `new`. It keeps the one instance in a static field and hands it out through a static method, usually called `getInstance()`. "Scope" here means the boundary inside which there is one instance: for plain Java that is one per ClassLoader, which in a normal app means one per running JVM.

## Why it exists

Some objects should exist once: an app-wide config holder, a shared registry. If every part of the code could call `new PaymentConfig()`, you would get many copies, each possibly with different settings, and no single source of truth. Making the constructor private stops that. Callers can no longer build their own; they must go through the one access point, so everyone shares the same object.

## How it works

The hard part is creating that one instance safely when several threads ask for it at once. These are the common ways, from simplest to safest.

| Way | Created | Thread-safe? |
|---|---|---|
| Eager `static final` field | When the class is first used | Yes: the JVM runs class setup once |
| [Double-checked locking](card:double-checked-locking) | On the first call | Only if the field is `volatile` |
| [Holder idiom](card:holder-idiom) | On first use of a nested class | Yes: the JVM runs class setup once |
| [Enum](card:enum-singleton) with one constant | When the enum is first used | Yes, and no copies by reflection or deserialisation |

1. Decide when the instance is built: eagerly, when the class loads, or lazily, on the first `getInstance()` call.
2. If it is lazy and plain, two threads can both see the field as null and both build an object. That breaks the single-instance rule.
3. The holder idiom and the enum both lean on a JVM guarantee: a class is initialised only once, and that step is locked, so the instance is built exactly once.
4. So the key is to let class initialisation do the locking for you, rather than writing your own locks.

## Example

The payment service keeps one config holder. The enum form is the one to reach for first.

```java
enum PaymentConfig {
    INSTANCE;                                 // the single object; built once by the JVM
    String currency() { return "INR"; }
}

// Every caller gets the same object:
PaymentConfig.INSTANCE.currency();            // "INR"
boolean same = PaymentConfig.INSTANCE == PaymentConfig.INSTANCE;   // true
```

What to notice:

- `INSTANCE` is the one and only object; writing `enum` with a single constant is the whole pattern.
- There is no `new` anywhere a caller can reach, so no second instance can be created.
- Reflection cannot break it: `Constructor.newInstance` throws `IllegalArgumentException` for an enum class. Deserialisation returns the same constant by name, so no duplicate appears. With a hand-written `private` constructor, both of these can create a second instance.

## Rules and defaults

- **Thread safety is not automatic:** a plain lazy `if (instance == null)` can create two instances under load. Use an enum or the holder idiom.
- **Volatile with double-checked locking:** if you write the classic double-checked form, the field must be `volatile`, or a thread can see a half-built object.
- **Spring default scope:** a Spring bean is `singleton` scope by default, meaning one instance per bean definition per container (Spring Framework 7.0). Two bean definitions of the same class give two instances.
- **Not cluster-wide:** "one instance" is per JVM. Across servers, shared state goes in a database or cache.

## Not to be confused with

A [static utility class](card:static-utility-class) also has a private constructor, but it has no instance at all: only static methods. A singleton is a real object you can pass around, inject, or hide behind an interface. Rule: need an object (state, an interface, a test double) use a singleton; just stateless helper methods use a static class.

## Common mistakes

- **"Spring saves me from writing singletons, so Spring beans are globally unique."** A Spring singleton is per container, so per server. Run three servers and you have three instances of that bean.
- **"Double-checked locking without volatile is fine."** Without `volatile`, the write that stores the object and the writes inside its constructor can be reordered, so another thread sees a non-null reference to an object whose fields are still defaults.

## Interview Qs

### How do you make a singleton thread-safe?

Use a one-constant enum, or the holder idiom where the instance lives in a static field of a nested class. Both rely on the JVM initialising a class only once under a lock, so the object is built exactly once. Double-checked locking also works, but only with a `volatile` field.

### Why does double-checked locking need volatile?

Without it, the write that publishes the reference and the writes inside the constructor can be reordered. A second thread can then see a non-null instance whose fields are still at their defaults. `volatile` forbids that reordering, so a thread that sees the reference also sees a fully built object.

### Is a Spring singleton bean the same as a GoF singleton?

No. A GoF singleton is one instance per ClassLoader. A Spring singleton is one instance per bean definition per container. Two bean definitions of one class give two instances, and separate servers each hold their own, so it is not globally unique.
