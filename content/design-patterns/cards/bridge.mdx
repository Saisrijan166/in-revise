## What it is

Bridge is a way to split one class that varies in two independent directions into two separate class hierarchies. One side is the **abstraction**, the high-level thing the caller uses, such as a kind of payment. The other side is the **implementor**, the low-level work, such as the provider that moves the money. The abstraction holds an implementor in a field and calls it; that field is the bridge. Because the two sides are separate, you can add a payment type or a provider without touching the other.

## Why it exists

Suppose payments vary by type (one-time, subscription) and by provider (UPI, card). If you subclass both at once, you get one class for every pair: `OneTimeUpiPayment`, `SubscriptionCardPayment`, and so on. The count is types times providers, and each new provider multiplies it again. Bridge keeps type and provider as two hierarchies linked by a field, so the count becomes types plus providers, and each side grows on its own.

1. The abstraction `Payment` keeps a `PaymentProvider` field, set when the payment is created.
2. The caller uses a `Payment` subclass, such as `OneTimePayment`, and calls its high-level method.
3. That method does its own high-level logic, then delegates the actual money movement to the provider in its field.
4. To add a provider you write one new `PaymentProvider`; every payment type can use it at once.

So the key is that the two sides meet only through the field, so neither multiplies the other.

## Example

A `Payment` holds a `PaymentProvider` and delegates the real transfer to it.

```java
interface PaymentProvider { void transfer(BigDecimal amount); }      // implementor side
abstract class Payment {                                             // abstraction side
    protected final PaymentProvider provider;                        // the bridge (a field)
    Payment(PaymentProvider provider) { this.provider = provider; }
    abstract void collect(BigDecimal amount);
}
class OneTimePayment extends Payment {
    OneTimePayment(PaymentProvider p) { super(p); }
    @Override void collect(BigDecimal amount) { provider.transfer(amount); }
}
PaymentProvider upi = amount -> System.out.println("UPI transfer " + amount);
new OneTimePayment(upi).collect(BigDecimal.valueOf(500));
```


What to notice:

- `Payment` varies by type through subclasses, while `PaymentProvider` varies by provider through implementations; the two never multiply.
- The `provider` field is the bridge: `collect` does type-level logic, then calls `provider.transfer` for the provider-level work.
- Add a `CardNetworkProvider` and every payment type can use it with no new subclass; add an `EmiPayment` and it works with every provider.
- Here the provider is a lambda; a real one would be a class calling the provider's SDK.

## Rules and defaults

- **Two dimensions:** use Bridge only when a class really varies in two independent ways; one dimension does not need it.
- **Composition, not inheritance of both:** the abstraction holds the implementor rather than subclassing it, which is why the counts add instead of multiply.
- **Plan it early:** Bridge is designed in before the classes exist; retrofitting one mismatched class later is [Adapter](card:adapter), a different intent.

## Not to be confused with

An [adapter](card:adapter) also puts one object behind another through an interface, but it is added after the fact to make an existing, mismatched class fit, and it does not aim to let two sides vary. Rule: two planned dimensions of change means Bridge; making one existing class fit means Adapter.

## Interview Qs

### How is Bridge different from Adapter?

Bridge is planned at design time to let an abstraction and its implementation grow separately, so you choose the two sides up front. Adapter is applied to existing code, to make one class with the wrong interface work with yours. Same code shape, different timing and intent.

### When would you use Bridge?

When a class varies along two independent dimensions and subclassing both would need one class per combination. Split it into an abstraction hierarchy and an implementor hierarchy, and connect them with a field, so the class count adds instead of multiplying.
