## Why it exists

Payments vary in two ways: the type (one-time, subscription) and the provider. Subclassing both gives one class per pair, and each new provider multiplies the count.

## How it works

<Mermaid
  alt="Payment, the abstraction, has two subclasses, OneTimePayment and SubscriptionPayment. Payment holds a PaymentProvider, the implementor, which has two implementations, UpiProvider and CardNetworkProvider."
  chart={`flowchart LR
  P[Payment] -- "has a" --> I{{PaymentProvider}}
  O[OneTimePayment] -- extends --> P
  S[SubscriptionPayment] -- extends --> P
  U[UpiProvider] -- implements --> I
  N[CardNetworkProvider] -- implements --> I`}
/>

- Adding a provider means one new `PaymentProvider` class; every payment type can use it at once.
- It is [composition over inheritance](card:composition-over-inheritance) applied to two dimensions of change.

## Example

```java
interface PaymentProvider { void transfer(BigDecimal amount); }      // implementor side
abstract class Payment {                                             // abstraction side
    protected final PaymentProvider provider;                        // the bridge
    Payment(PaymentProvider provider) { this.provider = provider; }
    abstract void collect(BigDecimal amount);
}
class OneTimePayment extends Payment {
    OneTimePayment(PaymentProvider p) { super(p); }
    @Override void collect(BigDecimal amount) { provider.transfer(amount); }
}
// new OneTimePayment(new UpiProvider()).collect(BigDecimal.valueOf(500));
```

## Interview Qs

### How is Bridge different from Adapter?

Bridge is planned at design time to let an abstraction and its implementation evolve separately. Adapter is applied to existing code, to make an incompatible class work with yours.

### When would you use Bridge?

When a class varies along two independent dimensions and subclassing would need one class per combination. Split it into two hierarchies and connect them with a field.
