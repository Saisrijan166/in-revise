## What it is

Many patterns are built from the same shape: one object holds another and passes work to it. [Adapter](card:adapter), [Decorator](card:decorator) and [Proxy](card:proxy) all look like that, and so do several behavioural pairs. Because the structure is identical, you cannot name a pattern from its class diagram alone. This concept is a set of quick questions that separate the look-alikes by their intent, the problem each one was made to solve.

## Why it exists

In an interview it is easy to call something a Decorator when it is really a Proxy, because their diagrams match exactly. Memorising all thirteen confusable pairs is hard and fades under pressure. One question per pair, tied to the problem the pattern solves, is faster to recall and is what the interviewer wants to hear anyway: not "they look different" but "they solve different problems".

## How it works

Start with the wrappers, which cause the most confusion. Ask one question at a time.

1. Ask whether the wrapper changes the interface the caller sees. If it fits an existing expected interface, it is an Adapter; if it offers one new, simpler interface over many classes, it is a Facade.
2. If the interface stays the same, ask what the wrapper adds: new behaviour means Decorator, access control (security, caching, lazy loading) means Proxy, and holding child objects means Composite.
3. For behaviour pairs, ask who picks the behaviour and when, using the table below.

So the key is that these patterns share a structure but differ in intent. Name the intent and the pattern names itself.

## Example

A single class exposes `charge(amount)` and, inside, calls three separate gateway SDKs for card, UPI and wallet. It is tempting to call it an Adapter because it wraps other classes. It is a Facade: it is not fitting one SDK to an interface the client already expected, it is inventing one simple method over a whole subsystem. The test is intent, not the number of classes wrapped.

## Interview Qs

### Two patterns share the same class diagram. How do you tell them apart?

Ask what problem each one solves. Most patterns here are one object delegating to another, so the structure is the same; only the intent differs. Name the intent, such as "add behaviour" versus "control access", and the pattern follows from it.

### Adapter, Decorator and Proxy all wrap an object. What is the difference?

Only the Adapter changes the interface, fitting a class to one the client expects. Decorator and Proxy keep the interface: a Decorator adds new behaviour the caller wanted, such as logging or retry, while a Proxy controls access to the real object, such as security, caching or lazy loading.

### What do Bridge, State and Strategy have in common, and how do they differ?

All three hold an object behind an interface and delegate to it, so they share one structure. The intent differs: Strategy swaps an interchangeable algorithm chosen by the caller, State changes behaviour as an object's status changes, and Bridge splits an abstraction from its implementation so the two can vary independently.
