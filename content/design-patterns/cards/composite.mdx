## What it is

Composite is a way to build a tree where a single item and a group of items share one interface. A node with no children is a **leaf**, which does the real work. A node that holds children is a **composite**, which forwards each call to its children. Both implement the same interface, called the **component**, so a caller cannot tell whether it holds one item or a whole group. A composite's children are components too, so a child can be another composite, and trees nest to any depth.

## Why it exists

Some data is naturally a tree: a payment split into parts, a folder of files and sub-folders, a menu with sub-menus. Without a shared interface, every caller must check at each node "is this a single item or a group?" and branch with if-else, repeating that check everywhere and breaking when the tree gets deeper. Composite removes the check by giving leaves and groups the same interface, so one call handles the whole tree.

## How it works

1. The caller holds a `PaymentStrategy` and calls `pay`, without checking its kind.
2. If it is a leaf, such as `WalletPayment`, it does the real charge.
3. If it is a composite, it loops over its children and calls `pay` on each.
4. A child that is itself a composite repeats step 3, so the call travels down the whole tree.

So the key is that one `pay` call fans out across every node, leaf or group.

## Example

A split payment is a composite whose children are leaves; calling `pay` fans out to each.

```java
class CompositePayment implements PaymentStrategy {                   // composite
    private final Map<PaymentStrategy, BigDecimal> parts = new LinkedHashMap<>();
    CompositePayment add(PaymentStrategy part, BigDecimal share) { parts.put(part, share); return this; }
    @Override
    public void pay(BigDecimal total) {                               // same method as a leaf
        BigDecimal sum = parts.values().stream().reduce(BigDecimal.ZERO, BigDecimal::add);
        if (sum.compareTo(total) != 0) throw new IllegalArgumentException("shares must add up to " + total);
        parts.forEach((part, share) -> part.pay(share));              // a part may be a composite too
    }
}
new CompositePayment().add(a -> System.out.println("Wallet " + a), BigDecimal.valueOf(300))
    .add(a -> System.out.println("UPI " + a), BigDecimal.valueOf(200)).pay(BigDecimal.valueOf(500));
```

```text output
Wallet 300
UPI 200
```

What to notice:

- `CompositePayment` implements `PaymentStrategy`, the same interface as a single payment, so it can be used wherever one payment is expected.
- `pay` loops over the children and calls `pay` on each; a child could itself be another `CompositePayment`, and the same loop would handle it.
- The check that the shares add up to the total runs once, in the composite, not in every caller.
- Each child here is a leaf written as a lambda; replace one with a nested `CompositePayment` and the caller code does not change.

## Rules and defaults

- **Shared interface:** the composite must implement the same interface as its leaves, or callers could not treat one and many alike.
- **Child methods:** `add` and `remove` live either on the composite only (leaves stay clean) or on the shared interface (every node looks the same but leaves get empty methods); it is a design choice.
- **In the JDK:** `java.awt.Container` is a `Component` that holds other `Component` objects, a UI tree built as a Composite.

## Interview Qs

### When would you use Composite?

When the data is naturally a tree and callers should treat a single item and a group the same way: products packed in nested boxes, a UI of panels holding panels, files in folders, or a payment split across several methods. It removes the per-node "one or many?" check.

### Where should add and remove child methods go?

Two choices. On the composite only keeps leaves clean, but callers must know which node type they hold. On the shared interface lets callers treat every node alike, but leaves inherit methods that make no sense for them. GoF calls the first safer and the second more transparent.

### How does Composite relate to recursion?

A composite forwards a call to its children, and a child may be another composite, so one call recurses down the whole tree. The leaves are the base case that stops the recursion by doing the real work instead of forwarding.
