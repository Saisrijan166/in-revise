## What it is

Visitor is a pattern that lets you add a new operation over a fixed group of classes, called the **elements**, without editing those classes. You put the operation in a separate **visitor** class that has one method per element type. Each element has an `accept(visitor)` method that calls back the matching method on the visitor. So the operation's code lives in the visitor, and the element classes stay untouched when you add another operation.

## Why it exists

Fees, GST and settlement reports each need different logic for `UpiPayment`, `CardPayment` and `WalletPayment`. If you add each one as a method on all three classes, those classes swell with unrelated concerns and change every time a new report appears. Visitor collects one operation into a single class, so a new report is a new visitor and the payment classes are never edited. This fits when the set of types is stable but the operations keep growing.

## How it works

1. The client calls `element.accept(visitor)`. This first call picks the method by the element's runtime type, because `accept` is overridden per element.
2. Inside `accept`, the element calls `visitor.visit(this)`. Because `this` is known here as the concrete type, this second call picks the visitor's matching `visit` method.
3. The chosen `visit` method runs the operation for that exact type and returns its result.

So the key is the two calls, called double dispatch: the element's type and the visitor's type together decide which code runs, which a single overloaded call cannot do.

## Example

Modern Java expresses the same idea without `accept`/`visit`: a sealed interface fixes the types, and an exhaustive switch is the "visitor". This one computes the fee per type.

```java
sealed interface PaymentMethod permits UpiPayment, CardPayment, WalletPayment { }
record UpiPayment() implements PaymentMethod { }
record CardPayment() implements PaymentMethod { }
record WalletPayment() implements PaymentMethod { }

BigDecimal fee(PaymentMethod m, BigDecimal amount) {           // one "visitor"
    return switch (m) {                                        // exhaustive: no default needed
        case UpiPayment u    -> BigDecimal.ZERO;
        case CardPayment c   -> amount.multiply(new BigDecimal("0.02"));   // example rate
        case WalletPayment w -> amount.multiply(new BigDecimal("0.01"));
    };
}
System.out.println(fee(new CardPayment(), BigDecimal.valueOf(500)));
```

```text output
10.00
```

What to notice:

- The switch chooses by the runtime type of `m`, so it does the job that classic Visitor needed `accept`/`visit` and double dispatch to do.
- The interface is `sealed`, so the compiler knows the three permitted types. The switch has no `default`, so it must cover all three; a `gst(...)` method is just another such switch.
- Add a fourth type to the `permits` list and this switch stops compiling until it handles the new case, which is how the compiler stops you forgetting a type.

## Rules and defaults

- **Double dispatch:** classic Visitor needs `accept` on the element (dispatch on the element type) and `visit` on the visitor (dispatch on the visitor), because one Java call dispatches on only one type.
- **Overloads will not do it:** overloaded methods are resolved from the declared (compile-time) type (JLS 15.12), so `visitor.visit(payment)` with `payment` typed as the interface does not reach the per-type overload.
- **Sealed + switch (Java 17 / Java 21):** a sealed interface plus an exhaustive `switch` with no `default` gives compile-time safety when a new type is added; JEP 441 itself notes this replaces much Visitor boilerplate.
- **In the JDK:** `Files.walkFileTree` calls a `FileVisitor` for each file and directory it walks.

## Not to be confused with

[Strategy](card:strategy) swaps one interchangeable behaviour behind one interface, chosen at runtime. Visitor spreads one operation across several fixed element types at once, with a method per type. Rule: Strategy = one behaviour, many implementations; Visitor = one operation over many types.

## Common mistakes

- **"Visitor is always the right tool for operations over a type hierarchy."** Only when the types are stable. If new element types arrive often, every visitor must change, which is painful; plain methods on each class (or a sealed switch) handle changing types better.

## Interview Qs

### When should you use Visitor, and when not?

Use it when the set of element types is stable but new operations over them keep arriving, so each operation becomes one visitor and the element classes stay untouched. Avoid it when new element types are added often, because then every existing visitor must gain a method for each new type.

### Why do you need accept() and double dispatch instead of just overloading visit()?

Java resolves overloaded methods at compile time from the variable's declared type, which is the common interface, so `visitor.visit(payment)` cannot reach the per-type overload. The virtual `accept()` call dispatches on the element's runtime type, and inside it `visitor.visit(this)` dispatches on the visitor; together they pick the exact method.

### What is the modern Java alternative to Visitor?

A sealed interface (Java 17) that fixes the permitted types, with pattern matching for `switch` (Java 21). The compiler knows every permitted type, so an exhaustive `switch` with no `default` must handle each one. Adding a new type makes every such switch fail to compile until it is updated, so no case is silently missed.
