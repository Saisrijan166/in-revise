## Why it exists

Fees, GST and reports all need different logic per payment type. Adding each one as a method to UpiPayment, CardPayment and WalletPayment bloats classes that should stay stable.

## How it works

<Mermaid
  alt="The client calls accept with a FeeVisitor on a CardPayment. The CardPayment calls visit with itself, so the visitor's CardPayment method runs and returns the fee. Two calls pick the code: the element's runtime type and the visitor's type."
  chart={`sequenceDiagram
  participant Cl as Client
  participant P as CardPayment
  participant V as FeeVisitor
  Cl->>P: accept(feeVisitor)
  P->>V: visit(this) as CardPayment
  V-->>Cl: fee`}
/>

- First dispatch picks the element's `accept`; the second picks the visitor's `visit`.
- `GstVisitor` is just another visitor over the same three types.
- JDK: `Files.walkFileTree` calls a `FileVisitor` for each file and directory.

## Example

```java
sealed interface PaymentStrategy permits UpiPayment, CardPayment, WalletPayment {
    void pay(BigDecimal amount);
}

BigDecimal fee(PaymentStrategy method, BigDecimal amount) {    // the "visitor"
    return switch (method) {                                   // exhaustive: no default
        case UpiPayment u    -> BigDecimal.ZERO;
        case CardPayment c   -> amount.multiply(new BigDecimal("0.02"));  // example rate
        case WalletPayment w -> amount.multiply(new BigDecimal("0.01"));
    };
}
```

## Interview Qs

### When should you use Visitor?

When the set of types is stable but new operations keep coming. If new types arrive often, every visitor must change, so plain methods on each class are better.

### What replaces Visitor in modern Java?

A sealed interface (Java 17) with a pattern-matching switch (Java 21). The compiler knows all permitted types, so a switch with no default must cover each one; add a new type and each such switch stops compiling until it handles it.
