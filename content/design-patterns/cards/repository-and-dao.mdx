## Why it exists

When SQL and EntityManager calls sit inside services, every rule change touches query code, and testing a rule needs a database.

## How it works

<Compare id="repository-vs-dao" />

- Spring Data creates a repository proxy for your interface; you write no implementation class.
- A derived query method such as `findByStatus` is parsed from its name; `@Query` gives an explicit query.

## Example

```java
@Entity
public class Payment {
    @Id @GeneratedValue Long id;
    BigDecimal amount;
    PaymentStatus status;                 // CREATED, PENDING, SUCCESS, ...
}

public interface PaymentRepository extends JpaRepository<Payment, Long> {
    List<Payment> findByStatus(PaymentStatus status);   // query built from the name
}
```

## Interview Qs

### Why use a repository instead of calling the EntityManager in the service?

The service then depends on one interface, not on JPA. Business rules stay readable, query code lives in one place, and a unit test can pass an in-memory fake instead of a database.

### How does Spring Data implement an interface you never coded?

It creates a proxy for the interface at bootstrap. CRUD methods come from CrudRepository and JpaRepository; a method like `findByStatus` is turned into a query from its name, or you write one with `@Query`.

### Should you wrap JpaRepository in your own generic repository?

Usually not. The Spring Data interface already is the repository layer, so a generic wrapper repeats it. Add domain-specific query methods to the interface instead.
