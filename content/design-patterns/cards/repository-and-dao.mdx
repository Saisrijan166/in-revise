## What it is

A repository or a DAO is an interface that stands between your business code and the database. Business code calls simple methods on it, like `save(payment)` or `findByStatus(SUCCESS)`, and the actual SQL or JPA code lives behind the interface. The two names come from different books: a Repository looks like a collection of domain objects and speaks in domain words; a DAO (Data Access Object) wraps all access to one data source and speaks in storage words. In Spring they blur, because `@Repository` marks both.

## Why it exists

If the SQL and `EntityManager` calls sit inside your services, every service is tied to the database. Changing one business rule means editing query code, two services may write the same query twice, and testing a rule needs a running database. Putting all data access behind a repository interface keeps the query code in one place and lets business code [depend on the interface](card:dependency-injection), so a test can pass an in-memory fake instead.

## How it works

<Compare id="repository-vs-dao" />

1. You define an interface in domain terms, such as `PaymentRepository` with `save` and `findByStatus`.
2. Your service depends on that interface, not on JDBC or the `EntityManager`.
3. With Spring Data, you extend `JpaRepository`, and at startup Spring creates a proxy that implements the interface for you.
4. A method named `findByStatus` is turned into a query from its name; `@Query` lets you write an explicit query when the name is not enough.

So the service reads like business logic, and the storage details stay in one layer.

## Example

The entity and its repository. The interface has no body, yet both methods work.

```java
@Entity
public class Payment {
    @Id @GeneratedValue Long id;
    BigDecimal amount;
    PaymentStatus status;                 // CREATED, PENDING, SUCCESS, ...
}

public interface PaymentRepository extends JpaRepository<Payment, Long> {
    List<Payment> findByStatus(PaymentStatus status);   // query built from the name
}
```

What to notice:

- `JpaRepository<Payment, Long>` already brings `save`, `findById`, `findAll` and `delete`, so you write none of them.
- `findByStatus` has no body. Spring Data reads the name and builds `where status = ?`; a wrong field name in the method fails at startup, not silently.
- The service injects `PaymentRepository` and never sees SQL, so a test can inject a fake that keeps payments in a list.

## Rules and defaults

- **No implementation class:** Spring Data generates a proxy for each repository interface at startup.
- **Derived queries:** a method whose name follows the rules (`findBy`, `countBy`, `And`, `OrderBy`) becomes a query; otherwise add `@Query`.
- **One repository per aggregate root:** the Spring Data guidance is a repository for each aggregate root, not one per table.
- **@Repository:** optional on a Spring Data interface, but on a hand-written DAO it also turns native persistence exceptions into Spring's `DataAccessException`.

## Not to be confused with

A [service](card:single-responsibility) holds business rules and decides *what* to do; a repository only loads and saves objects and decides *how* to reach storage. Rule: if a method makes a business decision, it belongs in the service; if it only reads or writes data, it belongs in the repository.

## Interview Qs

### Why use a repository instead of calling the EntityManager in the service?

The service then depends on one domain interface, not on JPA. Business rules stay readable, every query lives in one layer instead of being copied across services, and a unit test can inject an in-memory fake rather than start a real database.

### How does Spring Data implement an interface you never coded?

At startup it creates a proxy for the interface. CRUD methods come from `CrudRepository` and `JpaRepository`. A method like `findByStatus` is parsed from its name into a query, or you supply one with `@Query`. You write no implementation class.

### Is Repository a Gang of Four pattern?

No. Repository comes from Fowler's Patterns of Enterprise Application Architecture and Evans's Domain-Driven Design; DAO comes from the Core J2EE Patterns catalogue. Neither is among the original 23 GoF patterns, although both are everyday patterns in enterprise Java.
