## What it is

Debugging with kubectl means reading, in a fixed order, what the cluster has already recorded about a failing object. Kubernetes keeps three records: the object's **status**, its **events** (short notes such as "Pulled image" or "Back-off restarting failed container") and each container's **logs**. kubectl reads all three. Two more commands, `exec` and `debug`, let you run commands inside the Pod when the records are not enough.

## Why it exists

When payment-service fails, guessing is expensive. You might delete the Pod and lose its logs, or blame the network when the Service selector has a typo. The cluster has usually written down the reason already. An outside-in order reads the broadest, cheapest clue first and goes inside a container last, so each step either finds the cause or tells you which command to run next.

## How it works

1. **get.** `kubectl get pods -n payments -o wide` shows each Pod's status, restart count and node. The status word names the failed stage, as in [Pod errors](card:pod-errors).
2. **describe and events.** `kubectl describe pod NAME` shows each container's State and Last State, with Reason and Exit Code, then the Pod's events at the bottom. Scheduling, image pull and probe failures are named here. `kubectl events --for pod/NAME` lists the same events on their own; events are kept only for a short time (see [events and logs](card:observability-in-k8s)).
3. **logs.** `kubectl logs NAME` prints what the app wrote to stdout and stderr. Add `--previous` (or `-p`) for the run that crashed, and `-c NAME` to pick one container in a multi-container Pod.
4. **exec or debug.** `kubectl exec -it NAME -- sh` opens a shell, if the image has one. A small or distroless image often has none, so `kubectl debug` adds an ephemeral container: a temporary extra container, built from an image you choose, inside the running Pod.

So the key is: never jump straight to step 4; steps 1 to 3 solve most cases.

## Example

payment-service Pods are Running and ready, but the Service gives connection errors. Follow the Service path:

```bash
kubectl get endpointslices -n payments -l kubernetes.io/service-name=payment-service
kubectl get svc payment-service -n payments -o jsonpath='{.spec.selector}'; echo
kubectl get pods -n payments --show-labels
```

```text output
NAME                    ADDRESSTYPE   PORTS     ENDPOINTS   AGE
payment-service-gnwgd   IPv4          <unset>   <unset>     23s
{"app":"payments"}
NAME                             READY   STATUS    RESTARTS   AGE   LABELS
payment-service-c5cf79fb-85jgv   1/1     Running   0          26s   app=payment-service,pod-template-hash=c5cf79fb
payment-service-c5cf79fb-n9nff   1/1     Running   0          26s   app=payment-service,pod-template-hash=c5cf79fb
```

What to notice:

- An EndpointSlice with no endpoints means the Service has no Pod to send traffic to. With every Pod ready, the selector must be wrong.
- The Service selects `app: payments`, but the Pods carry `app: payment-service`. One typo, and no network tool would have found it.
- Fix the selector and the endpoints appear within seconds. If they appear but stay not ready, the next suspect is the readiness probe (see [Probes](card:probes)).

## Rules and defaults

- **Service check order:** the Kubernetes Debug Services guide checks that the Service exists, that its name resolves in DNS, that it has EndpointSlices, that its Pods work, and then kube-proxy. Also confirm `targetPort` matches the port the app listens on and that no [NetworkPolicy](card:network-policies) blocks the traffic.
- **kubectl debug:** ephemeral containers are stable since Kubernetes 1.25. They are never restarted and may not have ports or probes.
- **--target:** shares the process namespace of the named container, so `ps` shows the app's processes. It needs support from the container runtime.
- **--copy-to:** debugs a copy of the Pod instead, for example with a changed command or image, when the original crashes too fast to attach to. Delete the copy afterwards.
- **Node debugging:** `kubectl debug node/NAME -it --image=busybox:1.37` starts a Pod on that node with the node's root filesystem mounted at `/host`.
- **Node conditions:** `kubectl describe node` shows Ready, MemoryPressure, DiskPressure, PIDPressure and NetworkUnavailable. Ready becomes Unknown when the node has not reported for the node-monitor grace period, 50 seconds by default.
- **port-forward:** with `service/NAME` or `deployment/NAME`, kubectl picks one matching Pod; the session ends when that Pod ends.

## Not to be confused with

`kubectl exec` runs a command inside an existing container, so it can use only the tools that image contains. `kubectl debug` adds a new container, from an image you choose, to the same Pod, or copies the Pod, or opens a Pod on a node. Rule: exec borrows the app's tools; debug brings your own.

## Common mistakes

- **"Delete the crashing Pod first, to see if a fresh one works."** The old Pod's containers and their logs go with it. Read `describe` and `logs --previous` first, then delete.

## Interview Qs

### A Service does not respond. How do you debug it?

Check that its Pods are ready, that the EndpointSlices list them as ready, and that the Service selector matches the Pod labels. Then check that `targetPort` matches the container port, that the Service name resolves in DNS from another Pod, and that no NetworkPolicy blocks the traffic.

### The image has no shell. How do you look inside?

Use `kubectl debug -it POD --image=busybox:1.37 --target=CONTAINER`. It adds an ephemeral container with your tools to the running Pod, and `--target` lets it see the app's processes. If the app crashes too quickly, `--copy-to` debugs a copy with a different command.

### A node shows NotReady. What do you check?

`kubectl describe node NAME`: the Ready condition, the pressure conditions for memory, disk and process IDs, and recent events. A node that stopped reporting shows Unknown. `kubectl debug node/NAME` opens a shell in a Pod on that node, with its filesystem at `/host`, to check the kubelet and runtime.
