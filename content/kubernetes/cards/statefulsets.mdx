## What it is

A StatefulSet runs Pods that are not interchangeable, such as the replicas of a database. Each Pod gets a fixed name with a number (`payments-db-0`, `payments-db-1`) and its own disk, requested through a PersistentVolumeClaim (PVC), which you will meet in [Persistent Volumes and Claims](card:persistent-storage). A headless Service, one with no shared virtual IP, gives each Pod its own DNS name. Pods start and stop in a fixed order.

## Why it exists

A [Deployment](card:deployments-and-replicasets) treats its Pods as copies: random names, no disk of their own, any order. That is wrong for PostgreSQL. A replacement database Pod must find its own data files again, and a replica must be able to reach the primary by a name that never changes. A StatefulSet ties a name, a DNS entry and a disk to each ordinal, so `payments-db-0` comes back as `payments-db-0` with its data.

## How it works

<Compare id="deployment-vs-statefulset-vs-daemonset" />

1. You create the headless Service and the StatefulSet with `replicas: 2` and a `volumeClaimTemplates` entry.
2. The controller creates `payments-db-0` and a claim `data-payments-db-0` for it, and waits until that Pod is Running and Ready.
3. Only then does it create `payments-db-1` with its own claim, `data-payments-db-1`.
4. If `payments-db-1` is deleted, the controller creates a new Pod with the same name and attaches the same claim, so it sees the same files.
5. On scale-down or a rolling update, it works from the highest number down, one Pod at a time.

So the key is: the number in the name is the identity, and the disk and DNS name follow that number.

## Example

A two-Pod PostgreSQL StatefulSet for payments, with the password read from a Secret:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: payments-db, namespace: payments }
spec:
  serviceName: payments-db          # headless Service: one DNS name per Pod
  replicas: 2
  selector: { matchLabels: { app: payments-db } }
  template:
    metadata: { labels: { app: payments-db } }
    spec:
      containers:
        - { name: postgres, image: "postgres:18", envFrom: [{ secretRef: { name: payments-db } }],
            volumeMounts: [{ name: data, mountPath: /var/lib/postgresql }] }
  volumeClaimTemplates:             # one claim per Pod, named data-payments-db-<n>
    - { metadata: { name: data }, spec: { accessModes: [ReadWriteOnce], resources: { requests: { storage: 1Gi } } } }
```

After applying it with its headless Service and Secret, list the Pods and claims:

```bash
kubectl get pods -n payments -l app=payments-db
kubectl get pvc -n payments -o name
```

```text output
NAME            READY   STATUS    RESTARTS   AGE
payments-db-0   1/1     Running   0          50s
payments-db-1   1/1     Running   0          42s
persistentvolumeclaim/data-payments-db-0
persistentvolumeclaim/data-payments-db-1
```

What to notice:

- The Pods are numbered, not random, and `payments-db-0` is 8 s older: the controller waited for it to be Ready before creating `payments-db-1`. Each Pod has its own claim, named after the template and the Pod.
- `serviceName` points at a headless Service you must create yourself; through it, other Pods reach one replica as `payments-db-0.payments-db.payments.svc.cluster.local`.
- Two Pods means two separate, empty databases. Making `payments-db-1` a copy of `payments-db-0` needs PostgreSQL replication, set up by you or an operator.

## Rules and defaults

- **podManagementPolicy:** `OrderedReady` by default (one Pod at a time, each Ready first). `Parallel` starts and stops all Pods at once; names stay, order goes.
- **Updates:** `RollingUpdate` by default, from the highest ordinal down, one Pod at a time. `OnDelete` updates a Pod only when you delete it.
- **Claims:** deleting or scaling down the StatefulSet keeps its claims. `persistentVolumeClaimRetentionPolicy` (stable since 1.32) can set `whenDeleted` or `whenScaled` to `Delete`.
- **Headless Service:** required for the per-Pod DNS names, and you are responsible for creating it.
- **Do not set a grace period of 0:** the docs call it unsafe. A StatefulSet promises at most one Pod per identity, and a forced delete can leave two `payments-db-1` Pods running, which can lose data.

## Common mistakes

- **"Call payments-db-0 by its Pod IP."** The IP can change when the Pod is recreated; the DNS name through the headless Service does not.

## Interview Qs

### Deployment or StatefulSet for a database?

A StatefulSet, because each replica needs a fixed name and its own disk that follows it. It does not replicate data or fail over, so in production also weigh a managed database or a database operator.

### Why does a StatefulSet need a headless Service?

The headless Service gives each Pod its own DNS name, such as `payments-db-0.payments-db`, instead of one shared virtual IP. Clients can then reach one specific replica, for example the primary, even after its Pod is recreated with a new IP.

### What happens to the volumes when you scale a StatefulSet down?

By default the claims stay, so scaling back up reattaches the same data to the Pod with the same number. `persistentVolumeClaimRetentionPolicy`, stable since Kubernetes 1.32, can delete them on scale-down or on delete instead.
