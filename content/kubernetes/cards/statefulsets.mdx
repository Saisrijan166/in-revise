## Why it exists

Databases and brokers need each replica to keep its name and its disk across restarts. Deployment Pods are interchangeable, with generated names and no per-Pod disk.

## How it works

<Compare id="deployment-vs-statefulset-vs-daemonset" />

- podManagementPolicy Parallel starts and stops Pods together, keeping names but dropping the order.
- Rolling updates go from the highest ordinal down, one Pod at a time.
- Clients connect by Pod DNS name, never by Pod IP.

## Example

```text
$ kubectl get pods,pvc -n payments -l app=payments-db
pod/payments-db-0                          1/1   Running
pod/payments-db-1                          1/1   Running
persistentvolumeclaim/data-payments-db-0   Bound
persistentvolumeclaim/data-payments-db-1   Bound
# DNS: payments-db-0.payments-db.payments.svc.cluster.local
```

## Defaults

| What | Default | Where |
|---|---|---|
| podManagementPolicy | OrderedReady | Kubernetes 1.37 |
| updateStrategy | RollingUpdate (or OnDelete) | Kubernetes 1.37 |

## Interview Qs

### Deployment or StatefulSet for a database?

A StatefulSet, because each replica needs a fixed name and its own volume. It does not replicate or fail over, so for production also weigh a managed database or an operator.

### Why does a StatefulSet need a headless Service?

The headless Service gives each Pod a DNS name such as payments-db-0.payments-db, so clients can reach one specific replica, for example the primary.

### What happens to the volumes when you scale a StatefulSet down?

By default the PVCs stay, so scaling back up reattaches the same data. persistentVolumeClaimRetentionPolicy, stable since 1.32, can delete them instead.
