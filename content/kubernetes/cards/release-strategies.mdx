## Why it exists

A [rolling update](card:rolling-updates-rollbacks) mixes versions and rolls back slowly. Risky releases need an instant way back, or a test on a few real users first.

## How it works

<Compare id="rolling-vs-blue-green-vs-canary" />

- Blue-green: Pods carry `version: blue` or `version: green`; the Service selector picks one set.
- Canary by replicas: both sets share `app: payment-service`; a `track` label tells them apart.
- Weights live on an [HTTPRoute](card:ingress-and-gateway-api); a weight is a share of the rule's total.

## Example

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: payments, namespace: payments }
spec:
  parentRefs: [{ name: public-gateway }]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api/payments } }]
      backendRefs:
        - { name: payment-service-v1, port: 80, weight: 90 }
        - { name: payment-service-v2, port: 80, weight: 10 }
```

## Interview Qs

### How do you do blue-green on plain Kubernetes?

Run two Deployments, payment-service-blue and payment-service-green, with a version label. Test green, then point the Service selector (or the HTTPRoute backend) at green. Rollback is switching it back; remove blue later.

### Why is canary by replica count coarse?

The Service spreads requests over all ready Pods, so the share follows Pod counts: 1 canary among 4 Pods gets about a quarter. A 5% share needs 19 stable Pods. Route weights split by ratio instead.

### How do you decide to promote a canary?

Compare its error rate and latency with the stable version for a fixed time. Argo Rollouts and Flagger automate this: they raise the weight in steps and roll back when a metric check fails.
