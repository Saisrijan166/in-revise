## What it is

Blue-green and canary are two ways to release a new version by moving traffic, not by replacing Pods in place. In both, the old and the new version run at the same time as two separate [Deployments](card:deployments-and-replicasets). Blue-green keeps the new copy (green) idle until you switch all traffic from the old one (blue) at once. Canary sends a small share of real traffic to the new version first, and grows it step by step.

## Why it exists

A [rolling update](card:rolling-updates-rollbacks) mixes versions while it runs, and going back means replacing the Pods again. For a risky payment release you may want a way back that takes seconds, or proof from a few real users before everyone gets it. Blue-green gives the fast switch back, because the old Pods keep running. Canary limits the damage, because a bug in 1.5.0 hits only the small share that reaches it.

## How it works

1. You deploy 1.5.0 as a second Deployment next to 1.4.0. Its Pods carry a label that tells them apart, such as `version: green` or `track: canary`.
2. **Blue-green:** you test green directly, then change the [Service](card:services) selector from `version: blue` to `version: green`. All new requests go to green at once.
3. **Canary:** you send a small share to 1.5.0. Either both Deployments share the Service's label, so the share follows the Pod counts, or an [HTTPRoute](card:ingress-and-gateway-api) splits traffic by weight.
4. You watch error rate and latency for the new version. If they stay healthy, you raise the canary share, or keep green; if not, you switch back or set the canary weight to 0.
5. When the new version has proved itself, you remove the old Deployment.

So both strategies are a traffic switch in front of two Deployments; Kubernetes gives you the pieces, not the procedure.

## Example

The payment route sends 10% of `/api/payments` traffic to the 1.5.0 canary.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: payments, namespace: payments }
spec:
  parentRefs: [{ name: public-gateway }]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api/payments } }]
      backendRefs:
        - { name: payment-service-v1, port: 80, weight: 90 }
        - { name: payment-service-v2, port: 80, weight: 10 }
```

What to notice:

- Each `backendRefs` entry is a separate Service, one per version, each over its own Deployment.
- A weight is a share of the total in this rule, not a %: 90 and 10 out of 100 means 10%. Weights 9 and 1 give the same split.
- To promote, raise `v2`'s weight step by step; to roll back, set it to 0. Pod counts do not change the split.

## Rules and defaults

- **Deployment strategies:** only `RollingUpdate` and `Recreate` exist in the Deployment spec (Kubernetes 1.37).
- **Weights:** a backend's weight defaults to 1; a single backend with weight above 0 takes all the traffic, and weight 0 forwards none (Gateway API v1.6).
- **Blue-green keeps blue:** do not delete the blue Deployment until green has run well for a while; it is your rollback.
- **Tools:** Argo Rollouts and Flagger add a Rollout or Canary resource that shifts traffic in steps, checks metrics and rolls back by itself when a check fails.
- **Data:** both versions run at once and share the database, so schema changes must work with both.

## Not to be confused with

A canary release sends real traffic to a new version of the **code**. A feature flag ships the code to everyone but keeps a feature switched off until you turn it on in configuration. Rule: canary chooses which Pods serve a request; a feature flag chooses which code path runs inside one Pod.

## Interview Qs

### How do you do blue-green on plain Kubernetes?

Run two Deployments, payment-service-blue and payment-service-green, each with its own version label. Test green through a separate Service or port-forward. Then change the main Service selector, or the HTTPRoute backend, to green. Rollback is switching it back. Remove blue only once green has run well.

### Why is canary by replica count coarse?

The Service spreads requests over all ready Pods, so the share follows Pod counts: 1 canary among 4 Pods gets about a quarter. A 5% share would need 19 stable Pods. Route weights, such as HTTPRoute `backendRefs` weights, split by ratio instead, whatever the Pod counts.

### How do you decide to promote a canary?

Compare its error rate and latency with the stable version over a fixed time, with enough traffic to be meaningful. Argo Rollouts and Flagger automate this: they raise the weight in steps, run metric checks after each step, and roll back by themselves when a check fails.
