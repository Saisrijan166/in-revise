## What it is

Pod security has two parts. The first is `securityContext`, a set of fields in the [Pod](card:pods) spec that limit what the container's processes may do on the node: which user ID they run as, whether they can gain more rights, and which Linux capabilities they keep. A capability is one slice of root's power, such as opening raw network sockets. The second part is Pod Security Admission, a check inside the API server that rejects Pods that break one of three levels, chosen per [namespace](card:namespaces-labels-selectors) by a label.

## Why it exists

A container is a process that shares the node's kernel. If it runs as root with extra capabilities, or with `privileged: true`, a bug in the app can let an attacker break out to the node and reach every Pod on it. Each developer could forget a setting, so the cluster cannot trust every manifest. securityContext makes each Pod safe, and admission makes unsafe Pods impossible to create.

1. You label the `payments` namespace with the level to enforce, for example `restricted`, and optionally a level for `warn` and `audit`.
2. When you apply a Deployment, admission checks its Pod template in warn and audit modes only. You may see a warning, but the Deployment is created.
3. When the ReplicaSet creates each Pod, enforce mode checks that Pod. A Pod that breaks the level is rejected, and the reason appears in the ReplicaSet's events.
4. An accepted Pod is scheduled, and the kubelet starts the container with the securityContext settings. With `runAsNonRoot: true`, it refuses to start a container whose image would run as root (UID 0).

So the key is: securityContext makes a Pod safe, and the namespace label makes the safe settings compulsory.

## Example

The payment-service Pod template meets the restricted level, and its namespace enforces it.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels: { pod-security.kubernetes.io/enforce: restricted }
---
# Pod template of the payment-service Deployment (part)
spec:
  securityContext: { runAsNonRoot: true, runAsUser: 1000, seccompProfile: { type: RuntimeDefault } }
  containers:
    - name: payment-service
      image: payment-service:1.4.0
      securityContext: { allowPrivilegeEscalation: false, capabilities: { drop: [ALL] } }
```

What to notice:

- The Pod-level `securityContext` applies to every container; a value set on a container overrides the Pod value for that container.
- `runAsUser: 1000` gives a non-root user, so `runAsNonRoot` passes even if the image has no `USER` line.
- `drop: [ALL]` removes every capability. Restricted lets you add back only `NET_BIND_SERVICE`, needed to listen on ports below 1024.
- Remove `allowPrivilegeEscalation: false` and the namespace rejects every new payment-service Pod.

## Rules and defaults

What the restricted level requires (Kubernetes 1.37):

| Field | Required value | What it stops |
|---|---|---|
| `runAsNonRoot` | `true` | Starting a container whose user is root (UID 0) |
| `allowPrivilegeEscalation` | `false` | A process gaining more rights than its parent |
| `capabilities.drop` | `[ALL]` | Extra kernel powers such as `NET_RAW` |
| `seccompProfile.type` | `RuntimeDefault` or `Localhost` | Unneeded system calls |

- **Levels add up:** baseline already blocks privileged containers, `hostNetwork`, `hostPID` and `hostPath` volumes; restricted adds the table above.
- **Extra hardening:** `readOnlyRootFilesystem: true` stops writes to the container's own files. Restricted does not require it.
- **Modes:** a namespace can set any of `enforce`, `audit` and `warn`, each with its own level. An optional `-version` label pins a level to one Kubernetes version; its value can also be `latest`.
- **Custom rules:** for rules the three levels do not cover, such as allowed image registries, use ValidatingAdmissionPolicy (built in, rules written in CEL, stable since 1.30), Kyverno or OPA Gatekeeper.

## Common mistakes

- **"The Deployment was accepted, so it is compliant."** Enforce checks only Pods. Read the warning and the ReplicaSet events, or the rollout stalls with zero Pods.
- **Switching a busy namespace straight to enforce restricted.** Existing Pods keep running, but replacements fail. Use warn and audit first.

## Interview Qs

### How do you stop containers running as root?

Set `runAsNonRoot: true` in securityContext; the kubelet then refuses any container whose user would be UID 0. Build images with a non-root `USER` or set `runAsUser`. Then enforce the restricted level on the namespace, so a Pod without these settings is rejected.

### What replaced PodSecurityPolicy?

Pod Security Admission, stable since Kubernetes 1.25, the release that removed PodSecurityPolicy. It applies three fixed levels, privileged, baseline and restricted, set by namespace labels. Rules beyond those levels go to ValidatingAdmissionPolicy, Kyverno or OPA Gatekeeper.

### How do you move an existing namespace to restricted safely?

Keep enforce at baseline, and set audit and warn to restricted. Preview with `kubectl label --dry-run=server --overwrite ns payments pod-security.kubernetes.io/enforce=restricted`, which lists the running Pods that would fail. Fix those workloads, then switch enforce to restricted.
