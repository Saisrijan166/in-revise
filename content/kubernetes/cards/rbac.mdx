## What it is

RBAC (role-based access control) is how the [API server](card:kubernetes-architecture) decides whether a caller may do an action. Every `kubectl` command and every program that manages the cluster sends its request to the API server. The caller is called a subject: a user, a group or a [ServiceAccount](card:service-accounts). A Role lists allowed actions, such as "update Deployments", in one [namespace](card:namespaces-labels-selectors), and a RoleBinding gives that Role to subjects.

## Why it exists

Many people and programs use the same cluster. The CI pipeline only needs to update the payment-service Deployment; a developer only needs to read Pods and logs. Without RBAC, any of them could read every Secret or delete any Deployment, and one leaked CI token would give an attacker the whole cluster. RBAC gives each caller only the actions it needs, so a mistake or a leak stays small.

## How it works

<Steps label="One request to the API server">
  <Step title="Authenticate">Who is calling? A client certificate or a token says so. Unknown caller: 401 Unauthorized.</Step>
  <Step title="Authorise">RBAC looks for a rule that allows this verb on this resource. None found: 403 Forbidden.</Step>
  <Step title="Admission">Admission controllers may change or reject a write. One rejection is final.</Step>
  <Step title="Store">The object is validated and saved in etcd.</Step>
</Steps>

1. The CI pipeline runs `kubectl set image` on the payment-service Deployment. The API server first checks the token and learns the caller is `system:serviceaccount:payments:payments-deployer`.
2. RBAC collects every RoleBinding in the `payments` namespace and every ClusterRoleBinding that names this subject.
3. It looks through the rules of those roles for one that matches the API group (`apps`), the resource (`deployments`) and the verb (`patch`). One matching rule is enough.
4. If no rule matches, the request stops with 403 Forbidden. If one matches, it goes on to admission and is saved.

So the key is: no matching rule means no access.

## Example

The CI pipeline gets its own ServiceAccount that may update Deployments in `payments` and nothing else.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: deployer, namespace: payments }
rules:
  - apiGroups: ["apps"]                       # Deployments live in the apps group
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "patch", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: payments-deployer, namespace: payments }
subjects: [{ kind: ServiceAccount, name: payments-deployer, namespace: payments }]
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: Role, name: deployer }
```

What to notice:

- `apiGroups: ["apps"]` is needed because Deployments belong to the `apps` group. Pods, ConfigMaps and Secrets belong to the core group, written as `""`.
- `get` reads one named object and `list` reads all of them. Leave out `list` and `kubectl get deployments` fails with 403.
- The Role has no `delete` and no `secrets`, so a leaked CI token cannot remove the app or read its passwords.
- Both objects live in `payments`, so the rights end at that namespace.

```bash
kubectl auth can-i patch deployments -n payments --as=system:serviceaccount:payments:payments-deployer
kubectl auth can-i get secrets -n payments --as=system:serviceaccount:payments:payments-deployer
```

```text output
yes
no
```

What to notice:

- `--as` makes the API server answer for the CI ServiceAccount instead of for you, using the real bindings.
- `patch` is allowed by the Role; `secrets` appears in no rule, so the answer is `no` and a real request would get 403.

## Rules and defaults

- **Additive only:** there are no deny rules. To take a right away, remove the rule or the binding.
- **roleRef is fixed:** changing it fails validation; delete the binding and create a new one.
- **No privilege escalation:** you can create a Role only with permissions you already hold, and bind a Role only if you hold all its permissions, unless you are granted the `escalate` or `bind` verb.
- **Built-in roles:** `cluster-admin` (everything), `admin`, `edit` and `view`. `edit` can read Secrets and run Pods as any ServiceAccount in the namespace; `view` cannot see Secrets.
- **Hidden reach:** `list` and `watch` on Secrets also return their contents, and anyone who may create Pods in a namespace can mount its Secrets ([Secrets](card:configmaps-and-secrets)).

## Not to be confused with

A Role belongs to one namespace. A ClusterRole has no namespace, so it can cover cluster-wide resources such as nodes, or be reused in many namespaces. A RoleBinding grants rights inside its own namespace, even when it points to a ClusterRole; a ClusterRoleBinding grants them in every namespace. Rule: the binding decides how far the rights reach.

RBAC also differs from a [NetworkPolicy](card:network-policies): RBAC controls API calls, a NetworkPolicy controls Pod network traffic.

## Common mistakes

- **"Give the CI ServiceAccount cluster-admin so the pipeline never fails."** A leaked CI token then controls the whole cluster. Grant a Role per namespace with the exact verbs.
- **Using `*` in verbs or resources.** A wildcard also covers resources and verbs added later, so rights grow without anyone noticing.

## Interview Qs

### How do you check what a ServiceAccount is allowed to do?

Ask the API server: `kubectl auth can-i list configmaps -n payments --as=system:serviceaccount:payments:payment-service` answers yes or no. Add `--list` to print every allowed action in that namespace. This checks the real bindings, so it is safer than reading YAML by hand.

### What is the difference between 401 and 403 from the API server?

401 means authentication failed: the server does not know who you are, for example because the token expired. 403 means you are known, but no RBAC rule allows that verb on that resource. Fix a 403 with a Role and binding, not with a new token.

### Why use a ClusterRole in a RoleBinding?

To write a rule set once, like the built-in `view` or `edit`, and grant it namespace by namespace. The RoleBinding keeps the rights inside its own namespace, so the same ClusterRole can give a team read access in `payments` only.
