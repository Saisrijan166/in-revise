## What it is

A DaemonSet is a workload that runs one copy of a Pod on every node in the cluster, or on every node that matches a selector. It has no replica count: the number of Pods is the number of eligible nodes. It is used for node agents, programs that must run on each machine, such as a log collector that reads that node's log files.

## Why it exists

A log collector must read `/var/log` on every node, so it needs exactly one copy per node. A [Deployment](card:deployments-and-replicasets) with 3 replicas cannot promise that: two copies can share a node, and when a fourth node joins, nothing runs there. You would have to edit the replica count by hand each time the cluster changes. A DaemonSet follows the nodes instead of a number.

## How it works

1. You apply the DaemonSet with a Pod template, and optionally a nodeSelector.
2. The DaemonSet controller lists the nodes that match and creates one Pod for each, aimed at that node.
3. The scheduler binds each Pod to its node, and the node's kubelet starts it.
4. When a node joins, the controller adds a Pod there. When a node is removed, its Pod is garbage collected.
5. When you change the template, the Pods are replaced node by node, one at a time by default.

So the key is: one Pod per eligible node, kept in step with the node list.

## Example

A log agent that reads every node's log files:

```yaml
apiVersion: apps/v1
kind: DaemonSet                    # no replicas field
metadata: { name: log-agent, namespace: logging }
spec:
  selector: { matchLabels: { app: log-agent } }
  template:
    metadata: { labels: { app: log-agent } }
    spec:
      containers:
        - name: agent
          image: log-agent:2.0
          volumeMounts: [{ name: varlog, mountPath: /var/log, readOnly: true }]
      volumes: [{ name: varlog, hostPath: { path: /var/log } }]
```

What to notice:

- There is no `replicas` line. On a 3-node cluster you get 3 Pods; add a node and you get 4.
- The `hostPath` volume mounts the node's own `/var/log` into the Pod, read-only. That is why each node needs its own agent: each Pod reads only its node's files.
- Add `nodeSelector` under the template's `spec` and only matching nodes get an agent.

## Rules and defaults

- **Update strategy (Kubernetes 1.37):** `RollingUpdate` by default, with `maxUnavailable: 1` and `maxSurge: 0`, so one node at a time loses its agent briefly. `OnDelete` replaces a Pod only when you delete it.
- **restartPolicy:** must be `Always`, the default.
- **Automatic tolerations:** DaemonSet Pods tolerate taints such as `node.kubernetes.io/not-ready` and `node.kubernetes.io/unschedulable`, so agents keep running on nodes that are unhealthy or being drained.
- **Tainted nodes:** for other taints, such as on control-plane nodes, add a matching toleration yourself; see [Taints and Tolerations](card:taints-and-tolerations).
- **Typical users:** log collectors, node monitoring agents, network and storage plugins. kubeadm runs kube-proxy as a DaemonSet.

## Interview Qs

### When do you use a DaemonSet?

For an agent that must run on every node, or on every node of a kind: log shipping, node metrics, network or storage plugins. It adds the Pod to new nodes and removes it from nodes that leave, with no replica count to maintain.

### How do you run a DaemonSet on only some nodes?

Set a nodeSelector or node affinity in the Pod template; the controller creates Pods only on matching nodes. To include tainted nodes, such as control-plane nodes, add matching tolerations.

### Why not use a Deployment with replicas equal to the number of nodes?

A Deployment does not guarantee one Pod per node: two replicas can share a node and leave another empty. It also does not react when nodes join or leave, so the count drifts. A DaemonSet ties each Pod to a node.
