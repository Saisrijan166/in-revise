## What it is

Kubernetes architecture is the set of programs that make up a [cluster](card:what-is-kubernetes), split into two halves. The control plane is the decision-making half: it stores what you asked for, chooses where each Pod runs and reacts when something changes. The worker nodes are the machines that run your Pods. Each half is made of a few programs, called components, and they all communicate through one of them, the API server.

## Why it exists

Many machines must agree on one picture of what should run. If every machine kept its own list and talked to every other machine, the lists would drift apart and nobody could manage the cluster as one. Kubernetes keeps a single source of truth, etcd behind the API server, and gives every other component one narrow job: the scheduler places, controllers fix drift, the kubelet runs. When a worker node dies, only its Pods are lost, and the control plane can replace them on other nodes.

Follow what happens when you ask for 3 payment-service Pods:

1. kubectl sends the Deployment to the kube-apiserver, which checks it and saves it in etcd.
2. A controller in kube-controller-manager sees the new Deployment and asks the API server for 3 Pods. They are saved with no node yet. ([Deployments](card:deployments-and-replicasets) shows the exact chain.)
3. The kube-scheduler sees Pods without a node, picks a suitable node for each, and records the choice in the API server. This step is called binding.
4. The kubelet on each chosen node gets its new Pod from the API server and tells the container runtime to start the containers.
5. The kubelet reports the Pod's status back to the API server, so kubectl and the controllers see it running.

So every component reads and writes through the API server; none of them talk to each other directly.

## Example

A one-node [kind](https://kind.sigs.k8s.io/) test cluster runs its control plane components as Pods in the `kube-system` namespace, so you can list them:

```bash
kubectl get pods -n kube-system -o name
```

```text output
pod/coredns-559f6c778d-496p6
pod/coredns-559f6c778d-jj8z7
pod/etcd-k8s-basics-control-plane
pod/kindnet-686b8
pod/kube-apiserver-k8s-basics-control-plane
pod/kube-controller-manager-k8s-basics-control-plane
pod/kube-proxy-7g7mv
pod/kube-scheduler-k8s-basics-control-plane
```

What to notice:

- `etcd`, `kube-apiserver`, `kube-scheduler` and `kube-controller-manager` are the control plane. Their Pod names end with the node they run on.
- `kube-proxy` runs one copy per node, because each node needs its own network rules for [Services](card:services), the stable addresses in front of Pods. `kindnet` is the network plugin kind installs.
- `coredns` is an add-on: cluster DNS that runs as an ordinary workload, here with 2 copies.
- In this one-node test cluster the same node also ran the payment-service Pods. Real setups keep them apart, as the rules below say.

## Rules and defaults

- **Hub and spoke:** all requests from nodes and Pods end at the API server; the other control plane components expose no remote services.
- **etcd access:** access to etcd equals root on the cluster, so ideally only the API server reaches it. Back etcd up; without it the cluster forgets every object.
- **Where the control plane runs:** setup tools usually put all control plane components on the same machines and keep user containers off them. Production spreads them over several machines (see [high availability](card:high-availability)).
- **Worker nodes:** a cluster needs at least one to run Pods.
- **Add-ons:** cluster DNS and similar features run as normal workloads in the `kube-system` namespace. Every cluster should have cluster DNS.

## Not to be confused with

The control plane stores the cluster's state and makes decisions: the API server, etcd, the scheduler and the controller managers. A worker node runs Pods: the kubelet, the container runtime and usually kube-proxy. Rule: the control plane decides, worker nodes do, and they meet only at the API server.

## Common mistakes

- **"The kubelet schedules Pods across the cluster."** The kubelet works only on its own node and only runs Pods already bound to it. Choosing the node is the scheduler's job.

## Interview Qs

### What does etcd store, and why protect it?

Every object: the spec you asked for and the status the cluster reports. Lose etcd without a backup and the cluster forgets its whole state. Access to etcd equals root on the cluster, so only the API server should reach it, over TLS.

### Is kube-proxy always needed?

No. kube-proxy keeps network rules on each node so that traffic to a Service address reaches the right Pods. Some network plugins do that forwarding themselves; with those, nodes do not need kube-proxy.

### What does the cloud-controller-manager do?

It links the cluster to a cloud provider's API: it checks whether a node that stopped responding was deleted in the cloud, sets up network routes, and creates cloud load balancers for Services. Clusters on your own servers or on a laptop do not have one.
