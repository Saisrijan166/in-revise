## What it is

A Pod is the smallest thing Kubernetes runs: a wrapper around one or more containers that always run together on one node. The containers in a Pod share one IP address and can share files through volumes, which are directories the Pod gives its containers. Most Pods hold just one container, like the payment-service Pod. Kubernetes never places a bare container on a node; it places a Pod, and that node's [kubelet](card:kubernetes-architecture) starts the containers inside it.

## Why it exists

Some helpers must sit right next to the app. A log shipper must read the app's log files, and a local proxy must be reachable on the same machine. If Kubernetes placed every container on its own, these two could land on different nodes. A Pod makes them one unit: placed on the same node, given one network address, sharing files, and started and stopped together. For the common one-container case, the Pod is a thin wrapper.

1. You, or a controller, send a Pod manifest to the API server.
2. The scheduler picks a node for the Pod. The Pod is bound to that node for its whole life.
3. The kubelet on that node asks the container runtime to pull each image and start the containers. The Pod gets its own IP address.
4. Containers inside the Pod reach each other on `localhost`. Other Pods reach it on the Pod IP.
5. If a container crashes, the kubelet restarts it inside the same Pod, on the same node. If the Pod is deleted or its node fails, the Pod is gone for good.

So the key is: containers get restarted, Pods get replaced, and only a controller does the replacing.

## Example

The payment-service image from the Docker tech, run as a bare Pod in the `payments` namespace:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-service
  namespace: payments
  labels: { app: payment-service }
spec:
  containers:
    - name: payment-service
      image: payment-service:1.4.0   # fixed tag, so the pull policy becomes IfNotPresent
      ports:
        - containerPort: 8080        # documents the port; does not publish it
```

After `kubectl apply`, delete the Pod and list what is left:

```bash
kubectl delete pod payment-service -n payments
kubectl get pods -n payments
```

```text output
pod "payment-service" deleted from payments namespace
No resources found in payments namespace.
```

What to notice:

- `kind: Pod` has no controller around it, so after the delete nothing creates it again and the namespace is empty. In real apps a Deployment writes this same container list as its Pod template.
- The tag `1.4.0` is fixed, so the node reuses an image it already has. With `:latest` or no tag, the pull policy becomes `Always` and the node pulls on every container start.
- `containerPort` does not make the app reachable from outside the cluster. Other Pods can already reach 10.244.x.x:8080; outside callers need a [Service](card:services), which you will see in the next topic.

## Rules and defaults

- **Restarts stay local:** the kubelet restarts failed containers in the same Pod on the same node. A Pod is never moved to another node.
- **Pod IP:** each new Pod gets a new IP from the cluster network, so callers must never store a Pod IP.
- **imagePullPolicy (Kubernetes 1.37):** if you leave it out, it is set to `Always` for a `:latest` tag or no tag, and to `IfNotPresent` for any other tag or a digest. It is set once, when the Pod is created.
- **Ports inside a Pod:** containers share one port space, so two containers in one Pod cannot listen on the same port.
- **Use a controller:** the Kubernetes docs advise creating Pods through workload resources such as Deployments or Jobs, even when you need only one copy.

## Not to be confused with

A container is one running process started from an image. A Pod is the Kubernetes object that wraps one or more containers and gives them a shared IP, shared volumes and one place on one node. Rule: Kubernetes schedules and replaces Pods; the kubelet starts and restarts containers.

## Interview Qs

### Why does Kubernetes run Pods instead of containers directly?

A Pod gives its containers one network, shared volumes and one lifecycle on one node. That lets a helper, such as a log shipper, sit beside the app and reach it on localhost. Kubernetes schedules and tracks Pods, and the kubelet runs the containers inside them.

### What happens when you delete a Pod?

It depends on who owns it. A Pod you created yourself is gone for good. A Pod owned by a ReplicaSet is replaced, because the ReplicaSet sees one Pod too few and creates a new one, with a new name and usually a new IP.

### Can two containers in one Pod both listen on port 8080?

No. Containers in a Pod share one network namespace, so they share the IP address and the port space. The second container fails to bind the port. Give each container its own port and let them talk over localhost.
