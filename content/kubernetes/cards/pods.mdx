## Why it exists

Tightly coupled processes need the same machine, network and files. A Pod groups them so Kubernetes can place, start and stop them as one unit.

## How it works

<Compare id="container-vs-pod" />

- Most Pods hold one container; a helper container is the exception: [Init Containers and Sidecars](card:multi-container-pods).
- Pods are created from a template by a controller: [Deployments and ReplicaSets](card:deployments-and-replicasets).
- Phases, restarts and shutdown: [Pod Lifecycle](card:pod-lifecycle).

## Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-service
  namespace: payments
spec:
  containers:
    - name: payment-service
      image: payment-service:1.4.0   # fixed tag, so IfNotPresent
      ports:
        - containerPort: 8080        # informational only
```

## Interview Qs

### Why does Kubernetes run Pods instead of containers directly?

A Pod gives its containers one network, shared volumes and one lifecycle, so a helper can sit beside the app. Kubernetes schedules and manages Pods; the containers come along.

### Is a Pod the same as a container?

No. A container runs a process from an image. A Pod wraps one or more containers that share an IP, ports and volumes and always run on the same node.

### What happens when you delete a Pod?

A bare Pod is gone for good. A Pod owned by a ReplicaSet is replaced by a new Pod with a new name and, usually, a new IP.
