## What it is

Observability means you can tell from the outside what a running system is doing. On Kubernetes there are three signals. Logs are the lines the app prints. Events are short records of what Kubernetes itself did to your objects, such as "pulled image" or "killed container". Metrics are numbers measured over time, such as CPU use or requests per second. Kubernetes keeps only a little of each, so long-term storage comes from add-on tools.

## Why it exists

On a single server you log in and read a log file. The payment service runs as 3 Pods that are replaced at every rollout, each with a new name, and an evicted Pod takes its logs with it. Without central logs and metric history, you cannot answer "what happened at 02:10 last night?" or "has memory been growing all week?". Collecting the signals off the Pods keeps the answers after the Pods are gone.

1. The app writes its logs to stdout and stderr. The container runtime saves them in files on the node, and `kubectl logs` reads them through the kubelet.
2. A log agent, run as a [DaemonSet](card:daemonsets) so there is one per node, reads those files and sends every line to a central log store.
3. Kubernetes components record events as API objects. `kubectl describe` shows them at the bottom, and they are deleted after 1 hour by default.
4. The kubelet measures each container's CPU and memory. metrics-server collects the latest values for `kubectl top` and the [HPA](card:autoscaling).
5. Prometheus scrapes, that is, regularly fetches over HTTP, the app's metrics endpoint and kube-state-metrics, which turns object state such as "2 of 3 replicas ready" into metrics. It stores the history, and Grafana draws dashboards from it.

So the key is: Kubernetes shows you the present; add-ons keep the past.

## Example

Where to look for each signal of the payment service:

```bash
kubectl logs deploy/payment-service -n payments --since=10m           # logs from one of its Pods
kubectl logs payment-service-7d9f8-x2k4q -n payments --previous       # the crashed container before this one
kubectl get events -n payments --field-selector type=Warning          # what went wrong, last hour only
kubectl top pods -n payments                                          # live CPU and memory (needs metrics-server)
```

What to notice:

- `--previous` works only because the kubelet keeps one terminated container's logs after a restart; once the Pod is deleted, even that is gone.
- `type=Warning` filters out the routine Normal events, such as Scheduled and Pulled, so problems stand out.
- `kubectl top` shows only the current values; for "memory over the last week" you need Prometheus.
- In Spring Boot 4.1, the app exposes metrics for Prometheus by adding `micrometer-registry-prometheus` and exposing the Actuator `prometheus` endpoint at `/actuator/prometheus`.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Event lifetime | 1 hour (`--event-ttl`) | kube-apiserver, Kubernetes 1.37 |
| Container log rotation | 10Mi per file, 5 files | kubelet, Kubernetes 1.37 |
| metrics-server collection | Every 15 seconds | metrics-server (kubernetes-sigs) |

- **No log storage:** Kubernetes has no built-in store for log data; you add a logging backend.
- **Traces:** OpenTelemetry creates and exports traces, metrics and logs from the app; it is not a storage backend itself.

## Not to be confused with

metrics-server holds only the latest CPU and memory values, so the HPA can scale. Prometheus stores every metric as history, answers queries in PromQL and fires alerts. Rule: metrics-server is for autoscaling now; Prometheus is for monitoring over time. Logs and events also differ: logs come from your app, events come from Kubernetes.

## Interview Qs

### A container keeps crashing. Where are its logs, and how do you keep them?

`kubectl logs --previous` shows the last crashed container, because the kubelet keeps one. When the Pod is deleted or evicted, its logs go too, so run a node log agent as a DaemonSet that ships every line to a central store. You will use these commands in [debugging with kubectl](card:kubectl-debugging).

### How do you monitor a Kubernetes cluster?

Prometheus scrapes the apps and kube-state-metrics and stores the history; Grafana draws dashboards; Prometheus alert rules warn the team when something crosses a limit. Logs go to a central store through a DaemonSet agent. metrics-server only feeds autoscaling and `kubectl top`.
