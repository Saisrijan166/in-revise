## Why it exists

Load changes through the day. Fixed counts waste money at night and fail at the peak, so Kubernetes resizes from metrics.

## How it works

<Compare id="hpa-vs-vpa-vs-cluster-autoscaler" />

- Scale-up acts at once; scale-down waits for the stabilisation window, so replicas do not flap.
- The `behavior` field tunes both directions per HPA: windows, step size and tolerance.

## Example

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: payment-service, namespace: payments }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: payment-service }
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

At 105% average CPU of the 250m request: ceil(3 × 105 ÷ 70) = ceil(4.5) = 5 Pods.

## Defaults

| What | Default | Where |
|---|---|---|
| HPA check interval | 15 s | kube-controller-manager, Kubernetes 1.37 |
| Scale-down stabilisation window | 300 s (scale-up: 0 s) | HPA behaviour, Kubernetes 1.37 |
| Tolerance (no action this close to target) | 10% | HPA, Kubernetes 1.37 |

## Interview Qs

### The HPA is set but never scales. What do you check?

Does `kubectl top pods` work (metrics-server)? Do containers set CPU requests? Then `kubectl describe hpa`: its ScalingActive condition and events say why.

### Horizontal or vertical scaling: which, and when?

Horizontal adds replicas: best for stateless services like payment-service, and it adds availability. Vertical gives each Pod more CPU or memory: for apps that cannot run many copies.

### The HPA wants 10 Pods, but 4 stay Pending. Why?

HPA only sets the replica count. A node autoscaler, Cluster Autoscaler or Karpenter, must add nodes; without one the Pods wait.
