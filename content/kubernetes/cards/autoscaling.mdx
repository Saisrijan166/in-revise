## What it is

Autoscaling means Kubernetes changes the size of an app by itself, from live numbers such as CPU use. There are three kinds. The HorizontalPodAutoscaler (HPA) changes how many Pods a [Deployment](card:deployments-and-replicasets) runs. The VerticalPodAutoscaler (VPA) changes the CPU and memory [requests](card:resource-requests-limits) of each Pod. A node autoscaler, such as Cluster Autoscaler or Karpenter, adds or removes whole nodes.

## Why it exists

Load on payment-service changes through the day. If you fix the replica count for the evening peak, you pay for idle Pods all night; if you fix it for the night, the peak overloads the Pods and payments time out. Changing `replicas` by hand means someone must watch graphs all day. An autoscaler watches the metric for you, adds Pods when load rises and removes them when it falls.

## How it works

1. metrics-server, a small add-on, collects the CPU and memory use of every Pod.
2. Every 15 seconds the HPA reads the average use of the Deployment's Pods and divides it by the request, which gives the utilisation %.
3. It works out `ceil(current replicas × current ÷ target)` and writes that count to the Deployment, within `minReplicas` and `maxReplicas`.
4. The Deployment creates the extra Pods, and the scheduler places them on nodes with enough CPU and memory not yet reserved by other requests.
5. If no node has room, the Pods stay Pending; a node autoscaler sees them and adds a node.

So the HPA decides **how many Pods**; only a node autoscaler decides **how many machines**.

## Example

The HPA for payment-service keeps 3 to 10 Pods and aims for 70% of the CPU request.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: payment-service, namespace: payments }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: payment-service }
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

What to notice:

- `scaleTargetRef` names the Deployment; the HPA changes its replica count and nothing else.
- `averageUtilization: 70` means 70% of each container's CPU request. With a 250m request, the target is 175m per Pod. Remove the request and this metric does nothing.
- At an average of 105%, the HPA asks for ceil(3 × 105 ÷ 70) = ceil(4.5) = 5 Pods.
- `minReplicas: 3` keeps three Pods even at night, so one Pod crashing never leaves the service without a copy.

## Rules and defaults

- **Built in or not:** the HPA API and controller come with Kubernetes; metrics-server, the VPA and node autoscalers are add-ons you install.
- **Check interval:** 15 s, set by kube-controller-manager (Kubernetes 1.37).
- **Tolerance:** no scaling while the ratio is within 10% of the target. Since Kubernetes 1.37 you can also set `tolerance` per HPA under `behavior.scaleUp` or `behavior.scaleDown`.
- **Stabilisation:** scale-down waits 300 s and uses the highest recommendation in that window; scale-up has no window. You can change both under `behavior` (Kubernetes 1.37).
- **Your manifest:** once an HPA manages a Deployment, remove `spec.replicas` from the Deployment's manifest, or every `kubectl apply` resets the count.
- **Scale to zero:** `minReplicas: 0` works only with object or external metrics, never with CPU or memory (beta and on by default in Kubernetes 1.37).
- **VPA modes (VPA 1.8):** `Recreate` (default) evicts Pods to apply new requests; `InPlaceOrRecreate` and `InPlace` resize running Pods; `Initial` sets requests only at creation; `Off` only shows recommendations.

## Not to be confused with

The HPA changes the **number** of Pods, the VPA changes the **size** of each Pod, and a node autoscaler changes the **number of nodes**. Rule: HPA for stateless services with changing load, VPA to find the right requests, a node autoscaler so new Pods have somewhere to run.

## Common mistakes

- **"The HPA adds machines when the cluster is full."** It only sets a replica count. Extra Pods stay Pending until a node autoscaler adds a node.
- **"Node autoscalers react to high CPU on a node."** They react to Pending Pods and to unused requests. They look at what Pods request, not what they really use.

## Interview Qs

### The HPA is set but never scales. What do you check?

First, does `kubectl top pods` work? If not, metrics-server is missing. Second, do the containers set CPU requests? Utilisation is a % of the request, so without one the HPA takes no action. Then run `kubectl describe hpa`: its conditions, such as ScalingActive, and its events say why it is not scaling.

### Horizontal or vertical scaling: which one, and when?

Horizontal scaling adds replicas. It suits stateless services like payment-service, and more copies also mean more availability. Vertical scaling gives each Pod more CPU or memory. It suits apps that cannot run as many copies, and the VPA is mostly used to find good requests.

### Why does the HPA scale down slowly?

To avoid flapping. Load often dips for a moment, and removing Pods then adding them back wastes work and risks errors. The default 300-second scale-down window makes the HPA use the highest recommendation of the last five minutes, while scale-up acts at once.
