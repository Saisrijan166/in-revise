## Why it exists

One app needs many manifests, and each environment changes a few values. Copying YAML per environment drifts; teams need packaging, reuse and a way back.

## How it works

<Compare id="helm-vs-kustomize" />

- Helm is a CLI on your machine that talks to the API server; it needs no database of its own.
- Charts come from a chart repository or an OCI registry (`oci://`).
- Shipping the chart from Git automatically is [GitOps](card:gitops).

## Example

One payment-service chart, two environments:

```bash
helm install payment-service ./payment-chart -n payments -f values-prod.yaml
helm upgrade payment-service ./payment-chart -n payments -f values-prod.yaml \
  --set image.tag=1.4.1
helm history payment-service -n payments      # revisions 1, 2
helm rollback payment-service 1 -n payments   # creates revision 3
# The Kustomize way: base/ + overlays/dev and overlays/prod
kubectl apply -k overlays/prod
```

## Defaults

| What | Default | Where |
|---|---|---|
| `helm rollback` with no revision | The previous revision | Helm 4.3 |
| Release history storage | Kubernetes Secrets in the cluster | Helm 4.3 |
| Kustomize in kubectl | Built in since kubectl 1.14 | Kubernetes |

## Interview Qs

### How do you deploy the same app to dev and prod without copying YAML?

With Helm: one chart and a values file per environment (`-f values-prod.yaml`). With Kustomize: a shared base and an overlay per environment that patches replicas, image tags or resources.

### What are a chart, a release and a revision?

A chart is the package of templates and default values. A release is one installed copy of it, with its own name. Every install, upgrade or rollback adds a numbered revision, shown by `helm history`.
