## What it is

Helm and Kustomize are two tools that turn one set of [manifests](card:kubectl-and-manifests) into the right YAML for each environment. Helm is a package manager. Its package, a chart, holds YAML templates with placeholders plus a `values.yaml` file of default values; Helm fills the placeholders and installs the result as a release. Kustomize uses no templates: you keep plain YAML in a base folder and write a small overlay per environment that changes it.

## Why it exists

The payment service needs a Deployment, a Service, a ConfigMap and an HPA. Dev wants 1 replica and a test image; prod wants 3 replicas and more memory. If you copy the whole folder per environment, a fix made in one copy is forgotten in another. Third-party software, such as PostgreSQL or Prometheus, ships dozens of manifests that you want to install and upgrade as one versioned package. Helm and Kustomize keep one source and change only what differs.

## How it works

<Compare id="helm-vs-kustomize" />

1. `helm install payment-service ./payment-chart -f values-prod.yaml` merges the values: the chart's `values.yaml` first, then your files, then any `--set`.
2. Helm renders the templates into plain manifests on your machine and sends them to the API server.
3. It saves a record of this release, revision 1, as a Secret in the release's namespace. Helm runs no server of its own in the cluster.
4. `helm upgrade` renders again and applies the changes as revision 2. `helm rollback` re-applies an older revision's manifests and records that as a new revision.
5. With Kustomize, `kubectl apply -k overlays/prod` loads the base, applies the overlay's changes and sends the result. Nothing is recorded, so Git is your history.

So the key is: Helm adds packaging and release history; Kustomize adds only patching.

## Example

The prod overlay for the payment service changes two things in the shared base.

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: payments
resources:
  - ../../base               # the shared Deployment, Service and ConfigMap
images:
  - name: payment-service
    newTag: "1.4.1"          # prod runs this image tag
replicas:
  - name: payment-service
    count: 3
```

What to notice:

- The base files stay untouched; the overlay lists only the differences, so a fix in the base reaches dev and prod.
- `images` changes the tag of every container that uses the `payment-service` image, without a patch file.
- `kubectl kustomize overlays/prod` prints the final YAML without applying it, which is a safe way to review a change.

The same change done with Helm, as a release you can roll back:

```bash
helm upgrade payment-service ./payment-chart -n payments -f values-prod.yaml --set image.tag=1.4.1
helm history payment-service -n payments        # lists revisions 1 and 2
helm rollback payment-service -n payments       # back to revision 1, saved as revision 3
```

What to notice:

- `--set image.tag=1.4.1` wins over the same key in `values-prod.yaml`, which wins over the chart's `values.yaml`.
- The rollback names no revision, so Helm picks the previous one. It does not erase revision 2; history only grows.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| `helm rollback` with no revision | The previous revision | Helm 4.3 |
| Release records | Secrets in the release's namespace | Helm 4.3 |
| Kustomize in kubectl | Built in since kubectl 1.14 | Kubernetes |

- **Revisions:** every install, upgrade or rollback adds 1 to the revision number; a rollback never deletes history.
- **Where charts come from:** a chart repository, a local folder, or an OCI registry with `oci://` addresses.
- **Shipping from Git:** applying charts or overlays automatically from a Git repository is [GitOps](card:gitops).

## Not to be confused with

`helm rollback` restores every object of the release, including ConfigMaps and Services. [`kubectl rollout undo`](card:rolling-updates-rollbacks) changes only one Deployment's Pod template back to its previous version. Rule: rollout undo = one Deployment; helm rollback = the whole release.

## Interview Qs

### How do you deploy the same app to dev and prod without copying YAML?

With Helm: one chart and a values file per environment, passed with `-f values-prod.yaml`. With Kustomize: a shared base and an overlay per environment that changes replicas, image tags or resources. Either way, a fix is made once and reaches every environment.

### What are a chart, a release and a revision?

A chart is the package: templates plus default values. A release is one installed copy of it in a cluster, with its own name, so the same chart can be installed twice. Every install, upgrade or rollback adds a numbered revision, which `helm history` lists.

### When would you choose Kustomize over Helm?

For your own app with small per-environment differences, when you want reviewers to read plain YAML with no template logic. Choose Helm to install third-party software, or to ship your app as a versioned package that others install with their own values.
