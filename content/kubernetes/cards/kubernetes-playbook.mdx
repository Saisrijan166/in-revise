## What it is

The playbook is the closing summary of this Kubernetes course. It follows one request, applying the payment-service Deployment, from your terminal to a ready Pod that takes payments. It then lists which object to pick for each need, the defaults worth naming, and the wrong answers interviewers hear most. It adds no new facts: every row links to the concept that teaches it, so you can revise here and jump back where you feel unsure.

## Why it exists

Most Kubernetes questions are either "what happens when…" or "which object would you use for…". Candidates who know each object still lose marks by giving a bare definition, or by repeating a half-truth such as "a failed readiness probe restarts the Pod". One end-to-end path, one picker and one answer order make every answer complete and correct.

## How it works

1. kubectl sends the Deployment to the [API server](card:kubernetes-architecture), using the cluster and credentials in your kubeconfig.
2. The API server authenticates you, checks your permissions with [RBAC](card:rbac), and runs admission controllers, which may reject the object or fill in defaults.
3. It stores the object in etcd and replies. `kubectl apply` returns here.
4. The Deployment controller creates a ReplicaSet, and the ReplicaSet controller creates 3 Pods ([Deployments](card:deployments-and-replicasets)).
5. The [scheduler](card:scheduling) picks a node for each Pod, using its requests, labels and taints.
6. On each node, the kubelet has the container runtime pull `payment-service:1.4.0` and start it.
7. The readiness [probe](card:probes) passes, so the Pod is marked ready.
8. Ready Pods appear in the [Service's](card:services) EndpointSlices and start getting payment requests.

So the key is: apply is done at step 3, but the app is live only at step 8.

## Example

"What is a readiness probe?" answered in five steps:

1. **What:** a check the kubelet runs on a container, such as an HTTP call to `/actuator/health/readiness`, to decide whether the Pod should get traffic.
2. **Why:** a payment-service Pod that is still starting, or has lost its database, would otherwise get requests and fail them.
3. **How:** after a set number of failures in a row, the Pod is marked not ready and leaves the Service's endpoints; when the check passes again, it comes back.
4. **Default:** in Kubernetes 1.37 the probe runs every 10 seconds, and 3 failures in a row mark it failed. A container with no readiness probe counts as ready.
5. **Trap:** a failed readiness probe never restarts the container; that is the liveness probe's job.

## Rules and defaults

Pick the object by the need:

| You need | Use |
|---|---|
| A stateless app with interchangeable copies | [Deployment](card:deployments-and-replicasets) |
| A database with a stable name and its own disk | [StatefulSet](card:statefulsets) with a [PersistentVolumeClaim](card:persistent-storage) |
| One agent Pod on every node | [DaemonSet](card:daemonsets) |
| A task that ends; the same task on a schedule | [Job; CronJob](card:jobs-and-cronjobs) |
| A stable address for a set of Pods | [Service](card:services) |
| HTTP routes from outside the cluster | [Gateway API or Ingress](card:ingress-and-gateway-api) |
| Settings; passwords and keys | [ConfigMap; Secret](card:configmaps-and-secrets) |
| Traffic only to healthy Pods; restarts for stuck ones | [Readiness; liveness probes](card:probes) |
| More Pods under load | [HorizontalPodAutoscaler](card:autoscaling) |
| Enough Pods kept up during node drains | [PodDisruptionBudget](card:high-availability) |
| Who may call the API; which Pods may talk | [RBAC](card:rbac); [NetworkPolicy](card:network-policies) |

Defaults worth naming (Kubernetes 1.37):

| Default | Taught in |
|---|---|
| Service type is ClusterIP | [Services](card:services) |
| Deployment strategy is RollingUpdate, with maxSurge and maxUnavailable at 25% | [Rolling updates](card:rolling-updates-rollbacks) |
| restartPolicy is Always; the grace period is 30 s | [Pod lifecycle](card:pod-lifecycle) |
| No namespace given means the context's namespace, usually default | [Namespaces](card:namespaces-labels-selectors) |
| Secrets are stored unencrypted in etcd unless encryption at rest is turned on | [Secrets](card:configmaps-and-secrets) |

- **Defaults can change:** admission policies, cluster settings or a managed platform can set other values, so say which setting you mean.

## Common mistakes

- **"A failed readiness probe restarts the Pod."** It only stops traffic; a failed [liveness probe](card:probes) restarts the container.
- **"kubectl apply worked, so the app is up."** apply stores the desired state; check `kubectl rollout status` ([rollouts](card:rolling-updates-rollbacks)).
- **"Call the Pod by its IP."** A replaced Pod gets a new IP; call the [Service](card:services) name.
- **"The CPU request caps CPU."** The request reserves CPU for scheduling; the [limit](card:resource-requests-limits) caps it.
- **"Secrets are encrypted."** They are base64-encoded, and stored [unencrypted in etcd](card:configmaps-and-secrets) by default.
- **"CrashLoopBackOff is the cause."** It is a [symptom](card:pod-errors) of a container that keeps exiting.
- **"Kubernetes needs Docker."** It needs any [CRI runtime](card:kubernetes-and-docker), such as containerd.

## Interview Qs

### What happens when you run kubectl apply on a Deployment?

The API server authenticates and authorises the request, runs admission, and stores the Deployment in etcd. The Deployment controller creates a ReplicaSet, which creates the Pods. The scheduler binds each Pod to a node, the kubelet starts the containers, and Pods that pass readiness join the Service's endpoints and receive traffic.

### How would you run a Spring Boot service on Kubernetes?

A Deployment with 3 replicas and a ClusterIP Service, with an HTTPRoute or Ingress for outside traffic. A ConfigMap and a Secret for settings, readiness and liveness probes on the Actuator health endpoints, memory and CPU requests and limits, an HPA for load, and a PodDisruptionBudget for node drains.
