## What it is

A Job is a workload for a task that should finish, such as a database migration or a settlement report. It starts Pods and keeps retrying until the task succeeds, then stops; the finished Pods are not restarted. A CronJob creates a new Job on a schedule written in cron syntax (minute, hour, day of month, month, day of week). Where a [Deployment](card:deployments-and-replicasets) keeps an app running for ever, a Job is meant to end.

## Why it exists

Run a nightly report as a Deployment and its container exits when the report is done; the kubelet restarts it, and the report runs again and again. Batch work needs the opposite rule: run, succeed, stop, and retry only on failure. A Job gives exactly that, plus a retry limit and a time limit. A CronJob adds the clock, so you do not need a cron server outside the cluster.

## How it works

  R -- no --> F[Job Failed]`}
/>

1. At 01:30 the CronJob controller creates a Job from its `jobTemplate`.
2. The Job creates a Pod. Its container runs the report and exits.
3. Exit code 0 means success. The Job counts one completion; when it has enough (1 by default), it is Complete.
4. A non-zero exit is a failure. With `restartPolicy: OnFailure` the kubelet reruns the container in the same Pod; with `Never` the Job creates a new Pod.
5. After `backoffLimit` failures (6 by default), or when `activeDeadlineSeconds` runs out, the Job is marked Failed and its running Pods are stopped.

So the key is: success ends a Job, and only failures cause retries.

## Example

The nightly settlement report for payments, at 01:30 India time:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata: { name: settlement-report, namespace: payments }
spec:
  schedule: "30 1 * * *"             # minute 30, hour 1, every day
  timeZone: Asia/Kolkata
  concurrencyPolicy: Forbid          # skip a run while the last one is still going
  jobTemplate:
    spec:
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers: [{ name: report, image: "settlement-report:1.0" }]
```

What to notice:

- `timeZone` makes 01:30 mean India time. Without it, the schedule uses the local time zone of the kube-controller-manager, which may not be yours.
- `concurrencyPolicy: Forbid` skips a new run if last night's report is still running. Remove it and the default `Allow` lets two reports run at once.
- `restartPolicy: OnFailure` reruns a failed container in the same Pod. A Job accepts only `OnFailure` or `Never`; `Always` is rejected, because a finished container must stay finished.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| backoffLimit (retries) | 6 | Kubernetes 1.37 Job |
| completions, parallelism | 1 each | Kubernetes 1.37 Job |
| concurrencyPolicy | Allow (runs may overlap) | Kubernetes 1.37 CronJob |
| History kept | 3 successful, 1 failed Job | Kubernetes 1.37 CronJob |

- **completions and parallelism:** how many Pods must succeed in total, and how many may run at once.
- **activeDeadlineSeconds:** caps the whole Job's run time and takes precedence over `backoffLimit`.
- **Clean-up:** `ttlSecondsAfterFinished` deletes a finished Job and its Pods after that many seconds; the docs recommend setting it for Jobs no CronJob manages.
- **Retries need care:** a Pod can be started twice even with parallelism 1, so the task must handle leftover files, locks and half-written output.
- **startingDeadlineSeconds:** a run that cannot start within this many seconds of its time is skipped.

## Interview Qs

### What is the difference between a Job and a Deployment?

A Job runs Pods until enough succeed, then stops; its `restartPolicy` must be `Never` or `OnFailure`. A Deployment keeps Pods running all the time and replaces them when they exit, with `restartPolicy: Always`. Use a Job for migrations and reports, a Deployment for servers.

### Last night's CronJob run is still going when the next one is due. What happens?

With the default `Allow`, both run at the same time. Set `concurrencyPolicy: Forbid` to skip the new run, or `Replace` to stop the running Job and start the new one.

### Why must a CronJob's task be idempotent?

Kubernetes does not promise exactly one run per tick: in some situations two Jobs are created, or none, and failed Pods are retried. A settlement task that runs twice must not settle a payment twice, so it should record what it has done and skip finished work.
