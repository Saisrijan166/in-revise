## Why it exists

One image must run in dev, test and prod with different settings. Baking settings or passwords into the image forces a rebuild per environment and leaks credentials.

## How it works

<Compare id="configmap-vs-secret" />

- Deliver one key with `env`, every key with `envFrom`, or mount a volume where each key becomes a file.
- Grant `get` on Secrets narrowly with [RBAC](card:rbac): `list` or `watch` reveals every Secret value in the namespace.
- Anyone who can create a Pod in a namespace can mount its Secrets, so keep each app in its own namespace.

## Example

```yaml
# payment-service container (Deployment Pod template)
containers:
  - name: payment-service
    image: payment-service:1.4.0
    envFrom:
      - configMapRef: { name: payment-config }   # SPRING_PROFILES_ACTIVE=prod
    env:
      - name: SPRING_DATASOURCE_PASSWORD           # Spring Boot binds spring.datasource.password
        valueFrom:
          secretKeyRef: { name: payment-db-secret, key: password }
```

## Defaults

| What | Default | Where |
|---|---|---|
| Secret `type` | Opaque | Kubernetes 1.37 |
| Encryption of Secrets in etcd | Off (stored as plain text) | kube-apiserver, Kubernetes 1.37 |

## Interview Qs

### Is a Secret more secure than an environment variable?

Different things: a Secret stores the value; an env var is one way to hand it over. Env vars leak easily, so mounted files are often preferred (Spring Boot reads them with `configtree:`).

### You changed a ConfigMap. Why does the app still see the old value?

Env vars are set only at container start, so run `kubectl rollout restart deployment/payment-service`. Mounted files update after the kubelet syncs, but the app must re-read them.

### How do you keep Secrets out of Git?

Commit an encrypted [SealedSecret](card:sealed-secrets), or keep values in a vault and sync them with [External Secrets Operator](card:external-secrets-operator). A base64 Secret manifest is readable by anyone who sees the file.
