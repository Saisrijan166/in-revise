## What it is

A ConfigMap is a Kubernetes object that stores plain settings as key-value pairs, such as `SPRING_PROFILES_ACTIVE=prod`. A Secret is the same idea for confidential values, such as the database password. Both live in a [namespace](card:namespaces-labels-selectors), separate from the image, and a [Pod](card:pods) in that same namespace reads them as environment variables or as files in a folder.

## Why it exists

The payment service image must run in dev, test and prod, and each needs a different database URL and password. If you bake those values into the image, you build one image per environment, and the password travels with every copy of the image and its registry. With a ConfigMap and a Secret you build one image, and each cluster supplies its own values when the Pod starts.

## How it works

  alt="The ConfigMap payment-config and the Secret payment-db-secret sit in the payments namespace. When the kubelet starts the payment-service container, it copies their values in, either as environment variables or as files in a mounted folder."
  chart={`flowchart LR
  CM[ConfigMap payment-config] --> K[kubelet starts the container]

  K -- "configMap / secret volume" --> F[Files, one per key]`}

1. You create the ConfigMap and the Secret in the `payments` namespace, with `kubectl apply` or `kubectl create`.
2. The Pod template names them: `envFrom` takes every key, `env.valueFrom` takes one key, and a `configMap` or `secret` volume turns each key into a file.
3. When the kubelet starts the container, it reads the values. Environment variables are fixed from this moment. Mounted files appear under the mount path.
4. If a referenced ConfigMap or Secret does not exist, and the reference is not marked `optional: true`, the container does not start.
5. When you change the object later, the kubelet refreshes mounted files after its sync period plus a cache delay. Environment variables in a running container never change.

So the key is: files can follow a change, environment variables need new Pods.

## Example

First, see what a Secret really stores. This command only prints the object, without creating it:

```bash
kubectl create secret generic payment-db-secret -n payments \
  --from-literal=password=s3cret --dry-run=client -o yaml
```

```text output
apiVersion: v1
data:
  password: czNjcmV0
kind: Secret
metadata:
  name: payment-db-secret
  namespace: payments
```

Then the payment-service container reads both objects:

```yaml
# payment-service Deployment, Pod template
containers:
  - name: payment-service
    image: payment-service:1.4.0
    envFrom:
      - configMapRef: { name: payment-config }    # every key: SPRING_PROFILES_ACTIVE, LOG_LEVEL
    env:
      - name: SPRING_DATASOURCE_PASSWORD          # Spring Boot binds spring.datasource.password
        valueFrom:
          secretKeyRef: { name: payment-db-secret, key: password }
```

What to notice:

- `czNjcmV0` is only `s3cret` in base64: `echo czNjcmV0 | base64 -d` gives the password back. Committing this YAML to Git publishes the password.
- `envFrom` copies every ConfigMap key as a variable; `secretKeyRef` copies one key and gives it a new name, which Spring Boot maps to `spring.datasource.password`.
- If `payment-db-secret` is missing or has no `password` key, the container does not start. Add `optional: true` only for values the app can live without.

## Rules and defaults

- **Same namespace:** a Pod can use only the ConfigMaps and Secrets of its own namespace.
- **Size (Kubernetes 1.37):** each ConfigMap or Secret holds at most 1 MiB. Bigger data belongs in a volume or a database.
- **Secret types:** `Opaque` is the default. Built-in types such as `kubernetes.io/tls` and `kubernetes.io/dockerconfigjson` require certain keys.
- **`stringData`:** lets you write Secret values as plain text in YAML; they are stored base64-encoded under `data`.
- **On the node:** a Secret is sent only to nodes that run a Pod using it, and a mounted Secret is kept in tmpfs (memory), never on the node's disk.
- **Encryption at rest:** off by default. A cluster admin turns it on in the API server configuration.
- **`immutable: true` (stable since 1.21):** the data can no longer change, and the kubelet stops watching the object, which lowers API server load. To change it, delete and recreate it, then restart the Pods.

## Not to be confused with

A ConfigMap and a Secret work the same way; the Secret only adds handling for confidential data, such as tmpfs on the node and built-in types. Rule: same delivery, but anything confidential goes in a Secret.

A Secret is also not the same as an environment variable. The Secret is where the value is stored in the cluster. An environment variable is one way to hand it to a process, and it adds no protection of its own; a mounted file is the other way, and Spring Boot can read a folder of such files with `configtree:`. Rule: Secret = storage; environment variable or file = delivery.

## Common mistakes

- **"I updated the ConfigMap, so the app uses the new value."** Environment variables need new Pods. Mounted files change on disk, but the app still has to re-read them, and a `subPath` mount never changes.
- **"Base64 is safe enough to commit."** Anyone with the file decodes it. Commit an encrypted [SealedSecret](card:sealed-secrets), or keep values in a vault and sync them with the [External Secrets Operator](card:external-secrets-operator).

## Interview Qs

### Is a Secret more secure than an environment variable?

They are different things. A Secret stores the value in the cluster; an environment variable is one way to pass it into the container. A Secret can also be mounted as a file instead. Environment variables are not a secure store, so protect the Secret itself with encryption at rest and RBAC.

### You changed a ConfigMap. Why does the app still see the old value?

If the app reads it through environment variables, they were set when the container started, so run `kubectl rollout restart deployment/payment-service`. If it reads mounted files, the kubelet updates them after its sync delay, but the app must re-read the file, and a `subPath` mount never updates.

### How do you protect Secrets in a cluster?

Turn on encryption at rest so etcd holds ciphertext. Grant `get` on Secrets narrowly with [RBAC](card:rbac), and almost never `list` or `watch`, because those return every Secret's value. Give each app its own namespace, since creating a Pod is enough to read a Secret. Keep real values out of Git.
