## What it is

A rolling update is how a [Deployment](card:deployments-and-replicasets) moves to a new version: it replaces old Pods with new ones a few at a time instead of all at once. Each version of the Pod template is a revision, kept as its own ReplicaSet. A rollback is going back to an earlier revision, by scaling its ReplicaSet up again.

## Why it exists

To upgrade payment-service without this, you would stop every 1.4.0 Pod and then start the 1.5.0 Pods. Customers get errors for the whole gap, and if 1.5.0 is broken, nothing serves at all. A rolling update keeps most Pods serving during the change and stops when new Pods do not become Ready. Keeping old ReplicaSets means a bad release is undone in seconds, without rebuilding anything.

## How it works

1. You change the Pod template, for example the image from 1.4.0 to 1.5.0. The Deployment creates a new ReplicaSet with 0 Pods.
2. It works out its limits. `maxSurge` is how many Pods may run above the replica count; `maxUnavailable` is how many may be missing. With 3 replicas and the 25% defaults they round to 1 and 0: at most 4 Pods, at least 3 available.
3. The new ReplicaSet starts one 1.5.0 Pod. The Deployment waits until the Pod passes its [readiness probe](card:probes).
4. The old ReplicaSet then stops one 1.4.0 Pod, and steps 3 and 4 repeat until 3 new Pods run.
5. The old ReplicaSet stays at 0 replicas as the previous revision. `kubectl rollout undo` scales it back up the same rolling way.

So readiness is the brake: a version that never becomes Ready never replaces the old Pods.

## Example

You release payment-service 1.5.0, record why, and check the history.

```bash
kubectl -n payments set image deployment/payment-service payment-service=payment-service:1.5.0
kubectl -n payments annotate deployment/payment-service kubernetes.io/change-cause="1.5.0: UPI retry fix"
kubectl -n payments rollout status deployment/payment-service
kubectl -n payments rollout history deployment/payment-service
kubectl -n payments rollout undo deployment/payment-service    # or --to-revision=1
```

What to notice:

- `set image` changes the Pod template, so it starts a new revision. `kubectl scale` would not.
- The `kubernetes.io/change-cause` annotation is what `rollout history` shows in its CHANGE-CAUSE column. The old `--record` flag for this is deprecated.
- `rollout status` waits and fails if the rollout passes its progress deadline, so a CI job can stop on a bad release.
- `rollout undo` does not delete the new ReplicaSet. It makes the old template current again, which gets a new revision number.

## Rules and defaults

- **Strategy:** `RollingUpdate` by default; the other choice is `Recreate`, which stops all old Pods before any new one starts (Kubernetes 1.37).
- **Surge and unavailable:** both 25% by default. A % `maxSurge` rounds up, a % `maxUnavailable` rounds down, and the two cannot both be 0.
- **minReadySeconds:** 0 by default. Set it, for example to 10, so a Pod must stay Ready that long before it counts as available.
- **progressDeadlineSeconds:** 600 by default. When it passes, the Deployment reports `ProgressDeadlineExceeded` and keeps trying; it never rolls back by itself.
- **revisionHistoryLimit:** 10 old ReplicaSets kept by default. Set it to 0 and you cannot undo.
- **Restart without a change:** `kubectl rollout restart` rolls all Pods with the same version, for example to reload a changed Secret.

## Not to be confused with

A rolling update mixes old and new Pods behind one Service for a short time. [Blue-green and canary](card:release-strategies) run two separate sets of Pods and move traffic between them. Rule: a rolling update is built into the Deployment; blue-green and canary need a second Deployment and a traffic switch.

## Common mistakes

- **"Scaling the Deployment creates a revision I can roll back."** Only Pod template changes create revisions. Changing `replicas` does not.
- **"maxUnavailable 0 is always safest."** It never loses capacity, but each step needs room for a surge Pod. On a full cluster the new Pod stays Pending and the rollout stalls.

## Interview Qs

### What do maxSurge and maxUnavailable mean with 4 replicas?

With the 25% defaults both become 1: up to 5 Pods may run and at least 3 must be available. `maxSurge: 1` with `maxUnavailable: 0` never drops below 4 available Pods, but needs room for one extra Pod. `maxSurge: 0` with `maxUnavailable: 1` needs no extra room but runs one Pod short.

### A rollout is stuck. What happens, and what do you do?

The old Pods keep serving, because unready new Pods do not replace them. After `progressDeadlineSeconds` the Deployment reports ProgressDeadlineExceeded, but nothing is rolled back. Check the new Pods' events and logs, then fix forward or run `kubectl rollout undo`.

### When would you choose Recreate over RollingUpdate?

When two versions must never run at the same time, for example when the new version needs an incompatible schema change, or the app holds a lock only one version may take. The price is a short outage between stopping the old Pods and starting the new ones.
