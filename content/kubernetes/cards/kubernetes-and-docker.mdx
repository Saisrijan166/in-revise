## What it is

The Container Runtime Interface (CRI) is the standard API through which Kubernetes runs the containers you build with Docker. Docker is a tool that builds images and runs containers on one machine, but Kubernetes never builds images. On each node, the [kubelet](card:kubernetes-architecture) asks a container runtime, the program that actually runs containers, to pull the image and start it. Because the request goes through CRI, any runtime that implements CRI works.

## Why it exists

Early Kubernetes talked to Docker Engine through a built-in adapter called dockershim. That tied Kubernetes to one product and added a needless layer, because Docker Engine itself runs containers through containerd. With CRI, the kubelet speaks one API to any runtime, so Kubernetes removed dockershim in version 1.24. Your images did not change: Docker builds them in the standard OCI image format, which every runtime can run.

## How it works

1. You build the payment-service image with `docker build` and push it to a registry, a server that stores images.
2. The scheduler binds a Pod that uses this image to a node.
3. The kubelet on that node calls the runtime over CRI, a gRPC API, to pull the image and create the container.
4. containerd or CRI-O hands the actual start to a low-level OCI runtime such as runc, which creates the isolated Linux process.
5. The kubelet keeps asking the runtime for each container's state and reports it to the API server.

So Docker's job ends at the registry; from there, the node's runtime takes over.

## Example

You build and push with Docker, as in the Docker tech. Nothing in this step mentions Kubernetes:

```bash
docker build -t registry.example.com/payments/payment-service:1.4.0 .
docker push registry.example.com/payments/payment-service:1.4.0
```

Then you ask the cluster which runtime each node uses:

```bash
kubectl get nodes -o custom-columns=NODE:.metadata.name,RUNTIME:.status.nodeInfo.containerRuntimeVersion
```

```text output
NODE                       RUNTIME
k8s-basics-control-plane   containerd://2.3.4
```

What to notice:

- The node runs containerd 2.3.4, the runtime kind nodes use, not Docker Engine. The image built with `docker build` still runs on it.
- The kubelet reports this value after asking the runtime, over CRI, for its name and version.
- The image name in the Pod spec must match what you pushed, including the tag; the runtime pulls exactly that.

## Rules and defaults

- **dockershim:** removed in Kubernetes 1.24. Docker Engine on a node now needs the cri-dockerd adapter, maintained outside the Kubernetes project by Mirantis and Docker.
- **CRI version:** since Kubernetes 1.26 the kubelet needs a runtime that supports the v1 CRI API. Otherwise the node does not register.
- **Supported runtimes:** containerd, CRI-O, or any other CRI implementation.

## Not to be confused with

Docker Engine is the full tool on one machine: CLI, image builds, networks and volumes. containerd is the runtime underneath that runs containers; Docker Engine uses it, and Kubernetes can use it directly. Rule: Docker builds, containerd runs, Kubernetes decides where.

## Interview Qs

### Why do we need Kubernetes when Docker already exists?

Docker packages an app as an image and runs containers on one host. Kubernetes coordinates many hosts: it schedules Pods onto nodes, replaces failed ones, scales copies, gives them stable network names and rolls out new versions. Teams use both: Docker to build, Kubernetes to run in production.

### Can Kubernetes run without Docker?

Yes. Each node needs a CRI runtime, most often containerd or CRI-O. Docker Engine works only through the cri-dockerd adapter. Developers can still build with Docker, because the images are standard OCI images.

### Is Docker Compose the same as Kubernetes?

No. Compose starts a multi-container app from one file on one host, which suits local development, tests and single-host deployments. Kubernetes adds scheduling across many nodes, replacement of lost Pods, rolling updates and autoscaling.
