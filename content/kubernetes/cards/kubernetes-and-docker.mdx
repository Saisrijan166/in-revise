## Why it exists

People mix up the tool that builds containers with the system that runs them at scale. Kubernetes needs only a runtime that speaks CRI on each node.

## How it works

<Compare id="docker-vs-compose-vs-kubernetes" />

- On a node: kubelet → CRI → containerd or CRI-O → runc starts the container.
- Docker Engine itself uses containerd inside, so moving nodes to containerd drops a layer.
- Where the runtime sits in the cluster: [Kubernetes architecture](card:kubernetes-architecture).

## Example

```bash
docker build -t registry.example.com/payments/payment-service:1.4.0 .
docker push registry.example.com/payments/payment-service:1.4.0
kubectl apply -f payment-service.yaml   # the node's runtime pulls and runs it
kubectl get nodes -o wide               # CONTAINER-RUNTIME, e.g. containerd://...
```

## Interview Qs

### Does Kubernetes replace Docker?

No. Docker builds and ships images; Kubernetes schedules and heals containers across machines. Teams still build with Docker, then let Kubernetes run the images on containerd or CRI-O.

### Can Kubernetes run without Docker?

Yes. It needs any CRI runtime on each node, most often containerd or CRI-O. Docker Engine still works only through the cri-dockerd adapter, kept by Mirantis and Docker.

### Is Docker Compose the same as Kubernetes?

No. Compose starts a multi-container app from one file on one host: good for local development, tests and single-host deploys. Kubernetes adds scheduling over many nodes, self-healing and rolling updates.
