## What it is

A probe is a health check that the [kubelet](card:kubernetes-architecture), the agent on each node, runs on a container again and again. The kubelet can see that a container's process is running, but not whether the app inside it works. A probe asks the app itself, for example by calling an HTTP URL, and the kubelet acts on the answer. There are three probes, each with its own question and its own action when the answer is "no".

## Why it exists

Without probes, Kubernetes treats a container as healthy while its process exists. A payment service stuck in a deadlock keeps its process alive, so nobody restarts it, and payments hang. A new payment Pod that is still loading its Spring context gets requests from the [Service](card:services) at once, so the first payments fail. Probes let the app say "I am stuck" or "I am not ready yet", and Kubernetes restarts it or holds traffic back.

## How it works

<Compare id="liveness-vs-readiness-vs-startup" />

1. When the container starts, the kubelet runs the startup probe, if there is one. Liveness and readiness wait until it passes once. If it fails `failureThreshold` times in a row, the kubelet kills the container and restarts it.
2. After that, the kubelet runs the liveness and readiness probes every `periodSeconds`, for the whole life of the container. Each probe uses one check: `httpGet` passes on an HTTP status from 200 to 399, `tcpSocket` if the port accepts a connection, `exec` if a command exits with 0, and `grpc` if the gRPC health check answers SERVING.
3. When readiness fails `failureThreshold` times in a row, the kubelet sets the Pod's `Ready` condition to false. The Pod's IP is then removed from the EndpointSlices of every Service that selects it, so new requests go to the other replicas. Readiness keeps running, and when it passes again, traffic returns.
4. When liveness fails `failureThreshold` times in a row, the kubelet kills the container and restarts it, following the Pod's `restartPolicy`.

So readiness controls traffic, and liveness and startup control restarts.

## Example

The payment service container from the Deployment, with all three probes on Spring Boot's Actuator health URLs:

```yaml
# payment-service container (Spring Boot 4.1, port 8080)
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30        # 30 x 10 s = up to 300 s to boot
  periodSeconds: 10
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
```

What to notice:

- The startup probe gives the app up to 300 seconds to boot, and liveness does not run during that time. Remove it, and a boot slower than about 30 seconds is killed by liveness before it finishes.
- Startup and liveness use the same liveness URL. Spring Boot's liveness group reports only the app's own state, so a database outage does not restart the Pods.
- Readiness runs every 5 seconds, so with the default `failureThreshold` of 3 a Pod leaves the Service after about 15 seconds of failures and comes back soon after it recovers.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| `initialDelaySeconds` | 0 | Kubernetes 1.37 |
| `periodSeconds` / `timeoutSeconds` | 10 s / 1 s | Kubernetes 1.37 |
| `failureThreshold` / `successThreshold` | 3 / 1 | Kubernetes 1.37 |
| Actuator liveness and readiness groups | on | Spring Boot 4.1 |

- **successThreshold:** must be 1 for liveness and startup probes; only readiness may ask for several successes in a row.
- **Startup budget:** the time a startup probe allows is `failureThreshold × periodSeconds`.
- **A probe that is not set:** counts as passing. With no liveness probe, only a crash restarts the container. With no startup probe, liveness and readiness start right away.
- **Spring Boot 4.1:** `/actuator/health/liveness` and `/actuator/health/readiness` are on by default; `management.endpoint.health.probes.enabled=false` turns them off.

## Common mistakes

- **"A long initialDelaySeconds is the way to handle a slow start."** The delay must cover the slowest boot, and a real hang in that time goes unnoticed. A startup probe ends as soon as the app is up, and liveness takes over at once.
- **"Put the database check in readiness, to be safe."** If every replica shares that database, an outage takes all of them out of the Service together. Include a shared dependency only if you accept that.

## Interview Qs

### What happens when a readiness probe fails?

After `failureThreshold` failures in a row, the kubelet marks the Pod not ready, and its IP is removed from the EndpointSlices of every matching Service, so it gets no new requests. The container keeps running and is probed again. When the probe passes, the Pod gets traffic again.

### Why should a liveness probe not check the database?

If the database goes down, every replica fails liveness and the kubelet restarts all of them together. A restart cannot fix the database, so you only lose in-flight requests and add load during recovery. Spring Boot's liveness group checks only the app's own state for this reason.

### When do you need a startup probe, and how do you size it?

When the app can take longer to boot than liveness allows before restarting it. Point the startup probe at the liveness endpoint and set `failureThreshold × periodSeconds` above the slowest boot, for example 30 × 10 s. Liveness keeps its strict settings once startup has passed.

### Why does a rolling update need a readiness probe?

A Deployment counts a new Pod as available only when it is ready, and only then removes more old Pods. Without a readiness probe, a Pod is ready as soon as it starts, so old Pods go away while new ones are still booting, and requests fail. You will see this in [rolling updates](card:rolling-updates-rollbacks).
