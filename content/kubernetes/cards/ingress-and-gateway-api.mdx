## What it is

Ingress is a Kubernetes object that holds routing rules for HTTP and HTTPS traffic coming from outside the cluster, such as "requests for `api.example.com/payments` go to the Service `payment-service`". The rules do nothing alone. An Ingress controller reads them and routes the traffic. It is a proxy, a program that receives requests and passes them on, which you install in the cluster. Gateway API is the newer set of objects for the same job, split into a GatewayClass, a Gateway and routes such as HTTPRoute.

## Why it exists

A [Service](card:services) of type LoadBalancer exposes one Service and sees only ports, not URLs. With eight public microservices you would pay for eight load balancers, hand out eight addresses and set up HTTPS eight times. Ingress and Gateway API put all of them behind one entry point. It reads the host and path of each request, sends `/payments` and `/orders` to different Services, and decrypts HTTPS in one place.

## How it works

1. The infrastructure provider or cluster admin installs a controller and a GatewayClass that names it.
2. The platform team creates a Gateway: a listener on port 443 for `api.example.com`, with the TLS certificate stored in a Secret (you will see Secrets in [ConfigMaps and Secrets](card:configmaps-and-secrets)). The controller gives it an address, for example by creating a cloud load balancer.
3. The payments team creates an HTTPRoute in its own namespace that attaches to the Gateway and maps `/payments` to `payment-service`.
4. A request for `https://api.example.com/payments/42` arrives. The Gateway decrypts it, finds the matching route and sends it to the Service, which forwards it to a ready Pod.

With Ingress the flow is the same, but one Ingress object holds the host, path and TLS settings together.

## Example

The same `/payments` route, first as an Ingress, then as a Gateway API HTTPRoute:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: payments, namespace: payments }
spec:
  ingressClassName: nginx            # which controller handles it
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /payments
            pathType: Prefix         # required on every path
            backend:
              service: { name: payment-service, port: { number: 80 } }
```

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: payments, namespace: payments }
spec:
  parentRefs: [{ name: public-gateway, namespace: infra }]  # the shared Gateway
  hostnames: [api.example.com]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /payments } }]
      backendRefs: [{ name: payment-service, port: 80 }]
```

What to notice:

- Both send traffic to the Service on port 80, not to Pods. The Service still picks the ready Pod.
- `pathType: Prefix` matches `/payments` and `/payments/42`, but not `/paymentsx`, because matching works on whole path parts.
- The HTTPRoute names a Gateway owned by another team in another namespace. The app team never touches the listener or the certificate.
- Without an installed controller for `nginx`, or for the Gateway's class, both objects are stored but nothing routes.

## Rules and defaults

- **Controller:** required for both; you choose one and set it up in the cluster. Gateway API's objects are add-on custom resources, also installed by you or your provider.
- **Ingress is frozen:** it stays stable and supported, with no plans to remove it, but it gets no new features.
- **Ingress protocols:** HTTP and HTTPS only. Other protocols use a NodePort or LoadBalancer Service, or Gateway API's TCPRoute and UDPRoute, stable since v1.6.
- **IngressClass:** an Ingress without `ingressClassName` uses the IngressClass marked as default, if there is one.
- **Path matching:** the longest matching path wins; on a tie, `Exact` beats `Prefix`.
- **TLS:** the certificate and key live in a Secret. HTTPS ends at the entry point; traffic to the Service and Pods is plain HTTP unless something else encrypts it.
- **Gateway routes (Gateway API v1.6):** a Gateway accepts routes only from its own namespace unless `allowedRoutes` allows others.
- **Weights:** an HTTPRoute can split traffic between Services by weight, which you will see in [canary releases](card:release-strategies).

## Not to be confused with

A LoadBalancer Service is a Service type: it gives one Service its own external load balancer for any TCP or UDP port. Ingress and Gateway API are routing objects that put many HTTP Services behind one entry point. Rule: LoadBalancer for one Service or a non-HTTP port; Gateway or Ingress for many HTTP routes. The controller's proxy itself is often exposed through one LoadBalancer.

## Common mistakes

- **"Ingress is deprecated."** It is frozen, not deprecated. Existing Ingresses keep working; new features go into Gateway API.
- **Staying on Ingress NGINX.** Existing installations still run, but they get no security fixes. Move to a maintained Gateway API implementation or another maintained controller.

## Interview Qs

### Why use Ingress or a Gateway when a LoadBalancer Service already exposes the app?

A LoadBalancer gives one Service its own load balancer and sees only ports. Ingress or a Gateway puts many Services behind one address, routes by host and path, and handles TLS once. That means fewer load balancers, one certificate setup and one place for HTTP rules.

### How is Gateway API better than Ingress?

It splits the work by role: the platform team owns the Gateway, and app teams own their routes in their own namespaces. Header matching, traffic weights and gRPC, TCP and UDP routes are part of the API, where Ingress needed controller-specific annotations. The Kubernetes project recommends it for new work.

### Ingress NGINX is retired. What do you do?

Its maintenance ended in March 2026: no new releases and no security fixes. Running installations keep working, so the risk grows over time. Plan a migration to a Gateway API implementation, as the Kubernetes project suggests, and convert each Ingress to a Gateway and HTTPRoutes.
