## What it is

GitOps is a way to run deployments where Git holds the desired state of the cluster: the [manifests](card:kubectl-and-manifests) for every Deployment, Service and ConfigMap. An agent, usually running inside the cluster, pulls those manifests and applies them, then keeps comparing the cluster with Git. The two common agents are Argo CD and Flux. CI (continuous integration) still builds and tests the image; GitOps changes how that image reaches the cluster.

## Why it exists

Without it, people deploy with `kubectl apply` from laptops, or the pipeline holds admin access to the cluster and pushes changes. Nobody can easily say what is running or who changed it, and a quick `kubectl edit` during an incident is never written down, so environments slowly drift apart. With GitOps every change is a reviewed commit, the history is `git log`, and the agent notices any difference between the cluster and Git.

1. A merge to main runs the tests, and CI builds the image and pushes `payment-service:1.5.0`. The tag is never reused.
2. CI, or a person, opens a pull request that changes the image tag in the config repository. A reviewer approves it.
3. The agent sees the new commit, either by polling or through a webhook, and applies the changed manifest to the cluster.
4. The Deployment starts a [rolling update](card:rolling-updates-rollbacks) to 1.5.0.
5. The agent keeps comparing the live objects with Git. Argo CD shows Synced and Healthy, or OutOfSync when someone changed the cluster by hand.

So the pipeline never touches the cluster; Git is the only way in.

## Example

An Argo CD Application tells the agent which Git folder to keep in sync with the payments namespace.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: payment-service, namespace: argocd }
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/payments-config.git
    targetRevision: main
    path: payment-service/prod
  destination: { server: https://kubernetes.default.svc, namespace: payments }
  syncPolicy:
    automated: { prune: true, selfHeal: true }
```

What to notice:

- `source` is the Git folder that holds the manifests; `destination` is the cluster and namespace they go to. `kubernetes.default.svc` means the cluster Argo CD itself runs in.
- `automated` makes Argo CD apply new commits without anyone pressing Sync.
- `selfHeal: true` makes it undo manual changes in the cluster. Without it, drift is only reported.
- `prune: true` deletes objects that were removed from Git. It is off by default, so a deleted manifest would otherwise leave the object running.

## Rules and defaults

- **Four principles (OpenGitOps 1.0):** the desired state is declarative, versioned and immutable, pulled automatically, and continuously reconciled.
- **Argo CD polling:** it checks Git about every 3 minutes by default (120 s plus up to 60 s jitter); a Git webhook makes it react at once (Argo CD 3.5).
- **Argo CD safety defaults:** automated sync does not prune and does not self-heal unless you turn them on (Argo CD 3.5).
- **Secrets:** never commit plain Secrets to Git; use one of the tools in [ConfigMaps and Secrets](card:configmaps-and-secrets).
- **Image tags:** the Kubernetes docs advise against `:latest` in production; use a unique tag or pin the image digest.
- **Manifest format:** plain YAML, Helm charts or Kustomize overlays all work; you will meet them in [Helm and Kustomize](card:helm-and-kustomize).

## Not to be confused with

In push-based CD the pipeline runs `kubectl` or `helm` against the cluster at the end of a build, and nobody checks the cluster afterwards. In pull-based GitOps an agent in the cluster fetches the desired state from Git and keeps reconciling it. Rule: push deploys once; pull deploys and keeps checking.

## Interview Qs

### Push-based vs pull-based deployment: what is the difference?

In push-based CD the pipeline holds cluster credentials and runs `kubectl` or `helm` at the end of a build. In pull-based GitOps an agent inside the cluster watches Git, applies changes and keeps comparing, so drift is caught and the pipeline never needs cluster access.

### Why not deploy the latest tag?

A moving tag hides which build is running, and two Pods started at different times may run different code. Git would say `latest` for both versions, so rollback by commit does not work. The Kubernetes docs advise against `:latest` in production: use a unique tag per build, or pin the digest.

### How do you roll back with GitOps?

Revert the commit that changed the image tag. The agent syncs the old manifest and the Deployment rolls back. A `kubectl rollout undo` alone leaves the cluster different from Git, so the agent reports drift, and with self-heal on it puts the bad version back. Argo CD also blocks its own rollback while automated sync is on.
