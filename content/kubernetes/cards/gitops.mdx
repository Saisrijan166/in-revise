## Why it exists

kubectl changes from laptops and pipelines leave no record and drift apart. Keeping the desired state in Git gives review, history and an easy way back.

## How it works

<Steps label="Releasing payment-service 1.5.0 with GitOps">
  <Step title="Test">A merge to main runs the tests.</Step>
  <Step title="Build">CI builds the image and pushes payment-service:1.5.0; the tag is never reused.</Step>
  <Step title="Change Git">A pull request changes the image tag in the config repo.</Step>
  <Step title="Sync">Argo CD or Flux sees the commit and applies it; the Deployment rolls out.</Step>
  <Step title="Watch">The tool shows Synced and Healthy, or OutOfSync if someone edits the cluster.</Step>
</Steps>

- Manifests can be plain YAML, [Helm or Kustomize](card:helm-and-kustomize).
- Never commit plain Secrets to Git: see [Secrets](card:configmaps-and-secrets).

## Interview Qs

### Push-based vs pull-based deployment?

Push: the pipeline runs kubectl or helm against the cluster at the end of a build. Pull: an agent, usually in the cluster, watches Git, applies changes and keeps checking, so drift is caught.

### Why not deploy the latest tag?

A moving tag hides which build runs and makes rollback unreliable; the Kubernetes docs advise against `:latest` in production. Use a unique tag per build, or pin the image digest.

### How do you roll back with GitOps?

Revert the commit that changed the tag; the agent syncs the old manifest back. A `kubectl rollout undo` alone leaves the cluster out of sync with Git.
