## Why it exists

Some work must finish before the app starts; some helpers must run beside it all the time. Extra containers keep that work out of the app image.

## How it works

<Compare id="init-container-vs-sidecar" />

- Helper patterns: sidecar (log shipper), ambassador (proxies the app's outbound calls), adapter (converts output, such as metrics, to a standard format).
- If an init container fails, the kubelet retries it; with restartPolicy Never the whole Pod fails.

## Example

```yaml
spec:
  initContainers:
    - name: wait-for-db              # runs first, must exit 0
      image: busybox:1.37
      command: ["sh", "-c", "until nslookup payments-db; do sleep 2; done"]
    - name: log-shipper              # native sidecar: keeps running
      image: log-agent:2.0
      restartPolicy: Always
  containers:
    - name: app
      image: payment-service:1.4.0
```

## Interview Qs

### What is the difference between an init container and a sidecar?

Init containers run one by one to completion before the app starts. A native sidecar is an init container with restartPolicy Always: it starts before the app, runs beside it, supports probes and stops after it.

### When do two containers belong in one Pod instead of two Pods?

Only when they are tightly coupled: they share files or localhost and must live and die together, like the app and its log shipper. Anything that scales on its own gets its own Pod.
