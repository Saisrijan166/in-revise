## What it is

A [Pod](card:pods) can hold helper containers next to the app container. An init container runs once, before the app starts, and must exit with success, for example to wait until the database's address can be found. A sidecar is a helper that keeps running beside the app for the Pod's whole life, such as a log shipper. A native sidecar, stable since Kubernetes 1.33, is written as an init container with `restartPolicy: Always`.

## Why it exists

Without init containers, payment-service would need its own retry code for "wait until the database exists", and setup tools would be baked into the app image. Without native sidecars, a log shipper written as a normal container starts in no fixed order, may stop before the app has written its last lines, and never exits, so a Job using it never finishes. Init containers give a fixed setup order; sidecars give a fixed start and stop order around the app.

## How it works

<Compare id="init-container-vs-sidecar" />

1. The kubelet starts the entries in `initContainers` one by one, in the order you list them.
2. A plain init container must exit with code 0 before the next entry starts. If it fails, the kubelet retries it; with the Pod's `restartPolicy: Never`, the whole Pod fails instead.
3. An entry with `restartPolicy: Always` is a sidecar. Once it has started, the kubelet moves on to the next entry and leaves the sidecar running.
4. After all init entries are done, the app containers start.
5. On shutdown, the app containers stop first. Then the sidecars stop, in reverse order.

So the order is fixed: setup, helpers, app; and the helpers outlive the app.

## Example

The payment-service Pod waits for its database, then starts with a log shipper beside it:

```yaml
spec:
  initContainers:
    - name: wait-for-db                # plain init container: must exit 0
      image: busybox:1.37
      command: ["sh", "-c", "until nslookup payments-db.payments.svc.cluster.local; do sleep 2; done"]
    - name: log-shipper                # native sidecar: keeps running
      image: log-agent:2.0
      restartPolicy: Always
  containers:
    - name: payment-service
      image: payment-service:1.4.0
```

What to notice:

- `wait-for-db` loops until the database Service's DNS name resolves, then exits 0. While it loops, `kubectl get pod` shows the status `Init:0/2`.
- `log-shipper` sits in `initContainers` but has `restartPolicy: Always`, so it starts before the app and keeps running. Remove that line and the Pod would wait for the log shipper to exit, so the app would never start.
- The app container starts only after `wait-for-db` succeeded and `log-shipper` has started.

## Rules and defaults

- **Not allowed on plain init containers:** `lifecycle`, `livenessProbe`, `readinessProbe` and `startupProbe`. Sidecars may use all of them.
- **Idempotent setup:** an init container can run again, for example after the Pod restarts, so its work must be safe to repeat.
- **Secrets for setup only:** an init container can use tools or Secrets that the app container cannot see.
- **Other helper patterns:** an ambassador proxies the app's outgoing calls; an adapter converts the app's output, such as metrics, into a standard format.

## Not to be confused with

A regular second container in `containers` starts in no fixed order and runs as an equal part of the Pod. A native sidecar is declared in `initContainers` with `restartPolicy: Always`, so it starts before the app and stops after it. Rule: helper that must be up first and down last = native sidecar.

## Interview Qs

### What is the difference between an init container and a sidecar?

An init container runs to completion before the app starts, one after another, and supports no probes. A native sidecar is an init container with `restartPolicy: Always`: it starts before the app, runs beside it for the Pod's life, supports probes and stops after the app.

### When do two containers belong in one Pod instead of two Pods?

Only when they are tightly coupled: they share files or localhost and must live and die together, like the app and its log shipper. Anything that scales on its own, such as another microservice or a database, gets its own Pod.

### What happens if an init container keeps failing?

The app container never starts. The kubelet keeps restarting the init container with a growing delay, and the Pod status shows `Init:Error` or `Init:CrashLoopBackOff`. If the Pod's `restartPolicy` is `Never`, the Pod is marked Failed instead.
