## What it is

Pod networking is the set of rules for how Pods talk to each other. Every Pod gets its own IP address in the cluster, and any Pod can reach any other Pod at that IP, on any node, without address translation (NAT). A CNI plugin builds this network. CNI (Container Network Interface) is the standard through which the container runtime plugs in a network add-on, such as Calico, Cilium or Flannel. On top of it, the cluster DNS server, usually CoreDNS, gives every [Service](card:services) a name.

## Why it exists

With plain Docker on several machines, containers on different hosts cannot reach each other directly. You publish container ports on host ports and track which host port belongs to which app, and two apps cannot both take host port 8080. Kubernetes gives each Pod its own IP instead, so every app listens on its normal port and is reachable as it is. DNS then removes the last address from the configuration: the app calls `http://payment-service.payments`, and the name always points at the current Service.

## How it works

1. When a Pod starts, the CNI plugin gives it an IP and connects it to the Pod network. The kubelet writes the Pod's DNS settings: the cluster DNS server, and a search list that starts with the Pod's own namespace.
2. order-service looks up `payment-service.payments`. CoreDNS answers with the Service's ClusterIP.
3. order-service connects to that ClusterIP. Forwarding rules from [kube-proxy](card:kubernetes-architecture) on its own node change the destination to the IP of one ready payment Pod.
4. The Pod network carries the packet straight to that Pod IP, even when the Pod runs on another node.

So DNS turns a name into a ClusterIP, kube-proxy turns the ClusterIP into a Pod IP, and the CNI network delivers it.

## Example

The DNS settings that the kubelet writes into an order-service Pod in namespace `orders` (10.96.0.10 is an example address of the cluster DNS Service):

```text
# /etc/resolv.conf inside the order-service Pod
nameserver 10.96.0.10
search orders.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

What to notice:

- `search` starts with `orders.svc.cluster.local`. The short name `payment-service` therefore becomes `payment-service.orders.svc.cluster.local`, which does not exist, because the Service lives in `payments`.
- `payment-service.payments` is completed by the second entry to `payment-service.payments.svc.cluster.local`, which resolves to the ClusterIP.
- `ndots:5` means a name with fewer than five dots is tried with each search entry first, before it is tried as it is. That is why `payment-service.payments` works, and why one short name can cost several DNS lookups.

## Rules and defaults

- **Name format:** `<service>.<namespace>.svc.<cluster domain>`; the cluster domain is usually `cluster.local`.
- **dnsPolicy:** `ClusterFirst` by default (Kubernetes 1.37): cluster names go to the cluster DNS, other names are forwarded upstream. The policy named `Default` is not the default; it uses the node's DNS settings.
- **Cluster DNS:** CoreDNS is the usual server; its Service keeps the old name `kube-dns` in `kube-system`.
- **Headless Service:** its name returns the Pod IPs, not one ClusterIP. A [StatefulSet](card:statefulsets) uses this to give each Pod its own name.
- **kube-proxy modes on Linux (1.37):** `iptables` is the default; `nftables` is stable since 1.33, needs kernel 5.13 or later and is planned as the future default; `ipvs` is deprecated since 1.35 and will be off by default from 1.40. Set the mode explicitly so an upgrade does not change it.
- **Without kube-proxy:** some CNI plugins handle Service traffic themselves, and those nodes run no kube-proxy.
- **Open by default:** every Pod can reach every Pod until a [NetworkPolicy](card:network-policies), the next concept, limits it.

## Not to be confused with

A Pod IP belongs to one real Pod and changes when that Pod is replaced. A ClusterIP is the Service's virtual IP: no machine owns it, it exists only in the forwarding rules on each node, and it stays fixed. Rule: Pod IP = one Pod, temporary; ClusterIP = the Service, stable.

## Common mistakes

- **Mixing up CNI and kube-proxy.** The CNI plugin connects Pods and carries packets between nodes. kube-proxy only turns Service IPs into Pod IPs. A broken CNI breaks all Pod traffic; a broken kube-proxy breaks only calls through Services.

## Interview Qs

### How does a Pod on one node reach a Pod on another node?

Directly by Pod IP: the CNI plugin connects the nodes so that Pod IPs are reachable everywhere, without NAT. When the call goes through a Service, kube-proxy, or the CNI's own proxy, first changes the ClusterIP into one Pod IP.

### Why does payment-service resolve in one namespace but not in another?

A short name is completed with the caller's own namespace first, through the search list in the Pod's DNS settings. From another namespace, add the namespace: `payment-service.payments`, or use the full name.

### What does DNS return for a headless Service?

The IPs of the Pods it selects instead of one ClusterIP, so the client chooses a Pod itself. Combined with a StatefulSet, each Pod also gets a stable name, such as `payments-db-0.payments-db.payments.svc.cluster.local`.
