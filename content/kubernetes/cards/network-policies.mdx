## What it is

A NetworkPolicy is a Kubernetes object that says which network connections may reach a group of Pods, or leave them. It selects its Pods by [labels](card:namespaces-labels-selectors). It then lists allowed sources (ingress rules) or allowed destinations (egress rules) by Pod labels, namespace labels or IP ranges, with ports. It works at the IP and port level, so it never sees URLs or HTTP methods.

## Why it exists

As [Pod networking](card:cluster-networking-dns) showed, every Pod can connect to every other Pod by default. If an attacker takes over one Pod, such as a reporting job, it can open a connection to the payments database. A NetworkPolicy limits each Pod to the connections it needs: only order-service and the gateway may call payment-service on port 8080, and only payment-service may reach the database.

## How it works

1. While no policy selects a Pod, all connections into and out of it are allowed.
2. When a policy selects the Pod for a direction, for example Ingress, the Pod becomes isolated in that direction. Only connections allowed by some policy get in. Replies to an allowed connection pass automatically.
3. If several policies select the same Pod, their allow lists add up. Order does not matter, and no rule can deny.
4. For a connection between two Pods, the sender's egress and the receiver's ingress must both allow it.
5. The CNI plugin enforces all this on each node. If it has no policy support, the policies are stored and do nothing.

## Example

First a default deny for incoming traffic in `payments`, then the callers that payment-service allows:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: payments }
spec:
  podSelector: {}          # every Pod in payments
  policyTypes: [Ingress]   # no ingress rules, so nothing may come in
```

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: payment-service-callers, namespace: payments }
spec:
  podSelector: { matchLabels: { app: payment-service } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: orders } }
          podSelector: { matchLabels: { app: order-service } }    # same item: AND
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: infra } }  # new item: OR
      ports: [{ port: 8080 }]
```

What to notice:

- `podSelector: {}` selects every Pod in the namespace. With no ingress rules, the first policy lets nothing in, including Pods that no other policy selects.
- In the second policy, the first `from` item has two selectors without a dash between them, so a caller must be an order-service Pod and also be in namespace `orders`. The dash before the infra selector starts a new item: any Pod in `infra` may connect too.
- `kubernetes.io/metadata.name` is a label that Kubernetes puts on every namespace automatically, so you can pick a namespace by its name.
- The policies add up: payment Pods accept those two callers on 8080; the database Pods in `payments` still accept nobody.

## Rules and defaults

- **No policy:** all traffic in and out is allowed (Kubernetes 1.37).
- **policyTypes left out:** the policy always covers Ingress, and covers Egress only if it has egress rules.
- **Peers:** `podSelector` alone means Pods in the policy's own namespace; `namespaceSelector` means all Pods in those namespaces; `ipBlock` means IP ranges, usually outside the cluster.
- **Always allowed:** traffic from the Pod's own node, and a Pod's traffic to itself.
- **DNS:** a default deny for egress also blocks DNS lookups. Allow egress on port 53, UDP and TCP, to the cluster DNS Pods.
- **Not possible:** selecting a Service by name, deny rules, rules on URLs or TLS, logging of blocked connections, and one default policy for the whole cluster. Each namespace needs its own default deny.

## Not to be confused with

A namespace is a name scope that groups objects; it does not block traffic. [RBAC](card:rbac), which you will see later, controls who may call the Kubernetes API, such as who may create a Pod. A NetworkPolicy controls which Pods may open network connections to which. Rule: RBAC for API calls, NetworkPolicy for Pod traffic.

## Common mistakes

- **Writing a Service name in a policy.** Policies select Pods by labels. To protect payment-service, select its Pods' label `app: payment-service`.
- **Testing on a cluster whose plugin ignores policies.** The policy is accepted and looks correct, but traffic still flows. Check that the CNI plugin supports NetworkPolicy.

## Interview Qs

### How do you let only order-service call payment-service?

Add a default deny for ingress in `payments` with `podSelector: {}` and no rules. Then add a policy that selects the payment Pods and allows, in one `from` item, namespace `orders` and the label `app: order-service`, on port 8080. Check that the CNI plugin enforces policies.

### You added a default deny for egress, and now nothing resolves. Why?

DNS lookups leave the Pod as egress traffic on port 53, so the deny blocks them. Add an egress rule to the cluster DNS Pods on port 53 for UDP and TCP, then the egress rules each service really needs.

### Does a NetworkPolicy work on every cluster?

No. The API server accepts it everywhere, but the CNI plugin enforces it. A plugin without policy support, or one set up without it, ignores the policy, so traffic still flows.
