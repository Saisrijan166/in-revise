## Why it exists

Commands typed against a live cluster leave no record. Manifests in Git can be reviewed and repeated, and describe the end state, not the steps.

## How it works

<Compare id="kubectl-apply-vs-create" />

- kubectl calls the API server named in the current kubeconfig context; `-n payments` sets the namespace for one command.
- Server-side apply (`--server-side`, stable since 1.22) lets the API server track which tool owns each field.
- `kubectl delete -f` removes what the file describes. After apply, follow the rollout: [debugging with kubectl](card:kubectl-debugging).

## Example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: payments
spec:                          # desired state; status is added by the cluster
  replicas: 3
  selector: { matchLabels: { app: payment-service } }
  template:
    metadata: { labels: { app: payment-service } }
    spec: { containers: [{ name: app, image: "payment-service:1.4.0" }] }
```

## Interview Qs

### How is kubectl replace different from apply?

replace overwrites the whole live object, so fields missing from your file, even ones the cluster set, are lost. apply sends a patch and keeps changes made by other writers.

### How do you check a manifest before applying it?

`kubectl diff -f` shows what would change. `--dry-run=server` lets the API server check it but saves nothing; `--dry-run=client` only prints it. `kubectl explain deployment.spec` documents any field.

### Why do we write YAML instead of running commands?

The file is the desired state: it lives in Git, gets reviewed, and builds the same objects everywhere. Typed commands leave no record beyond the live objects.
