## What it is

kubectl is the command-line tool you use to work with a cluster: every kubectl command becomes an HTTPS request to the [API server](card:kubernetes-architecture). A manifest is a YAML file that describes one or more Kubernetes objects, such as the Deployment that runs the payment service. Each object in it states its type, its name and its desired state. You keep manifests in Git and send them to the cluster with `kubectl apply`.

## Why it exists

You could create everything with typed commands, such as `kubectl create deployment`. But typed commands leave no record: nobody reviews them, and building the same setup in another cluster means remembering every step. A manifest is the desired state written down. It is reviewed in a pull request, can be applied again safely, and creates the same objects in test and in production.

## How it works

1. kubectl reads your kubeconfig file to learn the cluster address, your credentials and your default namespace. This group of settings is called a context.
2. `kubectl apply -f` reads the manifest and checks, for each object, whether it already exists.
3. A new object is created. For an existing one, kubectl sends a patch with only the fields that differ.
4. The API server validates the object and stores it in etcd. kubectl prints `created`, `configured`, or `unchanged` when nothing differed.
5. Controllers then act on the new spec and write the object's status. apply has already returned by then.

So apply records what you want; whether it works shows up only later, in status.

## Example

The payment service's Deployment as a manifest:

```yaml
apiVersion: apps/v1                  # API group and version for Deployments
kind: Deployment
metadata:
  name: payment-service
  namespace: payments
spec:                                # desired state; the cluster adds status
  replicas: 3
  selector: { matchLabels: { app: payment-service } }
  template:                          # the Pod to make 3 copies of
    metadata: { labels: { app: payment-service } }
    spec:
      containers:
        - { name: payment-service, image: "registry.example.com/payments/payment-service:1.4.0" }
```

Apply it twice:

```bash
kubectl apply -f payment-service.yaml
kubectl apply -f payment-service.yaml
```

```text output
deployment.apps/payment-service created
deployment.apps/payment-service unchanged
```

What to notice:

- `apiVersion: apps/v1` and `kind: Deployment` together pick the object type. With `apiVersion: v1` instead, apply fails with `no matches for kind "Deployment" in version "v1"`.
- You never write `status`. Kubernetes fills it in, and `kubectl get deployment payment-service -n payments -o yaml` shows both halves.
- The second apply printed `unchanged` and did nothing. Change `replicas` to 5 and apply again, and it prints `configured`.

## Rules and defaults

- **kubeconfig:** kubectl reads `$HOME/.kube/config` unless the `KUBECONFIG` variable or the `--kubeconfig` flag names another file.
- **Version skew:** kubectl is supported within one minor version, older or newer, of the API server.
- **One technique per object:** manage each object with typed commands, with create and replace on files, or with apply. Mixing them on one object gives undefined behaviour.
- **Server-side apply:** `kubectl apply --server-side` (stable since 1.22) runs the merge in the API server, which records which tool owns each field and reports conflicts.
- **Deleting:** `kubectl delete -f payment-service.yaml` removes the objects the file describes.
- **Looking up a field:** `kubectl explain deployment.spec.replicas` prints the API documentation for that field.

## Not to be confused with

`kubectl apply` sends the desired state and creates or patches to match. `kubectl create` makes a new object and fails if it exists. `kubectl replace` swaps the whole live object for your file. Rule: apply for files you keep in Git; create for one-off experiments; replace almost never.

## Common mistakes

- **Testing a change by applying it to production.** `kubectl diff -f` shows what would change. `--dry-run=server` runs every server check without saving anything, while `--dry-run=client` only prints the object kubectl would send.

## Interview Qs

### Why do we write YAML manifests instead of running commands?

The file is the desired state: it lives in Git, is reviewed like code, and builds the same objects in every cluster. Applying it again is safe. Typed commands leave no record beyond the live objects, so nobody can tell later how the cluster got its shape.

### How is kubectl replace different from apply?

replace overwrites the whole live object with your file, so any field missing from the file is lost, even fields another tool set. apply sends a patch of the fields you manage and keeps changes made by other writers.

### What are spec and status?

spec is the desired state you write, such as `replicas: 3`. status is the current state, written by Kubernetes components, such as how many replicas are ready. Controllers keep working to make status match spec.
