## Why it exists

Pods must prove who they are to the API server and to cloud services. Sharing an admin key, or storing cloud keys in Secrets, gives every leak full power.

## How it works

<Mermaid
  alt="The payment-service Pod runs as the ServiceAccount payment-service. The kubelet mounts a short-lived token into the Pod. The Pod sends the token to the API server, which checks RBAC bindings for that ServiceAccount. On a cloud, the same identity is mapped to an IAM role through workload identity."
  chart={`flowchart LR
  SA[ServiceAccount payment-service] --> P[payment-service Pod]
  K[kubelet] -- short-lived token --> P
  P -- token --> API[API server]
  API --> R[RBAC check]
  P -- workload identity --> C[Cloud IAM role]`}
/>

- The token is mounted at `/var/run/secrets/kubernetes.io/serviceaccount/token`.
- Rights come only from [RBAC](card:rbac) bindings that name the ServiceAccount.

## Example

```yaml
apiVersion: v1
kind: ServiceAccount
metadata: { name: payment-service, namespace: payments }
---
# payment-service Deployment, Pod template
spec:
  serviceAccountName: payment-service   # a Role lets it get payment-config only
  containers:
    - name: payment-service
      image: payment-service:1.4.0
```

## Interview Qs

### How does a Pod reach AWS S3 without access keys?

Use workload identity: associate an IAM role with the Pod's ServiceAccount through EKS Pod Identity or IRSA. The AWS SDK then gets temporary credentials for that role; no keys sit in Secrets.

### Why set automountServiceAccountToken to false?

Most apps never call the Kubernetes API. Without a token, a compromised container has nothing to use against the API server. Set it on the ServiceAccount or the Pod; the Pod setting wins.
