## What it is

A ServiceAccount is an identity for software, not for a person. A process in a Pod presents it, as a token, when it calls the [API server](card:kubernetes-architecture), so the server knows which workload is calling. Each ServiceAccount lives in one namespace. What it may do is granted separately, through RBAC, which you will see in [RBAC](card:rbac).

## Why it exists

Some workloads call the Kubernetes API: a controller that watches Pods, or a CI job that deploys the payment service. Without a per-workload identity you would hand them a person's or an admin's credentials, and a leak would give an attacker all those rights. The same applies to clouds: AWS keys kept in a [Secret](card:configmaps-and-secrets) are long-lived and work from anywhere once leaked. A ServiceAccount gives each workload its own narrow identity with short-lived tokens.

## How it works

1. Kubernetes creates a ServiceAccount named `default` in every namespace. You create your own, such as `payment-service`.
2. The Pod names it in `spec.serviceAccountName`; without that field it runs as `default`.
3. The kubelet requests a short-lived token for that ServiceAccount and mounts it at `/var/run/secrets/kubernetes.io/serviceaccount/token`. It renews the token once it is older than 80% of its lifetime or 24 hours.
4. The app sends the token with each API call. The API server identifies the caller as `system:serviceaccount:payments:payment-service` and checks what RBAC allows.
5. On a managed cloud, workload identity maps the ServiceAccount to a cloud role, so the cloud SDK in the Pod gets temporary credentials without stored keys.

So the key is: the ServiceAccount says who is calling, and RBAC or the cloud role says what it may do.

## Example

The payment service gets its own identity, and because it never calls the Kubernetes API, it gets no token:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata: { name: payment-service, namespace: payments }
automountServiceAccountToken: false     # the app never calls the Kubernetes API
---
# payment-service Deployment, Pod template (part)
spec:
  serviceAccountName: payment-service
  containers:
    - name: payment-service
      image: payment-service:1.4.0
```

What to notice:

- A dedicated ServiceAccount keeps rights apart: anything granted to `payment-service` does not reach other Pods that run as `default`.
- With `automountServiceAccountToken: false`, no token file is mounted, so an attacker inside the container has nothing to use against the API server.
- If the app later needs the API, remove that line and bind a Role to the ServiceAccount. A Pod can also set the field itself, and the Pod's value wins.

## Rules and defaults

- **default ServiceAccount:** created in every namespace and recreated if deleted. With RBAC on, it has only the API discovery rights that every authenticated caller gets.
- **Token:** since Kubernetes 1.22 the mounted token is short-lived and rotated by the kubelet. The app must re-read the file, for example every few minutes.
- **Legacy token Secrets:** not created automatically since 1.24. They never expire and never rotate, so create one only when nothing else works.
- **Set at creation:** `serviceAccountName` cannot be changed on a running Pod; change the Pod template and roll out.
- **Namespaced:** a ServiceAccount belongs to one namespace, but a RoleBinding in another namespace can give it rights there.

## Not to be confused with

A ServiceAccount is an identity: it answers "who is calling?". An RBAC Role is a list of permissions, and a RoleBinding connects that Role to an identity. Rule: ServiceAccount = who; Role and RoleBinding = what it may do.

## Interview Qs

### How does a Pod reach AWS S3 without access keys?

Use workload identity: associate an IAM role with the Pod's ServiceAccount through EKS Pod Identity or IRSA. The AWS SDK in the Pod then gets temporary credentials for that role, so no access keys sit in Secrets or images. GKE and AKS have their own versions of the same idea.

### Why set automountServiceAccountToken to false?

Most apps never call the Kubernetes API. Without a mounted token, a compromised container has nothing to present to the API server. You can set it on the ServiceAccount or on the Pod; if both set it, the Pod's value wins.

### Why give each app its own ServiceAccount instead of using default?

Every Pod in the namespace that sets nothing runs as `default`. If you grant `default` rights for one app, every other Pod there gets them too. A dedicated ServiceAccount per app keeps each one at least privilege.
