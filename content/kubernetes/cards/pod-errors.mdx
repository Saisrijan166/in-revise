## Why it exists

`kubectl get pods` shows one word per Pod. The word names the failing stage, so it tells you where to look first.

## How it works

| Status | Means | First check |
|---|---|---|
| Pending | Not scheduled: no node fits | `describe` events: CPU, memory, [taints](card:taints-and-tolerations) |
| ContainerCreating | Still starting: image, Secret data | `describe` events |
| ErrImagePull, ImagePullBackOff | Image not pulled; retrying | Image name, tag, registry, pull secret |
| CreateContainerConfigError | Container config not built | Missing [ConfigMap or Secret](card:configmaps-and-secrets) or key |
| CrashLoopBackOff | App exits again and again | `logs --previous`, exit code |
| OOMKilled | OOM kill: over its limit, or node out of memory | [Limits](card:resource-requests-limits), JVM heap |
| Evicted | Node under pressure | [QoS and eviction](card:qos-and-eviction) |
| Stuck Terminating | Deleted, but a finalizer remains | Finalizers, webhooks; do not strip them blindly |

- Phases and restart back-off: [Pod lifecycle](card:pod-lifecycle). Commands in order: [debugging](card:kubectl-debugging).

## Example

```text
$ kubectl get pods -n payments
NAME                              READY   STATUS             RESTARTS
payment-service-7d9f8c6b5-x2k4q   0/1     CrashLoopBackOff   5
$ kubectl describe pod payment-service-7d9f8c6b5-x2k4q -n payments
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
```

The JVM outgrew the 512Mi limit: raise the limit or cap the heap.

## Interview Qs

### How do you debug CrashLoopBackOff?

Read `kubectl logs --previous`, then `describe`: Last State, exit code, events. Exit 1 is usually an app or config error, 137 a kill, often OOM. Also check probes and dependencies.

### A Pod is stuck in Pending. Why?

No node fits. Usual causes: requests bigger than any node's unreserved capacity, a nodeSelector or affinity no node matches, or a taint the Pod does not tolerate. The events name the reason.
