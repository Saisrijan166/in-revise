## What it is

A Pod error is the one word that `kubectl get pods` shows in the STATUS column when a Pod is not working, such as Pending or CrashLoopBackOff. It is often not the Pod's phase from [Pod lifecycle](card:pod-lifecycle): when a container is waiting or has ended, kubectl shows that container's reason instead, because it says more. Each word belongs to one stage of starting a Pod, so it tells you where to look first.

## Why it exists

After a bad release, all you know is that payment-service is down. The cause could be a full cluster, a wrong image tag, a missing ConfigMap key or a bug in the code, and guessing between them wastes time. The status word narrows it to one stage, and each stage has one place to look: the scheduler's events, the image name, the configuration or the app's own logs. A vague outage becomes a short checklist.

## How it works

Follow a payment-service Pod from creation, and see what each stage shows when it fails:

1. **Find a node.** The [scheduler](card:scheduling) looks for a node with enough unreserved CPU and memory, the right labels and tolerated taints. If none fits, the Pod stays **Pending**, and its events say why.
2. **Pull the image.** The kubelet on that node asks the runtime to pull the image. A wrong name or tag, or a private registry without a pull secret, shows **ErrImagePull**, then **ImagePullBackOff** while the kubelet waits before the next try.
3. **Mount volumes and build the config.** A Secret or ConfigMap used as a volume that does not exist keeps the Pod in **ContainerCreating**, with FailedMount events. An env var pointing at a missing ConfigMap, Secret or key gives **CreateContainerConfigError**.
4. **Run the app.** The container starts. If it keeps exiting, the kubelet restarts it with a growing delay and shows **CrashLoopBackOff**. If it went over its memory limit, the reason is **OOMKilled**.
5. **Stop.** A Pod the kubelet removed to save a starved node shows **Evicted** (see [QoS and eviction](card:qos-and-eviction)). A deleted Pod that never goes away is stuck **Terminating**, usually because a finalizer is still on it.

So the key is: the status tells you the stage, and the stage tells you the next command.

## Example

Five broken payment-service Pods in a test cluster, one per stage. The status column alone sorts them:

```bash
kubectl get pods -n payments
```

```text output
NAME                     READY   STATUS                       RESTARTS       AGE
payment-bad-tag          0/1     ImagePullBackOff             0              6h2m
payment-missing-key      0/1     CreateContainerConfigError   0              6h2m
payment-missing-volume   0/1     ContainerCreating            0              6h2m
payment-oom              0/1     CrashLoopBackOff             70 (75s ago)   5h40m
payment-too-big          0/1     Pending                      0              6h2m
```

Then `describe` gives the reason and exit code for the crashing one:

```bash
kubectl describe pod payment-oom -n payments | grep -A4 "Last State"
```

```text output
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      Thu, 22 Oct 2026 17:48:27 +0530
      Finished:     Thu, 22 Oct 2026 17:48:28 +0530
```

What to notice:

- payment-too-big asks for 64 CPUs, so it stays Pending; its FailedScheduling event says "Insufficient cpu".
- payment-missing-key and payment-missing-volume both lack configuration, but the env var gives CreateContainerConfigError while the missing Secret volume waits in ContainerCreating.
- payment-oom needs more than its 64Mi memory limit. The kernel kills it with exit code 137 (128 + 9, SIGKILL), and RESTARTS keeps rising.
- Only fixing the cause helps. Restarting a Pod in CrashLoopBackOff starts the same failure again.

## Rules and defaults

- **Image pull back-off:** the wait between pull attempts grows to a fixed limit of 300 seconds (Kubernetes 1.37).
- **Restart back-off:** CrashLoopBackOff uses the restart delays from [Pod lifecycle](card:pod-lifecycle): 10 s, doubling, up to 5 minutes.
- **Exit codes:** 0 is success. Any other number below 128 is chosen by the app; 1 usually means it failed on its own, such as a bad setting. 128 + N means signal N killed it: 137 is SIGKILL (9), 143 is SIGTERM (15).
- **Missing ConfigMap or Secret:** by default both are required, so a Pod that refers to a missing one, or to a missing key, does not start. Mark the reference `optional: true` and the Pod starts without it.
- **Stuck Terminating:** usually a finalizer the control plane cannot remove, for example because an admission webhook blocks the update. Do not delete finalizers by hand until you know what cleanup they protect.

## Not to be confused with

OOMKilled means the kernel killed one container because it used more than its own memory limit; the kubelet restarts it in the same Pod. Evicted means the kubelet removed the whole Pod because the node itself ran short of memory or disk; a controller makes a new Pod. Rule: OOMKilled is the container breaking its limit; Evicted is the node running short. The details are in [QoS and eviction](card:qos-and-eviction).

## Interview Qs

### How do you debug CrashLoopBackOff?

Read `kubectl logs POD --previous` for the run that crashed, then `kubectl describe pod` for Last State, the reason, the exit code and events. Exit 1 is usually an app or config error; 137 is a kill, often OOMKilled. Then check the command, env vars, limits, probes and whether dependencies such as the database are reachable.

### A Pod is stuck in Pending. Why?

The scheduler found no node for it. Usual causes: requests bigger than any node's free capacity, a nodeSelector or affinity no node matches, or a taint the Pod does not tolerate. The FailedScheduling event in `describe` names the reason.

### What does exit code 137 mean?

It is 128 + 9: the process was killed with SIGKILL. If the reason is OOMKilled, it went over its memory limit. Otherwise something else sent SIGKILL, such as the kubelet after the grace period ran out.
