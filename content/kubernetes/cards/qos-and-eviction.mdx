## What it is

Kubernetes puts every Pod into a Quality of Service (QoS) class, worked out from its containers' [requests and limits](card:resource-requests-limits): Guaranteed, Burstable or BestEffort. You do not set the class; it appears in the Pod's `status.qosClass`. Eviction is the kubelet stopping some Pods on its node to free memory or disk when the node runs short. The QoS class tells you which Pods are likely to be evicted first.

## Why it exists

Requests can be lower than limits, so the Pods on a node can together try to use more memory than the node has. If nothing stops them, the node itself fails and every Pod on it dies. Eviction gives up a few Pods, in a known order, to keep the node and the rest alive. QoS classes let you choose where the payment service sits in that order.

## How it works

| Class | Rule (CPU and memory) | When the node runs short of memory |
| --- | --- | --- |
| Guaranteed | Every container sets requests and limits, and each request equals its limit | Evicted last |
| Burstable | Not Guaranteed, but some container sets a request or limit | Evicted if it uses more than it requested |
| BestEffort | No container sets any request or limit | Evicted first: any usage is above its zero request |

1. The kubelet watches eviction signals on its node, such as `memory.available` (free memory) and `nodefs.available` (free disk).
2. When a signal crosses a threshold, for example free memory below 100Mi, it first tries to free resources without touching Pods. For disk, it deletes dead containers and unused images.
3. If that is not enough, it ranks the Pods. First come Pods using more than their requests, ordered by [priority](card:priorityclass) and then by how far above their requests they are. Pods within their requests come last.
4. It evicts the Pod at the top: it stops its containers and sets the Pod's phase to Failed, with reason Evicted. It repeats until the signal is back under the threshold.
5. The Deployment or other controller sees a missing replica and creates a new Pod, which the scheduler places on a node with room.

So the safest place is a Pod that stays within its requests, which a Guaranteed Pod always does for memory.

## Example

The payment service sets requests equal to limits, so its Pods are Guaranteed. You can check the class Kubernetes gave them:

```yaml
resources:
  requests: { cpu: 500m, memory: 512Mi }
  limits: { cpu: 500m, memory: 512Mi }
```

```bash
kubectl get pods -l app=payment-service -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
```

What to notice:

- Both CPU and memory have requests equal to limits, in every container. Set the memory limit to 1Gi, and the Pod becomes Burstable.
- A Guaranteed Pod can never use more memory than it requested, so under memory pressure it is ranked after every Pod that is over its requests.
- The class is read from `status.qosClass`; you cannot write it. Change the resources, and Kubernetes works out the class again for the new Pods.

## Rules and defaults

- **Default hard thresholds (kubelet, Kubernetes 1.37):** `memory.available<100Mi` (Linux), `nodefs.available<10%`, `imagefs.available<15%`, `nodefs.inodesFree<5%` (Linux).
- **Hard vs soft threshold:** a hard threshold evicts at once, with no graceful shutdown. A soft threshold waits for a grace period you configure.
- **What node-pressure eviction ignores:** your PodDisruptionBudgets and the Pod's `terminationGracePeriodSeconds`. API-initiated eviction, as `kubectl drain` uses, respects both; you will see PodDisruptionBudgets in [high availability](card:high-availability).
- **QoS and disk:** the kubelet does not rank by QoS class; the class only predicts the order for memory. It does not apply under disk pressure.
- **Kernel out of memory first:** if the node runs out of memory before the kubelet acts, the kernel kills a container. Kubernetes biases that choice so BestEffort containers die first and Guaranteed ones last. A container killed this way restarts; an evicted Pod does not.
- **Priority:** a PriorityClass maps a name to a number. A higher number ranks later for eviction, and the scheduler may preempt, that is evict, lower-priority Pods to fit a pending higher-priority Pod.

## Not to be confused with

OOMKilled is about one container: the kernel killed it, usually for going over its own memory limit, and the kubelet restarts it in the same Pod. Evicted is about the whole Pod: the kubelet failed it because the node was short, and a controller must create a new Pod. Rule: OOMKilled = container over its limit, restarted; Evicted = node short, Pod replaced. Debugging both is in [Pod errors](card:pod-errors).

## Interview Qs

### Which Pods go first when a node runs low on memory?

Pods using more than their memory requests: all BestEffort Pods and Burstable Pods that are over. Among them, lower priority goes first, then the Pod furthest above its request. Guaranteed Pods and Pods within their requests go last.

### How do you protect a critical Pod from eviction?

Make it Guaranteed, with requests equal to limits for CPU and memory in every container, so it never uses more than it reserved. Give it a high PriorityClass. Run several replicas spread over nodes, because no setting makes one Pod safe from a node failure.

### Does a PodDisruptionBudget stop evictions?

Only API-initiated ones, such as `kubectl drain`, which ask before evicting. Node-pressure eviction by the kubelet ignores PodDisruptionBudgets and the grace period. Preemption by the scheduler respects them only on a best-effort basis.
