## What it is

A taint is a mark on a node that repels Pods: the scheduler does not place a Pod there unless the Pod has a matching toleration. A taint has a key, an optional value and an effect, written `key=value:effect`, such as `dedicated=payments:NoSchedule`. A toleration is an entry in the Pod spec that says "I accept this taint". [Scheduling](card:scheduling) checks taints in its filter step.

## Why it exists

Some nodes are meant for a few workloads only: GPU nodes, nodes reserved for the payments team, or the control-plane nodes. With node affinity you can pull your own Pods towards those nodes, but nothing stops every other Pod in the cluster from landing there too. A taint turns the default around: the node is closed to all Pods, and only Pods with a toleration may use it.

## How it works

<Compare id="taints-vs-node-affinity" />

1. An admin taints a node, for example `kubectl taint nodes node-7 dedicated=payments:NoSchedule`.
2. When the scheduler filters nodes for a new Pod, it ignores every taint the Pod tolerates. A toleration matches when the key and effect are the same and either the value is equal (operator `Equal`, the default) or the operator is `Exists`, which needs no value.
3. Any taint left over acts on the Pod. A `NoSchedule` taint keeps the Pod off the node; a `PreferNoSchedule` taint only makes the scheduler avoid it.
4. A `NoExecute` taint also acts on Pods already running there. Pods that do not tolerate it are evicted at once. Pods that tolerate it with `tolerationSeconds` stay that many seconds, then are evicted; without `tolerationSeconds` they stay.

So taints only filter nodes out; they never pull a Pod in.

## Example

A dedicated node pool for the payment service. First the admin marks node-7:

```bash
kubectl taint nodes node-7 dedicated=payments:NoSchedule
kubectl label nodes node-7 dedicated=payments
```

Then the payment-service Pod template tolerates the taint and requires the label:

```yaml
tolerations:
  - { key: dedicated, operator: Equal, value: payments, effect: NoSchedule }
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - { key: dedicated, operator: In, values: [payments] }
```

What to notice:

- The taint keeps every Pod without the toleration off node-7. Pods already running there stay, because the effect is `NoSchedule`.
- The toleration matches key, value and effect, so payment Pods may use node-7. Without the `affinity` block they could still land on any other node.
- The required node affinity sends payment Pods only to nodes labelled `dedicated=payments`. The taint and the label are separate: a taint is not a label.
- `kubectl taint nodes node-7 dedicated=payments:NoSchedule-`, with a trailing minus, removes the taint.

## Rules and defaults

- **Control-plane nodes:** kubeadm taints them `node-role.kubernetes.io/control-plane:NoSchedule`, so application Pods stay off them.
- **Built-in taints:** when a node has a problem, Kubernetes taints it, for example `node.kubernetes.io/not-ready` or `node.kubernetes.io/unreachable` with `NoExecute`, and `node.kubernetes.io/memory-pressure` or `disk-pressure`.
- **300 seconds (Kubernetes 1.37):** Kubernetes adds tolerations for `not-ready` and `unreachable` with `tolerationSeconds: 300` to every Pod that does not set them, so Pods stay on a failed node for 5 minutes before eviction.
- **DaemonSet Pods:** tolerate `not-ready` and `unreachable` with no time limit, so they are never evicted for them.
- **Several taints:** a node can have many. The Pod must tolerate every `NoSchedule` and `NoExecute` taint to be placed there.
- **Tolerate everything:** a toleration with an empty key and operator `Exists` matches every key and value.
- **nodeName:** a Pod that sets `nodeName` skips the scheduler and lands even on a `NoSchedule` node, but a `NoExecute` taint still evicts it.

## Interview Qs

### Why do normal Pods not run on control-plane nodes?

kubeadm taints those nodes with `node-role.kubernetes.io/control-plane:NoSchedule`. Only Pods that tolerate it, usually system components, are placed there. Removing the taint, as single-node test clusters often do, lets any Pod in.

### What happens to Pods when a node becomes unreachable?

Kubernetes taints the node `node.kubernetes.io/unreachable` with `NoExecute`. Every Pod has an automatic toleration for it with `tolerationSeconds: 300`, so about 5 minutes later the Pods are evicted, and their controllers create new Pods on healthy nodes. Set your own toleration to change that wait.

### How do you reserve nodes for one workload?

Taint the nodes so other Pods stay off, and label them. Give the workload a toleration for the taint and a required node affinity to the label. The taint alone lets the workload in but does not keep it there; the affinity alone keeps it there but lets everyone else in too.
