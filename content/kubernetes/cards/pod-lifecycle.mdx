## Why it exists

Rollouts, scale-in and node drains stop Pods all the time. A fixed shutdown order lets the app finish in-flight payments first.

## How it works

<Steps label="What happens when a Pod is deleted">
  <Step title="Terminating">The API server records the deletion and the grace period.</Step>
  <Step title="Out of endpoints">In parallel, the Pod's endpoints turn not ready, so Services stop sending new requests.</Step>
  <Step title="preStop hook">If set, it runs inside the container first.</Step>
  <Step title="SIGTERM">Sent to process 1 in each container; the app drains and exits.</Step>
  <Step title="SIGKILL">Anything still running when the grace period ends is killed.</Step>
</Steps>

- Endpoint removal and SIGTERM race, so a short preStop sleep keeps late requests from hitting a closing app.
- Error reasons such as CrashLoopBackOff: [Pod Errors](card:pod-errors).

## Example

```yaml
spec:
  terminationGracePeriodSeconds: 45   # preStop 10 s + Spring Boot 30 s + margin
  containers:
    - name: app
      image: payment-service:1.4.0
      lifecycle:
        preStop:
          sleep: { seconds: 10 }      # let endpoint removal catch up
```

## Defaults

| What | Default | Where |
|---|---|---|
| Grace period | 30 seconds | Kubernetes 1.37, terminationGracePeriodSeconds |
| restartPolicy | Always | Kubernetes 1.37 Pod spec |
| Web server shutdown | graceful, 30 s per phase | Spring Boot 4.1, server.shutdown and spring.lifecycle.timeout-per-shutdown-phase |

## Interview Qs

### How does Kubernetes stop a Pod gracefully?

It marks the Pod Terminating and takes it out of Service endpoints, runs any preStop hook, sends SIGTERM, waits up to terminationGracePeriodSeconds, then sends SIGKILL.

### A Pod shows Running but users get errors. Why?

Running only means the containers started. The app may still be warming up or broken; a readiness probe keeps such Pods out of traffic. See [Probes](card:probes).
