## Why it exists

Kubernetes knows Deployments, not databases. Running PostgreSQL well needs backups, leader election and careful upgrades: work a human operator would do.

## How it works

<Compare id="crd-vs-operator" />

- The operator runs the same [reconcile loop](card:what-is-kubernetes) as built-in controllers: compare desired with actual, then act.
- Admission webhooks let an extension check or change objects on write: mutating ones run first, then validating.

## Example

With the CloudNativePG operator installed, payments-db is one object:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: payments-db
  namespace: payments
spec:
  instances: 3
  storage:
    size: 20Gi
```

## Interview Qs

### When would you use an operator?

For stateful software with real operating know-how: databases, Prometheus, certificates. Use an existing operator first; write your own only if none fits.

### Helm or an operator: what is the difference?

Helm installs or upgrades manifests when you run it, then stops. An operator keeps running, watches its objects and reacts later: it takes backups, upgrades the software with its schema and can pick a new leader.

### Should config go in a ConfigMap or a custom resource?

A ConfigMap, if a program in a Pod just reads it as a file or env vars. A custom resource, if you want kubectl and API support, and automation that watches it and manages other objects.
