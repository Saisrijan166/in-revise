## What it is

A CustomResourceDefinition (CRD) teaches the API server a new kind of object, such as `Cluster` for a PostgreSQL database. Once it is applied, you can create, list and delete objects of that kind, called custom resources, with `kubectl`, just like Deployments. An operator is a program that runs in the cluster and watches those objects. It is a custom controller: like the built-in ones from [what Kubernetes is](card:what-is-kubernetes), it compares what an object asks for with what exists, and acts to close the gap.

## Why it exists

Kubernetes knows how to keep 3 Pods running, but not how to run PostgreSQL well. A database also needs one primary and some replicas, backups, careful upgrades, and a new primary when the old one fails. Without an operator, a person does these steps by hand from a runbook, often at night. An operator turns that know-how into code that keeps watching, and the CRD lets you ask for it with one short object.

## How it works

1. You install the CRD, usually together with the operator. The API server now serves a new URL path for the kind, such as `/apis/postgresql.cnpg.io/v1/.../clusters`.
2. You apply a custom resource that describes what you want: 3 instances with 20Gi each. The API server checks it against the CRD's schema and stores it. Nothing else happens yet.
3. The operator, running as an ordinary Deployment, is told about the new object through a watch.
4. It compares the request with what exists and creates the missing pieces, then writes progress into the object's `status`.
5. It keeps watching. If the primary fails, it promotes a replica; if you change `instances`, it adds or removes one.

So the key is: the CRD is the form you fill in; the operator is the worker who reads it and does the job.

## Example

With the CloudNativePG operator installed, the payment service's database is one short object.

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: payments-db
  namespace: payments
spec:
  instances: 3          # one primary and two replicas
  storage:
    size: 20Gi          # one volume of this size per instance
```

What to notice:

- `apiVersion` names the group `postgresql.cnpg.io`, which exists only because the operator's CRD added it.
- You say what you want, not how: there is no StatefulSet, no failover script and no backup Job in your YAML.
- CloudNativePG manages its Pods and volumes directly, without a StatefulSet, so it can choose which instance to restart or promote.
- Change `instances: 3` to `5` and apply again: the operator adds two replicas.

## Rules and defaults

- **Delete with care:** deleting a CRD removes the kind from the API and deletes every custom object of that kind.
- **Naming:** a CRD's name must be `<plural>.<group>`, such as `clusters.postgresql.cnpg.io`. Its scope is either namespaced or cluster-wide.
- **Validation:** the CRD carries an OpenAPI schema, and the API server rejects custom resources that do not match it.
- **Admission webhooks:** an operator may also register webhooks that check or change its objects when they are written; mutating ones run first, then validating ones.

## Not to be confused with

[Helm](card:helm-and-kustomize) installs or upgrades manifests when you run it, then stops. An operator keeps running and reacts later, for example when a Pod fails at 3 a.m. Rule: Helm installs once; an operator looks after the app all the time. Operators are often installed with Helm.

## Interview Qs

### When would you use an operator?

For stateful software that needs real operating know-how: databases, Prometheus monitoring, TLS certificates. Use a mature existing operator first; write your own only when none fits, because you then own its bugs and upgrades.

### Should config go in a ConfigMap or a custom resource?

A [ConfigMap](card:configmaps-and-secrets), if a program in a Pod only reads it as a file or environment variables. A custom resource, if you want API support, with `kubectl get` and validation, and a controller that watches it and manages other objects.

### How is an operator like the built-in Deployment controller?

Both follow the same control loop: watch objects through the API, compare the desired spec with what exists, act, and write `status`. The Deployment controller is built into the control plane and knows only Deployments. An operator usually runs as your own Deployment and knows one application, such as PostgreSQL.
