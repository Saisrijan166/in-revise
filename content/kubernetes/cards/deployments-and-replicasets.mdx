## What it is

A Deployment is the object you use to run a stateless app, such as payment-service, as several identical Pods. It holds a Pod template (the Pod spec to copy) and a replica count. A ReplicaSet is the [controller](card:what-is-kubernetes) object underneath: it keeps exactly that many Pods matching its label selector alive. You write the Deployment; the Deployment creates and resizes the ReplicaSets for you.

## Why it exists

A bare [Pod](card:pods) that dies stays dead, and changing its image means deleting it and creating a new one, with downtime. You want three copies that come back on their own, and upgrades that swap old Pods for new ones a few at a time. The ReplicaSet solves the first problem by counting Pods. The Deployment solves the second by creating a new ReplicaSet for each new version and moving Pods across gradually, keeping the old one for rollback.

## How it works

1. You apply the Deployment with `replicas: 3` and a Pod template.
2. The Deployment controller creates a ReplicaSet named after the Deployment plus a hash of the template, such as `payment-service-56d69c59b6`.
3. The ReplicaSet creates 3 Pods from the template. It finds its Pods by their labels.
4. A Pod dies. The ReplicaSet counts 2 of 3 and creates a new Pod.
5. You change the image in the template. The Deployment creates a second ReplicaSet, scales it up while it scales the old one down, and leaves the old one at 0 Pods for rollback.

So the key is: the ReplicaSet keeps the count, and the Deployment manages versions.

## Example

The payment-service Deployment in the `payments` namespace:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: payment-service, namespace: payments }
spec:
  replicas: 3
  selector:
    matchLabels: { app: payment-service }
  template:                                # Pod template: a change here starts a rollout
    metadata:
      labels: { app: payment-service }     # must match the selector
    spec:
      containers:
        - name: payment-service
          image: payment-service:1.4.0
          ports: [{ containerPort: 8080 }]
```

After `kubectl apply`, list what the Deployment created:

```bash
kubectl get rs,pods -n payments
```

```text output
NAME                                         DESIRED   CURRENT   READY   AGE
replicaset.apps/payment-service-56d69c59b6   3         3         3       3s

NAME                                   READY   STATUS    RESTARTS   AGE
pod/payment-service-56d69c59b6-6zkbg   1/1     Running   0          3s
pod/payment-service-56d69c59b6-8tkt5   1/1     Running   0          3s
pod/payment-service-56d69c59b6-lk9lx   1/1     Running   0          3s
```

What to notice:

- `selector.matchLabels` and the template's `labels` must agree; if they do not, the API server rejects the Deployment.
- The ReplicaSet is named after the Deployment plus a hash of the template (`56d69c59b6`), and each Pod adds a random suffix. Change anything in `template`, such as the image tag, and a second ReplicaSet with a new hash appears.
- `replicas: 3` is the only number you manage. Change it with `kubectl scale` and the current ReplicaSet just adds or removes Pods.

## Rules and defaults

- **replicas:** 1 if you leave it out (Kubernetes 1.37). An autoscaler can change it for you; see [Autoscaling](card:autoscaling).
- **Selector:** required in `apps/v1`, must match the template labels, and is immutable after creation. To change it, create a new Deployment.
- **What starts a rollout:** only a change to `.spec.template`. Scaling never creates a revision.
- **History:** `revisionHistoryLimit` keeps 10 old ReplicaSets by default. Delete one and you can no longer roll back to that revision.
- **restartPolicy:** a Deployment's Pod template allows only `Always`.
- **Do not edit owned ReplicaSets:** the Deployment controller resets them. How the swap happens and how to undo it is in [Rolling Updates and Rollbacks](card:rolling-updates-rollbacks).
- **Replicas are not machines:** 3 replicas can land on one node; the scheduler only prefers to spread them unless you add rules (see [Scheduling](card:scheduling)).

## Not to be confused with

A ReplicaSet only keeps N matching Pods running; it does not update Pods that already exist when its template changes. A Deployment sits on top and adds versions: a new ReplicaSet per template change, a gradual swap, and rollback. A [Service](card:services), which you will meet next, does not run anything; it gives the Pods one stable address. Rule: Deployment = what runs and how it updates; ReplicaSet = how many; Service = how to reach them.

## Interview Qs

### Which resource keeps a desired number of replicas running?

A ReplicaSet does the counting: it compares running Pods with the wanted number and creates or deletes Pods. In practice you create a Deployment, which manages the ReplicaSet and adds rolling updates and rollbacks.

### Why use a Deployment instead of a ReplicaSet directly?

A ReplicaSet does not update Pods that already exist when its template changes, and it keeps no history. A Deployment creates a new ReplicaSet per template change, moves Pods over gradually and keeps old ReplicaSets so you can roll back.

### What does kubectl scale deployment payment-service --replicas=5 change?

Only the desired count. The current ReplicaSet creates two more Pods from the same template. No new ReplicaSet or revision is made, because the Pod template did not change.
