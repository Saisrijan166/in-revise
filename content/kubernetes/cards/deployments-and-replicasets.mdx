## Why it exists

Stateless apps need N identical copies that come back when one dies and can be upgraded without downtime. ReplicaSets keep the count; Deployments add versioned updates.

## Example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: payment-service, namespace: payments }
spec:
  replicas: 3
  selector:
    matchLabels: { app: payment-service }
  template:                                # Pod template: change it to roll out
    metadata:
      labels: { app: payment-service }     # must match the selector
    spec:
      containers:
        - name: app
          image: payment-service:1.4.0
          ports: [{ containerPort: 8080 }]
```

## Interview Qs

### Which resource keeps a desired number of replicas running?

A ReplicaSet does the counting, but you create a Deployment, which manages the ReplicaSet and adds rolling updates and rollbacks.

### Why use a Deployment instead of a ReplicaSet directly?

A ReplicaSet does not update existing Pods when its template changes. A Deployment makes a new ReplicaSet per template change, moves Pods over gradually and keeps old ReplicaSets for rollback.

### What does `kubectl scale deployment payment-service --replicas=5` change?

Only the desired count: the current ReplicaSet adds two Pods. No new ReplicaSet or revision is made, because the Pod template did not change.
