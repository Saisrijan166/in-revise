## What it is

Kubernetes, often written K8s, is an open-source platform that runs containers on a group of machines and keeps them running. The group is a cluster, and each machine in it is a node. Kubernetes runs containers inside Pods: a Pod is its smallest unit, one or more containers that share a network address. You tell Kubernetes the result you want, and small programs called controllers keep working until the cluster matches it.

## Why it exists

With Docker alone you start each container by hand, on one machine. If it crashes at night, or the whole machine dies, it stays down until someone notices. With ten machines you must also choose where every container goes and remember it. Kubernetes takes over these jobs: it picks a node for each Pod, restarts containers that fail, replaces Pods lost with a node, and adds copies when you ask for more.

## How it works

<Mermaid
  alt="The control loop. The desired state says 3 payment-service Pods. A controller observes that only 2 are running, sees the difference, and creates 1 new Pod. Then it observes again. If nothing differs, it just keeps watching."
  chart={`flowchart LR
  D["Desired: 3 Pods"] --> O["Observe: 2 running"]
  O --> F{"Differ?"}
  F -- "yes" --> A["Act: create 1 Pod"]
  A --> O
  F -- "no" --> O`}
/>

1. You describe the result in an object, a record stored in the cluster. Its `spec` field holds what you want: a [Deployment](card:deployments-and-replicasets), the object that keeps copies of a Pod running, gets `replicas: 3`.
2. Kubernetes saves the object. From now on it works to make that record true.
3. A controller watches the cluster and compares the actual state, which Kubernetes writes in the object's `status` field, with the spec.
4. When they differ, for example because one Pod was lost and only 2 run, the controller asks for a new Pod.
5. It never stops checking. This repeating compare-and-fix is called reconciliation.

So the key is that you describe the end result, not the steps to reach it.

## Analogy

<Analogy title="A thermostat" limit="A thermostat controls one number in one room. Kubernetes runs many independent controllers, each watching its own kind of object.">
You set 22 °C, the desired state. The thermostat reads the room, the actual state, and switches the heater on or off until the two match. You never tell it when to switch.
</Analogy>

## Example

The payment service runs as 3 Pods in `payments`, a named section of the cluster. Using kubectl, the command-line tool ([kubectl and manifests](card:kubectl-and-manifests) teaches it), delete one Pod and list them again; `-n payments` says which section to look in:

```bash
kubectl delete pod payment-service-75745d8486-2pcwn -n payments
kubectl get pods -n payments
```

```text output
pod "payment-service-75745d8486-2pcwn" deleted from payments namespace
NAME                               READY   STATUS    RESTARTS   AGE
payment-service-75745d8486-7lx6j   1/1     Running   0          51s
payment-service-75745d8486-bx24c   1/1     Running   0          32s
payment-service-75745d8486-hwwkk   1/1     Running   0          51s
```

What to notice:

- There are still 3 Pods. `2pcwn` is gone, and `bx24c`, with a fresh name and a younger `AGE`, took its place.
- Nobody ran a "start" command. The controller saw 2 Pods against 3 wanted and created one.
- To really run fewer Pods you change `replicas` in the spec. Deleting Pods only makes the controller replace them.

## Not to be confused with

Docker builds images and runs containers on one machine. Docker Compose starts a multi-container app from one file, also on one machine. Kubernetes runs containers across many machines and keeps the desired state true. Rule: Docker and Compose run containers on one host; Kubernetes runs and heals them across a cluster.

## Interview Qs

### What is container orchestration, and how does Kubernetes do it?

Orchestration means deciding where containers run, how many run and what happens when they fail, across many machines. Kubernetes does not run a fixed script like "first A, then B". Many independent controllers each compare the desired state with the actual state and act, so the cluster keeps moving toward what you declared.

### What does self-healing cover, and what are its limits?

The kubelet restarts failed containers, and controllers such as a Deployment's replace lost Pods, also when a node dies. A Pod is replaced only if a controller manages it. Self-healing cannot fix application bugs or broken storage: a container that crashes on start keeps crashing.

### What does Kubernetes give you, and what does it not do?

It gives service discovery and load balancing, rolling updates and rollbacks, Secrets and configuration, batch jobs, scaling and self-healing. It does not build your app or deploy source code; the CI/CD pipeline does. It ships no built-in database, cache or message bus, and does not choose your logging or monitoring tools.
