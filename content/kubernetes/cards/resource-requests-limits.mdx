## What it is

Each container can declare two amounts of CPU and memory under `resources`. The request is the amount reserved for it on a node; the limit is the most it may use. CPU is counted in cores, where `250m` (250 millicores) is a quarter of a core. Memory is counted in bytes, where `512Mi` means 512 mebibytes.

## Why it exists

A node has fixed CPU and memory, shared by all its Pods. Without requests, the [scheduler](card:kubernetes-architecture) cannot tell whether a new payment Pod fits on a node, so it may pack too many Pods onto one machine. Without limits, one container with a memory leak can use all of the node's memory and hurt every other Pod there. Requests make placement safe; limits contain a container that misbehaves.

## How it works

<Compare id="requests-vs-limits" />

1. You set requests and limits per container. A Pod's request is the sum of its containers' requests.
2. The scheduler places the Pod only on a node where this Pod's requests, added to the requests of the Pods already there, fit within the node's allocatable capacity. It does not look at real usage.
3. When the Pod starts, the kubelet passes the numbers to the container runtime, which sets them in the Linux kernel's cgroups, the feature that controls how much CPU and memory a group of processes gets.
4. While the container runs, it may use more than its request whenever the node has spare. If it reaches its CPU limit, the kernel makes it wait, so it runs slower.
5. If it goes over its memory limit, the kernel may kill it when it detects memory pressure. The status shows OOMKilled with exit code 137, and the kubelet restarts the container.

So requests decide where a Pod runs, and limits decide how far it may grow there.

## Example

The payment service container reserves a quarter core and 512Mi, and sizes the Java heap to the limit:

```yaml
containers:
  - name: payment-service
    image: payment-service:1.4.0
    resources:
      requests: { cpu: 250m, memory: 512Mi }
      limits: { cpu: 500m, memory: 512Mi }
    env:
      - name: JDK_JAVA_OPTIONS
        value: "-XX:MaxRAMPercentage=75"   # heap up to 75% of 512Mi
```

What to notice:

- The scheduler reserves 250m CPU on the chosen node. The app may use up to 500m when the node has spare CPU; above that it is throttled.
- The memory request equals the limit, so the Pod never uses more memory than it reserved. [QoS and eviction](card:qos-and-eviction) shows why that protects it when a node runs short.
- Java 25 reads the container's memory limit and, by default, caps the heap at 25% of it, here 128Mi. `MaxRAMPercentage=75` raises that to 384Mi and leaves 128Mi for memory outside the heap.
- Remove the memory limit, and a leak can grow until the whole node runs short of memory.

## Rules and defaults

- **Limit without request:** Kubernetes copies the limit and uses it as the request, unless a LimitRange in the namespace already set a default request.
- **Neither set:** no reservation and no cap, unless the namespace has a [LimitRange](card:limitrange) that adds defaults.
- **Unit case matters:** `m` means milli, so `400m` of memory is 0.4 bytes. Use `Mi` (2^20 bytes) or `M` (10^6 bytes) for memory.
- **CPU request when the node is busy:** it works as a weight, so a container with a larger request gets more CPU time.
- **Namespace guard rails:** a LimitRange sets defaults and minimum and maximum values per container; a [ResourceQuota](card:resourcequota) caps the total requests and limits of a namespace.
- **In-place resize (stable since Kubernetes 1.35):** you can change the CPU and memory of a running Pod without recreating it, through the Pod's `resize` subresource.

## Common mistakes

- **"The Pod ran fine on my laptop, so it needs no requests."** Without requests, the scheduler treats the Pod as needing nothing, so it can land on a node that is already full. Set requests from measured usage.
- **"The memory limit is only for the Java heap."** It covers every byte the container uses, including metaspace, thread stacks and native buffers, so the heap must stay well below it.

## Interview Qs

### What happens when a container goes over its CPU limit, and over its memory limit?

Over the CPU limit, the kernel throttles it, so it only gets slower. Over the memory limit, the kernel may kill it when it detects memory pressure; the status shows OOMKilled with exit code 137, and the kubelet restarts the container.

### What happens if a container sets no requests?

If it sets only a limit, Kubernetes copies the limit as the request. If it sets neither and no LimitRange adds defaults, it gets no reservation and no cap. A Pod in which no container sets any CPU or memory value is BestEffort, the first to be evicted.

### How do you size memory for a Spring Boot container?

Measure real usage, set the memory request and limit from it, and size the heap below the limit. Java 25 reads the container limit and caps the heap at 25% of it by default; raise that with `-XX:MaxRAMPercentage`, leaving room for metaspace, threads and native memory, or the container is OOM-killed.
