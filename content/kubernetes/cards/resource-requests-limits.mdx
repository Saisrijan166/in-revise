## Why it exists

Many Pods share one node. Without declared needs the scheduler cannot pack nodes safely, and one greedy container can starve the rest.

## How it works

<Compare id="requests-vs-limits" />

- With neither set, a container is unbounded unless a namespace [LimitRange](card:limitrange) injects defaults.
- They also decide the [QoS class and eviction order](card:qos-and-eviction); the [HPA](card:autoscaling) needs CPU requests.
- [In-place resize](card:in-place-resize) (stable since 1.35) changes a running Pod's CPU and memory without recreating it.

## Example

```yaml
containers:
  - name: payment-service
    image: payment-service:1.4.0
    resources:
      requests: { cpu: 250m, memory: 512Mi }
      limits: { cpu: 500m, memory: 512Mi }
    env:
      - name: JDK_JAVA_OPTIONS
        value: "-XX:MaxRAMPercentage=75"   # heap up to 75% of 512Mi
```

## Interview Qs

### What happens when a container goes over its CPU limit, and over its memory limit?

Over CPU, the kernel throttles it, so it only gets slower. Over memory, the kernel's OOM killer stops it; the status shows OOMKilled, exit code 137, and the kubelet restarts it.

### What happens if a container sets no requests?

If it sets only a limit, the request copies the limit. If it sets neither and no LimitRange adds defaults, it gets no reservation and no cap; a Pod with none at all is BestEffort.

### How do you size memory for a Spring Boot container?

Java 25 reads the container's memory limit by default, and the heap gets 25% of it. Raise that with `-XX:MaxRAMPercentage`, but leave room for memory outside the heap, or the container is OOM-killed.
