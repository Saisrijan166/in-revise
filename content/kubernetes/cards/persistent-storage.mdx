## What it is

A PersistentVolume (PV) is a piece of storage in the cluster, such as a cloud disk or an NFS share, that exists on its own, outside any Pod. A PersistentVolumeClaim (PVC) is a request for storage made inside a namespace: "I need 20 GiB that one node can read and write". A StorageClass describes a kind of storage, such as fast SSD, and how to create it. The Pod never names the disk; it mounts the claim through a [persistentVolumeClaim volume](card:volumes).

## Why it exists

The PostgreSQL Pod behind the payment service must keep its data when the Pod restarts, moves to another node or is replaced in an update. An emptyDir dies with the Pod. Writing a cloud disk's ID into the Pod spec would tie every manifest to one cloud and one disk. With a PVC, the app team asks only for size and access mode; the cluster finds or creates matching storage, and the same manifest works on any cluster.

## How it works

1. The app team applies a PVC with a size, an access mode and, optionally, a `storageClassName`. With no class name, the cluster's default StorageClass is used, if there is one.
2. With dynamic provisioning, the class's provisioner, usually a CSI driver, creates a new disk and a PV for it. With static provisioning, an admin created PVs in advance, and a matching one is chosen.
3. A control loop binds the PVC to the PV, one to one; no other claim can use that PV. If nothing matches, the claim stays unbound until a match appears.
4. The Pod lists a `persistentVolumeClaim` volume with the claim's name, and the kubelet mounts the disk on the Pod's node.
5. When the Pod is deleted, the PVC and PV stay. When the PVC is deleted, the PV's reclaim policy decides: `Delete` removes the PV and the disk, and `Retain` keeps both as `Released` for an admin.

So the key is: Pods come and go, the claim keeps the data.

## Example

An admin defines a storage tier once, and the payments database claims 20 GiB of it:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: fast-ssd }
provisioner: ebs.csi.aws.com            # AWS EBS CSI driver, gp3 disks by default
reclaimPolicy: Retain                   # keep the disk if the claim is deleted
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: payments-db-data, namespace: payments }
spec:
  storageClassName: fast-ssd
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 20Gi } }
```

What to notice:

- `reclaimPolicy: Retain` protects the payments data. Leave it out and the class uses `Delete`, so deleting the claim also deletes the disk.
- `WaitForFirstConsumer` creates the disk only when a Pod uses the claim, in the zone where that Pod can run. With the default `Immediate`, a zonal disk can land where the Pod cannot be scheduled.
- `allowVolumeExpansion: true` lets you raise `storage` later, for example to `50Gi`. You can never shrink a claim.
- A [StatefulSet](card:statefulsets) does not need this PVC written by hand: its `volumeClaimTemplates` create one claim per replica.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Reclaim policy, dynamic PV | `Delete` (inherited from the StorageClass) | Kubernetes 1.37 |
| Reclaim policy, manually created PV | `Retain` | Kubernetes 1.37 |
| `volumeBindingMode` | `Immediate` | StorageClass, Kubernetes 1.37 |

- **Access modes:** ReadWriteOnce (RWO, one node), ReadOnlyMany (ROX), ReadWriteMany (RWX) and ReadWriteOncePod (RWOP, one Pod; CSI volumes only, stable since 1.29). A volume is mounted with one mode at a time.
- **Modes are for matching:** apart from RWOP, access modes do not enforce anything after mounting; a ReadOnlyMany volume is not guaranteed to be read-only.
- **No dynamic provisioning:** `storageClassName: ""` turns it off for that claim, which then binds only to a PV with no class.
- **Protection while in use:** a PVC that a Pod uses, and a PV bound to a PVC, are not removed until they are no longer in use.
- **Recycle:** this old reclaim policy is deprecated; use dynamic provisioning instead.

## Interview Qs

### What happens to the data when you delete the PVC?

The PV's reclaim policy decides. With `Delete`, Kubernetes removes the PV and the backing disk. With `Retain`, the PV and the disk stay, marked `Released`; an admin cleans up or reuses the disk by hand. Dynamically provisioned PVs take their policy from the StorageClass, which defaults to `Delete`.

### Static or dynamic provisioning?

Static: an admin creates PVs in advance, and claims bind to a matching one. Dynamic: the StorageClass's provisioner, usually a CSI driver, creates a PV when a claim appears. Dynamic is the normal choice on clouds, because nobody has to guess sizes or pre-create disks.

### Why use WaitForFirstConsumer?

With `Immediate`, the disk is created as soon as the claim exists, without knowing where the Pod will run, so a zonal disk can end up in a zone the Pod cannot use. `WaitForFirstConsumer` waits until a Pod uses the claim, then creates the disk where that Pod can be scheduled.
