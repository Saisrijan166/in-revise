## Why it exists

Databases need data that survives Pod restarts and moves. Apps should ask for storage without knowing whether it is a cloud disk or NFS.

## How it works

<Compare id="pv-vs-pvc-vs-storageclass" />

- A PVC with no `storageClassName` gets the default StorageClass, if one is set; `storageClassName: ""` binds only to a PV with no class.
- Access modes mainly match claims to volumes; ReadOnlyMany does not make a mount read-only.

## Example

```yaml
# PostgreSQL data for the payments database
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: payments-db-data
  namespace: payments
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 20Gi
```

See [StatefulSets](card:statefulsets) for one claim per replica.

## Defaults

| What | Default | Where |
|---|---|---|
| Reclaim policy, dynamic PV | Delete | StorageClass `reclaimPolicy`, Kubernetes 1.37 |
| Reclaim policy, manual PV | Retain | PersistentVolume API, Kubernetes 1.37 |
| `volumeBindingMode` | Immediate | StorageClass, Kubernetes 1.37 |

## Interview Qs

### What happens to the data when you delete the PVC?

The PV's reclaim policy decides. Delete removes the PV and the backing disk. Retain keeps both as Released; an admin cleans up or reuses the disk by hand. Recycle is deprecated.

### Why use WaitForFirstConsumer?

With Immediate, a zonal disk may be created where the Pod cannot be scheduled. WaitForFirstConsumer waits for a Pod using the claim, then provisions the disk to fit that Pod's node.

### Static or dynamic provisioning?

Static: an admin creates PVs in advance and claims bind to them. Dynamic: the StorageClass's provisioner, usually a CSI driver, creates a PV when a claim appears.
