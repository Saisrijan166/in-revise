## What it is

A namespace is a named section inside one cluster. Object names must be unique inside a namespace, but the same name can exist in two namespaces, so `payments` and `orders` can each have an object called `api`. A label is a short key-value tag on an object, such as `app: payment-service`. A selector is a query on labels, such as "every Pod with `app=payment-service`", which Kubernetes objects and kubectl use to find a group of objects.

## Why it exists

One cluster usually holds many apps and teams. Without namespaces, two teams could never both name something `api`, and permissions and quotas could only be set for the whole cluster. Without labels, a Deployment would need a fixed list of Pod names, but Pods are replaced all the time and get new names. With a selector, the Deployment says "my Pods are the ones labelled `app=payment-service`" and always finds the current ones.

1. You place each object in a namespace with `metadata.namespace`, or with `-n` on the command line.
2. You add labels under `metadata.labels`. A Deployment's Pod template, the Pod description it copies, carries labels, so every Pod it creates gets them.
3. The Deployment holds a selector. Kubernetes compares it with the labels of Pods in the same namespace only.
4. A Pod whose labels match is counted as one of the Deployment's Pods. A Pod that does not match, like `app=fraud-check`, is ignored.
5. A [Service](card:services) uses a selector the same way to decide which Pods get its traffic; you will meet it in Services.

So a selector is a live query, not a fixed list: new Pods with the right labels are found at once.

## Example

The payment-service Deployment with its namespace, labels and selector:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: payments
  labels: { app.kubernetes.io/part-of: checkout }
  annotations: { example.com/owner: "payments team" }      # a note for tools, never selected
spec:
  replicas: 3
  selector: { matchLabels: { app: payment-service } }      # which Pods belong to it
  template:
    metadata: { labels: { app: payment-service, tier: backend } }   # must include the selector
    spec: { containers: [{ name: payment-service, image: "registry.example.com/payments/payment-service:1.4.0" }] }
```

```bash
kubectl get pods -n payments -l app=payment-service,tier=backend
```

```text output
NAME                               READY   STATUS    RESTARTS   AGE
payment-service-6c97df9496-5gmtz   1/1     Running   0          7s
payment-service-6c97df9496-jqfz2   1/1     Running   0          8s
payment-service-6c97df9496-k7z2t   1/1     Running   0          9s
```

What to notice:

- The template's labels include everything in the selector. Change the template to `app: payments` and the API server rejects it: `selector` does not match template `labels`.
- The template may carry extra labels, like `tier: backend`. The comma in `-l` means AND, so a Pod must have both labels.
- Without `-n payments`, kubectl looks in your context's namespace, usually `default`, and prints `No resources found in default namespace.`

## Rules and defaults

- **Initial namespaces:** `default`, `kube-system` (system components and add-ons), `kube-public` (readable by everyone) and `kube-node-lease` (node heartbeats). The `kube-` prefix is reserved.
- **Label syntax:** a label value is at most 63 characters and starts and ends with a letter or digit. A key may have a prefix. The recommended labels share the `app.kubernetes.io/` prefix (`name`, `instance`, `version`, `part-of`), so different tools describe apps the same way.
- **Set-based selectors:** `in`, `notin` and "key exists", as in `-l 'env in (prod, qa)'`.
- **Deployment selector:** in `apps/v1` it cannot be changed after creation, by apply, edit or patch. To change it, delete the Deployment and create it again.
- **Other namespaces:** calling a Service in another namespace needs the namespace in its DNS name (see [Pod networking and DNS](card:cluster-networking-dns)).

## Not to be confused with

A namespace is a hard boundary for names: every namespaced object sits in exactly one. A label is a soft tag: an object can carry many, and many objects can share one. An annotation also sits in `metadata`, but holds notes for tools and is never used by selectors. Rule: namespace = where it lives; label = how it is found; annotation = extra information.

## Common mistakes

- **Two Deployments with the same selector in one namespace.** Kubernetes does not stop you, but the two controllers fight over the same Pods and behave unpredictably. Give every Deployment a unique label, such as its own `app` value.

## Interview Qs

### How would you separate teams that share one cluster?

Give each team a namespace. Bind [RBAC](card:rbac) roles per namespace so a team can change only its own objects, set a ResourceQuota per namespace to cap CPU and memory, and add a default-deny [NetworkPolicy](card:network-policies) with rules that allow only the traffic each team needs.

### How does a Deployment know which Pods are its own?

Through its label selector. The Deployment, through the ReplicaSet it manages, counts the Pods in its namespace whose labels match, and creates or removes Pods until the count equals `replicas`. Pod names play no part, so replaced Pods with new names are still found.

### Why can you not change a Deployment's selector?

In `apps/v1` the selector is immutable after creation, so apply, edit and patch are rejected. A new selector would no longer match the Pods the Deployment already runs. Delete and recreate the Deployment; `--cascade=orphan` on the delete keeps the old Pods running meanwhile.
