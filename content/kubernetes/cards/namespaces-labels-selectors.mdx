## Why it exists

One cluster serves many teams and apps. Namespaces stop names from clashing; labels let Services and controllers find their Pods without fixed lists of names.

## How it works

<Compare id="labels-vs-annotations" />

- Equality-based: `kubectl get pods -l app=payment-service,tier!=web`. Set-based: `-l 'env in (prod, qa)'`.
- Shared tools read the recommended `app.kubernetes.io/` labels: name, instance, version, component, part-of, managed-by.
- Reaching a Service in another namespace needs the namespace in its DNS name: [Pod networking and DNS](card:cluster-networking-dns).

## Example

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  namespace: payments
  labels: { app.kubernetes.io/name: payment-service, app.kubernetes.io/part-of: checkout }
  annotations: { example.com/on-call: "payments team, #payments-oncall" }
spec:
  selector: { app: payment-service }     # every Pod with this label, in payments only
  ports: [{ port: 80, targetPort: 8080 }]
```

| What | Default | Where |

## Interview Qs

### How would you separate teams that share one cluster?

A namespace per team, [RBAC](card:rbac) Roles bound in each namespace, a ResourceQuota per namespace, and a default-deny [NetworkPolicy](card:network-policies) plus rules that allow only the traffic each team needs.

### Why can you not change a Deployment's selector?

In apps/v1 it is immutable after creation, so apply and edit are rejected. Delete and recreate the Deployment; deletion removes its Pods too, unless you use `--cascade=orphan`.
