## What it is

High availability (HA) means payment-service keeps serving when parts of the cluster fail or are taken down for maintenance. On Kubernetes it is not one setting but several layers: enough replicas, placed on different nodes and zones, traffic only to ready Pods, and a PodDisruptionBudget (PDB). A PDB is a small object that says how many Pods of an app must stay up while admins evict Pods, for example when they drain a node for an upgrade.

## Why it exists

Nodes fail, whole zones go down, and admins drain nodes for upgrades every few weeks. A Deployment with 3 replicas only promises 3 Pods, not 3 Pods in 3 places: all three may sit on one node and die together. And during an upgrade, an admin draining two nodes at once could evict every copy. HA design makes sure one failure or one maintenance step never removes all copies.

## How it works

| Layer | What you do | It survives |
|---|---|---|
| Replicas | 3 or more (HPA `minReplicas: 3`) | One Pod crashing |
| Placement | [Topology spread or anti-affinity](card:scheduling) over nodes and zones | A node or a zone going down |
| Traffic | [Readiness probes](card:probes) | Requests sent to Pods not ready yet |
| Shutdown | [Graceful shutdown](card:pod-lifecycle) | Payments cut off mid-request |
| Evictions | PDB `minAvailable: 2` | A drain removing too many Pods |
| Control plane | 3+ control-plane nodes, odd etcd count, load balancer | Losing one API server or etcd member |

1. An admin runs `kubectl drain node-1` before an upgrade. First it cordons the node: no new Pods are placed there.
2. Drain then asks the Eviction API, the API call that removes a Pod only if its budget allows, to evict each Pod on the node. It checks the PDB: with 3 Pods available and 2 required, one eviction is allowed.
3. The evicted Pod shuts down gracefully, and the ReplicaSet creates a replacement, which the scheduler places on another node.
4. If a second drain tries to evict another payment Pod before the replacement is Ready, the Eviction API refuses, and drain retries until the budget allows it.
5. A node crash skips all of this: nothing asks permission. The Pods on other nodes keep serving while replacements start.

So spreading handles crashes, and the PDB handles planned work.

## Example

The PDB for payment-service keeps at least 2 Pods available during drains.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: payment-service-pdb, namespace: payments }
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: payment-service }
```

What to notice:

- `selector` must match the Pods' labels, `app: payment-service`, the same labels the Deployment uses.
- With 3 replicas, `minAvailable: 2` allows one eviction at a time. With only 2 replicas it allows none, and a drain would wait forever.
- You set either `minAvailable` or `maxUnavailable`, never both. `maxUnavailable: 1` means the same here, and the docs prefer it because it follows the replica count when the HPA adds Pods.

## Rules and defaults

- **Who honours PDBs:** only callers of the Eviction API, such as `kubectl drain`, node upgrades and node autoscalers. `kubectl delete pod` bypasses them (Kubernetes 1.37).
- **Rolling updates:** a Deployment's rollout is limited by `maxUnavailable`, not by the PDB. But Pods down during a rollout count against the budget, so a drain at the same time may wait.
- **Percentages:** a % in a PDB is rounded up to a whole number of Pods.
- **Control plane, kubeadm:** stacked etcd runs one etcd member on each control-plane node and needs at least 3 such nodes; external etcd needs at least 3 more hosts. A managed service (EKS, GKE, AKS) runs the control plane for you.
- **etcd size:** use an odd number of members. 4 members tolerate only 1 failure, the same as 3.

## Not to be confused with

Cordon only marks a node unschedulable; the Pods already on it keep running. Drain cordons the node and then evicts its Pods, honouring PDBs. Rule: cordon stops new Pods arriving; drain also moves the existing ones off.

## Interview Qs

### Are 3 replicas enough for high availability?

Only if they run on different nodes, ideally in different zones. Three Pods on one node die together when that node fails. By default the scheduler only prefers to spread them, so add topology spread constraints or pod anti-affinity, and a PDB so maintenance does not take two down at once.

### Why an odd number of etcd members?

etcd needs a majority, (n/2)+1, to commit a write. 3 members need 2 and survive 1 failure. 4 members need 3 and still survive only 1, so the extra member adds cost, not safety. 5 members survive 2 failures, which is enough in most cases.

### Does a PDB slow down a rolling update?

No. A rollout follows the Deployment's `maxSurge` and `maxUnavailable`, not the PDB. The two meet only because Pods down during a rollout count against the budget, so a node drain that runs at the same time may have to wait.
