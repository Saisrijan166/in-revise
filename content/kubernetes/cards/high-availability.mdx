## Why it exists

Nodes fail, and admins drain them for upgrades. Without planning, one bad node or upgrade takes every copy of payment-service down.

## How it works

| Layer | Do this | Survives |
|---|---|---|
| Replicas | 3 or more (HPA min 3) | One Pod crashing |
| Placement | [Topology spread or anti-affinity](card:scheduling) over nodes and zones | A node or zone going down |
| Traffic | [Readiness probes](card:probes) | Requests to Pods not ready |
| Shutdown | [Graceful shutdown](card:pod-lifecycle) | Payments cut off mid-request |
| Evictions | PDB minAvailable 2 | A drain removing too many Pods |
| Control plane | 3+ nodes, odd etcd members, load balancer | Losing one API server or etcd member |

- `kubectl drain` evicts Pods through the Eviction API, which honours PDBs; deleting Pods skips them.

## Example

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: payment-service-pdb, namespace: payments }
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: payment-service }
```

With 3 replicas, a drain may evict one Pod; the next eviction waits until a replacement is ready elsewhere.

## Interview Qs

### Are 3 replicas enough for high availability?

Only if they run on different nodes, ideally in different zones. Three Pods on one node die together. Spread them with topology spread constraints or anti-affinity.

### Why an odd number of etcd members?

etcd needs a majority, (n/2)+1, to commit a write. 3 members survive 1 failure; 4 also survive only 1, so the extra member adds cost, not safety. A 5-member cluster survives 2 failures, enough in most cases.

### Does a PDB slow down a rolling update?

No. Rollouts follow maxSurge and maxUnavailable, not the PDB. But Pods down during a rollout count against the budget, so a drain at the same time may have to wait.
