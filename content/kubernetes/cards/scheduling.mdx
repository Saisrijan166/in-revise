## What it is

Scheduling is choosing a node for each new Pod. The [kube-scheduler](card:kubernetes-architecture), a control-plane component, does it: it watches for Pods that have no node yet, picks one, and records the choice in the Pod. You steer its choice with rules in the Pod spec, such as [labels](card:namespaces-labels-selectors) the node must carry, or other Pods to stay away from.

## Why it exists

A cluster can have hundreds of nodes with different free capacity, hardware and zones. Picking a node by hand for every payment Pod would be slow, and would break as soon as a node fails. Worse, all three replicas could land on one node, and one failure would take the whole service down. The scheduler places every Pod automatically, and your rules tell it what a good node means for this app.

## How it works

1. A new Pod is created, for example by the payment Deployment, and it has no node yet.
2. Filter: the scheduler drops every node that cannot run the Pod: too little unreserved CPU or memory for its requests, a missing required label, or a taint the Pod does not tolerate (you will see taints in [Taints and Tolerations](card:taints-and-tolerations)). If no node is left, the Pod stays Pending.
3. Score: it ranks the remaining nodes, for example higher for nodes that match preferred rules or that keep replicas spread apart.
4. Bind: it writes the best node's name into the Pod through the API server. The kubelet on that node sees the Pod and starts its containers.

So the scheduler only chooses; the kubelet runs.

## Example

The payment service asks for its 3 replicas to be spread evenly over zones, one per zone when there are three:

```yaml
# payment-service Pod template
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: { app: payment-service }
```

What to notice:

- `maxSkew: 1` means the number of payment Pods in any two zones may differ by at most 1.
- `topologyKey` is the node label that defines a group, here the zone. Use `kubernetes.io/hostname` to spread over nodes instead.
- `DoNotSchedule` makes the rule hard: a Pod that would break it stays Pending. `ScheduleAnyway` turns it into a preference.
- `labelSelector` decides which Pods are counted, here only payment-service Pods.

## Rules and defaults

- **nodeSelector:** the simplest rule; the node must carry every listed label.
- **Node affinity:** `requiredDuringSchedulingIgnoredDuringExecution` is hard; `preferredDuringSchedulingIgnoredDuringExecution` is soft, with a weight from 1 to 100. Operators include `In`, `NotIn`, `Exists` and `DoesNotExist`.
- **IgnoredDuringExecution:** rules are checked only at placement. If a node's labels change later, Pods already running there stay.
- **Pod affinity and anti-affinity:** place a Pod near, or away from, Pods with given labels, within a group set by `topologyKey`, such as one node or one zone.
- **Built-in spreading (Kubernetes 1.37):** with no constraints of your own, the scheduler uses soft defaults of maxSkew 3 per node and 5 per zone, with `ScheduleAnyway`.
- **whenUnsatisfiable:** defaults to `DoNotSchedule` in a constraint you write.
- **nodeName:** setting it skips the scheduler, and the named node's kubelet runs the Pod; it is meant for custom schedulers.

## Not to be confused with

A [taint](card:taints-and-tolerations) is set on a node and keeps away every Pod that does not tolerate it. Node affinity is set on a Pod and draws that Pod to nodes with certain labels. Rule: affinity attracts this Pod; a taint repels all other Pods.

## Common mistakes

- **"The scheduler moves running Pods to better nodes."** It places only Pods that have no node. A running Pod stays on its node until it is deleted or evicted; only its replacement is scheduled again.

## Interview Qs

### Why is a Pod stuck in Pending?

No node passed the filter: not enough free CPU or memory for its requests, no node with the required labels or affinity, or an untolerated taint. `kubectl describe pod` shows a FailedScheduling event that says how many nodes failed and why.

### nodeSelector or node affinity?

nodeSelector is the simplest: the node needs all listed labels. Node affinity can do the same and more: operators such as `In` and `NotIn`, and soft preferred rules with weights. Use nodeSelector for one fixed label, affinity for anything richer.

### Pod anti-affinity or topology spread for replicas?

Required anti-affinity allows at most one matching Pod per group, so replicas beyond the number of nodes or zones stay Pending. Topology spread allows several Pods per group and keeps the counts even, so it scales with the replica count.
