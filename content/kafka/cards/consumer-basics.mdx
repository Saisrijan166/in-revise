## What it is

A consumer is a program that reads records from Kafka topics. In Java it is a `KafkaConsumer` object inside your service, for example the Notification service that reads `PaymentCompleted` records from the `payments` topic. The consumer works in a poll loop: it calls `poll()` to fetch the next batch of records, processes them, and calls `poll()` again. Kafka never sends records on its own; the consumer pulls them.

## Why it exists

The Payment service may write 1,000 payments a second while the Notification service can send only 200 emails a second. If the brokers pushed every record as it arrived, the slow service would be flooded. Because the consumer pulls, it takes the next batch only when it is ready. The unread records wait safely in the partition log, and the consumer catches up later.

## How it works

1. The service creates a `KafkaConsumer` with the broker addresses, a `group.id` and two deserializers. A deserializer turns the key and value bytes back into objects, the reverse of the [producer's serializers](card:producer-basics).
2. It calls `subscribe(List.of("payments"))`. The consumer joins its group, and the group decides which partitions this consumer reads (the next concept, [consumer groups](card:consumer-groups)).
3. It calls `poll()`. The client fetches records from its partitions, starting at its [position](card:offsets), the next offset it has not read yet. If nothing is new, the broker holds the request for a short time instead of answering empty at once. This is called a long poll.
4. The code processes each record in the batch, for example by sending a "payment received" message to the customer.
5. It calls `poll()` again. If it does not do so within `max.poll.interval.ms`, the group treats it as stuck and gives its partitions to another consumer.

So the loop is the consumer: keep it running, and keep each batch short.

## Example

The Notification service reads `payments` and sends a message per record.

```java
var props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "notification-service");
props.put("key.deserializer", StringDeserializer.class.getName());
props.put("value.deserializer", StringDeserializer.class.getName());
try (var consumer = new KafkaConsumer<String, String>(props)) {
    consumer.subscribe(List.of("payments"));
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String, String> rec : records) {
            sendNotification(rec.key(), rec.value());   // key = orderId
        }
    }
}
```

What to notice:

- `poll(Duration.ofMillis(500))` waits at most 500 ms. With no new payments it returns an empty batch, and the loop simply polls again.
- The deserializers must match what the Payment service wrote. If it wrote JSON strings, `StringDeserializer` works; a mismatch gives garbage values or a deserialization error.
- `try (...)` closes the consumer when the loop ends, so it leaves its group cleanly and its partitions move at once instead of after a timeout.
- Nothing here saves progress by hand. By default the client does it automatically; [committing offsets](card:offset-commits) shows how, and why you may turn that off.

## Rules and defaults

- **Poll deadline:** `max.poll.interval.ms` is 300000 ms (5 minutes) by default in Kafka 4.3. Miss it and the client leaves the group.
- **Threads:** `KafkaConsumer` is not thread-safe. Use one per thread. The only method another thread may call is `wakeup()`, which makes a blocked `poll()` throw `WakeupException`, a clean way to stop the loop.
- **subscribe() or assign():** `subscribe()` joins a group and lets Kafka hand out partitions. `assign()` reads partitions you name yourself, with no group management, so nothing moves them if this consumer dies.

## Not to be confused with

A consumer is one client object in one process, reading the partitions it was given. A [consumer group](card:consumer-groups), which you will see next, is all the consumers that share one `group.id` and split a topic's partitions between them. Rule: consumer = one reader; group = the team of readers and where it resumes.

## Interview Qs

### Why does Kafka use pull instead of push?

With pull, each consumer reads at its own speed. A slow consumer falls behind and catches up later instead of being flooded, and it can fetch large batches when it is ready. Long polling stops an idle consumer from spinning: the broker holds the request until data arrives or a short wait ends.

### Can two threads share one KafkaConsumer?

No. KafkaConsumer is not thread-safe; only wakeup() may be called from another thread. Run one consumer per thread, or use one polling thread that hands records to a worker pool, taking care that offsets are not saved before the workers finish.

### When would you use assign() instead of subscribe()?

When you must read specific partitions yourself, for example a tool that re-reads partition 3 of payments. assign() uses no group, so there is no rebalancing and no automatic failover. For normal services, subscribe() is the choice, because the group spreads the partitions and moves them when a consumer dies.
