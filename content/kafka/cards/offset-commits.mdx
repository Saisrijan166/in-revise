## What it is

Committing an offset means telling Kafka how far a consumer group has got in one partition. You learnt in [offsets](card:offsets) that a consumer's position is the next offset it will read. The position lives only in the consumer's memory; a commit saves it. Kafka keeps one committed offset per group and partition, in an internal topic called `__consumer_offsets`.

## Why it exists

If the Notification service restarts, its in-memory position is gone. Without a saved offset, the new consumer would either skip everything sent while it was down or read the whole partition again. With a commit, it resumes where the group stopped. The same happens when a partition moves to another member of the [group](card:consumer-groups). When you commit decides what a crash costs: lost records or repeated ones.

## How it works

1. `poll()` returns records 0 to 3 of `payments-0`, and the consumer's position moves to 4.
2. The Notification service processes all four records.
3. It commits 4, the next offset to read. With auto commit the client does this on a timer; with manual commit your code calls `commitSync()` or `commitAsync()`.
4. The group coordinator stores (notification-service, payments-0) = 4 in `__consumer_offsets`.
5. The service processes 4 to 6 and crashes before its next commit. The next owner starts at 4, so 4, 5 and 6 run twice.

So commit after processing: the worst case is a repeat, never a gap.

## Example

The Notification service commits by hand: quickly inside the loop, and once more, safely, before it stops.

```java
props.put("enable.auto.commit", "false");   // the app decides when to commit
try {
    while (running) {
        for (var rec : consumer.poll(Duration.ofMillis(500))) {
            process(rec);                    // send the notification
        }
        consumer.commitAsync();              // fast, does not block the loop
    }
} finally {
    consumer.commitSync();                   // final commit before leaving
    consumer.close();
}
```

What to notice:

- `commitAsync()` with no arguments commits the offsets of the records the last `poll()` returned. It runs only after the whole batch is processed, so nothing is committed early.
- `commitAsync()` does not wait for the broker. If one fails, the next commit in the loop usually covers it.
- `commitSync()` in `finally` waits for the answer, so the last progress is saved before the consumer leaves.
- To commit one record, pass a map: `commitSync(Map.of(partition, new OffsetAndMetadata(rec.offset() + 1)))`. Note the `+ 1`.

## Rules and defaults

- **Auto commit (Kafka 4.3):** `enable.auto.commit=true` and `auto.commit.interval.ms=5000` by default.
- **When auto commit is safe:** only if you finish every record from one `poll()` before the next call. If records go to other threads, the commit can run ahead of the work and lose records.
- **Only members commit:** a consumer that has left the group, for example after missing `max.poll.interval.ms`, cannot commit; it may get `CommitFailedException`.
- **`__consumer_offsets`:** 50 partitions and replication factor 3 by default (Kafka 4.3 broker settings).

## Not to be confused with

The position is the next offset `poll()` will return; it moves on every poll and lives in memory. The committed offset is the saved copy that a restarted or new owner starts from. Rule: position = where this consumer is now; committed = where the group restarts.

## Interview Qs

### What does the committed offset mean?

It is the offset of the next record the group will read in that partition. After processing 0 to 3 you commit 4. After a restart or a rebalance, the partition's owner starts reading there.

### Is auto commit safe?

Only when every record from a poll is processed before the next poll. If the code hands records to other threads, the commit can run ahead, and a crash loses records. For payments, turn it off, commit after processing, and make the handler safe to run twice; idempotent consumers, later in this course, show how.

### commitSync or commitAsync?

commitSync blocks until the commit succeeds or fails for good, which slows the loop. commitAsync returns at once and reports through a callback. Use commitAsync inside the loop for speed, and commitSync on shutdown or before giving up partitions, when the result must be certain.
