## Why it exists

Consumers crash and partitions move. Kafka knows how far a group got only if the group commits it, so the next owner resumes without skipping or redoing much.

## How it works

<Compare id="auto-commit-vs-manual-commit" />

- Auto commit runs inside poll(); with async hand-off it can commit ahead of the work and lose records.
- Common pattern: commitAsync() in the loop, then commitSync() before close().
- Which guarantee this gives is [delivery semantics](card:delivery-semantics); commit on revoke is in [rebalancing](card:rebalancing).

## Example

```text
payments partition 0:   0  1  2  3 | 4  5  6
processed 0-3, commit 4   -> stored for (payment-service, payments-0) = 4
processed 4-6, crash before the next commit
restart -> resume at 4    -> 4, 5, 6 run twice (make the handler idempotent)
```

## Interview Qs

### What does the committed offset mean?

It is the offset of the next record the group will read in that partition. After processing 0 to 3 you commit 4. After a restart or rebalance, the owner starts there.

### Is auto commit safe?

Only if every record from a poll is processed before the next poll. With async hand-off, the commit can run ahead and a crash loses records. For payments, commit manually after processing and make the handler [idempotent](card:idempotent-consumers).

### commitSync or commitAsync?

commitSync blocks until the commit succeeds or fails for good. commitAsync returns at once and reports through a callback. Use async in the loop for speed and sync on shutdown for the final commit.
