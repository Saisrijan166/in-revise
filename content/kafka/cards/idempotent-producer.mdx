## Why it exists

A producer that gets no reply resends. If the first write had landed, the log would hold the payment twice. Idempotence lets the broker spot that retry and drop it.

- Conflicting settings quietly turn it off; set `enable.idempotence=true` explicitly to get a `ConfigException` instead.
- Atomic writes across partitions, with consumer offsets: [transactions](card:kafka-transactions).

## Defaults

| What | Default | Where |
|---|---|---|
| `enable.idempotence` | `true` (since 3.0) | Kafka 4.3 producer |
| `max.in.flight.requests.per.connection` | 5 | Kafka 4.3 producer |

## Interview Qs

### What is an idempotent producer?

A producer whose retries cannot create duplicates. The broker gives it a producer id; each batch carries a sequence number per partition, and the broker drops a batch it has already written. It also keeps order during retries.

### Does the idempotent producer give exactly-once?

Only for writes from one producer session into the log. It does not catch an application sending the same event twice or a consumer processing a record twice. For consumers, see [idempotent consumers](card:idempotent-consumers).

### Why must max.in.flight.requests.per.connection be 5 or less?

The broker keeps state for at most the last 5 batches of each producer. With more in flight, it could no longer check older batches for duplicates.
