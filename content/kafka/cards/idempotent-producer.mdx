## What it is

An operation is idempotent when doing it twice has the same effect as doing it once. The idempotent producer is a producer whose retries can never put the same batch into the log twice. When it starts, the broker side gives it a producer ID (PID). Every batch it sends to a partition carries a sequence number that goes up by one each time, so the leader can tell a new batch from a repeat of one it already has.

## Why it exists

The producer retries when it gets no reply in time. But "no reply" does not mean "not written": the broker may have stored the batch and the reply got lost on the way back. Without idempotence the retry is appended again, and the `payments` topic now holds the ₹500 payment twice, so the Notification service may send two receipts. Retries can also reorder records when several requests are in flight. Idempotence removes both problems inside Kafka, at almost no cost.

## How it works

  chart={`sequenceDiagram

  P->>B: batch, seq 0

  B-->>P: seq 0 already written: success, no second copy`}
/>

1. When the producer starts, it gets a producer ID that is unique to this producer session.
2. For each partition, it numbers its batches: 0, 1, 2 and so on.
3. The leader remembers, per producer and partition, the sequence numbers it has recently written.
4. A batch with a number it already has is a retry: the leader does not append it again, and answers with success.
5. A batch whose number skips ahead means an earlier one is missing, so the leader rejects it as out of order and nothing is written out of sequence.

So the key is the pair (producer ID, sequence number): together they identify each batch exactly.

## Example

The Payment service asks for idempotence explicitly but also sets `acks=1`. The producer refuses to start:

```java
var props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", StringSerializer.class.getName());
props.put("value.serializer", StringSerializer.class.getName());
props.put("enable.idempotence", "true");   // asked for explicitly
props.put("acks", "1");                    // conflicts: idempotence needs acks=all
try (var producer = new KafkaProducer<String, String>(props)) {
    System.out.println("producer created");
} catch (ConfigException e) {
    System.out.println("ConfigException: " + e.getMessage());
}
```

```text output
ConfigException: Must set acks to all in order to use the idempotent producer. Otherwise we cannot guarantee idempotence.
```

What to notice:

- Setting `enable.idempotence=true` explicitly turns a conflict into a startup error, so you find it before production.
- Remove the `enable.idempotence` line and the same code prints `producer created`: idempotence is then quietly switched off, and retries can duplicate payments.
- Remove the `acks` line too and you keep the defaults, `acks=all` with idempotence on, which is what a payment service wants.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| `enable.idempotence` | `true` (since Kafka 3.0) | Kafka 4.3 producer |
| `max.in.flight.requests.per.connection` | 5 | Kafka 4.3 producer |

- **Requirements:** `acks=all`, `retries` above 0, and `max.in.flight.requests.per.connection` of 5 or less.
- **Quiet switch-off:** if `acks` or `retries` conflict and you did not set `enable.idempotence` yourself, the producer turns idempotence off and only logs it. If you set it to `true`, it throws a `ConfigException`.
- **In-flight above 5:** with idempotence on, a value above 5 throws a `ConfigException` at startup, because the broker keeps state for only the last 5 batches of each producer.
- **Transactions:** setting `transactional.id` turns idempotence on as well; atomic writes across partitions are [Kafka transactions](card:kafka-transactions).

## Not to be confused with

The idempotent producer stops duplicate **writes** caused by producer retries; the broker does the work. An [idempotent consumer](card:idempotent-consumers) stops duplicate **effects**: your code skips an event it has already handled, using its own database. Rule: idempotent producer = clean log; idempotent consumer = each payment handled once.

## Common mistakes

- **"Kafka will drop it if my code sends the same event again."** A second `send()` is a new record with a new sequence number, so both are stored. Only the producer's own retries are deduplicated.
- **"A restarted producer continues where it stopped."** It gets a new producer ID, so a batch it sent just before the crash and sends again after restart is not caught.

## Interview Qs

### What is an idempotent producer?

A producer whose retries cannot create duplicates in the log. The broker gives it a producer ID; each batch carries a sequence number per partition, and the leader does not append a batch it has already written. It also keeps records in order when batches are retried. It is on by default since Kafka 3.0.

### Does the idempotent producer give exactly-once processing?

No. It only protects writes from one producer session into the log. It does not catch an application that sends the same event twice, or a consumer that processes a record twice after a crash. For the consumer side you need [idempotent consumers](card:idempotent-consumers) or transactions.

### Why must max.in.flight.requests.per.connection be 5 or less?

The broker keeps deduplication state for only the last 5 batches of each producer. With more requests in flight, an older batch could be retried after its state was dropped, and the broker could no longer check it for duplicates or order.
