## What it is

The producer has dozens of settings, but a service needs only a few. Three are required: where to find the cluster (`bootstrap.servers`) and how to turn the key and value into bytes (the two serializers). The safety settings from earlier concepts, `acks=all` and idempotence, are already on by default. The rest are mostly time limits that decide how long a send may block, wait and retry before it is reported as failed.

## Why it exists

A producer that waits too little drops events during a short broker restart; one that waits forever hides an outage and lets memory fill up. Many teams try to fix this by raising `retries`, which changes nothing, because retrying is already limited by time. Knowing which setting bounds which part of a send lets you decide how long a payment event may keep trying and what your code does when it finally fails.

## How it works

1. `send()` first needs the topic's metadata and space in the producer's buffer (`buffer.memory`). If either is missing, it blocks for up to `max.block.ms`, then fails the send with a `TimeoutException`.
2. Once `send()` returns, the `delivery.timeout.ms` clock starts for that record.
3. The record waits in its batch for up to `linger.ms`, then goes to the leader in a request.
4. Each request attempt waits up to `request.timeout.ms` for the broker's reply. On a temporary error the producer retries.
5. When the broker confirms, or when `delivery.timeout.ms` runs out, the callback runs with the result or the error.

So the key is that two clocks matter: `max.block.ms` for the `send()` call itself, and `delivery.timeout.ms` for everything after it.

## Example

The Payment service's producer settings: a few brokers, a name, the serializers, and an explicit time budget.

```properties
bootstrap.servers=kafka-1:9092,kafka-2:9092,kafka-3:9092
client.id=payment-service
key.serializer=org.apache.kafka.common.serialization.StringSerializer
value.serializer=org.apache.kafka.common.serialization.StringSerializer
delivery.timeout.ms=120000
```

What to notice:

- Three brokers are listed, so the producer can still start when one of them is down. It finds the rest of the cluster from metadata.
- `client.id=payment-service` makes broker request logs and quotas show which app sent each request.
- `retries` and `acks` are not set on purpose: the defaults (almost unlimited retries, `acks=all`, idempotence on) are the safe ones.
- `delivery.timeout.ms=120000` is the default written out, so the team sees and owns the 2-minute budget. Change it here, not through `retries`.

## Rules and defaults

| Config | Controls | Default (Kafka 4.3) |
|---|---|---|
| `bootstrap.servers` | Brokers to contact first | none (required) |
| `key.serializer`, `value.serializer` | Object to bytes | none (required) |
| `client.id` | App name sent with each request | empty |
| `retries` | Resends after temporary errors | 2147483647 |
| `delivery.timeout.ms` | Total time to report success or failure | 120000 (2 min) |
| `request.timeout.ms` | Wait for one broker reply | 30000 (30 s) |
| `max.block.ms` | How long `send()` may block | 60000 (1 min) |
| `buffer.memory` | Memory for records waiting to be sent | 33554432 (32 MiB) |

- **Timeout rule:** `delivery.timeout.ms` must be at least `request.timeout.ms` + `linger.ms`.
- **Already covered:** `acks` in [producer acks](card:producer-acks), batching and compression in [batching](card:batching-and-compression), `enable.idempotence` in [idempotent producer](card:idempotent-producer).
- **Spring Boot 4.1:** common settings have their own properties, such as `spring.kafka.producer.acks` and `spring.kafka.producer.compression-type`. Others, such as `linger.ms`, go in `spring.kafka.producer.properties[linger.ms]`. Spring Boot defaults the serializers to `StringSerializer` and `bootstrap-servers` to `localhost:9092`. More in [Spring for Apache Kafka](card:spring-kafka).

## Interview Qs

### What is the difference between request.timeout.ms and delivery.timeout.ms?

`request.timeout.ms` is how long the producer waits for one broker reply before it treats that attempt as failed and may retry. `delivery.timeout.ms` bounds the whole send after `send()` returns: waiting in the batch, every attempt and every retry. When it expires, the callback receives the error.

### When does send() block?

When it must fetch the topic's metadata first, or when the producer's buffer (`buffer.memory`) is full because records arrive faster than they can be sent. It blocks for up to `max.block.ms`, then fails the send with a `TimeoutException`. So a cluster outage can hold a request thread for a minute by default.

### Which producer configs would you set for a payment service?

`bootstrap.servers` with several brokers, the serializers and a `client.id`. I keep the defaults `acks=all` and idempotence on, and do not touch `retries`. I choose `delivery.timeout.ms` for how long a payment event may keep retrying, and handle the final failure in the callback.
