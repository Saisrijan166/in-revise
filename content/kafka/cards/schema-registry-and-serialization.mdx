## What it is

A schema is the agreed shape of an event: its fields and their types. A schema registry is a separate service that stores each event's schema with every version it has had. The producer's [serializer](card:producer-basics), which turns an object into bytes, checks the schema against the registry before sending. The consumer's deserializer uses the registry to turn the bytes back into an object. The common one is Confluent Schema Registry.

## Why it exists

Kafka treats every value as plain bytes and never looks inside. The Payment service and the Notification service deploy on different days. If the Payment team renames a field or changes its type, nothing stops the deploy, and every consumer fails at runtime when the new records arrive. A registry turns that runtime failure into a rejected change at the producer, before any bad record is written.

## How it works

  N->>R: get schema 7
  N->>N: decode`}
/>

1. A subject is one version history. By default it is the topic name plus `-key` or `-value`, so `payments-value`.
2. On send, the serializer registers its schema if it is new; the registry checks it against the subject's earlier version.
3. A compatible schema gets an ID; an incompatible one is refused, and the send fails at the producer.
4. By default the record value starts with one version byte (0) and the 4-byte schema ID, then the encoded data, so the schema itself is never repeated in each record.
5. The consumer fetches the schema for that ID and decodes with it.

## Example

Version 2 of the `PaymentCompleted` Avro schema adds `upiRef`, and the producer points its serializer at the registry:

```json
{
  "type": "record",
  "name": "PaymentCompleted",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "amountPaise", "type": "long" },
    { "name": "method", "type": "string" },
    { "name": "upiRef", "type": ["null", "string"], "default": null }
  ]
}
```

```properties
value.serializer=io.confluent.kafka.serializers.KafkaAvroSerializer
schema.registry.url=http://schema-registry:8081
```

What to notice:

- `upiRef` has `"default": null`, so a reader using version 2 can still read old version 1 records: it fills in null. That makes the change BACKWARD compatible.
- Remove the default and the registry rejects version 2, because new readers could not fill `upiRef` in old records.
- `KafkaAvroSerializer` talks to the registry at `schema.registry.url`; the consumer needs the matching deserializer and the same URL.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Compatibility mode | BACKWARD, checked against the latest version only | Confluent Schema Registry 8.x |
| Subject name | topic name plus `-key` or `-value` | Confluent serializers 8.x |
| Registering schemas | serializers register new schemas automatically | Confluent serializers 8.x |
| Schema storage | the `_schemas` topic, one partition | Confluent Schema Registry 8.x |

- **BACKWARD:** new readers can read old data. Adding a field with a default and deleting a field are allowed; upgrade consumers first.
- **FORWARD:** old readers can read new data. Upgrade producers first.
- **FULL:** both at once, so producers and consumers can upgrade in any order. A `_TRANSITIVE` mode checks against every earlier version, not just the latest.

## Common mistakes

- **"JSON needs no schema."** Plain JSON still has an implied shape that consumers rely on. Without a registry, a renamed field is found only when a consumer breaks.

## Interview Qs

### What does a schema registry give you that Kafka does not?

Kafka treats keys and values as bytes. A registry stores versioned schemas, gives each an ID that records carry, and rejects incompatible changes at the producer. So producers and consumers can deploy at different times without breaking each other.

### Which changes are safe under BACKWARD compatibility?

Adding a field with a default, and deleting a field. Adding a field without a default breaks it, because new readers cannot fill it in old records. Under BACKWARD you upgrade consumers before producers.

### Why Avro or Protobuf instead of plain JSON?

Both are compact binary formats with a strict schema, so records are smaller and every field has a known type. JSON repeats field names in every record and has no built-in contract; JSON Schema adds the contract but not the compact size.
