## Why it exists

Producers and consumers deploy separately. Without a shared contract, one changed field breaks every reader at runtime, and Kafka itself cannot notice.

## How it works

<Steps label="Sending and reading a PaymentCompleted record">
  <Step title="Register">The producer's serializer registers or looks up the schema under the subject payments-value.</Step>
  <Step title="Check">The registry accepts a new version only if it passes the subject's compatibility mode, then returns the schema ID.</Step>
  <Step title="Send">The record holds the schema ID plus the encoded bytes.</Step>
  <Step title="Read">The consumer's deserializer fetches the schema by that ID and decodes the record.</Step>
</Steps>

- Serializer settings belong to the producer: see [producer basics](card:producer-basics).

## Example

```json
{
  "type": "record",
  "name": "PaymentCompleted",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "amountPaise", "type": "long" },
    { "name": "method", "type": "string" },
    { "name": "upiRef", "type": ["null", "string"], "default": null }
  ]
}
```

Version 2 adds upiRef with a default, so it passes BACKWARD: new readers see null in old ₹500 records.

## Defaults

| What | Default | Where |
|---|---|---|
| Compatibility mode | BACKWARD | Confluent Schema Registry 8.x |
| Subject name | topic name plus -key or -value (TopicNameStrategy) | Confluent serializers 8.x |
| Schema storage | the _schemas topic, one partition | Confluent Schema Registry 8.x |

## Interview Qs

### What does a schema registry give you that Kafka does not?

Kafka treats keys and values as bytes. A registry stores versioned schemas, gives each an ID that records carry, and rejects incompatible changes, so producers and consumers can change at different times.

### Which changes are safe under BACKWARD compatibility?

Adding a field with a default, and deleting a field. Adding a field without a default breaks it, because new readers cannot fill it in old records.
