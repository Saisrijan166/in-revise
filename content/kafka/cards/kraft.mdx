## What it is

KRaft (Kafka Raft) is how Kafka's controllers store and agree on the cluster metadata. The metadata, which topics and partitions exist and who leads each one, is kept as a log of changes inside Kafka itself. Raft is a voting method: one controller leads and writes the log, the others copy it, and a change counts once a majority of them has it. Before KRaft, a separate system called ZooKeeper held the metadata.

## Why it exists

With ZooKeeper you ran and secured two different systems, each with its own configuration and failures. When the controller broker died, the new one had to reload all metadata from ZooKeeper before it could act, which was slow on big clusters. KRaft keeps the metadata inside Kafka and on every controller, so there is one system to run, and a standby can take over at once.

## How it works

<Mermaid
  alt="Three controllers. Controller 1 is active and writes the metadata log; controllers 2 and 3 copy it as hot standbys. The three brokers fetch new metadata records from the controllers."
  chart={`flowchart LR
  C1["Controller 1 (active)"] -- copies log --> C2[Controller 2: standby]
  C1 -- copies log --> C3[Controller 3: standby]

  C1 -. new metadata .-> B2[Broker 2]
  C1 -. new metadata .-> B3[Broker 3]`}
/>

1. An admin creates the topic `payments`. The request reaches the active controller.
2. The active controller adds a record such as "topic payments, 3 partitions, these leaders" to the `__cluster_metadata` log.
3. The standby controllers copy the record. Once a majority (2 of 3) has it, the change is final.
4. Brokers fetch the new records and update their view, so a client that asks any broker for metadata now sees `payments`.
5. If the active controller dies, the others vote in a new leader. It already holds the whole log, so it takes over quickly.

## Example

One of three dedicated controllers. Every controller and broker lists the controllers in `controller.quorum.bootstrap.servers`:

```properties
process.roles=controller
node.id=1
listeners=CONTROLLER://controller1:9093
controller.listener.names=CONTROLLER
controller.quorum.bootstrap.servers=controller1:9093,controller2:9093,controller3:9093
```

To see who leads, ask the cluster (here a test cluster of three servers):

```bash
bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status
```

```text output
ClusterId:              VIqNm6FxSKiiUtGdiY-BwA
LeaderId:               2
LeaderEpoch:            2
HighWatermark:          35600
MaxFollowerLag:         0
MaxFollowerLagTimeMs:   213
CurrentVoters:          [{"id": 1, "endpoints": ["CONTROLLER://kbs-1:9093"]}, {"id": 2, "endpoints": ["CONTROLLER://kbs-2:9093"]}, {"id": 3, "endpoints": ["CONTROLLER://kbs-3:9093"]}]
CurrentObservers:       []
```

What to notice:

- `process.roles=controller` makes this server a controller only; it stores no topic data.
- `LeaderId: 2` is the active controller. `LeaderEpoch: 2` means a second election has happened: this cluster was restarted once.
- `CurrentVoters` lists the three controllers that vote. `MaxFollowerLag: 0` means the standbys have copied the whole metadata log.

## Rules and defaults

- **Quorum size:** run 3 or 5 controllers. To survive N failures you need 2N + 1.
- **No majority, no change:** with too few controllers up, no metadata change (new topic, new leader) can be made.
- **Combined mode:** `process.roles=broker,controller` is fine for development; the docs advise against it in critical deployments.
- **Controller list:** every broker and controller sets `controller.quorum.bootstrap.servers` (the older `controller.quorum.voters` is deprecated for new clusters).
- **Upgrade path:** a ZooKeeper cluster migrates to KRaft on a 3.x bridge release (last: 3.9); a 4.x broker cannot start in ZooKeeper mode.

## Not to be confused with

ZooKeeper mode kept the metadata in a separate ZooKeeper cluster, and one broker at a time acted as the controller. KRaft keeps the metadata in Kafka's own log, run by dedicated controllers that vote. Rule: ZooKeeper = an outside system, up to Kafka 3.9; KRaft = built in, the only mode in Kafka 4.x.

## Interview Qs

### What is KRaft, and why did Kafka drop ZooKeeper?

KRaft is Kafka's Raft-based metadata mode: controllers keep the metadata in an internal log and agree on it by majority. It removes a second system to run and secure, makes controller failover fast because standbys already hold the log, and lets a cluster hold more partitions.

### How many controllers do you run?

Three or five. A majority must stay up: three survive one failure, five survive two. In production, run them separately from the brokers.

### How do you move a ZooKeeper cluster to Kafka 4.x?

Migrate the metadata to KRaft first on a 3.x bridge release, the last being Kafka 3.9, then upgrade to 4.x. A 4.x broker cannot start in ZooKeeper mode.
