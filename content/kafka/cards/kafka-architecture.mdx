## What it is

Kafka runs as a cluster: a group of servers that work as one system. Most of them are brokers, servers that store topic data on disk and answer producers and consumers. A few are controllers, which keep the cluster's metadata: which topics exist, how each is split into [partitions](card:partitions), and which broker is the leader of each partition, the one that handles its reads and writes.

## Why it exists

One server can hold only so much data, and if it crashes every service that uses it stops. Kafka spreads each topic's partitions over many brokers. To store or serve more, you add brokers. Copies of each partition on other brokers keep it available when one broker fails ([replication](card:replication), later).

## How it works

<Mermaid
  alt="The Payment service asks broker 1 for metadata, then sends its event straight to broker 2, the leader of payments partition 1. Each of three brokers leads one payments partition. The controllers send metadata to every broker. The Notification service reads from broker 3."

  PS[Payment service] -- "1. metadata?" --> B1["Broker 1: payments-0"]
  PS -- "2. send to the leader" --> B2["Broker 2: payments-1"]
  B3["Broker 3: payments-2"] -- "3. fetch" --> NS[Notification service]
  K[Controllers] -. metadata .-> B1
  K -. metadata .-> B2
  K -. metadata .-> B3`}
/>

1. The Payment service starts with `bootstrap.servers`, a short list of broker addresses.
2. It asks one of them for metadata. Every broker has it, because the controllers keep all brokers up to date.
3. The answer lists all brokers, the partitions of `payments`, and the leader broker of each partition, with the address to reach it.
4. The Payment service sends each event straight to the leader of the chosen partition. Consumers read from leaders the same way.
5. If a leader moves, for example because its broker crashed, the client gets an error, asks for fresh metadata and retries with the new leader.

So there is no router in front of Kafka: clients find the right broker themselves. How the controllers agree on the metadata is [KRaft](card:kraft), next.

## Example

A broker running in Docker, with client apps on the host machine:

```properties
process.roles=broker
node.id=2
listeners=PLAINTEXT://0.0.0.0:9092
advertised.listeners=PLAINTEXT://localhost:9092
controller.quorum.bootstrap.servers=controller1:9093
controller.listener.names=CONTROLLER
```

What to notice:

- `listeners` is where the broker accepts connections: every network interface, port 9092.
- `advertised.listeners` is the address put into metadata answers. Clients on the host can reach `localhost:9092`. If it named the container's internal hostname instead, host clients would receive that name and fail to connect: the classic Docker problem.
- `process.roles=broker` and `controller.quorum.bootstrap.servers` say that this server is only a broker and where it finds the controllers.

## Rules and defaults

- **listeners default (Kafka 4.3):** `PLAINTEXT://:9092`.
- **advertised.listeners default (Kafka 4.3):** not set, so the `listeners` value is used.
- **bootstrap.servers:** list more than one broker; the client still discovers all the others from metadata.
- **Who talks to whom:** producers and consumers talk to brokers; brokers get their metadata from the controllers.

## Not to be confused with

A broker is a server. A topic is a name for a stream of events, and a partition is one ordered log of that topic, stored on a broker. One broker holds partitions of many topics. Rule: topic = what the events are about; partition = one log of it; broker = the machine that stores it.

## Interview Qs

### What is a broker?

A Kafka server. It stores partitions on its disk, leads some of them, and answers produce, fetch and metadata requests. A cluster has several brokers so that data and traffic are spread out and a failed broker can be replaced by copies on the others.

### Clients outside Docker cannot connect, though port 9092 is open. Why?

The first connection works, but the metadata answer contains the advertised address, often the container's internal name. The client then tries that name and fails. Set `advertised.listeners` to an address the clients can reach.

### How does a producer know which broker to send to?

It asks any bootstrap broker for metadata: the topics, their partitions and each partition's leader. It then sends straight to the leader, and refreshes the metadata when a leader moves.
