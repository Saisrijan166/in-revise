## Why it exists

One server cannot hold every event or survive its own crash. Kafka spreads partitions over many brokers, so storage and traffic grow by adding machines.

## How it works

- No routing tier: producers send to the partition leader; copies live on other brokers ([replication](card:replication)).
- How controllers agree on the metadata: [KRaft](card:kraft).

## Example

A broker in Docker, with clients on the host machine:

```properties
process.roles=broker
node.id=2
listeners=PLAINTEXT://0.0.0.0:9092
advertised.listeners=PLAINTEXT://localhost:9092
controller.quorum.bootstrap.servers=controller1:9093
controller.listener.names=CONTROLLER
```

## Defaults

| What | Default | Where |
|---|---|---|
| `listeners` | `PLAINTEXT://:9092` | Kafka 4.3 broker |
| `advertised.listeners` | unset: the `listeners` value is used | Kafka 4.3 broker |

## Interview Qs

### What is a broker?

A Kafka server. It stores replicas of some partitions, leads some of them, and answers produce, fetch and metadata requests.

### Clients outside Docker cannot connect, though port 9092 is open. Why?

The first connection works, but metadata returns the advertised address, often the container's internal name. Set `advertised.listeners` to an address the clients can reach.

### How does a producer know which broker to send to?

It asks any bootstrap broker for metadata: topics, partitions and each partition's leader. It then sends straight to the leader and refreshes metadata when leaders move.
