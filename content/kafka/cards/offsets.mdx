## What it is

An offset is the position number of an event inside one [partition](card:partitions). The first event in a partition gets offset 0, the next gets 1, and so on; each partition counts on its own. Consumers use offsets to track progress: a consumer group saves, for each partition, the offset of the next event it should read. That saved number is called the committed offset.

## Why it exists

A consumer must know where it stopped, or after a restart it would read everything again or skip events. A queue tracks each message separately and removes it when done. Kafka keeps the events and numbers them in order, so a group's whole progress in a partition is one number. Different groups keep different numbers for the same partition and never disturb each other.

## How it works

| Marker in payments-0 | Means | Example |
| --- | --- | --- |
| Log-start offset | The oldest event still kept | 0 |
| Committed offset | Saved progress: where the group restarts | 3 |
| Position | The next event this running consumer will get | 5 |
| High watermark | Events below it are copied to every up-to-date copy of the partition; consumers read only below it | 7 |
| Log-end offset | Where the next new event will be written | 8 |

1. The producer writes an event; the leader stores it at the log-end offset, and the log-end moves up by one.
2. Once the copies on other brokers have it, the high watermark moves past it, and consumers may read it.
3. A consumer reads from its position, and the position moves forward as it receives events.
4. After processing, the consumer commits: it saves its position as the group's committed offset ([offset commits](card:offset-commits), later).
5. After a crash, the group restarts from the committed offset, not from where it actually stopped.

So the gap between committed offset and log-end offset is the work still to do, called [consumer lag](card:consumer-lag).

## Example

The Analytics group has read six payment events. Two more events then arrive, one in partition 0 and one in partition 2. Ask Kafka for the group's offsets:

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group analytics
```

```text output
GROUP           TOPIC           PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG             CONSUMER-ID     HOST            CLIENT-ID
analytics       payments        0          2               3               1               -               -               -
analytics       payments        1          2               2               0               -               -               -
analytics       payments        2          2               3               1               -               -               -
```

What to notice:

- `CURRENT-OFFSET` is the committed offset: in partition 0 the group has processed offsets 0 and 1 and will read offset 2 next.
- `LAG` is `LOG-END-OFFSET` minus `CURRENT-OFFSET`: one unread event in partitions 0 and 2, none in partition 1.
- Every partition shows offset 2 as the next to read: each partition counts on its own.
- `CONSUMER-ID` is `-` because no Analytics consumer is running now. The offsets stay saved anyway.

## Rules and defaults

- **Identity:** topic + partition + offset together point to exactly one event.
- **Offsets only grow:** a new event always gets a higher offset than the one before it.
- **Missing offset:** if a consumer asks for an offset that was removed, it gets the next higher one that exists.
- **Transactions:** a consumer set to `read_committed` stops even earlier, before any open [transaction](card:kafka-transactions) (later).

## Interview Qs

### Is an offset unique across a topic?

No. Every partition counts from its own start, so offset 5 exists in payments-0 and in payments-1. Topic, partition and offset together identify one event. For business identity, use an id carried in the event, such as eventId.

### What is the difference between the committed offset and the position?

The position is where a running consumer is now: the next offset it will receive. The committed offset is the progress saved for the group. They differ until the consumer commits; after a crash, the group restarts from the committed offset, so events in between are read again.

### A consumer is at position 5. What has it read?

Offsets 0 to 4 of that partition, and it gets offset 5 next. If offset 5 was compacted away or is a transaction marker, it gets the next higher offset instead.
