## What it is

A share group is a second kind of group in which several consumers read the same partition at the same time. It was added by KIP-932, "Queues for Kafka". Instead of one committed offset per partition, each record gets its own result: accepted, released for another try, or rejected. Consumers use `KafkaShareConsumer`. Share groups were a preview in Kafka 4.1 and are production-ready since Kafka 4.2.

## Why it exists

In a [consumer group](card:consumer-groups), a partition has one owner, so a 4-partition topic can keep only 4 consumers busy. One slow record also holds up every record behind it in that partition. Some work does not need order: sending a receipt email for each payment is independent of every other email. For such work you want 20 workers on 4 partitions and a retry per record. Before share groups, that meant adding partitions or running a separate queue system.

## How it works

<Mermaid
  alt="One partition P0 of the payments topic is read by three consumers of the share group email-workers at the same time. Each consumer gets different records, and each record is locked to one consumer until it is acknowledged."
  chart={`flowchart LR
  P0[payments P0] -- "record 10, locked" --> W1[worker 1]
  P0 -- "record 11, locked" --> W2[worker 2]
  P0 -- "record 12, locked" --> W3[worker 3]`}

1. Several workers create a `KafkaShareConsumer` with the same `group.id` and subscribe to `payments`.
2. On `poll()`, the broker gives each worker a batch of records and locks each record to that worker for a time limit, the acquisition lock. While it is locked, no other member gets it.
3. The worker processes each record and acknowledges it: ACCEPT (done), RELEASE (could not do it now; try again) or REJECT (can never be processed; do not deliver again). RENEW extends the lock when the work takes longer.
4. The next `poll()` or a commit sends the acknowledgements to Kafka.
5. A released record, or one whose lock ran out because the worker crashed, is delivered again. Each delivery is counted, and at the limit Kafka stops delivering it.

So a share group behaves like a queue on top of the same topic.

## Example

Email workers send a receipt per payment and decide each record's result themselves:

```java
props.put("group.id", "email-workers");
props.put("share.acknowledgement.mode", "explicit");
try (var consumer = new KafkaShareConsumer<String, String>(props)) {
    consumer.subscribe(List.of("payments"));
    while (running) {
        for (var rec : consumer.poll(Duration.ofMillis(500))) {
            boolean sent = sendEmail(rec.value());
            consumer.acknowledge(rec, sent ? AcknowledgeType.ACCEPT : AcknowledgeType.RELEASE);
        }
        consumer.commitSync();   // send the acknowledgements to Kafka
    }
}
```

What to notice:

- `explicit` mode makes you acknowledge every record before the next `poll()`; forgetting one throws `IllegalStateException`.
- A failed email gets RELEASE, so the record comes back later, maybe to another worker. A record that can never work, like a malformed payload, should get REJECT instead.
- There is no offset arithmetic: progress is tracked per record, not as one number per partition.
- Remove the `share.acknowledgement.mode` line and the default, `implicit`, applies: the next `poll()` or commit accepts the whole batch.

## Rules and defaults

- **Lock time (Kafka 4.3):** 30 s by default, set by the group config `share.record.lock.duration.ms`.
- **Delivery limit (Kafka 4.3):** `share.delivery.count.limit` is 5 by default; the minimum is 2.
- **Ordering:** none across records. Within one poll, records from one partition come in offset order, but redeliveries and other workers break that.
- **State topic:** share progress is stored in the internal topic `__share_group_state`, which needs 3 brokers by default. On a smaller cluster, lower `share.coordinator.state.topic.replication.factor` and `share.coordinator.state.topic.min.isr` before using share groups.
- **Threads:** `KafkaShareConsumer` is not thread-safe either; only `wakeup()` is safe from another thread.

## Not to be confused with

A consumer group gives each partition one owner and keeps the order inside it; progress is one committed offset per partition. A share group lets many members read one partition with no order; progress is one result per record. Rule: ordered event stream = consumer group; independent jobs that must scale = share group.

## Interview Qs

### Can Kafka act as a queue?

Yes, since Kafka 4.2, with share groups. Consumers share partitions, can outnumber them, and acknowledge each record. Failed records are redelivered up to a limit. Ordering is not guaranteed, so use them for independent jobs, not for ordered event streams.

### What happens if a share consumer crashes in the middle of a record?

Its acquisition lock runs out, 30 seconds by default, and the record becomes available to another consumer in the group. The attempt is counted. When the delivery limit is reached, Kafka stops delivering that record, so one bad record cannot loop forever.
