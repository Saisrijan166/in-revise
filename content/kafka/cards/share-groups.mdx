## Why it exists

Some work, like sending order emails, needs no order but must scale past the partition count. Consumer groups cannot do that, so Kafka added share groups.

## How it works

<Compare id="consumer-group-vs-share-group" />

- Acknowledge types: ACCEPT (done), RELEASE (try again), REJECT (unprocessable, no retry), RENEW (still working, since 4.2).
- State lives in the internal topic __share_group_state: 3 replicas by default, so 3 brokers or a config change.
- The share.version feature (kafka-features.sh) controls it; Spring support: [Spring for Apache Kafka](card:spring-kafka).

## Example

```java
props.put("group.id", "notification-service");
props.put("share.acknowledgement.mode", "explicit");
try (var consumer = new KafkaShareConsumer<String, String>(props)) {
    consumer.subscribe(List.of("orders"));
    while (running) {
        for (var rec : consumer.poll(Duration.ofMillis(500))) {
            boolean sent = sendEmail(rec.value());   // OrderPlaced -> email
            consumer.acknowledge(rec, sent ? AcknowledgeType.ACCEPT : AcknowledgeType.RELEASE);
        }
        consumer.commitSync();
    }
}
```

## Interview Qs

### Can Kafka act as a queue?

Yes, since Kafka 4.2, with share groups. Consumers share partitions, can outnumber them, and acknowledge each record. Ordering is not guaranteed, so use them for independent jobs, not ordered event streams.

### What happens if a share consumer crashes in the middle of a record?

Its acquisition lock runs out and the record goes to another consumer. Every attempt is counted; when the delivery limit is reached, Kafka stops delivering that record.
