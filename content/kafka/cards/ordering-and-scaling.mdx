## What it is

Ordering and scaling pull in opposite directions in Kafka. [Partitions](card:partitions) are the unit of parallel work: a group can run one consumer per partition. But Kafka guarantees order only inside one partition, never across a topic. Designing a topic means deciding which order you really need, choosing the [key](card:partition-keys) that keeps it, and picking a partition count.

## Why it exists

A topic with one partition is fully ordered, but only one consumer per group can read it, so it cannot keep up as traffic grows. A topic with 12 partitions and no key spreads load well, but two events of the same order can land in different partitions and be processed in the wrong order, for example "refunded" before "paid". Keying by orderId gives both: order where it matters, parallelism everywhere else.

## How it works

  alt="Producer sends events keyed by orderId. ord-1001 events go to partition 0, ord-1002 events go to partition 2. Consumer A reads partition 0, consumer B reads partition 2, so each order stays in sequence while the two orders run in parallel."

  P[Payment Service] -- "key ord-1001" --> P0[(partition 0)]
  P -- "key ord-1002" --> P2[(partition 2)]
  P0 --> A[Consumer A]
  P2 --> B[Consumer B]`}

1. The producer sends each event with key `orderId`. The default partitioner picks the partition as hash(key) mod the partition count, so one order always maps to one partition.
2. The [idempotent producer](card:idempotent-producer) keeps the records of a partition in send order even when batches are retried.
3. The consumer group gives each partition to exactly one consumer, which reads it in offset order.
4. The consumer handles a partition's records one after another. Handing them to a thread pool can let a later record finish first, so order then needs extra care.
5. To scale, you add partitions and consumers. Each order still has one partition, but which one depends on the count.

So order is per key, and only as long as the partition count stays the same.

## Example

The `orders` topic is grown from 6 to 12 partitions, then someone tries to shrink it back:

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic orders --partitions 12
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic orders --partitions 6
```

```text output
ERROR org.apache.kafka.common.errors.InvalidPartitionsException: The topic orders currently has 12 partition(s); 6 would not be an increase.
```

This program applies the default partitioner's formula to four order ids, before and after the change:

```java
for (String orderId : List.of("ord-1001", "ord-1002", "ord-1009", "ord-1011")) {
    byte[] key = orderId.getBytes(StandardCharsets.UTF_8);
    int hash = Utils.toPositive(Utils.murmur2(key));      // what the default partitioner uses
    System.out.println(orderId + ": partition " + hash % 6 + " of 6, " + hash % 12 + " of 12");
}
```

```text output
ord-1001: partition 0 of 6, 6 of 12
ord-1002: partition 2 of 6, 8 of 12
ord-1009: partition 2 of 6, 2 of 12
ord-1011: partition 1 of 6, 1 of 12
```

What to notice:

- Growing succeeds silently; shrinking is refused. A partition count can only go up.
- Two of the four orders move. New events of ord-1001 now go to partition 6, while its older events are still in partition 0, which another consumer may be behind on.
- Existing records are not moved. Kafka only changes where new records go.

## Rules and defaults

- **Order guarantee:** only within a partition. Records with the same key go to the same partition while the partition count is unchanged.
- **Sizing:** measure what one partition handles for producing (p) and consuming (c). For a target throughput t, use at least max(t/p, t/c) partitions, plus headroom for growth.
- **Cost of too many:** each partition adds open files on the brokers, memory in clients, and more work when leaders change after a failure.
- **Reducing:** not supported in Kafka 4.3. Create a new topic with fewer partitions and move producers and consumers to it.
- **Internal topics:** never add partitions to topics such as `__consumer_offsets`.

## Interview Qs

### How do you guarantee ordering in Kafka?

Only per partition. Key every event by the entity whose order matters, such as orderId, keep the idempotent producer on, and process each partition's records in sequence. If one global order is truly required, the topic must have one partition, so only one consumer per group can read it.

### How do you choose the number of partitions?

Measure what one partition handles for producing (p) and consuming (c). For target throughput t, take at least max(t/p, t/c), then add headroom, because adding partitions later moves keys. Do not go far beyond that: every partition costs open files, client memory and failover time.

### Can you reduce a topic's partition count?

No, Kafka does not support it. The usual way is to create a new topic with the smaller count, point producers at it, let consumers finish the old topic, then switch them over.
