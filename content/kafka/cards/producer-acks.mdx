## What it is

`acks` (short for acknowledgements) is a producer setting that says when the leader broker may tell the producer "your write worked". Each partition usually has copies, called replicas, on several brokers: one leader takes the writes and the followers copy from it. The in-sync replicas (ISR) are the copies that are fully caught up. `acks` picks how many of those copies must hold the record before the reply: none (`0`), the leader (`1`) or the whole ISR (`all`).

## Why it exists

A record is safe only when more than one broker holds it, but waiting for copies costs time on every send. Payment events must never vanish; a click-stream counter can lose a few records if that makes it faster. Without `acks`, Kafka would force one choice on both. With it, each producer picks its own point between speed and safety. You will see how copies are made in [replication](card:replication).

## How it works

1. The producer sends a batch to the partition's leader. With `acks=0` it treats the send as done at this point and never reads a reply.
2. The leader appends the batch to its own log. With `acks=1` it replies now, before any follower has a copy.
3. The followers fetch the new records from the leader and write them to their own logs.
4. With `acks=all` the leader waits until every replica in the ISR has the records, then replies.
5. If an error comes back, the producer can retry. With `acks=0` there is no reply, so it never learns of a failure.

So the key is when the reply comes: before the write, after the leader's write, or after the in-sync copies.

## Example

The same payment event sent three times, once with each `acks` value, to the `payments` topic.

```java
for (String acks : List.of("0", "1", "all")) {
    var props = new Properties();
    props.put("bootstrap.servers", "localhost:9092");
    props.put("acks", acks);
    props.put("key.serializer", StringSerializer.class.getName());
    props.put("value.serializer", StringSerializer.class.getName());
    try (var producer = new KafkaProducer<String, String>(props)) {
        var meta = producer.send(new ProducerRecord<>("payments", "o-101", "PaymentCompleted")).get();
        System.out.println("acks=" + acks + " -> partition " + meta.partition() + ", offset " + meta.offset());
    }
}
```

```text output
acks=0 -> partition 2, offset -1
acks=1 -> partition 2, offset 2
acks=all -> partition 2, offset 3
```

What to notice:

- With `acks=0` the offset is `-1`: the producer never heard back, so it does not know where the record went.
- The `acks=0` record was still written (it took offset 1), which is why the next one got 2. "No acknowledgement" does not mean "not written"; it means "not confirmed".
- On this one-broker test, `1` and `all` behave the same. The difference appears only when followers exist and the leader fails.

## Rules and defaults

- **Default:** `acks=all` since Kafka 3.0; it was `1` before. Kafka 4.3 keeps `all`.
- **Same value, two names:** `acks=-1` means exactly the same as `acks=all`.
- **acks=0:** retries never happen, because the producer never sees a failure.
- **Idempotence needs all:** the [idempotent producer](card:idempotent-producer) requires `acks=all`.
- **acks=all is not a copy count:** if the ISR has shrunk to the leader alone, one copy satisfies it. The topic setting [min.insync.replicas](card:isr-and-min-insync) sets the minimum ISR size for such writes.

## Not to be confused with

`acks` is a producer setting: it says how long the producer waits. `min.insync.replicas` is a topic or broker setting: it says how small the ISR may be before the leader refuses `acks=all` writes. Rule: acks = when the producer hears back; min.insync.replicas = how many copies must exist for that answer to be "yes".

## Interview Qs

### What is the difference between acks=0, acks=1 and acks=all?

With `0` the producer does not wait, so failures go unseen. With `1` the leader replies after its own write; the record is lost if the leader fails before followers copy it. With `all` the leader replies after every in-sync replica has it: the strongest guarantee, with the most latency.

### Can acks=all still lose data?

Yes, if the ISR has shrunk to just the leader. The write is then acknowledged with one copy, and losing that broker loses it. Use replication factor 3 with `min.insync.replicas=2`, so the leader refuses `acks=all` writes when fewer than two copies are in sync.

### Which acks would you pick for a payment service?

`acks=all`, which is already the default, so a ₹500 UPI payment event survives the crash of one broker. I would use `0` or `1` only for data where losing a few records is acceptable, such as metrics or click-streams.
