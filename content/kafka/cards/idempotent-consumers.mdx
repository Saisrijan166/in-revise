## Why it exists

With at-least-once delivery, a record can arrive again after a crash, a rebalance or a replay. Charging a ₹500 UPI payment twice is far worse than processing it late.

## How it works

| Technique | How | Fits |
|---|---|---|
| Processed-events table | Insert the eventId under a unique key, in the same transaction as the effect | Any effect in the same database |
| Upsert | Write the final state by id: `ON CONFLICT DO UPDATE` | State, not increments |
| Version check | Update only when the event's version is newer than the stored one | Updates that may arrive out of order |

- Dedupe on an id inside the event: a re-sent copy lands at a new [offset](card:offsets).
- If the dedupe insert and the effect commit separately, a crash between them still double-charges or skips.

## Example

```sql
CREATE TABLE processed_events (event_id text PRIMARY KEY);

BEGIN;
INSERT INTO processed_events (event_id) VALUES ('evt-7f3a')
  ON CONFLICT DO NOTHING;     -- 0 rows inserted: a repeat, so ROLLBACK
INSERT INTO ledger (payment_id, amount_inr) VALUES ('pay-77', 500);
COMMIT;
```

## Interview Qs

### How do you prevent duplicate processing in Kafka?

Accept that delivery is at-least-once and make the consumer idempotent. Store each eventId in a processed-events table in the same transaction as the business change, or make the write itself idempotent with an upsert or a version check.

### Why not use the offset as the dedupe key?

An offset is only a position in one partition. If the producer or an outbox relay sends the same event again, the copy gets a new offset, so only a business id inside the event shows it is a repeat.
