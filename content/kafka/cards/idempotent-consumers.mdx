## What it is

An operation is idempotent when doing it twice has the same effect as doing it once. An idempotent consumer is one whose processing has this property: if the same event arrives again, nothing changes the second time. The usual way is deduplication: the consumer stores the id of every event it has handled and skips an id it has seen before.

## Why it exists

Kafka's default is [at-least-once](card:delivery-semantics): after a crash or a rebalance, a consumer resumes from the last committed offset and sees some events again. A producer, or an outbox relay, can also send the same event twice. For a notification that may only mean a second SMS, but charging a ₹500 UPI payment twice is a real loss. Since Kafka cannot remove these repeats, the consumer makes them harmless.

## How it works

  E[PaymentCompleted evt-7f3a] --> I{"Insert evt-7f3a: new row?"}

  S --> C`}
/>

1. Every event carries a unique id set by the producer, such as `eventId`, or a business id such as `paymentId`.
2. The consumer opens a database transaction and inserts that id into a `processed_events` table whose id column is unique.
3. If the insert adds a row, the event is new: the consumer applies its effect, such as a ledger row, in the same transaction.
4. If the id already exists, the insert adds nothing, and the consumer skips the effect.
5. The database transaction commits, and only then the consumer commits its Kafka offset. A crash before that offset commit only causes a repeat, which step 4 absorbs.

So the id check and the effect succeed or fail together, which closes every gap.

## Example

The Ledger consumer handles `PaymentCompleted` with one PostgreSQL statement. The insert into `processed_events` is the check:

```sql
WITH first_time AS (
  INSERT INTO processed_events (event_id) VALUES ('evt-7f3a')
  ON CONFLICT DO NOTHING
  RETURNING event_id
)
INSERT INTO ledger (payment_id, amount_inr)
SELECT 'pay-77', 500 FROM first_time;
```

Run once, then again for the redelivered event:

```text output
INSERT 0 1
INSERT 0 0
```

What to notice:

- `ON CONFLICT DO NOTHING` skips the insert when `evt-7f3a` is already there, and `RETURNING` then returns no row.
- The ledger insert selects from `first_time`, so it writes a row only when the event id was new: `INSERT 0 1` the first time, `INSERT 0 0` the second.
- It is one statement, so it is one transaction: there is no moment where the id is stored but the ledger row is not.
- The key is the event id, not the Kafka offset. If the producer had re-sent the event, the copy would have a new offset but the same `evt-7f3a`.

## Rules and defaults

There are three ways to make a write idempotent:

| Technique | How | Fits |
|---|---|---|
| Processed-events table | Insert the event id under a unique key, in the same transaction as the effect | Any effect in the same database |
| Upsert | Write the final state by id: `INSERT ... ON CONFLICT DO UPDATE` | Setting state, not adding amounts |
| Version check | Update only if the event's version is newer than the stored one | Updates that may arrive out of order |

- **Effects outside the database:** an SMS or a payment gateway call cannot join the database transaction. Pass the event id as the provider's idempotency key, if it supports one.
- **Housekeeping:** the processed-events table grows; delete ids older than the longest time a repeat can arrive, such as the topic's retention.

## Not to be confused with

The [idempotent producer](card:idempotent-producer) stops one producer's retries from writing the same batch twice into Kafka; it is a Kafka setting, on by default. An idempotent consumer stops a repeated event from having a second effect in your own database; you write it yourself. Rule: producer idempotence protects the log, consumer idempotence protects your data.

## Interview Qs

### How do you prevent duplicate processing in Kafka?

Accept that delivery is at-least-once and make the consumer idempotent. Store each event id in a processed-events table with a unique key, in the same transaction as the business change, so a repeat changes nothing. Where possible, make the write itself idempotent with an upsert or a version check.

### Why not use the offset as the dedupe key?

An offset is only a position in one partition. If the producer or an outbox relay sends the same event again, the copy gets a new offset, and a replay into a new topic changes offsets too. Only an id inside the event stays the same on every copy.

### Why must the dedupe record and the effect be in one transaction?

If they commit separately, a crash between them breaks deduplication. Effect first, id second: after the crash the effect runs again. Id first, effect second: the repeat is skipped, so the effect never happens. In one transaction both happen or neither does.
