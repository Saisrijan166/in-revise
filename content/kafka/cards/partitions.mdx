## What it is

A partition is one ordered, append-only log that holds part of a topic. A topic with 3 partitions is really 3 separate logs: `payments-0`, `payments-1` and `payments-2`. Each new event goes into exactly one partition and is added at its end, where it gets the next number, called its [offset](card:offsets). Each partition is stored on brokers, with one broker as its leader.

## Why it exists

If a topic were one log on one broker, that broker's disk and network would cap how much the topic can store and how fast it can be read. Only one consumer of a group could read it at a time. Splitting the topic into partitions lets several brokers store it and several consumers read it in parallel, one partition each.

1. The producer picks one partition for each event, usually from the event's key ([partition keys](card:partition-keys), next).
2. The leader broker of that partition adds the event at the end of its log and gives it the next offset.
3. Each partition grows on its own, so `payments-0` can be at offset 3 while `payments-2` is at 1.
4. A consumer reads one partition from start to end in offset order. Several consumers of one group read different partitions at the same time.

So the partition is the unit of order, of parallel reading and of storage.

## Example

The `payments` topic received six events, in this order: order-101 paid, order-102 paid, order-101 refunded, order-105 paid, order-102 refunded, order-105 refunded. Read them all back, printing where each one sits:

```bash
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic payments \
  --from-beginning --max-messages 6 \
  --formatter-property print.partition=true --formatter-property print.offset=true \
  --formatter-property print.key=true
```

```text output
Partition:0	Offset:0	order-102	PaymentCompleted
Partition:0	Offset:1	order-102	RefundIssued
Partition:2	Offset:0	order-105	PaymentCompleted
Partition:2	Offset:1	order-105	RefundIssued
Partition:1	Offset:0	order-101	PaymentCompleted
Partition:1	Offset:1	order-101	RefundIssued
```

What to notice:

- Inside each partition the order is kept: for every order, `PaymentCompleted` comes before `RefundIssued`.
- Across partitions it is not: order-101 was written first but is read last. A second run printed partition 1 first; the order inside each partition stayed the same.
- Each partition counts its own offsets from 0, so offset 0 exists three times.

## Rules and defaults

- **Order:** guaranteed per partition only.
- **Parallelism cap:** inside one consumer group, each partition is read by one consumer, so the partition count limits how many consumers can work.
- **Size:** one partition must fit on one broker's disk.
- **On disk:** each partition is a folder named after the topic and partition number, such as `payments-0` ([log storage](card:log-storage)).
- **Copies:** with a replication factor above 1, each partition has a leader and follower copies on other brokers ([replication](card:replication), later).

## Not to be confused with

A topic is the name of a stream; a partition is one ordered log of that topic; a broker is the server that stores partitions. Replication factor is also different: 3 partitions with replication factor 3 is still 3 partitions, each with 3 copies. Rule: partitions split the data; replicas copy it.

## Interview Qs

### What is a partition, and why split a topic?

A partition is one ordered, append-only log of a topic. Splitting spreads storage and load over brokers, and lets several consumers in a group read in parallel, one partition each.

### Does Kafka guarantee order across a topic?

No, only within a partition. If several events must be processed in order, such as the events of one order, give them the same key so they go to the same partition. A topic with one partition is fully ordered but cannot be read in parallel.

### Where does a partition live on disk?

As a folder named after the topic and partition number, such as `payments-0`, holding segment files. The leader and each follower keep their own copy on their own broker.
