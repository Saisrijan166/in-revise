## Why it exists

If the Order Service saves an order and crashes before sending OrderPlaced, no one hears of it. Sending first risks an event for an order that rolled back.

## How it works

<Mermaid
  alt="The Order Service writes the order row and an outbox row in one database transaction. A relay, a poller or Debezium reading the database log, publishes OrderPlaced with key orderId to the orders topic. Consumers skip repeats by eventId."
  chart={`flowchart LR
  S[Order Service] -- "one DB transaction" --> DB[("orders + outbox")]
  DB -- "poll or read the log" --> R[Relay]
  R -- "OrderPlaced, key orderId" --> K[[orders topic]]
  K --> C[Consumers skip repeats by eventId]`}
/>

- The event is published only if the transaction commits, but maybe more than once ([idempotent consumers](card:idempotent-consumers)).
- Log tailing reads the MySQL binlog or PostgreSQL WAL ([CDC with Connect](card:kafka-connect)).

## Example

```sql
BEGIN;
INSERT INTO orders (order_id, customer_id, total_inr)
VALUES ('ord-1001', 'c-42', 500);
INSERT INTO outbox (id, aggregatetype, aggregateid, type, payload)
VALUES ('evt-9b1c', 'order', 'ord-1001', 'OrderPlaced',
        '{"orderId":"ord-1001","totalInr":500}');
COMMIT;   -- both rows or neither
```

## Interview Qs

### What is the dual-write problem?

A service updates its database and publishes an event, but the two cannot share one transaction. A crash between them leaves an order with no event, or an event for an order never saved.

### Polling publisher or log tailing?

Polling is simple and works with any SQL database, but keeping order is tricky. Log tailing, such as Debezium, reads the database log instead, but needs database-specific setup.

### Does the outbox give exactly-once delivery?

No. A relay that crashes after publishing but before recording it sends the event again. Consumers dedupe on the event id.
