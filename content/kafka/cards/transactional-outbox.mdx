## What it is

The transactional outbox is a pattern for a service that must both update its database and publish an event. Instead of sending to Kafka directly, the service inserts the event as a row into an outbox table, in the same database transaction as its business data. A separate process, the relay, reads new outbox rows and publishes them to Kafka. The database transaction alone decides whether the event exists.

## Why it exists

The Payment service saves a payment and must publish `PaymentCompleted`. If it saves first and crashes before sending, the payment exists but no service hears of it. If it sends first and the database transaction then rolls back, consumers act on a payment that does not exist. This is the dual-write problem. A [Kafka transaction](card:kafka-transactions) cannot help, because it does not include the database. One database transaction can include both rows.

## How it works

  S[Payment Service] -- "one DB transaction" --> DB[("payments + outbox")]

1. The Payment service starts a database transaction, inserts the payment row and inserts an outbox row holding the `PaymentCompleted` event, then commits. Both rows exist, or neither does.
2. The relay finds the new outbox row. A polling publisher queries the table for unsent rows; a log-tailing relay, such as Debezium, reads the database's change log (the PostgreSQL WAL or the MySQL binlog).
3. The relay publishes the event to Kafka, keyed by the order id, and marks the row as sent or moves its position in the log.
4. If the relay crashes between steps 3 and its marking, it publishes the event again, so consumers must be [idempotent](card:idempotent-consumers).

So the event is published if and only if the data committed, but possibly more than once.

## Example

The Payment service's transaction, in PostgreSQL. The outbox columns follow the defaults of Debezium's outbox event router:

```sql
BEGIN;
INSERT INTO payments (payment_id, order_id, amount_inr, status)
VALUES ('pay-77', 'ord-1001', 500, 'COMPLETED');
INSERT INTO outbox (id, aggregatetype, aggregateid, type, payload)
VALUES ('evt-9b1c', 'payment', 'ord-1001', 'PaymentCompleted',
        '{"paymentId":"pay-77","orderId":"ord-1001","amountInr":500}');
COMMIT;
```

What to notice:

- Both inserts are in one transaction. When the outbox insert failed in a test run (a duplicate `id`), PostgreSQL rolled back the payment row too: no payment without its event.
- `aggregateid` holds the order id because Debezium uses this column as the Kafka key, which keeps one order's events in one partition.
- `id` travels with the event as a header; it is the event id consumers deduplicate on.
- By default Debezium routes by `aggregatetype`, to a topic named `outbox.event.payment`; a router setting can rename it to `payments`.

## Rules and defaults

- **Polling publisher:** works with any SQL database and is easy to build, but publishing events in order is tricky.
- **Log tailing (CDC):** reads every committed change from the database log, so nothing is missed, but needs database-specific setup; Debezium runs as a [Kafka Connect](card:kafka-connect) source connector, covered later.
- **Debezium outbox router (3.7):** expects the columns `id`, `aggregatetype`, `aggregateid`, `type` and `payload`; `aggregateid` becomes the message key.
- **Delivery:** at-least-once. The outbox removes lost and phantom events, not duplicates.
- **Clean-up:** delete or archive outbox rows once they are published, or the table keeps growing.

## Interview Qs

### What is the dual-write problem?

A service updates its database and publishes an event, but the two writes cannot share one transaction. A crash between them leaves data with no event, or an event for data that was rolled back. Other services then hold a different picture of the world than the service that owns the data.

### Polling publisher or log tailing?

A polling publisher queries the outbox table for unsent rows: simple, and it works with any SQL database, but keeping events in order is tricky. Log tailing, such as Debezium, reads the database's change log instead, so it sees every committed change, but it needs database-specific setup, usually with Kafka Connect.

### Does the outbox give exactly-once delivery?

No. A relay that crashes after publishing but before recording it publishes the event again. The outbox guarantees that every committed change produces an event and that rolled-back changes produce none. Consumers still deduplicate on the event id.
