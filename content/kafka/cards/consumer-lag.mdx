## Why it exists

Producers can write faster than consumers process. Lag shows the gap early, before a delay reaches users or records expire unread.

## How it works

| Cause | Fix |
|---|---|
| Slow processing per record | Optimise it; batch the database writes |
| Slow database or API downstream | Bulk writes, caching, rate limits; pause() partitions |
| Fewer consumers than partitions | Add consumers, up to the [partition count](card:consumer-groups) |
| Every partition already has a consumer | Add partitions ([ordering and scaling](card:ordering-and-scaling)) |
| Frequent rebalances | Fix poll timeouts, use static membership ([rebalancing](card:rebalancing)) |

- Pull model: a slow consumer falls behind and catches up later; it does not slow the producers.
- pause() and resume() stop and restart fetching chosen partitions while the consumer keeps polling.
- Client metric records-lag-max uses the consumer's position, not its committed offset.

## Example

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group payment-service
# TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# payments  0          900             1000            100
# payments  1          1000            1000            0
```

## Interview Qs

### What is consumer lag and how do you monitor it?

The gap between the newest offset and the group's committed offset, per partition. Check it with kafka-consumer-groups.sh --describe or the records-lag-max metric, and alert when it keeps growing, not on one spike.

### What causes lag, and how do you fix it?

Slow processing, slow downstream calls, too few consumers, too few partitions or frequent rebalances. Fix the slow part first, then add consumers up to the partition count, then add partitions.
