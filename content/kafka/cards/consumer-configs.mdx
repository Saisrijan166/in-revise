## Why it exists

The consumer has dozens of settings, but interviews and incidents keep coming back to the same few. This table picks them and points to where each is explained.

## How it works

| Config | Controls | Default (Kafka 4.3) |
|---|---|---|
| group.id | The group to join | see [consumer groups](card:consumer-groups) |
| key/value.deserializer | Bytes to objects | required; see [poll loop](card:consumer-basics) |
| auto.offset.reset | Start point with no valid commit | latest |
| enable.auto.commit | Background commits | see [offset commits](card:offset-commits) |
| max.poll.records | Records per poll() | 500 |
| fetch.min.bytes, fetch.max.wait.ms | Long-poll size and wait | 1 byte, 500 ms |
| session.timeout.ms, max.poll.interval.ms | When a member is dead | see [rebalancing](card:rebalancing) |
| isolation.level | Hide aborted transactions | see [transactions](card:kafka-transactions) |
| group.protocol | classic or consumer | see [rebalancing](card:rebalancing) |
| client.rack | Rack, for nearby replicas | see [replication](card:replication) |

- max.poll.records limits what poll() returns, not how much is fetched.

## Example

```properties
group.id=analytics
auto.offset.reset=earliest
enable.auto.commit=false
max.poll.records=200
# Spring Boot 4.1: spring.kafka.consumer.auto-offset-reset=earliest
```

## Interview Qs

### What does auto.offset.reset do?

It decides where a group starts when it has no valid committed offset. latest (default) reads only new records, earliest reads from the oldest retained one, none throws. Since Kafka 4.0, by_duration:P1D starts one day back.

### A slow handler keeps getting the consumer kicked out of the group. What helps?

Lower max.poll.records so each batch finishes sooner, or raise max.poll.interval.ms. Speeding up the handler is better, since a longer interval also delays rebalances.
