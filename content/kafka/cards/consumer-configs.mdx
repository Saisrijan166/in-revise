## What it is

This concept collects the consumer settings you meet most in interviews and in incidents. Each one is a key and a value in the consumer's `Properties`, or a `spring.kafka.consumer.*` property in Spring Boot. Most of them were explained in the earlier consumer concepts; the new ones here decide where a new group starts reading and how much one `poll()` brings back.

## Why it exists

The consumer has dozens of settings, but most surprises come from a few. A new group that missed a week of history, a slow handler thrown out of its group, and auto commit losing records each come down to one setting. Knowing these few and their defaults lets you predict what a consumer will do before it runs.

## How it works

| Setting | Controls | Default (Kafka 4.3) |
|---|---|---|
| `group.id` | The group to join | none; see [consumer groups](card:consumer-groups) |
| `key.deserializer`, `value.deserializer` | Bytes back to objects | none; see [the poll loop](card:consumer-basics) |
| `auto.offset.reset` | Start point with no valid commit | `latest` |
| `enable.auto.commit` | Commits on a timer | `true`; see [committing offsets](card:offset-commits) |
| `max.poll.records` | Records returned by one `poll()` | 500 |
| `fetch.min.bytes`, `fetch.max.wait.ms` | How long a fetch waits for data | 1 byte, 500 ms |
| `max.poll.interval.ms`, `session.timeout.ms` | When a member counts as gone | 5 min, 45 s; see [rebalancing](card:rebalancing) |
| `isolation.level` | Whether records of aborted transactions are shown | `read_uncommitted` |

Follow a brand-new Analytics consumer as it starts:

1. It joins the group named by `group.id`.
2. The group has no committed offset yet, so `auto.offset.reset` decides the start: `latest` means only new records.
3. Each fetch waits until at least `fetch.min.bytes` is ready or `fetch.max.wait.ms` passes.
4. Each `poll()` hands the code at most `max.poll.records` records.
5. Unless `enable.auto.commit` is off, the client commits every 5 s; the next restart uses that commit, and `auto.offset.reset` is not used again.

## Example

The Analytics service wants the full history the first time it starts, and commits by hand:

```properties
group.id=analytics
auto.offset.reset=earliest
enable.auto.commit=false
max.poll.records=200
# Spring Boot 4.1: spring.kafka.consumer.auto-offset-reset=earliest
```

What to notice:

- `earliest` matters only on the very first start, or if the saved offset's records have been deleted. Later restarts resume at the committed offset.
- With `enable.auto.commit=false`, the code must commit, or every restart reads the history again.
- `max.poll.records=200` keeps each batch small, so slow processing still finishes well inside `max.poll.interval.ms`.

## Rules and defaults

- **auto.offset.reset values:** `latest` (default), `earliest`, `none`, which throws an exception, and `by_duration:<ISO 8601 duration>` since Kafka 4.0, for example `by_duration:P1D` for one day back.
- **max.poll.records:** limits what one `poll()` returns, not how much the client fetches from the broker.
- **isolation.level:** `read_committed` hides records from transactions that were aborted or are still open; you will see why in [Kafka transactions](card:kafka-transactions).
- **client.rack:** tells Kafka where the consumer runs, so it can read from a nearby copy of the data; [replication](card:replication) explains this later.

## Interview Qs

### What does auto.offset.reset do?

It decides where a group starts in a partition when it has no valid committed offset: a new group, or an offset whose records were deleted. latest, the default, reads only new records; earliest starts from the oldest record still kept; none throws an exception. Since Kafka 4.0, by_duration starts a set time back.

### A slow handler keeps getting the consumer removed from its group. What helps?

The batch takes longer than max.poll.interval.ms. Lower max.poll.records so each batch finishes sooner, or raise max.poll.interval.ms. Making the handler faster is the real fix, because a longer interval also means a stuck consumer is noticed later.
