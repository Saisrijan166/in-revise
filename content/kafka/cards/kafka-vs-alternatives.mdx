## Why it exists

Kafka, a queue, a REST call, a database and Redis can all pass data between services, but each solves a different problem. Name the need, then pick.

## How it works

<Compare id="kafka-vs-message-queue" />

- Kafka 4.2+ [share groups](card:share-groups) add queue-style reading; RabbitMQ streams add a replayable log. The line is blurring.

## Example

The online shop picks one tool per need:

| Need | Pick |
|---|---|
| Checkout needs the price now | REST call |
| Tell payments, stock and email that an order was placed | Kafka topic |
| Give each image-resize job to one worker, ack each one | Queue, or a Kafka share group |
| Show an order's status, search orders | Database |
| Cache the product page, count views | Redis |

## Interview Qs

### Kafka vs RabbitMQ?

RabbitMQ routes messages through exchanges to queues and deletes each one once acked: good for task work. Kafka keeps an ordered log per partition that many consumer groups read and replay: good for event streams.

### Can Kafka replace the database?

No. Kafka keeps an append-only history that consumers read by offset; a database answers queries and updates rows in place. Keep state in the database and publish its changes to Kafka, for example with the [outbox](card:transactional-outbox).

### When is REST better than Kafka?

When the caller needs the answer to continue, such as a price check or a login. Kafka suits telling others that something happened. See [Kafka vs REST](compare:kafka-vs-rest).
