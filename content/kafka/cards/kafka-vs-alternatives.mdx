## What it is

Kafka is one of five common ways to move or hold data between services, and interviewers often ask "why Kafka and not X?". The other four are a REST call (an HTTP request where the caller waits for the response), a message queue such as RabbitMQ (a broker that hands each message to one consumer), a database (the current state, ready to query) and Redis (an in-memory store used as a fast cache).

## Why it exists

All five can carry a payment from one service to another, so it is easy to pick by habit. Use Kafka where a REST call fits and checkout waits for nothing; use REST where Kafka fits and one slow reader blocks payments. Knowing what each tool is built for lets you choose one per need and explain the choice.

## How it works

<Compare id="kafka-vs-message-queue" />

Walk through the needs in this order:

1. Does the caller need an answer before it can continue? Use a REST call.
2. Must a fact reach several services, or be kept so it can be read again? Write an event to a Kafka topic.
3. Is it a job that exactly one worker should do, confirmed job by job? Use a queue, or a Kafka [share group](card:share-groups).
4. Do you need the current value, to query, search or update it? Use a database.
5. Do you need very fast reads of hot data, or counters? Use Redis.

So the key is to name the need first. A real system often uses all five side by side.

## Example

The payment system picks one tool per need:

| Need | Pick |
|---|---|
| Checkout needs "card approved?" before it continues | REST call |
| Tell Notification and Analytics that a payment completed | Kafka topic `payments` |
| Send each receipt PDF job to one free worker | Queue, or a Kafka share group |
| Show a payment's status, search payments by date | Database |
| Count today's payments for a live dashboard | Redis |

What to notice:

- Only one row uses Kafka, and it is the row where one fact goes to many readers.
- The status page reads the database, not Kafka: a topic is read in order from an offset, not queried by any column.
- The same payment shows up in several tools: approved over REST, stored in the database, announced on Kafka.

## Common mistakes

- **"Kafka cannot do queue-style work."** Since Kafka 4.2, share groups are production-ready: several consumers share one partition's records, and each record is acknowledged on its own.
- **"A queue can never replay."** RabbitMQ streams keep messages after they are read, like a log. The line between the two kinds of tool is now blurring.

## Interview Qs

### Kafka vs RabbitMQ?

RabbitMQ routes messages through exchanges to queues, pushes them to consumers and deletes each one once it is acknowledged: good for task work. Kafka keeps an ordered log per partition that many consumer groups pull from and can replay: good for event streams that several services read.

### Can Kafka replace the database?

No. Kafka keeps an append-only history that consumers read by position; a database answers queries and updates rows in place. Keep state in the database and publish its changes to Kafka, for example with the [transactional outbox](card:transactional-outbox), which you will see later.

### When is REST better than Kafka?

When the caller needs the answer to continue, such as checking a card or logging in. Kafka gives the producer no reply from its readers, so it suits telling others that something already happened.
