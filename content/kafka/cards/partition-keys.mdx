## Why it exists

Events of one order must be read in order. Order holds only inside a [partition](card:partitions), so related events must reach the same one.

## How it works

| The record has | Partition chosen (Kafka 4.3 producer) | Order |
| --- | --- | --- |
| A partition number | That partition | Per partition |
| A key | murmur2(key bytes) mod partition count | Kept per key |
| Neither | A sticky partition, changed after batch.size bytes | None between records |

- `partitioner.class` picks RoundRobinPartitioner or your own Partitioner; `partitioner.ignore.keys` (default false) can ignore keys.
- More partitions remap keys and old data stays put: [ordering vs scaling](card:ordering-and-scaling).
- Hot key fixes: a key with more values, or sub-keys (merchant-42-0 to -3) with order only per sub-key.

## Example

```java
// Every event of order-101 uses the same key, so the same partition
var record = new ProducerRecord<>("orders", "order-101", orderPlacedJson);
producer.send(record, (meta, ex) -> {
    if (ex == null) log.info("partition {} offset {}", meta.partition(), meta.offset());
});
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `partitioner.class` | not set: built-in hash or sticky logic | Kafka 4.3 producer |

## Interview Qs

### Why send a key with a record?

So all events of one orderId go to one partition: they stay in order and one consumer in the group sees them all. Compaction also works per key.

### What causes a hot partition, and how do you fix it?

One key carries most traffic, such as a big merchant. Use a key with more values, or split the hot key into sub-keys, with order only per sub-key. More partitions do not help: one key maps to one partition.
