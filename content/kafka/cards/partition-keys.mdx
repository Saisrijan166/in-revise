## What it is

A partition key is a value sent with each event, such as the order id `order-101`, that decides which [partition](card:partitions) the event goes to. The producer turns the key into a number with a hash function, a formula that always gives the same number for the same input. Because of that, events with the same key always land in the same partition, while the count stays the same.

## Why it exists

Order is kept only inside one partition. A payment for order-101 and its refund must be handled in that order; if they landed in different partitions, a consumer could see the refund first. Sending both with the key `order-101` puts them in one partition, read by one consumer, in the order they were written. Different orders still spread over all partitions.

## How it works

<Mermaid
  alt="The producer looks at each record. If it names a partition, that partition is used. If it has a key, murmur2 of the key bytes modulo the partition count picks the partition. If it has neither, the sticky partitioner fills one partition until about batch.size bytes, then moves to another."
  chart={`flowchart TD
  R[New record] --> Q1{Partition number given?}
  Q1 -- yes --> A[Use that partition]
  Q1 -- no --> Q2{Key given?}
  Q2 -- yes --> H["murmur2(key) mod partition count"]
  Q2 -- no --> S[Sticky: fill one partition, then switch]`}
/>

1. The producer checks whether the record names a partition. If it does, that partition is used.
2. If not and the record has a key, the producer hashes the key bytes with murmur2 and takes the result modulo the partition count. `order-101` with 3 partitions always gives partition 1.
3. If there is no key either, the producer keeps adding records to one partition until about `batch.size` bytes, the size of one batch of records ([batching](card:batching-and-compression), later), have gone there, then switches to another. Batches stay large, and over time the load evens out.

So the key is the only thing that ties related events together; without one, there is no order between records.

## Example

The Payment service sends three events, keyed by order id. The producer setup lines are explained in [producers](card:producer-basics), later:

```java
var props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", StringSerializer.class.getName());
props.put("value.serializer", StringSerializer.class.getName());

String[][] events = { {"order-101", "PaymentCompleted"}, {"order-102", "PaymentCompleted"}, {"order-101", "RefundIssued"} };
try (var producer = new KafkaProducer<String, String>(props)) {
    for (String[] e : events) {
        var record = new ProducerRecord<>("payments", e[0], e[1]);   // topic, key, value
        RecordMetadata meta = producer.send(record).get();             // wait, only to print
        System.out.printf("%s %s -> partition %d, offset %d%n", e[0], e[1], meta.partition(), meta.offset());
    }
}
```

```text output
order-101 PaymentCompleted -> partition 1, offset 0
order-102 PaymentCompleted -> partition 0, offset 0
order-101 RefundIssued -> partition 1, offset 1
```

What to notice:

- Both `order-101` events went to partition 1, at offsets 0 and 1, so any consumer reads the payment before the refund.
- `order-102` went elsewhere: different keys spread over partitions.
- `new ProducerRecord<>("payments", e[1])`, with no key, would let the producer pick partitions in batches, and the two `order-101` events could end up in different partitions.
- `.get()` waits for each send only so the example can print the result; real producers do not block like this.

## Rules and defaults

- **Partition named in the record:** it always wins over the key.
- **partitioner.class (Kafka 4.3):** not set by default, so the built-in key hash and sticky logic is used. Set it to `RoundRobinPartitioner` or your own `Partitioner` class to change that.
- **partitioner.ignore.keys (Kafka 4.3):** `false` by default; `true` makes keyed records use the sticky logic too.
- **Partition count changes:** adding partitions changes `hash mod count`, so keys move; existing events are not moved ([ordering vs scaling](card:ordering-and-scaling)).

## Common mistakes

- **"More partitions will fix a hot partition."** One key always maps to one partition. Use a key with more distinct values, or split the hot key into sub-keys such as `merchant-42-0` to `merchant-42-3`, keeping order only per sub-key.
- **Keying by a value with few options**, such as the payment method. With three values, at most three partitions get data, whatever the partition count.

## Interview Qs

### Why send a key with a record?

So all events of one entity, such as one orderId, go to one partition. They then stay in order, and one consumer in the group sees all of them. Log compaction also works per key.

### What happens to records without a key?

The built-in partitioner sends a run of records to one partition until about `batch.size` bytes, then moves to another partition. This keeps batches large. There is no ordering between such records, and true round-robin needs `RoundRobinPartitioner`.

### What causes a hot partition, and how do you fix it?

One key carries most of the traffic, such as a big merchant. Choose a key with more values, or split the hot key into sub-keys and accept order only per sub-key. More partitions do not help, because one key still maps to one partition.
