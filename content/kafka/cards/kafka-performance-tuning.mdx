## What it is

Performance tuning is two things for Kafka. First, knowing why Kafka is already fast, a very common interview question. Second, knowing which settings to change when it is not fast enough. The page cache is memory the operating system uses to keep recently read or written file data. Zero-copy is the OS sending file bytes to the network without copying them through the application.

## Why it exists

Kafka handles very high event rates on ordinary disks, which surprises people who think "disk is slow". Interviewers ask why, and then how you would make a slow pipeline faster. Without a clear list of levers, people turn random knobs, or add consumers that sit idle. Each lever below lives in its own concept; this one shows them together.

## How it works

| Where | Lever | Owner |
|---|---|---|
| Producer | Bigger batches, some `linger.ms`, compression | [Batching](card:batching-and-compression) |
| Producer | `acks`: speed against safety | [acks](card:producer-acks) |
| Producer | Async `send()` with a callback, not `get()` per record | [Producers](card:producer-basics) |
| Topic | Enough partitions, no hot keys | [Count](card:ordering-and-scaling), [hot keys](card:partition-keys) |
| Broker | More brokers, several fast drives | [Brokers](card:kafka-architecture) |
| Consumer | Fetch and poll sizes | [Consumer configs](card:consumer-configs) |
| Consumer | More instances, batched downstream writes | [Lag](card:consumer-lag) |

1. A producer sends a compressed batch, and the broker appends it to the end of a [log segment](card:log-storage): a sequential write, with no seeking.
2. The OS keeps that new data in the page cache, so it is in memory without Kafka managing a cache.
3. A consumer that keeps up asks for those records soon after; the broker finds them in the page cache, not on disk.
4. The broker uses zero-copy (`sendfile`) to send the bytes from the page cache to the socket, still compressed.
5. To make it faster, find the bottleneck from lag and metrics, change one lever from the table, and measure again.

## Example

Before and after each change, measure. Kafka ships a load-test tool; here it sends 50,000 one-KB records to `payments` at 5,000 per second:

```bash
kafka-producer-perf-test.sh --bootstrap-server localhost:9092 --topic payments \
  --num-records 50000 --record-size 1000 --throughput 5000 \
  --command-property acks=all compression.type=lz4
```

```text output
24977 records sent, 4992.4 records/sec (4.76 MB/sec), 765.7 ms avg latency, 1333.0 ms max latency.
50000 records sent, 4957.366647 records/sec (4.73 MB/sec), 395.47 ms avg latency, 1333.00 ms max latency, 123 ms 50th, 1195 ms 95th, 1258 ms 99th, 1307 ms 99.9th.
```

What to notice:

- The early lines are progress reports; the last line is the summary: throughput, average latency and latency percentiles.
- The run reached the target of about 5,000 records per second. The 99th percentile, 1258 ms, is what slow requests feel like; watch it, not only the average.
- These numbers come from one small test container; on your cluster they will differ. Change one setting, such as `linger.ms` or the codec, and run again.

## Rules and defaults

- **Flushing:** by default Kafka does not force an fsync on each write; the OS flushes, and replication protects against a lost broker.
- **Zero-copy and TLS:** zero-copy is not used on TLS connections, because the bytes must be encrypted in the application first.
- **Memory:** Kafka relies on the page cache, which can use all free memory, instead of caching data in the JVM heap, where objects take extra space and garbage collection slows down. Leave the OS plenty of free memory.

## Common mistakes

- **"Add consumers to go faster."** Consumers beyond the partition count sit idle. Check lag per partition and the downstream calls first.

## Interview Qs

### Why is Kafka so fast?

Sequential appends to disk, the OS page cache instead of a cache in the JVM, zero-copy `sendfile` from cache to socket, and batches that stay compressed from producer to consumer.

### What is zero-copy, and when does Kafka not use it?

The broker asks the OS to send file bytes from the page cache straight to the network socket, skipping copies into the application. Kafka cannot use it when TLS is on, because encryption runs in the application.

### Does Kafka need fsync on every write to be durable?

No. By default Kafka leaves flushing to the OS. Durability comes from replication: a failed broker recovers its data from the other replicas.
