## Why it exists

Interviewers ask why Kafka is fast and how to make it faster. Both answers are short lists of levers, each explained in its own concept.

## How it works

| Where | Lever | Owner |
|---|---|---|
| Producer | Bigger batches, some linger.ms, compression | [Batching](card:batching-and-compression) |
| Producer | acks: speed against safety | [acks](card:producer-acks) |
| Producer | Async send() with a callback, not get() per record | [Producers](card:producer-basics) |
| Topic | Enough partitions, no hot keys | [Count](card:ordering-and-scaling), [hot keys](card:partition-keys) |
| Broker | More brokers, several fast drives | [Brokers](card:kafka-architecture) |
| Consumer | Fetch and poll sizes | [Consumer configs](card:consumer-configs) |
| Consumer | More instances, batched downstream writes | [Lag](card:consumer-lag) |

- Append-only [segments](card:log-storage) keep disk access sequential.
- Caught-up consumers read from the page cache, so the disks see almost no reads.

## Interview Qs

### Why is Kafka so fast?

Sequential appends to disk, the OS page cache instead of a JVM cache, zero-copy sendfile from cache to socket, and batches that stay compressed from producer to consumer.

### What is zero-copy, and when does Kafka not use it?

The broker asks the OS to send file bytes from the page cache straight to the network socket, skipping copies into the application. Kafka cannot use it when TLS is on, because encryption runs in user space.

### Does Kafka need fsync on every write to be durable?

No. By default Kafka leaves flushing to the OS. Durability comes from replication: a failed broker recovers its data from the other replicas.
