## Why it exists

Some records fail. A failed payment record must not be lost, and one bad record must not hold up every record behind it in the partition.

## How it works

<Compare id="blocking-vs-non-blocking-retries" />

- Spring for Apache Kafka names: DefaultErrorHandler retries in place; DeadLetterPublishingRecoverer writes the DLT ([setup](card:spring-kafka)).
- @RetryableTopic creates the retry topics and the DLT for one listener.
- ErrorHandlingDeserializer turns a bad payload into an error the handler can route, instead of a crash loop.

## Example

```text
topic:   payments-dlt
value:   {"paymentId":"pay-77","amount":"five hundred"}   original bytes
headers: kafka_dlt-exception-cause-fqcn = java.lang.NumberFormatException
         kafka_dlt-exception-message    = ...; For input string: "five hundred"
         kafka_dlt-original-topic       = payments
         kafka_dlt-original-partition   = 2
         kafka_dlt-original-offset      = 18734
```

## Interview Qs

### How would you handle failed messages in Kafka?

Classify the error. Retry transient ones with exponential backoff and a maximum attempt count. Send permanent ones, and records that run out of attempts, to a dead letter topic with the error and origin in headers. Alert on it.

### What is a poison message?

A record that fails on every attempt, such as malformed JSON. If the consumer keeps retrying it in place, the partition's offset never moves forward and every later record waits. Cap the retries, then send it to the DLT.

### What do you do with records in the DLT?

Someone owns the DLT and is alerted when it grows. They read the headers to find the cause, fix the code or data, then re-drive the records to the main topic.
