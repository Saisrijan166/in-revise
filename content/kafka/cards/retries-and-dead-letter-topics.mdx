## What it is

When a consumer cannot process a record, it has two tools. A retry tries the same record again, usually after a wait that grows each time, which is called exponential backoff. A dead letter topic (DLT) is a separate topic where records that still fail are parked, so the consumer can move on. A record that fails on every attempt, such as malformed JSON, is called a poison message.

## Why it exists

A consumer must not lose a failed payment event, and it must not get stuck on it either. Its [committed offset](card:offset-commits) can only move past a record once that record is handled, so a record that is retried forever blocks every record behind it in the partition. Skipping it silently loses money. Retrying for a limited time fixes short outages; the DLT keeps the rest safe for a person to fix, while the partition keeps flowing.

## How it works

<Compare id="blocking-vs-non-blocking-retries" />

1. The consumer's processing code throws an exception while handling a record.
2. An error handler, the code that decides what happens to failed records, checks the exception type. A permanent error, such as a deserialisation failure, skips the retries.
3. A transient error is retried after a wait: in place, holding the partition (blocking), or by moving the record to a delayed retry topic (non-blocking).
4. When the attempts run out, the record is published to the DLT, with headers saying what failed and where it came from.
5. The consumer commits past the record and continues. An alert on the DLT tells the owning team to look.

So the key is to retry only what can pass, cap the attempts, and never let one record hold a partition.

## Example

The Notification service uses Spring for Apache Kafka (covered in [Spring for Apache Kafka](card:spring-kafka)), which calls a listener method for each record. This bean tells it what to do when the method throws:

```java
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);  // writes to payments-dlt
    var backOff = new ExponentialBackOffWithMaxRetries(3);        // 3 retries after the first try
    backOff.setInitialInterval(1_000L);                            // wait 1 s, then 2 s, then 4 s
    backOff.setMultiplier(2.0);
    var handler = new DefaultErrorHandler(recoverer, backOff);
    handler.addNotRetryableExceptions(PaymentValidationException.class);  // no retries: DLT at once
    return handler;
}
```

What to notice:

- These are blocking retries: the consumer thread waits 1, 2 and 4 seconds in place, so the order of the partition is kept.
- `DeadLetterPublishingRecoverer` sends the failed record to `payments-dlt`, to the same partition number, with headers such as `kafka_dlt-exception-message` and `kafka_dlt-original-offset`.
- `PaymentValidationException` and deserialisation errors skip the retries, because a bad record will never pass.
- Without this bean, the default handler tries 10 times with no wait and then only logs the record, so it is lost.

## Rules and defaults

- **Default handler (Spring for Apache Kafka 4.1):** `DefaultErrorHandler` with `FixedBackOff(0, 9)`: ten attempts, no delay, then the record is logged and skipped.
- **Not retried by default:** `DeserializationException`, `MessageConversionException`, `ConversionException`, `MethodArgumentResolutionException`, `NoSuchMethodException` and `ClassCastException`.
- **Spring Boot wiring:** declare the handler as a `@Bean` and Boot adds it to the auto-configured listener container factory.
- **DLT name and partitions:** by default `<topic>-dlt`, same partition number, so the DLT needs at least as many partitions as the original topic.
- **Long waits:** blocking retries suspend the consumer thread; keep the total wait well under `max.poll.interval.ms` (5 min by default), or the consumer is removed from its group.
- **Bad bytes:** wrap the deserialiser in `ErrorHandlingDeserializer`, so a record that cannot be parsed reaches the error handler instead of failing every poll.

## Common mistakes

- **"Infinite retries are the safe choice."** They turn one bad record into a stopped partition and growing lag. Always cap the attempts.
- **Creating a DLT and never reading it.** Records there are payments nobody handled. Alert on new DLT records, and have a way to re-send fixed ones to the main topic.

## Interview Qs

### How would you handle failed messages in Kafka?

Classify the error first. Retry transient errors with exponential backoff and a maximum number of attempts. Send permanent errors, and records that run out of attempts, to a dead letter topic with the error and the original topic, partition and offset in headers. Alert on the DLT and re-send records once the cause is fixed.

### What is a poison message?

A record that fails on every attempt, such as malformed JSON or data from an unknown schema version. If the consumer keeps retrying it in place, the partition's offset never moves forward and every later record waits. Detect it as a permanent error, or cap the retries, then send it to the DLT.

### What do you do with records in the DLT?

The DLT has an owning team that is alerted when records arrive. They read the headers to find the cause, fix the code or the data, then re-drive the records, which means publishing them again to the main topic. Consumers should be idempotent, because a re-driven record may already have been partly processed.
