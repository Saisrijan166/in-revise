## What it is

Replay means reading events again that a consumer group has already read. It works because Kafka keeps events after they are read ([log storage](card:log-storage)), and because a group's progress is only a committed [offset](card:offsets) per partition. Move that offset back, and the group's next reads start from the older events. Nothing changes in the topic itself.

## Why it exists

A bug in the Analytics service counted yesterday's payments wrongly, or a new Fraud service needs past payments. Without replay you would ask the Payment service to send every event again, which it may not even be able to do. With Kafka the events are still there, so the reader rewinds and reads them again, and the producer does nothing.

## How it works

| Way | How | Use it for |
| --- | --- | --- |
| `seek()`, `seekToBeginning()` | Consumer code sets its own position | A start-up rule in the app |
| `offsetsForTimes()`, then `seek()` | Finds the first offset at or after a time | Start from 00:00 yesterday |
| `--reset-offsets` | The CLI moves a stopped group's committed offsets | Reprocess after a bug fix |
| A new `group.id` | No committed offsets, so `auto.offset.reset` picks the start | Backfill a new service |

For a reprocess after a bug fix, the CLI way runs like this:

1. Deploy the fixed Analytics code, but keep it stopped.
2. Stop every Analytics instance, so the group has no running members.
3. Preview the reset with `--dry-run` to see the new offsets.
4. Apply it with `--execute`. The group's committed offsets now point to older events.
5. Start the instances. They fetch from the new offsets and process those events again.

## Example

Preview moving the Analytics group back to the first payment event of 22-10-2026:

```bash
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group analytics \
  --topic payments --reset-offsets --to-datetime 2026-10-22T00:00:00.000 --dry-run
```

```text output
GROUP           TOPIC           PARTITION  NEW-OFFSET
analytics       payments        0          0
analytics       payments        2          0
analytics       payments        1          0
```

What to notice:

- `NEW-OFFSET` is where each partition would restart. All events in this test topic are from that day, so every partition goes back to offset 0.
- `--dry-run` changes nothing. Replace it with `--execute` to apply the move.
- Only the `analytics` group moves. The Notification group's offsets stay where they are.
- Other moves: `--to-earliest` (oldest kept event) and `--shift-by -1` (one event back in each partition).

## Rules and defaults

- **Inactive group:** the reset works only when no member of the group is running.
- **Preview by default (Kafka 4.3):** without `--execute` the tool only shows the new offsets. It warns that Kafka 5.0 will require `--dry-run` or `--execute`, so always write one.
- **Retention limit:** you can replay only events that are still kept; a time before the oldest kept event starts at the oldest one.
- **New groups:** `auto.offset.reset` decides where a group without committed offsets starts ([consumer configs](card:consumer-configs), later).

## Common mistakes

- **Replaying into a consumer with side effects.** A replay sends every email or refund again. Make the consumer [idempotent](card:idempotent-consumers) first, so it skips events it has already handled.
- **Expecting a replay of last month with 7-day retention.** Deleted segments are gone. For a full current state, keep a compacted topic; for long history, raise retention or use tiered storage.

## Interview Qs

### How would you reprocess yesterday's payments after fixing a bug?

Deploy the fix, stop every instance of the group, reset its offsets with `--to-datetime`, then start it again. Only that group rereads; other groups are untouched. The consumer must be idempotent, so a ₹500 payment is not counted, charged or mailed twice.

### Can a new service read all past events?

Only what retention still keeps. A new `group.id` with `auto.offset.reset=earliest` starts at the oldest kept event. If the service needs the current state of every key rather than the full history, keep a compacted topic.

### Does replaying affect other consumers?

No. Each consumer group has its own committed offsets, and the events in the topic do not change. Rewinding the Analytics group leaves the Notification group exactly where it was.
