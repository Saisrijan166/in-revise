## What it is

Apache Kafka is a system that stores events and lets services share them. An event is a small record that something happened, such as "payment for order-101 completed, ₹500". A producer is a program that writes events; a consumer is a program that reads them. Kafka keeps events in topics, named streams such as `payments`, on servers called brokers. Inside a topic, events sit in append-only logs: lists where new events are only added at the end.

## Why it exists

Without Kafka, the Payment service would call the Notification service, the Analytics service and every future reader over HTTP, one by one. A slow or crashed reader then slows or breaks payments, and each new reader means changing the Payment service. With Kafka, the Payment service writes one event and moves on. Each reader takes it when it is ready, and a new reader just starts reading.

## How it works

1. The Payment service, a producer, sends a `PaymentCompleted` event to the `payments` topic.
2. A Kafka broker adds the event to the end of the topic's log and saves it to disk.
3. The Notification service and the Analytics service, two consumers, each ask Kafka for new events and get this one. Each reads at its own speed and remembers its own place.
4. The event stays in the topic after they read it, until the topic's retention time ends (see [log storage](card:log-storage)). A service that starts tomorrow can still read it.

So Kafka sits between services as a shared, durable history of events. A topic is also split into parts called [partitions](card:partitions), so it can spread over many brokers; you will see that in the storage topic.

## Example

This is what one `PaymentCompleted` event looks like inside Kafka:

```text
key:       order-101
value:     {"type":"PaymentCompleted","orderId":"order-101","amount":500,"currency":"INR"}
timestamp: 2026-10-20T10:15:00Z
headers:   source=payment-service
```

What to notice:

- The value carries the facts: what happened and the data a reader needs. Kafka stores it as bytes and does not look inside.
- The key, here the order id, groups related events. All events with the same key go to the same partition and keep their order ([partition keys](card:partition-keys)).
- The event is written in the past tense. It records a fact that already happened; it is not a command to another service.

## Rules and defaults

- **Readers pull:** consumers ask Kafka for new events; Kafka does not push them ([consumers](card:consumer-basics)).
- **No reply:** a producer gets a confirmation from Kafka that the event was stored, never an answer from the readers.
- **Five Java APIs:** Producer, Consumer, Admin, Streams and Connect (Kafka 4.3).

## Not to be confused with

A traditional message queue, such as RabbitMQ, hands each message to one consumer and deletes it once that consumer confirms it. Kafka keeps every event for the retention time, and every reading service gets all of them. Rule: a queue hands out work once; Kafka keeps a history that many can read. The full comparison is in [Kafka vs alternatives](card:kafka-vs-alternatives).

## Interview Qs

### What is Kafka?

A distributed event streaming platform. Producers publish events to topics; Kafka stores them durably, split into partitions and copied across brokers; consumers read them at their own pace, now or later. It is used to move events between services and to process streams of events as they arrive.

### Why put Kafka between services instead of calling each one?

The producer writes once and does not wait. A slow or crashed reader does not slow the producer, because events wait in the topic. New readers join without any producer change, and events can be read again after a bug fix.

### What is Kafka used for?

Messaging between services, website activity tracking, metrics, log aggregation, stream processing pipelines, event sourcing, and a commit log that keeps copies of data in sync. These are the main uses listed in the Kafka docs.
