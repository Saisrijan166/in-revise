## Why it exists

If the Order Service calls payments, stock, email and analytics one by one, a slow or failed service holds up checkout. Kafka sits in between and keeps the events.

## How it works

<Mermaid
  alt="The Order Service publishes OrderPlaced events to the orders topic. Four consumer groups read the same topic independently: payment-service, inventory-service, notification-service and analytics."
  chart={`flowchart LR
  O[Order Service] -- OrderPlaced --> T[(orders topic)]
  T --> P[payment-service]
  T --> I[inventory-service]
  T --> N[notification-service]
  T --> A[analytics]`}
/>

- Each service reads as its own [consumer group](card:consumer-groups), so all four get every event.
- A topic is split into [partitions](card:partitions) spread over brokers, so reads and writes scale out.

## Example

An event has a key, a value, a timestamp and optional headers. OrderPlaced, keyed by orderId:

```text
key:       ord-1042
value:     {"type":"OrderPlaced","orderId":"ord-1042","amount":500,"currency":"INR"}
timestamp: 2026-10-20T10:15:00Z
headers:   source=order-service
```

## Interview Qs

### What is Kafka?

A distributed event streaming platform. Apps publish and subscribe to streams of events; Kafka stores them durably in partitioned, replicated topics, and they can be processed as they arrive or later.

### Why put Kafka between services instead of calling each one?

The producer writes once and moves on. Each service reads when ready, a slow one does not slow checkout, new ones join without code changes, and events can be replayed. See [Kafka vs REST](compare:kafka-vs-rest).

### What is Kafka used for?

Messaging between services, website activity tracking, metrics, log aggregation, stream processing pipelines, event sourcing, and a commit log that keeps copies of data in sync.
