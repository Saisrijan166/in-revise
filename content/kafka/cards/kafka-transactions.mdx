## What it is

A Kafka transaction groups several writes so that they take effect together or not at all. It is made for read-process-write services: a service reads a record from one topic, processes it, and writes a result to another topic. The transaction holds both the result records and the consumer's offsets, so the two can no longer get out of step. This is how Kafka provides the exactly-once semantic from [delivery semantics](card:delivery-semantics).

## Why it exists

Suppose the Payment service reads `orders`, charges each order and writes `PaymentCompleted` to `payments`. If it crashes after writing the event but before committing its offset, the next instance reads the order again and writes a second event. Committing the offset first instead risks losing the event. A transaction makes "event written" and "offset committed" one step, so a crash leaves either both or neither.

## How it works

1. At start-up the producer calls `initTransactions()` with its `transactional.id`. A broker role called the transaction coordinator finishes or aborts any transaction left open by an earlier instance with the same id, and raises the id's epoch.
2. For each batch, the producer calls `beginTransaction()`, sends the result records, and sends the consumed offsets with `sendOffsetsToTransaction()`.
3. The coordinator records which partitions the transaction touched in the internal topic `__transaction_state`.
4. On `commitTransaction()`, the coordinator writes a commit marker into every touched partition. On `abortTransaction()`, it writes an abort marker instead; the aborted records stay in the log.
5. Downstream consumers with `isolation.level=read_committed` return only records whose transaction committed, and wait at an open transaction.

So the transaction does not delete anything; it marks records as valid or not, and read_committed readers honour the marks.

## Example

The Payment service's loop, with plain Kafka clients:

```java
producer.initTransactions();                           // once: fences an older instance
while (true) {
    var records = consumer.poll(Duration.ofMillis(500));
    if (records.isEmpty()) continue;
    producer.beginTransaction();
    try {
        for (var r : records)
            producer.send(new ProducerRecord<>("payments", r.key(), charge(r.value())));
        producer.sendOffsetsToTransaction(records.nextOffsets(), consumer.groupMetadata());
        producer.commitTransaction();                  // results and offsets together
    } catch (ProducerFencedException e) { producer.close(); throw e; }   // a newer instance took over
    catch (KafkaException e) { producer.abortTransaction(); }           // then rewind and retry
}
```

What to notice:

- The consumer never calls `commitSync()`. Its offsets travel inside the transaction through `sendOffsetsToTransaction`, so the consumer runs with `enable.auto.commit=false`.
- `records.nextOffsets()` gives, for each partition, the offset after the last record polled, which is the value to commit.
- After `abortTransaction()`, the consumer must seek back to its last committed offsets; otherwise the next `poll()` continues after the aborted batch.
- `charge(...)` must not call an external payment gateway: if the transaction aborts, that call is not undone.

## Rules and defaults

- **Consumers of the output:** `isolation.level` is `read_uncommitted` by default (Kafka 4.3), which also returns aborted records. Set `read_committed` for exactly-once.
- **read_committed reads up to the last stable offset:** the offset before the first still-open transaction, so a long transaction delays its readers.
- **Timeout:** `transaction.timeout.ms` is 60 s by default (Kafka 4.3 producer); the coordinator aborts a transaction open longer than that. The broker caps it with `transaction.max.timeout.ms` (15 min).
- **Cluster size:** the `__transaction_state` topic needs RF 3 and 2 in-sync replicas by default, so transactions need at least three brokers.
- **Kafka Streams:** `processing.guarantee=exactly_once_v2` does all of the above for you; the default is `at_least_once`.

## Not to be confused with

The [idempotent producer](card:idempotent-producer) stops one producer's retries from writing a batch twice to one partition. A transaction makes many writes, across partitions and with the consumer offsets, all-or-nothing, and survives a restart thanks to the `transactional.id`. Rule: idempotence = no retry duplicates; transaction = all or nothing.

## Interview Qs

### How do Kafka transactions give exactly-once?

The producer writes the output records and the consumed offsets in one transaction. On commit both become valid together; on abort neither does, and the input is processed again. Consumers with read_committed skip aborted records, so a crash leads to a retry, not to a visible duplicate.

### What is zombie fencing?

A zombie is an old instance that seems dead, for example frozen in a long pause, but later wakes up. Its replacement uses the same transactional.id, and initTransactions() raises the epoch for that id. When the zombie tries to write or commit, it gets ProducerFencedException, so it cannot add duplicates.

### Do Kafka transactions give exactly-once into a database?

No. They cover only Kafka topics and consumer offsets. A database write or an API call made inside the loop is not rolled back when the transaction aborts. For those, use an idempotent consumer, store the offsets in the same database transaction, or use the transactional outbox.
