## Why it exists

In read-process-write, a crash after writing the output but before committing the offset makes the next run write it again. A transaction joins both steps.

## How it works

<Mermaid
  alt="The Payment Service reads the orders topic. Inside one transaction it sends results to the payments topic and sends its consumed offsets to __consumer_offsets. It registers its partitions with, and commits through, the transaction coordinator, which keeps state in __transaction_state and writes commit markers into the payments topic."
  chart={`flowchart LR
  IN[(orders)] --> APP[Payment Service]
  APP -- send --> OUT[(payments)]
  APP -- sendOffsetsToTransaction --> OFF[(__consumer_offsets)]
  APP -- add partitions, commit --> TC[Transaction coordinator]
  TC --> TS[(__transaction_state)]
  TC -. commit markers .-> OUT`}
/>

- Aborted records stay in the log; `read_committed` consumers skip them and wait while a transaction is open.
- The consumer sets `enable.auto.commit=false`; the producer commits its offsets.
- [Kafka Streams](card:kafka-streams) does all of this with `processing.guarantee=exactly_once_v2`.

## Example

```java
producer.initTransactions();                       // once: fences older instances
while (true) {
    var records = consumer.poll(Duration.ofMillis(500));
    producer.beginTransaction();
    try {
        for (var r : records)
            producer.send(new ProducerRecord<>("payments", r.key(), charge(r.value())));
        producer.sendOffsetsToTransaction(records.nextOffsets(), consumer.groupMetadata());
        producer.commitTransaction();
    } catch (ProducerFencedException e) { producer.close(); throw e; } // newer instance won
    catch (KafkaException e) { producer.abortTransaction(); }          // then seek back
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `isolation.level` | `read_uncommitted` | Kafka 4.3 consumer |
| `transaction.timeout.ms` | 60 s, then the coordinator aborts | Kafka 4.3 producer |
| `processing.guarantee` | `at_least_once` | Kafka Streams 4.3 |

## Interview Qs

### How do Kafka transactions give exactly-once?

The producer writes output records and the consumed offsets in one transaction. On commit both become visible; on abort neither does. read_committed consumers skip aborted records, so a crash means a retry, not a visible duplicate.

### What is zombie fencing?

A paused old instance and its replacement share a transactional.id. initTransactions in the new one bumps the epoch, so the old one gets ProducerFencedException.
