## Why it exists

With a plain consumer, counting or joining events means hand-writing state, recovery and scaling. Kafka Streams provides them inside a Java app.

## How it works

<Mermaid
  alt="Topology: payments topic, source, filter completed, group by method and count (using a state store copied to a changelog topic), sink, payment-counts topic."
  chart={`flowchart LR
  P[[payments]] --> SRC[Source]
  SRC --> F[filter completed]
  F --> C[groupBy method, count]
  C <--> ST[(State store)]
  ST -.-> CL[[changelog topic]]
  C --> SNK[Sink]
  SNK --> OUT[[payment-counts]]`}
/>

- A moved task rebuilds its store by replaying the changelog topic, so a crash loses no state.
- Reading a topic as a [KStream, KTable or GlobalKTable](compare:kstream-vs-ktable) decides what a repeated key means.
- Windows (tumbling, hopping, sliding, session) group one key's records by time.

## Example

```java
StreamsBuilder builder = new StreamsBuilder();
KStream<String, Payment> payments = builder.stream("payments");   // key: orderId

payments.filter((orderId, p) -> p.completed())
        .groupBy((orderId, p) -> p.method())       // re-key by UPI, CARD, WALLET
        .count()                                   // KTable<String, Long>
        .toStream()
        .to("payment-counts", Produced.with(Serdes.String(), Serdes.Long()));

new KafkaStreams(builder.build(), props).start();  // props: application.id, serdes
```

## Interview Qs

### How is Kafka Streams different from a plain consumer?

A consumer hands you records; state, joins, windows, recovery and exactly-once are your job. Kafka Streams adds them on top of the same clients. For one-record-at-a-time work a plain consumer is enough.

### How does Kafka Streams give exactly-once?

Set processing.guarantee=exactly_once_v2. It uses [Kafka transactions](card:kafka-transactions) to commit input offsets, state store updates and output records together. By default it needs at least three brokers.
