## What it is

Kafka Streams is a Java library for stream processing: working on records continuously as they arrive, instead of in a nightly batch job. You add it to your own service as a dependency. You describe the work as a chain of steps, called a topology: read a topic, filter, group, count or join, and write the result to another topic. It uses normal [consumers](card:consumer-groups) and producers underneath.

## Why it exists

With a plain consumer, "count completed payments per method" means writing a lot yourself: a map of counts, saving it so a crash does not lose it, rebuilding it when partitions move to another instance, and avoiding double counts. Kafka Streams provides all of that. You write the business steps; it handles state, recovery, scaling and, if you ask, exactly-once.

## How it works

<Mermaid

  P[[payments]] --> SRC[Source]

1. At start-up the app joins a consumer group named by its `application.id`, and Kafka Streams creates one task per input partition.
2. Each task reads its partition's records and passes them through the topology, one record at a time.
3. Stateless steps such as `filter` decide using the record alone. Stateful steps such as `count` read and update a local state store.
4. Every change to a store is also written to a compacted changelog topic, and results go to the output topic.
5. If an instance dies, its tasks move to another instance, which replays the changelog to rebuild the store, then continues.

## Example

The Analytics service counts completed payments per payment method, live:

```java
StreamsBuilder builder = new StreamsBuilder();
KStream<String, Payment> payments = builder.stream("payments");   // key: orderId

payments.filter((orderId, p) -> p.completed())
        .groupBy((orderId, p) -> p.method())       // new key: UPI, CARD, WALLET
        .count()                                   // KTable<String, Long>
        .toStream()
        .to("payment-counts-by-method", Produced.with(Serdes.String(), Serdes.Long()));

new KafkaStreams(builder.build(), props).start();  // props: id, servers, serdes
```

What to notice:

- `builder.stream("payments")` reads the topic as a KStream, where every record is a new event.
- `groupBy` changes the key from orderId to the method, so Kafka Streams first writes the records through an internal repartition topic. That way all UPI payments meet in one task.
- `count()` returns a KTable: one running total per method, kept in a state store. Each new payment updates the total for its key.
- `props` must set `application.id`, `bootstrap.servers` and the default serdes (serializer plus deserializer); without them the app cannot start or read records.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| `processing.guarantee` | `at_least_once`; set `exactly_once_v2` for exactly-once | Kafka Streams 4.3 |
| `exactly_once_v2` | needs at least 3 brokers with the default settings | Kafka Streams 4.3 |
| `num.standby.replicas` | 0: no warm copy of a task's state elsewhere | Kafka Streams 4.3 |
| Persistent store | RocksDB, on the instance's local disk | Kafka Streams 4.3 |

- **`application.id` is required:** it is the consumer group id, the prefix of internal topic names and the state directory name. Two apps with the same id share work as one app.
- **Windows:** tumbling, hopping, sliding and session windows group one key's records by time, for example "payments per minute".

## Not to be confused with

A plain [consumer](card:consumer-basics) hands you records; anything you remember between records is your problem. Kafka Streams is built on consumers and producers and adds state stores, joins, windows, recovery and exactly-once. Apache Flink is a separate engine that runs on its own cluster. Rule: one record at a time, use a consumer; counts, joins or windows inside a Java service, use Kafka Streams.

## Interview Qs

### How is Kafka Streams different from a plain consumer?

A consumer hands you records; state, joins, windows, recovery and exactly-once are your job. Kafka Streams adds them on top of the same clients, inside your app. For one-record-at-a-time work such as sending a receipt, a plain consumer is enough.

### How does Kafka Streams scale and recover?

Each input partition becomes a task, and the group spreads tasks over the running instances, so you scale by starting instances up to the partition count. State lives in local stores copied to changelog topics; a moved task replays its changelog to rebuild the store.

### How does Kafka Streams give exactly-once?

Set `processing.guarantee=exactly_once_v2`. It uses [Kafka transactions](card:kafka-transactions) to commit the input offsets, the state store changes and the output records together, so a crash cannot leave one without the others. With default settings it needs at least three brokers.
