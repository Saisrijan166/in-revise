## Why it exists

Kafka keeps events after reading so many groups can read and replay them. Disks are finite, so old data must go by a clear rule.

## How it works

<Steps label="Life of a segment in payments-0">
  <Step title="Append">Writes go to the end of the active segment.</Step>
  <Step title="Roll">At 1 GiB or after 7 days (segment.ms) the segment is closed and a new one starts.</Step>
  <Step title="Clean">Closed segments are deleted once past retention, or recopied keeping only the latest value per key.</Step>
</Steps>

- A segment is deleted when its newest record is older than retention.ms.
- Compaction: a record with a key and a null value (a tombstone) deletes that key.
- [Tiered storage](card:tiered-storage) (production-ready since Kafka 3.9) moves closed segments to remote storage such as S3.

## Example

```properties
# payments topic: event history, kept 30 days
cleanup.policy=delete
retention.ms=2592000000

# customer-addresses topic: only the latest address per customerId
cleanup.policy=compact
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `cleanup.policy` | `delete` | Kafka 4.3 topic config |
| Broker-wide time limit | `log.retention.hours=168` (7 days) | Kafka 4.3 broker |
| Tombstones kept for | 1 day (`delete.retention.ms`) | Kafka 4.3 topic config |

## Interview Qs

### When does Kafka delete old data?

When a closed segment passes retention.ms or the partition passes retention.bytes. It drops whole segments, oldest first, whether or not anyone has read them.

### What is log compaction, and when do you use it?

cleanup.policy=compact keeps at least the latest record per key and drops older ones in the background. Use it for latest state, such as each customer's address, that readers rebuild from the topic.
