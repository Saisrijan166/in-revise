## Why it exists

Teams kept writing the same glue code to copy data into and out of Kafka. Connect is one framework for it, with offsets and scaling handled.

## How it works

<Mermaid
  alt="A source connector reads the shop database's change log and writes to a Kafka topic; a sink connector copies that topic to a search index or warehouse."
  chart={`flowchart LR
  DB[(Shop database)] -- change log --> S[Source connector]
  S --> K[[Kafka topic]]
  K --> SK[Sink connector]
  SK --> W[(Search index or warehouse)]`}
/>

- A connector splits its job into tasks; distributed workers share them and rebalance when a worker joins or fails.
- Converters turn records into bytes (JSON, Avro); single message transforms make small per-record edits.
- You create and manage connectors through a REST API on each worker.

## Example

```json
{
  "name": "shop-orders-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "orders-db",
    "database.port": "5432",
    "database.user": "debezium",
    "database.dbname": "shop",
    "topic.prefix": "shop",
    "table.include.list": "public.orders"
  }
}
```

## Defaults

| What | Default | Where |
|---|---|---|
| REST API port | 8083, HTTP | Kafka Connect 4.3 |
| Change event topic | prefix.schema.table, e.g. shop.public.orders | Debezium 3.7 PostgreSQL connector |

## Interview Qs

### What is Kafka Connect, and when would you use it?

A framework that runs connectors to copy data between Kafka and databases, search indexes or storage. Use it for plain data movement; write your own producer or consumer when business logic decides what to send.

### What is change data capture, and how does Debezium do it?

CDC turns each committed insert, update and delete into an event. Debezium reads the database's own log (MySQL binlog, PostgreSQL logical decoding) instead of polling tables. It is a common relay for the [transactional outbox](card:transactional-outbox).
