## What it is

Kafka Connect is a framework, shipped with Apache Kafka, for copying data between Kafka and other systems. A connector is a ready-made plug-in for one system, such as PostgreSQL or Elasticsearch. A source connector brings data into Kafka; a sink connector takes data out of Kafka. You give a connector a JSON configuration, and Connect worker processes run it.

## Why it exists

Without Connect, every team writes its own glue service: read rows from a database, call `send()`, remember how far it got, restart after a crash, and scale when the table grows. That code is the same everywhere and easy to get wrong. Connect does this work once: it tracks progress, restarts failed work and spreads it over several machines, so you only write configuration.

## How it works

1. You send a connector's JSON config to the REST API of any worker.
2. The connector splits the job into tasks, at most `tasks.max` of them.
3. In distributed mode, the workers share those tasks. A source task uses a producer to write to Kafka; a sink task uses a consumer to read from it.
4. A converter turns each record into bytes (JSON or Avro), and optional single message transforms make small per-record edits on the way.
5. Workers save configs, offsets and status in Kafka topics. When a worker dies, the others rebalance and continue its tasks from the saved offsets.

## Example

The Analytics team wants every change to the payments table as an event. This Debezium source connector config is sent with `POST /connectors` to a worker:

```json
{
  "name": "payments-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "plugin.name": "pgoutput",
    "database.hostname": "payments-db",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "${file:/secrets/db.properties:password}",
    "database.dbname": "payments",
    "topic.prefix": "paydb",
    "table.include.list": "public.payments"
  }
}
```

What to notice:

- Debezium reads PostgreSQL's write-ahead log, so the database must run with `wal_level=logical`. `pgoutput` is the decoding plug-in built into PostgreSQL; the default, `decoderbufs`, must be installed separately.
- Change events go to the topic `<topic.prefix>.<schema>.<table>`, here `paydb.public.payments`.
- On its first start the connector takes a snapshot of the existing rows, then streams new changes.
- `${file:...}` reads the password from a file through the `FileConfigProvider`, which the worker config enables with `config.providers=file` and `config.providers.file.class=org.apache.kafka.common.config.provider.FileConfigProvider`. Without it, the secret would sit in plain text in the connector config.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| REST API | HTTP on port 8083 | Kafka Connect 4.3 |
| `errors.tolerance` | `none`: the task fails on the first bad record | Kafka Connect 4.3 |
| Dead letter queue | off; set `errors.tolerance=all` and `errors.deadletterqueue.topic.name` on a sink | Kafka Connect 4.3 |
| `snapshot.mode` | `initial`: snapshot existing rows on first start | Debezium 3.7 PostgreSQL |

- **Standalone mode:** one process with offsets in a local file. Good for a laptop, but there is no fault tolerance.
- **Distributed mode:** for production. Create the three internal topics (configs, offsets, status) yourself, replicated and compacted, because auto-created topics may get unsuitable settings.

## Common mistakes

- **"Use Connect for everything that touches Kafka."** Connect is for plain data movement. When business logic decides what to publish, such as a `PaymentCompleted` event after a charge succeeds, write the producer in the service, or use an [outbox](card:transactional-outbox) table that Debezium relays.

## Interview Qs

### What is Kafka Connect, and when would you use it?

A framework that runs connectors to copy data between Kafka and databases, search indexes or storage. Use it for plain data movement, because it already handles offsets, restarts and scaling. Write your own producer or consumer when business logic decides what to send or how to process it.

### What is change data capture, and how does Debezium do it?

CDC turns each committed insert, update and delete into an event. Debezium reads the database's own log, the MySQL binlog or PostgreSQL logical decoding, instead of polling tables, so it misses no change and adds little load. It is a common relay for the [transactional outbox](card:transactional-outbox).

### Why not just poll the table with a SELECT every minute?

Polling misses deletes, misses a row that changed twice between two polls, needs a reliable "updated at" column, and puts query load on the database. Reading the change log sees every committed change, in commit order.
