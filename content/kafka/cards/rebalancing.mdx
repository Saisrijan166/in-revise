## What it is

A rebalance is the moment a [consumer group](card:consumer-groups) re-decides which member owns which partition. It happens when the members change, or when the subscribed topic changes. Partitions that move to a new owner pause, and the new owner starts each one at the group's [committed offset](card:offset-commits). How the group runs a rebalance is set by its group protocol: the older classic protocol, or the newer consumer protocol.

## Why it exists

Every partition must always have exactly one owner in the group. If a Notification instance crashes, its partitions would never be read again unless someone hands them to a survivor. If you start a fourth instance, it would sit idle unless partitions are moved to it. Rebalancing does both. The price is a pause on the moved partitions and repeated work for records processed after the last commit.

1. Something changes: here, a third Notification instance, N3, joins. A crash, a clean shutdown or a missed poll deadline would start the same process.
2. The group coordinator tells the members that the assignment must change.
3. Partitions that will move are taken away. The client calls your `onPartitionsRevoked()` first, so you can commit the work you have finished.
4. A new split is computed, by an assignor running in the clients (classic protocol) or by the broker (consumer protocol).
5. Each new owner gets `onPartitionsAssigned()` and starts reading at the committed offset.

In the old eager style, every member gives up all its partitions in step 3, so the whole group stops. In cooperative style, and in the consumer protocol, only the partitions that move are paused.

## Example

The Notification service saves its progress just before a partition is taken away:

```java
consumer.subscribe(List.of("payments"), new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        consumer.commitSync(processed);   // save progress before handing over
    }
    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        System.out.println("Now reading " + partitions);
    }
});
```

What to notice:

- `processed` is a map your loop keeps up to date: partition → offset of the last finished record + 1.
- Both callbacks run inside your own `poll()` call, on the polling thread, so using `consumer` there is safe.
- Without the commit on revoke, the next owner starts at the last periodic commit and repeats everything after it.
- If partitions are lost instead, for example after a session timeout, Kafka calls `onPartitionsLost()`. Committing there would fail, because another member may already own them.

## Rules and defaults

- **Default protocol:** the Java client uses `group.protocol=classic` in Kafka 4.3. The consumer protocol (KIP-848) reached general availability in Kafka 4.0; it is enabled on the broker by default, but a Java client still opts in with `group.protocol=consumer`. It is expected to become the client default in a later release.
- **Heartbeats (classic, Kafka 4.3):** the client sends a small "still alive" message, a heartbeat, every 3 s (`heartbeat.interval.ms`) from a background thread. If none arrives for `session.timeout.ms` (45 s), the member is removed.
- **Classic assignors:** `partition.assignment.strategy` defaults to `RangeAssignor, CooperativeStickyAssignor`, so the group starts with the eager Range assignor. To switch to cooperative, list only `CooperativeStickyAssignor`, using a rolling restart.
- **Consumer protocol settings:** the session timeout, heartbeat interval and assignor move to the broker (`group.consumer.session.timeout.ms` 45 s, `group.consumer.heartbeat.interval.ms` 5 s). The client settings for them are not supported.
- **Static membership:** set a unique `group.instance.id` per instance. A second consumer with the same id is fenced with `FencedInstanceIdException`.

## Not to be confused with

Eager rebalancing takes every partition from every member, then hands them all out again. Cooperative rebalancing (Kafka 2.4, KIP-429) takes away only the partitions that change owner, in two rounds, so the rest keep working. Rule: eager = stop everyone; cooperative = move only what must move.

## Interview Qs

### What triggers a rebalance?

A consumer joins or leaves the group, stops sending heartbeats for the session timeout, or does not call poll() within max.poll.interval.ms. A change to the subscribed topics also triggers one, such as added partitions or a new topic that matches a subscribed pattern.

### How do you reduce rebalance pain?

Use CooperativeStickyAssignor or group.protocol=consumer, so only moved partitions pause. Set group.instance.id so rolling restarts do not rebalance. Keep each batch short, so the poll deadline is never missed. Commit in onPartitionsRevoked, so the next owner repeats as little as possible.

### What is static membership?

A consumer with a group.instance.id keeps the same identity across restarts. If it comes back before the session timeout, it gets its old partitions back without a rebalance. It was added in Kafka 2.3 (KIP-345) to make rolling deployments cheap.
