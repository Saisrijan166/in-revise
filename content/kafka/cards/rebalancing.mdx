## Why it exists

Group members come and go, and each partition must always have exactly one owner. Someone has to hand out partitions again, without stopping the whole group for long.

## How it works

<Compare id="eager-vs-cooperative-rebalancing" />

- Kafka 4.0 brokers run the consumer protocol (KIP-848): no global sync barrier; the broker assigns partitions.
- With it, heartbeat, session timeout and assignor are broker settings; client assignor configs no longer apply.
- Commit in onPartitionsRevoked, so the next owner starts at the right offset.

## Example

```java
consumer.subscribe(List.of("payments"), new ConsumerRebalanceListener() {
    public void onPartitionsRevoked(Collection<TopicPartition> parts) {
        consumer.commitSync(processedOffsets);   // save progress before handing over
    }
    public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
});
```

## Defaults

| What | Default | Where |
|---|---|---|
| Session timeout (classic) | 45 s, session.timeout.ms | Kafka 4.3 consumer |
| Heartbeat interval (classic) | 3 s, heartbeat.interval.ms | Kafka 4.3 consumer |
| Assignors (classic) | RangeAssignor, CooperativeStickyAssignor | Kafka 4.3 consumer |

## Interview Qs

### What triggers a rebalance?

A consumer joins or leaves, misses heartbeats for the session timeout, or does not call poll() within max.poll.interval.ms. Adding partitions, or a new topic matching a subscribed pattern, also triggers one.

### How do you reduce rebalance pain?

Use CooperativeStickyAssignor or group.protocol=consumer so only moved partitions pause. Set group.instance.id for rolling restarts. Keep each batch short, and commit in onPartitionsRevoked.

### What is static membership?

A consumer with group.instance.id keeps its identity across restarts. If it returns within the session timeout, it gets its partitions back with no rebalance (KIP-345, since Kafka 2.3).
