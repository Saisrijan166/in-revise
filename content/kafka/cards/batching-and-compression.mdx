## What it is

Batching means the producer does not send each record on its own. It collects records headed for the same partition into a batch in memory and sends the batch in one request. Two settings decide when a batch leaves: `batch.size`, its largest size in bytes, and `linger.ms`, how long the producer may wait for more records. Compression shrinks each batch with a codec such as lz4 or zstd before it goes over the network.

## Why it exists

Each request has a fixed cost: a network round trip, request headers, and work on the broker. If the Payment service sent 10,000 events per second one by one, it would pay that cost 10,000 times, and the network and broker would spend more effort on overhead than on data. Batching pays it once for many records. Compression then works better too, because similar JSON events in one batch share a lot of repeated text.

1. Each `send()` adds the record to the open batch of its partition.
2. Under heavy traffic the batch fills to `batch.size` and is ready to go at once, without waiting for `linger.ms`.
3. Under light traffic the batch never fills, so it leaves after `linger.ms`.
4. The producer compresses the batch once. The broker checks it and appends it to the log still compressed, and consumers decompress it.

So the key is that one setting limits size and the other limits waiting, and compression rides on top of the batch.

## Example

The Payment service at peak hours favours throughput. These producer settings trade a few milliseconds for fuller, compressed batches:

```properties
linger.ms=20
batch.size=65536
compression.type=lz4
```

What to notice:

- `linger.ms=20` lets each batch wait up to 20 ms to collect more events. At peak, batches fill earlier and leave at once.
- `batch.size=65536` (64 KiB) allows bigger batches than the 16 KiB default, so each request carries more events.
- `compression.type=lz4` compresses each batch with a fast codec. Leave this line out and batches travel and are stored uncompressed, because the default is `none`.
- Measure before and after: the right values depend on event size and traffic.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| `batch.size` | 16384 bytes; `0` turns batching off | Kafka 4.3 producer |
| `linger.ms` | 5 ms (0 before Kafka 4.0) | Kafka 4.3 producer |
| `compression.type` | `none`; also `gzip`, `snappy`, `lz4`, `zstd` | Kafka 4.3 producer |
| `compression.type` | `producer`: keep the producer's codec | Kafka 4.3 topic |

- **Per partition:** each partition has its own batch, so records for different partitions never share one.
- **Topic codec wins:** if the topic sets a codec other than `producer`, the broker stores batches in that codec, recompressing them if needed.
- **Tuning across producer, broker and consumer:** see [performance tuning](card:kafka-performance-tuning).

## Common mistakes

- **"Compression happens on the broker."** The producer compresses; the broker keeps the batch compressed unless the topic asks for a different codec.
- **"linger.ms=0 means no batching."** Even with 0, records that arrive while a request is in flight collect into a batch. `batch.size=0` is what turns batching off.

## Interview Qs

### How does producer batching work?

Records for the same partition collect in one batch in memory. The batch is sent when it reaches `batch.size` bytes or when `linger.ms` has passed, whichever comes first. Under heavy load, batches fill quickly, so batching happens even with a small `linger.ms`.

### Where does compression happen, and what does it cost?

On the producer, once per batch. The broker validates the batch and keeps it compressed in the log, and consumers decompress it. This saves network bandwidth and disk space, and it costs CPU on the producer and the consumer.

### What do you trade when you raise linger.ms?

Fewer, fuller requests and a better compression ratio, for up to `linger.ms` of extra waiting when traffic is light. Kafka 4.0 changed the default from 0 to 5 ms because the gains from bigger batches usually keep latency the same or lower it.
