## What it is

Replication means Kafka keeps several copies of every [partition](card:partitions), each on a different [broker](card:kafka-architecture). Each copy is called a replica, and the number of copies is the replication factor (RF). One replica is the leader: producers write to it. The others are followers: they copy the leader's log, record by record, so they can replace it.

## Why it exists

A partition stored on one broker is lost when that broker's disk fails, and it cannot be read or written while the broker restarts. In the payment example, that means `PaymentCompleted` events that nobody can read, or that are gone. With RF 3, the same partition also lives on two other brokers. One broker can fail and the data is still there, and another copy takes over the writes.

## How it works

  chart={`flowchart LR

1. When you create a topic with RF 3, Kafka places the 3 replicas of each partition on 3 different brokers and makes one of them the leader. It spreads the leaders so each broker leads a fair share of partitions.
2. The Payment Service sends each record to the leader of its partition. The leader appends it to its log.
3. Each follower keeps asking the leader for new records, the same way a consumer does, and appends them at the same offsets in the same order.
4. If the leader's broker fails, a follower that is fully caught up becomes the new leader. Which followers count as caught up is the subject of the next concept, [ISR](card:isr-and-min-insync).

So the key is: one writer per partition, and identical copies behind it.

## Example

The payments topic is created with 3 partitions and RF 3 on a three-broker cluster, then described:

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --create --topic payments \
  --partitions 3 --replication-factor 3 --config min.insync.replicas=2
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic payments
```

```text output
Topic: payments  TopicId: Kbf63MnoSEGMnJDJk5254g  PartitionCount: 3  ReplicationFactor: 3  Configs: min.insync.replicas=2
  Topic: payments  Partition: 0  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2  Elr:   LastKnownElr:
  Topic: payments  Partition: 1  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3  Elr:   LastKnownElr:
  Topic: payments  Partition: 2  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1  Elr:   LastKnownElr:
```

What to notice:

- `PartitionCount: 3` stays 3. RF 3 gives each partition three replicas (nine in total); it does not create more partitions.
- `Replicas: 3,1,2` lists the brokers that hold partition 0. The first one, broker 3, is its preferred leader, and here it is the leader.
- Each broker leads exactly one partition, so the write load is shared.
- `Isr` lists the replicas that are caught up; all three are, because nothing has failed. `min.insync.replicas` and `Elr` belong to the [ISR](card:isr-and-min-insync) concept.

## Rules and defaults

- **RF is per topic:** set it at creation. Topics created without one take the broker's `default.replication.factor` (see [topics](card:topics)).
- **Copies on different brokers:** two replicas of one partition never share a broker. With `broker.rack` set, Kafka also spreads them over racks or zones.
- **Writes:** always go to the leader. Followers never accept writes from producers.
- **Reads:** go to the leader by default. Since Kafka 2.4 (KIP-392), a consumer with `client.rack` can read from a nearby follower when the brokers set `replica.selector.class`.
- **Failures survived:** with RF replicas, up to RF − 1 brokers holding the partition can fail without losing committed records.
- **Leadership comes back:** after a broker returns, `auto.leader.rebalance.enable` (true by default, Kafka 4.3) moves leadership back to the preferred leader.

## Not to be confused with

A [partition](card:partitions) is a slice of a topic's data; more partitions means more parallel work. A replica is a copy of one partition; more replicas means more safety. Rule: partitions split the data, replicas copy it.

## Interview Qs

### What is the difference between a leader and a follower?

The leader of a partition takes every write and, by default, serves the reads. Followers fetch from the leader and keep a copy of its log with the same offsets and order. They exist so that one of them, if it is in sync, can become leader when the leader's broker fails.

### Can a consumer read from a follower?

Yes, since Kafka 2.4 (KIP-392). The brokers set `broker.rack` and `replica.selector.class` to the rack-aware selector, and the consumer sets `client.rack`. The consumer then reads from a replica in its own zone, which saves cross-zone network cost. Records may arrive slightly later than from the leader.

### How many broker failures does RF 3 survive?

Up to two of the three brokers holding a partition can fail without losing its committed records, because each in-sync replica has them all. Whether producers can still write during those failures depends on [min.insync.replicas](card:isr-and-min-insync).
