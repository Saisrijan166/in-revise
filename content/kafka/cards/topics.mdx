## What it is

A topic is a named stream of one kind of event, such as `payments` or `refunds`. Producers write events to a topic by its name, and consumers read from it by the same name; they never need to know each other. Kafka stores each topic as one or more [partitions](card:partitions), ordered logs placed on different brokers. A topic also has its own settings, such as how long its events are kept.

## Why it exists

Producers and consumers need one agreed place to meet. Without a named stream, the Payment service would have to know where each reader lives. Different kinds of events also need different handling: payment events may need 3 copies and 14 days of history, while page clicks may need 1 day. A topic gives each stream a name and its own settings.

1. An admin creates the topic with a name, a partition count and a replication factor, the number of copies of each partition.
2. The controllers record the new topic and place each partition's copies on brokers, choosing one leader per partition.
3. Producers write events that name the topic. Each event lands in exactly one partition.
4. Each consumer group reads the whole topic, all of its partitions, keeping its own position. Inside one group the partitions are shared out among its members ([consumer groups](card:consumer-groups), later).

## Example

Create the `payments` topic on a three-broker cluster, then look at where Kafka placed it:

```bash
# payments: 3 partitions, 3 copies of each, keep events 14 days (this topic only)
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic payments \
  --partitions 3 --replication-factor 3 --config retention.ms=1209600000

bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic payments
```

```text output

	Topic: payments	Partition: 1	Leader: 2	Replicas: 2,3,1	Isr: 2,3,1	Elr: 	LastKnownElr: 
	Topic: payments	Partition: 2	Leader: 3	Replicas: 3,1,2	Isr: 3,1,2	Elr: 	LastKnownElr: 
```

What to notice:

- Each partition has a different leader broker (1, 2, 3), so the write and read load is spread over all three.
- `Replicas` lists the three brokers holding a copy; `Isr` lists the copies that are up to date ([ISR](card:isr-and-min-insync), later).
- `--config retention.ms=1209600000` (14 days) changes only this topic. Without it, the topic keeps the broker default of 7 days. `min.insync.replicas=1` is a cluster default shown here; you will meet it with ISR.

## Rules and defaults

- **Partitions when none are given (Kafka 4.3):** 1, from the broker's `num.partitions`.
- **Copies when none are given (Kafka 4.3):** 1, from `default.replication.factor`. The Kafka docs advise 2 or 3 in production.
- **Auto-creation (Kafka 4.3):** `auto.create.topics.enable=true`, so a write to a missing topic creates it with these defaults.
- **Changing the count later:** you can add partitions but never remove them; see [ordering vs scaling](card:ordering-and-scaling).
- **Internal topics:** Kafka runs its own topics, such as `__consumer_offsets`; never add partitions to them by hand.

## Interview Qs

### Can many producers write to one topic, and many consumers read it?

Yes to both. A topic accepts writes from any number of producers. Every consumer group reads every event in it; inside one group, the partitions are shared out so each event is handled by one member of that group.

### Why not rely on topic auto-creation in production?

An auto-created topic takes the broker defaults: one partition and one copy, unless the broker was changed. That gives no parallel reading and no copy to fail over to, and a typo in a topic name silently creates a new topic. Create topics on purpose, with planned partitions and replication factor.

### What decides the settings of a topic?

The broker defaults, unless the topic overrides them. You pass overrides with `--config` at creation, or change them later with `kafka-configs.sh`. Retention time, cleanup policy and segment size are common per-topic settings.
