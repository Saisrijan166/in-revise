## Why it exists

Producers and consumers need a shared name for a stream, so the Order Service and every reader of orders meet in one place without knowing each other.

## How it works

<Compare id="topic-vs-partition-vs-broker" />

- Each [consumer group](card:consumer-groups) reads the whole topic with its own progress: payment-service and analytics never block each other.
- Order holds per [partition](card:partitions), never across the topic.
- Retention and compaction are topic configs: see [log storage](card:log-storage).

## Example

```bash
# orders: 6 partitions, 3 copies of each, keep 14 days (this topic only)
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders \
  --partitions 6 --replication-factor 3 --config retention.ms=1209600000

# Shows each partition's leader, replicas and ISR
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Partitions when none are given | 1 (`num.partitions`) | Kafka 4.3 broker |
| Copies when none are given | 1 (`default.replication.factor`) | Kafka 4.3 broker |
| Create a topic on first use | `true` (`auto.create.topics.enable`) | Kafka 4.3 broker |

## Interview Qs

### Can many producers write to one topic, and many consumers read it?

Yes to both. Kafka topics are multi-producer and multi-subscriber. Every consumer group reads every record; inside one group, the partitions are shared out among its consumers.

### Why not rely on topic auto-creation in production?

Auto-created topics take the broker defaults: one partition and one copy unless changed. That gives no parallelism and no copy to fail over to. Create topics explicitly with planned partitions and replication factor.
