## What it is

A delivery semantic is the promise a system makes about how many times each record is processed when something fails. There are three: at-most-once (never twice, but maybe never), at-least-once (never lost, but maybe twice) and exactly-once (once, with no loss and no repeat). In Kafka the consumer side is decided mostly by when it [commits its offset](card:offset-commits) relative to the work.

## Why it exists

Crashes happen between two steps. A consumer that has sent an SMS but not yet committed will, after a restart, read the same event and send it again. A consumer that committed first and then crashed will skip the event for good. No setting removes both risks for free, so you choose which one your use case can live with, and design around it.

## How it works

<Compare id="at-most-once-vs-at-least-once-vs-exactly-once" />

1. The consumer polls a batch of records.
2. It either commits the batch's offsets first and then does the work (at-most-once), or does the work first and then commits (at-least-once).
3. A crash happens between the two steps. The group gives the partition to another consumer, which starts from the last committed offset.
4. With commit-first, the records that were in progress are past that offset, so they are skipped. With work-first, they are before it, so they run again.
5. Exactly-once removes the gap only when the work is "write to another Kafka topic": the output and the offset are committed together in one [transaction](card:kafka-transactions), which comes next.

So the order of "work" and "commit" decides between loss and repeats.

## Example

The Notification service reads `PaymentCompleted` events and sends an SMS for each:

```java
while (true) {
    var records = consumer.poll(Duration.ofMillis(500));
    for (var record : records) {
        sendSms(record.value());       // 1. do the work
    }
    consumer.commitSync();             // 2. then save "done up to here"
}
```

What to notice:

- The SMS is sent before the commit, so this loop is at-least-once. A crash between the two lines makes the next consumer send the same SMSes again.
- Move `commitSync()` above the `for` loop and it becomes at-most-once: a crash during the loop loses those SMSes instead.
- The loop assumes `enable.auto.commit=false`. Auto commit saves offsets on a timer, unrelated to whether `sendSms` finished.
- The cure for the repeat is not a different order but an [idempotent consumer](card:idempotent-consumers) that skips a paymentId it has already handled.

## Rules and defaults

- **Kafka's default:** at-least-once. The producer retries failed sends, and a consumer that commits after processing repeats work after a crash.
- **At-most-once on purpose:** disable producer retries and commit before processing.
- **Exactly-once inside Kafka:** a transactional producer that also commits the consumed offsets, and consumers with `isolation.level=read_committed`; or Kafka Streams with `processing.guarantee=exactly_once_v2`.
- **Exactly-once into another system:** not automatic. Either store the offsets in the same database transaction as the output, or make the write idempotent.
- **Producer side:** the [idempotent producer](card:idempotent-producer) stops duplicates caused by producer retries; it does nothing about consumer repeats.

## Interview Qs

### At-most-once vs at-least-once vs exactly-once?

At-most-once commits the offset before processing, so a crash loses records but never repeats them. At-least-once processes first, so a crash repeats records but never loses them; this is Kafka's default. Exactly-once commits output and offsets in one Kafka transaction, so neither happens, but only for Kafka-to-Kafka work.

### Why is at-least-once with idempotent consumers the usual choice?

It never loses data, it works with any destination, such as a database, an API or an SMS gateway, and it costs no transactions. The repeats it causes are made harmless by deduplicating on a business id inside the event. Exactly-once is reserved for Kafka-to-Kafka pipelines.

### How would you design a reliable Kafka pipeline?

Topics with RF 3 and min.insync.replicas 2; producers with acks=all and idempotence; consumers that commit only after processing and deduplicate on an event id; failed records retried, then sent to a dead letter topic; and alerts on consumer lag. The result is at-least-once delivery where duplicates do no harm.
