## What it is

Database per service is the rule that each service owns its data. Only that service reads and writes its tables. Other services get the data by calling its API or by listening to the events it publishes; an event is a message that says something happened, such as PaymentFailed. "Owns" is about access, not hardware: the tables may sit in a private schema on a server that other services also use.

## Why it exists

In a [monolith](card:monolith-and-microservices) every module can read every table. If the Order and Payment services kept doing that after a split, a column the Payment team renames would break the Order service, and both teams would again have to change and release together. One service's heavy query would also slow the other. With private data, each service hides its tables behind its API, so it can change its schema and deploy alone.

## How it works

1. Each service gets its own tables, schema or server, and a database user that can reach only those.
2. When the Order service needs payment data once, it calls the Payment service's API, for example `GET /payments/42`.
3. When it needs a few payment fields on every request, it keeps a local copy of just those fields and updates the copy from the Payment service's events.
4. When one business action changes data in two services, each service commits its own local transaction, and a [saga](card:saga) links the steps (you will see it in the messaging topic).

So the key is one owner per table, and everyone else asks the owner.

## Example

The Order service gets its own schema and database user on the shop's shared PostgreSQL server:

```sql
CREATE SCHEMA orders;
CREATE ROLE order_svc LOGIN PASSWORD 'secret';
GRANT USAGE, CREATE ON SCHEMA orders TO order_svc;   -- nothing on schema payments
```

```yaml
# order-service application.yaml
spring:
  datasource:
    url: jdbc:postgresql://db.shop.internal:5432/shop?currentSchema=orders
    username: order_svc
```

What to notice:

- `order_svc` has rights only on `orders`. A query such as `select * from payments.payment` fails with "permission denied for schema payments", so the database enforces the ownership, not just a team agreement.
- `currentSchema=orders` makes table names without a schema resolve inside `orders`, so the service code never names the schema.
- The server is shared, which keeps cost low. If the Order service later needs its own server, only the URL changes.

## Rules and defaults

- **Three ways to keep data private:** private tables per service, a schema per service, or a database server per service. Only some high-throughput services might need a server of their own.
- **Enforce it with credentials:** give each service a database user that can reach only its own data. A rule that only lives in a wiki gets broken under deadline pressure.
- **Queries across services:** the application does the join, by calling each owner (API composition) or by reading a view built from their events ([CQRS](card:cqrs), coming next in this topic).
- **Writes across services:** no single database transaction spans two services' databases; a saga with local transactions replaces it.
- **Polyglot persistence is allowed, not required:** each service may choose its own database type, but every extra type is one more thing to run.

## Not to be confused with

A shared database **server** is one machine that several services use, each in its own schema with its own user; that is fine. A [shared database](term:shared-database) means several services read and write the **same tables**; that is the anti-pattern, and it turns the system into a distributed monolith. Rule: sharing the server is fine; sharing the tables is not.

## Common mistakes

- **"Reading another service's tables is harmless if I only read."** A read still depends on that service's column names and meaning, so the owner can no longer change its schema without breaking you.
- **"Keeping a copy of another service's data breaks the rule."** A local copy fed by the owner's events is allowed. The owner stays the truth, the copy is read-only, and it may be a little behind.

## Interview Qs

### Should each microservice have its own database?

It must own its data: no other service touches its tables. A separate server is optional. Private schemas with separate credentials on one server cost the least, and only some high-throughput services might need a server of their own.

### Why is a shared database an anti-pattern?

Services couple through the schema: every change needs all the teams that use those tables to agree, and one service's heavy queries can slow the others. Independent deployment, the main reason for microservices, is lost.

### Orders need the customer's name, but customers live in another service. What do you do?

Call the Customer service and join the results in memory (API composition), or keep the name in the Order service, updated from CustomerUpdated events. The copy is eventually consistent: for a short time after a change it can show the old name.
