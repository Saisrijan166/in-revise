## Why it exists

If services share tables, one team's schema change can break another team's service, and they can no longer change or deploy on their own.

## How it works

<Mermaid
  alt="The Order service uses its own Orders database and the Payment service its own Payments database. The Order service asks the Payment service for data over its API and receives PaymentFailed events from it. It never reads the Payments database directly."
  chart={`flowchart LR
  OS[Order Service] --> ODB[(Orders DB)]
  PS[Payment Service] --> PDB[(Payments DB)]
  OS -- "GET /payments/42" --> PS
  PS -- "PaymentFailed event" --> OS
  OS -. "never reads directly" .-> PDB`}
/>

- Need data you do not own? Ask the owner ([API composition](card:api-composition)) or keep a [local copy](card:data-duplication) fed by its events.
- A change across services runs as a [saga](card:saga), not one ACID transaction.
- Fast views over many services' data: [CQRS](card:cqrs).

## Example

```yaml
# order-service: its own schema and user on the shared PostgreSQL server
spring:
  datasource:
    url: jdbc:postgresql://db.shop.internal:5432/shop?currentSchema=orders
    username: order_svc   # granted rights on schema "orders" only
```

## Interview Qs

### Should each microservice have its own database?

It must own its data: no other service touches its tables. A separate server is optional: private schemas with separate credentials on one server cost the least. Only some high-throughput services need their own.

### Why is a shared database an anti-pattern?

Services couple through the schema: every change needs all teams to agree, and one service's heavy queries can slow the others. Independent deployment, the main reason for microservices, is lost.

### Orders need the customer's name, but customers live in another service. What do you do?

Call the Customer service and join in memory (API composition), or keep the name in the Order service, updated from CustomerUpdated events. The copy is eventually consistent.
