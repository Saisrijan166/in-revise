## Why it exists

Networks and consumers fail mid-way, so a broker must choose between losing a message and sending it again. Your code must cope with the choice.

## How it works

<Compare id="at-most-vs-at-least-vs-exactly-once" />

- Kafka's default is at-least-once; at-most-once means no producer retries and committing first.
- Storing the consumer's position with its output gives exactly-once without 2PC.
- Keys for HTTP retries are a different tool: [idempotency keys](card:idempotency).

## Example

```java
@KafkaListener(topics = "payments", groupId = "order-service")
@Transactional
public void on(PaymentFailed event) {
    if (processed.existsById(event.eventId())) {
        return;                                  // duplicate: already applied
    }
    processed.save(new ProcessedEvent(event.eventId()));  // primary key = eventId
    orders.markPaymentFailed(event.orderId());   // same DB transaction
}
```

## Defaults

| What | Default | Where |
|---|---|---|
| `enable.idempotence` | `true` | Kafka 4.3 producer |
| `isolation.level` | `read_uncommitted` | Kafka 4.3 consumer |

## Interview Qs

### Is exactly-once delivery possible?

Inside Kafka, yes: a transaction writes the output and the consumer offsets together, and readers use read_committed. Across a database or an external API you get exactly-once effects only by making the consumer idempotent.

### How do you make a consumer idempotent?

Give every event a unique eventId. In one local transaction, insert the id into a processed table with a unique key and apply the change. A redelivered event hits the key and is skipped.
