## What it is

A delivery guarantee says how often a message can reach the consumer's processing when something fails. At-most-once means it can be lost but never repeats; at-least-once means it is never lost but can repeat; exactly-once means neither, inside a stated boundary. Which one you get depends mostly on when the consumer commits its [offset](card:kafka-fundamentals). An idempotent consumer is one where processing the same message twice has the same effect as processing it once.

## Why it exists

Inventory Service reserves stock for each OrderCreated. It can crash after reserving but before telling Kafka it has finished. On restart Kafka delivers the event again, and without care the stock is reserved twice. If it marks the event done first and crashes before reserving, the order never gets its stock. No broker can avoid both risks, so you choose one and write the consumer to be safe with it.

## How it works

<Compare id="at-most-vs-at-least-vs-exactly-once" />

1. The consumer reads a record from its partition.
2. At-most-once: it commits the offset, then processes. A crash in between loses the record, because the restart begins after the committed offset.
3. At-least-once: it processes, then commits the offset. A crash in between means the record is processed again after the restart.
4. Exactly-once inside Kafka: when the output also goes to Kafka topics, the output records and the input offsets are committed in one Kafka transaction, and readers use `read_committed`, so they see only committed results.
5. Anything outside Kafka, such as a database or a payment API, gets at-least-once delivery. An idempotent consumer turns the repeat into a no-op.

So the plan is: accept at-least-once, and make every consumer idempotent.

## Example

Inventory Service records each event id in the same transaction as the reservation:

```java
@KafkaListener(topics = "orders", groupId = "inventory")
@Transactional
public void onOrderCreated(OrderCreated event) {
    if (processed.existsById(event.eventId())) {
        return;                                           // seen before: skip
    }
    processed.save(new ProcessedEvent(event.eventId()));  // primary key = eventId
    stock.reserve(event.orderId(), event.items());        // same DB transaction
}
```

What to notice:

- The id check, the insert and the reservation run in one database transaction, so either both rows are saved or neither is.
- If the service crashes after the database commit but before the offset commit, the redelivered event finds its id and is skipped.
- `eventId` is the primary key, so two copies processed at the same moment cannot both insert. The loser's transaction rolls back, and so does its reservation.
- This guards only Inventory's own database. For an external call, such as charging ₹500, pass a stable key to the provider as its [idempotency key](card:idempotency).

## Rules and defaults

- **Spring for Apache Kafka (4.1):** sets `enable.auto.commit=false` and, in the default `BATCH` ack mode, commits offsets after the listener has processed all records from a poll. A crash before that commit redelivers them, so you get at-least-once.
- **Plain Kafka consumer (4.3):** `enable.auto.commit=true` by default, committing every 5 seconds (`auto.commit.interval.ms`).
- **Idempotent producer (Kafka 4.3):** `enable.idempotence=true` by default. It stops duplicates caused by the producer's own retries. It does not stop your code from sending the same event twice or a consumer from processing it twice.
- **Exactly-once in Kafka:** needs a `transactional.id` on the producer, consumers with `isolation.level=read_committed` (the default is `read_uncommitted`), and auto commit off. Kafka Streams, Kafka's stream-processing library, sets all of this up when you set `processing.guarantee=exactly_once_v2`; its default is `at_least_once`.
- **Outside Kafka:** the Kafka docs suggest storing the consumer's position in the same place as its output, or deduplicating by id as above.

## Not to be confused with

- **Idempotent producer:** a Kafka setting that removes duplicates from send retries, between producer and broker.
- **Idempotent consumer:** your code, which makes a repeated delivery harmless.
- **[Idempotency key](card:idempotency):** an id that a client sends with an HTTP request so a retried call does not act twice.

Rule: producer idempotence protects the log; consumer idempotence protects your data; an idempotency key protects an API.

## Interview Qs

### Is exactly-once delivery possible?

Inside Kafka, yes: a transaction writes the output records and the consumer offsets together, and readers use read_committed. Across a database or an external API you cannot get exactly-once delivery, but you get exactly-once effects by making the consumer idempotent, or by storing the offset in the same transaction as the output.

### How do you make a consumer idempotent?

Give every event a unique eventId. In one local transaction, insert the id into a processed table that has a unique key on it, and apply the change. A redelivered event finds its id and is skipped; two racing copies cannot both insert. Where possible, also make the change naturally safe to repeat, such as "set status = PAID".

### The idempotent producer is on by default. Why do I still get duplicates?

It only removes duplicates caused by the producer's own retries of one send. A consumer that crashes before committing its offset reads the record again, and an application that calls send twice writes two records. Both cases need an idempotent consumer.
