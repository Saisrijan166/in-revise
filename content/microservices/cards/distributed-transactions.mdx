## What it is

A local transaction is a group of changes in one database that commit together or roll back together. It gives the ACID guarantees: atomic (all or nothing), consistent, isolated (others do not see half-done work) and durable. A distributed transaction must change data in several databases or services as one such unit. Two-phase commit (2PC) is the classic protocol for it: a coordinator first asks every participant to prepare, and only when all agree tells them all to commit.

## Why it exists

Placing an order changes the Order, Inventory and Payment databases, because each service [owns its data](card:database-per-service). Each database commits on its own. If the payment fails after the stock is reserved, nothing rolls the stock back automatically, and a Spring `@Transactional` method cannot reach the other databases. You need a way to keep them consistent. 2PC is one answer, and its cost explains why microservices usually choose another.

## How it works

<Mermaid
  alt="Two-phase commit. Phase 1: the coordinator asks the Order database and the Inventory database to prepare; both save their work and vote yes. Phase 2: because all voted yes, the coordinator tells both to commit. If any had voted no, it would tell all to roll back."
  chart={`sequenceDiagram
  participant C as Coordinator
  participant O as Order DB
  participant I as Inventory DB
  C->>O: prepare
  C->>I: prepare
  O-->>C: yes
  I-->>C: yes
  C->>O: commit
  C->>I: commit`}
/>

1. The coordinator, a transaction manager, starts the transaction on every participant, and each one does its part of the work.
2. Phase 1, prepare: the coordinator asks each participant to prepare. Each one saves its work to disk so it can still commit after a crash, keeps its locks, and votes yes or no.
3. Phase 2, decide: if every vote is yes, the coordinator tells all to commit. If any vote is no, or a participant does not answer, it tells all to roll back.
4. Between the phases, a prepared participant cannot decide alone. If the coordinator crashes, the participant keeps its locks and waits until the coordinator recovers.

So 2PC gives all-or-nothing, at the price of locks held while messages cross the network.

## Example

Order Service hopes one annotation covers the whole order:

```java
@Transactional
public void placeOrder(Order order) {
    orders.save(order);                                  // local: rolled back on error
    inventoryClient.reserve(order.id(), order.items());  // remote: committed in Inventory
    paymentClient.charge(order.id(), 500);               // throws: payment timed out
}   // the order row rolls back; the stock stays reserved
```

What to notice:

- `@Transactional` manages Order Service's own database only. The rollback removes the order row and nothing else.
- Inventory committed the reservation in its own database the moment `reserve` returned. No message tells it to release the stock.
- A timeout does not mean "not charged": Payment may have taken the ₹500 just before the reply was lost.
- The fix is not a bigger transaction. Each step needs a compensating action, organised by a [saga](card:saga), which comes next.

## Rules and defaults

- **Spring `@Transactional`:** a local transaction on one transaction manager's resource, usually one database. Spanning several resources needs a global transaction manager based on Jakarta Transactions (JTA).
- **HTTP calls:** a call to another service never joins your database transaction. It commits on the other side as soon as that service finishes.
- **XA:** the standard interface that lets one transaction manager run 2PC across several resource managers. MySQL's InnoDB supports XA transactions.
- **PostgreSQL 18:** `max_prepared_transactions` is 0 by default, so `PREPARE TRANSACTION` is disabled. The docs say it is meant for an external transaction manager, and a prepared transaction keeps holding its locks.
- **Brokers:** a message broker, or a database, may not support 2PC at all, so the protocol cannot always span both.

## Not to be confused with

Two-phase commit makes several databases commit together at the end, holding locks until then. A [saga](card:saga) lets each service commit its own step at once and fixes failures with compensating steps, with no locks held between services. Rule: 2PC = one atomic commit with locks; saga = many local commits plus compensation.

## Interview Qs

### Why do microservices avoid two-phase commit?

Prepared participants hold their locks while they wait for the coordinator, so one slow or crashed coordinator stalls every service in the transaction. Not every broker or database supports 2PC, and it ties each service's availability to all the others. Microservices use local transactions plus sagas instead.

### Does @Transactional work across two microservices?

No. It manages a transaction on your own transaction manager, usually one database. A call to another service commits on that side as soon as it finishes, and your rollback cannot reach it. To undo it you need a compensating action, such as releasing the stock or refunding the payment.

### What are the two phases of two-phase commit?

Phase 1, prepare: the coordinator asks every participant to make its work durable and vote yes or no, while keeping its locks. Phase 2, commit or roll back: if all voted yes the coordinator tells all to commit; otherwise it tells all to roll back.
