## Why it exists

Placing an order touches the Order, Inventory and Payment databases. Each commits on its own, so nothing makes all three succeed or fail together.

## How it works

<Mermaid
  alt="Two-phase commit. Phase 1: the coordinator asks the Order database and the Payment database to prepare; both save their work and vote yes. Phase 2: because all voted yes, the coordinator tells both to commit. If any had voted no, it would tell all to roll back."
  chart={`sequenceDiagram
  participant C as Coordinator
  participant O as Order DB
  participant P as Payment DB
  C->>O: prepare
  C->>P: prepare
  O-->>C: yes
  P-->>C: yes
  C->>O: commit
  C->>P: commit`}
/>

- A prepared participant waits for the coordinator's decision and keeps its locks meanwhile.
- The usual microservices answer: [saga](card:saga), with an [outbox](card:outbox-and-inbox) for each step's event.

## Example

```java
@Transactional
public void checkout(Order order) {
    orders.save(order);                                  // local: rolled back on error
    paymentClient.charge(order.id(), order.totalInr());  // remote: ₹ already taken
    inventoryClient.reserve(order.items());              // throws: out of stock
}   // the order row rolls back, the charge does not
```

## Interview Qs

### Why do microservices avoid two-phase commit?

Participants hold locks while waiting for the coordinator, so one slow or failed coordinator stalls every service in the transaction. Many message brokers and databases do not support it, and it couples each service tightly to the others.

### Does @Transactional work across two microservices?

No. It manages the resources of your own transaction manager, usually one database. A call to another service commits on its own side, so you need a compensating action such as a refund.
