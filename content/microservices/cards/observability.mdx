## What it is

Observability is how well you can understand what is happening inside a running system from the data it sends out. In microservices that data comes as three signals. Logs are records of single events, metrics are numbers measured over time, and traces show the path of one request through many services. Every service produces all three, and they are collected in one place.

## Why it exists

One checkout in the shop touches the Order, Inventory, Payment and Notification services, and each runs as several instances (copies) on different machines. When a customer says "order 1001 failed", the cause could be on any of them. Without collected signals you would search log files machine by machine and guess. With them, an alert tells you something is wrong, and one ID leads you to the exact service and log line.

## How it works

<Compare id="logs-vs-metrics-vs-traces" />

1. Each service writes structured log lines, one JSON object per event, to standard output. Every line carries the request's trace ID.
2. A log agent on each machine ships those lines to one central store, where you search all instances at once.
3. Each service also counts requests, errors and response times. A metrics system collects these numbers regularly and draws dashboards and fires alerts from them.
4. Each service records a timed step, a span, for its part of every request and sends it to a tracing backend; [Distributed Tracing](card:distributed-tracing) shows how the spans join up.
5. When something breaks, you go from the alert, to the trace that shows which service failed or was slow, to that service's logs for the same trace ID.

## Example

A simplified structured log line from the Payment Service. The real field names depend on the format you choose.

```json
{
  "timestamp": "2026-10-20T10:15:02.114Z",
  "level": "WARN",
  "service": "payment-service",
  "traceId": "0af7651916cd43dd8448eb211c80319c",
  "orderId": "1001",
  "message": "Payment failed: card declined, amount ₹500"
}
```

What to notice:

- Each value is a separate field, so the central store can filter `service = payment-service AND level = WARN` without text matching.
- `traceId` is the same in every service's log for this checkout. Leave it out and you can no longer join this line to the Order Service's lines.
- `orderId` belongs in logs, where one value per line is fine. As a metric label it would create a new series per order.
- The line has no card number or token: logs are read by many people and kept for a long time.

## Rules and defaults

- **Structured logging:** Spring Boot 4.1 writes JSON logs with `logging.structured.format.console=ecs`; `logstash` and `gelf` are the other built-in formats.
- **Trace IDs in logs:** with Micrometer Tracing, Spring Boot 4.1 adds `traceId` and `spanId` to each log line by default.
- **Where logs go:** the service writes to standard output and does not manage log files; the platform collects and routes them.
- **Sensitive data:** keep tokens, passwords and personal data out of every log line, as [Securing Microservices](card:microservices-security) explains.
- **Watch outcomes:** a fast HTTP 200 with the wrong content is still an error, so also track results such as orders paid per minute.

## Not to be confused with

A correlation ID is any ID copied into every log line of one call chain, so the lines can be found together. A trace ID does that job too, and also links timed spans into a tree that shows the order and duration of each call. Rule: correlation ID joins log lines; trace ID joins log lines and spans.

## Interview Qs

### How do you debug one request across many services?

Take the trace ID from the error or the response. Open the trace to see which span failed or was slow, then search the central logs by that ID for the reason. Check the metrics to see whether it was one request or a trend.

### Why should a user ID not be a metric label?

Each distinct label value creates a separate time series. Millions of users would mean millions of series, which uses a lot of memory and makes queries slow. Metrics should stay low in distinct values; per-user detail belongs in logs and traces.

### A service returns HTTP 200, yet customers say orders fail. How would you have caught it?

The status code only says the request finished. Measure the business outcome too, such as the share of placed orders that reach "paid", and alert when it drops. Also log a clear event when an order fails, with its trace ID.
