## What it is

A deployment strategy is the plan for replacing the running version of a service with a new one: which users get the new version, and when. A rolling update replaces Pods a few at a time. Blue-green keeps two full copies, blue (the current version) and green (the new one), and switches all traffic from one to the other at once. A canary sends a small share of traffic to the new version first and grows it while the numbers look good.

## Why it exists

Every release replaces running code, and some releases are bad. If you stop all old Pods and then start the new ones, users get errors in between, and a broken version reaches everybody at once. A strategy keeps enough Pods serving during the change, limits how many users a bad version can hurt, and decides how fast you can go back.

## How it works

<Compare id="rolling-vs-blue-green-vs-canary" />

A rolling update of Order Service from 1.4.2 to 1.4.3, with the settings in the example below:

1. You change the image tag in the Deployment. Only a change to the Pod template starts a rollout; changing `replicas` only scales.
2. Kubernetes creates a new ReplicaSet and starts one new Pod, so for a moment 5 Pods exist.
3. When the new Pod passes its [readiness probe](card:health-probes), it counts as available, and Kubernetes stops one old Pod.
4. This repeats until all 4 Pods run 1.4.3. If a new Pod never gets ready, no more old Pods are stopped and the rollout stalls.
5. If 1.4.3 misbehaves, `kubectl rollout undo deployment/order-service` rolls back to the previous revision, whose ReplicaSet was kept.

So during a rolling update, the old and the new version serve users at the same time.

## Example

Order Service keeps all 4 Pods serving during every update.

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most 5 Pods during the update
      maxUnavailable: 0    # never fewer than 4 available
```

What to notice:

- `maxUnavailable: 0` means capacity never drops: an old Pod stops only after a new one is ready.
- `maxSurge: 1` allows one extra Pod at a time. The update is slower, but it needs room for only one more Pod.
- With the defaults (25% each) and 4 replicas, Kubernetes may stop 1 old Pod before a new one is ready, so the service briefly runs on 3.
- Both settings depend on readiness. A Pod without a readiness probe counts as ready as soon as it starts, so old Pods are removed too early.

## Rules and defaults

- **Default strategy:** `RollingUpdate` with `maxSurge` 25% (rounded up) and `maxUnavailable` 25% (rounded down) (Kubernetes 1.37).
- **Recreate:** the other built-in type. It stops all old Pods before starting new ones, so there is a short outage.
- **Rollback history:** 10 old ReplicaSets are kept by default (`revisionHistoryLimit`), so `kubectl rollout undo` can go back.
- **Stuck rollouts:** after `progressDeadlineSeconds`, 600 s by default, the Deployment reports that it failed to progress. It does not roll back by itself.
- **Blue-green and canary:** not built into the Deployment. Blue-green uses two Deployments and repoints the Service; a canary uses weighted routes in Gateway API or a service mesh.
- **Compatible changes:** while two versions run, change APIs, events and columns by [expand and contract](card:expand-and-contract): add the new form, move everyone over, then remove the old form.

## Not to be confused with

Deploying puts new code on the servers. Releasing lets users use the new feature. A feature flag separates the two: the code is deployed switched off, and the feature is switched on later, for some users or for all, without a new deploy. Rule: deploy = the code is running; release = users get the feature.

## Interview Qs

### How do you deploy a microservice without downtime?

Roll out gradually with readiness probes, so a Pod gets traffic only once it is ready. Keep APIs, events and the schema backward compatible, because two versions run together. Watch error rates and roll back quickly. Zero downtime is a design goal, not a Kubernetes guarantee.

### How do you rename a database column with zero downtime?

Expand: add the new column and write to both. Migrate: copy the old values over and move every reader to the new column. Contract: drop the old column once no running version uses it. Each step is its own deploy.

### When would you choose canary over blue-green?

Canary when the risk is a bug that only real traffic shows: a small share of users meets it first. Blue-green when you need an instant switch back and can pay for a second full environment; everyone moves at once, so you test green well before switching.
