## Why it exists

Every release replaces running code. The strategy decides how many users see a bad version, and how fast you can switch back.

## How it works

<Compare id="rolling-vs-blue-green-vs-canary" />

- During most rollouts two versions run at once: change APIs and schemas by [expand and contract](card:expand-and-contract).
- A feature flag splits deploy (the code is live) from release (users see it).

## Example

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most 5 Pods during the update
      maxUnavailable: 0    # never fewer than 4 available
```

## Interview Qs

### How do you deploy a microservice without downtime?

Roll out gradually with readiness probes, keep APIs and the schema backward compatible, and watch error rates so you can roll back. Zero downtime is a design goal, not a Kubernetes guarantee.

### How do you rename a database column with zero downtime?

Expand: add the new column and write to both. Migrate: backfill it and move every reader. Contract: drop the old column once no running version uses it.
