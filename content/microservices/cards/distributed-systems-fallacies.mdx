## What it is

The fallacies of distributed computing are eight false beliefs that programmers tend to hold about the network, such as "the network is reliable". L. Peter Deutsch listed seven of them at Sun Microsystems in 1994, and James Gosling added the eighth around 1997. A distributed system is one where separate programs work together by sending messages over a network, which is exactly what [microservices](card:monolith-and-microservices) are.

## Why it exists

Inside a monolith, a method call either runs or throws, almost instantly. Once Order calls Payment over the network, the call can be lost, delayed, or answered after Order has stopped waiting. Code written as if the network were perfect hangs when Payment is slow, or charges the customer twice when it simply tries again. Each fallacy turns into a design rule that prevents one of these failures.

## How it works

| The false belief | What it means for a service |
|---|---|
| The network is reliable | Give every call a timeout and safe, limited retries |
| Latency is zero | Avoid chatty calls; batch, cache or call in parallel |
| Bandwidth is infinite | Paginate; send only the fields that are needed |
| The network is secure | Encrypt and authenticate every call, even inside the data centre |
| Topology doesn't change | Find instances by name through service discovery, not fixed IPs |
| There is one administrator | Many teams own the parts; observe the whole request path |
| Transport cost is zero | Turning objects into bytes and moving them costs time and money |
| The network is homogeneous | Use standard protocols and contracts, such as HTTP and JSON |

The first belief hides the hardest problem. Follow one call from Order to Payment:

1. Order sends the request. The network can drop it before Payment sees it.
2. Payment receives the request, checks it and charges ₹500.
3. Payment sends the reply. The network can drop it or delay it.
4. Order waits. If no reply arrives before its timeout, it cannot tell whether step 2 happened.

So the key is: a timeout means the outcome is unknown, not that the call failed. Each rule in the table has its own concept later in this tech.

## Example

Order charges ₹500 and must handle the case where no reply comes back:

```java
HttpRequest charge = HttpRequest.newBuilder(URI.create("http://payment:8080/payments"))
        .POST(HttpRequest.BodyPublishers.ofString("{\"orderId\":42,\"amount\":500}"))
        .timeout(Duration.ofSeconds(2))
        .build();
try {
    HttpResponse<String> reply = http.send(charge, BodyHandlers.ofString());
    return reply.statusCode() == 201 ? "PAID" : "FAILED";
} catch (HttpTimeoutException e) {
    // Unknown outcome: Payment may have charged ₹500 and only the reply was lost.
    return "UNKNOWN";   // do not charge again; ask Payment for order 42's status first
}
```

What to notice:

- A 201 or an error status is a real answer. Only the timeout branch leaves Order not knowing what happened.
- The method returns `UNKNOWN`, not `FAILED`. Treating a timeout as a failure and charging again is how customers get billed twice.
- The safe next steps are to ask Payment for the order's status, or to resend with an [idempotency key](card:idempotency) so Payment can recognise a repeat. You will see both later.

## Common mistakes

- **"Both services are up, so the call between them will succeed."** The network between them can still drop or delay the call, which is a partial failure.
- **"Traffic inside our own network is safe, so it needs no encryption."** That is the "network is secure" fallacy; internal calls are encrypted and authenticated too.

## Interview Qs

### What are the fallacies of distributed computing?

Eight false beliefs: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology does not change, there is one administrator, transport cost is zero, and the network is homogeneous. Each one leads to a design rule, such as timeouts for the first.

### A payment call timed out. Was the customer charged?

You cannot know: the request may have been lost, or processed with only the reply lost. Ask the Payment service for the status, or retry with the same idempotency key, before charging again.

### What happens if one service goes down?

Its callers see errors or timeouts, and threads waiting on it can pile up and spread the failure to them. Use timeouts, bounded retries, circuit breakers and a fallback where it is safe, and monitor each dependency. Not every failure can be hidden from the user.
