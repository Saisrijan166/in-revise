## What it is

Event-driven architecture (EDA) is a style in which services work together by publishing and reacting to events. An event is a record of something that already happened, such as OrderCreated. The service that publishes it is the producer, and the services that receive it are consumers. Events travel through a message broker, the middleman you met in [asynchronous communication](card:sync-and-async-communication).

## Why it exists

Without events, Order Service would call Inventory, Notification and every future service itself after each order. It would need to know all of them, wait for all of them, and fail when one is down, and every new feature would change Order Service. With an event, Order Service announces the order once. Each interested service reacts in its own time, and a new one joins without touching the producer.

## How it works

  chart={`flowchart LR
  O[Order Service] -- OrderCreated --> B[[Broker]]
  B --> I[Inventory Service]

/>

1. A customer places an order. Order Service saves it in its own database, publishes OrderCreated to the broker, and answers the customer without waiting for anyone.
2. The broker stores the event and delivers a copy to every service that subscribed to it.
3. Inventory Service reserves stock, and Notification Service emails "order received". Each works at its own pace, and one being down does not stop the other.
4. Months later a Loyalty service subscribes to the same event. Order Service is not changed or redeployed.

So the key is: the producer states what happened, and each consumer decides what it means for it.

## Example

Order Service publishes this OrderCreated event for a ₹500 order:

```json
{
  "eventId": "7f3c2a9e-1b4d-4c55-9a0e-2d6f8b1e4c07",
  "type": "OrderCreated",
  "version": 2,
  "occurredAt": "2026-10-21T10:15:00Z",
  "correlationId": "req-81f2",
  "orderId": "ord-456",
  "totalInr": 500,
  "currency": "INR"
}
```

What to notice:

- `eventId` is unique per event, so a consumer can spot the same event delivered twice. You will use it in [delivery guarantees](card:delivery-guarantees).
- The event carries `totalInr`, so Notification can write "₹500 paid" without calling Order Service. This style is event-carried state transfer. An event with only `orderId` is event notification, and every consumer must call back for details.
- Version 2 added `currency`. Version 1 consumers ignore the unknown field and keep working. Renaming `totalInr` instead would break them.
- `correlationId` ties the event to the request that caused it, so a trace can follow the order across services.

## Rules and defaults

- **Naming:** name events in the past tense (OrderCreated, PaymentFailed). An event reports a fact, so a consumer cannot refuse it.
- **Backward-compatible changes:** add optional fields; never rename a field or change its meaning. For a breaking change, publish a new version or event type and keep the old one until every consumer has moved. A schema registry can reject incompatible schema changes before they ship.
- **Consumers must cope with delivery:** an event can arrive late, more than once, or out of order, so a consumer must not assume it sees each event exactly once and in sequence.
- **Data copies are eventually consistent:** a service that keeps a local copy from events sees changes a little after the producer makes them.

## Not to be confused with

- **Command:** asks one service to do something, such as ReserveStock, and that service may refuse.
- **Event:** reports that something happened, such as OrderCreated, and any number of services may react.
- **[Event sourcing](card:event-sourcing):** stores one service's own state as a list of events. EDA is about services telling each other what happened, and works without event sourcing.

Rule: command = "please do this"; event = "this happened"; event sourcing = how one service stores its data.

## Interview Qs

### What is event-driven architecture, and when would you use it?

Services publish events, facts such as OrderCreated, to a broker, and other services subscribe and react. Use it when several services must react to the same change, when the producer should not wait for them, and when new reactions will be added later. Use a direct call when the caller needs an answer now.

### How do you change an event without breaking consumers?

Make only backward-compatible changes: add optional fields, and never rename a field or change its meaning. Consumers ignore fields they do not know. For a breaking change, publish a new version or a new event type alongside the old one, and retire the old one after all consumers have moved. A schema registry can enforce these rules.

### What are the downsides of event-driven design?

The end-to-end flow is not written in any one codebase, so you need tracing and good naming to follow it. Data copied by events is eventually consistent. Consumers must handle late, repeated and out-of-order events, and you need a broker to run and monitor.
