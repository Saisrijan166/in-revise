## Why it exists

If Order Service had to call Inventory, Payment and Notification itself, it would break whenever one is down. Publishing one event lets each service react independently.

## How it works

<Compare id="command-vs-event" />

- **Event notification**: the event carries ids; a consumer calls back for details.
- **Event-carried state transfer**: the event carries the data, so consumers keep a local copy.
- The event passes through a [message broker](card:message-brokers); put a correlation id in it so traces connect.

## Example

```json
{
  "eventId": "7f3c2a9e-1b4d-4c55-9a0e-2d6f8b1e4c07",
  "type": "OrderCreated",
  "version": 2,
  "occurredAt": "2026-10-20T10:15:00Z",
  "orderId": "ord-456",
  "totalInr": 1499.00,
  "currency": "INR"
}
```

Version 2 added `currency` as a new field; version 1 consumers ignore it and keep working.

## Interview Qs

### What is the difference between an event and a command?

An event says something already happened, any number of services may listen, and it cannot be refused. A command asks one receiver to act, and the receiver may reject it.

### How do you change an event without breaking consumers?

Make backward-compatible changes: add optional fields, never rename or change meaning. For a breaking change publish a new version or topic, and let consumers ignore fields they do not know. A schema registry can enforce this.

### What are the downsides of event-driven design?

The end-to-end flow is not visible in any one codebase, so you need tracing. Data in other services is eventually consistent, and consumers must handle late, repeated or out-of-order events.
