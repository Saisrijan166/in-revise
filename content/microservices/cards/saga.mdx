## What it is

A saga is one business transaction made of a sequence of local transactions, one per service. Each step commits in its own database and then triggers the next step with an [event](card:event-driven-architecture) or a command. If a step fails, the saga runs compensating transactions: business actions, such as releasing stock or refunding money, that undo the effect of the steps already done. It is the usual replacement for [two-phase commit](card:distributed-transactions) in microservices.

## Why it exists

Placing an order must reserve stock, charge ₹500 and confirm, across three databases. Two-phase commit would hold locks in all three while messages cross the network, and the broker may not support it. A saga gives up the single atomic commit. Each step commits at once, so no locks are held between services, and when something fails, new transactions bring the data back to a consistent state.

## How it works

1. Order Service saves the order with status PENDING and publishes OrderCreated through its [outbox](card:outbox-and-inbox).
2. Inventory Service reserves the stock in its own transaction and publishes StockReserved.
3. Payment Service tries to charge ₹500. The card is declined, so it publishes PaymentFailed.
4. Compensations run for the finished steps: Inventory releases the reserved stock, and Order Service marks the order CANCELLED.
5. On the success path, Order Service marks the order CONFIRMED, and Notification sends the confirmation.

So each step commits on its own, and a failure is repaired by new transactions, not by a rollback.

## Example

With orchestration, an orchestrator in Order Service reacts to each reply and decides the next command:

```java
@KafkaListener(topics = "payment-replies", groupId = "order-saga")
@Transactional
public void onPaymentReply(PaymentReply reply) {
    OrderSaga saga = sagas.findById(reply.orderId()).orElseThrow();
    if (reply.success()) {
        saga.confirm();                                   // order CONFIRMED
        commands.send("notification-commands", new SendConfirmation(saga.orderId()));
    } else {
        saga.startCompensation();                         // order CANCELLING
        commands.send("inventory-commands", new ReleaseStock(saga.orderId()));
    }
}
```

What to notice:

- The saga's state is saved in Order Service's database, so after a crash the orchestrator knows which step it reached.
- `commands.send` writes to the outbox in the same transaction, so a state change and its next command are never separated.
- On failure the orchestrator sends `ReleaseStock`, a compensating command. Nothing is rolled back automatically.
- The reply may arrive twice, so `confirm()` and `startCompensation()` must do nothing when the saga is already in that state.

## Rules and defaults

- **Three kinds of step:** compensable steps come first and can be undone; the pivot step is the point of no return; retryable steps come after it and must be idempotent. In the shop, the ₹500 charge is the pivot.
- **No isolation:** other requests can see in-between states, such as stock reserved for an order that will be cancelled. A semantic lock, such as the status PENDING, marks a record as part of an unfinished saga. Other countermeasures are updates that work in any order and re-reading a value before changing it.
- **Idempotent steps:** each step and each compensation may receive its message twice, so each must be safe to repeat.
- **Compensation is not erasure:** the cancelled order and the refund stay in the history. A refund is a new payment in the other direction, and some actions, such as a sent email, cannot be undone at all, so place them after the pivot.

## Not to be confused with

In orchestration, one orchestrator sends a command to each service and tracks the saga's state, so the flow is visible in one place. In choreography, there is no coordinator: each service reacts to the previous event and publishes its own, so the flow is spread across services. Rule: orchestration for complex or growing flows; choreography for a short flow with few services.

## Common mistakes

- **"The charge call timed out, so compensate."** A timeout means the result is unknown, and the ₹500 may have been taken. Retry with the same [idempotency key](card:idempotency), or ask Payment for the status, before deciding.
- **"Compensations always succeed."** They can fail too. Make them idempotent, retry them, and flag the saga for manual handling with an alert if they still fail.

## Interview Qs

### How do you handle a transaction across several services?

With a saga. Each service commits a local transaction and triggers the next step by an event or a command. If a step fails, compensating transactions undo the finished steps, such as releasing stock and cancelling the order. A local @Transactional cannot do this, because it covers only one database.

### Orchestration or choreography?

Orchestration: one orchestrator sends commands and stores the saga's state, which keeps complex flows clear and avoids cyclic dependencies, but it is one more component that can fail. Choreography: services react to each other's events with no coordinator; it suits short flows but becomes hard to follow and to test as it grows.

### What if a compensating step fails?

Compensations can fail too, so make them idempotent and retry them until they succeed. If they keep failing, mark the saga as needing manual action and raise an alert. Never assume the data fixed itself; monitoring sagas that are stuck is part of the design.

### How do you deal with the lack of isolation in a saga?

Use a semantic lock: a status such as PENDING tells other requests that the order is not final, so they can wait or refuse. Order the steps so the risky, irreversible ones come after the pivot, and re-read a value before changing it when another saga may have changed it.
