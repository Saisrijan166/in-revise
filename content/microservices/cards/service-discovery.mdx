## What it is

Service discovery is how one service finds the network address of another at the moment it calls it. An instance is one running copy of a service; Payment Service may run as three instances, each with its own IP address and port. A service registry is a live list of those instances. Callers use a stable service name, such as `payment-service`, and discovery turns it into the address of a healthy instance.

## Why it exists

With [horizontal scaling](card:scaling-services), instances start, stop, crash and multiply, and each new one gets a new address. If Order Service has `10.0.3.17:8080` written in its config, it breaks as soon as that instance is replaced, and it never uses the two extra instances added for a sale. Discovery keeps an up-to-date list, so callers always reach instances that exist now.

## How it works

<Compare id="client-side-vs-server-side-discovery" />

1. When a Payment instance starts, it is added to the registry. Either it registers itself (self-registration), or the platform registers it (third-party registration), as Kubernetes does.
2. While it runs, the instance sends heartbeats, small "I am alive" messages at a fixed interval, or the platform runs health checks on it.
3. An instance that stops renewing, or fails its health check, is removed from the list.
4. Order Service asks for `payment-service`. In client-side discovery, it gets the list and picks an instance itself; in server-side discovery, it calls a router, such as a Kubernetes Service, that picks for it.
5. The call goes to the chosen instance. Choosing well is [load balancing](card:load-balancing), the next concept.

## Example

Order Service calls Payment Service by name with Spring Cloud LoadBalancer and Eureka:

```java
@Configuration
class ClientConfig {
    @Bean @LoadBalanced                      // resolve service names through discovery
    RestClient.Builder restClientBuilder() { return RestClient.builder(); }
}

// In Order Service, with the builder injected:
PaymentStatus status = restClientBuilder.build().get()
        .uri("http://payment-service/payments/{id}", paymentId)  // a name, not a host
        .retrieve()
        .body(PaymentStatus.class);
```

What to notice:

- `payment-service` is a service name. For each call, Spring Cloud LoadBalancer looks up its instances in the registry and swaps the name for a real host and port.
- `@LoadBalanced` is what turns this on. Without it, the client would look up a host literally called `payment-service`, which fails outside Kubernetes.
- On Kubernetes you can leave it out: a Service named `payment-service` resolves through DNS, and the platform picks the instance (server-side discovery).
- By default the instance is picked in turn (round robin), as [load balancing](card:load-balancing) explains.

## Rules and defaults

- **Eureka heartbeat:** every 30 seconds by default (`eureka.instance.leaseRenewalIntervalInSeconds`, Spring Cloud Netflix 5.0). A new instance can take up to 3 heartbeats to become visible to callers.
- **Cached lists:** Eureka clients keep the registry in memory, and Spring Cloud LoadBalancer caches each instance list for 35 seconds by default. So a dead instance can still be picked for a short while; timeouts and retries must cover that.
- **A highly available registry:** run several Eureka servers. They replicate registrations to their peers.
- **Kubernetes names:** a Service gets the DNS name `payment-service.shop.svc.cluster.local`; inside the same namespace, `payment-service` alone works.

## Not to be confused with

Discovery answers "where are the instances of this service now?". [Load balancing](card:load-balancing) picks one of them for this call. The [API gateway](card:api-gateway) is the front door for outside clients, and it uses discovery to find the services it routes to. Rule: discovery finds, the load balancer chooses, the gateway lets outsiders in.

## Interview Qs

### Why not hardcode service IP addresses?

Instances are replaced, scaled and moved, so their addresses keep changing. A hardcoded IP breaks when its instance goes away and ignores new instances. A registry tracks the live ones, and callers use a stable service name instead.

### What happens if the registry goes down?

Clients keep their cached copy of the registry, so calls keep working for a while, but the copy grows stale: new instances are not seen and dead ones are not removed. That is why the registry runs as several nodes; Eureka servers replicate to their peers.

### Client-side or server-side discovery?

Client-side has one hop less and lets the caller choose smartly, but needs a discovery library in every language you use. Server-side keeps clients simple, since they call one name, but adds a router that must itself be highly available. On Kubernetes, server-side comes built in.
