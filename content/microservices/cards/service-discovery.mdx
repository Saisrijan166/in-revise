## Why it exists

Instances restart, scale out and move, and each gets a new address. A caller needs the current list of healthy instances, not an IP written in config last month.

## How it works

<Compare id="client-side-vs-server-side-discovery" />

- An instance that stops renewing, or fails its health check, drops out of the registry.
- On Kubernetes a Service gives a stable DNS name: [Containers and Kubernetes](card:containers-and-kubernetes).
- Choosing among the instances: [Load Balancing](card:load-balancing).

## Example

```java
@Bean @LoadBalanced                 // Spring Cloud LoadBalancer resolves names
RestClient.Builder restClientBuilder() { return RestClient.builder(); }

// "payment-service" is a service name, not a host: an instance is picked per call
PaymentStatus status = restClientBuilder.build().get()
        .uri("http://payment-service/payments/{id}", paymentId)
        .retrieve()
        .body(PaymentStatus.class);
```

## Interview Qs

### Why not hardcode service IP addresses?

Instances are replaced, scaled and moved, so addresses change all the time. A registry tracks the live ones, and callers use a stable service name.

### What happens if the registry goes down?

Clients cache registry data, so calls keep working for a while, but the cache grows stale. Run the registry as several nodes; Eureka servers replicate to their peers.

### Client-side or server-side discovery?

Client-side has fewer hops but needs discovery code in each language. Server-side keeps clients simple but adds a router that must be highly available. See the comparison above.
