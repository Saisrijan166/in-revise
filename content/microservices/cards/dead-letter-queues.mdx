## What it is

A poison message is a message that fails every time a consumer processes it, for example an OrderCreated whose items list is missing. A dead-letter queue (DLQ) is a separate queue or topic where such messages are parked after a fixed number of failed attempts, so the consumer can go on to the next message. In Kafka it is a dead-letter topic; in RabbitMQ it is a dead-letter exchange and the queue behind it.

## Why it exists

A Kafka partition is read in order. If Inventory retries a broken OrderCreated forever, every order behind it in that partition waits, and [consumer lag](card:kafka-fundamentals) keeps growing. If it drops the message instead, an order silently never gets its stock. Bounded retries plus a DLQ keep the partition moving and keep the bad message, with its error, for someone to fix and replay.

## How it works

An alert on orders-dlt leads to a fix and a replay."

1. Inventory's listener throws while processing a record from `orders`.
2. The error handler waits (backoff) and delivers the same record again, up to a set number of attempts. Errors that can never pass, such as unreadable data, skip the retries.
3. After the last failed attempt, a recoverer, the component that decides what happens to a record that has run out of attempts, publishes the record to `orders-dlt`, adding headers with the exception and the original topic, partition and offset.
4. The record's offset is committed, and the consumer moves on to the next record.
5. An alert on the dead-letter topic fires. A developer fixes the bug or the data and republishes the parked records to `orders`.

So the key is: retry what may pass, park what will not, and never leave the parked messages unattended.

## Example

Inventory Service retries twice, one second apart, then parks the record:

```java
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var toDlt = new DeadLetterPublishingRecoverer(template);   // orders -> orders-dlt
    var handler = new DefaultErrorHandler(toDlt, new FixedBackOff(1000L, 2L));
    handler.addNotRetryableExceptions(IllegalArgumentException.class);
    return handler;
}
```

What to notice:

- `FixedBackOff(1000L, 2L)` means two retries one second apart, so three attempts in all. During those seconds the partition waits.
- `DeadLetterPublishingRecoverer` publishes to `orders-dlt` in the same partition number, so the dead-letter topic needs at least as many partitions as `orders`.
- `IllegalArgumentException` goes to the dead-letter topic on the first failure, because bad data will fail the same way every time.
- Spring Boot applies this bean to its auto-configured listener container factory. Without the recoverer, failed records would only be logged.

## Rules and defaults

- **Spring for Apache Kafka 4.1 default:** `DefaultErrorHandler` uses `FixedBackOff(0, 9)`: 10 attempts with no delay, then it logs the record at ERROR level and skips it.
- **Not retried by default:** `DeserializationException`, `MessageConversionException`, `ConversionException`, `MethodArgumentResolutionException`, `NoSuchMethodException` and `ClassCastException` go straight to the recoverer. Add your own with `addNotRetryableExceptions`.
- **Blocking retries:** `DefaultErrorHandler` retries the record in place, so the records behind it wait, but order is kept.
- **Retry topics (non-blocking):** a failed record moves to delayed retry topics, such as `orders-retry-1000`, and then to `orders-dlt`. Later records continue at once, but Kafka's ordering for that topic is lost.
- **RabbitMQ 4.0+ quorum queues:** the delivery limit is 20 by default. After that, the message is dropped, or dead-lettered if a dead-letter exchange is configured.

## Not to be confused with

A transient failure, such as a timeout or a database restart, will pass if you wait, so you retry it with backoff, as in [timeouts and retries](card:timeouts-and-retries). A poison message fails the same way every time, so retrying it only wastes time and blocks the partition. Rule: transient = retry with backoff; poison = straight to the DLQ.

## Common mistakes

- **"Replaying the DLQ is safe because those messages never ran."** A message may have failed half-way, after some of its work was saved. Replay only to idempotent consumers.

## Interview Qs

### What is a poison message, and how do you handle it?

A message that fails every time, often because of bad data or a bug. Count the attempts, stop after a few, and move it to a dead-letter queue with the error so the consumer continues. Skip the retries for errors that cannot pass. Then alert, fix the cause and replay.

### Why not retry a failed Kafka message until it works?

A partition is read in order, so one stuck record holds back every record behind it, and lag grows without limit. Bound the retries, then dead-letter the record. If ordering does not matter for that topic, retry topics let later records continue while the failed one waits.

### How do you reprocess messages from a dead-letter queue?

First fix the cause: deploy the bug fix or correct the data. Then republish the parked messages to the original topic, with a small tool or job, and watch that they succeed. Consumers must be idempotent, because some messages may have been partly processed before they failed.
