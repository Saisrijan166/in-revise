## What it is

A service mesh is a layer of small network proxies that carries all calls between your services. A proxy is a program that receives a call and passes it on. In the classic design, each instance gets its own proxy, called a sidecar, running right beside it. All the proxies together form the data plane, and a separate control plane configures them from one place.

## Why it exists

Every service needs the same network features: mTLS (encryption where both sides prove who they are with certificates), retries, timeouts and metrics. With dozens of services in Java, Go and Python, each team builds these with a different library, unevenly, and changing a policy means redeploying every service. A mesh moves these features out of the app into the proxies, so they work the same in every language and change by configuration.

## How it works

1. Order app calls `http://payment-service` as usual. The call goes to its own sidecar, not straight onto the network.
2. The sidecar picks a Payment instance (load balancing), applies the timeout and retry policy, and records metrics.
3. It sends the call, encrypted with mTLS, to Payment's sidecar; both proxies prove their identity with certificates.
4. Payment's sidecar checks the access policy, decrypts the call and hands it to Payment app on the same host.
5. Meanwhile, the control plane, such as istiod in Istio, sends routes, policies and certificates to every proxy.

## Example

Adding the shop's services to an Istio mesh on Kubernetes needs no change to their code:

```bash
# Istio: inject a sidecar proxy into every new Pod in the shop namespace
kubectl label namespace shop istio-injection=enabled

# Running Pods get a sidecar only when they are recreated
kubectl rollout restart deployment/order-service -n shop
```

What to notice:

- A Pod is the unit in which Kubernetes runs one instance; you will see it in [Containers and Kubernetes](card:containers-and-kubernetes). The label tells Istio to add a proxy to each new Pod in `shop`.
- Injection happens only when a Pod is created, which is why the restart is needed.
- After the restart, Order Service's calls to `payment-service` pass through the proxies and get mTLS and metrics, with no new code.

## Rules and defaults

- **Retries need idempotency:** Linkerd's docs say to use retries only on idempotent methods. A mesh that retries `POST /payments` can charge twice unless the endpoint uses an [idempotency key](card:idempotency).
- **Ambient mode:** since Istio 1.24 (GA), a mesh can run without sidecars. A per-node proxy (ztunnel) handles mTLS, and an optional waypoint proxy adds HTTP features such as retries.
- **The cost is real:** every proxy adds a hop of latency and uses CPU and memory, and the mesh is one more system to upgrade and debug.

## Not to be confused with

An [API gateway](card:api-gateway) handles calls coming into the system from outside clients; a service mesh handles calls between your own services. Libraries such as Spring Cloud LoadBalancer put network features inside each app, per language; a mesh puts them in proxies outside the app. Rule: gateway at the edge, mesh inside; library in the code, mesh beside it.

## Interview Qs

### What is the sidecar pattern?

A helper process or container deployed beside each app instance, sharing its life cycle: it starts and stops with the app. In a mesh, the sidecar is the proxy that all of the instance's traffic passes through, so the app gets network features without code.

### When is a service mesh not worth it?

For a few services, or a team that uses one language with good libraries, a proxy per instance costs more than it gives. Very latency-sensitive, chatty calls also suffer from the extra hops. It pays off with many services, several languages, or a firm requirement for mTLS everywhere.

### What is the difference between the data plane and the control plane?

The data plane is the set of proxies that actually carry every request. The control plane never touches requests: it tells the proxies what to do, sending them routes, retry policies and certificates.
