## What it is

An API gateway is a single entry point that sits between outside clients, such as a web app or a mobile app, and your services. Every client calls the gateway, and the gateway routes each request to the service that owns it, for example `/orders` to Order Service. On the way, it applies rules that every service would otherwise repeat, such as checking the login token and limiting how many requests a client may send. A Backend for Frontend (BFF) is a separate gateway for one kind of client.

## Why it exists

Without a gateway, the mobile app must know the address of Order, Payment and Inventory services, and each service must handle HTTPS, token checks and throttling on its own. When you split or move a service, every client has to change. A gateway gives clients one address and hides how the system is split, so services can change behind it. Shared rules live in one place, and one client call can be answered from several services.

## How it works

1. The mobile app sends `GET /orders/9001`, with its token, to the gateway's one public address.
2. The gateway ends the HTTPS connection (TLS termination), checks the token and the client's rate limit. A failed check is answered at once, for example with `401` or `429 Too Many Requests`.
3. It matches the path to a route: `/orders/**` belongs to Order Service.
4. It forwards the request to a running instance of Order Service and passes the reply back to the client.
5. For a screen that needs data from several services, it can call them all and combine the results into one response. This is called aggregation.

## Example

The shop's routes in Spring Cloud Gateway (Spring Cloud 2025.1):

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: orders
              uri: lb://order-service      # a service name, not a host
              predicates:
                - Path=/orders/**
            - id: payments
              uri: lb://payment-service
              predicates:
                - Path=/payments/**
```

What to notice:

- Each route maps a path pattern to a service: `/orders/9001` matches the first route, `/payments/77` the second.
- `lb://` means "a service name": the gateway asks [service discovery](card:service-discovery), the next concept, for a live instance. If none is found, it answers `503` by default.
- Clients never see `order-service`. You can split or move it and change only this file.
- The `spring.cloud.gateway.server.webflux` prefix dates from Spring Cloud 2025.0; older guides show `spring.cloud.gateway.routes`.

## Rules and defaults

- **No business logic:** prices, discounts and order rules stay in the service that owns them. The gateway does only routing and cross-cutting concerns, the jobs that every service shares.
- **Services still check access:** the gateway's token check is not enough; each service also checks its caller, as [Securing Microservices](card:microservices-security) shows later.
- **No way around it:** services must not be reachable from outside except through the gateway.
- **Several instances:** every request passes through the gateway, so run several instances behind a load balancer, or it is a single point of failure.

## Not to be confused with

A load balancer spreads requests over the instances of one service; it does not care about API paths or tokens. Service discovery is the internal address book that says where instances run right now. Rule: the gateway decides which service, discovery says where it runs, and the load balancer picks which instance.

## Interview Qs

### Why use a gateway if services already have APIs?

Clients get one address and an API shaped for them, instead of knowing every internal service. The gateway hides how services are split, so they can change freely, cuts round trips by aggregating calls, and applies TLS, authentication and throttling once instead of in every service.

### When would you use Backend for Frontend?

When web, mobile and partner clients need very different data or shapes. Each client type gets its own gateway, with an API made for it. One shared gateway would otherwise fill up with client-specific code that every team has to change.

### Can the gateway become a bottleneck?

Yes: every request passes through it. Size it for peak traffic, run several instances behind a load balancer, set timeouts towards the services, and keep it thin, with no business logic.
