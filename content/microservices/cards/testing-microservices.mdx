## Why it exists

Each service is tested alone, but bugs hide between services. A field renamed in Payment Service can pass every Payment test and still break Order Service.

## How it works

<Compare id="contract-vs-integration-vs-e2e-test" />

- Consumer-driven: the consumer writes the contract and the provider's build verifies it, with Pact for example.
- Spring Cloud Contract left the Spring Cloud release trains in July 2026; it continues as Stubborn Contract.
- Chaos engineering injects real failures to prove the resilience you designed.

## Example

```text
Contract written by Order Service tests:
  GET /payments/42  ->  200  { "paymentStatus": "PAID" }

Payment Service renames the field to "status".
Payment's build replays the contract:
  FAILED  body.paymentStatus is missing
The break is caught before deploy, not in production.
```

## Interview Qs

### Why use contract tests instead of end-to-end tests to catch API breaks?

Each side is checked alone, fast, in its own build, without deploying every service. End-to-end tests find the break later, run slowly and fail for unrelated reasons.

### What do you test beyond the happy path?

Timeouts, retries that cause duplicates, repeated or out-of-order messages, and a dependency that is down. Chaos engineering runs such experiments on purpose.
