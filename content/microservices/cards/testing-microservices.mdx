## What it is

Testing microservices means checking each service on its own, and also checking that the services still fit together. A unit test checks one class in memory, with its collaborators replaced by test doubles such as mocks. An integration test runs the service's code against real infrastructure, such as its PostgreSQL database. A contract test checks that a consumer, the service that calls an API, and a provider, the service that offers it, agree on that API. An end-to-end test drives a whole user journey across deployed services.

## Why it exists

Each team tests its own service, but many bugs live between services. If Payment Service renames the field `paymentStatus` to `status`, every Payment test still passes, and Order Service breaks in production. Running all services together for every change would find this, but such tests are slow and fail for unrelated reasons. A contract test catches the break in Payment's own build, in seconds.

## How it works

<Mermaid
  alt="The test pyramid. At the top, a few end-to-end tests: slow, across deployed services. In the middle, some integration tests and contract tests. At the base, many unit tests: fast, in memory."
  chart={`flowchart TB
  E["A few end-to-end tests: slow, across deployed services"]
  M["Some integration tests and contract tests"]
  U["Many unit tests: fast, in memory"]
  E --- M --- U`}

1. On every change, unit tests check the service's logic in memory in a few seconds.
2. Integration tests start real infrastructure, such as PostgreSQL or Kafka in a throwaway container with Testcontainers, and check SQL, mappings and messaging.
3. Order Service's tests record a contract: the requests it sends to Payment Service and the fields it reads from the answers.
4. Payment Service's build replays that contract against the real Payment code. If a field Order Service needs is missing, Payment's build fails before deploy.
5. After deploying to a test environment, a few end-to-end tests walk the key journeys, such as placing and paying for an order.

So each level catches what the level below cannot, and the higher the level, the fewer tests it has.

## Example

The contract that Order Service's tests record, and what happens when Payment Service renames a field:

```text
Contract written by Order Service tests:
  GET /payments/42  ->  200  { "paymentStatus": "PAID" }

Payment Service renames the field to "status".
Payment's build replays the contract:
  FAILED  body.paymentStatus is missing
```

What to notice:

- The contract is written from the consumer's side and holds only the fields Order Service really reads.
- The failure happens in Payment's build, before deploy, so the team that made the change sees it at once.
- Adding a new field would not fail: the provider may return fields that the contract does not mention. Only removing or renaming a field the consumer relies on breaks it.

## Rules and defaults

- **Consumer-driven:** the consumer writes the contract and the provider's build verifies it; Pact is a common tool for HTTP and messages.
- **Real infrastructure:** prefer Testcontainers with the real database or broker over an in-memory fake, which can behave differently.
- **Failure paths:** test timeouts, retries that cause duplicates, repeated or out-of-order messages, and a dependency that is down. Chaos engineering injects such failures on purpose to prove the resilience you designed.
- **Spring Cloud Contract:** in July 2026 Spring announced it is removed from future Spring Cloud release trains; it continues as Stubborn Contract, led by its original author.

## Not to be confused with

A contract test checks that two services agree on one API, each side in its own build. An integration test checks one service against its real database or broker. An end-to-end test checks a whole journey across many deployed services. Rule: contract = do we agree; integration = do I work with my infrastructure; end-to-end = does the journey work.

## Interview Qs

### Why use contract tests instead of end-to-end tests to catch API breaks?

Each side is checked alone, fast, in its own build, without deploying every service. The team that breaks the API finds out at once. End-to-end tests find the break later, run slowly and often fail for unrelated reasons.

### What is consumer-driven contract testing?

The consumer records its expectations: the requests it sends and the fields it reads. The provider's build replays them against the real provider code. The provider may change anything that no consumer relies on, and learns at once when a change would break one.

### What do you test beyond the happy path?

Timeouts, retries that cause duplicates, repeated or out-of-order messages, and a dependency that is down. Chaos engineering runs such failures on purpose in a running system to check that timeouts, retries and circuit breakers really work.
