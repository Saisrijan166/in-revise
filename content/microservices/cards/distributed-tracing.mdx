## What it is

Distributed tracing records the journey of one request through all the services it touches. The record is called a trace. A trace is made of spans: a span is one timed step, such as the Order Service handling a call, with a start, an end and a parent span. All spans of one request share one trace ID. OpenTelemetry is the open standard and set of libraries most services use to create and send this data.

## Why it exists

A checkout takes 1.6 seconds, and the cause could be in any of four services. [Logs and metrics](card:observability) from each service show that service alone; they cannot tell you which call waited on which, or how long each took. A trace puts all the calls of that one request in one picture, in order and with their times, so the slow hop is plain to see.

## How it works

<Mermaid

  chart={`flowchart TD
  G["Gateway 1,640 ms (root span)"] --> O["Order Service 1,610 ms"]

/>

1. The gateway receives the checkout, creates a new trace ID and starts the root span.
2. When it calls the Order Service, it adds a `traceparent` header holding the trace ID and its own span ID.
3. The Order Service reads the header and starts a child span with the same trace ID and the gateway span as its parent. It does the same for its calls to Inventory and Payment.
4. Each service sends its finished spans to a tracing backend, often through the OpenTelemetry Collector, which receives, processes and forwards the data.
5. The backend groups spans by trace ID and draws the tree. A parent span includes its children's time, so you look for the deepest slow span.

## Example

The header the Order Service sends to the Payment Service, and the Spring Boot code that makes it happen.

```text
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
```

```java
@Configuration
class PaymentClientConfig {
    @Bean
    RestClient paymentClient(RestClient.Builder builder) {   // Boot's builder: adds tracing
        return builder.baseUrl("http://payment-service").build();
    }
}
```

What to notice:

- The header has four parts: version `00`, the 32-character trace ID, the 16-character ID of the calling span, and flags `01`, meaning "sampled".
- The `RestClient.Builder` parameter is the one Spring Boot auto-configures, so every call through this client adds the header.
- Replace it with `RestClient.create("http://payment-service")` and the header is not sent. Payment then starts a new trace, and the checkout splits in two.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| `management.tracing.sampling.probability` | 0.1 (10% of traces kept) | Spring Boot 4.1 |
| Propagation format it sends | W3C (`traceparent`) | Spring Boot 4.1 |

- **Clients:** build `RestClient`, `RestTemplate` and `WebClient` from Boot's auto-configured builders; clients made without them do not propagate traces.
- **Libraries:** Spring Boot 4.1 traces through Micrometer Tracing, over OpenTelemetry (`spring-boot-starter-opentelemetry`) or Brave.
- **Head sampling** decides at the start of a trace, which is cheap. **Tail sampling** decides after the trace ends, so it can keep every trace with an error, but a component must store all the spans until it decides.

## Interview Qs

### Why does a trace split in two at the Payment Service?

The Order Service did not forward the trace context on that call, so Payment saw no `traceparent` header and started a new trace. A common cause in Spring Boot is a `RestClient` built by hand instead of from the auto-configured builder.

### What is OpenTelemetry?

A vendor-neutral open-source project with APIs, SDKs, a wire protocol (OTLP) and a Collector for traces, metrics and logs. It produces and sends telemetry but is not a backend: you send the data to a tool such as Jaeger, Prometheus or a vendor's service.

### Head sampling or tail sampling?

Head sampling decides at the first span, for example "keep 10%", so it is cheap but may drop the one failing request. Tail sampling waits until the trace is complete and can keep all errors and slow traces, but the component that decides must store large amounts of span data and is harder to run.
