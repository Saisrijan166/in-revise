## Why it exists

URLs, pool sizes and passwords differ per environment. Baking them into code means a rebuild for each environment and credentials in Git.

## How it works

<Mermaid
  alt="One build, order-service 1.4.2, is promoted to test and to production. A config source (environment variables, a ConfigMap or a config server) supplies settings to both. A secret manager supplies the rotated database password to production."
  chart={`flowchart LR
  B[One build: order-service 1.4.2] --> T[Test]
  B --> P[Prod]
  C[(Config: env vars, ConfigMap or config server)] --> T
  C --> P
  V[(Secret manager)] -- "DB password, rotated" --> P`}
/>

- On Kubernetes a [ConfigMap](card:kubernetes-configmap) and a [Secret](card:kubernetes-secret) are built in; Spring Cloud Config adds one Git-backed source for all services.
- A secret manager can also issue short-lived credentials, so nothing long-lived leaks.

## Example

```properties
# application.properties: no real values in the repo
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
payment.timeout=${PAYMENT_TIMEOUT:2s}
```

## Interview Qs

### Config server or Kubernetes ConfigMaps?

On Kubernetes, ConfigMaps and Secrets need no extra service. A config server such as Spring Cloud Config gives every service one Git-backed source with history, and can read secrets from Vault.

### How do you handle secrets in microservices?

Never in code or images. Keep them in a secret manager, give each service only its own, inject them at runtime, rotate them, and never log them.

### Why promote the same artifact instead of rebuilding per environment?

A rebuild can pick up different code or dependencies, so what you tested is not what you ship. Twelve-Factor keeps build, release and run apart; only the config differs.
