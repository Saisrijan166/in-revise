## What it is

An operation is idempotent when doing it twice has the same effect as doing it once. "Set order 9001 to PAID" is idempotent; "charge ₹500" is not, because a second run charges again. An idempotency key is a unique id that the client sends with a request, so the server can tell a repeat from a new request. Together they make a retry, sending the same request again after a failure, safe.

## Why it exists

Order Service sends "charge ₹500" to Payment Service, and the reply is lost on the network. Order Service cannot tell whether the request never arrived or the charge succeeded and only the reply was lost (the [unknown outcome](card:distributed-systems-fallacies)). If it does not retry, a paid order may stay unpaid; if it retries a plain POST, the customer may pay ₹1,000. With an idempotency key, Payment Service recognises the retry and returns the first result, so the customer pays once.

## How it works

1. The client creates a unique key, such as a UUID, for one business action and sends it in the `Idempotency-Key` header. Every retry of that action reuses the same key.
2. Before doing any work, the server tries to insert the key into a table whose key column is unique.
3. If the insert succeeds, the key is new: the server charges, stores the result next to the key, and answers `201 Created`.
4. If the key already exists and the first request has finished, the server returns the stored result without charging again.
5. If the first request is still running, it answers `409 Conflict`; if the same key arrives with a different body, it answers `422`.

So the key is: the database's unique constraint, not an `if` in the code, decides which request is first.

## Example

Payment Service's key table in PostgreSQL 18, with the first request and its retry:

```sql
CREATE TABLE idempotency_keys (
  idem_key     text PRIMARY KEY,   -- unique: the same key cannot be stored twice
  request_hash text NOT NULL,      -- spots the same key sent with a different body
  response     jsonb               -- filled in when the charge finishes
);

-- The first request
INSERT INTO idempotency_keys (idem_key, request_hash)
VALUES ('5f1c9a2e-7b3d-4c1a-9e0f-2a6b8c4d1e7f', 'sha256:ab12')
ON CONFLICT (idem_key) DO NOTHING;
-- The retry, with the same key
INSERT INTO idempotency_keys (idem_key, request_hash)
VALUES ('5f1c9a2e-7b3d-4c1a-9e0f-2a6b8c4d1e7f', 'sha256:ab12')
ON CONFLICT (idem_key) DO NOTHING;
```

```text output
CREATE TABLE
INSERT 0 1
INSERT 0 0
```

What to notice:

- `INSERT 0 1` means one row was inserted: the key is new, so go on and charge. `INSERT 0 0` means a repeat: read `response` and return it instead of charging.
- `PRIMARY KEY` makes the column unique, so even two copies that arrive at the same moment cannot both insert.
- `request_hash` lets the server reject the same key with a different body (`422`), which usually means a client bug.
- Without the unique constraint, two racing retries could both find "no key yet" and both charge.

## Rules and defaults

- **Not a standard yet:** the `Idempotency-Key` header is an IETF draft (draft-07, expired April 2026), not an RFC. Payment providers such as Stripe use it.
- **Key lifetime:** delete old keys after a window you publish; Stripe (API v1) may remove keys once they are at least 24 hours old.
- **Prefer natural idempotency:** absolute updates ("set status to PAID") are safe to repeat; relative ones ("add ₹500") need a key.
- **Pass it on:** when Payment Service calls an outside payment provider, it sends that provider an idempotency key too, if the provider supports one.
- **Messages too:** a consumer can receive the same message twice; [Delivery Guarantees](card:delivery-guarantees) applies the same idea there.

## Not to be confused with

Deduplication recognises a repeat by its id and skips it, so it needs a stored record of the ids already handled. Idempotency is the property that a repeat does no extra harm, which some operations have by nature. An idempotency key is deduplication used to make a POST idempotent. Delivery guarantees, such as at-least-once, describe how often a message may arrive; idempotency is how the receiver survives the repeats. Rule: idempotency is the goal; deduplication is one way to reach it.

## Common mistakes

- **"A new key for every attempt."** The server then sees each retry as a new payment. Create the key once per business action and reuse it.
- **"Store the key after charging."** If the service crashes between the charge and the insert, the retry finds no key and charges again. Insert the key first.

## Interview Qs

### How do you prevent duplicate payment processing?

The client sends an Idempotency-Key with the payment request. Payment Service inserts the key under a unique constraint before charging, stores the payment status with it, and returns the saved result to any retry. It also passes a key to the external payment provider, if supported, so that call cannot charge twice either.

### Is POST idempotent?

Not by definition: two identical POSTs may create two orders. You make a POST endpoint idempotent with an idempotency key, or design the create as a PUT to a URL the client chooses, such as `PUT /orders/{client-generated-id}`.

### How long should you keep idempotency keys?

Longer than any client will keep retrying, and publish that window. Stripe (API v1) may remove keys once they are at least 24 hours old. A retry after the window is treated as a new request, so clients must not retry past it.
