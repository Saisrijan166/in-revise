## Why it exists

Networks drop replies. The client cannot tell "never arrived" from "done, reply lost", so it retries, and a non-idempotent POST could charge ₹2,499 twice.

## How it works

<Mermaid
  alt="A POST to /payments arrives with an Idempotency-Key. If the key is new, the server inserts it, charges and stores the result, then answers 201 Created. If the key was seen and the first request finished, it returns the saved result. If the first request is still running, it answers 409 Conflict. If the same key comes with a different body, it answers 422 Unprocessable Content."
  chart={`flowchart TD
  R([POST /payments + Idempotency-Key]) --> K{Key seen?}
  K -- new --> S[Insert key, charge, store result]
  S --> A([201 Created])
  K -- "seen, finished" --> SAVED([Return the saved result])
  K -- "seen, still running" --> C([409 Conflict])
  K -- "seen, different body" --> U([422 Unprocessable Content])`}
/>

- Prefer natural idempotency: "set status = PAID" is safe to repeat; "add ₹500" is not.
- Purge old keys after a published window; Stripe keeps them at least 24 hours.
- Messages need the same idea on the consumer side: see [Delivery Guarantees](card:delivery-guarantees).

## Interview Qs

### How do you prevent duplicate payment processing?

The client sends an Idempotency-Key. Payment Service saves the key and payment status under a unique constraint, returns the saved result on a retry, and passes a key to the payment provider too, if it supports one.

### Is POST idempotent?

Not by definition: two POSTs may create two orders. You make a POST endpoint idempotent with an idempotency key, or by creating with PUT on a client-chosen URI.

### Is idempotency the same as deduplication?

No. Deduplication spots a repeat by its id and skips it; idempotency makes the repeat harmless. See [Idempotency vs Deduplication](compare:idempotency-vs-deduplication).
