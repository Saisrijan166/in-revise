## Why it exists

One noisy client or a sudden spike can use all the capacity. Limits keep a fair share per client and protect services before they fall over.

## How it works

<Mermaid
  alt="A client calls the API gateway, which checks the client's limit. Over the limit, the gateway answers 429 with Retry-After. Under the limit, the request goes to the Order service. If the Order service is overloaded, it sheds low-priority requests with 503; otherwise it calls its database."
  chart={`flowchart LR
  C[Client] --> G{"Gateway: under the client's limit?"}
  G -- no --> R1["429 + Retry-After"]
  G -- yes --> S{"Order service overloaded?"}
  S -- "yes, low priority" --> R2["503: shed"]
  S -- no --> DB[(Database)]`}
/>

- Enforce per-client limits at the [API gateway](card:api-gateway), before work reaches the services.
- Shedding keeps the server alive by doing less, for example rejecting work above a cap on requests in flight.

## Example

```text
GET /orders?page=1 HTTP/1.1
X-API-Key: shop-mobile-app

HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Limiter | Redis token bucket, keyed by the user's principal; answers 429 | Spring Cloud Gateway 5.0 `RequestRateLimiter` |

## Interview Qs

### Rate limiting vs load shedding?

A rate limit looks at one client: has it sent too much? Load shedding looks at the server: is it overloaded? Then it drops the least important work first, whoever sent it.

### How do you rate limit across ten gateway instances?

Keep the counters in a shared fast store such as Redis, so every instance sees the same count per client.
