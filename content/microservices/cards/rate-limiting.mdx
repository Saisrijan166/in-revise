## What it is

Rate limiting caps how many requests one client may send in a period of time, such as 10 per second per API key. Requests over the cap get HTTP 429 Too Many Requests, usually with a `Retry-After` header that says how long to wait. Load shedding is the server-side partner: when a server is close to overload, it drops its least important work, whoever sent it. Both usually start at the [API gateway](card:api-gateway), before work reaches the services.

## Why it exists

One buggy mobile app retrying in a loop, or one big customer running a batch job, can use all of Order's capacity, and every other customer gets slow pages. Without limits the service falls over first and recovers later. A limit per client keeps a fair share for each one. Shedding keeps the server alive by doing less, instead of doing everything badly.

1. A request reaches the gateway, which works out the key: who is counted, such as the user, the API key or the IP address.
2. The gateway checks that key's token bucket in a shared store such as Redis. The bucket refills at a steady rate, and each request takes one token.
3. If a token is left, the request goes on to the Order service. If not, the gateway answers 429 with `Retry-After` at once.
4. Inside Order, if the number of requests in flight passes its own cap, Order sheds low-priority work with 503 Service Unavailable.
5. A well-behaved client waits as long as `Retry-After` says, then retries with [backoff](card:timeouts-and-retries).

So the key is: a rate limit protects fairness between clients; shedding protects the server itself.

## Example

The gateway's limit for the shop's mobile app, followed second by second, and the answer a rejected request gets:

```text
Limit for API key shop-mobile-app: bucket holds 20 tokens, refills 10 per second

t = 0 s   bucket full (20); 25 requests arrive -> 20 pass, 5 get 429
t = 1 s   10 new tokens;    10 requests arrive -> all 10 pass

HTTP/1.1 429 Too Many Requests
Retry-After: 1
```

What to notice:

- The bucket size (20) is the largest burst that can pass at once; the refill rate (10 per second) is the steady limit after that.
- The 5 rejected requests did no work in Order at all. The limit stopped them at the gateway.
- `Retry-After: 1` tells the app to wait one second, when new tokens will be there, instead of retrying at once in a loop.

## Rules and defaults

- **Spring Cloud Gateway 5.0 `RequestRateLimiter`:** answers 429 by default when a request is not allowed. The default key is the logged-in user's name (`PrincipalNameKeyResolver`), and if no key is found the request is denied by default.
- **Its Redis rate limiter is a token bucket:** `replenishRate` is tokens added per second, `burstCapacity` is the bucket size, and `requestedTokens` is the cost of one request (default 1).
- **Algorithms:** besides the [token bucket](card:token-bucket), there are the leaky bucket and fixed or sliding windows; the tree lists how they differ.

## Not to be confused with

A rate limit looks at one client: has this client sent too much? Load shedding looks at the server: is it overloaded? Then it drops the least important work first, whoever sent it. A [bulkhead](card:bulkhead) is different again: it caps a service's outgoing calls to one dependency. Rule: rate limit = per client, for fairness; load shedding = per server, for survival; bulkhead = per dependency, for isolation.

## Interview Qs

### How do you rate limit across ten gateway instances?

Keep the counters in a shared fast store such as Redis, so every instance sees the same count for a client. With counters in each instance's memory, a client could get ten times its limit by spreading requests across instances.

### What should a client do when it gets a 429?

Stop and wait as long as `Retry-After` says. If there is no header, back off with jitter before retrying. Retrying at once only spends more of its limit and adds load.

### Why use a token bucket instead of a fixed window?

A token bucket allows short bursts up to the bucket size and then a smooth steady rate. A fixed window resets its counter each period, so a client can send a full window's worth just before and just after the reset, twice the limit in a moment.
