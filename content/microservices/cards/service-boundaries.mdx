## Why it exists

A wrong split costs more than no split: services that must change together still need joint releases, now with network calls between them.

## How it works

| Check | Good sign | Bad sign |
|---|---|---|
| Responsibility | One business capability | A technical layer |
| Calls | Few, coarse calls | Chatty: many calls per operation |
| Release | Deploys alone | Must deploy with others |
| Data | Owns its tables | Reads another service's tables |
| Team | One small team owns it | Many teams edit it |

- Start from a bounded context; a service should not span two of them.
- Aggregates and domain services are the usual candidates; then adjust for scale, security and team size.
- Shared tables break this; see [database per service](card:database-per-service).

## Example

```text
Order service       orders, order status        -> orders DB
Payment service     payment attempts, refunds   -> payments DB
Inventory service   stock, reservations         -> inventory DB
"Product" in Catalog = name, price, photos
"Product" in Inventory = SKU, quantity per warehouse
```

## Interview Qs

### How do you identify service boundaries?

Model the domain with DDD: find subdomains and bounded contexts, then aggregates. Map each capability to a service that owns its data. Validate: one responsibility, no chatty calls, deploys alone, small owning team.

### What is a distributed monolith?

Services that are separate at runtime but tightly coupled: they share tables, or a change in one forces lockstep changes and deploys in others. You pay network costs and get none of the independence.

### What is a bounded context?

A boundary inside which one domain model and its terms are consistent. The same word, like "Product", can mean different things in two contexts, and each context keeps its own model.
