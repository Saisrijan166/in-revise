## What it is

A fallback is the answer a service gives when a call to a dependency cannot succeed: cached data, a default value, or a clear error. Graceful degradation is the plan behind it: when a part fails, the core features keep working and the extras switch off. A soft dependency is one a feature can live without, like reviews on a product page. A hard dependency, like Payment for a purchase, cannot be replaced.

## Why it exists

[Retries](card:timeouts-and-retries) and [circuit breakers](card:circuit-breaker) decide when to stop calling; they do not say what to show the user. Without a plan, an outage of a small service such as Reviews turns the whole product page into an error page, and the shop loses sales over a feature nobody needed in order to buy. With a fallback per feature, the page loads without reviews and the order still goes through.

## How it works

| Shop feature | Its dependency fails | Degrade to |
| --- | --- | --- |
| Product page stock label | Inventory service | "Stock is checked at checkout" |
| Product page reviews | Review service | Show the page without reviews |
| Order confirmation email | Notification service | Queue it; send when it is back |
| Payment | Payment service | A clear error or "payment pending", never "paid" |

1. For each feature, mark every dependency as soft or hard.
2. For a soft dependency, pick a fallback: hide the section, show cached or default data, or queue the work for later.
3. Run the fallback when retries run out, the breaker is OPEN, or the [bulkhead](card:bulkhead) is full.
4. For a hard dependency, fail clearly or accept the work as pending; never pretend it succeeded.
5. Alert when instances serve degraded answers, so nobody mistakes degraded for healthy.

## Example

The product page asks Inventory for a stock label and falls back to a safe text when the call fails or the breaker is OPEN:

```java
@CircuitBreaker(name = "inventory", fallbackMethod = "stockUnknown")
public StockLabel stockLabel(String sku) {
    int left = inventory.stock(sku);                         // remote call to Inventory
    return new StockLabel(left > 0 ? left + " in stock" : "Out of stock");
}

// same parameters plus the exception, same return type
private StockLabel stockUnknown(String sku, Exception e) {
    return new StockLabel("Stock is checked at checkout");   // the page still loads
}
```

What to notice:

- `fallbackMethod` names a method in the same class. Resilience4j calls it with the original arguments plus the exception, so the signature must match, with one extra exception parameter.
- The parameter type `Exception` catches every failure, including the `CallNotPermittedException` thrown while the breaker is OPEN, so the page never waits on a dead service.
- The fallback is honest: it does not claim stock exists. Checkout still makes the real reservation, a hard dependency, and fails clearly if Inventory is down.

## Rules and defaults

- **Keep fallback code simple:** AWS advises that failure paths be tested and much simpler than the main path; complex fallbacks fail in ways nobody has seen.
- **Avoid fallbacks that add load:** if every server falls back to the database when the cache fails, the database gets the whole load at once.
- **Correctness first for money:** for payment processing, consistency matters more than staying available.

## Not to be confused with

A retry repeats the same call, hoping a brief fault has passed. A fallback gives a different answer once the call cannot succeed. Rule: retry first, fall back last.

## Interview Qs

### When should you avoid a fallback?

When a wrong answer costs more than an error, as with payments and other transactions. Also when the fallback itself adds load, such as every server hitting the database once the cache fails, or when it is so rarely run that it is likely broken.

### Is it safe to show stale cached data?

It depends on the feature. A product description or reviews from an hour ago are fine. A price or stock level at checkout is not, because the customer acts on it. Decide per feature, and mark stale data where users could be misled.

### What happens to writes while a dependency is down?

For soft work, such as a confirmation email, accept the request and buffer it in a queue until the dependency is back. For hard work, such as a payment, either fail clearly or record it as pending and finish it later, so the customer is never told something false.
