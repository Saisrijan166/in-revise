## What it is

Spring Boot is the Java framework that turns one service into a stand-alone program, with an embedded web server, sensible defaults, and health and metrics endpoints. Spring Cloud is a family of projects on top of Spring Boot that add what a system of many services needs: a gateway, service discovery, central configuration, client-side load balancing and circuit breakers. Every service is one Spring Boot app; you add Spring Cloud projects one by one, only where you need them.

## Why it exists

Every service needs the same plumbing: an HTTP API, calls to other services, discovery, configuration, resilience and telemetry. If Order, Payment, Inventory and Notification each write it by hand, you get four slightly different, little-tested versions. Spring gives one tested library for each need, and Spring Boot's defaults wire it up, so each team writes business code instead of plumbing.

## How it works

| Need | Spring choice |
|---|---|
| [HTTP API](card:rest-apis) | Spring Web MVC, `@RestController` |
| Call another service | `RestClient`, `WebClient`, or an HTTP service client on top of them |
| [Edge gateway](card:api-gateway) | Spring Cloud Gateway (Server Web MVC or Server WebFlux) |
| [Discovery](card:service-discovery) | Eureka with Spring Cloud LoadBalancer, or Kubernetes Services |
| [Config](card:configuration-management) | Spring Cloud Config, or Kubernetes ConfigMaps |
| [Circuit breaker](card:circuit-breaker) | Resilience4j through Spring Cloud CircuitBreaker |
| [Kafka](card:kafka-fundamentals) | Spring for Apache Kafka: `KafkaTemplate`, `@KafkaListener` |
| [Health, metrics, traces](card:observability) | Spring Boot Actuator with Micrometer |

One order placed in a Spring-based shop:

1. The client's request reaches Spring Cloud Gateway, which routes `/orders/**` to Order Service.
2. Order Service, a Spring Boot app, handles it in a `@RestController`.
3. To reach Payment, it calls through a `RestClient` built from a `@LoadBalanced` builder; Spring Cloud LoadBalancer turns the name `payment-service` into one instance's address.
4. The call has a timeout and runs inside a Resilience4j circuit breaker, through Spring Cloud CircuitBreaker.
5. Order Service publishes `OrderPlaced` with `KafkaTemplate`, and Actuator with Micrometer reports health, metrics and traces.

## Example

Order Service declares Payment's API as a Java interface, an HTTP service client, and Spring builds the class that makes the HTTP call.

```java
interface PaymentApi {                                    // an HTTP service client
    @GetExchange("/payments/{orderId}")
    PaymentStatus status(@PathVariable long orderId);
}

@Bean
PaymentApi paymentApi(RestClient.Builder builder) {       // the @LoadBalanced builder
    var factory = new JdkClientHttpRequestFactory();
    factory.setReadTimeout(Duration.ofSeconds(2));        // never wait forever
    RestClient http = builder.baseUrl("http://payment-service")
            .requestFactory(factory).build();
    return HttpServiceProxyFactory.builderFor(RestClientAdapter.create(http))
            .build().createClient(PaymentApi.class);
}
```

What to notice:

- `PaymentApi` is only an interface. `HttpServiceProxyFactory` creates the object behind it, which sends `GET /payments/42` and turns the JSON answer into a `PaymentStatus`.
- The builder is the `@LoadBalanced` one from [service discovery](card:service-discovery), so `payment-service` is a service name, not a host.
- `setReadTimeout` makes a slow answer fail after 2 seconds. In a test against a server that waited 4 seconds, the call failed after about 2 s with a `ResourceAccessException`.
- This is the declarative style that OpenFeign offered, but built into Spring Framework, with no extra project.

## Rules and defaults

- **Versions:** Spring Cloud projects ship together as a release train, a set of versions tested together. Spring Cloud 2025.1 (Oakwood) works with Spring Boot 4.0 and 4.1 (4.1 from 2025.1.2). Pick the release train that matches your Boot version.
- **RestTemplate:** deprecated in Spring Framework 7.0 in favour of `RestClient`, and to be removed in a future version.
- **OpenFeign:** feature-complete since Spring Cloud 2022.0: bug fixes and small community changes only. Spring suggests HTTP service clients instead.
- **On Kubernetes:** Eureka and Config Server are optional; Kubernetes Services and ConfigMaps cover discovery and config, and Spring Cloud Kubernetes connects them to Spring's APIs.
- **Contract tests:** Spring Cloud Contract is no longer part of new release trains; see [Testing Microservices](card:testing-microservices) for where it went and for Pact.

## Not to be confused with

Spring Boot builds and runs one service: starters, auto-configuration, an embedded server and Actuator. Spring Cloud adds tools for many services that talk over a network, and each of its release trains matches certain Boot versions. Rule: Spring Boot for every service; a Spring Cloud project only for a distributed need you really have.

`RestClient` is the blocking client for new code, `WebClient` the non-blocking one for reactive apps, and OpenFeign an older declarative client that is feature-complete: Spring adds only bug fixes and small community changes.

## Interview Qs

### Which HTTP client would you use in a new Spring service?

`RestClient` for blocking code, usually behind an HTTP service client interface with `@GetExchange`, and `WebClient` in reactive apps. `RestTemplate` is deprecated in Spring Framework 7.0, and OpenFeign is feature-complete, so I would not start new code on either. Every client gets a timeout.

### Do you need Eureka on Kubernetes?

Usually not. Kubernetes Services already give each service a stable DNS name and spread calls over ready Pods. Spring Cloud Kubernetes plugs Spring's discovery and config APIs into the platform when code needs them.
