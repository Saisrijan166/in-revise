## What it is

Apache Kafka is a broker that stores messages, called records, in a log: an append-only list where each new record goes at the end and stays there after it is read. Records are grouped into topics, such as `orders`. Each topic is split into partitions, so several servers and consumers can work on it in parallel. A record's position in its partition is its offset.

## Why it exists

Many services need the same order events, in the right order for each order, and some join months later or must reprocess after a bug. A queue that deletes a message once it is acknowledged cannot give that. Kafka keeps the log, so each consumer group reads at its own pace and can rewind. Partitions spread one topic over several brokers, so throughput grows as you add them.

## How it works

1. Order Service sends a record to the topic `orders` with key = orderId. Kafka hashes the key to pick a partition, so every record of one order lands in the same partition.
2. The partition's leader broker appends the record at the next offset and copies it to follower replicas on other brokers. With the default `acks=all`, the producer gets its confirmation once all in-sync replicas, the copies that are fully caught up with the leader, have the record.
3. Payment Service runs two instances in the consumer group `payment`. Kafka gives each partition to exactly one of them: C1 reads P0 and P1, and C2 reads P2.
4. Each consumer reads its partitions in offset order and commits the offset it has reached, so after a restart it continues from there.
5. Notification Service, in its own group, reads all three partitions with its own offsets, unaffected by Payment.

So the key decides the partition, and order is kept only inside a partition.

## Example

Order Service sends with a key, and Payment Service joins a consumer group:

```java
// Order Service: the key (orderId) decides the partition
kafka.send("orders", event.orderId(), event);

// Payment Service: every instance joins the consumer group "payment"
@KafkaListener(topics = "orders", groupId = "payment")
public void onOrderCreated(OrderCreated event) {
    payments.charge(event.orderId(), event.totalInr());
}
```

What to notice:

- The second argument of `send` is the key. OrderCreated and OrderCancelled for `ord-456` share it, so they reach the same partition and are read in that order.
- Remove the key and records spread over partitions, so a consumer can see the cancel before the create.
- Every Payment instance uses `groupId = "payment"`, so they split the partitions between them. A different `groupId` would make a second, independent reader that gets every record.
- The partition count is the upper limit of useful consumers in one group.

## Rules and defaults

- **Durability:** a replication factor of 3 is a common production setting. The Kafka docs suggest `min.insync.replicas=2` with `acks=all`, so a write needs two copies; the default `min.insync.replicas` is 1. If too few replicas are in sync, the producer gets an error instead of a weak write.
- **One consumer per partition in a group:** extra consumers sit idle. Share groups (production-ready in Kafka 4.2) let several consumers read one partition and acknowledge each record on its own, for work-queue jobs where order does not matter.
- **Consumer lag:** the log-end offset minus the consumer's committed offset, per partition. Lag that keeps growing means consumers cannot keep up.
- **No ZooKeeper:** since Kafka 4.0, Kafka runs only in KRaft mode, where its own controller nodes keep the cluster metadata.

## Not to be confused with

A Kafka topic is not the same as a "topic" in the queue-or-topic sense. Inside one consumer group, Kafka acts like a queue: each record is handled by one instance. Across groups it acts like a topic: every group gets every record. Rule: same group = share the work; different groups = each gets a copy.

## Interview Qs

### How does Kafka keep order?

Only inside a partition. The producer sends records with the same key to the same partition, and one consumer in a group reads that partition in offset order. There is no order across partitions, so related events, such as all events of one order, must share a key.

### You add consumers but throughput does not grow. Why?

A consumer group gives each partition to exactly one consumer, so consumers beyond the partition count sit idle. Add partitions, keeping in mind that new partitions change which partition a key maps to. If order does not matter, a share group lets more consumers read the same partitions.

### What is consumer lag, and why watch it?

Lag is how far a consumer group is behind: the log-end offset minus its committed offset, per partition. Growing lag means consumers process slower than producers write, so events are handled later and later. It is the first metric to check when a consumer seems slow or stuck.
