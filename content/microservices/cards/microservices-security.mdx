## Why it exists

A monolith has one door to guard. Microservices make many network calls, so an attacker who gets inside can reach every service that trusts its neighbours.

## How it works

<Mermaid
  alt="The user logs in at the identity provider and gets a token. The user calls the API gateway with the bearer token; the gateway authenticates it and forwards the token to the Order Service, which checks its own rules. The Order Service calls the Payment Service over mTLS with a token, and the Payment Service also checks its rules."
  chart={`flowchart LR
  IdP[(Identity provider)] -. token .-> U([User])
  U -- "Bearer token" --> G[API gateway: authenticate]
  G -- token --> O[Order Service: authorise]
  O -- "mTLS + token" --> P[Payment Service: authorise]`}
/>

- Zero trust (NIST SP 800-207): network location grants nothing; each request is authenticated and authorised.
- A [service mesh](card:service-mesh) can add mTLS and rotate certificates without app code.
- Secrets live in a vault or the platform's secret store, never in code: see [Configuration and Secrets](card:configuration-management).

## Interview Qs

### How do services authenticate each other?

With mTLS, each service holds a certificate and both sides verify each other. Or the caller gets an OAuth client-credentials token and sends it; the callee validates it. Token calls still run over TLS.

### The gateway already checks tokens. Why check again in each service?

A call can bypass the gateway or come from a compromised service inside. Also, only the Order Service knows rules such as "user 42 may cancel only their own order".

### What is zero trust?

No implicit trust because a call comes from the internal network. Every request is authenticated and authorised, and you protect resources, not network segments.
