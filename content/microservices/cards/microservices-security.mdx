## What it is

Securing microservices means checking every call between the user and the services, and between the services themselves. Each check asks two questions: who is calling (authentication) and may they do this (authorisation). The caller usually proves who it is with a token: a signed string that a login server, the identity provider, hands out after login. Traffic between services is also encrypted, and passwords and keys are kept out of the code.

## Why it exists

A monolith has one door to guard: check the user once, and all code behind it is trusted. In the shop, an order now travels over the network from the [gateway](card:api-gateway) to the Order, Inventory and Payment services. If those services trust any call that comes from inside, one broken service, say Notification, can ask Payment to refund anything. Checking at each service limits the damage to the one service that was broken.

## How it works

1. The user logs in at the identity provider and receives a token.
2. The user's app sends the token with each call. The gateway rejects calls with no token or an invalid one.
3. The gateway forwards the call and the token. The Order Service validates the token again and checks its own rule, such as "users cancel only their own orders".
4. When the Order Service calls the Payment Service, it proves its own identity with a certificate over mTLS (mutual TLS, where both sides show a certificate) or with a service token. Payment checks that Order is allowed to charge.
5. Each service writes security events, such as a refused call, to an audit log, without the token itself.

So the key is: the gateway filters, but every service decides for itself.

## Example

The Order Service checks ownership before it cancels an order. The gateway cannot do this, because it does not know who owns order 1001.

```java
@PostMapping("/orders/{id}/cancel")
ResponseEntity<Void> cancel(@PathVariable long id, @AuthenticationPrincipal Jwt jwt) {
    Order order = orders.findById(id).orElseThrow();
    if (!order.customerId().equals(jwt.getSubject())) {   // user 42 may cancel only their own orders
        return ResponseEntity.status(HttpStatus.FORBIDDEN).build();
    }
    order.cancel();
    return ResponseEntity.noContent().build();
}
```

What to notice:

- Spring Security has already validated the token before this method runs; `@AuthenticationPrincipal Jwt` hands the method the validated token.
- `jwt.getSubject()` reads the `sub` claim, the user's ID. A valid token proves who the user is, not that this order is theirs.
- Remove the `if` and any logged-in user can cancel any order. The token check alone would still pass.

## Rules and defaults

- **Zero trust (NIST SP 800-207):** a call gets no trust from where it comes from on the network; each request is authenticated and authorised.
- **Edge and service checks:** coarse checks (valid token, right scope, a scope being a permission the token carries) can run at the gateway; business rules run in the service that owns the data.
- **Service identity:** with mTLS both sides present certificates, which proves identity and encrypts the traffic. A [service mesh](card:service-mesh) can add mTLS and rotate certificates without app code. The token option, the OAuth client credentials flow, comes in [the next concept](card:jwt-and-oauth).
- **Encryption:** use TLS for every network hop (in transit) and encrypt stored data (at rest).
- **Secrets:** keep passwords, keys and certificates out of code and out of browser-visible config; you will see where they go in [Configuration and Secrets](card:configuration-management).
- **Logs:** never log tokens, passwords or personal data.

## Not to be confused with

Authentication answers "who are you?": the token is valid, so this is user 42. Authorisation answers "may you do this?": may user 42 cancel order 1001? Rule: authentication gives an identity; authorisation is checked again for every action.

## Common mistakes

- **"HTTPS at the gateway is enough."** Traffic behind the gateway also crosses the network, so internal hops need TLS too, often as mTLS.
- **"One shared service account for every service."** If one service is broken, the attacker gets the rights of all. Give each service its own identity and only the rights it needs.

## Interview Qs

### How do services authenticate each other?

With mTLS, each service holds a certificate, and both sides check each other's certificate when the connection opens. Or the calling service gets an OAuth client-credentials token for itself and sends it; the receiving service validates it. Token calls still run over TLS, so the token cannot be read on the way.

### The gateway already checks tokens. Why check again in each service?

A call can bypass the gateway, or come from a service inside that an attacker has broken into. Also, only the service that owns the data knows its rules: only the Order Service knows that user 42 may cancel order 1001 but not order 1002.

### What is zero trust?

A security model in which no request is trusted because of where it comes from, such as the internal network. Every request is authenticated and authorised, access is the minimum needed, and you protect each resource rather than drawing one wall around the network.
