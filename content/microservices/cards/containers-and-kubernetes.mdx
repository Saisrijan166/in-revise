## What it is

A container is a service running as an isolated process, packed with everything it needs: the Java runtime, the libraries and the jar. It starts from an image, a read-only template that is built once and has a version, such as `order-service:1.4.2`. Kubernetes is a platform that runs containers on a group of machines, called a cluster. It keeps the number of copies you ask for and gives each service one stable address.

## Why it exists

Without containers, every server needs the right Java version and libraries installed by hand, so a service that works in test can fail in production. Without an orchestrator, someone must start three copies of Order Service on different machines, notice when one dies, start a new one and tell every caller the new address. Containers make a service run the same everywhere. Kubernetes does the starting, replacing and addressing for you.

## How it works

1. You build an image of the service, usually from a Dockerfile, and push it to a registry, a store for images.
2. You write a Deployment: the desired state, saying which image to run and how many copies (replicas).
3. Kubernetes starts that many Pods. A Pod is the smallest unit it runs: one or more containers that share one network address. The Deployment's ReplicaSet keeps the count right; if a Pod dies, it starts a new one.
4. A Service gives the Pods one stable name, such as `order-service`, and spreads calls over the Pods that are ready. Pods get a new address each time they are replaced, so callers use the name.
5. Traffic from outside the cluster enters through an Ingress or a Gateway, Kubernetes objects that route outside HTTP calls to Services, and a HorizontalPodAutoscaler can change the replica count when load grows.

So the key is desired state: you describe what should run, and Kubernetes keeps making reality match it.

## Example

The Order Service runs as three Pods behind one Service name.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-service }
spec:
  replicas: 3
  selector: { matchLabels: { app: order } }
  template:
    metadata: { labels: { app: order } }
    spec:
      containers:
        - name: order
          image: registry.example.com/order-service:1.4.2
```

```yaml
apiVersion: v1
kind: Service
metadata: { name: order-service }
spec:
  selector: { app: order }
  ports: [ { port: 80, targetPort: 8080 } ]
```

What to notice:

- `replicas: 3` is the desired state. Delete one Pod by hand and the ReplicaSet starts a replacement.
- The label `app: order` ties everything together: the Deployment finds its Pods by it, and the Service sends calls to every ready Pod that carries it.
- Other services call `http://order-service`. Port 80 on the Service is forwarded to port 8080 in the container.
- The image has a fixed version tag. Changing `1.4.2` to `1.4.3` starts a rolling update, which you will see in [Deployment Strategies](card:deployment-strategies).

## Rules and defaults

- **Service type:** `ClusterIP` by default, so the Service is reachable only inside the cluster (Kubernetes 1.37).
- **Ingress:** the Ingress API is frozen; Kubernetes recommends Gateway API for new setups. An Ingress does nothing without an Ingress controller installed.
- **Data:** the container's writable layer is deleted with the container. Keep data in a volume or a database.
- **Not Kubernetes' job:** it does not build your application, and it cannot see business errors such as a wrong order total. It restarts processes; [timeouts and retries](card:timeouts-and-retries) stay in your code.

## Not to be confused with

Docker is a tool that builds images and runs containers, usually on one machine. Kubernetes runs, scales and heals containers across a whole cluster, and since version 1.24 it uses runtimes such as containerd instead of Docker Engine; images built with Docker still run. Rule: Docker builds and runs a container; Kubernetes keeps many of them running.

## Common mistakes

- **Calling a Pod by its IP address.** Pods are replaced on every deploy and crash, and each new Pod gets a new IP. Call the Service name.

## Interview Qs

### What is the difference between a container and a virtual machine?

A container is an isolated process that shares the host's operating system kernel, so it is small and starts in seconds. A virtual machine emulates hardware and runs its own full operating system, so it is heavier and slower to boot.

### What do a Pod, a Deployment and a Service do?

A Pod runs one or more containers with one network address. A Deployment declares which image and how many Pods, and replaces them on failure or on a new version. A Service gives those changing Pods one stable name and spreads calls over the ready ones.

### If Kubernetes restarts failed Pods, why do we still need resilience patterns?

A restart fixes a crashed process, not a slow dependency or a wrong result. Callers still need timeouts, retries and [circuit breakers](card:circuit-breaker), and monitoring must catch business errors that Kubernetes cannot see.
