## Why it exists

Each service must run the same way on every machine, in many copies that recover from crashes. Containers solve the first; an orchestrator such as Kubernetes solves the second.

## How it works

- Pods come and go; the Service keeps one name and sends calls only to ready Pods.
- Settings arrive through a ConfigMap and Secret: see [Configuration and Secrets](card:configuration-management).
- Kubernetes does not replace [timeouts and retries](card:timeouts-and-retries) inside the app.

## Example

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-service }
spec:
  replicas: 3
  selector: { matchLabels: { app: order } }
  template:
    metadata: { labels: { app: order } }
    spec:
      containers:
        - name: order
          image: registry.example.com/order-service:1.4.2
```

## Interview Qs

### What is the difference between a container and a virtual machine?

A container is an isolated process that shares the host's OS kernel, so it is small and starts fast. A VM virtualises hardware and carries a full OS, so it is heavier and slower to boot.

### If Kubernetes restarts failed Pods, why do we still need resilience patterns?

Restarts fix crashed processes, not slow dependencies or wrong results. Callers still need timeouts, retries and [circuit breakers](card:circuit-breaker), and monitoring must catch business errors.
