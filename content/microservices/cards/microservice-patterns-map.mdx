## Why it exists

Interviewers name a problem and expect a pattern, or name a pattern and expect its problem. One map keeps the pairs, and the look-alikes, apart.

## How it works

| Problem | Pattern (mixed up with) |
|---|---|
| Where to split? | [Business capability, bounded context](card:service-boundaries) |
| One entry for clients | [API gateway, BFF](card:api-gateway) ([vs load balancer](compare:api-gateway-vs-load-balancer)) |
| Instances come and go | [Service discovery](card:service-discovery) ([vs gateway](compare:service-discovery-vs-api-gateway)) |
| Network code in every service | [Sidecar, service mesh](card:service-mesh) |
| Slow or failing dependency | [Timeout, retry](card:timeouts-and-retries), [circuit breaker](card:circuit-breaker) ([vs retry](compare:retry-vs-circuit-breaker)) |
| One dependency takes all threads | [Bulkhead](card:bulkhead) ([vs breaker](compare:circuit-breaker-vs-bulkhead)) |
| Too many requests | [Rate limiting](card:rate-limiting) |
| Shared tables couple teams | [Database per service](card:database-per-service) |
| A write spans services | [Saga](card:saga) ([vs 2PC](compare:saga-vs-two-phase-commit)) |
| Save and publish together | [Outbox](card:outbox-and-inbox) ([vs inbox](compare:outbox-vs-inbox)) |
| The same message twice | [Idempotent consumer](card:delivery-guarantees) ([vs dedup](compare:idempotency-vs-deduplication)) |
| Reads differ from writes | [CQRS](card:cqrs) ([vs event sourcing](compare:cqrs-vs-event-sourcing)) |
| A request crosses services | [Distributed tracing](card:distributed-tracing) |
| Release without downtime | [Probes](card:health-probes), [rolling, blue-green, canary](card:deployment-strategies) |
| Replace a monolith | [Strangler fig](card:strangler-fig-migration), [anti-corruption layer](card:anti-corruption-layer) |
| One instance must coordinate | [Leader election](card:leader-election) |

- **Leader election:** instances race for a lease; the holder leads and renews it, others take over when it lapses.

## Interview Qs

### Which patterns would you use for an order and payment flow?

Database per service, a saga for order, stock and payment, an outbox so events are not lost, idempotent consumers, and timeouts with a circuit breaker on sync calls.

### When do you need leader election?

When peer instances need one coordinator so they do not clash over shared work. Use a lease or a tool like ZooKeeper. If they only share one resource, plain locking is enough.
