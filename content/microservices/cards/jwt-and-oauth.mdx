## Why it exists

Services need to know who is calling and what they may do without asking a login server on every call. A signed token carries that proof.

## How it works

<Steps label="A JWT from login to the Order Service">
  <Step title="Log in">The user signs in at the identity provider.</Step>
  <Step title="Get tokens">The app gets an access token, often a refresh token and, with OIDC, an ID token.</Step>
  <Step title="Call">It sends `Authorization: Bearer <access token>` to the gateway.</Step>
  <Step title="Validate">The service checks the signature with allowed algorithms only, then exp, iss and aud.</Step>
  <Step title="Authorise">It checks scopes and business rules, then acts.</Step>
</Steps>

- RFC 9700 (2025): do not use the implicit or password grants. OAuth 2.1, still a draft, builds in these rules.
- Opaque tokens are checked by introspection: it can reflect revocation, but every call adds a hop.

## Example

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.shop.example
          audiences: order-service
```

## Defaults

| What | Default | Where |
|---|---|---|
| Checks with `issuer-uri` set | signature, exp, nbf, iss | Spring Security 7.1 resource server |
| Audience (aud) check | only when `audiences` is set | Spring Boot 4.1 property |
| Clock skew allowed | 60 seconds | Spring Security 7.1 |

## Interview Qs

### How do you log out a user who holds a JWT?

You cannot delete a self-contained token. Keep access tokens short-lived, revoke the refresh token, and if needed put the token's jti on a denylist until it expires.

### Access token vs refresh token?

The access token is short-lived and sent to APIs. The refresh token lives longer, goes only to the authorization server, and gets a new access token without a new login.
