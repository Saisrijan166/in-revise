## What it is

These are three standards that work together. OAuth 2.0 is a standard way for an app to get an access token, a credential that lets it call an API with limited permissions called scopes, such as `orders.read`. OpenID Connect (OIDC) adds login on top: it also returns an ID token that tells the app who the user is. A JWT (JSON Web Token) is a token format: a small JSON object of claims, such as the user ID and the expiry time, signed so that any change is detected.

## Why it exists

The [previous concept](card:microservices-security) said every service checks the caller. If the token were only a random string, the Order Service would have to ask the login server "who is this?" on every call: one extra network hop per request, and the login server becomes a bottleneck. A signed JWT carries the answer inside it, so each service checks it alone. OAuth also means the shop's app never handles the user's password; only the identity provider sees it.

## How it works

1. The shop's app sends the user to the identity provider to log in. This is the authorization code flow. With PKCE, the app first makes a random secret and sends only its hash (method S256).
2. After login, the identity provider returns a one-time code. The app sends the code and the secret, and gets back a short-lived access token, often a refresh token and, with OIDC, an ID token.
3. The app sends `Authorization: Bearer <access token>` with every call.
4. The Order Service checks the signature with the identity provider's public keys, which it downloaded once and caches. It accepts only the algorithms it expects, then checks `exp` (expiry time), `iss` (who issued it) and `aud` (which service it is meant for).
5. It checks the scopes and its own business rules, then acts.
6. When the access token expires, the app sends the refresh token to the identity provider for a new one, without a new login.

A service with no user, such as a nightly job, uses the client credentials flow instead: it sends its own client ID and secret and gets a token for itself.

## Example

A decoded access token for user 42, and the Order Service configuration that validates it.

```json
{
  "iss": "https://idp.shop.example",
  "sub": "42",
  "aud": "order-service",
  "scope": "orders.read orders.write",
  "iat": 1792570200,
  "exp": 1792570500
}
```

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.shop.example
          audiences: order-service
```

What to notice:

- `exp` minus `iat` is 300 seconds, so this token lives five minutes. A stolen copy is useful only until then.
- The payload is readable by anyone who has the token. Put IDs and scopes in it, never card numbers or passwords.
- `issuer-uri` makes Spring Security find the identity provider's public keys and check `iss`. Remove `audiences` and a token meant for the Inventory Service would also be accepted here.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Checks with `issuer-uri` set | signature, `exp`, `nbf` (not before), `iss` | Spring Security 7.1 resource server |
| `aud` check | only when `audiences` is set | Spring Boot 4.1 property |
| Clock skew allowed | 60 seconds | Spring Security 7.1 |
| Public keys (JWK set) cached | in memory, 5 minutes | Spring Security 7.1 |

- **Scopes become authorities:** Spring Security turns scope `orders.write` into the authority `SCOPE_orders.write`.
- **PKCE (RFC 9700, 2025):** public clients, such as mobile apps, must use it; for server-side apps it is recommended.
- **Old flows:** RFC 9700 says the password grant must not be used and the implicit grant should not be. OAuth 2.1, still an Internet-Draft in 2026, leaves both out.
- **Algorithms:** accept only the signing algorithms you expect; never accept `alg: none`, which means "no signature".
- **Refresh tokens** go only to the identity provider, never to an API.

## Not to be confused with

OAuth 2.0 is about access: it lets an app call an API on your behalf. OIDC is about identity: it tells the app who logged in. A JWT is neither; it is only a token format that both often use. Rule: OAuth = access token for the API; OIDC = ID token for the app; JWT = the envelope.

## Interview Qs

### How do you log out a user who holds a JWT?

You cannot delete a self-contained token; it stays valid until `exp`. So keep access tokens short-lived, revoke the refresh token so no new access token can be issued, and if you must cut access at once, keep the token's `jti` (its ID) on a denylist until it expires.

### Access token vs refresh token?

The access token is short-lived and sent to APIs with every call. The refresh token lives longer, goes only to the identity provider, and gets a new access token without a new login. Keeping them apart means the long-lived token never travels to every service.

### Why does the authorization code flow use PKCE?

Another app on the device could intercept the one-time code. With PKCE, the app sends a hash of a random secret at the start and the secret itself when it swaps the code. An attacker who stole only the code cannot get tokens.
