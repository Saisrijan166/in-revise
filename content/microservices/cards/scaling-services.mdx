## Why it exists

Load grows unevenly: checkout spikes during a sale while profile pages stay quiet. Microservices let you scale only the busy service, if it keeps no state of its own.

## How it works

<Compare id="vertical-vs-horizontal-scaling" />

- Avoid sticky sessions: keep sessions in Redis or use tokens.
- Scaling changes capacity; [load balancing](card:load-balancing) spreads requests across it; a deployment changes the version.
- Track latency as a percentile, not an average ([metrics](card:metrics-and-slos)).

## Example

```text
Order service: 50 ms per request, 200 requests/s
  in flight = 200 × 0.05 = 10
Target 2,000 requests/s at 50 ms -> 100 in flight

8 instances × 10 connections (HikariCP default) = 80
PostgreSQL 18 max_connections = 100 (typical default)
  -> 2 more instances and the database refuses connections
```

## Defaults

| What | Default | Where |
|---|---|---|
| Pool size (`maximumPoolSize`) | 10 | HikariCP, the pool Spring Boot 4.1 picks first |
| Max connections | 100 (typical) | PostgreSQL 18 `max_connections` |

## Interview Qs

### What is the difference between scaling and load balancing?

Scaling changes capacity: bigger machines or more instances. Load balancing spreads requests across the instances you have. You need both: new instances get no traffic without a load balancer, and balancing cannot add capacity.

### Availability vs reliability?

Availability is the share of time the service is usable, such as 99.9% a month. Reliability is wider: the service does its intended job correctly and consistently whenever it is expected to.

### Why should a microservice be stateless?

So any instance can take any request. Instances can then be added, removed or restarted freely, and no user loses a session when one instance dies.
