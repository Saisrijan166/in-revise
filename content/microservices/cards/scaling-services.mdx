## What it is

Scaling a service means changing how much load it can handle. Vertical scaling gives one instance a bigger machine, with more CPU or memory. Horizontal scaling runs more instances of the same service, with a load balancer, a component that spreads incoming requests across them; you will see it in [load balancing](card:load-balancing). Horizontal scaling works only if the service is stateless: it keeps nothing about a user in its own memory between requests.

## Why it exists

Load is uneven. During a sale, checkout traffic may grow many times while profile pages stay quiet. A monolith must be copied whole to cope; with [microservices](card:monolith-and-microservices) you add instances of only the Order service. But two things break this. If an instance keeps a user's session in memory, the next request may land on another instance and lose it. And every new instance needs database connections that the database may not have.

## How it works

<Compare id="vertical-vs-horizontal-scaling" />

1. Measure first: find the bottleneck, the part that runs out first. It may be the instance's CPU, the database, or a service it calls.
2. Make the service stateless: move sessions and carts to a shared store such as Redis or the database, or into a signed token the client sends with each request.
3. Add instances behind the load balancer. Each new instance gets a share of the requests.
4. Check the shared parts: every instance opens its own pool of database connections, so the total must stay under the database's limit.
5. Size with Little's law: requests in flight = throughput × latency. Throughput is requests per second; latency is how long one request takes.

So the key is: adding instances helps only while the instance is the bottleneck.

## Example

The Order service before a sale, with the numbers worked out:

```text
Now:    200 requests/s × 0.050 s = 10 requests in flight
Sale:   2,000 requests/s × 0.050 s = 100 requests in flight

Pools:  8 instances × 10 connections (HikariCP default) = 80
Limit:  PostgreSQL 18 max_connections = 100, minus 3 reserved = 97
Scale to 10 instances -> pools want 100 connections -> some are refused
```

What to notice:

- Little's law turns the sale into a concrete number: ten times the throughput at the same latency means ten times the requests in flight.
- The database limit, not the instance count, is the ceiling. Ten instances with default pools already ask for more connections than the 97 the app may use.
- Fixes: smaller pools per instance, or faster queries, so each connection is busy for less time. Adding instances alone makes this worse.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Pool size (`maximumPoolSize`) | 10 per instance | HikariCP, the pool Spring Boot 4.1 picks first |
| Max connections | Typically 100 | PostgreSQL 18 `max_connections` |
| Reserved for superusers | 3 | PostgreSQL 18 `superuser_reserved_connections` |

- **No sticky sessions:** keep session data in a shared store, so a request can go to any instance.
- **Backpressure:** when a part cannot keep up, it should make the senders slow down, for example with a bounded queue, instead of accepting work until it crashes.
- **Scale up what cannot be split:** a single database primary is usually given a bigger machine rather than more copies.

## Interview Qs

### What is the difference between scaling, load balancing and deployment?

Scaling changes capacity: bigger machines or more instances. Load balancing spreads requests across the instances you have. A deployment changes the version that runs. You need scaling and balancing together: new instances get no traffic without a load balancer, and balancing cannot add capacity.

### Why should a microservice be stateless?

So any instance can take any request. Instances can then be added, removed or restarted freely, and no user loses a session or a cart when one instance dies.

### Availability vs reliability?

Availability is a number: the share of time the service does its job successfully when asked, such as 99.9% in a month. Reliability is the wider goal: the service does its intended job correctly and consistently whenever it is expected to. Availability is the usual way to measure it.
