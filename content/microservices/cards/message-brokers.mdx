## What it is

A message broker is a server that receives messages from producers, stores them, and delivers them to consumers. It offers two delivery shapes. A queue gives each message to one consumer, and a topic gives every subscriber its own copy. Apache Kafka and RabbitMQ are two widely used brokers, and they store messages in different ways.

## Why it exists

If Order Service sent OrderCreated straight to Notification Service, both would have to be running at that moment. During a Notification restart, Order Service would have to hold the message and retry, or lose it. A broker stores the message, so the producer hands it over and moves on, and a slow or restarting consumer catches up later. The same broker lets you add workers when the load grows.

## How it works

<Compare id="queue-vs-topic" />

1. The producer sends a message to the broker, which stores it and can confirm to the producer that it has it.
2. With a queue, the broker gives each message to one of the consumers reading that queue. Adding consumers shares the work; this is the competing consumers pattern.
3. With a topic, each subscribing service gets its own copy, so Inventory and Notification both see every OrderCreated.
4. The consumer processes the message and sends an acknowledgement (ack). A message that is never acknowledged, for example because the consumer crashed, can be delivered again.

So a queue answers "who does this job?" and a topic answers "who needs to know?"

## Example

The shop uses both shapes:

| Message | Shape | Why |
|---|---|---|
| OrderCreated | Topic | Inventory and Notification each need every order |
| SendEmail | Queue | Three Notification instances share the slow email work |

If SendEmail were a topic and each instance subscribed separately, every customer would get three identical emails.

## Rules and defaults

- **Kafka keeps records:** reading does not delete. A record stays until the topic's retention ends, 7 days by default (`retention.ms`, Kafka 4.3), so a consumer can rewind and read again. One consumer group behaves like a queue; one group per service behaves like a topic. Details are in [Kafka Fundamentals](card:kafka-fundamentals).
- **RabbitMQ routes, then removes:** a producer publishes to an exchange, and bindings route the message to queues. The exchange types are direct, fanout, topic and headers. A queue message is removed once a consumer acknowledges it.
- **RabbitMQ streams (3.9+):** an append-only log in which reading does not delete, so messages can be replayed.
- **A broker does not process anything:** it stores and delivers. A message can still arrive late or twice, and a consumer can still fail on it.

## Not to be confused with

Kafka is a log: records stay in order inside partitions, and many consumer groups read the same records at their own pace. RabbitMQ is a router: exchanges send each message to the right queues, and a queue hands it off and forgets it after the ack. Rule: replayable event stream read by many services = Kafka; task queue with routing rules = RabbitMQ.

## Interview Qs

### Why use a broker instead of calling the other service directly?

A direct call needs both services up at the same time, and the caller waits. A broker stores the message, so the producer moves on, and a consumer that is slow or restarting catches up later. It also spreads work over several consumer instances and lets new consumers subscribe without changing the producer.

### Kafka or RabbitMQ: how do you choose?

Kafka when many services read the same event stream and need replay or per-key ordering. RabbitMQ when you need task queues, per-message acknowledgements and flexible routing through exchanges. Both are mature; the use case, the team's experience and what you can operate decide, not raw speed.

### Does a broker guarantee my message is processed?

No. It stores and delivers the message, but delivery can be late or repeated, and a consumer can fail on it. Consumers must handle repeats, as [delivery guarantees](card:delivery-guarantees) shows, and messages that keep failing need a [dead-letter queue](card:dead-letter-queues).
