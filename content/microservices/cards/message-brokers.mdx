## Why it exists

Direct calls need both services up at the same moment. A broker holds messages, so a slow or restarting consumer catches up later and the producer is not blocked.

## How it works

<Compare id="queue-vs-topic" />

- A queue with many workers is the **competing consumers** pattern: more instances, more throughput.
- Kafka covers both: one consumer group behaves like a queue, one group per service like a topic.
- How Kafka does it inside: [Kafka Fundamentals](card:kafka-fundamentals). Choosing a product: [Kafka vs RabbitMQ](compare:kafka-vs-rabbitmq).

## Interview Qs

### Kafka or RabbitMQ: how do you choose?

Kafka when many services read the same event stream and need replay or per-key ordering. RabbitMQ when you need task queues, per-message acks and flexible routing. The use case decides, not speed alone.

### What is the difference between a queue and a topic?

In a queue each message is processed by one consumer, so workers share the work. In a topic every subscriber receives every message, so several services react to the same event.

### Does a broker guarantee my message is processed?

No. It stores and delivers it, but delivery can be late or repeated, and a consumer can fail. Consumers must be idempotent and failures need a [dead-letter queue](card:dead-letter-queues).
