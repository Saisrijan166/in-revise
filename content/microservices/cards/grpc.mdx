## What it is

gRPC is a framework for calling a method on another service as if it were a local method. This is called a remote procedure call (RPC). You describe the service and its messages once, in a `.proto` file, and a tool generates client and server code from it in many languages. Messages travel as Protocol Buffers (protobuf), a compact binary format, over HTTP/2, a version of HTTP that carries many calls on one connection.

## Why it exists

With [REST](card:rest-apis), each team writes its client code by hand, turns objects into JSON text and back, and finds a renamed field only when a call fails at runtime. For frequent internal calls, the text also costs bytes and CPU. gRPC makes the `.proto` file the single contract: the generated client has typed methods, so a mismatch shows up when you compile, and binary messages are smaller and faster to parse than JSON. It also supports streams, not only one reply per request.

## How it works

1. You write the `.proto` file: the service, its methods, and the messages, with a number for each field.
2. The protobuf compiler, `protoc`, with the gRPC plugin, generates a client stub (a class with one method per RPC) and a server base class.
3. Payment Service implements the server class. Order Service calls `charge(...)` on the stub.
4. The stub encodes the request as protobuf, sends it over HTTP/2, and decodes the reply into a typed object.
5. If the reply does not arrive before the call's deadline, the client stops waiting with `DEADLINE_EXCEEDED`, and the server sees the call cancelled.

## Example

The shop's Payment Service contract, with one normal call and one stream:

```proto
syntax = "proto3";

service PaymentService {
  rpc Charge (ChargeRequest) returns (ChargeReply);           // unary: one request, one reply
  rpc WatchStatus (PaymentId) returns (stream PaymentStatus); // server streaming
}

message ChargeRequest {
  string order_id = 1;      // field numbers, not names, identify fields on the wire
  int64 amount_paise = 2;   // 50000 = ₹500; whole paise, no floating point
}
message ChargeReply   { string payment_id = 1; string status = 2; }
message PaymentId     { string payment_id = 1; }
message PaymentStatus { string status = 1; }
```

What to notice:

- `= 1` and `= 2` are field numbers. The wire carries these numbers, not the names, so changing or reusing a number breaks old clients.
- `stream` makes `WatchStatus` server streaming: one request, then a status message each time the payment changes.
- Adding a new field with a new number is safe: old code skips fields it does not know.
- Money is a whole number of paise. A floating-point amount carries rounding errors: 0.1 + 0.2 is not exactly 0.3.

## Rules and defaults

- **Deadline:** the point in time after which the client stops waiting for a reply. gRPC sets none by default, so a call can wait forever. Set one on every call.
- **Deadline propagation:** Java and Go pass the remaining deadline on to the calls a server makes; in C++ you must enable it. The server must stop its own work when a call is cancelled.
- **Deleted fields:** mark their numbers (and names) as `reserved`, so nobody reuses them.
- **Browsers:** they cannot call gRPC directly. gRPC-Web goes through a proxy, such as Envoy, and supports only unary and server-streaming calls.
- **Errors:** gRPC returns its own status codes, such as `DEADLINE_EXCEEDED` or `UNAVAILABLE`, not HTTP status codes.

## Not to be confused with

REST exposes resources over HTTP, usually as JSON text, and any browser or tool can call it without generated code. gRPC exposes typed methods from a `.proto` contract, with binary messages over HTTP/2. Rule: REST at the edge for browsers and partners; gRPC inside for fast, typed or streaming calls.

## Interview Qs

### When would you choose gRPC over REST?

For internal service-to-service calls that need low latency, strict typed contracts or streaming, especially when many languages share one contract. REST stays better for public APIs, browsers and partners, because anyone can call it with plain HTTP and JSON.

### What are the four kinds of gRPC call?

Unary: one request, one reply. Server streaming: one request, a stream of replies. Client streaming: a stream of requests, one reply. Bidirectional streaming: both sides send streams that run independently.

### How do you change a .proto file without breaking clients?

Add new fields with new numbers; old clients ignore them. Never change a field's number, almost never its type, and never reuse the number of a deleted field: mark it `reserved`. For a truly incompatible change, add a new method or a new versioned service.
