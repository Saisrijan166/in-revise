## Why it exists

Chatty internal calls pay for text JSON and hand-written clients. gRPC gives one shared contract, generated code in many languages and a compact binary format.

## How it works

```proto
syntax = "proto3";

service PaymentService {
  rpc Charge (ChargeRequest) returns (ChargeReply);           // unary
  rpc WatchStatus (PaymentId) returns (stream PaymentStatus); // server streaming
}

message ChargeRequest {
  string order_id = 1;      // field numbers mark fields on the wire
  int64 amount_paise = 2;   // never reuse a deleted field's number
}
```

- `protoc` with the gRPC plugin generates the client stub and the server code.
- A client that passes its deadline gets `DEADLINE_EXCEEDED`; the server sees the call cancelled.
- Old code ignores new fields, so adding fields is safe.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Deadline | none: the call can wait forever | gRPC (deadlines guide) |
| Deadline propagation | on in Java and Go | gRPC |
| Message format | Protocol Buffers | gRPC |

## Interview Qs

### When would you choose gRPC over REST?

For internal service-to-service calls that need low latency, strict typed contracts or streaming. REST stays better for public APIs and browsers; see [gRPC-Web](card:grpc-web). See [REST vs gRPC](compare:rest-vs-grpc).

### What are the four kinds of gRPC call?

Unary (one request, one reply), server streaming, client streaming, and bidirectional streaming, where both sides send streams independently.
