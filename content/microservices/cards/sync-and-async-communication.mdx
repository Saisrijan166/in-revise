## What it is

Services talk to each other over the network in one of two styles. In synchronous communication, the caller sends a request, such as an HTTP call, and waits until the reply comes back. In asynchronous communication, the sender hands a message to a message broker, a separate program that stores messages, and carries on; the receiver reads the message later. A message is a small piece of data, such as "order 9001 was created".

## Why it exists

Inside a monolith, one module calls another in the same process, and the call always arrives. Between services, the other side may be slow or down ([the fallacies](card:distributed-systems-fallacies)). If every step of placing an order is a waiting call, one slow service makes the user wait, and one stopped service fails the whole order. Choosing the style for each call decides who waits, and what breaks when a service fails.

## How it works

<Compare id="rest-vs-messaging" />

1. Synchronous: Order Service sends `GET /stock/101` to Inventory Service, and its thread waits.
2. Inventory Service replies with the stock level, or the call fails or times out; Order Service must handle each case before it can answer the user.
3. Asynchronous: Order Service saves the order and publishes an `OrderCreated` message to the broker.
4. The broker stores the message, and Order Service answers the user without waiting for Inventory, Payment or Notification.
5. Inventory, Payment and Notification each read the message when they are ready, even if one of them was down when it was sent.

So the key is: a sync call needs the receiver to be up now; an async message needs only the broker to be up now.

## Example

Placing an order in the shop uses both styles: a sync stock check, then an async event for the rest of the flow.

```java
Order placeOrder(Order order, long productId) {
    // Synchronous: this thread waits here until Inventory replies or fails
    StockLevel stock = restClient.get()
            .uri("http://inventory-service/stock/{id}", productId)
            .retrieve()
            .body(StockLevel.class);

    // Asynchronous: send() returns at once; Kafka gets the message in the background
    Order saved = orderRepository.save(order);                  // status PENDING
    kafkaTemplate.send("orders", saved.id(), new OrderCreated(saved.id(), 500));
    return saved;   // the user gets an answer; stock, payment and email happen later
}
```

What to notice:

- The `restClient` call blocks: if Inventory Service is down, `placeOrder` fails right there, and the user sees an error.
- `kafkaTemplate.send` queues `OrderCreated` (₹500) for the broker, here Kafka, and returns a future without waiting. Reserving stock, charging and the email happen in other services, later.
- The order is returned as `PENDING`, because the payment has not happened yet. The user's screen must show that honestly.
- Saving and sending are two separate steps: a crash between them loses the message. You will see the fix in [Transactional Outbox](card:outbox-and-inbox).

## Rules and defaults

- **Long work over HTTP:** answer `202 Accepted` with a `Location` header that points to a status URL. The client polls it; it returns `200` with the current state until the work finishes (the Asynchronous Request-Reply pattern).
- **Non-blocking is not asynchronous messaging:** a non-blocking HTTP client frees the thread while it waits, but the caller still needs the reply, and the receiver must be up.
- **Avoid long chains of sync calls:** if a request needs data from another service every time, keep a local copy of that data, updated by events.
- **Async does not mean processed:** a message can arrive late, arrive twice, or end up in a [dead-letter queue](card:dead-letter-queues), as later concepts show.

## Not to be confused with

An async message can be a command or an event. A command asks one service to do something, such as `ReserveStock`, and that service may refuse. An event announces something that already happened, such as `OrderCreated`, to anyone who listens. Separately, a queue hands each message to one consumer, while a topic gives every subscriber its own copy. Rule: sync or async is about waiting; command or event is about meaning; queue or topic is about who receives it.

## Interview Qs

### How do microservices communicate?

Synchronously over HTTP, with REST or gRPC, when the caller needs an immediate answer, and asynchronously through a broker such as Kafka or RabbitMQ for events and background work. The choice depends on whether the caller needs the result now, how much coupling is acceptable, and which delivery guarantees you need. Most systems use both.

### Is asynchronous communication always better?

No. It removes the need for both services to be up together and lets work finish later. But it adds a broker to run, duplicate or late messages, ordering questions, harder debugging and briefly stale data. A login check or a stock check needs a sync answer.

### Why is a chain of synchronous calls a problem?

Each hop adds its latency to the user's request, and the request fails if any service in the chain fails or slows down. Availability also multiplies: three services at 99.9% each give about 99.7% together. Keep a local copy of the data you need, updated by events, or move work to async messages.
