## What it is

A replica is a copy of the same data kept on another node, which is another server, so the data survives one machine failing and more reads can be served. The CAP theorem says what replicated data can promise when the network between replicas breaks, which is called a network partition. While a partition lasts, the system can stay consistent (every read sees the latest write) or available (every node keeps answering), not both. Consistency models name the promises in between.

## Why it exists

Two replicas of the Inventory service's stock data both hold the last unit of a phone. The link between them drops, and one customer reaches each replica. If both sell, the shop sells a phone it does not have. If one refuses until the link is back, that customer sees an error. Without a clear rule the system makes this choice by accident. CAP makes you choose on purpose, operation by operation.

## How it works

1. Normally, a write to node 1 is copied to node 2, so both nodes give the same answer.
2. A partition starts: the two nodes cannot exchange messages, but clients can still reach each of them.
3. Client A writes to node 1, and node 1 cannot tell node 2 about it.
4. With the CP choice, the side that cannot confirm the write refuses or waits, so no reader sees old data, but some requests fail.
5. With the AP choice, both nodes keep answering, and node 2 serves the old value until the partition heals and the copies converge.

So the key is that P is not a choice: while a partition lasts you choose C or A, and when there is none you can have both.

## Example

A cluster of three nodes, such as etcd, makes the CP choice safely with a quorum: a majority, (n/2)+1, which is 2 of 3. A partition cuts node C off from nodes A and B:

| Side of the partition | Nodes | Has a quorum? | What it does |
|---|---|---|---|
| A and B | 2 of 3 | Yes | Keeps accepting writes and elects a leader if needed |
| C alone | 1 of 3 | No | Stops accepting writes; its leader, if it was one, steps down |

What to notice:

- Only one side can hold a majority, so the two sides never both act as the owner of the data. That failure, two sides making conflicting decisions, is called [split brain](term:split-brain).
- The cluster stays available for clients that reach A or B, and unavailable for those that reach only C. CP does not mean "everything stops".
- With four nodes split 2 and 2, neither side has a majority and both stop. This is why clusters use an odd number of nodes: three nodes tolerate one failure, like four, with one machine less.

## Rules and defaults

- **C in CAP is linearizability:** each operation appears to take effect at one instant, in real-time order, as if there were a single copy.
- **A in CAP:** every request that reaches a node that has not crashed gets a non-error response.
- **No partition (PACELC):** the trade-off moves to latency against consistency. Waiting for other replicas to confirm a write keeps reads fresh but makes each write slower.
- **Choose per operation:** the choice between C and A can differ by operation, data or user inside one system, so a shop can keep stock reservation consistent and review counts available.
- **Weaker models between the two ends:** read-your-writes (a client always sees its own writes), causal (operations linked by cause are seen in the same order by everyone) and eventual (copies converge once updates stop).

## Not to be confused with

The C in ACID means a transaction keeps the database's rules, such as unique keys and constraints, true. The C in CAP means every read sees the latest write across replicas; Brewer notes it is a much narrower idea than ACID's C. Rule: ACID C = the rules hold inside one database; CAP C = all copies agree.

## Common mistakes

- **"PostgreSQL is CP" or "Cassandra is AP", full stop.** Real systems give different guarantees depending on how they are configured and which operation you run. Say what happens to reads and writes during a partition instead.

## Interview Qs

### Explain CAP with an example.

Two Inventory replicas lose contact. If both keep selling the last unit, they stay available but disagree (AP). If one refuses until it reaches the other, the data stays correct but that replica is unavailable (CP). Without a partition, both can be consistent and available.

### How do you keep data consistent across microservices?

Use a local ACID transaction inside each service, then spread the change with events or a saga. Accept eventual consistency where the business allows it, and handle duplicate, late and stale messages on purpose with [idempotency](card:idempotency). Keep strong consistency inside one service for rules like stock reservation.

### Does eventual consistency mean the data is wrong?

No. If updates stop and messages get through, all copies reach the same value. Stale reads are a temporary window that the design must tolerate, such as a review count that is a few seconds old.
