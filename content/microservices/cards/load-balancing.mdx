## What it is

Load balancing is spreading requests across the instances of a service so that no single instance is overloaded. A load balancer is the part that does it: a separate program, such as NGINX or a cloud load balancer, or a library inside the caller. For each request it picks one instance using an algorithm, such as taking turns. It also stops sending to instances that fail their health checks.

## Why it exists

Adding instances helps only if the requests reach them evenly. If Order Service sent every payment call to the first instance in its [discovery](card:service-discovery) list, that one would overload while the others sat idle, and a crashed instance would keep receiving calls. A load balancer shares the work by a rule and takes failed instances out, so three instances really carry about three times the load.

## How it works

1. A request for Payment Service reaches the load balancer, or the load-balancing library inside Order Service.
2. The balancer takes the current list of healthy instances, from discovery or from its own health checks.
3. It applies its algorithm. Round robin takes each instance in turn; least connections picks the one with the fewest active requests; hashing sends the same key, such as a user id, to the same instance.
4. It forwards the request to the chosen instance.
5. When an instance fails its health checks, or too many requests to it fail, the balancer takes it out of the list until it recovers.

## Example

An NGINX load balancer in front of two Payment instances:

```nginx
upstream payment_service {
    least_conn;                                   # without this line: round robin
    server payment-1:8080 weight=2;               # gets about twice the share
    server payment-2:8080 max_fails=3 fail_timeout=30s;
}
```

What to notice:

- `least_conn` switches the algorithm to least connections. Remove the line and NGINX uses round robin, its default.
- `weight=2` makes `payment-1` count double, for example because it runs on a bigger machine; a server without a weight counts 1.
- `max_fails=3 fail_timeout=30s`: if 3 attempts to `payment-2` fail within 30 seconds, NGINX stops sending it requests for 30 seconds. This is a passive health check, based on real traffic.
- Without any health check, a hung `payment-2` would keep receiving its share of calls.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Algorithm | round robin | NGINX upstream; Spring Cloud LoadBalancer |
| Server weight | 1 | NGINX upstream |
| Passive check | `max_fails=1`, `fail_timeout=10s` | NGINX upstream |

- **Active health checks:** in NGINX, periodic checks of an endpoint need NGINX Plus; the open-source version has only passive checks.
- **Layer 4 or layer 7:** a layer 4 balancer, such as AWS NLB, forwards TCP or UDP connections by IP and port without reading them. A layer 7 balancer, such as AWS ALB, reads each HTTP request and can route by path or header.
- **Sticky sessions:** pinning a user to one instance spreads load unevenly and loses the session when that instance dies. Keep [services stateless](card:scaling-services) instead.

## Not to be confused with

A load balancer spreads requests over the instances of one service. An [API gateway](card:api-gateway) decides which service handles an API call and applies policies such as authentication; it often runs behind a load balancer itself. Scaling changes how many instances exist; load balancing shares requests among the instances that exist. Rule: gateway = which service; load balancer = which instance.

## Common mistakes

- **"Least connections always picks the best instance."** An instance that fails fast finishes its requests quickly, looks idle, and draws even more traffic. Count recent errors as load, too.
- **"A healthy instance can take any load."** A health check says the instance is alive, not that it has spare capacity.

## Interview Qs

### Round robin or least connections?

Round robin when requests cost about the same, because it is simple and even. Least connections when costs vary widely, such as slow reports next to quick reads, because busy instances get fewer new requests.

### What is the difference between layer 4 and layer 7 load balancing?

Layer 4 sees only IP addresses and ports and forwards TCP or UDP connections, so it is fast and works for any protocol. Layer 7 reads each HTTP request, so it can route by path, header or cookie, but it does more work per request.

### Does a load balancer make a service fault tolerant?

Only partly. It survives a crashed instance only if health checks remove it quickly. It does not help when every instance shares a failing database, and a healthy but overloaded instance still slows requests down.
