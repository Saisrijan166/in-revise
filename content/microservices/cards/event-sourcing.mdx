## Why it exists

A normal table keeps only the latest state, so history is lost. Some domains, like payments and orders, need every change kept and the state rebuildable at any time.

## How it works

| # | Event appended to order 42 | State after replay |
|---|---|---|
| 1 | OrderCreated (₹1,200) | CREATED, ₹1,200 |
| 2 | ItemAdded (₹300) | CREATED, ₹1,500 |
| 3 | OrderPaid | PAID, ₹1,500 |

- Loading: read the latest snapshot, then replay only the later events.
- Two writers at once: the append fails if the stream changed since it was read.
- Its events are low level; other services usually get separate integration events.

## Example

```java
sealed interface OrderEvent {}
record OrderCreated(long totalInr) implements OrderEvent {}
record ItemAdded(long priceInr) implements OrderEvent {}
record OrderPaid() implements OrderEvent {}
record Order(String status, long totalInr) {
    Order apply(OrderEvent e) { return switch (e) {
        case OrderCreated c -> new Order("CREATED", c.totalInr());
        case ItemAdded i    -> new Order(status, totalInr + i.priceInr());
        case OrderPaid p    -> new Order("PAID", totalInr);
    }; }
}
// replay: for (OrderEvent e : events) order = order.apply(e);
```

## Interview Qs

### Is replaying slow for long streams?

It can be. Save a snapshot every N events and replay only the events after it. A snapshot is an optimisation; the events stay the truth.

### How do you fix a wrong event or delete personal data?

Never edit events: append a compensating event. Keep personal data outside the event store and reference it by id, or encrypt it per person and delete the key (crypto-shredding).

### When should you not use event sourcing?

For simple CRUD, lookup data, prototypes, or views that must be up to date instantly. It changes how you test, query and evolve data, and is costly to undo.
