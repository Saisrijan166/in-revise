## What it is

A cache is a fast store, usually in memory, that keeps copies of data you read often, so the next read skips the slower database. A read that finds the data in the cache is a hit; a read that does not is a miss. In microservices a cache is either local, inside each instance's own memory, or shared, such as Redis, which all instances use over the network. The database stays the source of truth; the cache only holds copies.

## Why it exists

On a sale day the Inventory service reads the same product's name and price thousands of times a second. Each read goes to PostgreSQL, so the database becomes the bottleneck you met in [scaling services](card:scaling-services), and every page waits for it. A cache serves those repeat reads from memory, which cuts latency and takes load off the database. The cost is that a copy can be stale, older than the database, just like the eventually consistent replicas in [CAP](card:cap-and-consistency).

## How it works

1. To read, the service looks up the key, such as `product:7`, in the cache. On a hit it returns the value at once.
2. On a miss it loads the row from the database, stores it in the cache with a TTL, and returns it. A TTL (time to live) is an expiry time after which the cache removes the key by itself.
3. To write, the service updates the database first, then deletes the cached key.
4. The next read misses and loads the new value. If a delete is ever lost, the TTL still removes the old copy later.

So the key is that the application fills the cache on demand, and a write removes the copy instead of trusting it.

## Example

The Inventory service caches product names in Redis through Spring's `StringRedisTemplate`:

```java
String productName(long id) {
    String key = "product:" + id;
    String name = redis.opsForValue().get(key);
    if (name == null) {                                             // miss
        name = repo.findById(id).orElseThrow().getName();
        long ttl = ThreadLocalRandom.current().nextLong(600, 660);  // 10 min + jitter
        redis.opsForValue().set(key, name, Duration.ofSeconds(ttl));
    }
    return name;
}
void rename(long id, String name) {
    repo.updateName(id, name);       // 1. the database first
    redis.delete("product:" + id);   // 2. then delete the cached copy
}
```

What to notice:

- `get` returns `null` on a miss, and only then does the code touch the database.
- The TTL is a random 600 to 659 seconds. Keys loaded together at startup then expire at different moments instead of all at once.
- In `rename`, swap the two lines and a read that arrives between them misses, loads the old name, and caches it until the TTL ends.
- An id that does not exist throws, so nothing is cached and every request for it reaches the database; that is the penetration problem below.

## Rules and defaults

- **TTL length:** too short and the service keeps reloading from the database; too long and readers see stale data. Caching suits data that changes rarely or is read very often.
- **Local caches disagree:** each instance has a private copy, so after a write some instances still serve the old value. Expire local entries sooner, or use a shared cache.
- **The cache is optional:** if Redis is down, the service can still read the database, only slower. Design it so a cache failure is not an outage.
- **Do not cache:** sensitive data in a cache that many applications share, or data that almost never gets a hit, where the extra lookup only adds work.
- **Three ways a miss floods the database:** a stampede (a hot key expires and many requests reload it; let one request reload it), penetration (requests for ids that do not exist always miss; a Bloom filter can say "definitely absent" first) and an avalanche (many keys expire together; add TTL jitter).

## Not to be confused with

In **cache-aside** the application fills the cache on a miss and deletes the key on a write. In **write-through** every write updates the database and the cache together, so readers see the new value right after the write. In **write-behind** the cache takes the write first and the database is updated later. Rule: cache-aside loads on a miss; write-through writes both now; write-behind writes the cache now and the database later.

## Common mistakes

- **"The cache can hold data the database does not have."** A cache evicts keys when it runs out of space, and a cache failure can lose them. Keep every important value in the database.

## Interview Qs

### Local cache or Redis?

A local cache is fastest, but each instance has its own copy, so instances can disagree after a write. Redis is shared by all instances, at the cost of a network hop. Many systems use both, with a small local cache with a short TTL in front of Redis.

### Can a Redis lock make sure only one instance charges a payment?

Not on its own. A lock set with `SET key value NX PX` expires, and a holder that pauses longer than that keeps working after another instance takes the lock. For correctness, add a fencing token, a number that grows with each new lock so the database rejects an older holder, or rely on a unique constraint and [idempotency](card:idempotency).

### What is a cache stampede, and how do you prevent it?

A hot key expires and many requests miss at once, so they all hit the database for the same row. Let one request reload the key while the others wait or get the old value, and add jitter to TTLs so hot keys do not expire together.
