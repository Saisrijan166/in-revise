## Why it exists

Many requests read the same product or price again and again. Serving those from memory cuts latency and protects the database, as long as slightly old data is acceptable.

## How it works

<Steps label="Cache-aside (lazy loading)">
  <Step title="Read">Look up the key in the cache. Hit: return it.</Step>
  <Step title="Miss">Load from the database, store it with a TTL, return it.</Step>
  <Step title="Write">Update the database first, then delete the key.</Step>
</Steps>

- [Stampede](card:cache-stampede): let one request reload the key while the others wait or get the old value.
- [Penetration](card:cache-penetration): check a Bloom filter first; it can say "definitely absent" without asking the database.
- [Avalanche](card:cache-avalanche): add random jitter to TTLs so keys do not expire together.

## Example

```java
String productName(long id) {
    String key = "product:" + id, name = redis.opsForValue().get(key);
    if (name == null) {                                        // miss
        name = repo.findById(id).orElseThrow().getName();
        long ttl = ThreadLocalRandom.current().nextLong(600, 660);  // 10 min + jitter
        redis.opsForValue().set(key, name, Duration.ofSeconds(ttl));
    }
    return name;
}
void rename(long id, String name) {                     // 1. database, 2. then the cache
    repo.updateName(id, name); redis.delete("product:" + id);
}
```

## Interview Qs

### Local cache or Redis?

A local cache is fastest, but each instance has its own copy, so instances can disagree after a write. Redis is shared by all instances, at the cost of a network hop. Many systems use both, local in front.

### Can a Redis lock make sure only one instance charges a payment?

Not on its own. A lock with an expiry can run out during a long pause, so two holders are possible. For correctness, add a fencing token the database checks, or rely on a unique constraint and [idempotency](card:idempotency).
