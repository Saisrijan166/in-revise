## What it is

The strangler fig is a way to replace a [monolith](card:monolith-and-microservices) gradually instead of in one rewrite. You put a facade, a proxy such as an [API gateway](card:api-gateway), in front of the old system. Then you move one capability at a time, for example payments, into a new service and point that capability's requests at it. When nothing is left in the monolith, you switch it off.

## Why it exists

Rewriting a large monolith in one go takes months or years. The business keeps changing the old system meanwhile, and the switch-over day is one big risk. With the strangler fig the shop keeps running, every step is small and can be rolled back, and each capability that moves delivers value early.

## How it works

<Mermaid
  alt="Clients send every request to a facade. The facade sends /payments requests to the new Payment Service, which has its own database, and all other requests to the monolith, which still uses the old database."
  chart={`flowchart LR
  C([Clients]) --> F[Facade or gateway]
  F -- "/payments/**" --> N[New Payment Service]
  F -- "everything else" --> M[Monolith]
  N --> ND[(Payment DB)]
  M --> MD[(Old database)]`}
/>

1. Put the facade in front of the monolith. At first it sends every request to the monolith, and clients notice nothing.
2. Choose a fairly decoupled capability, one with few calls back into the monolith, such as Payment.
3. Build the new service with its own database. Copy the existing data with ETL (extract, transform, load), keep it in sync with change data capture, and check that both sides match.
4. Change the facade so that the capability's paths go to the new service.
5. Once the new service has proved itself, delete the old code and tables, then repeat with the next capability. At the end, remove the facade or keep it as the gateway.

So the key is: clients keep one address, and only the facade knows which part has moved.

## Analogy

<Analogy title="The strangler fig plant" limit="The plant takes over its host by itself. In software you must move each part and delete the old code yourself, or the monolith never goes away.">
A strangler fig starts as a vine in a nook of a host tree. It grows around the tree, reaches the ground and grows its own roots. In the end the old tree may die, and the fig stands on its own in the same shape.
</Analogy>

## Example

The shop's facade is Spring Cloud Gateway. Payments have moved; orders have not yet.

```yaml
spring:
  cloud:
    gateway:
      server:
        webmvc:                                # Spring Cloud Gateway 5.0
          routes:
            - id: payments-moved
              uri: http://payment-service      # the new service
              predicates: [ "Path=/payments/**" ]
            - id: orders-not-yet
              uri: http://legacy-shop:8080     # still the monolith
              predicates: [ "Path=/orders/**" ]
```

What to notice:

- `/payments/**` goes to the new service and `/orders/**` still goes to the monolith. Clients call the same gateway address either way.
- Moving orders later is a change to one `uri` in this file, not a change in any client.
- Rolling payments back means pointing `payments-moved` at `legacy-shop` again, which works only while the monolith's payment code and data still exist.

## Rules and defaults

- **Rollback window:** you can go back while the old tables and the sync still exist. After you remove them, going back means restoring them and replaying the changes, so remove legacy parts only after the new service is validated.
- **Facade:** run it with enough instances and capacity, because every request passes through it; it must not become a single point of failure.
- **Not a fit:** when requests to the old system cannot be intercepted, when the system is small enough to replace in one step, or when it must be switched off quickly.

## Not to be confused with

The facade decides **where** a request goes: to the old code or to the new service. An [anti-corruption layer](card:anti-corruption-layer) **translates** between the old and the new model when one side must call the other, so the new service never adopts the legacy schema or API. It holds translation only, no business rules. Rule: the facade routes; the anti-corruption layer translates.

## Interview Qs

### How would you move a monolith to microservices?

Step by step with the strangler fig: a facade routes traffic, one capability moves at a time with its data, and its old path is retired before the next. I avoid a big-bang rewrite, because it delivers nothing until the end and puts all the risk on one day.

### Which service do you extract first?

A fairly decoupled one with few calls back into the monolith, so the team learns to build, deploy and run a service at low risk. After that, take the parts that change most often or matter most to the business.

### How do you move a capability's data?

Copy the existing rows to the new database with ETL, keep both in sync with change data capture while the old system still writes, check that they match, and then make the new database the system of record. Remove the old tables last.
