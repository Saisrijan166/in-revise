## Why it exists

Teams must agree on how services ask and answer. REST reuses plain HTTP meanings, so any client understands the calls.

## How it works

| Method | Use | Safe | Idempotent |
| --- | --- | --- | --- |
| GET | Read | Yes | Yes |
| POST | Create, or run an action | No | No |
| PUT | Create or replace at a known URI | No | Yes |
| PATCH | Change some fields | No | No, unless designed so |
| DELETE | Remove | No | Yes |

- Know the [status codes](card:client-error-codes) by family: 2xx done, 4xx caller's fault, 5xx server's fault.
- Send every error in one format, such as problem details (RFC 9457).
- Version in the URI (`/v2/`) for simplicity; a header keeps the URI the same.

## Example

```text
POST /api/v1/orders       {"productId": 101, "quantity": 2}
-> 201 Created
   Location: /api/v1/orders/9001

POST /api/v1/orders       {"productId": 101, "quantity": 0}
-> 422 Unprocessable Content
   Content-Type: application/problem+json
   {"type": "https://shop.example/problems/bad-quantity",
    "title": "Quantity must be at least 1", "status": 422}
```

## Interview Qs

### PUT, POST or PATCH: which one?

POST creates when the server picks the id, PUT replaces the whole resource at a known URI, PATCH changes some fields. Only PUT is idempotent. See [PUT vs POST vs PATCH](compare:put-vs-post-vs-patch).

### 409 or 422 for a request that breaks a rule?

422 when the content is well-formed but its values are wrong, like quantity 0. 409 when it conflicts with the resource's current state, like editing a stale version.

### How do you change an API without breaking clients?

Add optional fields; clients that ignore unknown fields keep working. For removals or renames, publish a new version and keep the old one. Guard it with [contract tests](card:testing-microservices).
