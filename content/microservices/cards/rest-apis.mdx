## What it is

REST is a way of designing HTTP APIs around resources. A resource is a thing the API exposes, such as an order, and each one has its own URL, like `/orders/9001`. The client acts on it with standard HTTP methods: GET reads, POST creates. The server answers with a status code, a three-digit number that says what happened, and usually a JSON body. Most [synchronous calls](card:sync-and-async-communication) between services are REST calls.

## Why it exists

Order Service and Payment Service are built by different teams that must agree on how to ask and answer. If each team invents its own style, such as `/doPayment` or `/getPaymentInfoById`, every client must learn every API, and errors and retries behave differently everywhere. REST reuses meanings that HTTP already defines: what each method does, which methods are safe to repeat, and what each status code means. Any client, proxy or developer can then read a call without extra notes.

## How it works

| Method | Use | Safe (read-only) | Idempotent |
| --- | --- | --- | --- |
| GET | Read | Yes | Yes |
| POST | Create, or run an action | No | No |
| PUT | Create or replace at a known URL | No | Yes |
| PATCH | Change some fields | No | No, unless designed so |
| DELETE | Remove | No | Yes |

1. The client picks the resource URL: the collection, `/orders`, or one item, `/orders/9001`.
2. It picks the method for the action and sends a JSON body that matches the API contract, the agreed shape of requests, responses and errors.
3. The server validates the request, does the work, and answers with a status code: 2xx for success, 4xx for the caller's mistake, 5xx for the server's failure.
4. On an error, the body explains it in one standard format, such as problem details (RFC 9457), so every client reads errors the same way.

## Example

The shop's checkout creates an order, then sends one with a wrong quantity.

```text
POST /api/v1/orders       {"productId": 101, "quantity": 2}
-> 201 Created
   Location: /api/v1/orders/9001

POST /api/v1/orders       {"productId": 101, "quantity": 0}
-> 422 Unprocessable Content
   Content-Type: application/problem+json
   {"type": "https://shop.example/problems/bad-quantity",
    "title": "Quantity must be at least 1", "status": 422}
```

What to notice:

- `201 Created` with a `Location` header tells the client the new order's URL, so it does not have to guess the id.
- The second request is well-formed JSON with a bad value, so the answer is `422`, not `400`. Broken JSON would be `400`.
- `application/problem+json` is the RFC 9457 format: `type`, `title` and `status` mean the same in every service, so one error handler fits all.
- The `/v1/` in the path is the API version. A breaking change would go to `/v2/` while `/v1/` keeps working.

## Rules and defaults

- **Safe methods:** GET, HEAD, OPTIONS and TRACE only read; they must not change anything on the server (RFC 9110).
- **Idempotent methods:** a method is idempotent when sending the same request twice has the same effect as sending it once. PUT, DELETE and the safe methods are; POST and PATCH are not, so a retried POST can create a second order; [idempotency](card:idempotency) shows the fix.
- **401 needs a challenge:** a 401 response includes a `WWW-Authenticate` header that says how to authenticate (RFC 9110).
- **Send DTOs:** a DTO (data transfer object) is a class shaped for the API. Returning database entities instead means a renamed column breaks every client.
- **Evolve by adding:** a new optional field is safe for clients that ignore unknown fields. Removing or renaming a field is a breaking change that needs a new version.

## Not to be confused with

POST asks the server to process the body, usually to create a new item whose id the server picks. PUT stores the whole body at a URL the client already knows, so repeating it changes nothing more. PATCH changes only the fields it sends. Rule: POST creates, PUT replaces, PATCH edits. [gRPC](card:grpc), the next concept, is a different style that calls typed methods instead of acting on resources.

## Common mistakes

- **Verbs in URLs, such as `/createOrder`.** The method already carries the verb. Use `POST /orders`.
- **`200 OK` with an error inside the body.** Clients, proxies and monitoring read the status code. A failure must use a 4xx or 5xx code.

## Interview Qs

### PUT, POST or PATCH: which one?

POST creates when the server picks the id, such as `POST /orders`. PUT replaces the whole resource at a known URL. PATCH changes only some fields. PUT is idempotent; POST is not, and PATCH is not unless designed so. For a create that may be retried, I add an idempotency key to the POST.

### 409 or 422 for a request that breaks a rule?

422 when the content is well-formed but its values are wrong, such as quantity 0. 409 Conflict when the request clashes with the resource's current state, such as updating an order that someone else changed first, or cancelling one that has already shipped.

### How do you change an API without breaking clients?

Add optional fields; clients that ignore unknown fields keep working. For removals or renames, publish a new version and run the old one until clients move. Contract tests, covered in [Testing Microservices](card:testing-microservices), catch a breaking change before it ships.
