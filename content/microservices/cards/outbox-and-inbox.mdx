## Why it exists

Order Service saves an order and must publish OrderCreated. If it crashes between the commit and the send, the order exists but nobody hears about it.

## How it works

<Mermaid
  alt="Order Service writes the order row and the outbox row in one local transaction. A relay reads the outbox, by polling or by tailing the database log, and publishes to Kafka. Payment Service consumes the event and records its id in an inbox table together with its own change."
  chart={`flowchart LR
  S[Order Service] -- "one transaction" --> DB[(orders + outbox)]
  DB -- "poll or CDC" --> R[Relay]
  R -- OrderCreated --> K[[Kafka]]
  K --> C[Payment Service]
  C -- "eventId + change" --> IN[(payments + inbox)]`}
/>

- Debezium's outbox router uses `aggregateid` as the Kafka key, so one order's events stay in order.
- Polling works on any SQL database; log tailing reads the binlog or WAL and is database-specific.
- The inbox is how an [idempotent consumer](card:delivery-guarantees) remembers what it applied.

## Example

```java
@Transactional
public Order place(NewOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(new OutboxEvent(UUID.randomUUID(), "order", order.id(),
            "OrderCreated", json.write(order)));   // same transaction
    return order;                                  // both rows commit, or neither
}
```

## Interview Qs

### The database update succeeds but publishing the event fails. What do you do?

Use the transactional outbox. Save the event as a row in the same local transaction as the change, then a relay publishes it after commit and retries until the broker accepts it. No event is lost.

### Does the outbox remove duplicates?

No. The relay can crash after publishing but before marking the row sent, so it publishes again. The outbox stops lost events; idempotent consumers (an inbox) stop duplicate effects.
