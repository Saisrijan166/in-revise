## What it is

The transactional outbox is a pattern for publishing an event reliably when a service changes its database. Instead of sending the event to the broker directly, the service saves it as a row in an outbox table, in the same local transaction as the business change. A local transaction is one database's commit-or-rollback unit. A separate relay later reads the outbox and publishes the rows. The inbox is the receiving side: a table of event ids already applied, which makes the consumer [idempotent](card:delivery-guarantees).

## Why it exists

Order Service must save the order and publish OrderCreated, but the database and the broker commit separately. This is the dual-write problem. Publish first, and the save may fail: an event for an order that does not exist. Save first, crash before sending, and the order exists but Inventory never reserves stock. A distributed transaction across the database and the broker, called two-phase commit, is often not supported by one side or the other; you will see it in [distributed transactions](card:distributed-transactions). The outbox turns the two writes into one database write.

## How it works

  S[Order Service] -- "one transaction" --> DB[(orders + outbox)]

/>

1. In one local transaction, Order Service inserts the order row and an outbox row holding OrderCreated. Both commit, or neither does.
2. A relay finds the new outbox row. A polling publisher queries the table every few seconds; log tailing, also called change data capture (CDC), reads the database's transaction log, as Debezium does.
3. The relay publishes the event to Kafka with key = orderId, then marks the row as sent (polling) or saves its position in the log (CDC).
4. If the relay crashes after publishing but before that mark, it publishes the event again after restart.
5. Inventory Service consumes the event. In one local transaction it saves the eventId in its inbox table and reserves stock, so a second copy is skipped.

So the outbox stops lost events, and the inbox stops duplicate effects.

## Example

Order Service places an order without calling Kafka at all:

```java
@Transactional
public Order placeOrder(NewOrder request) {
    Order order = orders.save(Order.pending(request));        // business row
    outbox.save(new OutboxEvent(UUID.randomUUID(), "order",
            order.id(), "OrderCreated", json.write(order)));   // event row
    return order;                  // both rows commit together, or neither
}
```

What to notice:

- There is no `kafkaTemplate.send(...)`. The method writes only to its own database, so it cannot half-succeed.
- The fields match Debezium's outbox router: `id`, `aggregatetype` ("order"), `aggregateid` (the order id), `type` and `payload`. Debezium uses `aggregateid` as the Kafka key, so all events of one order stay in one partition.
- If the method throws after `outbox.save`, both rows roll back, and no event is ever published for this order.
- The `UUID` becomes the event's id, which the consumer stores in its inbox.

## Rules and defaults

- **Polling publisher:** simple and works on any SQL database, but each event waits for the next poll, and publishing strictly in commit order is tricky.
- **Log tailing (CDC):** reads the MySQL binlog or the PostgreSQL write-ahead log (WAL), so it sees each committed insert without querying the table. It needs a CDC tool such as Debezium and database-specific setup.
- **Debezium outbox router (3.7):** expects the columns `id`, `aggregatetype`, `aggregateid`, `type` and `payload`; it routes events to the topic `outbox.event.<aggregatetype>` by default.
- **Order:** keying every event by its aggregate id, as Debezium does, keeps the events of one order in one partition and in sequence.
- **Delivery:** the relay gives at-least-once publishing, never exactly-once. Every consumer still needs an inbox or another idempotency check.

## Not to be confused with

The outbox lives in the sending service's database and makes publishing reliable: a committed change always gets its event. The inbox lives in the receiving service's database and makes consuming safe to repeat: a delivered event is applied once. Rule: outbox = never lose an event; inbox = never apply one twice.

## Common mistakes

- **"Send the event in an after-commit hook, and it is safe."** A crash, or a broker outage, between the commit and the send still loses the event. The outbox row survives the crash, and the relay retries it.
- **"Sending inside the transaction is fine because KafkaTemplate throws on failure."** `send()` is asynchronous and returns a `CompletableFuture`, so the method can commit before the broker has answered.

## Interview Qs

### The database update succeeds but publishing the event fails. What do you do?

Use the transactional outbox. Save the event as a row in the same local transaction as the change. A relay publishes it after commit and retries until the broker accepts it, so a committed change never loses its event. Then make consumers idempotent, because the relay may publish twice.

### Does the outbox remove duplicates?

No. The relay can crash after publishing but before marking the row sent, so it publishes again. The outbox prevents lost events; idempotent consumers, usually with an inbox table, prevent duplicate effects. The two patterns are used together.

### Polling publisher or log tailing?

Polling is simple and works on any SQL database, but each event waits for the next poll, and strict ordering is tricky. Log tailing with a CDC tool such as Debezium reads the database's transaction log, so it sees each commit without querying the table, but it is database-specific and is one more system to run.
