## What it is

A monolith is an application built and deployed as one unit: one program, usually with one database. Deploying means putting a new version of the program on the servers. Microservices split the same application into several small programs called services, each owning one business job, such as orders, payments or stock, and its own data. Each service runs as one or more instances, which are running copies of the program, and services talk through network calls: messages sent over the network, such as HTTP requests.

## Why it exists

In a monolith, every change waits for the same build, the same test run and the same release, and the whole app is scaled together, even when only checkout is busy. With many developers in one codebase, teams block each other. Microservices let the Payment team change, test and release Payment alone, and let you run more instances of only the busy service. The price: calls that were method calls now cross the network, where they can be slow or fail.

Follow one order in the microservices version of the shop:

1. The customer's app sends "place order" to the Order service, which saves the order in its own database.
2. The Order service calls the Inventory service over the network to reserve the stock.
3. It calls the Payment service to charge ₹500, and Payment records the charge in its own database.
4. It tells the Notification service to send the confirmation email.
5. Later, each team releases its own service on its own schedule, as long as the API others call stays compatible.

In the monolith, steps 2 to 4 are method calls inside one program, often in one database transaction. So the key is: the same business flow, but the parts become separate programs joined by the network.

## Example

Reserving stock looks like this in each style:

```java
// Monolith: Inventory is a class inside the same program.
boolean reserved = inventory.reserve("SKU-42", 1);          // a method call

// Microservices: Inventory is a separate program, reached over the network.
HttpRequest request = HttpRequest.newBuilder(URI.create("http://inventory:8080/reservations"))
        .POST(HttpRequest.BodyPublishers.ofString("{\"sku\":\"SKU-42\",\"qty\":1}"))
        .header("Content-Type", "application/json")
        .timeout(Duration.ofSeconds(2))                       // the network may never answer
        .build();
HttpResponse<String> response = http.send(request, BodyHandlers.ofString());
boolean reserved = response.statusCode() == 201;            // could also be 503, or an exception
```

What to notice:

- The monolith line either returns or throws at once. The network version can also be slow, return an error status, or never answer.
- The `timeout` line matters: without it, the JDK `HttpClient` waits forever for a reply that may never come. You will see why in [timeouts and retries](card:timeouts-and-retries).
- `inventory` in the URL is the name of another program. Finding its running instances is a job of its own, covered in [service discovery](card:service-discovery).

## Rules and defaults

- **Own data:** only the Inventory service reads and changes the stock tables; other services ask through its API. You will see this in [database per service](card:database-per-service).
- **Independent deployment:** a service can be released without releasing the others. If two services must always ship together, the split has failed.
- **One owning team:** each service has one team that builds, releases and runs it. By Conway's law, a system's structure copies how its teams communicate, so services follow team lines.
- **Monolith first:** Martin Fowler observes that almost all successful microservice systems began as a monolith that grew too big. Split once the boundaries are known.

## Not to be confused with

A modular monolith is still one deployable program, but its code is split into strict business modules that call each other only through module APIs. Microservices put each module in its own program, with its own data and release. Rule: modular monolith = boundaries inside one program; microservices = boundaries between programs, crossed over the network.

## Common mistakes

- **"Our codebase is large, so we need microservices."** Size alone is not a reason. Split when a part needs its own team, release cycle or scaling, and the boundary is clear.

## Interview Qs

### Why do we need microservices if a monolith already works?

Often we do not. Microservices help when many teams must release, scale and own parts of the system independently. The price is network calls, data that other services see only a little later, harder testing and more operations work, so a working monolith, ideally a modular one, may be the better choice.

### How do you decide whether to create a new microservice?

Split when a business capability has a clear boundary, its own data and an owning team, and when releasing or scaling it on its own has real value. Do not split so finely that every operation needs many remote calls.

### Are microservices just several Spring Boot apps?

No. Separate apps that share tables or must be deployed together are a distributed monolith. Microservices need their own data, stable contracts and independent deployment; the framework does not create those.
