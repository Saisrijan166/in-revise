## What it is

A health probe is a check that Kubernetes runs against a container on a schedule, for example an HTTP GET to `/actuator/health/liveness`. There are three kinds, and each answers one question. Liveness: is the process stuck, so it should be restarted? Readiness: can it serve requests now, so it should get traffic? Startup: has it finished starting, so the other two may begin?

## Why it exists

A running process is not always a working one. Order Service may be deadlocked, with every thread blocked while the process stays alive. Or it may still be loading its cache 40 seconds after start. Without probes Kubernetes sends traffic to it anyway, and users get errors. Probes let Kubernetes restart a stuck container and hold traffic back from one that is not ready. These are two different decisions, so they need two different checks.

## How it works

<Compare id="liveness-vs-readiness-probe" />

1. The container starts. If it has a startup probe, Kubernetes runs only that probe until it passes; liveness and readiness wait.
2. Once startup has passed, Kubernetes runs liveness and readiness for the rest of the container's life, by default every 10 seconds.
3. When readiness passes, the Pod's address is added to its Service, so it gets calls. If readiness later fails 3 times in a row, the Pod is removed from the Service but keeps running. When it passes again, it gets calls again.
4. If liveness fails 3 times in a row, the kubelet, the agent on each machine, kills the container and starts it again. A startup probe that never passes leads to the same restart.

So the key is: readiness controls traffic, liveness controls restarts.

## Example

Order Service runs on Spring Boot 4.1, whose Actuator module serves ready-made health endpoints. All three probes point at Actuator's health groups.

```yaml
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30     # up to 30 x 10 s = 5 minutes to start
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
```

What to notice:

- With the default `periodSeconds` of 10, `failureThreshold: 30` gives the app up to 5 minutes to start. Only after that does liveness begin, so a slow start is not mistaken for a stuck process.
- Startup and liveness use the liveness group, which reports only the app's own state. A database outage does not restart the Pods.
- Readiness uses the readiness group. Spring Boot reports "refusing traffic" until the app's startup runners have finished, then "accepting traffic".
- Remove the startup probe from a service that needs 90 seconds to start, and liveness can restart it before it ever finishes starting.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| `periodSeconds` (how often) | 10 s | Kubernetes 1.37 |
| `timeoutSeconds` (one check) | 1 s | Kubernetes 1.37 |
| `failureThreshold` (misses in a row) | 3 | Kubernetes 1.37 |
| `initialDelaySeconds` | 0 | Kubernetes 1.37 |

- **Probe types:** an HTTP GET (status 200 to 399 counts as success), a TCP connection, a command (exit code 0) or a gRPC health check.
- **No probe set:** Kubernetes treats it as passing, so a Pod without a readiness probe gets traffic as soon as its container runs.
- **Readiness never stops:** it runs during the whole life of the container, so a Pod can leave and rejoin the Service many times.
- **Spring Boot 4.1:** the liveness and readiness groups are on by default; `management.endpoint.health.probes.enabled=false` turns them off. By default neither group checks external systems; you add a check to readiness with `management.endpoint.health.group.readiness.include`.

## Common mistakes

- **Leaving out the readiness probe.** Kubernetes then counts the Pod as ready the moment its container starts, so users get errors while the app is still starting.
- **Making readiness check a database that every Pod shares.** If it goes down, every Pod turns unready and the Service has no Pods left. Add a dependency to readiness only if the Pod truly cannot serve anything without it.

## Interview Qs

### What is the difference between liveness and readiness probes?

Liveness decides whether to restart the container: it should fail only when the process is stuck. Readiness decides whether the Pod gets traffic: failing it only removes the Pod from the Service, and the container keeps running until it is ready again.

### When do you need a startup probe?

When the app may take longer to start than liveness allows. The startup probe gives it failureThreshold × periodSeconds to start, and liveness and readiness begin only after it passes. Without it you would need a long initial delay, which also slows down detecting a real hang.

### Why must liveness not check the database?

If the shared database fails, every instance fails liveness, and Kubernetes restarts all of them together. The restarts cannot fix the database and only add load when it returns. Both the Kubernetes and Spring Boot docs warn that this causes cascading failures.
