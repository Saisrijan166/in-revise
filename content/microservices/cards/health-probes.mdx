## Why it exists

A running process is not always a working one. Kubernetes must know when to restart a container and when to stop sending it requests, and those are different questions.

## How it works

<Compare id="liveness-vs-readiness-probe" />

- Each probe is an HTTP GET, a TCP connect, a command or a gRPC call.
- A rolling update counts a new Pod as available only once it is ready: see [Deployment Strategies](card:deployment-strategies).

## Example

```yaml
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  failureThreshold: 30     # up to 30 x 10 s = 5 minutes to start
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
```

## Interview Qs

### What is the difference between liveness and readiness probes?

Liveness decides whether to restart the container. Readiness decides whether the Pod gets traffic; failing it only removes the Pod from the Service endpoints, and the container keeps running.

### When do you need a startup probe?

When the app may take longer to start than liveness allows. The startup probe gives it failureThreshold × periodSeconds to boot; liveness and readiness begin only after it succeeds.

### Should the readiness probe check the database?

Only if the Pod truly cannot serve without it. If a shared database is down, every Pod turns unready and the Service has no endpoints. Spring Boot adds no dependency checks to readiness by default.
