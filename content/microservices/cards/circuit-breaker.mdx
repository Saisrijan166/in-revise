## What it is

A circuit breaker is a guard placed around the calls to one dependency, such as Payment. It records whether recent calls failed or were too slow. When too many did, it stops sending calls for a while and fails them at once, which is called failing fast. After the wait, it lets a few trial calls through to see whether the dependency has recovered.

## Why it exists

When Payment is down, every Order request still waits for its full [timeout](card:timeouts-and-retries), and retries make it wait longer. Threads pile up, Order slows down, and the callers of Order fail next. This chain is a cascading failure. Meanwhile the struggling Payment service keeps receiving traffic it cannot handle. A breaker fixes both: callers get an answer at once, and Payment gets quiet time to recover.

## How it works

<Mermaid
  alt="Circuit breaker states. CLOSED moves to OPEN when the failure rate reaches the threshold. OPEN moves to HALF_OPEN when the wait time ends. HALF_OPEN goes back to CLOSED if the trial calls succeed, or to OPEN if they fail."
  chart={`stateDiagram-v2
  [*] --> CLOSED
  CLOSED --> OPEN: failure rate reaches threshold
  OPEN --> HALF_OPEN: wait time ends
  HALF_OPEN --> CLOSED: trial calls succeed
  HALF_OPEN --> OPEN: trial calls fail`}
/>

1. CLOSED: calls pass normally, and the breaker records each result in a sliding window, such as the last 100 calls.
2. Once enough calls are recorded, if the share of failed calls, or of slow calls, reaches the threshold, the breaker switches to OPEN.
3. While OPEN, every call fails at once without touching the network. In Resilience4j it throws `CallNotPermittedException`.
4. When the wait time has passed, the breaker moves to HALF_OPEN and lets a few trial calls through. In Resilience4j this happens on the next call, unless automatic transition is switched on.
5. If the trial calls succeed, it goes back to CLOSED. If they still fail, it opens again for another wait.

So the key is: the breaker decides from a rate over many calls, not from one error.

## Example

A small breaker around calls to Payment, which is down, so every call fails:

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
        .slidingWindowSize(4).minimumNumberOfCalls(4)      // judge the last 4 calls
        .failureRateThreshold(50)                           // open at 50% failures or more
        .waitDurationInOpenState(Duration.ofSeconds(30))    // stay OPEN for 30 s
        .build();
CircuitBreaker breaker = CircuitBreaker.of("payment", config);
for (int i = 1; i <= 5; i++) {
    try {
        breaker.executeCallable(() -> { throw new IOException("payment timed out"); });
    } catch (Exception e) {
        System.out.println(i + ": " + e.getClass().getSimpleName() + ", state " + breaker.getState());
    }
}
```

```text output
1: IOException, state CLOSED
2: IOException, state CLOSED
3: IOException, state CLOSED
4: IOException, state OPEN
5: CallNotPermittedException, state OPEN
```

What to notice:

- Calls 1 to 3 really reach Payment and fail, but the breaker stays CLOSED: it has fewer than 4 recorded calls, so it does not judge yet.
- Call 4 completes the window with 100% failures, so the breaker opens right after it.
- Call 5 never reaches Payment. It fails at once with `CallNotPermittedException`, which is what saves the caller's threads.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Opens at | 50% failed calls, over a count-based window of the last 100 calls | Resilience4j 2.x |
| Calls needed first | 100 recorded calls (`minimumNumberOfCalls`) | Resilience4j 2.x |
| Slow call | slower than 60 s; opens at 100% slow calls | Resilience4j 2.x |
| Stays OPEN | 60 s, then 10 trial calls in HALF_OPEN | Resilience4j 2.x |

- **What counts as a failure:** every exception, unless you set `recordExceptions` or `ignoreExceptions`. A 404 your code turns into an exception counts too.
- **Slow calls:** the 60 s default is longer than most call timeouts, so set `slowCallDurationThreshold` lower if slowness should open the breaker.
- **Timeout first:** a hung call is recorded only when it ends, so each call needs a short timeout under the breaker.

## Not to be confused with

A retry repeats one failed call, hoping a brief fault has passed. A circuit breaker stops calling after many failures. A [bulkhead](card:bulkhead), which you will see next, keeps calls going but caps how many run at once. Rule: retry for a blip, breaker for an outage, bulkhead for a slow dependency.

## Common mistakes

- **"One breaker for all outgoing calls."** Then Payment's failures would block calls to a healthy Inventory too. Give each dependency its own breaker.

## Interview Qs

### How do you prevent cascading failures?

Give every call a timeout, retry a few times with backoff, put a breaker on each dependency, use bulkheads so one slow service cannot take every thread, and rate limit incoming work. Monitor each dependency's errors and latency to spot trouble early.

### Why HALF_OPEN, and not straight back to CLOSED?

A service that is just recovering may fall over again under full traffic. A few trial calls test it gently first; only if they succeed does the breaker let all traffic through.

### What should the caller return while the breaker is OPEN?

Something useful at once: a fallback such as cached data or a default, or a clear error the user understands. Never a fake success for an operation like a payment. You will see the choices in [fallbacks](card:fallback-and-degradation).
