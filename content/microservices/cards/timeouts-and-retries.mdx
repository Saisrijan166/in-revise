## What it is

A timeout is the longest a caller waits for a reply before it gives up on that attempt. A retry is a new attempt at the same call after a failure. Backoff means waiting before each retry, and exponential backoff doubles that wait each time. Jitter makes each wait a little random. Together they turn a brief network fault into a success without overloading the service you call.

## Why it exists

Without a timeout, an Order thread calling a hung Inventory service waits forever; the JDK `HttpClient` has no request timeout unless you set one. Soon every thread is stuck and Order stops answering too. Without retries, one dropped packet becomes an error for the customer. Careless retries are worse still: hundreds of clients retrying at once, at every layer, can keep a struggling service down. That surge is called a retry storm.

## How it works

| Failure | Retry? |
| --- | --- |
| Timeout, connection reset | Yes |
| 429 Too Many Requests, 503 Service Unavailable | Yes, after the wait the server asks for, or a backoff |
| 500, 502, 504 | Yes, a few times |
| 400, 401, 403, 404, 422 | No: the same request fails the same way again |

1. Order calls Inventory with a timeout, for example 2 s, chosen from Inventory's slowest normal replies so that healthy calls rarely time out.
2. The attempt fails: it times out, the connection is reset, or Inventory answers 503.
3. Order checks the table above. A transient fault, one that may pass by itself, is worth another try; a 400 or 404 is not.
4. It waits with backoff and jitter: about 200 ms, then about 400 ms, each randomised.
5. It tries again, at most twice more, and only if repeating is safe: a read, or a write with an [idempotency key](card:idempotency).
6. If every attempt fails, it stops and returns an error, or a fallback, which you will see in [fallbacks](card:fallback-and-degradation).

## Example

Order reads stock from Inventory with Resilience4j's `Retry`. The first two attempts fail with a network error (simulated here), the third succeeds:

```java
RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)                                     // 1 call + 2 retries
        .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(
                Duration.ofMillis(200), 2.0, 0.5))          // about 200 ms, then 400 ms, ±50%
        .retryExceptions(IOException.class)                 // retry only network errors
        .build();
Retry retry = Retry.of("inventory", config);
AtomicInteger attempt = new AtomicInteger();
String stock = retry.executeCallable(() -> {
    int n = attempt.incrementAndGet();
    System.out.println("attempt " + n);
    if (n < 3) throw new IOException("connection reset");  // attempts 1 and 2 fail
    return "7 in stock";
});
System.out.println(stock);
```

```text output
attempt 1
attempt 2
attempt 3
7 in stock
```

What to notice:

- `maxAttempts(3)` counts the first call, so there are only two retries. The caller never sees the two failures.
- `ofExponentialRandomBackoff(200 ms, 2.0, 0.5)` gives a wait between 100 and 300 ms before attempt 2, and between 200 and 600 ms before attempt 3. The randomness is the jitter.
- `retryExceptions(IOException.class)` limits retries to network errors. Remove it, and a bug such as an `IllegalArgumentException` is retried three times too.

## Rules and defaults

- **Resilience4j 2.x Retry:** 3 attempts in total, 500 ms apart, by default.
- **What it retries by default:** every exception, until you list `retryExceptions` or `ignoreExceptions`.
- **JDK `HttpClient` (Java 25):** a request without `timeout(...)` can wait forever; with one, `send` throws `HttpTimeoutException` when it passes.
- **Choosing the timeout:** Amazon picks an acceptable rate of false timeouts, such as 0.1%, and uses the callee's matching latency percentile, p99.9.
- **Limit retries overall:** a [retry budget](card:retry-budget) stops retrying once retries are a set share of all requests.

## Not to be confused with

A timeout ends one attempt: it decides when to stop waiting. A retry starts a new attempt: it decides whether to try again. Each attempt has its own timeout, and the number of attempts is capped. Rule: timeout = when to give up on this attempt; retry = whether to make another.

## Common mistakes

- **"Retry at every layer, to be safe."** Attempts multiply down the call chain. Amazon's practice is to retry at a single point in the stack.

## Interview Qs

### Why add jitter to exponential backoff?

Clients that failed at the same moment would otherwise wait the same time and retry together, in waves that hit the recovering service again. Random waits spread the retries out over time.

### Which errors would you retry?

Transient ones: timeouts, connection resets, 429 and 503 after the requested wait, and 500, 502 or 504 a few times. Never 400, 401, 403, 404 or 422, which fail the same way again. A write is retried only if it is idempotent or has an idempotency key.

### How do you choose a timeout value?

From the callee's measured latency, not a guess. Pick how many false timeouts you accept, such as 0.1% of healthy calls, and use the matching percentile, p99.9. Also keep the total time of all attempts below what your own caller waits for you.
