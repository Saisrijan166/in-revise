## Why it exists

Remote calls hang or fail for a moment. Without a timeout, threads can wait forever; a careful retry turns a blip into a success.

## How it works

| Failure | Retry? |
| --- | --- |
| Timeout, connection reset | Yes |
| 429, 503 | Yes, after `Retry-After` or a backoff |
| 500, 502, 504 | Yes, a few times |
| 400, 401, 403, 404, 422 | No: the same request fails again |

- A timeout ends one attempt; a retry starts a new one. You need both.
- Set the timeout from the callee's latency, for example its p99.9.
- Repeat only [idempotent](card:idempotency) calls: the first attempt may have worked.

## Example

```yaml
resilience4j:
  retry:
    instances:
      inventory:                      # GET stock
        maxAttempts: 3                # first call + 2 retries
        waitDuration: 200ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
        enableRandomizedWait: true    # jitter
        retryExceptions: [java.io.IOException]
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Attempts | 3 in total, 500 ms apart | Resilience4j 2.x Retry |
| Errors retried | every exception, unless you list `retryExceptions` | Resilience4j 2.x Retry |
| Request timeout | none: `send()` blocks forever | JDK `HttpClient`, Java 25 |

## Interview Qs

### Timeout vs retry?

A timeout stops waiting for one attempt; a retry makes a new attempt. Each attempt has its own timeout, and attempts are capped.

### Why add jitter to exponential backoff?

Clients that failed together would retry together, in waves that hit the recovering service again. Random waits spread them out.
