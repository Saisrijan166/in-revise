## What it is

CQRS, Command Query Responsibility Segregation, means using one model to change data and a different model to read it. A command asks to change something, such as PlaceOrder; a query only asks for data, such as "show my orders". The write side checks the business rules and saves the change. The read side keeps ready-made views shaped for each screen, often in a separate store.

## Why it exists

The shop's "My orders" page shows each order with its payment status. With [database per service](card:database-per-service), orders and payments live in two services, so one SQL join is impossible, and calling both services on every page load is slow and fails when one is down. CQRS keeps a view that already holds the combined row, updated each time one of the services reports a change. The page then runs one simple query.

## How it works

1. The client sends the command PlaceOrder to the Order service, which checks it and saves the order in its own database.
2. After the commit, the Order service publishes an OrderCreated event through a message broker such as Kafka, the middleman you met in [asynchronous communication](card:sync-and-async-communication), which delivers it to every interested listener.
3. A projector, a small consumer whose only job is to keep a view up to date, receives the event and writes a row into the order summary view. A PaymentCompleted event from the Payment service later updates the same row's status.
4. The client's query, `GET /my-orders`, reads only the view: one table, no joins, no calls to other services.
5. For a moment after the command, the view may not show the new order yet. This lag is the eventual consistency you met in [CAP](card:cap-and-consistency).

So the key is that the write side is the truth, and the view is a copy you can delete and rebuild.

## Example

The projector in the Order service listens to order events and keeps one summary row per order:

```java
@Component
class OrderSummaryProjector {
    private final OrderSummaryRepository views;
    OrderSummaryProjector(OrderSummaryRepository views) { this.views = views; }

    @KafkaListener(topics = "order-events", groupId = "order-summary")
    void on(OrderCreated e) {   // save by orderId: a repeated event overwrites the same row
        views.save(new OrderSummary(e.orderId(), e.customerName(), e.totalInr(), "CREATED"));
    }
}
```

What to notice:

- The projector has no business rules. It only copies event data into the shape the screen needs.
- The row is saved by `orderId`, so if Kafka delivers OrderCreated twice the second save overwrites the same row. An insert here would show the order twice; this is [idempotency](card:idempotency) again.
- Kafka does not delete events when they are read. If the projector is down for a minute, the view falls behind and then catches up from the waiting events; meanwhile the page shows slightly old data.

## Rules and defaults

- **Same or separate store:** the two models may share one database. Separate stores let each side scale and use its own technology, but then the write side must keep the read store in sync.
- **Sync safely:** the database write and the event publish usually cannot share one transaction, so use a [transactional outbox](card:outbox-and-inbox) (later in the messaging topic) and an idempotent projector.
- **Queries never change data:** the read side returns data only and holds no business logic.
- **Use it for parts, not the whole system:** apply CQRS to the one area that needs it, such as order history. For most systems it adds risky complexity.

## Not to be confused with

CQRS changes **who** writes and who reads: two models instead of one. [Event sourcing](card:event-sourcing), the next concept, changes **what** you store: the list of events instead of the current row. They are often combined, but either one can be used alone. Rule: CQRS = two models; event sourcing = events as the truth.

## Common mistakes

- **"CQRS needs two databases."** The read and write models can share one database with different tables or queries. Separate stores are an option for scale, not a requirement.

## Interview Qs

### When would you use CQRS?

When reads and writes differ a lot in shape or load, or a query needs data from several services. Reads often far outnumber writes, so the read side can scale on its own. For simple CRUD it adds moving parts and stale reads for no gain.

### How is the read model kept in sync?

The write side publishes an event after each change, safely through an outbox. A consumer updates the view. Make it idempotent, because events can arrive twice, and expect a short lag between the write and the view.

### Why not just add a read replica of the database?

A plain replica copies the same tables in the same shape, from one database. A CQRS view can have its own shape, built for one screen, and can combine data from several services' events, which a replica of one service's database cannot do.
