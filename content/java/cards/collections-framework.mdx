## What it is

The Collections Framework is the part of `java.util` that holds groups of objects. It has [interfaces](card:abstract-classes-interfaces) that describe a kind of container, such as `List`, and classes that implement them, such as `ArrayList`. `Collection` is the root interface for containers of single items; `List`, `Set` and `Queue` extend it. `Map`, which stores key-value pairs, is a separate hierarchy.

## Why it exists

An array has a fixed length set when it is created, and it has no methods of its own: no "add", no "contains", no "sort". Without the framework every team would write its own growable list and lookup table. The framework gives one set of tested containers with shared interfaces, so `List<Payment>` works the same whether the class behind it is an `ArrayList` or a `LinkedList`, and you can swap one for the other.

Choosing a collection is a short series of questions:

1. Decide what you store. Single items go in a `Collection`; pairs such as "payment id → payment" go in a `Map`.
2. For single items, decide the rules. Duplicates and positions allowed: `List`. Each item once: `Set`. Items waiting to be processed in order: `Queue` or `Deque`.
3. Decide the order you need: none, the order of insertion, or sorted.
4. Pick the class whose operations are cheap for your use (table below).
5. Declare the variable with the interface type and create the class: `List<Payment> payments = new ArrayList<>()`.

The table uses Big-O notation: O(1) means the time does not grow with the number of items, O(log n) grows very slowly, and O(n) grows in step with the size. Amortised O(1) means O(1) on average over many calls, although an occasional call is slower.

| Class | Find | Add | Remove |
|---|---|---|---|
| ArrayList | `get(i)` O(1), `contains` O(n) | at the end: amortised O(1) | in the middle: O(n) |
| LinkedList | `get(i)` O(n) | at either end: O(1) | at either end: O(1) |
| HashSet, HashMap | O(1) on average | O(1) on average | O(1) on average |
| TreeSet, TreeMap | O(log n) | O(log n) | O(log n) |
| PriorityQueue | `peek` O(1) | O(log n) | `poll` O(log n) |

Each class gets its own concept next in this topic.

## Example

A loop removes failed payments. Every `Collection` is `Iterable`, so a for-each loop works on it; under the hood the loop uses an `Iterator`, an object that walks the items one by one.

```java
enum Status { PENDING, PAID, FAILED }
record Payment(String id, long amount, Status status) {}   // amount in paise

List<Payment> payments = new ArrayList<>(List.of(
        new Payment("p1", 900, Status.FAILED),
        new Payment("p2", 500, Status.PAID),
        new Payment("p3", 300, Status.PENDING)));

// for (Payment p : payments) if (p.status() == Status.FAILED) payments.remove(p);  // throws
Iterator<Payment> it = payments.iterator();
while (it.hasNext()) {
    if (it.next().status() == Status.FAILED) it.remove();   // remove through the iterator
}
System.out.println(payments.size() + " left, first is " + payments.get(0).id());
```

```text output
2 left, first is p2
```

What to notice:

- The commented loop calls `payments.remove(p)` behind the iterator's back. On the next step the iterator sees the list changed and throws `ConcurrentModificationException`.
- `it.remove()` removes the item the iterator just returned, so the iterator stays in step with the list.
- `payments.removeIf(p -> p.status() == Status.FAILED)` (Java 8) does the same in one line. The `p -> ...` part is a lambda, which [lambdas](card:lambdas) explains later.

## Rules and defaults

- **Fail-fast iterators:** the iterators of `ArrayList`, `HashSet` and `HashMap` throw `ConcurrentModificationException` when the collection is changed other than through the iterator. The check is best effort, so use it to find bugs, not to make a program correct.
- **Optional operations:** a collection that does not support a method, such as `add` on an unmodifiable list, throws `UnsupportedOperationException`.
- **Unmodifiable collections:** `List.of`, `Set.of` and `Map.of` (Java 9) create collections that never change and reject `null`.
- **SequencedCollection (Java 21):** a new interface shared by `List`, `Deque`, `LinkedHashSet` and `TreeSet`, so all of them offer `getFirst()`, `getLast()` and `reversed()`.
- **Thread safety:** the general-purpose classes are not synchronised. Shared collections need a lock or a [concurrent collection](card:concurrent-collections), which you will see in Concurrency.

## Not to be confused with

`Collection` is the root interface that `List`, `Set` and `Queue` extend. `Collections` is a class of static helper methods, such as `Collections.sort(list)` and `Collections.max(list)`. `Arrays` is the same kind of helper class, but for arrays, such as `Arrays.sort(arr)`. Rule: singular `Collection` is a type you store things in; plural `Collections` and `Arrays` are toolboxes.

## Interview Qs

### Why does Map not extend Collection?

A `Collection` holds single elements, so its `add(E)` takes one item. A map holds key-value pairs, which do not fit that method. Instead a map offers three collection views: `keySet()`, `values()` and `entrySet()`, so you can still loop over it.

### Fail-fast vs fail-safe iterators?

A fail-fast iterator, as in `ArrayList` or `HashMap`, throws `ConcurrentModificationException`, on a best-effort basis, if the collection changes during the loop. Most [concurrent collections](card:concurrent-collections) have weakly consistent iterators instead (the JDK term; "fail-safe" is the informal one): they never throw it and may or may not show later changes.

### Why declare List rather than ArrayList?

The rest of the code depends only on the `List` methods, so you can later switch to another implementation by changing one `new` expression. It also stops callers from relying on methods that only `ArrayList` has.
