## Why it exists

Freeing memory by hand causes crashes and leaks. The JVM finds objects nothing can reach and reuses their memory.

## How it works

| Collector | How it pauses | Choose it for | Flag |
|---|---|---|---|
| Serial | one GC thread, app stopped | heaps up to about 100 MB, one CPU | `-XX:+UseSerialGC` |
| Parallel | many GC threads, app stopped | throughput; 1 s pauses are fine | `-XX:+UseParallelGC` |
| G1 | mostly concurrent, meets a pause goal | general use; default on most machines | `-XX:+UseG1GC` |
| ZGC | concurrent, pauses under 1 ms | low latency, heaps up to 16 TB | `-XX:+UseZGC` |

- New objects start in the young generation; survivors of a few minor GCs move to the old generation.

## Example

```java
class Demo {
    static final List<byte[]> CACHE = new ArrayList<>();
    void handle() {
        CACHE.add(new byte[1_000_000]);   // never removed: leak
    }
    void cycle() {
        Node a = new Node(), b = new Node();
        a.next = b; b.next = a;           // a cycle
        a = null; b = null;               // no root reaches them: both can go
    }
}
```

## Interview Qs

### How does the JVM decide that an object is garbage?

It follows references from the GC roots: locals of running methods, static fields, live threads. Anything not reached is garbage.

### Can a Java program have a memory leak?

Yes: objects still referenced but no longer needed. Usual causes: static collections or caches that only grow, and `ThreadLocal` values never removed on pooled threads.

### Which collector would you choose?

Start with the JVM's choice, usually G1. Use Parallel for throughput-first batch jobs, ZGC when response time matters most.
