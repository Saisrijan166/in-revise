## What it is

Garbage collection is the JVM freeing heap memory used by objects your program can no longer reach. An object is reachable if a chain of references leads to it from a GC root: a local variable of a method that is still running, a static field, or a live thread. The garbage collector (GC) is the part of the JVM that finds unreachable objects and reuses their memory. You never free memory yourself; you only stop referring to objects.

## Why it exists

In languages like C, you free memory by hand. Free it too early and the program later reads memory that now holds something else; forget it and memory fills up slowly. Both bugs are hard to find. Java removes them: when no reference reaches a `Payment` any more, the GC frees it. The price is CPU time for the GC, and short pauses while it works, which is why there are several collectors to choose from.

## How it works

1. New objects are created in the young generation, in an area called eden.
2. When eden fills up, the GC runs a minor collection. It starts at the GC roots, follows every reference, and marks each object it reaches.
3. It copies the reached objects to a survivor space. Everything left in eden is garbage, so eden is reused as a whole. Most objects die young, so this step is cheap.
4. An object that survives several minor collections is moved, or promoted, to the old generation.
5. As the old generation fills up, the GC cleans it too, which takes longer than a minor collection. During some phases it stops every application thread, a stop-the-world pause, so collectors differ mainly in how long and how often these pauses are.

So the key is: the GC keeps what it can reach from the roots; it does not look for objects you "forgot".

## Example

`PaymentAudit` leaks memory, and `cycle` shows that a cycle is not a leak:

```java
class PaymentAudit {
    static final List<Payment> SEEN = new ArrayList<>();      // lives as long as the class
    void record(Payment p) {
        SEEN.add(p);                                          // never removed: a leak
    }
}

void cycle() {
    Node a = new Node(), b = new Node();
    a.next = b; b.next = a;                // a cycle: each points at the other
    a = null; b = null;                    // no root reaches them: both can be freed
}
```

What to notice:

- `SEEN` is a static field, which is a GC root. Every payment added to it stays reachable, so the list grows until `OutOfMemoryError`, although no code reads those payments again.
- After `a = null; b = null`, the two nodes still point at each other, but no root leads to them, so the GC can free both.
- The fix for the leak is to remove entries, cap the list, or not keep it at all. Calling `System.gc()` does not help, because the payments are still reachable.

## Rules and defaults

| Collector | How it pauses | Choose it for | Flag |
|---|---|---|---|
| Serial | one GC thread, application stopped | small data, up to about 100 MB, or one CPU | `-XX:+UseSerialGC` |
| Parallel | many GC threads, application stopped | throughput, when pauses of a second or more are acceptable | `-XX:+UseParallelGC` |
| G1 | mostly concurrent, aims at a pause goal | general use; the default on most machines | `-XX:+UseG1GC` |
| ZGC | concurrent, pauses under a millisecond | low latency, heaps from a few hundred MB to 16 TB | `-XX:+UseZGC` |

- **Default collector (JDK 25):** G1 on a server-class machine, which means 2 or more CPUs and at least 1792 MB of memory; Serial otherwise.
- **G1 pause goal:** `-XX:MaxGCPauseMillis` is 200 ms by default. It is a goal G1 meets with high probability, not a guarantee.
- **System.gc():** only a suggestion; the JVM may ignore it.

## Not to be confused with

The [JVM](card:jdk-jre-jvm) is the whole program that runs your bytecode. The GC is one part of it that frees heap memory. The JIT compiler is another part, which turns frequently run methods into machine code; you will see it in [class loading and JIT](card:class-loading-jit). Rule: JVM runs, JIT speeds up, GC cleans up.

## Common mistakes

- **"Setting a variable to null frees the object."** It removes one reference. The object is freed later, by the GC, and only if no other reference reaches it.
- **"Java cannot leak memory because it has a GC."** The GC frees only unreachable objects. Growing static collections and `ThreadLocal` values never removed on pooled threads keep objects reachable for ever.

## Interview Qs

### How does the JVM decide that an object is garbage?

It follows references from the GC roots: local variables of running methods, static fields and live threads. Every object it reaches is live; everything else is garbage, including groups of objects that point at each other but that no root reaches.

### Can a Java program have a memory leak?

Yes. A leak in Java is an object the program no longer needs but still references, so the GC cannot free it. Usual causes are static collections or caches that only grow, and `ThreadLocal` values that are never removed on pooled threads, which live as long as the thread.

### Which collector would you choose?

Start with the JVM's choice, which is usually G1, and measure. Use Parallel for batch jobs where total throughput matters and long pauses are acceptable, and ZGC when response time matters most, since its pauses stay under a millisecond. Serial suits small heaps and single-CPU containers.
