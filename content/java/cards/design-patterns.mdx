## What it is

A design pattern is a named, reusable solution to a design problem that keeps coming up, such as "only one object of this class may exist" or "the algorithm must be swappable". It is a shape for classes, not a library you import. Patterns are grouped into three families: creational (how objects are created), structural (how objects are combined) and behavioural (how objects share work). The JDK itself uses many of them.

## Why it exists

Without shared names, a team explains the same idea again and again: "a class that wraps a reader and adds a buffer to it". With patterns, one word carries it: decorator. Each pattern also brings known trade-offs, so you do not rediscover the threading bug in a hand-written singleton. Interviewers ask patterns to see whether you can pick the right one and name its cost.

## How it works

| Pattern | Family | Problem it solves | In the JDK |
|---|---|---|---|
| Singleton | creational | exactly one shared instance | `Runtime.getRuntime()` |
| Factory | creational | a method decides which class to create | `Calendar.getInstance()` |
| Builder | creational | build an object with many optional parts, step by step | `HttpRequest.newBuilder()` (Java 11) |
| Decorator | structural | wrap an object to add behaviour | `BufferedReader` around a `Reader` |
| Adapter | structural | make one interface fit another | `InputStreamReader`, `Arrays.asList` |
| Strategy | behavioural | swap the algorithm | a `Comparator` passed to `sort` |
| Observer | behavioural | notify subscribers of a change | listeners; `java.util.Observable` is deprecated since Java 9 |

Singleton is the pattern you are most often asked to write. A lazy, thread-safe one with double-checked locking is built like this:

1. Make the constructor `private`, so no other class can call `new`.
2. Keep the one instance in a `private static volatile` field, empty at first.
3. In `getInstance()`, check the field without a lock. After the first call it is set, so later calls return at once.
4. If it is empty, lock on the class and check again, because another thread may have created it while you waited.
5. Create the instance and assign it. `volatile` makes sure other threads see a fully built object.

## Example

`PaymentConfig` is a lazy singleton built with double-checked locking.

```java
final class PaymentConfig {
    private static volatile PaymentConfig instance;    // volatile: no half-built object
    private PaymentConfig() { }                        // nobody else can call new
    static PaymentConfig getInstance() {
        if (instance == null) {                        // check 1: no lock on later calls
            synchronized (PaymentConfig.class) {
                if (instance == null) {                // check 2: another thread may have won
                    instance = new PaymentConfig();
                }
            }
        }
        return instance;
    }
}
```

What to notice:

- `getInstance() == getInstance()` is always `true`: every caller gets the same object.
- Remove the second check and two threads that both passed check 1 each create an instance, one after the other.
- Remove `volatile` and the code still compiles and usually works, but a thread can see the reference before the constructor's writes, as the [memory model](card:synchronization) allows.

## Rules and defaults

- **Eager singleton:** `private static final PaymentConfig INSTANCE = new PaymentConfig();` is thread-safe through class initialisation, and is created when the class is first used.
- **Holder idiom:** put that field in a private nested class. The nested class is initialised only when `getInstance()` first reads it, so the instance is lazy and thread-safe with no lock.
- **Enum singleton:** `enum PaymentConfig { INSTANCE; }`. Java forbids creating enum objects through reflection, and deserialisation returns the existing constant.
- **Breaking a class singleton:** reflection can call the private constructor, so throw there if the instance exists. Deserialisation makes a copy unless the class defines `readResolve()` to return the instance. Do not implement `Cloneable`.

## Common mistakes

- **"Every shared service should be a singleton."** Code that calls `PaymentConfig.getInstance()` is tied to that class and cannot be given a fake in a test. Passing the object in through the constructor gives one instance without the global access.

## Interview Qs

### How do you write a thread-safe singleton?

The holder idiom: a private nested class holds a `static final` instance, and class initialisation makes it lazy and thread-safe with no lock. Alternatives are double-checked locking with a `volatile` field, a `synchronized` getter that locks on every call, or a one-constant enum.

### How can a singleton be broken, and how do you stop it?

Reflection can call the private constructor, so throw an exception there if the instance already exists. Serialisation creates a new copy on reading, so add `readResolve()` returning the instance. Cloning makes a copy, so do not implement `Cloneable`. An enum singleton blocks reflection and serialisation copies by itself.

### Why use dependency injection instead of creating objects with new?

Calling `new UpiGateway()` inside `PaymentService` breaks [dependency inversion](card:solid-principles): the class is tied to UPI. Dependency injection is the fix in practice: the gateway arrives through the constructor, so `new PaymentService(new CardGateway())` switches to cards with no edit, and a test passes a fake. Frameworks such as Spring automate this wiring.
