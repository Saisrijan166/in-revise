## Why it exists

Design problems repeat: one shared object, complex construction, swappable rules. A pattern names the fix, so a team can just say "use a builder".

## How it works

| Singleton way | Lazy | Thread-safe | Note |
|---|---|---|---|
| Eager: `static final` field | on first class use | yes | simplest |
| `synchronized getInstance()` | yes | yes | locks on every call |
| Double-checked locking | yes | only with `volatile` | lock only on first call |
| Holder idiom | yes | yes, no lock | inner class loads on first `getInstance()` |
| Enum with `INSTANCE` | on first enum use | yes | safe from reflection and serialisation |

- The [enum](card:enums) way is the only one the JVM itself protects; the others need guards against reflection and serialisation.

## Example

```java
final class Config {
    private static volatile Config instance;          // volatile: no half-built object
    private Config() { }
    static Config getInstance() {
        if (instance == null) {                       // 1st check, no lock
            synchronized (Config.class) {
                if (instance == null) instance = new Config();   // 2nd check
            }
        }
        return instance;
    }
}
```

## Interview Qs

### How do you write a thread-safe singleton?

Holder idiom: a nested class holds the instance; class initialisation makes it lazy and safe with no lock. Or double-checked locking with `volatile`, or an enum.

### How can a singleton be broken, and how do you stop it?

Reflection calls the private constructor: throw there if an instance exists. Serialisation makes a copy: add `readResolve()`. Cloning: do not implement `Cloneable`. An enum handles the first two for you.

### Why use dependency injection instead of creating objects with new?

The class receives what it needs through its constructor, so tests pass a fake and UPI can be swapped for card payments without editing it. Spring automates the wiring.
