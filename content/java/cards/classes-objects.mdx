## What it is

A class is a blueprint for one kind of thing, such as a payment. It declares fields, the data each thing holds, and methods, the actions it can do. An object is one real thing built from that blueprint with `new`: payment 1 and payment 2 are two objects of the class `Payment`, each with its own field values. A variable of type `Payment` does not hold the object itself; it holds a reference, a pointer that leads to the object.

## Why it exists

A shop handles thousands of payments, and each has an id, an amount and a status. Without classes you would keep parallel arrays of ids, amounts and statuses and hope the indexes never drift apart. A class keeps one payment's data together with the code that works on it. You describe the kind once, then create as many objects as you need.

## How it works

1. `new Payment()` reserves memory for one object on the heap, the memory area where all objects live.
2. Every field gets its default value: 0 for numbers, `false` for booleans, `null` for references. Then a [constructor](card:constructors) runs; you will see it next.
3. `new` returns a reference to the object, and `Payment a = ...` stores that reference in the variable `a`.
4. `Payment b = a` copies the reference. There is still only one object, now reachable through `a` and `b`.
5. A call such as `b.markPaid()` runs the method on the object that `b` points to, so its fields change for everyone who points there.

So the key is: variables point to objects; only `new` makes a new one.

## Example

A `Payment` class with fields and two methods, and two variables that share one object.

```java
class Payment {
    long amount;                   // fields: each object has its own; paise
    String status = "PENDING";
    void markPaid() { status = "PAID"; }        // method: works on this object's fields
    long withFees(long... fees) {               // varargs: fees is a long[] inside
        long total = amount;
        for (long f : fees) total += f;
        return total;
    }
}
Payment a = new Payment();
a.amount = 50000;                              // Rs 500
Payment b = a;                                 // copies the reference only
b.markPaid();
System.out.println(a.status + " " + a.withFees() + " " + a.withFees(500, 250));
```

```text output
PAID 50000 50750
```

What to notice:

- `b.markPaid()` changed the status seen through `a`, because `b = a` copied the reference, not the payment.
- `withFees()` with no arguments works: `fees` is an empty array, so the total is just the amount.
- `markPaid` and `withFees` have no `static`, so they are instance methods: each call works on one object's fields. [static](card:static-keyword) shows the other kind.

## Rules and defaults

- **Field defaults:** fields start at 0, `false` or `null` until code sets them. Local variables get no default and must be assigned before use (see [primitive types](card:data-types)).
- **Signature:** two methods in one class may share a name only if their parameter types differ; a different return type alone does not compile.
- **Varargs:** at most one varargs parameter per method, and it must be the last one, as in `void log(String tag, long... values)`.
- **Passing objects to methods:** a method receives a copy of the reference, as [pass-by-value](card:pass-by-value) explains.

## Not to be confused with

The stack is memory that holds each running method's local variables, including reference variables such as `a` and `b`, and frees them when the method returns. The heap is shared memory that holds the objects themselves. Rule: the variable lives on the stack, the object it points to lives on the heap. [JVM memory](card:jvm-memory) covers both in depth later.

## Interview Qs

### What is the difference between a class and an object?

A class is the definition: the fields and methods a kind of thing has. It is written once in source code. An object is one instance created at run time with `new`, with its own field values. One `Payment` class can produce millions of payment objects.

### Is the return type part of the method signature?

No. The signature is the method name plus the parameter types. That is why [overloading](card:polymorphism), which you will see later, needs a different parameter list: two methods that differ only in return type do not compile, because a call could not tell them apart.

### What are the rules for varargs?

A method may have only one varargs parameter, and it must be the last one. Inside the method it is an array. Callers may pass zero or more values, or an array directly.
