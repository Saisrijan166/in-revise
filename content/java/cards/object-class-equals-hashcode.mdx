## Why it exists

Two `new Point(1, 2)` objects are different objects but mean the same value. equals() and hashCode() let collections treat them as one.

## How it works

<Compare id="equals-vs-double-equals" />

- equals() must be reflexive, symmetric, transitive and consistent, and `x.equals(null)` is false.
- Hash collections narrow the search with hashCode(), then confirm with equals(): see [HashMap](card:map-hashmap).
- toString() defaults to `ClassName@hexHash`; override it for readable logs.

## Example

```java
final class Point {
    private final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {       // Object, not Point
        return o instanceof Point p && x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
}
Point a = new Point(1, 2), b = new Point(1, 2);
System.out.println(a == b);           // two objects
System.out.println(a.equals(b));      // same value
```

```text output
false
true
```

## Interview Qs

### Why must equals() take Object, not Point?

`equals(Point p)` is an overload, not an override, so HashSet, which calls `equals(Object)`, never uses it. `@Override` turns this mistake into a compile error.

### What happens if you override equals() but not hashCode()?

Equal objects usually get different identity hash codes, so a HashSet stores both and `map.get(equalKey)` returns null.

### Can a mutable field be used in hashCode()?

It works, but if the field changes while the object is a map key, the Map docs leave behaviour unspecified; lookups usually miss it. Prefer [immutable](card:immutability) keys.
