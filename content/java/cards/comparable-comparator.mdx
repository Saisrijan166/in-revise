## What it is

To sort payments, Java must be able to ask "which of these two comes first?". `Comparable` is an [interface](card:abstract-classes-interfaces) a class implements to answer that itself, in one method, `compareTo(other)`; this is its natural order. `Comparator` is a separate object with a method `compare(a, b)` that answers the same question from outside the class. Both return an int whose sign gives the answer.

## Why it exists

`Collections.sort`, `TreeSet` and `TreeMap` cannot guess an order for your class. A payment could be sorted by id, by amount or by status, and you may need all three on different screens. Some classes, such as those from a library, cannot be edited at all. Comparable gives a class one default order; Comparators give every other order without touching the class.

## How it works

<Compare id="comparable-vs-comparator" />

When you call `list.sort(byAmount)` or `Collections.sort(list)`:

1. The sort picks two items, a and b, to compare.
2. It calls `byAmount.compare(a, b)`, or `a.compareTo(b)` when no Comparator is given.
3. A negative result puts a before b, a positive result puts b before a, and zero means they are equal for this order.
4. It repeats this for other pairs until the whole list is in order. Items that compare as equal keep their original order, because `Collections.sort` is stable.

So the key is: you never write the sorting, only the rule for one pair.

## Example

`Payment` gets a natural order by id; then a Comparator sorts the same list by amount, using the id to break ties.

```java
record Payment(String id, long amount, Status status) implements Comparable<Payment> {
    public int compareTo(Payment other) { return id.compareTo(other.id); }  // natural order: by id
}

List<Payment> list = new ArrayList<>(List.of(new Payment("p3", 500, Status.PAID),
        new Payment("p1", 900, Status.PAID), new Payment("p2", 500, Status.FAILED)));

Collections.sort(list);                                   // uses compareTo: p1, p2, p3
System.out.println(list.get(0).id());
list.sort(Comparator.comparingLong(Payment::amount)       // by amount, low to high
        .thenComparing(Payment::id));                     // same amount: by id
for (Payment p : list) System.out.print(p.id() + " ");
```

```text output
p1
p2 p3 p1 
```

What to notice:

- `compareTo` hands the work to `String.compareTo`, which already gives a natural order for text.
- `Payment::amount` is a method reference: a short way to say "call `amount()` on each payment". You will meet it properly in [lambdas](card:lambdas).
- p2 and p3 both have 500 paise, so `thenComparing(Payment::id)` decides between them. Without it, they would stay in their earlier order.
- Adding `.reversed()` after `comparingLong(Payment::amount)` would sort from the highest amount down.

## Rules and defaults

- **Natural order users:** `Collections.sort(list)`, `list.sort(null)`, `new TreeSet<>()` and `new TreeMap<>()` all use `compareTo`. Pass a Comparator to any of them to use another order.
- **Ready-made orders:** `Comparator.naturalOrder()` and `Comparator.reverseOrder()` give the natural order up and down; `Comparator.nullsFirst(...)` and `nullsLast(...)` place `null` items.
- **Primitive arrays:** `Arrays.sort(int[])` sorts only from low to high. A Comparator needs an object array, such as `Integer[]`.
- **Consistent with equals:** if `compareTo` can return 0 for two objects that are not `equals`, a `TreeSet` keeps only one of them. `BigDecimal` is a known case: `4.0` and `4.00` compare as 0, but `equals` says they differ.

## Not to be confused with

`compareTo` and `compare` answer "which comes first?" and return a negative, zero or positive int. `equals` answers "are these the same value?" and returns a boolean; [equals and hashCode](card:object-class-equals-hashcode) covers it. Rule: ordering methods decide the order; `equals` decides sameness, and the two should agree.

## Common mistakes

- **"`Comparator.comparingLong(p -> p.amount()).reversed()` will compile."** It does not. A call followed by `.reversed()` gets no target type, so the lambda's `p` is treated as `Object`, and `amount()` cannot be found. Write `Payment::amount` or `(Payment p) -> p.amount()`.
- **"compareTo must return -1, 0 or 1."** Any negative or positive number is fine; only the sign counts. Never test `compare(a, b) == -1`.

## Interview Qs

### Why do we need both Comparable and Comparator?

A class has only one `compareTo`, but you may need many orders, or need to sort a class you cannot edit. Comparable gives the one default order, used automatically by sorts and sorted collections. Comparators give every other order from outside the class.

### What does "consistent with equals" mean?

`compareTo` returns 0 exactly when `equals` returns true. If not, a `TreeSet` or `TreeMap` breaks the usual Set or Map rules: it compares with `compareTo`, so it treats two unequal objects as one and silently drops the second.

### How do you sort by two fields, one descending?

Chain comparators: `Comparator.comparing(Employee::dept).thenComparing(Employee::salary, Comparator.reverseOrder())`. The first field decides; the second is used only when the first ties. `.reversed()` at the end would reverse the whole chain, not just the last field.
