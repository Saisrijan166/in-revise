## Why it exists

Threads share objects. Without rules, two threads can interleave a read-modify-write, or one thread may never see another's update.

## How it works

<Compare id="synchronized-vs-volatile" />

- **Happens-before:** if action A happens-before B, B sees A's writes. This is the Java Memory Model's core rule.
- Edges: unlock then a later lock of that monitor, volatile write then read, `start()`, and `join()` returning.
- For a shared counter, [AtomicInteger](card:atomic-integer) is atomic without a lock.

## Example

```java
class Counter {
    private int count;
    synchronized void increment() { count++; }     // locks this
    int get() { synchronized (this) { return count; } }
}

class Worker implements Runnable {
    private volatile boolean running = true;       // one writer, many readers
    public void run() { while (running) { /* work */ } }
    void stop() { running = false; }               // the next read in run() sees it
}
```

## Interview Qs

### Why volatile if synchronized exists?

volatile is lighter: no lock and no blocking. It suits one field that one thread writes and others read, like a stop flag. Any read-modify-write still needs synchronized, a lock or an atomic class.

### synchronized method or synchronized block?

A block locks only the lines that need it and can lock a private object, so other threads wait less. A method locks the whole body on this, or on the Class object if static.

### Can two threads run a static and an instance synchronized method at once?

Yes. They use different monitors: the static one locks the Class object, the instance one locks this.
