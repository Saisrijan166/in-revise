## What it is

When two [threads](card:threads) change the same object at the same time, the result can depend on their timing. This bug is a race condition. `synchronized` is Java's built-in fix: every object has a monitor (also called its intrinsic lock), and code marked `synchronized` must take that monitor before it runs. `volatile` is a lighter keyword for a single field, and the Java Memory Model is the set of rules that says when one thread sees another thread's writes.

## Why it exists

The payment service adds every payment to a shared total. `totalPaise += paise` looks like one step, but the CPU reads the value, adds, and writes it back. Two threads can both read 5,000 and both write 5,500, so one payment disappears from the total. A second problem is visibility: a thread may keep using a value it read earlier and never see another thread's write. `synchronized` fixes both: one thread at a time, and its writes are published to the next.

## How it works

1. Thread A calls `stats.add(500)`. The method is `synchronized`, so A first takes the monitor of the `stats` object.
2. Thread B calls `stats.add(300)`. The monitor is taken, so B waits in the BLOCKED state.
3. A finishes the method and releases the monitor, even if the method threw an exception.
4. B takes the monitor and runs. The Memory Model guarantees that B now sees every write A made before releasing it.

So the key is that a lock does two jobs: it keeps threads apart, and it carries their writes from one thread to the next. Other rules give the same visibility: a write to a `volatile` field is seen by every later read of it, everything before `t.start()` is seen by thread `t`, and everything thread `t` did is seen after `t.join()` returns. These ordering guarantees are called happens-before.

## Example

`PaymentStats` keeps the running total for the payment service, and two threads add to it at once.

```java
class PaymentStats {
    private long totalPaise;
    synchronized void add(long paise) { totalPaise += paise; }   // locks this
    synchronized long total() { return totalPaise; }             // locks this too
}

PaymentStats stats = new PaymentStats();
Runnable addPayments = () -> { for (int i = 0; i < 100_000; i++) stats.add(1); };
Thread a = new Thread(addPayments), b = new Thread(addPayments);
a.start(); b.start();
a.join(); b.join();
System.out.println(stats.total());
```

```text output
200000
```

What to notice:

- Both methods lock the same object, `this`, so an `add()` and a `total()` can never run at the same time.
- Remove `synchronized` from `add()` and the program still runs, but some runs print less, such as `188812`. The bug appears only now and then, which is what makes races hard to find.
- `total()` is synchronized too, not for exclusion but so that the reading thread is sure to see the latest total.

## Rules and defaults

- **Method or block:** a `synchronized` instance method locks `this`; a `static synchronized` method locks the `Class` object. A `synchronized (lock) { ... }` block locks any object you choose, and only around the lines inside it.
- **Release is automatic:** the monitor is released when the method or block ends, normally or by an exception.
- **Reentrant:** a thread holding a monitor can call another method synchronized on the same object without blocking itself.
- **volatile:** goes on a field only. It suits a field that one thread writes and others read, such as a stop flag. It never blocks a thread.
- **wait() and notify():** call them only while holding that object's monitor. `wait()` releases that monitor until another thread calls `notify()` or `notifyAll()`. A thread can wake up without a notify, so always check the condition in a `while` loop around `wait()`.

## Not to be confused with

`synchronized` gives mutual exclusion and visibility: one thread at a time, and its writes are seen by the next. `volatile` gives only visibility and ordering for one field; it never makes a read-modify-write such as `count++` safe. Rule: one writer and a flag, use `volatile`; any update based on the old value, use `synchronized`, a lock or an atomic class (you will see these in [concurrent collections](card:concurrent-collections)).

## Common mistakes

- **"synchronized on a method makes the whole class thread-safe."** It protects only code that locks the same monitor. A second, unsynchronized method that touches `totalPaise` can still race with `add()`.

## Interview Qs

### Why use volatile if synchronized exists?

volatile is lighter: no lock and no blocked threads. It is right for a single field that one thread writes and others read, such as a stop flag or a reference to a finished object. Any read-modify-write still needs synchronized, a lock or an atomic class.

### synchronized method or synchronized block?

A block locks only the lines that need it, so other threads wait less. It can also lock a private object that outside code cannot lock, which prevents strangers from holding your lock. A method locks the whole body on `this`, or on the `Class` object if it is static.

### Why are wait() and notify() in Object, not in Thread?

They act on an object's monitor, and every object has one. A thread waits on the object it has locked, and another thread wakes it through the same object. The waiting is about a condition on shared data, not about a particular thread.
