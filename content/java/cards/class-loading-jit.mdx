## What it is

Class loading is how the [JVM](card:jdk-jre-jvm) brings a class into memory the first time your program needs it. A class loader, an object that finds class files, reads the class's bytes; the JVM checks and prepares them, then runs the class's [static](card:static-keyword) initialisers. JIT (just-in-time) compilation comes next: the JVM first runs bytecode with an interpreter, one instruction at a time, and compiles the methods that run often into machine code for the CPU.

## Why it exists

A payment service has thousands of classes on its class path, from your code and its libraries, and one run uses only some of them. Loading all of them at start-up would waste time and memory, so the JVM loads each class when it is first needed. Interpreting bytecode keeps Java portable, but it is slow. Compiling everything before the program starts would make start-up slow, so the JIT compiles only the hot methods, using what it saw while they ran.

## How it works

1. Your code uses a class for the first time, for example `new PaymentService()`. The application class loader is asked for it.
2. The application loader first asks its parent, the platform loader, which first asks the bootstrap loader. Only if no parent can find the class does the application loader read it from your class path. This is parent delegation.
3. The JVM links the class. Verification checks that the bytecode is well formed and safe; preparation creates the static fields with default values (0, false, null); resolution turns names in the bytecode into real references, either now or on first use.
4. The JVM initialises the class: it runs the static field assignments and `static` blocks once, after initialising the superclass.
5. The interpreter runs the class's methods and counts how often each one runs.
6. A method that runs often enough is compiled by C1, which compiles fast. If it stays hot, C2 recompiles it into highly optimised machine code. This two-step scheme is called tiered compilation.

## Example

`Config` prints when it is initialised, which shows that a constant does not trigger initialisation but a static method call does:

```java
class Config {
    static final int MAX_RETRIES = 3;                // a constant variable
    static { System.out.println("Config initialised"); }
    static void load() { }
}
class Main {
    public static void main(String[] args) {
        System.out.println(Config.MAX_RETRIES);      // constant: copied in at compile time
        Config.load();                               // first active use: initialise now
        Config.load();                               // already initialised: nothing printed
    }
}
```

```text output
3
Config initialised
```

What to notice:

- `3` prints before `Config initialised`. `MAX_RETRIES` is a constant variable, a `static final` primitive or String set to a compile-time constant, so javac copies its value into `Main`.
- Remove `final` and `MAX_RETRIES` becomes an ordinary static field: reading it is then a first active use, and `Config initialised` prints first.
- The second `load()` prints nothing, because a class is initialised only once.

## Rules and defaults

- **Built-in loaders:** bootstrap, built into the JVM, loads core classes such as `String` and is shown as `null` by `getClassLoader()`; platform loads the other Java SE and JDK classes, such as `java.sql`; application loads the class path and module path.
- **Class identity:** a class is identified by its name plus the loader that defined it, so two loaders can each load a different `Config`.
- **Core classes:** only the platform loader or its ancestors may define classes in `java.*` packages; any other loader gets a `SecurityException`.
- **Class.forName vs loadClass:** `Class.forName(name)` loads and initialises the class; `ClassLoader.loadClass(name)` only loads it.
- **Tiered compilation:** on by default in HotSpot; you rarely tune it.

## Not to be confused with

javac compiles your `.java` source into bytecode before the program runs; see [JDK, JRE and JVM](card:jdk-jre-jvm). The JIT compiles bytecode into machine code while the program runs, and only for hot methods. Rule: javac = source to bytecode, ahead of time; JIT = bytecode to machine code, at run time.

## Interview Qs

### What is parent delegation, and why is it used?

Each class loader asks its parent before loading a class itself. So a class that the parent can see is loaded once, by the parent, and core `java.*` classes always come from the JDK, never from application code. Without it, two copies of a class could exist, or an application could replace `String`.

### ClassNotFoundException vs NoClassDefFoundError?

ClassNotFoundException is a checked exception: code asked for a class by name, as with `Class.forName("app.Plugin")`, and no loader found it. NoClassDefFoundError is an Error: a class that was present when the code was compiled is missing, or failed to initialise, when the JVM needs it at run time.

### What does the JIT compiler do, and why does Java get faster after start-up?

HotSpot first interprets bytecode and records how often each method runs. Hot methods are compiled to machine code, first quickly by C1, then with full optimisation by C2, using the profile it gathered. Until that happens the code runs slower, so a freshly started service needs a warm-up before it reaches full speed.
