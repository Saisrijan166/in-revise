## What it is

An exception is an object that Java creates when something goes wrong while a method runs, such as dividing by zero or opening a file that does not exist. Throwing it stops the method at that line and hands the object to whatever code can handle it. Every exception class extends `Throwable`, in an ordinary [inheritance](card:inheritance) tree. Java sorts these classes into two kinds: checked exceptions, which the compiler forces you to deal with, and unchecked ones, which it does not.

## Why it exists

Without exceptions, a method would return a special value, such as -1 or null, and every caller would have to check it. Forget one check and the program carries on with bad data. Exceptions jump straight to the code that handles the failure. Some failures are expected, like a missing receipt file, and the caller must plan for them; others are bugs, like a null where an object was needed. Java marks the expected kind as checked, so the compiler stops you from forgetting it.

## How it works

<Compare id="checked-vs-unchecked" />

1. When you compile, javac looks at every checked exception a method can throw. Each one must be caught there or listed in the method's `throws` clause, or the code does not compile. Unchecked exceptions are not checked.
2. When the program runs and something fails, the JVM or your code creates an exception object and throws it. The rest of the method is skipped.
3. Java looks for a matching catch in the current method, then in the method that called it, and so on up the chain of calls. A catch for a class also catches its subclasses.
4. If nothing catches it, the thread stops and the JVM prints the exception with its stack trace, the list of method calls that led to it. This happens the same way for checked and unchecked exceptions.

So the key is: checked or unchecked decides what the compiler demands, not when the exception happens.

## Example

`PaymentService` has one method that can fail in an expected way and one that fails only on a bug:

```java
class PaymentService {
    String loadReceipt(String file) throws IOException {  // checked: declared here
        return Files.readString(Path.of(file));
    }
    long splitPaise(long amountPaise, int people) {
        return amountPaise / people;                       // unchecked: compiles fine
    }
}
```

The caller must handle the checked one, but nothing forces it to handle the other:

```java
var service = new PaymentService();
try {
    service.loadReceipt("receipt-42.txt");                 // the file does not exist
} catch (IOException e) {
    System.out.println("Caught: " + e);
}
service.splitPaise(1000, 0);                               // nobody catches this one
```

```text output
Caught: java.nio.file.NoSuchFileException: receipt-42.txt
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at PaymentService.splitPaise(Main.java:7)
	at Main.main(Main.java:17)
```

What to notice:

- Remove `throws IOException` and `loadReceipt` stops compiling, because `Files.readString` can throw a checked exception that is neither caught nor declared.
- `catch (IOException e)` also caught `NoSuchFileException`, because that class is a subclass of `IOException`.
- Division by zero compiled without any handling. At run time nothing caught it, so main stopped, and the JVM printed the exception, followed by its stack trace: the `at` lines, newest call first.

## Rules and defaults

- **Checked:** `Exception` and every subclass of it that is not under `RuntimeException`, for example `IOException`, `SQLException` and `InterruptedException`.
- **Unchecked:** `RuntimeException`, `Error` and all their subclasses, for example `NullPointerException`, `IllegalArgumentException`, `ArithmeticException` and `OutOfMemoryError`.
- **Unreachable catch:** a catch for a checked exception that the try block can never throw is a compile error. `Exception` and `Throwable` are exempt from this rule.
- **Error:** the Java API says these are serious problems that a reasonable application should not try to catch. Where `OutOfMemoryError` and `StackOverflowError` come from is covered in [JVM memory](card:jvm-memory).

## Common mistakes

- **"`catch (Exception e)` is a safe default."** It also catches every `RuntimeException`, so real bugs are handled as if they were expected failures. Catch the specific types you can actually handle.
- **"An empty catch block is fine for now."** It hides the failure completely: the program carries on as if nothing went wrong. At least log the exception, or let it propagate.

## Interview Qs

### Why have checked exceptions if unchecked ones exist?

They put expected failures, like a missing file, into the method's signature, so the compiler makes every caller plan for them. Bugs, like a null reference, can happen almost anywhere; declaring them on every method would only add noise. Oracle's rule: if a caller can reasonably recover, make it checked; if not, unchecked.

### Should you catch Error or Throwable?

Normally no. An `Error` such as `OutOfMemoryError` means the JVM itself is in trouble, and application code cannot fix that. `catch (Throwable t)` would catch those errors too, along with every exception, and hide the real problem.

### What is an unreachable catch block error?

A compile error for a catch that can never run. Either it names a checked exception that the try block cannot throw, or an earlier catch already covers its type, as when `catch (IOException e)` comes before `catch (FileNotFoundException e)`.
