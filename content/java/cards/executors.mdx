## What it is

An `ExecutorService` is an object that runs tasks for you on threads it manages. The usual kind is a thread pool: a small set of worker threads that stay alive and take one task after another from a queue. You call `submit(task)`, and it returns at once with a `Future`, an object that will hold the task's result, or its exception, once a worker has run it.

## Why it exists

With `new Thread(task).start()` for every payment, 10,000 payments at once means 10,000 threads. Each thread costs memory and setup time, and the operating system can run only a limited number of them. A pool of, say, 8 threads runs all 10,000 tasks a few at a time and reuses the same threads. Your code also stops managing threads: it only says what to run.

## How it works

<Steps label="A task arrives at a ThreadPoolExecutor">
  <Step title="Below core size">The pool starts a new thread for the task, even if other threads are idle.</Step>
  <Step title="At core size">The task waits in the queue until a thread is free.</Step>
  <Step title="Queue full">The pool starts an extra thread, up to the maximum size.</Step>
  <Step title="At max and queue full">The task is rejected, by default with RejectedExecutionException.</Step>
</Steps>

1. You create a pool with a core size, a maximum size and a queue. No thread exists yet: core threads start only when tasks arrive.
2. Each `submit()` goes through the four checks above, in that order.
3. A worker thread that finishes a task takes the next one from the queue, so threads are reused.
4. The task's return value, or the exception it threw, is stored in its `Future`. `get()` hands it back, waiting if the task has not finished yet.
5. When you are done, you shut the pool down so its threads end.

So the key is the order: threads up to core size, then the queue, then extra threads. With an unbounded queue, step 3 never happens and the maximum size has no effect.

## Example

The payment service charges a payment on a pool, and a second task fails. The last lines build a production-style pool.

```java
try (ExecutorService pool = Executors.newFixedThreadPool(4)) {           // close(): Java 19+
    Future<String> paid = pool.submit(() -> "payment 42 PAID");          // a Callable
    System.out.println(paid.get(2, TimeUnit.SECONDS));                   // waits at most 2 s

    Future<?> failed = pool.submit(() -> { throw new IllegalStateException("bank down"); });
    try { failed.get(); }
    catch (ExecutionException e) { System.out.println("failed: " + e.getCause().getMessage()); }
}   // close() shuts the pool down and waits for its tasks

ExecutorService bounded = new ThreadPoolExecutor(4, 8, 60, TimeUnit.SECONDS,  // core, max, keep-alive
        new ArrayBlockingQueue<>(100),                 // at most 100 waiting tasks
        new ThreadPoolExecutor.CallerRunsPolicy());    // when full, the caller runs the task
```

```text output
payment 42 PAID
failed: bank down
```

What to notice:

- The lambda returns a value, so it is a `Callable` and the `Future` holds a `String`. You will compare the two task types in [Runnable vs Callable](compare:runnable-vs-callable).
- The failing task printed nothing by itself. Its exception appeared only through `get()`, wrapped in an `ExecutionException`; `getCause()` gives the original.
- Without try-with-resources or `shutdown()`, the pool's threads stay alive and the program does not exit.
- `CallerRunsPolicy` makes the submitting thread run the task itself when the pool is full, which slows the producer down instead of losing work.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Rejection policy | `AbortPolicy`: throws `RejectedExecutionException` | ThreadPoolExecutor, Java SE 25 |
| Core threads | Started only when tasks arrive | ThreadPoolExecutor, Java SE 25 |
| Keep-alive | Ends idle threads above core size; core threads only with `allowCoreThreadTimeOut(true)` | ThreadPoolExecutor, Java SE 25 |
| Idle threads in `newCachedThreadPool()` | Removed after 60 seconds | Executors, Java SE 25 |

- **Other policies:** `CallerRunsPolicy` runs the task on the caller, `DiscardPolicy` drops it silently, and `DiscardOldestPolicy` drops the oldest waiting task and retries.
- **Factory pools:** `newFixedThreadPool(n)` and `newSingleThreadExecutor()` use an unbounded queue. The single-thread executor runs tasks one after another, in order.
- **Shutdown:** `shutdown()` stops new tasks and lets queued ones finish, but does not wait. `awaitTermination(timeout)` waits. `shutdownNow()` interrupts running tasks and returns the ones that never started.

## Common mistakes

- **Calling `get()` right after every `submit()`.** The caller then waits for each task in turn, which is no better than one thread. Submit all tasks first, then collect the results.

## Interview Qs

### Why use ExecutorService if Thread already exists?

A `Thread` is one worker for one task. An `ExecutorService` reuses a few threads for many tasks, queues the extra work, limits how many tasks run at once, returns `Future`s with results and exceptions, and shuts everything down in one call.

### How do you shut an executor down cleanly?

Call `shutdown()` so no new tasks are accepted and queued ones finish, then `awaitTermination` with a timeout. If it times out, call `shutdownNow()`, which interrupts running tasks and returns those never started. On Java 19+, `close()` in try-with-resources does the waiting for you.

### How do you choose the size of a pool?

Measure, then size by the kind of work. CPU-heavy tasks gain nothing from more threads than cores, so `Runtime.getRuntime().availableProcessors()` is a starting point. Tasks that mostly wait on I/O can use more threads. Always bound the queue so overload is rejected instead of filling memory.
