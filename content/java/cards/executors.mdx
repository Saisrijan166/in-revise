## Why it exists

Creating a thread per task is costly and unbounded. A pool keeps a few worker threads, feeds them from a queue, and separates submitting work from managing threads.

## How it works

<Steps label="A task arrives at a ThreadPoolExecutor">
  <Step title="Below core size">Start a new thread, even if others are idle.</Step>
  <Step title="At core size">Put the task in the queue.</Step>
  <Step title="Queue full">Start an extra thread, up to the max size.</Step>
  <Step title="At max and queue full">Reject: by default throw RejectedExecutionException.</Step>
</Steps>

- With an unbounded queue, step 3 never happens: the max size has no effect.

## Example

```java
try (ExecutorService pool = Executors.newFixedThreadPool(4)) {       // close(): Java 19+
    Future<Integer> f = pool.submit(() -> 6 * 7);                    // a Callable
    System.out.println(f.get(1, TimeUnit.SECONDS));
}

ExecutorService bounded = new ThreadPoolExecutor(
        4, 8, 60, TimeUnit.SECONDS,                 // core, max, idle keep-alive
        new ArrayBlockingQueue<>(100),              // bounded queue
        new ThreadPoolExecutor.CallerRunsPolicy()); // full: the caller runs it
```

```text output
42
```

## Defaults

| What | Default | Where |
|---|---|---|
| Rejection policy | AbortPolicy: throws RejectedExecutionException | ThreadPoolExecutor, Java SE 25 |
| Core threads | Started only when tasks arrive | ThreadPoolExecutor, Java SE 25 |
| Idle threads in newCachedThreadPool | Removed after 60 seconds | Executors, Java SE 25 |

## Interview Qs

### Why ExecutorService if Thread already exists?

A Thread is one worker for one task. An ExecutorService reuses threads, queues tasks, limits concurrency, returns Futures and handles shutdown.

### How do you shut an executor down cleanly?

Call shutdown() so queued tasks finish, then awaitTermination with a timeout. If it times out, shutdownNow() interrupts running tasks and returns the ones never started.

### A submitted task threw an exception, but nothing was logged. Why?

submit() stores the exception in the Future; it surfaces only when you call get(), as an ExecutionException. With execute() it reaches the thread's uncaught exception handler.
