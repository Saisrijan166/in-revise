## What it is

A virtual thread (final in Java 21) is a `Thread` that the JVM manages itself, instead of one backed for its whole life by an operating-system thread. The threads you have used so far are platform threads: each one wraps an OS thread, which is costly, so a program can have only a limited number of them. The JVM runs a virtual thread on a platform thread, called its carrier, and lets the carrier go whenever the virtual thread waits.

## Why it exists

The simplest server code gives each request its own thread and lets it block while it waits for the bank or the database. With platform threads, a server runs out of threads long before the CPU is busy, because most threads are just waiting. The usual workaround, callback-style asynchronous code, is hard to read and debug. Virtual threads keep the simple blocking style and make threads cheap enough to have one per request.

## How it works

1. You start a virtual thread. It costs little memory, and no OS thread is created for it.
2. The JVM's scheduler, a `ForkJoinPool` with about one carrier thread per CPU core, mounts it on a free carrier, and it runs.
3. The task makes a blocking call, such as a socket read or `Thread.sleep`. The JVM unmounts the virtual thread and saves its state.
4. The carrier is now free and runs another virtual thread.
5. When the I/O finishes, the virtual thread is mounted again, possibly on a different carrier, and continues from the same line.

So the key is that waiting no longer holds an OS thread: thousands of tasks can wait at once on a handful of carriers.

## Example

The payment service makes 10,000 calls to the bank, each waiting 1 second, as in the JEP 444 example.

```java
Instant start = Instant.now();
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {   // Java 21+
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));    // stands in for a slow call to the bank
            return "PAID";
        });
    }
}   // close() waits for all 10,000 tasks
System.out.println("10,000 calls took about " + Duration.between(start, Instant.now()).toSeconds() + " s");
```

What to notice:

- On our runs this printed 1 or 2 seconds. Changing only the executor to `Executors.newFixedThreadPool(200)` took 50 seconds, because only 200 tasks could wait at a time.
- The task code is ordinary blocking code. Nothing in it says "async"; only the executor changed.
- The executor creates a new virtual thread for every task and never reuses one; that is how virtual threads are meant to be used.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Scheduler | A `ForkJoinPool` in FIFO mode | JDK 21+ |
| Carrier threads | Number of available processors (`jdk.virtualThreadScheduler.parallelism`) | JDK 21+ |
| Daemon | Always true; the JVM does not wait for them at exit | Thread, Java SE 25 |
| Priority | Always `NORM_PRIORITY`; setPriority is ignored | Thread, Java SE 25 |

- **Creating them:** `Thread.ofVirtual().start(task)`, `Thread.startVirtualThread(task)` or `Executors.newVirtualThreadPerTaskExecutor()`.
- **Limit access with a Semaphore:** to allow only 10 database calls at once, wrap the call in `semaphore.acquire()` and `release()` in `finally`, instead of using a pool of 10 threads.
- **Pinning:** a virtual thread that runs a native method or a foreign function cannot unmount, so it blocks its carrier. On Java 21 to 23, blocking inside `synchronized` also pinned; Java 24 removed that (JEP 491). JDK Flight Recorder's `jdk.VirtualThreadPinned` event reports long pinning.
- **ThreadLocal:** supported, but do not use it to cache an expensive object per thread; with one thread per task, every task builds a new one.

## Common mistakes

- **Putting virtual threads in a fixed pool "to be safe".** Pools exist to share scarce threads, and virtual threads are not scarce. A pool of them only limits concurrency in a roundabout way; a `Semaphore` says it directly.

## Interview Qs

### When should you not use virtual threads?

For CPU-bound work: if every task is computing, more threads than cores add no throughput. Also be careful with code that blocks inside native calls, which pins the carrier. On Java 21 to 23, long blocking inside `synchronized` pinned as well; Java 24 fixed that.

### Should you pool virtual threads?

No. They are cheap, so create one per task, for example with `newVirtualThreadPerTaskExecutor()`. Pools exist to share an expensive resource. If you need to cap access to something, such as 10 calls to a rate-limited bank API, use a `Semaphore` with 10 permits.

### Virtual threads or CompletableFuture for I/O-heavy code?

Both let many I/O calls wait at once. A [CompletableFuture](card:completable-future) chain does it with callbacks, which split the logic across lambdas and make stack traces harder to read. Virtual threads let you write plain sequential code with try/catch and loops, and the JVM handles the waiting. On Java 21+, virtual threads are often the simpler choice.
