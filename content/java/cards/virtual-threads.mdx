## Why it exists

Thread-per-request code is simple, but platform threads are costly, so a server runs out of them before the CPU is busy.

## How it works

<Mermaid
  alt="Many virtual threads share a few carrier threads. The JVM scheduler, a ForkJoinPool, mounts a runnable virtual thread on a carrier platform thread. When the virtual thread blocks on I/O it unmounts, and the carrier runs another virtual thread."
  chart={`flowchart LR
  V1[Virtual thread 1] --> S{{JVM scheduler}}
  V2[Virtual thread 2] --> S
  V3[Virtual thread 10,000] --> S
  S -- mount --> C1[Carrier 1]
  S -- mount --> C2[Carrier 2]
  C1 --> OS[OS threads]
  C2 --> OS`}
/>

- Most blocking JDK calls, like socket reads and `BlockingQueue.take()`, unmount the thread and free its carrier.
- Code stays plain blocking style: loops, try/catch and readable stack traces, unlike async callback chains.

## Example

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {   // Java 21+
    for (String url : urls) {                     // say, 10,000 URLs
        executor.submit(() -> download(url));     // blocking I/O unmounts it
    }
}                                                 // close() waits for all tasks

Thread.ofVirtual().start(() -> System.out.println("hello"));
```

## Defaults

| What | Default | Where |
|---|---|---|
| Scheduler parallelism | Number of available processors | JDK 21+ (jdk.virtualThreadScheduler.parallelism) |
| Daemon | Always true; cannot be changed | Thread, Java SE 25 |
| Priority | Fixed at NORM_PRIORITY | Thread, Java SE 25 |

## Interview Qs

### When should you not use virtual threads?

For CPU-bound work: more threads than cores does not help. Also watch native calls, which pin the carrier, and on Java 21–23, synchronized blocks around long I/O.

### Should you pool virtual threads?

No. They are cheap, so create one per task. Pools exist to share scarce threads; to cap access to a resource, such as 10 database calls, use a Semaphore.
