## Why it exists

Objects that can change cause bugs when threads share them or when they are map keys. An object that never changes needs no locks and no copies.

## How it works

<Steps label="Make a class immutable">
<Step title="Block subclasses">Declare the class `final`, or make constructors private and use factory methods.</Step>
<Step title="Lock the fields">Make every field `private final` and set it once in the constructor.</Step>
<Step title="No setters">A change returns a new object, like `withItem(...)`.</Step>
<Step title="Copy mutable parts">Copy mutable inputs in, and never hand out the internal object.</Step>
</Steps>

- A [record](card:records-sealed) does steps 1–3 for you; step 4 is still yours.
- Equal-by-value immutable objects make safe keys: see [hashCode()](card:object-class-equals-hashcode).

## Example

```java
public final class Order {
    private final List<String> items;
    public Order(List<String> items) {
        this.items = List.copyOf(items);   // copy in (Java 10+; rejects nulls)
    }
    public List<String> items() { return items; }   // unmodifiable: safe to share
    public Order withItem(String item) {             // a change = a new object
        var next = new ArrayList<>(items);
        next.add(item);
        return new Order(next);
    }
}
```

## Interview Qs

### Why are immutable objects thread-safe?

Their state is fixed once the constructor finishes, so threads can only read it. No thread can see a half-done update, so no locking is needed.

### How do you return a mutable field safely?

Return a copy, or an unmodifiable list such as one from `List.copyOf`. Returning the internal `ArrayList` or `Date` lets the caller change your object.
