## What it is

An immutable object is one whose state cannot change after its constructor finishes. A mutable object, by contrast, has methods that change its fields, such as a setter. To "change" an immutable object you create a new one with the new values. `String`, `BigDecimal` and `LocalDate` from the JDK work this way: `amount.add(fee)` returns a new `BigDecimal` and leaves `amount` as it was.

## Why it exists

`PaymentService` hands one `Payment` to a logger thread, a cache and a report. If any of them can change its amount, the others may see a value they did not expect, or a half-finished update from another thread. If the payment is a `HashMap` key, a change can make it impossible to find, as you saw in [hashCode()](card:object-class-equals-hashcode). An immutable payment removes all three problems: nobody can change it, so it is safe to share with no locks and no copies.

## How it works

<Mermaid
  alt="Defensive copy. The caller's ArrayList is copied by List.copyOf into the payment's own unmodifiable list. When the caller later adds to its ArrayList, the payment's list does not change."
  chart={`flowchart LR
  C["caller's ArrayList: upi"] -- "List.copyOf" --> P["payment.tags: upi (unmodifiable)"]
  C -- "later: add refund" --> C2["caller's list: upi, refund"]
  P -. unchanged .-> P2["payment.tags: upi"]`}
/>

1. Declare the class `final`, so no subclass can add setters or changeable fields.
2. Make every field `private final`. The compiler then forces each field to be set exactly once, by the time the constructor ends.
3. In the constructor, copy every mutable input, such as a `List`. The caller keeps its own list, and changing it later cannot reach inside your object.
4. Add no setters. A method that "changes" something, such as `withAmount`, builds and returns a new object.
5. Never return a mutable internal object. Return an unmodifiable list, or a copy.

So the key is: `final` fixes the fields, and copies stop anyone reaching the objects those fields point to.

## Example

An immutable `Payment` with a list of tags. The caller changes its own list after building the payment.

```java
public final class Payment {                         // final: no subclass can add state
    private final long id, amountPaise;
    private final List<String> tags;
    public Payment(long id, long amountPaise, List<String> tags) {
        this.id = id; this.amountPaise = amountPaise;
        this.tags = List.copyOf(tags);               // copy in (Java 10+)
    }
    public List<String> tags() { return tags; }      // unmodifiable: safe to hand out
    public Payment withAmount(long paise) { return new Payment(id, paise, tags); }
}
var input = new ArrayList<>(List.of("upi"));
var p = new Payment(42, 10_000, input);
input.add("refund");                                 // the caller changes its own list
System.out.println(p.tags());
```

```text output
[upi]
```

What to notice:

- The payment still has only `upi`. Replace `List.copyOf(tags)` with `tags` and it prints `[upi, refund]`: the caller changed your object.
- `p.tags().add("x")` throws `UnsupportedOperationException`, because the list from `List.copyOf` is unmodifiable. So the getter can return it without copying again.
- `withAmount` does not touch `p`. It returns a second `Payment` that shares the same, unchangeable tag list.

## Rules and defaults

- **List.copyOf (Java 10):** returns an unmodifiable list and throws `NullPointerException` if any element is null. If its input is already unmodifiable, it usually returns the same list without copying.
- **Shallow, not deep:** an unmodifiable list of mutable objects still lets each object change. The whole thing is immutable only if the elements are immutable too.
- **Visibility to other threads:** once the constructor finishes, other threads are guaranteed to see the correct values of `final` fields, provided the constructor did not leak `this` to them first.
- **Records:** a [record](card:records-sealed) gives you steps 1, 2 and 4 automatically; copying mutable components is still your job.

## Not to be confused with

A `final` field cannot be pointed at another object, but the object it points to may still change: `final List<String> tags` can still get new items. Immutability is about the object's whole state. Rule: `final` = the reference is fixed; immutable = nothing reachable from the object can change. For read-only lists, `List.copyOf` gives a fixed snapshot, while `Collections.unmodifiableList` gives a read-only view of a list that may still change.

## Interview Qs

### How do you make a class immutable?

Make the class `final`, every field `private final` and set in the constructor, and add no setters. Copy mutable inputs in the constructor and never return a mutable internal object. Methods that need a different value return a new object.

### Why are immutable objects thread-safe?

Their state is fixed once the constructor finishes, so threads can only read it. No thread can see a half-done update, so no locking is needed, and the Java memory model guarantees other threads see the final fields correctly.

### How do you return a mutable field safely?

Return a copy, or an unmodifiable list such as one from `List.copyOf`. Returning the internal `ArrayList` lets the caller change your object without calling any of its methods.
