## What it is

`throw` is the statement that raises an exception: `throw new IllegalArgumentException("amount must be positive")` creates the object and throws it at once. `throws` is a list in a method's signature, such as `void pay(long paise) throws PaymentFailedException`, that tells callers which [checked exceptions](card:exception-hierarchy) may come out of it. A custom exception is a class you write yourself, extending `Exception` for a checked one or `RuntimeException` for an unchecked one.

## Why it exists

Your own code finds problems that only it can see, such as a negative amount or a declined payment, so it needs a way to raise them: that is `throw`. Callers need to know which expected failures to plan for, and the compiler checks this through `throws`. The JDK's exceptions describe technical failures, like `IOException`. A name such as `PaymentFailedException` tells a caller what went wrong in business terms, and lets it catch that failure apart from all others.

## How it works

  M --> C["3. catch: getMessage(), getCause()"]`}

1. `gateway.charge` fails and throws an `IOException`. The rest of `charge` is skipped.
2. Java looks for a matching catch in `charge`, finds none, and passes the exception up to its caller, `pay`. This moving up the calls is called propagation.
3. `pay` catches the `IOException` and throws a new `PaymentFailedException`, passing the `IOException` as its cause. This wrapping is called exception chaining.
4. `pay` declares `throws PaymentFailedException`, because that checked exception now leaves the method. Without it, `pay` does not compile.
5. `main` catches `PaymentFailedException`. `getCause()` returns the original `IOException`, and a printed stack trace shows it as a `Caused by:` line.

So the key is: `throw` acts, `throws` declares, and the cause links the new exception to the old one.

## Example

`PaymentService` raises a standard exception for a bad argument and its own checked exception for a gateway failure:

```java
class PaymentFailedException extends Exception {             // checked
    PaymentFailedException(String message, Throwable cause) {
        super(message, cause);                               // keep the cause
    }
}

void pay(long paise) throws PaymentFailedException {
    if (paise <= 0) throw new IllegalArgumentException("amount must be positive");
    try {
        gateway.charge(paise);                               // may throw IOException
    } catch (IOException e) {
        throw new PaymentFailedException("charge failed for " + paise, e);
    }
}
```

With a gateway that always times out, the caller prints the message and the cause:

```java
try {
    service.pay(500);
} catch (PaymentFailedException e) {
    System.out.println(e.getMessage());
    System.out.println("cause: " + e.getCause());
}
```

```text output
charge failed for 500
cause: java.io.IOException: gateway timeout
```

What to notice:

- `throws PaymentFailedException` is required, because the exception is checked and leaves `pay`. `IllegalArgumentException` is unchecked, so it needs no entry in `throws`.
- `super(message, cause)` hands both values to `Throwable`, which stores them. Drop the cause argument and `getCause()` prints `null`, so the gateway's real error is lost.
- The caller catches the business-level exception only; it does not need to know that the gateway uses I/O.

## Rules and defaults

- **throw:** takes exactly one object whose class is `Throwable` or a subclass. A statement right after it in the same block is unreachable, which is a compile error.
- **throws:** must list every checked exception that can escape the method or constructor; unchecked ones may be listed for documentation, but need not be.
- **Overriding:** an overriding method cannot declare broader checked exceptions than the parent method; see [polymorphism](card:polymorphism).
- **Naming:** by convention a custom exception's name ends in `Exception`.

## Not to be confused with

`throw` is an action inside a method body that raises one exception object now. `throws` is a declaration in the signature, naming exception classes that may leave the method later. Rule: throw = do it, throws = warn about it.

## Common mistakes

- **"Every business error needs its own exception class."** Reuse standard ones when they fit: `IllegalArgumentException` for a bad argument, `IllegalStateException` for a call at the wrong time. Write your own only when callers must tell your failure apart.
- **"Catch, then throw new RuntimeException()."** With no cause, the original exception and its stack trace are gone. Write `throw new RuntimeException("context", e)`.

## Interview Qs

### Why do we need both throw and throws?

They do different jobs. `throw` is the action that raises one exception at a specific line. `throws` is part of the method's contract: it lists what may escape so callers can handle it, and the compiler requires it for checked exceptions. One method can throw without declaring, if the exception is unchecked.

### When should you write a custom exception?

When no standard exception describes the failure, or when callers need to catch your failure separately from others, such as `PaymentFailedException`. Make it checked if the caller can reasonably recover, unchecked if it signals a bug. Otherwise reuse standard ones such as `IllegalArgumentException`.

### What is exception chaining, and why does it matter?

Wrapping a low-level exception as the cause of a higher-level one, through a constructor that takes a `Throwable`, or through `initCause()`. `getCause()` returns the original, and the stack trace prints it as `Caused by:`. Without it, you see where the wrapper was thrown, but not what really failed.
