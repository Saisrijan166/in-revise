## What it is

Polymorphism means "many forms": one method call can run different code. Java has two kinds. Overloading is several methods with the same name but different parameter lists, and the compiler picks one from the arguments. Overriding is a subclass giving its own version of an inherited method with the same signature (the method name plus its parameter types), and the JVM picks the version of the real object while the program runs.

## Why it exists

`PaymentService` handles card, UPI and wallet payments. Without overriding it would need a chain like `if (m instanceof CardPayment) ... else if ...` for every fee rule, and each new payment kind would mean editing every chain. With overriding, the service writes `m.fee(amount)` once and each subclass supplies its own fee. Overloading solves a smaller problem: one name such as `pay` for several argument forms, instead of `payInPaise` and `payWithCurrency`.

## How it works

<Compare id="overloading-vs-overriding" />

Follow the call `m.fee(10_000)` from the example below, where `m` is declared as `PaymentMethod` but holds a `CardPayment`.

1. The compiler looks at the declared type of `m`, which is `PaymentMethod`, and checks that it has a method `fee(long)`. If it does not, the code does not compile.
2. If several overloads share the name, the compiler picks the most specific one that fits the declared types of the arguments. That choice is fixed in the bytecode.
3. At run time the JVM looks at the class of the actual object, here `CardPayment`, and runs that class's override. If the class has none, the parent's version runs. This is called dynamic dispatch.
4. Writing `PaymentMethod m = new CardPayment()` is upcasting: a child object is held in a parent-type variable. It needs no cast and never fails, and step 3 still runs the child's method.

So the key is: overloading is decided by the compiler from declared types, overriding by the JVM from the object.

## Example

A card payment overrides the fee rule, and an overload call shows the compile-time choice.

```java
class PaymentMethod {
    long fee(long paise) { return 0; }
}
class CardPayment extends PaymentMethod {
    @Override long fee(long paise) { return paise * 2 / 100; }   // 2% card fee
}
static void print(Object o) { System.out.println("Object"); }
static void print(String s) { System.out.println("String"); }

PaymentMethod m = new CardPayment();      // upcast: no cast needed
System.out.println(m.fee(10_000));        // overriding: CardPayment's version
Object o = "hi";
print(o);                                 // overloading: o is declared as Object
```

```text output
200
Object
```

What to notice:

- `m` is declared as `PaymentMethod`, yet `fee` returns 200, the card fee. The JVM used the real object's class.
- `print(o)` prints `Object` even though `o` holds a String. The compiler only knows the declared type, `Object`. Calling `print("hi")` directly would print `String`.
- `@Override` asks the compiler to check that the method really overrides something. Misspell it as `fees` and you get a compile error instead of a silent new method.

## Rules and defaults

- **Overloading:** the parameter lists must differ in number, types or order of types. Constructors and static methods can be overloaded.
- **Return type:** an override returns the same type or a subtype, called a covariant return. Two methods in one class that differ only in return type do not compile.
- **Access:** an override may widen access but not narrow it. Overriding a `public` method with a package-private one is a compile error.
- **Checked exceptions:** an override may throw the same checked exceptions, narrower ones or none, never new or broader ones. Unchecked exceptions are always allowed.
- **Not overridable:** a `final` method gives a compile error if a child redefines it. A `private` method is not inherited, so a child method with that name is a new, unrelated method. Constructors are not inherited at all.
- **Fields:** fields are not overridden. A child field with the same name hides the parent's, and the declared type decides which one you read.
- **Downcasting:** `(CardPayment) m` compiles, but throws `ClassCastException` at run time if `m` does not hold a `CardPayment`. Check with `instanceof` first.

## Not to be confused with

Overriding replaces an instance method, and the object decides which version runs. Hiding happens when a child declares a [static method](card:static-keyword) with the same signature: no object is involved. If both classes declare `static void audit()`, then `PaymentMethod m = new CardPayment(); m.audit()` runs the parent's version. Rule: instance methods are overridden and follow the object; static methods are hidden and follow the declared type.

## Interview Qs

### Can we overload a method by changing only its return type?

No. Two methods with the same name and parameter types clash at compile time, whatever they return. The compiler picks an overload from the arguments, and a call like `test()` gives it nothing to choose by when only the return type differs.

### Why use upcasting if the child object already exists?

So code is written once against the parent type. A method that takes a `PaymentMethod` works for card, UPI and every future subclass, and each object still runs its own override. The caller does not change when a new payment kind is added.

### Can you override a static or a private method?

No. A static method with the same signature in a child hides the parent's, and the declared type decides which runs. A private method is not inherited, so a child method with the same name is a separate method, and the parent's code keeps calling its own private version.
