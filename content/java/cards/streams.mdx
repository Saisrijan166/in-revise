## What it is

A stream is a pipeline that takes elements from a source, such as a `List`, passes them through steps and produces one result. Steps such as `filter` (keep some elements) and `map` (change each element) are intermediate operations: each returns a new stream and does no work yet. The last step, such as `toList()` or `count()`, is the terminal operation: it runs the pipeline and ends the stream. Most steps take a [lambda](card:lambdas). A stream stores nothing and never changes its source.

## Why it exists

Without streams, "the amounts of paid payments" is a `for` loop, an `if`, a new list and an `add` call. The how (loop, temporary list) hides the what (keep the paid ones, take their amounts). A stream writes only the what, as a chain of named steps that reads top to bottom. The same pipeline can also run on several threads with one call, `parallelStream()`, although that is not automatically faster.

## How it works

  chart={`flowchart LR

/>

1. `payments.stream()` opens a stream on the list. No element is read yet.
2. Each intermediate call, such as `.filter(...)` and `.map(...)`, adds a step and returns a new stream. Still nothing runs; this is called lazy evaluation.
3. The terminal operation starts the work. It pulls one element at a time through every step: payment 1 goes through `filter` and `map` before payment 2 is read. A `sorted` step is the exception: it must collect every element before it passes on the first.
4. A short-circuiting terminal operation, such as `findFirst`, `anyMatch` or a `limit` step, stops once it has its answer. The rest of the source is never read, so it can even finish on an endless stream like `Stream.iterate(1, x -> x + 1)`.
5. After the terminal operation, the stream is used up. To compute something else, open a new stream from the source.

## Example

This pipeline finds the amount of the first paid payment. `peek` prints each payment as it passes, so you can watch the laziness.

```java
List<Payment> payments = List.of(new Payment(1, 20_000, Status.FAILED),
        new Payment(2, 80_000, Status.PAID), new Payment(3, 90_000, Status.PAID));
Optional<Long> firstPaid = payments.stream()
        .peek(p -> System.out.println("read " + p.id()))
        .filter(p -> p.status() == Status.PAID)
        .map(Payment::amountPaise)
        .findFirst();                                 // terminal, short-circuits
System.out.println(firstPaid.orElse(0L));
```

```text output
read 1
read 2
80000
```

What to notice:

- `read 3` never prints. Payment 2 is paid, so `findFirst` has its answer and stops reading.
- If the chain ended at `.map(...)`, with no terminal operation, nothing would print at all: the pipeline never runs.
- `findFirst` returns an `Optional<Long>`, a box that is empty when no payment matches. `orElse(0L)` gives 0 in that case; [Optional](card:optional) explains it later in this topic.
- `peek` exists mainly for debugging. Do not put real work in it.

## Rules and defaults

- **Intermediate operations:** `filter`, `map`, `flatMap`, `distinct`, `sorted`, `limit`, `skip` and `peek`. Each returns a new stream.
- **Terminal operations:** `toList`, `collect`, `forEach`, `count` (returns a `long`), `reduce`, `min`, `max`, `findFirst`, `findAny`, `anyMatch`, `allMatch` and `noneMatch`.
- **Single use:** operate on a stream only once. The JDK throws `IllegalStateException` when it detects reuse.
- **reduce:** `reduce(0L, Long::sum)` returns the value, and the starting value 0 for an empty stream. `reduce(Long::max)` has no starting value, so it returns an `Optional`. The function must be associative, `(a + b) + c == a + (b + c)`, so parallel parts can be combined in any grouping.
- **count() may skip the steps:** if the count is known from the source, as in `list.stream().peek(...).count()`, the JDK may not run the steps at all, so their side effects never happen.
- **Do not change the source** while the stream runs, and keep lambdas free of side effects.

## Not to be confused with

A [collection](card:collections-framework) stores elements and can be read and changed many times; a stream stores nothing and computes one result, once. `map` turns each element into exactly one new element; `flatMap` turns each element into a stream and joins those streams into one, for example orders into all their items. `reduce` combines elements into one new value, such as a sum; `collect` adds each element into a container, such as a list or map, which [Collectors](card:collectors) covers.

Rule: keep data in a collection; open a stream when you need a result.

## Interview Qs

### Why use a stream if a for loop already works?

A loop gives explicit, step-by-step control and is fine for many tasks. A stream describes the work as named steps, filter, map, collect, which often reads more clearly and can run in parallel with one call. It is not automatically faster, so pick whichever states the intent best.

### What is lazy evaluation in streams, and why does it matter?

Intermediate operations only build the pipeline; nothing runs until a terminal operation starts it. Then each element flows through all the steps one at a time. So `findFirst` or `limit` can stop early without reading the whole source, and an endless stream can still give an answer.

### What does allMatch return on an empty stream?

`true`, and so does `noneMatch`; `anyMatch` returns `false`. With no elements there is no counter-example, so "all match" holds. A validation such as `payments.stream().allMatch(p -> p.amountPaise() > 0)` therefore passes for an empty list; check `isEmpty()` first if that matters.
