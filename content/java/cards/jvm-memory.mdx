## What it is

JVM memory is the set of areas the [JVM](card:jdk-jre-jvm) uses while your program runs. Each [thread](card:threads) has its own stack, where every method call gets a frame: a small block holding that call's local variables. All threads share one heap, where every object created with `new` lives. Class information, such as each class's methods and fields, sits in a separate area that HotSpot, the usual JVM, calls Metaspace.

## Why it exists

Data lives for very different lengths of time. A loop counter is needed only while one method runs, but a `Payment` object may be passed around and kept for minutes. If everything lived in one area, the JVM would have to search for what it can free after every call. With a stack, a method's locals disappear the moment it returns, at no cost. Only heap objects need the [garbage collector](card:garbage-collection), the next concept, to decide when they can be freed.

1. When the JVM starts, it creates the heap and the area for class data, shared by every thread.
2. When a class is first used, its methods, fields and bytecode are stored in Metaspace; you will see this in [class loading](card:class-loading-jit).
3. Each new thread gets its own stack, plus a PC register that points at the instruction it is running.
4. Each method call pushes a frame onto that thread's stack, holding the call's local variables: primitive values, and references to objects.
5. `new Payment(...)` puts the object on the heap. The local variable holds only a reference to it.
6. When the method returns, its frame is popped and its locals are gone. The object stays on the heap until nothing refers to it, and then the GC can free it.

## Example

`pay` creates a payment and passes it on. The comments say where each value lives:

```java
void pay(PaymentService service) {
    long paise = 50_000;                     // primitive local: stored in pay's frame
    Payment p = new Payment(42, paise, Status.PENDING);   // p in the frame; object on the heap
    service.save(p);                         // pushes a frame for save(); popped on return
}

int depth(int n) {
    return depth(n + 1);                     // no base case: StackOverflowError
}
```

What to notice:

- `p` is not the object; it is a reference stored in the frame. `save` gets a copy of that reference, so both frames point at the same `Payment` on the heap.
- When `pay` returns, `paise` and `p` disappear, but the `Payment` survives if `save` stored it somewhere, such as in a list.
- `depth` pushes a new frame on every call and never returns, so the thread's stack fills up and the JVM throws `StackOverflowError`.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Thread stack size, `-Xss` | 1024 KB on Linux x64 | JDK 25 `java` command |
| Maximum heap, `-Xmx` | 1/4 of physical memory | JDK 25 GC ergonomics |
| Initial heap, `-Xms` | 1/64 of physical memory | JDK 25 GC ergonomics |
| Maximum Metaspace, `-XX:MaxMetaspaceSize` | no limit, apart from native memory | JDK 25 `java` command |

- **Static fields:** in HotSpot on Java 8 and later, static variables are stored on the heap, with the class's `Class` object; Metaspace holds only class metadata.
- **Running out:** `StackOverflowError` when one thread's call chain is too deep; `OutOfMemoryError` when the heap, Metaspace or native memory cannot satisfy a request, even after GC.

## Not to be confused with

The JVM stack is the memory for one thread's method calls; `java.util.Stack` and `ArrayDeque` are [collections](card:queue-deque) you create yourself, stored on the heap like any object. The heap is likewise not the heap data structure behind `PriorityQueue`. Rule: memory stack and heap = where the JVM stores calls and objects; Stack and heap collections = data structures in your code.

## Interview Qs

### What is the difference between StackOverflowError and OutOfMemoryError?

StackOverflowError: one thread needs a deeper stack than allowed, usually because of recursion with no base case. OutOfMemoryError: the heap, Metaspace or native memory cannot satisfy a request, even after garbage collection, for example because a cache keeps every object. Both are `Error` subclasses, which a normal application should not try to catch.

### Why did Metaspace replace PermGen in Java 8?

PermGen was a part of the heap for class metadata, with a maximum fixed by `-XX:MaxPermSize`, so applications that loaded many classes could run out of it. HotSpot now keeps class metadata in native memory, limited only by what the machine has, unless you set `-XX:MaxMetaspaceSize`.

### Where are static variables stored?

In HotSpot on Java 8 and later, static fields are on the heap, inside the class's `Class` object, not in Metaspace. Metaspace holds only class metadata, such as the methods and field descriptions of each class.
