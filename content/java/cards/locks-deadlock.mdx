## Why it exists

synchronized cannot give up, time out or be interrupted while waiting. Explicit locks add that control, and every lock brings the risk of a deadlock.

## How it works

<Mermaid
  alt="Deadlock cycle. Thread A holds lock 1 and waits for lock 2. Thread B holds lock 2 and waits for lock 1. Neither can continue."
  chart={`flowchart LR
  A[Thread A] -- holds --> L1[(Lock 1)]
  A -. waits for .-> L2[(Lock 2)]
  B[Thread B] -- holds --> L2
  B -. waits for .-> L1`}
/>

- **Fix:** take locks in one global order, so no cycle can form.
- Or use `tryLock` with a timeout: release what you hold and retry. Retrying in step can cause [livelock](card:livelock).
- **Find it:** a thread dump (`jstack <pid>`) shows who holds what; `ThreadMXBean.findDeadlockedThreads()` reports the cycle.

## Example

```java
private final ReentrantLock lock = new ReentrantLock();

boolean update() throws InterruptedException {
    if (!lock.tryLock(1, TimeUnit.SECONDS)) return false;   // back off, no deadlock
    try {
        // critical section
        return true;
    } finally {
        lock.unlock();                                       // always release
    }
}
```

## Interview Qs

### When would you choose ReentrantLock over synchronized?

When you need tryLock, a timeout, an interruptible wait, fairness, or several Condition objects. Otherwise synchronized is simpler and cannot forget to unlock.

### Deadlock vs livelock vs starvation?

Deadlock: threads blocked forever, each waiting for another. Livelock: threads are active but keep reacting to each other, so none progresses. Starvation: one thread rarely gets a resource because greedy threads hold it.
