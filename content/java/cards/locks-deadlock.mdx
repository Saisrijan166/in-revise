## What it is

`ReentrantLock`, in `java.util.concurrent.locks`, is a lock you hold as an object. You call `lock()` to take it and `unlock()` to release it. It gives the same one-thread-at-a-time rule and the same visibility as [synchronized](card:synchronization), and adds choices such as waiting only for a limited time. Deadlock is the danger that comes with any lock: two or more threads each hold a lock and wait for a lock another one holds, so none of them can ever continue.

## Why it exists

A thread waiting to enter `synchronized` code waits with no limit and cannot be interrupted. If the lock is never released, it waits forever. `ReentrantLock` lets the thread try for a while and then give up, or stop waiting when interrupted. Deadlock matters because it gives no error: the service just stops responding, so you must design it away before it happens.

A transfer between two wallets locks both of them. Follow two transfers that run at the same time:

1. Thread A runs `transfer(wallet1, wallet2)` and locks wallet 1.
2. Thread B runs `transfer(wallet2, wallet1)` and locks wallet 2.
3. A tries to lock wallet 2, which B holds, so A waits.
4. B tries to lock wallet 1, which A holds, so B waits. Each waits for the other, and neither will release first: this is deadlock.

All four conditions hold here: a lock has one owner (mutual exclusion), each thread holds one lock while waiting for another (hold and wait), nobody can take a lock away (no preemption), and the waiting forms a circle (circular wait). So the key is to remove one condition; the easiest is circular wait.

## Example

The fix makes every transfer lock the wallet with the lower id first, so the circle in step 4 cannot form.

```java
static void transfer(Wallet from, Wallet to, long paise) {
    Wallet first = from.id < to.id ? from : to;     // always lock the lower id first
    Wallet second = (first == from) ? to : from;
    first.lock.lock();
    try {
        second.lock.lock();
        try {
            from.balancePaise -= paise;
            to.balancePaise += paise;
        } finally { second.lock.unlock(); }
    } finally { first.lock.unlock(); }
}
```

What to notice:

- Each `Wallet` has its own `final ReentrantLock lock`. Two threads moving money in opposite directions now both lock wallet 1 first, so one simply waits for the other.
- With `first = from` and `second = to`, two threads sending 100,000 transfers each in opposite directions hung on our test run: a real deadlock.
- Every `unlock()` sits in a `finally` block. If the code inside throws and skips `unlock()`, the lock stays held and every later transfer on that wallet waits forever.

## Rules and defaults

- **Idiom:** call `lock()` just before `try`, and `unlock()` as the first line of `finally`.
- **Fairness (Java SE 25):** the default is non-fair, with no order promised among waiting threads. A fair lock favours the longest waiter and prevents starvation, but the Javadoc warns it can be much slower. The untimed `tryLock()` ignores fairness and takes a free lock at once.
- **Interruptible wait:** `lockInterruptibly()` waits for the lock but stops with `InterruptedException` if the thread is interrupted.
- **Conditions:** `newCondition()` gives `await()` and `signal()`, which work like `wait()` and `notify()`, and one lock can have several of them.
- **Reentrant:** the thread that holds the lock can call `lock()` again; it must call `unlock()` once for each `lock()`.

## Not to be confused with

Deadlock: threads are blocked forever, each waiting for a lock another holds. Livelock: threads are not blocked but keep reacting to each other, for example both releasing and retrying in step, so no one progresses. Starvation: one thread rarely gets a resource because others keep taking it. Rule: deadlock = stuck and waiting; livelock = busy but stuck; starvation = one thread left out.

## Common mistakes

- **"Nested locks are fine as long as each one is released in finally."** Release does not help if two threads take the same locks in opposite orders. Order matters as much as release.

## Interview Qs

### When would you choose ReentrantLock over synchronized?

When you need something `synchronized` lacks: `tryLock` with or without a timeout, an interruptible wait, a fair order, or several `Condition` objects on one lock. Otherwise `synchronized` is simpler and cannot leak a lock, because the JVM releases it at the end of the block.

### How do you prevent a deadlock?

Take locks in one global order, for example by account id, so no cycle can form. Hold as few locks as possible, and for as short a time. Where an order is hard to keep, use `tryLock` with a timeout: if a thread cannot get the second lock, it releases the first and retries later.

### What is a ReadWriteLock and when does it help?

It is a pair of locks. Any number of threads can hold the read lock at the same time as long as no thread holds the write lock, which one thread holds alone. It helps when data is read far more often than written, such as a cache of exchange rates; `ReentrantReadWriteLock` is the standard implementation.
