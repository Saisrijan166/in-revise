## Why it exists

A plain [Future](card:future-interface) only lets you block on get(). Real work has steps that depend on each other, run in parallel and can fail.

## How it works

<Mermaid
  alt="A CompletableFuture pipeline. supplyAsync loads a user. thenCompose calls an async method to load the user's orders. thenApply counts them. exceptionally returns 0 on any failure. join waits for the final value."
  chart={`flowchart LR
  S["supplyAsync: load user"] --> C["thenCompose: load orders async"]
  C --> A["thenApply: count"]
  A --> E["exceptionally: 0"]
  E --> J(["join()"])`}
/>

- A failure skips the next steps until `exceptionally` or `handle` deals with it.
- Pass your own Executor for blocking I/O: the shared common pool may not add threads when tasks block.

## Example

```java
CompletableFuture<Integer> orderCount = CompletableFuture
        .supplyAsync(() -> api.findUser(id), ioPool)   // runs on ioPool
        .thenCompose(user -> api.ordersAsync(user))    // returns CompletableFuture<List<Order>>
        .thenApply(orders -> orders.size())            // plain value
        .exceptionally(ex -> 0);                       // fallback on any failure

CompletableFuture<Price> price = CompletableFuture.supplyAsync(() -> api.price(id), ioPool);
CompletableFuture.allOf(orderCount, price).join();     // wait for both
int count = orderCount.join();                         // already done: no blocking
```

## Interview Qs

### Future vs CompletableFuture?

Future can only be waited on or cancelled. CompletableFuture can also be completed by hand, chained, combined and recovered without blocking, and it still implements Future.

### Which thread runs the steps?

Async methods run on the Executor you pass, or else on ForkJoinPool.commonPool(). Non-async steps like thenApply may run on the thread that completed the previous stage, or on the caller.
