## Why it exists

The old `Date` is mutable and `SimpleDateFormat` breaks when threads share it. Java 8 added `java.time`: clear, immutable types for each kind of date and time.

## How it works

| You need | Class | Looks like |
|---|---|---|
| A date, such as a birthday | `LocalDate` | `2026-10-19` |
| A time, such as opening hours | `LocalTime` | `11:30` |
| Date and time, no zone | `LocalDateTime` | `2026-10-19T11:30` |
| Date, time and zone | `ZonedDateTime` | `2026-10-19T11:30+05:30[Asia/Kolkata]` |
| A machine timestamp | `Instant` | `2026-10-19T06:00:00Z` |
| An amount of time | `Duration`, `Period` | `PT1H30M`, `P1M` |

- Across a daylight-saving change, a `Period` of one day keeps the clock time; a `Duration` of one day adds exactly 24 hours.
- `DateTimeFormatter` is immutable and thread-safe, so one constant can serve every thread.

## Example

```java
DateTimeFormatter fmt = DateTimeFormatter.ofPattern("dd-MM-uuuu");
LocalDate start = LocalDate.parse("20-10-2026", fmt);
LocalDate due = start.plusMonths(1);                 // new object; start unchanged
long days = ChronoUnit.DAYS.between(start, due);     // 31
Period gap = Period.between(start, due);             // P1M
Duration call = Duration.ofMinutes(90);              // PT1H30M
```

## Interview Qs

### Why replace Date and SimpleDateFormat?

A shared `Date` can be changed by any code holding it. `SimpleDateFormat` is not synchronized, so threads sharing one corrupt each other's results. The java.time types are immutable and thread-safe.

### LocalDateTime or Instant for the time an event happened?

`Instant`: it marks one exact moment. A `LocalDateTime` has no zone, so the same value is a different moment in Mumbai and London. Add a zone only when showing it to a user.
