## What it is

SOLID is a set of five design principles, one per letter, made popular by Robert C. Martin. Each one is a rule about how classes and [interfaces](card:abstract-classes-interfaces) depend on each other. They are not Java features: the compiler checks none of them. They describe habits that make code easier to change and to test.

## Why it exists

Picture a `PaymentService` that charges UPI and cards in one big `switch`, builds the receipt email and writes the CSV report. A change to the email text means editing, and retesting, the payment code. Adding wallets means another `case` in a method that already works. SOLID gives each job its own class and puts interfaces between them, so one change touches one place.

## How it works

| Letter | Rule | The smell it prevents |
|---|---|---|
| S | One reason to change per class | `PaymentService` that also builds emails and writes CSV |
| O | Add new code instead of editing old code | a `switch (type)` that grows with every payment type |
| L | A subtype works wherever the parent is expected | an override that throws `UnsupportedOperationException` |
| I | Small, focused interfaces | a `Worker` interface that forces a robot to implement `eat()` |
| D | Depend on abstractions | `new UpiGateway()` written inside business code |

1. Find the jobs in a class. Each group of people who might ask for a change (payments team, marketing, finance) is one reason to change, so give each job its own class (S).
2. Put the part that varies, here the payment gateway, behind an interface (D).
3. Write one class per variant. A new variant is a new class, and old code is not edited (O).
4. Check that every implementation keeps the interface's promises, so any of them can be passed in (L).
5. Keep each interface to what its callers use, and split it when some implementers cannot support a method (I).

So the key is: an interface at the point of change, plus the concrete class passed in from outside.

## Example

`PaymentService` depends only on a `PaymentGateway` interface, and each gateway is its own class.

```java
interface PaymentGateway { boolean charge(long paise); }               // D: the abstraction

class UpiGateway implements PaymentGateway {
    public boolean charge(long paise) { return true; }                // calls the UPI provider
}
class CardGateway implements PaymentGateway {                         // O: added, nothing edited
    public boolean charge(long paise) { return paise <= 10_000_000; } // card limit: Rs 1 lakh
}
class PaymentService {                                                // S: only payment rules
    private final PaymentGateway gateway;
    PaymentService(PaymentGateway gateway) { this.gateway = gateway; } // passed in from outside
    PaymentStatus pay(long paise) {
        return gateway.charge(paise) ? PaymentStatus.PAID : PaymentStatus.FAILED;
    }
}
```

What to notice:

- `PaymentService` never names `UpiGateway` or `CardGateway`. Adding a `WalletGateway` is one new class, and `PaymentService` is not edited.
- The gateway arrives through the constructor. This is [dependency injection](card:dependency-injection), which you will see in the next concept; a test can pass a fake gateway.
- `PaymentService` holds no email or report code, so a change to the receipt text never touches it.
- Replace the field type with `UpiGateway` and you lose all three: every new gateway would mean editing this class.

## Not to be confused with

Dependency inversion is the design rule: business code depends on an interface, not on a concrete class. Dependency injection is the technique that supplies the concrete object from outside, through a constructor or a setter. Rule: inversion says what to depend on; injection says how the object gets there.

## Common mistakes

- **"SOLID means an interface for every class."** An interface helps where behaviour varies or must be faked in tests. One for a class with a single, stable implementation is only extra code.
- **"Single responsibility means one method per class."** It means one reason to change. A class can have many methods that all serve the same job.

## Interview Qs

### Explain SOLID with one Java example.

A `PaymentService` holds only payment rules (S). It depends on a `PaymentGateway` interface (D). Adding wallets means a new `WalletGateway` class, not an edit to `PaymentService` (O). Every gateway must behave like one, so any can be passed in (L). The interface has only the method callers need (I).

### Give an example that breaks Liskov substitution.

`Square extends Rectangle`. To stay square, `setWidth` must also change the height. Code that sets width 5 and height 4 expects area 20, but the square returns 16. The fix is no inheritance between them, or immutable shapes that have no setters.

### How do open-closed and dependency inversion relate?

Dependency inversion makes open-closed possible. Because `PaymentService` depends on an interface, a new behaviour is a new implementation passed in from outside, and the existing class stays closed to edits.
