## What it is

Object-oriented programming (OOP) builds a program from objects, each keeping its data together with the methods that work on that data. Four principles describe how such code is organised. [Encapsulation](card:encapsulation) keeps data private behind methods. [Abstraction](card:abstraction) shows what an object does and hides how. Inheritance lets a class reuse a parent class. Polymorphism lets one method call run different code depending on the object.

## Why it exists

In a large program where any code can change any data, one wrong assignment, such as a negative amount, can come from anywhere, and every change risks breaking something far away. OOP limits who can touch what: each object guards its own data, callers depend only on a small contract, and new kinds of objects can reuse old code or replace parts of it without changing the callers.

## How it works

| Principle | What it means | Java tool | Taught in |
|---|---|---|---|
| Encapsulation | data is reached only through the object's methods | `private` fields, public methods | this concept |
| Abstraction | callers use a contract, not the implementation | interfaces, abstract classes | [Abstract classes and interfaces](card:abstract-classes-interfaces) |
| Inheritance | a child class reuses and extends a parent class | `extends` | [Inheritance](card:inheritance), next |
| Polymorphism | one call, different code per object | overriding, overloading | [Polymorphism](card:polymorphism) |

Encapsulation in action, when a caller wants to mark a payment as paid:

1. The caller cannot write `payment.status = "PAID"`, because `status` is private.
2. It calls the public method `markPaid()` instead.
3. `markPaid()` checks the current state first and refuses if the payment is not pending.
4. Only then does it change the field, so a payment can never be paid twice.

## Example

`Payment` hides its fields and allows only valid changes.

```java
public class Payment {
    private final long amount;                 // hidden: no code outside can set it
    private String status = "PENDING";

    public Payment(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        this.amount = amount;
    }
    public long getAmount() { return amount; }  // getter; there is no setter
    public String getStatus() { return status; }
    public void markPaid() {                    // the only way to change status
        if (!status.equals("PENDING")) throw new IllegalStateException("already " + status);
        status = "PAID";
    }
}
```

What to notice:

- `throw` stops the method with an error; you will see exceptions properly in [exceptions](card:exception-hierarchy). Here it means no payment with a zero or negative amount can ever exist.
- `amount` has a getter but no setter, so callers can read it but never change it. Leaving out a setter is part of encapsulation.
- Calling `markPaid()` twice throws `IllegalStateException: already PAID`. With a public `status` field, nothing would stop a second payment.

## Not to be confused with

Encapsulation is about protecting data: an object's fields are private, and its own methods decide what changes are allowed. Abstraction is about design: callers depend on a simple contract, such as an interface with a `charge()` method, and do not know which class does the work. Rule: encapsulation hides the data, abstraction hides the implementation.

## Interview Qs

### What is the difference between encapsulation and abstraction?

Encapsulation is about data: keep fields private and allow changes only through methods that check them. Abstraction is about design: show a simple contract, such as an interface, and hide how it is done. A class can be well encapsulated and still expose a poor abstraction.

### Why use a getter and setter instead of a public field?

A setter can validate the value, keep the object consistent and log or reject changes. The field's type or storage can change later without breaking callers. You can also offer a getter with no setter, making the field read-only from outside. A public field allows any value from anywhere.

### What are the two kinds of polymorphism in Java?

Compile-time polymorphism is method overloading: the compiler picks a method by the argument types. Run-time polymorphism is method overriding: the JVM picks the child's version based on the actual object. Both are covered in [polymorphism](card:polymorphism).
