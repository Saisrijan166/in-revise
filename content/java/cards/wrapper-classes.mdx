## What it is

A wrapper class is a class whose object holds one primitive value. Each of the eight [primitive types](card:data-types) has one: `int` has `Integer`, `double` has `Double`, `char` has `Character`, and so on. Autoboxing is Java turning a primitive into its wrapper for you, and unboxing is the reverse. Because a wrapper is an object, a wrapper variable holds a reference, which can be `null`.

## Why it exists

Java's collections, such as `List`, hold only objects, so `List<int>` does not compile. Without wrappers you could not keep a list of payment amounts as numbers. A wrapper puts the number inside an object, so `List<Integer>` works. Wrappers also give `null` for "no value", and they hold helpers such as `Integer.parseInt("42")` and `Integer.MAX_VALUE`. Autoboxing removes the conversion code you would otherwise write by hand.

## How it works

<Compare id="primitive-vs-wrapper" />

1. Where an object is needed and you give an `int`, the compiler inserts `Integer.valueOf(...)`. This is autoboxing.
2. `Integer.valueOf` returns a cached object for -128 to 127 and usually a new object for other values.
3. Where an `int` is needed and you give an `Integer`, the compiler inserts `.intValue()`. This is unboxing, and it throws `NullPointerException` if the reference is `null`.
4. With `==`, if one side is a primitive, Java unboxes the other and compares values. If both sides are wrappers, it compares references.

So the conversions are invisible, which is exactly why their failures surprise people.

## Example

A list of payment amounts, then the comparisons interviewers ask about:

```java
List<Integer> amounts = new ArrayList<>();
amounts.add(500);                     // autoboxing: int 500 becomes an Integer
int first = amounts.get(0);           // unboxing: Integer back to int
Integer a = 127, b = 127;
System.out.println(a == b);           // true: both are the one cached object
Integer c = 1000, d = 1000;
System.out.println(c == d);           // false: two objects, == compares references
System.out.println(c.equals(d));      // true: same value
System.out.println(c == 1000);        // true: one side is int, so c is unboxed
Integer missing = null;
// int x = missing;                   // would throw NullPointerException
```

```text output
true
false
true
true
```

What to notice:

- `List<Integer>` is required; `List<int>` would not compile. The `add` and `get` calls convert silently.
- 127 and 1000 behave differently only because of the cache. The code is identical, which is why `==` on wrappers is a classic bug.
- `c == 1000` is a value comparison, because the literal is an `int`.
- Uncomment the last line and the program compiles but crashes there, possibly far from where the `null` came from.

## Rules and defaults

- **Guaranteed cache:** when a constant value is boxed, the JLS promises one shared object for `true` and `false`, `char` values `\u0000` to `\u007f`, and whole numbers -128 to 127. `Integer.valueOf` always caches -128 to 127.
- **Bigger cache:** HotSpot can cache more `Integer` values with `-XX:AutoBoxCacheMax`, but only -128 to 127 is guaranteed.
- **parseInt vs valueOf:** `Integer.parseInt("42")` returns an `int`; `Integer.valueOf("42")` returns an `Integer`. Both throw `NumberFormatException` for text that is not a number.
- **Constructors:** `new Integer(5)` and `new Integer("5")` are deprecated since Java 9; use `valueOf` or autoboxing.
- **Field default:** an `Integer` field starts as `null`, not `0`.

## Interview Qs

### Why do we need wrapper classes?

Collections and generics accept only objects, so `List<Integer>` needs the wrapper. A wrapper can also be `null` to mean "no value", for example an optional field. And the wrapper classes hold helpers and constants such as `Integer.parseInt` and `Integer.MAX_VALUE`.

### Why is 127 == 127 true but 128 == 128 false for Integer?

Boxing reuses cached objects for -128 to 127, so both variables point to one object and `==`, which compares references, is true. 128 is outside the guaranteed range, so boxing usually creates two objects and `==` is false. Use `equals` for values.

### When does autoboxing throw NullPointerException?

When a `null` wrapper is unboxed: assigning it to an `int`, doing arithmetic with it, comparing it with an `int` using `==`, or returning a `null` `Integer` from a method declared to return `int`. The stack trace points at that line, not where the `null` was set.
