## What it is

JDBC (Java Database Connectivity) is the standard Java API, in the `java.sql` package, for talking to relational databases with SQL. It is mostly interfaces: `Connection` (an open session with the database), `PreparedStatement` (SQL to run) and `ResultSet` (the rows that come back). A JDBC driver is the database vendor's library that implements these interfaces for PostgreSQL, MySQL or Oracle.

## Why it exists

Every database speaks its own network protocol. Without a common API, code written for PostgreSQL would have to be rewritten for MySQL. JDBC fixes the Java side: your code calls the same interfaces, and you change only the driver jar and the connection URL. Libraries such as Hibernate, which map Java objects to tables, also send their SQL through JDBC.

## How it works

1. Get a `Connection` from a `DataSource`, an object set up once with the database URL and login, by calling `getConnection()`. `DriverManager.getConnection(url, user, password)` also works, and finds the driver on the classpath by itself.
2. Prepare the SQL with `?` placeholders: `con.prepareStatement("SELECT id, status FROM payment WHERE status = ?")`, then set each value by its number: `ps.setString(1, "PAID")`.
3. Execute it. `executeQuery()` returns a `ResultSet`; `executeUpdate()` returns the number of rows changed.
4. Read the rows with `while (rs.next())`. The cursor starts before the first row, and `next()` returns `false` when the rows run out. Read columns with `rs.getString("status")` or `rs.getString(2)`.
5. Close the `ResultSet`, statement and connection, best by opening all of them in [try-with-resources](card:try-catch-finally), so they close even after an exception.

## Example

A transaction is a group of SQL statements that are made permanent together at commit, or undone together at rollback. `markPaid` debits the user's wallet and marks the payment `PAID` as one transaction, on a `Connection con` from the `DataSource`.

```java
con.setAutoCommit(false);                                   // group the next statements
try (PreparedStatement debit = con.prepareStatement(
         "UPDATE wallet SET balance = balance - ? WHERE user_id = ?");
     PreparedStatement mark = con.prepareStatement(
         "UPDATE payment SET status = 'PAID' WHERE id = ?")) {
    debit.setLong(1, amount);                               // first ?
    debit.setString(2, userId);                             // second ?
    debit.executeUpdate();
    mark.setString(1, paymentId);
    mark.executeUpdate();
    con.commit();                                           // both changes become permanent
} catch (SQLException e) {
    con.rollback();                                         // undo the debit too
    throw e;
}
```

What to notice:

- In a test on PostgreSQL 18, a second payment larger than the balance broke the wallet's `balance >= 0` check. `rollback()` ran, and that payment stayed `PENDING` with the wallet unchanged.
- Remove `setAutoCommit(false)` and each `executeUpdate` commits at once, so a failure in `mark` would leave the wallet debited.
- Values go in through `setLong` and `setString`, never by joining strings into the SQL; see [Statement vs PreparedStatement](compare:statement-vs-preparedstatement).

## Rules and defaults

- **Auto-commit:** on for every new `Connection`. Calling `setAutoCommit` in the middle of a transaction, with a change of mode, commits that transaction.
- **Closing with an open transaction:** the result depends on the driver, so the API docs strongly recommend calling `commit()` or `rollback()` before `close()`.
- **ResultSet:** forward-only and read-only by default. It closes by itself when its statement is closed or run again.
- **Drivers:** `DriverManager` loads drivers on the classpath as service providers, so `Class.forName("org.postgresql.Driver")` is not needed with current drivers.
- **Connection pool:** opening a connection is slow, so apps use a pool, for example HikariCP, behind a `DataSource`. Calling `close()` on a pooled connection returns it to the pool.

## Common mistakes

- **"close() on a pooled connection is wasteful, so skip it."** For a pooled connection, `close()` is what hands it back. Without it the connection stays borrowed, and the pool soon has none left.

## Interview Qs

### What are the steps to query a database with JDBC?

Get a `Connection` from a `DataSource`, create a `PreparedStatement` with `?` placeholders, set the values by number from 1, call `executeQuery()`, loop with `rs.next()` and read the columns, then close everything. try-with-resources does the closing, even when an exception is thrown.

### How do you run two updates as one transaction?

Call `setAutoCommit(false)` on the connection, run both updates, then call `commit()`. In the `catch` block call `rollback()`, so neither change stays if one fails. Without this, auto-commit makes each update permanent the moment it runs.

### Why use a connection pool?

Opening a database connection is slow, because it needs a network connection and a login. A pool keeps a set of connections open and lends them out. When code calls `close()`, the connection goes back to the pool for the next request instead of being shut.
