## What it is

A `Map` stores key-value pairs: each key appears once and leads to one value, such as a payment id leading to its `Payment`. `HashMap` is the usual class. It keeps an internal array of buckets, and each bucket holds the entries whose keys hash to it. `LinkedHashMap` adds a remembered order, and `TreeMap` keeps the keys sorted. A `HashSet`, from the [previous concept](card:set-hashset-treeset), is a `HashMap` that uses only the keys.

## Why it exists

To find payment p2 in a list you check every payment until the id matches, which is O(n). With a million payments, every lookup walks up to a million items. A hash table jumps straight to the one bucket where p2 must be, so `get("p2")` takes about the same time with ten entries or ten million.

## How it works

What `map.put(key, value)` does in OpenJDK 25:

1. It calls `key.hashCode()` and mixes the high bits into the low bits, so keys that differ only in the high bits still spread out. A `null` key gets hash 0.
2. It turns the hash into a bucket index with `(capacity - 1) & hash`. The capacity is always a power of two, so this keeps the last few bits.
3. It looks at the entries in that bucket. If one has the same hash and `equals` returns true, it replaces that entry's value and returns the old one.
4. If none matches, it adds a new entry. If the bucket already held 8 entries, it turns into a red-black tree (a balanced, sorted tree, so a search there is O(log n)), provided the table has at least 64 buckets; otherwise the table grows instead.
5. If the number of entries now exceeds capacity × load factor, it doubles the bucket array and moves every entry to its new bucket.

`get(key)` follows steps 1 to 3 and returns the value, or `null` if no key matches.

## Example

Payments are indexed by id, then totalled per status in a `TreeMap`, using the `Payment` record from [the framework](card:collections-framework).

```java
List<Payment> payments = List.of(new Payment("p1", 500, Status.PAID),
        new Payment("p2", 900, Status.FAILED), new Payment("p3", 300, Status.PAID));

Map<String, Payment> byId = new HashMap<>();
for (Payment p : payments) byId.put(p.id(), p);           // key: id, value: the payment
System.out.println(byId.get("p2").amount() + " " + byId.get("p9"));  // p9 is missing

Map<Status, Long> totals = new TreeMap<>();               // keys kept sorted
for (Payment p : payments)
    totals.put(p.status(), totals.getOrDefault(p.status(), 0L) + p.amount());
for (var e : totals.entrySet()) System.out.println(e.getKey() + " = " + e.getValue());
```

```text output
900 null
PAID = 800
FAILED = 900
```

What to notice:

- `byId.get("p9")` returns `null` because no such key exists. Calling `.amount()` on it would throw `NullPointerException`.
- `getOrDefault(..., 0L)` gives 0 for a status seen for the first time, so the running total needs no `if`.
- `TreeMap` sorts enum keys in declaration order (`PENDING`, `PAID`, `FAILED`), so `PAID` prints before `FAILED`. A `HashMap` would promise no order.
- `entrySet()` gives each key with its value in one loop; `totals.forEach((k, v) -> ...)` does the same with a lambda.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Initial capacity | 16 buckets | HashMap, Java SE 25 |
| Load factor | 0.75: a good balance of memory and lookup speed, per the Javadoc | HashMap, Java SE 25 |
| Resize | above capacity × 0.75 entries (12 at first), to about twice the buckets | HashMap, Java SE 25 |
| Bucket to tree | adding to a bucket of 8 entries, when there are 64 or more buckets | HashMap, OpenJDK 8 to 25 |

- **Keys:** a key class must override `equals` and `hashCode` together, and should be immutable; strings, numbers, enums and records work well.
- **Sizing:** if you know you will store n entries, `HashMap.newHashMap(n)` (Java 19) creates a map big enough to hold them without resizing.
- **Tree buckets:** they help most when the colliding keys are `Comparable`, because the tree can then order them. Many keys with the same `hashCode` still slow any hash table down.
- **Thread safety:** `HashMap` is not synchronised. Use [ConcurrentHashMap](card:concurrent-collections) when threads share a map.

## Not to be confused with

`HashMap` gives the fastest lookups but no order. `LinkedHashMap` is a `HashMap` that also keeps the order in which keys were added, or, if you ask, the order in which they were last used. `TreeMap` keeps keys sorted and adds range methods such as `floorKey` and `subMap`, at O(log n) per operation. Rule: HashMap by default, LinkedHashMap for a predictable order, TreeMap for sorted keys.

## Interview Qs

### What is the load factor, and why 0.75?

It is how full the table may get before it grows: with 16 buckets and 0.75, the 13th entry triggers a resize. The Javadoc calls 0.75 a good trade-off: a higher value saves memory but makes buckets longer, so `get` and `put` slow down; a lower value wastes memory.

### HashMap vs Hashtable?

`Hashtable` is a legacy class from Java 1.0 whose methods are all synchronised, and it rejects `null` keys and values. `HashMap` is not synchronised and allows one `null` key. For a map shared by threads, use `ConcurrentHashMap`, not `Hashtable`.

### How would you build an LRU cache in plain Java?

Extend `LinkedHashMap` with access order on: `super(16, 0.75f, true)`. Each `get` then moves the key to the end. Override `removeEldestEntry` to return `size() > max`, so after each `put` the least recently used entry, at the front, is removed.
