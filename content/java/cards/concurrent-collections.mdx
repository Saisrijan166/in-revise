## Why it exists

HashMap and ArrayList are not thread-safe, and wrapping them in one lock makes every thread wait. These classes stay correct under sharing with far less waiting.

## How it works

| Need | Use | Why it fits |
|---|---|---|
| Shared map | `ConcurrentHashMap` | Reads do not lock; atomic `merge`, `compute` |
| Read-mostly list, like listeners | `CopyOnWriteArrayList` | Each write copies the array; iterators use a snapshot |
| Producer-consumer hand-off | `BlockingQueue` | `put` waits while full, `take` while empty |
| Shared counter | `AtomicInteger`, `LongAdder` | Atomic without locks; LongAdder for heavy contention |

- Hashtable and `Collections.synchronizedMap` are thread-safe, but one lock guards everything: see [the comparison](compare:hashmap-vs-concurrenthashmap).

## Example

```java
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge(word, 1, Integer::sum);           // atomic add-or-insert

BlockingQueue<Job> queue = new ArrayBlockingQueue<>(100);
queue.put(job);                                // producer: waits while full
Job next = queue.take();                       // consumer: waits while empty

AtomicInteger hits = new AtomicInteger();
hits.incrementAndGet();                        // an atomic count++
```

## Interview Qs

### Why is ConcurrentHashMap faster than Hashtable?

Hashtable guards the whole map with a single lock, so threads queue up. ConcurrentHashMap has no single exclusion lock: any number of reads and many writes run at the same time.

### Why does ConcurrentHashMap not allow null?

If get() returns null, you could not tell "absent" from "mapped to null". In a single thread you check containsKey; with other threads the map may change between the two calls.

### When would you use CopyOnWriteArrayList?

When reads and iteration far outnumber writes, like a list of listeners. Iterators see a snapshot and never fail; every write copies the whole array, so frequent writes are costly.
