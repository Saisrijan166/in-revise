## What it is

Concurrent collections are the thread-safe collections in `java.util.concurrent`. Many threads can use one of them at the same time without corrupting it, and mostly without waiting for each other. The atomic classes in `java.util.concurrent.atomic`, such as `AtomicInteger`, do the same for a single number. They are the ready-made answer to the race conditions you saw in [synchronization](card:synchronization).

## Why it exists

A [HashMap](card:map-hashmap) is not safe to share: its Javadoc says you must lock it yourself if any thread changes it while others use it. Wrapping it in one lock, as `Hashtable` or `Collections.synchronizedMap` do, is safe, but then every reader waits for every writer. Payment threads that only read a merchant's settings should not queue behind one thread that is updating a different merchant. Concurrent collections let reads and writes on different parts run at the same time.

## How it works

| Need | Use | Why it fits |
|---|---|---|
| Shared map | `ConcurrentHashMap` | Reads generally do not block; `merge` and `compute` are atomic per key |
| Read-mostly list, such as listeners | `CopyOnWriteArrayList` | Each write copies the array, so readers never wait |
| Passing work between threads | `BlockingQueue` | `put` waits while full, `take` waits while empty |
| Shared counter | `AtomicInteger`, `AtomicLong`, `LongAdder` | Atomic updates without a lock |

1. A thread reading a `ConcurrentHashMap` generally does not block, so reads can overlap with writes.
2. A write such as `merge(key, 1, Integer::sum)` updates only that key's entry, atomically, so writes to different keys rarely wait for each other.
3. An `AtomicInteger` update such as `updateAndGet(f)` reads the value, computes the new one and calls `compareAndSet(old, new)`, which stores it only if the value is still `old`. If another thread changed it first, it tries again.
4. A `CopyOnWriteArrayList` write builds a new copy of the array and swaps it in, so an iterator keeps reading the old copy undisturbed.

## Example

The payment service counts four payments per status (two PAID, one FAILED, one PENDING; 2,400 paise in all) and adds up their amounts, from four threads at once.

```java
var countByStatus = new ConcurrentHashMap<Status, Integer>();
var totalPaise = new AtomicLong();

try (var pool = Executors.newFixedThreadPool(4)) {
    for (Payment p : payments) {
        pool.submit(() -> {
            countByStatus.merge(p.status(), 1, Integer::sum);   // atomic add-or-insert for this key
            totalPaise.addAndGet(p.amountPaise());              // atomic +=, no lock
        });
    }
}   // close() waits for all tasks
System.out.println(new TreeMap<>(countByStatus) + " total=" + totalPaise.get());
```

```text output
{PENDING=1, PAID=2, FAILED=1} total=2400
```

What to notice:

- `merge` puts 1 for a new status, or adds 1 to the old count, as one atomic step. A plain `HashMap` here could lose counts.
- `addAndGet` is the atomic version of `total += amount`; with a plain `long` field, updates could be lost as in the race example.
- `new TreeMap<>(...)` only sorts the output by enum order. `ConcurrentHashMap`, like `HashMap`, promises no iteration order.

## Rules and defaults

- **No nulls:** `ConcurrentHashMap` throws `NullPointerException` for a null key or value. A `get()` that returns null always means "absent".
- **Keep compute functions short:** while `compute`, `computeIfAbsent` or `merge` runs its function, other updates may wait. The function must not modify the map itself.
- **Estimates:** `size()`, `isEmpty()` and `containsValue()` reflect a passing state while other threads update. Do not use them to make decisions.
- **LongAdder:** better than `AtomicLong` when many threads update one counter, at the cost of more memory. Its `sum()` is not an exact snapshot during updates, so use it for statistics, not for control.
- **CopyOnWriteArrayList:** every write copies the whole array, so it suits lists that are rarely changed.

## Not to be confused with

`Collections.synchronizedMap(map)` wraps any map so that every call takes one shared lock, and you must lock it yourself while iterating. `ConcurrentHashMap` is built for sharing: reads generally do not block and iteration never throws `ConcurrentModificationException`. Rule: synchronizedMap = one lock for everything; ConcurrentHashMap = shared access by design.

## Interview Qs

### Why is ConcurrentHashMap faster than Hashtable?

`Hashtable` guards the whole map with one lock, so every call, even a read, waits for the current one. `ConcurrentHashMap` reads generally do not block, and it never locks the whole table, so many readers and writers on different keys run at the same time.

### Why does ConcurrentHashMap not allow null?

If `get()` returned null, you could not tell "absent" from "mapped to null". In one thread you would check `containsKey` afterwards, but with other threads the map may change between the two calls, so the answer would be unreliable. Banning null removes the doubt.

### How does AtomicInteger work without a lock?

It uses lock-free atomic operations. The basic one is `compareAndSet(expected, new)`: store the new value only if the current value still equals `expected`. Methods such as `updateAndGet` loop on it: read, compute, compare-and-set, and retry if another thread changed the value first. No thread ever blocks.
