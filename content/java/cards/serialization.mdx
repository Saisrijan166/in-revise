## What it is

Serialisation is turning an object into a sequence of bytes, so it can be written to a file or sent over a network. Deserialisation is the reverse: reading those bytes and building a new object with the same field values. In Java, `ObjectOutputStream` and `ObjectInputStream`, two of the [byte streams](card:java-io), do this work. A class takes part only if it implements `Serializable`, an interface with no methods that only marks the class as allowed.

## Why it exists

Objects live only in the memory of one running JVM. When the program stops, a pending `Payment` is gone, and another JVM cannot read it from your memory. Without serialisation you would write each field to a file by hand and parse it back. Java serialisation does both steps for the whole object, including the objects its fields point to.

## How it works

1. `writeObject(payment)` checks that the class implements `Serializable`, and writes a description of the class, including its `serialVersionUID`.
2. It writes every field that is not `static` and not `transient`. A field that points to another object writes that object too, so the whole graph is saved.
3. `readObject()` reads the class description and compares its `serialVersionUID` with the loaded class. A mismatch throws `InvalidClassException`.
4. It creates the object without calling the class's constructors, then fills the saved fields from the bytes. Fields that were not saved keep their default value.

## Example

A `Payment` is written to a file and read back; its one-time password is marked `transient`.

```java
class Payment implements Serializable {
    private static final long serialVersionUID = 1L;    // version of this class's byte form
    String id = "P1";
    long amount = 50_000;                               // paise
    PaymentStatus status = PaymentStatus.PAID;
    transient String otp = "4821";                      // never written
}
try (var out = new ObjectOutputStream(new FileOutputStream("payment.bin"))) {
    out.writeObject(new Payment());                     // object -> bytes
}
try (var in = new ObjectInputStream(new FileInputStream("payment.bin"))) {
    Payment copy = (Payment) in.readObject();           // bytes -> new object
    System.out.println(copy.id + " " + copy.amount + " " + copy.status + " " + copy.otp);
}
```

```text output
P1 50000 PAID null
```

What to notice:

- `otp` prints `null`, not `"4821"`: it was not written, and the field initialiser does not run on reading.
- `status` is an [enum](card:enums), which serialises by its constant name, so the copy holds the same `PAID` constant.
- Remove `implements Serializable` and `writeObject` throws `NotSerializableException`.

## Rules and defaults

- **serialVersionUID:** if you do not declare one, Java computes it from the class's details, so a small change breaks old data. The API docs strongly recommend declaring it, `private` where possible.
- **Static fields:** never written, because they belong to the class, not to the object.
- **Non-serialisable superclass:** its fields are not written. On reading, its no-arg constructor runs, and it must be accessible to the subclass.
- **Records (Java 16):** a serialisable [record](card:records-sealed) is rebuilt through its canonical constructor, so its checks still run.
- **Custom control:** `Externalizable` lets the class write and read its own state. `readResolve()` replaces the object that was read, which keeps a [singleton](card:design-patterns) single.
- **Untrusted data:** the API docs say deserialising it is inherently dangerous and should be avoided. If you must, set an [ObjectInputFilter](card:serialization-filter) (Java 9) to allow only known classes.

## Interview Qs

### What is serialVersionUID and why should you declare it?

It is the version number of a serialisable class. Reading bytes written with a different version fails with `InvalidClassException`. The computed default changes with small edits and can differ between compilers, so the API docs strongly recommend declaring it yourself, ideally `private static final long`.

### Which fields are not serialised?

Static fields, because they belong to the class, and transient fields, which you mark to skip. Fields inherited from a superclass that is not serialisable are also skipped; that superclass needs an accessible no-arg constructor, which runs on reading.

### Why is Java serialisation discouraged today?

It builds objects without running their constructors, so crafted bytes can create objects that break the class's rules, or trigger dangerous code during reading. It is also tied to Java class details. Explicit formats such as JSON are safer and readable by other languages.
