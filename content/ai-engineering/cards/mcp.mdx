## What it is

The Model Context Protocol (MCP) is an open standard for connecting AI apps to tools and data. The AI app is the host; it runs one MCP client for each server it connects to, and each server exposes features the app can use. It is built on [JSON-RPC](term:json-rpc), a simple request-and-reply message format. MCP does the same job for AI apps and tools that the Language Server Protocol did for code editors and languages: one shared standard replaces many one-off integrations.

## Why it exists

Without a standard, every AI app wires each tool its own way, and a tool built for one app cannot be reused in another. If five apps each need an orders tool, someone writes it five times. MCP fixes this: you build the orders tool once as an MCP server, and any MCP host can connect to it and use it. The model still asks for the tool through [tool calling](card:tool-calling); MCP only standardises how the app finds and invokes tools that live on servers.

1. The host app starts one MCP client for each server, and each client connects to exactly one server.
2. The client asks the server what it offers; the server advertises its tools, resources and prompts.
3. The model, through tool calling, decides it wants a tool; the host's client sends that call to the right server.
4. The server runs the tool and returns the result to the client, which hands it back to the host.
5. The host keeps the full conversation; servers see only what they are sent, so they stay isolated from each other.

## Example

The host's client calls a tool on the orders server. The message is JSON-RPC 2.0; `method` is `tools/call`.

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "get_payment_status", "arguments": { "orderId": 42 } }
}
```

What to notice:

- `"jsonrpc": "2.0"` and the numeric `id` mark this as a JSON-RPC request that expects a matching reply.
- `"method": "tools/call"` is the standard MCP request for running a tool; the server replies with the result for that `id`.
- `params.name` picks the tool and `params.arguments` holds its arguments, the same shape the model produced through tool calling.
- The host, not the server, decides to send this call, so user consent and permission checks happen on the host side first.

## Rules and defaults

- **One client per server:** each MCP client has a 1:1 connection to one server, which keeps servers isolated and enforces security boundaries.
- **Server features:** a server may expose tools (the model can call them), resources (data to read) and prompts (ready-made templates).
- **Transports:** stdio for a local server process, Streamable HTTP for a remote server; the spec defines both.
- **Stateless:** every request carries its own protocol version and capabilities (MCP spec 2026-07-28), so there is no shared session state to assume.
- **Authorisation:** remote HTTP servers use OAuth 2.1; local stdio servers read credentials from the environment instead.

## Not to be confused with

[Tool calling](card:tool-calling) is the model asking your app to run one function. MCP is a protocol between apps and tool servers, so the same tools can be discovered and reused by any host. Rule: tool calling = the model-to-app mechanism; MCP = the app-to-server standard built on top of it.

## Common mistakes

- **"MCP is a replacement for function calling."** It is not. The model still produces a tool call; MCP standardises how that call reaches a shared server and how servers are discovered.
- **"Any MCP server is safe to connect."** A server runs code, and its tool descriptions are untrusted text the model reads. Prefer trusted, least-privilege servers, ask for user consent before calls, and use OAuth for remote servers.

## Interview Qs

### How is MCP different from function calling?

Function calling is the model asking your app to run a function. MCP is a protocol between the app and tool servers, so the same tools can be discovered and reused by any MCP host instead of being wired into one app. The model still uses tool calling; MCP standardises what sits behind it.

### What are the roles in MCP?

The host is the AI application. Inside it, each MCP client holds a connection to exactly one MCP server, which keeps servers isolated. Servers expose tools the model can call, resources to read, and prompt templates. The host keeps the full conversation and controls what each server is allowed to see.

### What are the security concerns with MCP?

An MCP server runs real code, so the host must get user consent before calls, prefer least-privilege and trusted servers, and use OAuth 2.1 for remote servers. Treat tool descriptions as untrusted text unless the server is trusted, and keep the full conversation on the host so servers see only what they need.
