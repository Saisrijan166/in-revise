## Why it exists

Without a standard, every AI app wires each tool its own way. MCP gives one standard, so an orders server written once works in any MCP host.

## How it works

<Mermaid
  alt="The host (the support app) talks to the LLM and holds one MCP client per server: client 1 reaches an orders server over Streamable HTTP, client 2 a local docs server over stdio."
  chart={`flowchart LR
  subgraph H[Host: support app]
    C1[MCP client 1]
    C2[MCP client 2]
  end
  H <--> L[LLM]
  C1 -- Streamable HTTP --> S1[Orders MCP server]
  C2 -- stdio --> S2[Docs MCP server]`}
/>

- The host asks the user before invoking tools; tool descriptions are untrusted unless the server is trusted.
- Authorisation is optional: HTTP servers use OAuth 2.1; stdio servers read credentials from the environment.
- Servers never see the whole conversation; the host keeps it and controls what each server gets.

## Example

The host's client asks the orders server to run a tool (JSON-RPC 2.0):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "get_order_status", "arguments": { "orderId": 42 } }
}
```

## Interview Qs

### How is MCP different from function calling?

Function calling is the model asking your app to run a function. MCP is a protocol between the app and tool servers, so the same tools can be discovered and reused by any MCP host instead of being wired per app.

### What are the roles in MCP?

The host is the AI application. Inside it, each MCP client holds a connection to exactly one MCP server. Servers offer tools, resources and prompts; clients can offer elicitation.

### What are the security concerns with MCP?

Tools are arbitrary code, so the host needs user consent before calls, least-privilege servers, and OAuth for remote servers. Treat tool descriptions as untrusted unless they come from a trusted server.
