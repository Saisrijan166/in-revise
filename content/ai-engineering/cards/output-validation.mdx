## What it is

Output validation is checking the model's reply before your app uses it. The model returns text, and that text might be malformed, factually wrong, or steered by [prompt injection](card:prompt-injection). So you treat the reply the way you treat a form submitted by an unknown user: parse it, confirm it obeys your rules, and only then act. A guardrail is a check placed around the model: one that screens the input before the call, or the output after it.

## Why it exists

If you pass model output straight into another system, its mistakes become your mistakes. Rendered text with a script tag becomes XSS; a generated query run as-is becomes SQL injection; a suggested refund taken at face value becomes money lost. OWASP calls this Improper Output Handling (LLM05, 2025). Validation puts a gate between the model and any real action, so a bad reply is caught instead of executed.

## How it works

The output passes through a fixed set of checks before anything happens.

<Steps label="Checks between the model and any action">
  <Step title="Parse">Map the reply to a typed object, and reject it if the schema does not fit ([structured output](card:structured-output)).</Step>
  <Step title="Business rules">Compare its values with facts from your database: the order owner, the refundable amount, the current status.</Step>
  <Step title="Safety and permission">Confirm this user is allowed to do this, and that the content is safe to show or send.</Step>
  <Step title="Act or fall back">Act, or on failure show an error, retry once, or send the case to a human.</Step>
</Steps>

1. Parse first, so you never read fields from a reply that is the wrong shape.
2. Check business rules against your own data, because the model's numbers and claims are not trusted.
3. Screen for safety and permission; a moderation API can flag unsafe content here.
4. Only then act. If any step fails, fall back instead of proceeding.

So the key is that passing one check does not grant the next: shape, values and permission are each verified.

## Example

The model suggests a refund. Your backend decides, using the order loaded from the database.

```java
record Suggestion(long orderId, int refundRupees) {}
record Order(long id, int totalRupees, int refundedRupees) {}
static String check(Suggestion s, Order o) {      // o is loaded from the database
    int refundable = o.totalRupees() - o.refundedRupees();
    if (s.orderId() != o.id()) return "REJECT: not this order";
    if (s.refundRupees() <= 0 || s.refundRupees() > refundable)
        return "REJECT: refundable is " + refundable;
    return "OK: queue for approval";
}
// order 42: total 1499, already refunded 500
System.out.println(check(new Suggestion(42, 1000000), new Order(42, 1499, 500)));
System.out.println(check(new Suggestion(42, 999), new Order(42, 1499, 500)));
```

```text output
REJECT: refundable is 999
OK: queue for approval
```

What to notice:

- `refundable` is computed from database values, so the absurd 10,00,000 suggestion is rejected without trusting the model.
- The `orderId` is re-checked, so the model cannot refund a different order than the one in question.
- Even a valid amount returns `queue for approval`, not an immediate payout: a human confirms high-impact actions.
- Remove the `refundable` check and the first line would pay out 10,00,000, which is exactly the OWASP LLM05 failure.

## Rules and defaults

- **Parse before read:** a reply that fails the schema is rejected, never partially used.
- **Facts from the database:** amounts, ownership and state are read from your data; the model's values are only a suggestion.
- **Never execute model text:** no `eval`, shell command or raw SQL built from the reply.
- **Encode for the destination:** HTML-escape before rendering, parameterise before querying, so the output cannot act as code.
- **On failure:** reject, retry once, or route to a human; do not proceed on a failed check.

## Not to be confused with

[Structured output](card:structured-output) makes the model return a given shape (for example, valid JSON matching a schema). Output validation is broader: it uses that shape as the first check, then verifies the *values* and permissions. Rule: structured output gets the form right; output validation decides whether what the form says may be acted on.

## Common mistakes

- **"Structured output means I do not need to validate."** It guarantees shape, not correct or permitted values. A schema-valid refund can still be the wrong amount or the wrong user's order.
- **"The model is behind our login, so its output is trusted."** The output can still be wrong or injected. Checks protect against bad output, not only bad users.

## Interview Qs

### The model says "refund ₹10,00,000". What stops it?

The backend. It loads the order, checks the amount against the refundable balance in the database and confirms the user owns the order, then refunds inside a transaction. The model only suggests; code decides and acts.

### What is improper output handling?

Passing model output to other systems without checks: unescaped HTML causing XSS, generated SQL run without parameters, or file paths and shell commands taken from the reply. OWASP LLM05 (2025). Treat the model as an untrusted user and encode output for wherever it is going.

### When do you add human review?

For high-impact or irreversible actions, such as large refunds or account changes, and whenever an automatic check fails. The model drafts the action; a person approves it before it takes effect.
