## What it is

Prompt design is writing the text you send the model so it does the job well. A model follows the words you give it, not the intent in your head, so the prompt is the main thing you control. A useful prompt names five parts: the **role** (who the model is), the **task** (its one job), the **context** (the facts it needs), the **constraints** (limits and rules) and the **output format** (the shape of the reply). The mnemonic R-T-C-C-O keeps them in mind.

## Why it exists

A vague prompt like "help the customer" leaves the model to guess the tone, the length and what facts it may use, so replies vary and often invent details. Without a fixed output format, your code also has to parse free prose. Naming the role, task, context, constraints and output format removes the guessing: the reply is accurate, consistent between calls, and easy for code to read.

## How it works

Each part answers one question. Filled in for the payments support assistant:

| Part | Carries | Payments assistant |
|---|---|---|
| Role | Who the model is | Support assistant for the payments app |
| Task | The one job | Explain the status of the refund |
| Context | Facts it needs | The order row and the relevant policy text |
| Constraints | Limits and rules | Under 80 words; promise no dates the data lacks |
| Output | Shape of the reply | Plain text, or [JSON](card:structured-output) for code |

1. Write the role and the task as plain, positive instructions.
2. Add the context the model needs, and wrap any document or user text in tags so the model knows it is data.
3. State the constraints: length, tone, and what not to claim.
4. Say the output format, and add examples only if the format is unusual ([few-shot](card:zero-and-few-shot)).
5. Store the prompt in code and re-run your eval set whenever you change it.

So the key is clarity, not length: a short prompt that is specific beats a long one full of overlapping rules.

## Example

A template for the payments assistant. The `{order}`, `{policy}` and `{question}` placeholders are filled at run time; Spring AI's `PromptTemplate` does this substitution.

```text
You are the support assistant for the payments app.
Task: tell the customer the status of their refund.
Use only the order data and policy below. If they do not cover it, say you do not know.
Keep it under 80 words. Do not promise dates the data does not show.

<order>{order}</order>
<policy>{policy}</policy>

Customer: {question}
```

What to notice:

- The role and task are the first two lines, so the model knows who it is and its one job before any data.
- The order and policy are wrapped in `<order>` and `<policy>` tags, marking them as context the model reads, not instructions to obey; this also blunts [prompt injection](card:prompt-injection).
- "If they do not cover it, say you do not know" is a positive rule that curbs invented answers.
- Remove the 80-word and no-dates constraints and the model may ramble or promise a refund date the data does not support.

## Rules and defaults

- **Be clear and specific:** state the task, format and length exactly; both Anthropic and OpenAI put specificity first.
- **Prefer positive instructions:** "do X" is followed more reliably than "do not do Y".
- **Give the reason for a rule:** a rule with its reason generalises to cases you did not spell out.
- **Delimit untrusted text:** wrap documents and user input in tags or fences so the model separates data from instructions.
- **Treat prompts like code:** store them in version control, and test each change against an eval set ([evals](card:ai-evaluation)) rather than by eyeballing one reply.

## Not to be confused with

**Prompt design** is shaping one prompt well. [Prompt chaining](card:prompt-chaining) is splitting a task across several prompts, each a separate call. [Few-shot prompting](card:zero-and-few-shot) is one technique inside prompt design, adding worked examples. Rule: design shapes a prompt; chaining connects several; few-shot adds examples to one.

## Interview Qs

### What is prompt engineering?

Designing the instructions, context, examples and output format so the model gives reliable output. In a production app it also means templating prompts, keeping them in version control, and testing every change against an eval set, the way you would with code.

### How do you structure a prompt for a production feature?

Name the role, task, context, constraints and output format, and add examples only if the format is unusual. Wrap untrusted text in tags, ask for structured output so code can read it, and check each prompt change against an eval set before shipping.

### Why prefer positive instructions and delimited context?

Positive instructions ("answer in two lines") tell the model what to produce, which it follows more reliably than a "do not" rule. Delimiting context in tags lets the model tell your instructions from the data, which improves accuracy and reduces prompt injection from text hidden in that data.
