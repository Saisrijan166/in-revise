## Why it exists

A model does what the prompt says, not what you meant. A clear, structured prompt makes replies accurate, consistent and easy for code to use.

## How it works

| Part | Carries | Refund assistant |
|---|---|---|
| Role | Who the model is | Support assistant for shop.example |
| Task | The one job | Explain the refund status |
| Context | Facts it needs | Order row, policy chunks |
| Constraints | Limits and rules | Under 80 words; no promised dates |
| Output | Shape of the reply | Plain text or [JSON](card:structured-output) |

- Examples are an optional sixth part: see [few-shot](card:zero-and-few-shot).
- Tags keep data apart from instructions, which also helps against [prompt injection](card:prompt-injection).
- Spring AI's `PromptTemplate` fills `{placeholders}` at runtime.

## Example

```text
You are the support assistant for shop.example.
Task: tell the customer the status of their refund.
Use only the order data and policy below. If they do not cover it, say so.
Keep it under 80 words. Do not promise dates the data does not show.

<order>{order}</order>
<policy>{policy}</policy>

Customer: {question}
```

## Interview Qs

### What is prompt engineering?

Designing the instructions, context, examples and output format so a model gives reliable output. In an app it also means templating, versioning and testing prompts like code.

### How do you structure a prompt for a production feature?

Role, task, context, constraints and output format, plus examples if the format is unusual. Put untrusted text inside tags, ask for structured output, and check every prompt change against an eval set ([AI evaluation](card:ai-evaluation)).
