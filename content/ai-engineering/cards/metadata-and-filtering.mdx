## Why it exists

One shared vector store holds many shops' policies and internal notes. Without filters, shop B's customer can get shop A's chunk, a leak OWASP lists as LLM08 (2025).

## How it works

```json
{
  "id": "refund-policy#4",
  "content": "UPI refunds reach the customer in 5-7 working days.",
  "metadata": {
    "tenant_id": "shop-17", "document_id": "refund-policy",
    "title": "Refund policy", "page": 2,
    "access_group": "customer", "effective_from": "2026-04-01"
  }
}
```

- **Pre-filtering** limits the search to allowed rows; **post-filtering** drops rows after the nearest-neighbour search.
- Strong isolation: a table or partition per tenant (pgvector's advice), or [row-level security](card:pg-row-level-security).
- Removed or replaced documents: delete their chunks by `document_id`.

## Example

```java
String ask(String question, Jwt user) {
    String tenant = user.getClaimAsString("tenant_id");   // from the login, never from the prompt
    return chat.prompt().user(question)
        .advisors(a -> a.param(QuestionAnswerAdvisor.FILTER_EXPRESSION,
            "tenant_id == '" + tenant + "' && access_group in ['customer', 'public']"))
        .call().content();
}
```

- In Spring AI 2.0 this per-request filter replaces the advisor's default filter, so repeat every condition.

## Interview Qs

### How do you stop one customer seeing another tenant's documents?

Store `tenant_id` on every chunk and filter on it in the vector query, taking the tenant from the authenticated session. For stronger isolation, use a partition or table per tenant, or row-level security.

### Why can a filtered vector search return fewer results than K?

Approximate indexes such as HNSW find candidates first and filter after. With pgvector's default `hnsw.ef_search` of 40 and a filter matching 10% of rows, about 4 rows survive. Enable iterative index scans or use partitions.

### Can a system prompt enforce permissions?

No. Instructions can be overridden by [prompt injection](card:prompt-injection), and the text has already leaked into the context. Enforce access in code and SQL; see [securing LLM apps](card:llm-security).
