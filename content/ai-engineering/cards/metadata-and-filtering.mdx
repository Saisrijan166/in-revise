## What it is

Metadata is the set of fields you store next to each chunk's vector, such as tenant, document id, page and who may read it. Filtering means using those fields to narrow a [vector search](card:vector-databases) to the rows the current user is allowed to see, so forbidden chunks are never ranked or returned. Permission-aware retrieval applies that filter using the user's identity from the login. It is how a [RAG system](card:rag-pipeline) sharing one store across many customers keeps their data apart.

## Why it exists

One vector store usually holds many shops' policies and internal notes together. If a search ranks every chunk by similarity alone, shop B's customer can receive shop A's chunk, because similarity does not know about ownership. That is a real data leak, and OWASP lists it as LLM08 (2025), Vector and Embedding Weaknesses. The obvious-looking fix, telling the model in the prompt to hide other shops' text, fails: the text is already in the context, so one prompt injection can pull it out. Metadata filtering removes the chunk before it ever reaches the model.

## How it works

Each stored chunk carries metadata you can filter on.

```json
{
  "id": "refund-policy#4",
  "content": "UPI refunds reach the customer in 5-7 working days.",
  "metadata": {
    "tenant_id": "shop-17", "document_id": "refund-policy",
    "title": "Refund policy", "page": 2,
    "access_group": "customer", "effective_from": "2026-04-01"
  }
}
```

What to notice:

- `tenant_id` and `access_group` are the fields the query will filter on; without them stored on the chunk, no filter is possible.
- `document_id` lets you delete or replace a whole document's chunks when the file changes.
- `title` and `page` feed citations and make a retrieval trace easy to debug.

The query applies the filter in two possible places. Pre-filtering limits the search to allowed rows before ranking. Post-filtering ranks first and drops disallowed rows after, which can leave fewer than K results.

## Example

The filter is built from the signed-in user's token, so the user can never widen it.

```java
String ask(String question, Jwt user) {
    String tenant = user.getClaimAsString("tenant_id");   // from the login, not the prompt
    return chat.prompt().user(question)
        .advisors(a -> a.param(QuestionAnswerAdvisor.FILTER_EXPRESSION,
            "tenant_id == '" + tenant + "' && access_group in ['customer', 'public']"))
        .call().content();
}
```

What to notice:

- `tenant` comes from the JWT claim, so the value is set at login and the user cannot change it through the question text.
- The filter expression runs inside the vector search, so chunks from other tenants are never ranked and never reach the prompt.
- In Spring AI 2.0 a per-request `FILTER_EXPRESSION` replaces the advisor's default filter rather than adding to it, so you must repeat every condition you still want.
- Drop the filter and the search ranks all tenants' chunks together, which is exactly the LLM08 leak.

## Rules and defaults

- **Filter before retrieval, never in the prompt:** a chunk that reaches the context can be revealed; enforce access in code and SQL.
- **Identity from the session:** read the tenant and groups from the authenticated token, not from anything the user typed.
- **Strong isolation options:** pgvector suggests a table or partition per tenant for hard separation, or use [row-level security](card:pg-row-level-security).
- **Approximate indexes can under-return:** with pgvector's default `hnsw.ef_search` of 40 and a selective filter, a filtered search may return fewer than K rows; enable iterative index scans (pgvector 0.8+) or partition by tenant.

## Interview Qs

### How do you stop one customer seeing another tenant's documents in RAG?

Store `tenant_id` on every chunk and filter on it inside the vector query, taking the tenant from the authenticated session rather than the prompt. For stronger isolation, give each tenant its own table or partition, or use row-level security, so the search physically cannot reach other tenants' rows.

### Why can a filtered vector search return fewer than K results?

An approximate index such as HNSW finds the nearest candidates first and applies the filter afterwards. With pgvector's default `hnsw.ef_search` of 40 and a filter matching only a small fraction of rows, few candidates survive. Fix it by raising `ef_search`, enabling iterative index scans, or partitioning by tenant.

### Can a system prompt enforce permissions?

No. A prompt instruction can be overridden by [prompt injection](card:prompt-injection), and in any case the forbidden text has already entered the context, so it can leak. Enforce access in code and SQL, before or during retrieval; see [securing LLM apps](card:llm-security).
