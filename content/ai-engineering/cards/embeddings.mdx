## What it is

An embedding is a fixed-length list of numbers that stands for the meaning of a piece of text. That list of numbers is called a [vector](card:vector). An [embedding model](card:embedding-model) is a separate model from the chat [LLM](card:what-is-an-llm): you give it text and it returns one vector, not an answer. The vectors are placed so that two texts with similar meaning get vectors that sit close together, which is what lets you search by meaning.

## Why it exists

A computer cannot compare the meaning of two sentences directly: "refund not received" and "money not back yet" share no word, so a plain word match misses the link. Numbers, on the other hand, are easy to compare. Embeddings turn each text into numbers placed by meaning, so "near in meaning" becomes "near in numbers", and the second sentence can find the first with no shared keyword.

## How it works

The embedding model does the same job on documents (once, up front) and on each incoming question.

<Compare id="embeddings-vs-llm" />

1. At ingestion, you send every document chunk to the embedding model and store the vector it returns in a [vector database](card:vector-databases).
2. When a question arrives, you send the question to the **same** model and get one query vector back.
3. You compare the query vector against the stored vectors and keep the closest ones; closeness is measured with [cosine similarity](card:similarity-search).

So the key is that the same model turns both sides into the same kind of vector, so they can be compared.

## Example

These numbers are tiny and made up to show the idea; a real embedding has hundreds or thousands of values.

```text
"refund not received"   -> [ 0.12, -0.45, 0.73, ...]   near
"money not back yet"    -> [ 0.10, -0.41, 0.70, ...]   near
"change my password"    -> [-0.66,  0.32, 0.05, ...]   far
```

What to notice:

- The first two lists have similar numbers because the two texts mean a similar thing, even though they share no word.
- The third list points a different way because its meaning is unrelated; a search for a refund will rank it last.
- Each text becomes one list of the same length. In Spring AI, `EmbeddingModel.embed(String)` returns this list as a `float[]`.

## Rules and defaults

- **One vector per text:** the model returns a single fixed-length vector for each input, computed once at ingestion for documents.
- **Length is fixed by the model:** text-embedding-3-small returns 1,536 numbers by default (OpenAI, 2026); this length must match the column in your vector database.
- **Same model on both sides:** documents and queries must use the same embedding model, or their vectors live in different spaces and cannot be compared.
- **Changing models means re-embedding:** a different model builds a different space, so every stored document must be re-embedded before you compare against it.

## Interview Qs

### What are embeddings and why are they useful?

Embeddings are vectors of numbers that capture the meaning of text (or images). Items with similar meaning get vectors that sit close together, so you can search, cluster or recommend by meaning rather than by exact words. This is the basis of semantic search and RAG retrieval.

### Can you switch embedding models without re-indexing?

No. Two models build different vector spaces, so their vectors cannot be compared. You must re-embed every document with the new model, often into a new column, and only then switch the query over. Mixing vectors from two models gives meaningless results.

### Why not use the chat LLM for search instead of an embedding model?

A chat LLM returns text, not a vector you can index and compare. An embedding model returns one vector per chunk, computed once at ingestion, so each search only has to embed the question and compare vectors. That is far cheaper and faster than asking an LLM to read everything.
