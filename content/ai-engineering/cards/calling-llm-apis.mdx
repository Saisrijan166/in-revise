## What it is

Calling an LLM API means the hardening you put around each model call so it stays fast and reliable. An LLM call is a slow HTTP request to a paid, rate-limited service that sometimes fails. Four pieces make it production-ready: **streaming** the reply so the user sees words early, **timeouts** so a stuck call does not hold resources, **retries** that fire only for errors worth retrying, and **rate limits** that cap each user. These sit in the [AI service](card:spring-ai-integration) around the `ChatClient` call.

## Why it exists

A single `.call()` with no guards breaks under load. Without streaming, the user stares at a spinner for seconds while a long reply is generated. Without timeouts, a stuck provider holds a request thread and a connection until both pools run dry. Without careful retries, a loop can refund the same payment twice or hammer a 401 forever. Without per-user limits, one user can exhaust your [token budget](card:model-selection-and-cost) and your provider quota.

## How it works

<Compare id="streaming-vs-blocking-response" />

1. Stream the reply so the first tokens reach the browser in well under a second, even when the full answer takes several seconds.
2. Set a connect timeout and a request timeout on every call, so a stuck provider cannot hold a thread or connection indefinitely.
3. On a transient failure (timeout, network error, 429 or 5xx) retry at one layer only, with capped exponential backoff and jitter, honouring any `Retry-After` header.
4. After repeated failures, let a circuit breaker fail fast and return a fallback message instead of retrying forever.
5. In front of the AI service, rate-limit each user by requests per minute and tokens per day, which also caps spend; see [unbounded consumption](card:llm-security).

So the key is to retry only what can succeed on a second try, and to protect threads, budget and other users while you do.

## Example

This Spring AI 2.0 endpoint streams tokens to the browser over server-sent events; it needs Reactor on the classpath, for example `spring-boot-starter-webflux`.

```java
@RestController
class AskStreamController {
    private final ChatClient chatClient;

    AskStreamController(ChatClient.Builder builder) { this.chatClient = builder.build(); }

    @GetMapping(value = "/api/ask/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<String> ask(@RequestParam String q) {
        return chatClient.prompt().user(q).stream().content();   // tokens as they arrive
    }
}
```

What to notice:

- `.stream().content()` returns a `Flux<String>` of text chunks, not one `String`; each chunk is pushed as it is generated.
- `produces = MediaType.TEXT_EVENT_STREAM_VALUE` tells Spring to send the chunks as server-sent events, which the browser reads incrementally.
- Change `.stream()` to `.call()` and the method would block until the whole reply is ready, so the user sees nothing until the end.
- An error can arrive mid-stream after the HTTP 200 line has been sent, so the client must handle a failure that appears partway through.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| OpenAI request timeout | 60 s | Spring AI 2.0, `spring.ai.openai.timeout` |
| OpenAI SDK retries | 3 | Spring AI 2.0, `spring.ai.openai.max-retries` (not `spring.ai.retry.*`) |

- **Retry transient only:** timeouts, network errors, 429 and 5xx. Not 400, 401, 403 or billing and quota 429s.
- **Backoff:** exponential with jitter and a max attempt count; wait at least any `Retry-After` value.
- **Idempotency:** send an idempotency key with any action, so a retried action runs once.

## Not to be confused with

A provider rate limit and your own rate limit are different guards. The provider caps you in requests and tokens per minute (RPM and TPM) across your whole account, and hits you with a 429 when you cross it. Your own per-user limiter sits in front of the AI service and caps each user, so one user cannot use the whole account quota or your budget. Rule: the provider protects itself; your limiter protects you and your other users.

## Interview Qs

### Why stream LLM responses?

Generation is token by token, so a long reply takes several seconds. Streaming sends the first words as soon as they are produced, so the user sees progress in under a second. Total generation time does not drop. One catch: an error can arrive mid-stream after a 200, so the client must handle a failure partway through.

### Which errors do you retry, and how?

Retry timeouts, network errors, 429 and 5xx with capped exponential backoff plus jitter and a max attempt count, waiting at least any `Retry-After` value. Do not retry 400, 401, 403 or billing and quota 429s, because they keep failing. For actions, send an idempotency key so a retry cannot run the action twice.

### How do you stop one user from burning the AI budget?

Put a rate limiter in front of the AI service: requests per user per minute, tokens per user per day, and an output-token cap per call. When a user crosses a limit, return 429 instead of calling the model. This bounds both the provider quota you use and the money you spend.
