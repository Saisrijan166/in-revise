## What it is

A vector database stores [embeddings](card:embeddings) and answers one question quickly: which stored vectors are nearest to a given query vector. It does this with an **ANN index** (approximate nearest neighbour), a structure that finds near matches while checking only a small part of the data. The two ANN indexes you meet most are [HNSW](card:hnsw) and [IVFFlat](card:ivfflat). pgvector adds this ability to PostgreSQL, so vectors can live beside your ordinary tables.

## Why it exists

[Similarity search](card:similarity-search) by exact comparison looks at every stored vector. With a handful of vectors that is fine, but comparing a question against millions of vectors one by one is too slow for a live request. An ANN index groups or links vectors in advance so a search only has to look at a small slice, keeping the query fast as the data grows. The cost is that it may skip a few true matches.

## How it works

A vector database keeps the embedding, the original text and any metadata together, and the ANN index sits on the embedding column.

<Compare id="vector-db-vs-relational-db" />

1. At ingestion, store each chunk's vector (plus its text and metadata such as the tenant) in the table.
2. Build an ANN index on the vector column, choosing a distance such as cosine.
3. At query time, embed the question and ask for the nearest vectors; the index returns a shortlist without scanning every row.
4. Apply exact filters, such as the tenant id, so one customer never sees another's chunks ([metadata filtering](card:metadata-and-filtering) covers the ordering of filter and search).

So the key is that the index gives up exact completeness, measured as [recall](card:ann-search), to keep search fast at scale.

## Example

This runs on PostgreSQL 18 with pgvector 0.8.7. Real vectors have 1,536 numbers; this uses 3 so the output is readable, and keeps the tenant filter that a real query needs.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE policy_chunk (
    id        bigserial PRIMARY KEY,
    tenant_id bigint NOT NULL,
    content   text NOT NULL,
    embedding vector(3) NOT NULL        -- length is fixed by the embedding model
);

CREATE INDEX ON policy_chunk USING hnsw (embedding vector_cosine_ops);

-- :q is the question's embedding; tenant comes from the logged-in user
SELECT id, content FROM policy_chunk
WHERE tenant_id = 1
ORDER BY embedding <=> '[0.88,0.12,0.0]' LIMIT 5;
```

```text output
 id |                content
----+----------------------------------------
  1 | Refunds reach your UPI app in 5-7 days
  2 | How to cancel a pending payment
(2 rows)
```

What to notice:

- `ORDER BY embedding <=> :q` sorts by cosine distance, so the chunk pointing most like the question comes first.
- `WHERE tenant_id = 1` runs alongside the search, so tenant 2's row is excluded; the output shows only tenant 1's two chunks.
- The `hnsw (embedding vector_cosine_ops)` index must name the same distance (`vector_cosine_ops`) that the `<=>` operator uses, or the index is not used.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| HNSW `m` / `ef_construction` | 16 / 64 | pgvector 0.8.7 |
| `hnsw.ef_search` | 40 | pgvector 0.8.7 |
| `ivfflat.probes` | 1 | pgvector 0.8.7 |
| Indexed `vector` dimensions | up to 2,000 (halfvec up to 4,000) | pgvector 0.8.7 |

- **HNSW builds on an empty table:** it has no training step, so you can create the index before loading data.
- **IVFFlat needs data first:** it learns its clusters from existing rows, so build it after the table has data or recall drops.
- **Recall is a knob, not a guarantee:** raise `hnsw.ef_search` (or `ivfflat.probes`) for more recall and a slower query; lower it for the opposite.

## Interview Qs

### Why do you need a vector database rather than a normal query?

To find the most similar embeddings among millions quickly. A relational `WHERE` matches exact values, not "closest in meaning". An ANN index checks only a small part of the data instead of every row, so similarity search stays fast as the data grows, which a full scan would not.

### Vector database or PostgreSQL: which do you pick?

Both, for different jobs. Keep orders and payments relational. Store embeddings with pgvector in the same PostgreSQL, or in a dedicated vector store such as Pinecone, Weaviate, Milvus or Qdrant when scale demands it. Spring AI's `VectorStore` abstraction supports all of these behind one interface.

### What does "approximate" actually cost you?

Recall: the index may miss some of the true nearest neighbours, so a result exact search would have returned can be absent. In pgvector you trade this off per query: raise `hnsw.ef_search` (or `ivfflat.probes`) for better recall and slower queries, lower it for speed with a little more risk of a miss.
