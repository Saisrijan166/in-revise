## Why it exists

Comparing a question with millions of vectors one by one is too slow. A vector index finds the nearest ones while checking only a small part.

## How it works

<Compare id="vector-db-vs-relational-db" />

- Without an index pgvector does exact search; an [HNSW](card:hnsw) or [IVFFlat](card:ivfflat) index makes it approximate.
- Results can differ from exact search: that gap is measured as [recall](card:ann-search).
- Filters such as tenant are covered in [metadata filtering](card:metadata-and-filtering).

## Example

Tested on PostgreSQL 18 with pgvector 0.8.7.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE policy_chunk (
    id        bigserial PRIMARY KEY,
    tenant_id bigint NOT NULL,
    content   text NOT NULL,
    embedding vector(1536) NOT NULL   -- size fixed by the embedding model
);

CREATE INDEX ON policy_chunk USING hnsw (embedding vector_cosine_ops);

-- $1 = the question's embedding, $2 = the caller's tenant
SELECT id, content FROM policy_chunk
WHERE tenant_id = $2
ORDER BY embedding <=> $1 LIMIT 5;
```

## Defaults

| What | Default | Where |
|---|---|---|
| HNSW `m` / `ef_construction` | 16 / 64 | pgvector 0.8 |
| `hnsw.ef_search` | 40 | pgvector 0.8 |
| `ivfflat.probes` | 1 | pgvector 0.8 |

## Interview Qs

### Why do we need a vector database?

To find the most similar embeddings among millions quickly. An ANN index checks a small part of the data instead of every row, so search stays fast as data grows.

### Vector database or PostgreSQL?

Both. Keep orders and payments relational. Store embeddings with pgvector in the same PostgreSQL, or in a dedicated vector store such as Pinecone, Weaviate, Milvus or Qdrant; Spring AI's `VectorStore` supports all of these.

### What does "approximate" cost you?

Recall: the index may miss some true nearest neighbours. In pgvector, raise `hnsw.ef_search` (or `ivfflat.probes`) for better recall, lower it for speed.
