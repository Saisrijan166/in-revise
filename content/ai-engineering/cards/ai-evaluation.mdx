## Why it exists

The same prompt can give different replies, and a prompt tweak that fixes one case can break five others. Evals measure quality so changes are decided by numbers, not by feel.

## How it works

<Steps label="The eval loop">
  <Step title="Define success">Pick criteria: correct, grounded, safe, valid format, fast, cheap enough.</Step>
  <Step title="Build the set">Real and edge questions with expected facts, for example "refund for order 42".</Step>
  <Step title="Run and score">Exact or schema checks, an LLM judge, a human sample.</Step>
  <Step title="Fix and re-run">Change prompt, retrieval or model; compare scores before release.</Step>
  <Step title="Keep going">Add production failures to the set; run it on every change.</Step>
</Steps>

- RAG: score retrieval and answer apart, so you know which half failed ([RAG failures](card:rag-failures)).
- A judge needs a clear rubric, pass / fail or pairwise output, and proven agreement with human labels.
- Live signals such as user ratings come from [observability](card:ai-observability).

## Example

| RAG metric (Ragas) | Asks |
|---|---|
| Context precision | Are relevant chunks ranked above irrelevant ones? |
| Context recall | Did retrieval find everything the reference answer needs? |
| Faithfulness | Is every claim backed by the retrieved context? |
| Answer relevancy | Does it address the question? (not a fact check) |

## Interview Qs

### What is LLM-as-a-judge, and what are its risks?

A model grades another model's answers against a rubric. It scales cheaply, but has position, verbosity and self-enhancement biases. Use pass / fail or pairwise formats and check it against human labels.

### How do you evaluate a RAG system?

Separately: retrieval (context precision and recall) and generation (faithfulness to the context, answer relevancy). A wrong answer from good chunks is a prompt problem; from bad chunks, a retrieval problem.
