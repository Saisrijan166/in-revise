## What it is

An AI agent is an [LLM](card:what-is-an-llm) that runs in a loop and drives its own next step. It is given a goal, it chooses a [tool](card:tool-calling) to call, your app runs the tool, the model reads the result, and then it decides what to do next. It keeps going until it thinks the goal is met or a limit stops it. The model, not your code, decides the order of steps.

## Why it exists

In [prompt chaining](card:prompt-chaining) and other workflows, you fix the steps in advance. That works when you know the steps, such as "classify, then draft, then check". But some tasks need steps nobody can list ahead of time: the next move depends on what the last result showed. An agent lets the model choose those steps itself, so the system can handle open-ended tasks instead of only the paths you hard-coded.

1. The agent starts with a goal and the list of tools it may use.
2. The model decides the next step: call a tool, or stop and answer.
3. If it calls a tool, your app runs it and sends the result back; this result is the ground truth for the next decision.
4. The model reads the result and decides again. This reason-then-act loop is the ReAct pattern.
5. The loop ends when the goal is met, or when a step limit or budget is reached.

So the key is the loop: the model keeps deciding, instead of following a path you wrote.

## Example

This is one run of the payments support agent, with a limit of 5 steps. The lines are a trace of its decisions, not program output.

```text
Goal: "Where is my refund for order 42?"   (limit: 5 steps)
Step 1  need the status -> call getPaymentStatus(42)
        result: delivered; refund of 500 to UPI, status PROCESSING
Step 2  enough to answer -> stop
Answer: explain that the 500 UPI refund for order 42 is in progress
Note: an actual refund would call refundPayment, which needs backend rules and human approval
```

What to notice:

- The model chose to call `getPaymentStatus` first because the goal needed live data; your code did not script that.
- The result from step 1 is what lets the model decide, in step 2, that it has enough to answer.
- The 5-step limit is a guardrail: without it, a confused model could loop and keep calling tools.
- Reading status is safe, but `refundPayment` moves money, so it stays behind backend rules and human approval, not the agent's free choice.

## Rules and defaults

- **Stop conditions are required:** an agent must stop on goal met, a step cap, or a spend/token budget; without them a loop can run forever and burn money.
- **Least privilege:** expose only the few tools the task needs. Too many tools or permissions is excessive agency, a known risk.
- **Human approval for risky actions:** keep money-moving or destructive tools behind a confirmation step, not the model's free choice.
- **Log every step:** record each decision and tool call so you can see what the agent did and debug it later.

## Not to be confused with

A workflow fixes the order of steps in your code; an agent lets the model pick the next step in a loop. Both use [tool calling](card:tool-calling), so they look alike. Rule: known steps = workflow (cheaper, faster, easier to test); unknown steps that depend on results = agent.

## Common mistakes

- **"Use an agent because it sounds powerful."** An agent is slower, costs more and is harder to test. If the steps are known, a single call or a workflow is better. Add autonomy only when it clearly helps.
- **"A smarter model does not need limits."** Any agent can get stuck repeating a step or chasing a dead end. Step caps, budgets and logging are needed no matter how good the model is.

## Interview Qs

### What is the difference between an AI agent and a workflow?

A workflow follows a path your code defines: you decide the steps, even if each step uses an LLM. An agent lets the model decide the next step itself, in a loop, based on the result of each tool call, until the goal is met or a limit stops it. The model controls the order of steps.

### How do you stop an agent looping forever or doing harm?

Cap the number of steps, tool calls and spend so it must stop. Expose only a few least-privilege tools. Require human approval for risky actions like refunds, and validate every tool argument in the backend. Log every step so you can see and debug what it did.

### When would you not use an agent?

When the steps are known. A single model call or a fixed workflow is cheaper, faster and far easier to test and debug. An agent adds cost, latency and unpredictability, so you add it only when the task truly needs steps that cannot be listed in advance.
