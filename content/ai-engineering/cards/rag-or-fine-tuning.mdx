## What it is

This is a choice, not a single technique: when answers are not good enough, you pick the right fix. [RAG](card:what-is-rag) and tools add knowledge at request time. [Fine-tuning](card:llm-training-stages) trains the model on examples so its behaviour changes. **Long context** means you simply place the documents in the prompt and send them every time. Each fixes a different problem at a different cost, so naming the problem first tells you which one to reach for.

## Why it exists

All three can improve answers, which is exactly why teams pick the wrong one and waste weeks. The classic mistake is fine-tuning a model to teach it facts that change every month: each change then needs a new training run, and the model still cannot cite where a fact came from. Framing the decision by the kind of gap, knowledge versus behaviour, avoids that.

## How it works

<Compare id="rag-vs-fine-tuning-vs-long-context" />

1. Write a clear prompt and an eval set first; often that alone meets the bar, and it also tells you which failures remain.
2. If the failures are missing, outdated or private facts, add them with RAG or a tool call.
3. If the failures are wrong format, tone or an inconsistent task, fine-tune on examples of the right behaviour.
4. If the needed documents are small, stable and allowed in full, just send them (long context), and use [prompt caching](card:model-selection-and-cost) to make resending the same prefix cheaper.

So the key is: there is no fixed ladder. Start with a prompt, then pull the lever your failures point to, and stack them if needed.

## Example

Each failure points to a different fix, based on whether it is a knowledge gap or a behaviour gap.

```text
"Answers use the old refund window"     -> knowledge -> RAG over the policy
"Order 42's refund status is wrong"     -> live data -> tool: getPaymentStatus(42)
"Replies ignore our support tone"       -> behaviour -> prompt, then fine-tune
"Only a 6-page FAQ, rarely changes"     -> small     -> long context
```

What to notice:

- The first two are knowledge gaps but need different fixes: a stored policy fits RAG, while a live status needs a [tool call](card:tool-calling), not retrieval.
- The tone problem is a behaviour gap; retrieving more documents would not change the style, so fine-tuning (or a better prompt) is the lever.
- The small FAQ needs none of the retrieval machinery; sending it in full is simpler and reliable.

## Rules and defaults

- **Fine-tuning with LoRA freezes the base model:** LoRA (Hu et al. 2021) and other PEFT methods leave the original weights untouched and train small added weights, so fine-tuning rarely means retraining the whole model.
- **Fine-tuning still goes stale:** whatever the method, it captures behaviour at one point in time and cannot cite sources, so it is wrong for fast-changing facts.
- **Provider platforms change:** which models you can fine-tune shifts fast (for example OpenAI has been winding down parts of its fine-tuning offering, noted 27-10-2026), so re-check availability before planning a project.
- **Long context has a ceiling:** Anthropic notes a knowledge base under about 200,000 tokens can often just go in the prompt; above that, prefer RAG.

## Not to be confused with

Pre-training and fine-tuning are both training, but at different stages. Pre-training teaches a base model general language from huge raw text. Fine-tuning takes that trained model and adjusts its behaviour on a smaller, task-specific set of examples. RAG is not training at all: it changes the prompt, not the weights. Rule: pre-training builds the base, fine-tuning shapes behaviour, RAG supplies knowledge.

## Interview Qs

### RAG vs fine-tuning?

RAG supplies knowledge at runtime: it is easy to update, it can cite sources, and it needs no training. Fine-tuning trains the model on examples to change behaviour such as format, tone or a narrow task. So knowledge goes to RAG and behaviour goes to fine-tuning, and the two can be combined in one app.

### Context windows are huge now. Why still use RAG?

Sending everything costs tokens and time on every single call, and a long input can bury the key fact so the model misses it (see [context window](card:context-window)). RAG also filters per user, which long context cannot. Anthropic notes a knowledge base under roughly 200,000 tokens can simply go in the prompt; above that, retrieval wins.

### Can fine-tuning keep the model up to date?

Not reliably. Each change to the facts needs a fresh training run, and the model cannot show where a fact came from, so you get no citations and no easy correction. For knowledge that changes, RAG is the right tool; fine-tuning is for behaviour (see [training stages](card:llm-training-stages)).
