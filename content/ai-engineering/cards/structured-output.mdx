## What it is

Structured output means making the model reply in a fixed, machine-readable shape, almost always JSON, instead of free prose. You tell the model the fields you want, such as `orderId`, `status` and `nextStep`, and it fills them. The strongest form, **structured outputs**, constrains the reply to a **JSON Schema** you supply, so the provider enforces the field names and types while generating. Your backend can then read named fields directly.

## Why it exists

Backend code needs specific values, like a status string and an order id, not a paragraph. If the model answers in prose, your code has to parse English, which is fragile and breaks the moment the wording changes. Worse, just asking for JSON in the prompt does not guarantee the model will actually return valid, correctly shaped JSON. A schema-constrained reply removes both problems: the JSON is valid and has the fields you asked for.

## How it works

There are three levels of guarantee, from weakest to strongest.

<Compare id="json-mode-vs-structured-outputs" />

1. Prompt-only: you ask for JSON in the text. It usually works but nothing enforces it.
2. JSON mode: the provider guarantees the reply is valid JSON, but not which fields or types it has.
3. Structured outputs: you pass a JSON Schema and the provider constrains the reply to it, so required fields and types are present (OpenAI `json_schema` with strict mode; Anthropic `output_config.format`).
4. Whatever the level, you still check the stop reason and validate the values, because a refusal or a cut-off reply can break the shape.

So the key is that a schema fixes the shape of the reply, not the truth of its values.

## Example

In Spring AI you define a Java record for the shape and ask the client to map the reply into it with `.entity()`. Spring AI adds the format instructions and parses the JSON for you.

```java
record RefundStatus(String orderId, String status, String nextStep) {}

@Service
class RefundAssistant {
    private final ChatClient chat;
    RefundAssistant(ChatClient.Builder builder) { this.chat = builder.build(); }

    RefundStatus status(String order) {
        return chat.prompt()
            .user(u -> u.text("Give the refund status for: {order}").param("order", order))
            .call().entity(RefundStatus.class);
    }
}
```

What to notice:

- The `RefundStatus` record is the schema: its three components become the required JSON fields.
- `.entity(RefundStatus.class)` tells Spring AI to request that shape and parse the reply straight into the record, so your code gets typed fields, not a raw string.
- If you called `.content()` instead, you would get free text and have to parse it yourself, which is exactly what this avoids.
- The parse succeeding does not mean `status` is correct; add business checks on the value before acting on it.

An example reply the model might produce (an example, not a reproducible run):

```json
{ "orderId": "42", "status": "REFUND_INITIATED", "nextStep": "The 500 rupees is on its way to your UPI account" }
```

What to notice: the three keys match the record components exactly, so Spring AI maps this straight into a `RefundStatus`; a reply missing `status` or cut off before the closing brace would fail to parse, which is why you check the stop reason too.

## Rules and defaults

- **Prefer schema-constrained structured outputs:** OpenAI recommends them over plain JSON mode where the model supports them.
- **Provider shapes differ:** OpenAI uses the `json_schema` format with strict mode; Anthropic uses `output_config.format` (the older `output_format` is deprecated, verified 21-10-2026).
- **Spring AI maps for you:** `.entity(Type.class)` adds format instructions and parses the reply; it can also use the provider's native structured mode.
- **Always re-check output:** a refusal or a reply cut off by the token limit may not match the schema, so check the stop reason, then validate values ([output validation](card:output-validation)).

## Not to be confused with

**Structured output** guarantees the shape of the reply: the fields and their types. **[Output validation](card:output-validation)** checks the content: whether the values are allowed and make business sense. Rule: a schema makes the JSON the right shape; validation decides whether the values are acceptable.

## Interview Qs

### What is the difference between JSON mode and structured outputs?

JSON mode only guarantees the reply is valid JSON; the field names and types are up to the model. Structured outputs constrain the reply to your JSON Schema, so required fields and their types are present. OpenAI recommends structured outputs over JSON mode wherever the model supports them.

### Can structured output still fail?

Yes. A refusal, or a reply cut off because it hit the output token limit, may not match the schema at all. Check the refusal field or the stop reason first, then retry or fall back, and finally validate the actual values before your code acts on them.

### If the JSON is valid and matches the schema, is the data correct?

Not necessarily. The schema fixes the shape, field names and types, not the meaning of the values. The model can still place a wrong status or a made-up id in a correctly typed field, so you apply business-rule checks on the values after parsing.
