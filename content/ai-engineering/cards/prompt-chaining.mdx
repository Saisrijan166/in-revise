## What it is

Prompt chaining is solving one hard task with several small LLM calls in a row, instead of one big prompt. Each call does one thing, and its output becomes the input to the next call. Between the calls, your code can check, fix or filter the output before passing it on. The whole sequence of steps is decided by your code, so the path is fixed before anything runs.

## Why it exists

A single prompt that must classify a message, extract an order id and write a reply all at once is hard to get right, and when it misbehaves you cannot tell which part failed. Breaking the task into steps lets you test and fix each step on its own, and insert code checks between them, so one wrong step is caught early instead of corrupting the final answer.

## How it works

Here is a chain for answering a refund email in the payments assistant.

<Steps label="Refund email chain">
  <Step title="1. Classify">An LLM call labels the intent: refund-status, payment-failed or other.</Step>
  <Step title="2. Extract">An LLM call returns the order id as [structured output](card:structured-output).</Step>
  <Step title="3. Gate and fetch">Your code checks the order belongs to this customer, then reads it from PostgreSQL. No LLM here.</Step>
  <Step title="4. Draft">An LLM call writes the reply using the fetched order data.</Step>
</Steps>

1. The classify call decides what kind of request this is, so later steps can branch.
2. The extract call pulls out just the order id, in a fixed shape code can read.
3. Your code gates: it verifies the id belongs to the customer and fetches the real data. This step has no LLM, so it cannot be tricked by the model.
4. The draft call writes the final reply from trusted, fetched data.

So the key is that code sits between the model calls, checking each output before the next step trusts it.

## Analogy

<Analogy title="An assembly line" limit="A real line never loops back or skips stations; a chain can branch on the classify result, and an agent could even reorder the stations itself.">
Each station does one small job and hands the part to the next. A faulty part is caught at the station that made it, not at the very end, so the whole line is easier to inspect and fix than one machine doing everything at once.
</Analogy>

## Example

Below, the classify step is one LLM call; its result decides whether the rest of the chain even runs. Code, not the model, routes on the label.

```java
String intent = chat.prompt()
    .user(u -> u.text("Classify as refund-status, payment-failed or other: {msg}")
                .param("msg", message))
    .call().content().trim();

if (intent.equals("refund-status")) {
    String orderId = extractOrderId(message);       // step 2: another LLM call
    Order order = gateAndFetch(orderId, customerId); // step 3: code only, no LLM
    return draftReply(order);                        // step 4: final LLM call
}
return "Sorry, I can only help with refunds and payments.";
```

What to notice:

- `intent` comes from the model, but the `if` that acts on it is plain Java, so the control flow is fixed and testable.
- `gateAndFetch` runs in code with no LLM, so it cannot be talked out of its permission check by the message text.
- Each helper is its own small, testable unit; you can swap the draft prompt without touching the classify step.
- If step 1 returns anything but `refund-status`, the later, costlier calls never run, saving latency and tokens.

## Rules and defaults

- **Put a code check between steps:** validate or clean each output before the next step trusts it; a wrong early step otherwise flows through the whole chain.
- **More calls, more cost:** each step adds latency, token cost and a new place to fail; chain only when the accuracy is worth it.
- **Other fixed patterns exist:** Anthropic also describes routing, parallelisation, orchestrator-workers and evaluator-optimiser as workflows where code controls the structure.
- **When the path cannot be fixed:** if the steps cannot be known in advance, an [agent](card:ai-agents) that decides them at run time fits better than a chain.

## Not to be confused with

A **chain** follows steps your code fixes in advance. An **[agent](card:ai-agents)** lets the model pick the next step and which tools to call, in a loop, until the task is done. Rule: in a chain your code owns the path; in an agent the model does.

## Interview Qs

### What is prompt chaining and when do you use it?

Breaking a task into a fixed sequence of LLM calls, each using the previous output, with code checks in between. Use it when the task splits cleanly into subtasks and accuracy matters more than latency, so each small step can be tested and fixed on its own.

### What are the downsides?

More calls mean more latency, more cost, and more places to fail. A mistake in an early step flows into every later step, so you must check each step's output in code before the next one runs. If the task does not split cleanly, chaining adds overhead for little gain.

### How is a chain different from an agent?

A chain follows steps fixed in your code, so the path is known before it runs. An agent lets the model decide the next step and which tools to call, in a loop, until the goal is met. The chain is more predictable; the agent handles tasks whose path cannot be fixed in advance.
