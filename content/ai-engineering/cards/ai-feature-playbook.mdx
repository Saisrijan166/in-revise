## What it is

The playbook is one ordered answer to the common closing question "how would you build an AI feature?". It ties the whole tech together: the steps are the concepts you have already met, placed in the order you would actually build them. Every AI feature has the same four core parts, Model, Prompt, Retrieval and Validation, wrapped in a backend that owns security. Learning the sequence lets you give a clear, confident answer instead of listing techniques at random.

## Why it exists

Asked to design an AI feature, many candidates jump between embeddings, prompts and agents with no thread, and forget the parts that make a feature production-ready. A fixed sequence stops the rambling: you walk one example end to end, then add the operational concerns. It also keeps the most important rule in front of you, that the backend, not the model, authorises and executes actions, which is where real designs go wrong.

1. Expose an API so the browser calls your backend and the key and rules stay server-side.
2. Authenticate and authorise the caller, so you know the user and tenant.
3. Retrieve allowed context if the answer needs private or fresh data, else skip this step.
4. Build the prompt (rules, context, question) and call the model.
5. Validate the reply against a schema and business rules, then return it, and wrap the whole path in the add-ons.

So the key is one example, in order, with the backend owning every action.

What to notice:

- A plain answer flows model to validate to the user, so nothing reaches the browser unchecked.
- A `refundPayment` request does not run itself: it goes to a backend auth check of user, amount and policy before the payment service executes it.
- The pgvector store feeds retrieval, so the model answers from your documents, not from memory alone ([grounding](card:grounding-and-citations)).

## Not to be confused with

The four core parts are easy to blur. The **model** generates text; the **prompt** instructs it; **retrieval** (embeddings plus a vector DB) supplies the right context; **validation** checks the reply. Two more sit around them: **tool calling** lets the model act through your code, and the **backend** enforces security and rules. Rule: the model and prompt produce words, retrieval supplies facts, and the backend decides what actually happens.

## Interview Qs

### How would you build an AI feature?

Walk the six steps on one example, such as a refund assistant: expose an API, authenticate, retrieve allowed context, build the prompt and call the model, validate, return. Then list the production add-ons: streaming, retries, rate limits, cost control, monitoring and injection defence. Stress that the backend, not the model, authorises and executes any action.

### In a payment app, should the LLM decide refunds?

No. The model may explain a failed payment and request a `refundPayment` action, but it must not issue the refund. The backend checks the user, the amount and the refund policy, and only then does the payment service execute it. The model has no view of who is allowed to do what, so authorisation stays in code.

### Where do most AI feature designs go wrong?

Three places. Letting the model act instead of only suggest, so an action runs without a backend check. Skipping retrieval filters, so a user sees another tenant's data. And trusting the raw reply, so malformed or injected output is passed on. Fixing each means the backend authorises actions, filters retrieval, and validates every reply.
