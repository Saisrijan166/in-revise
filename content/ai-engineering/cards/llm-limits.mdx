## What it is

This concept is the boundary line: what you can trust an [LLM](card:what-is-an-llm) to do, and what your backend must still own. An LLM is strong at working with language, which it generates, summarises, translates and reasons over. It is weak as a store of truth, because it holds no live data, keeps no memory between calls, and does not guarantee the same answer twice. Teams get into trouble when they wire it in as if it were a smart database.

## Why it exists

It is tempting to let the model answer everything, including "what is this customer's balance?" or "is this refund allowed?". But the model only knows what was in its training text or in the current request, and it gives no guarantees. Treating it as a data source or a rule engine leads to wrong balances, invented facts and unenforced permissions. Naming the limits tells you clearly which work stays in the backend and the database.

## How it works

The clearest way to see the limits is to compare the LLM with the two tools it is often mistaken for.

<Compare id="llm-vs-database-vs-search-engine" />

1. Decide what the task needs: an exact stored fact, a ranked set of documents, or new text written from given information.
2. Send exact facts (orders, payments, permissions) to the database, not the model.
3. Find relevant documents with search or [retrieval](card:what-is-rag), not the model's memory.
4. Give the model the facts and documents from those steps, and let it do the one thing it is good at: write the answer.

So the key is that the LLM is the last step that phrases the answer, not the place where facts or decisions live.

## Example

A short map of what to trust the model with, and what to keep in code.

```text
Trust the LLM to:                    Do NOT trust the LLM to:
  generate / summarise / translate     guarantee a fact is true
  classify and extract fields          enforce who is allowed to do what
  reason over context you supply       give the same output every time
  call tools you provide               know private or current data
  fill a JSON schema when constrained  run actions safely on its own
```

What to notice:

- The left column is all language work over information you supply; the right column is all truth, authority and determinism.
- For today's order status, the model must call a [tool](card:tool-calling) or use [RAG](card:what-is-rag); the wiring is in [ai-and-databases](card:ai-and-databases).
- History across calls is not in this table because the model has none; your app provides it, see [conversation memory](card:conversation-memory).

## Not to be confused with

A plain LLM call answers only from training; a RAG call answers from documents fetched for this request. The limits here are about the plain model; RAG lifts the "no private or current data" limit by supplying that data, but not the "not the source of truth" or "non-deterministic" ones. See [rag-vs-plain-llm](compare:rag-vs-plain-llm). Rule: RAG adds knowledge to the request; it does not make the model exact or authoritative.

## Interview Qs

### What is a knowledge cutoff, and how do you work around it?

It is the date the model's training data ends. The model knows nothing that happened after it, and it never knew your private data. You work around it by fetching current and private facts at request time with tools or RAG, so the real data is in the request rather than relied on from the model.

### Can the LLM decide whether a refund is allowed?

No. The rule and the check live in backend code against the database. The model may explain the decision in plain language, but the backend makes the decision and enforces it. Letting the model decide would put business logic and authorisation in an unreliable, non-deterministic place.

### Why does temperature 0 still give different answers sometimes?

Generation is not guaranteed to be deterministic; Anthropic's docs state that results can vary even at temperature 0. So you should not depend on identical output. Anything that must be exact or repeatable belongs in your code and database, not in the model's reply.
