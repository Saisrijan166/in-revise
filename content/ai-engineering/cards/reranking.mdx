## What it is

Reranking is a second pass placed after retrieval. First, fast search (vector, keyword or [hybrid](card:hybrid-search)) returns a shortlist of candidate chunks. Then a **cross-encoder** reads the query together with each candidate and gives it a fresh relevance score, and you keep only the top few for the prompt. A cross-encoder is a model that takes the (query, chunk) pair as one input, unlike the [embedding model](card:embeddings) that scores each text on its own.

## Why it exists

Fast retrieval has to scan millions of chunks, so it compares pre-computed vectors; the query and a chunk are embedded separately and never read together. That is quick but coarse, so the shortlist often contains chunks that are on the right topic yet do not actually answer the question. Reranking adds a slower model that reads each pair properly, pushing the chunks that truly answer the query to the top before they reach the LLM.

## How it works

The bi-encoder (used for retrieval) and the cross-encoder (used for reranking) differ in what they read together; the table shows it.

<Compare id="bi-encoder-vs-cross-encoder" />

1. Retrieve a shortlist, for example the top 50 candidates, with fast search.
2. For each candidate, run the cross-encoder on the (query, chunk) pair to get a relevance score.
3. Sort the candidates by that score and keep the final top K, for example 5.
4. Put only those K chunks into the prompt and let the LLM answer.

So the key is that the slow, accurate model runs only on the small shortlist, not on the whole corpus. The reranker can be a [hosted rerank API](card:hosted-rerank-api), an open [cross-encoder model](card:open-cross-encoder), or an [LLM used as a reranker](card:llm-reranker); shortlist size and final K are set in [retrieval tuning](card:retrieval-tuning).

## Example

For the query "Where is my refund for order 42?". The numbers are an example, not a fixed rule.

```text
hybrid search  -> 50 candidate chunks     (fast, approximate)
cross-encoder  -> scores all 50 (query, chunk) pairs
keep top 5     -> into the prompt -> LLM writes the answer
```

What to notice:

- Retrieval stays wide (50 candidates) so the right chunk is unlikely to be missed; precision is fixed later.
- The cross-encoder runs 50 times, once per candidate, which is why the shortlist is kept to tens, not thousands.
- Only the top 5 reach the prompt, so the LLM reads less text and the answer is grounded in the most relevant chunks.

## Rules and defaults

- **Two stages, not one:** retrieval is wide and fast; reranking is narrow and accurate. Do not replace retrieval with a reranker.
- **No pre-indexing:** a cross-encoder produces a score, not a reusable vector, so it must run at query time for every candidate.
- **Tune the shortlist:** a bigger shortlist improves recall but costs more latency; measure whether the answer quality gained is worth it.

## Interview Qs

### What is reranking and why use it?

A second pass that re-scores the chunks retrieval returned against the query and keeps the most relevant. Embedding search is fast but compares the query and chunks as separate vectors, so it is approximate. A cross-encoder reads both texts together and judges relevance more accurately, improving what the LLM finally sees.

### Why not use a cross-encoder for the whole search?

It produces no vector to index, so it cannot be pre-computed; it must run once per (query, document) pair. Over millions of documents that is far too slow for a live request. Use fast vector or hybrid search to get a shortlist, then apply the cross-encoder only to those candidates.

### What does reranking cost, and when is it worth it?

One extra model run per candidate, so latency grows with the shortlist size. It is worth it when retrieval returns topically-similar but off-target chunks and answer quality suffers. Keep the shortlist small, measure the quality gain against the added latency and cost, and drop it if the gain is marginal.
