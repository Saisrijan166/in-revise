## What it is

Choosing a model means picking the cheapest model that is still good enough for the task, and controlling cost means lowering the tokens and calls that drive the bill. Providers offer a range from small, fast, cheap models to large, slow, expensive ones. You bill for every token in and out, so the goal is the lightest model that passes your [evals](card:ai-evaluation), plus habits that trim how much you send and how often.

## Why it exists

The biggest model is the slowest and the dearest, and most requests do not need it. If you default to it for every call, you pay top price for FAQ lookups and simple rewrites, and the bill grows with traffic. Because the cost is per token, a bloated prompt or a reply with no length cap quietly multiplies the spend. Picking the right model and cutting tokens turns a large bill into a small one without hurting the answers that matter.

## How it works

| Factor | The question to ask |
|---|---|
| Quality | Does it pass our eval set on real questions? |
| Latency and cost | Fast and cheap enough at our volume? |
| Context and features | Does the prompt fit? Does it support tools, structured output, reasoning? |
| Data rules | Privacy, data residency, self-hosting needs? |
| Availability | Rate limits, regions, and is there a fallback model? |

1. Build an eval set from real questions and score candidate models on it.
2. Start from a cheap model and upgrade only the cases it fails, or start strong and step down while quality holds.
3. Cut tokens: shorter prompts, fewer [retrieved chunks](card:retrieval-tuning), and [output length caps](card:sampling-parameters).
4. Cut calls: a response cache for repeated answers, and a batch API for offline jobs.
5. Make the calls you keep cheaper with prompt caching and small models where they suffice.

## Example

Prompt caching only helps when the unchanging text comes first, so the provider can reuse that prefix.

```text
[ system rules + refund-policy text ]          same every call: cached prefix
[ user: "Where is my refund for order 42?" ]   changes: goes last
```

What to notice:

- The policy text is identical on every call, so placing it first lets the provider reuse the work it already did on that prefix.
- The user line changes each time, so it must come last; anything after the first changed token cannot be reused.
- Put the question first instead and the prefix differs every call, so nothing is cached and you pay full input cost each time.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Prompt caching | On for supported models | OpenAI docs |
| Prompt cache lifetime | 5 minutes, with a 1-hour option | Anthropic docs |

- **Batch discount:** offline jobs through the Batch API return within 24 hours at 50% off (OpenAI, Anthropic).
- **Response cache keys:** key on everything that changes the answer (tenant, user, model version) and set a TTL, or you risk serving a wrong, stale or someone else's answer.

## Not to be confused with

A prompt cache and a response cache both save money but work differently. Prompt caching is run by the provider and reuses an identical prompt prefix, so the model still runs every call but the input is cheaper and faster. A response cache is run by you and stores whole answers, so a hit skips the model entirely but risks a stale or personal answer. Rule: prompt caching is always safe; a response cache needs careful keys and a TTL.

## Interview Qs

### How do you choose a model for a feature?

Build an eval set from real questions and score candidate models on it. Start cheap and upgrade only where it fails, or start strong and step down while quality holds. Then check latency and cost at your volume, the features you need (tools, structured output, reasoning), and any data-residency or self-hosting rules.

### How do you reduce LLM cost?

Three levers. Fewer tokens: shorter prompts, fewer retrieved chunks, output-length caps. Fewer calls: a response cache for repeated, non-personal answers. Cheaper calls: a smaller model where it passes, prompt caching for shared prefixes, and the Batch API for offline jobs at half price.

### What can go wrong when you cache AI answers?

A response cache can serve another customer's answer, a stale answer after a policy change, or leaked sensitive data. Key the cache on whatever changes the answer, such as tenant, user and model version, and set a TTL so old answers expire. Prompt caching does not have this risk, because the model still generates each reply.
