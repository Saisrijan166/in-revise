## Why it exists

The biggest model is slow and dear, and most requests do not need it. Every token is billed.

## How it works

| Factor | Ask |
|---|---|
| Quality | Passes our eval set? |
| Latency, cost | Fast and cheap enough at volume? |
| Context, features | Prompt fits? Tools, structured output, reasoning? |
| Data rules | Privacy, residency, self-hosting? |
| Availability | Rate limits, regions, a fallback? |

- Fewer tokens: shorter prompts, fewer chunks ([top-K](card:retrieval-tuning)), [output caps](card:sampling-parameters).
- Fewer calls: a response cache; a batch API for offline jobs.

## Example

Prompt order for prompt caching:

```text
[ system rules + refund-policy text ]          same every call: cached prefix
[ user: "Where is my refund for order 42?" ]   changes: goes last
```

## Interview Qs

### How do you choose a model for a feature?

Build an eval set from real questions. Start cheap and upgrade where it fails, or start strong and step down; check latency, features and data rules.

### How do you reduce LLM cost?

Fewer tokens: shorter prompts, fewer chunks, output caps. Fewer calls: a response cache. Cheaper calls: small models, prompt caching, batch for offline jobs.

### What can go wrong when you cache AI answers?

Another customer's answer, a stale answer after a policy change, or leaked sensitive data. Key on whatever changes the answer (tenant, user, model version); set a TTL.
