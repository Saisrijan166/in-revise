## Why it exists

Model output can be steered by attackers or simply be wrong. Anything the model can reach or decide is attack surface.

## How it works

| OWASP LLM Top 10 (2025) | In one line |
|---|---|
| LLM01 Prompt Injection | Input overrides your instructions: [prompt injection](card:prompt-injection) |
| LLM02 Sensitive Information Disclosure | The app leaks PII, secrets or business data |
| LLM03 Supply Chain | Tampered third-party models, datasets, adapters or packages |
| LLM04 Data and Model Poisoning | Bad training, fine-tuning or embedding data plants backdoors |
| LLM05 Improper Output Handling | Output used unchecked: [output validation](card:output-validation) |
| LLM06 Excessive Agency | Too many tools, rights or autonomy: [agents](card:ai-agents) |
| LLM07 System Prompt Leakage | Secrets or rules in the prompt get exposed |
| LLM08 Vector and Embedding Weaknesses | Vector store leaks across users or is poisoned: [filters](card:metadata-and-filtering) |
| LLM09 Misinformation | Confident wrong answers: [hallucination](card:hallucination) |
| LLM10 Unbounded Consumption | Uncapped calls: outages, huge bills, model cloning: [limits](card:calling-llm-apis) |

- The model is a zero-trust user: what it asks for goes through the same checks as any user.
- API keys live in environment variables or a secrets manager: see [Spring AI setup](card:spring-ai-integration).

## Interview Qs

### How do you secure an LLM application?

Keep auth, permissions and business rules in code; give tools least privilege and run them as the user; keep secrets out of prompts; mask PII; validate output; ask a human before risky actions; rate-limit and monitor.

### What is the OWASP Top 10 for LLM Applications?

OWASP's list of the main LLM app risks (2025 edition): prompt injection first, then sensitive information disclosure, improper output handling, excessive agency, system prompt leakage, unbounded consumption and more.
