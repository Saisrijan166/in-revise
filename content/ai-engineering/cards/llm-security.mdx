## What it is

Securing an LLM application means deciding what the model is allowed to touch, and enforcing that in your own code rather than trusting the model. The model is treated as an untrusted user: it can be steered by [prompt injection](card:prompt-injection) or simply be wrong, so anything it can reach or decide is attack surface. The industry checklist for this is the OWASP Top 10 for LLM Applications 2025.

## Why it exists

A model's output is not under your full control. An attacker can push it off course, and even a clean prompt can produce a wrong or unsafe answer. If you let the model's words directly authorise a refund, run a query, or reveal a secret, one bad output becomes a breach. LLM security exists to draw a firm line: the model drafts, and your code checks and acts.

## How it works

The OWASP Top 10 for LLM Applications 2025 names the main risks. Each one maps to a concrete defence in your app.

| OWASP LLM Top 10 (2025) | In one line |
|---|---|
| LLM01 Prompt Injection | Input overrides your instructions: [prompt injection](card:prompt-injection) |
| LLM02 Sensitive Information Disclosure | The app leaks PII, secrets or business data |
| LLM03 Supply Chain | Tampered third-party models, datasets, adapters or packages |
| LLM04 Data and Model Poisoning | Bad training, fine-tuning or embedding data plants backdoors |
| LLM05 Improper Output Handling | Output used unchecked: [output validation](card:output-validation) |
| LLM06 Excessive Agency | Too many tools, rights or autonomy: [agents](card:ai-agents) |
| LLM07 System Prompt Leakage | Secrets or rules put in the prompt get exposed |
| LLM08 Vector and Embedding Weaknesses | A shared vector store leaks across users or is poisoned: [filters](card:metadata-and-filtering) |
| LLM09 Misinformation | Confident wrong answers: [hallucination](card:hallucination) |
| LLM10 Unbounded Consumption | Uncapped calls cause outages, huge bills or model cloning: [limits](card:calling-llm-apis) |

1. Start from authentication and authorisation in your backend, exactly as for any API.
2. Give the model and its tools least privilege: only the actions and data the task needs, run as the logged-in user.
3. Keep secrets out of the prompt; read API keys from environment variables or a secrets manager ([Spring AI setup](card:spring-ai-integration)).
4. Validate every output before it reaches a user or another system.

So the key is that the model is zero-trust: its requests pass the same checks you would apply to any outside user.

## Example

The support assistant can look up orders, but the identity must never come from the model.

```java
@Tool(description = "Get the current user's orders")
List<Order> getOrders(ToolContext context) {           // no userId parameter for the model
    Long userId = (Long) context.getContext().get("userId");  // from the session, not the model
    return orderRepository.findByUserId(userId);       // query scoped to that user
}
```

What to notice:

- The tool has no `userId` the model can fill in, so an injected message cannot ask for someone else's orders.
- The `userId` comes from Spring AI's `ToolContext`, which your code sets from the authenticated session and does not send to the model.
- The database query is scoped to that user, so even a hijacked model is limited to its own data. Remove the scoping and you reopen OWASP LLM06.

## Rules and defaults

- **Security decisions:** authentication, authorisation, input and output validation, and money-moving transactions run in code, never in the prompt.
- **Least privilege:** tools and database credentials grant only what the task needs; prefer read-only where possible.
- **Secrets:** API keys live in server-side config or a secrets manager, not in prompts, logs or client code (OWASP LLM07).
- **Provider data use:** on the OpenAI API, data sent via the API is not used to train models by default, and abuse-monitoring logs are kept for a limited window; confirm each provider's current terms before sending regulated data.

## Not to be confused with

[Prompt injection](card:prompt-injection) is one specific risk (LLM01): untrusted text overriding your instructions. LLM security is the whole programme that assumes injection and other failures *will* happen and contains them with code-side controls. Rule: prompt injection is an attack; LLM security is your defence-in-depth for all of the Top 10.

## Interview Qs

### How do you secure an LLM application?

Keep authentication, permissions and business rules in code; give tools least privilege and run them as the logged-in user; keep secrets out of prompts; mask PII before the call; validate output before use; ask a human before risky actions; and rate-limit and monitor the system.

### What is the OWASP Top 10 for LLM Applications?

OWASP's list of the main risks in LLM apps, 2025 edition. It starts with prompt injection, then sensitive information disclosure, supply chain, data and model poisoning, improper output handling, excessive agency, system prompt leakage, vector weaknesses, misinformation and unbounded consumption. It is the standard checklist interviewers expect.

### Should the model ever decide who is allowed to do something?

No. Authorisation is a security decision and must run in your code. The model can be injected or simply wrong, so let it suggest an action, then have the backend confirm the user's identity and rights before doing it.
