## What it is

Conversation memory is how a chatbot keeps track of what was said earlier, even though the LLM API is stateless. Stateless means each call stands alone: the model sees only the messages you send in that one request and remembers nothing afterwards. So "memory" is not inside the model. It is your app saving the messages of each conversation and sending the relevant earlier ones again on the next call.

## Why it exists

A follow-up like "and order 43?" makes sense only next to the question before it. But the API keeps no state, so if you send just that line, the model has no idea what came before and answers badly. To fix this your app must resend the earlier turns with each new message. The question then becomes how much history to resend, because the [context window](card:context-window) is limited and every resent message costs tokens.

## How it works

| Strategy | What is sent each turn | Watch out for |
|---|---|---|
| Full history | every earlier message | tokens and cost grow with every turn |
| Sliding window | only the last N messages | facts from early in the chat drop out |
| Summary | a short summary of old turns plus the recent turns | details can be lost in the summary |
| Long-term store | facts found by search, read on demand | needs per-user filters so histories stay separate |

1. Give each conversation an id, built on the server from the user and session.
2. Save every message under that id as the chat goes on.
3. On a new question, load the earlier messages for that id and choose how much to include (full, window or summary).
4. Send those messages plus the new question in one call, keeping the total within the context window.
5. For facts that must outlive the chat, store them in a searchable store and read them back like a [RAG pipeline](card:rag-pipeline).

So the key is that the app, not the model, decides what history the model sees each turn.

## Example

Spring AI's memory advisor loads and saves the history by conversation id for you.

```java
@Service
class SupportChat {
    private final ChatClient chat;
    SupportChat(ChatClient.Builder builder, ChatMemory memory) {
        this.chat = builder
            .defaultAdvisors(MessageChatMemoryAdvisor.builder(memory).build()).build();
    }
    String ask(String userId, String sessionId, String question) {
        return chat.prompt().user(question)
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, userId + ":" + sessionId))
            .call().content();
    }
}
```

What to notice:

- The advisor automatically loads the stored history for the conversation id and prepends it before the model call, then saves the new turn.
- The conversation id is `userId + ":" + sessionId`, built on the server, so one user's chat can never load another's.
- If you reused the same id across users, histories would mix and leak; the id must include the user.
- The default memory keeps only the last 20 messages, so older turns drop out unless you summarise them yourself.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Memory type | `MessageWindowChatMemory`, last 20 messages | Spring AI 2.0 auto-configured `ChatMemory` |
| Storage | `InMemoryChatMemoryRepository`, lost on restart | Spring AI 2.0 |

- **Stateless API:** the model never remembers; you must resend history each call. Provider-stored state (OpenAI `previous_response_id` or the Conversations API) saves you sending it, but the stored history is still billed as input tokens.
- **Per-user isolation:** build the conversation id on the server from user and session; only list or delete the current user's conversations.

## Not to be confused with

Short-term memory is the recent turns you resend each call, limited by the context window. Long-term memory is durable facts about the user, kept in a searchable store and read on demand like RAG. Rule: resend recent turns for continuity; search a store for facts that must outlive the chat.

## Interview Qs

### How does a chatbot remember earlier messages if the API is stateless?

It does not remember inside the model. The app stores the conversation and resends the relevant earlier messages with each request, so the model sees the context again. The model only seems to remember; the continuity comes from your app resending history every turn.

### The conversation is getting too long. What do you do?

Stop sending the whole history. Keep a sliding window of the most recent turns, summarise the older turns into a short note, and move durable facts into a searchable store you read on demand. This keeps the prompt within the context window and controls token cost, at the risk of losing some detail.

### How do you keep one user's history from leaking to another?

Build the conversation id on the server from the user and session, never from client input, so ids cannot be guessed or forged. When loading, listing or deleting conversations, filter to the current user only. This way one user's messages are never sent into another user's prompt.
