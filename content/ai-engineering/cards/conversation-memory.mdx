## Why it exists

A follow-up like "and order 43?" means nothing alone. The API keeps no state, so the app sends earlier turns.

## How it works

| Strategy | What is sent each turn | Watch out |
|---|---|---|
| Full history | every earlier message | tokens and cost grow each turn |
| Sliding window | only the last N messages | early facts drop out |
| Summary | a summary of old turns + recent turns | details can be lost |
| Long-term store | facts found by search, read on demand | needs per-user filters |

- The [context window](card:context-window) caps how much history fits; search-style memory works like a [RAG pipeline](card:rag-pipeline).
- Provider-managed state exists: OpenAI `previous_response_id` or the Conversations API.
- Follow-ups need rewriting before retrieval: see [retrieval tuning](card:retrieval-tuning).

## Example

Spring AI 2.0: a memory advisor loads and saves history by conversation id.

```java
@Service
class SupportChat {
    private final ChatClient chat;
    SupportChat(ChatClient.Builder builder, ChatMemory memory) {
        this.chat = builder
            .defaultAdvisors(MessageChatMemoryAdvisor.builder(memory).build()).build();
    }
    String ask(String userId, String sessionId, String question) {
        return chat.prompt().user(question)
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, userId + ":" + sessionId))
            .call().content();
    }
}
```

## Defaults

| What | Default | Where |
|---|---|---|
| Memory type | `MessageWindowChatMemory`, last 20 messages | Spring AI 2.0 auto-configured `ChatMemory` |
| Storage | `InMemoryChatMemoryRepository` (lost on restart) | Spring AI 2.0 |

## Interview Qs

### How does a chatbot remember earlier messages if the API is stateless?

The app stores the conversation and resends the relevant earlier messages with each request. The model only seems to remember.

### The conversation is getting too long. What do you do?

Keep a sliding window of recent turns, summarise older ones, and move durable facts to a searchable store.

### How do you keep one user's history from leaking to another?

Build the conversation id on the server from user and session, never from client input, and only list or delete the current user's conversations.
