## What it is

The context window is the maximum number of [tokens](card:tokens) a model can take in for a single request. It covers both the text you send and the text the model writes back: the two share one budget. It is not memory of past conversations. It is the working space for this one call, and it is empty again on the next call unless your app sends the history once more.

## Why it exists

A model cannot attend to unlimited text at once; the [transformer](card:transformer-and-attention) that runs it has a fixed size it was trained for. So there must be a hard limit on how much fits in one request. That limit forces your app to decide what to include, because anything you leave out simply does not exist for the model on that call: it cannot look past the window to find it.

## How it works

Every part of a request shares the same window, from the system prompt at the top to the model's reply at the bottom.

1. Your app assembles the request: system prompt, tool definitions, past turns, any retrieved chunks and the new question.
2. Those input tokens are counted; if they already exceed the window, the provider rejects the call with an error.
3. If they fit, the model generates its reply into the remaining room.
4. If the reply reaches the edge of the window, generation stops early and the answer is cut off.

So the key is that input and output compete for one budget, and the app, not the model, decides what gets in.

## Example

The window is measured in tokens, so the same budgeting from [tokens](card:tokens) applies to the whole request.

```java
// Rough budget before sending, so the request fits the window
int systemAndTools = 400;
int history        = 1200;
int retrievedChunks = 2500;   // trim this first when the request is too large
int question       = 50;
int maxOutput      = 800;     // reserve room for the reply inside the same window
int total = systemAndTools + history + retrievedChunks + question + maxOutput;
```

What to notice:

- `maxOutput` is part of the same total: reserving room for the reply is as important as trimming the input.
- `retrievedChunks` is the largest and most adjustable part, so it is the first thing to cut when the request is too big.
- If `total` exceeds the model's window, the request fails before the model runs; you must shrink one of these numbers.

## Rules and defaults

- **Input over the window:** Anthropic returns a 400 error; the call never runs.
- **Reply reaches the window:** OpenAI returns the response with status `incomplete`; Anthropic returns `stop_reason: max_tokens`. The answer is partial.
- **Reasoning tokens count too:** a reasoning model's hidden thinking tokens use part of the same window and the output cap.
- **Window size varies by model:** check the model's documented context length; do not assume it from another model.

## Not to be confused with

The context window holds only this one request; it is working space, not the model's knowledge or its memory. What the model learned lives in its weights from [training](card:how-models-learn). Memory across calls is something your app provides by re-sending history; see [conversation memory](card:conversation-memory). Rule: window = tokens for this call; weights = what it learned; memory = history your app re-sends.

## Common mistakes

- **"A huge window means I can skip RAG and send every document."** Long prompts cost more, run slower, and recall facts in the middle less reliably (Liu et al., 2023). Retrieval sends only the relevant part; see [RAG](card:what-is-rag).

## Interview Qs

### What happens when a conversation grows longer than the window?

The request fails, or the reply is cut off, because input and output share one token budget. The app must trim or summarise old turns and send fewer, more relevant chunks. Counting tokens before each call keeps the request inside the limit.

### If a model has a very large window, do we still need RAG?

Usually yes. A large window costs more and runs slower per call, and the model uses facts in the middle of a long prompt less reliably. Retrieval sends only the relevant part, which is cheaper, faster and often more accurate; see [RAG](card:what-is-rag).

### Is the context window the model's memory?

Only for this one request. It is working space that is empty again on the next call. The model's lasting knowledge is in its weights, and any memory of earlier turns exists only because the app re-sends that history.
