## What it is

Tool calling, also called function calling, is a way to let the model use functions you write. You give the model a list of tools; each tool has a name, a short description and a [JSON Schema](term:json-schema) for its arguments. The model still only produces text, but now one kind of reply is a request to call a named tool with arguments. Your code runs the real function and sends the result back.

## Why it exists

An [LLM](card:what-is-an-llm) can only write text from what it learnt during training. It cannot read today's payment status or start a refund, and it has no access to your database. Without tool calling you would be stuck pasting live data into the prompt by hand. Tool calling lets the model ask your backend for exactly the data or action it needs, through code you control, so its answers can be live and specific.

## How it works

1. Your app sends the user's question together with the tool definitions.
2. Instead of answering, the model replies that it wants to call `getPaymentStatus` with `orderId=42`.
3. Your code validates the arguments and checks that the signed-in user is allowed to see order 42.
4. Your backend runs the real function, reads the database and gets the status.
5. Your app sends that result back to the model, which now writes the final answer.

So the key is that the model decides *which* tool to call, but *your* code decides whether and how to run it.

## Example

The tool is a normal Spring bean. The user id comes from the session through `ToolContext`, which the model never sees or controls.

```java
@Component
class PaymentTools {
    private final PaymentService payments;
    PaymentTools(PaymentService payments) { this.payments = payments; }

    @Tool(description = "Get the status of one payment by its order id")
    PaymentStatus getPaymentStatus(long orderId, ToolContext ctx) {
        long userId = (long) ctx.getContext().get("userId"); // from the session
        return payments.statusFor(userId, orderId);          // checks ownership
    }
}
// chatClient.prompt(q).tools(paymentTools).toolContext(Map.of("userId", id)).call().content();
```

What to notice:

- `@Tool`'s `description` is what the model reads to decide when to call this function, so it must be clear and specific.
- `orderId` comes from the model, but `userId` comes from `ToolContext`, set from the session. The model cannot change it.
- `statusFor(userId, orderId)` checks the order belongs to that user, so a model asking for someone else's order gets nothing.
- If you removed the ownership check and trusted only the model's arguments, a crafted question could read another user's payment.

## Rules and defaults

- **The model never executes code:** it only returns a tool name and JSON arguments; your application runs the function.
- **Strict schema (opt-in):** OpenAI structured tool calls and Anthropic `strict: true` make the model's arguments match your JSON Schema, so you do not get malformed JSON. OpenAI recommends enabling it.
- **Parallel tool calls:** both providers may return several tool calls in one turn and both let you disable this when you need calls run one at a time.
- **Cost:** tool definitions are billed as input tokens on every request, so a long tool list is slow and expensive; keep tools few and narrow.
- **Safety:** make read-only tools the default, and require backend checks and confirmation for any action that moves money.

## Not to be confused with

Tool calling is a feature of the provider's LLM API: one app, one set of functions. [MCP](card:mcp) is an open protocol for sharing tools across apps, and the model still uses tool calling underneath it. Rule: tool calling = how the model asks for one function; MCP = how apps and servers share those tools.

## Common mistakes

- **"Give the model a tool for everything, just in case."** Each tool's definition is sent as input tokens every call, and a long list makes the model pick worse. Expose only the few tools the feature needs.
- **"Trust the ids the model sends."** The model's arguments are untrusted input. Take identity from the session, re-check permissions in the backend, and validate every argument.

## Interview Qs

### Does the LLM execute the function?

No. The model returns the tool name and JSON arguments as text. Your application decides whether to run it, validates the arguments, runs the real code, and sends the result back so the model can continue or write the final answer. The model never connects to your database or services.

### How do you stop the model refunding someone else's order?

Never let the model supply the user's identity. Pass the signed-in user id from the session, for example with Spring AI `ToolContext`, and look up the order for that user only. Check ownership and business rules in the backend, require confirmation for money-moving actions, and use an idempotency key so a retry cannot refund twice.

### Why keep the number of tools small?

Each tool definition is sent as input tokens on every request, which costs money and adds latency. A long tool list also makes the model more likely to pick the wrong one. Expose only the tools the feature needs, with clear descriptions.
