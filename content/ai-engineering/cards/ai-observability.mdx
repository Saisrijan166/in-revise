## Why it exists

AI calls are slow, priced per token and fail quietly: a wrong answer still returns HTTP 200. Traces show whether retrieval, the model or a tool caused it.

## How it works

| Record | Why |
|---|---|
| Latency and time to first token | Users feel the wait; streaming hides the rest |
| Input and output tokens, cost | Spend per feature and per user |
| Model name and version | Explains changes after a model switch |
| Errors, timeouts, 429s | Tune [retries and limits](card:calling-llm-apis) |
| Chunk ids and scores, tool calls | Find which step went wrong |
| User ratings | Feed the [eval set](card:ai-evaluation) |

- Spring AI emits Micrometer observations for ChatClient, advisors, models, tools and vector stores.
- Its token metric is `gen_ai.client.token.usage`, split into input and output.

## Example

One trace for "Where is my refund for order 42?" (timings illustrative):

```text
POST /api/support/chat                      2.4 s
├─ retrieval   refund-policy chunks 7, 12   120 ms
├─ chat        model, 1,850 in / 140 out    1.9 s
├─ execute_tool getOrderStatus(42)          40 ms
└─ validate    refund rules                 5 ms
```

## Defaults

| What | Default | Where |
|---|---|---|
| Log prompt / completion | false | Spring AI 2.0 (`spring.ai.chat.observations.log-prompt`) |
| Tool arguments and results | not recorded | Spring AI 2.0 (`spring.ai.tools.observations.include-content`) |

## Interview Qs

### What do you monitor in an LLM feature?

Latency and time to first token, tokens and cost, model version, error and 429 rates, retrieval scores and tool calls, and user feedback, all linked in one trace per request.

### Should you log prompts and responses?

Not by default. They can hold PII and secrets. Log ids, counts and scores; capture content only where needed, redacted, sampled and with short retention.
