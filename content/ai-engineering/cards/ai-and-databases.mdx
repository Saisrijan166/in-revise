## Why it exists

A model with raw database access can be talked into reading or changing any row. Tools give it only what this user may see.

- "Show my orders": the tool reads the user id from Spring AI's `ToolContext`, not from model arguments ([tool calling](card:tool-calling)).
- Text-to-SQL suits internal analytics; customer support uses fixed tools.
- Orders and policy chunks can share one PostgreSQL ([pgvector](card:vector-databases)).

## Example

Example: a read-only role for internal analytics (PostgreSQL 18).

```sql
CREATE ROLE ai_reader LOGIN;                          -- password from a secrets manager
CREATE VIEW order_stats AS                            -- allowlisted columns only
  SELECT id, status, total_inr, created_at FROM orders;
GRANT SELECT ON order_stats TO ai_reader;             -- no grant on the tables
ALTER ROLE ai_reader SET statement_timeout = '5s';    -- stop runaway queries
ALTER ROLE ai_reader SET default_transaction_read_only = on;   -- safety net
```

As `ai_reader`, the view works; `orders`, `DELETE` and a 7-second query fail. Sessions can turn read-only off: the `GRANT` is the real guard.

## Defaults

| What | Default | Where |
|---|---|---|
| `statement_timeout` | 0 (no timeout) | PostgreSQL 18 |
| `default_transaction_read_only` | off | PostgreSQL 18 |

## Interview Qs

### Should an LLM query the database directly?

No. It uses approved tools; the backend takes identity from the session, checks access and runs fixed, parameterised queries, so prompt injection cannot widen access.

### How would you make text-to-SQL safe?

Read-only role with SELECT on allowlisted views; parse and allow one SELECT; force a LIMIT; set a statement timeout; apply the user's permissions; log every query. Generated SQL is untrusted input.
