## What it is

AI with databases is how the model reads business data safely. The model is never given a database connection or allowed to run its own SQL on the live tables. Instead the backend exposes a few **approved tools**, each a fixed, parameterised query such as `getOrderStatus(orderId)`. When the model wants data it [requests a tool](card:tool-calling); the backend checks the logged-in user first, then runs the query. The same PostgreSQL database can also hold the [pgvector](card:vector-databases) chunks used for retrieval.

## Why it exists

A model with raw database access can be talked into reading or changing any row. Because its instructions can come from a retrieved document or the user's own text, a [prompt injection](card:prompt-injection) could tell it to run `SELECT * FROM orders` or a `DELETE`, and a raw connection would obey. Approved tools remove that risk: the model can only ask for a named, fixed query, and the backend decides, from the session and not the model, whether this user may see that data.

## How it works

1. The model decides it needs order data and requests the `getOrderStatus(42)` tool.
2. The backend runs the tool. It reads the user id from Spring AI's `ToolContext`, filled from the session, not from the model's arguments.
3. It checks whether that user may see order 42, and refuses if not.
4. If allowed, it runs the fixed, parameterised query and returns only that result to the model.

So the key is that identity and authorisation live in the backend tool, not in anything the model wrote. Text-to-SQL, where the model writes a query, suits internal analytics and needs its own guards; customer support uses fixed tools.

## Example

For internal analytics you may let the model write SQL, but it connects as a locked-down role (PostgreSQL 18).

```sql
CREATE ROLE ai_reader LOGIN;                          -- password from a secrets manager
CREATE VIEW order_stats AS                            -- allowlisted columns only
  SELECT id, status, total_inr, created_at FROM orders;
GRANT SELECT ON order_stats TO ai_reader;             -- no grant on the base tables
ALTER ROLE ai_reader SET statement_timeout = '5s';    -- stop a runaway query
ALTER ROLE ai_reader SET default_transaction_read_only = on;   -- safety net
```

What to notice:

- `GRANT SELECT ON order_stats` is the real guard: `ai_reader` can read the view but has no grant on `orders`, so a generated `DELETE` or a query on `orders` fails.
- The view exposes only four columns, so sensitive columns in `orders` are never reachable.
- `statement_timeout = '5s'` cancels a query that runs too long, so a 7-second query is killed.
- `default_transaction_read_only` is a safety net, not the main guard: a session can turn it off, so the `GRANT` must still be read-only on its own.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| `statement_timeout` | 0 (no timeout) | PostgreSQL 18 |
| `default_transaction_read_only` | off | PostgreSQL 18 |

- **Identity:** take the user id from the session via `ToolContext`, never from the model's tool arguments.
- **Generated SQL:** treat as untrusted input; parse to allow a single SELECT, parameterise, and add a LIMIT (OWASP LLM05).
- **Access:** a read-only role with SELECT on allowlisted views only, plus a statement timeout and row limit.

## Not to be confused with

A fixed tool and text-to-SQL are different ways for the model to reach data. A fixed tool runs a query you wrote, so the model only supplies arguments; it is the safe default for customer features. Text-to-SQL lets the model write the query itself, which is flexible for internal analytics but needs a read-only role and SQL validation. Rule: fixed tools for customer-facing features, guarded text-to-SQL for internal analytics only.

## Interview Qs

### Should an LLM query the database directly?

No. It should use approved tools. The backend takes the user's identity from the session, checks access, and runs fixed, parameterised queries. That way a prompt injection cannot widen access, because the model never chooses who it is or writes the SQL that runs on the live tables.

### How would you make text-to-SQL safe?

Connect as a read-only role with SELECT on allowlisted views only. Parse the generated SQL and allow a single SELECT. Parameterise values, force a LIMIT, and set a statement timeout. Apply the user's own permissions and log every query. Treat the generated SQL as untrusted input, because an injection could try to widen it.
