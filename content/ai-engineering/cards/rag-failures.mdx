## What it is

RAG failures are the distinct ways a [RAG pipeline](card:rag-pipeline) can produce a wrong answer. The same symptom, "the bot gave a wrong refund date", can come from a bad source document, a chunk that was never retrieved, a chunk ranked too low, too much noise around the right chunk, or the model misusing a chunk it did have. Sorting a failure into one of these types turns debugging from guessing into following the pipeline.

## Why it exists

Without a map of failure types, every wrong answer looks the same and people reach for the easiest change, usually a bigger model. That rarely helps, because most RAG failures happen in retrieval, where the model plays no part. Naming the failure type points you straight at the stage to fix, so you stop changing things that cannot matter.

## How it works

| Failure | Refund example | Likely fix |
|---|---|---|
| Data | Policy chunk still says 10 days | Fix and [re-index](card:rag-pipeline) the document |
| Retrieval | "UPI refund" chunk not in the results | [Chunking](card:chunking), [filters](card:metadata-and-filtering), [hybrid search](card:hybrid-search) |
| Ranking | Found at rank 9, but K is 5 | [Reranking](card:reranking), raise [top-K](card:retrieval-tuning) |
| Context | Right chunk sits among 20 noisy ones | Fewer, better chunks |
| Generation | Chunk present, model still says "3 days" | Fix the prompt, add [grounding](card:grounding-and-citations) |

1. For a failing question, log exactly which chunks were retrieved and in what order.
2. Check whether the chunk holding the answer is in that list at all.
3. If it is missing, the bug is upstream: fix the data, chunking, filters or search.
4. If it is present, the bug is downstream: fix the ranking, trim the noise, or fix the prompt and grounding.

So the key is to read the retrieved chunks first; their presence or absence splits every failure into a retrieval problem or a generation problem.

## Rules and defaults

- **Debug retrieval before generation:** inspecting the retrieved chunks is the first step; it tells you which half of the pipeline is at fault.
- **Measure both sides in evals:** use context recall and precision for retrieval, and faithfulness for the answer (see [evals](card:ai-evaluation)), so a change is only kept if the numbers improve.
- **RAG is never finished:** Barnett et al. found a RAG system can be validated only in operation, so keep monitoring real questions and extending the eval set.

## Interview Qs

### Your RAG bot gives wrong answers. How do you debug it?

Start by logging what was retrieved for the failing questions. If the right chunk is missing, fix the data, chunking, filters or search. If it was found but ranked low, rerank or raise K. If it was present but misused, fix the prompt and grounding. Then add each failing case to your evals.

### How do you improve a RAG system?

Work in order of cheapest, most likely wins: clean the documents, improve chunking, pick a suitable embedding model, add metadata filters, use hybrid search, add reranking, write a grounded prompt with citations, and keep evals that show whether each change actually helped.

### Is RAG ever "done"?

No. Barnett et al. found a RAG system can only be validated in operation, and its robustness evolves rather than being designed in up front. So you monitor the real questions users ask, keep extending the eval set, and treat tuning as ongoing rather than a one-time setup.
