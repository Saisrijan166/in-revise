## What it is

This playbook is a fixed order for answering the interview question "design a REST API for payments". It reuses the ₹500 payment, PAY101, that has run through this whole tech. Each step names one decision and links to the concept that explains it, so the answer covers the contract, security, correctness and failure handling, and leaves time to go deep where money is at risk.

## Why it exists

The question is open-ended, and under pressure candidates either list products, such as Redis and a queue, or forget a whole area, such as who may read a payment. A payment API adds one danger that most APIs do not have: a retry or a timeout can charge the customer twice. A fixed order makes sure nothing is skipped and brings the answer to the two places interviewers probe hardest, idempotency and timeouts.

<Steps label="The ₹500 request, in order">
  <Step title="Contract">The client calls `POST /api/payments` with the amount, currency, method and an `Idempotency-Key`; the payment is a [resource](card:resources-and-uris) that `GET /api/payments/{id}` reads.</Step>
  <Step title="Security">The API checks [who is calling](card:authentication-methods) over [HTTPS](card:https-tls), then checks that this caller [owns the account](card:owasp-api-security) being charged.</Step>
  <Step title="Validation">It checks amount, currency and format with [Bean Validation](card:request-binding-validation) and rejects bad input with one [error body](card:error-responses).</Step>
  <Step title="Idempotency">It looks up the key; if the same payment was already handled, it returns the first result instead of charging again ([idempotency keys](card:idempotency-keys)).</Step>
  <Step title="Saving">It stores PAY101 as PENDING in a durable database before calling anyone, so a crash cannot lose it.</Step>
  <Step title="Gateway call">It calls the gateway with a [timeout and bounded retries](card:retries-and-timeouts), passing the same key on each retry.</Step>
  <Step title="Status">It records SUCCESS or FAILED, or UNKNOWN after a timeout, which is [settled by checking with the gateway](card:unknown-outcomes); a declined payment is [a business result, not a 5xx](card:status-codes).</Step>
  <Step title="Async work">Receipts go to a queue and a worker; the final result arrives by [webhook](card:webhooks), and the page learns it by [SSE](card:websockets-and-sse) or a [status resource](card:long-running-operations).</Step>
  <Step title="Observability">One [trace ID](card:observability-for-apis) runs through the logs, metrics and traces of the whole request.</Step>
</Steps>

So the key is to name each failure before adding the component that handles it.

## Example

The request and response the design promises, with the key the client must reuse on a retry:

```text
POST /api/payments HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: order-789-payment
Content-Type: application/json

{"amount": 500, "currency": "INR", "method": "UPI"}

HTTP/1.1 201 Created
Location: /api/payments/PAY101

{"paymentId": "PAY101", "status": "PENDING", "amount": 500}
```

What to notice:

- The answer is 201 with a `Location`, and the status is PENDING, not SUCCESS: the gateway has not decided yet.
- If the client times out and sends the same request with the same `Idempotency-Key`, it gets this same response back and no second charge. A new key would mean a new payment.
- The body carries only what the client may set. The id, the status and the owner come from the server, which is how a [DTO](card:dto-mapping) keeps a caller from setting `"status": "SUCCESS"` itself.

## Rules and defaults

- **Stateless:** each request carries the token and the ids, and no server keeps a session, so [any instance can answer](card:statelessness).
- **Methods:** POST creates a payment and is not idempotent without a key; GET reads it; [PUT replaces a whole resource, PATCH changes part of it](compare:put-vs-patch-vs-post).
- **Status codes:** 201 with `Location` on create; [401 when not logged in, 403 when logged in but not allowed](compare:401-vs-403); [429 with Retry-After](card:rate-limiting) when a client sends too much.
- **Changes:** a breaking change gets [a new version](card:api-versioning), and the old one stays until clients move.
- **Provider code:** a strategy per payment method (UPI, card, wallet) and an adapter per gateway keep gateway-specific code in one place; the Design Patterns tech covers both.

## Common mistakes

- **"The gateway call timed out, so the payment failed."** The gateway may have charged. Mark it UNKNOWN and check before doing anything else.
- **Skipping the ownership check.** Logging in proves who the caller is, not that PAY101 is theirs. Without the check, changing the id in the URL shows another customer's payment.

## Interview Qs

### Design a REST API for payments. Where do you start?

With the resource and its states: PAY101 moves from PENDING to SUCCESS or FAILED, with UNKNOWN for timeouts. Then the contract, security, validation and idempotency, saving, the gateway call and status, async work and observability. Then I go deep on idempotency and timeouts, because that is where money gets charged twice.

### The gateway charged ₹500 but your call timed out. What now?

Do not charge again. Mark the payment UNKNOWN, ask the gateway for its status using our reference, or wait for its webhook, and retry only with the same idempotency key. A reconciliation job settles anything still open against the gateway's report.

### Which tests prove the design?

The [six payment cases](card:api-testing-strategy): a valid payment, an invalid amount, no login, another customer's token, a duplicate idempotency key and a gateway timeout. Each one checks a promise from this walkthrough, and the OpenAPI file documents them for other teams.
