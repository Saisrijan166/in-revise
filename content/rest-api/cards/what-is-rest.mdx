## What it is

An API (application programming interface) is the set of requests one program accepts from other programs, such as "create a payment". REST (Representational State Transfer) is a style for designing such APIs: six design rules, called constraints, on how a client and a server talk. Roy Fielding described it in 2000 by studying what lets the Web grow so large. A REST API is an API that follows these rules, usually with the [HTTP messages](card:http-request-response) you just saw.

## Why it exists

Without shared rules, every team shapes its API differently. One uses `POST /doPayment`, another `GET /getPaymentInfo?id=1`, and each needs its own manual. Generic tools cannot help either: a cache, which stores earlier responses to reuse them, cannot tell which calls only read data. REST gives every API the same shape. Things are named by URLs and handled with a few standard methods, and each message explains itself. So clients and caches work with any REST API in the same way.

## How it works

| Constraint | Rule | What you gain |
|---|---|---|
| Client-server | The screen and the stored data are separate | Each side changes on its own |
| Uniform interface | Every resource is used the same way | Simple calls any tool understands |
| Stateless | Each request carries all it needs | Any server can answer it |
| Layered system | Each part sees only the next layer | Gateways and caches fit in between |
| Cacheable | Responses say if they may be reused | Fewer calls to the server |
| Code on demand (optional) | The server may send code to run | Clients can be extended |

Follow one call, the app reading payment PAY101:

1. The app is the client and only shows screens. The payment server keeps the data (client-server).
2. The app names the payment by its address, `/api/payments/PAY101`, and uses a standard method, `GET`. The same few methods work for every resource (uniform interface).
3. The request carries everything, including who the caller is, so the server needs no memory of earlier calls (stateless).
4. On the way it may pass a gateway, proxy or load balancer, servers in the middle that forward requests, and the app neither knows nor cares (layered system).
5. The response says whether it may be reused for a while, so a cache can answer the next identical call (cacheable).

So REST is not one feature; it is these rules working together.

## Example

The same payment features designed without and with REST:

```text
Without REST: one URL per action        With REST: resources + methods
POST /createPayment                     POST /api/payments
POST /getPayment?id=PAY101              GET  /api/payments/PAY101
POST /refundPayment?id=PAY101           POST /api/payments/PAY101/refunds
```

What to notice:

- On the right, the URLs are nouns (payments, refunds) and the method carries the action. On the left, the action hides in the URL, so every API invents new words.
- `GET` tells every cache in between that this call only reads. On the left everything is `POST`, so no tool can tell reading from changing.
- A refund becomes its own resource under the payment, so it can later be read with `GET` like any other resource.

## Rules and defaults

- **Six constraints:** client-server, stateless, cacheable, uniform interface, layered system, and code on demand, which is the only optional one.
- **Uniform interface, four parts:** resources have identifiers; clients change them by sending representations; each message describes itself (for example, `Content-Type` names its format); and responses carry links to the next steps, which you will see in [HATEOAS](card:richardson-maturity-hateoas).
- **Not required by REST:** HTTP and JSON. They are the usual choices, not part of the definition.

## Not to be confused with

REST is the style: a set of constraints. A REST API is one API built to follow them. HTTP is the protocol that carries the requests and responses of most REST APIs. Rule: REST = the rules, REST API = the product, HTTP = the transport.

## Common mistakes

- **"Any API that sends JSON over HTTP is REST."** If every call is a `POST` to an action URL, the API skips the uniform interface. It is a remote procedure call over HTTP, even with JSON.

## Interview Qs

### What are the constraints of REST?

Client-server, stateless, cacheable, uniform interface, layered system, and the optional code on demand. The uniform interface means resources with identifiers, change through representations, self-descriptive messages and hypermedia links.

### Which REST constraint is optional, and why?

Code on demand: the server may send scripts for the client to run. Fielding marks it optional because it reduces visibility: a reader of the message can no longer see everything that will happen.

### Why do so many public APIs use REST?

It builds on HTTP, which every platform speaks, so any client can call it. Clients and servers change on their own because they share only URLs and representations. Stateless requests let you add servers freely, and cacheable responses cut load.
