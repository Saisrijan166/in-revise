## Why it exists

The Web needed to scale to millions of independent clients and servers. Fielding described the constraints that make that work, so APIs can copy them on purpose.

## How it works

| Constraint | Rule | What you gain |
|---|---|---|
| Client-server | UI and data storage are separate | Each side evolves on its own |
| Stateless | Each request carries everything needed | Any server can answer; see [statelessness](card:statelessness) |
| Cacheable | Responses say if they may be reused | Fewer calls; see [HTTP caching](card:http-caching) |
| Uniform interface | Same generic interface for every resource | Simple, visible interactions |
| Layered system | Each part sees only the next layer | Proxies, gateways and load balancers fit in |
| Code on demand (optional) | Server may send code to run on the client | Extensible clients |

- The uniform interface has four parts (see the tree); the last, hypermedia, is [HATEOAS](card:richardson-maturity-hateoas).
- REST is about the constraints. HTTP is the usual way to apply them; JSON is just a common format.

## Interview Qs

### What are the constraints of REST?

Client-server, stateless, cacheable, uniform interface, layered system, and the optional code on demand. The uniform interface means resources with identifiers, representations, self-descriptive messages and hypermedia links.

### REST vs REST API vs HTTP?

REST is the architectural style. A REST API is an API built to follow it. HTTP is the protocol most REST APIs use to carry requests and responses.

### Which REST constraint is optional?

Code on demand: the server may send scripts for the client to run. Fielding marks it optional because it reduces visibility.
