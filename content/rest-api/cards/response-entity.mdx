## Why it exists

Status and headers are part of the API contract. A controller needs a short way to send 201 with a Location, 204 with no body, or 404.

## How it works

| Builder | Sends | Use |
| --- | --- | --- |
| `ResponseEntity.ok(body)` | 200 | read or update |
| `created(uri).body(body)` | 201 + `Location` | new payment PAY101 |
| `accepted().body(body)` | 202 | work finishes later: [long-running operations](card:long-running-operations) |
| `noContent().build()` | 204 | nothing to return |
| `status(HttpStatus.CONFLICT).body(body)` | any code | everything else |

- `.header(name, value)` and `.eTag(tag)` add headers; ETag use: [HTTP caching](card:http-caching).
- Which code fits which case: [status codes](card:status-codes).

## Example

```java
@PostMapping
ResponseEntity<PaymentResponse> create(@Valid @RequestBody PaymentRequest req) {
    PaymentResponse p = service.create(req);                        // PAY101, PENDING
    URI location = ServletUriComponentsBuilder.fromCurrentRequest()
            .path("/{id}").buildAndExpand(p.paymentId()).toUri();   // /api/payments/PAY101
    return ResponseEntity.created(location).body(p);                // 201 + Location
}
```

## Interview Qs

### When do you return ResponseEntity instead of the object?

When the status or headers depend on the outcome: 201 with Location after a create, 202 for work still running, or an ETag header. For a plain 200, return the object.

### @ResponseStatus or ResponseEntity?

@ResponseStatus fixes one code at compile time and does not override a status set by ResponseEntity. Avoid its reason attribute in APIs: it calls sendError, and the container may write an HTML error page.
