## What it is

`ResponseEntity` is a return type that holds the whole HTTP response: status code, headers and body. A controller method that returns a plain object always answers 200 OK. Returning a `ResponseEntity` lets the method choose the status and headers while it runs, for example 201 Created with a `Location` header after it creates a payment.

## Why it exists

The status code and headers are part of the API contract, as [status codes](card:status-codes) showed. After POST `/api/payments` creates PAY101, the client should get 201 and the new payment's URL in `Location`, not 200. A cancel with nothing to return should get 204. A plain return value cannot say any of this; `ResponseEntity` can, without touching the low-level servlet response.

## How it works

| You write | Client gets | Payment API use |
| --- | --- | --- |
| `return p;` | 200 | read PAY101 |
| `ResponseEntity.created(uri).body(p)` | 201 + `Location` | create a payment |
| `ResponseEntity.accepted().body(p)` | 202 | work finishes later: [long-running operations](card:long-running-operations) |
| `ResponseEntity.noContent().build()` | 204, no body | cancel, nothing to return |
| `ResponseEntity.status(HttpStatus.CONFLICT).body(p)` | any code | everything else |

1. The method does its work and gets a result, here the new payment PAY101.
2. It starts a response with a static builder method; `created(location)` sets status 201 and the `Location` header.
3. It adds more headers if needed, with `.header(name, value)` or `.eTag(tag)` for [caching](card:http-caching).
4. It finishes with `.body(p)`, or `.build()` when there is no body.
5. Spring writes the status and headers, then converts the body to JSON, exactly as for a plain return value.

## Example

The create endpoint answers 201 and points to the new payment.

```java
@PostMapping
ResponseEntity<PaymentResponse> create(@RequestHeader("Idempotency-Key") String key,
                                       @Valid @RequestBody PaymentRequest req) {
    PaymentResponse p = service.create(key, req);                    // PAY101, PENDING
    URI location = ServletUriComponentsBuilder.fromCurrentRequest()  // .../api/payments
            .path("/{id}").buildAndExpand(p.paymentId()).toUri();    // .../api/payments/PAY101
    return ResponseEntity.created(location).body(p);                 // 201 + Location
}
```

```bash
curl -s -w '\n%{http_code} %header{location}\n' -X POST http://localhost:8080/api/payments \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: order-789-payment' \
  -d '{"amount": 500, "currency": "INR", "method": "UPI"}'
```

```text output
{"paymentId":"PAY101","status":"PENDING","amount":500}
201 http://localhost:8080/api/payments/PAY101
```

What to notice:

- `fromCurrentRequest()` starts from the URL the client called, so the `Location` has the right host, port and path without hardcoding them.
- The body is the same JSON as before; only the status line and the `Location` header changed.
- If the method returned `p` directly, the client would get 200 and no `Location`, although a payment was created.

## Rules and defaults

- **Plain return:** status 200, and the object is converted to the body.
- **`@ResponseStatus` on a method:** sets one fixed status. It does not override a status set by `ResponseEntity`.
- **`@ResponseStatus` with `reason`:** Spring calls `sendError` and ignores the method's return value. A plain servlet container then writes an HTML error page; in Spring Boot, a JSON client gets the generic `/error` JSON (timestamp, status, error, path). Either way your body is lost, so do not use `reason` in a REST API.
- **Builders:** `ok`, `created`, `accepted`, `noContent`, `notFound`, `badRequest` and `status(…)` start a response; `.header` and `.eTag` add headers.

## Common mistakes

- **"Return ResponseEntity from every method, just in case."** It adds noise to simple reads. Return the object when 200 is right, and use `ResponseEntity` only when the status or headers depend on the outcome.

## Interview Qs

### When do you return ResponseEntity instead of the object?

When the status or headers depend on the outcome: 201 with `Location` after a create, 202 for work still running, 204 for nothing to return, or an `ETag` header. For a plain 200, I return the object, which keeps the method short.

### @ResponseStatus or ResponseEntity?

`@ResponseStatus` fixes one code at compile time, which suits a method that always answers the same, such as 201 for a create with no `Location`. `ResponseEntity` decides at runtime and also sets headers. The annotation does not override a `ResponseEntity` status, and its `reason` attribute replaces your body with an error page, so avoid `reason` in APIs.

### How do you return 201 with a Location header?

Build the URI of the new resource, usually with `ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(id).toUri()`, and return `ResponseEntity.created(uri).body(dto)`. The client can follow `Location` to read the payment.
