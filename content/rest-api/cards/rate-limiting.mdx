## What it is

Rate limiting is the API counting requests per caller and refusing the ones over a set limit, for example 100 payment calls per minute per API key. The caller is identified by its user ID, [API key](card:authentication-methods) or IP address. A refused call gets the status 429 Too Many Requests (RFC 6585), often with a `Retry-After` header that says how many seconds to wait.

## Why it exists

Without a limit, one buggy retry loop or one attacker can send thousands of requests a second. The database slows down for every other merchant, a password-guessing script gets unlimited tries, and paid downstream calls, such as SMS messages, run up a bill. A limit per caller stops one client's traffic from hurting everyone else.

## How it works

| Algorithm | How it counts | Watch out |
|---|---|---|
| Fixed window | One counter per clock minute | Up to twice the limit in a short span around the window edge |
| Sliding window | Blends the last and current window counts | An approximation, not an exact count |
| Token bucket | Tokens refill steadily; each call takes one | Allows short bursts by design |
| Leaky bucket | Calls drain at a fixed rate | Bursts wait in a queue or are dropped |

1. A request arrives, usually at the API gateway, the single entry point in front of the services.
2. The limiter finds the caller's key, such as the API key, and its counter in a shared store such as Redis, so every server sees the same count.
3. It updates the counter in one atomic step, so two servers cannot both read 99 and let call 101 through, and compares it with the limit.
4. Under the limit, the request goes on to the service. Over the limit, the limiter answers 429 at once, and the service never sees the call.
5. A well-behaved client waits for `Retry-After` and retries with backoff, which you will see in [retries and timeouts](card:retries-and-timeouts).

## Example

A token bucket with room for 3 tokens that refills 1 token per second. Five calls arrive at the same moment.

```java
class TokenBucket {
    final int capacity; final double perSecond;
    double tokens; long last = System.nanoTime();
    TokenBucket(int capacity, double perSecond) { this.capacity = capacity; this.perSecond = perSecond; tokens = capacity; }
    synchronized boolean tryTake() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) / 1e9 * perSecond); // refill for time passed
        last = now;
        if (tokens < 1) return false;                  // bucket empty: the API answers 429
        tokens--;                                      // spend one token on this call
        return true;
    }
}
var bucket = new TokenBucket(3, 1);                    // burst of 3, then 1 per second
for (int i = 1; i <= 5; i++) System.out.println("call " + i + ": " + (bucket.tryTake() ? 200 : 429));
```

```text output
call 1: 200
call 2: 200
call 3: 200
call 4: 429
call 5: 429
```

What to notice:

- The bucket starts full, so the first three calls pass at once: the capacity is the allowed burst.
- Calls 4 and 5 arrive microseconds later, when far less than one token has refilled, so they get 429. A client that waits one second gets one more call.
- Remove the refill line and the bucket never fills again, so the caller stays blocked for ever.
- This bucket lives in one JVM. With ten servers, each would have its own, which is why real limiters keep the state in Redis or at the gateway.

## Rules and defaults

- **Status:** 429 Too Many Requests (RFC 6585), which MAY include `Retry-After`. `Retry-After` holds either seconds or a date (RFC 9110).
- **Who to count:** RFC 6585 leaves the choice open. Per user or API key is fairer than per IP, because many users behind one office network share an IP.
- **Quota headers:** the `RateLimit` and `RateLimit-Policy` fields are an IETF draft, not an RFC. `X-RateLimit-*` headers are vendor conventions, so document whichever you send.
- **Managed gateways:** Amazon API Gateway throttles with a token bucket and returns 429 when a limit is hit.

## Not to be confused with

429 says this caller sent too many requests and should slow down; the server is fine. 503 Service Unavailable says the server cannot serve anyone right now, for example during overload or maintenance. Rule: 429 = you, slow down; 503 = us, we are down.

## Interview Qs

### How do you rate limit across ten app servers?

Keep the counter in one shared store, such as Redis with an atomic increment and an expiry, or enforce the limit at the API gateway. Separate counters per server let a caller get up to ten times the limit, because the load balancer spreads its calls.

### Which algorithm would you pick?

Token bucket for most APIs: it allows a short burst, then holds a steady average rate, and Amazon API Gateway uses it. Cloudflare chose an approximate sliding window because it needs only a get and an increment on a shared counter.

### Throttling vs rate limiting?

Mostly the same idea, and the words are often used interchangeably. Amazon API Gateway, for example, calls its limits throttling and answers with 429 when they are hit.
