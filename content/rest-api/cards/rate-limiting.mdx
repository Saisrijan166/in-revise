## Why it exists

Without limits, one script can flood the API, guess passwords, or run up costs, and every other customer pays for it. OWASP lists this as [API4](card:owasp-api-security).

## How it works

| Algorithm | How it counts | Watch out |
|---|---|---|
| Fixed window | Counter per clock minute | Spikes around the window edge |
| Sliding window | Blends last and current window counts | An approximation, not exact |
| Token bucket | Tokens refill steadily; each call takes one | Allows short bursts by design |
| Leaky bucket | Calls drain at a fixed rate | Bursts wait or are dropped |

- Token bucket is the usual answer: Amazon API Gateway throttles with it.
- What the client does after a 429 belongs to [retries and timeouts](card:retries-and-timeouts).

## Example

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/problem+json

{"title": "Too many payment attempts", "status": 429}
```

## Interview Qs

### How do you rate limit across ten app servers?

Keep the counter in one shared store, such as Redis with an atomic increment and expiry, or enforce it at the API gateway. Separate counters per server let a caller get up to ten times the limit.

### Throttling vs rate limiting?

Mostly the same idea and often used interchangeably: Amazon API Gateway calls its limits throttling and returns 429.

### Which algorithm would you pick?

Token bucket: it allows a short burst, then holds a steady average rate. Cloudflare chose a sliding window because it needs only get and increment on a shared counter.
