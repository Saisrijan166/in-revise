## Why it exists

A list of every payment grows without limit. Pages keep each response small, and filters let a client fetch only the rows it needs.

## How it works

<Compare id="offset-vs-cursor-pagination" />

- One query parameter per filter field: `?status=SUCCESS`. Sort with `?sort=createdAt,desc`, the [Spring Data](card:spring-data-pageable) style.
- `?fields=id,status` trims big responses; still check the caller may see each field.
- Allow-list the field names clients may filter, sort or select by.

## Example

```text
GET /api/v1/payments?status=SUCCESS&sort=createdAt,desc&size=20

200 OK
Content-Type: application/json

{
  "items": [ { "paymentId": "PAY101", "amount": 500, "status": "SUCCESS" } ],
  "nextLink": "https://api.example.com/api/v1/payments?status=SUCCESS&size=20&cursor=8f3a2c"
}
```

## Interview Qs

### Offset or cursor pagination: which would you choose?

Offset for small, stable lists where users jump to page N, like an admin table. Cursor for large or fast-changing data, like a payment feed: each page costs the same, and new rows cause no skips or duplicates.

### How does the client find the next page?

The server returns it: a `nextLink` field in the body, or a [Link header](card:link-header-next) with `rel="next"`. On the last page there is no link, so the client never builds paging URLs itself.

### A client sends size=100000. What do you do?

Enforce the documented maximum: return at most the cap, or reject with 400. An unbounded page size lets one call overload the database.
