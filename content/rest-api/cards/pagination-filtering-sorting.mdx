## What it is

Pagination means the API returns a long list in pieces called pages, each with a fixed maximum number of items, instead of all items at once. Filtering and sorting are query parameters that let the client ask only for the rows it needs, in the order it wants: `?status=SUCCESS&sort=createdAt,desc`. All three follow the [URL rules](card:url-design-rules): the path names the collection, and the query string shapes it.

## Why it exists

`GET /payments` without pages works on day one, with 50 rows. A year later there are millions: one call makes the database read them all, the server builds a huge JSON body and may run out of memory, and the client waits seconds for rows it never shows. With pages, each call returns, say, 20 rows and a link to the next 20, so every response stays small however big the table grows.

## How it works

<Compare id="offset-vs-cursor-pagination" />

1. The client asks for the first page: `GET /payments?status=SUCCESS&sort=createdAt,desc&size=20`.
2. The server checks `size` against its maximum, and checks that `status` and `createdAt` are fields clients may filter and sort by.
3. It runs the query and returns up to 20 items, plus the link to the next page. With a cursor, that link carries an opaque token that marks where this page ended.
4. The client follows the link exactly as given; it never builds paging URLs itself.
5. The last page has no next link, so the client stops.

So the key is: the server decides where each page ends, and the client only follows links.

## Example

The merchant dashboard asks for successful payments, newest first, 20 at a time.

```text
GET /api/v1/payments?status=SUCCESS&sort=createdAt,desc&size=20

200 OK
Content-Type: application/json

{
  "items": [ { "paymentId": "PAY101", "amount": 500, "status": "SUCCESS" } ],
  "nextLink": "https://api.example.com/api/v1/payments?status=SUCCESS&size=20&cursor=8f3a2c"
}
```

What to notice:

- `nextLink` repeats the filter and size, and adds `cursor=8f3a2c`. The client treats the cursor as opaque and does not decode it.
- The list sits inside an object (`items`), so paging fields like `nextLink` have a place next to it. Microsoft's guidelines use the same shape, with `value` and `nextLink`.
- On the last page `nextLink` is left out, not sent as null, as Microsoft's guidelines require.
- A [Link header](card:link-header-next) with `rel="next"` is the standard alternative to a `nextLink` field in the body.

## Rules and defaults

- **Page size:** document a default and a maximum. A request above the maximum gets the maximum, or a 400.
- **Spring Data (Spring Boot 4.1):** `page` starts at 0, `size` defaults to 20, and `spring.data.web.pageable.max-page-size` is 2000. A larger `size` is cut to 2000 without an error.
- **Stable order:** offset pages need an `ORDER BY` that gives a unique order, such as `created_at, id`. Without it, PostgreSQL may return rows in a different order on each call, so pages overlap.
- **Allow-list:** accept only documented field names in filter, sort and `?fields=` parameters; reject others with 400. Spring Data passes sort names through without checking them against your fields, so this check is your code's job. Selecting fields with `?fields=id,status` still needs a check that the caller may see each field.

## Not to be confused with

A cursor is the opaque token the client sends back to get the next page. Keyset pagination is one way the server can build it: the token holds the last row's sort key, and the query asks `WHERE id < last id`, so the index skips seen rows. Rule: cursor = what the client sees; keyset = how the database finds the page.

## Interview Qs

### Offset or cursor pagination: which would you choose?

Offset for small, stable lists where users jump to page N, like an admin table. Cursor for large or fast-changing data, like a payment feed: every page costs the same, because the database does not read skipped rows, and new rows cause no skips or duplicates.

### How does the client find the next page?

The server returns it: a `nextLink` field in the body, or a Link header with `rel="next"`. On the last page there is no link, so the client stops. The client never builds paging URLs itself, so the server can change its paging method later.

### A client sends size=100000. What do you do?

Enforce the documented maximum: return at most the cap, or reject with 400. Without a cap, one call can make the database read a huge result and the server build a huge response, which slows everyone else. Spring Data caps it at 2000 by default.
