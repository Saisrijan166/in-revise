## Why it exists

Clients, proxies and crawlers must know which requests are harmless to send again. The method tells them before they read the body.

## How it works

| Method | ₹500 payment use | Safe | Idempotent | Cacheable |
|---|---|---|---|---|
| GET | read PAY101 | yes | yes | yes |
| HEAD | headers of PAY101, no body | yes | yes | yes |
| OPTIONS | which methods the URL allows | yes | yes | no |
| POST | create a payment | no | no | rarely |
| PUT | replace the whole note of PAY101 | no | yes | no |
| PATCH | change a few fields | no | no | rarely |
| DELETE | remove a saved card | no | yes | no |

- Idempotent requests may be retried automatically after a dropped connection; POST needs an [Idempotency-Key](card:idempotency-keys).
- OPTIONS is also the browser's [CORS preflight](card:cors).
- "Rarely": POST and PATCH replies are cacheable only with explicit freshness and Content-Location; most caches skip them.

## Example

```text
PATCH /api/payments/PAY101
Content-Type: application/merge-patch+json

{"note": "Rent for October", "tag": null}
```

The note is set and `tag` is removed; other fields stay as they are.

## Interview Qs

### What is the difference between safe and idempotent?

Safe: the client asks for no state change (GET). Idempotent: many identical requests have the same effect as one (PUT, DELETE). Every safe method is idempotent; DELETE is idempotent but not safe.

### Is PATCH idempotent?

Not by definition. Setting `note` to a value is idempotent; a JSON Patch "add" to an array is not. To stop a retried PATCH applying twice, send [If-Match](card:conditional-requests) with the ETag.
