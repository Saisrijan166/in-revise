## What it is

An HTTP method is the verb in the [request line](card:http-request-response) that says what the client wants done to the resource: `GET` reads it, `POST` creates one, `PUT` replaces it, `PATCH` changes part of it and `DELETE` removes it. Two properties of a method matter most. A method is safe if the client asks for no change on the server. It is idempotent if sending the same request many times has the same effect on the server as sending it once.

## Why it exists

Networks fail. If the connection drops after a request was sent, the client cannot tell whether the server did the work. The method answers the key question: is it harmless to send again? A repeated `GET` only reads again, and a repeated `DELETE` finds nothing more to delete. A repeated `POST` can create a second ₹500 payment. Browsers, proxies and HTTP libraries read the method to decide what they may retry, prefetch or cache.

## How it works

| Method | Payment use | Safe | Idempotent | Response cacheable |
|---|---|---|---|---|
| GET | read PAY101 | yes | yes | yes |
| HEAD | headers of PAY101, no body | yes | yes | yes |
| OPTIONS | which methods a URL allows | yes | yes | no |
| POST | create a payment | no | no | rarely |
| PUT | replace the whole note of PAY101 | no | yes | no |
| PATCH | change a few fields | no | no | rarely |
| DELETE | remove a saved card | no | yes | no |

What happens when a reply is lost:

1. The client sends a request, and the connection drops before the response arrives.
2. The client cannot tell whether the server did the work.
3. If the method is idempotent, the client sends it again: one run or two leave the same state.
4. If it is `POST`, RFC 9110 says a client should not retry it automatically, unless it knows this request is idempotent or was never applied.
5. So a payment `POST` carries an `Idempotency-Key` header that lets the server spot the repeat, as you will see in [idempotency keys](card:idempotency-keys).

## Example

The methods on the payment API, each sent twice:

```text
GET    /api/payments/PAY101        twice: the same payment read twice
POST   /api/payments               twice: PAY101 and PAY102, ₹1000 charged
PUT    /api/payments/PAY101/note   twice: the note is "Rent", as after once
PATCH  /api/payments/PAY101        twice: {"tag": "rent"} set again, no change
DELETE /api/saved-cards/CARD7      twice: 204, then 404; the card is gone
```

What to notice:

- `PUT` sends the whole new note, so the second run writes the same value again. That is why PUT is idempotent.
- `DELETE` returns different responses, 204 No Content and then 404 Not Found, but the state after both is the same. Idempotent is about the effect, not the reply.
- This `PATCH` only sets a field, so a repeat is harmless. A PATCH that adds an item to a list would add it twice, which is why PATCH is not idempotent by definition.

## Rules and defaults

- **Safe methods (RFC 9110):** `GET`, `HEAD`, `OPTIONS` and `TRACE`. The server may still write access logs; safe means the client did not ask for a change.
- **Idempotent methods:** the safe ones plus `PUT` and `DELETE`.
- **Automatic retries:** a client should not retry a non-idempotent request by itself, and a proxy must not.
- **Cacheable responses:** `GET` and `HEAD` in practice. `POST` and `PATCH` only in rare cases that need extra headers. `PUT`, `DELETE` and `OPTIONS` responses never.
- **PATCH body:** its media type says how to apply the change: JSON Merge Patch (`application/merge-patch+json`) or JSON Patch (`application/json-patch+json`).
- **OPTIONS:** also the browser's preflight check, which you will see in [CORS](card:cors).

## Not to be confused with

`PUT` sends the complete new resource to its own URL, so fields left out are gone. `PATCH` sends only the changes, so other fields stay. `POST` sends input to a collection or action, and the server decides what to create. Rule: PUT replaces, PATCH edits, POST creates or runs an action.

## Common mistakes

- **"PUT or PATCH validates input, checks permissions and runs in a transaction."** A method only states the intent. Validation, authorisation and transactions are the server's job, for every method.
- **"A GET that changes a little data is fine."** Crawlers, prefetchers and link checkers call GET freely. RFC 9110 makes the resource owner responsible for keeping actions off safe methods.

## Interview Qs

### What is the difference between safe and idempotent?

Safe: the client asks for no state change, like GET. Idempotent: many identical requests have the same effect as one, like PUT and DELETE. Every safe method is idempotent, but DELETE is idempotent without being safe, because it does change the state once.

### Is PATCH idempotent?

Not by definition. A PATCH that sets `note` to a value is idempotent; a JSON Patch `add` to an array is not, because each repeat adds again. To stop a retried PATCH from applying on top of a newer change, send [If-Match](card:conditional-requests) with the version you read.

### Why is POST not idempotent, and how do you make a payment POST safe to retry?

Each POST asks the server to create something new, so two POSTs create two payments. The client sends a unique `Idempotency-Key` header; the server stores the first result under that key and returns it for any repeat instead of charging twice. [Idempotency keys](card:idempotency-keys) covers the details.
