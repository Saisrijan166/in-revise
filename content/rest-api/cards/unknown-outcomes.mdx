## What it is

An unknown outcome is a call whose result you cannot know: you sent the request, but a timeout, a reset connection or a 500 means no clear answer came back. The other side may have done the work, failed, or never received it. For a payment, unknown is a third state next to success and failure. It is resolved by asking, never by guessing. It is why [timeouts and retries](card:retries-and-timeouts) need care.

## Why it exists

Your service asks the gateway to charge ₹500, and the request timeout fires. If you mark the payment FAILED and the customer pays again, they may be charged twice, because the first charge really went through. If you assume success instead, you may deliver goods for money you never received. Treating the timeout as UNKNOWN, and resolving it with the gateway, keeps both the money and your records correct.

## How it works

1. Before calling the gateway, you save PAY101 as PENDING, with a unique constraint on the order id, so the order can never get a second payment row.
2. The call times out. You mark PAY101 UNKNOWN, not FAILED, and do not start a new charge.
3. You ask the gateway for the payment by your own reference, or wait for its signed [webhook](card:webhooks), which you will see next.
4. If it is still unclear, you resend the call with the same idempotency key and body; the gateway either does the work once or returns its saved result.
5. A reconciliation job matches your rows against the provider's settlement report, its list of what it really charged and paid out, and fixes anything still open.

## Example

The payment service turns a timeout into UNKNOWN instead of FAILED.

```java
void pay(Payment payment) throws IOException {
    String key = "order-" + payment.orderId() + "-payment";    // same key on every attempt
    try {
        GatewayResult r = gateway.charge(payment.id(), payment.amount(), key);
        repo.updateStatus(payment.id(), r.succeeded() ? "SUCCESS" : "FAILED");
    } catch (HttpTimeoutException e) {
        repo.updateStatus(payment.id(), "UNKNOWN");   // not FAILED: the charge may have gone through
        resolver.checkLater(payment.id());            // ask the gateway, or wait for its webhook
    }
}
```

What to notice:

- FAILED is written only when the gateway clearly says declined. A timeout writes UNKNOWN and hands the payment to a resolver.
- The key comes from the order (`order-789-payment`), so a later retry by the resolver sends exactly the same key.
- `HttpTimeoutException` also covers `HttpConnectTimeoutException`. That one means no connection was opened, so the gateway never got the request; treating it as UNKNOWN too is still safe.
- A reset connection (`IOException`) or a 500 needs the same UNKNOWN path; this short version catches only timeouts.

## Rules and defaults

- **Stripe API v1:** after a network error, retry with the same key and parameters within 24 hours. If the outcome is still unknown after that, retry with neither the old key nor a new one: reconcile instead.
- **A 500 is unknown too:** Stripe treats a 500 as indeterminate, and caches it for that key, so a same-key retry returns the same 500. Resolve it by fetching the object and using webhook events.
- **Match by your reference:** Stripe advises storing your own id in the object's metadata, so a webhook or a report row can be matched to your payment.
- **Correctness lives in the database:** a unique constraint and a transaction stop duplicate payment rows. A distributed lock with an expiry only saves duplicate work.
- **Events:** to announce "payment succeeded" reliably, save the event in an outbox table in the same transaction as the status. A separate relay process publishes it, maybe twice, so consumers dedupe.

## Interview Qs

### The gateway timed out after charging ₹500. What do you do?

Mark the payment UNKNOWN, not FAILED. Ask the gateway for it by our reference, or wait for its signed webhook. Retry only with the same idempotency key and body. Anything still open goes to a reconciliation job against the provider's settlement report, so the customer is never charged twice.

### Is a Redis lock enough to stop double charges?

No. A lock with an expiry can run out during a long pause, such as a garbage-collection pause in the JVM, while the holder keeps working, so two workers act. Put a unique constraint on the order id in the database and work inside a transaction; the lock can only reduce duplicate work.

### Why a transactional outbox?

Saving the payment status and publishing its event are two separate writes, and one can fail after the other succeeds. The outbox saves the event in the same database transaction as the status. A relay then publishes it, possibly twice, so consumers must dedupe by event id.
