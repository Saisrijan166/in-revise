## Why it exists

The gateway may charge ₹500 and the reply may still be lost. Charging again bills the customer twice; marking it failed loses real money.

## How it works

<Steps label="Gateway charged ₹500, reply lost">
  <Step title="Save first">Insert PAY101 as PENDING, with a unique order id, before calling the gateway.</Step>
  <Step title="Timeout">Mark PAY101 UNKNOWN. Do not charge again with a new key.</Step>
  <Step title="Ask">Query the gateway by our reference, or wait for its signed webhook.</Step>
  <Step title="Retry safely">If still unclear, resend with the same idempotency key and body.</Step>
  <Step title="Reconcile">A job matches our rows to the settlement report and fixes leftovers.</Step>
</Steps>

- Store the "payment succeeded" event in a [transactional outbox](card:transactional-outbox), so the row and event never disagree.
- Stripe API v1: retry with the same key within 24 hours; after that, reconcile, never resend.
- Correctness lives in the database (transaction, unique constraint); a lock with an expiry only saves duplicate work.

## Interview Qs

### The gateway timed out after charging ₹500. What do you do?

Mark the payment UNKNOWN, not FAILED. Query the gateway by our reference or wait for its webhook. Retry only with the same idempotency key. Anything still open goes to reconciliation against the settlement report.

### Is a Redis lock enough to stop double charges?

No. A lock with an expiry can run out during a GC pause while the holder keeps working, so two workers act. Use a database transaction and a unique constraint on the order id.

### Why a transactional outbox?

Saving the payment and publishing its event are two writes. The outbox saves the event in the same database transaction; a relay publishes it, maybe twice, so consumers must dedupe.
