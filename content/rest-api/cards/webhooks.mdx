## Why it exists

The gateway learns the final status later, for example when a bank confirms a UPI payment. A webhook pushes that news to you, so you do not poll.

## How it works

<Steps label="Receive one webhook">
  <Step title="Verify">HMAC-SHA256 over the signed parts (ID, timestamp, raw body) with the secret; compare in constant time.</Step>
  <Step title="Check time">Reject a timestamp older than the tolerance, to stop replays.</Step>
  <Step title="Acknowledge">Save the event and return 2xx; heavy work goes to a queue.</Step>
  <Step title="Dedupe">Skip an event ID already processed (unique constraint on it).</Step>
  <Step title="Apply">Check current state; ignore an older event that arrives late.</Step>
</Steps>

- Verify the raw bytes: parsing and re-serialising JSON changes them, and the check fails.
- [Standard Webhooks](card:standard-webhooks) fixes the header names and signing format across providers.
- Clients polling a status URL instead: [long-running operations](card:long-running-operations).

## Example

```text
POST /webhooks/payments
webhook-id: msg_7Rq2LbX9
webhook-timestamp: 1792467000
webhook-signature: v1,4Ix0W12M+WijjIAw4p9AC6ZvsclvDEBYmIIbF7sRfWs=
{"type": "payment.succeeded", "paymentId": "PAY101"}

-> 204 No Content    (saved and queued; a worker marks PAY101 SUCCESS)
```

## Interview Qs

### How do you secure a webhook endpoint?

HTTPS only. Verify the HMAC signature over the raw body with the shared secret, reject old timestamps against replays, and rotate the secret. Stripe also advises accepting only its listed IP addresses.

### The same webhook arrives twice. What happens?

Expect it: delivery is at-least-once. Store each processed event ID under a unique constraint and skip repeats; make the update idempotent too, like setting status to SUCCESS.

### Why return 2xx before processing?

Slow handlers time out, and the provider then retries, sending duplicates. Save, acknowledge, and process from a queue at your own pace.
