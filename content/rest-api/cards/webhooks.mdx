## What it is

A webhook is an HTTP request that another system sends to your API when something happens there. You register a URL, such as `https://shop.example/webhooks/payments`, with the payment gateway, and when a payment settles, the gateway POSTs a small JSON event to it. The roles are reversed: the gateway is the client and your API is the server. It is how you resolve many [unknown outcomes](card:unknown-outcomes).

## Why it exists

A UPI payment may be confirmed by the bank seconds or minutes after your POST returned PENDING. Without webhooks you poll the gateway for every pending payment, which wastes calls and still learns the news late. A webhook tells you as soon as it happens. But the URL is public, so anyone could post a fake "payment succeeded", and the gateway retries on errors, so the same event can arrive twice. The receiver must handle both.

## How it works

1. The gateway signs the event: it computes an HMAC-SHA256 over the event id, the timestamp and the raw body with a secret only you and it know, and sends the result in a header.
2. Your endpoint computes the same HMAC over the raw bytes it received and compares the two in constant time. A mismatch gets 400.
3. It rejects a timestamp older than its tolerance, so a copied old request cannot be replayed.
4. It saves the event with its id under a unique constraint and returns 2xx at once. An id already saved is skipped.
5. A worker processes the event from a queue. It checks the payment's current state first, so a late, older event cannot undo a newer one.

## Example

A Standard Webhooks delivery to the payment API, and the Java check behind step 2 and 3.

```text
POST /webhooks/payments
webhook-id: msg_7Rq2LbX9
webhook-timestamp: 1792467000
webhook-signature: v1,Vm7/jdpQ7wr6+WH1QCt5m2dtpcYawn1p0cppNiwODrE=
{"type":"payment.succeeded","paymentId":"PAY101"}
```

```java
boolean verify(String secret, String id, String timestamp, String rawBody, String header)
        throws Exception {
    long age = Math.abs(Instant.now().getEpochSecond() - Long.parseLong(timestamp));
    if (age > 300) return false;                                 // older than 5 minutes
    Mac mac = Mac.getInstance("HmacSHA256");
    byte[] key = Base64.getDecoder().decode(secret.substring("whsec_".length()));
    mac.init(new SecretKeySpec(key, "HmacSHA256"));
    byte[] expected = mac.doFinal((id + "." + timestamp + "." + rawBody).getBytes(UTF_8));
    for (String sig : header.split(" ")) {                       // several during secret rotation
        if (sig.startsWith("v1,") && MessageDigest.isEqual(expected,
                Base64.getDecoder().decode(sig.substring(3)))) return true;  // constant time
    }
    return false;
}
```

What to notice:

- The signed text is `id.timestamp.body`, joined with full stops. The signature in the header was computed this way from a test secret, and the same check in Python gave the same value.
- In a test run, a fresh delivery returned true, the same delivery with `PAY101` changed to `PAY999` returned false, and a correct signature after a wrong one returned true.
- `MessageDigest.isEqual` takes the same time however many bytes match, so an attacker cannot guess the signature byte by byte from response times.
- Change the timestamp and the signature no longer matches, so an attacker cannot make an old request look new.

## Rules and defaults

- **Stripe retries:** in live mode, Stripe retries a failed delivery for up to three days with exponential backoff; in a sandbox, three times over a few hours.
- **Redirects fail:** Stripe treats a 3xx answer as a failed delivery, so register the final URL.
- **HTTPS only:** Stripe's live endpoints must be public HTTPS URLs using TLS 1.2 or 1.3. Stripe also publishes its webhook IP addresses for an allow-list.
- **Order:** Stripe does not guarantee event order, and its event timestamps are in seconds. Track event ids, not timestamps, to find duplicates.
- **Secret rotation:** during a rotation the sender signs with both secrets, so the header can hold two signatures (Stripe keeps the old secret for up to 24 hours).

## Not to be confused with

HTTPS proves to the gateway that it is talking to your real server, and hides the event from anyone on the network. It does not prove to you who sent the request, because anyone can call a public HTTPS URL. The signature proves that the sender knows the shared secret. Rule: HTTPS protects the connection; the signature proves the sender.

## Interview Qs

### How do you secure a webhook endpoint?

Accept HTTPS only. Verify the HMAC signature over the raw body with the shared secret, compare in constant time, and reject old timestamps to stop replays. Rotate the secret from time to time. Stripe also advises accepting only its published IP addresses.

### The same webhook arrives twice. What happens?

Expect it: delivery is at-least-once. Store each processed event id under a unique constraint and skip repeats. Make the update itself idempotent too, such as setting the status to SUCCESS rather than adding money to a balance.

### Why return 2xx before processing?

A slow handler times out on the sender's side, and the sender then retries, sending duplicates. Save the event, return 2xx, and process it from a queue at your own pace. A queue also absorbs spikes, such as many renewals at the start of a month.
