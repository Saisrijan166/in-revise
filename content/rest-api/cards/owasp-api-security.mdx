## What it is

OWASP is a non-profit foundation that publishes free security guidance. Its API Security Top 10, last updated in 2023, lists the ten weaknesses that attackers exploit most often in APIs. Most of them are missing authorisation checks, the "what may this caller do?" step from [authentication methods](card:authentication-methods): on an object, on one field of it, or on a whole function.

## Why it exists

APIs hand out object IDs, such as PAY101, and return raw data fields, so an attacker needs no clever exploit: they change an ID, add a field to the body, or call an admin URL directly. The app may hide those buttons, but the API can be called without the app. The list gives teams one shared checklist of these API-specific failures to design against and test for.

## How it works

| Risk (2023) | In the payment API |
|---|---|
| API1 BOLA (object level authorisation) | Customer A reads PAY101 of customer B |
| API2 Broken authentication | Weak [token checks](card:jwt), no limit on login attempts |
| API3 BOPLA (object property level) | Client sets `status: SUCCESS`, or sees card data |
| API4 Unrestricted resource consumption | No [rate limits](card:rate-limiting) or size limits |
| API5 BFLA (function level authorisation) | A customer calls an admin refund endpoint |
| API6 Sensitive business flows | Bots abuse a cashback offer |
| API7 SSRF (server-side request forgery) | The API fetches a webhook URL the caller chose |
| API8 Security misconfiguration | Stack traces in [error bodies](card:error-responses) |
| API9 Improper inventory management | A forgotten old [version](card:api-versioning) is still live |
| API10 Unsafe consumption of APIs | Trusting the payment provider's reply unchecked |

1. Authenticate the caller: validate the token fully and limit login attempts (API2).
2. Check the function: may this role call this endpoint at all? A customer must not reach an admin refund URL (API5).
3. Check the object: load PAY101 only if it belongs to this caller (API1).
4. Check the fields: accept and return only the fields this caller may set or see (API3).
5. Limit the cost: rate limits, page sizes and request body sizes (API4).

So the key is: the API itself must make every check, because a caller can skip the app.

## Example

The payment API reads one payment, with the ownership check inside the query.

```java
@GetMapping("/api/payments/{id}")
PaymentResponse get(@PathVariable String id, @AuthenticationPrincipal Jwt jwt) {
    return payments.findByIdAndCustomerId(id, jwt.getSubject())  // ownership in the query
            .map(PaymentResponse::from)                         // DTO: safe fields only
            .orElseThrow(PaymentNotFoundException::new);        // 404: hides others' payments
}
```

What to notice:

- `findByIdAndCustomerId` puts ownership into the database query, so another customer's PAY101 is simply not found. There is no separate check that a later change could forget.
- `jwt.getSubject()` takes the customer ID from the verified token, never from a request parameter the caller could change.
- `PaymentResponse::from` copies only safe fields into a DTO (data transfer object, the class that defines the API's response), so the card number stored with the payment never leaves the API (API3). You will see DTOs in [DTOs vs entities](card:dto-mapping).
- `PaymentNotFoundException` is turned into 404 by an exception handler ([exception handling](card:exception-handling), later), which RFC 9110 allows instead of 403, so the caller cannot even learn that PAY101 exists.

## Rules and defaults

- **Edition:** the 2023 edition replaced the 2019 one. It merged excessive data exposure and mass assignment into API3 BOPLA.
- **Injection:** it was API8 in the 2019 list and has no item of its own in 2023, but the defence still applies: parameterised queries, such as `PreparedStatement` with `?` placeholders or JPA named parameters, never string concatenation.
- **Validate on the server:** checks in the app can be skipped, so the API validates type, length and range itself ([how in Spring](card:request-binding-validation)).
- **Random IDs:** unguessable IDs make BOLA harder, but they are not an authorisation check.

## Not to be confused with

BOLA is about one object: customer A reads customer B's PAY101 through a normal endpoint. BFLA is about a whole function: a customer calls an endpoint meant only for admins, such as an admin refund URL. Rule: BOLA = wrong object; BFLA = wrong function.

## Common mistakes

- **"The admin button is hidden in the app, so customers cannot refund."** Anyone can call the URL directly with a valid token. Check the role on the server for every admin endpoint.

## Interview Qs

### What is BOLA and how do you prevent it?

Broken object level authorisation: the API trusts an object ID from the request and returns or changes that object without checking the caller may use it. Check ownership in every function that uses the ID, ideally in the query itself. Random IDs only make guessing harder.

### How do you prevent SQL injection?

Use parameterised queries (prepared statements), never string concatenation. In Java that means `PreparedStatement` with `?` placeholders or JPA named parameters. Add server-side input validation and a database user with least privilege, so a successful attack can do less.

### What is mass assignment?

The API binds a request body straight onto an internal object, so a client can set fields it should never control, such as `status` or `isAdmin`. In the 2023 list it is part of API3 BOPLA. Bind requests to DTOs that contain only the fields a client may set.
