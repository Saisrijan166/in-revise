## Why it exists

APIs hand out object IDs and raw data, so they fail in their own ways. OWASP keeps a list of the ten most common API risks.

## How it works

| Risk (2023) | In the payment API |
|---|---|
| API1 BOLA | Customer A reads PAY101 of customer B |
| API2 Broken authentication | Weak [token checks](card:jwt), no login limits |
| API3 BOPLA | Client sets `status: SUCCESS`, or sees card data ([DTOs](card:dto-mapping)) |
| API4 Unrestricted resource consumption | No [rate limits](card:rate-limiting) or size limits |
| API5 BFLA | A customer calls an admin refund endpoint |
| API6 Sensitive business flows | Bots abuse cashback offers |
| API7 SSRF | API fetches a caller-given webhook URL |
| API8 Security misconfiguration | Stack traces in [error bodies](card:error-responses) |
| API9 Improper inventory | Forgotten old [versions](card:api-versioning) still live |
| API10 Unsafe consumption of APIs | Trusting the payment provider's reply unchecked |

- Validate input on the server even if the app checks it ([how in Spring](card:request-binding-validation)).
- RFC 9110 allows 404 instead of 403 to hide another customer's payment.

## Example

```java
@GetMapping("/api/payments/{id}")
PaymentResponse get(@PathVariable String id, @AuthenticationPrincipal Jwt jwt) {
    return payments.findByIdAndCustomerId(id, jwt.getSubject())  // ownership in the query
            .map(PaymentResponse::from)                         // DTO: safe fields only
            .orElseThrow(PaymentNotFoundException::new);        // 404: hides others' payments
}
```

## Interview Qs

### What is BOLA and how do you prevent it?

The API trusts an object ID from the request. Check ownership in every function that uses the ID; random IDs only make guessing harder.

### How do you prevent SQL injection?

Use parameterised queries (prepared statements), never string concatenation. In Java that means `PreparedStatement` with `?` placeholders or JPA named parameters. Add server-side input validation and a least-privilege database user.
