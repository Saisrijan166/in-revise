## What it is

Statelessness is the REST rule that the server keeps no memory of a client between requests. Each request carries everything needed to handle it: who is calling, which resource, and any options. Who is calling is usually proven by a token, a string the client got at login and sends in the `Authorization` header. This memory of where a client is in its conversation is called session state; in REST the client keeps it and resends it.

## Why it exists

Suppose a server keeps each user's login in its own memory. Every later request from that user must reach that same server, which is called a sticky session. If the server restarts, the user is logged out. With stateless requests, any server can answer any request. A load balancer, the component that spreads requests across servers, can send each call anywhere, and you can add servers or lose one without users noticing.

## How it works

1. The app logs in once, receives a token and keeps it.
2. Request 1 carries the token in the `Authorization` header. The load balancer sends it to instance A, which checks the token and answers.
3. Request 2 carries the same token and lands on instance B. B has never seen this client and does not need to: everything it needs is in the request.
4. Both instances read and write payments in one shared database, so the data looks the same from either.

So the client keeps the conversation, and the server keeps only the resources.

## Example

The same "next page of payments" request, first stateful and then stateless:

```text
Stateful: the server remembers the page     Stateless: the client says the page
GET /api/payments/next-page                 GET /api/payments?page=2&size=20
Cookie: SESSION=8f3a                        Authorization: Bearer <token>
```

What to notice:

- On the left, "next" means nothing on its own. Only the server that holds session `8f3a` knows which page this user saw, and after a restart nobody knows.
- On the right, the request says exactly what it wants, so any instance can answer it, a cache can store it, and a retry gives the same page.
- The token is sent and checked again on every call. That repeated work is the price of statelessness.

## Rules and defaults

- **HTTP is stateless (RFC 9110):** each message can be understood on its own. Cookies (RFC 6265) are what let servers add a stateful session on top.
- **Two kinds of state:** session state lives on the client and travels with each request; resource state, such as the payments, lives on the server.
- **Server-side sessions:** a session kept on the server breaks this rule. Tools such as Spring Session store sessions in a shared store, such as Redis or a database, so any instance can read them. That removes sticky sessions, but every request now needs a lookup, and the session is still server state.

## Not to be confused with

A session cookie holds only an id; the server looks up the session data behind it, so the server keeps state. A token such as a [JWT](card:jwt), which you will see later, carries the signed facts about the caller itself, so any instance can check it without a lookup. Rule: session cookie = the server remembers; self-contained token = the request carries it.

## Interview Qs

### What makes a REST API stateless?

Each request carries everything needed to process it, such as credentials, ids and options. The server does not rely on anything stored from earlier requests of that client. Data such as payments can still live in a database; that is resource state.

### Why does statelessness help scaling?

No request needs a particular server, so a load balancer can send it to any instance. You add instances when traffic grows and lose one without logging users out. Fielding also lists visibility and reliability: one request is enough to understand it, and recovery after a failure is simpler.

### HTTP is stateless. Isn't every HTTP API stateless, then?

No. HTTP messages are self-contained, but cookies let a server keep a session and look it up on each request. An API that stores login or progress in a server session is stateful, even over HTTP.
