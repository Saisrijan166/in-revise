## What it is

OpenAPI is a standard format for describing an HTTP API in one file, written in YAML or JSON. The file lists every path, such as `/api/payments`, the [methods](card:http-methods) each path accepts, the shape of the request and response bodies, the [status codes](card:status-codes) it can return, and how callers log in. Swagger is a family of tools from the company SmartBear that read this file. The specification itself was named Swagger up to version 2.0.

## Why it exists

Without a shared description, an API is explained on a wiki page that slowly drifts away from the code. A client team guesses field names and learns that `currency` is required only when it gets a 400. Every team also writes its own client code by hand. An OpenAPI file is exact and machine-readable, so one file can produce the documentation, generate client code in many languages, and let tests check that responses keep the promise.

1. You choose how the file is made. Design-first: you write `openapi.yaml`, review it with the teams that will call the API, then write the code. Code-first: you write the controllers, and a library generates the file from them.
2. In Spring Boot, the springdoc-openapi library reads your [controllers](card:spring-rest-controllers), their mappings and their validation annotations at runtime, and serves the generated file at `/v3/api-docs`.
3. Swagger UI loads the file and shows each operation with its fields and responses, and lets you send a test request from the page.
4. Code generators such as Swagger Codegen read the same file and produce client libraries or server stubs.
5. You keep the file in Git next to the code, so a change to the contract is reviewed like any other change.

## Example

The contract for creating the ₹500 payment, as a small but valid OpenAPI 3.1 file:

```yaml
openapi: 3.1.0
info: { title: Payments API, version: 1.0.0 }
paths:
  /api/payments:
    post:
      requestBody:
        content:
          application/json:
            schema:
              type: object
              required: [amount, currency]
              properties: { amount: { type: integer, minimum: 1 }, currency: { type: string } }
      responses:
        '201': { description: Payment created with status PENDING }
        '400': { description: Invalid amount or currency }
```

What to notice:

- `openapi: 3.1.0` is the version of the specification the file follows; `info.version` is the API's own version. Delete the `info` line and a validator rejects the file, because `info` is required.
- `post` under `/api/payments` is one operation. Its body must be JSON with an integer `amount` of at least 1 and a `currency`, and both are required, so `{"amount": -500}` breaks the contract.
- Each response is keyed by its status code. A reader knows to expect 201 or 400, and a generated client gets one typed method for this call.
- In a real file the body schema moves to `components/schemas` and is referenced with `$ref`, so many operations share one definition.

## Rules and defaults

- **Required fields:** `openapi` and `info` (with `title` and `version`). In OAS 3.1 and later the file also needs at least one of `paths`, `components` or `webhooks`.
- **Versions:** OAS 3.0.0 came in July 2017, 3.1.0 in February 2021 and 3.2.0 in September 2025; the latest is 3.2.1 (September 2026). From 3.1, schemas are JSON Schema 2020-12.
- **springdoc-openapi 3.x (Spring Boot 4):** add `springdoc-openapi-starter-webmvc-ui`. The file is served at `/v3/api-docs` (YAML at `/v3/api-docs.yaml`) and Swagger UI at `/swagger-ui.html`. The generated file follows OAS 3.1 by default (`springdoc.api-docs.version`).
- **What springdoc reads:** mappings, parameter types and Bean Validation annotations such as `@NotNull`, `@Min`, `@Max` and `@Size`. Add `@Operation` and `@Schema` where the code alone does not explain enough.
- **Turning it off:** `springdoc.api-docs.enabled=false` disables springdoc's endpoints, for example where the API's map should not be public.

## Not to be confused with

[Design-first](card:design-first-openapi) means the file is written and agreed before the code, so consumers review the contract early; the OpenAPI Initiative recommends it. [Code-first](card:code-first-openapi) means the code comes first and the file is generated from it: the easiest start, but the file then describes whatever the code happens to do. Rule: design-first when other teams depend on the API; code-first for a small internal API, with the generated file still reviewed.

## Interview Qs

### What is the difference between OpenAPI and Swagger?

OpenAPI is the specification for describing HTTP APIs, run by the OpenAPI Initiative. Swagger was the specification's original name: in 2015 SmartBear donated Swagger 2.0 to the initiative, which renamed it OpenAPI, and 3.0 followed in 2017. Today Swagger means SmartBear's tools, such as Swagger UI, Swagger Editor and Swagger Codegen.

### Design-first or code-first?

Design-first for APIs that other teams or partners call: they review the contract before code exists and can build against it in parallel. Code-first is the easiest start for a small internal API. Either way, review the file, because it is the promise the API makes.

### How do you document a Spring Boot REST API?

Add springdoc-openapi 3.x. It reads the controllers, request mappings and validation annotations, and serves the OpenAPI file at `/v3/api-docs` and Swagger UI at `/swagger-ui.html`. Annotations such as `@Operation` and `@Schema` add descriptions where the code is not clear enough.
