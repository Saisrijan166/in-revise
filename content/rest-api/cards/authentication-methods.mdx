## Why it exists

A REST API is stateless, so every request must carry its own proof of who sent it. The server then decides what that caller may do.

## How it works

<Compare id="basic-vs-api-key-vs-bearer-token" />

- Credentials go in the `Authorization` header, not the URL: URLs end up in logs (RFC 6750).
- Bearer tokens usually come from [OAuth 2.0](card:oauth2-and-oidc) and are often a [JWT](card:jwt).
- All of these need [HTTPS](card:https-tls); over plain HTTP anyone on the path can copy them.

## Example

```text
POST /api/payments HTTP/1.1
Host: api.shop.example
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...
Content-Type: application/json

{"amount": 500, "currency": "INR", "method": "UPI"}
```

## Interview Qs

### Authentication vs authorisation?

Authentication proves identity: is this token valid? Authorisation checks rights: may this customer read PAY101? Authentication comes first; authorisation runs on every action. See [401 vs 403](compare:401-vs-403).

### Is an API key enough to secure an API?

Not for user data. A key ties a call to an app for quotas and billing; it does not prove which person is calling, and leaked keys work until revoked. Use OAuth 2.0 tokens for user access.

### Is Basic auth secure?

Only over TLS. Base64 is reversible, so the password travels on every request in readable form. RFC 7617 itself says the scheme is not secure on its own.
