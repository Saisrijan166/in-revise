## What it is

Authentication is the API checking who is calling. The caller sends a credential, a piece of proof, with each request: a password, an API key (a long secret string a provider gives to an app) or a bearer token (a short-lived pass issued after login). The server checks it before doing any work. Authorisation comes next and decides what this known caller may do, such as reading payment PAY101.

## Why it exists

A REST API is [stateless](card:statelessness): the server remembers nothing between requests, so it cannot rely on "this user logged in earlier". Without a credential on each request, anyone who knows the URL could create a ₹500 payment or read someone else's. Sending proof with every request lets any server instance check the caller on its own.

## How it works

<Compare id="basic-vs-api-key-vs-bearer-token" />

1. The client gets a credential once: a password it already knows, an API key from the provider's dashboard, or a token from a login server.
2. On every request it sends the credential in a request header, usually `Authorization`, never in the URL, because URLs are written to server and proxy logs.
3. The server checks the credential. If it is missing, wrong or expired, the server answers [401 Unauthorized](card:status-codes) with a `WWW-Authenticate` header naming the scheme to use.
4. If the credential is valid, the server knows the caller and moves on to authorisation: may this caller do this action on this object? If not, it answers 403 Forbidden.

So the key is: authentication on every request, then authorisation for every action and object.

## Example

The payment team's internal admin script uses Basic auth. These two commands show what the `Authorization: Basic` value really is.

```bash
echo -n 'shop-app:s3cret' | base64        # the client sends "Basic <this>"
echo 'c2hvcC1hcHA6czNjcmV0' | base64 -d   # anyone who sees the header can undo it
```

```text output
c2hvcC1hcHA6czNjcmV0
shop-app:s3cret
```

What to notice:

- The request header becomes `Authorization: Basic c2hvcC1hcHA6czNjcmV0`. Base64 is an encoding for safe transport, not encryption: no key is needed to reverse it.
- The second command recovers the password with no secret at all, so Basic auth is safe only inside an encrypted connection, which you will see in [HTTPS and TLS](card:https-tls).
- The same password travels on every request, so one leaked log line exposes it until someone changes it. A bearer token in the same header would at least expire.

## Rules and defaults

- **Where it goes:** the `Authorization` header (`Basic …` or `Bearer …`); API keys often use a vendor header such as `X-API-Key`. RFC 6750 says a token in the URL query SHOULD NOT be used, because the URL is likely to be logged.
- **HTTPS only:** RFC 6750 makes TLS mandatory for bearer tokens, and RFC 7617 says Basic auth is not secure without it.
- **Failure responses (RFC 6750):** an expired or bad token gets 401 with `WWW-Authenticate: Bearer error="invalid_token"`; a valid token without the needed scope gets 403 with `error="insufficient_scope"`.
- **Secrets:** keep API keys and client secrets in a secret manager or server-side configuration. Anything shipped in a browser or mobile app can be extracted.

## Not to be confused with

Authentication answers "who are you?" by checking the credential. Authorisation answers "what may you do?" by checking roles, scopes and ownership for this action. Rule: 401 means "we do not know who you are"; 403 means "we know, and the answer is no".

A session cookie holds only a random ID, and the server keeps the login in its session store. A bearer token carries the proof itself, often as a [JWT](card:jwt), the next concept.

## Common mistakes

- **"An API key tells us which user is calling."** It identifies the calling app or project. Use it for quotas and billing; user data needs a user token.
- **"The key is safe in the frontend bundle."** Anyone can read a web or mobile app's code. Keep the key on your server and let the server call the provider.

## Interview Qs

### What is the difference between authentication and authorisation?

Authentication proves identity: is this token valid, and whose is it? Authorisation checks rights: may this customer read PAY101 or refund it? Authentication comes first; authorisation runs for every action. Failing authentication gives 401, failing authorisation gives 403.

### Is an API key enough to secure an API?

Not for user data. A key ties a call to an app for quotas and billing; it does not prove which person is calling, and a leaked key works until someone revokes it. Use OAuth 2.0 tokens for user access, and keep keys for identifying partner apps.

### Why should a token never go in the URL?

URLs are stored in server access logs, proxy logs and browser history, so a token in the query string leaks to everyone who reads them. RFC 6750 says the query-parameter method SHOULD NOT be used; send the token in the `Authorization` header instead.
