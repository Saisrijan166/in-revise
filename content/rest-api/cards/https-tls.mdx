## Why it exists

Plain HTTP sends tokens, passwords and card details as readable text that anyone on the network can copy or change. TLS closes that gap.

## How it works

  alt="TLS in a payment API. The client connects over HTTPS using TLS 1.3 to the load balancer, which holds the certificate and decrypts the request. The load balancer forwards it to the payment service, either re-encrypted or over mTLS. The payment service calls the payment provider over mTLS or HTTPS."

- Basic auth, API keys and bearer tokens are only safe inside TLS ([authentication methods](card:authentication-methods)).
- HSTS is for browsers; API clients should simply refuse plain `http://` URLs.

## Interview Qs

### What does TLS protect, and what does it not?

It protects data in transit: nobody on the path can read or alter it, and the client knows it reached the real server. It does not protect stored data, a stolen token, or a bug in your authorisation.

### What is mTLS and when do you use it?

Mutual TLS: both sides present certificates, so the server also knows which client is calling. Each microservice can then prove who it is to the others, so it suits service-to-service calls.

### What is TLS termination?

The load balancer holds the certificate and decrypts traffic, so app servers skip that work. The trade-off: traffic behind it is plain unless you re-encrypt it.
