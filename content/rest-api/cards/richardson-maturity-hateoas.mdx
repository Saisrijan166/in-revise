## What it is

The Richardson Maturity Model is a scale from level 0 to level 3 that shows how fully an HTTP API uses the ideas of [REST](card:what-is-rest). Leonard Richardson devised it, and Martin Fowler explained it in a 2010 article. HATEOAS (Hypermedia as the Engine of Application State) is the top level. Hypermedia means data that contains links, like a web page, and HATEOAS means each response carries links to what the client can do next.

## Why it exists

Because "REST" is used loosely, "our API is RESTful" says little. The model gives a shared scale: you can say "level 2" and everyone knows what the API does. Hypermedia then solves a further problem. A client that hard-codes every URL breaks when the server changes one, and it must copy rules such as "only a successful payment can be refunded". With links, the client follows what the server offers.

## How it works

| Level | Adds | Payment example |
|---|---|---|
| 0 | One URI; every call is a POST | `POST /api` with the action in the body |
| 1 | One URI per resource | `/payments`, `/payments/PAY101` |
| 2 | HTTP methods and status codes | `GET /payments/PAY101` returns 200 |
| 3 | Hypermedia links in responses | PAY101 links to its refunds |

Climb the levels with the payment API:

1. Level 0: every call is `POST /api`, and the body names the action. HTTP only carries the messages; this is a remote procedure call (RPC), like calling a function on another machine.
2. Level 1: each resource gets its own URI, but every call is still a POST.
3. Level 2: methods and status codes mean what HTTP defines: `GET` reads, `POST` creates, a missing payment gets 404. You will meet them in [HTTP methods](card:http-methods) and [status codes](card:status-codes).
4. Level 3: responses carry links. A successful PAY101 links to its refunds; a failed one does not.

So each level adds one idea, and only level 3 is REST as Fielding defines it.

## Example

A level 3 response for PAY101 in the HAL format:

```json
{
  "paymentId": "PAY101",
  "status": "SUCCESS",
  "_links": {
    "self":    { "href": "/api/payments/PAY101" },
    "refunds": { "href": "/api/payments/PAY101/refunds" }
  }
}
```

What to notice:

- `_links` is where HAL puts links; each has a name, such as `refunds`, called its link relation, and an `href`.
- The app looks up the `refunds` link instead of building the URL itself, so the server can change that URL later.
- If the payment had failed, the server would leave the `refunds` link out, and the app would hide its Refund button.

## Rules and defaults

- **Fielding's view (2008):** an API that is not driven by hypermedia is not REST.
- **In practice:** many published APIs sit around level 2 (Azure guidance), and there is no general-purpose standard for HATEOAS links.
- **HAL:** media type `application/hal+json`; links under `_links`, embedded resources under `_embedded`. It is only an expired IETF draft.
- **Spring HATEOAS:** a Spring project for building responses with links; it supports HAL.
- **What the model is:** Fowler calls it a good way to think about REST's parts, not a definition of REST.

## Interview Qs

### What is HATEOAS?

Hypermedia as the Engine of Application State. Each response includes links to related resources and to the actions allowed now, so the client follows links instead of hard-coding URIs. The server can then change URIs, and add new actions, without breaking clients.

### Explain the Richardson Maturity Model.

Level 0 sends every call to one endpoint. Level 1 adds a URI per resource. Level 2 uses HTTP methods and status codes as HTTP defines them. Level 3 adds hypermedia links. Each level adds one idea, and Fielding treats level 3 as a precondition of REST.

### Why do most APIs stop at level 2?

Level 2 already gives clear URIs, standard methods and status codes, which generic tools understand. Level 3 needs a link format, and there is no general-purpose standard for one, and clients must be written to follow links. So many teams document their URIs instead.
