## What it is

OAuth 2.0 is a standard way for an app to get permission to call an API (RFC 6749). Four roles take part: the resource owner (the user), the client (the app), the authorization server (the login server that issues tokens) and the resource server (the API, such as the payment API). The client ends up with an access token, often a [JWT](card:jwt), limited by scopes such as `payments:write`. OpenID Connect (OIDC) is a thin layer on top that also tells the client who the user is.

## Why it exists

Before OAuth, a budgeting app that wanted your bank data asked for your bank password. It could then do anything as you, for as long as it liked, and the only way to stop it was to change your password. With OAuth 2.0 you log in at the bank itself, the app gets only a token with the scopes you approved, and you can revoke that token without touching your password.

## How it works

1. The app creates a random secret, the code verifier, and sends the user's browser to the authorization server with its SHA-256 hash (the code challenge) and the scopes it wants.
2. The user logs in and approves there. The app never sees the password.
3. The authorization server redirects back to the app with a short-lived, one-time authorization code.
4. The app sends the code and the code verifier to the token endpoint, the authorization server's URL that hands out tokens. The server hashes the verifier and compares it with the challenge. If they match, it returns an access token, often a refresh token, and an ID token if the scopes included `openid`.
5. The app calls the payment API with `Authorization: Bearer <access token>`, and the API validates it as in [JWT](card:jwt).

So the key is: a stolen code is useless without the verifier, which never left the app.

## Example

The payment API is a resource server: it only validates tokens and never shows a login page. In Spring Boot 4.1 this takes two properties.

```yaml
# starter: spring-boot-starter-security-oauth2-resource-server
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.shop.example
          audiences: payments-api
```

What to notice:

- `issuer-uri`: on the first request with a JWT, Spring Security reads the issuer's metadata, fetches its public keys, and from then on checks the signature, `exp`, `nbf` and `iss` of every token.
- `audiences`: Spring does not check `aud` by default. With this line, a token whose `aud` does not include `payments-api` gets 401. Remove it and a token issued for another API would be accepted.
- With `issuer-uri`, Spring accepts only the signing algorithms of the keys the issuer publishes, and allows 60 seconds of clock skew on the time checks.

## Rules and defaults

- **User present:** use authorization code with PKCE. RFC 9700 says public clients (apps that cannot keep a secret, such as mobile and browser apps) MUST use PKCE, recommends it for confidential clients (server-side apps), and names S256 as the method to use.
- **No user:** use client credentials. The service authenticates with its own client ID and secret, and RFC 6749 says a refresh token SHOULD NOT be issued.
- **Retired grants (RFC 9700):** the implicit grant SHOULD NOT be used; the resource owner password grant MUST NOT be used.
- **Audience:** RFC 9700 says access tokens SHOULD be restricted to the API they are for, and each API rejects tokens not meant for it.
- **Refresh token:** lives longer than the access token, is sent only to the authorization server, and swapped for a new access token without a new login.

## Not to be confused with

OAuth 2.0 answers "may this app call the API?" with an access token meant for the API. OpenID Connect answers "who logged in?" with an ID token meant for the client app; its `aud` is the client ID. Rule: access token goes to APIs; ID token stays in the app.

## Common mistakes

- **"OAuth 2.0 is a login protocol."** It is delegated authorisation: it says what an app may do, not who the user is. Login comes from OpenID Connect on top of it.
- **"A token with payments:read can read any payment."** The scope allows the action; the API must still check that PAY101 belongs to this user.

## Interview Qs

### Which OAuth flow for a mobile app, and which for a batch job?

A mobile app uses authorization code with PKCE: it cannot keep a client secret, and RFC 9700 requires PKCE for such public clients. A batch job calling another service uses client credentials, because no user is involved; the job authenticates as itself.

### Why do we need PKCE?

The app sends a hash of a one-time secret at the start, and the secret itself when it swaps the code for tokens. A code stolen from the redirect is then useless, because the thief does not know the secret. RFC 9700 makes it mandatory for public clients.

### Access token vs refresh token?

The access token is short-lived and goes to APIs on every call. The refresh token lives longer, goes only to the authorization server, and gets new access tokens without a new login. Revoking the refresh token is how you end a session early.
