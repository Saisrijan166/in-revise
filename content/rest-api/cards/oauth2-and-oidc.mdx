## Why it exists

Giving a third-party app your password hands over everything. OAuth 2.0 gives the app a limited, revocable token instead, and OIDC reuses the same flow for "log in with".

## How it works

<Compare id="oauth2-vs-oidc" />

- Scopes such as `payments:write` limit what a token may do; the API still checks ownership.
- The access token is often a [JWT](card:jwt), which the API validates by itself.

## Example

```yaml
# Spring Boot 4.1, starter spring-boot-starter-security-oauth2-resource-server
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.shop.example
          audiences: payments-api
```

## Interview Qs

### Which OAuth flow for a mobile app, and which for a batch job?

Mobile app: authorization code with PKCE, since it cannot keep a secret. Batch job calling another service: client credentials, because no user is involved.

### Why PKCE?

The app sends a hash of a one-time secret at the start and the secret itself when trading the code. A stolen authorization code is then useless. RFC 9700 requires it for public clients.

### Access token vs refresh token?

The access token is short-lived and goes to APIs. The refresh token lives longer, goes only to the authorization server, and gets new access tokens without a new login.
