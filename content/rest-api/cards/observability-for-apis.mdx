## What it is

Observability means you can tell what a running API is doing, and why it fails, from the data it sends out. That data comes in three kinds. A log is a record of one event, such as "provider timeout for PAY101". A metric is a number measured over time, such as requests per second. A trace follows one request through every service it touches; each step in it is a span. A correlation ID is one ID per request that appears in all three, so you can join them.

## Why it exists

One ₹500 payment passes through the API gateway, the payment service and the provider adapter. When a customer says PAY101 is stuck, you need the matching lines from all three services. Without a shared ID you search each service's logs by timestamp and guess. Averages hide problems too: if 1% of payments take 8 seconds, the average stays low while real customers wait. Shared IDs and the right metrics turn hours of searching into one query.

## How it works

<Compare id="logs-vs-metrics-vs-traces" />

1. The first service that receives the request reads its `traceparent` header, or starts a new trace with a new trace ID if there is none.
2. It records a span for its own work and writes the trace ID, and its span ID, into every log line for that request.
3. On each outgoing call it sends `traceparent` with the same trace ID and its own span ID as the parent, so the next service's span links to it.
4. Every service also counts requests, errors and durations per endpoint, and keeps durations as a histogram so p95 and p99 can be read.
5. During an incident you go from the metric that alerted, to a slow or failed trace, to the logs that carry that trace ID.

So the key is that one ID travels with the request everywhere it goes.

## Example

The payment service receives a request, calls the provider and logs a timeout:

```text
POST /api/payments HTTP/1.1
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

# payment service calls the provider: same trace-id, its own span as parent-id
POST /v1/charges HTTP/1.1
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-b7ad6b7169203331-01

{"level":"ERROR","traceId":"4bf92f3577b34da6a3ce929d0e0e4736","paymentId":"PAY101","msg":"provider timeout"}
```

What to notice:

- The header has four parts: version `00`, the 32-character trace ID, the 16-character parent span ID, and the flags, where `01` means "sampled".
- The trace ID stays the same on the outgoing call, but the parent ID changes to the payment service's own span. That is how a tracing tool draws the tree of calls.
- The log line is JSON with named fields, so a log search for that `traceId` or for `PAY101` finds it. It holds IDs only: no token and no card number.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Traces recorded | 10% of requests (`0.1`) | Spring Boot 4.1, `management.tracing.sampling.probability` |
| Header sent to other services | W3C `traceparent` | Spring Boot 4.1, `management.tracing.propagation.produce` |
| Request metric | `http.server.requests` | Spring Boot 4.1 with Actuator, for Spring MVC |
| Actuator endpoints over HTTP | `health` only | Spring Boot 4.1, `management.endpoints.web.exposure.include` |

- **Percentiles need a histogram:** set `management.metrics.distribution.percentiles-histogram.http.server.requests=true` so the monitoring system can compute p95 and p99 across instances.
- **Log correlation:** with Micrometer Tracing on the classpath, Spring Boot adds the trace ID and span ID to log lines; `logging.pattern.correlation` changes the format.
- **X-Request-ID:** a widely used header, but not a standard; prefer `traceparent`, or accept both at the edge.
- **Never log (OWASP):** access tokens, passwords, session IDs, encryption keys, card or bank data and sensitive personal data. Mask them or leave them out.

## Not to be confused with

A correlation ID is the general idea: any ID that ties together the log lines of one request, often sent as `X-Request-ID`. A trace ID is the standardised form from W3C Trace Context; it also links the spans of each service into a tree with timings. Rule: a correlation ID joins logs; a trace ID joins logs and shows where the time went.

## Interview Qs

### How do you follow one request across microservices?

Use distributed tracing. The first service starts a trace, each call sends the W3C `traceparent` header, and each service records its own span with the same trace ID. Logs carry that trace ID too, so one search shows the whole path and which hop was slow or failed.

### Which metrics do you watch for an API?

RED per endpoint: the request rate, the error rate and the duration. For duration, use p95 and p99 from a histogram, not the average, and alert on them together with the rate of 5xx responses.

### What must never go into logs?

Access tokens, passwords, session IDs, encryption keys, card or bank data and sensitive personal data. Mask them or drop them, and log IDs such as `paymentId` and `traceId` instead, which are enough to find everything else.
