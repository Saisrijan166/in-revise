## What it is

An exception is Java's way of reporting a failure: it stops the current method and travels up to the callers until some code handles it. Exception handling in Spring MVC turns an exception into an HTTP error response. An `@ExceptionHandler` method says "for this exception type, send this response". Put such methods in a class marked `@RestControllerAdvice` and they apply to every controller. They usually return Spring's `ProblemDetail`, the RFC 9457 body from [error responses](card:error-responses).

## Why it exists

The service knows that payment PAY999 does not exist, but it should not know about HTTP. Without a central handler, every controller wraps its calls in try/catch and builds its own error body, so errors come out in different shapes, and any exception nobody catches becomes a 500. With one advice class, the service just throws `PaymentNotFoundException`, and every controller answers 404 with the same body shape.

1. The service throws `PaymentNotFoundException`. The controller does not catch it, so it leaves the controller method.
2. Spring MVC first looks for an `@ExceptionHandler` for that type in the same controller.
3. If there is none, it looks in the advice classes, which apply to all controllers.
4. The matching handler returns a `ProblemDetail`. Its `status` becomes the HTTP status, and the body goes out as `application/problem+json`.
5. If no handler matches, the exception reaches Spring Boot's `/error` fallback, which usually answers 500.

## Example

One advice class serves the whole payment API.

```java
@RestControllerAdvice
class ApiErrors extends ResponseEntityExceptionHandler {   // also formats Spring MVC's errors

    @ExceptionHandler(PaymentNotFoundException.class)
    ProblemDetail notFound(PaymentNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Payment not found");
        return pd;                                          // 404, application/problem+json
    }
}
```

```bash
curl -s -w '\n%{http_code} %{content_type}\n' http://localhost:8080/api/payments/PAY999
```

```text output
{"detail":"No payment with id PAY999","instance":"/api/payments/PAY999","status":404,"title":"Payment not found"}
404 application/problem+json
```

What to notice:

- The service only threw an exception. The status 404 and the body came from the advice.
- Spring filled `instance` with the request path; the code set only status, detail and title.
- Extending `ResponseEntityExceptionHandler` makes Spring MVC's own errors, such as a failed `@Valid` or a missing header, come out as `ProblemDetail` too.
- Delete this class and the same request gets 500 with Spring Boot's generic JSON, because nothing maps the exception to 404.

## Rules and defaults

- **Order:** handlers in the controller itself run first; handlers in advice classes run after them.
- **Scope:** an advice applies to every controller by default. A package name or `annotations = RestController.class` narrows it.
- **Built-in errors as ProblemDetail (Spring Boot 4.1):** off by default. Set `spring.mvc.problemdetails.enabled=true`, or extend `ResponseEntityExceptionHandler` yourself as above.
- **No class for every error:** `throw new ResponseStatusException(HttpStatus.CONFLICT, "Payment already refunded")` sends that status; its reason becomes the `detail`.
- **Unhandled exceptions:** Spring Boot's `/error` sends JSON with timestamp, status, error and path. The exception message and stack trace are hidden by default (`spring.web.error.include-message` and `include-stacktrace` are `never`).

## Not to be confused with

`@ExceptionHandler` marks one method that handles one exception type. On its own, inside a controller, it covers only that controller. `@ControllerAdvice` marks a class whose handlers apply to all controllers, and `@RestControllerAdvice` is the same plus `@ResponseBody`, so the return value is the body. Rule: `@ExceptionHandler` says how to handle; the advice says where it applies.

## Common mistakes

- **"Send the exception message and stack trace so the client can debug."** They can reveal class names, SQL and internal paths. Log the details on the server, and send a safe `detail` the client can act on.

## Interview Qs

### How do you handle exceptions globally in Spring Boot?

A `@RestControllerAdvice` class with one `@ExceptionHandler` method per exception type, each returning a `ProblemDetail` with the right status. It applies to every controller. Extending `ResponseEntityExceptionHandler` also covers Spring MVC's own exceptions, so every error has the same shape.

### If @ExceptionHandler handles exceptions, why do we need @ControllerAdvice?

`@ExceptionHandler` is the mechanism, but inside a controller it covers only that controller. `@ControllerAdvice` makes the handlers global, so one class serves every controller instead of copying handlers into each.

### What does a client get for an exception nobody handles?

Spring Boot's `/error` mapping sends a JSON error, usually with status 500, holding timestamp, status, error and path. By default it hides the exception message and stack trace.

### How do you return validation errors as Problem Details?

Either set `spring.mvc.problemdetails.enabled=true`, or extend `ResponseEntityExceptionHandler` in your advice. Both handle `MethodArgumentNotValidException` and answer 400 with a `ProblemDetail`. Override its handler method to add the failing fields as an extra property.
