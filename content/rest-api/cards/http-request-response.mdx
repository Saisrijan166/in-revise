## What it is

HTTP (HyperText Transfer Protocol) is the set of rules two programs follow to exchange messages over a network. The program that asks is the client: a browser, a mobile app or another backend service. The program that answers is the server. Every exchange is one request from the client and one response from the server, and both are structured messages with the same four parts.

## Why it exists

A mobile app that wants to pay ₹500 must tell the payment server four things: what to do (create), to which thing (payments), with what data (₹500 by UPI) and in which format. Without a shared message format, every server would invent its own, and every client would need custom code for each server. HTTP fixes the parts of the message, so any client can talk to any server, and tools such as browsers and curl understand every message.

## How it works

| Part | In the request | In the response |
|---|---|---|
| First line | Method, target, version | Version, status code, reason |
| Headers | Host, Content-Type, Authorization | Content-Type, Location |
| Empty line | Ends the headers | Ends the headers |
| Body | The data sent (optional) | The result (optional) |

1. The client reads the URL, the address of what it wants, such as `https://api.example.com/api/payments`. It connects to the server named in it, `api.example.com`.
2. It sends the request line. The method says what to do (`GET` reads, `POST` creates), the target is the path `/api/payments`, and the version is `HTTP/1.1`.
3. It sends headers, one `Name: value` per line, with facts about the message: `Host` names the server, `Content-Type` says the body is JSON, `Content-Length` says how many bytes it has. An empty line ends the headers.
4. It sends the body, here the payment as JSON, and waits.
5. The server does the work and answers with a status line, such as `HTTP/1.1 201 Created`, then its own headers, an empty line and a response body.

So the first line says what to do or what happened, headers describe the message, and the body carries the data.

## Example

The app creates a ₹500 UPI payment. First the request:

```text
POST /api/payments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 51

{"amount": 500, "currency": "INR", "method": "UPI"}
```

Then the server's response:

```text
HTTP/1.1 201 Created
Location: /api/payments/PAY101
Content-Type: application/json
Content-Length: 44

{"paymentId": "PAY101", "status": "PENDING"}
```

What to notice:

- `Content-Length: 51` is the exact byte count of the JSON body. It tells the receiver where the message ends, so it must match the real body.
- The status code `201` is what the app checks. The words `Created` are only a hint for humans.
- `Location` gives the address of the new payment, so the app can read it later with `GET /api/payments/PAY101`.
- `status: PENDING` is the payment's own state, which is separate from the HTTP status code. You will see why in [status codes](card:status-codes).

## Rules and defaults

- **Host is required:** an HTTP/1.1 request must carry a `Host` header (RFC 9112), because one machine can serve many sites.
- **Where the body ends:** `Content-Length` gives its size in bytes; without it, HTTP/1.1 can send the body in chunks (chunked transfer coding).
- **Reason phrase:** optional and only a hint. RFC 9112 says clients should ignore it and act on the code.
- **No Content-Type:** the receiver may treat the body as raw bytes (`application/octet-stream`) or guess (RFC 9110), so always send it with a body.
- **JSON text:** JSON sent between systems must be UTF-8 (RFC 8259).
- **Same meaning in every version:** HTTP/2 and HTTP/3 carry the same methods, headers and codes, sent as binary fields instead of text lines (RFC 9110).

## Interview Qs

### What are the parts of an HTTP request and response?

A request has a request line (method, target, version), headers, an empty line and an optional body. A response has a status line (version, status code, optional reason phrase), headers, an empty line and an optional body. Headers describe the message; the body carries the data, usually JSON for APIs.

### HTTP/1.1 vs HTTP/2 vs HTTP/3?

They share the same methods, headers and status codes. HTTP/1.1 sends text over TCP. HTTP/2 sends binary frames and multiplexes many requests on one TCP connection. HTTP/3 runs over QUIC on UDP, so one lost packet stalls only its own stream, not the others. An API does not change between them.

### What does synchronous mean for an HTTP API?

The client sends a request and waits until the response arrives. This is simple, but if the work takes long, such as waiting for a bank, the client waits too and may time out. Slow work is better accepted at once and finished later, as you will see in [long-running operations](card:long-running-operations).
