## Why it exists

Every REST call is one HTTP message each way. Knowing the parts tells you where each piece of data belongs and what to check when a call fails.

## How it works

| Part | Request | Response |
|---|---|---|
| First line | Method, target, version | Version, status code, reason |
| Headers | Host, Content-Type, Authorization | Content-Type, Location |
| Empty line | Ends the headers | Ends the headers |
| Body | The data sent (optional) | The result (optional) |

- What each part means: [methods](card:http-methods), [headers](card:headers-content-negotiation), [status codes](card:status-codes).
- Slow work should not keep the client waiting: return 202 and a status link, see [long-running operations](card:long-running-operations).

## Example

```text
POST /api/payments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 51

{"amount": 500, "currency": "INR", "method": "UPI"}

HTTP/1.1 201 Created
Location: /api/payments/PAY101
Content-Type: application/json
Content-Length: 44

{"paymentId": "PAY101", "status": "PENDING"}
```

## Interview Qs

### What are the parts of an HTTP request and response?

Request: request line (method, target, version), headers, an empty line, an optional body. Response: status line (version, code, reason phrase), headers, an empty line, an optional body.

### HTTP/1.1 vs HTTP/2 vs HTTP/3?

Same methods, headers and codes. HTTP/1.1 is text over TCP. HTTP/2 is binary and multiplexes many requests on one TCP connection. HTTP/3 runs over QUIC on UDP, so one lost packet does not stall other streams.
