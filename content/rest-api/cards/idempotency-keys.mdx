## What it is

An idempotency key is a unique value the client sends with a request, in the `Idempotency-Key` header, so the server can recognise a repeat of the same operation. POST is not idempotent: sending `POST /api/payments` twice creates two payments ([HTTP methods](card:http-methods)). With a key, the server saves the result of the first request under that key. A retry with the same key gets that saved result, and the work is not done again.

## Why it exists

The client sends a ₹500 POST. The server charges and saves PAY101, but the response is lost on a weak mobile network. The client cannot tell whether it worked, so it retries, and without a key the server sees a brand-new payment and charges ₹500 again. With the key, the server sees `order-789-payment` again and returns PAY101's saved 201 response. The request arrives twice, but the payment happens once.

1. The client creates one key for the payment, such as a random UUID, and stores it with its order before the first attempt.
2. The server inserts a row with the key and a fingerprint (a hash of the body) before doing any work. A unique constraint on the key column allows only one such row.
3. If the insert succeeds, the request is new: the server charges, saves the response in that row and returns 201.
4. If the insert fails, the key exists. The server returns the saved response if that request finished with the same fingerprint, 409 if it is still running, and 422 if the body is different.
5. After the published retention window, the server deletes old keys. A key reused after that is treated as a new request.

## Example

The checkout app pays ₹500, loses the response and sends the identical request again.

```text
POST /api/payments
Idempotency-Key: order-789-payment
{"amount": 500, "currency": "INR", "method": "UPI"}
-> 201 Created  {"paymentId": "PAY101", "status": "PENDING"}

(response lost; the same request is sent again)
-> 201 Created  {"paymentId": "PAY101", "status": "PENDING"}   (saved copy)
```

What to notice:

- Both attempts carry the same key and the same body, so the second one gets the same `paymentId`: one payment, not two.
- The second 201 is a copy from the key's row; the gateway is not called again. Stripe marks such a copy with `Idempotent-Replayed: true`.
- The key comes from the order (`order-789`), so even a restarted app sends the same key; Stripe suggests this too. A random UUID works as well if it is saved before the first attempt.

## Rules and defaults

- **Standard status:** the `Idempotency-Key` header is IETF draft-07, which expired on 18-04-2026. It is widely used, but it is not an RFC.
- **Draft errors:** a missing key on an endpoint that requires one gets 400; the same key with a different body gets 422; a repeat while the first is still running gets 409.
- **Key format:** the draft recommends a UUID or a similar random value, because a guessable key could let another client read your saved result. It also advises storing the key together with the client's identity, so two clients never share a key. Stripe allows up to 255 characters and no personal data, such as an email address.
- **What Stripe API v1 saves:** the status and body of the first request once the endpoint starts running, including a 500. A request rejected before that, such as by validation, saves nothing, so it can be retried.
- **GET and DELETE:** they are idempotent by definition, so they need no key.

## Not to be confused with

An idempotent method, such as PUT or DELETE, is idempotent by its HTTP definition: repeating it leaves the same state. An idempotency key makes a non-idempotent POST safe to repeat through the server's own bookkeeping. Rule: methods are idempotent by definition; POST becomes idempotent only with a key that the server stores.

## Interview Qs

### How do you stop a retry from charging ₹500 twice?

The client sends an Idempotency-Key that it reuses on every retry. Before charging, the server inserts the key under a unique constraint, then saves the result in the same row. Any retry with the same key and body gets the saved result instead of a new charge.

### Where does the key come from, and how long do you keep it?

The client creates it once per operation: a random UUID v4, or a value derived from the order, like order-789-payment, never personal data. The server keeps it for a published window; Stripe keeps keys at least 24 hours. A key reused after it is deleted runs as a new request.

### Two requests with the same key arrive together. What happens?

Only one insert of the key can succeed, because of the unique constraint. That request does the work. The other sees the key with the work still running and gets 409 Conflict; it waits, retries with the same key and body, and then receives the saved result.
