## What it is

A resource is anything an API lets clients work with: one payment, the list of all payments, the refunds of a payment. Its URI (Uniform Resource Identifier) is the name that identifies it, such as `/api/payments/PAY101`. The client never receives the resource itself. It receives a representation: a copy of the resource's current state in a format such as JSON, which the [Content-Type](card:http-request-response) header names.

## Why it exists

If an API exposed its storage, such as `/payments_table/row/17`, every change to the database would break every client. Clients only need two things: a stable way to say which thing they mean, and its data in a format they can read. Resources give them exactly that. The server can split tables or move a payment to another database, and the URI and the JSON stay the same.

## How it works

The parts of one URI (RFC 3986), `https://api.example.com/api/payments/PAY101?includeRefunds=true`:

| Part | Value | Its job |
|---|---|---|
| Scheme | `https` | How to reach the server: HTTP over a secure connection |
| Authority | `api.example.com` | Which server |
| Path | `/api/payments/PAY101` | Which resource; `PAY101` is a path parameter |
| Query | `includeRefunds=true` | Options for the result; a query parameter |

1. The client puts the path and query into the request line: `GET /api/payments/PAY101?includeRefunds=true`.
2. The server reads the path to find the resource: the collection `/api/payments`, then the item `PAY101` inside it.
3. It reads the query for options: also include the refunds.
4. It loads the payment's state from wherever it keeps it, perhaps two tables.
5. It turns that state into a representation, JSON, and sends it with `Content-Type: application/json`.

So the path says which thing, the query says how you want it, and a body carries a representation.

## Example

Four requests on the payments resources:

```text
GET  /api/payments                  the collection: a list of all payments
POST /api/payments                  add a new item to the collection
GET  /api/payments/PAY101           one item: payment PAY101
GET  /api/payments?status=SUCCESS   the same collection, filtered
```

What to notice:

- `GET /api/payments` and `POST /api/payments` are two endpoints on one URI. An endpoint is the method plus the path.
- `PAY101` sits in the path because it names one resource. `status=SUCCESS` sits in the query because it only narrows the list.
- Without the query, the API returns the collection unfiltered, so every query parameter needs a sensible default.

## Rules and defaults

- **URI, URL, URN (RFC 3986):** a URI identifies; a URL is a URI that also gives a way to reach the resource, such as `https://`; a URN is a `urn:` name meant to stay unique and lasting.
- **Fragment:** the part after `#` is handled by the client alone; it is cut off before the request is sent.
- **Body:** carries a representation the client sends, mostly with `POST`, `PUT` and `PATCH`.
- **Naming:** the rules for good paths (plural nouns, nesting depth) are in [URL design rules](card:url-design-rules).

## Not to be confused with

A path parameter, such as `PAY101`, picks one resource; change it and you address a different thing. A query parameter, such as `status=SUCCESS`, filters, sorts, pages or tunes the result of the same resource. Rule: path = which resource; query = which part of it, or how.

## Interview Qs

### What is a resource in REST?

Any named thing the API exposes: a payment, an order, a list of payments. It has a URI, and clients read or change it only through representations such as JSON. It is a concept, not a table row: one resource may come from several rows.

### URI vs URL?

A URI identifies a resource. A URL is a URI that also says how to reach it, such as `https://api.example.com/...`. Every URL is a URI, but a name like `urn:isbn:...` is a URI that is not a URL. RFC 3986 advises using the general term URI.

### Path, query or body: where does the data go?

The path says which resource, such as `PAY101`. The query holds options such as filters, sorting or the page number. The body carries the representation you create or update, such as the new payment's JSON.
