## Why it exists

Clients need a stable way to say which thing they mean and to get its data in a format they understand, without knowing how the server stores it.

## How it works

<Compare id="path-vs-query-parameter" />

- The request body carries a representation the client sends, as in POST, PUT and PATCH.
- RFC 3986 parts: scheme, authority, path, query, fragment. Naming rules: [URL design](card:url-design-rules).

## Example

```text
https://api.example.com/api/payments/PAY101?includeRefunds=true
scheme:    https
authority: api.example.com
path:      /api/payments/PAY101   (PAY101 is a path parameter)
query:     includeRefunds=true    (a query parameter)
```

## Interview Qs

### What is a resource in REST?

Any named thing the API exposes: a payment, an order, a list of payments. It has a URI, and clients read or change it through representations such as JSON.

### URI vs URL?

A URI identifies a resource. A URL is a URI that also says how to reach it, such as https://. RFC 3986 advises using the general term URI.

### Path, query or body: where does the data go?

Path: which resource (PAY101). Query: options such as filters, sorting or pages. Body: the representation you create or update.
