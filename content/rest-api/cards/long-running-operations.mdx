## What it is

A long-running operation is a request whose work takes longer than a client can sensibly wait for, from many seconds to hours. Instead of answering at the end, the API answers at once with 202 Accepted and the URL of a status resource: a small resource that reports how the job is going. The client checks that URL until the job ends. This is called the asynchronous request-reply pattern.

## Why it exists

A large merchant asks for a month's payment statement as a PDF, which takes five minutes to build. If `POST /api/statements` waits for the PDF, the client, a proxy or the load balancer gives up first. The client then cannot tell whether the job ran, and a server thread stays busy the whole time. With 202, the request returns in milliseconds, the work runs in the background, and the client always has a URL that tells it the truth.

1. The client sends `POST /api/statements`. The API checks the request, queues job OP55 and answers 202 Accepted with `Location: /api/operations/OP55` and `Retry-After: 5`.
2. The client waits 5 seconds, then sends `GET /api/operations/OP55`. It gets 200 with status Running.
3. A worker builds the statement in the background and records the result.
4. The next check returns 303 See Other with the result's URL, and the client fetches it with GET.
5. If the job fails, the status resource says Failed and includes a [problem details](card:error-responses) error.

## Example

The same flow as raw HTTP, with the bodies cut short.

```text
POST /api/statements                     {"merchantId": "M42", "month": "2026-09"}
-> 202 Accepted
   Location: /api/operations/OP55
   Retry-After: 5

GET /api/operations/OP55
-> 200 OK                                {"status": "Running"}

GET /api/operations/OP55
-> 303 See Other
   Location: /api/statements/ST9
```

What to notice:

- The 202 has no statement in it, only where to look. The status resource is a normal resource, read with GET.
- `Retry-After: 5` tells the client how often to check, so it does not hammer the API.
- 303 See Other tells the client to fetch the `Location` with a GET, whatever method it used before.
- If the client stops checking after the 202, it never learns whether the job worked.

## Rules and defaults

- **202 is noncommittal:** RFC 9110 says the request may still be refused or fail when it is processed.
- **Retry-After:** a number of seconds or an HTTP date (RFC 9110).
- **Cancel:** an API may offer `DELETE /api/operations/OP55` to cancel the job (Azure pattern).
- **Push instead of checking:** a client that can receive calls can get the result by [webhook](card:webhooks) or [Server-Sent Events](card:websockets-and-sse); you will see both later.

## Not to be confused with

201 Created means the resource exists now: PAY101 is saved as PENDING, and its own URL shows progress. 202 Accepted means only that the work was queued, so the client follows a separate status resource. Rule: the resource exists now = 201; only a job exists = 202.

Checking the status URL every few seconds is short polling. Long polling, SSE and WebSockets keep a connection open so the server can answer as soon as something changes.

## Interview Qs

### How do you design an API for a job that takes minutes?

Accept quickly with 202 Accepted, a Location header for a status resource, and Retry-After. The client checks that URL; at the end it gets 303 See Other or a link to the result, or a Failed status with an error. A webhook can tell the client instead, so it does not need to check.

### 201 with status PENDING, or 202?

201 when the resource already exists, like payment PAY101 saved as PENDING; its own URL shows progress. 202 when you only queued the request and nothing exists yet, so you point to a separate status resource.

### Does 202 guarantee that the work will be done?

No. RFC 9110 calls 202 noncommittal: the request may still be rejected or fail when it is processed. The client must check the final status, or receive a webhook, before it treats the job as done.
