## Why it exists

Some work takes minutes, like a monthly statement PDF or a bank settlement run. Holding one HTTP call open that long ends in timeouts and ties up servers.

## How it works

<Mermaid
  alt="Long-running operation. The client sends POST /api/statements. The API queues job OP55 for a worker and answers 202 Accepted with Location /api/operations/OP55 and Retry-After 5. The client polls GET /api/operations/OP55 and gets 200 with status PENDING. After the worker finishes, the next poll returns 303 See Other with Location /api/statements/ST9, and the client fetches the result with GET."
  chart={`sequenceDiagram
  participant C as Client
  participant A as API
  participant W as Worker
  C->>A: POST /api/statements
  A->>W: queue job OP55
  A-->>C: 202 Accepted, Location /api/operations/OP55, Retry-After 5
  C->>A: GET /api/operations/OP55
  A-->>C: 200 status PENDING
  W-->>A: job OP55 done
  C->>A: GET /api/operations/OP55
  A-->>C: 303 See Other, Location /api/statements/ST9`}
/>

- A failed job shows FAILED with an [error body](card:error-responses) on the status resource.
- Optional cancel: `DELETE /api/operations/OP55`.
- No polling: push the result by [webhook](card:webhooks) or [SSE](card:websockets-and-sse).

## Interview Qs

### How do you design an API for a job that takes minutes?

Accept quickly with 202 Accepted, a Location header for a status resource and Retry-After. The client polls that URL; at the end it gets the result link or 303 See Other. Offer a webhook to avoid polling.

### 201 with status PENDING, or 202?

201 when the resource already exists, like payment PAY101 saved as PENDING; its own URL shows progress. 202 when you only queued the request, so you point to a separate status resource.

### Does 202 guarantee the work will be done?

No. RFC 9110 calls 202 noncommittal: the request may still be rejected when it is processed. The client must check the final status.
