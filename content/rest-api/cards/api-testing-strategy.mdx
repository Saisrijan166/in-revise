## Why it exists

No single kind of test catches everything. Mocks hide wiring bugs, and full end-to-end runs are slow and flaky. Each level catches one class of bug cheaply.

## How it works

<Compare id="unit-vs-integration-vs-contract-test" />

- A [test double](card:test-double) is a stub, mock or fake standing in for a real dependency, such as the payment provider.
- The Spring annotations for each level live in [Testing Spring REST Controllers](card:spring-api-testing).
- Push each check as low as it can go; keep end-to-end tests to a few key journeys.

## Example

| Case for `POST /api/payments` | Expect | Rule lives in |
|---|---|---|
| Valid ₹500, token, new key | 201, Location, status PENDING | [Status codes](card:status-codes) |
| Amount -500 | 400 or 422 with a problem body | [Error responses](card:error-responses) |
| No `Authorization` header | 401 | [401 vs 403](compare:401-vs-403) |
| Token of another customer | 403 | [OWASP API Top 10](card:owasp-api-security) |
| Same `Idempotency-Key` twice | Same response, one charge | [Idempotency keys](card:idempotency-keys) |
| Provider times out | Stays recoverable, never charged twice | [Unknown outcomes](card:unknown-outcomes) |

## Interview Qs

### What would you test for a payment endpoint?

The happy path (201), bad input (400 or 422), no token (401), another customer's token (403), a repeated Idempotency-Key that must not charge twice, and a provider timeout that leaves the payment recoverable.

### What is the difference between a mock and a stub?

A stub returns canned answers. A mock is also set up with expected calls and fails the test if they do not happen. Both are test doubles.

### Why contract tests if we already have integration tests?

Integration tests against a fake only prove you can parse the fake. A contract test checks the real provider against what consumers need, without deploying every service together.
