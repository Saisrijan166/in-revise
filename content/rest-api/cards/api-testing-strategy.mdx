## What it is

An API testing strategy is the plan for which kinds of tests you write for an API and what each one checks. A unit test checks one class on its own, with its dependencies replaced by a [test double](card:test-double), a stand-in object. An integration test runs your code with real parts, such as the database and the HTTP layer. A contract test checks that the API and the clients calling it agree on requests and responses. An end-to-end test runs the whole deployed system.

## Why it exists

With only end-to-end tests, the suite is slow and often fails for reasons unrelated to your change, such as a network blip, and a failure does not point to the broken line. With only unit tests and mocks, a wrong JSON field name, a broken SQL query or a missing security rule still passes, because the mock never runs them. Each level catches one kind of bug cheaply, so you need a mix.

## How it works

<Compare id="unit-vs-integration-vs-contract-test" />

1. List the promises the endpoint makes: its status codes, its error body, who may call it, what happens on a repeated request, and what happens when a dependency fails.
2. Test each business rule, such as "the amount must be positive", in a fast unit test of the class that owns it.
3. Test the HTTP contract of the controller, meaning status codes, JSON fields and 401 or 403, with a web-layer test; the Spring annotations for this are in [Testing Spring REST Controllers](card:spring-api-testing).
4. Run integration tests against a real database of the same kind, so queries and the unique constraint on the idempotency key really execute.
5. Where another team calls your API, add contract tests, and keep end-to-end tests for a few journeys, such as "pay and see SUCCESS".

So the key is: push each check down to the lowest level that can still catch its bug.

## Example

The six cases that prove `POST /api/payments`, with the level that tests each one:

| Case | Expect | Test level |
|---|---|---|
| Valid ₹500, valid token, new key | 201, `Location` header, status PENDING | Web layer, then integration |
| Amount -500 | 400 or 422 with a [problem details](card:error-responses) body | Unit (rule) and web layer |
| No `Authorization` header | 401 | Web layer with security on |
| Token of another customer | 403 | Web layer with security on |
| Same `Idempotency-Key` sent twice | Same response, one charge | Integration (real unique constraint) |
| Provider times out | Payment stays recoverable, never charged twice | Unit with a provider stub that times out |

What to notice:

- The 401 and 403 rows need the security rules switched on in the test. A web-layer test that disables security passes even if any customer can read any payment.
- The duplicate-key row needs a real database, because the protection is the unique constraint from [idempotency keys](card:idempotency-keys); a mocked repository would happily save twice.
- The timeout row uses a stub that never answers, so you can check the [unknown outcome](card:unknown-outcomes) handling without a real provider.

## Rules and defaults

- **Kinds of test double:** dummy, fake, stub, spy and mock; Mockito builds stubs, spies and mocks in Java.
- **Contract test tools:** Pact is consumer-driven: the consumer's tests write a contract file, and the provider replays it. Spring Cloud Contract writes contracts in a DSL, such as Groovy or YAML, and generates provider tests and WireMock stubs.
- **Postman:** good for exploring an API by hand and saving requests as collections. To run collections in CI, use the Postman CLI; Newman is no longer maintained and does not support the collection v3 format of Postman v12.

## Not to be confused with

A testing strategy decides which level checks which promise. `@WebMvcTest` and `@SpringBootTest` are only the Spring tools that run two of those levels, the web layer and the full application, as [Testing Spring REST Controllers](card:spring-api-testing) showed. Rule: the strategy says what to test where; the annotations say how Spring runs it.

## Interview Qs

### What would you test for a payment endpoint?

The happy path (201 with a `Location`), bad input (400 or 422 with a problem body), no token (401), another customer's token (403), a repeated `Idempotency-Key` that must not charge twice, and a provider timeout that leaves the payment recoverable instead of failed or charged twice.

### What is the difference between a mock and a stub?

A stub returns canned answers so the code under test can run. A mock is also set up with the calls it expects, and the test fails if they do not happen. Both are test doubles; Mockito can build either.

### Why contract tests if we already have integration tests?

An integration test against a fake of another service only proves you can parse the fake. A contract test checks the real provider against what each consumer actually uses, without deploying every service together, so a breaking change is caught before release.
