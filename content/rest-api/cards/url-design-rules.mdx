## What it is

URL design rules are a few naming habits that make every URL of an API look alike. A URL has a path, such as `/api/payments/PAY101`, and an optional query string after the `?`, such as `?status=SUCCESS`. The rules say what goes in the path (nouns that name [resources](card:resources-and-uris)), what goes in the query string (options such as filters), and what stays out of the URL: the action, because the [HTTP method](card:http-methods) already says it.

## Why it exists

Without rules, each developer names URLs in their own way: `/createPayment`, `/payment/get?id=PAY101`, `/Payments_List`. A client cannot guess any URL, so it needs the documentation for every endpoint, and renaming one later breaks the apps that already call it. With one pattern, a developer who has seen `GET /payments/PAY101` can guess `GET /refunds/RF7` and `POST /payments` without reading anything.

## How it works

| Do | Don't | Rule |
|---|---|---|
| `POST /api/payments` | `POST /api/createPayment` | The method is the verb |
| `GET /api/payments/PAY101` | `GET /api/payment?id=PAY101` | Plural collection, id in the path |
| `GET /api/payments/PAY101/refunds` | `/users/10/orders/7/payments/PAY101` | At most collection/item/collection |
| `GET /api/payments?status=SUCCESS` | `GET /api/successPayments` | Filters go in the query string |
| `POST /api/payments/PAY101:cancel` | `GET /api/payments/PAY101/cancel` | An action that changes state is a POST |

1. Name the collection with a plural noun: `/payments` stands for all payments.
2. Put the item's id after it: `/payments/PAY101` is one payment.
3. Choose the method for the action: POST to the collection creates, GET reads, DELETE removes.
4. Nest only a child that belongs to its parent, one level deep: the refunds of one payment are `/payments/PAY101/refunds`.
5. Put options in the query string: `?status=SUCCESS` filters the list; paging follows in the [next concept](card:pagination-filtering-sorting).
6. For an action that fits no method, first try to make it a noun (a refund is a resource). If that fails, POST to the item with the action name after a colon.

So the key is: the path says which thing, the method says what to do, the query says how.

## Example

The URL map of the payment API follows every rule above.

```text
POST   /api/v1/payments                     create a ₹500 payment
GET    /api/v1/payments/PAY101              read one payment
GET    /api/v1/payments?status=SUCCESS      list payments, filtered
POST   /api/v1/payments/PAY101/refunds      refund part of PAY101
GET    /api/v1/refunds/RF7                  read one refund directly
POST   /api/v1/payments/PAY101:cancel       an action with no noun
```

What to notice:

- Only nouns appear in the paths. The same `/payments` URL creates with POST and lists with GET.
- A refund is created under its payment, but read at `/refunds/RF7`. Once the client has the refund id, it does not need the payment id, so the URL stays at collection/item depth.
- `:cancel` is a custom method in the style of Microsoft and Google guidelines. It is a POST because it changes state.
- The `/v1` prefix is the API version; you will see it in [API versioning](card:api-versioning).

## Rules and defaults

- **Case:** Microsoft's Azure guidelines prefer kebab-case path segments, such as `/payment-links`; Google's AIP-122 uses camelCase. Pick one for the whole API.
- **Ids are opaque:** Microsoft's guidelines treat ids as opaque, case-sensitive strings. A client must not build or parse them.
- **Colon in ids:** if you use `:action` URLs, do not allow `:` inside ids, so an id can never look like an action (Microsoft).
- **GET never changes state:** GET is a safe method (RFC 9110), so software may call it at any time, for example to prefetch a link.

## Not to be confused with

A path parameter, such as `PAY101` in `/payments/PAY101`, identifies which resource you mean. A query parameter, such as `status=SUCCESS`, changes how a collection is returned: filtered, sorted or paged. Rule: path = which thing; query = which rows and in what shape.

## Common mistakes

- **"/payments?id=PAY101 is the same as /payments/PAY101."** The query form gives the payment no URI of its own, so links, caches and logs cannot point at it cleanly. Put the id in the path.

## Interview Qs

### What are the best practices for naming REST URLs?

Use plural nouns for collections and put the id after them. Let the HTTP method be the verb, keep one case style everywhere and nest at most one level. Put filters, sorting and paging in the query string, and keep verbs out of paths.

### How do you model an action that is not CRUD, like cancelling a payment?

First try to make it a noun: a refund can be its own resource with an id and a status. If that does not fit, POST to the item with an action name, like `POST /payments/PAY101:cancel`, the style of Microsoft and Google. Never GET, because GET must not change state.

### Is /users/10/orders/7/payments a good URL?

No. Keep URLs at collection/item/collection. Once a client has the payment id, it calls `/payments/PAY101` directly. Deep chains repeat relationships in every URL, and they break when those relationships change.
