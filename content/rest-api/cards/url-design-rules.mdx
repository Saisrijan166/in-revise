## Why it exists

Clients guess, read and remember URLs. One predictable pattern for every [resource](card:resources-and-uris) means less documentation and fewer breaking renames later.

## How it works

| Do | Don't | Rule |
|---|---|---|
| `POST /api/payments` | `POST /api/createPayment` | The method is the verb |
| `GET /api/payments/PAY101` | `GET /api/payment?id=PAY101` | Plural collection, id in the path |
| `GET /api/users/10/payments` | `/users/10/orders/7/payments/PAY101` | At most collection/item/collection |
| `GET /api/payments?status=SUCCESS` | `GET /api/successPayments` | Filters go in the query string |
| `POST /api/payments/PAY101:cancel` | `GET /api/payments/PAY101/cancel` | An action changes state: POST, never GET |

- If an action has its own id and status, make it a noun: `POST /api/payments/PAY101/refunds`.
- Filters, sorting and paging: [Pagination](card:pagination-filtering-sorting). The `/v1` prefix: [API versioning](card:api-versioning).

## Interview Qs

### What are the best practices for naming REST URIs?

Plural nouns for collections, the id in the path, HTTP methods as verbs, one case style everywhere, shallow nesting, and query parameters for filters, sorting and paging.

### How do you model an action that is not CRUD, like cancelling a payment?

First try a noun: a refund can be its own resource. Otherwise POST to the item with an action name, like `POST /payments/PAY101:cancel` (Microsoft and Google style). Never GET, because GET must not change state.

### Is /users/10/orders/7/payments a good URL?

No. Keep URLs at collection/item/collection. Once a client has the payment id, it calls `/payments/PAY101` directly, so the URL does not break when relationships change.
