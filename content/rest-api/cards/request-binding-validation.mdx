## What it is

Request binding is Spring copying values from the request into your method's parameters and converting the text into Java types: a path segment into a `String`, a query value into an `int`, the JSON body into an object. Validation then checks those values against rules you write as annotations on the fields, such as `@NotNull` or `@Positive`. These rules come from Jakarta Bean Validation, the Java standard for declaring constraints. `@Valid` on a parameter asks Spring to run them.

## Why it exists

Everything in an HTTP request arrives as text. Without binding, each method would parse strings, catch number errors and check for nulls by hand, and each endpoint would reject bad input in its own way. The checks cannot live only in the mobile app either, because anyone can call the API with curl. Binding and validation run on the server, the same way for every endpoint, and bad input gets 400 before your method runs.

## How it works

| Annotation | Reads | Payment API example |
| --- | --- | --- |
| `@PathVariable` | a `{placeholder}` in the path | `/api/payments/{id}` → `PAY101` |
| `@RequestParam` | a query parameter | `?status=SUCCESS` |
| `@RequestHeader` | one request header | `Idempotency-Key: order-789-payment` |
| `@RequestBody` | the whole body, through Jackson | JSON → `PaymentRequest` |

1. Spring picks the controller method, as in the [previous concept](card:spring-rest-controllers).
2. For each parameter, it reads the part of the request named by its annotation and converts it to the parameter's type. A missing required value, or a failed conversion such as `"abc"` for a number, stops here with 400.
3. For `@RequestBody`, Jackson builds a `PaymentRequest` from the JSON.
4. If the parameter has `@Valid`, the validator checks every constraint on its fields.
5. If any check fails, Spring throws `MethodArgumentNotValidException`, the method never runs, and the client gets 400. Otherwise your method runs with clean values.

## Example

The create endpoint takes the idempotency key from a header and the payment from the body. The rules sit on the request record.

```java
record PaymentRequest(
        @NotNull @Positive BigDecimal amount,              // 0 and -500 fail
        @NotBlank @Size(min = 3, max = 3) String currency, // "INR"
        @NotNull PaymentMethod method) { }                 // UPI, CARD or WALLET

@PostMapping
PaymentResponse create(@RequestHeader("Idempotency-Key") String key,
                       @Valid @RequestBody PaymentRequest req) {
    return service.create(key, req);
}
```

```bash
curl -s -X POST http://localhost:8080/api/payments -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-789-payment' -d '{"amount": -500, "currency": "INR", "method": "UPI"}'
```

```text output
{"timestamp":"2026-10-21T16:35:54.311Z","status":400,"error":"Bad Request","path":"/api/payments"}
```

What to notice:

- The amount −500 fails `@Positive`, so `service.create` never runs and no payment exists.
- Remove `@Valid` and nothing is checked: −500 reaches the service.
- A request without the `Idempotency-Key` header also gets 400, because `@RequestHeader` is required by default.
- Spring Boot's default error body does not say which field failed. [Exception handling](card:exception-handling), two concepts on, sends a clearer body.

## Rules and defaults

- **Required by default:** `@RequestParam` and `@RequestHeader` values must be present, or the client gets 400. `required = false` or a `defaultValue` makes them optional.
- **Nested objects:** `@Valid` checks a nested object, such as a billing address inside the request, only if that field also has `@Valid`.
- **Constraints on parameters (Spring Framework 6.1+):** a constraint placed directly on a parameter, like `@RequestParam @Max(100) int size`, runs Spring MVC's built-in method validation. A failure throws `HandlerMethodValidationException`, also 400, so handle both exceptions. Do not put `@Validated` on the controller class: it switches to the older proxy-based checks.
- **Validator needed:** Spring Boot's web starter has no validator. Add `spring-boot-starter-validation`, which brings Hibernate Validator.

## Not to be confused with

`@PathVariable` reads the part of the path that names the resource, PAY101 in `/api/payments/PAY101`. `@RequestParam` reads an option after `?`, such as `status=SUCCESS`. Separately, `@Valid` is the Jakarta annotation that turns on validation, and `@Validated` is Spring's version, which can also select validation groups. Rule: path = which resource, query = how to filter it.

## Interview Qs

### How do you validate a request body?

Put Jakarta constraints such as `@NotNull` and `@Positive` on the DTO fields, and mark the `@RequestBody` parameter with `@Valid`. A failure throws `MethodArgumentNotValidException`, which Spring MVC turns into 400 before the method runs. In Spring Boot this needs `spring-boot-starter-validation` on the classpath.

### @PathVariable vs @RequestParam?

`@PathVariable` reads a segment of the path that identifies the resource, like PAY101. `@RequestParam` reads a query parameter that filters, sorts or pages, like `?status=SUCCESS`. Both are required by default.

### @Valid vs @Validated?

`@Valid` is the Jakarta annotation: validate this object, and nested objects whose fields also carry `@Valid`. `@Validated` is Spring's: it can name validation groups, for example different rules for create and update, and on a service class it turns on method validation through a proxy.

### If the client already validates, why validate on the server?

Client checks are for user experience. Anyone can skip them by calling the API directly, so only server checks protect the data. OWASP treats server-side validation as the real control.
