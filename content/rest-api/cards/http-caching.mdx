## What it is

HTTP caching means keeping a copy of a response and reusing it for a later identical request, instead of asking the server again. A cache is private when it serves one user, like the browser's own store. It is shared when it serves many users, like a proxy or a CDN, a network of servers placed close to users. The server controls caching with the `Cache-Control` [header](card:headers-content-negotiation), and with an ETag, a version label of the response.

## Why it exists

The list of payment methods (UPI, card, wallet) changes perhaps once a week, but every app start downloads it again. That wastes bandwidth, server time and the user's time. Caching lets the copy be reused for a while with no network call at all. After that, revalidation asks the server "is my copy still good?" and gets a tiny 304 reply instead of the full body when nothing changed.

## How it works

1. The first `GET /api/payment-methods` gets 200 with the list, `Cache-Control: max-age=600` and `ETag: "v7"`. The cache stores it.
2. For the next 10 minutes the copy is fresh, so the cache answers by itself, with no network call.
3. After 10 minutes the copy is stale. The cache sends the request again with `If-None-Match: "v7"`.
4. If the list is unchanged, the server answers 304 Not Modified with no body, and the copy is fresh for another 10 minutes. If it changed, the server sends 200 with the new list and a new ETag.

So `max-age` decides how long to trust the copy, and the ETag makes checking it cheap.

## Example

A Spring controller that serves the payment methods with both headers:

```java
@GetMapping("/api/payment-methods")
ResponseEntity<List<PaymentMethod>> methods() {
    return ResponseEntity.ok()
            .cacheControl(CacheControl.maxAge(Duration.ofMinutes(10)))
            .eTag(catalogue.version())   // Spring answers 304 if If-None-Match matches
            .body(catalogue.findAll());
}
```

What to notice:

- `CacheControl.maxAge(...)` writes `Cache-Control: max-age=600`, so caches reuse the reply for 10 minutes.
- `.eTag(...)` writes the version as the ETag. When a request's `If-None-Match` matches it, Spring sends 304 with an empty body instead of the list.
- `findAll()` still runs on every request here; the 304 saves the transfer, not the work. Spring's `WebRequest.checkNotModified(eTag)` lets you skip the work too.

## Rules and defaults

- **Directives (RFC 9111):** `max-age=N` fresh for N seconds; `s-maxage=N` overrides it for shared caches only; `private` only the user's own cache; `no-cache` store but revalidate before each reuse; `no-store` never store; `must-revalidate` never reuse a stale copy without checking.
- **Methods:** which methods have cacheable responses is in [HTTP methods](card:http-methods). A successful `PUT`, `POST` or `DELETE` also makes caches drop their stored copies of that URL (RFC 9111).
- **Logged-in requests:** a shared cache must not reuse a reply to a request with `Authorization` unless `public`, `s-maxage` or `must-revalidate` allows it.
- **No Cache-Control:** for codes such as 200 and 404, a cache may guess a lifetime, typically 10% of the time since `Last-Modified`.
- **Last-Modified:** a date validator, sent back in `If-Modified-Since`; it has one-second resolution, so an ETag is more precise.

## Not to be confused with

`no-cache` lets a cache store the response but makes it ask the server before every reuse, which is cheap with an ETag. `no-store` forbids storing it at all, for data such as card details. Rule: no-cache = always check; no-store = never keep.

## Interview Qs

### Should payment responses be cached?

Card or account details: `no-store`. Other per-user data, such as a payment's status: `private`, so a CDN never serves it to another user. Public data, such as the list of payment methods, can use `max-age` with an ETag.

### A response has no Cache-Control. Is it safe from caching?

No. For codes such as 200 and 404, RFC 9111 lets a cache guess a lifetime, for example 10% of the time since `Last-Modified`. Send an explicit directive on every response.

### How does an ETag save bandwidth?

The client keeps the ETag of its copy and sends it in `If-None-Match`. If the server's current version has the same ETag, it answers 304 with no body, so only headers cross the network. Only a changed resource sends the full body again.
