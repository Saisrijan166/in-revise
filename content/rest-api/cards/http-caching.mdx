## Why it exists

Downloading the same unchanged data again wastes bandwidth and server time. Caching reuses a stored reply, and revalidation confirms it cheaply.

## How it works

<Steps label="Caching and revalidating GET /api/payment-methods">
  <Step title="First GET">200 with the list, `Cache-Control: max-age=600` and `ETag: "v7"`.</Step>
  <Step title="Within 10 minutes">The copy is fresh: the cache answers, with no network call.</Step>
  <Step title="After 10 minutes">The copy is stale: the client sends `If-None-Match: "v7"`.</Step>
  <Step title="Unchanged">304 Not Modified, no body; the cache reuses its copy. Changed: 200 with a new ETag.</Step>
</Steps>

- `s-maxage` overrides `max-age` for shared caches such as a CDN.
- A shared cache does not reuse a reply to a request with Authorization, unless `public`, `s-maxage` or `must-revalidate` allows it.
- Last-Modified with If-Modified-Since works the same way, at one-second resolution.

## Example

```java
@GetMapping("/api/payment-methods")
ResponseEntity<List<PaymentMethod>> methods() {
    return ResponseEntity.ok()
            .cacheControl(CacheControl.maxAge(Duration.ofMinutes(10)))
            .eTag(catalogue.version())   // Spring sends 304 if If-None-Match matches
            .body(catalogue.findAll());
}
```

## Interview Qs

### Should payment responses be cached?

Card or account details: `no-store`. Other per-user data: `private`, so a CDN never serves it to another user. Public data, like the list of payment methods, can use `max-age`.

### A response has no Cache-Control. Is it safe from caching?

No. For codes such as 200 and 404, a cache may guess a lifetime, for example 10% of the time since Last-Modified (RFC 9111). Send an explicit directive.
