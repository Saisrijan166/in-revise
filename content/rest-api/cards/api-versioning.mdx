## What it is

API versioning is how you change an API without breaking the apps that already call it. A breaking change is one an existing client notices and fails on, such as a removed or renamed field. The rule is simple: make additive changes in place, and publish a new major version, such as v2, only for a breaking change. The old version keeps running until an end date you announced.

## Why it exists

A mobile app released last year still calls `GET /api/payments/PAY101` and reads `amount` as a number. If you rename that field to `amountInPaise`, every old app on customers' phones shows an error, and you cannot force them all to update. With versioning, the new shape lives in v2 while v1 keeps the old one, so old and new apps both work, and you remove v1 only on a date its users were told about.

## How it works

| Change | Breaks old clients? |
|---|---|
| Add an optional field or a new endpoint | No |
| Remove or rename a field, or change its type | Yes |
| Add a required request field or a required header | Yes |
| Change the documented error codes | Yes |
| Add paging to a list that returned everything | Yes |

1. You prefer additive changes. A new optional field stays in v1, and tolerant readers, clients that ignore unknown fields, do not notice it.
2. When a break cannot be avoided, you add v2 next to v1. The client chooses a version in the path, a header or the media type of the [Accept header](card:headers-content-negotiation).
3. You mark v1 as deprecated: its responses carry a `Deprecation` header and a `Sunset` header with the date it stops.
4. You watch v1 traffic fall, then remove v1 after the Sunset date.

## Example

Spring Framework 7.0 can route by version itself. Here the client chooses the version with an `API-Version` header.

```java
@Configuration
class WebConfig implements WebMvcConfigurer {
    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        configurer.useRequestHeader("API-Version");          // client sends API-Version: 2
    }
}
@RestController
@RequestMapping("/api/payments")
class PaymentController {
    @GetMapping(path = "/{id}", version = "1")
    PaymentV1 getV1(@PathVariable String id) { return new PaymentV1(id, 500); }
    @GetMapping(path = "/{id}", version = "2+")              // 2 and later supported versions
    PaymentV2 getV2(@PathVariable String id) { return new PaymentV2(id, 50_000, "INR"); }
}
```

What to notice:

- Both methods share one URL. Spring picks the method from the `API-Version` header.
- In a test run, `API-Version: 1` returned `{"id":"PAY101","amount":500}` and `API-Version: 2` returned the v2 body with `amountInPaise`.
- No header gave 400 ("API version is required"), and `API-Version: 3` gave 400 too, because no mapping declares 3 and it was not configured as supported.
- `"1"` is read as version 1.0.0, so a client sending `1.0.0` gets the same v1 method.

## Rules and defaults

- **Version required:** with versioning on, Spring Framework 7.0 answers 400 when the version is missing. You can make it optional (the latest version is used) or set a default version.
- **Supported versions:** by default Spring treats the versions declared in mappings as supported; any other version gets 400.
- **Baseline "2+":** matches version 2 and higher supported versions, unless a mapping for a more specific version exists.
- **Deprecation headers:** Spring's `StandardApiVersionDeprecationHandler` can add `Deprecation`, `Sunset` and `Link` headers for a deprecated version.
- **Header dates:** `Deprecation: @1688169599` is a Unix time (RFC 9745). The Sunset date must not be earlier than the Deprecation date.

## Not to be confused with

Deprecation means "do not build anything new on this": the resource still works exactly as before. Sunset is the date it stops responding. Rule: Deprecation = warned, still working; Sunset = the switch-off date.

## Interview Qs

### How do you version a REST API?

Mostly by not breaking it: additive changes keep v1 working for tolerant clients. A breaking change ships as a new major version, often `/api/v2`. Both run side by side, v1 announces its end with Deprecation and Sunset headers, and it is removed after that date.

### Which changes are breaking?

Anything an old client notices: a removed, renamed or retyped field, a new required field or header, changed error codes, or paging added to a list that used to return everything. Adding an optional field or a new endpoint is safe, as long as clients ignore unknown fields.

### How do you retire an old version?

Announce a date, keep the version running and send Deprecation and Sunset headers on every response; Spring Framework 7.0 can add them. Watch its traffic, contact the remaining clients, and remove it only after the Sunset date.
