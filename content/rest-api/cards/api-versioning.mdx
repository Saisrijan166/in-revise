## Why it exists

Mobile apps and partners update on their own schedule, so a changed contract breaks them. Changes must be additive or ship as a new version.

## How it works

| Change | Breaks old clients? |
|---|---|
| Add an optional response field or a new endpoint | No |
| Remove or rename a field, or change its type | Yes |
| Make a field required, or add a required header | Yes |
| Change top-level error codes | Yes |
| Add paging to a list that returned everything | Yes |

- Where the version goes: [path, header or media type](compare:uri-vs-header-vs-media-type-versioning).
- Spring Framework 7.0 maps versions itself: `configurer.useRequestHeader("API-Version")`, or path, query or media type.

## Example

```java
@RestController
@RequestMapping("/api/payments")
class PaymentController {
    private final PaymentService service;
    PaymentController(PaymentService service) { this.service = service; }

    @GetMapping(path = "/{id}", version = "1")
    PaymentV1 getV1(@PathVariable String id) { return service.findV1(id); }

    @GetMapping(path = "/{id}", version = "2+")   // 2 and later
    PaymentV2 getV2(@PathVariable String id) { return service.findV2(id); }
}
```

## Defaults

| What | Default | Where |
|---|---|---|
| Version required | Yes: no version gives 400 | Spring Framework 7.0 versioning |
| Version format | Semantic: "1" means 1.0.0 | Spring Framework 7.0 versioning |

## Interview Qs

### How do you version a REST API?

Mostly by not breaking it: additive changes keep v1 working. A breaking change ships as v2, often as /api/v2, and both run until v1's Sunset date.

### Which changes are breaking?

Anything an old client notices: a removed, renamed or retyped field, a new required field or header, changed error codes, or new paging. Additions are safe if clients ignore unknown fields.

### How do you retire an old version?

Keep it running and send Deprecation and Sunset headers, so every response shows the dates; Spring Framework 7.0 can add them. Remove it only after the Sunset date.
