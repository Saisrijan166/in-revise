## Why it exists

Clients need to react without parsing every body: retry, log in again, fix the input or give up. The three-digit code says which.

## How it works

| Code | Means | ₹500 payment case |
|---|---|---|
| 200 OK | worked, body follows | GET PAY101 |
| 201 Created | new resource made | POST created PAY101 |
| 204 No Content | worked, no body | DELETE a saved card |
| 400 Bad Request | malformed request | broken JSON |
| 401 Unauthorized | no valid credentials | expired token |
| 403 Forbidden | known caller, not allowed | agent without refund rights |
| 404 Not Found | no such resource | GET PAY999 |
| 405 Method Not Allowed | method not supported here; send Allow | PUT on /api/payments |
| 409 Conflict | clashes with current state | refund a FAILED payment |
| 422 Unprocessable Content | valid JSON, wrong meaning | amount -500 |
| 500 Internal Server Error | unexpected server failure | NullPointerException |

- Elsewhere: [202](card:long-running-operations), [304](card:http-caching), [406 and 415](card:headers-content-negotiation), [412](card:conditional-requests), [429](card:rate-limiting); 502, 503, 504: [compare](compare:502-vs-503-vs-504).
- The body's shape is one [error format](card:error-responses) for all codes.

## Interview Qs

### Invalid amount: 400 or 422?

Both are defensible. 400 covers any client error; 422 (RFC 9110, formerly WebDAV's "Unprocessable Entity") means the syntax is fine but the content cannot be processed. Pick one for validation errors and use it everywhere.

### Why is 301 or 302 risky for a POST?

Clients may change a redirected POST into a GET, for historical reasons. Use 307 (temporary) or 308 (permanent): they must keep the method.
