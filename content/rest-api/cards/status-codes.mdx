## What it is

A status code is the three-digit number in the response's [status line](card:http-request-response) that tells the client how its request went. The first digit is the class: 1xx is an interim message, 2xx success, 3xx go somewhere else, 4xx the client made a mistake and 5xx the server failed. The client acts on the number; the short reason phrase after it, such as `Created`, is only for people.

## Why it exists

A client must react without reading every body: show the result, ask the user to log in again, fix the input, try later or give up. If an API returned 200 for everything with an error hidden in the body, every client would need custom parsing. Generic tools such as monitors, gateways and retry libraries could not tell success from failure either. Standard codes let all of them react the same way.

## How it works

| Code | Means | Payment case |
|---|---|---|
| 200 OK | worked, body follows | GET PAY101 |
| 201 Created | new resource made | POST created PAY101 |
| 204 No Content | worked, no body | DELETE a saved card |
| 400 Bad Request | malformed request | broken JSON |
| 401 Unauthorized | no valid credentials | expired token |
| 403 Forbidden | known caller, not allowed | agent without refund rights |
| 404 Not Found | no such resource | GET PAY999 |
| 405 Method Not Allowed | method not supported here | PUT on /api/payments |
| 409 Conflict | clashes with current state | refund a FAILED payment |
| 422 Unprocessable Content | valid JSON, wrong meaning | amount -500 |
| 500 Internal Server Error | unexpected server failure | a bug throws an exception |

How a client reacts to a response:

1. It reads the first digit. A code it does not know, such as 471, counts as the x00 of its class, here 400.
2. On 2xx it uses the body; after a 201 it can also read the new resource's address from `Location`.
3. On 3xx it follows the `Location` header to the new address.
4. On 4xx it must change something first, such as logging in or fixing the input. The same request sent again usually fails again.
5. On 5xx the server failed, so the same request may work later, and a careful retry can make sense.

So the class tells the client what to do next, even before it reads the body.

## Example

Reading a payment that the bank declined:

```text
GET /api/payments/PAY101

HTTP/1.1 200 OK
Content-Type: application/json

{"paymentId": "PAY101", "status": "FAILED", "reason": "BANK_DECLINED"}
```

What to notice:

- `200` means the read worked. The bank's decline is a business result, so it lives in the body as `status: FAILED`.
- A `500` here would tell monitors that the server broke and tell retry libraries to try again, which would be wrong on both counts.
- When the decline happens during `POST /api/payments`, a 4xx is also fine; Stripe answers a declined card with a 4xx. Either way, it is not a 5xx.

## Rules and defaults

- **401 (RFC 9110):** must include a `WWW-Authenticate` header that says how to authenticate.
- **405 (RFC 9110):** must include an `Allow` header listing the methods the URL supports.
- **201:** the new resource is named by the `Location` header, or by the request URL when there is none.
- **Hiding a resource:** a server may answer 404 instead of 403, so a caller cannot learn that the resource exists.
- **Codes owned by later concepts:** [202](card:long-running-operations), [304](card:http-caching), [406 and 415](card:headers-content-negotiation), [412](card:conditional-requests) and [429](card:rate-limiting).

## Not to be confused with

401 means the server does not know who you are, because the credentials are missing or invalid. 403 means it knows who you are, but you may not do this. 502, 503 and 504 are server-side failures: a bad reply from the server behind a gateway, a server too busy or under maintenance, and a gateway that gave up waiting. Rule: 401 = log in, 403 = not allowed; 502 = bad reply, 503 = not now, 504 = no reply in time.

## Common mistakes

- **"Return 200 with an error inside the body."** Clients, monitors and retry tools then see success. Use the code that matches the outcome, and put the details in the [error body](card:error-responses).

## Interview Qs

### Invalid amount: 400 or 422?

Both are defensible. 400 covers any client error. 422 (RFC 9110, formerly WebDAV's "Unprocessable Entity") means the syntax is fine but the content cannot be processed, such as an amount of -500. Pick one for validation errors and use it everywhere in the API.

### Why is 301 or 302 risky for a POST?

For historical reasons, clients may turn a redirected POST into a GET, so the body is lost. Use 307 (temporary) or 308 (permanent), which RFC 9110 names for this case: with them the client keeps the method and the body when it follows the redirect.

### What should a client do with a status code it does not know?

Treat it as the x00 code of its class, as RFC 9110 requires: an unknown 471 is handled as 400 and an unknown 599 as 500. This is why the first digit must always match the meaning.
