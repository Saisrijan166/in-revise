## Why it exists

Two support agents edit the note on PAY101 at the same time. Without a check, the second save erases the first without anyone noticing.

## How it works

<Steps label="Two agents edit PAY101">
  <Step title="Both read">Asha and Ravi GET PAY101 and receive `ETag: "v3"`.</Step>
  <Step title="Asha saves">PATCH with `If-Match: "v3"` matches: 200, the ETag becomes `"v4"`.</Step>
  <Step title="Ravi saves">PATCH with `If-Match: "v3"` no longer matches: 412, nothing changes.</Step>
  <Step title="Ravi retries">He GETs `"v4"`, reapplies his edit and sends If-Match `"v4"`.</Step>
</Steps>

- In JPA, a `@Version` column does the same check in the database; its value makes a good ETag.
- If the same change already seems applied (a lost reply), the server may answer 2xx instead of 412.
- ETags and 304 for reads: [HTTP caching](card:http-caching).

## Example

```text
PATCH /api/payments/PAY101
If-Match: "v3"
Content-Type: application/merge-patch+json

{"note": "Rent for October"}

HTTP/1.1 412 Precondition Failed
```

## Interview Qs

### 409 or 412 for a version clash?

412 when a precondition header such as If-Match fails. 409 when the body itself conflicts with the current state, for example an old version number inside the JSON (RFC 9110 gives this example for PUT).

### Why must If-Match use a strong ETag?

A weak ETag (W/"v3") only says two versions are equivalent, not identical. If-Match must block any change, so RFC 9110 requires strong comparison.
