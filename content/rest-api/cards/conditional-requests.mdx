## What it is

A conditional request is a request the server carries out only if a condition about the resource's current version is true. For a write, the client sends the [ETag](card:http-caching) it read in the `If-Match` header, meaning "apply this change only if the payment is still at this version". This is called optimistic concurrency: nobody holds a lock while a user edits, and a clash is detected only when the write arrives.

## Why it exists

Two support agents, Asha and Ravi, open payment PAY101 at the same time to edit its note. Asha saves first; Ravi saves a minute later. Without a check, Ravi's save replaces the whole note, and Asha's change disappears without anyone noticing. This is the lost update problem. With `If-Match`, Ravi's save is refused because the payment changed after he read it, so he sees Asha's note before writing his own.

1. Asha and Ravi both read PAY101 and receive `ETag: "v3"`.
2. Asha sends her PATCH with `If-Match: "v3"`. It matches the current version, so the server saves it, and the ETag becomes `"v4"`.
3. Ravi sends his PATCH with `If-Match: "v3"`. The server checks the condition before doing anything, finds `"v4"`, and answers 412 Precondition Failed without writing.
4. Ravi's app reads PAY101 again, shows Asha's note, and sends his edit with `If-Match: "v4"`.

So the version travels with the write, and the server compares it at the last moment.

## Example

Ravi's refused write on the wire:

```text
PATCH /api/payments/PAY101
If-Match: "v3"
Content-Type: application/merge-patch+json

{"note": "Rent for October"}

HTTP/1.1 412 Precondition Failed
```

What to notice:

- `If-Match: "v3"` is the version Ravi read. The server compares it with the current ETag before it applies the change.
- 412 means nothing was written, so it is always safe for the client to re-read and try again.
- Remove the `If-Match` line and the same PATCH succeeds, erasing Asha's note. A server that answers such writes with 428 Precondition Required forces every client to send the header.

## Rules and defaults

- **Strong comparison (RFC 9110):** `If-Match` must use it, so a weak ETag (`W/"v3"`) never matches.
- **`If-Match: *`:** true only if the resource exists; useful to stop a PUT from creating a new one.
- **Checked first:** the server evaluates `If-Match` before performing the method and must not perform it when the condition is false.
- **Already applied:** if a failed condition is due to the same change having already succeeded, such as a lost reply, the server may answer 2xx instead of 412.
- **In the database:** with JPA, Java's standard API for mapping objects to tables, a `@Version` column makes the same check on UPDATE; its value makes a good ETag.

## Not to be confused with

`If-Match` guards writes: it uses strong comparison, and a mismatch gives 412. `If-None-Match` serves reads in [caching](card:http-caching): it accepts weak ETags, and a match gives 304. Rule: If-Match = "write only if unchanged"; If-None-Match = "send the body only if changed".

## Interview Qs

### How do you prevent lost updates in a REST API?

Return an ETag with every GET and require `If-Match` on PUT and PATCH, answering 428 when it is missing. If the ETag no longer matches, reply 412 and write nothing; the client re-reads and retries. Inside the service, a JPA `@Version` column gives the same check in the database.

### 409 or 412 for a version clash?

412 when a precondition header such as `If-Match` fails. 409 when the body itself conflicts with the current state, for example when the JSON carries an old version number. RFC 9110 gives that second case as an example of 409 for PUT.

### Why must If-Match use a strong ETag?

A weak ETag (`W/"v3"`) only says two versions are equivalent for practical use, not byte-for-byte identical. If-Match must block a write after any change at all, so RFC 9110 requires strong comparison.
