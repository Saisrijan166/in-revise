## Why it exists

Services and networks fail briefly. A timeout frees the waiting thread; a careful retry turns a blip into success.

## How it works

| Failure | Retry? |
| --- | --- |
| Connection reset, timeout, 408 | Yes, if idempotent or keyed |
| 429, 503 | Yes, after `Retry-After` or a backoff |
| 500, 502, 504 | Yes, a few times |
| 400, 401, 403, 404, 422 | No: the same request fails again |

- Set both a connect and a read timeout; Spring setup is in [HTTP clients](card:rest-clients).
- Base the timeout on the callee's latency, say its p99.9.
- A dependency that keeps failing needs a breaker, not more retries: [Retry vs Circuit Breaker](compare:retry-vs-circuit-breaker).

## Example

```java
// Full jitter over a capped exponential; retry = 0, 1, 2 ...
Duration backoff(int retry) {
    long maxMs = Math.min(20_000, 100L << retry);   // base 100 ms, cap 20 s
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(maxMs + 1));
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Request timeout | none: `send()` blocks forever | JDK `HttpClient`, Java 25 |
| Attempts | 3 in total, 20 s wait cap | AWS SDKs, standard mode |

## Interview Qs

### Which failures do you retry?

Connection errors, timeouts, 408, 429, 500, 502, 503 and 504, for idempotent or keyed requests only. Never 400, 401, 403, 404 or 422.

### Why add jitter to exponential backoff?

Clients that failed together retry together, in waves that knock the recovering service over. A random wait spreads them out; AWS SDKs use full jitter.

### Connect timeout vs read timeout?

Connect timeout limits opening a new connection; read timeout limits waiting for data on an open one. A slow payment gateway trips the read timeout.
