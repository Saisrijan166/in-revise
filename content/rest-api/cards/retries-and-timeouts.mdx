## What it is

A timeout is the longest time a caller waits for another service before it gives up. A retry sends the same request again after a failure that is likely to pass, such as a dropped connection or a 503. Backoff means each retry waits longer than the one before, and jitter makes each wait a random amount, so many clients do not retry at the same moment.

## Why it exists

Without a timeout, a call to a hung payment gateway can wait forever, holding a thread, until the server has no threads left. Without retries, one dropped packet fails a customer's payment. Careless retries hurt too: thousands of clients retrying at once hit a struggling service in waves, and retries at every layer multiply the load. So you put a limit on every call, and retry only the right failures, a few times, with backoff and jitter.

## How it works

| Failure | Retry? |
| --- | --- |
| Connection reset, timeout, 408 | Yes, if idempotent or keyed |
| 429, 503 | Yes, after `Retry-After` or a backoff |
| 500, 502, 504 | Yes, a few times |
| 400, 401, 403, 404, 422 | No: the same request fails again |

1. Before calling, you set a connect timeout (for opening the connection) and a request timeout (for waiting on the answer). Base them on the other service's real latency, such as its p99.9: the time within which 99.9% of its calls finish.
2. The call fails. You classify the failure with the table: transient, so worth a retry, or permanent.
3. You check that repeating is safe: the method is idempotent, or the request carries the same [idempotency key](card:idempotency-keys).
4. You wait: the `Retry-After` value if the server sent one, otherwise a random time between 0 and a limit that doubles each retry, up to a cap.
5. You stop after a few attempts, three in total for example, and return the error.

So the key is: retry at one layer only. Three tries at each of five layers is 3⁵ = 243 calls to the bottom service.

## Example

The payment service calls the gateway with both timeouts and the same key on every attempt, and computes its waits with full jitter.

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(2))           // limit for opening a new connection
        .build();
HttpRequest request = HttpRequest.newBuilder(URI.create("https://gateway.example/charges"))
        .timeout(Duration.ofSeconds(5))                  // limit for waiting on the response
        .header("Idempotency-Key", "order-789-payment")  // same key on every attempt
        .POST(HttpRequest.BodyPublishers.ofString(body))
        .build();

static Duration backoff(int retry) {                     // retry = 0, 1, 2 ...
    long limitMs = Math.min(20_000, 100L << Math.min(retry, 8));  // 100, 200, 400 ... 20 s
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(limitMs + 1));
}
```

What to notice:

- Remove `.timeout(...)` and `send()` waits forever for a response; that is the JDK default.
- The connect timeout applies only when a new connection is opened. A reused connection is limited by the request timeout alone.
- `backoff` returns a random wait between 0 and the limit. In a test run the limits were 100, 200, 400 … 12,800 ms, then 20,000 ms from the ninth retry; the actual waits were random values below them.
- The key never changes between attempts, so a retry after a lost response cannot charge twice.

## Rules and defaults

- **JDK HttpClient (Java 25):** no request timeout is set by default, so `send()` can block forever. A request timeout throws `HttpTimeoutException`; a connect timeout throws `HttpConnectTimeoutException`.
- **AWS SDKs, standard mode:** 3 attempts in total (1 call and 2 retries), full jitter, and no single wait longer than 20 seconds. A retry quota, a budget of tokens that each retry spends and each success refills, stops retries when many calls fail.
- **Retry-After:** RFC 9110 defines it for 503 and redirects; RFC 6585 allows it on a 429 from [rate limiting](card:rate-limiting). When it is present, wait at least that long.
- **One layer:** the Amazon Builders' Library advises retrying at a single point in the call stack.

## Not to be confused with

A retry sends the call again soon, betting that the fault will pass in milliseconds. A circuit breaker stops sending calls to a dependency that keeps failing, and fails them at once for a while. Rule: retry for blips, circuit breaker for outages, and no retries while the breaker is open.

## Interview Qs

### Which failures do you retry?

Connection errors, timeouts, 408, 429, 500, 502, 503 and 504, and only for idempotent requests or ones with an idempotency key. Never 400, 401, 403, 404 or 422: the same request would fail again the same way, so a retry only adds load.

### Why add jitter to exponential backoff?

Clients that failed together would retry together, in waves that knock the recovering service over again. A random wait between 0 and the backoff limit spreads them out. AWS SDKs use full jitter.

### Connect timeout vs read timeout?

A connect timeout limits opening a new connection; it trips when the server is unreachable. A read timeout limits waiting for data on an open connection; a slow payment gateway trips it. The JDK HttpClient has no separate read timeout; its request timeout limits the wait for the response. Either one is an unknown outcome: the server may have done the work.
