## What it is

A header is one `Name: value` line in a request or response that describes the message instead of carrying its data. Content negotiation is how the client and the server agree on the format of a [representation](card:resources-and-uris). The client lists the formats it can read in the `Accept` header, and the server picks one and names it in `Content-Type`. A format is written as a media type, such as `application/json`.

## Why it exists

A body is only bytes, and one payment can be sent as JSON or XML. Without a label, the receiver must guess how to read the bytes. Without a way to ask, the client gets whatever the server prefers. Headers carry the label and the request, and other facts such as credentials, outside the body. So the body stays pure data, and both sides know how to read it.

## How it works

  B -- no --> E1[415 Unsupported Media Type]
  B -- yes --> A{Can produce an accepted type?}
  A -- no --> E2[406, or send the default type]
  A -- yes --> OK["201 + Content-Type + Vary: Accept"]`}
/>

1. The client sends `Content-Type` to label its body, and `Accept` to list the formats it can read, best first.
2. The server checks whether it can read the body's media type. If not, it answers 415 Unsupported Media Type.
3. It picks the best type from `Accept` that it can produce. If there is none, it answers 406 Not Acceptable, or RFC 9110 lets it send its default type anyway.
4. It sends the body with `Content-Type` naming the chosen type, plus `Vary: Accept`, which tells caches that the reply depends on the `Accept` header.

So the request labels what it sends and asks for what it wants, and the response labels what it actually sent.

## Example

A client that prefers JSON but can also read XML:

```text
GET /api/payments/PAY101
Accept: application/json, application/xml;q=0.5

HTTP/1.1 200 OK
Content-Type: application/json
Vary: Accept
```

What to notice:

- `application/json` has no `q`, so its weight is 1. XML has 0.5, so the server sends it only if it cannot send JSON.
- The response's `Content-Type` is what the client parses by; it is the server's final choice.
- Without `Vary: Accept`, a shared cache could hand this JSON copy to a later client that accepts only XML.

## Rules and defaults

- **Case:** header names are case-insensitive (RFC 9110); HTTP/2 sends them in lower case (RFC 9113).
- **Media type:** `type/subtype` plus optional parameters, such as `text/html; charset=utf-8`.
- **No Accept header:** the client has no preference, so any type is fine.
- **Other common headers:** `Authorization` carries credentials ([authentication](card:authentication-methods)), `Location` points to a resource, `Cookie` and `Set-Cookie` carry cookies, and `Cache-Control` controls [caching](card:http-caching).
- **Custom names (RFC 6648, 2012):** new header names should not start with `X-`; old ones such as `X-Request-ID` still work.

## Not to be confused with

`Content-Type` describes the body that travels in the same message, so it appears in requests that have a body and in responses. `Accept` is sent in requests and asks for the format of the response; a 415 reply may also carry it, to list the body formats the server takes. Rule: Content-Type = "this is what I sent"; Accept = "this is what I can read".

## Interview Qs

### What is content negotiation?

The client states which formats it can read in `Accept`, with optional q weights, and the server chooses the best one it can produce and labels the body with `Content-Type`. If nothing matches, it answers 406 or sends its default type. `Vary: Accept` keeps caches from mixing formats.

### Why should a new header not start with X-?

`X-` names often spread into wide use. Making one a standard then means renaming it or living with both names forever. RFC 6648 (2012) therefore deprecates the prefix for new names; existing ones like `X-Request-ID` still work.
