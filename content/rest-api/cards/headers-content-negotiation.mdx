## Why it exists

One payment can be sent as JSON or XML. Headers let client and server agree on the format, and carry other data (credentials, links) outside the body.

## How it works

<Mermaid
  alt="The client sends POST /api/payments with Content-Type application/json and Accept application/json. If the server cannot read the body's media type it replies 415 Unsupported Media Type. If it can produce no type the client accepts, it replies 406 Not Acceptable or sends its default type. Otherwise it replies 201 with Content-Type application/json and Vary: Accept."
  chart={`flowchart LR
  C([Client]) -- "Content-Type + Accept" --> B{Can read the body type?}
  B -- no --> E1[415 Unsupported Media Type]
  B -- yes --> A{Can produce an accepted type?}
  A -- no --> E2[406, or send the default type]
  A -- yes --> OK["201 + Content-Type + Vary: Accept"]`}
/>

- RFC 9110 lets the server ignore Accept and send its default instead of 406.
- Credentials go in Authorization ([how](card:authentication-methods)); request IDs in [observability](card:observability-for-apis); caching headers in [HTTP caching](card:http-caching).

## Example

```text
GET /api/payments/PAY101
Accept: application/json, application/xml;q=0.5

HTTP/1.1 200 OK
Content-Type: application/json
Vary: Accept
```

## Interview Qs

### What happens if a client posts XML to a JSON-only API?

The server replies 415 Unsupported Media Type. It can add an Accept response header listing the types it does accept.

### Why should a new header not start with X-?

"X-" names leak into wide use; making one a standard then means a rename or living with both names. RFC 6648 (2012) deprecates the prefix for new names; existing ones like X-Request-ID still work.
