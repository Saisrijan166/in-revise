## What it is

A JSON Web Token (JWT) is a compact string that carries facts about the caller, called claims, such as the user ID and the expiry time. It has three parts joined by dots: a header that names the signing algorithm, a payload with the claims, and a signature. The login server signs the token with its key. An API that receives it as a [bearer token](card:authentication-methods) checks the signature before it trusts any claim.

## Why it exists

With a session ID, every API must look the session up in a shared store on each request: one more network call, and one more system that can fail. A JWT carries the claims itself, and the signature proves that the login server issued them. So the payment API checks the token on its own with the login server's public key, a key that can check signatures but not create them, and needs no lookup, which fits a [stateless](card:statelessness) API. The cost: a token cannot be cancelled before it expires.

## How it works

1. The API takes the token from `Authorization: Bearer` and splits it at the dots into header, payload and signature.
2. It reads `alg` from the header but accepts only the algorithm it expects, such as RS256. A token that says `alg: none`, or names any other algorithm, is rejected (RFC 8725).
3. It verifies the signature with the issuer's public key (RS256) or the shared secret (HS256). If any byte of the header or payload was changed, this check fails.
4. It checks the time: now must be before `exp` (expiry) and not before `nbf` (not before).
5. It checks who: `iss` (issuer) must be the trusted login server, and `aud` (audience) must name this API.
6. Only then does it trust `sub` (the caller) and `scope` (what the caller may do) for authorisation. Any failed check gives 401.

So the key is: decoding is free for anyone; trust comes only from the checks.

## Example

The payment API receives this token. The code reads its header and payload the way any holder could, without a key.

```java
String token = "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9"           // header
    + ".eyJpc3MiOiJodHRwczovL2F1dGguc2hvcC5leGFtcGxlIiwic3ViIjoiY3VzdG9tZXItNDIiLCJhdWQiOiJwYXltZW50cy1hcGkiLCJleHAiOjE3OTI0ODQxMDB9"
    + ".c2lnbmF0dXJl";                                        // signature (fake here)
String[] parts = token.split("\\.");                          // header . payload . signature
Base64.Decoder decoder = Base64.getUrlDecoder();              // no key needed
System.out.println(new String(decoder.decode(parts[0])));
System.out.println(new String(decoder.decode(parts[1])));
```

```text output
{"alg":"RS256","typ":"JWT"}
{"iss":"https://auth.shop.example","sub":"customer-42","aud":"payments-api","exp":1792484100}
```

What to notice:

- `Base64.getUrlDecoder()` with no key reads every claim, so a card number, password or phone number in the payload is visible to anyone who holds the token.
- The signature here is fake, and decoding still works. Reading a token says nothing about whether it is genuine; only the signature check in step 3 does.
- `exp` is a Unix time in seconds (20-10-2026, 08:15 UTC). After it, the API must reject the token even though the signature is still correct.

## Rules and defaults

- **Signed is not encrypted:** a normal JWT is a JWS (JSON Web Signature): tamper-evident but readable. Hiding the claims needs a JWE (JSON Web Encryption).
- **HS256 vs RS256 (RFC 7518):** HS256 signs and verifies with one shared secret, so every API that can verify could also create tokens. RS256 signs with a private key and verifies with a public key, so many APIs can verify while only the login server signs.
- **Registered claims:** `iss`, `sub`, `aud`, `exp`, `nbf`, `iat` and `jti` (a unique token ID) are defined in RFC 7519 section 4.1. All are optional in the spec, so your API must require the ones it checks.
- **Expiry:** RFC 7519 says a token MUST NOT be accepted after `exp`. There is no built-in revoke, so keep access tokens short-lived.
- **Early logout:** revoke the refresh token (next concept), or keep a denylist of `jti` values until they expire. A denylist brings server state back.

## Not to be confused with

A session cookie holds only a random ID, and the server looks the session up in its store on every request. A JWT holds the claims themselves, signed, so the server needs no lookup. Rule: session = state on the server, easy to delete; JWT = state in the token, valid until `exp`.

## Interview Qs

### Can you decode a JWT without the key?

Yes. The header and payload are Base64url-encoded JSON, so anyone can read them. The key is needed only to create or verify the signature. That is why the payload must hold no secrets or personal data, unless you use an encrypted JWE.

### How do you log out a user who holds a JWT?

You cannot delete a self-contained token. Keep access tokens short-lived and revoke the refresh token, so no new access token is issued. To stop one token at once, deny its `jti` until it expires, which means a lookup on every request again.

### What is the alg none attack?

An attacker changes the header to `alg: none` and removes the signature. A careless library reads the header, skips verification and accepts the forged claims. The fix is to verify only with an allow-list of algorithms you chose, never the one the token names (RFC 8725).

### HS256 or RS256 for many microservices?

RS256. Only the login server holds the private key; every service verifies with the public key, so a hacked service cannot mint tokens. With HS256 every verifier holds the shared secret and could sign tokens itself.
