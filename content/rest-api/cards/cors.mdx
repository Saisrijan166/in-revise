## What it is

An origin is the scheme, host and port of a web page, such as `https://shop.example`. By default a browser lets a page read responses only from its own origin; this rule is the same-origin policy. Cross-Origin Resource Sharing (CORS) is a set of response headers with which an API, such as `https://api.shop.example`, tells the browser: "pages from these other origins may read my responses".

## Why it exists

The shop's web app runs on `shop.example` but calls the payment API on `api.shop.example`, a different origin. Without CORS headers, the browser blocks the page from reading the answer, and checkout breaks. The same-origin policy itself must stay, because it stops any site you visit from reading your bank's API with your cookies. CORS lets the API open the door only for origins it trusts.

1. The page calls the API with `fetch`, and the browser adds an `Origin: https://shop.example` header.
2. If the request is not simple, for example a POST with a JSON body, a PUT or DELETE, or one with an `Authorization` header, the browser first sends an `OPTIONS` preflight asking which method and headers are allowed. A preflight never carries cookies.
3. The API answers with `Access-Control-Allow-Origin` and the allowed methods and headers. If they do not match, the browser stops and never sends the real request.
4. The browser sends the real request and checks `Access-Control-Allow-Origin` again on the response before it lets the page read it.

So the key is: the API only declares the rules; the browser enforces them.

## Example

This is the preflight the browser sends before the checkout page's `POST /api/payments`, and the API's answer.

```text
OPTIONS /api/payments HTTP/1.1
Origin: https://shop.example
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.example
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 3600
```

What to notice:

- The `Access-Control-Request-*` lines are the browser asking; the `Access-Control-Allow-*` lines are the API answering. `authorization` is listed because the page sends a bearer token.
- `Allow-Origin` names exactly `https://shop.example`. A page on `evil.example` gets no matching header, so the browser hides the response from it.
- `Max-Age: 3600` lets the browser reuse this answer for an hour. Without the header it is cached for only 5 seconds, so almost every call would cost an extra `OPTIONS` round trip.

## Rules and defaults

- **Simple requests skip the preflight:** GET, HEAD or POST with only safelisted headers and a `Content-Type` of `application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain` (MDN). The browser still checks the response headers.
- **Credentials:** to send cookies, the page sets `credentials: "include"`, the API returns `Access-Control-Allow-Credentials: true`, and `Allow-Origin` must be one exact origin, not `*`.
- **Spring `@CrossOrigin` (Spring Framework 7.0):** allows all origins, all headers and the methods the handler is mapped to; credentials are off and max age is 30 minutes. Global `addCorsMappings` allows only GET, HEAD and POST by default. Name your real origins in production.
- **With Spring Security:** CORS must be processed before security, because the preflight carries no credentials and would otherwise be rejected as unauthenticated. Enable it with `http.cors(...)` (Spring Security 7.1).

## Not to be confused with

CORS controls whether a page from another origin may read your API's responses. CSRF (cross-site request forgery) is an attack in which another site makes the user's browser send a request that carries the user's cookies automatically, such as a hidden form that posts a payment. Rule: CORS controls who may read; CSRF protection, such as CSRF tokens and SameSite cookies, guards writes that ride on cookies.

## Common mistakes

- **"A CORS error means the server rejected the request."** A simple request, such as a form-style POST, has no preflight, so it reaches the server and may change data; the browser only hides the answer from the page.
- **"Allow every origin to make the error go away."** `*` exposes the API's responses to every website. List the origins of your own apps instead.

## Interview Qs

### Why does my API work from Postman but fail in the browser?

Postman is not a browser, so it does not apply the same-origin policy. The browser blocks the response because the API did not send a matching `Access-Control-Allow-Origin`, or because the preflight failed: a method or header the page uses was not in the allowed list.

### Is Access-Control-Allow-Origin: * safe?

Only for public data without credentials. Any website can then read the responses, and browsers refuse `*` for requests that send cookies or HTTP authentication. For a private API, name the exact origins.

### How do you enable CORS in Spring Boot?

Put `@CrossOrigin(origins = "https://shop.example")` on a controller or method, or set global rules in a `WebMvcConfigurer` with `addCorsMappings`. With Spring Security, also call `http.cors(...)`, so the preflight is answered before authentication runs.
