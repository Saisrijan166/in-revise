## What it is

A REST controller is the Java class in a Spring Boot app that receives HTTP requests and returns responses. Spring Boot is a Java framework that runs a web server inside your app and creates your main objects for you. You give it instructions with annotations, labels starting with `@` that Spring reads at startup. `@RestController` says "this class handles requests, and what its methods return is the response body". A mapping annotation on each method says which path and HTTP method it handles.

## Why it exists

Without a framework you would read the raw request yourself: parse the request line, compare the path and method with every endpoint, turn the JSON body into an object, then write the status line, headers and JSON back. Every endpoint would repeat that code. With a controller you write one plain Java method per endpoint. Spring does the routing and the JSON conversion, so your method only deals with Java objects.

1. At startup, Spring finds every `@RestController` class and records each mapping, such as GET `/api/payments/{id}` → `get()`.
2. A request arrives. The DispatcherServlet, Spring MVC's single entry point for all requests, looks up the method whose path and HTTP method both match.
3. Spring fills the method's parameters from the request, here `id = "PAY101"`. The next concept, [binding](card:request-binding-validation), covers this.
4. The method calls the service and returns a `PaymentResponse` object.
5. An HttpMessageConverter, Spring's converter between Java objects and body formats, writes that object into the body. For JSON it uses Jackson, a JSON library, and the status is 200 unless the method sets another.

So you only declare the mappings; Spring does the routing and the conversion.

## Example

The payment API's controller reads one payment. `PaymentResponse` is a small data class with the fields the client sees.

```java
@RestController                          // return values go into the response body
@RequestMapping("/api/payments")         // shared path for every method below
class PaymentController {
    private final PaymentService service;

    PaymentController(PaymentService service) { this.service = service; }

    @GetMapping("/{id}")                 // GET /api/payments/PAY101
    PaymentResponse get(@PathVariable String id) {
        return service.find(id);         // Jackson writes it as JSON, status 200
    }
}
```

After payment PAY101 has been created, a client reads it:

```bash
curl -s http://localhost:8080/api/payments/PAY101
```

```text output
{"paymentId":"PAY101","status":"PENDING","amount":500}
```

What to notice:

- The full path is the class path plus the method path: `/api/payments` + `/{id}`.
- The method returns a Java object, not JSON text. Jackson turned its three fields into the JSON keys.
- Spring creates the controller and passes the `PaymentService` into its constructor, so the controller never builds its own service.
- Swap `@RestController` for plain `@Controller` and Spring would treat the return value as the name of an HTML page to render.

## Rules and defaults

- **One HTTP method per mapping:** `@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping` and `@DeleteMapping` each match one method. A `@RequestMapping` without a `method` attribute matches all of them, so use it only on the class, for the shared path.
- **No matching method:** a known path with an unmapped HTTP method gets 405 Method Not Allowed, with an `Allow` header listing the mapped methods. An unknown path gets 404.
- **JSON (Spring Boot 4.x):** Jackson 3, package `tools.jackson`, is the default; Spring Boot 3.x used Jackson 2.
- **Port:** the embedded server listens on 8080 by default; `server.port` changes it.

## Not to be confused with

`@Controller` marks a class whose methods return a view name, which a template engine turns into an HTML page. `@RestController` is `@Controller` plus `@ResponseBody`, so every method's return value is the response body itself. Rule: HTML pages → `@Controller`; a JSON API → `@RestController`.

## Common mistakes

- **"The controller is the place for the payment rules."** Rules in a controller cannot be reused by a scheduled job or a message listener, and are hard to unit-test. The controller reads input, calls the service and picks the status; the service holds the rules.

## Interview Qs

### @RequestMapping vs @GetMapping?

`@GetMapping` is a shortcut for `@RequestMapping(method = GET)`. A plain `@RequestMapping` matches every HTTP method, so I use it on the class for the shared path, and the shortcuts on methods so each endpoint answers only its own method.

### How does a returned object become JSON?

`@RestController` includes `@ResponseBody`, so Spring passes the return value to an HttpMessageConverter that can write the media type the client accepts. For JSON that is the Jackson converter; in Spring Boot 4 it uses Jackson 3.

### What happens when a request reaches a Spring Boot app?

The embedded server hands it to the DispatcherServlet. It finds the controller method by path and HTTP method, binds the parameters, calls the method, and writes the return value through a message converter. No match on the path gives 404; a match on the path but not the method gives 405.

### Why keep the controller thin?

The controller only translates HTTP: bind input, call the service, choose the status. Business rules in a service can be reused by other callers, such as a batch job, and unit-tested without any HTTP.
