## Why it exists

In HTTP the client always speaks first. A payment screen still has to learn when PENDING turns into SUCCESS.

## How it works

<Compare id="polling-vs-long-polling-vs-sse-vs-websocket" />

- On reconnect, SSE sends `Last-Event-ID`, so the server can resume the stream.
- Server-to-server pushes are [webhooks](card:webhooks): the gateway calls your URL.

## Example

```text
GET /api/payments/PAY101/events
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream

event: status
data: {"paymentId":"PAY101","status":"SUCCESS"}
```

## Interview Qs

### SSE or WebSocket?

SSE when only the server sends: plain HTTP, automatic reconnect, simple. WebSocket when both sides send often with low delay, such as chat or trading screens; restrictive proxies may block it.

### How does long polling work?

The client sends a request; the server holds it open until there is news or a timeout, then replies. The client sends the next request at once.
