## What it is

A real-time update is the server telling the client that something changed, such as PAY101 moving from PENDING to SUCCESS, without the user pressing refresh. Plain HTTP cannot do this, because the client always sends the request first. Polling works around it by asking again and again. Server-Sent Events (SSE) keep one response open so the server can write events into it. A WebSocket turns the connection into a two-way channel.

## Why it exists

After the customer pays, the checkout page must show the result, which arrives seconds later from the gateway. Asking `GET /api/payments/PAY101` every second wastes requests, since most answers say "still PENDING", and the result can still show up to a second late. Keeping a connection open lets the server send the result the moment it knows. The choice between SSE and WebSocket depends on whether the page also needs to send.

## How it works

<Compare id="polling-vs-long-polling-vs-sse-vs-websocket" />

1. The page runs `new EventSource('/api/payments/PAY101/events')`, which sends a GET with `Accept: text/event-stream`.
2. The server answers 200 with `Content-Type: text/event-stream` and keeps the response open.
3. When the gateway's [webhook](card:webhooks) says the payment succeeded, the server writes one event: `id`, `event` and `data` lines, ended by a blank line.
4. If the connection drops, the browser reconnects by itself and sends a `Last-Event-ID` header with the last id it got, so the server can resume.
5. When the status is final, the page calls `close()`, or the server ends the stream and answers the next reconnect with 204 No Content, which stops further reconnects.

## Example

A Spring MVC endpoint that streams the final status of a payment:

```java
@RestController class PaymentEventsController {
    private final Map<String, SseEmitter> open = new ConcurrentHashMap<>();
    @GetMapping(path = "/api/payments/{id}/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    SseEmitter events(@PathVariable String id) {
        SseEmitter emitter = new SseEmitter(300_000L);          // time out after 5 minutes
        open.put(id, emitter);
        return emitter;                                         // the response stays open
    }
    void onFinalStatus(String id, String status) throws IOException {   // called by the webhook handler
        SseEmitter emitter = open.remove(id);
        if (emitter == null) return;                            // nobody is watching
        emitter.send(SseEmitter.event().id("1").name("status").data(status));
        emitter.complete();                                     // end the stream
    }
}
```

What a client received, from a real run with `curl -N` while the webhook handler called `onFinalStatus("PAY101", "SUCCESS")`:

```text
HTTP/1.1 200
Content-Type: text/event-stream
Transfer-Encoding: chunked
Date: Wed, 21 Oct 2026 16:46:31 GMT

id:1
event:status
data:SUCCESS
```

What to notice:

- Returning an `SseEmitter` tells Spring MVC to keep the response open after the method returns. Any later thread, here the webhook handler, can call `send()`.
- Each event becomes `id`, `event` and `data` lines plus a blank line. The browser fires a `status` event, and remembers id `1` for `Last-Event-ID`.
- `300_000L` is the timeout in milliseconds. Without it, the timeout configured for Spring MVC async requests applies, or else the server's own default.
- `complete()` ends the response once the status is final. The browser would then reconnect, so a full version answers requests for a finished payment with 204 No Content, which stops it.

## Rules and defaults

- **SSE format:** UTF-8 text with the fields `event`, `data`, `id` and `retry`; a blank line ends each event, and `retry` sets the reconnect wait in milliseconds.
- **Stopping reconnects:** answer a reconnect with 204 No Content, or call `close()` on the client; otherwise the browser keeps reconnecting after each drop.
- **Auth for SSE:** `EventSource` accepts only a `withCredentials` option, so it cannot send an `Authorization` header. Use a cookie, or read the stream with `fetch()` if you need a bearer token.
- **WebSocket handshake:** a GET with `Upgrade: websocket` is answered with `101 Switching Protocols`. `ws://` uses port 80 by default; use `wss://`, which runs over TLS on port 443.
- **Spring WebSocket:** implement a `WebSocketHandler`, put `@EnableWebSocket` on a configuration class and map the handler in `WebSocketConfigurer.registerWebSocketHandlers`.

## Not to be confused with

SSE pushes events to a browser over a connection the browser opened and keeps open. A [webhook](card:webhooks) is one server calling another server's URL with an HTTP POST when something happens, such as the gateway notifying your API. Rule: a browser waiting for news uses SSE; a server being notified uses a webhook. A payment usually uses both, one after the other.

## Interview Qs

### SSE or WebSocket?

SSE when only the server sends: it is plain HTTP, and the browser reconnects by itself and resumes with `Last-Event-ID`. WebSocket when both sides send often with low delay, such as chat or trading screens; it needs its own message handling and some restrictive proxies block it.

### How does long polling work?

The client sends a request, and the server holds it open until there is news or a timeout, then replies. The client sends the next request at once. It gives near-instant updates over plain HTTP, but each message costs a full request with headers.

### How does the checkout page learn that the payment succeeded?

The gateway sends a signed webhook to our server. Our server updates PAY101 to SUCCESS and pushes an event over the SSE stream that the checkout page opened. If the stream is down, the page falls back to `GET /api/payments/PAY101`, so the database stays the source of truth.
