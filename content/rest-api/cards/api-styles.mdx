## What it is

An API style is the overall way a client and a server agree to talk. [REST](card:what-is-rest), used so far in this tech, puts resources at URLs and acts on them with HTTP methods. SOAP sends each call as an XML message in an envelope, described by a WSDL file. GraphQL offers one endpoint where the client sends a query naming the fields it wants. gRPC lets a client call methods on a remote service as if they were local, using a `.proto` contract and binary messages over HTTP/2.

## Why it exists

REST fits most public APIs, but some needs strain it. A dashboard screen that needs a payment, its customer and its refunds makes three calls, or gets one large response full of fields it ignores; this is under-fetching and over-fetching. Internal services making thousands of calls a second want small typed messages and streams. Older bank systems often require SOAP with a WSDL. Knowing the styles lets you choose one and explain its cost.

## How it works

<Compare id="rest-vs-soap-vs-graphql-vs-grpc" />

1. Ask who calls the API. Browsers, mobile apps and outside partners get REST by default: it works everywhere, it is easy to read, and HTTP caching applies.
2. Ask whether many clients need different shapes of the same data. If each screen needs its own mix of fields, GraphQL lets each client ask for exactly that mix in one call.
3. Ask whether the calls stay inside your own system and need speed or streams. For service-to-service traffic, gRPC gives typed generated code, small binary messages and streaming.
4. Ask whether a partner dictates the contract. If it hands you a WSDL, you use SOAP, because the choice is not yours.

So the key is to start from REST and move only for a named problem.

## Example

The same question, "what is the status and amount of PAY101?", asked in GraphQL, and the gRPC contract for it:

```text
POST /graphql
Content-Type: application/json

{ "query": "{ payment(id: \"PAY101\") { status amount } }" }
```

```proto
syntax = "proto3";

service PaymentService {
  rpc GetPayment (GetPaymentRequest) returns (Payment);              // unary: one in, one out
  rpc WatchPayment (GetPaymentRequest) returns (stream Payment);     // server streaming
}

message GetPaymentRequest { string id = 1; }

message Payment {
  string id = 1;        // field numbers identify fields on the wire
  string status = 2;
  int64 amount = 3;
}
```

What to notice:

- The GraphQL query names only `status` and `amount`, so the reply holds only those, inside a `data` object. Add `customer { name }` to the query and the same single call also returns the customer.
- In REST this would be `GET /api/payments/PAY101`, a URL that caches can store. The GraphQL call is a POST to one URL, which ordinary HTTP caches do not store.
- In the `.proto` file, `stream` makes `WatchPayment` push every change to the caller. The numbers `= 1`, `= 2` identify fields in the binary message, so they must never change once clients use them.

## Rules and defaults

- **GraphQL over HTTP:** servers must accept POST; GET is optional and allowed only for queries, never for mutations (writes). A response can carry both `data` and an `errors` list, and a request that returns data still gets a 2xx status even when some fields failed.
- **gRPC status:** each call ends with a gRPC status code, such as `OK` (0), `NOT_FOUND` (5) or `DEADLINE_EXCEEDED` (4), not with the HTTP status codes a REST client reads.
- **Protocol Buffers changes:** adding a field is safe for old clients, which ignore it; changing or reusing a field number is not safe.
- **SOAP:** SOAP 1.2 (W3C, 2007) defines the Envelope, an optional Header and a required Body; WSDL 2.0 (W3C, 2007) describes the operations, bindings and endpoint.

## Not to be confused with

SOAP is a protocol: it fixes the message format and the processing rules. REST is an architectural style: a set of constraints such as statelessness and a uniform interface, with no message format of its own. gRPC is a framework for remote procedure calls, where you call named methods instead of acting on resources. Rule: SOAP = a protocol; REST = a style; gRPC = remote method calls.

## Interview Qs

### When would you choose gRPC over REST?

For internal service-to-service calls that need a strict typed contract, small binary messages, low latency or streaming. I keep REST at the edge for browsers and partners, because a browser needs gRPC-Web and a proxy to reach a gRPC service.

### What problem does GraphQL solve?

Over-fetching and under-fetching: different screens need different fields, and REST resources return a fixed shape. The client sends one query naming the fields, to one endpoint, and gets just those back. The costs are harder HTTP caching and more work on the server to resolve and limit queries.

### What is the difference between REST and SOAP?

SOAP is an XML messaging protocol with a strict envelope format and a WSDL contract, often used by older enterprise and bank systems. REST is an architectural style over plain HTTP, usually with JSON, where each resource has a URL. REST is lighter and easier to cache; SOAP brings a formal contract that some partners require.
