## What it is

An error response is what the API sends when it cannot do what was asked: a [status code](card:status-codes) plus a body that explains the problem. Problem details, defined in RFC 9457, is the standard JSON shape for that body. It is sent with the media type `application/problem+json` in the [Content-Type header](card:headers-content-negotiation). It has a few standard members, such as `type`, `title`, `status` and `detail`, and lets you add your own, such as a stable `errorCode`.

## Why it exists

A status code alone says 422 but not which field was wrong, or how to fix it. If every endpoint invents its own error body, `{"msg": ...}` here and `{"error": {"text": ...}}` there, each client needs custom parsing for each endpoint. A client that compared message strings also breaks the day someone rewords a message. One standard shape lets a client handle every error with the same code: show `detail` to a developer, branch on `type` or `errorCode`, and highlight the bad fields.

## How it works

| Member | Meaning |
|---|---|
| `type` | A URI naming the kind of problem; `about:blank` when left out |
| `title` | A short summary of that type; the same every time |
| `status` | A copy of the HTTP status code; it must match the real one |
| `detail` | This occurrence, written to help the client fix it |
| `instance` | A URI for this one occurrence |

1. Your code finds a problem: the request asks for a payment of -500.
2. It chooses the status code that fits, here 422 Unprocessable Content.
3. It fills a problem details body: a `type` URI for "invalid amount", a fixed `title`, the same `status`, and a `detail` for this request.
4. It adds extension members: a stable `errorCode` and an `errors` list with one entry per bad field.
5. It sends the body with `Content-Type: application/problem+json`. The full exception stays in the server log.

## Example

The payment API rejects a negative amount.

```text
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/invalid-amount",
  "title": "Invalid amount",
  "status": 422,
  "detail": "amount must be greater than 0, but was -500",
  "errorCode": "PAYMENT_INVALID_AMOUNT",
  "errors": [ { "pointer": "#/amount", "detail": "must be greater than 0" } ]
}
```

What to notice:

- `type` is the same URI every time this kind of problem happens, so a client can branch on it. It may point to a page that documents the problem.
- `detail` describes this request (-500) and tells the client how to fix it. It is written for people, not for code.
- `errorCode` and `errors` are extension members. `pointer` is a JSON Pointer (`#/amount`) to the bad field, as in RFC 9457's own example.
- Nothing reveals the server's internals: no exception class, no stack trace, no SQL.

## Rules and defaults

- **All members are optional** (RFC 9457). A missing `type` means `about:blank`, which says "nothing more than the status code"; its `title` should then be the standard status phrase.
- **status is only advisory:** it must equal the real HTTP status, and clients trust the real one.
- **Unknown extensions:** clients must ignore extension members they do not recognise, so adding one is safe.
- **Several problems:** list problems of the same type in one extension member, such as `errors`. For problems of different types, return the most relevant or urgent one.
- **Error codes are contract:** Microsoft's guidelines document error codes as part of the API contract, so changing one is a breaking change.
- **RFC 7807:** RFC 9457 (July 2023) replaced RFC 7807 with the same format. Spring's `ProblemDetail` builds this body; you will see it in [exception handling](card:exception-handling).

## Not to be confused with

The HTTP status code is the class of outcome, which any HTTP software understands: caches, proxies, monitoring and retry logic. The `type` or `errorCode` is your API's specific reason, which only your clients understand. Rule: status for HTTP software, `type` or `errorCode` for client logic, `detail` for humans.

## Common mistakes

- **"Return 200 OK with `{"success": false}` for errors."** Monitoring, retry logic and caches read the status code, so they count the failure as a success. Send the real 4xx or 5xx status with a problem details body.

## Interview Qs

### What should an API error response contain?

The right HTTP status plus one consistent body: RFC 9457 problem details with `type`, `title`, `status` and `detail`, and extensions such as a stable `errorCode` and per-field errors. It must never contain a stack trace or other internals.

### Why a stable error code when there is already a message?

Messages get reworded and translated, but client code needs a fixed value to compare. RFC 9457 says consumers should not parse `detail`, and Microsoft's guidelines treat error codes as part of the API contract.

### What is the difference between RFC 7807 and RFC 9457?

RFC 9457, from July 2023, replaced RFC 7807 from March 2016. The JSON format is the same. RFC 9457 adds a registry of common problem types, and guidance for reporting several problems and for using `type` URIs that do not resolve.
