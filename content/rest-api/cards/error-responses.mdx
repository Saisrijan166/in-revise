## Why it exists

A status code alone cannot say which field was wrong. If every endpoint invents its own error body, every client needs custom parsing code for each one.

## How it works

| Member | Meaning |
|---|---|
| `type` | A URI naming the kind of problem; `about:blank` when left out |
| `title` | Short summary of that type; the same every time |
| `status` | A copy of the HTTP status; it must match the real one |
| `detail` | This occurrence, written to help the client fix it |
| `instance` | A URI for this one occurrence |

- Status choice: [status codes](card:status-codes). Spring's `ProblemDetail`: [exception handling](card:exception-handling).
- Error text can leak internals: see [OWASP API risks](card:owasp-api-security).

## Example

```text
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/invalid-amount",
  "title": "Invalid amount",
  "status": 422,
  "detail": "amount must be greater than 0, but was -500",
  "errorCode": "PAYMENT_INVALID_AMOUNT",
  "errors": [ { "pointer": "#/amount", "detail": "must be greater than 0" } ]
}
```

## Interview Qs

### What should an API error response contain?

The right HTTP status plus one consistent body: RFC 9457 problem details with type, title, status and detail, and extensions like a stable errorCode and per-field errors. Never a stack trace.

### Why a stable error code when there is already a message?

Messages get reworded and translated; client code needs a fixed value to compare. Microsoft's guidelines make error codes part of the API contract, and RFC 9457 says clients should not parse detail.

### What is the difference between RFC 7807 and RFC 9457?

RFC 9457 (July 2023) replaced RFC 7807 (March 2016). The format is the same; it adds a registry of common problem types and guidance for several problems at once.
