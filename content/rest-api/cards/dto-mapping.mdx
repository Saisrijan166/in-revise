## What it is

A DTO (data transfer object) is a small class shaped for the API: it holds only the fields a client sends or receives in one call. An entity is the class mapped to a database table, usually with JPA (Jakarta Persistence), the Java standard that saves objects as rows. The controller accepts a request DTO and returns a response DTO. The service copies values between DTOs and entities, which is called mapping.

## Why it exists

The `Payment` entity holds everything the database needs: the gateway reference, audit fields, a link to the merchant. If the controller returns it, Jackson writes all of it to the client. If the request body is bound onto it, a client can send `"status": "SUCCESS"` and set a field it must never control; OWASP calls this mass assignment, as [OWASP API risks](card:owasp-api-security) showed. DTOs stop both, and the tables can change without changing the JSON clients depend on.

## How it works

<Compare id="dto-vs-entity" />

1. Jackson reads the JSON body into `PaymentRequest`, which has only amount, currency and method. Any other field in the JSON is ignored.
2. The service checks the business rules and builds a new `Payment` entity, setting `status = PENDING` itself.
3. The repository saves the entity to the database.
4. The service maps the saved entity to a `PaymentResponse` with only `paymentId`, `status` and `amount`.
5. The controller returns that DTO, and Jackson writes only those three fields.

So the entity never crosses the API boundary, in either direction.

## Example

The response DTO is a record with a small mapping method written by hand.

```java
record PaymentResponse(String paymentId, String status, BigDecimal amount) {
    static PaymentResponse from(Payment p) {               // entity -> DTO, by hand
        return new PaymentResponse(p.getPaymentId(), p.getStatus().name(), p.getAmount());
    }
}
// Payment (the entity) also has gatewayRef and audit fields: they never leave the service.
```

What to notice:

- Only the three fields named in the record reach the client. A new column in `Payment` changes nothing in the JSON until someone adds it here.
- `status` is turned from an enum into text here, so the API can keep its wording even if the enum is renamed.
- A record is immutable: its fields are set once in the constructor. That suits a DTO, but a JPA entity must be a non-final class, so the entity stays a normal class.

## Rules and defaults

- **Unknown JSON fields (Jackson 3, Spring Boot 4.x):** ignored by default, because `FAIL_ON_UNKNOWN_PROPERTIES` is false. A DTO without a `status` field therefore cannot receive one.
- **Separate DTOs:** use one DTO for the request and another for the response. A shared one would let clients send `paymentId` or `status`.
- **Where constraints go:** `@NotNull`, `@Positive` and the other checks belong on the request DTO, as in [validation](card:request-binding-validation).
- **Open-in-view (Spring Boot 4.1):** `spring.jpa.open-in-view` is `true` by default, so a returned entity can still load lazy relations while Jackson writes it, running extra queries during the response.
- **Mapping tools:** a static `from()` method is fine for a few DTOs. MapStruct generates the same plain method calls at compile time and warns about target fields it could not map.

## Common mistakes

- **"One `Payment` class can be the entity, the request and the response."** Then every column is exposed, every column can be set by clients, and a schema change is an API change. Keep three shapes for three jobs.

## Interview Qs

### If the entity already holds the data, why do we need a DTO?

The entity is shaped by the database; the DTO is the API contract. A DTO hides internal fields, blocks mass assignment because it has no fields a client should not set, and lets you change tables without breaking clients.

### Why is returning a JPA entity from a controller risky?

Jackson writes every property it can reach, so internal fields leak. With open-in-view on, lazy relations load while the JSON is written, running extra queries. A table change also becomes a breaking API change.

### Mapping by hand or MapStruct?

By hand is plain and fine for a few DTOs. MapStruct generates the same plain method calls at compile time, so there is no reflection cost, and it reports unmapped fields during the build. I choose it when there are many DTOs.
