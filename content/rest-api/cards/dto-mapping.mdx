## Why it exists

The database model and the API contract change for different reasons. Sending entities out leaks internal fields, ties clients to your tables, and lets clients set fields they should not.

## How it works

<Compare id="dto-vs-entity" />

- Map entity to DTO in the service; the controller sees only DTOs.
- Binding a body straight onto an entity lets a client send `"status": "SUCCESS"` (mass assignment): [OWASP API risks](card:owasp-api-security).
- Constraints go on the request DTO: [validation](card:request-binding-validation).

## Example

```java
record PaymentResponse(String paymentId, String status, BigDecimal amount) {
    static PaymentResponse from(Payment p) {                  // entity -> DTO, by hand
        return new PaymentResponse(p.getPaymentId(), p.getStatus().name(), p.getAmount());
    }
}
// The Payment entity also has gatewayRef and internal audit fields: never sent out.
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `spring.jpa.open-in-view` | `true`: lazy loading still works while the response is written | Spring Boot 4.1 |

## Interview Qs

### If the entity already holds the data, why do we need a DTO?

The entity is shaped by the database; the DTO is the API contract. A DTO hides internal fields, blocks mass assignment, and lets you change tables without breaking clients.

### Why is returning a JPA entity from a controller risky?

Jackson writes every property it can reach. With open-in-view on, lazy relations load while the JSON is written, running extra queries. Internal fields leak, and a table change breaks clients.

### Mapping by hand or MapStruct?

By hand is plain and fine for a few DTOs. MapStruct generates the same plain method calls at compile time, so it stays fast and reports mapping mistakes at build time.
