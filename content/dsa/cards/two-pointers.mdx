## Why it exists

Checking every pair with two nested loops is O(n²). On sorted data one pass with two indices does the same job.

## How it works

| Type | Start | Move | Classic problems |
|---|---|---|---|
| [Opposite ends](card:opposite-ends-pointers) | `0` and `n - 1` | inward, by comparing | Two Sum II, Valid Palindrome, Container With Most Water |
| [Read / write](card:read-write-pointers) | both at `0` | read every item; write the keepers | Remove Duplicates, Move Zeroes |
| [One per array](card:one-pointer-per-array) | `0` in each | advance the smaller | Merge Sorted Array |

- Pointers never move back, so the whole run is at most n steps.
- [3Sum](card:three-sum): sort, fix each value, run opposite ends on the rest: O(n²).

## Example

```java
boolean hasPair(int[] nums, int target) {       // nums is sorted
    int left = 0, right = nums.length - 1;
    while (left < right) {
        int sum = nums[left] + nums[right];
        if (sum == target) return true;
        if (sum < target) left++;               // need a bigger sum
        else right--;                           // need a smaller sum
    }
    return false;
}
```

## Interview Qs

### Why does moving the left pointer never miss the answer?

If `nums[left] + nums[right]` is too small, `nums[right]` is the largest value left, so `nums[left]` cannot reach the target with anything. Dropping it is safe. The same logic drops `right` when the sum is too big.

### How do you solve 3Sum?

Sort the array, then for each index run opposite-end pointers on the part to its right, looking for the remaining sum. That is O(n²) time instead of O(n³).
