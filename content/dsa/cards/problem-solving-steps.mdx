## What it is

A problem-solving routine is the same order of steps you follow for every coding question, from first reading to final test. It has six steps: clarify, work examples, state the brute force, optimise the bottleneck, code, and test. The brute force is the simplest correct solution, usually trying every option. The bottleneck is the slowest part of a solution, the step that decides its [Big-O](card:big-o).

## Why it exists

Under pressure, many candidates start typing at once. They solve a slightly different problem, or get stuck halfway with no plan, and the interviewer sees no reasoning. A routine gives you a next step at every moment, even before you see the answer. It also shows how you think: interviewers score communication, problem solving, coding and testing, not only whether the code runs.

## How it works

1. Restate the problem in your own words and ask about the input size, the value range, empty input, sorting and duplicates. The answers can change the solution.
2. Solve two or three small inputs by hand, including a tricky one. Write them down: they are your tests later.
3. State the brute force and its time and space cost. You need not code it; it proves you understand the problem.
4. Find the work the brute force repeats and replace it, using the table below. Explain the idea and wait for the interviewer to agree.
5. Write the code with clear names, saying what each part does as you write it.
6. Dry-run your examples line by line, then the boundary inputs (you will see the list in [Edge Cases](card:edge-cases)), and state the final time and space.

| Repeated work in the brute force | Replace it with |
| --- | --- |
| Searching for a value again and again | [HashMap or HashSet](card:hashmap-hashset) lookup |
| Adding up the same range again | [Prefix sums](card:prefix-sum) |
| Solving the same subproblem many times | Caching: [dynamic programming](card:dynamic-programming) |
| Nested loops over pairs of a sorted array | [Two pointers](card:two-pointers) or [binary search](card:binary-search) |
| Sorting everything to get the top k | [A heap of size k](card:top-k-heap) |

So the key is: the brute force tells you exactly what to optimise.

## Example

The routine applied to Two Sum: find the two indexes in `nums = [2, 7, 11, 15]` whose values add up to 9.

```text
Clarify:     exactly one answer? yes.  Use one item twice? no.
Examples:    [2, 7, 11, 15], 9 -> [0, 1]      [3, 3], 6 -> [0, 1]
Brute force: try every pair i < j          -> O(n²) time, O(1) space
Bottleneck:  the inner loop searches for 9 - nums[i]
Optimise:    store seen values in a HashMap -> O(n) time, O(n) space
Test:        dry-run both examples, then a one-item input
```

What to notice:

- "Exactly one answer" lets the code return at the first match; without that answer you would have to ask what to return when no pair exists.
- The bottleneck line names the repeated work, searching for the partner, so the fix follows: a HashMap answers "have I seen 9 - x?" in O(1) average time. The code is in [Counting with a HashMap](card:frequency-counting).
- The faster version trades memory for time: O(n) extra space. Say this trade-off aloud.
- `[3, 3]` checks that one item is never paired with itself.

## Rules and defaults

- **Ask, do not assume:** if the problem leaves something open, ask; if the interviewer leaves it to you, state your assumption aloud.
- **Code only after agreement:** explain the approach first and start typing once the interviewer agrees.
- **Know the floor:** if every item must be read at least once, O(n) is the best possible time, so stop optimising once you reach it.
- **Not done yet:** do not announce that you are finished; review for off-by-one errors and test first.

## Common mistakes

- **"I must find the optimal solution before saying anything."** Say the brute force early. A correct slow idea earns credit and often shows the way to the fast one.
- **"Silence helps me think."** The interviewer cannot score reasoning they cannot hear, and their replies often contain hints.

## Interview Qs

### What do you do first when you get a problem?

Restate it, then ask two or three clarifying questions: input size, value range, empty input, sorted or not, duplicates. Then solve a small example by hand and confirm it with the interviewer, so you both agree on what the output should be.

### Should you mention the brute force if you already know a better way?

Yes, briefly, with its cost. It shows you understand the problem, gives a baseline to compare against, and makes the optimisation easy to explain: you name the work it repeats and what removes it.

### What do you do when you are stuck?

Go back to the brute force and ask what it recomputes. Try each common structure in turn: would a HashMap, a heap, a stack or sorting remove that work? Solve a bigger example by hand and turn your own shortcuts into rules.
