## What it is

Dynamic programming (DP) is a way to solve a problem from the answers to smaller versions of the same problem, called subproblems, computing each subproblem only once. It works when two things are true. The same subproblems are needed many times (overlapping subproblems). And the best answer can be built from the best answers to subproblems (optimal substructure). Each subproblem is called a state, and you store its answer the first time you compute it.

## Why it exists

A plain [recursive](card:recursion) solution often asks for the same subproblem again and again. Fibonacci shows it: fib(5) calls fib(3) twice and fib(2) three times, and the number of calls grows exponentially with n. Storing each answer the first time it is computed means every later request is a lookup. The work drops to the number of distinct states, which is often only n or n × m.

Coin change asks for the fewest coins from {1, 2, 5} that make 11. Write any DP in five steps:

1. **State:** say what one entry means in words. dp[x] = the fewest coins that make the sum x.
2. **Transition:** say how a state follows from smaller ones. The last coin c leaves the sum x - c, so dp[x] = 1 + the minimum of dp[x - c] over every coin c that fits.
3. **Base case:** dp[0] = 0, because no coins make 0. A sum that cannot be made yet is marked "impossible".
4. **Order:** fill the states so the smaller ones come first: x = 1, 2, ..., 11.
5. **Answer:** read dp[11], which is 3 (5 + 5 + 1).

So the key is to define the state precisely in words before writing any code.

## Example

The five steps above, as a bottom-up table:

```java
int coinChange(int[] coins, int amount) {
    int[] dp = new int[amount + 1];            // dp[x] = fewest coins that make x
    Arrays.fill(dp, Integer.MAX_VALUE);        // MAX_VALUE marks "not possible yet"
    dp[0] = 0;                                 // base case: 0 coins make 0
    for (int x = 1; x <= amount; x++)          // order: smaller sums first
        for (int c : coins)
            if (c <= x && dp[x - c] != Integer.MAX_VALUE)
                dp[x] = Math.min(dp[x], dp[x - c] + 1);   // transition
    return dp[amount] == Integer.MAX_VALUE ? -1 : dp[amount];
}

System.out.println(coinChange(new int[] {1, 2, 5}, 11));
```

```text output
3
```

What to notice:

- Each of the 12 states is computed once, from states already filled. There are amount + 1 states and each tries every coin, so the time is O(amount × coins) and the space O(amount).
- The test `dp[x - c] != Integer.MAX_VALUE` matters. Without it, `MAX_VALUE + 1` overflows to a negative number, which `Math.min` would pick as the best answer.
- A sum that no coin combination makes stays at `MAX_VALUE`, and the method returns -1 for it. With coins {2} and amount 3, the answer is -1.

## Rules and defaults

- **Cost:** time = number of states × work per state; space = number of states stored.
- **Fill order:** in a table, every state must be filled after the states it reads. In a memo, the recursion finds that order for you.
- **Less memory:** if dp[i] reads only dp[i - 1] and dp[i - 2], keep two variables. Many 2D tables need only the previous row.
- **Common shapes:** 1D DP over a position or a sum (Climbing Stairs, House Robber, coin change), and 2D DP over two indices (a grid, or prefixes of two strings).

## Not to be confused with

Memoisation keeps the recursive code and adds a cache, so it computes only the states it reaches. Tabulation drops the recursion and fills a table with loops, starting from the base cases. Both are DP. [Divide and conquer](card:merge-sort), as in merge sort, also splits a problem into smaller ones, but they do not repeat, so there is nothing to store. Rule: repeated subproblems, use DP; independent subproblems, divide and conquer. You will compare DP with [greedy](card:greedy) next.

## Interview Qs

### How do you know a problem needs DP?

It asks to count the ways, or to minimise or maximise something. The answer can be built from smaller versions of the same problem, and a brute-force recursion would ask for the same smaller versions many times. Writing that recursion first and spotting repeated arguments is the usual way to confirm it.

### Memoisation or tabulation?

Both compute each state once and have the same Big-O. Memoisation is easier to write from the recursion and skips states it never needs. Tabulation has no recursion, so a deep input cannot overflow the call stack, and it makes it easy to keep only the last rows. Many people write the memo first, then convert.

### How do you cut the memory of a DP?

Look at which states the transition reads. If dp[i] reads only dp[i - 1] and dp[i - 2], as in Climbing Stairs, keep two variables instead of an array, so space drops from O(n) to O(1). In a 2D table where each row reads only the row above, keep two rows.
