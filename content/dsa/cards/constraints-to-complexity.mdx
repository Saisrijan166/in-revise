## Why it exists

Constraints quietly tell you which solution is expected. Checking them first rules out approaches that are too slow before you write any code.

## How it works

For a time limit of about one second:

| Input size n | Cost that still fits | Typical approach |
| --- | --- | --- |
| n ≤ 10 | O(n!) | Try every order |
| n ≤ 20 | O(2^n) | Try every subset |
| n ≤ 500 | O(n³) | Three nested loops |
| n ≤ 5000 | O(n²) | Two nested loops |
| n ≤ 10^6 | O(n log n) or O(n) | Sort, hash, one pass |
| larger | O(log n) or O(1) | Math or binary search |

- No constraints given? Ask for the input size and value range.
- Check the value range too, not only n: see [int overflow](card:java-pitfalls).

## Example

```text
n = 100,000
O(n²)      → 10,000,000,000 steps   too slow
O(n log n) → about 1,700,000 steps   fine
O(n)       → 100,000 steps           fine
```

## Interview Qs

### How do the constraints help you choose an approach?

Put the largest n into each cost and compare with a few hundred million steps per second.

### The interviewer gives no constraints. What do you do?

Ask how large the input can be and what range the values have. The answer decides the target cost and whether sums need long.
