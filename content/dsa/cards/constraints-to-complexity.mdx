## What it is

Constraints are the limits a problem gives on its input, such as "1 ≤ n ≤ 10^5" for the array length or "values up to 10^9". Reading them tells you how fast your solution must be. You put the largest n into each [Big-O](card:big-o) cost you are considering, and keep only the ones whose step count fits in the time limit.

## Why it exists

Without this check you may spend twenty minutes perfecting a nested-loop solution, only to learn it is far too slow for the real input. The constraints quietly say which solution is expected. A limit of 10^5 means "O(n²) will not pass"; a limit of 20 means "trying every subset is allowed". Checking them first rules out wrong approaches before you write any code.

## How it works

The table assumes a time limit of about one second.

| Largest n | Cost that still fits | Typical approach |
| --- | --- | --- |
| n ≤ 10 | O(n!) | Try every order |
| n ≤ 20 | O(2^n) | Try every subset |
| n ≤ 500 | O(n³) | Three nested loops |
| n ≤ 5000 | O(n²) | Two nested loops |
| n ≤ 10^6 | O(n log n) or O(n) | Sort, hash, one pass |
| larger | O(log n) or O(1) | Maths or binary search |

1. Find the largest n in the constraints. If none is given, ask the interviewer.
2. Write down the Big-O of each idea you have, starting with the brute force.
3. Put n into each cost and compare with a budget of a few hundred million simple steps per second.
4. Keep the ideas that fit; the cheapest one that fits is usually what the interviewer expects.
5. Check the value range: it decides whether sums and products need `long`.

So the key is: the input size picks the complexity, and the complexity narrows down the pattern.

## Example

Suppose an array has up to 100,000 values, each up to 10^9.

```text
n = 100,000
O(n²)      -> 10,000,000,000 steps    too slow (tens of seconds)
O(n log n) -> about 1,700,000 steps   fine
O(n)       -> 100,000 steps           fine

largest sum = 100,000 × 10^9 = 10^14  > int max 2,147,483,647 -> use long
```

What to notice:

- log₂ of 100,000 is about 17, so O(n log n) costs only about 17 times more than O(n). Sorting is almost always affordable.
- The O(n²) line is nearly 6,000 times bigger than the O(n log n) line, so no small speed-up rescues it.
- The last line is a separate check on values, not n. Even an O(n) solution gives a wrong answer if its sum overflows an `int`; you will see how this fails in [Java Pitfalls](card:java-pitfalls).

## Rules and defaults

- **Assumed budget:** some hundreds of millions of simple steps per second, and a one-second limit. It is a rule of thumb, not a guarantee for any judge or language.
- **No constraints given:** ask for the input size and value range. The answer decides the target cost and whether you need `long`.
- **int limit:** a Java `int` holds values from -2,147,483,648 to 2,147,483,647, about ±2.1 × 10^9.
- **Constants still matter:** Big-O hides constant factors, so near a limit a solution with heavy constant work can still be too slow.

## Common mistakes

- **"Small n means my solution is too slow."** The reverse is true: a small n allows a slower, simpler solution, and an interviewer giving n ≤ 20 often expects one.
- **Checking n and forgetting the values.** A correct O(n) algorithm still fails when its `int` sum overflows.

## Interview Qs

### How do the constraints help you choose an approach?

Put the largest n into each candidate cost and compare it with a few hundred million steps per second. For n = 10^5, O(n²) is 10^10 steps, too slow, so you need O(n log n) or O(n). This tells you which patterns are worth considering before you write code.

### The interviewer gives no constraints. What do you do?

Ask how large the input can be and what range the values have. The size decides the target complexity, and the value range decides whether sums need `long`. If they leave it open, state an assumption, such as "up to 10^5 items", and design for it.
