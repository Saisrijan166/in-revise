## What it is

Merge sort is a divide-and-conquer sort. Divide and conquer means splitting a problem into smaller parts, solving each part the same way, and combining the answers. Merge sort splits the array into two halves, sorts each half with a [recursive](card:recursion) call, then merges the two sorted halves into one sorted range. Merging means comparing the front items of both halves and always taking the smaller one.

## Why it exists

The simple sorts from [sorting basics](card:sorting-basics) take O(n²), which is about 10^12 steps for a million items. Merging two lists that are already sorted is cheap: one pass, O(n). Merge sort turns sorting into many cheap merges, so the total cost drops to O(n log n) on every input, with no bad case. That makes it the choice when you need a guaranteed bound, a stable sort, or a sort for a linked list.

1. Split `[15, 2, 11, 7]` at the middle into `[15, 2]` and `[11, 7]`.
2. Keep splitting until each part has one item. A single item is already sorted: this is the base case.
3. Merge neighbours back: `[15]` and `[2]` give `[2, 15]`; `[11]` and `[7]` give `[7, 11]`.
4. Merge `[2, 15]` with `[7, 11]`: compare the fronts and take 2, then 7, then 11, then 15.
5. Count the cost: halving gives about log n levels, and the merges on one level touch each of the n items once, so O(n log n).

So the real work happens in the merge, on the way back up from the recursive calls.

## Example

The whole sort, with one helper array shared by every merge.

```java
static void sort(int[] a, int lo, int hi, int[] tmp) {
    if (lo >= hi) return;                                // 0 or 1 item: sorted
    int mid = lo + (hi - lo) / 2;
    sort(a, lo, mid, tmp); sort(a, mid + 1, hi, tmp);    // sort both halves first
    System.arraycopy(a, lo, tmp, lo, hi - lo + 1);       // copy, then merge back
    for (int k = lo, l = lo, r = mid + 1; k <= hi; k++) {
        if (l > mid) a[k] = tmp[r++];                    // left half used up
        else if (r > hi || tmp[l] <= tmp[r]) a[k] = tmp[l++];  // <= keeps ties stable
        else a[k] = tmp[r++];
    }
}

int[] nums = {15, 2, 11, 7};
sort(nums, 0, nums.length - 1, new int[nums.length]);
System.out.println(Arrays.toString(nums));
```

```text output
[2, 7, 11, 15]
```

What to notice:

- `if (lo >= hi) return;` is the base case: a range of 0 or 1 item is already sorted.
- Both recursive calls run before the loop, so each half is sorted by the time the merge starts.
- `tmp[l] <= tmp[r]` takes the left item on a tie. With `<`, the right item would win ties and the sort would no longer be stable.
- `tmp` is created once with n slots and reused by every merge. That array is the O(n) extra space; creating a new one in every call would only add work.

## Rules and defaults

- **Cost:** O(n log n) time in the best, average and worst case. On arrays, O(n) extra space for the helper array plus O(log n) stack for the recursion.
- **Linked lists:** merging relinks nodes instead of copying them, so no helper array is needed. A list also cannot jump to an index, which merge sort never needs.
- **Bottom-up version:** merge runs of size 1, then 2, then 4, and so on with plain loops. It does the same work without recursion.
- **In Java:** you do not write it yourself; `List.sort` and `Arrays.sort(Object[])` already use a stable merge sort, as [sorting basics](card:sorting-basics) explains.

## Interview Qs

### Why is merge sort O(n log n)?

Halving the range gives about log n levels of recursion. On each level, all the merges together touch every item once, which is O(n). So the total is n work on each of log n levels. The split is always at the middle, so this holds for every input.

### Why is merge sort a good choice for linked lists?

Merging two lists only changes `next` links, so it needs no helper array. It also never needs to jump to an index, which a linked list cannot do quickly. It stays O(n log n) on any list, sorted or not.

### How do you count inversions in an array?

An inversion is a pair i < j with `nums[i] > nums[j]`. Run merge sort, and each time the merge takes an item from the right half, add the number of items still waiting in the left half, since all of them are larger. The total is the inversion count, in O(n log n).
