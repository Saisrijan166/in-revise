## What it is

Global state is state that many components across the app need, not just one component or a pair of siblings. Choosing where to keep it is really one decision repeated per value, from the cheapest tool to the most powerful: local [useState](card:use-state), then [lifted state](card:lifting-state-up), then [Context](card:context-api), then a store. A store is one shared object that lives outside the component tree, which any component can read from and update; Redux Toolkit and Zustand are two popular stores.

## Why it exists

Some values are needed far apart in the tree. The cart count shows in the header, and the cart contents show on the payments page; threading that through every layer in between is painful and error-prone. A shared place that any component can reach removes the threading. The skill is picking the *smallest* such place, because a full store adds setup, indirection and re-render rules that a simple value does not need.

## How it works

The table maps each kind of state to the smallest tool that fits it.

| The state is… | Keep it in |
|---|---|
| Used by one component | Its own [`useState`](card:use-state) |
| Shared by nearby siblings | [Their common parent](card:lifting-state-up) |
| Read widely, changes rarely (theme, user) | [Context](card:context-api) |
| Shared widely, changes often (cart) | A store (Redux Toolkit or Zustand) |
| A copy of backend data (payments) | [A query cache](card:data-fetching) |
| Search text, filters, current page | [The URL](card:react-router) |

The two big splits to make first: client state (the app owns it) versus server state (a copy of backend data), and read-widely-but-rarely-changing (Context) versus shared-and-often-changing (a store).

## Example

A Redux Toolkit slice for the cart: `createSlice` writes the state and its reducers together, and `configureStore` builds the one store.

```jsx
import { createSlice, configureStore } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    addItem(state, action) { state.items.push(action.payload); }, // Immer makes this safe
  },
});

export const { addItem } = cartSlice.actions;                       // action creator, generated
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
```

What to notice:

- `createSlice` generates the `addItem` action creator for you, so you do not write action type strings by hand.
- `state.items.push(...)` looks like a mutation, but Redux Toolkit includes Immer, which turns it into a new immutable state behind the scenes.
- `configureStore` builds the single store and already adds the thunk middleware and DevTools, so there is no manual wiring.
- A component dispatches `addItem(payment)` and reads the cart with `useSelector`; only components whose selected slice changed re-render.

## Rules and defaults

- **Redux Toolkit 2 is the recommended way to write Redux:** `configureStore` plus `createSlice`, not hand-written stores and action constants (redux.js.org).
- **Immer is built into createSlice:** writing `state.x = y` inside a reducer produces a new immutable state; you never mutate the real state.
- **Zustand needs no Provider:** `create()` returns a hook you import and call anywhere, unlike Context and Redux which wrap the tree in a Provider.
- **Server state is not client state:** backend data belongs in [a query cache](card:data-fetching), which handles staleness and refetching; a store does not.

## Not to be confused with

Context is a transport: it carries one value down to any component without props, but it does not store or update anything by itself; you still hold the value in `useState` or `useReducer`. A store (Redux, Zustand) both holds the state and defines how it changes, and lives outside the tree. Rule: Context passes a value through; a store owns a value. They are often combined, not swapped.

## Interview Qs

### How do you decide between useState, Context and a state manager?

Start with the smallest tool. Local `useState` for one component; lift to a common parent for nearby siblings; Context for a value read widely that changes rarely, like theme; a store (Redux Toolkit or Zustand) for client state shared widely that changes often. Backend data goes in a query cache, and filters go in the URL.

### What is the difference between client state and server state?

Client state is state the app owns and fully controls, like the cart or the open menu. Server state is a local copy of backend data, like the payments list, which can go stale and must be refetched. Server state belongs in a query cache that handles caching and refetch, not in a client store.

### Why might a team pick Zustand over Redux Toolkit?

Zustand needs far less code: `create()` returns a store hook with no Provider and no boilerplate, and components re-render only when the slice they select changes. Redux Toolkit suits larger teams that want a strict, uniform structure, a traceable action log and rich DevTools.
