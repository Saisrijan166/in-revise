## Why it exists

The cart is needed far apart, in the header and on /cart. Passing it through every layer is painful, so it moves to a shared place.

## How it works

| The state is… | Put it in |
|---|---|
| Used by one component | Its `useState` |
| Shared by nearby siblings | [Their common parent](card:lifting-state-up) |
| Read widely, changes rarely (theme) | [Context](card:context-api) |
| Shared widely, changes often (cart) | A store (Redux Toolkit, Zustand) |
| Data from the API (products) | [TanStack Query](card:data-fetching) |
| Search text, filters, page | [The URL](card:react-router) |

## Example

```jsx
import { createSlice, configureStore } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    addToCart(state, action) { state.items.push(action.payload); }, // Immer makes this immutable
  },
});
export const { addToCart } = cartSlice.actions;    // action creator, generated
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
```

## Interview Qs

### Context API vs Redux: when do you use which?

Context only passes a value down; all consumers re-render when it changes. Redux Toolkit adds one store, actions, reducers, selectors and DevTools. Context for theme or user; Redux for large, often-changing shared state.

### Explain the Redux data flow.

The UI dispatches an action; the store runs the reducer on the old state and saves the result. Components whose selected data changed re-render. One direction, so every change is traceable.

### Why might a team pick Zustand over Redux Toolkit?

Less code: `create` returns a store hook, with no Provider. Components re-render only when their selected slice changes. Redux Toolkit suits large teams that want strict structure.
