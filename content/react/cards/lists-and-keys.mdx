## What it is

To show a list, you map an array of data to an array of JSX elements. A **key** is a special attribute you put on each of those elements. It is a stable name tag that React uses to recognise the same item from one render to the next. The key is not shown to the user and is not passed to the component as a prop; it is only a hint for React's [reconciliation](card:what-is-react).

## Why it exists

When the list changes, React must line up the old rows with the new ones to decide what to update. Without a reliable name, it falls back to matching by position, so after you delete or reorder an item, React can keep a row's DOM and [state](card:use-state) but pair it with a different item. A typed value or a focused input then jumps to the wrong row. A stable key from the data lets React match each item correctly, so it moves, adds or removes exactly the right rows.

## How it works

Which key you choose decides what happens when the list changes:

| Key | Result when the list changes |
|---|---|
| `payment.id` (from the data) | Each row keeps its own state and DOM; React moves the right rows |
| Array index | Rows can swap state after an insert, delete or reorder |
| `Math.random()` (new each render) | Every row is treated as new and remounts, losing input and focus |

1. You render the list with `data.map(item => <Row key={item.id} ... />)`, putting the key on the element `map` returns.
2. On the next render React builds the new list and reads each item's key.
3. React matches new items to old ones by key: same key means the same item, so it reuses that row's DOM and state.
4. Items whose key disappeared are removed, and keys that are new are mounted fresh.

So the key is that identity comes from the key, not from the position in the array.

## Example

The key goes on the `<li>` returned by `map`, and it comes from the payment's own id.

```jsx
function PaymentList({ payments, onRefund }) {
  return (
    <ul>
      {payments.map(payment => (
        <li key={payment.id}>
          <PaymentRow payment={payment} onRefund={onRefund} />
        </li>
      ))}
    </ul>
  );
}
```

What to notice:

- The key is on the `<li>`, the element `map` returns, not inside `PaymentRow`. React needs it at the level of the repeated element.
- `payment.id` is stable and unique among these payments, so a row stays matched to its payment even if the list is sorted or filtered.
- `PaymentRow` cannot read `payment.id` through a `key` prop; the id is passed again via `payment`. `key` is for React only.
- Switching to `key={index}` would keep each row matched to a position, so reordering or deleting would move state to the wrong payment.

## Rules and defaults

- **Unique among siblings:** a key must be unique within its own list, not across the whole app; two different lists may use the same key values.
- **Stable and from the data:** use an id that belongs to the item; for new local items, generate one id once and keep it, rather than making a key during render.
- **No key given:** React warns in development and falls back to the array index, which is the behaviour that causes the misattached-state bug.
- **Change a key on purpose:** giving a component a different `key` deliberately remounts it, which is a clean way to reset its state.

## Not to be confused with

A **key** identifies an item inside one list for matching across renders. An **id prop** is ordinary data the child can read and use. The **array index** is the item's current position, which changes when the list changes, so it is a poor key. Rule: key for identity, id prop for data; never lean on the index when the list can change.

## Interview Qs

### Why does React need keys in a list?

Keys let React match items between renders by identity instead of by position. With a stable key, React knows which old row corresponds to which new one, so it can move, add and remove the correct rows and keep each row's state and DOM. Without good keys, it guesses by position and can attach the wrong state to an item.

### What goes wrong when you use the array index as the key?

Index keys are tied to position, not to the item. Delete or reorder the list and every index shifts, so React matches a row's state to whatever item now sits at that position. A quantity or note typed in one row then appears on another. It is safe only for a static list that never changes order or length.
