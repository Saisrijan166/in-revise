## What it is

A web page arrives as plain text: an HTML file plus the CSS and JavaScript files it names. The browser reads the HTML and builds the **DOM** (Document Object Model), a tree of objects, one per element, that your code can read and change. It reads the CSS into the **CSSOM**, a matching tree of styles, combines the two into the render tree, and turns that into the pixels you see. This whole journey, from the first byte of HTML to pixels, is the critical rendering path.

## Why it exists

You cannot fix what you cannot see. When the first screen is slow to appear, or scrolling stutters, the cause is almost always one named step in this pipeline: a stylesheet that blocks painting, a script that blocks parsing, or a change that forces the browser to redo layout. Knowing the steps tells you which one to look at instead of guessing.

## How it works

<Steps label="From URL to pixels">
  <Step title="Fetch the HTML">DNS finds the server's IP, TCP (and TLS for HTTPS) opens the connection, and the browser downloads the HTML.</Step>
  <Step title="HTML to DOM">The browser parses the HTML into the DOM tree and starts fetching the CSS, scripts and images it names.</Step>
  <Step title="CSS to CSSOM">It parses the CSS into the CSSOM. Painting waits for this, so CSS is render-blocking.</Step>
  <Step title="Render tree">It joins the DOM and CSSOM into the render tree: every visible node with its final styles.</Step>
  <Step title="Layout">It calculates the size and position of every box. This step is also called reflow.</Step>
  <Step title="Paint and composite">It fills in the pixels for each layer, then stacks the layers to produce the final screen.</Step>
</Steps>

So the key is that layout and paint are the expensive steps, and a change that re-triggers them is what makes a page feel slow.

## Example

This is the top of a shop page. The three ways of loading a script behave very differently.

```html
<head>
  <link rel="stylesheet" href="/shop.css" />   <!-- render-blocking -->
  <script src="/analytics.js" async></script>  <!-- runs the moment it arrives -->
  <script src="/app.js" defer></script>        <!-- runs after parsing, in order -->
</head>
```

What to notice:

- The stylesheet is render-blocking: the browser will not paint the page until `shop.css` is downloaded and the CSSOM is built.
- `app.js` uses `defer`, so it downloads alongside parsing and runs only after the DOM is complete; the page content still appears quickly. See [async vs defer](compare:async-vs-defer).
- Remove `defer` from `app.js` and it becomes a classic script: parsing stops while it downloads and runs, so the page goes blank for longer.
- `analytics.js` uses `async`: it is independent of your page, so running it as soon as it arrives is fine.

## Rules and defaults

- **CSS blocks rendering:** the browser waits for every stylesheet in the `<head>` before it paints, so keep them small and few.
- **Classic scripts block parsing:** a `<script src>` with no `async` or `defer` stops DOM building until it runs.
- **Modules defer by default:** a `<script type="module">` behaves like `defer` without the keyword.
- **Reflow versus repaint:** changing geometry (width, height, top, left) forces layout plus paint; changing only colour or shadow forces paint but not layout, which is cheaper.
- **Compositor-only properties:** animating only `transform` and `opacity` can skip layout and paint, so such animations stay smooth.

## Not to be confused with

Reflow (layout) and repaint are not the same. Reflow recomputes the size and position of boxes, then repaints them; repaint only refills pixels when something like a colour changes, with no layout. Rule: geometry changes cause a reflow (costly); colour-only changes cause just a repaint (cheaper).

## Interview Qs

### What happens from typing a URL to seeing the page?

DNS resolves the host to an IP, TCP (and TLS for HTTPS) opens the connection, and the browser downloads the HTML. It parses HTML into the DOM and CSS into the CSSOM, combines them into the render tree, then runs layout, paint and composite. Scripts and stylesheets can block parts of this.

### What triggers a reflow, and how do you avoid extra ones?

A reflow fires when geometry changes: width, height, position, inserting nodes, or a window resize. To reduce them, batch DOM reads and writes, animate `transform` and `opacity` instead of box properties, and set width and height on images so their arrival does not shift the layout.

### Why load app code with defer instead of a plain script in the head?

A plain script in the head pauses HTML parsing while it downloads and runs, so the user stares at a blank page. A deferred script downloads in parallel with parsing and runs after the DOM is built, in document order, so content appears first and the script still sees the full page.
