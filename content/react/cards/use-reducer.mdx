## What it is

`useReducer` is a hook that manages state, like [useState](card:use-state), but it keeps the rules for changing that state in one separate function called a reducer. A reducer takes the current state and an action, and returns the next state: `(state, action) => nextState`. An action is a small object that describes what happened, such as `{ type: 'added', id: 'mouse' }`. Instead of calling a setter with the new value, your components `dispatch` an action, and the reducer works out the new state.

## Why it exists

When several event handlers all change the same piece of state, each in its own way, that update logic spreads across the component and gets hard to follow. One handler adds to the cart, another removes, a third changes a quantity, and each writes its own `setCart`. Bugs hide in that scatter. A reducer gathers every rule for updating that state into one function, so you read, log and test all the transitions in one place, and the handlers only announce what happened.

## How it works

Compare it with `useState` first; then see the cycle of dispatch and reduce.

<Compare id="usestate-vs-usereducer" />

1. You call `const [cart, dispatch] = useReducer(cartReducer, [])`, giving the reducer and the initial state.
2. An event handler calls `dispatch({ type: 'added', id })` to say what happened; it does not compute the new state itself.
3. React calls `cartReducer(currentCart, action)`, and the value it returns becomes the next state.
4. React re-renders with that new state; because the reducer returned a fresh array, React sees the change.

So the key is the split: handlers describe events, and the reducer alone decides the next state.

## Example

The dashboard's cart updates run through one reducer. Here it is called directly, as plain functions, so the output is real.

```javascript
function cartReducer(cart, action) {
  switch (action.type) {
    case 'added':   return [...cart, { id: action.id, qty: 1 }];
    case 'removed': return cart.filter((i) => i.id !== action.id);
    case 'qty':     return cart.map((i) => (i.id === action.id ? { ...i, qty: action.qty } : i));
    default:        throw new Error(`Unknown action: ${action.type}`);
  }
}
let cart = cartReducer([], { type: 'added', id: 'mouse' });
cart = cartReducer(cart, { type: 'qty', id: 'mouse', qty: 2 });
console.log(cart);
```

```text output
[ { id: 'mouse', qty: 2 } ]
```

What to notice:

- Each `case` returns a new array (`[...cart]`, `filter`, `map`) and never changes the old one, so React can detect the change.
- The reducer is pure: given the same cart and action, it always returns the same result, with no side effects.
- The handlers that would call `dispatch` carry no update logic; all of it sits in this one function.
- A reducer is just a function, so this runs outside React, which is exactly how you unit-test it.

## Rules and defaults

- **Purity:** the reducer runs during rendering and may be called more than once, so it must not fetch, set timers or mutate state; Strict Mode calls it twice in development to catch slips.
- **Stable dispatch:** React keeps `dispatch` the same across renders, so you can pass it to children or list it in dependency arrays without causing re-renders.
- **No immediate read:** `dispatch` schedules the update; the new state appears on the next render, not on the line after the call.

## Common mistakes

- **"dispatch updates state right away."** It schedules a re-render, like a state setter; the current render still holds the old value.
- **Throwing away the action object shape.** Keep a consistent `type` plus data; it is what lets you log actions and switch on them cleanly.

## Interview Qs

### When would you pick useReducer over useState?

When several event handlers change the same state in related ways, or when update bugs keep appearing. A reducer puts all those transitions in one place you can read and test. For a single simple value, `useState` is shorter and clearer.

### Why must a reducer be pure?

React calls it during rendering, sometimes more than once. It must return the same next state for the same input and must not fetch, start timers or mutate the old state. Purity makes the result predictable and lets you unit-test the reducer on its own, without a component.

### How do you share a reducer's state with deep children?

Call `useReducer` in a parent, then pass `cart` and `dispatch` down through two [contexts](card:context-api). Any child reads the cart or dispatches an action without prop drilling. Redux applies the same reducer idea across the whole app ([global state](card:global-state)).
