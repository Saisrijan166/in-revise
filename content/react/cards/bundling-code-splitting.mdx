## What it is

A bundler is a build tool, such as Vite or the one inside Next.js, that follows the `import` lines in your code and joins all those files into JavaScript the browser can load. That output is the bundle. Code splitting is cutting the bundle into smaller pieces, called chunks, so the first visit downloads only part of it. Lazy loading is fetching one of those chunks later, only when the user reaches the part that needs it.

## Why it exists

The browser must download, parse and run your JavaScript before the page can respond to clicks. If everything is in one bundle, a first-time visitor waits for code they may never use, such as a checkout flow or an admin screen, before anything is interactive. Splitting the bundle and loading parts on demand means the first screen ships only its own code, so the page becomes usable sooner.

## How it works

<Steps label="From your source files to the browser">
  <Step title="Resolve">The [bundler](card:bundler) starts at the entry file and follows every `import` to build the full list of modules.</Step>
  <Step title="Transform">It turns JSX and TypeScript into the plain JavaScript browsers run.</Step>
  <Step title="Tree-shake and minify">It drops exports that nothing imports, then shortens names and removes spaces to make the file smaller.</Step>
  <Step title="Split">Each dynamic `import()` becomes a separate chunk, loaded on demand rather than up front.</Step>
</Steps>

1. The bundler resolves every import into one module list, then transforms JSX and TypeScript to plain JavaScript.
2. Tree shaking removes exports nothing imports, and minification shrinks what is left.
3. Wherever your code uses a dynamic `import()`, the bundler puts that module in its own chunk instead of the main bundle.
4. At runtime the browser fetches a chunk only when the code reaches its `import()`, so the first load carries less.

So the key is that a dynamic `import()` is the seam the bundler splits on.

## Example

The checkout flow is heavy and most visitors never reach it, so it loads only when the user clicks to pay.

```jsx
import { lazy, Suspense, useState } from 'react';
const Checkout = lazy(() => import('./Checkout.jsx')); // module level: Checkout gets its own chunk

export default function Cart({ cart }) {
  const [paying, setPaying] = useState(false);
  if (!paying) return <button onClick={() => setPaying(true)}>Checkout</button>;
  return (
    <Suspense fallback={<p>Loading checkout…</p>}>
      <Checkout cart={cart} />
    </Suspense>
  );
}
```

What to notice:

- `lazy(() => import('./Checkout.jsx'))` tells the bundler to put `Checkout` in its own chunk; it is fetched only when `Checkout` first renders, after the user clicks.
- The `lazy(...)` call sits at module level, outside `Cart`. Inside the body it would create a new lazy component each render and reset its state.
- `Checkout` must be a `default` export, which is what `import('./Checkout.jsx')` resolves to.
- `Suspense` shows the `fallback` while the chunk is downloading; without a Suspense boundary above a lazy component, React throws.

## Rules and defaults

- **React.lazy needs a default export:** the imported module's `default` is used as the component.
- **A Suspense boundary is required:** a lazy component must render inside a `<Suspense>` with a `fallback`, or React throws while it loads.
- **Declare lazy at module level:** calling `lazy()` inside a component body recreates the component each render and loses its state.
- **Tree shaking needs ES modules:** static `import`/`export` lets the bundler see which exports are used before any code runs; `require()` with a computed path cannot be shaken reliably.
- **New apps:** Create React App was deprecated on 14-02-2025; use Next.js 16 or Vite 8 instead.

## Interview Qs

### What is the difference between code splitting and lazy loading?

Code splitting is the build-time step that cuts the bundle into separate chunks. Lazy loading is the runtime behaviour of fetching a chunk only when it is needed, for example `React.lazy` loading the checkout page's chunk the first time it renders. Splitting creates the chunks; lazy loading decides when each one is fetched.

### Why must lazy() be declared outside the component?

Calling `lazy()` inside the component body creates a brand-new lazy component on every render. React sees a different component each time and resets its state and remounts it. Declaring it once at module level means the same lazy component is reused across renders, so its state and loaded chunk persist.

### Why does tree shaking need ES modules?

Static `import` and `export` are fixed at the top of a file, so the bundler can tell which exports are actually imported before running any code, and drop the rest. CommonJS `require()` can take a computed path and run conditionally, so the bundler cannot be sure an export is unused and must keep it.
