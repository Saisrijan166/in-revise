## Why it exists

A plain local variable starts again on every render, and changing it does not update the screen. State is kept by React between renders, and setting it triggers a new one.

## How it works

<Steps label="What happens after a click">
  <Step title="Set">The handler calls setQty; React queues the update.</Step>
  <Step title="Batch">React waits until the whole handler has run.</Step>
  <Step title="Re-render">It calls the component again with the new state.</Step>
  <Step title="Commit">The DOM shows the new quantity.</Step>
</Steps>

- Copying a prop into state stops following the prop: use the prop directly.
- What else causes re-renders: [re-renders](card:re-renders).

## Example

```jsx
const [qty, setQty] = useState(1);
const total = qty * product.price;        // derived, not state

function addTwo() {
  setQty(qty + 1);
  setQty(qty + 1);                        // both read 1: qty becomes 2
}
function addTwoSafely() {
  setQty(q => q + 1);
  setQty(q => q + 1);                     // each gets the latest: 1 → 3
}
setCart([...cart, product]);              // new array, not cart.push()
```

## Interview Qs

### Why does console.log right after setState print the old value?

State is a snapshot for the current render. The setter only queues the change; the new value exists in the next render.

### What is batching?

React waits until an event handler finishes, then applies all its state updates in one re-render. Since React 18 this also happens in timeouts, promises and native event handlers.

### Why must state not be mutated?

React compares the old and new value with `Object.is`. A mutated object is still the same reference, so React may skip the render. Create a new object or array with spread, `map` or `filter`.
