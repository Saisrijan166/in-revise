## What it is

A **component** is a JavaScript function that takes one object of inputs, called **props**, and returns [JSX](card:what-is-react) describing what to show. You build a UI by composing small components: a `PaymentRow` inside a `PaymentList` inside a page. **Props** are how a parent passes data into a child, like passing `payment` to a `PaymentRow`. The child reads its props but is not allowed to change them.

## Why it exists

A whole page written as one block is hard to read, reuse and test. Splitting it into components lets you write `PaymentRow` once and use it for every payment. Props make that reuse possible: the same `PaymentRow` function shows a different payment each time, just by receiving a different `payment` prop. Without props, each row would need its own copy of the code.

## How it works

JSX looks like HTML but is JavaScript, so it follows a few rules:

| JSX rule | Write | Not |
|---|---|---|
| One root element | `<>...</>` or one wrapper | two siblings at the top |
| Close every tag | `<img />` | `<img>` |
| camelCase attributes | `className`, `onClick` | `class`, `onclick` |
| JavaScript goes in braces | `{payment.amount}` | `"payment.amount"` |

Data then flows in one direction:

1. The parent owns the data as its [state](card:use-state) and passes pieces of it down to each child as props.
2. The child reads its props and returns JSX. It treats props as read-only.
3. When the child needs something to change, it calls a **callback prop** (a function the parent passed down, such as `onRefund`).
4. The parent runs that callback, updates its own state, re-renders, and the new value flows back down as fresh props.

So the key is that data always moves down, and change requests always move up through callbacks.

## Example

`PaymentRow` receives a `payment` to show and an `onRefund` callback to call when the button is clicked.

```jsx
function PaymentRow({ payment, onRefund }) {
  return (
    <tr>
      <td>{payment.id}</td>
      <td>₹{payment.amount}</td>
      <td>{payment.status}</td>
      <td><button onClick={() => onRefund(payment.id)}>Refund</button></td>
    </tr>
  );
}

<PaymentRow payment={{ id: 1, amount: 799, status: 'PAID' }} onRefund={refund} />
```

What to notice:

- `{ payment, onRefund }` destructures the one props object into the two inputs the row uses.
- The row never changes `payment`; it only reads fields like `payment.amount` inside braces.
- The button does not do the refund itself. It calls `onRefund(payment.id)`, handing the request up to the parent, which owns the payments.
- Remove `onRefund` from the props and the button could no longer tell the parent anything, because a child cannot reach into the parent directly.

## Rules and defaults

- **Props are read-only:** React assumes a component does not change its props; mutating them does not trigger a re-render and breaks one-way data flow (React 19).
- **Default values:** `function Row({ qty = 1 })` uses `1` only when the prop is missing or `undefined`, not when it is `null`.
- **`children` prop:** JSX nested between a component's tags arrives as `props.children`, so a wrapper can render whatever it is given.
- **Falsy rendering:** React renders nothing for `false`, `null` and `undefined`, but it does render `0` and `''`; guard with `count > 0 &&`.

## Not to be confused with

**Props** are inputs passed in from the parent and are read-only in the child. **State** is a component's own internal memory that it can change (see [state vs props](compare:state-vs-props)). A **callback prop** is just a prop whose value is a function; it lets a child trigger logic that lives in the parent. Rule: props come in from above, state is owned here, callbacks send requests up.

## Interview Qs

### How does a child component send data to its parent?

The parent passes a function down as a prop, such as `onRefund={refund}`. The child calls that function with the data, for example `onRefund(payment.id)`. The parent runs it, updates its own state, and the new value flows back down to the child as props. Data never flows upward directly.

### Why are props read-only, and what breaks if you mutate them?

Props belong to the parent, which owns that data. Mutating the child's copy does not change the parent's state and does not queue a re-render, so the screen and the data drift apart. One-way data flow relies on the child only reading props and asking for changes through callbacks.

### What are Fragments and when do you use them?

A Fragment, written `<>...</>`, groups several elements so a component can return one root without adding an extra wrapper node to the real DOM. Use `<Fragment key={id}>` when each item in a list needs a key but you do not want a wrapper element around it.
