## What it is

Lifting state up means moving a piece of [state](card:use-state) out of a component and into a parent, so that more than one component can read the same value. State colocation is the opposite move: keeping each piece of state in the lowest component that actually uses it. Together they answer one question for every value: which component should own it. The owner holds the `useState`; everyone else receives the value as a prop.

## Why it exists

A payments screen has a status filter and a list of payments, and both need the chosen status. If each keeps its own `useState`, there are two copies of the status, and changing the filter does not change the list: they drift apart. Giving the value one owner fixes this. The common parent holds the status and passes it to both the filter and the list, so there is a single source of truth and they always agree.

## How it works

1. Find the two components that need the same value, and find their closest common parent in the tree.
2. Remove the `useState` from the children and add it to that parent instead.
3. Pass the value down to each child as a prop.
4. Pass a callback down too, so a child can ask the parent to change the value; the child never changes it directly.
5. When the callback runs, the parent updates its state, re-renders, and both children receive the new value.

So the key is: lift only the shared value, and no higher than the closest common parent.

## Example

`PaymentsPage` owns the status; the filter and the list both read it through props.

```jsx
import { useState } from 'react';

export default function PaymentsPage({ payments }) {
  const [status, setStatus] = useState('all');          // lifted: both children need it
  const shown = status === 'all'
    ? payments
    : payments.filter((p) => p.status === status);
  return (
    <>
      <StatusFilter status={status} onStatusChange={setStatus} />
      <PaymentList payments={shown} />
    </>
  );
}
```

What to notice:

- The `status` lives only in `PaymentsPage`. `StatusFilter` shows it and `PaymentList` reads the filtered result; neither keeps its own copy.
- `onStatusChange={setStatus}` is the callback the child calls to change the value. Data flows down as props; change requests flow up as calls.
- `shown` is derived from `status` and `payments` during render, so it is never stale and needs no state of its own.
- If each child kept its own `useState('all')` instead, picking a status in the filter would leave the list unfiltered, because they would be two unrelated values.

## Rules and defaults

- **One owner per value:** put each piece of state in exactly one component. A second copy is a bug waiting to drift.
- **Lift to the closest common parent, not higher:** lifting past it forces middle components to forward props they do not use (prop drilling).
- **Derive, do not store:** a value you can compute from props or state (like `shown`) should be computed in render, not kept in its own `useState`.
- **Colocate the rest:** state only one component uses stays in that component, so an update re-renders only its subtree.

## Not to be confused with

Lifting state up is about moving state *up* to a shared parent so siblings agree. State colocation is about keeping state *down* in the one component that uses it, so updates stay cheap. They are two sides of the same rule: state belongs with its single owner. [Context](card:context-api) is a different tool again: it carries a value to far-apart components without threading props, and you reach for it only after lifting is not enough.

## Common mistakes

- **"Shared state should be as high as possible."** No. The higher it lives, the more components re-render on each change and the more props are drilled through. Put it at the closest common parent, no higher.
- **"Derived data needs its own state."** A filtered list computed from `status` and `payments` is derived; store it in state and you must keep it in sync by hand. Compute it during render instead.

## Interview Qs

### What does "lifting state up" mean, and when do you do it?

It means moving state from a child into a shared parent so two or more components can use the same value. You do it when sibling components must agree on something, such as a filter and the list it filters. The parent owns the state and passes it down as props, with a callback for changes.

### What is prop drilling, and how do you reduce it?

Prop drilling is passing a prop through components that do not use it, only to reach a deep child. You reduce it by passing JSX as `children` so middle layers never see the prop, or, when the value is needed far apart, by using [Context](card:context-api) or a [store](card:global-state).

### What is state colocation, and why does it help performance?

Colocation is keeping state in the lowest component that uses it. A change then re-renders only that small subtree, not the whole page, so components that do not use the value are skipped. Lifting state higher than needed makes more of the tree re-render on every change.
