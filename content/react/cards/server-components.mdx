## Why it exists

Shipping every component to the browser makes bundles big and puts data fetching behind extra API calls. Server Components keep non-interactive UI and its data access on the server.

## How it works

<Compare id="server-vs-client-components" />

- On first load, Client Components are also prerendered to HTML, then [hydrated](card:hydration).
- A Server Component can pass another Server Component to a Client Component as `children`.
- [Server Functions](card:server-functions) (`'use server'`) let the client call server code, such as a form action.

## Example

```jsx
// app/products/[id]/page.jsx: a Server Component (the default)
import AddToCartButton from './AddToCartButton';
export default async function ProductPage({ params }) {
  const product = await db.products.find((await params).id); // server only
  return <main><h1>{product.name}: ₹{product.price}</h1><AddToCartButton id={product.id} /></main>;
}

// app/products/[id]/AddToCartButton.jsx
'use client';
export default function AddToCartButton({ id }) {
  return <button onClick={() => addToCart(id)}>Add to cart</button>; // addToCart: cart context
}
```

## Interview Qs

### When do you need 'use client'?

For state, Effects, event handlers, browser APIs such as `localStorage`, and custom hooks that use them. Put it at the top of the smallest file that needs them, not on the whole app.

### Can a Server Component use useState or Context?

No. It cannot use state or Effects, and cannot create Context. It can render a Client Component provider, and Client Components inside it read the value.

### Is it safe to read secrets in a Server Component?

Yes: its code stays on the server. In Next.js only `NEXT_PUBLIC_` variables reach the browser. Server Function arguments come from the client, so validate them and check the user.
