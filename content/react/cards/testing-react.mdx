## Why it exists

Tests tied to internals break on every refactor yet miss real bugs. Testing like a user gives confidence that the shop still works after changes.

## How it works

| Query priority | Use for |
|---|---|
| 1. `ByRole` | Almost everything: buttons, links, headings, inputs |
| 2. `ByLabelText` | Form fields |
| 4. `ByText` | Non-interactive text (3 is `ByPlaceholderText`) |
| Last: `ByTestId` | Only when nothing above fits |

- `ByRole` finds what has a role and an accessible name: [semantic HTML](card:semantic-html-accessibility) gives both.
- `findBy` is `getBy` plus `waitFor`; await it for anything that appears after a fetch.
- [MSW](card:msw) intercepts requests at the network level, so the component's `fetch` stays unchanged.

## Example

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { test, expect } from 'vitest';
import ProductList from './ProductList'; // API mocked with MSW

test('search filters the products', async () => {
  const user = userEvent.setup();
  render(<ProductList />);
  await user.type(screen.getByRole('searchbox'), 'mouse'); // <input type="search">
  await screen.findByText('Wireless Mouse');
  expect(screen.queryByText('Laptop Stand')).toBeNull();
});
```

## Interview Qs

### getBy vs queryBy vs findBy?

`getBy` throws when nothing matches, `queryBy` returns null (use it to assert absence), and `findBy` returns a Promise that retries until the element appears or times out. All three throw on more than one match.

### Why user-event instead of fireEvent?

`fireEvent` dispatches one event. user-event simulates the full interaction a browser would produce, such as focus, key presses and input, and refuses to click hidden or disabled elements.

### Are snapshot tests enough?

No. They only flag that output changed. Keep them small, review them like code, and never update them with `-u` without checking why they failed.
