## What it is

A React test renders a component into a test DOM, acts on it the way a user would, and checks the result. The common tools are React Testing Library, which finds elements by role, label or text; [user-event](card:user-event), which simulates real clicks and typing; and [MSW](card:msw), which fakes HTTP responses so the component's own [fetch](card:data-fetching) calls are unchanged. Tests come in three sizes: unit (one piece), integration (a few pieces together) and end-to-end (the whole app in a real browser, usually with Playwright).

## Why it exists

A test that reads a component's state or checks its CSS class names breaks whenever you refactor, even when nothing the user sees has changed, and it can pass while the visible button is broken. The point of a test is confidence that the app still works for the user. Finding elements the way a user does, by their visible text and role, gives that confidence: the test only fails when the real behaviour changes, and writing it the accessible way nudges the markup towards being usable with a screen reader.

## How it works

React Testing Library offers several queries. Prefer the ones highest in this list, because they match how a real user finds things.

| Query | Use for |
|---|---|
| `getByRole` | Almost everything: buttons, links, headings, inputs |
| `getByLabelText` | Form fields, found by their visible label |
| `getByText` | Non-interactive text such as a paragraph |
| `getByTestId` | Last resort, only when nothing above fits |

1. Render the component with `render(<Component />)`.
2. Find an element with a query. `getByRole` needs the element to have a role and an accessible name, which [semantic HTML](card:semantic-html-accessibility) provides.
3. Act on it with `user-event`, which performs the full browser interaction, not a single event.
4. For anything that appears after a fetch, await a `findBy` query, which retries until the element shows up or times out.

So the key is: query the way a user would look, act the way a user would act, and assert on what a user would see.

## Example

This test types into a search box and checks that the list filters. The API is faked with MSW, so no real network call happens.

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { test, expect } from 'vitest';
import ProductList from './ProductList'; // its fetch is intercepted by MSW

test('search filters the products', async () => {
  const user = userEvent.setup();
  render(<ProductList />);
  await user.type(screen.getByRole('searchbox'), 'mouse'); // an <input type="search">
  await screen.findByText('Wireless Mouse'); // waits for the filtered result
  expect(screen.queryByText('Laptop Stand')).toBeNull(); // now absent
});
```

What to notice:

- `getByRole('searchbox')` finds the input by its role, so renaming its CSS class or wrapping it in a `<div>` does not break the test.
- `findByText` is awaited because the filtered list appears after an async update; `getByText` would throw immediately, before the list changed.
- `queryByText(...).toBeNull()` is the correct way to assert absence. `getByText` would throw instead of returning null, failing the test for the wrong reason.

## Rules and defaults

- **`findBy` and `waitFor` timeout:** retries for 1000 ms by default before failing, in Testing Library.
- **Single-match queries throw on duplicates:** `getBy`, `queryBy` and `findBy` all throw when more than one element matches; use the `getAllBy` family for lists.
- **user-event is async:** its methods return Promises, so `await` them, and call `userEvent.setup()` once per test.
- **Tool versions:** Vitest 5 or Jest 30 as the runner, React Testing Library 16, which works with either.

## Common mistakes

- **"Snapshot tests prove the component works."** A snapshot only flags that the output changed, not whether the change is correct. Keep snapshots small, review them like code, and never blindly update them with `-u`.
- **"Test every component in isolation as a unit."** Isolated unit tests miss how pieces work together. Integration tests, which render a component with its real children, catch more real bugs for the effort.

## Interview Qs

### What is the difference between getBy, queryBy and findBy?

`getBy` returns the element or throws if it is missing, for things that must be present now. `queryBy` returns null instead of throwing, which is how you assert something is absent. `findBy` returns a Promise that retries until the element appears or times out, for UI that shows after a fetch. All three throw when more than one element matches.

### Why use user-event instead of fireEvent?

`fireEvent` dispatches a single raw event. `user-event` simulates the full interaction a real browser produces, such as focusing, pressing keys and firing input events, and it refuses to click a hidden or disabled element. That makes tests behave like a real user and catch bugs that `fireEvent` would walk straight past.

### How do you test a component that fetches data?

Fake the network with MSW, which intercepts the request at the HTTP level so the component's own `fetch` code is unchanged. Render the component, then await a `findBy` query for the content that appears once the request resolves. This tests the real loading and success path without hitting a server.
