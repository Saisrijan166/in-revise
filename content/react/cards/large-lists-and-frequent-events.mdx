## What it is

This concept covers two slow spots that show up at scale. The first is a long list: a page that puts thousands of rows into the DOM at once. The second is a frequent event: typing, scrolling or resizing, which fire an event many times a second. The fixes are virtualization for the list, and debounce or throttle for the events. The [comparison](compare:debounce-vs-throttle) below separates debounce from throttle.

## Why it exists

The browser has to create and lay out every DOM node, so 10,000 rows make the first render and every scroll slow, even though only about twenty rows are visible. Separately, a keystroke or a scroll fires its event on each small change; doing heavy work, or calling an API, for every one of those is wasted effort and can overwhelm the server. These techniques cut the DOM down to what is seen and cut the work down to what is needed.

## How it works

Pick the fix by the shape of the problem: too many nodes, or too many events.

<Compare id="debounce-vs-throttle" />

1. For a long list, virtualize: keep only the rows inside the viewport in the DOM, plus a small overscan so scrolling shows no blank gap, and replace them as the user scrolls. [TanStack Virtual](card:tanstack-virtual) or [react-window](card:react-window) do this; pagination or infinite scroll is an alternative.
2. For a search box, debounce the work: restart a short timer on each keystroke and act only when the timer finally fires, so one API call is made after typing stops.
3. For scroll or resize, throttle the handler: run it, then ignore further events until an interval passes, so it runs at a steady maximum rate during the activity.
4. If the slow part is rendering and not a network call, reach for [useDeferredValue](card:use-deferred-value) instead of a timer: it has no fixed delay and its background render can be interrupted.

## Example

A debounce wraps a function so it runs only after calls stop for the given delay. This is a common coding-round question.

```javascript
function debounce(fn, ms) {
  let timer;                                 // kept alive by the closure between calls
  return (...args) => {
    clearTimeout(timer);                     // a new key press cancels the pending call
    timer = setTimeout(() => fn(...args), ms);
  };
}
const search = debounce((q) => console.log(`GET /api/payments?q=${q}`), 300);
['m', 'mo', 'mou', 'mous', 'mouse'].forEach((q, i) => setTimeout(() => search(q), i * 100));
```

```text output
GET /api/payments?q=mouse
```

What to notice:

- `timer` lives in the [closure](card:closures), so it survives between calls; each call can clear the previous timer.
- Every keystroke fires within the 300 ms window, so each `clearTimeout` cancels the pending run; only the last one, 300 ms after the final `mouse`, actually fires.
- The output is a single request for the final value `mouse`, not one per keystroke, which is the point of debouncing.
- Change the gap in the `forEach` to 400 ms (longer than 300) and each keystroke would complete its own call, printing five lines.

## Rules and defaults

- **Virtualization keeps the DOM small:** only visible rows plus overscan exist; TanStack Virtual's default overscan is 1 extra row.
- **Debounce timing:** the delay is how long a pause must last before the work runs; a new event during the wait restarts it.
- **Throttle timing:** the interval is the minimum gap between two runs; events in between are ignored.
- **Debounce still needs stale-response handling:** it cuts the number of calls, but you must still [ignore an out-of-order response](card:data-fetching) so an old reply does not overwrite a newer one.

## Interview Qs

### How would you render a list of 10,000 payments without the page freezing?

Virtualize it: render only the roughly twenty rows in the viewport plus a small overscan, and swap them as the user scrolls, using a library like TanStack Virtual or react-window. The DOM then holds about twenty rows instead of ten thousand. Pagination or infinite scroll, loading fewer rows at a time, is an alternative.

### Write a debounce function.

Keep a timer variable in a closure. The returned function clears the previous timer on each call and starts a new one with `setTimeout`. The wrapped function runs only when calls stop for the given delay, because each new call cancels the pending run. See the example above.

### For a search box, would you debounce or use useDeferredValue?

Debounce the network request, because that is what reduces the number of API calls. `useDeferredValue` does not cut calls; it helps when the render itself is slow, by letting React keep showing the old UI while the heavy render happens in the background and can be interrupted. The two can be combined.
