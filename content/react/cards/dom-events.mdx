## What it is

When you click something, the browser does not just notify the clicked element. The event makes a round trip through its ancestors: first down from the top to the clicked element (the capturing phase), then the element itself (the target phase), then back up through the ancestors (the bubbling phase). [Event delegation](term:event-delegation) is the trick this makes possible: you add one listener to a parent and let bubbling bring every child's event up to it, so one handler serves many elements.

## Why it exists

A product list can hold hundreds of buttons, and rows are added and removed as the user filters. Attaching a separate click listener to every button is wasteful and, worse, a button added after you wired things up has no listener at all. Because events bubble up to ancestors, a single listener on the list receives clicks from every button inside it, present or future. You read `event.target` to see exactly which one was clicked.

## How it works

1. The click starts at the top and travels down through each ancestor to the clicked element; this is the capturing phase, where only listeners added with `capture: true` run.
2. The event reaches the clicked element, the target.
3. The event travels back up through the same ancestors; this is the bubbling phase, where ordinary listeners run. On each ancestor, `event.target` is still the clicked element while `event.currentTarget` is that ancestor.
4. A listener may call `preventDefault()` to cancel the browser's built-in action, or `stopPropagation()` to stop the event continuing its travel.

## Example

One listener on the product list handles clicks from any button inside it, and the click still bubbles on to the body.

```javascript
const list = document.querySelector("#product-list");
list.addEventListener("click", (event) => {
  const button = event.target.closest("button[data-id]");
  if (!button) return;
  console.log("add", button.dataset.id, "| listener on", event.currentTarget.id);
});
document.body.addEventListener("click", () => console.log("body heard it too"));
document.querySelector('[data-id="cable"]').click();
```

```text output
add cable | listener on product-list
body heard it too
```

What to notice:

- `event.target` is the clicked button, but `event.currentTarget` is the product list, the element whose listener is running: that is why one listener can serve many buttons.
- `closest("button[data-id]")` walks up from the clicked element to find the button, so a click on an icon inside the button still works.
- The click still reaches the body listener, because nothing called `stopPropagation`; the event keeps bubbling.

## Rules and defaults

- **Listener phase:** by default a listener runs during bubbling. Pass `{ capture: true }` as the third argument to `addEventListener` to run it during capturing instead.
- **target vs currentTarget:** `event.target` is the element the event started on and does not change; `event.currentTarget` is the element handling it now.
- **preventDefault vs stopPropagation:** the first cancels the default action (link navigation, form submit); the second stops the event travelling further. They are independent.
- **Passive listeners:** `{ passive: true }` promises the listener will not call `preventDefault`. It is the default for `wheel`, `mousewheel`, `touchstart` and `touchmove` on `window`, `document`, `<html>` and `<body>`, so scrolling is not delayed.

## Interview Qs

### What is event delegation, and why is it useful?

You attach one listener to a shared parent instead of one per child, then read `event.target` (often with `closest`) to find which child was clicked. It uses fewer listeners, and children added to the DOM later are handled automatically because the event still bubbles up to the parent.

### What is the difference between preventDefault and stopPropagation?

`preventDefault` cancels the browser's built-in response to the event, such as following a link or submitting a form; the event still bubbles. `stopPropagation` stops the event moving to the next element in its path; the default action still happens unless you also prevent it. They solve different problems.

### What does passive: true do on a listener?

It tells the browser the listener will not call `preventDefault`, so the browser can start scrolling immediately instead of waiting to see. It is already the default for touch and wheel events on the top-level nodes, which keeps scrolling smooth.
