## What it is

A re-render is React calling your component function again to work out what the UI should now look like. The function runs, reads its current [state](card:use-state) and props, and returns JSX, which is React's description of the UI. A re-render by itself is just this recalculation. It is a separate step from changing the real page, which React does afterwards and only where needed.

## Why it exists

Something has to decide what changes on screen when data changes. Without re-rendering you would hunt down each DOM node and update it by hand after every click or response, which is error-prone. React instead re-runs the component to get the new JSX, compares it with the old, and updates only the parts that differ. You change state; React works out the rest.

## How it works

1. A trigger fires: the component's own state changes, its parent re-renders, or a context it reads gets a new value.
2. React calls the component function again. It computes fresh JSX from the current state and props.
3. React compares the new JSX with the previous output. This comparison is called reconciliation.
4. If some output changed, React updates only those DOM nodes and the browser paints. If nothing changed, the DOM is left untouched.

So the key is that running the component is cheap; only a real DOM change costs much.

## Example

In the payments dashboard, a status filter and the list of rows start in one component. Moving the filter state down means flipping it no longer re-runs the whole list.

```jsx
import { useState } from 'react';

function Dashboard({ payments }) {
  return (                            // flipping the filter re-renders only FilterBar
    <main>
      <FilterBar />
      <PaymentList payments={payments} />
    </main>
  );
}

function FilterBar() {
  const [status, setStatus] = useState('all'); // state kept low, next to its use
  return <button onClick={() => setStatus(status === 'all' ? 'failed' : 'all')}>{status}</button>;
}
```

What to notice:

- `status` lives inside `FilterBar`, so changing it re-renders only `FilterBar`, not `Dashboard` or `PaymentList`.
- If `status` instead lived in `Dashboard`, every click would re-render `Dashboard`, which re-runs `PaymentList` and all its rows.
- `PaymentList` still re-renders when its `payments` prop truly changes, because that means `Dashboard` re-rendered with new data.
- This is the first and cheapest fix: keep state low. You reach for [memo](card:memoization) only when moving state is not enough.

## Rules and defaults

- **Three triggers:** a re-render happens only on the component's own state change, a parent re-render, or a new value from a context it reads. Nothing else re-renders it.
- **Props are not a trigger:** a child re-renders because its parent did; the new props are a result of that, not the cause.
- **A parent re-renders its children:** by default every child runs again when the parent does, whatever its props. [React.memo](card:memoization) is how you opt a child out.
- **Re-render is not commit:** React first re-renders (computes JSX), then commits (updates the DOM) only where output differs.

## Common mistakes

- **"Fewer re-renders is always the goal."** The goal is a fast UI. A re-render that does light work is fine; profile first, and optimise only a re-render that profiling shows is slow and frequent.
- **"memo is the first thing to reach for."** The cheaper fixes come first: keep state low so fewer components re-render, or pass a slow subtree as `children` so it is created outside and skipped. Add `memo` only after those are not enough.

## Interview Qs

### Is a re-render the same as a DOM update?

No. A re-render runs the component function to compute JSX. React then reconciles the new output against the old and, in the commit step, changes only the DOM nodes whose output differs. If nothing differs, the DOM is not touched at all, so a re-render can cost almost nothing.

### What are the three things that trigger a re-render?

Its own state changing, its parent re-rendering, or a context it reads getting a new value. New props do not trigger a re-render on their own; a child receives new props only because its parent re-rendered.

### A small toggle re-renders a big list next to it. How do you stop that?

Move the toggle state into its own small component, so flipping it no longer re-runs the parent that holds the list. If the list must stay under the same parent, pass it as `children`. Use `memo` on the list only if those do not help.
