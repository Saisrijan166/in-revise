## What it is

Semantic HTML means choosing each element for its meaning, not its looks: a `<button>` for an action, an `<a>` for a link, `<nav>` for navigation, `<label>` for a field name. Accessibility (often written a11y) is making the page usable by people who navigate with a keyboard, a screen reader (software that reads the page aloud) or other assistive tools. Semantic elements are the base of accessibility, because the browser already knows how each one behaves. In the [DOM](card:how-browsers-render) you met earlier, these are the nodes that carry meaning.

## Why it exists

A screen reader, a keyboard and a search engine understand a page only through its elements. A `<div>` with a click handler looks like a button on screen, but to a screen reader it is just a box, and a keyboard user cannot tab to it or press it. Rebuilding that behaviour by hand (focus, Enter, Space, the correct announced role) is a lot of error-prone code. A real `<button>` gives all of it for free, so the right element is less work and more correct.

## How it works

Match each need to the element that already means it:

| Need | Use | Not |
|---|---|---|
| A click action | `<button>` | `<div onClick>` |
| Navigate to a URL | `<a href>` | `<span onClick>` |
| Page regions | `<header>`, `<nav>`, `<main>`, `<footer>` | plain `<div>`s |
| Image meaning | `alt="Wireless mouse"` | an image with no `alt` |
| Field name | `<label htmlFor="q">` | an input with no label |

1. Reach for the native element whose meaning matches what you are building.
2. Give images an `alt` (descriptive, or empty for decoration) and inputs a `<label>`.
3. Keep headings in order (one `h1`, then `h2`, `h3`) so the page has an outline users can jump through.
4. Only when no native element fits (a custom tabs widget, say) add an ARIA role, and then write the keyboard behaviour yourself.

So the key is: native element first, ARIA last.

## Example

In JSX the label is tied to the input with `htmlFor` (JSX spells the `for` attribute this way, because `for` is a reserved word in JavaScript).

```jsx
function SearchBox({ query, onQueryChange }) {
  return (
    <form>
      <label htmlFor="q">Search products</label>
      <input id="q" value={query} onChange={(e) => onQueryChange(e.target.value)} />
      <button type="submit">Search</button>
    </form>
  );
}
```

What to notice:

- `htmlFor="q"` matches the input's `id="q"`, so clicking the label focuses the field and a screen reader announces "Search products" when the field gets focus.
- The submit control is a real `<button type="submit">`, so pressing Enter in the field submits the form with no extra key handling.
- Remove the `<label>` and the input has no accessible name: a screen reader just says "edit text", leaving the user unsure what to type.

## Rules and defaults

- **ARIA first rule:** if a native HTML element gives the behaviour you need, use it instead of adding an ARIA role to a generic element.
- **A role is only a name:** `role="button"` changes what a screen reader announces, not what the element does; you still have to add the keyboard handling.
- **Contrast (WCAG 2.2 AA):** normal text needs a contrast ratio of at least 4.5:1, large text at least 3:1.
- **Visible focus:** do not set `outline: none` without providing another visible focus style, or keyboard users lose track of where they are.
- **tabindex:** add `tabindex="0"` only to custom interactive controls; native controls are already in the tab order.

## Interview Qs

### Why prefer semantic HTML over styled divs?

Assistive tech and search engines read the meaning of elements. Landmarks and headings let screen-reader users jump around the page, native buttons and links work with the keyboard out of the box, and search engines weigh headings and links more than plain divs. A styled `<div>` conveys none of this.

### When should you use ARIA, and what is the risk?

Only when no native element does the job, such as a custom tabs or combobox widget. The risk is that a role is a promise: `role="button"` makes a screen reader say "button", but if you do not also handle focus and key presses, the control is broken for keyboard users. No ARIA is better than wrong ARIA.

### How do you make a custom interactive page keyboard accessible?

Prefer native controls so Tab, Enter and Space work without effort. Keep the source order logical, since Tab follows it. Never remove the focus outline without a replacement. For any custom control, add `tabindex="0"` to make it reachable and handle the keys that the matching native element would handle.
