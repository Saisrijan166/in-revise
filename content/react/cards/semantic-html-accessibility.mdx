## Why it exists

Screen readers, keyboards and search engines understand a page through its elements. A div with a click handler looks fine but tells them nothing.

## How it works

| Need | Use | Not |
|---|---|---|
| A click action | `<button>` | `<div onClick>` |
| Page regions | `<header>`, `<nav>`, `<main>`, `<footer>` | plain `<div>`s |
| Image meaning | `alt="Wireless Mouse"` | no `alt` at all |
| Field name | `<label htmlFor="q">` | an unlabelled input |
| Focus | a visible `:focus-visible` outline | `outline: none` with no replacement |

- First rule of ARIA: use a native element when one exists; ARIA adds meaning, not behaviour.
- WCAG 2.2 has levels A, AA and AAA; Contrast (1.4.3) and Focus Visible (2.4.7) are AA.
- Tests that find elements by role check this too: [testing React](card:testing-react).

## Example

```jsx
function SearchBox({ query, onQueryChange }) {
  return (
    <form>
      <label htmlFor="q">Search products</label>
      <input id="q" value={query} onChange={(e) => onQueryChange(e.target.value)} />
      <button type="submit">Search</button>
    </form>
  );
}
```

## Interview Qs

### Why use semantic HTML?

Assistive tech reads the meaning: landmarks and headings let screen reader users jump around, buttons work with the keyboard, and search engines weigh headings and links more than plain divs.

### When should you use ARIA?

Only when no native element does the job, such as a custom tabs widget. A role is a promise: you must also build the keyboard behaviour. No ARIA is better than bad ARIA.

### How do you make a page keyboard accessible?

Use native controls so Tab, Enter and Space work, keep a logical source order, never remove the focus outline without a replacement, and add `tabindex="0"` only to custom controls.
