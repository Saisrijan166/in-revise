## Why it exists

A blank page waiting for JavaScript is slow to show and harder for crawlers to read. Where and when HTML is built trades speed, freshness and server cost.

## How it works

<Compare id="csr-vs-ssr-vs-ssg-vs-isr" />

- [Hydration](card:hydration) attaches React to server HTML with `hydrateRoot`; until then the page shows but does not respond.
- [Streaming SSR](card:streaming-ssr) sends HTML in chunks, so the browser paints before the slowest data arrives.
- Server HTML helps LCP; heavy hydration JS can hurt INP. [Measure both](card:measuring-performance).

## Example

```jsx
// app/products/[id]/page.jsx (Next.js 16, without Cache Components)
export const revalidate = 3600; // ISR: regenerate at most once an hour

export async function generateStaticParams() {
  return [{ id: '1' }, { id: '2' }]; // prerendered at build time
}

export default async function ProductPage({ params }) {
  const { id } = await params;
  const product = await fetch(`https://shop.example/api/products/${id}`).then((r) => r.json());
  return <h1>{product.name}: ₹{product.price}</h1>;
}
```

## Interview Qs

### What is hydration, and what causes a mismatch?

Hydration attaches React and its event handlers to server-rendered HTML. A mismatch happens when the first client render differs: `typeof window` checks, browser-only APIs, timestamps or different data. Treat it as a bug; show client-only values after an Effect.

### Which rendering would you pick for an online shop?

Product pages: ISR, fast like static and refreshed hourly. Search results: SSR, they depend on the query. Cart: CSR in a Client Component, private and interactive. Help pages: SSG.

### Is SSR always faster than CSR?

No. SSR usually paints sooner, but rendering per request can raise TTFB, and the page still waits for hydration before it responds. Static HTML from a CDN is fastest.
