## What it is

A rendering strategy decides **where** a page's HTML is built (in the browser or on a server) and **when** (once at build time, or freshly for each request). The four common choices are CSR, SSR, SSG and ISR. They are not React features; they are deployment choices a framework like Next.js makes for you per page. The strategy only decides the first HTML the browser receives. After that, React takes over through [hydration](card:hydration): it attaches event handlers to the HTML so clicks and typing work.

## Why it exists

A pure [client-rendered](card:what-is-react) app sends near-empty HTML and makes the browser build everything with JavaScript. The user sees a blank page until the JS loads and runs, and a search crawler may see no content at all. Building the HTML on a server instead means the first thing the browser receives already shows the page, so it paints sooner and crawlers read it. Each strategy picks a different point on the trade-off between first-paint speed, how fresh the data is, and how much server work each visit costs.

## How it works

<Compare id="csr-vs-ssr-vs-ssg-vs-isr" />

1. The browser asks for a page. What comes back depends on the strategy: near-empty HTML (CSR), HTML built right now on the server (SSR), or a pre-built HTML file (SSG and ISR).
2. The browser paints that HTML. With SSR, SSG and ISR the user already sees content; with CSR they see a blank page or a spinner.
3. The page's JavaScript downloads and React [hydrates](card:hydration) the HTML, attaching event handlers so the page becomes interactive.
4. With ISR, once the page is older than its revalidate time, the next request still gets the old page instantly, and the server rebuilds it in the background for later visitors.

So the key is: server-built HTML trades a little server work for a faster first paint and readable content, while CSR pushes all the work to the browser.

## Example

In the Next.js App Router, this product page is prerendered at build time (SSG) and refreshed hourly (ISR). The `'use cache'` directive marks the function as cacheable, and `cacheLife('hours')` sets the refresh interval.

```jsx
// app/products/[id]/page.jsx — needs cacheComponents: true in next.config
import { cacheLife } from 'next/cache';

async function getProduct(id) {
  'use cache';
  cacheLife('hours'); // after 1 hour: serve old page, rebuild in the background
  const res = await fetch(`https://shop.example/api/products/${id}`);
  return res.json();
}
export const generateStaticParams = () => [{ id: '1' }, { id: '2' }]; // prebuilt; others on first visit

export default async function ProductPage({ params }) {
  const product = await getProduct((await params).id);
  return <h1>{product.name}: ₹{product.price}</h1>;
}
```

What to notice:

- `generateStaticParams` lists which pages to build at build time (SSG). Ids not in the list are built on their first visit and then cached.
- `cacheLife('hours')` turns SSG into ISR: the page's HTML is reused for an hour, then rebuilt in the background. Remove it and the page stays fixed until the next full build.
- There is no `window` or `localStorage` here, so the same code runs safely on the server. Browser-only reads would break this page.

## Rules and defaults

- **Next.js 16 default:** a page is prerendered (static) unless it reads request-time data such as cookies, headers or `searchParams`, or uncached data, in which case it renders per request (SSR).
- **`cacheLife('hours')`:** revalidates after 1 hour, in Next.js 16. The `hours` profile is for content updated several times a day.
- **Hydration mismatch:** React warns, and in development throws, when the server HTML and the first browser render differ. The fix is to make both renders identical, not to suppress the warning.
- **No freshness guarantee from ISR:** a user can see a page that is up to one revalidate period out of date.

## Not to be confused with

Rendering strategy and [Server Components](card:server-components) are different questions. The strategy decides **when** HTML is built (build time vs per request). Server Components decide **which** components run only on the server and ship no JavaScript. A page can use any strategy and still mix Server and Client Components.

## Common mistakes

- **"SSR is always faster than CSR."** SSR usually paints sooner, but building HTML on every request can raise the time to first byte, and the page is still not clickable until hydration finishes. Static HTML from a CDN avoids the per-request render entirely.
- **"ISR shows live data."** It shows data that is at most one revalidate period old. For truly live data, use SSR or fetch in the browser.

## Interview Qs

### What is hydration, and what causes a mismatch?

Hydration is React attaching its event handlers to server-built HTML so the page becomes interactive without rebuilding it. A mismatch happens when the first browser render differs from the server HTML: `typeof window` checks, browser-only APIs, timestamps or random values. Treat it as a bug and move browser-only values into an Effect.

### Which rendering would you pick for an online shop?

Product pages: ISR, so they are fast and refreshed hourly. Search results: SSR, because they depend on the query. The cart: CSR in a Client Component, since it is private and interactive. Static help pages: SSG, built once and served from a CDN.

### Is SSR always faster than CSR?

No. SSR usually gives a faster first paint and readable HTML for crawlers, but rendering on every request can raise the time to first byte, and the page still waits for hydration before clicks work. Static HTML served from a CDN skips the render cost and is often fastest.
