## What it is

The browser gives a page several ways to remember data between reloads. **localStorage** and **sessionStorage** together are Web Storage: they hold string key-value pairs in the browser and are never sent to the server. A **cookie** is a small piece of data the server or a script sets; the browser then attaches every matching cookie to each request to that site, so cookies travel with requests on their own. **IndexedDB** is a larger async database for structured data and files. Each store is tied to an [origin](card:how-browsers-render).

## Why it exists

A shop has to remember the cart and who is logged in after the user reloads or comes back tomorrow. These needs differ: the cart is private page data the server does not need on every request, while the login session must be proved to the server on each request and must not be readable by stray scripts. One store does not fit all three, and the wrong choice leaks data: a token in localStorage is exposed to any script, and a cart in cookies is sent needlessly on every request.

## How it works

<Compare id="localstorage-vs-sessionstorage-vs-cookies" />

1. For private page data (the cart, a theme), write a string to `localStorage` or `sessionStorage`; stringify objects first.
2. For the login session, let the server send a cookie with `Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Lax; Max-Age=3600`.
3. On every later request to that site, the browser attaches the cookie automatically; your code does nothing.
4. Because the browser sends cookies by itself, cookie-based sessions need [CSRF defence](card:frontend-security).

So the key is: Web Storage for data the server never needs, cookies for what the server must check on each request.

## Example

A tiny React hook keeps the cart in `localStorage`, so it survives a reload. Web Storage holds strings, so the array is stringified on the way in and parsed on the way out.

```jsx
import { useEffect, useState } from 'react';

function useSavedCart() {
  const [cart, setCart] = useState(() => JSON.parse(localStorage.getItem('cart') ?? '[]'));

  useEffect(() => {
    localStorage.setItem('cart', JSON.stringify(cart));
  }, [cart]);

  return [cart, setCart];
}
```

What to notice:

- `localStorage.getItem('cart')` returns a string or `null`; `?? '[]'` supplies an empty array the first time, so `JSON.parse` never fails.
- `JSON.stringify(cart)` is required because Web Storage stores strings only; saving the array object directly would store the text `[object Object]`.
- The write is inside an Effect that lists `cart`, so every change to the cart is saved; see [useEffect](card:use-effect).

## Rules and defaults

- **Cookie with no Max-Age or Expires:** it is a session cookie, deleted when the browsing session ends (MDN).
- **Cookie with no SameSite:** Chrome and Edge treat it as `Lax`, but Firefox and Safari do not, so set it explicitly (Chrome 80+, Edge 86+, MDN).
- **Web Storage size:** about 5 MiB per origin; a cookie is about 4 KB and browsers cap the number per domain (MDN).
- **SameSite=None:** only works together with `Secure`; without it the browser rejects the cookie.
- **Max-Age=0:** deletes the cookie immediately.

## Interview Qs

### Where would you store a login token, and why?

In a cookie set by the server with `HttpOnly`, `Secure` and `SameSite`. `HttpOnly` keeps page scripts from reading it, so an XSS bug cannot steal it. Because the browser then sends it automatically, you must add CSRF protection. localStorage is the wrong choice, as any script on the page can read it.

### Is sessionStorage shared between tabs?

No. Each tab (and each window) gets its own sessionStorage, which survives reloads within that tab and is cleared when the tab closes. localStorage, by contrast, is shared by every tab of the same origin and persists until code or the user clears it.

### Why not keep everything in cookies?

A cookie is limited to about 4 KB, browsers cap how many a domain may have, and every matching request carries all of them, which wastes bandwidth. Use Web Storage or IndexedDB for data the server never needs, and keep cookies for what must be checked on each request, such as the session.
