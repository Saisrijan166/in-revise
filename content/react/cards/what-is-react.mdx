## Why it exists

Changing the DOM by hand for every click gets hard to keep correct as an app grows. React lets you describe each state instead.

## How it works

<Steps label="One update in React">
  <Step title="Trigger">The first render, or a state update in the component or a parent.</Step>
  <Step title="Render">React calls your components and builds a new element tree.</Step>
  <Step title="Reconcile">It compares the new tree with the previous one.</Step>
  <Step title="Commit">It applies only the needed DOM changes; the browser then paints.</Step>
</Steps>

- Same element type: React keeps the DOM node and updates changed attributes. A different type rebuilds that subtree.
- A re-render is not always a DOM update: see [re-renders](card:re-renders).

## Example

Browsers cannot run JSX. A compiler turns it into plain function calls (real esbuild output, automatic JSX runtime):

```jsx
<button className="add" onClick={addToCart}>Add to cart</button>
```

```text output
import { jsx } from "react/jsx-runtime";
/* @__PURE__ */ jsx("button", { className: "add", onClick: addToCart, children: "Add to cart" });
```

## Interview Qs

### What is the virtual DOM? Is it faster than the real DOM?

It is React's in-memory tree of elements. It is not faster by itself: diffing is extra work. Its value is declarative code, with React applying only the DOM changes that are needed.

### How does reconciliation work?

React diffs the new tree against the old one in O(n) with two rules: a different element type means a new subtree, and [keys](card:lists-and-keys) match list items.

### What is JSX and how does it become JavaScript?

JSX is HTML-like syntax inside JavaScript. A compiler such as Babel turns each tag into a `jsx()` call that returns a plain element object describing the UI; React later renders it.
