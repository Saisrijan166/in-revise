## What it is

Data fetching is loading data from a backend API and showing it in your components. Unlike a plain variable, a fetch takes time, can fail, and can return out of order, so the UI must handle three outcomes: loading, error and the data itself. You can fetch inside a [`useEffect`](card:use-effect) by hand, or let a library (a query cache) do it. Either way, the central problem is not calling `fetch`; it is coping with time.

## Why it exists

Say you load the payments list when the page opens. If you only render the data, the screen is blank while the request is in flight and crashes if it fails. And when the user changes a filter quickly, two requests go out, and the slower, older one can come back last and overwrite the newer result. Handling all three states, plus the ordering of responses, is what turns a raw `fetch` call into correct data fetching.

1. The component renders a loading view first, because the data is not there yet.
2. The effect starts the request for the current query and creates an `AbortController` for it.
3. If the query changes, the effect's cleanup runs and calls `controller.abort()`, cancelling the old request before the new one starts.
4. When a response arrives, the component shows the error view if it failed, or the data view if it succeeded.

So the key is: the cleanup makes a stale request's result count for nothing, so only the newest request can update the screen.

## Example

TanStack Query removes the manual effect, loading flags and race handling. `useQuery` caches by its `queryKey` and gives you the three states.

```jsx
import { useQuery } from '@tanstack/react-query';
// getPayments(status, signal): fetch('/api/payments?status=' + status, { signal }), throw if !res.ok

function PaymentList({ status }) {
  const { data: payments, isPending, isError } = useQuery({
    queryKey: ['payments', status],                      // one cache entry per status
    queryFn: ({ signal }) => getPayments(status, signal),
  });
  if (isPending) return <p>Loading…</p>;
  if (isError) return <p>Could not load payments.</p>;
  return <ul>{payments.map((p) => <li key={p.id}>{p.id}: ₹{p.amount}</li>)}</ul>;
}
```

What to notice:

- `queryKey: ['payments', status]` names the cache entry. A new `status` fetches new data; the same `status` returns the cached result instead of refetching.
- The library passes a `signal` into `queryFn`, so when the query changes it aborts the old request for you; you do not write the race handling.
- `isPending` is the loading flag in v5 (it replaced `isLoading`), and `isError` covers the failure case, so all three states are handled in a few lines.
- Removing the `isPending` and `isError` guards would render `payments.map` while `payments` is still `undefined`, which throws.

## Rules and defaults

- **staleTime: 0 by default (TanStack Query v5):** fetched data is treated as stale at once, so the library refetches it on mount, on window focus and on reconnect.
- **gcTime: 5 minutes (TanStack Query v5):** a query with no active component is kept in the cache for 5 minutes, then garbage collected.
- **retry: 3 by default (TanStack Query v5):** a failed query is retried 3 times with exponential backoff before the error is shown.
- **Raw effects have none of this:** a hand-written `useEffect` caches nothing and refetches on every mount, and you must add the abort-in-cleanup yourself.

## Not to be confused with

Fetching in a raw `useEffect` is you running the request and managing loading, errors and races by hand. A query cache like TanStack Query wraps that and adds caching, de-duping, retries and background refetch. There is also a newer path: React 19 lets a component read a promise with [`use()` and Suspense](card:use-promise-suspense), and [Server Components](card:server-components) fetch on the server before the HTML is sent. Rule: raw effect for a one-off, a query cache for most client apps.

## Common mistakes

- **"isError means the data is wrong, not that the request failed."** No. `isError` means the `queryFn` threw, usually because the response was not ok or the network failed. Your `queryFn` must throw on a bad response, or TanStack Query treats it as success.
- **"A mutation updates the list automatically."** It does not. After `useMutation` succeeds, call `invalidateQueries` for the list's key so the cached list is marked stale and refetched.

## Interview Qs

### What is a race condition in data fetching, and how do you fix it?

Two requests, such as searches for "mo" and "mouse", can resolve out of order, so the slower, older one finishes last and overwrites the newer result. You fix it in the effect cleanup: set an ignore flag so a late result is dropped, or call `controller.abort()` to cancel the old request when the query changes.

### Why use TanStack Query instead of fetching in useEffect?

A raw effect caches nothing, refetches on every mount, and needs manual loading flags and race handling. TanStack Query caches by `queryKey`, de-dupes identical requests, retries on failure, refetches stale data in the background, and gives `isPending` and `isError` out of the box.

### How do you keep a list fresh after creating or updating an item?

Send the change with `useMutation`. On success, call `queryClient.invalidateQueries` for that list's `queryKey`. That marks the cached list stale, so TanStack Query refetches it and the UI shows the new data without a manual reload.
