## What it is

Responsive design is building one page that reshapes itself to fit any screen, from a narrow phone to a wide monitor, instead of making separate sites. It rests on three tools: the **viewport meta tag**, which tells a phone to use its real width; **media queries**, which apply extra CSS once the screen passes a chosen width (a **breakpoint**); and **relative units** like `rem` and `%`, which size things in proportion, not in fixed pixels. A newer tool, the **container query**, reacts to a component's own width.

## Why it exists

A fixed pixel layout built for a desktop overflows a phone: text runs off the edge, and the user has to scroll sideways or pinch to zoom. You could ship a second mobile site, but then you maintain two codebases that drift apart. Responsive design keeps one set of HTML and CSS and lets it rearrange, so a three-column card layout folds down to one column on a phone with a few extra rules rather than a whole separate page.

## How it works

Relative units are the foundation, because they let sizes scale instead of staying frozen.

| Unit | Relative to | Good for |
|---|---|---|
| px | Nothing: a fixed CSS pixel | Borders and thin lines |
| % | The parent (a width % is of the parent's width) | Fluid widths |
| em | The element's own font size (the parent's, for font-size) | Padding that grows with the text |
| rem | The root (html) font size | Font sizes and consistent spacing |
| vw / vh | 1% of the viewport width / height | Full-screen sections |

1. Add the viewport meta tag in the HTML head so the phone lays the page out at its real width.
2. Write the base CSS for the smallest screen, with a single-column, stacked layout.
3. Add `@media (min-width: ...)` blocks that switch to wider layouts as more space appears, placing each breakpoint where the content starts to look cramped.
4. Size type and spacing in `rem`, and let images shrink with `img { max-width: 100% }`, so everything scales within each layout.

So the key is to start from the constrained screen and add complexity upward, which keeps the mobile case simple and correct by default.

## Example

This grid grows from one column on a phone to four on a desktop, then adapts a single component with a container query.

```css
.payment-cards { display: grid; gap: 1rem; }             /* phone: one column */

@media (min-width: 40em) {
  .payment-cards { grid-template-columns: repeat(2, 1fr); } /* tablet */
}
@media (min-width: 64em) {
  .payment-cards { grid-template-columns: repeat(4, 1fr); } /* desktop */
}

.summary { container-type: inline-size; }
@container (min-width: 400px) { .summary-row { display: flex; } }
```

What to notice:

- The base rule has no media query, so the single column is the phone default; the `min-width` queries only add columns as the screen widens, which is the mobile-first pattern.
- Breakpoints are in `em`, so they scale with the user's font-size preference instead of assuming exact device pixels.
- `container-type: inline-size` on `.summary` lets `@container` react to that box's width, so the same summary component can be a row in a wide slot and stacked in a narrow one.
- A container query checks the component's container, not the viewport, so the component behaves correctly wherever it is placed on the page.

## Rules and defaults

- **Viewport meta:** without `<meta name="viewport" content="width=device-width, initial-scale=1">`, phones assume a canvas about 980px wide and zoom out; with it, the page uses the device width.
- **Media query direction:** `min-width` queries build up from mobile (recommended); `max-width` queries apply below a width and are easy to layer wrongly.
- **Container queries:** Baseline since 2023; the container needs `container-type: inline-size` (or `size`) before `@container` can read its width.
- **Dynamic viewport:** `vh` is the large viewport height and ignores toolbars; `dvh` follows the visible area as toolbars show and hide.

## Interview Qs

### Media queries versus container queries?

A media query checks the viewport, the whole browser window, so it is right for page-level layout changes. A container query checks the nearest ancestor that has `container-type` set, so it reacts to the space a component actually gets. That lets one card component lay out differently in a narrow sidebar and in the wide main column, without knowing where it was placed.

### Why is 100vh often too tall on mobile?

`vh` is defined against the large viewport, as if the browser toolbars were hidden, and it does not shrink when the address bar is showing. So a `height: 100vh` box is taller than the visible area while the bar is on screen, and its bottom gets cut off or causes scrolling. The fix is `100dvh`, the dynamic viewport height, which tracks the visible area as the bar appears and disappears.

### How do you choose breakpoints?

Set them where the content itself starts to look wrong, such as when a card grid becomes too cramped at one column or text lines grow too long, rather than targeting specific device widths like "iPhone" or "iPad". Devices change constantly, but content-driven breakpoints stay correct, and expressing them in `em` keeps them tied to readable text sizes.
