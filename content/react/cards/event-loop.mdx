## What it is

The **event loop** is the mechanism that lets single-threaded JavaScript handle timers, network and user events without freezing. JavaScript runs on one thread with one **call stack**: the list of functions currently running. It can do only one job at a time. When slow work like a timer or a `fetch` finishes, its callback is not run straight away; it is put on a queue. The event loop is the simple rule that decides, again and again, which queued callback runs next.

## Why it exists

JavaScript has a single thread, so if it waited in place for a network reply or a one-second timer, the whole page would freeze: no clicks, no scrolling, no drawing. To avoid that, the slow work is started and set aside, and the thread keeps running other code. When the work is done it queues a callback. The event loop then runs these callbacks one at a time, in a fixed order, so the code stays responsive and the result order is predictable.

## How it works

<Steps label="One turn of the browser event loop">
  <Step title="Run one task">The current task, such as the script, a timer callback or an event handler, runs until the call stack is empty.</Step>
  <Step title="Drain microtasks">Every queued microtask runs, including ones queued while draining, until the microtask queue is empty.</Step>
  <Step title="Render">The browser may update the screen now.</Step>
  <Step title="Next task">Take the oldest task from a task queue and start again from step 1.</Step>
</Steps>

Two queues feed this loop, and microtasks always win.

So the key is: current code first, then all microtasks, then one task; a `setTimeout` callback cannot jump ahead of a promise callback.

## Example

This mixes synchronous code, a timer and promises. Predicting the order is a very common interview question. The output comes from running it with Node.

```javascript
console.log("A");
setTimeout(() => console.log("B"), 0);           // a task
Promise.resolve().then(() => console.log("C"));  // a microtask
(async () => {
  console.log("D");                              // runs now
  await null;
  console.log("E");                              // microtask, after await
})();
console.log("F");
```

```text output
A
D
F
C
E
B
```

What to notice:

- `A`, `D`, `F` print first: they are the current code, run top to bottom. An async function runs normally until its first `await`.
- `C` and `E` are microtasks, so they run as soon as the current code finishes, before any timer.
- `B` is a task from `setTimeout`, so it runs last, even with a `0` delay.
- Remove the `await null` and `E` would print with `D`, in the synchronous run.

## Rules and defaults

- **One task per turn:** the loop runs exactly one task, then drains all microtasks, then may render.
- **Microtasks run to empty:** a microtask that queues more microtasks keeps the loop in the drain step, which can starve tasks and rendering.
- **Timer minimum:** `setTimeout(fn, 0)` queues `fn` as a task; browsers also clamp deeply nested timers (after 5 levels) to at least 4 ms.
- **No preemption:** a running job is never paused partway; the next job waits for the stack to empty.

## Interview Qs

### Why does D print before F in an async function?

An async function runs synchronously until its first `await`, so `console.log("D")` runs in line with the surrounding code, before `F`. Only the code after `await` is split off and queued as a microtask, so `E` runs later, after the current code finishes.

### Can a microtask starve the page?

Yes. In each turn the loop drains the microtask queue completely before it runs the next task or lets the browser render. So a microtask that keeps queueing more microtasks never lets the loop move on, blocking timers, input handling and painting.
