## What it is

This is the closing page: a map from the questions you are actually asked back to the concepts in this tech, plus a shape for answering them well. Knowing a concept is only half of an interview; the other half is picking the right one quickly and explaining it clearly. Two habits do most of the work: answer any "what is X" in four beats (what it is, why it exists, an example, one trade-off), and for any performance question, measure before changing code.

## Why it exists

Under time pressure it is easy to ramble, or to reel off every optimisation you have heard of. Interviewers read that as someone who memorised facts but cannot reason from evidence. A fixed answer shape keeps each reply short and complete, and a measure-first rule for performance shows you fix the cause rather than guessing. This page also lets you revise the whole tech quickly, because each row links to the concept that owns the real answer.

## How it works

For a performance question, match the symptom to its fix. Each fix is explained in full on its own concept page.

| Performance symptom | First fix |
|---|---|
| Not sure what is slow | [Profile it](card:measuring-performance) |
| Children re-render with unchanged props | [Find the trigger](card:re-renders), [move state down](card:lifting-state-up), then [memoize](card:memoization) |
| A slow calculation runs on every render | [useMemo](card:memoization) |
| State copied from a prop drifts out of sync | [Compute it during render instead](card:use-state) |
| The first download is too big | [Split code and lazy-load](card:bundling-code-splitting) |
| Thousands of rows, or a handler firing on every keystroke | [Virtualise, debounce or throttle](card:large-lists-and-frequent-events) |
| Heavy images | [Size and lazy-load them](card:measuring-performance) |
| Too much client JavaScript in Next.js | [Use Server Components](card:server-components) |

1. Read the symptom the interviewer describes, or the one your profiling found.
2. Go to the matching row and name that fix, not a list of all of them.
3. Apply it, then measure again to confirm the symptom is gone.

So the key is: one symptom, one matching fix, confirmed by measuring.

## Common mistakes

- **"More optimisations means a better answer."** Each unneeded optimisation adds complexity and can even slow a build. The strong answer finds the cause and applies the one fix that matches it.
- **"Finish the whole feature before mentioning trade-offs."** Say your assumptions and what you will skip as you go. Interviewers score the reasoning they hear, not only the final code.

## Interview Qs

### How do you optimise a slow React app?

Reproduce it in a production build with CPU throttling, record it in the React Profiler or the browser Performance panel, and find the single costliest component, calculation or download. Apply the one fix that matches that cause, from re-render fixes to code splitting to virtualisation, then record again to confirm the gain. Measure before and after, every time.

### How do you approach a UI coding round, such as building an autocomplete?

Clarify the requirements first. Build a working core, then add loading, empty and error states, handling of stale requests, and keyboard support. Test after each step and say aloud what you are skipping if time runs short. Interviewers want to see a working path and clear reasoning, not a perfect first attempt.
