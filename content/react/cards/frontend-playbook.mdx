## Why it exists

Knowing the concepts is half the job; interviews also test whether you pick the right one fast. This page routes each symptom or question to its concept.

## How it works

| Performance symptom | First fix |
|---|---|
| Not sure what is slow | [Profile it](card:measuring-performance) |
| Children re-render with the same props | [Find the trigger](card:re-renders), [move state down](card:lifting-state-up), then [memoize](card:memoization) |
| Slow calculation on every render | [useMemo](card:memoization) |
| State copied from props | [Compute it during render](card:use-state) |
| Big first download | [Split code and lazy-load](card:bundling-code-splitting) |
| Thousands of rows, or input firing per key | [Virtualise, debounce or throttle](card:large-lists-and-frequent-events) |
| Heavy images | [Size and lazy-load them](card:measuring-performance) |
| Too much client JS in Next.js | [Server Components](card:server-components) |

- Machine coding: a [debounced search box](card:large-lists-and-frequent-events), a [cart with useReducer](card:use-reducer), a [fetched list with loading and error](card:data-fetching).
- Say "a re-render is not a DOM update" and know why: [re-renders](card:re-renders).

## Interview Qs

### How do you optimise a slow React app?

Reproduce it on a slow device with a production build, profile to find which components or downloads cost most, apply the matching fix from the table, then measure again to prove it helped.

### How do you approach a UI coding round, such as an autocomplete?

Clarify requirements, build a working core, then add loading, empty and error states, stale-request handling and keyboard support. Test after each step and say what you skipped.
