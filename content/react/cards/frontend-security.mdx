## Why it exists

The browser runs code from many places and sends cookies by itself. Attackers abuse both, so the frontend must never run untrusted code or trust a cross-site request.

## How it works

<Compare id="xss-vs-csrf" />

- Same-origin policy: a script may read a response only if scheme, host and port match; cross-origin form posts are still allowed.
- CORS: the server opts in with `Access-Control-Allow-Origin`; PUT, JSON bodies or custom headers first send an `OPTIONS` preflight.
- Content Security Policy: a response header listing allowed script sources; a backup layer, not the main fix.

## Example

```jsx
import { renderToStaticMarkup } from 'react-dom/server';

const review = { text: '<img src=x onerror="alert(1)">' };

function Review({ review }) {
  return <p>{review.text}</p>;
}

console.log(renderToStaticMarkup(<Review review={review} />));
```

```text
<p>&lt;img src=x onerror=&quot;alert(1)&quot;&gt;</p>
```

## Interview Qs

### How does React protect against XSS, and where can it still happen?

React escapes strings it renders as text. Holes remain: `dangerouslySetInnerHTML` with unsanitised HTML, user-supplied URLs, and direct DOM writes through refs. Sanitise with DOMPurify and validate URLs.

### What is a CORS preflight?

Before a non-simple cross-origin request, such as PUT or a JSON body, the browser sends `OPTIONS` naming the method and headers. The real request goes only if the server's reply allows them.

### Is SameSite enough to stop CSRF?

OWASP treats it as defence in depth. Use CSRF tokens (or your framework's built-in protection) on state-changing requests and never change data on GET. Any XSS bug defeats every CSRF defence.
