## What it is

These are the three web-security terms every frontend interview touches. **XSS** (cross-site scripting) is when an attacker's JavaScript runs inside your page, usually sneaked into content the page renders. **CSRF** (cross-site request forgery) is when another site makes the victim's browser send a request that carries the victim's [cookies](card:browser-storage-cookies), so it runs as them. **CORS** (cross-origin resource sharing) is the browser rule that lets a server say which other [origins](card:how-browsers-render) may read its responses.

## Why it exists

The browser runs code and loads data from many places, and it attaches cookies to requests on its own. Attackers abuse both facts: they try to slip their script into your page (XSS) or to make the victim's browser fire a request they could not send themselves (CSRF). Without defences, a single review field that renders raw HTML, or an endpoint that trusts a cookie alone, hands an attacker control. Knowing which attack each defence stops is what keeps you from, for example, trusting CORS to protect an API it cannot protect.

## How it works

<Compare id="xss-vs-csrf" />

1. The same-origin policy is the browser's base rule: a script may read a response only when scheme, host and port all match. (A cross-origin form can still be submitted, which is why CSRF is possible.)
2. CORS relaxes that rule on the server's terms: the server sends `Access-Control-Allow-Origin` to name origins it permits to read the response.
3. For a request that is not "simple" (a `PUT`, a JSON body or a custom header), the browser first sends an `OPTIONS` preflight and proceeds only if the server's reply allows it.
4. A Content Security Policy (a response header listing allowed script sources) is a backup layer that limits what runs if an XSS hole slips through.

## Example

This proves React's built-in XSS defence. The review text contains an image tag with an `onerror` script. We render it as JSX text and print the HTML React actually produces.

```jsx
import { renderToStaticMarkup } from 'react-dom/server';

const review = { text: '<img src=x onerror="alert(1)">' };

function Review({ review }) {
  return <p>{review.text}</p>;
}

console.log(renderToStaticMarkup(<Review review={review} />));
```

```text output
<p>&lt;img src=x onerror=&quot;alert(1)&quot;&gt;</p>
```

What to notice:

- React escaped `<`, `>` and `"` into `&lt;`, `&gt;` and `&quot;`, so the browser shows the characters as text; no `<img>` element is created and `onerror` never runs.
- This escaping happens for any value placed in JSX as text, which is why plain `{...}` output is safe by default.
- Replace `<p>{review.text}</p>` with `<p dangerouslySetInnerHTML={{ __html: review.text }} />` and React inserts the raw HTML, the `<img>` is created, and `onerror` fires. That is why such HTML must be sanitised with DOMPurify first.

## Rules and defaults

- **JSX text is escaped:** values rendered as text in `{...}` are HTML-escaped, so they cannot inject markup.
- **dangerouslySetInnerHTML is not:** it inserts raw HTML unchanged, so sanitise first.
- **React 19 blocks `javascript:` URLs** in `href` and `src`, but you should still validate user-supplied URLs.
- **CORS with credentials:** when the request sends cookies, the server must echo the one exact origin and set `Access-Control-Allow-Credentials: true`; the wildcard `*` is not allowed with credentials.
- **CSRF on GET:** never change data on a `GET`; state changes belong on `POST`, `PUT` or `DELETE` protected by a token.

## Common mistakes

- **"CORS secures my API."** CORS only governs whether a browser lets a page read a cross-origin response. A non-browser client (curl, a server, a script) ignores it completely, so the API still needs real authentication and authorisation.
- **"SameSite cookies alone stop CSRF."** OWASP treats SameSite as defence in depth, not the primary fix. Use a CSRF token on state-changing requests as well, because browser and gateway behaviour around SameSite varies.

## Interview Qs

### How does React protect against XSS, and where can it still happen?

React escapes any string it renders as text, so injected tags appear as plain characters. Gaps remain where you bypass that: `dangerouslySetInnerHTML` with unsanitised HTML, user-supplied URLs in attributes, and direct DOM writes through refs. Sanitise HTML with DOMPurify, validate URLs, and add a Content Security Policy as a backup.

### What is a CORS preflight, and when does it happen?

Before a non-simple cross-origin request, such as a `PUT` or one with a JSON body or custom header, the browser first sends an `OPTIONS` request naming the method and headers it wants to use. The real request is sent only if the server's response allows that origin, method and those headers.

### Is SameSite enough to stop CSRF on its own?

OWASP treats it as defence in depth rather than a complete fix. Use a CSRF token (or your framework's built-in protection) on every state-changing request, and never mutate data on a `GET`. Also remember that any XSS bug defeats CSRF defences, since the attacker's script runs on your origin.
