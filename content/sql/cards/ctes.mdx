## What it is

A CTE (common table expression) is a [subquery](card:subqueries) that you name with `WITH` and write before the main query. The main query then reads it by name, like a table. A recursive CTE, written `WITH RECURSIVE`, refers to its own name, so it can repeat a step: it is how SQL walks a tree such as an org chart, where each employee row stores its manager's id.

## Why it exists

A query with two or three nested subqueries reads inside-out: you start in the middle and work outwards. A CTE turns each subquery into a named step, read top to bottom, and a step used twice is written once. Trees are the second problem. Each join climbs exactly one level, so a fixed number of joins cannot reach every report at any depth. A recursive CTE keeps going until no new rows appear.

A plain CTE is computed or merged into the main query, which then reads it by name. A recursive CTE runs like this:

1. The anchor query runs once and returns the starting rows, here the employee with no manager.
2. Those rows go into the result and become the working set.
3. The step query runs, joining the table to the working set only: it finds the direct reports of the last level.
4. The new rows are added to the result and become the next working set.
5. Steps 3 and 4 repeat until a step returns no rows; then the full result goes to the main query.

## Example

Net paid per customer: paid totals minus refunds. Each total gets its own named step before the join, so a customer with several payments and refunds is not counted twice.

```sql
WITH paid AS (
  SELECT customer_id, SUM(amount) AS total
  FROM payments WHERE status = 'PAID'
  GROUP BY customer_id
),
refunded AS (
  SELECT p.customer_id, SUM(r.amount) AS total
  FROM refunds r JOIN payments p ON p.id = r.payment_id
  GROUP BY p.customer_id
)
SELECT c.name, paid.total - COALESCE(refunded.total, 0) AS net_paid
FROM paid
JOIN customers c ON c.id = paid.customer_id
LEFT JOIN refunded ON refunded.customer_id = paid.customer_id
ORDER BY c.name;
```

```text output
 name | net_paid
------+----------
 Asha |  1200.00
 Ravi |     0.00
```

What to notice:

- `paid` and `refunded` are separated by a comma, and the main query joins them like two tables.
- Ravi's 700 payment was refunded, so his net is 0. Asha has no refund, so `refunded` has no row for her and `COALESCE` turns the NULL into 0.
- The recursive form follows the same layout: `WITH RECURSIVE team AS (anchor UNION ALL step) SELECT * FROM team`. On the org chart it returns Asha at level 1, Ravi and Kabir at level 2 and Meena at level 3.
- Both queries return the same rows on PostgreSQL 18 and MySQL 9.7.

## Rules and defaults

- **Scope:** a CTE exists only for the statement it belongs to.
- **Versions:** PostgreSQL has had CTEs and `WITH RECURSIVE` since 8.4; MySQL since 8.0.
- **Inlining (PostgreSQL 12+):** a non-recursive `SELECT` CTE that is used once and has no side effects is merged into the main query. `MATERIALIZED` forces it to be computed apart; `NOT MATERIALIZED` forces merging. A CTE used twice is computed once by default.
- **Recursion limit:** MySQL 9.7 aborts after `cte_max_recursion_depth` iterations (default 1000). PostgreSQL has no limit.
- **Stopping cycles:** in PostgreSQL 14+ write `CYCLE id SET is_cycle USING path`; anywhere, keep a path of visited ids or a depth counter in the step.
- **UNION vs UNION ALL in recursion:** `UNION` drops rows already found, which can end a simple cycle; `UNION ALL` keeps all rows and is the usual choice.

## Interview Qs

### What is the difference between a CTE and a subquery?

Both are a query used inside another. A CTE is named and written first with WITH, so it reads top to bottom and can be referenced several times; it can also be recursive. A subquery is written inside the expression that uses it. Neither is faster by rule: PostgreSQL 12+ inlines a single-use CTE.

### How do you get every employee under a manager, at any depth?

Use a recursive CTE. The anchor selects the manager. The step joins employees whose `manager_id` is in the rows found by the previous step, and adds a level counter. It repeats until a step finds no one. A fixed number of self-joins only reaches a fixed depth.

### How do you stop a recursive CTE from looping forever?

Cyclic data, where a row leads back to itself, makes the step find rows forever. In PostgreSQL 14+ add the CYCLE clause, which marks a repeated row and stops that path. In any database you can carry a path or a depth column and stop when it repeats or passes a limit. MySQL also stops at cte_max_recursion_depth, 1000 by default.
