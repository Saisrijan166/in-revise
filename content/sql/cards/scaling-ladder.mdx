## Why it exists

Teams often jump to the hardest fix, like sharding, when an index would do. Each rung costs more money and complexity, so climb only when the one below runs out.

## How it works

<Steps label="Rungs, and the sign to move up">
  <Step title="Fix queries and indexes">Read the [plan](card:explain-query-plans), add [indexes](card:indexes). Next if good plans still saturate the server.</Step>
  <Step title="Pool connections">Use a [connection pool](card:connection-pooling). Next if load, not connection count, is the limit.</Step>
  <Step title="Cache hot reads">Put repeated reads in a [cache](card:caching-redis). Next if uncached reads still dominate.</Step>
  <Step title="Add read replicas">[Replicas](card:replication) share reads. Next if writes are the bottleneck.</Step>
  <Step title="Scale up">A bigger server. Next at the largest size you can buy.</Step>
  <Step title="Partition big tables">[Partitions](card:partitioning) keep huge tables fast. Next if one server still cannot hold the writes or data.</Step>
  <Step title="Shard">[Split rows across servers](card:sharding). Last: joins and transactions get hard.</Step>
</Steps>

## Interview Qs

### Vertical or horizontal scaling: what is the difference?

Vertical: a bigger machine, simple, but it reaches a hardware limit. Horizontal: more machines, as replicas for reads or shards for writes; it grows further but adds lag and routing.

### Writes are the bottleneck. What helps?

Not caching or replicas. Drop unused indexes, since each one slows every insert. Then scale up, partition big tables, and shard if one server still cannot keep up.
