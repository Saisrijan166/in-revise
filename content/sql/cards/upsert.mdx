## Why it exists

Sync jobs, imports and retries must write a row whether or not it already exists. Doing that in two steps races when requests run at the same time.

## How it works

| Need | PostgreSQL 18 | MySQL 9.7 |
|---|---|---|
| Insert or update | `ON CONFLICT (k) DO UPDATE` | `ON DUPLICATE KEY UPDATE` |
| Insert or skip | `ON CONFLICT DO NOTHING` | `INSERT IGNORE` (also hides other ignorable errors) |
| The proposed row's values | `EXCLUDED.col` | row alias, `new.col` |
| Get the row back | `RETURNING` | no; `LAST_INSERT_ID()` for the id |

- Needs a unique index: without one, PostgreSQL errors and MySQL inserts a duplicate.
- With `SET x = EXCLUDED.x`, running it twice leaves the same row, so retries are safe.

## Example

```sql
-- PostgreSQL 18: email has a UNIQUE constraint
-- asha@example.in is already row 1
INSERT INTO users (email, name, city)
VALUES ('asha@example.in', 'Asha', 'Pune')
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name, city = EXCLUDED.city
RETURNING id, (old.id IS NULL) AS inserted;  -- old/new: PostgreSQL 18+
```

```text output
 id | inserted
----+----------
  1 | f
```

```sql
-- MySQL 9.7
INSERT INTO users (email, name, city)
VALUES ('asha@example.in', 'Asha', 'Pune') AS new
ON DUPLICATE KEY UPDATE name = new.name, city = new.city;
```

## Interview Qs

### ON CONFLICT or MERGE in PostgreSQL?

ON CONFLICT is the upsert for concurrent writes: if another insert wins the race, it updates instead. MERGE syncs a table from a source with insert, update and delete branches; the docs say the two are not interchangeable.

### How do you get the generated id after an insert?

PostgreSQL: `INSERT … RETURNING id` in the same round trip. MySQL has no RETURNING: read `LAST_INSERT_ID()` on the same connection, or JDBC `getGeneratedKeys()`. See [id generation](card:id-generation).
