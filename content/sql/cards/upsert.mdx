## What it is

An upsert (update + insert) is one statement that inserts a row, or updates the existing row if one with the same key is already there. The key is the primary key or a column with a [UNIQUE constraint](card:constraints); the database uses it to detect the clash. PostgreSQL writes an upsert as `INSERT … ON CONFLICT`, and MySQL as `INSERT … ON DUPLICATE KEY UPDATE`.

## Why it exists

A payment gateway calls the payment service with "payment 105 is now PAID", and it may send the same call again when a reply is slow. With check-then-insert, two such calls arriving together can both run the `SELECT`, both see no row, and both `INSERT`: one fails on the primary key, or, without a unique key, a duplicate row appears. An upsert decides insert-or-update inside the database in one statement, and running it twice leaves the same row, so retries are safe.

## How it works

| Need | PostgreSQL 18 | MySQL 9.7 |
|---|---|---|
| Insert or update | `ON CONFLICT (k) DO UPDATE` | `ON DUPLICATE KEY UPDATE` |
| Insert or skip | `ON CONFLICT DO NOTHING` | `INSERT IGNORE` (also hides other ignorable errors) |
| The proposed row's values | `EXCLUDED.col` | row alias, `new.col` |
| Get the row back | `RETURNING` | no RETURNING; `LAST_INSERT_ID()` for an auto-increment id |

1. The database tries to insert the proposed row.
2. It checks the unique index or constraint: the one named in `ON CONFLICT (id)` in PostgreSQL, any unique key in MySQL.
3. No clash: the row is inserted.
4. Clash: instead of raising an error, it runs the update part on the existing row. Even when another session inserts the same key at the same moment, PostgreSQL guarantees one of the two outcomes, insert or update.
5. In PostgreSQL, `RETURNING` sends back values from the row just written.

## Example

The gateway reports that payment 105, now `PENDING`, is `PAID`. PostgreSQL 18:

```sql
-- PostgreSQL 18: payment 105 exists, status PENDING
INSERT INTO payments (id, customer_id, amount, status, created_at)
VALUES (105, 2, 75.00, 'PAID', '2026-10-05 15:45')
ON CONFLICT (id)
DO UPDATE SET status = EXCLUDED.status
RETURNING id, old.status AS before, new.status AS after;
```

```text output
 id  | before  | after
-----+---------+-------
 105 | PENDING | PAID
```

The same in MySQL 9.7:

```sql
-- MySQL 9.7: payment 105 exists, status PENDING
INSERT INTO payments (id, customer_id, amount, status, created_at)
VALUES (105, 2, 75.00, 'PAID', '2026-10-05 15:45') AS new
ON DUPLICATE KEY UPDATE status = new.status;
SELECT ROW_COUNT();   -- 1 inserted, 2 updated, 0 unchanged
```

```text output
+-------------+
| ROW_COUNT() |
+-------------+
|           2 |
+-------------+
```

What to notice:

- `EXCLUDED.status` and `new.status` both mean "the value I tried to insert", here `PAID`. Only `status` is in the update list, so the stored amount and date stay as they are.
- `old.status` is `PENDING` and `new.status` is `PAID`, so the row was updated. For a new payment, such as 106, `old.status` would be NULL.
- Run either statement a second time and the row stays the same: PostgreSQL shows `PAID | PAID`, and MySQL's `ROW_COUNT()` is 0. The retry is harmless.

## Rules and defaults

- **Unique key required:** PostgreSQL raises an error if no unique index matches the `ON CONFLICT` target. A target is required for `DO UPDATE` and optional for `DO NOTHING`.
- **One row once (PostgreSQL):** `DO UPDATE` may not change the same row twice in one statement. Two proposed rows with the same key raise a cardinality violation error.
- **Several unique keys (MySQL):** the manual advises avoiding `ON DUPLICATE KEY UPDATE` on a table with more than one unique index, because a clash on any of them triggers the update.
- **VALUES() in MySQL:** referring to the new row with `VALUES(col)` is deprecated since 8.0.20, and 9.7 shows a warning. Use the row alias `AS new` (8.0.19+).
- **Generated ids:** PostgreSQL returns them with `RETURNING id`. MySQL has no RETURNING: read `LAST_INSERT_ID()` on the same connection, or use JDBC `getGeneratedKeys()`. See [id generation](card:id-generation).

## Not to be confused with

`INSERT … ON CONFLICT` is an insert with a fallback: built to stay correct when many sessions write the same key at once. `MERGE` (PostgreSQL 15+) syncs a table from a source table or query, with separate branches to insert, update or delete. The PostgreSQL docs point to `ON CONFLICT` when a concurrent insert must turn into an update, and say the two are not interchangeable. Rule: one row that may already exist = `ON CONFLICT`; syncing a whole set = `MERGE`.

## Common mistakes

- **"An upsert needs only the columns I want to update."** The proposed row must also be a valid insert. In PostgreSQL 18, `INSERT INTO payments (id, status) VALUES (105, 'PAID') ON CONFLICT …` fails with a not-null error on `customer_id`, even though payment 105 exists.

## Interview Qs

### How do you make a webhook or retry handler safe to run twice?

Write the change as an idempotent upsert on a unique key, such as the payment id or an event id: `ON CONFLICT DO UPDATE` or `DO NOTHING` in PostgreSQL, `ON DUPLICATE KEY UPDATE` in MySQL. A second delivery then updates the same row to the same values instead of inserting a duplicate or failing.

### ON CONFLICT or MERGE in PostgreSQL?

ON CONFLICT is the upsert for concurrent writes: if another insert wins the race, it takes the update path instead of failing. MERGE syncs a table from a source with insert, update and delete branches. The docs say the two are not interchangeable.

### How do you get the generated id after an insert?

PostgreSQL: `INSERT … RETURNING id`, in the same round trip. MySQL has no RETURNING: read `LAST_INSERT_ID()` on the same connection, or JDBC `getGeneratedKeys()`.
