## What it is

Denormalisation means storing some data more than once, or storing a precomputed answer, on purpose. It starts from a [normalised](card:normalization) schema and adds redundancy in one chosen place. There are two common forms: a copied column, such as the customer's name kept inside each payment row, and a precomputed value, such as a table of revenue per day. The original data stays where it was; the copy is extra.

## Why it exists

In a normalised schema, the payments screen joins payments to customers on every request just to show a name, and the revenue dashboard sums every payment row each time it loads. When such a read runs thousands of times a minute and measurements show it is too slow, doing that work once and storing the result is cheaper. The price moves to the writes: every change to the original must also change the copy.

## How it works

<Compare id="normalization-vs-denormalization" />

1. Measure first: find the one read that is too slow and confirm that the join or the aggregate is the cause.
2. Try an index; if the query still has to join or sum many rows, choose what to store, a copied column or a precomputed table.
3. Fill the copy once from the original data.
4. Change every write path so the copy is updated too: in the same transaction as the original, by a trigger (code the database runs on each change; you will see it in [Stored procedures and triggers](card:stored-procedures-triggers)), or by a scheduled job when slightly old data is acceptable.
5. Point the slow read at the copy, and keep the original as the source of truth.

So the key is that the copy is never the master: if they disagree, rebuild the copy from the original.

## Example

This copies the customer's name into payments, then shows the read it speeds up and the write it slows down.

```sql
ALTER TABLE payments ADD COLUMN customer_name text;
UPDATE payments p SET customer_name = c.name
FROM customers c WHERE c.id = p.customer_id;     -- fill the copy once

-- the hot read: no join to customers
SELECT id, customer_name, amount FROM payments WHERE status = 'PAID';

-- the price: a rename must fix every copy, in one transaction
BEGIN;
UPDATE customers SET name = 'Asha K' WHERE id = 1;
UPDATE payments  SET customer_name = 'Asha K' WHERE customer_id = 1;
COMMIT;
```

What to notice:

- The SELECT reads one table. Without the copy it would join customers on every call.
- The rename now touches one customer row plus every one of her payment rows; a customer with 10,000 payments means 10,000 extra row updates.
- Both UPDATEs sit in one transaction, so no reader sees the new name in one table and the old one in the other. Drop the second UPDATE and the payment list shows the old name for good.
- The fill uses PostgreSQL's `UPDATE ... FROM`. MySQL writes it as `UPDATE payments p JOIN customers c ON c.id = p.customer_id SET p.customer_name = c.name`.

## Rules and defaults

- **Source of truth:** the normalised table stays the master; the copy can always be rebuilt from it.
- **Keep copies in sync:** same transaction (always current), trigger (current, but hidden from app code), or a job or materialized view refresh (cheaper, but stale between runs; materialized views come in [Views](card:views)).
- **Try cheaper fixes first:** an index, a better query or a cache may fix the read without redundant data.
- **No automatic sync:** neither PostgreSQL nor MySQL updates a copied column for you; only your write paths do.

## Common mistakes

- **"We will fix the copy later in a nightly job, it is fine."** Only if users can live with a stale value all day. For a name or a balance shown to the customer, update it in the same transaction.
- **"Denormalise everything up front for speed."** That multiplies write paths before any read is proven slow. Denormalise one measured read at a time.

## Interview Qs

### When would you denormalise?

When a frequent read is measurably slow because of joins or aggregates, and an index, a better query or caching did not fix it. Typical cases are counters on a feed, dashboards with daily totals, and reporting tables. I keep the normalised tables as the source of truth.

### How do you keep denormalised data correct?

Update the copy in the same transaction as the original, so they always agree, or use a trigger so every writer is covered. If slightly old data is fine, rebuild it with a scheduled job or a materialized view refresh, and say how stale it can be.

### Denormalise or add an index?

Try the index first, because the database keeps it in sync for you and it adds no new facts. An index helps find rows quickly. If the query still has to join several tables or add up many rows, denormalise.
