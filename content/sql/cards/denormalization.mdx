## Why it exists

A normalised schema can need several joins for one screen. When that read runs constantly and is too slow, storing the answer ready-made is cheaper.

## How it works

<Compare id="normalization-vs-denormalization" />

- Keep copies in sync in the same transaction, with a trigger, or with a scheduled job.
- In PostgreSQL, a [materialized view](card:materialized-view) is denormalisation the database rebuilds on each REFRESH.

## Example

```sql
-- the read: no join to users
SELECT id, amount, user_name FROM orders WHERE user_id = 7;

-- the price: a rename must also fix every copy
BEGIN;
UPDATE users  SET name = 'Asha K' WHERE id = 7;
UPDATE orders SET user_name = 'Asha K' WHERE user_id = 7;
COMMIT;
```

## Interview Qs

### When would you denormalise?

When a frequent read is measurably slow because of joins or aggregates, and indexes or caching did not fix it. Typical cases: feed counters, dashboards and reporting tables.

### How do you keep denormalised data correct?

Update the copy in the same transaction as the source, or use a trigger. If slightly old data is fine, rebuild it with a job or a materialized view refresh.

### Denormalise or add an index?

Try the index first: the database keeps it in sync for you. Denormalise when the query still needs joins or aggregates that an index cannot remove.
