## What it is

OLTP and OLAP are two kinds of database workload. OLTP (online transaction processing) is the app's day-to-day work: create a payment, mark it PAID, show one customer's history, each as a short transaction touching a few rows. OLAP (online analytical processing) is the business asking questions of that data, such as revenue per city per month, where each query reads and sums a large share of the history. Each workload is usually served by a differently designed store.

## Why it exists

The checkout needs a payment insert to finish in milliseconds; finance needs a sum over three years of payments. If both run on the same database, the big scan uses the CPU, memory and disk that checkout transactions need, and checkout slows down. The normalised tables that keep app writes correct also make reports long, with many joins. Separating the two lets each side use the design that suits it.

## How it works

<Compare id="oltp-vs-olap" />

Follow one payment from the app to a report:

1. The app inserts the payment into the OLTP database in a short transaction, into normalised, row-stored tables.
2. On a schedule, or as changes arrive, an ETL or ELT job copies new rows out of the OLTP database.
3. The job loads them into a data warehouse, a separate store that collects data from many systems for analysis.
4. In the warehouse the data is laid out as a star schema: each payment becomes a row in a fact table, with keys to dimension tables such as date and city.
5. Reports query the warehouse, often in a column store, and the OLTP database never sees that load.

So the key is to keep heavy reads away from the database that takes the app's writes.

## Example

The same payments data, used both ways, run on PostgreSQL 18. All five payments were made in January 2026.

```sql
-- OLTP: one customer action, one row, found by its key
UPDATE payments SET status = 'PAID' WHERE id = 5;

-- OLAP: a business question that reads every PAID row
SELECT date_trunc('month', p.created_at)::date AS month,
       c.city, SUM(p.amount) AS revenue
FROM payments p JOIN customers c ON c.id = p.customer_id
WHERE p.status = 'PAID'
GROUP BY 1, 2
ORDER BY 1, 2;
```

```text output
   month    | city  | revenue
------------+-------+---------
 2026-01-01 | Delhi |  700.00
 2026-01-01 | Pune  | 1400.00
```

What to notice:

- The UPDATE uses the primary key, so it touches one row however large the table grows. That is the OLTP shape.
- The report touches every PAID row and joins customers. With five rows it is instant; with fifty million, it is a long scan that competes with checkout.
- `date_trunc` is PostgreSQL; in MySQL, group by `DATE_FORMAT(p.created_at, '%Y-%m-01')`.

## Rules and defaults

- **Storage:** PostgreSQL and MySQL InnoDB are row stores, built for OLTP. Warehouses usually store data by column.
- **Fact and dimension tables:** the fact table keeps growing with every event; dimension tables stay small and describe the events.
- **ETL vs ELT:** ETL transforms the data in a separate engine before loading; ELT loads raw data first and transforms it inside the target store.
- **First step before a warehouse:** send reports to a read replica, a copy of the database that serves reads; you will see it in [Replication](card:replication).

## Interview Qs

### What is a star schema?

A fact table in the middle holds events with numeric measures, such as payment amounts, plus keys to dimension tables. Dimension tables, such as date, customer and city, describe those events and are used to filter and group. Reports join the fact table to a few dimensions, which keeps queries short.

### What is the difference between ETL and ELT?

Both move data from source systems into an analytics store. ETL transforms it in a separate engine before loading. ELT loads the raw data first and transforms it inside the target store, using the warehouse's own power.

### Why not run analytics on the OLTP database?

Large aggregates scan many rows and use a lot of CPU, memory and disk, so they slow down or block business transactions. Highly normalised tables also make report queries long, with many joins. A replica or warehouse takes that load away from the primary.
