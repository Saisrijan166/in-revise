## What it is

Both are ways to stop a lost update: two transactions read the same row, each changes it in memory, and the later write silently erases the earlier one. Pessimistic locking takes a [row lock](card:locking) before the change, so the second transaction waits. Optimistic locking takes no lock. It keeps a version number in the row and makes the UPDATE change nothing if the version moved since you read it.

## Why it exists

Two support agents open payment 2 at the same time. Both load it as `PENDING`, version 0. One saves `FAILED`, the other saves `PAID` a second later, and the first agent's change is gone without any error. READ COMMITTED, PostgreSQL's default [isolation level](card:isolation-levels), does not stop this, because each UPDATE is valid on its own. You need either waiting (pessimistic) or detecting (optimistic).

## How it works

<Compare id="optimistic-vs-pessimistic-locking" />

The optimistic way, step by step:

1. Read the row together with its version: `SELECT status, version FROM payments WHERE id = 2` returns `PENDING`, 0.
2. The user or the code works for as long as needed. No lock is held.
3. Write with the old version in the WHERE, and raise the version: `… SET status = 'PAID', version = version + 1 WHERE id = 2 AND version = 0`.
4. Check the row count. 1 means your write won. 0 means someone changed the row, or deleted it, since you read it: re-read and retry, or show a conflict.

The pessimistic way is shorter: `BEGIN`, `SELECT … FOR UPDATE`, change the row, `COMMIT`. A second transaction's `FOR UPDATE` waits until the first one commits, then reads the new value.

## Example

Two agents both read payment 2 at version 0 and then save (run on PostgreSQL 18 and MySQL 9.7):

```sql
UPDATE payments SET status = 'PAID', version = version + 1
WHERE id = 2 AND version = 0;                -- agent 1: 1 row, version is now 1
UPDATE payments SET status = 'FAILED', version = version + 1
WHERE id = 2 AND version = 0;                -- agent 2: 0 rows, conflict
-- when the new value depends only on the old one, one statement is enough:
UPDATE wallets SET balance = balance - 500
WHERE customer_id = 2 AND balance >= 500;    -- 0 rows: Ravi has only ₹300
```

What to notice:

- Agent 2's UPDATE changes 0 rows because the version is already 1. The app must check that count; ignoring it silently loses agent 2's intent.
- The wallet UPDATE needs no version. It reads and changes the balance in one statement, and the `balance >= 500` condition refuses an overdraft.

In JPA, a `@Version` field makes the provider add the version check for you:

```java
@Entity
@Table(name = "payments")
class Payment {
    @Id Integer id;
    BigDecimal amount;
    String status;
    @Version int version;   // JPA adds "AND version = ?" to every UPDATE and increments it
}
```

What to notice:

- You never write the version check. When the UPDATE changes 0 rows, JPA throws `OptimisticLockException` and the transaction is marked for rollback.
- Remove `@Version` and the same code silently overwrites the other agent's change.

## Rules and defaults

- **Zero rows:** means the version changed or the row was deleted. Re-read and retry, or report the conflict; never ignore the count.
- **No lock during user think time:** never hold a pessimistic lock while a user edits a form. Carry the version in the form instead.
- **JPA pessimistic:** `LockModeType.PESSIMISTIC_WRITE` asks the database for an exclusive row lock on the entity.
- **Atomic UPDATE:** at READ COMMITTED, PostgreSQL re-checks the WHERE on the newest version of a row that another transaction just changed, so `balance >= 500` is tested against the real current balance.

## Interview Qs

### When do you choose optimistic over pessimistic locking?

Optimistic when conflicts are rare or the edit is long, like a form open for minutes: no lock is held, and a retry is needed now and then. Pessimistic when the same rows are fought over often or a retry is costly, such as one hot stock row.

### What does it mean when an optimistic UPDATE affects 0 rows?

Someone changed the row since you read it, so the version no longer matches, or the row no longer exists. Re-read and retry, or show the user a conflict. Never ignore the row count.

### How do you prevent a lost update on a counter or a balance?

Often with neither lock: one atomic statement such as `SET balance = balance - 500 WHERE customer_id = ? AND balance >= 500`. The database reads and writes the row in one step, under the row lock. Use a version column or `FOR UPDATE` only when the new value needs logic outside SQL.
