## Why it exists

Two requests read a balance of 1000, each subtracts its own amount and saves: one change vanishes. This [lost update](card:lost-update) needs either waiting or detecting.

## How it works

<Compare id="optimistic-vs-pessimistic-locking" />

- [JPA](card:orm-jpa) does the version check for a `@Version` field; a conflict throws `OptimisticLockException` and rolls the transaction back.

## Example

```sql
-- accounts(id, balance, version)
SELECT balance, version FROM accounts WHERE id = 1;     -- 1000, version 7
UPDATE accounts SET balance = 500, version = version + 1
WHERE id = 1 AND version = 7;                           -- 0 rows: conflict, retry
-- or, when the new value depends only on the old one:
UPDATE accounts SET balance = balance - 500
WHERE id = 1 AND balance >= 500;                        -- 0 rows: not enough money
```

```java
@Entity
class Account {
    @Id Long id;
    BigDecimal balance;
    @Version long version;   // checked and bumped on every update
}
```

## Interview Qs

### When do you choose optimistic over pessimistic locking?

Optimistic when conflicts are rare and reads are long, like editing a form: no locks held, just a retry now and then. Pessimistic when conflicts are frequent or a retry is costly, like a hot stock row.

### What does it mean when an optimistic UPDATE affects 0 rows?

Someone changed the row since you read it (or it no longer exists). Re-read and retry, or report the conflict. Never ignore the row count.
