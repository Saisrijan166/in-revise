## What it is

ACID is a short name for the four guarantees a database gives every [transaction](card:transactions): Atomicity, Consistency, Isolation and Durability. Together they say what stays true when many users write at the same time and when the server crashes at a bad moment. PostgreSQL and MySQL's InnoDB storage engine give all four.

## Why it exists

A payment system must never lose a committed payment, charge a wallet without recording the payment, or store a negative balance, even with thousands of requests at once and a crash at any moment. Without these guarantees, every application would need its own crash-recovery and coordination code, and most would get it wrong. ACID moves that work into the database, and gives everyone four words to ask about it precisely.

## How it works

| Letter | What it promises | What gives it |
| --- | --- | --- |
| A, atomicity | All or nothing | `ROLLBACK`, and crash recovery that discards unfinished work |
| C, consistency | Valid before and after | [Constraints](card:constraints): keys, `CHECK`, `NOT NULL`, foreign keys |
| I, isolation | No mixing of unfinished work | Isolation levels, the next concept |
| D, durability | Committed means kept | A log written to disk at commit (the write-ahead log, later in this topic) |

Follow one wallet payment through the four letters:

1. `BEGIN` starts the transaction, and the debit and the payment insert run. Isolation: at READ COMMITTED or stricter, other sessions keep seeing the old balance until `COMMIT`.
2. Each statement is checked against the declared constraints. Consistency: a debit that would make the balance negative is refused.
3. If any statement fails, or the server crashes before `COMMIT`, all of the transaction's changes are discarded. Atomicity.
4. At `COMMIT` the database writes the change to its log on disk before it reports success. Durability: after a crash, the log restores every committed change.

## Example

Ravi (customer 2) has ₹300 and Meera (customer 3) has ₹0. A transfer of ₹500 from Meera to Ravi credits Ravi first (PostgreSQL 18):

```sql
BEGIN;
UPDATE wallets SET balance = balance + 500 WHERE customer_id = 2;   -- credit Ravi
UPDATE wallets SET balance = balance - 500 WHERE customer_id = 3;   -- debit Meera
-- ERROR: new row for relation "wallets" violates check constraint "wallets_balance_check"
ROLLBACK;
SELECT customer_id, balance FROM wallets WHERE customer_id IN (2, 3);
```

```text output
 customer_id | balance
-------------+---------
           2 |  300.00
           3 |    0.00
```

What to notice:

- Consistency: the `CHECK (balance >= 0)` refuses Meera's negative balance.
- Atomicity: `ROLLBACK` also undoes Ravi's credit, which had already succeeded. Ravi is back at ₹300, so no money was created.
- If the code had run `COMMIT` instead, PostgreSQL would still roll back, but MySQL would save Ravi's credit, as [Transactions](card:transactions) showed. Atomicity needs the application to roll back on error.

## Not to be confused with

ACID's consistency means the data obeys the rules you declared, after every commit, on one database. The consistency in the [CAP theorem](card:cap-theorem), which you will see in Scaling, means that every read on any copy of the data returns the latest write. Rule: ACID C = rules hold; CAP C = all copies agree.

## Interview Qs

### Explain ACID with a money transfer.

Atomicity: the debit and the credit both happen or neither does. Consistency: no balance breaks the `CHECK (balance >= 0)`. Isolation: other transactions do not see the half-done transfer. Durability: after commit, a crash or power cut cannot lose the transfer.

### Which ACID property depends most on the application?

Consistency. The database enforces only the constraints you declare. A business rule kept only in application code is not protected: two concurrent requests can both pass the check in code and commit data that breaks it.
