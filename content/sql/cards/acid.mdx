## Why it exists

Many users change data at once, and servers crash. ACID names the four promises a transaction gives so that money, stock and orders stay correct anyway.

## How it works

| Letter | What it promises | What gives it |
| --- | --- | --- |
| A | All or nothing | `ROLLBACK`, and crash recovery that discards unfinished work |
| C | Valid before and after | Constraints: keys, `CHECK`, `NOT NULL` |
| I | No interference | [Isolation levels](card:isolation-levels), via [MVCC](card:mvcc) and [locks](card:locking) |
| D | Committed means kept | The [log](card:wal) is flushed to disk at commit |

- The C here is not the C of the [CAP theorem](card:cap-theorem); see the trap.

## Example

```sql
ALTER TABLE accounts ADD CHECK (balance >= 0);
BEGIN;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;  -- id 1 has 300: CHECK fails
ROLLBACK;  -- A: the credit to id 2 is undone too. C: no negative balance.
```

## Interview Qs

### Explain ACID with a bank transfer.

Atomicity: the debit and credit both happen or neither does. Consistency: no balance breaks the `CHECK`. Isolation: other transactions do not see the half-done transfer. Durability: after commit, a crash cannot lose the transfer.

### Which ACID property depends most on the application?

Consistency. The database enforces only the constraints you declare; a business rule kept only in code is not protected.
