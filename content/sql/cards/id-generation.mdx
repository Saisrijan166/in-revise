## What it is

A generated id is a primary-key value the database creates for each new row, so the app does not have to pick one. In PostgreSQL the column is declared as an identity column, which takes numbers from a sequence: a small database object that hands out 1, 2, 3 and so on. MySQL gives the column the AUTO_INCREMENT attribute, backed by a counter per table. The alternative is a UUID, a 128-bit id such as `01a15f41-6427-7f59-baa2-9cc6992844ff` that any program can create on its own.

## Why it exists

Every payment needs a unique [primary key](card:keys). If the app computes "highest id plus one", two requests arriving together read the same highest id and both try to insert it; one fails. A sequence or counter hands out each number exactly once, even to many sessions at the same moment, without the sessions waiting for each other's transactions. A UUID removes the central counter altogether, which matters when ids are made on many servers or devices.

## How it works

<Mermaid
  alt="Two sessions insert at the same time. The sequence gives number 1 to session A and number 2 to session B. Session B rolls back, so number 2 is lost. The next insert gets number 3, leaving a gap."
  chart={`flowchart LR
  Q[(Sequence)] -- "1" --> A[Session A: INSERT, COMMIT]
  Q -- "2" --> B[Session B: INSERT, ROLLBACK]
  Q -- "3" --> C[Next INSERT, COMMIT]
  B -. "2 is lost" .-> G([Gap: ids 1 and 3])`}
/>

1. An INSERT arrives without an id, so the database asks the column's sequence (PostgreSQL) or counter (MySQL) for the next number.
2. The number is handed out at once and is never handed out again, whatever happens to the transaction that asked.
3. The row is written with that id, and the transaction commits or rolls back.
4. If it rolls back or the insert fails, the row disappears, but the number stays used: the table now has a gap.
5. With a UUID column the app, or a database function, generates the id instead, and no shared counter is involved.

So the key is that a generator promises unique numbers, not consecutive ones.

## Example

This creates the payments id column and shows a gap after a rollback, run on PostgreSQL 18.

```sql
CREATE TABLE pay_ids (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  amount numeric(10,2) NOT NULL
);
INSERT INTO pay_ids (amount) VALUES (500);   -- gets id 1
BEGIN;
INSERT INTO pay_ids (amount) VALUES (200);   -- takes id 2
ROLLBACK;
INSERT INTO pay_ids (amount) VALUES (300);   -- gets id 3
SELECT id, amount FROM pay_ids ORDER BY id;
```

```text output
 id | amount
----+--------
  1 | 500.00
  3 | 300.00
```

What to notice:

- Id 2 is missing although no row was ever deleted; the rolled-back insert used it up. MySQL 9.7 with `id BIGINT AUTO_INCREMENT PRIMARY KEY` gives the same 1 and 3.
- `GENERATED ALWAYS` rejects `INSERT ... (id, amount) VALUES (10, 50)` with an error unless you add `OVERRIDING SYSTEM VALUE`, so nobody slips in a manual id by accident.
- `PRIMARY KEY` is still needed: an identity column is NOT NULL but does not by itself guarantee uniqueness.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| First value, step | 1, 1 | PostgreSQL 18 identity and sequences; MySQL 9.7 AUTO_INCREMENT |
| Sequence `CACHE` | 1 (no numbers preallocated) | PostgreSQL 18 |
| `UUID()` | Version 1 (time plus node) | MySQL 9.7 |

- **ALWAYS vs BY DEFAULT (PostgreSQL):** ALWAYS rejects a manual id without `OVERRIDING SYSTEM VALUE`; BY DEFAULT accepts it, like a normal default.
- **Manual ids:** with SERIAL or BY DEFAULT, a manual id does not move the sequence, so a later normal insert can hit a duplicate key. MySQL moves its counter up when you insert a larger explicit id.
- **UUIDs:** PostgreSQL 18 has `uuidv7()` and `uuidv4()` (`gen_random_uuid()` is v4). MySQL 9.7 has no v4 or v7 function, so the app generates them; store them as 16 bytes with `UUID_TO_BIN()`, not as a 36-character string.

## Not to be confused with

A sequence is the number generator itself; an identity column is a column that is tied to its own sequence and filled from it automatically. SERIAL also creates a sequence and a column default, but it is a PostgreSQL shortcut rather than SQL-standard syntax and it accepts manual ids silently. Rule: in PostgreSQL write `GENERATED ALWAYS AS IDENTITY`; the comparison below covers numbers versus UUIDs.

## Interview Qs

### Why does my id column have gaps?

A number is used up the moment it is handed out. If the insert then fails or its transaction rolls back, the row disappears, but the number is never reused, so a gap remains. This keeps id generation fast under concurrency. Never rely on ids being gap-free or on ids to count rows.

### IDENTITY or SERIAL in PostgreSQL?

IDENTITY. It is SQL-standard syntax, and with ALWAYS it rejects manual ids that would later collide with the sequence. SERIAL is an older shortcut that creates a sequence plus a default and silently accepts any value you supply.

### Auto-increment or UUID as the primary key?

Auto-increment is small, ordered and fast to insert. A UUID can be made anywhere without a central counter, which suits offline clients, several services or merging databases. If you need a UUID, prefer UUIDv7 to random v4, so new keys are added near the end of the index instead of all over it.
