## Why it exists

Every row needs a unique key, and making one in the app breaks under concurrency. The database hands out ids safely to many sessions at once.

## How it works

| Generator | Product | Remember |
|---|---|---|
| `GENERATED ALWAYS AS IDENTITY` | PostgreSQL 10+, SQL standard | Rejects a manual id unless `OVERRIDING SYSTEM VALUE` |
| `SERIAL` / `BIGSERIAL` | PostgreSQL | A sequence plus a column default |
| Sequence | PostgreSQL | `nextval()` is never rolled back |
| `AUTO_INCREMENT` | MySQL | One counter per table |
| UUIDv4 / UUIDv7 | Both: 128 bits | PostgreSQL 18 has `uuidv7()`; MySQL `UUID()` is v1 |

- Identity does not make a column unique: add `PRIMARY KEY` or `UNIQUE`.
- MySQL: store UUIDs with `UUID_TO_BIN()` in 16 bytes, not as a 36-character string.

## Example

```sql
CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL,
  amount  numeric(10,2)
);
-- MySQL: id BIGINT AUTO_INCREMENT PRIMARY KEY

-- PostgreSQL 18: a time-ordered UUID key
CREATE TABLE events (id uuid DEFAULT uuidv7() PRIMARY KEY, name text);
```

## Defaults

| What | Default | Where |
|---|---|---|
| First value, step | 1, 1 | PostgreSQL 18 sequences and identity |
| Sequence `CACHE` | 1 (no preallocated numbers) | PostgreSQL 18 |

## Interview Qs

### Why does my id column have gaps?

A number is used up when handed out, even if the insert fails or rolls back, and it is never reused. Gaps are normal; never rely on gap-free ids.

### Auto-increment or UUID as the primary key?

Auto-increment: small, ordered, fast to insert. UUID: made anywhere without a central counter. If you need a UUID, prefer UUIDv7 to random v4. See [the comparison](compare:auto-increment-vs-uuid).
