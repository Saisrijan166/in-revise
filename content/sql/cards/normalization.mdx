## What it is

Normalisation is a way of designing tables so that each fact is stored exactly once, in the table it describes. A wide table that repeats information is split into smaller tables, linked by [primary and foreign keys](card:keys). The rules for how far to split are called normal forms; interviews ask about 1NF, 2NF and 3NF. They are built on one idea, a functional dependency: column B depends on column A when the same A value always comes with the same B value, as a customer's city does with customer_id.

## Why it exists

Picture one spreadsheet of payments where every row also carries the customer's name and city. Asha has two payments, so her city is written twice. When she moves, an update that misses one row leaves the table saying two different things. That is an update anomaly. Two more follow from the same design: you cannot save a customer before their first payment (insertion anomaly), and deleting a customer's only payment also deletes the customer (deletion anomaly). Normalisation removes all three by keeping the city in one row of a customers table.

## How it works

<Steps label="Normalise one payments spreadsheet">
  <Step title="Start">payment_sheet(payment_id, customer_id, customer_name, city, amount, status, refunds = '201, 202'): customer details on every row, a list in one cell.</Step>
  <Step title="1NF">One value per cell: the refund list moves to its own table, refunds(id, payment_id, amount), one row per refund.</Step>
  <Step title="2NF">Check for a two-column key. payment_id is one column, so nothing can depend on part of it, and 2NF already holds.</Step>
  <Step title="3NF">customer_name and city depend on customer_id, not on the payment. Move them to customers(id, name, city) and keep only customer_id in payments.</Step>
  <Step title="Result">customers, payments and refunds: each fact once, joined back with [joins](card:joins).</Step>
</Steps>

1. Find what each column depends on. In payment_sheet, amount and status depend on payment_id, but city depends on customer_id.
2. Apply 1NF first: any cell holding a list or repeated group becomes rows in a separate table.
3. Apply 2NF only to tables with a key of two or more columns. A column that depends on just one part of that key moves to its own table. In order_lines(order_id, product_id, qty, product_name), product_name depends on product_id alone, so it moves to products.
4. Apply 3NF: a column that depends on another non-key column moves to the table where that column is the key.
5. Link the new tables with foreign keys, so a join rebuilds the original rows when you need them.

So the key is William Kent's line: every non-key column must state a fact about the key, the whole key, and nothing but the key.

## Example

This shows the update anomaly in the spreadsheet design: Asha's city is changed in one row only.

```sql
CREATE TABLE payment_sheet (
  payment_id int PRIMARY KEY, customer_id int, customer_name text,
  city text, amount numeric(10,2), status text);
INSERT INTO payment_sheet VALUES
 (1, 1, 'Asha', 'Pune', 500, 'PAID'),
 (2, 1, 'Asha', 'Pune', 200, 'FAILED'),
 (3, 2, 'Ravi', 'Delhi', 300, 'PAID');
UPDATE payment_sheet SET city = 'Mumbai' WHERE payment_id = 1;
SELECT DISTINCT customer_id, customer_name, city
FROM payment_sheet WHERE customer_id = 1
ORDER BY city;
```

```text output
 customer_id | customer_name |  city
-------------+---------------+--------
           1 | Asha          | Mumbai
           1 | Asha          | Pune
```

What to notice:

- One customer now has two cities. Nothing in the database stopped it, because the table allows each row its own copy.
- The UPDATE targeted one payment, which is normal for a payments screen. The design, not the query, caused the bug.
- In the normalised schema the same change is `UPDATE customers SET city = 'Mumbai' WHERE id = 1`: one row, and every payment sees it through the join.

## Rules and defaults

- **Order:** each form includes the one before it. A table in 3NF is also in 2NF and 1NF.
- **2NF needs a composite key:** a table whose candidate keys are all single columns is in 2NF as soon as it is in 1NF.
- **BCNF:** stricter than 3NF. Anything that decides another column must be a key. 3NF allows one exception, when the decided column is itself part of a candidate key.
- **Usual target:** 3NF. Higher forms (4NF, 5NF) deal with rare multi-valued cases and are seldom asked.

## Not to be confused with

Normalisation splits data so each fact lives once and correctness is easy. [Denormalisation](card:denormalization), the next concept, copies some facts back on purpose so one slow read skips a join. Rule: normalise first for correctness, then denormalise one measured read at a time.

## Interview Qs

### What problems does normalisation solve?

It prevents three anomalies. Update: a fact copied into many rows must change in all of them, or they disagree. Insertion: you cannot store a customer until they make a payment. Deletion: deleting a customer's last payment also loses the customer. Storing each fact once removes all three.

### Explain 1NF, 2NF and 3NF with an example.

1NF: one value per cell, so a list of refund ids becomes rows in a refunds table. 2NF: with a key like (order_id, product_id), product_name depends only on product_id, so it moves to products. 3NF: in payments, city depends on customer_id, not on the payment, so it moves to customers.

### How is BCNF different from 3NF?

In BCNF, the column set on the left of every non-trivial functional dependency must be a superkey. 3NF also allows the dependent column to be part of a candidate key. So every BCNF table is in 3NF, but a few 3NF tables with overlapping candidate keys are not in BCNF.

### Is a fully normalised schema always the best choice?

No. It is the right default for an application database because writes stay correct. But a screen that joins many tables on every request may be too slow, and then you denormalise that one read after measuring it.
