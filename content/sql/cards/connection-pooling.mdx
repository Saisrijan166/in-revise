## Why it exists

A new connection per request is slow, and every database caps how many connections it accepts.

## How it works

<Mermaid
  alt="Request threads borrow connections from a HikariCP pool that holds 10 open connections to PostgreSQL. Threads 1 and 2 get a connection. Thread 11 waits in the pool until one is returned."
  chart={`flowchart LR
  T1[Request thread 1] --> P
  T2[Request thread 2] --> P
  T11[Request thread 11] -. waits .-> P
  P[["Pool: 10 open connections"]] --> DB[(PostgreSQL)]`}
/>

- Extra requests queue in the pool instead of overloading the database.
- App instances × pool size must stay below the server's `max_connections`.

## Example

```java
try (Connection con = dataSource.getConnection();      // borrow
     PreparedStatement ps = con.prepareStatement(
         "SELECT name FROM users WHERE id = ?")) {
    ps.setLong(1, id);
    try (ResultSet rs = ps.executeQuery()) {
        return rs.next() ? rs.getString("name") : null;
    }
}                                                       // closed = returned
```

## Defaults

| What | Default | Where |
|---|---|---|
| Max connections in the pool | 10 | HikariCP 7.1 `maximumPoolSize` |
| Wait for a free connection | 30 seconds | HikariCP 7.1 `connectionTimeout` |
| Server connection limit | 100 / 151 | `max_connections`, PostgreSQL 18 / MySQL 9.7 |

## Interview Qs

### Why use a connection pool?

To skip the slow connect and login on every request, and to cap how many sessions reach the database at once.

### How big should the pool be?

Small. HikariCP's guide suggests starting near (CPU cores × 2) + disks and load-testing. Too many connections make the database switch between them, so latency rises.
