## What it is

A database connection is an open, logged-in session between your app and the database server; every SQL statement and every [transaction](card:transactions) runs over one. A connection pool is a set of connections the app opens once and then reuses. A request borrows a connection, runs its SQL and hands it back. In Java the pool sits behind a `DataSource`, the standard interface the app asks for connections, and HikariCP is the pool Spring Boot uses.

## Why it exists

Without a pool, every request opens a new connection: a network handshake, a password check and, in PostgreSQL, a new server process for that session. This setup can take longer than the query itself. And if 500 requests arrive together, the app opens 500 sessions, while PostgreSQL 18 accepts only 100 by default. A pool pays the setup cost once and caps the number of sessions, so extra requests wait inside the app instead of overloading the database.

## How it works

1. At startup HikariCP opens its connections. By default it keeps 10 open, because `minimumIdle` equals `maximumPoolSize`.
2. A request calls `dataSource.getConnection()`, and the pool hands it an idle connection.
3. The request runs its SQL and calls `close()`. The pool takes the connection back; the session to the database stays open for the next request.
4. If all 10 connections are busy, the next caller waits. If none comes back within `connectionTimeout` (30 seconds), it gets an `SQLException`.
5. The pool retires connections older than `maxLifetime` (30 minutes) once they are returned, and opens fresh ones.

So the key is to borrow late and return early: a connection that is held for one query can serve many requests a second.

## Example

The payment service reads a payment's status. Boot builds the pool from properties, and the code only borrows and returns.

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/shop
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.connection-timeout=30000
```

```java
String paymentStatus(long paymentId) throws SQLException {
    try (Connection con = dataSource.getConnection();          // borrow one
         PreparedStatement ps = con.prepareStatement(
             "SELECT status FROM payments WHERE id = ?")) {
        ps.setLong(1, paymentId);
        try (ResultSet rs = ps.executeQuery()) {
            return rs.next() ? rs.getString("status") : null;
        }
    }                                                          // close() returns it
}
```

What to notice:

- The two pool values are the HikariCP defaults written out. Change them only when a load test shows a need.
- `try (...)` calls `close()` even when the query throws. On a pooled connection, `close()` returns it to the pool rather than ending the session.
- Remove the `try` and the connection is never returned. After 10 such calls every request waits 30 seconds and then fails.
- The `?` is a placeholder for the id; [SQL injection](card:sql-injection), the next concept, shows why values go there and not into the SQL text.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Most connections in the pool | 10 | HikariCP 7.1 `maximumPoolSize` |
| Idle connections kept open | same as the maximum | HikariCP 7.1 `minimumIdle` |
| Wait for a free connection | 30 seconds | HikariCP 7.1 `connectionTimeout` |
| Oldest a connection may get | 30 minutes | HikariCP 7.1 `maxLifetime` |
| Leak warning | off (0) | HikariCP 7.1 `leakDetectionThreshold` |
| Server connection limit | 100 / 151 | `max_connections`, PostgreSQL 18 / MySQL 9.7 |

- **Which pool:** Spring Boot 4.1 always picks HikariCP when it is present, then the Tomcat pool, Commons DBCP2 and Oracle UCP. `spring.datasource.type` overrides the choice.
- **Connection budget:** app instances × pool size must stay below the server's `max_connections`.
- **Finding leaks:** set `leakDetectionThreshold`, for example to 10 seconds, and HikariCP logs a warning when a connection stays out of the pool longer than that.
- **maxLifetime:** set it a few seconds shorter than any time limit the database or network puts on connections.

## Not to be confused with

HikariCP is a pool inside one app instance: each instance has its own connections. PgBouncer is a separate server between many app instances and PostgreSQL; in transaction mode it gives a client a server connection only while a transaction runs, so many app connections share a few database connections. Rule: HikariCP = reuse inside one app; PgBouncer = share across many apps.

## Common mistakes

- **"close() on a pooled connection closes the network session."** It only returns the connection to the pool. The pool closes real sessions itself, at `maxLifetime` or on shutdown.
- **"Keep a connection open for the whole request, in case it is needed."** A borrowed connection is unavailable to everyone else until it is closed. Hold it only for the SQL, not during slow work such as calling another service.

## Interview Qs

### Why use a connection pool?

Opening a connection costs a network handshake, a login and, in PostgreSQL, a new server process. A pool pays that once and reuses connections. It also caps how many sessions reach the database, so a traffic spike queues in the app instead of overloading the server.

### How big should the pool be?

Small. HikariCP's sizing guide suggests starting near (CPU cores × 2) + disks on the database server, then load-testing. More connections than the server can run at once only make queries wait and switch, so latency rises. Also keep instances × pool size under `max_connections`.

### What happens when the pool is exhausted?

New callers wait for a returned connection. After `connectionTimeout`, 30 seconds by default in HikariCP, they get an `SQLException`. The usual causes are leaks, slow queries or a connection held during slow work; a bigger pool rarely fixes them.
