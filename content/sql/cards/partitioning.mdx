## What it is

Partitioning is splitting one large table into smaller tables, called partitions, that all live on the same database server. A column called the partition key, such as the payment date, decides which partition stores each row. The app still reads and writes the parent table, `payments`, and the database sends each row to the right partition.

## Why it exists

A payments table that grows by millions of rows a month gets hard to manage. Deleting last year's rows means one huge DELETE that runs for a long time and, in PostgreSQL, leaves dead rows for VACUUM to clean. Every index on the table keeps growing too. With one partition per month, a query for this month reads only this month's partition, and removing an old month means dropping one small table.

## How it works

| Type | Each partition holds | Typical key |
|---|---|---|
| [Range](card:range-partitioning) | A range of values: lower bound included, upper bound not | `created_at`, one month each |
| [List](card:list-partitioning) | The values you list | `city` or `country` |
| [Hash](card:hash-partitioning) | Rows whose key hashes to it | `customer_id`, for an even spread |

1. You create the parent table with `PARTITION BY RANGE (created_at)`, which names the partition key.
2. You create one partition per range, such as October 2026: from 1 October, included, to 1 November, not included.
3. On INSERT, the database reads the row's `created_at` and stores the row in the matching partition. A row that matches none is rejected.
4. On SELECT, the planner compares the WHERE condition with each partition's range and leaves out the ones that cannot match. This is [partition pruning](card:partition-pruning).
5. To remove old data, you drop or detach the old month's partition.

So the key is: the database works per partition, and a filter on the key decides how many partitions it touches.

## Example

The `payments` table gets one partition per month, and a query for October shows pruning in its plan.

```sql
CREATE TABLE payments (
  id bigint, customer_id bigint, amount numeric(10,2), status text, created_at date,
  PRIMARY KEY (id, created_at)          -- must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE payments_2026_09 PARTITION OF payments
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
CREATE TABLE payments_2026_10 PARTITION OF payments
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

EXPLAIN (COSTS OFF)
SELECT sum(amount) FROM payments WHERE created_at >= '2026-10-01';
```

```text output
                     QUERY PLAN
----------------------------------------------------
 Aggregate
   ->  Seq Scan on payments_2026_10 payments
         Filter: (created_at >= '2026-10-01'::date)
(3 rows)
```

What to notice:

- The plan scans only `payments_2026_10`. September was pruned, because its range ends before 1 October.
- `PRIMARY KEY (id)` alone is rejected: PostgreSQL says a unique constraint on a partitioned table must include all partitioning columns. MySQL 9.7 rejects it too.
- Change the WHERE to `customer_id = 7` and the plan scans both partitions, because the filter says nothing about dates.
- `DROP TABLE payments_2026_09;` removes all of September at once, with no row-by-row DELETE.

## Rules and defaults

- **Pruning is on by default:** `enable_partition_pruning = on` in PostgreSQL 18. It also prunes at run time when a value is known only then.
- **No matching partition:** the INSERT fails, in PostgreSQL 18 and MySQL 9.7. In PostgreSQL, a `DEFAULT` partition receives rows that fit no other partition.
- **Changing the key:** in PostgreSQL, an UPDATE that changes `created_at` to another month moves the row to that month's partition.
- **Detach without blocking:** `ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY` (PostgreSQL) takes a weaker lock on the parent than a plain detach.
- **MySQL InnoDB:** a partitioned table cannot have foreign keys, and no table can reference it. A table has at most 8192 partitions.
- **When it is worth it:** PostgreSQL's rule of thumb is a table bigger than the server's memory. Too many partitions slow down planning.

## Not to be confused with

Partitioning splits a table into pieces **inside one server**. [Sharding](card:sharding), the next concept, splits rows **across separate servers**. Rule: partitioning helps one server manage a huge table; sharding adds servers when one is not enough.

## Interview Qs

### Why drop a partition instead of running DELETE?

Dropping or detaching a partition removes the whole table piece at once and is far faster. A bulk DELETE must find and remove every row, writes all of it to the log, and in PostgreSQL leaves dead rows for VACUUM to clean up.

### Why must the primary key include the partition key?

Each partition has its own index, which can check uniqueness only inside that partition. If the key includes the partition column, two equal keys always land in the same partition, so the per-partition check is enough. PostgreSQL and MySQL both require it.

### How do you choose the partition key?

Pick the column that most large queries filter on, and that your cleanup works by. For payments that is usually the date: reports ask for a month, and old months are dropped. A key that queries rarely filter on gives no pruning, so every query pays for all partitions.
