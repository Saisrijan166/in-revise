## What it is

A SQL statement is one command you send to the database, such as "create this table" or "read these rows". Statements are sorted into five groups by what they touch: DDL (data definition) changes the structure, DML (data manipulation) changes rows, DQL (data query) reads rows, DCL (data control) changes permissions, and TCL (transaction control) ends a transaction. A transaction is a group of changes that the database keeps together (commit) or undoes together (rollback).

## Why it exists

The group tells you how much a statement can damage and whether you can take it back. An UPDATE run by mistake inside a transaction can be rolled back. A DROP TABLE in MySQL is committed the moment it runs, so the table and its data are gone. Interviewers use the groups to ask exactly this: what does DELETE, TRUNCATE or DROP remove, and which one can you undo.

## How it works

| Group | Job | Commands |
|---|---|---|
| DDL | Build or change structure | CREATE, ALTER, DROP, TRUNCATE |
| DML | Add, change, remove rows | INSERT, UPDATE, DELETE |
| DQL | Read rows | SELECT |
| DCL | Permissions | GRANT, REVOKE |
| TCL | Transactions | BEGIN, COMMIT, ROLLBACK, SAVEPOINT |

A payments table goes through all five groups in its life:

1. `CREATE TABLE payments (...)` builds the table. This is DDL.
2. `INSERT`, `UPDATE` and `DELETE` add, change and remove payment rows. This is DML.
3. `SELECT` reads them for a report. This is DQL, and it changes nothing.
4. `GRANT SELECT ON payments TO reporting` lets a reporting user read the table. This is DCL.
5. `BEGIN` starts a transaction around risky changes, and `COMMIT` or `ROLLBACK` ends it. This is TCL.

So the key is: know the group, and you know whether ROLLBACK can save you.

## Example

This PostgreSQL script deletes every row by mistake, then undoes it. The table is a small copy of two payments.

```sql
CREATE TABLE payments_archive (id INT PRIMARY KEY, amount DECIMAL(10,2));
INSERT INTO payments_archive VALUES (101, 500), (102, 800);

BEGIN;
DELETE FROM payments_archive;     -- no WHERE: every row goes
ROLLBACK;                         -- the delete is undone

SELECT COUNT(*) AS rows_left FROM payments_archive;
```

```text output
 rows_left
-----------
         2
(1 row)
```

What to notice:

- `DELETE` with no `WHERE` removed both rows, with no error. The `BEGIN` before it is what made the mistake recoverable.
- Put `TRUNCATE payments_archive` in place of the `DELETE` and PostgreSQL still shows 2 rows after `ROLLBACK`. MySQL 9.7 shows 0, because its `TRUNCATE` commits first.
- Without `BEGIN`, each statement commits on its own as soon as it succeeds, so `ROLLBACK` would have nothing to undo.

## Rules and defaults

- **Autocommit:** PostgreSQL 18 and MySQL 9.7 both commit each statement on its own unless you start a transaction with `BEGIN` or `START TRANSACTION`.
- **MySQL implicit commit:** DDL such as CREATE, ALTER, DROP and TRUNCATE commits the open transaction before it runs, so earlier changes in that transaction are committed too.
- **PostgreSQL transactional DDL:** CREATE, ALTER, DROP and TRUNCATE roll back with the transaction. A few commands, such as `CREATE DATABASE`, refuse to run inside a transaction at all.
- **The groups are a teaching convention:** the MySQL manual files SELECT under data manipulation statements, and some books call TRUNCATE DML.

## Not to be confused with

DELETE removes the rows that match its WHERE condition, one by one, and the table stays. TRUNCATE empties the whole table at once, and the table stays. DROP TABLE removes the table itself, with its indexes and constraints. Rule: DELETE = some rows, TRUNCATE = all rows, DROP = the table.

## Common mistakes

- **"UPDATE without WHERE gives an error."** It does not: it changes every row. Before a risky UPDATE or DELETE, run a SELECT with the same WHERE to see which rows it hits, and run the change inside `BEGIN` so you can roll it back.

## Interview Qs

### What is the difference between DELETE, TRUNCATE and DROP?

DELETE removes chosen rows, one at a time, and fires delete triggers. TRUNCATE removes all rows at once without scanning them, and the table stays. DROP removes the table with its data, indexes and constraints. DELETE can always be rolled back inside a transaction; TRUNCATE and DROP can be rolled back in PostgreSQL but not in MySQL.

### Is TRUNCATE DDL or DML?

It is usually filed as DDL. MySQL treats it as DDL and commits implicitly, so you cannot roll it back. PostgreSQL treats it like a fast delete of every row that still obeys the transaction, so ROLLBACK undoes it.

### You ran UPDATE without WHERE in production. What could have prevented the damage?

Running it inside a transaction: BEGIN, run the UPDATE, check the reported row count, then COMMIT or ROLLBACK. Running a SELECT with the same WHERE first also shows which rows will change. Without a transaction, autocommit has already saved the change, and only a backup can restore it.
