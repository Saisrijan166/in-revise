## Why it exists

Interviewers sort SQL statements by job: defining structure, changing data, reading, permissions and transactions. Knowing the group tells you whether a statement can be undone.

## How it works

| Group | Job | Commands |
|---|---|---|
| DDL | Define objects | CREATE, ALTER, DROP, TRUNCATE |
| DML | Change rows | INSERT, UPDATE, DELETE |
| DQL | Read rows | SELECT |
| DCL | Permissions | GRANT, REVOKE |
| TCL | Transactions | COMMIT, ROLLBACK, SAVEPOINT |

<Compare id="delete-vs-truncate-vs-drop" />

- Transactions themselves are in [Transactions](card:transactions).

## Example

```sql
INSERT INTO users (name, city) VALUES ('Asha', 'Pune'), ('Ravi', 'Delhi');
UPDATE users SET city = 'Delhi' WHERE id = 1;  -- one row
DELETE FROM users WHERE id = 1;                -- one row
DELETE FROM users;                             -- every row, can roll back
TRUNCATE users;                                -- every row, fast
DROP TABLE users;                              -- the table is gone
```

## Interview Qs

### What is the difference between DELETE, TRUNCATE and DROP?

DELETE removes chosen rows and fires delete triggers. TRUNCATE empties the whole table without scanning it. DROP removes the table, its indexes and constraints.

### Is TRUNCATE DDL or DML?

Usually DDL. MySQL calls it DDL and commits implicitly. PostgreSQL treats it like a fast unqualified DELETE that still obeys the transaction.
