## Why it exists

Most apps read the same rows again and again. A cache serves those repeated reads from memory and takes that load off the database.

## How it works

<Steps label="Cache-aside with Redis">
  <Step title="Read">Look up `user:42` in Redis. On a hit, return it.</Step>
  <Step title="Miss">Read the row from the database, store it with a TTL, return it.</Step>
  <Step title="Write">Update the database, then delete `user:42`.</Step>
  <Step title="Next read">It misses and loads the fresh row.</Step>
</Steps>

- A TTL heals any delete that was missed, so set one on every cached key.
- [Redis](card:redis) also serves sessions, counters, rate limits, locks and pub/sub.

## Example

```java
User find(long id) {
    String key = "user:" + id;
    User u = cache.get(key);
    if (u != null) return u;                      // hit
    u = userRepo.findById(id).orElseThrow();      // miss: read the DB
    cache.set(key, u, Duration.ofMinutes(5));     // store with a TTL
    return u;
}
void rename(long id, String name) {
    userRepo.updateName(id, name);                // 1. database
    cache.delete("user:" + id);                   // 2. drop the copy
}
```

## Defaults

| What | Default | Where |
|---|---|---|
| Key lifetime | none: keys live until deleted | Redis 8.x, without EXPIRE |
| Disk persistence | RDB snapshots to `dump.rdb`; AOF off | Redis 8.x |
| AOF fsync policy | `everysec` (lose up to about 1 s) | Redis 8.x, when AOF is on |

## Interview Qs

### Why not keep everything in Redis instead of the database?

Redis keeps data in memory, so size costs RAM, and a crash can lose recent writes: about a second with AOF everysec, minutes with RDB alone. The database gives durable storage, constraints, joins and transactions.

### How do you keep the cache and the database consistent?

Not perfectly, without extra cost. Update the database, then delete the key, and set a TTL so a missed delete heals itself. Do not cache data that must never be stale.
