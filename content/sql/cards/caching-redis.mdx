## What it is

A cache is a fast store that keeps copies of data the app reads often, so the next read does not need the database. Redis is the usual choice: a server that keeps keys and their values in memory (RAM), so a lookup by key is much faster than a database query. The database stays the source of truth: the one place whose data counts when the two disagree. Cache-aside is the common way to use them together: the app itself fills and clears the cache.

## Why it exists

A payments app shows the customer's name on every page, so it runs the same `SELECT` thousands of times for data that changes rarely. Each one borrows a pooled connection and uses database time. A cache answers those repeated reads from memory, so the database is left for writes and less common reads. The price is that the copy can be briefly out of date, so you cache only data that may be stale for a short time.

## How it works

<Mermaid
  alt="Cache-aside read path. The app asks Redis for the key. On a hit it returns the cached value. On a miss it reads the database, stores the value in Redis with a TTL, and returns it."
  chart={`flowchart LR
  A[App] -- "1. GET key" --> R[(Redis)]

  A -- "4. SET key EX 300" --> R`}

1. The app asks Redis for the key, such as `customer:1:name`.
2. On a hit, Redis returns the copy and the database is not touched.
3. On a miss, the app reads the row from the database, stores a copy in Redis with a TTL, and returns it.
4. On a write, the app updates the database first, then deletes the key.
5. The next read misses and loads the fresh value from the database.

So the key is that the app, not Redis, keeps the two in step.

## Example

The payment service caches customer names for 300 seconds. `redis` is a Jedis client, a Java library for Redis; `findName` and `updateName` run plain SQL.

```java
String customerName(long id) throws SQLException {
    String key = "customer:" + id + ":name";
    String name = redis.get(key);                // 1. try the cache
    if (name != null) return name;               // hit: no database trip
    name = findName(id);                         // 2. miss: read the database
    redis.set(key, name, SetParams.setParams().ex(300));  // 3. copy, 300 s TTL
    return name;
}

void rename(long id, String newName) throws SQLException {
    updateName(id, newName);                     // 1. the database first
    redis.del("customer:" + id + ":name");       // 2. then delete the old copy
}
```

What to notice:

- The first call reads the database; a second call within 300 seconds returns the cached name without SQL.
- `ex(300)` is the TTL. Remove it and the key never expires, so one missed delete leaves a wrong name for good.
- `rename` deletes the key instead of writing the new name into it. The next read loads whatever the database now holds.
- Swap the two lines in `rename` and a read between them can cache the old name again.

## Rules and defaults

- **Key lifetime (Redis 8):** no expiry by default; a key lives until it is deleted or evicted. Set a TTL with `SET … EX` or `EXPIRE`.
- **Persistence (Redis 8 defaults):** periodic RDB snapshots (a copy of all data written to disk) are on and the append-only file (AOF), a log of every write, is off, so a crash can lose the writes since the last snapshot. With AOF on, the default `everysec` sync can lose about one second of writes.
- **Memory limit:** `maxmemory` is 0 (no limit) by default on 64-bit systems. When a limit is set and reached, the default policy `noeviction` rejects new writes; for a cache the Redis docs suggest `allkeys-lru`, which drops the least recently used keys.
- **What not to cache:** data that must never be stale, such as a balance checked before a payment, and anything whose only copy would be in Redis.

## Not to be confused with

The database is the durable source of truth: committed data survives a crash thanks to the [write-ahead log](card:wal), and it has constraints, joins and transactions. The cache is a copy kept in memory for speed: it may be stale, and it may lose data in a crash. Rule: if losing it would lose information, it belongs in the database.

## Common mistakes

- **"Write the new value into the cache on every update."** Two updates running at the same time can reach the database in one order and the cache in the other, leaving the older value cached until the TTL ends. Deleting the key avoids that race, because the next read loads from the database.

## Interview Qs

### Why not keep everything in Redis instead of the database?

Redis keeps data in memory, so size costs RAM, and a crash can lose recent writes: about a second with AOF `everysec`, and everything since the last snapshot with RDB alone. The database gives durable storage, constraints, joins and transactions. Redis is the fast layer in front, not the record.

### How do you keep the cache and the database consistent?

Not perfectly without extra cost. Update the database first, then delete the key, and set a TTL on every key so a missed delete heals itself. Do not cache data that must never be stale.

### What else is Redis used for in a backend?

Besides caching: [session storage](card:redis-sessions), [counters and rate limits](card:redis-rate-limiter) with atomic `INCR`, [distributed locks](card:redis-distributed-lock) and [pub/sub messaging](card:redis-pub-sub). In each case the database still holds the permanent data.
