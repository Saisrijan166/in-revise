## Why it exists

Tables with joins suit related data, but some workloads read one shape at huge scale. NoSQL stores give up joins or a fixed schema to serve that shape fast.

## How it works

- Types: [document](card:document-database), [key-value](card:key-value-store), [wide-column](card:wide-column-store), [graph](card:graph-database).
- Consistency trade-offs across nodes belong to the [CAP theorem](card:cap-theorem).

## Example

One order as a MongoDB document. SQL would split it into `users`, `orders` and `order_items` and join them on read.

```json
{
  "_id": 101,
  "user": { "id": 1, "name": "Asha" },
  "items": [
    { "sku": "PEN", "qty": 2 },
    { "sku": "BOOK", "qty": 1 }
  ]
}
```

## Interview Qs

### When would you pick NoSQL over SQL?

When one access pattern dominates and must scale out (values by key in Redis, huge partitioned tables in Cassandra), or records vary in shape. For related data that needs joins and transactions, choose SQL.

### Can a NoSQL database run transactions?

Some can. MongoDB supports multi-document ACID transactions on replica sets since 4.0 and on sharded clusters since 4.2. Its docs add that embedding related data in one document makes them unneeded in many cases.

### Name the NoSQL types with an example each.

Document: MongoDB. Key-value: Redis. Wide-column: Cassandra. Graph: Neo4j.
