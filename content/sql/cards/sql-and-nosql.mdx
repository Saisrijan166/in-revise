## What it is

"SQL databases" means [relational databases](card:relational-databases): data in tables with fixed columns, queried with SQL. "NoSQL" is a family name for stores that do not use tables, such as MongoDB, which keeps each record as a JSON-like document. The difference is where related data lives. SQL keeps each fact in one table and combines tables when you query; a NoSQL record usually carries its related data inside it.

## Why it exists

Splitting data into tables keeps every fact in one place, but each read must combine the pieces again, and one database server can only grow so far. Some workloads read one shape at huge scale, such as "the profile for user 42", millions of times a second. NoSQL stores give up general joins, and often a fixed schema, so that this one read is a single lookup that can be spread across many servers.

## How it works

<Compare id="sql-vs-nosql" />

1. With SQL you design tables around the data itself: customers in one table, payments in another, linked by the customer's id.
2. At query time the database combines them, for example "every payment with its customer's name". Combining tables on a shared id is called a join; [joins](card:joins) covers it later.
3. With a document store you design around the read: if a screen shows a payment with its customer and refunds, you store exactly that as one document.
4. The read becomes one lookup by key, and the store can place documents on different servers by that key. The price is that a customer's name copied into many documents must be updated in each of them.

So the key is: SQL designs for the data, NoSQL designs for the query.

## Example

One payment stored as a MongoDB document. In SQL the same data would sit in three tables, `customers`, `payments` and `refunds`, joined on read.

```json
{
  "_id": 10,
  "customer": { "id": 1, "name": "Asha", "city": "Pune" },
  "amount": 500.00,
  "status": "PAID",
  "refunds": [ { "id": 1, "amount": 100.00 } ]
}
```

What to notice:

- The customer's name sits inside the payment. Reading the payment screen needs one lookup and no join.
- If Asha changes her name, every payment document that copied it must be updated; in SQL you change one row in `customers`.
- `refunds` is a list inside the document. In SQL it would be its own table with a column pointing back to the payment.

## Rules and defaults

- **Schema:** SQL declares columns and types up front with `CREATE TABLE`. MongoDB accepts documents of any shape unless you add schema validation rules to the collection.
- **Transactions:** relational databases run multi-row transactions by default. MongoDB supports multi-document ACID transactions (all changes succeed or none do) on replica sets (one database copied to several servers) since 4.0, and on sharded clusters (data split across servers) since 4.2. Its docs note that embedding related data often removes the need for them.
- **Scaling out:** a typical PostgreSQL or MySQL setup has one server that accepts writes and copies that serve reads. Cassandra spreads data over many nodes by partition key as part of its design.

## Interview Qs

### When would you pick NoSQL over SQL?

When one access pattern dominates and must scale out, such as values by key in Redis or huge time-ordered data partitioned by key in Cassandra, or when records really vary in shape. For related data that needs joins, constraints and transactions, I choose SQL. Many systems use both side by side.

### Can a NoSQL database run transactions?

Some can. MongoDB supports multi-document ACID transactions on replica sets since 4.0 and on sharded clusters since 4.2. Its docs add that keeping related data in one document often makes them unnecessary, because a write to a single document is already atomic.

### Name the NoSQL types with an example each.

Document store: MongoDB, which keeps JSON-like documents. Key-value store: Redis, where each value is found by its key. Wide-column store: Cassandra, with rows partitioned across nodes. Graph database: Neo4j, which stores nodes and the relationships between them.
