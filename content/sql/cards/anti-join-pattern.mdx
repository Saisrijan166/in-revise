## Why it exists

A normal join drops rows that have no match, so missing data stays hidden. You need a filter that keeps the rows whose match does not exist.

## How it works

| Form | Returns | If orders.user_id has a NULL |
|---|---|---|
| `NOT EXISTS (… WHERE o.user_id = u.id)` | Users with no order | Still correct |
| `LEFT JOIN orders o … WHERE o.id IS NULL` | Users with no order | Still correct |
| `u.id NOT IN (SELECT user_id …)` | Users with no order | No rows at all |
| `EXISTS (…)`, a semi-join | Users with an order, once each | Still correct |

- Why NOT IN breaks: [NULL comparisons](card:null-handling) give unknown, never true.
- MySQL rewrites NOT EXISTS and NOT IN subqueries into antijoins internally.

## Example

```sql
-- Users with no orders
SELECT u.id, u.name
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);
-- Same with a join: keep users that matched no order
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

## Interview Qs

### NOT EXISTS, LEFT JOIN … IS NULL or NOT IN: which is fastest?

Plans differ by product and version, so check with [EXPLAIN](card:explain-query-plans). Choose for correctness first: NOT IN changes the answer when NULLs exist. NOT EXISTS is NULL-safe.

### Find users who placed at least one order, without duplicates.

`WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)`. An inner join returns a user once per order.
