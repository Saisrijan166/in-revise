## Why it exists

An index helps only when the planner can match it to the query and expects it to be cheaper.

## How it works

| Cause | Example | Fix |
|---|---|---|
| Matches a big share of rows | `status = 'PAID'` on most rows | Fine as is; partial index on rare values |
| Function on the column | `lower(email) = '...'` | Expression index on `lower(email)` |
| Type mismatch | MySQL: VARCHAR `phone = 98100` | Compare with a string: `'98100'` |
| Leading wildcard | `name LIKE '%kumar'` | PostgreSQL `pg_trgm` GIN index |
| First index column missing | index `(user_id, status)`, `WHERE status = ...` | Index on `status` |
| Stale statistics | right after a bulk load | `ANALYZE` / MySQL `ANALYZE TABLE` |
| OR on two columns | `user_id = 7 OR city = 'Pune'` | An index on each column, or `UNION` |

- Read the plan first: [EXPLAIN](card:explain-query-plans).

## Example

```sql
CREATE INDEX idx_users_email ON users (email);
-- skipped: the index holds email, the query asks for lower(email)
SELECT id FROM users WHERE lower(email) = 'asha@example.com';

-- fix: index the same expression
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

## Interview Qs

### Why does a function on an indexed column stop the index?

The index stores `email`, not `lower(email)`, so the database cannot seek on the computed value. Index the expression, or store the value already normalised.

### What are selectivity and cardinality?

Selectivity: the share of rows a condition keeps; smaller helps an index. Cardinality: distinct values in a column; email is high, status is low.
