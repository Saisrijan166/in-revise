## What it is

A backup is a copy of the database, kept somewhere safe, from which you can rebuild it. Recovery is using that copy, and usually the log of later changes, to bring the data back after a failure. High availability (HA) is a related but different goal: staying up when a server dies, usually by failing over to a [standby replica](card:replication). Backups fix lost or damaged data; HA fixes downtime.

## Why it exists

Two different disasters need two different tools. If the primary's server dies, a standby can take over in minutes. If someone runs `DELETE FROM payments` without a WHERE, the standby deletes the rows too, within a second. Only a backup taken earlier, plus the [log](card:wal) of changes up to just before the mistake, brings those rows back. This is point-in-time recovery (PITR).

## How it works

  chart={`flowchart LR
  B["1. Base backup, 02:00"] --> W["2. WAL archived all day"] --> M["3. 11:00: DROP TABLE"]
  M --> R["4. Restore base backup on a spare server"] --> P["5. Replay WAL up to 10:59"]`}
/>

1. Every night, take a physical base backup, a copy of the data files, with `pg_basebackup`.
2. All day, archive every finished WAL file (PostgreSQL) or keep the binary logs (MySQL).
3. At 11:00 someone drops a table. You note the time of the mistake.
4. On a spare server, restore the latest base backup taken before 11:00.
5. Replay the archived log up to a target just before the mistake, such as 10:59, and stop there. The data is now as it was at 10:59.

So the key is: the base backup is the starting point, and the log carries you forward to any moment after it.

## Example

The `payments` table was dropped at 16:30:13. On a spare server holding the restored base backup, PostgreSQL 18 replays the archived WAL up to 16:30:12.

```bash
# in the restored base backup's data directory
cat >> postgresql.conf <<'EOF'
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-10-21 16:30:12+00'
EOF
touch recovery.signal                       # start in recovery mode
pg_ctl -D . start                           # replays WAL up to the target, then pauses
psql -c "SELECT pg_wal_replay_resume();"    # end recovery, accept writes
psql -c "SELECT * FROM payments;"
```

```text output
 id | amount
----+--------
  1 | 500.00
  2 | 250.00
(2 rows)
```

What to notice:

- `restore_command` tells PostgreSQL how to fetch each archived WAL file: `%f` is the file name, `%p` where to put it.
- Replay stops before the first commit after the target time, so the DROP at 16:30:13 is not replayed and the rows are back. A target after 16:30:13 would replay the DROP too.
- `recovery.signal` makes the server start in recovery instead of as a normal primary. By default it pauses at the target (`recovery_target_action = pause`); `pg_wal_replay_resume()` ends recovery.

## Rules and defaults

- **Whole server only:** a PostgreSQL physical backup restores the entire server, never one table. To get one table back, restore on a spare server and copy the table over.
- **Keep every log file:** PITR needs an unbroken chain of WAL files from the start of the base backup, and the target time must be after the base backup finished.
- **MySQL PITR:** restore the full backup, then replay later binary logs with `mysqlbinlog --stop-datetime="..." binlog.000007 | mysql`. Binary logging is on by default in MySQL 9.7.
- **RPO and RTO:** RPO decides how often you back up and ship the log; RTO decides how fast restore or failover must be.
- **Failover:** PostgreSQL does not detect a failed primary by itself. Promote the standby with `pg_ctl promote` or `pg_promote()`, and make sure the old primary cannot take writes again.
- **Test restores:** schedule real restores and time them; an untested backup may not work.

## Not to be confused with

A [logical backup](card:logical-backup) is SQL text, made by `pg_dump` or `mysqldump`, that rebuilds the tables and rows; you can restore one table or load it into a newer version. A [physical backup](card:physical-backup) is a copy of the data files; it is faster for big databases and is the base for PITR in PostgreSQL. Rule: logical for one table or an upgrade; physical plus the log for production recovery.

## Interview Qs

### What is the difference between RPO and RTO?

RPO, the recovery point objective, is how much data, measured in time, you can afford to lose: hourly backups mean up to an hour. RTO, the recovery time objective, is how long the service may stay down before it is back.

### How do you recover a table someone dropped an hour ago?

Restore the last base backup on a separate server and replay the WAL or binary log to just before the DROP. Then copy the table back to production, or switch over to the restored server. A replica cannot help, because it replayed the DROP too.

### Logical or physical backup for a 2 TB production database?

Physical, with continuous log archiving: copying files is much faster than dumping and reloading rows, and it allows point-in-time recovery. Keep logical dumps for moving single tables or upgrading to a new major version.
