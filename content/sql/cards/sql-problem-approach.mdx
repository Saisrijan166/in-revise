## What it is

This is a six-step method for any SQL question, including one you have never seen. The first step fixes the output grain: what one row of the answer stands for, such as "one row per city". The later steps follow the order in which the database runs the clauses ([Logical order of a SELECT](card:query-order)), so each step only uses what the earlier steps produced.

## Why it exists

Without a method, people write the `SELECT` list first and patch the query until the output looks right. That hides two classic bugs: a count of payments where the question asked for customers, and a sum that doubles because a join repeated rows. Fixing the grain first and checking edge cases last catches both before the interviewer does.

## How it works

1. Say the grain aloud: "one row per city". That key goes into `GROUP BY` (rows collapse) or `PARTITION BY` (rows stay).
2. Choose the tables and the join keys. Ask of each join: can one row on this side match many on the other? If so, the join repeats rows.
3. Put every condition on a single row in `WHERE`.
4. Group with `GROUP BY` to get one row per group, or rank with a [window function](card:window-functions) to keep every row. The question's words pick the pattern (table below).
5. Filter the result: `HAVING` for groups, or an outer query for ranks, since a window result cannot appear in `WHERE`.
6. Test the edge cases: NULLs, ties, duplicates, groups with no rows, and an empty table.

| The question says | Pattern |
|---|---|
| "second highest", "top 3 in each", "latest per customer" | [Rank, then filter](card:top-n-per-group) |
| "more than once", "remove the copies" | [Duplicates](card:duplicates) |
| "never", "without any" | [Anti-join](card:anti-join-pattern) |
| "running", "versus the previous", "days in a row" | [Window over ordered rows](card:running-totals-and-streaks) |
| "as columns", "including zero", "above average" | [Group patterns](card:group-aggregation-patterns) |
| "manager chain", "all levels below" | [Recursive CTE](card:ctes) |

## Example

The question: "For each city, how many customers made a successful payment, and how much did they pay?" The grain is one row per city.

```sql
SELECT c.city,
       COUNT(DISTINCT c.id) AS payers,     -- customers, not payments
       COUNT(*)             AS payments,   -- joined rows, for comparison
       SUM(p.amount)        AS total_paid
FROM customers c
JOIN payments p ON p.customer_id = c.id    -- one customer, many payments
WHERE p.status = 'PAID'                    -- condition on one row
GROUP BY c.city                            -- the grain
ORDER BY c.city;
```

```text output
 city  | payers | payments | total_paid
-------+--------+----------+------------
 Delhi |      2 |        2 |    1000.00
 Pune  |      1 |        3 |    1600.00
```

What to notice:

- Pune has 1 payer but 3 payments: Asha paid three times. `COUNT(*)` counts joined rows, so only `COUNT(DISTINCT c.id)` answers "how many customers".
- Mumbai is missing. Kabir has no payments, so the inner join dropped him. If the question says "every city", start from `customers` with a `LEFT JOIN` and put the status test in `ON`.
- The edge-case step is what found both points; the query ran without errors either way.

## Rules and defaults

- **Window results stay out of WHERE:** filter a rank in an outer query, as [Logical order of a SELECT](card:query-order) explains.
- **One-to-many joins repeat the parent:** aggregate the child table in a subquery first, or count with `DISTINCT`.
- **NULL edge cases:** `COUNT(column)` skips NULLs, and `SUM` over no rows is NULL, not 0 ([Aggregates](card:aggregates-group-by)).
- **Ties:** when the answer must have exactly N rows, add a unique tie-breaker such as `id` to every `ORDER BY`.

## Not to be confused with

`GROUP BY` collapses each group into one output row, so the detail rows are gone. `PARTITION BY` in a window splits rows into groups but keeps every row and adds a value beside it. Rule: "one row per group" means `GROUP BY`; "every row, with something about its group" means `PARTITION BY`.

## Interview Qs

### How do you start a SQL question you have never seen?

I ask what one output row means, and how to treat ties, NULLs and groups with no rows. Then I write FROM and the joins, WHERE, then GROUP BY or a window, then HAVING or an outer filter, and test the edge cases on a few rows.

### Why is my SUM too big after a join?

A one-to-many join repeats the parent row once per child. In our data, Asha paid 1600, but joining her payments to refunds, with one payment refunded in two parts, gives `SUM(p.amount)` of 2300, because that payment is counted twice. Aggregate the refunds per payment first, then join.

### Which questions do you ask the interviewer before writing?

What one result row stands for, whether ties should all be returned, whether groups with no rows should appear with 0, and whether NULLs count as values. Each answer changes the query, so asking shows you know where queries go wrong.
