## Why it exists

Most SQL interview questions are a few known shapes. Fixed steps turn a vague question into the right shape and catch the usual edge cases.

## How it works

<Steps label="Six steps for any SQL question">
  <Step title="Grain">Say "one row per …": user, department, day.</Step>
  <Step title="Tables">Pick tables and join keys; one-to-many joins repeat rows.</Step>
  <Step title="Filter rows">Row conditions go in `WHERE`.</Step>
  <Step title="Group or rank">`GROUP BY` collapses rows; a window function keeps them.</Step>
  <Step title="Filter again">`HAVING` for groups; an outer `WHERE` for ranks.</Step>
  <Step title="Edge cases">NULLs, ties, duplicates, empty groups, no rows.</Step>
</Steps>

| The question says | Pattern |
|---|---|
| "second highest", "top 3 in each", "latest per user" | [Rank, then filter](card:top-n-per-group) |
| "duplicate", "more than once" | [GROUP BY + HAVING](card:duplicates) |
| "never", "without any", "not in" | [NOT EXISTS](card:anti-join-pattern) |
| "running", "versus previous", "in a row" | [Window over ordered rows](card:running-totals-and-streaks) |
| "as columns", "including zero", "above average" | [Conditional aggregation](card:group-aggregation-patterns) |
| "manager chain", "all levels below" | [Recursive CTE](card:ctes) |

## Example

```sql
-- Grain: one row per city
SELECT u.city, COUNT(DISTINCT u.id) AS buyers   -- DISTINCT: a user has many orders
FROM users u
JOIN orders o ON o.user_id = u.id               -- tables and key
WHERE o.status = 'PAID'                         -- filter rows
GROUP BY u.city                                 -- group
HAVING COUNT(DISTINCT u.id) > 2;                -- filter groups
```

## Interview Qs

### How do you start a SQL question you have never seen?

Ask what one output row means and how to treat ties, NULLs and empty groups. Then write FROM, WHERE, GROUP BY or a window, and HAVING, in the [order the database runs them](card:query-order).

### Why is my SUM too big after a join?

A one-to-many [join](card:joins) repeats the parent row once per child, so its values are added many times. Aggregate the child table first, then join.
