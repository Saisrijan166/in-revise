## What it is

English to SQL is the habit of reading a question word by word and giving each signal word one SQL clause. "How many" becomes `COUNT`, "per customer" becomes `GROUP BY`, "only paid ones" becomes `WHERE`. You then write those clauses in the order SQL requires. This concept is the word list; the [next one](card:sql-problem-approach) is the method for harder questions.

## Why it exists

Interview questions arrive as a sentence, not as SQL. Without a word list, people type `SELECT` and guess, and the usual result is a condition in the wrong clause: "more than 500 in total" put in `WHERE`, which fails because `WHERE` cannot see a sum. When each word has exactly one home, a long question becomes a short checklist.

## How it works

| The question says | SQL |
|---|---|
| show, list · unique | `SELECT` · `DISTINCT` |
| only, between, one of, starts with, missing | `WHERE`, `BETWEEN`, `IN`, `LIKE 'A%'`, `IS NULL` |
| how many, total, average, highest, lowest | `COUNT`, `SUM`, `AVG`, `MAX`, `MIN` |
| per, for each · groups with more than | `GROUP BY` · `HAVING` |
| sorted, highest first · top 5 | `ORDER BY … DESC` · `LIMIT 5` |
| with their customer · including those with none | `JOIN` · `LEFT JOIN` |
| label each, custom sort · 0 if missing | `CASE`, `ORDER BY CASE` · `COALESCE(x, 0)` |
| never, has none · more than once | [NOT EXISTS](card:anti-join-pattern) · [GROUP BY + HAVING](card:duplicates) |
| Nth highest, top N in each, running, in a row | a pattern: see [the method](card:sql-problem-approach) |

1. Underline every signal word in the question.
2. Look up each word's clause in the table.
3. Write the clauses in the written order: `SELECT`, `FROM`, `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`.
4. Check both ways: every word has a clause, and no clause is there without a word.

## Example

The question: "Show the 2 customers who paid the most, counting only successful payments, and only if they paid more than 500 in total." Each comment names the word that produced the line.

```sql
SELECT c.name, SUM(p.amount) AS total_paid   -- paid the most → SUM
FROM customers c
JOIN payments p ON p.customer_id = c.id      -- customers + payments → JOIN
WHERE p.status = 'PAID'                      -- only successful → WHERE
GROUP BY c.id, c.name                        -- per customer → GROUP BY
HAVING SUM(p.amount) > 500                   -- more than 500 in total → HAVING
ORDER BY total_paid DESC, c.id               -- the most → DESC, id breaks ties
LIMIT 2;                                     -- the 2 → LIMIT
```

```text output
 name | total_paid
------+------------
 Asha |    1600.00
 Ravi |     700.00
```

What to notice:

- `WHERE` removed Asha's FAILED payment and Meena's PENDING one before grouping, so Meena never reached a group. Kabir has no payments, so the inner join dropped him.
- `HAVING` removed Neha, whose only paid total is 300. Put that test in `WHERE` and the query fails: an aggregate is not allowed there.
- Grouping by `c.id` as well as `c.name` keeps two customers who share a name apart.
- `LIMIT 2` runs last. Only two customers were left here, so it removed nothing.

## Rules and defaults

- **Written order is fixed:** `SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT`. The database runs them in a different order, which [Logical order of a SELECT](card:query-order) explains.
- **LIMIT counts rows, not values:** "the top 3 amounts" with two payments of 700 needs `SELECT DISTINCT amount … ORDER BY amount DESC LIMIT 3`. `DISTINCT` runs before `LIMIT`, so `LIMIT` then counts amounts.
- **A tie-breaker makes LIMIT repeatable:** without a unique column at the end of `ORDER BY`, tied rows can come back in any order, so `LIMIT` can return a different row each time.
- **Group by the key:** for "per customer", group by `c.id`, not only `c.name`.

## Not to be confused with

`WHERE` tests one row at a time, before grouping: "only PAID payments", "customers in Pune". `HAVING` tests a whole group, after grouping: "more than 500 in total", "more than 2 payments". Rule: a condition that uses `COUNT`, `SUM` or `AVG` goes in `HAVING`; any other condition goes in `WHERE`.

## Interview Qs

### "Top 3 payment amounts": do you return rows or values?

Ask the interviewer, because ties change the answer. For rows: `ORDER BY amount DESC, id LIMIT 3`, which can repeat an amount. For amounts: `SELECT DISTINCT amount FROM payments ORDER BY amount DESC LIMIT 3`, which gives three different values.

### Pune customers who paid more than 1000 in total: WHERE or HAVING?

Both. The city belongs to each row, so `WHERE c.city = 'Pune'` filters rows before grouping. "In total" is a sum, so `GROUP BY c.id HAVING SUM(p.amount) > 1000` filters the groups afterwards.

### Why is GROUP BY c.name risky for "total per customer"?

Two different customers can share a name, and grouping by name alone merges them into one row with a combined total. Group by the key, `c.id`, and add `c.name` so you can still select it.
