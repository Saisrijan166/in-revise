## Why it exists

An API must not return a million rows at once. Pages fix that, but the obvious `OFFSET` gets slower with every page.

## How it works

<Compare id="offset-vs-keyset-pagination" />

- The client sends back the last row's `(created_at, id)`: that pair is the cursor.
- MySQL: the row comparison gives correct rows but may not get an index range scan. Spell it out: `created_at < ? OR (created_at = ? AND id < ?)`.

## Example

```sql
CREATE INDEX idx_orders_created ON orders (created_at, id);

-- first page
SELECT id, amount, created_at FROM orders
ORDER BY created_at DESC, id DESC LIMIT 20;

-- next page: values from the last row of the previous page
SELECT id, amount, created_at FROM orders
WHERE (created_at, id) < ('2026-10-01 10:00', 981)
ORDER BY created_at DESC, id DESC LIMIT 20;
```

## Interview Qs

### Why is OFFSET slow on deep pages?

The database must still find, sort and discard every skipped row: `OFFSET 100000` reads 100,020 rows to return 20. The cost grows with the page number.

### How does keyset (cursor) pagination work?

Sort by a unique order such as `(created_at, id)`, index it, and ask for rows after the last row the client saw. The database seeks straight there, so page 1 and page 5,000 cost the same.

### When is OFFSET still fine?

When users need page numbers and the offsets stay small, such as an admin screen. Always pair it with an ORDER BY on a unique order, or pages are unpredictable.
