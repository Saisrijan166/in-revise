## What it is

These are three report patterns built on [GROUP BY](card:aggregates-group-by). A pivot turns row values into columns, such as one count column per payment status. A zero count keeps groups that have no rows, such as a customer with no payments. An above-average filter compares each row with an average. Each one fills a gap that a plain `GROUP BY` leaves.

## Why it exists

`GROUP BY status` gives one row per status, but a report usually wants one row per customer with PAID and FAILED side by side. An inner join drops customers who have no payments, so the report hides them. And `WHERE amount > AVG(amount)` is rejected, because `WHERE` runs before any average exists. Each pattern solves one of these three problems.

## How it works

| Need | Pattern | Watch out |
|---|---|---|
| Categories as columns | `SUM(CASE WHEN … THEN 1 ELSE 0 END)`, or `COUNT(CASE WHEN … THEN 1 END)` | Without `ELSE 0`, SUM gives NULL when nothing matches |
| Groups with zero rows | Parent `LEFT JOIN` child, `COUNT(child.id)` | A child condition in `WHERE` drops the empty groups again |
| Above the overall average | `WHERE x > (SELECT AVG(x) FROM …)` | The subquery must return one value |
| Above the group's own average | `AVG(x) OVER (PARTITION BY g)` in a subquery | Or a correlated subquery |

1. Pivot: for each output column, write one aggregate over a `CASE` that keeps only that category. `CASE` returns 1 for a match and 0 otherwise, so `SUM` counts the matches.
2. Zero counts: start `FROM` the parent table (customers), `LEFT JOIN` the child (payments), and count the child's key. An unmatched customer has one row with NULL in `p.id`, which `COUNT(p.id)` skips.
3. Empty sums: `SUM` over no values returns NULL, so wrap it as `COALESCE(SUM(…), 0)`.
4. Above average: compare with a scalar subquery for the overall average. For each group's own average, compute `AVG() OVER (PARTITION BY …)` in a subquery and compare in the outer query.

## Example

One row per customer, with every customer shown, payment counts per status, and the amount paid.

```sql
SELECT c.name,
       COUNT(p.id)                                          AS payments,
       SUM(CASE WHEN p.status = 'PAID'   THEN 1 ELSE 0 END) AS paid,
       SUM(CASE WHEN p.status = 'FAILED' THEN 1 ELSE 0 END) AS failed,
       COALESCE(SUM(CASE WHEN p.status = 'PAID' THEN p.amount END), 0) AS paid_amount
FROM customers c
LEFT JOIN payments p ON p.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY c.id;
```

```text output
 name  | payments | paid | failed | paid_amount
-------+----------+------+--------+-------------
 Asha  |        4 |    3 |      1 |     1600.00
 Ravi  |        1 |    1 |      0 |      700.00
 Meena |        1 |    0 |      0 |           0
 Kabir |        0 |    0 |      0 |           0
 Neha  |        1 |    1 |      0 |      300.00
```

What to notice:

- Kabir shows 0 payments because the query counts `p.id`. With `COUNT(*)` he would show 1, the joined row that holds no payment.
- Meena's only payment is PENDING, so the `CASE` inside `paid_amount` gives NULL for it, and `SUM` of only NULLs is NULL. `COALESCE` turns that into 0. MySQL prints it as `0.00`.
- The three status columns are written into the query. A new status, such as REFUNDED, needs a new line; plain SQL has no automatic pivot.

## Rules and defaults

- **FILTER clause:** PostgreSQL accepts `COUNT(*) FILTER (WHERE p.status = 'PAID')`, which feeds the aggregate only matching rows. MySQL 9.7 rejects `FILTER`, so the `CASE` form is the one that runs on both.
- **Child conditions go in ON:** after a `LEFT JOIN`, `WHERE p.status = 'PAID'` removes Kabir and Meena again. Put the condition in `ON`, or inside the `CASE`, as above ([Joins](card:joins)).
- **Scalar subquery:** `(SELECT AVG(amount) FROM payments)` must return exactly one value; a subquery that returns several rows is an error.

## Not to be confused with

`WHERE` removes rows before the aggregates run, so a condition there changes every column. A `CASE` inside an aggregate only decides what one column counts, and every row still reaches the group. Rule: to filter the whole report, use `WHERE`; to count one category beside others, use `CASE` inside the aggregate.

## Interview Qs

### Find payments above their customer's own average.

Compute `AVG(amount) OVER (PARTITION BY customer_id) AS cust_avg` in a subquery and keep `amount > cust_avg` outside. Here that returns payments 1 and 4, since Asha averages 475. A correlated subquery, `amount > (SELECT AVG(p2.amount) FROM payments p2 WHERE p2.customer_id = p.customer_id)`, gives the same rows.

### How do you turn rows into columns?

Write one aggregate over a `CASE` for each output column, grouped by the row key. PostgreSQL also offers `FILTER (WHERE …)`. The list of columns is fixed in the query text, so new categories need a change to the query.
