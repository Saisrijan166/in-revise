## What it is

Replication is keeping copies of the same database on several servers, updated automatically. One server, the primary, accepts all writes. The others, called replicas or standbys, receive the primary's change log and replay it, so a moment later they hold the same data. That log is the change log you met in [the write-ahead log](card:wal): the WAL in PostgreSQL, the binary log in MySQL (where the primary is called the "source").

## Why it exists

With one database server, a crash stops every payment until someone repairs the machine, and every read and write competes for that one server. With a replica, you can promote the standby to be the new primary in minutes; this switch is called failover. Read-heavy work, such as payment history pages and reports, moves to the replicas, which leaves the primary free for writes.

## How it works

  chart={`flowchart LR
  App -- "1. writes" --> P[(Primary)]
  P -- "2. log streamed" --> R1[(Replica 1)]

  App -. "4. reads" .-> R1
  App -. "4. reads" .-> R2`}

1. The app sends `UPDATE payments SET status = 'PAID' ...` to the primary, which commits it and records it in its log.
2. The primary streams the new log records to each replica. By default it tells the app "committed" without waiting for them.
3. Each replica replays the records in order, so its copy catches up a little later. That gap is the replication lag.
4. The app sends reads that can accept slightly old data to a replica. A replica accepts only reads; a write sent there fails.
5. If the primary dies, a tool or an operator promotes a replica to primary, and the app sends its writes there.

So the key is: one place for writes, many places for reads, and a small delay in between.

## Example

The payment service keeps two connection sources: the primary for writes and a replica for reads. A customer who has just paid reads from the primary, so their receipt is never stale.

```java
public class PaymentDb {
    private final DataSource primary;   // takes every write
    private final DataSource replica;   // read-only copy that may lag

    public PaymentDb(DataSource primary, DataSource replica) {
        this.primary = primary;
        this.replica = replica;
    }

    public Connection forWrite() throws SQLException { return primary.getConnection(); }
    public Connection forRead(boolean userJustWrote) throws SQLException {
        // read-your-writes: a user who just wrote reads from the primary
        return (userJustWrote ? primary : replica).getConnection();
    }
}
```

What to notice:

- Writes always use `primary`. An UPDATE sent through `replica` would fail, because a replica is read-only.
- `forRead(true)` is the read-your-writes rule: right after a write, that user reads from the primary, which already has the change.
- Other reads, such as the monthly statement, use `replica` and take load off the primary. If you always read the replica, a receipt can show `PENDING` for a payment that is already `PAID`.

## Rules and defaults

- **Asynchronous by default:** in PostgreSQL 18 and MySQL 9.7 a commit does not wait for any replica. If the primary crashes, commits that had not reached the replica are lost after failover. Synchronous replication closes that gap at the cost of slower commits.
- **PostgreSQL:** [streaming replication](card:streaming-replication) replays the WAL and copies the whole server; queries on a standby are allowed by default (`hot_standby = on`). [Logical replication](card:logical-replication) copies chosen tables and works across major versions.
- **MySQL:** replicas pull the source's binary log; GTIDs give each transaction an id, so a replica knows what it has already applied.
- **Delayed replica:** `recovery_min_apply_delay` (PostgreSQL) or `SOURCE_DELAY` (MySQL) keeps a replica deliberately behind, for example by one hour, so a mistake can be caught before it is replayed there. Both default to 0.
- **Failover is not built into PostgreSQL:** it does not detect a failed primary by itself; an outside tool or an operator promotes the standby.

## Not to be confused with

Replication copies the **same** data to every server. [Sharding](card:sharding), which you will see two concepts later, splits **different** rows across servers. Rule: replication = copy, which scales reads; sharding = split, which scales writes.

## Common mistakes

- **"Send every read to the replicas to spread the load."** Some reads must be fresh, such as the balance check before a refund or the page right after a payment. Send those to the primary.

## Interview Qs

### A user updates a profile and the page still shows old data. Why?

The read went to a replica that had not yet replayed the write: replication lag. Replication is asynchronous by default, so this is normal. Read that user's data from the primary for a short time after a write, or pin their session to the primary.

### Does adding replicas scale writes?

No. Every write still runs on the one primary, and each replica must replay every write too. Replicas scale reads and availability. To scale writes, reduce or tune them, move to a bigger server, and only then consider sharding.

### What happens to committed data if the primary crashes?

With asynchronous replication, commits the replica had not received yet are lost when you fail over to it. With synchronous replication, each commit waited until a standby had stored it, so it survives unless both servers fail.
