## What it is

These are three kinds of code you store in the database itself, written in SQL or a database language such as PostgreSQL's PL/pgSQL. A stored procedure is a named job you run with `CALL`, such as "mark old pending payments as failed". A function takes inputs and returns a value, so you can use it inside a query like any built-in function. A trigger is code the database runs automatically when rows in a table are inserted, updated or deleted.

## Why it exists

Some jobs need many SQL statements in a row; sent one by one from the app, each pays a network round trip. Some rules must hold however the data is written: every status change of a payment should be audited, whether it comes from the app, a script or a support engineer at the console. Code stored next to the data runs in one call and, for triggers, applies to every writer without anyone remembering to call it.

## How it works

  U([UPDATE payments]) --> B[BEFORE trigger: check or change NEW]

  A -. error .-> R`}

Follow one UPDATE on a table with triggers:

1. The statement starts inside a transaction, the group of changes that is saved together at COMMIT or undone together at ROLLBACK.
2. For each row, a BEFORE trigger runs first. It sees the old row as `OLD` and the new row as `NEW`, and it can change `NEW` or reject the change.
3. The database writes the row.
4. An AFTER trigger runs, typically to write an audit row or update a summary.
5. If any trigger raises an error, the whole statement fails and its changes, including the triggers' own writes, are rolled back.

So the key is that a trigger is part of the write, not a step after it.

## Example

This audits every status change of a payment, run on PostgreSQL 18. The trigger calls a function that returns the special type `trigger`.

```sql
CREATE TABLE payment_audit (payment_id bigint, old_status text, new_status text);

CREATE FUNCTION log_status() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO payment_audit VALUES (OLD.id, OLD.status, NEW.status);
  RETURN NEW;
END $$;

CREATE TRIGGER payment_status_audit
  AFTER UPDATE OF status ON payments
  FOR EACH ROW EXECUTE FUNCTION log_status();

UPDATE payments SET status = 'PAID' WHERE id = 5;
SELECT * FROM payment_audit;
```

```text output
 payment_id | old_status | new_status
------------+------------+------------
          5 | PENDING    | PAID
```

What to notice:

- The UPDATE says nothing about auditing; the audit row appears because the trigger ran inside the same statement.
- `UPDATE OF status` fires only when the status column is set. MySQL has no `OF` list: write `AFTER UPDATE ON payments FOR EACH ROW INSERT INTO payment_audit VALUES (OLD.id, OLD.status, NEW.status)`; it fires on every update.
- `FOR EACH ROW` runs once per changed row; an UPDATE of 1,000 payments writes 1,000 audit rows.

A procedure for a nightly job looks like this; it commits its own work:

```sql
CREATE PROCEDURE fail_old_pending(cutoff timestamptz) LANGUAGE plpgsql AS $$
BEGIN
  UPDATE payments SET status = 'FAILED'
  WHERE status = 'PENDING' AND created_at < cutoff;
  COMMIT;
END $$;
CALL fail_old_pending(now() - interval '1 day');
```

What to notice:

- It runs with `CALL` and returns nothing; you cannot write it inside a SELECT.
- The `COMMIT` inside works only when the CALL is not inside your own BEGIN block; there PostgreSQL raises "invalid transaction termination".

## Rules and defaults

- **Row or statement triggers:** PostgreSQL supports `FOR EACH ROW` and `FOR EACH STATEMENT`; a statement trigger fires even when zero rows change. MySQL triggers are row-level only.
- **INSTEAD OF (PostgreSQL):** a row trigger on a view that writes the base tables instead.
- **BEFORE returning NULL (PostgreSQL):** skips the operation for that row silently.
- **Cascades:** MySQL triggers are not activated by foreign key actions such as ON DELETE CASCADE.
- **No COMMIT in functions or triggers:** not allowed in either product. Procedures may commit (PostgreSQL 11+ when not called inside an explicit transaction).

## Not to be confused with

A procedure is a job you start on purpose with CALL; a function is an expression you use inside a query and it returns a value; a trigger is never called by name and runs because a table changed. Rule: CALL it, SELECT it, or let a change fire it.

## Interview Qs

### What is the difference between a stored procedure and a function?

A function returns a value, or in PostgreSQL also a set of rows, and is used inside SELECT or WHERE. A procedure runs on its own with CALL, returns data only through OUT parameters or, in MySQL, result sets, and may COMMIT part-way through. Functions cannot commit in either product.

### When would you use a trigger, and why be careful?

For audit logs, an updated_at column, or a rule every writer must follow. Be careful: triggers are invisible to anyone reading the app code, add work to every write, can fire other triggers, and in MySQL do not run for cascaded foreign key changes.

### Should business logic live in stored procedures?

Usually only small, data-heavy parts. Logic in the app is easier to test, version, review and deploy, and ties you less to one database. Procedures earn their place for batch jobs that touch many rows, where one call saves thousands of round trips.
