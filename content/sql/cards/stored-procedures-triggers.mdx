## Why it exists

Some jobs take many SQL statements, and some rules must hold however data is written. Code next to the data saves round trips and applies to every writer.

## How it works

<Mermaid
  alt="UPDATE salary, then a BEFORE trigger checks or changes the new row, the row is written, an AFTER trigger inserts an audit row. Any error fails the statement and undoes its changes."
  chart={`flowchart LR
  U([UPDATE salary]) --> B[BEFORE trigger: check or change NEW]
  B --> W[(Row written)]
  W --> A[AFTER trigger: insert audit row]
  A --> C([Statement done])
  B -. error .-> R([Statement rolled back])
  A -. error .-> R`}
/>

- Row-level triggers run once per changed row; statement-level ones once per statement (PostgreSQL only; MySQL triggers are per row).

## Example

```sql
CREATE FUNCTION log_salary() RETURNS trigger AS $$
BEGIN
  INSERT INTO salary_audit (emp_id, old_salary, new_salary)
  VALUES (OLD.id, OLD.salary, NEW.salary);
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER salary_change AFTER UPDATE OF salary ON employees
  FOR EACH ROW EXECUTE FUNCTION log_salary();
```

MySQL puts the body in the trigger itself: `... FOR EACH ROW INSERT INTO salary_audit ...`.

## Interview Qs

### Stored procedure vs function?

A function returns a value (PostgreSQL: also a table) and is used inside a query. A procedure runs alone with CALL, returns data only through OUT parameters or, in MySQL, result sets, and may COMMIT. See [the comparison](compare:stored-procedure-vs-function).

### When would you use a trigger, and why be careful?

For audit logs, an updated_at column, or a rule every writer must follow. Careful: they are invisible to app code, add work to every write, and can fire other triggers.
