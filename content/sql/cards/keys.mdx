## What it is

A key is a column, or a set of columns, used to identify or link rows. The primary key is the column that identifies each row: no two rows share a value, and it is never empty (NULL, the SQL marker for "no value"). A foreign key is a column in one table whose values must match a key in another table. In the payments example, `payments.customer_id` is a foreign key pointing to `customers.id`.

## Why it exists

Without a primary key, two rows can look the same, and "update Asha's row" might hit both or neither. Without a foreign key, a payment can keep `customer_id = 99` after customer 99 is deleted, or be inserted with a typo, and reports quietly lose money. Keys give every row a stable id, and foreign keys make the database itself refuse links to rows that do not exist. This guarantee is called referential integrity.

## How it works

1. You find the candidate keys: each smallest set of columns that is unique for every row, such as `id`, or `email`.
2. You pick one as the primary key, usually a generated `id`. The database then forbids duplicates and NULL in it; it enforces uniqueness with an index, a lookup structure covered in [indexes](card:indexes).
3. You declare the foreign key: `payments.customer_id REFERENCES customers (id)`.
4. On every insert or update of a payment, the database checks that the `customer_id` exists in `customers`; if not, it rejects the row.
5. On every delete of a customer, it checks for payments that still point to that customer. What it then does is set by the foreign key's action, covered in [constraints](card:constraints).

## Example

The `payments` table links to `customers` (Asha is 1, Ravi is 2). Two bad inserts follow:

```sql
CREATE TABLE payments (
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  amount      NUMERIC(12,2) NOT NULL
);
INSERT INTO payments VALUES (10, 1, 500.00), (11, 1, 250.00), (12, 2, 900.00);
INSERT INTO payments VALUES (10, 3, 100.00);   -- id 10 is taken
INSERT INTO payments VALUES (13, 99, 100.00);  -- no customer 99
```

```text output
CREATE TABLE
INSERT 0 3
ERROR:  duplicate key value violates unique constraint "payments_pkey"
DETAIL:  Key (id)=(10) already exists.
ERROR:  insert or update on table "payments" violates foreign key constraint "payments_customer_id_fkey"
DETAIL:  Key (customer_id)=(99) is not present in table "customers".
```

What to notice:

- Payments 10 and 11 both hold `customer_id = 1`. Repeating a foreign key value is normal: one customer, many payments.
- The primary key rejects a second row with id 10, and the foreign key rejects customer 99. The output above is from PostgreSQL 18.
- `NOT NULL` makes the customer required. Without it, a payment with `customer_id` NULL would pass the foreign key check.

## Rules and defaults

- **One primary key per table:** it may be composite, made of several columns that are unique only together, such as `(customer_id, offer_id)`.
- **What a foreign key may point to:** a primary key or a unique key of the referenced table.
- **NULL in a foreign key:** a NULL value is not checked, so it means "no parent". Add `NOT NULL` when every row must have one.
- **MySQL inline syntax:** MySQL 8.4 parses `REFERENCES` written inside a column definition but ignores it, so no foreign key exists. Write `FOREIGN KEY (customer_id) REFERENCES customers (id)`. MySQL 9.7 enforces the inline form too.
- **Indexes:** whether the foreign key column gets an index of its own differs by product; see [indexes](card:indexes) later.

## Not to be confused with

A primary key identifies a row in its own table. A foreign key points from a row to a key in another table. Rule: primary key = who am I; foreign key = whom do I belong to. A unique key is also unique, but allows NULL and a table can have many; the comparison below shows the difference.

## Common mistakes

- **"Use the email as the primary key; it is unique anyway."** Emails change, and every foreign key copying it would have to change too. Use a surrogate `id` as the primary key and keep email `UNIQUE`. How to generate ids is in [ID generation](card:id-generation).

## Interview Qs

### Super key vs candidate key vs primary key?

A super key is any set of columns that is unique for every row, even with extra columns, such as `(id, name)`. A candidate key is a smallest super key: drop any column and it is no longer unique. The primary key is the candidate key you choose; the others become alternate keys.

### Can a foreign key be NULL or repeated?

Yes to both. Many child rows can hold the same parent id, which is how one customer has many payments. A NULL foreign key means "no parent" and passes the check. Add `NOT NULL` when every child must have a parent.

### Surrogate key or natural key?

A surrogate key is a generated id with no business meaning; a natural key is real data, such as an email or a product code. I prefer a surrogate primary key because it never changes and stays small, and I put a `UNIQUE` constraint on the natural key to stop duplicates.
