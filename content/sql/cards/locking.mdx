## What it is

A lock is a mark a transaction puts on a row, or on a whole table, so that other transactions must wait before doing conflicting work with it. A shared lock means "I rely on this row; do not change it", and many transactions can hold one on the same row. An exclusive lock means "I am changing this row", and only one transaction can hold it. A transaction keeps its locks until it commits or rolls back.

## Why it exists

[MVCC](card:mvcc) lets plain reads skip waiting, but some work must still wait. Two transactions that change the same payment cannot both win. A worker that reads a `PENDING` payment and then charges the card must be sure no other worker charges it too. Locks make the second transaction wait, fail or skip the row, instead of acting on data that is about to change.

## How it works

| Statement | Lock it takes |
| --- | --- |
| Plain `SELECT` | No row lock: it reads a snapshot |
| `SELECT … FOR SHARE` | Shared row lock: others may also share it, nobody may change the row |
| `UPDATE`, `DELETE`, `SELECT … FOR UPDATE` | Exclusive row lock |
| `DROP TABLE`, `TRUNCATE`, many `ALTER TABLE` forms | PostgreSQL: a table lock that blocks even plain SELECTs |

Two workers want payment 2 at the same time:

1. Worker A runs `SELECT … FOR UPDATE` on payment 2 and gets its exclusive row lock.
2. Worker B runs a plain SELECT on payment 2. It takes no lock, reads its snapshot and does not wait.
3. Worker B runs `SELECT … FOR UPDATE` on payment 2. It waits, because A holds the exclusive lock. With `NOWAIT` it would fail at once; with `SKIP LOCKED` it would skip the row.
4. Worker A commits. Its lock is released, and B's waiting statement continues.

## Example

Several workers charge `PENDING` payments from the same table, each taking a different one. Run on PostgreSQL 18 and MySQL 9.7, with payments 2 and 3 pending:

```sql
BEGIN;
SELECT id, amount FROM payments
WHERE status = 'PENDING'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;     -- worker A gets payment 2; worker B, at the same moment, gets 3
-- charge the card for that payment, then:
UPDATE payments SET status = 'PAID' WHERE id = 2;   -- the id returned above
COMMIT;                                              -- releases the lock
```

What to notice:

- `SKIP LOCKED` makes worker B pass over payment 2, which A holds, and take payment 3. Without it, B would wait for A, and the workers would run one at a time.
- With `NOWAIT` instead, B gets an error at once: "could not obtain lock on row" in PostgreSQL, error 3572 in MySQL.
- The lock lasts until `COMMIT`. Without `BEGIN`, the SELECT would be its own transaction, its lock would end at once, and two workers could charge the same payment.

## Rules and defaults

- **Plain SELECT:** takes no row lock in PostgreSQL, or in InnoDB below SERIALIZABLE.
- **Writes:** UPDATE and DELETE take an exclusive lock on each row they change, held until the transaction ends.
- **Table locks, PostgreSQL:** `DROP TABLE`, `TRUNCATE` and many `ALTER TABLE` forms take an ACCESS EXCLUSIVE lock, which blocks even plain SELECTs on that table.
- **InnoDB locks index records:** a locking read, UPDATE or DELETE locks every index record it scans. With no suitable index, a full table scan locks every row of the table.
- **InnoDB gap locks:** at REPEATABLE READ, range scans also lock the gaps between index records, so other sessions cannot insert there. READ COMMITTED turns gap locking off for searches and index scans.
- **Lock wait timeout:** InnoDB gives up after 50 seconds (`innodb_lock_wait_timeout`). PostgreSQL's `lock_timeout` is 0 by default, which means wait without limit.

## Not to be confused with

A shared lock (`FOR SHARE`) lets other transactions take shared locks too but stops every change. An exclusive lock (`UPDATE`, `FOR UPDATE`) stops all other locks on the row. Neither blocks a plain SELECT. A row lock covers one row; a table lock covers the whole table. Rule: shared = keep it from changing; exclusive = I am changing it.

## Interview Qs

### What does SELECT … FOR UPDATE do?

It locks the rows it returns as if you were updating them, so other transactions cannot change or lock them until you commit. Use it inside a transaction when you read a value and then write based on it, such as checking a payment is still `PENDING` before charging it.

### How do several workers pull jobs from one table safely?

`SELECT … FOR UPDATE SKIP LOCKED` with `ORDER BY` and `LIMIT`, inside a transaction. Each worker locks a different row and skips rows that others hold, so no job is taken twice and nobody waits. Mark the job done and commit to release it.

### Why can a missing index make locking worse in MySQL?

InnoDB locks the index records a statement scans, not just the rows it finally changes. Without a suitable index, an UPDATE scans the whole table and locks every row, blocking other writers and inserts. A good index keeps the scan, and so the locks, small.
