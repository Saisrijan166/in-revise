## Why it exists

[MVCC](card:mvcc) keeps readers apart from writers, but two writers on one row, or a read you will act on, still need someone to wait.

## How it works

| Statement | Lock it takes |
| --- | --- |
| Plain `SELECT` | No row lock (reads a snapshot) |
| `SELECT … FOR SHARE` | Shared row lock: others may read-lock, not change |
| `UPDATE`, `DELETE`, `SELECT … FOR UPDATE` | Exclusive row lock |
| Most `ALTER TABLE`, `DROP TABLE`, `TRUNCATE` | PostgreSQL: a table lock that blocks even plain reads |

- In autocommit mode the transaction is one statement, so a lone `FOR UPDATE` protects nothing afterwards.
- Long open transactions hold locks for longer: never wait for user input inside one.

## Example

```sql
BEGIN;
SELECT id FROM orders
WHERE status = 'NEW'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;          -- each worker gets a different order
UPDATE orders SET status = 'PROCESSING' WHERE id = 42;  -- the id returned above
COMMIT;
```

## Interview Qs

### What does SELECT … FOR UPDATE do?

It locks the rows it returns as if you were updating them, so other transactions cannot change or lock them until you commit. Use it inside a transaction when you read a value and then write based on it.

### How do several workers pull jobs from one table safely?

`SELECT … FOR UPDATE SKIP LOCKED` with `LIMIT`: each worker locks a different row and skips rows others hold, so no job is taken twice and nobody waits.
