## What it is

A deadlock happens when two transactions each hold a [lock](card:locking) the other one needs. Transaction A has locked Asha's wallet and waits for Ravi's; transaction B has locked Ravi's wallet and waits for Asha's. Neither can ever continue, so the database detects the cycle and rolls back one of them, called the victim.

## Why it exists

Row locks are held until commit, so any two transactions that change the same two rows in opposite order can end up in this cycle. No explicit `LOCK` statement is needed. Without detection, both transactions, and everyone queued behind them, would hang. With detection, one transaction fails fast with a known error code, the other finishes, and the application can run the victim again.

## How it works

  chart={`flowchart LR
  T1([T1]) -- holds --> A1[(Asha's wallet)]

  T2 -. waits for .-> A1
  D{{cycle found}} --> V[roll back one: the victim]`}

1. T1 debits Asha's wallet and gets its exclusive row lock.
2. T2 debits Ravi's wallet and gets that row's lock.
3. T1 tries to credit Ravi's wallet and waits for T2.
4. T2 tries to credit Asha's wallet and waits for T1. Now each waits for the other.
5. The database finds the cycle. PostgreSQL checks once a lock wait has lasted `deadlock_timeout`; InnoDB's detector is on by default.
6. It rolls back the victim's whole transaction and returns an error. The other transaction gets its lock and commits.

## Example

The four steps above, run as two sessions on both databases, end with an error for the victim:

```text
PostgreSQL 18:  ERROR:  40P01: deadlock detected
MySQL 9.7:      ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

The application catches that error and runs the whole transfer again:

```java
void runWithRetry(Tx transfer) throws SQLException {   // Tx: one method, run() throws SQLException
    for (int attempt = 1; ; attempt++) {
        try {
            transfer.run();                      // the whole transaction, BEGIN to COMMIT
            return;
        } catch (SQLException e) {
            String state = e.getSQLState();      // 40P01: PostgreSQL deadlock; 40001: MySQL deadlock
            boolean retryable = "40P01".equals(state) || "40001".equals(state);
            if (!retryable || attempt == 3) throw e;
        }
    }
}
```

What to notice:

- `transfer.run()` is the whole transaction, not the failed statement, because the victim's earlier work was rolled back too.
- 40001 is also PostgreSQL's serialization failure from [isolation levels](card:isolation-levels), so the same loop serves both. Other errors, such as a duplicate key (23505), are thrown at once.
- The limit of three attempts makes a problem that keeps coming back visible instead of looping forever.

## Rules and defaults

- **PostgreSQL 18:** waits `deadlock_timeout` (1 s by default) before checking for a cycle. Which transaction becomes the victim is not predictable.
- **MySQL 9.7 InnoDB:** `innodb_deadlock_detect` is on by default. InnoDB tries to roll back a small transaction, measured by the rows it inserted, updated or deleted.
- **Prevention:** lock rows in one fixed order everywhere, keep transactions short, index the WHERE columns so fewer rows are locked, and skip locking reads you do not need.
- **Retry anyway:** prevention lowers the rate but never removes it, so retry code is always needed.

## Not to be confused with

A lock wait is normal: one transaction waits for another that will finish. A deadlock is a cycle in which nobody can finish, so the whole victim transaction is rolled back. A [lock wait timeout](card:lock-wait-timeout) fires when a normal wait lasts too long; in InnoDB it rolls back only the waiting statement. Rule: cycle = deadlock, whole transaction undone; long wait = timeout, one statement undone.

## Interview Qs

### How do you prevent deadlocks?

Take locks in one fixed order, for example by ascending id, keep transactions short, add indexes so statements lock fewer rows, and avoid locking reads you do not need. Still write retry code, because prevention is never perfect.

### What does the database do when it detects a deadlock?

It picks one transaction as the victim, rolls back all of its work and returns an error: SQLSTATE 40P01 in PostgreSQL, error 1213 in MySQL. That releases the victim's locks, so the other transaction continues. The application should retry the victim's whole transaction.
