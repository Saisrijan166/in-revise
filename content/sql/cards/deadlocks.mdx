## Why it exists

Once transactions lock more than one row, two of them can wait for each other forever. Without detection, both would hang.

## Example

```java
void transferWithRetry(long from, long to, BigDecimal amount) throws SQLException {
    for (int attempt = 1; ; attempt++) {
        try {
            transfer(from, to, amount);   // the whole transaction, BEGIN to COMMIT
            return;
        } catch (SQLException e) {
            String state = e.getSQLState();
            boolean retry = "40P01".equals(state) || "40001".equals(state);
            if (!retry || attempt == 3) throw e;   // 40001: MySQL deadlock or serialization failure
        }
    }
}
```

## Interview Qs

### How do you prevent deadlocks?

Take locks in one fixed order (for example, by ascending id), keep transactions short, add indexes so fewer rows are locked, and avoid locking reads you do not need. Still write retry code: prevention is never perfect.

### Deadlock vs lock wait timeout?

A deadlock is a cycle: no one can ever proceed, so the database detects it and rolls back a whole transaction. A [lock wait timeout](card:lock-wait-timeout) has no cycle: one transaction simply waited longer than the limit.
