## What it is

A data type is the kind of value a column holds: whole numbers, exact decimals, text, dates or JSON. You choose it in `CREATE TABLE`, and the database then accepts only values of that kind. The type also decides how values compare and sort (numbers by size, text by letters) and how many bytes each value takes.

## Why it exists

If every column were plain text, `'100' < '9'` would be true, because text compares letter by letter, and nothing would stop `'abc'` in an amount column. A wrong type causes quieter bugs too: money stored as FLOAT loses paise in sums, an INT id runs out after about 2.1 billion rows, and a time stored without a zone means different moments to servers in different countries. Picking the right type makes the database reject bad values and store good ones correctly.

## How it works

| Need | PostgreSQL 18 | MySQL 9.7 |
|---|---|---|
| Ids, counts | `integer`, `bigint` | `INT`, `BIGINT` |
| Money | `numeric(12,2)` | `DECIMAL(12,2)` |
| Text | `text`, `varchar(n)` | `VARCHAR(n)`, `TEXT` |
| A moment in time | `timestamptz` | `TIMESTAMP` or `DATETIME` |
| True / false | `boolean` | `BOOLEAN`, a synonym for `TINYINT(1)` |
| JSON | `jsonb` (or `json`) | `JSON`, stored in a binary form |

1. When you create the table, each column gets a type, such as `amount NUMERIC(12,2)`: 12 digits in total, 2 of them after the decimal point.
2. On every insert or update, the database converts the value to that type. If it cannot, it rejects the row: text too long for `VARCHAR(10)` or a number too big for `INT` gives an error.
3. It stores the value in the type's own format: exact digits for NUMERIC, a binary approximation for FLOAT, UTC for `timestamptz`.
4. When you query, comparisons and sorting follow the type, and `timestamptz` is shown in your session's time zone.

## Example

Adding 0.1 and 0.2 as a float and as an exact decimal, and rounding to the money scale, in PostgreSQL 18:

```sql
SELECT 0.1::float8  + 0.2::float8  AS as_float,
       0.1::numeric + 0.2::numeric AS as_numeric,
       1999.999::numeric(12,2)     AS rounded;
```

```text output
      as_float       | as_numeric | rounded
---------------------+------------+---------
 0.30000000000000004 |        0.3 | 2000.00
(1 row)
```

What to notice:

- `::float8` turns the value into a double-precision float. 0.1 has no exact binary form, so the sum is off in the 17th digit. Add that error over millions of payments and totals stop matching.
- `numeric` keeps decimal digits exactly, so 0.1 + 0.2 is exactly 0.3.
- `numeric(12,2)` keeps two decimal places, so 1999.999 is rounded to 2000.00 rather than rejected. MySQL 9.7 gives the same three results with `DOUBLE` and `DECIMAL(12,2)`.

## Rules and defaults

- **Integers:** `INT` is 4 bytes (−2,147,483,648 to 2,147,483,647); `BIGINT` is 8 bytes. Storing a value outside the range is an error. MySQL does this in its default strict SQL mode; with strict mode off, it clips the value to the limit and only warns.
- **Text:** `VARCHAR(n)` counts characters, not bytes. Longer text is an error (in MySQL, under its default strict SQL mode). PostgreSQL's `text` and plain `varchar` accept any length (up to about 1 GB), and its docs advise them over `char(n)`, which is usually the slowest there.
- **Time in PostgreSQL:** `timestamptz` stores an instant in UTC. Plain `timestamp` has no time zone at all, so it is only safe when every writer uses the same zone.
- **Time in MySQL:** `TIMESTAMP` converts from the session time zone to UTC and back, from 1970 to 2038-01-19 03:14:07 UTC. `DATETIME` stores the value exactly as given, from year 1000 to 9999, with no zone.
- **JSON in PostgreSQL:** `json` keeps the exact text; `jsonb` stores a parsed binary form and can be indexed (see [index types](card:index-types) later).

## Not to be confused with

`CHAR(n)` is fixed length: shorter text is padded with spaces up to n. `VARCHAR(n)` stores only what you give, and rejects anything longer than n. Rule: CHAR pads, VARCHAR limits. For money versus measurements, see the DECIMAL vs FLOAT comparison below.

## Interview Qs

### CHAR vs VARCHAR?

`CHAR(n)` is fixed length and pads short values with spaces to n. `VARCHAR(n)` stores only the characters you give, up to n, and rejects longer text. In PostgreSQL the docs advise `text` or `varchar`, because `char(n)` is usually the slowest of the three there.

### JSON vs JSONB in PostgreSQL?

`json` stores the exact input text and parses it again on every use. `jsonb` stores a parsed binary form: a little slower to write, much faster to query, and it can be indexed. It drops whitespace and key order, and keeps only the last value of a duplicate key.

### TIMESTAMP vs DATETIME in MySQL?

`TIMESTAMP` converts the value from the session time zone to UTC when it stores it, and back when it reads it; its range ends on 19 January 2038. `DATETIME` stores the value exactly as given, up to year 9999, with no time zone conversion.
