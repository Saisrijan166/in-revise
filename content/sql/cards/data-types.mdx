## Why it exists

The type decides what a column accepts, how it compares and sorts, and its size. A wrong type causes silent rounding, overflow or time-zone bugs.

## How it works

| Need | PostgreSQL 18 | MySQL 9.7 |
|---|---|---|
| Ids, counts | `integer`, `bigint` | `INT`, `BIGINT` |
| Money | `numeric(12,2)` | `DECIMAL(12,2)` |
| Text | `text`, `varchar(n)` | `VARCHAR(n)`, `TEXT` |
| A moment in time | `timestamptz` | `TIMESTAMP` or `DATETIME` |
| True / false | `boolean` | `BOOLEAN` = `TINYINT(1)` |
| JSON | `jsonb` (or `json`) | `JSON` (binary) |

- JSONB indexes are in [index types](card:index-types); id choices are in [ID generation](card:id-generation).

## Example

```sql
SELECT 0.1::float8  + 0.2::float8  AS f,
       0.1::numeric + 0.2::numeric AS n;
```

```text
          f          |  n
---------------------+-----
 0.30000000000000004 | 0.3
```

## Interview Qs

### CHAR vs VARCHAR?

CHAR(n) is fixed length and pads short values with spaces. VARCHAR(n) stores only what you give, up to n characters. PostgreSQL docs advise text or varchar: char is usually the slowest there.

### JSON vs JSONB in PostgreSQL?

`json` stores the exact text and reparses it on every use. `jsonb` stores a binary form: a little slower to write, much faster to query, and it can be indexed. It drops whitespace, key order and duplicate keys.

### TIMESTAMP vs DATETIME in MySQL?

TIMESTAMP converts the value to UTC using the session time zone and back on read; its range ends in 2038. DATETIME stores the value exactly as given, up to year 9999, with no zone.
