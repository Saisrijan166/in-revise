## What it is

Fixing a slow query is a repeatable method: find which query costs the most, read its plan, change the one thing that costs most, and check the result. It uses the tools from earlier in this topic: [indexes](card:indexes), [EXPLAIN](card:explain-query-plans) and the reasons [an index is skipped](card:index-not-used).

## Why it exists

A slow page can come from a missing index, a query that reads too many rows, an app that runs the same small query thousands of times, or a query waiting for a lock. Each needs a different fix. Guessing usually means adding an index, which slows every write and may not touch the real cost. Working in a fixed order finds the real one.

## How it works

1. Find the query. Rank statements by total time, which is calls times mean time, not by one slow run.
2. Read its plan with `EXPLAIN ANALYZE`: look for full scans that keep few rows, the join method, and estimated rows far from actual.
3. Fix access to the data: add or change the index the plan needs, or rewrite a filter the index cannot serve.
4. Cut the work: select only the columns you need, return fewer rows with [pagination](card:pagination), and stop running one query per row, the N+1 problem you will see in [N+1 queries](card:n-plus-one).
5. Check what the plan does not show: stale statistics, waits for [locks](card:locking) held by other transactions, and waits for a free connection in the [pool](card:connection-pooling). Both are covered in later topics.
6. Measure again, and check that writes and other queries did not get slower.

## Example

The "latest payments of a customer" query is slow. Steps 1 to 3 and the measurement, on 100,000 payments in PostgreSQL 18:

```sql
-- 1. Find: the statements that used the most total time
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;

-- 2. Read the plan of the slow one
EXPLAIN ANALYZE SELECT id, amount, status FROM payments
WHERE customer_id = 7 ORDER BY created_at DESC LIMIT 5;

-- 3. Fix the biggest cost, then measure again
CREATE INDEX idx_payments_cust_created ON payments (customer_id, created_at);
EXPLAIN ANALYZE SELECT id, amount, status FROM payments
WHERE customer_id = 7 ORDER BY created_at DESC LIMIT 5;
```

What to notice:

- pg_stat_statements listed the query as `... WHERE customer_id = $1 ... LIMIT $2`: runs for customer 7 and customer 8 were counted as one statement.
- The first plan was a `Seq Scan` with `Rows Removed by Filter: 99990` and then a `Sort`: about 13 ms to return 5 rows.
- After the [composite index](card:composite-indexes), the plan was `Index Scan Backward using idx_payments_cust_created`: equality on `customer_id`, rows already in `created_at` order, and it stopped after 5. About 0.1 ms.

## Rules and defaults

- **pg_stat_statements:** add it to `shared_preload_libraries`, restart PostgreSQL, then run `CREATE EXTENSION pg_stat_statements` in the database. It records calls, total and mean execution time per statement, in milliseconds.
- **MySQL slow query log:** off by default in MySQL 9.7. Turn on `slow_query_log`, lower `long_query_time` from its default of 10 seconds, and summarise the log with `mysqldumpslow`.
- **ORDER BY with LIMIT:** an index that matches the ORDER BY lets the database read only the first rows; without one, it must sort every matching row first.

## Not to be confused with

A slow query is one statement that takes long each time; its plan shows the cost. Too many queries is many fast statements, such as one per payment in a loop; each plan looks fine, and you spot it by a huge `calls` count. Rule: slow query = fix the plan; too many queries = fix the code that sends them.

## Interview Qs

### How do you optimise a slow query?

Find it by total time, read its plan with EXPLAIN ANALYZE, then fix the biggest cost: a missing or unusable index, too many rows or columns, a bad join or stale statistics. Check lock waits and the connection pool too. Then measure again, including the effect on writes.

### Does SELECT * slow a query?

It can. It reads and sends columns nobody uses, which adds work and network traffic, and it rules out an index-only scan, because the query now needs columns the index does not hold.

### How do you find slow queries in production?

In PostgreSQL, `pg_stat_statements` keeps calls and total and mean time per normalised statement, so you rank by total time. In MySQL, the slow query log records statements slower than `long_query_time`, and `mysqldumpslow` summarises it.
