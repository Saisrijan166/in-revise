## Why it exists

A slow query has many possible causes. Working in a fixed order finds the real one; guessing adds indexes that slow writes and miss the cost.

## How it works

<Steps label="Fixing a slow query">
  <Step title="Find it">Rank queries by total time, not by one slow run.</Step>
  <Step title="Read the plan">[EXPLAIN ANALYZE](card:explain-query-plans): scans, joins, estimated vs actual rows.</Step>
  <Step title="Fix access">Add or change an index the plan needs ([why one is skipped](card:index-not-used)).</Step>
  <Step title="Cut work">Fewer columns and rows, [pagination](card:pagination), no [N+1 calls](card:n-plus-one).</Step>
  <Step title="Check the rest">Join conditions, stale statistics, [lock waits](card:locking), the [connection pool](card:connection-pooling).</Step>
  <Step title="Measure again">Confirm it is faster and writes did not suffer.</Step>
</Steps>

## Example

```sql
-- PostgreSQL: the 5 queries that use the most total time
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;
```

MySQL: turn on `slow_query_log`, lower `long_query_time`, then summarise the log with `mysqldumpslow`.

## Interview Qs

### How do you optimise a slow query?

Find it, read its plan with EXPLAIN ANALYZE, then fix the biggest cost: a missing index, too many rows or columns, a bad join or stale statistics. Check lock waits and the pool, then measure again.

### Does SELECT * slow a query?

It can. It returns columns nobody uses, and it stops index-only scans, because the query now needs columns the index does not hold.

### How do you find slow queries in production?

PostgreSQL: `pg_stat_statements` keeps calls and total and mean time per statement. MySQL: the slow query log records statements over `long_query_time`.
