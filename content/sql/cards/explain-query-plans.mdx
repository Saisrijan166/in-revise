## Why it exists

The same SQL can run many ways: a full scan or an index, this join order or that one. The chosen plan shows where the time goes and why a query is slow.

## How it works

<Steps label="What happens to one SELECT">
  <Step title="Parse">Check the syntax and build a query tree.</Step>
  <Step title="Rewrite">Replace views with the tables behind them.</Step>
  <Step title="Plan">List the ways to read and join the tables, estimate each cost, keep the cheapest.</Step>
  <Step title="Execute">Walk the plan and return the rows.</Step>
</Steps>

- Scans: PostgreSQL `Seq Scan`, `Index Scan`, `Index Only Scan`, `Bitmap Heap Scan`; MySQL `type` from `ALL` (worst) to `const`.
- Joins: nested loop, hash join, merge join. MySQL uses hash joins since 8.0.18.

## Example

```sql
EXPLAIN ANALYZE
SELECT id, amount FROM orders WHERE user_id = 7;
```

```text
Index Scan using idx_orders_user_id on orders
  (cost=0.43..8.50 rows=4 width=14)
  (actual time=0.02..0.03 rows=3.00 loops=1)
  Index Cond: (user_id = 7)
```

`rows=4` is the estimate; `rows=3.00` is the actual count (output trimmed).

## Interview Qs

### What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN only plans the query and shows estimates. EXPLAIN ANALYZE also runs it and shows actual rows and time per step, so for data changes run it inside a transaction and roll back.

### What do you look for in a query plan?

Full scans on big tables, the join method, and steps where estimated rows are far from actual rows. A big gap usually means stale statistics, so run ANALYZE.
