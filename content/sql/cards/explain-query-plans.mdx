## What it is

A query plan, or execution plan, is the list of steps the database chose to run one SQL statement: how to read each table, which index to use, and how and in what order to join tables. `EXPLAIN` shows the plan without running the query. `EXPLAIN ANALYZE` runs the query and adds what really happened: the actual rows and time of every step.

## Why it exists

SQL says which rows you want, not how to get them, so the same query can run as a full scan or an index lookup, with a hash join or a nested loop. When a query is slow, guessing the cause wastes time. The plan shows which step reads too many rows or takes the time, and whether an [index](card:indexes) was used or [skipped](card:index-not-used).

## How it works

<Mermaid
  alt="SQL text goes to the parser, which builds a query tree. The rewriter replaces views. The planner estimates the cost of each possible plan and keeps the cheapest. The executor runs it and returns rows. EXPLAIN prints the plan after planning; EXPLAIN ANALYZE prints it after execution."
  chart={`flowchart LR
  Q([SQL]) --> P[Parse] --> W[Rewrite views] --> PL[Plan: pick cheapest] --> E[Execute] --> R([Rows])
  PL -. EXPLAIN .-> X[Plan with estimates]
  E -. EXPLAIN ANALYZE .-> Y[Plan with actual rows and time]`}
/>

1. The parser checks the syntax and builds a query tree.
2. The rewriter replaces each [view](card:views) with the query behind it.
3. The planner lists ways to read and join the tables, estimates each one's cost from table statistics, and keeps the cheapest.
4. The executor runs the plan as a tree of nodes. Each node pulls rows from the nodes indented below it, and the top node returns the result.
5. `EXPLAIN` prints the tree after step 3, with estimates only; `EXPLAIN ANALYZE` prints it after step 4, with real numbers next to the estimates.

| Node | Meaning |
|---|---|
| `Seq Scan` (MySQL `type` ALL) | Reads every row of the table |
| `Index Scan` / `Index Only Scan` | Walks an index, then the rows / answers from the index alone |
| `Bitmap Heap Scan` | Collects row locations from an index first, then reads those pages in order |
| `Nested Loop` | For each outer row, searches the inner side; good when the inner side is indexed |
| `Hash Join` | Builds a hash table on one side, then probes it with each row of the other |
| `Merge Join` | Both sides sorted on the key, then merged in one pass |

## Example

Pending payments of customers in Pune, on 100,000 payments and 10,000 customers in PostgreSQL 18.

```sql
EXPLAIN ANALYZE
SELECT c.name, p.amount
FROM customers c JOIN payments p ON p.customer_id = c.id
WHERE c.city = 'Pune' AND p.status = 'PENDING';
```

```text output
Hash Join  (cost=230.25..3941.12 rows=750 width=19) (actual time=4.712..24.431 rows=1000.00 loops=1)
  Hash Cond: (p.customer_id = c.id)
  ->  Seq Scan on payments p  (cost=0.00..3703.00 rows=3000 width=14) (actual time=1.430..19.913 rows=3000.00 loops=1)
        Filter: (status = 'PENDING'::text)
        Rows Removed by Filter: 97000
  ->  Hash  (cost=199.00..199.00 rows=2500 width=21) (actual time=3.218..3.219 rows=2500.00 loops=1)
        ->  Seq Scan on customers c  (cost=0.00..199.00 rows=2500 width=21) (actual time=0.016..2.075 rows=2500.00 loops=1)
Execution Time: 24.636 ms
```

What to notice:

- Read from the most indented nodes outwards: PostgreSQL read the 2,500 Pune customers into a hash table, then read payments and probed the hash table with each pending payment.
- `rows=750` is the estimate and `rows=1000.00` the actual count, which is close. A large gap would point to stale statistics.
- `Rows Removed by Filter: 97000` says payments was read in full to keep 3,000 rows. That is the step to fix first, for example with a partial index on pending payments.
- The output is trimmed: PostgreSQL 18 also printed the customers `Filter` line, the hash `Buckets` line and `Buffers` lines (pages read from memory or disk), which `EXPLAIN ANALYZE` now includes by default.

## Rules and defaults

- **EXPLAIN ANALYZE executes:** for INSERT, UPDATE and DELETE, run it inside `BEGIN; ... ROLLBACK;` so the changes are undone.
- **Loops:** when a node runs many times, as the inner side of a nested loop does, its actual rows and time are averages per loop; multiply by `loops` for the total.
- **PostgreSQL 18:** `EXPLAIN ANALYZE` includes `BUFFERS` by default; turn it off with `EXPLAIN (ANALYZE, BUFFERS OFF)`.
- **MySQL:** `EXPLAIN FORMAT=TREE` prints a tree like PostgreSQL's; `EXPLAIN ANALYZE` (8.0.18+) runs the query and prints actual times. Hash joins exist since 8.0.18.

## Interview Qs

### What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN only plans the query and shows estimates. EXPLAIN ANALYZE also runs it and shows the actual rows and time of every step. Because it really executes the statement, run it for data changes inside a transaction and roll back.

### What do you look for in a query plan?

Full scans on big tables that keep few rows, the join method and join order, and steps where estimated rows are far from actual rows. A big gap usually means stale statistics, so run ANALYZE; then check whether a missing or unusable index explains the scan.

### When does the planner choose a nested loop instead of a hash join?

A nested loop suits a small outer input with an index on the inner side: each outer row does one quick lookup. A hash join suits larger inputs joined on equality with no useful index: it reads each side once. A merge join suits inputs already sorted on the join key.
