## What it is

The logical order of a SELECT is the order in which its clauses take effect, which differs from the order you write them. You write `SELECT` first, but the database starts from `FROM`: first it collects the rows, then filters, groups and sorts them. Each clause can use only what the clauses before it produced.

## Why it exists

If you read a query top to bottom, many errors look random. A column alias from `SELECT` works in `ORDER BY` but fails in `WHERE`, and `SUM(amount)` works in `HAVING` but fails in `WHERE`. Once you know the order, each of these has one reason: the clause ran before the thing it needs was created. You can then predict errors and write the fix at once.

## How it works

1. `FROM` and the joins build one set of rows from the tables.
2. `WHERE` tests each row and drops those whose condition is false or unknown. No groups or aliases exist yet.
3. `GROUP BY` folds the remaining rows into groups and computes aggregates like `SUM`, and `HAVING` then drops whole groups.
4. `SELECT` computes the output columns and gives them their aliases, and `DISTINCT` removes repeated output rows. Window functions are computed here too; you will see them in [Window functions](card:window-functions).
5. `ORDER BY` sorts the output, so it can use aliases, and `LIMIT` returns the first rows of that sorted list.

So the key is: a clause can use a name only if an earlier step created it.

## Example

Total paid amount per customer, keeping customers above 600. The data is the payments table: customer 1 has PAID payments of 500 and 700, customer 2 has one of 700.

```sql
SELECT customer_id, SUM(amount) AS total
FROM payments
WHERE status = 'PAID'          -- row filter: runs before grouping
GROUP BY customer_id
HAVING SUM(amount) > 600       -- group filter: the sum exists now
ORDER BY total DESC;           -- alias works: ORDER BY runs after SELECT
```

```text output
 customer_id |  total
-------------+---------
           1 | 1200.00
           2 |  700.00
```

What to notice:

- `status = 'PAID'` is a plain column test, so it goes in `WHERE` and cuts rows before any grouping.
- `HAVING` repeats `SUM(amount)` instead of using `total`. PostgreSQL rejects `HAVING total > 600`; MySQL accepts it, but the repeated form runs on both.
- Move `total > 600` into `WHERE` and both databases fail with "column total does not exist" (PostgreSQL) or "Unknown column 'total' in 'where clause'" (MySQL).

## Rules and defaults

- **WHERE and HAVING:** neither can use a SELECT alias in PostgreSQL 18; write the expression again.
- **GROUP BY:** PostgreSQL 18 and MySQL 9.7 both accept an output alias. If the name is also a column of the table, PostgreSQL uses the table column.
- **MySQL extension:** MySQL 9.7 also accepts aliases in `HAVING`. It is not portable, so do not rely on it.
- **Window functions:** allowed only in the SELECT list and `ORDER BY`. To filter on one, compute it in a subquery or CTE first; you will see both in [Subqueries](card:subqueries) and [CTEs](card:ctes).
- **No ORDER BY:** rows come back in whatever order is fastest, which can change between runs.

## Not to be confused with

The logical order says what each clause can see. The execution plan is how the engine really does the work, and it may filter early or read an index first. You will see plans in [EXPLAIN](card:explain-query-plans). Rule: logical order = what the query means; plan = how it is run.

## Common mistakes

- **"With SELECT DISTINCT, I can still sort by any column."** DISTINCT runs before ORDER BY, so after duplicates are dropped a column that is not in the select list has no single value to sort by. PostgreSQL 18 and MySQL 9.7 both reject such an `ORDER BY`.

## Interview Qs

### Why can't I use a SELECT alias in WHERE?

WHERE is evaluated before SELECT, so when WHERE runs the alias does not exist yet. Repeat the expression in WHERE, or put the query in a subquery or CTE and filter on the alias in the outer query. ORDER BY runs after SELECT, so the alias works there.

### Why can't you filter on ROW_NUMBER() in WHERE?

Window functions are computed together with the SELECT list, after WHERE, GROUP BY and HAVING. WHERE has already run, so it cannot see them. Compute the row number in a subquery or CTE, then filter `WHERE rn = 1` outside.

### Does the database really run FROM first, then WHERE, and so on?

Not necessarily. The order defines the result, not the plan. The planner may use an index, push a filter into a join, or stop early for LIMIT, as long as the rows returned are the same as the logical order would give.
