## What it is

`SELECT` is the statement that reads data. You name a table after `FROM`, list the columns you want after `SELECT`, and get back a result: a small table of rows built for this one query. `WHERE` keeps only the rows for which a condition is true, `ORDER BY` sorts the result, and `LIMIT` keeps only the first few rows. Nothing in the table changes; a SELECT only reads.

## Why it exists

A payments table can hold millions of rows, but a screen needs "the latest paid payments of customer 1". Fetching every row into Java and filtering there would move all that data over the network and waste memory. With WHERE, ORDER BY and LIMIT, the database does the work and sends back only the rows the screen shows.

## How it works

<Mermaid
  alt="A SELECT runs as a pipeline: FROM reads the payments table, WHERE keeps rows whose condition is true, the SELECT list picks and computes columns, ORDER BY sorts, and LIMIT keeps the first rows."
  chart={`flowchart LR
  F[FROM payments] --> W[WHERE keeps TRUE rows]
  W --> S[SELECT list: columns, CASE]
  S --> O[ORDER BY sorts]
  O --> L[LIMIT keeps first N]`}
/>

1. `FROM payments` gives the database the rows to start from.
2. `WHERE` tests each row and keeps it only if the condition is true.
3. The `SELECT` list builds the output columns. It can rename a column with `AS` or compute one with `CASE WHEN ... THEN ... ELSE ... END`, which returns the result of the first true `WHEN`.
4. `ORDER BY` sorts the kept rows; later columns in the list only break ties.
5. `LIMIT 10` returns at most 10 rows from the top; `OFFSET 20` would skip 20 first.

This is a simplified order; you will see the full one, with grouping, in [Logical order of a SELECT](card:query-order).

## Example

Paid payments of customers 1 and 3, largest first. The `payments` table has six rows; three of them match.

```sql
SELECT id, customer_id, amount,
       CASE WHEN amount >= 800 THEN 'large' ELSE 'normal' END AS size
FROM payments
WHERE status = 'PAID'
  AND (customer_id = 1 OR customer_id = 3)
ORDER BY amount DESC, id
LIMIT 10;
```

```text output
 id  | customer_id | amount |  size
-----+-------------+--------+--------
 102 |           1 | 800.00 | large
 106 |           3 | 800.00 | large
 101 |           1 | 500.00 | normal
(3 rows)
```

What to notice:

- Payments 102 and 106 tie at 800. The `id` in `ORDER BY` puts 102 first every time; without it, their order could change between runs.
- Remove the brackets and the query also returns payment 105, a PENDING payment of customer 3, because AND is evaluated before OR.
- `size` is a computed column: the CASE expression runs for each row, and the stored data does not change.

## Rules and defaults

- **Comparison operators:** `=`, `<>` (or `!=`), `<`, `>`, `<=`, `>=`; `IN ('PAID', 'PENDING')` means equal to any value in the list.
- **LIKE and case:** in PostgreSQL 18, `LIKE` is case-sensitive and `ILIKE` ignores case. In MySQL 9.7, `LIKE` follows the column's collation, its rules for comparing text, and the default collation ignores case (see [PostgreSQL vs MySQL](card:postgresql-and-mysql)).
- **First N rows:** both databases accept `LIMIT n OFFSET m`. PostgreSQL also accepts the standard `FETCH FIRST n ROWS ONLY`; MySQL does not.
- **Large offsets are slow:** the database still reads and throws away every skipped row; see [Pagination](card:pagination).
- **NULL:** a condition such as `city = NULL` is never true; the next concept, [NULL](card:null-handling), explains why.

## Common mistakes

- **"DISTINCT city, name gives each city once."** DISTINCT compares the whole selected row, so a city repeats once for every different name. To get each city once, select only `city`.

## Interview Qs

### Why should you not rely on the row order without ORDER BY?

SQL tables have no built-in order. The database returns rows in whatever order its way of reading them produces, which can change after an update, a new index or a version upgrade. ORDER BY is the only guarantee, and it needs a unique column at the end so tied rows get a fixed place too.

### Is BETWEEN inclusive?

Yes, at both ends. With timestamps that is a trap: BETWEEN '2026-02-01' AND '2026-02-28' ends at midnight at the start of 28 February, so a payment at 20:10 that day is missed. Use a half-open range: >= the first day AND < the day after the last.

### Why avoid SELECT * in application code?

It fetches every column, including large ones the screen never shows, so more data crosses the network. The result also changes when someone adds a column, which can break code that reads columns by position. Listing columns states exactly what the code needs.
