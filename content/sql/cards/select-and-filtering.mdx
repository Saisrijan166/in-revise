## Why it exists

Most SQL in an app is a read: some columns, some rows, in some order, a page at a time. These clauses say exactly that.

## How it works

| You write | It means |
|---|---|
| `city IN ('Pune', 'Delhi')` | equal to any value in the list |
| `amount BETWEEN 100 AND 500` | 100 and 500 are included |
| `name LIKE 'A%'` | `%` any run of characters, `_` exactly one |
| `LIMIT 10 OFFSET 20` | skip 20 sorted rows, return 10 |

- Case: PostgreSQL `LIKE` is case-sensitive (`ILIKE` is not); MySQL follows the collation, case-insensitive by default.
- Standard SQL writes `FETCH FIRST 10 ROWS ONLY` (PostgreSQL accepts it; MySQL uses `LIMIT`).
- Big offsets get slow: see [Pagination](card:pagination). NULL tests: see [NULL](card:null-handling).

## Example

```sql
SELECT id, name,
       CASE WHEN city = 'Pune' THEN 'local' ELSE 'other' END AS zone
FROM users
WHERE (city = 'Pune' OR city = 'Mumbai')
  AND name LIKE 'A%'
ORDER BY name, id          -- id breaks ties
LIMIT 10;
```

## Interview Qs

### Does DISTINCT apply to one column or the whole row?

To the whole selected row. `SELECT DISTINCT city, name` keeps each different (city, name) pair, so a city can repeat.

### Is BETWEEN inclusive?

Yes, at both ends. With timestamps, `BETWEEN '2026-01-01' AND '2026-01-31'` misses most of 31 January; use `>= start AND < next_day` instead.
