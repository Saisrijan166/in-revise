## What it is

PostgreSQL and MySQL are two popular open-source [relational databases](card:relational-databases), and backend interviews often ask about both. Both follow standard SQL, so tables, keys, [constraints](card:constraints) and basic queries look the same. Each also has its own defaults and extra syntax. MySQL stores tables through a pluggable storage engine, the layer that writes the data to disk; the default engine, InnoDB, is the one to know.

## Why it exists

Interviewers ask this because "it depends on the database" is a real answer in SQL. A query moved from one to the other can run without error and still return different rows, as the example below shows. Knowing the few defaults that change behaviour lets you give the standard answer first and then say exactly how PostgreSQL or MySQL differs.

## How it works

<Compare id="postgresql-vs-mysql" />

1. Start from standard SQL. `CREATE TABLE`, primary and foreign keys, `SELECT`, `WHERE` and joins work the same in both.
2. Check the defaults that change results: how text compares (collation), what `||` means, and the default isolation level, which decides what one transaction sees of another's changes (see [isolation levels](card:isolation-levels) later).
3. Check the syntax that differs: generated ids, upsert (insert or update in one statement) and `RETURNING`, which PostgreSQL has and MySQL does not.
4. Check how data is stored: InnoDB keeps a table's rows in primary key order, while PostgreSQL keeps rows in a separate heap. [Clustered indexes](card:clustered-indexes) explains why this matters.

## Example

The same two queries on the `customers` table, where the stored name is `'Asha'`:

```sql
SELECT count(*) AS n FROM customers WHERE name = 'ASHA';
SELECT 'pay' || 'ment' AS joined;
```

| Result | PostgreSQL 18.6 | MySQL 9.7.2 |
|---|---|---|
| `n` | 0 | 1 |
| `joined` | `payment` | 0, with a deprecation warning |

What to notice:

- MySQL's default collation, `utf8mb4_0900_ai_ci`, is case-insensitive (`ci`), so `'ASHA'` matches `'Asha'`. PostgreSQL's default collations compare exactly, so it finds no row.
- In MySQL `||` is a logical OR by default; the strings become numbers and the answer is 0. `CONCAT('pay', 'ment')` gives `payment` in both.
- Neither query fails. The danger is wrong results with no error, which is why you name the product in an answer.

## Rules and defaults

- **Versions:** PostgreSQL 18 is the current major release. MySQL 9.7 is the current LTS (long-term support) release, after 8.4 LTS.
- **Storage engine:** InnoDB is MySQL's default engine. It supports transactions, row-level locks and foreign keys. Other engines exist, but new tables use InnoDB unless you name another.
- **Isolation:** PostgreSQL defaults to `READ COMMITTED`; InnoDB to `REPEATABLE READ`.
- **`||` in MySQL:** with the `PIPES_AS_CONCAT` SQL mode turned on, `||` joins strings as in standard SQL. It is off by default.

## Interview Qs

### What are the main differences between PostgreSQL and MySQL?

Start with the defaults that change behaviour: default isolation level, how tables are stored (heap versus rows in primary key order) and case-sensitive text comparison. Then the syntax: identity versus `AUTO_INCREMENT`, `ON CONFLICT` versus `ON DUPLICATE KEY UPDATE`, and `RETURNING`. Finally, features only PostgreSQL has, such as JSONB, partial indexes, and table changes (DDL) that can be rolled back inside a transaction.

### Which would you choose for a new service?

Either works for a typical web app. I would pick PostgreSQL when I need its richer SQL, JSONB or extensions such as pg_trgm, and MySQL when the team and tooling already run it well. Either way I would check the defaults that differ before porting queries.

### Why does MySQL find 'ASHA' when the stored name is 'Asha'?

Because the default collation, `utf8mb4_0900_ai_ci`, ignores case and accents in comparisons. PostgreSQL compares exactly by default. For case-insensitive matching in PostgreSQL, compare `lower(name)`, use `ILIKE`, or define a nondeterministic collation.
