## Why it exists

One structure cannot serve every query. A sorted tree is great for `=` and ranges, but useless for "which rows contain this tag" or a table of a billion log rows.

## How it works

| Type | Best for | Where |
|---|---|---|
| B-tree | `=`, `<`, `BETWEEN`, `IN`, `ORDER BY`, `LIKE 'abc%'` | Default in both |
| Hash | `=` only | PostgreSQL; not InnoDB |
| GIN | Arrays, JSONB `@>` and `?`, full-text | PostgreSQL |
| GiST, SP-GiST | Geometry, ranges, nearest neighbour | PostgreSQL |
| BRIN | Huge tables whose values follow insert order | PostgreSQL |
| FULLTEXT, SPATIAL | Word search, geometry | MySQL InnoDB |

- **Unique**: rejects duplicate keys. In PostgreSQL only B-tree can be unique.
- **Partial** (PostgreSQL only): `CREATE INDEX ... WHERE`; indexes only the rows you search.
- **Expression**: indexes a computed value such as `lower(email)` ([the classic fix](card:index-not-used)).

## Example

```sql
-- partial: only pending orders are indexed
CREATE INDEX idx_orders_pending ON orders (created_at)
  WHERE status = 'PENDING';
-- GIN on a JSONB column (products.attrs)
CREATE INDEX idx_products_attrs ON products USING GIN (attrs);
SELECT id FROM products WHERE attrs @> '{"colour": "red"}';
```

MySQL calls an expression index a functional key part (8.0.13+): `CREATE INDEX idx_users_lower_email ON users ((LOWER(email)));`

## Interview Qs

### Which index would you use on a JSONB column?

GIN. The default class supports containment `@>` and key-exists `?`. `jsonb_path_ops` is usually smaller and faster but drops `?`. A B-tree only helps when comparing whole documents.

### What is a partial index, and when is it useful?

An index over only the rows that match a `WHERE`, such as pending orders. It is smaller and cheaper to maintain. PostgreSQL has it; MySQL's CREATE INDEX has no `WHERE` clause.
