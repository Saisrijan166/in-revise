## What it is

The index type is the data structure an index uses. In PostgreSQL you choose it with `USING` in `CREATE INDEX`; with no `USING` you get a B-tree, the sorted tree from [Indexes](card:indexes). Some options change which rows or values go into an index, not its structure: unique, partial (only some rows) and expression (a computed value).

## Why it exists

A sorted tree answers `customer_id = 7` or "payments in October" well. It cannot answer "which payments have `retry: true` inside their JSONB details", because each whole document is one sorted value and there is nothing to search inside it. Indexing all 100,000 payments is also wasteful when queries only ever look for the 3,000 pending ones. Other types and options fit these shapes of query.

## How it works

| Type | Best for | Where |
|---|---|---|
| B-tree | `=`, `<`, `BETWEEN`, `IN`, `ORDER BY`, `LIKE 'abc%'` | Default in both |
| Hash | `=` only | PostgreSQL; not InnoDB |
| GIN | JSONB `@>` and `?`, arrays, full-text | PostgreSQL |
| GiST, SP-GiST | Geometry, ranges, nearest neighbour | PostgreSQL |
| BRIN | Huge tables whose values follow insert order | PostgreSQL |
| FULLTEXT, SPATIAL | Word search, geometry | MySQL InnoDB |

To choose, follow the query:

1. Look at the operator in the WHERE clause. `=`, ranges, `ORDER BY` and `LIKE 'abc%'` point to a B-tree, the default.
2. If the column holds many values per row, such as JSONB, an array or a text document, and the query asks "contains", use GIN. It stores one entry per element, pointing to every row that contains it.
3. If the table is huge and the column grows with insert order, like `created_at` in a log, BRIN keeps only the min and max per range of table blocks and skips ranges that cannot match.
4. Then decide what goes in: UNIQUE to reject duplicates, a WHERE clause for a partial index, or an expression such as `lower(email)`.

## Example

Two indexes on `payments`, where `meta` is a JSONB column holding gateway details.

```sql
-- partial: only the pending payments are in the index
CREATE INDEX idx_payments_pending ON payments (created_at)
  WHERE status = 'PENDING';
SELECT id FROM payments
WHERE status = 'PENDING' AND created_at < '2026-02-01';

-- GIN on the JSONB column
CREATE INDEX idx_payments_meta ON payments USING GIN (meta);
SELECT id FROM payments WHERE meta @> '{"retry": true}';
```

What to notice:

- On 100,000 payments the partial index holds only the 3,000 pending ones, and the first query used it. The same query with `status = 'PAID'` ran a Seq Scan, because those rows are not in the index.
- PostgreSQL uses a partial index only when the query's WHERE clearly implies the index's WHERE. The check happens at planning time, so write `status = 'PENDING'` as a literal, not a parameter.
- `@>` means "contains". With a plain B-tree on `meta`, PostgreSQL still ran a Seq Scan; with the GIN index it used a Bitmap Index Scan.

## Rules and defaults

- **Default type:** B-tree, in PostgreSQL 18 and MySQL 9.7 InnoDB, when you name no type.
- **Unique:** in PostgreSQL only a B-tree can be unique. NULLs count as distinct by default, so a unique index allows many NULL rows; PostgreSQL 15+ `NULLS NOT DISTINCT` allows only one.
- **JSONB operator classes:** the default `jsonb_ops` supports `@>`, `?`, `?|` and `?&`. `jsonb_path_ops` is usually smaller and faster, but drops the `?` operators.
- **Prefix LIKE in PostgreSQL:** a B-tree serves `LIKE 'abc%'` only with the C collation or the `text_pattern_ops` operator class.
- **Expression index:** PostgreSQL indexes any expression; MySQL calls it a functional key part (8.0.13+), written with double brackets: `((LOWER(email)))`.
- **MySQL InnoDB:** no hash, GIN, BRIN or partial indexes; `CREATE INDEX ... WHERE` is a syntax error, and `USING HASH` quietly builds a B-tree.

## Not to be confused with

A B-tree keeps values sorted, so it answers `=`, ranges and `ORDER BY`. A hash index stores a hash code of each value, so it answers only `=`, and in PostgreSQL it cannot be unique or span several columns. Rule: B-tree unless you have measured a reason for hash.

## Interview Qs

### Which index would you use on a JSONB column?

GIN. The default operator class supports containment `@>` and the key-exists operators such as `?`. `jsonb_path_ops` is usually smaller and faster and supports `@>`, but not the `?` operators. A B-tree on the column cannot look inside documents.

### What is a partial index, and when is it useful?

An index over only the rows that match its WHERE, such as pending payments. It is smaller and cheaper to maintain, and a query whose filter implies that WHERE can use it. PostgreSQL has it; MySQL's CREATE INDEX has no WHERE clause.

### When would you choose a BRIN index?

For a very large table whose column follows the physical row order, such as `created_at` in an append-only log. BRIN stores a min and max per block range, so it is tiny, and range queries skip block ranges that cannot match. On randomly ordered data it helps little.
