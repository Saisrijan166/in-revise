## What it is

A view is a SELECT statement saved in the database under a name, which you then query as if it were a table. It holds no rows of its own: each time you read it, the database runs the saved SELECT on the real tables, called the base tables. A materialized view also starts from a SELECT, but it runs the query once and stores the resulting rows, like a summary table from [Denormalisation](card:denormalization).

## Why it exists

The same long query, say paid payments joined to customers, ends up copied into many reports and services; when the rule for "paid" changes, every copy must change. Some users should also see only a few columns of a table. A view gives the query one name and one place to change, and lets you grant access to the view instead of the table. When the query is too slow to run on every read, a materialized view keeps its answer ready.

## How it works

<Compare id="view-vs-materialized-view" />

1. `CREATE VIEW name AS SELECT ...` saves only the query text and its column list.
2. When a query reads the view, the database puts the saved SELECT in its place and runs the combined query on the base tables, so the result is always current.
3. `CREATE MATERIALIZED VIEW name AS SELECT ...` runs the query once and stores the rows, which you can index like a table.
4. Reads of the materialized view return those stored rows and ignore later changes to the base tables.
5. `REFRESH MATERIALIZED VIEW` reruns the query and replaces the stored rows; until then the data is stale.

So the key is that a view saves the question and a materialized view saves the answer.

## Example

This creates a view and a materialized view over payments, adds a payment of 100 for Asha (customer 1, who had paid 500 and 700), and reads both, run on PostgreSQL 18.

```sql
CREATE VIEW paid_payments AS
  SELECT id, customer_id, amount FROM payments WHERE status = 'PAID';
CREATE MATERIALIZED VIEW customer_totals AS
  SELECT customer_id, SUM(amount) AS total
  FROM payments WHERE status = 'PAID' GROUP BY customer_id;
CREATE UNIQUE INDEX ON customer_totals (customer_id);

INSERT INTO payments VALUES (6, 1, 100, 'PAID', '2026-01-10');

SELECT SUM(amount) AS from_view FROM paid_payments WHERE customer_id = 1;
SELECT total AS stored FROM customer_totals WHERE customer_id = 1;
REFRESH MATERIALIZED VIEW CONCURRENTLY customer_totals;
SELECT total AS refreshed FROM customer_totals WHERE customer_id = 1;
```

```text output
from_view
1300.00
stored
1200.00
refreshed
1300.00
```

What to notice:

- The view already includes the new 100, because it reran its SELECT. The materialized view still says 1200 until the REFRESH.
- `CONCURRENTLY` lets other sessions keep reading the old rows while it rebuilds. Remove the unique index and PostgreSQL refuses the concurrent refresh with an error.
- The view lists its columns instead of `SELECT *`; a `*` is expanded when the view is created, so columns added to payments later would not appear.

## Rules and defaults

- **Updatable view (PostgreSQL 18):** INSERT, UPDATE and DELETE work automatically when the view reads exactly one table and has no DISTINCT, GROUP BY, HAVING, LIMIT, OFFSET, WITH, UNION, aggregates or window functions. MySQL has similar rules.
- **WITH CHECK OPTION:** rejects a write through the view that would create a row the view cannot show, such as a FAILED payment through `paid_payments`. Without it, such a row is accepted.
- **Access:** by default the base tables are read with the view owner's rights (PostgreSQL; MySQL `SQL SECURITY DEFINER`), so granting only the view is enough.
- **Materialized views are read-only:** you cannot INSERT into one; only REFRESH changes it. A plain REFRESH can block reads while it runs.
- **MySQL 9.7:** the manual says materialized views are supported only on MySQL HeatWave (from 9.5), where the view is re-materialized automatically when a query reads it after its base tables changed. Elsewhere, use a summary table kept up to date by a job.

## Common mistakes

- **"I will put the slow query in a view to make it fast."** The view runs the same query, so it is exactly as slow. Index the base tables or use a materialized view.
- **"The materialized view updates itself when payments change."** In PostgreSQL nothing refreshes it automatically; schedule the REFRESH or run it after a data load.

## Interview Qs

### What is the difference between a view and a table?

A table stores rows. A view stores only a SELECT; each time you query it, the database runs that SELECT on the base tables, so the result is always current and takes no storage. Views are used to simplify queries, hide columns and control access.

### Can you insert or update through a view?

Yes, if the view is simple: one base table and no GROUP BY, DISTINCT, aggregates or LIMIT. The write goes to the base table. Add WITH CHECK OPTION to reject rows the view would not show. For a complex view, PostgreSQL needs an INSTEAD OF trigger that writes the base tables.

### How do you keep a materialized view up to date?

Run REFRESH MATERIALIZED VIEW on a schedule or after each data load; it recomputes the whole result. With CONCURRENTLY and a unique index on the view, reads are not blocked during the refresh. Choose it only when slightly old data is acceptable.
