## Why it exists

The same long query gets copied into many places, and some users should see only part of a table. A view gives that query one name.

## How it works

<Compare id="view-vs-materialized-view" />

- Without `WITH CHECK OPTION`, an insert through a view may create a row the view cannot show.
- PostgreSQL can index a materialized view like a table.

## Example

```sql
CREATE VIEW paid_orders AS
  SELECT id, user_id, amount FROM orders WHERE status = 'PAID';

CREATE MATERIALIZED VIEW user_totals AS
  SELECT user_id, SUM(amount) AS total FROM orders GROUP BY user_id;
CREATE UNIQUE INDEX ON user_totals (user_id);

-- reads keep working while it refreshes
REFRESH MATERIALIZED VIEW CONCURRENTLY user_totals;
```

## Interview Qs

### What is the difference between a view and a table?

A table stores rows. A view stores only a SELECT; each time you query it, the database runs that SELECT on the base tables, so it is always current.

### Can you insert or update through a view?

Yes, if it is simple: one table and no GROUP BY, DISTINCT or aggregates. Add WITH CHECK OPTION to reject rows the view would not show. Complex views need an INSTEAD OF trigger in PostgreSQL.

### How do you keep a materialized view up to date?

Run REFRESH MATERIALIZED VIEW on a schedule or after loads. With CONCURRENTLY and a unique index, reads are not blocked during the refresh.
