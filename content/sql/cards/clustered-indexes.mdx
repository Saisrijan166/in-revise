## Why it exists

Rows must be stored in some order. If that order is the key you search by most, one tree walk lands on the row; every other index needs a second step.

## How it works

<Compare id="clustered-vs-nonclustered-index" />

- Keep an InnoDB primary key short: every secondary index copies it.
- A query that needs only the secondary key and the PK skips the second lookup ([covering](card:composite-indexes)).

## Example

```sql
-- MySQL InnoDB
CREATE TABLE orders (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,  -- clustered: rows stored by id
  user_id BIGINT NOT NULL,
  amount DECIMAL(10,2),
  INDEX idx_orders_user (user_id)         -- entries: (user_id, id)
);
-- idx_orders_user gives the id, then the clustered index gives the row
SELECT amount FROM orders WHERE user_id = 7;
```

PostgreSQL: `CLUSTER orders USING orders_pkey;` rewrites the table in key order once, under an ACCESS EXCLUSIVE lock.

## Interview Qs

### How many clustered indexes can a table have?

One, because the rows can be stored in only one order. A table can have many non-clustered (secondary) indexes.

### Why should an InnoDB primary key be short?

Every secondary index entry stores the primary key value, so a long key such as an email makes every index bigger. A short auto-increment id keeps them small.

### Does PostgreSQL have clustered indexes?

No. Tables are heaps and every index is separate. `CLUSTER` reorders a table once, but later writes are not kept in that order.
