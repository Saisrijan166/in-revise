## What it is

A clustered index is an index whose leaf pages hold the full rows, so the table itself is stored in the order of that index's key. A non-clustered index, also called a secondary index, is a separate structure that holds the key and a way to reach the row. A table can have only one clustered index, because its rows can be stored in only one order. Whether a table has one depends on the [database](card:postgresql-and-mysql).

## Why it exists

Every index lookup ends by fetching the row. If the rows sit inside the index you searched, the walk ends at the row itself, and rows with neighbouring keys share pages, so a range such as ids 1,000 to 1,100 reads few pages. MySQL InnoDB stores every table this way, around the primary key. The price is that every other index needs a second step to reach the row.

## How it works

<Compare id="clustered-vs-nonclustered-index" />

Follow `WHERE customer_id = 7` on an InnoDB `payments` table:

1. InnoDB stores the payments rows in the leaf pages of the PRIMARY KEY index, sorted by `id`.
2. A secondary index on `customer_id` stores pairs of (`customer_id`, `id`), sorted by `customer_id`.
3. The query walks the secondary index and collects the ids of customer 7's payments.
4. For each id, InnoDB walks the clustered index down to the full row. If the query needs only `customer_id` and `id`, it skips this step, because the secondary index already holds both.
5. In PostgreSQL, by contrast, each index entry points straight to a row's place in the heap, the table's unordered storage, so there is no second tree walk.

So in InnoDB the primary key is copied into every secondary index.

## Example

The same lookup on InnoDB, once reading `amount` and once reading only `id`. The table holds 100,000 payments.

```sql
-- MySQL 9.7, InnoDB
CREATE TABLE payments (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,      -- clustered: rows stored by id
  customer_id BIGINT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  INDEX idx_payments_customer (customer_id)  -- entries: (customer_id, id)
);
EXPLAIN FORMAT=TREE SELECT amount FROM payments WHERE customer_id = 7;
EXPLAIN FORMAT=TREE SELECT id FROM payments WHERE customer_id = 7;
```

```text output
-> Index lookup on payments using idx_payments_customer (customer_id = 7)  (cost=3.5 rows=10)
-> Covering index lookup on payments using idx_payments_customer (customer_id = 7)  (cost=1.25 rows=10)
```

What to notice:

- `amount` is not in the secondary index, so each of the 10 matches needs a second walk through the clustered index: an "Index lookup".
- `id` is the primary key, and InnoDB stores it in every secondary index entry, so the second query is answered from `idx_payments_customer` alone: a "Covering index lookup", with a lower cost.
- Make `id` a long string and every entry of `idx_payments_customer` grows with it.

## Rules and defaults

- **InnoDB clustered key:** the PRIMARY KEY. With no primary key, the first UNIQUE index whose columns are all NOT NULL. With neither, InnoDB adds a hidden clustered index, `GEN_CLUST_INDEX`, on a 6-byte row id.
- **Short primary key:** every InnoDB secondary index entry carries the primary key, so a short key such as a BIGINT keeps all of them small.
- **PostgreSQL:** tables are heaps and every index is secondary. `CLUSTER payments USING payments_pkey` rewrites the table in that order once, under an ACCESS EXCLUSIVE lock that blocks reads and writes; later writes are not kept in order.

## Not to be confused with

A [primary key](card:keys) is a rule: each row has a unique, non-NULL id. A clustered index is a way of storing rows. In InnoDB the primary key becomes the clustered index; in PostgreSQL the primary key is an ordinary unique index over a heap. Rule: primary key = which rows are allowed; clustered index = where the rows live.

## Interview Qs

### How many clustered indexes can a table have?

One, because the rows themselves can be stored in only one order. A table can have many non-clustered (secondary) indexes, each a separate structure pointing to the rows.

### Why should an InnoDB primary key be short?

Every secondary index entry stores the primary key value to find the row. A long key, such as an email or a UUID string, makes every secondary index bigger and slower to search. A short auto-increment BIGINT keeps them small.

### Does PostgreSQL have clustered indexes?

No. Tables are heaps, and every index, including the primary key's, is stored separately. `CLUSTER` reorders a table once by an index, but PostgreSQL does not keep that order as rows are inserted or updated.
