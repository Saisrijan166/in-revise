## What it is

An index is a separate structure the database keeps next to a table, so it can find rows by the value of some columns without reading every row. The table's rows are not sorted by the columns you search on. The index holds one or more columns, such as `customer_id`, in sorted order, each value with a pointer to the row it came from. The database updates it on every change, and the [primary key](card:keys) already has one.

## Why it exists

Take `SELECT * FROM payments WHERE customer_id = 7` on 100,000 payments. With no index, the database reads all 100,000 rows and throws away the 99,990 that do not match, and the work grows with the table. With an index on `customer_id`, it walks the sorted index to the value 7, gets the 10 row pointers and reads only those rows. The cost now depends on how many rows match, not on how big the table is.

## How it works

<Mermaid
  alt="A query for customer_id 7. Without an index the database reads all 100,000 rows. With an index it goes from the root page to a branch page to the leaf page holding 7, gets 10 row pointers, and reads only those 10 rows."
  chart={`flowchart LR
  Q(["WHERE customer_id = 7"]) -. "no index" .-> S[("Read all 100,000 rows")]
  Q --> R[Root page]
  R --> B[Branch page]
  B --> L["Leaf page: 7 and 10 row pointers"]
  L --> T[("Read only those 10 rows")]`}
/>

1. You run `CREATE INDEX idx_payments_customer ON payments (customer_id)`. The database reads the table once and builds a B-tree: a balanced tree of pages whose leaf pages hold every `customer_id` value in sorted order with its row pointer.
2. A query arrives with `WHERE customer_id = 7`. The planner, the part of the database that chooses how to run a query, estimates how many rows match and compares using the index with reading the whole table.
3. If the index is cheaper, the database goes from the root page down a few levels to the leaf page that holds 7. Because the values are sorted, it never looks at the rest of the tree.
4. It follows the pointers and reads just the matching rows from the table.
5. From now on every INSERT, and every UPDATE or DELETE, also does the work to keep each index in step with the table.

So an index trades extra work on every write for much less work on matching reads.

## Analogy

<Analogy title="The index at the back of a book" limit="A book's index never changes, while a database index is updated on every write, and the database may still decide to read the whole table.">
To find "deadlock" you look it up in the sorted index, get the page numbers and open only those pages, instead of reading the book from page 1.
</Analogy>

## Example

The same query on 100,000 payments, before and after the index, on PostgreSQL 18. Customer 7 has 10 payments.

```sql
EXPLAIN ANALYZE SELECT id, amount FROM payments WHERE customer_id = 7;

CREATE INDEX idx_payments_customer ON payments (customer_id);

EXPLAIN ANALYZE SELECT id, amount FROM payments WHERE customer_id = 7;
```

What to notice:

- `EXPLAIN ANALYZE` runs the query and reports how the database read the table. You will learn to read it in [Query execution and EXPLAIN](card:explain-query-plans).
- Before the index, the plan was `Seq Scan on payments` with `Rows Removed by Filter: 99990`: all 100,000 rows were read to return 10, in about 15.7 ms.
- After the index, the plan used `idx_payments_customer` and read only the 10 matching rows, in about 0.13 ms.
- `customer_id` is a foreign key, yet PostgreSQL had not indexed it. MySQL InnoDB would have created this index by itself.

## Rules and defaults

- **Automatic indexes:** a PRIMARY KEY or UNIQUE constraint always creates a unique index, in PostgreSQL 18 and MySQL 9.7. Do not add a second index on the same column.
- **Foreign keys:** MySQL InnoDB needs an index on the foreign key columns and creates one if it is missing. PostgreSQL 18 does not; index the referencing column yourself, because joins use it and deleting a parent row must search the child table.
- **Building on a live table:** a plain PostgreSQL `CREATE INDEX` blocks INSERT, UPDATE and DELETE on the table until it ends, though reads continue. See the last interview question for the way around it.
- **Kept current for you:** the database updates every index on each write. You never refresh an index by hand after changing data.

## Not to be confused with

A [key or UNIQUE constraint](card:constraints) is a rule about the data: no two payments may share an id. An index is a lookup structure that makes finding rows fast. The database enforces a uniqueness rule with a unique index, which is why the two appear together, but you can index any column without adding a rule. Rule: constraint = what is allowed; index = how fast it is found.

## Common mistakes

- **"More indexes can only help."** Every index slows writes, and one that no query uses gives nothing back. In PostgreSQL, `pg_stat_user_indexes.idx_scan` counts each index's scans; an index that stays at 0 for a long period is a candidate to drop.

## Interview Qs

### What is an index, and what does it cost?

A separate sorted structure over some columns that finds rows by those columns without scanning the table. It costs disk space, and every insert, update and delete must also maintain each index, so too many indexes slow writes.

### Should you index foreign key columns?

Usually yes. Joins use them, and deleting or changing a parent row must search the child table for rows that point to it. MySQL InnoDB creates that index automatically; PostgreSQL leaves it to you.

### How would you add an index to a big production table without blocking writes?

In PostgreSQL, use `CREATE INDEX CONCURRENTLY`: it takes longer but lets inserts and updates continue, and it cannot run inside a transaction. If it fails, it leaves an invalid index to drop and rebuild. In MySQL InnoDB, adding a secondary index already allows concurrent writes.
