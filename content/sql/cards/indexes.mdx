## Why it exists

Without an index, `WHERE email = 'asha@example.com'` reads every row. With one, the database walks a few tree levels and reads only the matches.

## How it works

<Mermaid
  alt="Without an index the query reads every row. With one it walks root, branch and leaf pages to a row pointer, then reads only that row."
  chart={`flowchart LR
  Q([WHERE email = ...]) --> N[No index: read all rows]
  Q --> R[Root page]
  R --> B[Branch page]
  B --> L[Leaf: email + row pointer]
  L --> T[(Just that row)]`}
/>

- The planner uses an index only when it is cheaper than a full scan: [why an index is skipped](card:index-not-used).
- Pick the kind in [index types](card:index-types); for several columns see [composite indexes](card:composite-indexes).

## Analogy

<Analogy title="The index at the back of a book" limit="A book index never changes; a database index is updated on every write, and the database may still decide to read the whole table.">
Look up a word, get the page numbers, open only those pages.
</Analogy>

## Example

```sql
CREATE INDEX idx_users_email ON users (email);

-- now a tree lookup, not a full scan
SELECT id, name FROM users WHERE email = 'asha@example.com';

-- PostgreSQL: index the FK column yourself
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

## Interview Qs

### What is an index, and what does it cost?

A separate search structure that finds rows by key without scanning the table. It costs disk space, and every insert, update and delete must also change each index.

### Should you index foreign key columns?

Usually. Joins use them, and deleting a parent row must search the child table. InnoDB creates the index if missing; PostgreSQL leaves it to you.
