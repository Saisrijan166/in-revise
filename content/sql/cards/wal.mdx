## Why it exists

Writing every changed data page at each commit is slow. Logging the change first makes a commit one fast write that a crash cannot lose.

## How it works

<Steps label="One committed change">
  <Step title="Change in memory">The row is changed in a page held in memory.</Step>
  <Step title="Log it">A log record describing the change is appended.</Step>
  <Step title="COMMIT">The log is flushed to disk; only then does the client hear "success".</Step>
  <Step title="Pages later">Changed pages are written to disk later, in the background.</Step>
  <Step title="After a crash">The log is replayed to redo changes the pages missed.</Step>
</Steps>

- The same log feeds [replication](card:replication) and [point-in-time recovery](card:backup-recovery).
- PostgreSQL `synchronous_commit = off` may lose recent commits but never corrupts; `fsync = off` can corrupt.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `synchronous_commit` | `on`: commit waits for the WAL flush | PostgreSQL 18 |
| `innodb_flush_log_at_trx_commit` | `1`: flush redo log at each commit | MySQL 9.7 (InnoDB) |
| `log_bin` (binary log) | On | MySQL 9.7 |

## Interview Qs

### What is a write-ahead log, and why is it fast?

Every change is recorded in an append-only log before the data files change. Commit needs one sequential flush of the log, not random writes of every page; many small commits can share one flush.

### Redo log vs binary log in MySQL?

The redo log belongs to InnoDB and is used for crash recovery. The binary log belongs to the server and records changes for replicas and point-in-time recovery.
