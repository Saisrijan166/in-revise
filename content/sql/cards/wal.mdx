## What it is

The write-ahead log (WAL) is an append-only file in which the database records every change before it changes the data files that hold tables and indexes. A commit is safe once that transaction's log records are flushed to disk, meaning forced out of the operating system's memory onto the storage device. PostgreSQL calls this log the WAL; MySQL's InnoDB engine calls its version the redo log.

## Why it exists

[Durability](card:acid) says a committed payment survives a crash. Tables and indexes are stored on disk in fixed-size blocks called pages. The direct way is to write every changed page to disk at each `COMMIT`, which means many slow writes scattered over the disk. The log turns that into one sequential append, and when many small transactions commit together, one flush can cover them all. The data pages can be written later, because the log can redo them.

## How it works

<Mermaid
  alt="An UPDATE changes a page in memory and appends a log record. COMMIT flushes the log to disk and then reports success. Later the changed pages are written to the data files. After a crash, the log is replayed to redo changes the data files missed."
  chart={`flowchart LR
  U([UPDATE]) --> P[page in memory]
  U --> L[log record]
  C([COMMIT]) --> F[flush log to disk] --> OK([success])
  P -. later .-> D[(data files)]
  L -. after a crash: replay .-> D`}
/>

1. An UPDATE changes the row in a copy of its page held in memory.
2. A log record describing the change is added to the log.
3. At `COMMIT`, the database flushes the log to disk, and only then tells the client "success".
4. Later, in the background, the changed pages are written to the data files.
5. After a crash, the database replays the log and redoes every change the data files missed. Work from transactions that never committed is not kept.

The same log has a second job: copies of it are sent to replicas and archived for point-in-time recovery, which you will see in [Replication](card:replication) and [Backup and recovery](card:backup-recovery).

## Example

Check the durability settings on each database (output from PostgreSQL 18 and MySQL 9.7 with default settings):

```sql
-- PostgreSQL 18
SHOW synchronous_commit;   -- on
SHOW fsync;                -- on
-- MySQL 9.7
SELECT @@innodb_flush_log_at_trx_commit, @@log_bin, @@sync_binlog;   -- 1, 1, 1
```

What to notice:

- `synchronous_commit = on` and `innodb_flush_log_at_trx_commit = 1` both mean a commit waits until its log records are on disk. This is what makes durability real.
- `sync_binlog = 1` makes MySQL also sync the binary log to disk before each commit, so replicas and recovery do not miss committed changes.
- `fsync = on` makes PostgreSQL force its writes onto the disk with fsync calls. Turned off, a crash can leave the database corrupt, not just missing recent commits.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| `synchronous_commit` | `on`: commit waits for the WAL flush | PostgreSQL 18 |
| `innodb_flush_log_at_trx_commit` | `1`: write and flush the redo log at each commit | MySQL 9.7 (InnoDB) |
| `log_bin` (binary log) | On | MySQL 9.7 |
| `sync_binlog` | `1`: sync the binary log before each commit | MySQL 9.7 |

- **PostgreSQL `synchronous_commit = off`:** commits return before the WAL flush. A crash can lose the last few commits, up to three times `wal_writer_delay`, but the database stays consistent. It can be set per transaction.
- **MySQL `innodb_flush_log_at_trx_commit` = 0 or 2:** the log is flushed about once a second, so a crash can lose up to about a second of commits.
- **`fsync = off`:** never for data you keep; a crash can corrupt the database.

## Not to be confused with

The redo log belongs to InnoDB and is replayed after a crash. The binary log belongs to the MySQL server and records changes for replicas and point-in-time recovery. The [undo log](card:undo-log) from MVCC holds old values for rollback and old snapshots. In PostgreSQL one WAL does both crash recovery and replication. Rule: redo = crash recovery; binlog = replicas and recovery to a point in time; undo = rollback and old versions.

## Interview Qs

### What is a write-ahead log, and why is it fast?

Every change is recorded in an append-only log before the data files change. A commit needs one sequential flush of the log, not random writes of every changed page, and many small concurrent commits can share one flush. The data pages are written later.

### Redo log vs binary log in MySQL?

The redo log belongs to InnoDB and is used for crash recovery. The binary log belongs to the MySQL server and records data changes for replicas and point-in-time recovery. Both are flushed at commit with the default settings.
