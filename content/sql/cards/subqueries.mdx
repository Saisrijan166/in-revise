## What it is

A subquery is a complete `SELECT` written in brackets inside another query, called the outer query. The outer query uses its result as a value, a list or a table. A subquery is correlated when it refers to a column of the outer query, such as the current customer's id. One that does not is non-correlated and can be worked out once, on its own.

## Why it exists

Some questions need one answer before another: "payments above the average amount" needs the average first. Without a subquery you would run two queries and paste the first result into the second, and the pasted number goes stale when data changes. A subquery computes the inner answer in place, in the same statement, so the outer query always uses the current value.

## How it works

Four kinds, run on the running example. Payment amounts are 500, 300, 700, 700 and 200, so the average is 480; the IN and EXISTS rows filter `customers c`.

| Kind | Returns | Written as | Result |
|---|---|---|---|
| Scalar | one value | `WHERE amount > (SELECT AVG(amount) FROM payments)` | payments 1, 3, 4 |
| IN | one column of values | `WHERE id IN (SELECT customer_id FROM payments WHERE status = 'FAILED')` | Asha |
| EXISTS | true or false | `WHERE EXISTS (SELECT 1 FROM payments p WHERE p.customer_id = c.id)` | Asha, Ravi, Meena (Kabir has no payment) |
| Derived table | a table | `FROM (SELECT customer_id, SUM(amount) AS total FROM payments GROUP BY customer_id) AS t` | one row per customer who has payments |

For a correlated EXISTS, the logical steps are:

1. The outer query takes one customer row, for example Asha with `id = 1`.
2. The subquery runs with `c.id` replaced by 1 and looks for a matching payment.
3. As soon as it finds one row, EXISTS is true; it does not need the rest.
4. The outer query keeps Asha and moves to the next customer.
5. The planner may replace this loop with a semi-join: a join that keeps each outer row once, as soon as one match is found. It gives the same rows, often faster.

## Example

Customers with at least one PAID payment. Asha has two PAID payments, Ravi has one, Meena and Kabir have none.

```sql
SELECT c.name
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM payments p
  WHERE p.customer_id = c.id     -- c.id comes from the outer row
    AND p.status = 'PAID'
)
ORDER BY c.name;
```

```text output
 name
------
 Asha
 Ravi
```

What to notice:

- `p.customer_id = c.id` makes the subquery correlated: it is checked for each customer.
- Asha appears once even though she has two PAID payments. The same question written as `JOIN payments` returns Asha twice, one row per matching payment.
- `SELECT 1` could be `SELECT *`; EXISTS ignores the columns and only asks whether a row exists.

## Rules and defaults

- **Scalar subquery:** must return one column and at most one row. Two rows is an error at run time; no rows gives NULL, so `amount > (empty subquery)` keeps nothing.
- **IN subquery:** must return exactly one column.
- **NOT IN and NULL:** if the subquery returns a NULL, `NOT IN` keeps no rows at all; see [NULL](card:null-handling). Use `NOT EXISTS` for "has none".
- **Derived table:** standard SQL requires an alias, and MySQL 9.7 fails with "Every derived table must have its own alias". PostgreSQL 18 accepts it without one, but write `AS t` to stay portable.
- **Where it can go:** in `SELECT`, `FROM`, `WHERE` and `HAVING`.

## Not to be confused with

A [join](card:joins) puts columns from two tables side by side and repeats a row for every match. A subquery in `WHERE` only tests or supplies a value, so the outer rows are never repeated. Rule: need columns from the other table, use a join; only need to check it, use EXISTS or IN.

## Interview Qs

### What is the difference between a correlated and a non-correlated subquery?

A non-correlated subquery does not use the outer query's columns, so it can run once and its result is reused. A correlated subquery uses a column of the outer row, so logically it is evaluated again for each outer row. The planner may still rewrite it as a join; check with EXPLAIN.

### What happens if a scalar subquery returns two rows, or none?

Two rows makes the statement fail at run time, because a single value was expected. No rows is not an error: the result is NULL, so a comparison with it is never true. Return one row with an aggregate such as MAX, a filter on a unique key, or ORDER BY with LIMIT 1.

### When would you use EXISTS instead of a JOIN?

When you only need to know whether a related row exists. A join returns one row per match, so a customer with two payments appears twice and needs DISTINCT. EXISTS returns each outer row once and can stop at the first match. If you need columns from the other table, use the join.
