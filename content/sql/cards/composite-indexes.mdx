## Why it exists

Real queries filter on two or three columns together. One index sorted by all of them finds the rows in one seek, and can even answer the query by itself.

## How it works

| `WHERE` (index on `user_id, status, created_at`) | Seek uses |
|---|---|
| `user_id = 7` | `user_id` |
| `user_id = 7 AND status = 'PAID'` | `user_id, status` |
| `user_id = 7 AND status = 'PAID' AND created_at > '2026-01-01'` | all three |
| `user_id = 7 AND created_at > '2026-01-01'` | `user_id`; `created_at` is checked inside the index |
| `status = 'PAID'` | no seek (skip scan at best) |

- PostgreSQL: an index-only scan still checks the visibility map; recently changed pages need a table visit.

## Example

```sql
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- PostgreSQL 11+: amount is stored in the index, not searchable
CREATE INDEX idx_orders_user_cover ON orders (user_id) INCLUDE (amount);

EXPLAIN SELECT amount FROM orders WHERE user_id = 7;
-- PostgreSQL: Index Only Scan using idx_orders_user_cover
```

## Interview Qs

### What is a covering index?

An index holding every column a query reads, so the answer comes from the index alone. In PostgreSQL 11+ add non-key columns with `INCLUDE`.

### Two single-column indexes or one composite index?

For queries that filter on both, one composite index is usually faster. PostgreSQL can combine two indexes with a bitmap, at extra cost; separate indexes also serve each column alone.
