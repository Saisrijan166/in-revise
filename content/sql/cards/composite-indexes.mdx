## What it is

A composite index, also called a multicolumn index, is one index on several columns, such as `(customer_id, status)`. Its entries are sorted by the first column, then by the second within each value of the first, like a phone book sorted by surname and then by first name. A covering index is any index that holds every column a query reads, so the database can answer from the index without visiting the table.

## Why it exists

Real queries filter on more than one column: "failed payments of customer 7". With an index on `customer_id` only, the database finds customer 7's rows and then checks `status` on each row in the table. A composite index on both columns finds exactly the matching entries in one seek. If the index also carries `amount`, the query never touches the table at all.

## How it works

| `WHERE` (index on `customer_id, status, created_at`) | Seek uses |
|---|---|
| `customer_id = 7` | `customer_id` |
| `customer_id = 7 AND status = 'PAID'` | `customer_id, status` |
| `customer_id = 7 AND status = 'PAID' AND created_at > '2026-06-01'` | all three |
| `customer_id = 7 AND created_at > '2026-06-01'` | `customer_id`; `created_at` is checked inside the index |
| `status = 'PAID'` | no seek (skip scan at best) |

1. The index stores its entries sorted by `customer_id`, then `status`, then `created_at`.
2. For `customer_id = 7 AND status = 'PAID'`, the database seeks to the first (7, 'PAID') entry and reads forward while both still match. All matching entries sit next to each other.
3. A range on the next column, `created_at > '2026-06-01'`, narrows that same run of entries. This is why equality columns go first and the range column last.
4. For `status = 'PAID'` alone, the matching entries are spread under every customer, so there is no single place to start. This is the leftmost-prefix rule.
5. If every column the query reads is in the index, the database returns rows from the index alone. This is called an index-only scan.

## Example

A composite index, a filter it cannot serve, and a covering version, on 100,000 payments in PostgreSQL 18.

```sql
CREATE INDEX idx_payments_cust_status ON payments (customer_id, status);
EXPLAIN SELECT id FROM payments WHERE customer_id = 7 AND status = 'FAILED';
EXPLAIN SELECT id FROM payments WHERE status = 'FAILED';

-- amount is stored in the index, but you cannot search on it
CREATE INDEX idx_payments_cover ON payments (customer_id, status)
  INCLUDE (amount);
VACUUM payments;
EXPLAIN ANALYZE SELECT amount FROM payments
WHERE customer_id = 7 AND status = 'PAID';
```

What to notice:

- The first query got `Index Scan using idx_payments_cust_status` with both columns in the `Index Cond`.
- The second query got `Seq Scan on payments`: `status` is not the leftmost column, and with 10,000 distinct customers a skip scan was not worth it.
- The last query got `Index Only Scan using idx_payments_cover` with `Heap Fetches: 0`: `amount` came from the index, and the table was never read.
- `VACUUM` updated the visibility map first. Without it, recently changed pages would still need a visit to the table.

## Rules and defaults

- **Leftmost prefix:** a B-tree on `(a, b, c)` seeks on `a`; `a, b`; or `a, b, c`. The order of conditions inside the WHERE does not matter.
- **Equality, then sort:** for `WHERE customer_id = ? ORDER BY created_at DESC`, an index on `(customer_id, created_at)` returns rows already sorted; PostgreSQL reads it backward for DESC.
- **Skip scan:** MySQL 8.0.13+ and PostgreSQL 18 can use the index with no condition on the first column, by seeking each of its distinct values. It pays off only when that column has few values. MySQL also needs a range condition and a query that reads only indexed columns.
- **INCLUDE (PostgreSQL 11+):** adds non-key columns that an index-only scan can return. B-tree, GiST and SP-GiST support it.
- **Visibility map (PostgreSQL):** an index-only scan still checks whether each row's page is all-visible; pages changed since the last VACUUM need a heap visit, shown as `Heap Fetches`.
- **InnoDB:** every secondary index already holds the primary key, so `(customer_id)` covers `SELECT id ... WHERE customer_id = ?`, as in [clustered indexes](card:clustered-indexes).

## Not to be confused with

A composite index is about how many key columns an index has. A covering index is about one query: does the index hold every column that query reads? An index on `(customer_id)` covers `SELECT customer_id`, and a composite index fails to cover `SELECT *`. Rule: composite = several key columns; covering = enough columns for this query.

## Interview Qs

### What is a covering index?

An index holding every column a query reads, so the answer comes from the index alone, without reading table rows. In PostgreSQL 11+, add non-key columns with `INCLUDE`. In InnoDB, secondary indexes already contain the primary key.

### Two single-column indexes or one composite index?

For queries that filter on both columns, one composite index is usually faster: one seek finds exactly the matching entries. PostgreSQL can combine two single-column indexes with a bitmap, at extra cost. Separate indexes also serve each column alone, so the right answer depends on the queries you run.

### Why does column order matter in a composite index?

Entries are sorted by the first column, so a seek needs a condition on it. Put equality columns first and the range or sort column last. After a range column, later columns are only checked inside the index; they do not necessarily narrow the part of the index that is read.
