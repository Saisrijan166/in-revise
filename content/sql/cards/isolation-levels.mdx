## What it is

When two [transactions](card:transactions) run at the same time, one may read rows that the other is changing. An isolation level is the setting that decides what a transaction is allowed to see of that other work. The SQL standard defines four levels, from weakest to strongest: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ and SERIALIZABLE. It is the I of [ACID](card:acid), made adjustable.

## Why it exists

Perfect isolation means the result is the same as if the transactions had run one after another. That costs something: transactions wait for each other, or the database aborts one so it can be retried. Many requests can live with small read problems in return for speed, such as a dashboard that shows a status changed a moment ago. Levels let each transaction choose that trade-off instead of paying the full price everywhere.

## How it works

| Level (SQL standard) | Dirty read | Non-repeatable read | Phantom read |
| --- | --- | --- | --- |
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | no | possible | possible |
| REPEATABLE READ | no | no | possible |
| SERIALIZABLE | no | no | no |

The three read problems, called anomalies, appear in this order when transaction A reads while transaction B writes:

1. A reads payment 2: `PENDING`.
2. B sets payment 2 to `PAID` but has not committed. If A could see `PAID` now, that would be a dirty read: B may still roll back.
3. B commits. If A reads payment 2 again and now sees `PAID`, that is a non-repeatable read.
4. B inserts payment 8 as `PENDING` and commits. If A re-runs `WHERE status = 'PENDING'` and gets an extra row, that is a phantom read.
5. A's isolation level decides which of steps 2 to 4 it can notice.

So each level up closes one more of these doors. Two more anomalies sit outside the table: the [lost update](card:lost-update), where a later write erases an earlier one, and [write skew](card:write-skew), which only SERIALIZABLE stops.

## Example

Session A works at REPEATABLE READ in PostgreSQL 18 while session B marks payment 2 as paid:

```sql
-- Session A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM payments WHERE id = 2;            -- PENDING
-- Session B, autocommit: UPDATE payments SET status = 'PAID' WHERE id = 2;
SELECT status FROM payments WHERE id = 2;            -- still PENDING
UPDATE payments SET status = 'FAILED' WHERE id = 2;
-- ERROR: could not serialize access due to concurrent update
ROLLBACK;
```

What to notice:

- The second SELECT still shows `PENDING`: the whole transaction reads one snapshot, a fixed picture of the data committed at its first statement. At READ COMMITTED the same SELECT shows `PAID`.
- The UPDATE fails because the row changed after A's snapshot. Writing `FAILED` would silently erase B's `PAID`, so PostgreSQL aborts A with SQLSTATE 40001. A must retry from `BEGIN`.
- MySQL 9.7 at REPEATABLE READ does not fail here. Its UPDATE works on the latest committed row, so `FAILED` overwrites `PAID` without an error.

## Rules and defaults

- **Defaults:** READ COMMITTED in PostgreSQL 18; REPEATABLE READ in MySQL 9.7 InnoDB.
- **Setting it, PostgreSQL:** `BEGIN ISOLATION LEVEL …`, or `SET TRANSACTION ISOLATION LEVEL …` before the transaction's first query. After that the level cannot change.
- **Setting it, MySQL:** `SET TRANSACTION ISOLATION LEVEL …` before `START TRANSACTION` applies to the next transaction only; inside an open transaction it is an error.
- **PostgreSQL is stricter than the standard:** READ UNCOMMITTED behaves as READ COMMITTED, and REPEATABLE READ also blocks phantoms. It is snapshot isolation, which still allows write skew.
- **SERIALIZABLE, PostgreSQL:** adds no blocking beyond REPEATABLE READ. It watches for patterns that could not happen one-at-a-time and aborts one transaction with 40001.
- **SERIALIZABLE, MySQL InnoDB:** with autocommit off, a plain SELECT becomes `SELECT … FOR SHARE`, so readers lock rows and can block writers.
- **Retry:** at REPEATABLE READ or SERIALIZABLE in PostgreSQL, catch 40001 and rerun the whole transaction, not just the failed statement.

## Not to be confused with

A non-repeatable read is about one row whose values changed between two reads. A phantom read is about a set of rows, chosen by a WHERE, that gained or lost members. A lost update is two transactions writing the same row; write skew is two transactions writing different rows that together break a rule. Rule: changed values = non-repeatable; changed membership = phantom.

## Interview Qs

### What are the isolation levels, and what does each prevent?

READ UNCOMMITTED allows dirty reads. READ COMMITTED stops them. REPEATABLE READ also stops non-repeatable reads. SERIALIZABLE also stops phantoms and every other anomaly: the result equals some one-at-a-time order of the transactions. Products may be stricter than the standard, as PostgreSQL is.

### Why not run everything at SERIALIZABLE?

It costs throughput. In PostgreSQL, more transactions abort with 40001 and must be retried. In MySQL, plain reads take shared locks and block writers. Most requests are fine at READ COMMITTED with a targeted row lock or an atomic UPDATE; use SERIALIZABLE where a rule spans several rows.

### How does PostgreSQL REPEATABLE READ differ from MySQL's?

Both give plain reads one snapshot for the whole transaction. PostgreSQL also refuses to update a row changed after that snapshot and aborts with 40001. MySQL InnoDB updates the latest committed version without an error, and its locking reads use [next-key locks](card:next-key-lock), which you will see in Locks, to block phantoms.
