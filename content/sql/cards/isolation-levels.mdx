## Why it exists

Full isolation costs waits or retries. Levels let an app accept known anomalies in return for more concurrency.

## How it works

| Level (SQL standard) | Dirty read | Non-repeatable read | Phantom read |
| --- | --- | --- | --- |
| READ UNCOMMITTED | possible | possible | possible |
| READ COMMITTED | no | possible | possible |
| REPEATABLE READ | no | no | possible |
| SERIALIZABLE | no | no | no |

- The standard sets the minimum; a product may block more, like PostgreSQL REPEATABLE READ blocking phantoms.
- Beyond the table: [lost update](card:lost-update) and [write skew](card:write-skew); only SERIALIZABLE stops write skew.
- MySQL InnoDB: plain `SELECT` reads a snapshot; locking reads use next-key [locks](card:locking) instead.

## Example

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;              -- PostgreSQL
SELECT balance FROM accounts WHERE id = 1;          -- 1000
-- another session sets balance = 500 and commits
SELECT balance FROM accounts WHERE id = 1;          -- still 1000
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update (40001)
```

MySQL InnoDB at REPEATABLE READ does not fail here: the `UPDATE` changes the latest committed row (500 → 400).

## Interview Qs

### What are the isolation levels, and what does each prevent?

READ UNCOMMITTED allows dirty reads. READ COMMITTED stops them. REPEATABLE READ also stops non-repeatable reads. SERIALIZABLE also stops phantoms and every other anomaly: the result equals some one-at-a-time order.

### What is write skew?

Two transactions read the same rows, each writes a different row, and together they break a rule: two withdrawals each see enough in the joint total, and the total goes negative. Snapshot isolation allows it; SERIALIZABLE prevents it.
