## What it is

A transaction is a group of SQL statements that the database treats as one unit of work. You start it with `BEGIN` (the standard spelling is `START TRANSACTION`), run your statements, and end it with `COMMIT`, which keeps every change, or `ROLLBACK`, which undoes every change. These are the TCL commands from [SQL command types](card:sql-commands).

## Why it exists

In this topic each customer also has a wallet: `wallets(customer_id, balance)`, with `CHECK (balance >= 0)`. Paying ₹500 from a wallet takes two statements: lower the balance, then insert a `PAID` row in `payments`. If the app crashes, or the INSERT fails, between the two, the customer has lost ₹500 and has no payment to show for it. Fixing that by hand means writing undo code for every point of failure. In a transaction the database does the undo: both changes are saved, or neither is.

## How it works

  B([BEGIN]) --> W[statements]
  W --> S[SAVEPOINT sp]

  W2 --> R([ROLLBACK: undo all])`}
/>

1. `BEGIN` opens the transaction. Nothing you change from now on is permanent yet.
2. Each statement runs, and its changes are held inside the transaction.
3. `SAVEPOINT name` sets a named mark. `ROLLBACK TO SAVEPOINT name` undoes only the work done after the mark, and the transaction stays open.
4. `COMMIT` makes all the changes permanent at once. `ROLLBACK` throws all of them away instead.
5. Either way the transaction ends, and the row locks it took are released (you will see these in [Locks](card:locking)).

So the key is: nothing inside a transaction is permanent until `COMMIT`.

## Example

A nightly import inserts payments one by one. A savepoint before each row lets one bad row be skipped without losing the rows before it (PostgreSQL 18):

```sql
BEGIN;
INSERT INTO payments (id, customer_id, amount, status) VALUES (5, 1, 500, 'PAID');
SAVEPOINT before_next;
INSERT INTO payments (id, customer_id, amount, status) VALUES (6, 9, 300, 'PAID');
-- ERROR: violates foreign key constraint (customer 9 does not exist)
ROLLBACK TO SAVEPOINT before_next;   -- undo only the failed insert
INSERT INTO payments (id, customer_id, amount, status) VALUES (7, 2, 300, 'PAID');
COMMIT;                              -- payments 5 and 7 are saved
```

What to notice:

- The foreign key rejects payment 6. In PostgreSQL that error marks the whole transaction as failed: without the `ROLLBACK TO`, the next INSERT fails with "current transaction is aborted".
- `ROLLBACK TO` undoes only the work after the savepoint. Payment 5, inserted before it, stays and is committed.

In Java, a JDBC connection starts in autocommit mode, so the app turns it off to group the debit and the payment:

```java
void payFromWallet(Connection con, int customerId, int paymentId, BigDecimal amount) throws SQLException {
    con.setAutoCommit(false);                    // start a transaction: no commit per statement
    try (PreparedStatement debit = con.prepareStatement(
             "UPDATE wallets SET balance = balance - ? WHERE customer_id = ?");
         PreparedStatement pay = con.prepareStatement(
             "INSERT INTO payments (id, customer_id, amount, status) VALUES (?, ?, ?, 'PAID')")) {
        debit.setBigDecimal(1, amount); debit.setInt(2, customerId); debit.executeUpdate();
        pay.setInt(1, paymentId); pay.setInt(2, customerId); pay.setBigDecimal(3, amount); pay.executeUpdate();
        con.commit();                            // both changes become permanent together
    } catch (SQLException e) {
        con.rollback();                          // undo whatever ran before the failure
        throw e;
    }
}
```

What to notice:

- `setAutoCommit(false)` is what starts the transaction. Without it, each `executeUpdate` commits on its own, and a failed INSERT would leave the debit saved.
- The `catch` calls `rollback()`, so a failure in either statement leaves both tables unchanged. Customer 2's wallet holds ₹300, so paying ₹500 from it fails the `balance >= 0` check and saves nothing.

## Rules and defaults

- **Autocommit:** on by default in PostgreSQL 18, MySQL 9.7 and JDBC. A statement outside `BEGIN` is committed as soon as it finishes.
- **After an error, PostgreSQL:** the transaction is aborted. Every later statement fails until `ROLLBACK` or `ROLLBACK TO SAVEPOINT`, and a `COMMIT` ends it as a rollback.
- **After an error, MySQL InnoDB:** most errors, such as a duplicate key or a failed constraint, undo only that statement and leave the transaction open. A [deadlock](card:deadlocks), which comes later in this topic, undoes the whole transaction.
- **DDL:** PostgreSQL can roll back most DDL, such as `CREATE TABLE` and `ALTER TABLE`. MySQL commits the open transaction before most DDL (an implicit commit), so neither the DDL nor the work before it can be rolled back.
- **Savepoints:** you can roll back to the same savepoint more than once. Rolling back to a savepoint also removes the savepoints set after it.
- **Keep it short:** an open transaction holds its locks until it ends, so never wait for a user or a slow remote call inside one.

## Interview Qs

### What is a transaction, and why do we need one?

A group of statements the database treats as one unit: either all changes are committed or none are. Without it, a crash between a wallet debit and the payment insert would leave money taken and no payment recorded. With it, the database undoes the unfinished part for you.

### What is a savepoint, and when would you use one?

A named mark inside a transaction. `ROLLBACK TO` it undoes only the work done after the mark; earlier work stays, and the transaction can still commit. It is useful for skipping one bad row in a batch, especially in PostgreSQL, where an error otherwise blocks the rest of the transaction.

### Can you roll back a CREATE TABLE or ALTER TABLE?

In PostgreSQL, yes, for most DDL: it is part of the transaction like any data change. In MySQL, no: most DDL first commits the open transaction with an implicit commit, so the DDL and everything before it are already permanent.
