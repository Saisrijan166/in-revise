## Why it exists

A money transfer is two updates. If the app crashes between them, money vanishes. A transaction makes the group succeed or fail together.

## How it works

<Mermaid
  alt="A transaction starts with BEGIN, runs statements, and may set a SAVEPOINT. ROLLBACK TO the savepoint undoes only later work and the transaction continues. At the end, COMMIT keeps all changes, or ROLLBACK discards all of them."
  chart={`flowchart LR
  B([BEGIN]) --> W[statements]
  W --> S[SAVEPOINT sp]
  S --> W2[more statements]
  W2 -. "ROLLBACK TO sp" .-> S
  W2 --> C([COMMIT: keep all])
  W2 --> R([ROLLBACK: undo all])`}
/>

- `START TRANSACTION` is the standard spelling; `BEGIN` works in both PostgreSQL and MySQL.
- Keep transactions short: an open one holds its [locks](card:locking) until it ends.

## Example

```sql
BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE accounts SET balance = balance + 500 WHERE id = 3;  -- wrong account
ROLLBACK TO SAVEPOINT after_debit;                         -- undo only that
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;                                                    -- debit + right credit
```

## Interview Qs

### What is a transaction?

A group of statements that the database treats as one unit: either all changes are committed or none are. It is how a transfer avoids a debit without the matching credit.

### What is a savepoint?

A named mark inside a transaction. `ROLLBACK TO` it undoes only the work done after it; earlier work stays, and the transaction can still commit.

### Can you roll back a CREATE TABLE?

In PostgreSQL, yes for most DDL. In MySQL, no: most DDL ends the open transaction with an implicit commit first.
