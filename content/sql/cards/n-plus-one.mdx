## Why it exists

Lazy loading looks free in code: `order.getUser()` is only a getter. In a loop over 100 orders it quietly becomes 101 round trips to the database.

## How it works

| Fix | Queries for 100 orders | Use when |
|---|---|---|
| None (lazy in a loop) | 1 + 100 | never on a list page |
| JOIN FETCH or `@EntityGraph` | 1 | this use case needs the users |
| Batch fetching, size 25 | 1 + 4 | a safety net for all lazy loads |
| DTO projection | 1 | read-only lists and APIs |

- Hibernate turns batch fetching on with `@BatchSize` or `hibernate.default_batch_fetch_size`; it is off by default.
- The same bug exists without an ORM: any loop that runs one query per row.

## Example

```java
// N+1: 1 query for orders, then 1 per order for its user
for (CustomerOrder o : orderRepo.findByStatus("PAID")) {
    log.info(o.getUser().getName());
}

// Fixed: one query with a join
@Query("SELECT o FROM CustomerOrder o JOIN FETCH o.user WHERE o.status = :s")
List<CustomerOrder> findPaidWithUser(@Param("s") String s);

// Or let Spring Data add the fetch
@EntityGraph(attributePaths = "user")
List<CustomerOrder> findByStatus(String status);
```

## Interview Qs

### How do you detect N+1 in a Spring Boot app?

Log the SQL (`spring.jpa.show-sql` or Hibernate's SQL logging) or enable Hibernate statistics in a test, and count statements per request. A list page that runs one SELECT per row is the sign.

### JOIN FETCH or batch fetching?

JOIN FETCH loads parents and children in one query for that use case. Batch fetching stays lazy but loads many keys per query, so N extra queries become about N divided by the batch size.
