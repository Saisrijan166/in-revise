## What it is

The N+1 query problem is when code runs one query to load a list of N rows, and then one more query for each row to load related data: N+1 queries where one or two would do. With JPA it usually comes from a [lazy association](card:orm-jpa) read inside a loop. Lazy means the related object is loaded only when the code first touches it, so each touch costs its own query. The same bug exists without an ORM: any loop that runs one query per row.

## Why it exists

Lazy loading looks free in code: `payment.getCustomer()` is just a getter. In a loop over 100 payments it quietly becomes 101 round trips to the database, and each trip waits for the network and the server. The page gets slower as the list grows, and nothing in the Java code looks wrong. A [join](card:joins) could load the payments and their customers in one query, so the cure is to tell JPA what this use case needs before the loop starts.

## How it works

| Fix | Queries for N payments | Use it when |
|---|---|---|
| None (lazy access in a loop) | 1 + N | never on a list page |
| JOIN FETCH or `@EntityGraph` | 1 | this use case needs the customers |
| Batch fetching, size 25 | 1 + N / 25 | as a safety net for all lazy loads |
| DTO projection | 1 | read-only lists and API responses |

1. The first query loads the payments. Each payment's `customer` field holds a placeholder object that knows only the customer id.
2. The loop calls `getCustomer().getName()` on the first payment. Hibernate sees that the placeholder is empty and runs a `SELECT` on `customers` for that id.
3. The same happens for every payment whose customer is not loaded yet. A customer already loaded in this transaction is reused, not fetched again.
4. With `JOIN FETCH`, the first query joins `customers` and fills every customer at once, so the loop runs no more SQL.

## Example

The payments table has 3 paid payments, each from a different customer. Hibernate's SQL log is switched on:

```java
List<Payment> paid = em.createQuery(
        "select p from Payment p where p.status = 'PAID'", Payment.class)
    .getResultList();                                   // query 1
for (Payment p : paid) {
    System.out.println(p.getCustomer().getName());      // one more query each
}
```

```text output
Hibernate: select p1_0.id,p1_0.amount,p1_0.created_at,p1_0.customer_id,p1_0.status from payments p1_0 where p1_0.status='PAID'
Hibernate: select c1_0.id,c1_0.city,c1_0.name from customers c1_0 where c1_0.id=?
Asha
Hibernate: select c1_0.id,c1_0.city,c1_0.name from customers c1_0 where c1_0.id=?
Ravi
Hibernate: select c1_0.id,c1_0.city,c1_0.name from customers c1_0 where c1_0.id=?
Meera
```

What to notice:

- Each customer `SELECT` appears right before its name: the query runs at the getter, not when the list is loaded.
- 3 payments gave 4 queries. With 100 payments from 100 customers it would be 101.
- With `join fetch p.customer` in the query, the log shows a single `select … from payments p1_0 join customers c1_0 …` and the loop runs no SQL.

The fix for a Spring Data repository, in two equivalent forms:

```java
@Query("select p from Payment p join fetch p.customer where p.status = :status")
List<Payment> findWithCustomer(@Param("status") String status);   // one query

@EntityGraph(attributePaths = "customer")       // same fetch, no JPQL
List<Payment> findByStatusOrderByCreatedAt(String status);
```

Both load the payments and their customers in one query, and only for these methods; every other query stays lazy.

## Rules and defaults

- **Detecting it:** turn on `spring.jpa.show-sql=true` (default false) or the `org.hibernate.SQL` debug log, or set `hibernate.generate_statistics=true` in a test and count statements per request.
- **Batch fetching (Hibernate 7.4):** off by default. Turn it on for all lazy loads with `hibernate.default_batch_fetch_size`, or per association with `@BatchSize`. Hibernate then loads many customers with one `where id = any(?)` query on PostgreSQL.
- **JOIN FETCH is an inner join:** payments without a customer drop out of the result. Use `LEFT JOIN FETCH` when the association can be null.
- **DTO projection:** for read-only screens, select only the columns you show into a plain class or record. No entities are tracked, so nothing is lazy.

## Not to be confused with

Lazy loading is the feature: an association loads on first access. N+1 is the result of triggering it once per row in a loop. A plain `JOIN` in JPQL only filters or sorts by the related table; a `JOIN FETCH` also fills the association with the joined rows. Rule: `JOIN` = use it in the query; `JOIN FETCH` = load it into the objects.

## Interview Qs

### How do you detect N+1 in a Spring Boot app?

Log the SQL with `spring.jpa.show-sql` or Hibernate's `org.hibernate.SQL` logger, or enable Hibernate statistics in a test, and count statements per request. A list page that repeats the same SELECT with a different id for each row is the sign.

### JOIN FETCH or batch fetching?

JOIN FETCH loads the payments and their customers in one query, for one use case. Batch fetching stays lazy but loads many keys per query, so N extra queries become about N divided by the batch size. Use JOIN FETCH where you know the need, and batch fetching as a global safety net.

### Why not just make the association EAGER?

EAGER applies to every query of that entity, even ones that never use the customer. For a JPQL query, Hibernate still loads EAGER to-one associations with extra SELECTs, so you get the same N+1, only earlier. Keep associations LAZY and fetch per use case.
