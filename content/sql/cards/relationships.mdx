## What it is

A relationship describes how many rows of one table can link to rows of another. There are three kinds. One-to-many: one customer makes many payments. One-to-one: one customer has at most one wallet. Many-to-many: a customer can claim many offers, and an offer can be claimed by many customers. Each kind is built from [foreign keys](card:keys); what changes is where the foreign key goes.

## Why it exists

A foreign key column holds one value per row, so it can point to only one parent. Put it on the wrong side and the data cannot be stored: a `payment_id` column in `customers` would allow only one payment per customer. Many-to-many does not fit in either table at all. Knowing the three patterns tells you where each link goes, so data is stored once and every link can be checked.

1. Ask, for one row on each side: "how many rows on the other side can it link to?"
2. If one side is "many" (one customer, many payments), put the foreign key in the many-side table: `payments.customer_id`.
3. If both sides are "at most one" (customer and wallet), use the same foreign key and add `UNIQUE` to it, so a second wallet for the same customer is rejected.
4. If both sides are "many" (customers and offers), create a junction table holding a foreign key to each side, one row per link. Make the pair its primary key.
5. If a table links to itself (an employee's manager is also an employee), the foreign key points to its own table.

## Example

Two new tables in the payments example. `offers(id, code)` already holds CASHBACK50 (id 1) and FESTIVE10 (id 2).

```sql
CREATE TABLE wallets (                      -- one-to-one
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL UNIQUE REFERENCES customers (id),
  balance     NUMERIC(12,2) NOT NULL
);
CREATE TABLE customer_offers (              -- many-to-many
  customer_id BIGINT REFERENCES customers (id),
  offer_id    BIGINT REFERENCES offers (id),
  claimed_on  DATE NOT NULL,
  PRIMARY KEY (customer_id, offer_id)
);
INSERT INTO wallets VALUES (1, 1, 0), (2, 1, 0);
INSERT INTO customer_offers VALUES (1, 1, '2026-10-01'), (1, 2, '2026-10-02'), (2, 1, '2026-10-03');
INSERT INTO customer_offers VALUES (1, 1, '2026-10-05');
```

```text output
CREATE TABLE
CREATE TABLE
ERROR:  duplicate key value violates unique constraint "wallets_customer_id_key"
DETAIL:  Key (customer_id)=(1) already exists.
INSERT 0 3
ERROR:  duplicate key value violates unique constraint "customer_offers_pkey"
DETAIL:  Key (customer_id, offer_id)=(1, 1) already exists.
```

What to notice:

- `UNIQUE` on `wallets.customer_id` turns one-to-many into one-to-one: the second wallet for customer 1 is rejected. The whole statement fails, so neither wallet row is stored.
- In `customer_offers`, customer 1 appears twice and offer 1 appears twice; only the pair must be new. That is how both sides get "many".
- `claimed_on` is a fact about the link itself, so it lives in the junction table, not in `customers` or `offers`.

## Rules and defaults

- **Where the foreign key goes:** always on the side that has "one parent per row". For many-to-many, neither side qualifies, so a third table holds it.
- **Lists in a column:** PostgreSQL has array columns, but its docs warn that searching inside arrays often signals a design mistake, and advise a separate table with one row per item.
- **Self-reference:** the column must allow NULL for the top of the tree, such as the CEO, who has no manager.

## Common mistakes

- **"One-to-one needs the same id in both tables, so no constraint is required."** Without `UNIQUE` (or making the foreign key the primary key), nothing stops a second wallet for the same customer, and the link silently becomes one-to-many.

## Interview Qs

### How do you model a many-to-many relationship?

With a junction table that holds a foreign key to each side, one row per link, for example `customer_offers(customer_id, offer_id)`. Make the pair its primary key so the same link cannot be stored twice. Facts about the link, such as the claim date, go in the same table.

### How do you store each employee's manager?

Add a nullable `manager_id` column that references `employees.id` in the same table. The top manager has NULL. To list an employee with their manager, join the table to itself; to walk the whole chain upwards you use a recursive query, covered in [CTEs](card:ctes).

### How do you build a one-to-one relationship?

Put a foreign key in one table and make it `UNIQUE`, or make the foreign key the primary key of the child table. Either way each parent can have at most one child row. Put it in the table that is optional, such as `wallets`, so customers without a wallet need no row.
