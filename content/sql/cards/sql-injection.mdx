## Why it exists

Apps build queries from user input. If that input is pasted into the SQL text, an attacker can read, change or delete data they should never touch.

## How it works

| Email typed by the user | SQL the database runs |
|---|---|
| `asha@example.in` | `… WHERE email = 'asha@example.in'` |
| `' OR '1'='1` (concatenated) | `… WHERE email = '' OR '1'='1'`: every row |
| `' OR '1'='1` (bound to `?`) | looks for that exact text: no row |

- A bound value can never change the query's structure, only fill a slot.
- A stored procedure is safe only if it does not build SQL from its input.

## Example

```java
// Unsafe: input becomes part of the SQL text
String bad = "SELECT * FROM users WHERE email = '" + email + "'";

// Safe: the value is bound as data
PreparedStatement ps = con.prepareStatement(
    "SELECT id, name FROM users WHERE email = ?");
ps.setString(1, email);
ResultSet rs = ps.executeQuery();

// Dynamic sort column: allowlist it, never concatenate raw input
String col = Set.of("name", "city").contains(sort) ? sort : "id";
String sql = "SELECT id, name FROM users ORDER BY " + col;
```

## Interview Qs

### How do you prevent SQL injection?

Bind every value with prepared statements or ORM parameters, and allowlist anything that cannot be a parameter. Add a least-privilege database user and validation as extra layers.

### Can a table or column name be a ? parameter?

No. Placeholders hold values only. Map the user's choice to a fixed list of allowed names, or redesign so the name is not user input.

### Is an ORM automatically safe?

Only when values go through parameters, such as `setParameter` or `:name`. A JPQL, HQL or native query built by string concatenation is as injectable as raw JDBC.
