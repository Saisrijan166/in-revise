## What it is

SQL injection is an attack in which text typed by a user ends up inside an SQL statement as code, so it changes what the query does. It happens when the app builds the SQL by joining strings: the database cannot tell which part the developer wrote and which part came from the user. A prepared statement prevents it. The SQL is written once with `?` placeholders, and each value is passed separately, so a value can fill a slot but never change the query.

## Why it exists

Apps filter by user input all the time: a payments page searches by the status the user types. If that input is pasted into the SQL text, the input `' OR '1'='1` turns the filter into "always true", and the user sees every customer's payments. Other inputs can change or delete data. Prepared statements remove the problem at its root: the query's structure is fixed before any input arrives.

## How it works

| Status typed by the user | SQL the database runs |
|---|---|
| `PAID` | `… WHERE status = 'PAID'` |
| `' OR '1'='1` (joined into the text) | `… WHERE status = '' OR '1'='1'`: every row |
| `' OR '1'='1` (bound to `?`) | looks for a status equal to that exact text: no row |

1. You write the SQL once, with a `?` wherever a value goes.
2. `prepareStatement(sql)` fixes the structure: which table, which columns, which condition.
3. `setString(1, input)` attaches the input to slot 1 as a typed value.
4. On `executeQuery()` the driver passes the input as data, never as SQL code, so the database cannot run it.
5. The database compares `status` with the whole input text. No payment has that status, so no row matches.

So the key is that the SQL code is fixed before the data arrives.

## Example

The same attack against the payments table, first concatenated, then bound. `count()` is a small helper that counts the rows of a result.

```java
String status = "' OR '1'='1";                 // typed into the search box

// Unsafe: the input becomes part of the SQL text
String sql = "SELECT id, amount FROM payments WHERE status = '" + status + "'";
System.out.println(sql);
ResultSet bad = con.createStatement().executeQuery(sql);

// Safe: the SQL is fixed; the input is bound to the ? slot as a value
PreparedStatement ps = con.prepareStatement(
    "SELECT id, amount FROM payments WHERE status = ?");
ps.setString(1, status);
ResultSet good = ps.executeQuery();
System.out.println(count(bad) + " rows vs " + count(good) + " rows");
```

```text output
SELECT id, amount FROM payments WHERE status = '' OR '1'='1'
5 rows vs 0 rows
```

What to notice:

- The printed SQL shows the attack: the input's first quote closes the string, and `OR '1'='1'` is true for every row, so all 5 payments come back.
- The prepared version returns 0 rows, because no payment has the status `' OR '1'='1`. It returns the 3 paid payments when the input is `PAID`.
- The result is the same on PostgreSQL 18 and MySQL 9.7: injection depends on how the app builds SQL, not on the database.

## Rules and defaults

- **Every outside value:** goes through a placeholder: `?` with `setString` or `setLong` in JDBC, `:name` with `setParameter` in JPQL and HQL.
- **Names cannot be parameters:** a table name, a column name or `ASC`/`DESC` cannot be a `?`. In PostgreSQL `FROM ?` is a syntax error, and `ORDER BY ?` sorts by a constant text, not by the column. Pick names from an allowlist in code, such as `Set.of("amount", "created_at")`.
- **Stored procedures:** are safe only if they do not build dynamic SQL from their inputs.
- **Least privilege:** the app's database user gets only the rights it needs and never admin rights, so a successful injection can do less.
- **Error messages:** log database errors on the server and show users a generic message. Raw SQL errors reveal table and column names that help an attacker.

## Not to be confused with

A `Statement` runs a complete SQL string that your code built, values included. A `PreparedStatement` runs fixed SQL with `?` slots, and the values are bound separately. Input validation checks that a value looks right, such as a status being one of three words; it is a useful extra check, not a replacement. Rule: a value from outside always goes into a `?`; validation only adds a second wall.

## Common mistakes

- **"Using the PreparedStatement class makes the query safe."** Only the placeholders make it safe. SQL concatenated before `prepareStatement(...)` is as injectable as with `Statement`.
- **"An ORM protects me automatically."** Hibernate's generated SQL is parameterised, but a JPQL or native query you build with `+` is not. OWASP calls this HQL injection.

## Interview Qs

### How do you prevent SQL injection?

Bind every value with prepared statements or ORM parameters, never by joining strings. Pick table names, column names and sort directions from an allowlist in code. As extra layers, give the app a least-privilege database user, validate input, and never show raw database errors to users.

### Can a table or column name be a ? parameter?

No. Placeholders hold values only; the query's structure, including names, must be fixed when it is prepared. Map the user's choice to a fixed list of allowed names in code, with a safe default for anything else.

### Why is escaping not enough?

Escaping tries to neutralise special characters inside the SQL text, and the rules differ between databases and settings. One missed case reopens the hole. OWASP strongly discourages relying on it. Parameters avoid the problem, because the value never becomes part of the SQL text at all.
