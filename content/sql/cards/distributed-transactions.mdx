## What it is

A distributed transaction is one business action that must change data in more than one database, or in a database and a message broker, as one unit. A local [transaction](card:transactions) cannot do it, because COMMIT covers only one database. This happens with [shards](card:sharding), and with microservices, where each service owns its own database. There are two common answers: two-phase commit (2PC) and the saga.

## Why it exists

A refund changes the payments database (the payment becomes REFUNDED) and the wallet service's database (the customer is credited). If the first commits and the wallet service then crashes, the payment says "refunded" but no money came back, and no single ROLLBACK can fix both databases. You need either one commit across both, or a planned way to undo the finished part.

## How it works

<Compare id="two-phase-commit-vs-saga" />

Two-phase commit, run by a coordinator (a transaction manager):

1. Each database does its part of the work but does not commit yet.
2. Prepare phase: the coordinator asks every database to prepare. Each one stores its changes durably, keeps its locks and answers yes or no.
3. Commit phase: if all said yes, the coordinator tells all of them to commit; if any said no, it tells all of them to roll back.

A saga, for the same refund:

1. The payments service commits its local step (payment REFUNDED) and sends a message to the wallet service.
2. The wallet service commits its local step (customer credited).
3. If step 2 fails, the saga runs a compensating transaction for each step already committed, such as setting the payment back to PAID.

So the key is: 2PC holds everything locked until one decision; a saga never waits, but must undo by hand.

## Example

A saga step must commit its data and send a message. Writing both into one database, with an outbox table, makes them one local transaction.

```sql
-- outbox(id bigserial, aggregate_id, event_type, payload jsonb, sent_at)
BEGIN;
INSERT INTO payments (id, customer_id, amount, status)
VALUES (42, 7, 999.00, 'PAID');
INSERT INTO outbox (aggregate_id, event_type, payload)
VALUES (42, 'PaymentPaid', '{"paymentId": 42, "amount": 999.00}');
COMMIT;   -- both rows or neither

-- the relay later reads unsent events and publishes them
SELECT id, event_type, payload FROM outbox WHERE sent_at IS NULL ORDER BY id;
```

```text output
 id | event_type  |               payload
----+-------------+-------------------------------------
  1 | PaymentPaid | {"amount": 999.00, "paymentId": 42}
(1 row)
```

What to notice:

- The payment and its event commit together, so the event exists exactly when the payment does. No 2PC with the message broker is needed.
- Without the outbox, the app would commit the payment and then publish to the broker. A crash between the two loses the event.
- The relay can crash after publishing but before it sets `sent_at`, so it may publish the same event twice. Consumers must be [idempotent](term:idempotent-write): handling an event twice has the same effect as once.

## Rules and defaults

- **PostgreSQL 2PC:** `PREPARE TRANSACTION 'id'`, later `COMMIT PREPARED 'id'` or `ROLLBACK PREPARED 'id'`. It is off by default: `max_prepared_transactions = 0` in PostgreSQL 18, and PREPARE fails with "prepared transactions are disabled".
- **Meant for transaction managers:** the PostgreSQL docs say PREPARE TRANSACTION is not for application code.
- **Prepared work keeps its locks:** a forgotten prepared transaction blocks other sessions and holds back VACUUM until someone finishes it.
- **MySQL 2PC:** XA transactions (`XA START`, `XA END`, `XA PREPARE`, `XA COMMIT`); InnoDB supports them.
- **Saga styles:** in [choreography](card:choreography-saga), each service reacts to the previous step's event; in [orchestration](card:orchestration-saga), one orchestrator tells each service what to do next.
- **No isolation in a saga:** between steps, other requests can see a payment marked REFUNDED whose credit has not happened yet. Design for it, for example with a `PENDING` status.

## Common mistakes

- **"A compensation is a rollback."** A rollback erases uncommitted work. A compensation is a new, committed step that reverses an earlier effect, such as a refund that reverses a charge, and it can itself fail and need a retry.

## Interview Qs

### In 2PC, what if the coordinator crashes after everyone prepared?

The participants stay prepared and keep their locks. They cannot commit or roll back on their own, because they do not know the decision. They wait until the coordinator recovers, or an operator finishes each one with COMMIT PREPARED or ROLLBACK PREPARED.

### Why do microservices use sagas instead of 2PC?

Each service owns its database, and the databases or the message broker may not support 2PC. 2PC also adds round trips and holds locks across services, so one slow service blocks the others. A saga needs only local transactions and messages.

### What is the transactional outbox, and why use it?

An outbox is a table where a service saves the events it must publish, in the same local transaction as its data change. A separate relay reads unsent rows and publishes them. It solves the "commit, then crash before publishing" problem without 2PC.
