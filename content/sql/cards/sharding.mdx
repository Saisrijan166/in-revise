## What it is

Sharding is splitting the rows of a table across several separate database servers. Each server, called a shard, has the same tables but holds a different slice of the rows. A column called the shard key, such as `customer_id`, decides which shard owns each row. It is the same idea as [partitioning](card:partitioning), but the pieces live on different machines.

## Why it exists

[Replicas](card:replication) share the reads, but every write still goes to one primary on one machine. When the payment system takes more writes than the biggest server can handle, or stores more data than one server can hold, more replicas do not help. With sharding, each server takes only part of the writes and the data, so four shards can take about four times the writes, if the key spreads the load evenly.

## How it works

1. You choose the shard key, here `customer_id`, and a rule that maps a key to a shard: by [range](card:range-sharding), by [hash](card:hash-sharding), or through a [lookup table](card:directory-sharding).
2. On each write, a router computes the shard from the key and sends the statement only to that server. The router can be your app, a proxy, or a tool such as Vitess or Citus.
3. A read that includes the key, such as one customer's payment history, also goes to one shard.
4. A read without the key, such as today's total, goes to every shard, and the router merges the answers. The slowest shard sets the response time.
5. When the shards fill up, you add servers and move part of the rows to them. This is called resharding, and it is slow work that must not lose writes.

## Example

The payment service routes each customer by `customer_id` modulo the number of shards, the simplest hash rule. The program shows which customers move when a fifth shard is added.

```java
public class ShardRouter {
    static int shardFor(long customerId, int shards) {
        return (int) Math.floorMod(customerId, (long) shards);  // 0 to shards - 1, even for a negative id
    }

    public static void main(String[] args) {
        System.out.println("customer  4 shards  5 shards");
        for (long id : new long[] {10, 11, 20, 21}) {
            int before = shardFor(id, 4), after = shardFor(id, 5);
            System.out.printf("%-9d %-9d %d%s%n", id, before, after,
                    before == after ? "" : "  moves");
        }
    }
}
```

```text output
customer  4 shards  5 shards
10        2         0  moves
11        3         1  moves
20        0         0
21        1         1
```

What to notice:

- `Math.floorMod` takes the sign of the divisor, so with 4 shards it always returns 0 to 3. Plain `%` would return a negative number for a negative id.
- All payments of customer 10 live on shard 2, so their history is a one-shard query. Refunds should use the same key, so a payment and its refunds can be joined on one shard.
- Going from 4 to 5 shards moves customers 10 and 11. With modulo routing, most keys move whenever the count changes. [Consistent hashing](card:consistent-hashing) moves only a small share.

## Rules and defaults

- **Someone must route:** the app, a proxy or a sharding tool decides which server gets each query. Vitess does this for MySQL; Citus for PostgreSQL.
- **Keep related rows together:** shard every table a request joins (payments, refunds) by the same key, so those joins stay on one shard.
- **A good shard key:** many distinct values, spread evenly, present in most queries and never updated. A `status` column with three values is a bad key: at most three shards would ever get rows.
- **Unique ids:** an auto-increment counter on each shard starts at 1 on every shard, so ids collide. Use [UUIDs or another global scheme](card:id-generation).
- **Each shard is a full database:** it needs its own replicas, backups and monitoring.

## Not to be confused with

- [Partitioning](compare:partitioning-vs-sharding) splits one table into pieces **inside one server**; sharding spreads rows **over many servers**.
- [Replication](compare:replication-vs-sharding) **copies** the same data to every server; sharding **splits** different rows across servers.

Rule: partitioning = one server, replication = same data everywhere, sharding = different rows on different servers.

## Interview Qs

### How do you choose a shard key?

Pick a value that most queries filter on, with many distinct values, spread evenly and never changed, such as `customer_id` or a tenant id. Avoid ever-growing ids or timestamps with range routing, because all new rows then hit one shard.

### How do you join or run a transaction across shards?

Avoid it by design: shard related tables by the same key, so a customer's rows stay on one shard. Otherwise query each shard in parallel and merge the results in the app, and use a [saga](card:distributed-transactions) instead of one transaction.

### What is a hot shard, and how do you fix it?

A hot shard gets far more traffic than the others, for example because one huge tenant or all new ids map to it. Fix it with a better key, such as a hash of a high-cardinality column, or by splitting the busy range onto its own shard.
