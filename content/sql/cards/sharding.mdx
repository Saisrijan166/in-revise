## Why it exists

Replicas spread reads, but every write still hits one primary on one machine. When writes or data outgrow the biggest server, the data itself must be split.

## How it works

<Compare id="replication-vs-sharding" />

- Routing: [range](card:range-sharding), [hash](card:hash-sharding) or a [lookup directory](card:directory-sharding).
- A query without the shard key fans out to every shard; the slowest shard sets the latency.
- Shard last, after the cheaper steps of the [scaling ladder](card:scaling-ladder).

## Example

Plain `hash mod N` moves most keys when a shard is added; [consistent hashing](card:consistent-hashing) moves only a small share.

```text
user_id   % 4 (4 shards)   % 5 (5 shards)
10        2                0    moves
11        3                1    moves
20        0                0    stays
```

## Interview Qs

### How do you choose a shard key?

Pick a value most queries filter on, with many distinct values, spread evenly and rarely changed, such as `user_id` or a tenant id. Avoid ever-growing ids or timestamps with range routing: new rows all hit one shard.

### How do you join or run a transaction across shards?

Avoid it by design: keep related rows on one shard with the same key. Otherwise query each shard in parallel and merge in the app, and use a [saga](card:distributed-transactions) instead of one transaction.
