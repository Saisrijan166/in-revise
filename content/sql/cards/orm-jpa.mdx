## Why it exists

Hand-written JDBC for every insert, update and row-to-object mapping is long and repetitive. An ORM does the mapping and generates the routine SQL.

## How it works

<Mermaid
  alt="A request flows from the controller to the service, then to a repository, which calls Hibernate as the JPA provider. Hibernate sends SQL through JDBC and a connection pool to the database, and rows come back as objects."
  chart={`flowchart LR
  C[Controller] --> S[Service]
  S --> R[Repository]
  R --> H["Hibernate (JPA)"]
  H --> J["JDBC + pool"]
  J --> D[(Database)]`}
/>

- Spring Data JPA writes the repository; a method name such as `findByStatus` becomes a query.
- Hibernate still sends plain SQL through JDBC and the [connection pool](card:connection-pooling).

## Example

```java
@Entity
@Table(name = "orders")
class CustomerOrder {
    @Id @GeneratedValue Long id;
    BigDecimal amount; String status;
    @ManyToOne(fetch = FetchType.LAZY)       // the default would be EAGER
    User user;
}

interface OrderRepository extends JpaRepository<CustomerOrder, Long> {
    List<CustomerOrder> findByStatus(String status); // query derived from the name
}
```

## Interview Qs

### Why learn SQL if you use an ORM?

The ORM writes SQL, but you own its speed. You read the generated SQL, spot [N+1 queries](card:n-plus-one) and missing indexes, and write native SQL for reports, bulk updates and window functions.

### Which fetch type should associations use?

Hibernate's guide says almost all associations should be LAZY, because EAGER defaults load far more than a use case needs. Fetch what each use case needs with JOIN FETCH or an entity graph.

### What is the persistence context?

The set of entities one EntityManager manages, with exactly one object per row identity. Changes to managed entities are written to the database at flush or commit, without an explicit save call.
