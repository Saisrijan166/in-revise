## What it is

An ORM (object-relational mapping) library maps your classes to tables: one object stands for one row, and its fields for the columns. You load and save objects, and the library writes the SQL. In Java the standard is JPA (Jakarta Persistence 3.2), a specification of annotations and interfaces with no engine of its own. Hibernate is the most used implementation, and Spring Data JPA adds ready-made repositories on top.

## Why it exists

With plain JDBC, every query means writing the SQL, setting each parameter and copying each column of the `ResultSet` into a field by hand. For a dozen tables that is hundreds of near-identical lines, and renaming a column breaks them one by one. With an ORM you describe the mapping once, on the class, and the library generates the routine `SELECT`, `INSERT`, `UPDATE` and `DELETE` statements. Under the hood it still sends SQL through JDBC and the [connection pool](card:connection-pooling).

Follow one call, `payments.findById(101L)`:

1. The service calls the repository interface. Spring Data wrote its implementation at startup.
2. The repository calls `find` on JPA's `EntityManager`, the interface that loads and saves entities. Hibernate implements it.
3. Hibernate builds the SQL from the mapping, `select … from payments where id=?`, and runs it through JDBC on a pooled connection.
4. It copies the row into a new `Payment` object and keeps it in the persistence context: the set of objects it tracks in this transaction, one per row.
5. If the code changes a field of that object, Hibernate notices at flush, just before commit, and writes the `UPDATE` itself. This is called dirty checking.

## Example

The `payments` table mapped as an entity, with its foreign key to `customers` as a [many-to-one relationship](card:relationships):

```java
@Entity                                   // one Payment object = one row
@Table(name = "payments")
public class Payment {
    @Id Long id;                          // the primary key
    BigDecimal amount;
    String status;                        // PAID, FAILED or PENDING
    @Column(name = "created_at") LocalDateTime createdAt;

    @ManyToOne(fetch = FetchType.LAZY)    // the JPA default would be EAGER
    @JoinColumn(name = "customer_id")     // the foreign key column
    Customer customer;
}
```

```java
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    List<Payment> findByStatus(String status);  // query made from the method name
}
```

What to notice:

- `@Table` and `@Column` give the table or column name when it differs from the class or field name. Spring Boot's default naming already maps `createdAt` to `created_at`, but not `Payment` to `payments`.
- `fetch = FetchType.LAZY` means the customer is loaded only when code first reads it. Remove it and every payment query also loads its customer, needed or not.
- `findByStatus` has no body. Spring Data reads the method name and generates `select … from payments where status = ?`.
- `JpaRepository` already gives `findById`, `save`, `findAll` and `delete`, so routine data access needs no SQL.

## Rules and defaults

- **Entity class (JPA 3.2):** needs `@Entity`, an `@Id`, and a public or protected constructor with no parameters. It must not be final, so a Java record cannot be an entity.
- **Fetch defaults (JPA 3.2):** `@ManyToOne` and `@OneToOne` are EAGER; `@OneToMany` and `@ManyToMany` are LAZY.
- **EAGER is a requirement, LAZY is a hint:** the provider must load an EAGER association, and may load a LAZY one early. Hibernate's guide says almost all associations should be LAZY.
- **Changes need a transaction:** dirty checking writes changes only when a transaction flushes; outside one, edits to an object are not saved.

## Not to be confused with

JDBC is Java's low-level API: you write the SQL and copy the results yourself. JPA is the standard that says how mapping, the `EntityManager` and JPQL, its SQL-like query language over entities, must behave. Hibernate is a library that implements JPA and adds features of its own. Spring Data JPA writes repository classes for you on top of JPA. Rule: JDBC = the wire; JPA = the rules; Hibernate = the engine; Spring Data JPA = the repository writer.

## Common mistakes

- **"@ManyToOne is lazy by default."** In JPA it is EAGER. Write `fetch = FetchType.LAZY` on every to-one association, then fetch what each use case needs, as [N+1 queries](card:n-plus-one) shows next.

## Interview Qs

### Why learn SQL if you use an ORM?

The ORM writes SQL, but you own its speed. You read the generated SQL, spot [N+1 queries](card:n-plus-one) and missing indexes, and check plans with EXPLAIN. Reports, bulk updates and window functions are often clearer and faster as native SQL.

### What is the difference between JPA and Hibernate?

JPA (Jakarta Persistence) is a specification: annotations such as `@Entity`, the `EntityManager` interface and the JPQL query language. Hibernate is an implementation that does the work behind those interfaces and adds extras such as batch fetching. Code written against JPA can switch providers more easily.

### What is the persistence context?

The set of entities one `EntityManager` tracks, usually for one transaction, with exactly one object per row. Loading the same row twice returns the same object without new SQL. Changes to tracked entities are written at flush, before commit, without an explicit save call.
