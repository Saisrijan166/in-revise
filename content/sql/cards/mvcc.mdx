## Why it exists

With only locks, a long report blocks every update, and every update blocks readers. Keeping old versions lets both run at once.

## How it works

  T2([T2: UPDATE]) --> V2[v2: balance 500]
  V2 -. "older version" .-> V1[v1: balance 1000]

- When the snapshot is taken depends on the level: see [READ COMMITTED vs REPEATABLE READ](compare:read-committed-vs-repeatable-read).

## Example

```sql
-- Session A
BEGIN;
UPDATE accounts SET balance = 500 WHERE id = 1;   -- new version, not committed
-- Session B: not blocked, sees the old version
SELECT balance FROM accounts WHERE id = 1;        -- 1000
-- Session B: a second writer on the same row waits for A
UPDATE accounts SET balance = 900 WHERE id = 1;
```

## Interview Qs

### What is MVCC?

Multi-version concurrency control: a write creates a new version of the row, and each transaction reads the versions visible in its snapshot. Readers and writers do not block each other.

### Why does PostgreSQL need VACUUM?

An UPDATE or DELETE leaves the old version in the table. VACUUM removes dead versions so the space is reused, and freezes old rows to prevent transaction ID wraparound.

### Why is a long-running transaction harmful under MVCC?

Its snapshot keeps old versions alive, so VACUUM or purge cannot remove them: tables bloat in PostgreSQL and the undo history grows in InnoDB.
