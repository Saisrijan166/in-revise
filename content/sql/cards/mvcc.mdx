## What it is

MVCC (multi-version concurrency control) is how PostgreSQL and MySQL InnoDB give [isolation](card:isolation-levels) without making readers wait. When a row is updated, the database keeps the old version and adds a new one instead of overwriting it. Each transaction reads through a snapshot: a record of which committed changes it may see. So a reader keeps seeing the old version while a writer works on the new one.

## Why it exists

The older way to isolate transactions is with locks alone: a writer locks the row, and every reader waits until it commits. Then a twenty-minute report blocks every payment update on the rows it reads, and every busy row stalls the reports. With versions, a reader takes the version its snapshot allows and never waits for the writer, so reads and writes run side by side.

## How it works

1. Transaction A updates payment 2 to `PAID`. The database writes a new version of the row; the old `PENDING` version stays.
2. Transaction B runs a plain SELECT. Its snapshot does not include A's uncommitted change, so it reads `PENDING` at once, without waiting.
3. B tries to UPDATE the same row. One row cannot take two changes at once, so B waits for A's row lock.
4. A commits. New snapshots now see `PAID`, and at READ COMMITTED B's UPDATE goes ahead on the new version.
5. When no open snapshot needs the old version any more, cleanup removes it: VACUUM in PostgreSQL, purge in InnoDB.

When a snapshot is taken depends on the level: see [READ COMMITTED vs REPEATABLE READ](compare:read-committed-vs-repeatable-read).

## Example

Two sessions on payment 2, run on PostgreSQL 18 and on MySQL 9.7 with the same result:

```sql
-- Session A
BEGIN;
UPDATE payments SET status = 'PAID' WHERE id = 2;      -- new version, not committed
-- Session B: not blocked, reads the old version
SELECT status FROM payments WHERE id = 2;             -- PENDING
-- Session B: a second writer on the same row
UPDATE payments SET status = 'FAILED' WHERE id = 2;   -- waits until A commits
```

What to notice:

- B's SELECT answered at once with `PENDING`, even though A had changed the row. That is MVCC: B read the old version.
- B's UPDATE waited until A committed (about two seconds in the test run), then ran. Readers skip the wait; a second writer does not.
- If A had rolled back instead, its new version would be thrown away, and B's SELECT would never have seen it.

## Rules and defaults

- **PostgreSQL storage:** old versions stay in the table as dead tuples. VACUUM marks their space reusable; the autovacuum daemon runs it automatically and is on by default.
- **MySQL InnoDB storage:** the row is changed in place, and the old values go to the undo log. A read that needs an old version rebuilds it from there; purge removes undo records nobody needs.
- **Long transactions:** an old snapshot keeps old versions alive, so cleanup cannot remove them. Commit reports and batch jobs promptly.
- **Wraparound (PostgreSQL):** transaction IDs are 32-bit, so each table must be vacuumed before about two billion transactions pass. Autovacuum does this even when it is turned off.

## Interview Qs

### What is MVCC?

Multi-version concurrency control: a write creates a new version of the row, and each transaction reads the versions visible in its snapshot. Readers and writers do not block each other. Two writers on the same row still do, because the second waits for the first one's row lock.

### Why does PostgreSQL need VACUUM?

An UPDATE or DELETE leaves the old row version in the table. VACUUM marks the space of dead versions reusable, so the table does not keep growing. It also freezes old rows to prevent transaction ID wraparound, which is why autovacuum must keep running.

### Why is a long-running transaction harmful under MVCC?

Its snapshot keeps old versions alive, so VACUUM or purge cannot remove them. Tables bloat in PostgreSQL and the undo history grows in InnoDB. The transaction also holds any locks it took until it ends.
