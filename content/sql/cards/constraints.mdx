## Why it exists

Many apps and scripts write to one database, and each can have bugs. Constraints reject bad rows at the source, in one place.

## How it works

| Rule | Rejects | Example |
|---|---|---|
| `PRIMARY KEY` | duplicate or NULL ids | `id` |
| `FOREIGN KEY` | links to missing parents | `user_id REFERENCES users` |
| `UNIQUE` | repeated values | `email`, or `(user_id, sku)` |
| `NOT NULL` | missing values | `name` |
| `CHECK` | rows that fail a condition | `amount > 0` |
| `DEFAULT` | nothing: fills omitted columns | `status DEFAULT 'NEW'` |

- `ON DELETE` actions: `CASCADE` deletes the children; `SET NULL` clears the link; `RESTRICT` and `NO ACTION` refuse.
- PostgreSQL can defer `NO ACTION` to commit; `RESTRICT` never waits. InnoDB treats them the same and rejects `SET DEFAULT`.

## Example

```sql
CREATE TABLE orders (
  id         BIGINT PRIMARY KEY,
  user_id    BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  amount     NUMERIC(10,2) NOT NULL CHECK (amount > 0),
  status     TEXT NOT NULL DEFAULT 'NEW',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
INSERT INTO orders (id, user_id, amount) VALUES (1, 1, 0);
-- fails the CHECK; with 500 it works and status becomes 'NEW'
```

## Interview Qs

### What does ON DELETE CASCADE do, and when is it a bad idea?

Deleting a parent also deletes every row that references it. Good when the child is part of the parent (order items of an order). Bad between independent things, where one delete could silently remove much more data.

### What is the difference between RESTRICT and NO ACTION?

Both refuse to delete a parent that still has children. In PostgreSQL, NO ACTION can be checked at commit if the constraint is deferred; RESTRICT checks at once. In MySQL InnoDB they are identical.
