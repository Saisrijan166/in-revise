## What it is

An aggregate function takes many rows and returns one value: `COUNT` counts them, `SUM` adds a column, `AVG` averages it, and `MIN` and `MAX` find the smallest and largest. `GROUP BY customer_id` splits the rows into groups, one group per customer, and runs the aggregates once per group, so the result has one row per group. `HAVING` is a filter on those groups, written after GROUP BY.

## Why it exists

"Total paid per customer" is a typical report. Without GROUP BY you would run one SUM query per customer, or load every payment into Java and add them up yourself. GROUP BY answers it in one query, and the database sends back one row per customer instead of every payment.

## How it works

<Mermaid
  alt="Six payment rows go through WHERE, which keeps the four PAID ones. GROUP BY puts them into one group per customer. Aggregates compute a count and a sum per group. HAVING keeps only the groups whose sum is above 1000, which leaves customer 1 with a total of 1300."
  chart={`flowchart LR
  P[6 payment rows] --> W[WHERE status = PAID: 4 rows]
  W --> G[GROUP BY customer_id: 3 groups]
  G --> A[COUNT, SUM per group]
  A --> H[HAVING SUM > 1000: 1 group]`}
/>

1. `FROM payments` reads all six rows.
2. `WHERE status = 'PAID'` removes single rows; four paid payments remain.
3. `GROUP BY customer_id` puts the rows with the same customer_id into one group: customer 1 has two rows, customers 2 and 3 have one each.
4. The aggregates run once per group: customer 1 gets a count of 2 and a sum of 1300.
5. `HAVING SUM(amount) > 1000` drops whole groups; only customer 1 is left.
6. The SELECT list outputs one row for each remaining group.

So the key is: WHERE works on rows, HAVING works on groups.

## Example

Customers who have paid more than 1000 in total. Customer 1 paid 500 and 800; customer 2 paid 900 and has one FAILED payment; customer 3 paid 800 and has one PENDING payment.

```sql
SELECT customer_id, COUNT(*) AS paid_count, SUM(amount) AS paid_total
FROM payments
WHERE status = 'PAID'
GROUP BY customer_id
HAVING SUM(amount) > 1000
ORDER BY customer_id;
```

```text output
 customer_id | paid_count | paid_total
-------------+------------+------------
           1 |          2 |    1300.00
(1 row)
```

What to notice:

- `WHERE status = 'PAID'` runs before grouping, so the FAILED and PENDING payments are never counted or added.
- `HAVING SUM(amount) > 1000` is the only place this condition can go; in WHERE it would be an error, because no sums exist yet.
- `ORDER BY customer_id` is needed for a fixed order. GROUP BY does not sort the output in PostgreSQL 18 or MySQL 9.7.
- The result is the same in both databases.

## Rules and defaults

- **The select rule:** a selected column must appear in GROUP BY, sit inside an aggregate, or depend on the grouped key. Grouping by a primary key lets you select that row's other columns, in both PostgreSQL 18 and MySQL 9.7.
- **COUNT forms:** a column holding 10, 10 and NULL gives `COUNT(*)` = 3, `COUNT(col)` = 2 and `COUNT(DISTINCT col)` = 1.
- **NULL group:** rows whose grouped column is NULL form one group together, even though `NULL = NULL` is not true ([NULL](card:null-handling)); Meena's NULL city becomes its own group.
- **HAVING without GROUP BY:** the whole result is treated as one group, so `HAVING COUNT(*) > 3` returns one row or none.

## Not to be confused with

- **WHERE and HAVING:** WHERE tests single rows before any grouping; HAVING tests groups after the aggregates exist. Rule: plain column conditions in WHERE, aggregate conditions in HAVING.
- **GROUP BY and PARTITION BY:** GROUP BY folds each group into one output row. PARTITION BY, used with window functions, keeps every row and puts its group's total beside it. Rule: one row per group = GROUP BY; every row plus its group's number = PARTITION BY. You will see it in [Window functions](card:window-functions).

## Interview Qs

### COUNT(*) vs COUNT(column)?

COUNT(*) counts every row. COUNT(column) counts only the rows where that column is not NULL. With four customers, one of whom has a NULL city, COUNT(*) is 4 and COUNT(city) is 3. They give the same answer only when the column has no NULLs.

### Why does SELECT name, city, COUNT(*) FROM customers GROUP BY city fail?

The Pune group holds two customers with different names, so the database cannot pick one name for the group's single row. PostgreSQL and MySQL both reject it. Either group by name too, or wrap name in an aggregate, such as MIN(name).

### Can HAVING use a column that is not aggregated?

Yes, if the column is in GROUP BY, for example HAVING city = 'Pune'. But that condition tests single rows, so it belongs in WHERE, which removes the rows before grouping and saves work. Keep HAVING for conditions on aggregates.
