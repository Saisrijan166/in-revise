## What it is

Container **orchestration** is software that runs containers across a group of machines, called a **cluster**, and keeps them in the state you asked for. You declare "three copies of payment-service:1.4.0", and the orchestrator decides which machine (a **node**) runs each copy, replaces copies that fail, and rolls out new versions. Kubernetes is the most used orchestrator; Docker's own is Swarm mode.

## Why it exists

With `docker run` or [Compose](card:docker-compose), everything runs on one server. A restart policy brings back a crashed container, but if the server dies, the payment service dies with it, and adding capacity means a bigger server. An orchestrator spreads copies over many nodes, so losing one node only moves its containers, and scaling out means adding nodes.

## How it works

<Compare id="docker-vs-compose-vs-kubernetes" />

1. You build the image with Docker and push it to a registry, exactly as before.
2. You describe the desired state to Kubernetes, for example a Deployment with three replicas of that image.
3. The scheduler places the Pods on nodes. On each node the kubelet asks a container runtime, through the Container Runtime Interface (CRI), to pull the image and start the containers.
4. Controllers keep comparing the actual state with the desired one: when a Pod or a node fails, they create replacement Pods elsewhere.

So the key is: Docker builds the image; the orchestrator decides where and how many copies run.

## Rules and defaults

- **Runtimes:** since Kubernetes 1.24 the kubelet has no built-in Docker Engine support (dockershim). Nodes use containerd or CRI-O, or Docker Engine through the `cri-dockerd` adapter.
- **Images:** the dockershim removal FAQ confirms that images produced by `docker build` work with all CRI runtimes.
- **Compose in production:** possible on a single server, with production settings in an extra Compose file and a restart policy such as `restart: always`.
- **Swarm mode:** built into Docker Engine; it turns several Docker hosts into one cluster and can run Compose-style stacks.

## Not to be confused with

A container is one running process with its own filesystem. A [Pod](https://kubernetes.io/docs/concepts/workloads/pods/) is Kubernetes' wrapper around one or more containers that share one network address and can share volumes; Kubernetes schedules Pods, never bare containers. Rule: Docker runs containers; Kubernetes runs Pods, which contain containers.

## Interview Qs

### Does Kubernetes replace Docker?

No. Docker builds images and runs containers on one host; Kubernetes orchestrates containers across nodes. Since 1.24 Kubernetes no longer talks to Docker Engine directly (dockershim was removed), but images built with Docker still run unchanged, and Docker remains a common tool for building them.

### Can Kubernetes run without Docker?

Yes. Each node needs a container runtime that implements the CRI, such as containerd or CRI-O. Docker Engine can still serve as the runtime only through the `cri-dockerd` adapter.

### When is Compose enough, and when do you need Kubernetes?

Compose is enough for local development, CI tests and an app that fits on one server, where a short outage on a server failure is acceptable. I need Kubernetes when the app must survive a machine failure, scale across machines, or roll out updates without downtime.
