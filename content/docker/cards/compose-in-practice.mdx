## Why it exists

Each developer needs the same stack with small local changes: an image tag, a port, an admin UI. Editing the shared file breaks it for others.

## How it works

| Need | Use |
|---|---|
| A different image tag on my machine | `${PAYMENT_TAG}` in compose.yaml, value in `.env` |
| Dev-only ports or debug flags | `compose.override.yaml`, read automatically |
| An optional DB admin UI | `profiles: [debug]`, then `docker compose --profile debug up` |
| Rebuild or refresh on save | `develop.watch` rules, then `docker compose up --watch` |
| Three copies of one service | `docker compose up --scale payment-service=3` |

- Spring Boot 4.1 with `spring-boot-docker-compose`: `docker compose up` at app start, `stop` at shutdown, skipped in tests by default.

## Example

```yaml
services:
  payment-service:
    image: payment-service:${PAYMENT_TAG}   # value from .env
    env_file: payment.env                 # vars go into the container
  adminer:
    image: adminer
    profiles: [debug]                     # only with --profile debug
```

`PAYMENT_TAG=1.5.0` in `.env` gives `payment-service:1.5.0`; `SPRING_PROFILES_ACTIVE=dev` goes in `payment.env`.

## Interview Qs

### What is the difference between .env and env_file?

`.env` supplies values for `${VAR}` placeholders when Compose reads compose.yaml. `env_file` loads a file's variables into one service's containers. A `.env` value reaches a container only if `environment` or `env_file` uses it.

### How do you keep one Compose setup for dev and other environments?

Shared settings stay in compose.yaml; dev extras go in compose.override.yaml. Another environment uses `-f compose.yaml -f compose.prod.yaml`.

### How does Spring Boot work with Docker Compose?

At startup it finds compose.yaml, runs `docker compose up` and creates service connections for supported images, which win over datasource properties. If the stack already runs, it just connects.
