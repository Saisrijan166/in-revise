## What it is

These are the Compose features a team uses every day so that one shared `compose.yaml` fits every laptop. A `.env` file holds local values that Compose puts into `${VAR}` placeholders in the file, which is called **interpolation**. An **override file**, `compose.override.yaml`, adds settings on top of the shared file. A **profile** marks a service as optional, so it starts only when asked for.

## Why it exists

Each developer needs the same stack with small local changes: another image tag, a debug log level, a database admin UI. If everyone edits the shared `compose.yaml` for that, the changes collide in Git and break CI. These features keep the shared file stable and move the personal or optional parts beside it.

## How it works

<Mermaid
  alt="Compose builds the final model in order: it reads compose.yaml, merges compose.override.yaml on top, fills the ${VAR} placeholders from the shell and the .env file, removes services whose profile is not active, and then creates the containers with their environment and env_file variables."
  chart={`flowchart LR
  B[compose.yaml] --> M[merge compose.override.yaml]
  M --> I["fill VAR values: shell, then .env"]
  I --> P[drop inactive profiles]
  P --> C[containers get environment and env_file]`}
/>

1. Compose reads `compose.yaml`, then `compose.override.yaml` if it exists, and merges them. Single values and maps from the later file win; lists are appended.
2. It fills every `${VAR}` placeholder. A variable set in your shell wins; otherwise the value comes from `.env` in the project folder.
3. It drops services whose profiles are not active. A service with no `profiles` is always active.
4. It creates the containers. Each container gets only the variables listed under `environment:` or loaded with `env_file:`, nothing else from `.env`.

So the key is: `.env` changes the **file**; `environment` and `env_file` change the **container**.

## Example

The shared file uses a placeholder, an env file and a profile; `.env` holds `PAYMENT_TAG=1.5.0`, and `payment.env` holds `SPRING_PROFILES_ACTIVE=dev`.

```yaml
services:
  payment-service:
    image: payment-service:${PAYMENT_TAG}   # filled from the shell or .env
    env_file: payment.env                   # these variables go into the container
  adminer:
    image: adminer
    profiles: [debug]                       # only with --profile debug
```

```bash
docker compose config --images
PAYMENT_TAG=2.0.0 docker compose config --images
```

```text output
payment-service:1.5.0
payment-service:2.0.0
```

What to notice:

- `adminer` is missing from the output, because the `debug` profile is off. `docker compose --profile debug config --images` lists it too.
- The second command shows that a shell variable beats `.env`.
- Inside the container, `SPRING_PROFILES_ACTIVE=dev` is set from `payment.env`, but `PAYMENT_TAG` is not, because only `env_file` and `environment` reach the container.

## Rules and defaults

- **`.env` location:** the project folder, next to `compose.yaml`. `--env-file` uses another file instead.
- **Required values:** `${DB_PASSWORD:?set DB_PASSWORD}` stops Compose with that message when the variable is missing or empty.
- **Other files:** with `-f`, Compose reads only the files you list, in that order, for example `-f compose.yaml -f compose.prod.yaml`.
- **Compose Watch:** `docker compose up --watch` with `develop.watch` rules can `sync` changed files, `rebuild` the image, or `sync+restart` the container.
- **Spring Boot 4.1:** with `spring-boot-docker-compose`, the app runs `docker compose up` at startup, connects through the published ports, and runs `docker compose stop` at shutdown. If the stack is already running, it only connects. It is skipped in tests by default.

## Common mistakes

- **Putting a real password in a committed `.env`.** `.env` is plain text for local values; keep it out of Git and use [secrets](card:env-and-secrets) for real credentials.
- **Guessing what the merged file looks like.** Run `docker compose config` instead; it prints the exact model after merging, interpolation and profiles.

## Interview Qs

### What is the difference between .env and env_file?

`.env` supplies values for `${VAR}` placeholders while Compose reads `compose.yaml`; it changes the file, not the container. `env_file` loads a file's variables into one service's containers. A `.env` value reaches a container only if `environment:` or `env_file` passes it in.

### How do you keep one Compose setup for development and other environments?

Shared settings stay in `compose.yaml`. Development extras, such as published debug ports, go in `compose.override.yaml`, which Compose merges automatically. Another environment runs `docker compose -f compose.yaml -f compose.prod.yaml up`, and then the override file is not read.

### How does Spring Boot work with Docker Compose?

With the `spring-boot-docker-compose` dependency, the app finds `compose.yaml` at startup, runs `docker compose up`, and creates service connections for known images such as Postgres and Redis. Those connection details win over `spring.datasource.*` properties. At shutdown it runs `docker compose stop`.
