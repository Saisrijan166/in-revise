## Why it exists

A dead container leaves an exit code, logs and its final state. Read them in a fixed order.

## How it works

| Symptom | First check | Fix |
|---|---|---|
| Exits at once | The main process ended | Run the server in the foreground ([lifecycle](card:container-lifecycle)) |
| Exit 137 | `State.OOMKilled` | Heap plus overhead must fit the limit ([Java](card:java-in-containers)) |
| `docker stop` hangs, then 137 | Is java PID 1 and given SIGTERM? | [Exec form, graceful shutdown](card:signals-and-graceful-shutdown) |
| Refused from the host | Port published? App on 127.0.0.1? | [Publish](card:port-mapping); [listen on 0.0.0.0](card:docker-networking) |
| Unknown host `postgres` | Same user-defined network? | [Networks](card:docker-networking) |
| `exec format error` | Image CPU vs host CPU | [Build for both](card:buildkit-and-multi-platform) |
| Permission denied on a mount | Container UID vs file owner | [Mounts](card:volumes-and-mounts) |
| Old code still runs | Tag and image ID | Rebuild with a new tag ([cache](card:build-cache)) |

- 125: `docker run` itself failed; 126: the command cannot be invoked; 127: it was not found.

## Example

```bash
docker ps -a --filter name=payment-service
# STATUS  Exited (137) 2 minutes ago
docker inspect -f '{{.State.OOMKilled}}' payment-service
# true -> JVM memory went over --memory
docker logs --tail 50 payment-service
docker events --filter container=payment-service --since 1h
```

## Interview Qs

### A container exits right after `docker run -d`. Why?

Its main process ended: a crash, or a command that starts a background service and returns. Check `docker ps -a` and `docker logs`.

### What do exit codes 137 and 143 mean?

128 plus the signal number. 137 = SIGKILL: an OOM kill, `docker kill`, or a stop timeout. 143 = SIGTERM: the app stopped on `docker stop`.

### The container is running but the API is unreachable. What do you check?

Is the port published? Does the app listen on 0.0.0.0, not 127.0.0.1? Then test from inside with `docker exec`.
