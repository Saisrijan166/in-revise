## What it is

Troubleshooting a container means finding out why it stopped, restarts, or does not answer, by reading the evidence Docker keeps. A stopped container is not deleted until you run `docker rm`, so its **exit code**, its logs and its final state are still there. An exit code is the number a process returns when it ends: 0 means success, and anything else is an error or a signal.

## Why it exists

"The container died" has many causes: a crash at startup, memory, a wrong command, a network mistake. Guessing and restarting wastes time and hides the evidence. A fixed order of commands turns the symptom into a cause in a few minutes, and the same order works for every container.

## How it works

| Symptom | First check | Usual fix |
|---|---|---|
| Exits at once | Exit code and logs | Fix the crash; run the server in the foreground ([lifecycle](card:container-lifecycle)) |
| Exit 137 | `State.OOMKilled` | Make heap plus overhead fit the limit ([Java](card:java-in-containers)) |
| `docker stop` waits 10 s, then 137 | Is java PID 1 and given SIGTERM? | [Exec form, graceful shutdown](card:signals-and-graceful-shutdown) |
| Refused from the host | Port published? App on 127.0.0.1? | [Publish](card:port-mapping); listen on 0.0.0.0 |
| Unknown host `postgres` | Same user-defined network? | [Networks](card:docker-networking) |
| `exec format error` | Image CPU type vs host CPU type | [Build for both](card:buildkit-and-multi-platform) |
| Permission denied on a mount | Container UID vs file owner | Match the [USER](card:image-security) and the owner |
| Old code still runs | Container's image ID vs the new build | Recreate the container; [unique tags](card:registries) |

1. Run `docker ps -a` to see the container's status and exit code, including stopped containers.
2. Run `docker logs` to read what the app printed before it stopped.
3. Run `docker inspect` to read the state, such as `OOMKilled`, and the settings: mounts, networks, environment.
4. If it is still running, use `docker exec` to test from inside: resolve names, call ports, list files.
5. Use `docker stats` for live memory and CPU, and `docker events` for the history of kills, OOMs and restarts.

So the key is: read the evidence in order before you change anything.

## Example

The payment service was started with `--memory 256m` but a JVM heap of 1 GB, set through `JAVA_TOOL_OPTIONS`. It stopped a few seconds later.

```bash
docker ps -a --filter name=payment-service --format '{{.Names}}: {{.Status}}'
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' payment-service
docker events --filter container=payment-service --since 1m --until 0s --format '{{.Action}}'
```

```text output
payment-service: Exited (137) 4 seconds ago
137 true
create
start
oom
die
```

What to notice:

- 137 is 128 + 9, so the JVM got SIGKILL; it had no chance to log anything or shut down cleanly.
- `OOMKilled` is `true` and the events show `oom`, so the kernel killed it for going over the 256 MB limit. The fix is a smaller heap or a larger limit.
- After `docker kill`, the same container shows 137 with `OOMKilled` false and no `oom` event. That is why you check, not guess.

## Rules and defaults

- **Exit codes from Docker:** 125 means `docker run` itself failed, such as an unknown flag; 126 means the command cannot be run; 127 means it was not found.
- **Signal exit codes:** 128 + N means signal N: 137 SIGKILL, 139 SIGSEGV (a crash from an invalid memory access), 143 SIGTERM.
- **Stopped is not removed:** logs and state stay until `docker rm`. Starting with `--rm` deletes them on exit, so avoid it while debugging.
- **`docker compose up --exit-code-from <service>`:** returns that service's exit code, which helps CI fail on the right container.

## Not to be confused with

`docker stop` sends SIGTERM and, after the grace period, SIGKILL; a clean Java shutdown then gives exit code 143. `docker kill` sends SIGKILL at once, giving 137. Rule: 143 = asked to stop; 137 = killed, by you, a timeout or the OOM killer. [Graceful shutdown](card:signals-and-graceful-shutdown) explains the grace period.

## Interview Qs

### A container exits right after docker run -d. How do you find out why?

`docker ps -a` shows it with its exit code, and `docker logs` shows the error. A container lives only as long as its main process, so it stopped because that process ended: usually a startup crash, or a command that starts the server in the background and returns.

### What do exit codes 137 and 143 mean?

Both are 128 plus a signal number. 137 is SIGKILL: an OOM kill, `docker kill`, or a stop that ran past its timeout; `State.OOMKilled` tells them apart. 143 is SIGTERM, usually a normal `docker stop` that the app handled.

### The container is running, but the API is unreachable. What do you check?

From the host: is the port published, as shown in `docker ps`? From inside with `docker exec`: does the app answer on its port, and does it listen on 0.0.0.0 rather than 127.0.0.1? For another container: are both on the same user-defined network, using the service name?
