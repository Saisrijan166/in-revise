## What it is

A signal is a short message the operating system delivers to a process, such as "please stop" (`SIGTERM`) or "die now" (`SIGKILL`, which cannot be caught). Inside a container, the first process gets process ID 1 in its own PID namespace (see [namespaces](card:namespaces-and-cgroups)), and Docker sends its stop signal to that process only. Graceful shutdown means the app reacts to `SIGTERM` by refusing new work, finishing what is in progress and exiting on its own.

## Why it exists

Every deploy, scale-down or host reboot stops containers. If the payment service is killed halfway through a payment, the customer may be charged with no record saved. Docker gives the app a warning and some time, but only the process that is PID 1 hears the warning. So the app must be PID 1, must handle `SIGTERM`, and must finish before Docker's patience runs out.

## How it works

<Steps label="docker stop on the payment service">
  <Step title="Signal">Docker sends SIGTERM, or the image's STOPSIGNAL, to PID 1.</Step>
  <Step title="Stop taking work">Spring Boot stops accepting new requests.</Step>
  <Step title="Finish and exit">A payment in progress completes, and the JVM exits within the grace period.</Step>
  <Step title="Or killed">If the process still runs at the deadline, Docker sends SIGKILL.</Step>
</Steps>

1. You run `docker stop pay`. Docker sends `SIGTERM` to PID 1 in the container and starts a timer, 10 seconds by default on Linux.
2. The kernel delivers the signal only if PID 1 has a handler for it. The JVM installs one, so `java` as PID 1 receives it. `/bin/sh` as PID 1 has none, so the signal is dropped.
3. The JVM runs its shutdown hooks. Spring Boot's graceful shutdown stops taking new requests and waits for running ones, up to its own timeout.
4. The process exits, and the container becomes exited with code 143 (128 + 15, the number of `SIGTERM`).
5. If the timer runs out first, Docker sends `SIGKILL`. The process dies at once, with no cleanup, and the exit code is 137 (128 + 9).

So the key is: the right process must be PID 1, and it must finish inside the grace period.

## Example

The same stand-in payment app was built twice and run as two containers. `pay-shell` uses the shell form, `ENTRYPOINT java -cp /app Pay`; `pay-exec` uses the exec form below. Both were then stopped:

```dockerfile
ENTRYPOINT ["java", "-cp", "/app", "Pay"]
```

```bash
docker exec pay-shell ps -o pid=,args= -p 1
docker stop pay-shell && docker logs pay-shell
docker stop pay-exec && docker logs pay-exec
```

```text output
      1 /bin/sh -c java -cp /app Pay
pay-shell
payment-service started on 8080
pay-exec
payment-service started on 8080
SIGTERM received: finishing in-flight payment
Shutdown complete
```

What to notice:

- In `pay-shell`, PID 1 is `/bin/sh -c`, and `java` is only its child. Its stop took about 11 seconds, the logs show no shutdown, and the exit code was 137: Docker had to send `SIGKILL`.
- In `pay-exec`, `java` is PID 1. Its shutdown hook ran, the stop took about 3 seconds, and the exit code was 143.
- If a start script must run first, end it with `exec java ...`; `exec` replaces the shell with java, so java becomes PID 1.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Stop signal | `SIGTERM`; change with `STOPSIGNAL` or `--stop-signal` | Docker Engine 29 |
| Grace period | 10 s for Linux containers, 30 s for Windows; change with `docker stop -t`, `--stop-timeout` or Compose `stop_grace_period` | Docker Engine 29 |
| `server.shutdown` | `graceful`; set `immediate` to turn it off | Spring Boot 4.1 |
| `spring.lifecycle.timeout-per-shutdown-phase` | 30 s | Spring Boot 4.1 |

- **Make the timeouts agree:** with Spring's 30 s, use a Docker grace period of about 40 s, or the default 10 s will cut it short.
- **`--init`:** puts a tiny init process (Docker ships tini) at PID 1. It forwards signals to your app and reaps zombie processes, finished child processes that nobody collected. Use it when the app starts child processes.

## Not to be confused with

The exec form `["java", ...]` runs the program directly, so it is PID 1. The shell form `java ...` runs it through `/bin/sh -c`, so the shell is PID 1. Rule: exec form for the main process, always. The full comparison is in [RUN vs CMD vs ENTRYPOINT](card:run-cmd-entrypoint).

## Common mistakes

- **"My app handles SIGTERM, so shutdown is fine."** It still depends on the app being PID 1. A shell or wrapper script in front of it swallows the signal.
- **Testing shutdown with Ctrl+C in the IDE.** Some IDEs end the process at once. Test with `docker stop` and check the logs for the shutdown messages.

## Interview Qs

### Why does my container take 10 seconds to stop?

PID 1 ignored `SIGTERM`, so Docker waited the full grace period and sent `SIGKILL`. The usual cause is a shell-form `ENTRYPOINT`: `sh` is PID 1, has no handler and does not pass the signal to java. Use the exec form, or `exec java ...` at the end of the start script.

### Why is PID 1 special in a container?

The kernel delivers a signal to a namespace's PID 1 only if it installed a handler for that signal; from the host, only `SIGKILL` and `SIGSTOP` are forced through. PID 1 also adopts orphaned processes and must reap them. `--init` puts a small init there to forward signals and reap zombies.

### How do you stop a Spring Boot container without losing requests?

Start java in exec form so the JVM gets `SIGTERM`. Spring Boot's graceful shutdown, on by default, stops new requests and lets running ones finish, up to 30 s per phase. Set Docker's grace period above that, for example `--stop-timeout 40`.
