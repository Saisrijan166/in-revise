## Why it exists

Images must move from the build machine to CI and servers. A registry stores and serves them, and a name or digest says exactly which image to pull.

## How it works

| Part of the reference | Example | If left out |
|---|---|---|
| Registry host | `registry.example.com` | `docker.io` (Docker Hub) |
| Namespace | `payments` | `library` (Official Images) |
| Repository | `payment-service` | required |
| Tag | `:1.4.0` | `:latest` |
| Digest | `@sha256:…` | not used |

- Which tags CI should push: [Docker in CI/CD](card:docker-in-ci-cd). Pinning base images: [image security](card:image-security).
- One tag can cover several CPU types: [multi-platform builds](card:buildkit-and-multi-platform).

## Example

```bash
docker login registry.example.com
docker tag payment-service:1.4.0 registry.example.com/payments/payment-service:1.4.0
docker push registry.example.com/payments/payment-service:1.4.0   # prints the digest
# exact bytes, whatever the tag points to later:
docker pull registry.example.com/payments/payment-service@sha256:<digest>
```

## Interview Qs

### Registry vs repository vs Docker Hub?

A registry is the service that stores images. A repository is one image's collection of tags inside it. Docker Hub is Docker's public registry and the default one.

### How do you make sure production runs exactly the image you tested?

Deploy by digest (`name@sha256:…`), not by tag. Anyone can push a tag again with new content; a digest is a hash of the content, so it cannot change.

### CI fails to pull from Docker Hub with a rate-limit error. Why?

Docker Hub limits pulls: 100 per 6 hours per IP address without login. Log in with an account, or keep the images you need in your own registry.
