## Why it exists

A full JDK on a full distro is large, slow to pull and full of packages the app never uses, and each of them can carry a CVE.

## How it works

<Compare id="alpine-vs-slim-vs-distroless" />

- Leave Maven and the JDK in the build stage with [multi-stage builds](card:multi-stage-builds); trim the runtime further with [jlink](card:java-in-containers).
- Install and clean package caches in one `RUN`: [a later delete does not shrink the image](card:images-and-layers).
- Keep `.git` and `.env` out with `.dockerignore` ([build cache](card:build-cache)); check sizes with `docker image history` or dive.

## Example

```dockerfile
# final stage only; the build stage made target/payment-service.jar
FROM gcr.io/distroless/java25-debian13:nonroot
COPY --from=build /app/target/payment-service.jar /app/app.jar
# the image's entrypoint is already "java -jar"
CMD ["/app/app.jar"]
```

## Interview Qs

### How do you make a Docker image smaller?

Use a multi-stage build, run on a JRE in a small base, install only needed packages and clean caches in the same `RUN`, and exclude junk with `.dockerignore`. Then check with `docker image history`.

### Why can Alpine cause problems for a Java app?

Alpine uses musl libc instead of glibc. A JDK or native library built for glibc may fail. Use a JDK built for Alpine, such as the Temurin Alpine tags, or a glibc base.

### How do you debug a distroless container without a shell?

Switch to the image's `:debug` tag, which adds a busybox shell, and run it with `--entrypoint=sh`.
