## What it is

Image size optimisation means removing everything from the final image that the running app does not use. For the payment service that means the JDK, Maven, the source code and most of a Linux distribution. What remains is a **base image** (the starting layers from `FROM`) that is as small as the app allows, a Java runtime (JRE), and the jar.

## Why it exists

A full JDK on a full Linux distribution adds hundreds of megabytes. Every server and CI runner must download that before the container can start, and every extra package is one more thing a scanner can flag with a CVE. Most of it, such as the compiler, a package manager or a text editor, is never used at run time.

## How it works

<Compare id="alpine-vs-slim-vs-distroless" />

1. Build in a first stage with the JDK and Maven, then copy only the jar into the final stage ([multi-stage builds](card:multi-stage-builds)).
2. Choose a small final base: a JRE image, a slim Debian base, a distroless Java image or an Alpine-based JRE, compared above. [jlink](card:java-in-containers) can shrink the Java runtime further.
3. When you must install packages, install and clean the package cache in the same `RUN`, because a file deleted in a later step [stays in the earlier layer](card:images-and-layers).
4. Keep `.git`, `.env` and IDE folders out of the build with `.dockerignore` ([build cache](card:build-cache)).
5. Check the result with `docker image history`, which lists each layer and its size.

So the key is: the final stage decides the size, so put only the runtime and the jar there.

## Example

The final image of the payment service on a distroless Java 25 base, which runs as user `nonroot`.

```dockerfile
FROM gcr.io/distroless/java25-debian13:nonroot
COPY target/payment-service.jar /app/app.jar
# the base image's entrypoint is already "java -jar"
CMD ["/app/app.jar"]
```

```bash
docker run -d --name payment-service payment-service:distroless
docker logs payment-service
docker exec payment-service sh
```

```text output
payment-service 1.4.0 running as nonroot
OCI runtime exec failed: exec failed: unable to start container process: exec: "sh": executable file not found in $PATH
```

What to notice:

- `CMD` holds only the jar path, because the distroless image's `ENTRYPOINT` is already `/usr/bin/java -jar`. Writing `CMD ["java", "-jar", ...]` would pass `java` as the jar name.
- The `:nonroot` tag runs the app as UID 65532, so you get a non-root user without writing a `USER` line.
- `docker exec ... sh` fails because there is no shell. That also means an attacker who gets in has no shell to use.

## Rules and defaults

- **Distroless tags:** `latest`, `nonroot`, `debug` and `debug-nonroot`; the debug tags add a busybox shell.
- **Temurin images:** JRE and JDK images exist for each Java version; the `-alpine` variants are built for musl.
- **Slim images:** Debian slim tags remove docs, man pages and similar files from the full Debian image.
- **Layer rule:** deleting a file in a later `RUN` hides it but does not make the image smaller.

## Interview Qs

### How do you make a Docker image smaller?

Use a multi-stage build so the JDK and Maven stay in the build stage, run on a JRE in a small base, install only needed packages and clean caches in the same `RUN`, and exclude junk with `.dockerignore`. Then check each layer with `docker image history`.

### Why can Alpine cause problems for a Java app?

Alpine uses musl libc instead of glibc. A JDK or a native library built for glibc may crash or fail to load on it. Use a JDK built for Alpine, such as the Temurin `-alpine` tags, or choose a glibc base such as slim or distroless.

### Does a smaller image also make the app faster?

Not the running app: the JVM does the same work. It makes pulls, deploys and scale-outs faster, uses less disk on each host, and leaves fewer packages that can carry CVEs.
