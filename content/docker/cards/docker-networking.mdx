## What it is

A Docker network is a private virtual network that containers attach to, like computers plugged into one switch. Each container gets its own network stack, thanks to the network [namespace](card:namespaces-and-cgroups): its own IP address, its own ports and its own localhost. On a network you create yourself, Docker also runs a small DNS server, which turns a container's name into its current IP address.

## Why it exists

The payment service must talk to PostgreSQL in another container. Without networks you would look up the database container's IP address and paste it into the app's settings. That address changes every time the container is recreated, so the app breaks after each restart. A network with name lookup lets the app use a fixed name, `postgres`, and Docker finds the current address on every connection.

## How it works

1. You create a network with `docker network create payments-net`. Docker uses the bridge driver: a private network on this one host.
2. You start each container with `--network payments-net`. Docker gives each one an IP address on that network.
3. When the app connects to `postgres`, it asks Docker's DNS server, which answers with the database container's current IP address.
4. The app connects directly to port 5432 of that container. Containers on the same network reach all of each other's ports; no publishing is needed.

So the key is: same network you created, then use the container name.

## Example

The payment service's database starts on its own network, and two short-lived containers test whether the name `postgres` can be reached.

```bash
docker network create payments-net
docker run -d --name postgres --network payments-net \
  -e POSTGRES_PASSWORD=dev-only postgres:18

docker run --rm --network payments-net postgres:18 pg_isready -h postgres
# postgres:5432 - accepting connections
docker run --rm postgres:18 pg_isready -h postgres
# postgres:5432 - no response
```

What to notice:

- The first check runs on `payments-net`, so Docker's DNS resolves `postgres` and the database answers.
- The second check has no `--network`, so it lands on the default bridge network. That network has no name lookup, and the same command fails.
- `pg_isready -h localhost` on `payments-net` also fails: localhost is the checking container itself, and no database runs there.
- In the real setup the app gets `SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/payments`.

## Rules and defaults

- **No `--network` flag:** the container joins the default network named `bridge` (Docker Engine 29 on Linux). Docker calls it a legacy detail, not for production.
- **DNS server:** containers on a network you created use `127.0.0.11`; it answers container names and `--network-alias` names, and forwards other names to the host's DNS servers.
- **Drivers:** `bridge` (one host), `host` (share the host's network: no own IP, and `-p` is ignored with a warning), `none` (no network), `overlay` (across several Docker hosts, used by Swarm), `macvlan` and `ipvlan` (connect the container directly to the physical network).
- **More than one network:** `docker network connect` adds a running container to another network you created. Names do not resolve across networks.
- **Listen address:** an app inside a container must listen on `0.0.0.0` (all interfaces). An app listening on `127.0.0.1` cannot be reached from any other container or from the host.

## Not to be confused with

The default bridge network is the one every container joins when you give no `--network`; containers there reach each other only by IP address. A network you create with `docker network create` (Docker calls it a user-defined bridge) adds name lookup and keeps unrelated containers apart. Rule: for any app with more than one container, create a network.

## Common mistakes

- **"Containers need -p to talk to each other."** Not on the same network. `-p` opens a port on the host for clients outside Docker; see [Publishing Ports](card:port-mapping).
- **Hardcoding a container's IP address.** It changes when the container is recreated. Use the container name or a `--network-alias`.

## Interview Qs

### The app calls localhost:5432 and cannot reach PostgreSQL in another container. Why?

Each container has its own network stack, so localhost is the app container itself. Put both containers on one network you created and connect to the database by its container name, `postgres:5432`. Docker's DNS server resolves that name to the current IP address.

### Why prefer a user-defined network over the default bridge?

Containers on it find each other by name through Docker's DNS server, only the containers you attach can reach each other, and you can connect or disconnect a running container. On the default bridge, every container without `--network` shares one network and reaches others by IP address only.

### How does a container reach a service running on the host?

Use the name `host.docker.internal`. Docker Desktop provides it; on Linux start the container with `--add-host host.docker.internal=host-gateway`, which maps the name to the host's internal IP address. localhost would point to the container itself.
