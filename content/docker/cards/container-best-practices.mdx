## Why it exists

Containers are meant to be thrown away and replaced. Apps that hide state, settings or fixes inside a running container break when that happens.

## How it works

| Practice | Why | Details |
|---|---|---|
| Stateless container | data survives replacement | [volumes](card:volumes-and-mounts) or a managed database |
| Config from the environment | one image for every environment | [env and secrets](card:env-and-secrets) |
| Logs to stdout and stderr | Docker and log tools collect them | [logging](card:container-logging) |
| Health check | "running" is not "working" | [health checks](card:container-health-checks) |
| Graceful shutdown | in-flight ₹500 payments finish on SIGTERM | [signals](card:signals-and-graceful-shutdown) |
| Memory and CPU limits | one container cannot starve the rest | [resource limits](card:resource-limits) |
| Restart policy | Docker restarts only if a policy says so | [lifecycle](card:container-lifecycle) |
| Non-root, scanned image | a hacked app does less damage | [Secure Images](card:image-security) |

- These follow the [Twelve-Factor App](https://12factor.net/): config, processes, disposability, logs.
- Split the payment service, Postgres and Redis into three containers, not one.
- Promote one image through every environment: see [Docker in CI/CD](card:docker-in-ci-cd).

## Interview Qs

### Why one process per container?

Separate containers are easier to scale out and reuse. One process is a rule of thumb, not a hard rule: an init process, or workers the app starts itself, are fine.

### Why should containers be stateless?

A container can be deleted and replaced at any time, on a deploy, a crash or a scale-out. State kept inside its writable layer is lost then; keep it in volumes or external services.
