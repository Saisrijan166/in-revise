## What it is

Container best practices are a short list of habits that make containers safe to throw away. A container is meant to be **ephemeral**: you can stop it, delete it and start a new one from the same image with almost no set-up. Most of the habits follow the **Twelve-Factor App**, a well-known guide for cloud apps: keep config in the environment, keep processes stateless, start fast and stop cleanly, and write logs to the console.

## Why it exists

Docker, Compose and Kubernetes replace containers all the time: on every deploy, after a crash, when scaling out. An app that keeps data, settings or hand-made fixes inside its container breaks when that happens, and nobody knows what the running copy really contains. If every container is disposable, replacing it is routine instead of risky.

## How it works

| Practice | Why | Details |
|---|---|---|
| Stateless container | data survives replacement | [volumes](card:volumes-and-mounts) or a managed database |
| Config from the environment | one image for every environment | [env and secrets](card:env-and-secrets) |
| Logs to stdout and stderr | Docker and log tools collect them | [logging](card:container-logging) |
| Health check | "running" is not "working" | [health checks](card:container-health-checks) |
| Graceful shutdown | in-flight payments finish on SIGTERM | [signals](card:signals-and-graceful-shutdown) |
| Memory and CPU limits | one container cannot starve the rest | [resource limits](card:resource-limits) |
| Restart policy | Docker restarts only if a policy says so | [lifecycle](card:container-lifecycle) |
| Non-root, scanned image | a hacked app does less damage | [Secure Images](card:image-security) |

1. Split the app by concern: the payment service, Postgres and Redis each get their own container and image.
2. Build one image per release and give it a unique tag; never change it afterwards.
3. Start that same image in every environment, and pass the differences in as environment variables and secrets.
4. Keep anything that must survive, such as database files, in a volume or an outside service.
5. When something must change, build a new image and replace the container; the old one is simply deleted.

So the key is: the image is the only source of truth, and the container is a disposable copy of it.

## Example

A "hotfix" made inside a running container disappears when the container is replaced.

```bash
docker run -d --name payment-service payment-service:1.4.0
docker exec payment-service sh -c 'echo hotfix > /tmp/patch.txt'
docker rm -f payment-service
docker run -d --name payment-service payment-service:1.4.0
docker exec payment-service cat /tmp/patch.txt
```

What to notice:

- In a real run the last command printed `cat: /tmp/patch.txt: No such file or directory`: the new container starts from the image, not from the old container.
- Any change made with `docker exec` behaves the same way, whether it is a config edit or a patched file.
- The fix is to change the code or Dockerfile, build `payment-service:1.4.1`, and replace the container with it.

## Rules and defaults

- **One process per container:** a rule of thumb, not a hard rule. An init process, or workers the app starts itself, are fine.
- **Rebuild often:** `docker build --pull` checks for a newer base image; `--no-cache` also reruns every step.
- **No automatic restart:** Docker restarts a stopped container only when a restart policy says so.

## Interview Qs

### Why one process per container?

Separate containers can be scaled, upgraded and restarted on their own, and each image stays small and simple. It is a rule of thumb from the Docker docs, not a law: an init process, or an app that starts its own worker processes, is fine.

### Why should containers be stateless?

A container can be deleted and replaced at any time, on a deploy, a crash or a scale-out. Anything stored in its writable layer is lost then. Keeping state in volumes or external services means any copy of the container can serve any request.

### What does "immutable image" mean, and why does it matter?

Once an image is built and tagged for a release, it is never changed. A fix means a new build and a new tag. Every environment then runs exactly what was tested, and rolling back means starting the previous tag.
