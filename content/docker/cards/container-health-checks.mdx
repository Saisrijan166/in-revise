## What it is

A health check is a test command that Docker runs inside a running container, again and again on a timer. You declare it with the `HEALTHCHECK` instruction in the Dockerfile, or with `--health-*` flags on `docker run`. The command's exit code is the answer: 0 means the app is fine, 1 means it is not. Docker shows the result next to the container's status as starting, healthy or unhealthy.

## Why it exists

In the [container lifecycle](card:container-lifecycle), "running" only means the main process has not ended. The payment service can be running and still useless: stuck in a deadlock, out of database connections, or still starting up. Without a health check, Docker and every tool built on it would send work to that container. A health check tests the app the way a client would, so others can see whether the container is really ready.

## How it works

<Mermaid
  alt="Health states. A new container starts as starting. One passing check makes it healthy. A run of failed checks equal to retries makes it unhealthy. One passing check makes it healthy again. During the start period, failures do not count."
  chart={`stateDiagram-v2
  [*] --> starting
  starting --> healthy: check passes
  healthy --> unhealthy: retries failures in a row
  unhealthy --> healthy: check passes
  starting --> unhealthy: failures after start period`}
/>

1. The container starts, and its health status is `starting`.
2. After the first interval, Docker runs the check command inside the container, the way `docker exec` would. A check that runs longer than the timeout counts as failed.
3. Exit code 0 sets the status to `healthy`. A failure adds one to a counter; during the start period, failures are not counted.
4. When the counter reaches the retries value, 3 by default, the status becomes `unhealthy`. One passing check makes it `healthy` again and resets the counter.
5. Docker shows the status in `docker ps` and keeps the last few results in `docker inspect`, under `.State.Health`. It takes no other action.

## Example

The payment-service image gets curl, because the `eclipse-temurin:25-jre` image has none, and a check against Spring Boot Actuator's health endpoint:

```dockerfile
FROM eclipse-temurin:25-jre
# ... copy the app and set ENTRYPOINT as before ...
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
HEALTHCHECK --interval=10s --timeout=3s --start-period=60s --retries=3 \
  CMD curl -fsS http://localhost:8080/actuator/health || exit 1
```

```bash
docker run -d --name pay payment-service:1.4.0
docker inspect -f '{{.State.Health.Status}}' pay     # right away
docker inspect -f '{{.State.Health.Status}}' pay     # 15 seconds later
docker ps --filter name=pay --format '{{.Names}}  {{.Status}}'
```

```text output
c3a4e8acc677edabce60a4948206ccd947d6925b8543ba3a2072c0961344db6b
starting
healthy
pay  Up 16 seconds (healthy)
```

What to notice:

- `curl -f` exits with an error on an HTTP error status, such as the 503 Actuator returns when the app is down. `|| exit 1` turns any failure into exit code 1, because code 2 is reserved.
- The status was `starting` until the first check ran, 10 seconds after start, and `healthy` after it passed.
- With the check pointed at a wrong port, the same container became `unhealthy` after 3 failures, and its restart count stayed 0, even with `--restart unless-stopped`.

## Rules and defaults

| Option | Default | Where |
|---|---|---|
| `--interval` / `--timeout` | 30 s / 30 s | Docker Engine 29 |
| `--retries` | 3 | Docker Engine 29 |
| `--start-period` | 0 s | Docker Engine 29 |
| `--start-interval` | 5 s; checks run this often during the start period (needs Engine 25.0 or later) | Docker Engine 29 |

- **One per image:** if a Dockerfile has several `HEALTHCHECK` lines, only the last one counts. `HEALTHCHECK NONE` turns off a check inherited from the base image.
- **The tool must exist in the image:** a check that calls `curl` fails in an image without curl.
- **Who acts on it:** Compose can start a service only after another one is healthy (see [startup order](card:compose-startup-order)); Swarm replaces a task that becomes unhealthy; plain Docker does nothing.

## Not to be confused with

A health check reports whether the app answers. A [restart policy](card:container-lifecycle) restarts a container whose main process has exited. They do not talk to each other in plain Docker: an unhealthy container that keeps running is never restarted. Rule: health checks report, restart policies react to exits.

## Interview Qs

### Is a running container a healthy one?

No. Running means only that the main process is alive. The app may be deadlocked, out of database connections or still starting. A `HEALTHCHECK` tests the app itself and shows healthy or unhealthy in `docker ps`.

### Does Docker restart an unhealthy container?

Not with `docker run` or Compose: it only marks it unhealthy. Restart policies react to the container exiting. Docker Swarm does replace a task that fails its health check. In plain Docker, something else must act on the status, such as your monitoring.

### What should a Spring Boot health check call?

The Actuator endpoint `/actuator/health`. It returns HTTP 200 when the app is UP and 503 when it is DOWN or OUT_OF_SERVICE, so a `curl -f` check fails exactly when the app is unhealthy. The check tool must be in the image; the eclipse-temurin JRE image has no curl.
