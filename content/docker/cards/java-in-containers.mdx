## What it is

This concept is about running the payment service's JVM well inside a container. The JVM sizes itself from the machine it sees: the heap, the memory where Java objects live, gets a share of the available memory, and thread pools are sized from the CPU count. In a container, that machine should be the container's limits, which Docker enforces with [cgroups](card:namespaces-and-cgroups). It also covers packaging the jar so a code change re-ships only a small layer.

## Why it exists

A JVM that sized its heap from the host's 64 GB, not the container's 1 GB limit, would grow past the limit and be killed. Modern JVMs read the limit, but the default heap is only a quarter of it, so a 1 GB container gets a 256 MB heap and the rest sits idle. And a Spring Boot jar is one file, mostly libraries: copied as one layer, every code change re-ships all of them.

## How it works

| JVM option | What it controls | Default (Java 25, Linux) |
|---|---|---|
| `UseContainerSupport` | Read the container's memory and CPU limits | On |
| `-XX:MaxRAMPercentage` | Maximum heap, as a % of the memory limit | 25 |
| `-XX:InitialRAMPercentage` | Starting heap, as a % of the memory limit | 1.5625 |
| `-XX:ActiveProcessorCount` | CPU count used to size GC and pool threads | Detected |

1. At start, the JVM detects that it runs in a container and reads the memory and CPU limits from cgroups.
2. It sets the maximum heap to `MaxRAMPercentage` of the memory limit: 25% by default.
3. It takes the CPU count from the CPU limit and sizes garbage-collector and pool threads from it.
4. Memory outside the heap, such as metaspace for class data, one stack per thread, direct buffers and compiled code, also counts toward the limit. If the total passes it, the kernel kills the process.

So the key is: heap share plus non-heap memory must stay below the container's limit.

## Example

The payment-service image splits the jar into four layers and gives the heap 75% of the limit.

```dockerfile
FROM eclipse-temurin:25-jre AS extract
WORKDIR /x
COPY target/payment-service-1.4.0.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination out

FROM eclipse-temurin:25-jre
WORKDIR /app
COPY --from=extract /x/out/dependencies/ ./
COPY --from=extract /x/out/spring-boot-loader/ ./
COPY --from=extract /x/out/snapshot-dependencies/ ./
COPY --from=extract /x/out/application/ ./
ENV JDK_JAVA_OPTIONS="-XX:MaxRAMPercentage=75"
ENTRYPOINT ["java", "-jar", "application.jar"]
```

What to notice:

- `extract --layers` splits the jar into four folders, from least to most likely to change. Each `COPY` makes one layer, so after a code change only the `application` layer is rebuilt and pushed. In a small Spring Boot web app, `docker history` shows about 20 MB of dependencies and about 12 kB of application.
- `JDK_JAVA_OPTIONS` is read by the `java` launcher itself, so the exec-form `ENTRYPOINT` needs no shell to pick it up.
- 75% leaves a quarter of the limit for non-heap memory. Remove the `ENV` line and the heap falls back to 25%.

The same base image shows the default and the raised heap under a 1 GB limit:

```bash
docker run --rm -m 1g eclipse-temurin:25-jre \
  java -XX:+PrintFlagsFinal -version 2>/dev/null | grep -w MaxHeapSize
docker run --rm -m 1g eclipse-temurin:25-jre \
  java -XX:MaxRAMPercentage=75 -XX:+PrintFlagsFinal -version 2>/dev/null | grep -w MaxHeapSize
```

```text output
   size_t MaxHeapSize                              = 268435456                                 {product} {ergonomic}
   size_t MaxHeapSize                              = 805306368                                 {product} {ergonomic}
```

268435456 bytes is 256 MB, a quarter of 1 GB. With 75%, the heap may grow to 768 MB.

## Rules and defaults

- **Container support:** on by default on Linux since JDK 10, and backported to 8u191. Older Java 8 builds sized the heap from the host's memory.
- **Passing options:** put them in the `ENTRYPOINT` array, or in `JDK_JAVA_OPTIONS`. A `$JAVA_OPTS` inside an exec-form array is not expanded.
- **Layer index:** Spring Boot's Maven plugin writes `layers.idx` into the jar by default; it defines the layers `dependencies`, `spring-boot-loader`, `snapshot-dependencies` and `application`.
- **Headroom:** the right heap share depends on how much non-heap memory the app uses; measure it, then leave that much free below the limit.

## Not to be confused with

A Dockerfile is a recipe you write and maintain, step by step. Cloud Native Buildpacks, run by `mvn spring-boot:build-image`, inspect the project and build the image for you, with a base image and JVM chosen by the builder and a non-root user. Rule: buildpacks for a standard Spring Boot service; a Dockerfile when you need full control.

## Interview Qs

### Does Java know it runs in a container?

Yes. On Linux, since JDK 10 and 8u191, the JVM reads the container's memory and CPU limits; `UseContainerSupport` is on by default. It then takes 25% of the memory limit as the maximum heap unless you set `MaxRAMPercentage` or `-Xmx`.

### The container was killed for memory, but the heap looked fine. Why?

The limit covers the whole process: heap plus metaspace, thread stacks, direct buffers and the code cache. When the total passes the limit, the kernel kills it without a Java `OutOfMemoryError`. Lower `MaxRAMPercentage` or raise the limit.

### Why use a layered jar?

A fat jar copied as one file is one layer, so each code change re-ships every library. Extracted with `jarmode=tools`, the libraries sit in their own layers that stay cached in the build and in the registry, and only the small application layer changes.
