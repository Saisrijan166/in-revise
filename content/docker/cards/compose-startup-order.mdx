## What it is

`depends_on` is a setting on a Compose service that lists the services it needs. Compose then starts those services first and stops them last. By default it only waits until a dependency's container is **running**. With the long form you add a `condition`, such as `service_healthy`, so Compose waits until the dependency's [health check](card:container-health-checks) passes, which means it is **ready**.

## Why it exists

PostgreSQL needs a few seconds after its container starts before it accepts connections. If the payment service starts in that gap, its first database call fails and Spring Boot stops with a connection error. Restarting by hand until the timing works is not a fix. `depends_on` with a health condition makes Compose hold the app back until Postgres really answers.

## How it works

<Steps label="docker compose up with service_healthy">
  <Step title="Create dependencies">postgres and redis are created and started first.</Step>
  <Step title="Wait for healthy">Compose runs nothing more until the postgres healthcheck passes.</Step>
  <Step title="Start the app">Only then is payment-service created and started.</Step>
  <Step title="Stop in reverse">On down, payment-service is removed before postgres and redis.</Step>
</Steps>

1. Compose reads every `depends_on` and sorts the services, so dependencies come first.
2. It starts `postgres` and `redis`. For `redis` the condition is `service_started`, so a running container is enough.
3. For `postgres` the condition is `service_healthy`. Compose waits while the healthcheck, here `pg_isready`, runs on its timer. If it never passes, the app is not started and `up` fails.
4. When the check passes, Compose creates and starts `payment-service`.
5. On `docker compose down` the order is reversed: the app goes first, so it never runs without its database.

So the key is: the condition decides what "started" means. Without one it means "running".

## Example

The payment service waits for a healthy Postgres and a started Redis.

```yaml
services:
  payment-service:
    build: .
    depends_on:
      postgres: { condition: service_healthy, restart: true }
      redis: { condition: service_started }
  postgres:
    image: postgres:18
    environment: { POSTGRES_DB: payments, POSTGRES_PASSWORD: "${DB_PASSWORD}" }
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d payments"]
      interval: 5s
      retries: 5
  redis: { image: "redis:8" }
```

What to notice:

- `pg_isready` asks Postgres itself whether it accepts connections, which is the real meaning of ready.
- In a real run, `docker compose up -d` printed "postgres-1 Waiting", then "Healthy", and only then started the app, which connected at once. With `depends_on: [postgres]` instead, the same stand-in app exited with "Connection refused".
- `restart: true` restarts payment-service when a Compose command, such as `docker compose restart postgres`, restarts or updates Postgres.

## Rules and defaults

- **Default condition:** listing only names means `service_started`.
- **Healthcheck needed:** `service_healthy` works only if the dependency has a `healthcheck` in the file or a `HEALTHCHECK` in its image.
- **`restart: true`:** reacts only to restarts done by Compose commands, not to Docker's restart policy restarting a crashed container.
- **`required: false`:** Compose only warns if that dependency is not started or not available (Compose 2.20.0+).
- **`docker compose up --wait`:** waits until all services are running or healthy, then returns. CI jobs use it before running tests.

## Common mistakes

- **"With service_healthy the app needs no retry logic."** The condition covers startup only. If Postgres is recreated later, it gets a new IP and open connections close; the app must look up the name again and reconnect.
- **"A sleep in the app's command fixes the order."** A fixed sleep is too short on a slow machine and wastes time on a fast one. A health condition waits exactly as long as needed.

## Interview Qs

### How do you make container 1 start before container 2 in Compose?

Add `depends_on: [container1]` to container 2's service. Compose then creates container 1 first and removes it last. If container 2 needs container 1 to be ready, not only running, I use the long form with `condition: service_healthy` and a healthcheck on container 1.

### Does depends_on wait until the database is ready?

Not by default. The short form waits only until the database container is running, and a database needs time after that to accept connections. Readiness needs a healthcheck on the database, such as `pg_isready`, and `condition: service_healthy` on the app.

### With service_healthy in place, does the app still need retry logic?

Yes. The condition only controls the first start. Later, the database can restart, be recreated with a new IP or drop connections, and Compose does not hold the app back then. The app or its connection pool must reconnect.
