## What it is

Two ideas decide how fast a build is. The build context is the set of files that `docker build` sends to the builder, the part of Docker that runs the steps. It is the folder named by the last argument of `docker build`, usually `.`. The layer cache is the builder's store of earlier step results: when a step and its inputs have not changed, the builder reuses the saved [layer](card:images-and-layers) instead of running the step again.

## Why it exists

Downloading the payment service's Maven dependencies takes minutes. If every one-line code change ran that download again, every build would take minutes. The cache skips it, but only when the Dockerfile copies `pom.xml` and downloads dependencies before it copies the source. A large context costs time too: sending `.git` and IDE folders slows every build, and a stray `.env` file can end up inside the image.

## How it works

1. `docker build` collects the context, drops every file matched by `.dockerignore`, and sends the rest to the builder.
2. For each instruction, the builder looks for a cached result built on the same previous layer with the same instruction.
3. For `COPY` and `ADD`, it also compares a checksum of the copied files' content and metadata. A changed file is a miss; a new modification time alone is not.
4. For `RUN`, it compares only the command text. It never checks whether newer packages exist online.
5. After the first miss, every later step runs again, even if its own line did not change.

So the key is to put the steps that change rarely first and the source code last.

## Example

A cache-friendly order for the payment service, plus the `.dockerignore` next to it.

```dockerfile
FROM eclipse-temurin:25-jdk
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline
COPY src src
RUN ./mvnw package -DskipTests
```

```text
.git
.env
.idea
target/
```

What to notice:

- `pom.xml` is copied alone, so the slow `dependency:go-offline` layer depends only on it. A change to a `.java` file leaves that layer cached.
- Adding a dependency to `pom.xml` is a miss from line 3, so the download runs again, as it should.
- Write `COPY . .` before the download instead, and any change to any file, even a README, re-downloads every dependency.
- `target/` is ignored because Maven builds the jar inside the image. This image still ships the JDK and Maven; [multi-stage builds](card:multi-stage-builds), next, leave them behind.

## Rules and defaults

- **Inside the context only:** `COPY` sources are relative to the context root. A path such as `../config` does not escape it; Docker strips the `../`.
- **.dockerignore:** read from the root of the context. If the Dockerfile copies `target/*.jar` from the host, do not ignore `target/`.
- **`--no-cache` and `--pull`:** `--no-cache` runs every step again; `--pull` checks the registry for a newer base image. Use both for a fully fresh build.
- **Cache mounts (BuildKit):** `RUN --mount=type=cache,target=/root/.m2 ./mvnw package` keeps Maven's download folder between builds, so even after a miss only new or changed packages are downloaded.

## Common mistakes

- **".gitignore keeps files out of the image."** Docker reads only `.dockerignore`. A `.env` file that Git ignores is still in the context, and `COPY . .` puts it into the image.
- **"--pull fixes stale packages."** It refreshes only the base image. If the base has not changed, your own `RUN apt-get` steps stay cached; add `--no-cache`.

## Interview Qs

### How does the Docker build cache work?

Each instruction's result is stored as a layer. On the next build, Docker reuses it if the instruction text and, for `COPY` and `ADD`, the copied files are unchanged. Once one step misses, every later step runs again, so step order decides how much is reused.

### Why copy pom.xml before the source code?

Dependencies change less often than code. Copying `pom.xml` alone and downloading dependencies first keeps that slow step cached; a code change then reruns only the compile and package steps.

### What is the build context, and why use .dockerignore?

The context is the set of files the build can read, usually the folder passed to `docker build`. `.dockerignore` removes files the image does not need, such as `.git`, `.env` and IDE folders, so the context is sent faster and secrets cannot be copied in by accident.
