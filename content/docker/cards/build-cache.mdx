## Why it exists

Rebuilding everything after a one-line code change is slow. The cache skips steps whose inputs did not change, if the Dockerfile puts them in the right order.

## How it works

<Steps label="Cache-friendly order for the payment service">
  <Step title="COPY pom.xml">Changes rarely, so this layer stays cached.</Step>
  <Step title="RUN ./mvnw dependency:go-offline">Downloads libraries; reused while pom.xml is unchanged.</Step>
  <Step title="COPY src">Changes on every commit: the cache misses from here.</Step>
  <Step title="RUN ./mvnw package">Compiles only; the libraries are already in the layer above.</Step>
</Steps>

- `.dockerignore` keeps `.git`, `.env` and IDE files out of the context: smaller uploads, fewer misses, no leaked secrets.
- `RUN --mount=type=cache,target=/root/.m2` (BuildKit) keeps Maven downloads even after a miss.
- If the Dockerfile copies `target/*.jar`, do not ignore `target/`; a [multi-stage build](card:multi-stage-builds) avoids the problem.

## Example

```text
# .dockerignore
.git
.env
.idea
target/
```

## Interview Qs

### How does the Docker build cache work?

Each instruction's result is cached. If the instruction and its input files are unchanged, Docker reuses it. Once one step misses, every later step runs again.

### Why copy pom.xml before the source code?

Dependencies change less often than code. Copying pom.xml and downloading them first keeps that slow step cached; a code change only reruns the compile.

### What is the build context, and why use .dockerignore?

The context is the set of files the build can read, usually the folder passed to docker build. .dockerignore removes files the image does not need, such as .git and .env.
