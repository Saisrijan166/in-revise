## What it is

A mount puts storage from outside the container at a folder inside it. Docker has three kinds. A volume is storage that Docker creates and manages on the host. A bind mount is an existing host file or folder that appears inside the container as it is. A tmpfs mount is a folder kept only in the host's memory.

## Why it exists

As [images and layers](card:images-and-layers) showed, a container writes its files into its own writable layer, and `docker rm` deletes that layer. A PostgreSQL container for the payment service would lose every payment when you replace it with a newer image. Mounting a volume on the database's data folder sends those writes outside the container. The container becomes disposable, and the data stays.

## How it works

1. You create a named volume, `pgdata`. Docker keeps it in its own storage area on the host.
2. You start PostgreSQL with `-v pgdata:/var/lib/postgresql`. Writes to that folder go into the volume, not into the writable layer.
3. You remove the container with `docker rm`. Its writable layer is deleted; the volume is untouched.
4. A new container mounts the same volume and sees all the data.

So the key is: what lives in a mount survives the container; what lives in the writable layer does not.

## Example

The payment database keeps a table after its container is removed and recreated.

```bash
docker volume create pgdata
docker run -d --name postgres -e POSTGRES_PASSWORD=dev-only \
  -v pgdata:/var/lib/postgresql postgres:18
sleep 5                                # let PostgreSQL start
docker exec postgres psql -U postgres -c "CREATE TABLE payments(id int)"

docker rm -f postgres                  # container and writable layer gone
docker run -d --name postgres -e POSTGRES_PASSWORD=dev-only \
  -v pgdata:/var/lib/postgresql postgres:18
sleep 5
docker exec postgres psql -U postgres -c "\dt"   # payments is still listed
```

What to notice:

- `-v pgdata:/var/lib/postgresql` means "volume name : path in the container". The second container uses the same name, so it gets the same data.
- `postgres:18` keeps its data under `/var/lib/postgresql`; images up to 17 used `/var/lib/postgresql/data`. Mount the path your image version uses.
- Without `-v`, the image's VOLUME instruction makes Docker create an anonymous volume with a random name, and the second container would start empty.
- `docker volume inspect pgdata` shows where the data lives: `/var/lib/docker/volumes/pgdata/_data` on Linux.

## Rules and defaults

- **Survives removal:** `docker rm` never removes a named volume, and removing an image does not touch volumes. You delete a named volume on purpose with `docker volume rm`.
- **Anonymous volumes:** `docker rm -v` and containers started with `--rm` remove their anonymous volumes. Otherwise anonymous volumes stay behind, unattached.
- **Prune:** `docker volume prune` removes unused anonymous volumes; `-a` also removes unused named ones (API 1.42+, Docker Engine 23.0).
- **Hiding:** a mount hides the image's files at that path while it is mounted. An empty volume is first filled with those files; `volume-nocopy` stops that. A bind mount always hides them.
- **Syntax:** `-v` is short; `--mount type=volume,src=pgdata,dst=/var/lib/postgresql` is more explicit and is the form Docker recommends. Add `ro` (or `readonly`) to make a mount read-only.
- **Bind mount writes:** by default the container can change the host's files through a bind mount.
- **tmpfs:** Linux only, cannot be shared between containers, removed when the container stops. Its size limit is half of the host's RAM unless you set one, and its data can be swapped to disk.

## Not to be confused with

A volume lives in Docker's own storage area and is managed with `docker volume` commands. A bind mount is a host path you choose, so it depends on that host's folder layout. A tmpfs mount is memory that disappears when the container stops. Rule: volume for data, bind mount for host files in development, tmpfs for scratch data.

## Common mistakes

- **Running `docker volume prune -a` casually.** It deletes every named volume that no container uses, such as the database volume while its container is removed for an upgrade, and the data with it.
- **Editing files under `/var/lib/docker/volumes` by hand.** Work with volume data through a container, or back it up with a container that mounts the volume.

## Interview Qs

### How do you upgrade a database container without losing data?

Keep the database's data folder on a named volume. Remove the old container and start the new image with the same volume at the same path. The writable layer is thrown away, but the data was never in it.

### Volume or bind mount for a Spring Boot app in development?

A bind mount for the source code or configuration you edit on the host, so changes appear inside at once. A named volume for the database, because Docker manages it and it does not depend on any host folder. Bind mounts tie the container to one machine's folder layout.

### What happens to the image's files when you mount over a folder?

They are hidden while the mount is active. A bind mount or a non-empty volume shows only its own content. An empty volume is first filled with the image's files, which is how a fresh volume gets defaults from the image.
