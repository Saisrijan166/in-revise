## What it is

A multi-stage build is a Dockerfile with more than one `FROM` line. Each `FROM` starts a new stage: a separate build with its own base image and none of the earlier stage's files. A later stage can copy files out of an earlier one with `COPY --from`. Only the last stage becomes the image you ship; the earlier stages are scaffolding.

## Why it exists

The [cache-friendly Dockerfile](card:build-cache) builds the jar, but the image it ships still holds the JDK, Maven, the source code and every downloaded library. None of them is needed to run the jar. They make the image larger, slow down every pull, and add software that must be patched when a vulnerability is found. A multi-stage build keeps the building in one stage and ships only the result.

## How it works

1. Docker runs the first stage, named `build`, from the JDK image. Maven downloads libraries and produces the jar inside it.
2. The second `FROM` starts a new stage from the JRE image, a Java runtime without a compiler. None of the build stage's files are there.
3. `COPY --from=build` copies one file, the jar, out of the build stage into the new stage.
4. The last stage becomes the image. The build stage is not tagged or pushed; its layers stay only in the builder's cache, which speeds up the next build.

So the key is that you choose, file by file, what crosses into the shipped image.

## Example

The payment service is built and packaged in one Dockerfile, with no Maven needed on the build machine.

```dockerfile
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline
COPY src src
RUN ./mvnw package -DskipTests

FROM eclipse-temurin:25-jre
COPY --from=build /src/target/payment-service-1.4.0.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

What to notice:

- The first seven lines are the cache-friendly build from the previous concept, now named `build` with `AS build`.
- The final stage starts from `25-jre`, so the shipped image has a Java runtime but no compiler, Maven or source code.
- `COPY --from=build` names the stage, not a number, so it keeps working if someone adds a stage above it.
- Delete the last three lines and you ship the build stage itself. With a small Spring Boot web app, that stage takes about 840 MB on disk, against about 500 MB for the two-stage image.

## Rules and defaults

- **Stage names:** `FROM image AS name`. Stages without a name are numbered from 0, so `COPY --from=0` also works but breaks when stages move.
- **Any image as a source:** `COPY --from=` can also name an image, such as `COPY --from=nginx:1.30-alpine /etc/nginx/nginx.conf /nginx.conf`.
- **Target stage:** the last stage by default; `docker build --target <name>` stops at another one.
- **Skipped stages:** BuildKit builds only the stages the target depends on. The legacy builder built every stage up to the target.
- **Environment:** a stage inherits `ENV` values only from the stage it starts `FROM`, not from other stages it copies from.

## Common mistakes

- **Copying a whole folder across:** `COPY --from=build /src /app` brings the sources and the build output back into the final image. Copy only the jar.
- **"The tests ran because the image built."** `-DskipTests` skips them, and a separate test stage runs only when it is the target or the final stage depends on it.

## Interview Qs

### What is a multi-stage build, and why use it?

A Dockerfile with several `FROM` stages. Early stages compile and package; the final stage copies only the result with `COPY --from`. The shipped image has no build tools or sources, so it is smaller, pulls faster and has fewer packages to patch.

### How do you run tests or debug a single stage?

Build with `--target`, for example `docker build --target test .`. The build stops at that stage, so CI can run a test stage, or you can open a shell in the build stage to see why a step fails.

### Does the final image contain the build stage's layers?

No. The final image has its own base image's layers plus the files you copied in. The build stage's layers stay in the build cache, where they speed up the next build, but they are never part of the shipped image.
