## What it is

A container is your app running as a normal process, but walled off: it sees only its own files, network and list of processes. Its files come from an image, a package holding your app, the runtime it needs (such as Java 25) and a few OS files. A virtual machine (VM) is a whole simulated computer that boots its own operating system. The difference is the kernel, the core of the OS that talks to the hardware: every VM has its own, while all containers share the host's.

## Why it exists

Today you run `java -jar payment-service.jar` on your laptop and it works. On the server it fails, because the server has Java 21 instead of 25, or another library version. One old fix was a VM per app, but each VM carries a full OS: gigabytes of disk and a slow boot. A container carries the app together with its own Java and files, so it runs the same everywhere, and it starts as fast as a process.

## How it works

<Compare id="container-vs-vm" />

1. **Starting a VM:** a hypervisor, the software that splits one machine into several virtual ones, gives the VM virtual hardware. The VM boots its own kernel and OS services, and only then runs `java -jar`.
2. **Starting a container:** Docker asks the host kernel to start `java -jar` straight away, as a process with a private view of files, network and other processes. Nothing boots.
3. **Inside the container**, the process sees the files from its image, so it uses the image's Java, not the host's.
4. **Every system call**, such as opening a file or a network socket, goes to the one shared host kernel.

So the key is the kernel: a VM brings its own, a container borrows the host's. How Linux hides and limits a container is in [namespaces and cgroups](card:namespaces-and-cgroups).

## Example

The same machine, asked the same questions from the host and from a container. `docker run --rm IMAGE COMMAND` starts a container from an image, runs one command in it, and deletes the container when the command ends.

```bash
java -version 2>&1 | head -1                                         # host
docker run --rm eclipse-temurin:25-jre java -version 2>&1 | head -1  # container
grep PRETTY /etc/os-release                                          # host
docker run --rm eclipse-temurin:25-jre grep PRETTY /etc/os-release   # container
uname -r                                                             # host
docker run --rm eclipse-temurin:25-jre uname -r                      # container
```

```text output
openjdk version "21.0.12.1" 2026-08-18
openjdk version "25.0.4.1" 2026-08-18 LTS
PRETTY_NAME="Ubuntu 24.04.4 LTS"
PRETTY_NAME="Ubuntu 26.04.1 LTS"
7.0.0-38-generic
7.0.0-38-generic
```

What to notice:

- Java differs: the host has Java 21, but the container uses the Java 25 that ships inside the `eclipse-temurin:25-jre` image. This is how the payment service gets the same Java on every server.
- The OS files differ too: the image carries Ubuntu 26.04 libraries on an Ubuntu 24.04 host.
- `uname -r` prints the kernel version, and it is the same in both lines. The container has no kernel of its own.

## Rules and defaults

- **Linux needs Linux:** a Linux container needs a Linux kernel. On macOS and Windows, Docker Desktop runs a small Linux VM and the containers run inside it; on Windows the default backend is WSL 2.
- **Windows containers:** a separate kind of image built for the Windows kernel, so it needs a Windows host.
- **Not rivals:** in the cloud you rent VMs and run several containers on each one, so you get the VM's boundary and the container's packing.

## Common mistakes

- **"Containers replace VMs."** They solve different problems: VMs split hardware with a strong boundary, containers package and pack apps. Most production containers run inside VMs.
- **"The image must match the host's Linux distribution."** Only the kernel is shared. An image with Ubuntu or Alpine files runs on any Linux host with a suitable kernel.

## Interview Qs

### Can a Linux container run on a Windows or macOS machine?

Not directly, because its process needs a Linux kernel. Docker Desktop runs a small Linux VM, using WSL 2 by default on Windows, and the containers run inside that VM. Windows containers are a separate kind that need a Windows host.

### Does a container contain a full operating system?

No. It carries user-space files from its image, such as libraries, a shell and package lists, but no kernel. Every container on a host uses the host's kernel, which is why it starts like a process instead of booting.

### Why does a container start so much faster than a VM?

A VM must boot a guest kernel and OS services before your app runs. A container is a process the host kernel starts directly, with a restricted view of the system, so the start time is mostly your app's own start time.

### Containers or VMs: which would you choose?

Usually both. VMs give a strong boundary and can run any OS; containers pack many apps densely and start fast. In the cloud I run several containers on each VM, and I use separate VMs when tenants must not share a kernel.
