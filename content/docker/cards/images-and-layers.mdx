## Why it exists

Shipping a full filesystem for every version would waste disk and bandwidth. Layers let images share common parts, so Docker stores and moves only the layers that changed.

- List an image's layers with `docker history payment-service:1.4.0`.
- Data that must outlive the container goes in a [volume](card:volumes-and-mounts); slimming images is in [image size](card:image-size-optimization).

## Example

```dockerfile
FROM eclipse-temurin:25-jre               # base image: its layers come first
COPY payment-service.jar /app/app.jar     # new layer
LABEL team="payments"                     # metadata only, no layer
CMD ["java", "-jar", "/app/app.jar"]      # metadata only, no layer
```

## Interview Qs

### What is the difference between an image and a container?

An image is a read-only template: layers plus settings. A container is a runnable instance of it with its own writable layer. One image can run as many containers.

### A container writes a file. Where does it go, and when is it lost?

Into the container's writable layer. It survives stop and start, but docker rm deletes it. Keep data that must last, such as Postgres files, in a volume.

### Why is the second pull of a similar image fast?

Layers are shared. An image built on eclipse-temurin reuses base layers already on the host, so a pull downloads only the missing layers.
