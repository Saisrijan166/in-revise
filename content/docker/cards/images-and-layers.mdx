## What it is

An image is the read-only package a [container](card:containers-and-vms) starts from: files, such as the OS libraries, Java and your jar, plus settings, such as the command to run. It is stored as a stack of layers. A layer is one set of file changes, such as "add app.jar". When a container starts, Docker puts a thin writable layer on top, and every change the container makes goes there.

## Why it exists

Without layers, every release of the payment service would be one big file holding the OS files, Java and the jar, stored and downloaded again in full even when only the jar changed. With layers, the OS and Java layers are shared: a new release adds just a new jar layer, and servers download only that. Because the image is read-only, ten containers can share one copy of it on disk.

1. A build starts from a base image, named in the `FROM` line of a Dockerfile, the recipe file for an image. Its layers come first.
2. Each later step that changes files, such as `COPY` or `RUN`, adds one new read-only layer that records only what changed. Steps that only set settings, such as `CMD`, add no layer.
3. When the build ends, the image is fixed. Changing it means building a new image.
4. `docker run` adds an empty writable layer for the new container. Reading a file uses it straight from the image layer that holds it; nothing is copied.
5. The first time the container changes a file from the image, Docker copies it up into the writable layer and changes the copy. This is called copy-on-write.

So the key is: layers below are shared and never change, and each container writes only to its own layer on top.

## Example

A first Dockerfile for the payment service, saved next to its built jar. The [Dockerfile instructions](card:dockerfile-instructions) concept covers every instruction.

```dockerfile
FROM eclipse-temurin:25-jre
COPY target/payment-service.jar /app/app.jar
LABEL team="payments"
CMD ["java", "-jar", "/app/app.jar"]
```

Build it, then list the image's layers from the newest down:

```bash
docker build -q -t payment-service:1.4.0 .
docker history --format 'table {{.CreatedBy}}\t{{.Size}}' payment-service:1.4.0 | head -5
```

```text output
sha256:b708dc5a1185f3b55b4b3f6761d8a9519de3cfff034a8a235fa81853e831c0ea
CREATED BY                                      SIZE
CMD ["java" "-jar" "/app/app.jar"]              0B
LABEL team=payments                             0B
COPY target/payment-service.jar /app/app.jar…   12.3kB
ENTRYPOINT ["/__cacert_entrypoint.sh"]          0B
```

What to notice:

- `FROM eclipse-temurin:25-jre` brings all the base image's layers. The last line of the output is already one of them.
- `COPY` is the only step here that changes files, so it is the only one with a size. That small layer is all a server must download for a new release.
- `LABEL` and `CMD` show `0B`: they change only the image's settings. `CMD` is the command a container runs when it starts.
- `-t payment-service:1.4.0` gives the image a name and a version, called a tag. [Registries](card:registries) explains tags.

## Rules and defaults

- **Layer-making steps:** steps that change files, such as `RUN`, `COPY` and `ADD`, add a layer. Adding and deleting files both add a layer.
- **Read-only image:** a container never changes its image. A rebuild makes a new image; old containers keep running the old one.
- **Writable layer lifetime:** it survives `docker stop` and `docker start`, and `docker rm` deletes it. Data that must last goes in a [volume](card:volumes-and-mounts).
- **Write speed:** writes through copy-on-write are slower than the host's own disk, so write-heavy data such as database files belongs in a volume.

## Not to be confused with

An image is the read-only template that you build or pull. A container is one running copy of it, with its own writable layer and its own process. Rule: build and ship the image once; run as many containers from it as you need.

## Common mistakes

- **"Changing a file inside a running container updates the image."** The change goes only to that container's writable layer; the image and other containers do not see it.
- **"Each image keeps its own copy of the Java base."** Images built on the same base share those layers on disk and in downloads.

## Interview Qs

### What is the difference between an image and a container?

An image is a read-only template: a stack of layers plus settings such as the start command. A container is a runnable instance of it, with its own writable layer and process. One image can run as many containers as you need.

### A container writes a file. Where does it go, and when is it lost?

Into the container's thin writable layer. It survives a stop and start of the same container, but `docker rm` deletes it. Data that must last, such as PostgreSQL's files, belongs in a volume.

### Why is pulling a second, similar image so fast?

Layers are shared. An image built on `eclipse-temurin:25-jre` reuses the base layers already on the host, so the pull downloads only the layers that are missing.

### Why does deleting a file in a later step not shrink the image?

Each layer records only changes. The delete adds a new layer that hides the file, but the earlier layer still holds it and still counts towards the image size. Delete temporary files in the same step that creates them.
