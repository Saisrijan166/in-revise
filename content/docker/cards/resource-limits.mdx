## What it is

A resource limit is a cap on how much memory, CPU or how many processes one container may use. You set it with flags on `docker run`, and Docker turns them into [cgroup](card:namespaces-and-cgroups) settings, which the Linux kernel enforces. A limit is a hard ceiling. A reservation or a share is softer: it only decides who gets what when the host is short.

## Why it exists

Without limits, every container on a host competes for the same memory and CPU. One payment-service instance with a memory leak can eat all the host's RAM; then the kernel starts killing processes to survive, and any of them can go, including the database next to it. A limit keeps the damage inside the container that caused it, and makes its usage predictable when you plan how many containers fit on a host.

## How it works

| Flag | What it does |
|---|---|
| `--memory` (`-m`) | Hard memory cap, at least 6 MB; going over it means an OOM kill |
| `--memory-swap` | Memory plus swap; set it equal to `--memory` for no swap |
| `--memory-reservation` | Soft memory limit, applied only when the host runs low |
| `--cpus` | Hard CPU cap, for example `1.5` CPUs; going over it means throttling |
| `--cpu-shares` | Relative CPU weight, default 1024; counts only when CPUs are busy |
| `--pids-limit` | Maximum number of processes; after that, creating a new one fails |

1. You start the container with `--memory 1g --cpus 1.5`. Docker writes these values into the container's cgroup.
2. While the app runs below the limits, nothing happens; the limits cost nothing.
3. When the app wants more CPU than 1.5 CPUs, the kernel lets it run for 150 ms in each 100 ms period, summed over all CPUs, and then makes it wait. The app gets slower, not killed.
4. When the app's memory reaches 1 GB and cannot be reclaimed, the kernel's OOM (out of memory) killer kills a process in the container. If that is PID 1, the container exits with code 137 and `docker inspect` shows `OOMKilled: true`.

So the key is: memory over the limit kills, CPU over the limit only slows down.

## Example

Two runs of a stand-in payment app that keeps allocating memory, both with a 256 MB limit and no swap. The first also forces a 1 GB heap:

```bash
docker run -d --name pay-oom -e MODE=hog -e JAVA_TOOL_OPTIONS=-Xmx1g \
  --memory 256m --memory-swap 256m payment-service:1.4.0
docker run -d --name pay-heap -e MODE=hog --memory 256m --memory-swap 256m payment-service:1.4.0
docker inspect -f '{{.Name}} exit={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}}' pay-oom pay-heap
```

```text output
3ecd477cc830c3a5570187433944ecfa5cf5faf7426c9b0f56587f33c19fc92e
b2dcba41a4b143f13ee2e9967fe0deac585319ad31563241827e7a361b564343
/pay-oom exit=137 OOMKilled=true
/pay-heap exit=1 OOMKilled=false
```

What to notice:

- `pay-oom`: the heap could grow to 1 GB, past the 256 MB limit, so the kernel killed the JVM. Its logs show no Java error at all, only the end.
- `pay-heap`: with no `-Xmx`, the JVM read the limit and kept its heap to a quarter of it, so it threw `java.lang.OutOfMemoryError: Java heap space` and exited with 1. That is a Java error you can see and fix, not a kernel kill.
- `--memory-swap` equal to `--memory` turns swap off, so the limit is reached at once instead of the app slowly swapping. How to size the heap is in [Java in containers](card:java-in-containers).

## Rules and defaults

- **No limits by default:** a container gets no memory, CPU or process limit unless you set one (Docker Engine 29).
- **`--memory-swap` unset:** if only `--memory` is set and the host has swap, the container may use as much swap as its memory limit.
- **CPU period:** `--cpus 1.5` equals a quota of 150 ms per 100 ms period (`--cpu-period` default 100 ms).
- **Compose:** use `deploy.resources.limits` (`cpus`, `memory`, `pids`), or `mem_limit` and `cpus` on the service.
- **Check usage:** `docker stats` shows live memory and CPU use against each limit.

## Not to be confused with

A limit (`--memory`, `--cpus`) is a ceiling the container cannot pass. A reservation (`--memory-reservation`) or a share (`--cpu-shares`) does not reserve anything up front; it only decides who is squeezed first when the host is short. Rule: limits protect the host, shares settle contention.

## Interview Qs

### What happens when a container goes over its memory limit? And its CPU limit?

Memory: the kernel's OOM killer kills a process in the container; if it is PID 1, the container exits with code 137 and `docker inspect` shows `OOMKilled: true`. CPU: the container is throttled to its quota and runs slower, but keeps running.

### What is the difference between a limit and a reservation?

A limit is a hard cap the container can never pass. `--memory-reservation` is a soft limit and `--cpu-shares` a relative weight; both act only when the host runs short of memory or CPU, and neither guarantees the container any capacity.

### Why should every production container have a memory limit?

Without one, a single leaking container can use all the host's memory. The kernel then kills processes to recover, and any of them can go: other containers, or even the Docker daemon, although Docker lowers the daemon's chance of being picked. A limit makes the leaking container the one that is killed.
