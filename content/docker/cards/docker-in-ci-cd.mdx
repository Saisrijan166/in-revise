## What it is

CI/CD is the automated pipeline that turns each commit into a running release: continuous integration builds and tests it, continuous delivery deploys it. With Docker the pipeline's output is an **image** in a [registry](card:registries). The core rule is **build once, promote**: the image is built one time, and the same image moves from test to staging to production.

## Why it exists

If each environment rebuilds the image, production may get different base layers or dependency versions than the ones that passed the tests, and a bug can appear only in production. A tag such as `latest` makes it worse, because it can point to different images over time. Building once and deploying the same image by digest means production runs exactly what CI checked.

## How it works

<Steps label="One pipeline run for payment-service">
  <Step title="Build">One image per commit, using a registry cache.</Step>
  <Step title="Test">Unit tests, then integration tests with Testcontainers.</Step>
  <Step title="Scan">Fail the job on serious CVEs.</Step>
  <Step title="Tag and push">Git SHA and 1.4.0, pushed to the registry.</Step>
  <Step title="Deploy">Staging, then production, by digest.</Step>
</Steps>

1. The runner builds the image. Because runners start empty, it imports layers from a registry cache with `--cache-from` and saves new ones with `--cache-to` ([build cache](card:build-cache)).
2. It runs unit tests, then integration tests that start real services in throwaway containers.
3. It scans the image and fails the job on serious CVEs ([secure images](card:image-security)).
4. It tags the image with the commit SHA and the version, such as `1.4.0`, and pushes it. The push returns the image's digest.
5. Staging deploys that digest; after approval, production deploys the same digest. Only [configuration](card:env-and-secrets) differs.

So the key is: the pipeline produces one immutable image, and every later step reuses it.

## Example

An integration test for the payment repository against a real PostgreSQL 18, using Testcontainers and Spring Boot 4.1. Imports are left out.

```java
@Testcontainers
@SpringBootTest
class PaymentRepositoryTest {
    @Container @ServiceConnection
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:18");

    @Autowired PaymentRepository payments;

    @Test
    void savesUpiPayment() {
        payments.save(new Payment("UPI", 500));       // a ₹500 UPI payment
        assertEquals(1, payments.count());
    }
}
```

What to notice:

- `@Container` makes Testcontainers start the Postgres container before the tests and remove it afterwards; the CI runner only needs a Docker daemon.
- `@ServiceConnection` tells Spring Boot to connect the app to that container. Without it you would copy the random port and password into `spring.datasource.*` yourself.
- `PostgreSQLContainer` is from `org.testcontainers.postgresql`, the Testcontainers 2 package used with Spring Boot 4.

## Rules and defaults

- **Cache mode:** `--cache-to` uses `mode=min` by default, which saves only the layers of the final image; `mode=max` also saves the build stages, which helps multi-stage builds.
- **Never change a release:** a fix is a new build with a new tag, never a re-push of the old tag.
- **Docker inside CI:** Docker-in-Docker runs a daemon inside the CI container and needs `--privileged`; mounting the host's `docker.sock` hands the job control of the host daemon ([runtime security](card:container-runtime-security)). Allow either only for trusted pipelines.

## Interview Qs

### How would you build and deploy a Docker image in a CI/CD pipeline?

Build once with a registry cache, run unit and integration tests, scan the image, tag it with the git SHA and the version, and push it. Then deploy that image by digest to staging, and after approval the same digest to production, changing only configuration.

### Why not deploy latest to production?

`latest` is only the default tag name, not a version. It can move, so two hosts may pull different images, and a rollback has no fixed target. I deploy a unique version tag, or better, the digest.

### How do you test code that needs a real database?

With Testcontainers. The test starts PostgreSQL in a throwaway container, and Spring Boot's `@ServiceConnection` points the app at it. Tests run against the real database engine and SQL dialect, not a mock or an in-memory substitute, and each run starts clean.
