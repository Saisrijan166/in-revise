## What it is

Runtime security is the set of `docker run` settings that limit what a container may do once it runs. The main tool is **Linux capabilities**: the kernel splits root's power into small pieces, such as "bind a port below 1024" or "change file owners", and a process gets only the pieces it is given. On top of that, Docker applies **seccomp**, a filter that blocks risky system calls, and **AppArmor**, a profile that limits file and device access.

## Why it exists

All containers share one kernel with the host, as [namespaces and cgroups](card:namespaces-and-cgroups) showed. A default container is fairly safe, but a hacked app inside it can still use whatever the run settings allow. A few flags make it much safer, and a few others, like `--privileged`, remove nearly all isolation. A [non-root image](card:image-security) is the first layer; these settings are the second.

## How it works

| Setting | What it stops |
|---|---|
| `--cap-drop ALL` | root-only kernel actions, such as raw sockets or changing file owners |
| `--read-only` + `--tmpfs /tmp` | writes to the container's files; scratch space stays in memory |
| `--security-opt no-new-privileges=true` | processes gaining extra privileges after start, for example through setuid programs |
| no `--privileged` | full host access: all capabilities and devices |
| no `docker.sock` mount | the container taking over the Docker daemon, and so the host |

1. When Docker creates a container, it keeps an allowlist of 14 capabilities and drops the rest. `--cap-drop ALL` drops these 14 too.
2. It applies the default seccomp profile, which blocks about 44 of more than 300 system calls, and the `docker-default` AppArmor profile on hosts that use AppArmor.
3. Your flags then narrow the container further: a read-only root filesystem, no new privileges, a non-root user.
4. `--privileged` reverses all of this: every capability, every host device, and the seccomp and AppArmor profiles turned off.

So the key is: start from the defaults, remove more, and never add `--privileged`.

## Example

The payment service runs with no capabilities and a read-only filesystem. The second command tries to write a file inside it.

```bash
docker run -d --name payment-service \
  --read-only --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges=true \
  -p 8080:8080 payment-service:1.4.0
docker exec payment-service touch /app/test
```

```text output
touch: cannot touch '/app/test': Read-only file system
```

What to notice:

- The write fails, so an attacker cannot drop a script into the app folder. Writing to `/tmp` works, because `--tmpfs /tmp` mounts a writable in-memory folder there.
- The app still answered on `/actuator/health` in this run: a Java web app on port 8080 needs no capabilities at all.
- If the app had to bind port 80, you would add back only `--cap-add NET_BIND_SERVICE`.

## Rules and defaults

- **Default capabilities (Docker Engine 29):** 14 are kept, including `CHOWN`, `NET_RAW`, `SETUID` and `NET_BIND_SERVICE`; the rest are not granted.
- **Default seccomp:** on for every container; `--security-opt seccomp=unconfined` turns it off, so avoid it.
- **The docker group:** members can control the daemon, which the Docker docs call root-level privileges.
- **Rootless mode vs userns-remap:** both map container root to an unprivileged host user. With userns-remap the daemon still runs as root; in rootless mode the daemon and containers both run as a normal user.
- **Resource limits** against noisy neighbours are separate: see [resource limits](card:resource-limits).

## Interview Qs

### Are containers completely isolated?

No. They share the host kernel, so isolation depends on configuration: dropped capabilities, the seccomp and AppArmor or SELinux profiles, a non-root user, and not adding risky flags like `--privileged` or a Docker socket mount. A VM has its own kernel and is a stronger boundary.

### What does --privileged do, and when is it used?

It gives the container every capability and all host devices, makes `/sys` writable, and turns off the default seccomp and AppArmor profiles. Such a container can get a root shell on the host. It exists for special cases such as running Docker inside Docker; I never use it for application containers.

### Why is mounting /var/run/docker.sock dangerous?

The socket is the Docker daemon's API, and the daemon runs as root. A container that can call it can start a new privileged container with the host's `/` mounted, which means full control of the host. Treat that mount like giving out root.
