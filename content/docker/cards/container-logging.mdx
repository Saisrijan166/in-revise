## What it is

Every process has two standard output streams: stdout for normal output and stderr for errors. When you run `java -jar` in a terminal, both appear on your screen. In a container there is no screen, so Docker captures both streams of the main process. A logging driver is the part of Docker that decides where those lines go: into files on the host (the default) or to an external log service.

## Why it exists

Containers are created and deleted all the time, and a log file written inside a container is hard to reach and disappears with it. If every app instead writes to stdout and stderr, Docker can collect logs the same way for every container, whatever language it is written in. You can then read them with one command, or send all of them to a central place where they survive the container.

## How it works

1. The app writes a line to stdout or stderr. Spring Boot logs to the console by default, so it needs no change.
2. The Docker daemon reads the line from the container's output stream and hands it to the container's logging driver.
3. With `json-file`, the default, the driver appends the line, with a timestamp and the stream name, to a file on the host.
4. `docker logs pay` reads those lines back; `-f` keeps following new ones, and `--since 10m` limits the time range.
5. With a remote driver such as `fluentd` or `awslogs`, the line is sent away instead, and a local copy, the dual logging cache, lets `docker logs` still show it.

## Example

The payment service is started with log rotation turned on for this one container:

```bash
docker run -d --name pay --log-opt max-size=10m --log-opt max-file=3 payment-service:1.4.0
docker logs pay
docker inspect -f '{{json .HostConfig.LogConfig}}' pay
docker info -f '{{.LoggingDriver}}'
```

```text output
fba92bdb78007e4d3f3c45bbdc30b34222db146d5ca0ada94d2866078e11a346
payment-service started on 8080
{"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}
json-file
```

What to notice:

- `docker logs` printed the line the app wrote to stdout. A line written to a file inside the container would not appear.
- The container uses the `json-file` driver, the daemon's default, with at most 3 files of 10 MB each, so its logs can never take more than about 30 MB.
- Remove the two `--log-opt` flags and the file grows without limit, until you remove the container or the disk is full.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Logging driver | `json-file` | Docker Engine 29 |
| json-file `max-size` / `max-file` | unlimited / 1, so no rotation | Docker Engine 29 |
| local driver | 5 files of 20 MB, compressed, about 100 MB per container | Docker Engine 29 |

- **Daemon-wide setting:** set `"log-driver"` and `"log-opts"` in `daemon.json`. Values in `log-opts` must be strings, for example `"max-file": "3"`.
- **Only new containers:** a changed `daemon.json` applies after a daemon restart, and only to containers created after it. Existing containers keep their old settings until you recreate them.
- **`max-file` needs `max-size`:** without a size limit there is nothing to rotate.
- **Engine logs are separate:** the Docker daemon's own logs are in the system journal on Linux, for example `journalctl -xu docker.service`.

## Common mistakes

- **Logging to a file inside the container.** `docker logs` stays empty, and the file is lost when the container is removed. Log to the console instead; official images such as nginx link their log files to `/dev/stdout` and `/dev/stderr` for this reason.
- **Keeping production logs only on the host.** If the host dies, the logs go with it. Ship them to a central store with a remote driver or a log agent.

## Interview Qs

### docker logs is empty, but the app is running. Why?

The app writes to a file instead of stdout and stderr, or the container uses the `none` driver, or a remote driver runs with the dual logging cache turned off. Make the app log to the console, which is the Spring Boot default.

### Container logs filled the host's disk. How do you fix it?

The default `json-file` driver does not rotate. Set `max-size` and `max-file` in `daemon.json`, as strings, restart the daemon and recreate the containers, or set them per container with `--log-opt`. The `local` driver rotates and compresses by default.

### Where should production logs go?

Off the host, to a central log store, so they survive the container and the host and can be searched across all instances. Use a driver such as `fluentd`, `awslogs` or `gcplogs`, or an agent that reads the log files. `docker logs` keeps working through the dual logging cache.
