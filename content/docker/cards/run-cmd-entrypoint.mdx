## Why it exists

An image needs steps that prepare it once and a command each container runs. A fixed program with changeable arguments lets one image serve many runs.

## How it works

<Compare id="run-vs-cmd-vs-entrypoint" />

- Write ENTRYPOINT and CMD as JSON arrays: [exec vs shell form](compare:exec-form-vs-shell-form).
- If the base image has a CMD, setting ENTRYPOINT clears it; set CMD again.
- Why java must be PID 1: [graceful shutdown](card:signals-and-graceful-shutdown).

## Example

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--spring.profiles.active=prod"]
```

| You type | The container runs |
|---|---|
| `docker run payment-service:1.4.0` | `java -jar app.jar --spring.profiles.active=prod` |
| `docker run payment-service:1.4.0 --server.port=9090` | `java -jar app.jar --server.port=9090` |
| `docker run -it --entrypoint sh payment-service:1.4.0` | `sh`, for a look inside |

## Interview Qs

### What is the difference between RUN, CMD and ENTRYPOINT?

RUN executes at build time and saves its result in the image. ENTRYPOINT sets the program a container starts. CMD sets default arguments, or the default command when there is no ENTRYPOINT.

### How do CMD and ENTRYPOINT work together?

With an exec-form ENTRYPOINT, CMD becomes its default arguments. Arguments after the image name in docker run replace CMD and are passed to the ENTRYPOINT.

### Why prefer the exec form?

Exec form starts java directly, so it is PID 1 and receives SIGTERM from docker stop. A shell-form ENTRYPOINT runs under /bin/sh -c, which does not pass signals on.
