## What it is

These are three [Dockerfile instructions](card:dockerfile-instructions) that all take a command but act at different times. `RUN` executes its command once, while the image is built, for example to create a folder or install a package. `ENTRYPOINT` and `CMD` execute nothing during the build: they record what a container should start. `ENTRYPOINT` is the program itself; `CMD` holds default arguments for it, which you can change each time you start a container.

## Why it exists

One image should serve many runs: production with the prod profile, a test run on another port, a debug session with a shell. If the whole start command were fixed, each variation would need its own image. Splitting it into a fixed program (`ENTRYPOINT`) and changeable defaults (`CMD`) lets you change the arguments at `docker run` without rebuilding. `RUN` is separate because setup work should happen once, at build time, not at every start.

## How it works

<Compare id="run-vs-cmd-vs-entrypoint" />

1. During `docker build`, each `RUN` line runs in order, and its file changes become a layer. `CMD` and `ENTRYPOINT` are only saved in the image's configuration.
2. If the file has several `CMD` or `ENTRYPOINT` lines, the build keeps only the last of each.
3. At `docker run`, Docker builds the start command: the `ENTRYPOINT` array followed by the `CMD` array.
4. Words you type after the image name replace `CMD`; the `ENTRYPOINT` stays. The `--entrypoint` flag replaces `ENTRYPOINT` and also drops the image's `CMD`.
5. The program that starts becomes the container's first process, called PID 1. `docker stop` sends this process the SIGTERM signal, a polite request to shut down.

So the key is: `ENTRYPOINT` is the fixed part, and `CMD` is the default you may replace.

## Example

The payment service always runs `java -jar app.jar`, and the prod profile is only a default.

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--spring.profiles.active=prod"]
```

| You type | The container runs |
|---|---|
| `docker run payment-service:1.4.0` | `java -jar app.jar --spring.profiles.active=prod` |
| `docker run payment-service:1.4.0 --server.port=9090` | `java -jar app.jar --server.port=9090` |
| `docker run -it --entrypoint sh payment-service:1.4.0` | `sh`, a shell for looking inside the image |

What to notice:

- With no arguments, the container runs `ENTRYPOINT` plus `CMD`, so the prod profile is on.
- `--server.port=9090` replaces the whole `CMD`, not only part of it, so the prod profile is gone. Pass both if you need both.
- `--entrypoint sh` swaps `java` for a shell and drops `CMD`, so `sh` starts with no stray arguments.

## Rules and defaults

- **Exec form:** a JSON array, such as `["java", "-jar", "app.jar"]`, with double quotes only. Docker starts the program directly, with no shell.
- **Shell form:** a plain string, such as `java -jar app.jar`, which Docker runs as `/bin/sh -c "..."` on Linux. Fine for `RUN`, but avoid it for `ENTRYPOINT` and `CMD`.
- **No variables in exec form:** `$JAVA_OPTS` inside a JSON array is not expanded, because no shell runs. Pass JVM options through the `JDK_JAVA_OPTIONS` environment variable, which the `java` launcher reads itself.
- **Inherited CMD:** setting `ENTRYPOINT` resets a `CMD` that came from the base image, so set `CMD` again if you need defaults.
- **Stop timeout:** `docker stop` waits 10 seconds by default after SIGTERM, then sends SIGKILL, which ends the process at once.

## Not to be confused with

Exec form and shell form are two ways to write the same instruction. Exec form is a JSON array and starts the program itself; shell form is a plain string that a shell runs. With a shell-form `ENTRYPOINT`, the shell is PID 1: it ignores `CMD` and run arguments, and it does not pass SIGTERM to `java`. Rule: JSON arrays for `ENTRYPOINT` and `CMD`; either form for `RUN`. Why PID 1 must handle signals is covered in [graceful shutdown](card:signals-and-graceful-shutdown).

## Interview Qs

### What is the difference between RUN, CMD and ENTRYPOINT?

`RUN` executes at build time and saves its result as a layer. `ENTRYPOINT` sets the program a container starts. `CMD` sets default arguments for it, or the whole default command when there is no `ENTRYPOINT`. Only `RUN` changes the image's files.

### How do CMD and ENTRYPOINT work together, and how do you override each?

With an exec-form `ENTRYPOINT`, `CMD` supplies its default arguments. Arguments after the image name in `docker run` replace `CMD` and are passed to the `ENTRYPOINT`. To replace the program itself, use `docker run --entrypoint`.

### Why should ENTRYPOINT use the exec form?

In exec form, `java` is PID 1 and receives SIGTERM from `docker stop`, so the app can shut down cleanly. In shell form, `/bin/sh` is PID 1 and does not forward the signal, so after 10 seconds Docker kills the app without a clean shutdown.
