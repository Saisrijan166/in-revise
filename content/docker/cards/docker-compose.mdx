## What it is

Docker Compose is a tool that runs an application made of several containers from one YAML file, usually named `compose.yaml`. Each entry under `services:` is one part of the app: an image plus its settings, such as ports, environment variables and volumes. `docker compose up` creates and starts all of them, and `docker compose down` removes them. Everything Compose creates for one app belongs to a **project**, which is named after the folder unless you choose a name.

## Why it exists

The payment service needs PostgreSQL and Redis next to it. Without Compose you type three long `docker run` commands, create a [network](card:docker-networking) by hand, and repeat every port, variable and [volume](card:volumes-and-mounts) flag, on every laptop. One typo and the app cannot reach its database. Compose writes all of that down once, in a file kept in Git, so every developer and CI job starts the same stack with one command.

## How it works

1. Compose reads `compose.yaml` and works out the project name, here `payments`, from the folder.
2. It creates a bridge network named `payments_default` and the named volumes, such as `payments_pgdata`.
3. It builds or pulls each service's image and creates its container, named like `payments-postgres-1`.
4. Each container joins the network under its service name. The app connects to `postgres:5432`: the service name and the container port. The host port in `ports:` is only for your browser or tools on the host.
5. When you run `up` again after a change, Compose recreates only the services whose configuration or image changed. A recreated container keeps its name but gets a new IP address.

So the key is: one file in, one network out, and services talk to each other by name.

## Example

The payment service with PostgreSQL and Redis, plus the everyday commands. `DB_PASSWORD` comes from a local `.env` file, explained in [Compose for local development](card:compose-in-practice).

```yaml
services:
  payment-service:
    build: .
    ports: ["8080:8080"]
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/payments
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
  postgres:
    image: postgres:18
    environment: { POSTGRES_DB: payments, POSTGRES_PASSWORD: "${DB_PASSWORD}" }
    volumes: ["pgdata:/var/lib/postgresql"]
  redis: { image: "redis:8" }
volumes:
  pgdata:
```

```bash
docker compose up -d --build        # build the app image, start all three
docker compose ps                   # one line per service with its status
docker compose logs payment-service # what the app printed
docker compose down                 # remove containers and network
```

What to notice:

- The database URL uses `postgres`, the service name. With `localhost` the app would look inside its own container and fail.
- `build: .` builds the payment service from the Dockerfile in this folder; Postgres and Redis use ready-made images.
- `pgdata` is a named volume, so `down` keeps the payments data; `down -v` would delete it.
- There is no `depends_on`, so the app may start before Postgres accepts connections. In a real run this stand-in app exited with "Connection refused". The fix is in [startup order](card:compose-startup-order).

## Rules and defaults

- **File name:** `compose.yaml` is preferred; `compose.yml`, `docker-compose.yaml` and `docker-compose.yml` still work. If both kinds exist, `compose.yaml` wins.
- **Project name:** `-p` first, then `COMPOSE_PROJECT_NAME`, then a top-level `name:`, else the folder name. CI jobs set a unique one so parallel builds do not collide.
- **What down removes:** the services' containers, the default network and the networks in the file. Named volumes go only with `-v`; external networks and volumes never.
- **Attached mode:** `docker compose up` without `-d` shows all logs, and stops all containers when the command exits.
- **Versions:** Compose v2 and v5 are both `docker compose`; v5 (2025) works the same as v2 and adds a Go SDK.

## Not to be confused with

A [Dockerfile](card:dockerfile-instructions) describes how to build **one image**. `compose.yaml` describes how to **run several containers together**, and can point to a Dockerfile with `build:`. Rule: Dockerfile = how to build one image; compose.yaml = how to run the whole app. Compose also runs everything on one host; running across many machines is orchestration, which you will see in [Docker, Compose and Kubernetes](card:docker-and-orchestration).

## Interview Qs

### What is Docker Compose, and when do you use it?

It runs a multi-container app from one YAML file. I use it for local development, integration tests in CI and simple single-server setups. It runs on one Docker host, so when the app must survive a machine failure or spread over many machines, I need an orchestrator such as Kubernetes.

### How do containers in one Compose project talk to each other?

All services join the project's default network under their service names, and Docker's DNS resolves those names. The app connects to `postgres:5432`, never to an IP, because a recreated container gets a new IP. Service-to-service traffic uses the container port, not the published host port.

### What is the difference between docker compose down and down -v?

`down` stops and removes the project's containers and networks, but named volumes stay, so the database data survives. `down -v` also deletes the named volumes in the file and anonymous volumes attached to the containers, so the data is gone.
