## What it is

Image security means building the image so that it gives an attacker as little as possible. Every package in an image can have a **CVE**, a publicly listed security hole. The rules are: start from a trusted, small base image, run the app as a **non-root user**, keep secrets out of the image, and **scan** it, which means comparing its packages with the list of known CVEs.

## Why it exists

An image is shipped to many servers and kept for months. If it carries an old library with a known hole and the app runs as root, one exploit gives the attacker root inside the container, and any container escape is then far worse. A password copied into a layer leaks to anyone who can pull the image. These rules shrink each of those risks before the container ever runs.

## How it works

<Steps label="Securing the payment-service image">
  <Step title="Base">A trusted base with only what the app needs.</Step>
  <Step title="User">Create a user and switch to it with USER.</Step>
  <Step title="Secrets">Nothing secret in ENV, ARG or copied files.</Step>
  <Step title="Scan">CI fails the build on serious CVEs.</Step>
  <Step title="Attest and rebuild">Attach an SBOM; rebuild often.</Step>
</Steps>

1. Choose the base: Docker Official Images, Verified Publisher images or hardened images, as small as the app allows ([smaller images](card:image-size-optimization) compares them).
2. In the Dockerfile, create a system user and switch to it with `USER`. Every later `RUN`, and the `CMD` or `ENTRYPOINT` of the container, then runs as that user.
3. Pass secrets at build or run time, never in `ENV`, `ARG` or a copied file ([secrets](card:env-and-secrets) shows how).
4. In CI, scan the built image: `docker scout cves --exit-code` or `trivy image --exit-code 1 --severity HIGH,CRITICAL`. A non-zero exit code fails the job.
5. Build with `--sbom=true` to attach a software bill of materials (SBOM), and rebuild on a schedule so patched base layers come in.

## Example

The payment service image runs as a user called `app` instead of root.

```dockerfile
FROM eclipse-temurin:25-jre
RUN groupadd --system app && useradd --system --gid app app
WORKDIR /app
COPY --chown=app:app target/payment-service.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

```bash
docker run --rm --entrypoint id payment-service:1.4.0
```

```text output
uid=999(app) gid=999(app) groups=999(app)
```

What to notice:

- `USER app` comes after the setup steps, because creating users needs root. Remove that line and the same command prints `uid=0(root)`.
- `--chown=app:app` makes the jar owned by the app user; without it the file belongs to root.
- `useradd --system` picked UID 999 here. The Docker docs suggest a fixed UID when other systems, such as volume permissions, depend on it.

## Rules and defaults

- **Default user:** root, unless the image sets `USER` or you pass `--user`. The `eclipse-temurin` images set no `USER`.
- **Provenance:** BuildKit adds a provenance attestation with `mode=min` by default; `--provenance=mode=max` adds more detail, `--provenance=false` turns it off.
- **SBOM:** not added by default; opt in with `--sbom=true`.
- **Scanner exit codes:** `docker scout cves --exit-code` returns 2 when it finds vulnerabilities; Trivy exits 0 unless you set `--exit-code`.
- **Docker Hardened Images:** minimal images that run as non-root by default; the core catalogue is free under Apache 2.0.

## Not to be confused with

A [tag](card:registries), such as `25-jre`, is a movable name the publisher can point at a newer, patched image. A digest, `sha256:...`, names exactly one image and never changes. Rule: tags bring fixes but can change under you; digests are repeatable but need a bot or a person to move them.

## Interview Qs

### Why should a container not run as root?

By default, root inside the container is UID 0 on the host too, limited only by namespaces, capabilities and seccomp. If the app is hacked, the attacker has root inside the container, and any kernel or runtime escape is far worse. A non-root `USER` limits the damage.

### Should you pin the base image to a digest?

Yes, for repeatable builds: a tag can move, a digest cannot. But pinning opts out of automatic security fixes, so I let a tool such as Dependabot raise pull requests that move the digest, and rebuild on a schedule.

### What is an SBOM, and why attach it?

A software bill of materials lists every package and version in the image. When a new CVE appears, you can check which images contain the affected package without pulling and unpacking each one.
