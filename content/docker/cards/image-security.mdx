## Why it exists

Every package in an image can carry a known hole. If the app also runs as root, one exploit gives the attacker root in the container.

## How it works

<Steps label="Securing the payment-service image">
  <Step title="Base">A trusted base with only what the app needs ([Smaller Images](card:image-size-optimization)).</Step>
  <Step title="User">Create a user and set `USER`; `RUN`, `CMD` and `ENTRYPOINT` then run as it.</Step>
  <Step title="Secrets">Nothing secret in `ENV`, `ARG` or copied files: see [secrets](card:env-and-secrets).</Step>
  <Step title="Scan">`docker scout cves --exit-code` or `trivy image --exit-code 1` fails CI on findings.</Step>
  <Step title="Attest">`docker buildx build --sbom=true --provenance=mode=max --push` attaches both to the image.</Step>
</Steps>

- Pin `FROM` by [digest](compare:tag-vs-digest); a bot or rebuild job moves it.
- Run-time flags: [Locking Down a Running Container](card:container-runtime-security).

## Example

```dockerfile
FROM eclipse-temurin:25-jre
RUN groupadd --system app && useradd --system --gid app app
WORKDIR /app
COPY --chown=app:app target/payment-service.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

## Defaults

| What | Default | Where |
|---|---|---|
| User inside a container | `root` (UID 0); `eclipse-temurin` sets no `USER` | Docker Engine 29 |
| Provenance attestation | `mode=min` added by default; `--provenance=false` turns it off | BuildKit (Buildx) |

## Interview Qs

### Why should a container not run as root?

A hacked app running as root gives the attacker root inside the container, one step from the host. A non-root `USER` limits the damage.

### Should you pin the base image to a digest?

Yes, for repeatable builds: a tag can move, a digest cannot. But patched bases stop arriving, so bump the digest and rebuild on a schedule.

### What is an SBOM, and why attach it?

A Software Bill of Materials lists every package in the image, so new CVEs can be matched without pulling it.
