## What it is

A Dockerfile is a plain text file that lists, in order, the steps to build an [image](card:images-and-layers). Each line starts with an instruction, a keyword such as `FROM` or `COPY`, followed by its arguments. `docker build` reads the file from top to bottom. Some instructions add files, and each of those becomes a layer; the others are saved as settings that a container reads when it starts.

## Why it exists

Without a Dockerfile you would start a container, install Java by hand, copy the jar in and save the result with `docker commit`. Nobody could see how that image was made, and the next build would differ. A Dockerfile writes every step down, so the image can be rebuilt with one command, reviewed like code and kept in Git.

## How it works

| Instruction | When it acts | What it does |
|---|---|---|
| `FROM` | Build | Picks the base image to start from |
| `RUN` | Build | Runs a command; the changed files become a layer |
| `COPY`, `ADD` | Build | Put files into the image as a layer |
| `ARG` | Build | A variable that exists only during the build |
| `WORKDIR` | Build and run | Sets the folder for later steps and for the container; created if missing |
| `ENV` | Build and run | Sets an environment variable that later steps and containers see |
| `USER` | Build and run | Sets the user for later `RUN` steps and for the container's program |
| `LABEL` | Stored | Adds key-value metadata, such as a version |
| `EXPOSE` | Stored | Documents the port the app listens on; it does not open it |
| `VOLUME` | Stored | Marks a folder whose data should live outside the container |
| `CMD`, `ENTRYPOINT` | Stored | The program and arguments a container runs |
| `HEALTHCHECK`, `STOPSIGNAL` | Stored | How Docker checks health and which signal stops the container |

1. You run `docker build -t payment-service:1.4.0 .`. The `-t` flag names the image, and the final `.` is the build context, the folder whose files the build may read (more in [build context and cache](card:build-cache)).
2. `FROM` loads the layers of the base image, here a Java runtime.
3. Each `RUN`, `COPY` or `ADD` runs in order and saves its file changes as a new layer on top.
4. Settings such as `ENV`, `EXPOSE` and `ENTRYPOINT` are written into the image's configuration. Nothing runs for them.
5. Later, `docker run` reads that configuration to decide which program to start, as which user and in which folder.

You will meet `EXPOSE` again in [publishing ports](card:port-mapping), `VOLUME` in [volumes and mounts](card:volumes-and-mounts), `HEALTHCHECK` in [health checks](card:container-health-checks) and `USER` in [secure images](card:image-security).

## Example

The payment service is already packaged by Maven. This Dockerfile wraps its jar in a Java 25 runtime image.

```dockerfile
# syntax=docker/dockerfile:1
FROM eclipse-temurin:25-jre
WORKDIR /app
LABEL org.opencontainers.image.version="1.4.0"
COPY target/payment-service-1.4.0.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

```bash
./mvnw package                            # the jar must exist first
docker build -t payment-service:1.4.0 .
```

What to notice:

- `eclipse-temurin:25-jre` has a Java runtime but no compiler. That is enough, because the jar was built before `docker build` ran.
- `COPY` writes to `app.jar` inside `/app`, because a relative destination is taken from `WORKDIR`. Remove `WORKDIR` and the jar lands in the base image's folder, which is `/` for `eclipse-temurin`.
- `EXPOSE 8080` and `ENTRYPOINT` add no files. They are notes in the image that `docker run` reads later.
- If you skip `./mvnw package`, the build stops at `COPY` because `target/` has no jar.

## Rules and defaults

- **FROM first:** a Dockerfile must start with `FROM`. Only `ARG` lines, comments and parser directives, such as the syntax line below, may come before it.
- **Missing tag:** with no tag or digest, `FROM` uses `latest`. Pin a version such as `25-jre`; [registries](card:registries) explains tags and digests.
- **WORKDIR:** created if it does not exist. Without one, the folder is `/` or whatever the base image set.
- **Syntax line:** `# syntax=docker/dockerfile:1` on the first line makes BuildKit use the latest stable 1.x Dockerfile syntax.
- **USER:** applies to the rest of the stage, so put it after the steps that need root, such as installing packages.

## Not to be confused with

`COPY` copies files from the build context; `ADD` can also download URLs, clone Git repositories and unpack local tar archives. Rule: use `COPY` unless you need one of `ADD`'s extras. `ARG` is a variable only during the build; `ENV` is stored in the image and every container sees it. Rule: `ARG` for build choices, `ENV` for app settings. A Dockerfile builds one image; a `compose.yaml` runs several containers together, as you will see in [Docker Compose](card:docker-compose).

## Interview Qs

### What is a Dockerfile, and how do you build an image from it?

A text file of instructions that produces an image: a base with `FROM`, files with `COPY` and `RUN`, and start-up settings with `ENTRYPOINT` and `CMD`. `docker build -t payment-service:1.4.0 .` runs it, sending the current folder as the build context.

### Which instructions run at build time, and which only matter at start?

`FROM`, `RUN`, `COPY`, `ADD` and `ARG` act during the build. `CMD`, `ENTRYPOINT`, `EXPOSE` and `HEALTHCHECK` are only stored for containers. `ENV`, `USER` and `WORKDIR` affect both.

### Your COPY of target/app.jar fails during docker build. What do you check?

First, that the jar exists: `docker build` does not run Maven, so run `./mvnw package` first. Second, that the file sits inside the build context and is not excluded by `.dockerignore`. A [multi-stage build](card:multi-stage-builds), later in this topic, removes the problem by building the jar inside the Dockerfile.
