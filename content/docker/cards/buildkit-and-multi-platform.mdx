## Why it exists

Containers share the host kernel, so an image must match the server's CPU type. Teams build on ARM laptops but deploy to x86 and ARM servers.

## How it works

<Mermaid
  alt="docker build is the Buildx client. It sends the build to the BuildKit builder, which pushes payment-service:1.4.0 as an image index pointing to a linux/amd64 image and a linux/arm64 image. An x86 server pulls the amd64 image; an ARM server pulls the arm64 image."
  chart={`flowchart LR
  C["docker build (Buildx client)"] --> K["BuildKit builder"]
  K --> I["payment-service:1.4.0 image index"]
  I --> A["linux/amd64 image"]
  I --> R["linux/arm64 image"]
  A -.-> S1["x86 server"]
  R -.-> S2["ARM server"]`}

- Other platforms are built by QEMU emulation, native nodes per platform, or cross-compiling.
- Multi-platform images need the containerd image store, the default in Docker Desktop and fresh Engine 29.0+ installs.
- The start-up error on the wrong CPU: [troubleshooting](card:troubleshooting-containers).

## Example

```bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t registry.example.com/payment-service:1.4.0 --push .
```

## Interview Qs

### What is BuildKit, and how does it relate to Buildx?

BuildKit is the build engine that runs the steps. Buildx is the client that sends it builds; since Engine 23.0, `docker build` is an alias of `docker buildx build`.

### How do you ship one image for x86 and ARM servers?

Build with `--platform linux/amd64,linux/arm64` and push. The tag points to an image index, and each server pulls the variant for its own CPU.
