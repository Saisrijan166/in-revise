## What it is

BuildKit is Docker's build engine: the part that reads a Dockerfile, runs each step and keeps the [build cache](card:build-cache). Buildx is the client that sends builds to BuildKit, and `docker build` is an alias for `docker buildx build`. A platform is an operating system and CPU type, such as `linux/amd64` for x86 servers or `linux/arm64` for ARM servers and Apple silicon Macs. A multi-platform image is one tag that holds a separate image for each platform.

## Why it exists

A container runs its programs directly on the host's CPU, so an image built for one CPU type does not run natively on another. That is true for Java too: the code is portable, but the JVM inside the image is a native program. Teams build on ARM laptops and deploy to x86 servers, ARM servers or both. Without multi-platform images you would push one tag per CPU type and pick the right one for each server.

1. You run `docker build` with `--platform linux/amd64,linux/arm64`. Buildx sends the Dockerfile and the context to BuildKit.
2. BuildKit runs the Dockerfile once per platform and pulls the matching variant of each base image.
3. `COPY` steps work for any platform. A `RUN` step for a foreign CPU runs under QEMU emulation or on a builder node with that CPU.
4. BuildKit pushes one image per platform plus an image index, a small list that maps each platform to its image.
5. A server that pulls `payment-service:1.4.0` gets the index, and Docker picks the entry that matches its own platform.

## Example

The payment service runs on x86 and ARM servers, so CI builds both variants and pushes them under one tag.

```bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t registry.example.com/payment-service:1.4.0 --push .
```

What to notice:

- `--platform` lists both targets. Without it, BuildKit builds only for its own platform.
- `--push` sends both images and the index to the registry in one step.
- The multi-stage Dockerfile from before needs no change: its `RUN ./mvnw` steps run under emulation for the foreign CPU, which works but is slower.

## Rules and defaults

- **Default builder:** BuildKit, on Linux since Docker Engine 23.0 and in Docker Desktop. Builds of Windows containers still use the legacy builder, and `DOCKER_BUILDKIT=0` forces it on Linux.
- **Default platform:** the platform of the BuildKit daemon that runs the build.
- **Keeping it locally:** a multi-platform image needs the containerd image store, the default in Docker Desktop and Docker Engine 29.0 and later. Otherwise use a `docker-container` builder and push the result.
- **Sharing the cache:** `--cache-to type=registry,ref=<image>` exports the build cache and `--cache-from` imports it, so a fresh CI runner can reuse earlier layers.

## Interview Qs

### What is BuildKit, and how does it relate to Buildx and docker build?

BuildKit is the engine that executes builds: it solves the steps as a graph, skips unused stages, runs independent ones in parallel and manages the cache. Buildx is the client. Since Engine 23.0, `docker build` is an alias for `docker buildx build` and uses BuildKit by default on Linux.

### How do you ship one image for x86 and ARM servers?

Build with `--platform linux/amd64,linux/arm64` and push. The tag then points to an image index with one image per platform, and each server pulls the variant for its own CPU. `RUN` steps for the other CPU need emulation or a native builder node.

### Why can an image fail to start on a server even though it works on your laptop?

The image may contain only your laptop's platform, for example `linux/arm64`, while the server is x86. Its native programs, including the JVM, cannot run there without emulation. Building for the server's platform, or for both, fixes it.
