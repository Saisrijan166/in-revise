## What it is

The playbook is the whole Docker tech on one page: the path the payment service takes from source code to a running, monitored container, with a link to the concept that owns each step. It also gives one method for answering any Docker question. Read it last, as a review; every term in it was taught in an earlier concept.

## Why it exists

Most Docker interview questions reuse about a dozen rules, asked from different angles: image versus container, build time versus run time, ports, volumes, networks and configuration. Candidates who memorised flags get stuck when the angle changes. If you can see how the pieces connect, you can work out a new question from the mechanism.

1. **Write:** a [multi-stage Dockerfile](card:multi-stage-builds) builds the jar with JDK 25 and runs it on JRE 25, as a [non-root user](card:image-security).
2. **Build:** `docker build -t payment-service:1.4.0 .` turns it into an [image made of layers](card:images-and-layers), reusing the [build cache](card:build-cache).
3. **Ship:** [CI](card:docker-in-ci-cd) tests and scans that image once and pushes it to a [registry](card:registries).
4. **Run:** a [container](card:container-lifecycle) starts from the image; at run time you add [published ports](card:port-mapping), a [network](card:docker-networking), [volumes](card:volumes-and-mounts) and [configuration](card:env-and-secrets).
5. **Keep it healthy:** a [health check](card:container-health-checks), [memory limits](card:resource-limits), [logs](card:container-logging) on stdout and a [graceful shutdown](card:signals-and-graceful-shutdown).
6. **Scale:** [Compose](card:docker-compose) runs it with Postgres and Redis on one host; [Kubernetes](card:docker-and-orchestration) runs the same image across many.

So the key is: the image is built once and never changes; everything environment-specific is added when a container starts.

## Example

The five-beat method, used on "What is a Docker volume?":

- **What:** a storage area managed by Docker and mounted into a container, which lives on after the container is removed.
- **Problem:** files in a container's writable layer are deleted with `docker rm`, so Postgres would lose every payment on a redeploy.
- **How:** `-v pgdata:/var/lib/postgresql` mounts the named volume `pgdata`; a new Postgres container mounts the same volume and finds the same data.
- **Trap:** `docker compose down` does not delete it; only `down -v` does.
- **When not:** source code you edit live is better as a bind mount, and a password belongs in a secret, not a volume.

What to notice:

- Each beat is one sentence and uses the running example, which keeps the answer short and concrete.
- The command appears only in "How", as proof of the mechanism.

## Rules and defaults

- **Build time:** `FROM`, `RUN`, `COPY`, `ADD` and `ARG` shape the image during `docker build`.
- **Run time:** `CMD` and `ENTRYPOINT` give the start command; `-p`, `-v`, `-e` and `--network` are added by `docker run` or Compose.
- **Both:** `ENV` sets a default in the image, and `-e` overrides it when the container starts.

## Interview Qs

### What happens when you run docker run -p 8080:8080 payment-service:1.4.0?

Docker pulls the image if it is not on the host, creates a container with a thin writable layer on top of the image's layers, and connects it to the default bridge network. It publishes host port 8080 to container port 8080, then starts the ENTRYPOINT plus CMD as the container's main process.

### Explain Docker in one minute.

An image is a read-only template built from a Dockerfile in layers; a container is a running copy with its own writable layer. Containers share the host kernel, so they start fast. Ports are published with `-p`, data lives in volumes, settings come from environment variables, and Compose runs several containers together.

### How would you containerise a Spring Boot service, end to end?

A multi-stage Dockerfile: build the jar with a JDK, run it on a JRE base as a non-root user, in exec form so SIGTERM reaches Java. Set a memory limit the heap fits into and a health check on `/actuator/health`. CI builds once, scans and pushes a unique tag; Compose runs it locally with Postgres and Redis.
