## What it is

The container lifecycle is the set of states a container moves through, from the moment Docker makes it from an [image](card:images-and-layers) to the moment you delete it. A container always has one main process, the command the image starts, and it is "running" only while that process runs. A restart policy is a setting on the container that tells Docker what to do when that process ends.

## Why it exists

You need to know, at any moment, whether your service is running, stopped but still on disk, or gone. Without that, you lose data in a stopped container you thought was deleted, or you pile up hundreds of dead ones. And when the payment service crashes at night, something has to start it again. A restart policy lets the Docker daemon do that, so you do not need a cron job or a person watching it.

## How it works

1. `docker create` makes the container: a new writable layer on top of the image, plus its settings. Nothing runs yet; the status is `Created`.
2. `docker start` starts the main process. The status is `Up`. `docker run` does steps 1 and 2 in one command.
3. The main process ends, because the app finished, crashed, or got a stop signal. The container is now `Exited (code)`, and its files and logs are still there.
4. Docker checks the restart policy. If the policy matches this exit, Docker starts the same container again after a short delay. If not, it stays exited.
5. `docker rm` deletes the container and its writable layer. Until then, `docker start` can bring it back as it was.

So the key is: exiting and removing are two different steps.

## Example

The payment service should come back after a crash, but stay down when you stop it on purpose. Here a stand-in app exits with code 1 on start, and the policy allows three restarts:

```bash
docker run -d --name pay -e MODE=crash --restart on-failure:3 payment-service:1.4.0
docker inspect -f 'status={{.State.Status}} exit={{.State.ExitCode}} restarts={{.RestartCount}}' pay
```

```text output
2e7b8382ebf6a709e5722c564c08828853e4bf5b5dfc43e45d92e5d636143a65
status=exited exit=1 restarts=3
```

What to notice:

- `on-failure:3` restarted the container three times after each non-zero exit, then gave up. The container is still there, so `docker logs pay` shows all four failed starts.
- Without `--restart`, the same command gives `restarts=0`: the default policy `no` never restarts.
- For a long-running service, `unless-stopped` is the usual choice, because it also starts the container again after the host reboots.

## Rules and defaults

| `--restart` | Restarts after the process exits | After the daemon restarts |
|---|---|---|
| `no` (default) | Never | Not started |
| `on-failure[:max-retries]` | Only on a non-zero exit code | Not started |
| `always` | Yes, unless you stopped it by hand | Started, even if you stopped it |
| `unless-stopped` | Yes, unless you stopped it by hand | Started, unless you stopped it |

- **Delay between restarts:** Docker waits before each restart, starting at 100 ms and doubling each time, up to 1 minute. The delay resets to 100 ms once the container has run for at least 10 seconds (Docker Engine 29).
- **Manual stop wins:** after `docker stop`, the restart policy is ignored until the daemon restarts or you start the container yourself.
- **Containers only:** restart policies apply to plain containers. Swarm services and Kubernetes have their own restart settings.
- **Other statuses:** `paused` (processes frozen with the cgroup freezer), `restarting`, `removing` and `dead` also appear in `docker ps -a`.

## Not to be confused with

`docker stop` asks the main process to end and waits; `docker kill` ends it at once. Both leave an exited container; only `docker rm` deletes it. How the app should react to the stop signal is in [graceful shutdown](card:signals-and-graceful-shutdown).

## Common mistakes

- **"docker stop deletes the container."** It only ends the main process. The container and its writable layer stay until `docker rm`, or until it exits when it was started with `--rm`.
- **"always and unless-stopped are the same."** They differ only after a manual stop followed by a daemon restart: `always` starts the container again, `unless-stopped` does not.

## Interview Qs

### What are the states of a Docker container?

Created after `docker create`, running after `docker start`, paused while frozen, and exited when the main process ends. An exited container keeps its files until `docker rm` removes it. `docker ps -a` also shows restarting, removing and dead.

### The service crashed at night and stayed down. Why, and how do you fix it?

The default restart policy is `no`, so Docker never restarts it. Run it with `--restart on-failure` to restart after a non-zero exit, or `unless-stopped` to also survive daemon restarts. Docker waits between restarts, starting at 100 ms and doubling up to 1 minute.

### What is the difference between always and unless-stopped?

Both restart the container whenever it exits, and neither restarts it right after you stop it by hand. The difference is the next daemon restart, for example after a host reboot: `always` starts the stopped container again, `unless-stopped` leaves it stopped.
