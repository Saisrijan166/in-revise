## Why it exists

Dev and prod need different settings from the same image. A password baked into an image leaks to anyone who can pull it.

## How it works

| Value | Pass it with | Avoid |
|---|---|---|
| Plain config: profile, DB URL | `-e` or `--env-file` | Baking it into the image |
| Build-time secret: repo token | `docker build --secret` + `RUN --mount=type=secret` | ARG, ENV, COPY of the file |
| Run-time secret: DB password | Compose `secrets:` file, or Vault / AWS Secrets Manager | ENV in the Dockerfile |

- Spring Boot reads secret files with `spring.config.import=configtree:/run/secrets/`.
- A copied file deleted later still sits in an older [layer](card:images-and-layers).

## Example

```yaml
services:
  payment-service:
    image: payment-service:1.4.0
    environment:
      SPRING_PROFILES_ACTIVE: prod
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/payments
  postgres:
    image: postgres:18
    environment: { POSTGRES_PASSWORD_FILE: /run/secrets/db_password }
    secrets: [db_password]
secrets:
  db_password: { file: ./db_password.txt }
```

## Defaults

| What | Default | Where |
|---|---|---|
| Build secret mount path | `/run/secrets/<id>`, mode 0400 | Dockerfile reference (BuildKit) |
| Compose secret path | `/run/secrets/<name>`, Linux containers only | Compose docs |

## Interview Qs

### How do you run the same image in dev and prod?

Pass config at run time: `-e SPRING_PROFILES_ACTIVE=prod`, `--env-file` or Compose `environment:`. Spring Boot maps them to its properties.

### Why are environment variables a weak place for secrets?

Every process can read them, `docker inspect` shows them, and they can end up in logs. Secret files are granted per service and protected by file permissions.

### How do you use a private repo token during docker build without leaking it?

`docker build --secret id=repo_token,src=token.txt .` and `RUN --mount=type=secret,id=repo_token` in the Dockerfile. It exists for that step only and is in no layer.
