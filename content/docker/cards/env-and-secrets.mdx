## What it is

Configuration is every value that changes between environments: the active profile, the database URL, a password. An environment variable is a `NAME=value` pair that a process reads when it starts. A secret is configuration that must stay private, such as a password or an API token. Docker lets you give each container its settings as environment variables and its secrets as files, instead of building them into the [image](card:images-and-layers).

## Why it exists

Dev, test and prod need different database URLs from the same payment-service image. If the URL is built into the image, you need one image per environment, and the image you tested is not the one you ship. A password built into an image is worse: anyone who can pull the image can read it. Passing values at run time keeps one image for every environment and keeps secrets out of it.

## How it works

| Value | Pass it with | Do not use |
|---|---|---|
| Plain setting: profile, database URL | `-e NAME=value` or `--env-file` at `docker run` | A value built into the image |
| Secret needed during the build: a private repo token | `docker build --secret` and `RUN --mount=type=secret` | ARG, ENV, or COPY of the file |
| Secret needed at run time: the database password | A read-only file at `/run/secrets/<name>`, or a secret manager such as Vault or AWS Secrets Manager | ENV in the Dockerfile |

1. You build one image with no environment-specific values in it.
2. At `docker run`, Docker sets the environment variables you pass. They override any ENV default from the image.
3. Spring Boot reads them: `SPRING_PROFILES_ACTIVE=prod` sets `spring.profiles.active`.
4. Secrets arrive as files mounted read-only, so they never appear in the container's environment or in `docker inspect`.

## Example

The payment service gets its profile and URLs as environment variables and the database password as a read-only file.

```bash
docker run -d --name payment-service --network payments-net \
  -e SPRING_PROFILES_ACTIVE=prod \
  --env-file payment.env \
  -v ./db_password.txt:/run/secrets/db_password:ro \
  payment-service:1.4.0

docker inspect --format '{{.Config.Env}}' payment-service
```

What to notice:

- `payment.env` holds lines such as `SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/payments`; lines that start with `#` are comments.
- `docker inspect` prints every env var in plain text, including `SPRING_PROFILES_ACTIVE=prod`. The password file's content appears nowhere in it.
- The password is a [bind mount](card:volumes-and-mounts) with `:ro`, so the app can read it but cannot change it.
- The postgres image reads `POSTGRES_PASSWORD_FILE=/run/secrets/db_password` instead of `POSTGRES_PASSWORD`, so the database gets its password from a file too.

During a build, a secret is passed only to the one step that needs it:

```dockerfile
FROM eclipse-temurin:25-jdk AS build
WORKDIR /src
COPY . .
RUN --mount=type=secret,id=repo_token,env=REPO_TOKEN \
    ./mvnw -q package
```

What to notice: build it with `docker build --secret id=repo_token,src=token.txt .`. The `env=REPO_TOKEN` option hands the secret to this one `RUN` step as an environment variable; containers from the image do not have it, and `docker history` does not show it. With `ARG REPO_TOKEN` instead, `docker history` shows the token's value.

## Rules and defaults

- **Precedence:** a run-time `-e` value overrides the image's ENV default for the same name.
- **`--env-file` format:** one `NAME=value` per line; `#` starts a comment. `-e NAME` with no value copies `NAME` from your shell, and leaves it unset if your shell has none.
- **Spring Boot names (4.1):** to turn a property into an env var name, replace dots with underscores, remove dashes and use upper case: `spring.main.log-startup-info` becomes `SPRING_MAIN_LOGSTARTUPINFO`.
- **Build secrets:** mounted at `/run/secrets/<id>` by default, readable only by the owner (mode 0400); BuildKit is required.
- **Secret files in Spring Boot:** `spring.config.import=optional:configtree:/run/secrets/` turns each file into a property named after the file.
- **Compose:** a `secrets:` entry is mounted at `/run/secrets/<name>`, only into the services you grant it; you will use it in [Docker Compose](card:docker-compose).

## Not to be confused with

ARG is a variable for the build only; ENV is a variable stored in the image that every container sees, as [ARG vs ENV](compare:arg-vs-env) shows. A secret is neither: it is handed to one build step, or mounted as a file into one running container. Rule: ARG for build choices, ENV or `-e` for settings, secret files for passwords.

## Common mistakes

- **"Deleting the copied key file in a later step removes it."** The file still sits in the earlier [layer](card:images-and-layers), and anyone can extract it from the image.
- **Logging the whole environment at startup.** Every value passed with `-e`, including any password you put there, ends up in the logs.

## Interview Qs

### How do you run the same image in dev and prod?

Keep the image free of environment-specific values and pass them at run time with `-e`, `--env-file` or Compose `environment:`. Spring Boot maps env var names such as `SPRING_DATASOURCE_URL` to its properties. The image you tested is then exactly the image you ship.

### Why are environment variables a weak place for secrets?

`docker inspect` shows them in plain text, they are often available to every process in the container, and they can end up in logs or error reports. A secret file is mounted only into the containers that need it, is protected by file permissions, and its content does not appear in the container's metadata.

### How do you use a private repo token during docker build without leaking it?

Pass it with `docker build --secret id=repo_token,src=token.txt` and read it in `RUN --mount=type=secret,id=repo_token`. The file exists only during that step and is stored in no layer. An ARG would show the value in `docker history`.
