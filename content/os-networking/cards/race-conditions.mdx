## Why it exists

Threads share memory, and the scheduler can switch them mid-step. Without rules, two updates interleave and one is lost.

## How it works

| Step | Thread A | Thread B | count |
|---|---|---|---|
| 1 | reads 0 | | 0 |
| 2 | | reads 0 | 0 |
| 3 | adds 1, writes 1 | | 1 |
| 4 | | adds 1, writes 1 | 1, not 2 |

- Fixes: a [lock](card:locks) around the [critical section](card:critical-section), an atomic operation, or no shared mutable data.
- Races depend on timing: they appear under load and hide in tests.

## Example

Example run, two threads:

```java
static int plain = 0;
static AtomicInteger atomic = new AtomicInteger();

public static void main(String[] args) throws InterruptedException {
    Runnable work = () -> {
        for (int i = 0; i < 100_000; i++) { plain++; atomic.incrementAndGet(); }
    };
    Thread a = new Thread(work), b = new Thread(work);
    a.start(); b.start(); a.join(); b.join();
    System.out.println("plain  = " + plain);
    System.out.println("atomic = " + atomic.get());
}
```

```text output
plain  = 166973
atomic = 200000
```

## Interview Qs

### Two users buy the last item at the same time. How do you stop selling it twice?

Make check and update one database step: `UPDATE stock SET qty = qty - 1 WHERE id = 7 AND qty > 0`, and expect one changed row. Under Read Committed (the default), PostgreSQL re-checks the WHERE on the newest row.

### Race condition vs data race?

A data race (Java memory model) is two accesses to one variable, one a write, with no happens-before order. A race condition is a timing bug; check-then-act on two atomic calls has one without a data race.
