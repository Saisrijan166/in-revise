## What it is

A race condition is a bug that appears when two threads use the same data at the same time, at least one of them writes to it, and the final result depends on the order in which they happen to run. Threads share memory, and the OS can [switch between them](card:context-switching) in the middle of an update, so the steps of one thread can interleave with the steps of another. When that interleaving changes the answer, you have a race.

## Why it exists

The problem is that an update you write as one line is often several steps for the CPU. `count++` reads the value, adds one, and writes it back. If two threads do this on a shared counter, both can read the same old value, and one increment is overwritten, so the count is too low. The same thing happens when two requests both check "is stock left?" and both act on the answer, selling the last item twice. Naming these critical sections, and making them atomic, is what stops the lost update.

## How it works

The table follows two threads running `count++` on a shared counter.

| Step | Thread A | Thread B | count |
|---|---|---|---|
| 1 | reads 0 | | 0 |
| 2 | | reads 0 | 0 |
| 3 | adds 1, writes 1 | | 1 |
| 4 | | adds 1, writes 1 | 1, not 2 |

1. Thread A reads the counter as 0.
2. Before A writes, the OS switches to Thread B, which also reads 0.
3. A writes 1, then B writes 1 as well.
4. Two increments ran, but the counter is 1, not 2: one update is lost.

So the key is to let only one thread run those steps at a time (a [lock](card:locks)), or to do the whole read-add-write as one atomic step.

## Example

Two threads each add to a plain `int` and to an `AtomicInteger` a hundred thousand times. One is a race, the other is safe.

```java
static int plain = 0;
static AtomicInteger atomic = new AtomicInteger();

public static void main(String[] args) throws InterruptedException {
    Runnable work = () -> {
        for (int i = 0; i < 100_000; i++) { plain++; atomic.incrementAndGet(); }
    };
    Thread a = new Thread(work), b = new Thread(work);
    a.start(); b.start(); a.join(); b.join();
    System.out.println("plain  = " + plain);
    System.out.println("atomic = " + atomic.get());
}
```

```text output
plain  = 193862
atomic = 200000
```

What to notice:

- `plain` should be 200000 but comes out lower, and the number changes each run: that is the race, with lost updates.
- `atomic.incrementAndGet()` does read-add-write as one atomic step, so no update is lost and the total is exactly 200000.
- The race only shows under real concurrency; a single-threaded run or a light test would print 200000 and hide the bug.

## Rules and defaults

- **A race needs three things:** shared data, concurrent access, and at least one writer. Two threads only reading cannot race.
- **Atomic classes:** `AtomicInteger`, `AtomicLong` and friends in `java.util.concurrent.atomic` make one variable's update atomic without a lock.
- **Compare-and-swap (CAS):** atomic classes use it under the hood; it writes only if the value is unchanged, else it re-reads and retries in a loop.
- **Across servers:** a lock or atomic class guards one JVM only. For a shared total, make the database do the check and change in one step, such as `UPDATE stock SET qty = qty - 1 WHERE id = 42 AND qty > 0`.

## Not to be confused with

A race condition is a timing bug in the logic: the outcome depends on thread order. A [data race](card:data-race) is the narrower memory-model term for two accesses to one variable, one a write, with no happens-before order. Rule: every data race can cause a race condition, but a race condition can exist with no data race, for example a check-then-act built from two separate atomic calls.

## Common mistakes

- **"Making each step thread-safe makes the whole thing thread-safe."** Two atomic calls, a check and then an act, are each safe alone but still race: another thread can change the value between them. Guard the check and the act together, in one lock or one conditional update.

## Interview Qs

### Two users buy the last item at the same time. How do you stop selling it twice?

Make the check and the update one database step: `UPDATE stock SET qty = qty - 1 WHERE id = 42 AND qty > 0`, and treat "zero rows changed" as sold out. Under Read Committed, PostgreSQL's default, the database re-checks the WHERE against the latest row, so only one update succeeds.

### What is the difference between a race condition and a data race?

A data race, in the Java memory model, is two accesses to one variable where at least one writes and there is no happens-before order between them. A race condition is a broader timing bug. Check-then-act on two atomic calls has a race condition but no data race, because each call is individually ordered.
