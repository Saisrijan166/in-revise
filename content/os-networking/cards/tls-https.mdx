## Why it exists

Plain HTTP can be read and changed by anyone on the path, and a fake server can pretend to be api.shop.example.

## How it works

<Mermaid
  alt="TLS 1.3 handshake. The client sends ClientHello with its key share and the server name. The server replies with ServerHello and its key share, then, encrypted, its Certificate, CertificateVerify and Finished. The client sends Finished, then the encrypted GET /orders/42."
  chart={`sequenceDiagram
  participant C as Client
  participant S as api.shop.example
  C->>S: ClientHello (key share, SNI)
  S-->>C: ServerHello (key share)
  S-->>C: Certificate, CertificateVerify, Finished (encrypted)
  C->>S: Finished
  C->>S: GET /orders/42 (session keys)`}
/>

- The client checks the chain: each certificate signed by the next, up to a trusted root, valid dates, matching name.
- TLS sits between HTTP and TCP; "OSI Layer 6" is a loose fit. In HTTP/3 it runs inside [QUIC](card:http-versions).
- Load balancers often end TLS: see [TLS termination](card:load-balancers-and-proxies).

## Interview Qs

### Why does TLS use both asymmetric and symmetric crypto?

Asymmetric crypto lets strangers agree a secret and prove identity, but it is slow. So the handshake uses it once, and fast symmetric keys encrypt everything after.

### What is forward secrecy?

Each connection uses fresh ECDHE keys that are thrown away. If the server's private key leaks later, recorded old traffic still cannot be decrypted.

### How can one IP serve HTTPS for many domains?

The client puts the hostname in the ClientHello (the SNI extension). The server reads it and picks the matching certificate.
