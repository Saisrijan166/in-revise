## Why it exists

A thread per connection wastes memory and switches when most connections sit idle. The [C10k problem](card:c10k-problem) asked how one server can hold 10,000 clients at once.

## How it works

<Steps label="One turn of an event loop">
<Step title="Register">Add each socket fd once with `epoll_ctl`.</Step>
<Step title="Wait">`epoll_wait` sleeps until one or more fds are ready.</Step>
<Step title="Dispatch">Run the callback for each ready fd: accept, read or write.</Step>
<Step title="Repeat">Go back to waiting. A callback that blocks stalls every connection.</Step>
</Steps>

| API | Each call | Limit |
|---|---|---|
| `select` | passes and checks the whole fd set | fds below 1024 (glibc) |
| `poll` | passes and checks the whole list | none fixed; slow at thousands |
| `epoll` | returns only the ready fds | scales to many idle fds |

## Interview Qs

### select vs poll vs epoll?

select and poll pass the whole fd list on every call and the kernel checks each one; select also stops at fd 1023 in glibc. epoll keeps the list in the kernel and returns only the ready fds.

### What happens if you block inside an event-loop callback?

Every other connection on that loop waits, because one thread runs all callbacks. Move blocking or CPU-heavy work to a worker pool, as Node.js does with libuv's pool, and keep callbacks short.

### Level-triggered vs edge-triggered epoll?

Level-triggered, the default, keeps reporting an fd while data remains. Edge-triggered reports only new arrivals, so use non-blocking fds and read until EAGAIN, or the loop can wait forever on data already there.
