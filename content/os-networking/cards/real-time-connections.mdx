## Why it exists

Plain HTTP only answers when the client asks. Chat, live order status and dashboards need the server to send news as soon as it happens.

## How it works

<Compare id="polling-vs-sse-vs-websocket" />

- A client stays on one server, so events made elsewhere must be fanned out to it (for example by pub/sub).
- Each open connection costs a [file descriptor](card:files-and-file-descriptors); one server holds many with an [event loop](card:io-multiplexing).
- Load balancers must allow long idle times: see [load balancers](card:load-balancers-and-proxies).

## Example

Order 42 status over SSE:

```text
GET /orders/42/events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream

id: 7
event: status
data: {"order": 42, "status": "SHIPPED"}
```

## Interview Qs

### How does a WebSocket connection start?

As an HTTP/1.1 GET with `Upgrade: websocket` and a `Sec-WebSocket-Key`. The server answers 101 Switching Protocols with `Sec-WebSocket-Accept`; then both sides exchange frames on that TCP connection (`wss://` adds TLS).

### What happens when an SSE connection drops?

The browser's EventSource reconnects by itself and sends the last event id in `Last-Event-ID`, so the server can resume from there. The `retry:` field sets the wait.
