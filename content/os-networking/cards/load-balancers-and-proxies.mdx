## What it is

A load balancer is one machine that sits in front of several identical backend servers. Clients send every request to it, and it forwards each to one of the servers. It also runs a [health check](card:lb-health-check): a small repeated probe of each server. When a server stops answering the probe, the load balancer stops sending it traffic. A [reverse proxy](card:reverse-proxy) is the wider idea: any server that stands in front of your backends and speaks to clients for them. Load balancing is one job it can do.

## Why it exists

One server has a ceiling: at some traffic it runs out of CPU or memory and slows down or crashes. It is also a single point of failure, so if it dies the whole site is down, and you cannot restart it to deploy without downtime. Running several identical servers fixes both, but then clients would need to know all their addresses and pick one. A load balancer gives clients one address and makes that choice for them, so you can add servers and lose one without clients noticing.

1. Every client connects to one name, `api.shop.example`, which points at the load balancer.
2. The load balancer keeps a list of backend servers and an algorithm for choosing one; by default it takes them in turn (round robin).
3. In the background it probes each server, for example by requesting `/actuator/health` every few seconds.
4. When a request arrives, it picks the next healthy server and forwards the request there.
5. If a server fails its probe, the load balancer drops it from the pool and keeps using the rest, until it passes again.

So the key is that clients see one stable address, and the load balancer hides how many servers are behind it and which ones are alive.

## Example

This nginx config is a payment API behind three servers. Nginx here is both a reverse proxy (it ends TLS and forwards HTTP) and a load balancer (it spreads requests).

```nginx
upstream payments_api {
    server 10.0.1.11:8080 weight=2;       # bigger box, gets a double share
    server 10.0.1.12:8080;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=30s;
}
server {
    listen 443 ssl;                       # TLS is terminated here
    server_name api.shop.example;
    ssl_certificate shop.crt; ssl_certificate_key shop.key;
    location /payments/ { proxy_pass http://payments_api; }
}
```

What to notice:

- `upstream payments_api` is the pool of backend servers; `proxy_pass` forwards matching requests to that pool.
- `weight=2` makes the first server receive twice as many requests as the others, which fits a larger machine.
- `max_fails=3 fail_timeout=30s` is a passive health check: after 3 failed requests nginx stops using that server for 30 seconds.
- `listen 443 ssl` with a certificate means nginx ends the encrypted connection ([TLS termination](card:tls-termination)) and forwards plain HTTP to the backends, so they do not each need the certificate.

## Rules and defaults

- **Default algorithm:** nginx and AWS ALB use round robin (each server in turn) unless you configure another, such as least connections.
- **One address, many servers:** clients only ever see the load balancer's address; backend addresses stay private.
- **Not a single point of failure:** run at least two load balancers, or use a managed one spread across availability zones. An AWS ALB requires at least two subnets in two zones.
- **502 and 504 come from the proxy:** a 502 means the backend gave a bad reply, a 504 means it was too slow. These are reported by the load balancer, not the app.

## Not to be confused with

A [forward proxy](card:forward-proxy) acts for a group of clients and the client chooses it; it hides the clients. A [reverse proxy](card:reverse-proxy) acts for servers and the site owner sets it up; it hides the backends. A load balancer is a reverse proxy whose main job is spreading load. Rule: forward proxy speaks for clients, reverse proxy speaks for servers, load balancing is one thing a reverse proxy does.

## Common mistakes

- **"Pin each user to one server (sticky sessions) so their session is kept."** If that server dies, those users lose their session, and traffic goes uneven. Keep session data in a shared store or a signed token, so any server can serve any user.
- **"The backend reports 502 errors."** A 502 or 504 is reported by the load balancer about the backend: a bad or slow upstream reply. Look at the backend's own logs to find the real cause.

## Interview Qs

### When would you choose an L7 load balancer over an L4 one?

Choose L7 when routing depends on the HTTP request: the host, path, headers, or a session cookie, or when you want it to terminate TLS. Choose L4 for raw speed, for non-HTTP traffic, or when you need the TLS connection to reach the backend unbroken. Large systems chain both: L4 in front of L7.

### How do you stop the load balancer itself being a single point of failure?

Run at least two of them, or use a managed load balancer that the cloud spreads across availability zones. One address can map to several load balancer nodes through DNS or a virtual IP, so if one node dies the others keep serving. An AWS ALB needs subnets in at least two zones for this reason.

### Why should servers behind a load balancer be stateless?

Because the load balancer can send a user's next request to any server. If a server kept the session in its own memory, that request could land on a server that has never seen the user. Keeping session state in a shared store or a token lets every server answer every request, and lets you add or lose servers freely.
