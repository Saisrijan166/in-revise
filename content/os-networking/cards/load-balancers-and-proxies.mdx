## Why it exists

One server has a ceiling and is a single point of failure. A load balancer puts many servers behind one address, so you add capacity and survive a crash.

- [Health checks](card:lb-health-check): active probes of a path like `/actuator/health`, or passive marking after real requests fail.
- A [reverse proxy](card:reverse-proxy) also does [TLS termination](card:tls-termination), compression and caching, and hides backend addresses.
- 502 and 504 come from the proxy: bad or late upstream reply ([status codes](card:http-basics)).

## Example

```nginx
upstream orders_api {
    least_conn;                          # default: round robin
    server 10.0.1.11:8080 weight=2;      # bigger box, double share
    server 10.0.1.12:8080;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=30s;
}
server {
    listen 443 ssl;                      # TLS ends here
    server_name api.shop.example;
    ssl_certificate shop.crt; ssl_certificate_key shop.key;
    location /orders/ { proxy_pass http://orders_api; }
}
```

## Interview Qs

### L4 or L7 load balancer: which would you choose?

L7 when routing needs the host, path or headers, or cookie stickiness. L4 for raw speed, non-HTTP traffic or end-to-end TLS. Big setups chain both: L4 in front of L7.

### Why avoid sticky sessions?

If the pinned server dies, its users lose their session, and load gets uneven. Keep session state in a shared store or a token instead.

### How do you stop the load balancer itself being a single point of failure?

Run at least two nodes, or a managed load balancer across availability zones (an AWS ALB needs two).
