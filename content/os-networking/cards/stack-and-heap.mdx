## Why it exists

A method call needs scratch space that vanishes on return, while some data, like the order a request loads, must outlive the call and be shared.

## How it works

<Compare id="stack-vs-heap" />

- `main()` → `getOrder(42)` → `toJson()`: three frames on that thread's stack; the `Order` object (total ₹1,499) sits on the heap.
- The JVM heap is not the whole process: metaspace and every thread stack are native memory outside it.
- 10,000 platform threads need 10,000 stacks; see [thread pools](card:thread-pools).

## Example

Recursion with no base case adds a frame per call until the stack is full (example run, default -Xss):

```java
public class Deep {
    static int depth = 0;

    static void down() { depth++; down(); }   // one new frame per call

    public static void main(String[] args) {
        try { down(); }
        catch (StackOverflowError e) { System.out.println("StackOverflowError at depth ~" + depth / 1000 * 1000); }
    }
}
```

```text output
StackOverflowError at depth ~22000
```

## Interview Qs

### StackOverflowError vs OutOfMemoryError?

StackOverflowError: one thread's stack is full, usually from deep or endless recursion. OutOfMemoryError: the heap (or metaspace) cannot fit a new allocation, from too much live data or a leak.

### Java has a garbage collector. How can it leak memory?

The collector frees only unreachable objects. A static map or cache that keeps growing still references its entries, so they are never freed and the heap fills up.

### Manual memory vs garbage collection?

In C, you call malloc and free; forgetting free leaks, and using memory after free is a dangling pointer. A garbage collector frees unreachable objects for you, at the cost of GC work.
