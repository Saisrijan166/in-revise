## What it is

Within one process, memory for running code is kept in two main areas. The stack is a per-thread area that grows and shrinks as methods are called and return: each call gets a frame holding that call's local variables. The heap is a single area, shared by all the process's [threads](card:threads), where objects and arrays live. In Java you never place things by hand: locals and references go on the stack, and `new` puts the object on the heap.

## Why it exists

A method needs scratch space for its locals that should disappear the moment it returns, and nothing manages that better than a stack: push a frame on call, pop it on return, no cleanup code. But some data must outlive the call that created it, for example the `Order` object a request builds and then passes to other methods. That data goes on the heap, where it stays alive as long as something references it.

## How it works

<Compare id="stack-vs-heap" />

Follow a call chain `main()` → `getOrder(42)` → `toJson()`:

1. Calling `main()` pushes its frame onto the thread's stack.
2. `main()` calls `getOrder(42)`, which pushes a second frame holding the local `id = 42`.
3. `getOrder` does `new Order(...)`: the `Order` object (total ₹1,499) is created on the heap, and the frame holds only a reference to it.
4. `getOrder` calls `toJson()`, pushing a third frame; when `toJson()` returns, its frame is popped.
5. When `getOrder` returns the reference, its frame is popped too, but the `Order` object stays on the heap because the returned reference still points to it.

So the stack unwinds automatically call by call, while heap objects live until nothing references them.

## Example

Endless recursion pushes one frame per call until the stack is full, which shows the stack's fixed size (run with the default `-Xss`).

```java
public class Deep {
    static int depth = 0;

    static void down() { depth++; down(); }   // one new frame per call, never returns

    public static void main(String[] args) {
        try { down(); }
        catch (StackOverflowError e) {
            System.out.println("StackOverflowError at depth ~" + depth / 1000 * 1000);
        }
    }
}
```

```text output
StackOverflowError at depth ~22000
```

What to notice:

- `down()` never returns, so each call leaves its frame on the stack; after about 22,000 frames the 1024 KB stack is full and the JVM throws `StackOverflowError`.
- The error is about the stack, not the heap: the program barely uses any heap. A real `OutOfMemoryError` would instead mean the heap is full.
- A larger `-Xss` would push the depth higher but not make recursion infinite; the fix is usually a base case or an iterative loop.

## Rules and defaults

- **Thread stack size (`-Xss`):** 1024 KB on Linux x64 in JDK 25. Every thread, including each platform thread you start, gets its own stack of this size, so 10,000 platform threads reserve about 10 GB of stacks; see [thread pools](card:thread-pools).
- **Max heap (`-Xmx`):** if you do not set it, the JVM uses about 25% of available RAM (`MaxRAMPercentage`) in JDK 25.
- **The JVM heap is not the whole process:** metaspace (class metadata) and every thread stack are native memory outside the heap, so a process can run out of memory even with heap to spare.
- **Freeing:** stack frames are freed automatically on return; heap objects are freed by the garbage collector in Java, and by `free()` in C.

## Interview Qs

### StackOverflowError vs OutOfMemoryError?

StackOverflowError means one thread's stack is full, almost always from deep or endless recursion. OutOfMemoryError means the heap (or metaspace) cannot fit a new allocation, from too much live data or a leak. One is about call depth on a single thread; the other is about total live objects.

### Java has a garbage collector. How can it still leak memory?

The collector frees only objects that are unreachable. If you keep a reference, for example in a static map or cache that only grows, the objects stay reachable and can never be freed, so the heap fills up and eventually throws OutOfMemoryError. The fix is to drop references you no longer need.

### How is manual memory management different from garbage collection?

In C you call `malloc` to allocate and `free` to release; forgetting `free` leaks memory, and using memory after `free` is a dangling pointer. A garbage collector frees unreachable objects for you, which removes those two bug classes at the cost of CPU spent on GC and less control over timing.
