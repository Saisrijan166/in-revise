## What it is

A thread pool is a fixed set of [worker threads](card:threads) that take their work from a shared task queue. You submit a task, it waits in the queue, and the next free worker runs it, then comes back for another. The pool creates the threads once and reuses them, instead of starting a new thread for each piece of work.

## Why it exists

Our payment server could start one thread per incoming request. Each thread costs creation time, a stack of its own, and more [context switches](card:context-switching), and a traffic spike would create thousands of threads at once and exhaust memory. A pool fixes the number of threads: a spike just makes tasks wait in the queue, so the server stays up and uses a known amount of memory instead of melting down.

## How it works

<Mermaid
  alt="Requests enter a bounded task queue; workers 1 to N take tasks from it. When the queue is full, new tasks are rejected or run by the caller."
  chart={`flowchart LR
  R1([POST /payments]) --> Q[[Bounded task queue]]

1. The server submits each request as a task to the pool instead of running it on a new thread.
2. If a worker is free, it takes the task at once; otherwise the task waits in the queue.
3. A worker runs one task to completion, then returns to the queue for the next, so the N threads are reused forever.
4. If the queue is bounded and full, the pool applies its rejection policy: the default `AbortPolicy` throws, while `CallerRunsPolicy` makes the submitting thread run the task, which slows the senders down.

So the key is that N bounds how many run at once, and the queue policy bounds how much waiting work you allow.

## Example

A pool of two workers runs four payment tasks; only two run at a time, and the threads are reused.

```java
import java.util.concurrent.*;
public class Main {
    public static void main(String[] args) {
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {  // 2 reusable workers
            for (int id = 41; id <= 44; id++) {
                int payment = id;
                pool.submit(() -> System.out.println("payment " + payment + " on " + Thread.currentThread().getName()));
            }
        }                                                  // close() waits for queued tasks
    }
}
```

```text output
payment 41 on pool-1-thread-1
payment 42 on pool-1-thread-2
payment 43 on pool-1-thread-1
payment 44 on pool-1-thread-2
```

What to notice:

- Only two thread names appear (`pool-1-thread-1` and `pool-1-thread-2`), even for four tasks: the two workers are reused, not four threads created.
- The order varies between runs, because the two workers race for the next task; a pool gives no ordering guarantee.
- `newFixedThreadPool(2)` uses an unbounded queue, so all four tasks are accepted at once. Under real load that queue can grow without limit.
- The try-with-resources `close()` waits for the queued tasks to finish before the program exits.

## Rules and defaults

- **Fixed pool queue:** `Executors.newFixedThreadPool(n)` uses an unbounded `LinkedBlockingQueue`, so tasks never get rejected; they accumulate in memory. For overload protection, build a `ThreadPoolExecutor` with a bounded queue.
- **Rejection policy:** the default is `AbortPolicy`, which throws `RejectedExecutionException` when a bounded queue is full. `CallerRunsPolicy` instead runs the task on the caller, applying back-pressure.
- **Max request threads:** 200 by default in Spring Boot 4.1 (`server.tomcat.threads.max`).
- **Virtual threads:** off by default in Spring Boot 4.1 (`spring.threads.virtual.enabled`); when on, each request runs on its own virtual thread instead of a pooled platform thread.

## Not to be confused with

A thread pool is one way to run concurrent work; an event loop is another. A pool blocks a worker thread per in-progress task, while an event loop uses a few threads and callbacks. Rule: pool = one thread per running task; event loop = a few threads watching many sockets.

## Interview Qs

### How do you size a thread pool?

For CPU-bound work, about the core count, since more threads cannot do more CPU work. For I/O-bound work, use Little's Law: in-flight work equals throughput times latency (200 requests/s times 50 ms is about 10), because most threads are waiting. Then measure CPU use, queue length and latency and adjust.

### Why can a fixed thread pool still run the server out of memory?

Because `newFixedThreadPool` fixes only the thread count; its task queue is unbounded. When tasks arrive faster than the threads clear them, the queue grows without limit and consumes memory. A bounded queue with a rejection policy sheds the excess instead.

### Do virtual threads make thread pools obsolete?

Mostly, for blocking request code: Java 21 virtual threads are cheap, so you can give each request its own instead of pooling. The limit then moves to scarce resources such as database connections, which you still cap with a [semaphore](card:semaphores) or a [connection pool](card:connection-pooling).
