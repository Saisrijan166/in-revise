## Why it exists

A thread per request costs creation time, a stack each and more [context switches](card:context-switching); a spike can exhaust memory.

## How it works

<Mermaid
  alt="Requests enter a bounded task queue; workers 1 to N take tasks from it. When it is full, new tasks are rejected or run by the caller."
  chart={`flowchart LR
  R1([GET /orders/42]) --> Q[[Bounded task queue]]
  Q --> W1[Worker 1]
  Q --> WN[Worker N]
  Q -. full .-> X[Reject or caller runs]`}
/>

- 100 threads on 10 CPUs: at most 10 run at once; the rest wait.
- Full queue: AbortPolicy (default) throws; CallerRunsPolicy makes the caller run it, slowing senders.
- Java 21+ [virtual threads](card:virtual-thread): one per task, never pooled; cap scarce resources with [semaphores](card:semaphores).

## Example

Two workers, four orders (example run; order varies):

```java
import java.util.concurrent.*;
public class Main {
    public static void main(String[] args) {
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {  // 2 reusable workers
            for (int id = 41; id <= 44; id++) {
                int order = id;
                pool.submit(() -> System.out.println("order " + order + " on " + Thread.currentThread().getName()));
            }
        }                                                  // close() waits for queued tasks
    }
}
```

```text output
order 41 on pool-1-thread-1
order 42 on pool-1-thread-2
order 44 on pool-1-thread-2
order 43 on pool-1-thread-1
```

## Interview Qs

### How do you size a thread pool?

CPU-bound: about the core count. I/O-bound: by Little's Law, in-flight work = throughput × latency (200 requests/s × 50 ms = 10). Then measure CPU, queue length and latency.

### Do virtual threads make thread pools obsolete?

Mostly, for blocking request code. Limits move to scarce resources, such as database connections, via a semaphore or a [connection pool](card:connection-pooling).
