## What it is

When your payment server reads from a socket, file or database connection, it must wait for the data. These terms name three ways of waiting. In **blocking** I/O the [thread](card:threads) stops inside the read call until the data is ready. In **non-blocking** I/O the call returns immediately, even if nothing has arrived yet. In **asynchronous** (async) I/O you ask the kernel to do the whole transfer in the background and tell you when it finishes. Blocking and non-blocking are both synchronous: your own thread still copies the data.

## Why it exists

Backend work is mostly waiting. A database query might take a few milliseconds, during which the CPU has nothing to do. With blocking I/O, that one waiting call owns a whole thread, so 10,000 waiting connections need about 10,000 threads, and each thread costs memory and a [context switch](card:context-switching). Non-blocking and async I/O let one thread watch many connections, so the server holds far more connections on far fewer threads.

## How it works

The key question: while the data is not ready, who waits, and who copies it when it is?

| Model | While no data is ready | Who copies the data | Linux example |
|---|---|---|---|
| Blocking, sync | the thread sleeps inside the call | your thread | plain `read()` |
| Non-blocking, sync | the call returns `EAGAIN` at once | your thread | `read()` on an `O_NONBLOCK` fd |
| Readiness (multiplexed) | one thread waits on many fds | your thread, for the ready fds | [epoll](card:io-multiplexing) |
| Async completion | the kernel does the read in the background | the kernel | io_uring, POSIX aio |

1. With blocking I/O the thread calls `read()` and the kernel does not return until bytes are copied in. Simple, but the thread is stuck.
2. With non-blocking I/O the same `read()` returns at once; if nothing is ready it returns `EAGAIN`, so the thread moves on and retries later.
3. The first three rows are synchronous: your thread does the final copy. Only async I/O lets the kernel finish the transfer and then notify you.

So the key is that non-blocking removes the wait but not your work; async removes the work too.

## Example

In non-blocking mode a Java NIO read returns 0 bytes instead of waiting. The same channel, switched back to blocking, waits for the bytes.

```java
var addr = new InetSocketAddress("localhost", 8080);
try (var server = ServerSocketChannel.open().bind(addr);
     var client = SocketChannel.open(addr);
     var conn = server.accept()) {
    conn.configureBlocking(false);                  // like setting O_NONBLOCK
    System.out.println("non-blocking read: " + conn.read(ByteBuffer.allocate(64)));
    conn.configureBlocking(true);                   // reads wait again
    client.write(ByteBuffer.wrap("GET /orders/42".getBytes()));
    System.out.println("blocking read: " + conn.read(ByteBuffer.allocate(64)));
}
```

```text output
non-blocking read: 0
blocking read: 14
```

What to notice:

- `configureBlocking(false)` is Java's way of setting `O_NONBLOCK`. The first `read()` finds no data, so it returns `0` straight away instead of waiting.
- After `configureBlocking(true)` the channel blocks again, so the second `read()` waits until the 14 bytes of `GET /orders/42` arrive, then returns `14`.
- A non-blocking read returning `0` does not mean the connection is closed; it means "nothing ready yet". You would normally come back to this fd when [epoll](card:io-multiplexing) says it is readable, instead of spinning on it.

## Rules and defaults

- **Default mode:** sockets and pipes are created in blocking mode; you turn on non-blocking yourself with `O_NONBLOCK` (Java: `configureBlocking(false)`).
- **Non-blocking signal:** a non-blocking call that would have waited returns the `EAGAIN` error (also spelled `EWOULDBLOCK`), not real data.
- **Regular files:** on Linux `O_NONBLOCK` has no effect on normal disk files; a read of a file can still block, so true non-blocking disk I/O needs async interfaces.
- **Async on Linux:** `io_uring` (kernel 5.1, 2019) is the modern async interface, using shared submit and complete rings; the older POSIX `aio` is little used.
- **Java note:** classic `java.io` streams block; `java.nio` channels can be non-blocking; Java 21 virtual threads make blocking code cheap again by parking the virtual thread, not an OS thread.

## Not to be confused with

- **Non-blocking** describes one call: it returns rather than waiting.
- **Asynchronous** describes who finishes the work: the kernel does the whole operation and notifies you.
- **[I/O multiplexing](card:io-multiplexing)** is the pattern of one thread watching many non-blocking fds with epoll.

Rule: non-blocking = "do not wait on this call"; async = "the kernel completes it for me"; multiplexing = "one thread, many fds".

## Common mistakes

- **"A non-blocking read of 0 bytes means the client disconnected."** No. On a non-blocking socket, 0 or `EAGAIN` means nothing is ready yet; a real close shows up differently (end-of-stream, which in Java NIO is a read of `-1`).

## Interview Qs

### What is the difference between blocking and non-blocking I/O?

Blocking I/O makes the calling thread wait inside the call until it can complete, so one waiting call ties up one thread. Non-blocking I/O returns at once; if nothing is ready it returns `EAGAIN`, so the thread is free to serve other work and come back when the fd is ready.

### Is non-blocking the same as asynchronous I/O?

No. Non-blocking means a single call does not wait; your own thread still checks readiness and copies the data. Asynchronous I/O hands the whole operation to the kernel, which does the transfer in the background and reports completion, as `io_uring` does. Non-blocking is synchronous; only completion-based I/O is truly asynchronous.

### Does switching to non-blocking I/O make requests faster?

No. The database and network take the same time, so a single request is not quicker. The benefit is throughput under load: one thread can watch thousands of waiting sockets, so the server needs far fewer threads and survives much higher concurrency.
