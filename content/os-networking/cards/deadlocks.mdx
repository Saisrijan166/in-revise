## Why it exists

Code holding one lock that asks for another freezes for good if another thread does the reverse. Nothing crashes; requests hang.

## How it works

<Mermaid
  alt="Thread 1 holds L1 and wants L2; Thread 2 holds L2 and wants L1: a cycle."
  chart={`flowchart LR
  T1["Thread 1 holds L1"] -- "wants L2" --> T2["Thread 2 holds L2"]
  T2 -- "wants L1" --> T1`}
/>

- Prevent: break one condition. [Lock ordering](card:lock-ordering) is the usual fix.
- Avoid: the [Banker's algorithm](card:bankers-algorithm) grants a request only if all can still finish; rarely used.
- Detect: find a cycle in the [wait-for graph](card:wait-for-graph) and abort one; PostgreSQL does this.

## Example

```java
record Account(int id) {}

static void transfer(Account from, Account to) {
    Account first = from.id() < to.id() ? from : to;   // lower id first
    Account second = (first == from) ? to : from;
    synchronized (first) { synchronized (second) { /* move ₹1,499 */ } }
}
// two threads: transfer(a, b) and transfer(b, a), 100,000 times each
System.out.println("both done, no deadlock");
```

```text output
both done, no deadlock
```

## Interview Qs

### How would you prevent deadlocks?

Take locks in one global order, such as by account id. Use `tryLock` with a timeout and back off. In the database, update rows in the same order everywhere.

### What does PostgreSQL do when two transactions deadlock?

After `deadlock_timeout` (1 s by default in PostgreSQL 18) it checks for a cycle and aborts one transaction, which the app should retry.

### Can services deadlock?

Yes: A waits for B while B waits for A, or each holds a lock the other needs. Use timeouts on every call, locks that expire (leases), and one lock order across services.
