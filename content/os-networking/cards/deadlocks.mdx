## What it is

A deadlock is a state where a group of threads are all stuck waiting for each other, so none of them can go on. Each thread holds a [lock](card:locks) that another thread in the group needs, and is itself waiting for a lock that another holds. The waiting forms a cycle with no way out. Nothing crashes and no error appears; the threads simply freeze, and any request they are serving hangs.

## Why it exists

The problem appears as soon as a thread holds one lock and asks for a second. If one thread takes lock A then wants lock B, while another takes lock B then wants lock A, each ends up waiting for a lock the other is holding, and neither will ever release. This is easy to write by accident: two methods lock the same two objects in opposite orders. The value in naming the four conditions that make it possible is that breaking any one of them makes deadlock impossible.

## How it works

1. Thread 1 acquires lock L1; Thread 2 acquires lock L2.
2. Thread 1 now asks for L2, which Thread 2 holds, so Thread 1 waits.
3. Thread 2 now asks for L1, which Thread 1 holds, so Thread 2 waits.
4. Each waits for the other; the cycle never breaks and both threads hang.

So the key is the cycle in step 4: remove the chance of a cycle (a fixed lock order) and the deadlock cannot form.

## Example

Both threads lock the lower account id first, so the cycle can never form and the transfers finish.

```java
record Account(int id) {}

static void transfer(Account from, Account to) {
    Account first = from.id() < to.id() ? from : to;   // always lock lower id first
    Account second = (first == from) ? to : from;
    synchronized (first) { synchronized (second) { /* move the money */ } }
}
// two threads: transfer(a, b) and transfer(b, a), 100,000 times each
System.out.println("both done, no deadlock");
```

What to notice:

- Both calls lock the lower id first, so they request the two locks in the same order and never form a cycle.
- Remove the ordering and lock `from` then `to` directly, and `transfer(a,b)` with `transfer(b,a)` can deadlock within a few iterations.
- This breaks the circular-wait condition; the other three conditions still hold, which is enough to make deadlock impossible.

## Rules and defaults

- **Four Coffman conditions:** mutual exclusion, hold-and-wait, no preemption, and circular wait. All four must hold at once for a deadlock.
- **Prevention:** break one condition; a single global [lock order](card:lock-ordering) is the usual, cheapest fix for circular wait.
- **Avoidance:** the [Banker's algorithm](card:bankers-algorithm) grants a request only if everyone can still finish; it is rarely used in practice.
- **Detection:** find a cycle in the [wait-for graph](card:wait-for-graph) and abort one thread. PostgreSQL does this after `deadlock_timeout` (1 s by default, version 18).
- **The JVM:** does not detect or break deadlocks; stuck threads stay stuck until the process is killed.

## Not to be confused with

In a deadlock the threads are blocked in a cycle and nobody progresses. In [starvation](card:thread-starvation) one unlucky thread keeps being passed over while others run fine. In a [livelock](card:livelock) threads are not blocked at all but keep reacting to each other and still get nothing done. Rule: deadlock is stuck and idle, livelock is busy but stuck, starvation is one thread stuck while the rest move.

## Interview Qs

### How would you prevent deadlocks?

Take locks in one global order everywhere, such as by account id, which removes circular wait. Use `tryLock` with a timeout so a thread backs off instead of waiting forever. Keep critical sections and transactions short. In the database, update rows in the same order in every code path.

### What does PostgreSQL do when two transactions deadlock?

It runs a deadlock detector. After `deadlock_timeout`, 1 second by default in PostgreSQL 18, it checks the waits for a cycle, picks one transaction as the victim, and aborts it with a deadlock error. The application should catch that error and retry the aborted transaction.

### Can services deadlock, not just threads?

Yes. Service A waits on a response from B while B waits on A, or each holds a resource the other needs. The cure is the same shape: put a timeout on every call, use locks that expire on their own (leases), and apply one lock order across services.
