## What it is

Virtual memory is a trick the hardware and OS play together so that each [process](card:processes) sees its own private range of memory addresses, called its address space, as if it alone owned the machine's memory. These virtual addresses are not real RAM locations. A piece of CPU hardware, the Memory Management Unit (MMU), translates each virtual address a program uses into the real physical address in RAM, using tables the OS sets up per process.

## Why it exists

If every process used physical RAM addresses directly, two problems follow. First, one process could read or overwrite another's memory with a stray pointer, breaking isolation and security. Second, every program would have to know where in RAM it was loaded, which changes every run. Virtual memory removes both: each process gets the same clean, private address space, and the MMU keeps their real RAM separate, so a bad pointer in one process cannot touch another.

## How it works

<Mermaid

  A["Process A: 0x1000"] --> M{{"MMU + page tables"}}

  M --> F7[(RAM frame 7)]
  M --> F2[(RAM frame 2)]
  M -. "page swapped out" .-> S[(Swap space)]`}
/>

1. A program reads or writes a virtual address, say `0x1000`.
2. The MMU looks up that address in the current process's page tables to find the real RAM location.
3. Because each process has its own page tables, process A's `0x1000` and process B's `0x1000` land on different RAM, so they never collide.
4. If the address is invalid, or the access breaks permissions (such as writing a read-only page), the CPU raises a fault and the OS sends the process SIGSEGV, a segmentation fault.

So the key is that every access goes through per-process translation, which is what gives isolation.

## Analogy

<Analogy title="Hotel room numbers" limit="rooms do not move between floors, but swapped-out pages really do move to disk and back">
Every guest asks for "room 101", but each guest is on a different floor, so "room 101" means a different real room for each. The front desk (the MMU) maps your floor plus "101" to one real room. Two guests using the same room number never clash.
</Analogy>

## Example

An idle JVM reserves a large virtual address space but keeps very little in RAM. This run shows VSZ about 4.6 GiB and RSS only about 40 MiB.

```bash
echo 'class Idle { public static void main(String[] a) throws Exception { Thread.sleep(60_000); } }' > Idle.java
javac Idle.java
java -Xmx2g Idle &
sleep 1; ps -o pid,vsz,rss,comm -C java
```

```text output
    PID    VSZ   RSS COMMAND
 744281 4863172 40868 java
```

What to notice:

- VSZ (about 4.8 GB) is all the address space mapped, including the 2 GB heap reserved by `-Xmx2g` that the idle program never touches.
- RSS (about 40 MB) is what is actually in RAM. The gap shows overcommit: address space was reserved, but RAM follows only the pages that are touched.
- If you watch a container for OOM, compare RSS (not VSZ) against the memory limit.

## Rules and defaults

- **Overcommit (Linux, `vm.overcommit_memory=0`):** the default heuristic lets allocations reserve more address space than there is RAM; RAM is given on first touch.
- **OOM killer:** when RAM (or a cgroup's `memory.max`) is exhausted and nothing can be reclaimed, the kernel kills a chosen process to free memory. Inside a container, this happens at the cgroup limit.
- **Swap space:** optional disk space for pages evicted from RAM. It lets more run than fits in RAM, but a swapped-in access is far slower than a RAM access.
- **Invalid access:** a bad or permission-breaking address gives SIGSEGV, a segmentation fault, which normally ends the process.
- **Related mechanisms:** how pages are mapped and loaded is in [paging](card:paging-and-page-faults); choosing which page to evict is in [page replacement](card:page-replacement).

## Interview Qs

### What is virtual memory and why do we need it?

Virtual memory gives each process its own address space, mapped to physical RAM page by page by the MMU. We need it so processes stay isolated (one cannot touch another's memory), so programs need not know their real RAM location, and so RAM is handed out only to pages a process actually touches.

### malloc succeeded, yet the process was killed later. How?

Linux overcommits by default, so a successful allocation only reserves address space, not RAM. RAM is given as touched pages demand it. When the touched pages exhaust RAM or the cgroup limit and the kernel cannot reclaim enough, the OOM killer kills a process, which may be yours.

### VSZ vs RSS?

VSZ is the total virtual address space a process has mapped, much of which may never be touched. RSS is the part currently resident in RAM. For memory pressure and limits, watch RSS; a large VSZ by itself is harmless.
