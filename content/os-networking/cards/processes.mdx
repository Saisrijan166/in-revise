## Why it exists

Programs must not read or corrupt each other's memory. A process wraps one running program in its own address space.

## How it works

<Mermaid
  alt="Process states: New goes to Ready; the scheduler moves Ready to Running; a used-up slice sends it back to Ready; waiting for I/O makes it Blocked until the I/O is done, then Ready; on exit it is Terminated, a zombie until the parent calls wait."
  chart={`flowchart LR
  N([New]) --> R[Ready]
  R -- scheduled --> U[Running]
  U -- slice ends --> R
  U -- waits for I/O --> B[Blocked]
  B -- I/O done --> R
  U -- exits --> T([Terminated: zombie until wait])`}
/>

- Memory: code, data, a [heap](card:stack-and-heap) and a stack per thread, isolated by [virtual memory](card:virtual-memory).
- Three Spring Boot instances are three processes: one crashing leaves the others serving.
- A [container](card:linux-container) is a process tree with its own namespaces and cgroup limits, sharing the host kernel.

## Example

A child exits but its parent never calls wait(). A local run:

```bash
(sleep 0.2 & exec sleep 3) &
sleep 1; ps -o pid,ppid,stat,cmd --ppid $! -p $!
```

```text output
    PID    PPID STAT CMD
 726508  726507 S    sleep 3
 726510  726508 Z    [sleep] <defunct>
```

## Interview Qs

### Why are fork and exec separate calls?

Between them the child can prepare the new program, for example redirect its output or change directory. That is how a shell runs `java -jar app.jar > app.log`.

### Zombie vs orphan?

A zombie has exited, but its parent has not called wait(), so its PID and exit status linger. An orphan is still running after its parent died; init (PID 1) or a subreaper adopts and later reaps it.
