## What it is

These three words describe speed, and interviews mix them up. Latency is how long one request takes to travel there and back, measured in milliseconds. Bandwidth is the most data a link can carry per second, its top rate, measured in Mbps or Gbps. Throughput is how much data or work actually got through per second, always at or below the bandwidth because of distance, lost packets and slow stages. A useful unit is the round trip time (RTT): one message going and a reply coming back.

## Why it exists

Every performance question turns on these three, and confusing them leads to the wrong fix. If you treat a latency problem as a bandwidth problem, you pay for a faster link and the small API calls stay exactly as slow, because they were never limited by the link's capacity. Telling the three apart tells you what to change: shorten the path and cut round trips for latency, buy a faster link for a bandwidth-bound transfer, and remove the slowest stage to raise throughput.

## How it works

<Compare id="latency-vs-bandwidth-vs-throughput" />

1. A new HTTPS request spends several round trips before any data moves: a [DNS](card:dns) lookup, the [TCP handshake](card:tcp-handshake), and the [TLS 1.3](card:tls-https) handshake, each one RTT.
2. Only after those does the actual `GET` go out and the reply come back, adding the server's own work time.
3. Sequential calls add up: if one request calls service A, then B, then the database, its latency is the sum of all three.
4. At scale the slow tail dominates: if 1 call in 100 is slow, a request that fans out to 100 servers hits a slow one about 63% of the time (1 minus 0.99 to the power 100).

So the key is that small calls are decided by round trips and distance, while only large transfers are decided by bandwidth.

## Example

This counts the time before the first byte of the body, assuming each step is one 100 ms round trip on a fresh HTTPS connection with nothing cached.

```text
DNS lookup           1 RTT    100 ms
TCP handshake        1 RTT    100 ms
TLS 1.3 handshake    1 RTT    100 ms
GET /payments/42     1 RTT    100 ms + server time
Total                ~400 ms  before the first body byte
Reused connection    ~100 ms  (only the last line runs)
```

What to notice:

- Three of the four round trips are setup (DNS, TCP, TLS), not the request itself, so most of the 400 ms is spent before any useful data.
- Reusing an existing connection skips the first three steps and cuts the time to about 100 ms, which is why keep-alive and connection pooling matter.
- None of this is about bandwidth: the payload is tiny, so a faster link would not change the total.
- A far-away server makes every RTT larger, which is why a nearer region or a [CDN](card:caching-and-cdn) helps.

## Rules and defaults

- **Throughput is capped by bandwidth:** you can never push more per second than the slowest link allows, and packet loss or a slow stage lowers it further.
- **Latency is bound by distance and hops:** light and signals take time over distance, and each router and queue adds delay, so a shorter path is lower latency.
- **Long fast links need many bytes in flight:** to use a high-bandwidth, high-latency link fully, enough data must be unacknowledged at once (the [bandwidth-delay product](card:bandwidth-delay-product)).

## Interview Qs

### What is the difference between latency and bandwidth?

Latency is delay: how long data takes to arrive, in milliseconds. Bandwidth is capacity: how many bits per second the link can carry at most. They are independent, so a link can have huge bandwidth and still high latency (a satellite link), or low bandwidth and low latency (a short, thin wire). Small requests feel latency; large transfers feel bandwidth.

### Why track p99 rather than the average response time?

The average blends everyone together and hides the slow tail, but users feel the slow requests. At scale a request that fans out to many servers is likely to hit at least one slow one, so the tail decides the real experience. p99, the time 99% of requests stay within, exposes that tail so you can fix it.

### How do you cut latency for users who are far away?

Move the work closer: serve static content from a [CDN](card:caching-and-cdn) and run servers in a nearer region. Reuse connections so you skip the DNS, TCP and TLS round trips, prefer protocols with fewer round trips, and avoid long chains of sequential calls that add their latencies together.
