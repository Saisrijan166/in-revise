## Why it exists

Every performance question uses these three words. Mixing them up leads to the wrong fix, like buying bandwidth for a round-trip problem.

## How it works

<Compare id="latency-vs-bandwidth-vs-throughput" />

- A new HTTPS connection spends round trips before any data: [DNS](card:dns), [TCP](card:tcp-handshake), [TLS 1.3](card:tls-https).
- Fan-out: if 1 call in 100 is slow, a request touching 100 servers hits a slow one 63% of the time (1 − 0.99¹⁰⁰).
- Long, fast links need many bytes in flight: the [bandwidth-delay product](card:bandwidth-delay-product).

## Example

```text
Assume each step is one 100 ms round trip (new HTTPS, nothing cached)
DNS lookup           1 RTT    100 ms
TCP handshake        1 RTT    100 ms
TLS 1.3 handshake    1 RTT    100 ms
GET /orders/42       1 RTT    100 ms + server time
Total                ~400 ms before the first byte of the body
Reused connection    ~100 ms  (only the last line)
```

## Interview Qs

### Latency vs bandwidth?

Latency is delay: how long data takes to arrive. Bandwidth is capacity: how many bits per second the link can carry. A link can have huge bandwidth and still high latency.

### Why track p99, not the average?

The average hides the slow tail. At scale, a request that fans out to many servers is likely to hit at least one slow one, so the tail decides what users feel.

### How do you cut latency for users far away?

Serve from closer (a [CDN](card:caching-and-cdn) or a nearer region), reuse connections, use protocols with fewer round trips, and avoid long chains of sequential calls.
