## What it is

A semaphore is a counter of permits that controls how many threads may use something at the same time. A thread calls `acquire` to take a permit before entering, and `release` to give it back when it leaves; if no permit is left, `acquire` makes the thread wait until one is freed. A [lock](card:locks) lets exactly one thread in; a semaphore lets up to N in, where N is the number of permits it starts with. Historically `acquire` is called P or wait, and `release` is called V or signal.

## Why it exists

Some resources serve a limited number of users at once, not just one. A connection pool might hold 10 connections, or a payment partner's API might allow only 3 calls in flight. A [lock](card:locks) is too strict: it would force these down to one user at a time and waste the rest. Having no limit is worse: the pool runs dry or the partner rejects the flood. A semaphore sets the dial exactly: start it with N permits, and it lets through at most N threads, queuing the others until a permit frees up.

## How it works

<Compare id="mutex-vs-semaphore" />

1. The semaphore is created with N permits, for example 3 for a partner API.
2. A thread calls `acquire`; if a permit is free the count drops by one and the thread continues, otherwise it blocks.
3. The thread uses the limited resource while it holds the permit.
4. The thread calls `release` in `finally`; the count goes back up, and one waiting thread is woken to acquire it.

So the key is: the count never lets more than N threads past `acquire` at the same time.

## Example

Ten tasks share a semaphore of 3 permits, so no more than 3 ever run the slow call together.

```java
Semaphore permits = new Semaphore(3);              // 3 calls at a time
AtomicInteger inside = new AtomicInteger(), max = new AtomicInteger();
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10; i++) pool.submit(() -> {
        permits.acquire();                         // wait here for a permit
        try { max.accumulateAndGet(inside.incrementAndGet(), Math::max);
              Thread.sleep(50); }                  // the slow remote call
        finally { inside.decrementAndGet(); permits.release(); }
        return null;
    });
}                                                  // close() waits for all 10
System.out.println("most at once: " + max.get());
```

```text output
most at once: 3
```

What to notice:

- `max` tracks the highest number of tasks inside at any moment, and it never passes 3 because the semaphore only hands out 3 permits.
- `release()` is in `finally`, so a permit always returns even if `sleep` is interrupted; a missed release would shrink the limit permanently.
- Change `new Semaphore(3)` to `new Semaphore(10)` and all 10 run at once; the semaphore is the only thing holding the number down.

## Rules and defaults

- **Permits:** a semaphore starts with a fixed number N; `acquire` lowers the count, `release` raises it. A binary semaphore uses N = 1.
- **No owner:** unlike a mutex, any thread may `release`, so `acquire` and `release` can be in different threads to signal between them.
- **Fairness:** `new Semaphore(n)` is non-fair by default (Java 25); pass `true` for first-come-first-served order.
- **Release in finally:** a missed `release` leaks a permit for good; over time the limit falls to zero and all threads block.
- **Higher-level tools:** a `BlockingQueue` or a connection pool wraps this pattern, so you rarely use raw semaphores in Java application code.

## Not to be confused with

A [mutex](card:locks) protects one critical section and has an owner, so only the locking thread unlocks it. A semaphore holds a count and limits how many threads enter, with no owner. Rule: reach for a mutex to protect shared data, and for a semaphore to cap how many threads use a limited resource at once.

## Common mistakes

- **"A connection pool on three servers with Semaphore(3) means three total connections."** Each JVM has its own semaphore and its own 3 permits, so the real total is nine. A shared limit must live in a store that all instances see, such as the database or Redis.

## Interview Qs

### Three instances of your API each use Semaphore(3) for a partner API. How many calls can reach the partner at once?

Nine. A semaphore lives inside one JVM, so each of the three instances has its own 3 permits, and they do not coordinate. For one total limit of 3 across the fleet, the count must live in a shared store such as Redis, not in each process's memory.

### What are the drawbacks of semaphores?

They are easy to misuse. A missed `release()` leaks a permit for good, so release in `finally`. Acquiring several in the wrong order can deadlock, and because a semaphore has no owner, nobody can tell which thread forgot to release. A `BlockingQueue` or a pool hides most of this risk.
