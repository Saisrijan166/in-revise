## Why it exists

Some resources take N users, not one: a pool of 10 connections, or a partner API allowing 3 calls at once. A lock is too strict; no limit overloads them.

## How it works

<Compare id="mutex-vs-semaphore" />

- [Producer-consumer](card:producer-consumer): a bounded buffer uses two counting semaphores (empty slots, full slots) and a mutex for the buffer.
- In Java a `BlockingQueue` does this for you: `put` waits while full, `take` waits while empty.
- A pool of connections is permits too: see [connection pooling](card:connection-pooling).

## Example

Example run: 10 tasks, 3 permits.

```java
Semaphore permits = new Semaphore(3);              // 3 calls at a time
AtomicInteger inside = new AtomicInteger(), max = new AtomicInteger();
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10; i++) pool.submit(() -> {
        permits.acquire();                         // wait for a permit
        try { max.accumulateAndGet(inside.incrementAndGet(), Math::max);
              Thread.sleep(50); }                  // the slow remote call
        finally { inside.decrementAndGet(); permits.release(); }
        return null;
    });
}                                                  // close() waits for all 10
System.out.println("most at once: " + max.get());
```

```text output
most at once: 3
```

## Interview Qs

### Our API runs on three instances. Each uses Semaphore(3) for a partner API. How many calls can reach the partner at once?

Nine. A semaphore lives inside one JVM, so each instance has its own 3 permits. For one total limit, the count must live in a store that all instances share.

### What are the drawbacks of semaphores?

They are easy to misuse. A missed `release()` loses a permit for good, so release in `finally`. Taking them in the wrong order can deadlock, and with no owner nobody can tell which thread forgot. A `BlockingQueue` or a pool hides this.
