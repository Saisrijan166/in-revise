## What it is

The TCP handshake is the short exchange that opens a [TCP](card:tcp-and-udp) connection before any application data is sent. It takes three messages, which is why it is called the three-way handshake: the client sends a SYN, the server replies with a SYN-ACK, and the client sends a final ACK. Its job is to let both sides agree to talk and exchange their initial sequence number (ISN), the byte number each side will start counting from. A matching exchange of FIN messages closes the connection.

## Why it exists

The network can lose, delay or duplicate packets, so a connection cannot just start sending and assume the other side is there and in step. If it did, an old SYN left over from a previous connection could arrive late and be mistaken for a new request, opening a connection nobody asked for. The handshake removes this: each side picks a fresh starting sequence number and refuses to proceed until it sees the other side acknowledge that exact number. By the time data flows, both ends have proven they are present and have agreed where byte numbering begins.

## How it works

1. The client sends a SYN carrying its initial sequence number, `x`.
2. The server replies with one segment that is both a SYN (its own initial sequence number, `y`) and an ACK of the client's (`ack = x+1`).
3. The client sends the final ACK (`ack = y+1`). The connection is now open, and this ACK may already carry the first request bytes.
4. To close, each direction is shut separately: one side sends a FIN, the other ACKs it, and the same happens the other way, so a full close is up to four messages.
5. The side that sent the first FIN enters TIME_WAIT and waits a short while before the port can be reused, so that late segments from the old connection die out.

So the key is that three steps, not two, are the minimum for each side to send its sequence number and have the other confirm it.

## Example

The handshake is invisible in code: one `connect` call runs all three steps for you.

```java
// Client side: this single line performs SYN, SYN-ACK, ACK before it returns.
try (var socket = new Socket("api.shop.example", 443)) {
    socket.getOutputStream().write("GET /orders/42\r\n".getBytes());
    // ... read the reply ...
}   // closing the socket starts the FIN / ACK exchange
```

What to notice:

- `new Socket(host, port)` does not return until the three-way handshake has completed, so the one round trip of setup is spent inside this call.
- Only after `connect` returns can the first request byte go out; this is why a brand-new connection always pays one extra round trip before any response.
- Closing the socket (here at the end of the try block) sends the FIN that begins the close, and this client becomes the side that holds TIME_WAIT.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| TIME_WAIT length | 60 s (the constant `TCP_TIMEWAIT_LEN`, not a tunable sysctl) | Linux |
| SYN cookies | On-demand: used only when the SYN queue overflows | Linux `net.ipv4.tcp_syncookies` (default 1) |

- **RST aborts at once:** a reset ends a connection immediately and is also the reply to a SYN sent to a port with no listener.
- **SYN flood defence:** an attacker can flood half-open connections with fake SYNs; when the queue overflows, Linux switches to SYN cookies, encoding the connection state in the SYN-ACK sequence number instead of storing it (RFC 4987).

## Not to be confused with

Opening and closing are different exchanges. The open is a three-way handshake (SYN, SYN-ACK, ACK) because the server's SYN and ACK ride in one segment. The close takes up to four messages, because each direction is ended by its own FIN and ACK and either side may stop sending while still receiving (a half-close). Rule: open = three messages; graceful close = a FIN each way.

## Common mistakes

- **"TIME_WAIT is a leak to get rid of."** It is deliberate: it lets a repeated FIN be re-acknowledged and lets stray old segments expire before the port is reused. The real fix for a pile-up is fewer connections (keep-alive, pooling), not removing TIME_WAIT.
- **"The handshake carries no data."** The client's final ACK, and later TCP Fast Open, can carry request bytes, so setup and the first request need not be fully separate round trips.

## Interview Qs

### Why three steps and not two?

Each side must send its initial sequence number and see it acknowledged. The server's SYN and its ACK of the client fit in one segment, so the minimum is three messages. With only two, the server could not tell a fresh SYN from an old delayed duplicate, and could open a connection the client never wanted.

### A client shows thousands of sockets in TIME_WAIT. Is that a bug?

Not by itself; TIME_WAIT is normal on the side that closes first. Thousands of them usually mean the client opens a new connection per request, which can exhaust [ephemeral ports](card:ports-and-sockets). The fix is to reuse connections with HTTP keep-alive or a [connection pool](card:connection-pooling).

### What are SYN cookies, and when are they used?

They defend against SYN floods. Instead of storing state for every half-open connection, the server encodes that state into the SYN-ACK's sequence number and rebuilds it from the client's final ACK. Linux turns them on automatically only when the SYN queue overflows.
