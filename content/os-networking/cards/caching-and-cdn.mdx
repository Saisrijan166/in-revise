## What it is

A cache is a store that keeps a copy of a response, so the next request for the same thing is answered from the copy instead of reaching the origin server. The same response can be cached in the user's browser, a [CDN](card:cdn-edge) edge near the user, or a [reverse proxy](card:reverse-proxy). A CDN is a network of servers around the world that holds copies of your static files close to users. The `Cache-Control` header says how long the copy stays fresh and who may keep it.

## Why it exists

The same file or response is often sent again and again, and if every request travels to one origin server far away, each one pays the full round-trip distance and the origin does all the work. That is slow for users and wasteful for the server. Keeping a copy closer to the user answers most requests in a short hop and never touches the origin, which cuts latency and takes load off the origin. The cost is that a cached copy can be out of date, so the rules below control how long a copy is trusted.

## How it works

A response can be cached at several layers. Each layer follows the same `Cache-Control` rules.

| Cache | Shared across users? | Example for the payment site |
|---|---|---|
| Browser cache | No, one user | `GET /payments/42`: `private, no-cache` |
| CDN edge | Yes, many users | product image: `public, max-age=31536000` |
| Reverse proxy cache | Yes | only non-personal responses |
| App cache (Redis) | Yes, the app decides | hot database rows; HTTP rules do not apply here |

1. A request arrives at the nearest cache (the browser first, then a CDN edge).
2. If the cache holds a fresh copy (still inside its `max-age`), it serves that copy at once: a cache hit.
3. If it has no copy, or the copy is stale, it asks the next cache or the origin: a cache miss.
4. On a miss the response comes back with `Cache-Control`, and the cache stores it for next time if allowed.
5. When a stored copy is stale but has an `ETag`, the cache revalidates: it asks the origin "is it still this version?" and gets a small `304 Not Modified` if nothing changed, reusing the copy.

So the key is freshness: a fresh copy is reused with no server contact, and a stale one is cheaply rechecked.

## Example

This shows one response being cached, then revalidated on the next visit.

```text
GET /payments/42
200 OK
Cache-Control: private, no-cache
ETag: "v7"

GET /payments/42              (next visit: no-cache forces a revalidate)
If-None-Match: "v7"
304 Not Modified             (empty body: the stored copy is still good)
```

What to notice:

- `Cache-Control: private, no-cache` lets the browser store the copy but makes it revalidate before every reuse; `private` keeps a CDN from storing it at all.
- `ETag: "v7"` is a version tag for this copy of the resource.
- On the next visit the browser sends `If-None-Match: "v7"`, and the server replies `304` with no body, so the browser reuses its copy.
- If the resource had changed, the server would return `200` with the new body and a new ETag.

## Rules and defaults

- **max-age=N (RFC 9111):** the copy is fresh for N seconds; during that time caches reuse it without contacting the server.
- **no-cache:** a cache may store the response but must revalidate with the origin before each reuse.
- **no-store:** a cache must not keep the response at all; use it for sensitive data.
- **private vs public:** `private` allows only the user's browser to cache it; `public` also allows shared caches such as a CDN.
- **s-maxage:** sets freshness for shared caches only, overriding `max-age` there, so a CDN can cache longer than a browser.
- **Versioned names for static files:** give files a content hash (`app.3f2a.js`) so a deploy changes the URL; the old URL keeps its long cache safely.

## Common mistakes

- **"A CDN speeds up everything."** A CDN mainly helps cacheable, static or non-personal responses. A per-user response marked `private` is not stored at the edge, so it still reaches the origin.
- **"Just purge the CDN after each deploy."** Purging is slow and does not reach browser caches. Versioned file names are the reliable fix.

## Interview Qs

### What is the difference between no-cache and no-store?

`no-cache` lets a cache store the response but check with the origin before each reuse, usually getting a small `304 Not Modified`. `no-store` forbids keeping the response anywhere, which suits sensitive data. So `no-cache` still saves bandwidth on unchanged responses; `no-store` never does.

### How does a CDN make a site faster?

A CDN has edge servers near users that hold copies of static files. Most requests are answered by the nearest edge in a short hop, so they never cross the world to the origin, cutting latency. A miss the edge does not have goes to the origin once, and the edge caches it for the next user.

### You deploy new CSS but users still see the old file. How do you fix it for good?

The old file was cached with a long `max-age` and caches cannot be reliably told to delete it. Give static files a content hash in the name so each build produces a new URL; the browser then fetches the new file and the old URL keeps its cache harmlessly. Purge the CDN only as backup.
