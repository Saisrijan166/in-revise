## Why it exists

The same files and responses travel long distances again and again. A copy stored closer to the user cuts latency and takes load off the origin server.

## How it works

| Cache | Shared? | In our shop |
|---|---|---|
| Browser cache | No, one user | `GET /orders/42`: `private, no-cache` |
| CDN edge | Yes, many users | product image: `public, max-age=31536000` |
| Reverse proxy cache | Yes | only non-personal responses |
| App cache (Redis) | Yes, app decides | hot rows; HTTP rules do not apply |

- A CDN serves from the edge nearest the user (chosen by DNS or anycast, see [DNS](card:dns)); a miss is fetched from the origin once.
- Files that change get a hash in the name (`app.3f2a.js`): each deploy is a new URL. Purging the CDN is the fallback.
- The price is stale data: short TTLs for data that changes, or invalidate on write.

## Example

```text
GET /orders/42
200 OK
Cache-Control: private, no-cache
ETag: "v7"

GET /orders/42              (next visit: revalidate first)
If-None-Match: "v7"
304 Not Modified            (no body: reuse the stored copy)
```

## Interview Qs

### no-cache vs no-store?

no-cache: a cache may store the response but must check with the server before each reuse, usually getting a small 304. no-store: no cache may keep it at all.

### How does a CDN make a site faster?

Edge servers near users hold copies of static files, so most requests travel a short distance and never reach the origin. A miss goes to the origin once and is cached for the next user.

### You deployed new CSS but users still get the old file. Fix?

The old file was cached with a long max-age, and there is no standard way to delete it from caches. Use versioned file names so a deploy changes the URL; purge the CDN only as a fallback.
