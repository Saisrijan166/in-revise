## Why it exists

Networks drop packets, slow down and split while servers stay up. Without timeouts and safe retries, one slow dependency hangs threads or charges twice.

## How it works

  alt="The client sends POST /payments. The server charges the card but its reply is lost. The client times out and retries, and the server charges again."
  chart={`sequenceDiagram

  C->>S: retry POST /payments

- No timeout means waiting forever, holding a [thread](card:thread-pools) and a [pooled connection](card:connection-pooling).
- With an idempotency key the server stores key → result; the retry gets the first result.
- A [circuit breaker](card:circuit-breaker) stops calls for a while; a [partition](card:network-partition) forces a consistency trade-off.

## Example

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(2))      // connect within 2 s
        .build();
String key = UUID.randomUUID().toString();          // reuse this key on every retry
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.shop.example/payments"))
        .timeout(Duration.ofSeconds(5))             // reply within 5 s
        .header("Idempotency-Key", key)
        .POST(HttpRequest.BodyPublishers.ofString("{\"orderId\":42,\"amount\":1499}"))
        .build();
// throws HttpConnectTimeoutException or HttpTimeoutException
HttpResponse<String> res = client.send(req, HttpResponse.BodyHandlers.ofString());
```

## Interview Qs

### Why is a timeout not proof that the request failed?

The server may have done the work and only the reply was lost. Retrying a non-idempotent call can repeat it: a second payment.

### How do you make POST /payments safe to retry?

Send a unique Idempotency-Key; the server stores key → result and answers a retry with the stored result. The header is only an expired IETF draft.

### Why exponential backoff and jitter together?

Backoff spaces out retries so a struggling server can recover. Jitter adds randomness so clients do not all retry at the same moment.
