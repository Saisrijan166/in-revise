## What it is

Over a network, calls can be slow, lost, or interrupted while the server itself stays up and running. This concept is the set of defences for that: a timeout, which gives up waiting after a set time; a retry, which sends the call again; and idempotency, which means a call is safe to repeat because doing it twice has the same effect as once. The hard part is that a timeout does not tell you whether the server did the work; only that the reply did not arrive in time.

## Why it exists

Networks drop packets, slow down, and split apart, and remote servers can be busy or restarting, all while your code is waiting for an answer. Without a timeout, one slow dependency makes a request wait forever, holding a [thread](card:thread-pools) and a [pooled connection](card:connection-pooling) until the whole server runs out of them. Without care around retries, a lost reply to a payment leads to a second charge, and retries at every layer pile up into a storm that buries a service that was only briefly slow. These defences keep one failure from spreading.

1. The client sends the request and starts two clocks: a connect timeout to reach the server, and a request timeout to get the reply.
2. If a clock runs out, the client has no idea whether the server did the work; only that no reply came.
3. It retries only if the error looks transient and the call is idempotent, and only up to a small cap.
4. Before each retry it waits longer than the last time (exponential backoff) plus a random extra (jitter), so many clients do not retry at the same instant.
5. For a call that is not naturally safe to repeat, like a payment, the client sends an idempotency key, and the server uses it to return the first result instead of doing the work again.

So the key is: assume nothing on a timeout, retry carefully, and make repeats harmless.

## Example

This Java client sets both timeouts and sends an idempotency key, so a retry of the same payment is safe.

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(2))      // reach the server within 2 s
        .build();
String key = UUID.randomUUID().toString();          // reuse this same key on every retry
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.shop.example/payments"))
        .timeout(Duration.ofSeconds(5))             // get the reply within 5 s
        .header("Idempotency-Key", key)
        .POST(HttpRequest.BodyPublishers.ofString("{\"orderId\":42,\"amount\":1499}"))
        .build();
// a timeout throws HttpConnectTimeoutException (connect) or HttpTimeoutException (request)
HttpResponse<String> res = client.send(req, HttpResponse.BodyHandlers.ofString());
```

What to notice:

- `connectTimeout` and the request `timeout` are separate: one bounds reaching the server, the other bounds waiting for the reply.
- `key` is generated once and reused on every retry of this payment, so the server can recognise the retry as the same request.
- With no timeout set, a stuck call would wait forever and tie up the calling thread and its connection.
- `Idempotency-Key` is only an expired IETF draft, not a web standard, so the server must implement the store-and-replay logic itself.

## Rules and defaults

- **Set both timeouts:** always bound connect time and request time; a missing timeout defaults to waiting indefinitely.
- **Retry only when safe:** retry transient errors (timeouts, 503) on idempotent calls (GET, PUT, DELETE), not on a plain POST, and cap the number of attempts.
- **Backoff with jitter:** increase the wait each attempt and add randomness, as the AWS Builders' Library recommends, to avoid a retry storm.
- **Idempotency key is app-level:** the server must store key to result and replay it; nothing in HTTP does this for you.
- **Stronger tools:** a [circuit breaker](card:circuit-breaker) stops calling a failing service for a while; a [network partition](card:network-partition) forces a consistency-versus-availability choice.

## Interview Qs

### Why is a timeout not proof that the request failed?

Because the request and the reply travel separately. The server may have received the request, done the work, and only had its reply lost or delayed. So a timeout means "I did not hear back", not "it did not happen". Retrying a non-idempotent call on a timeout can repeat the work, for example charging a card twice.

### How do you make POST /payments safe to retry?

Have the client send a unique `Idempotency-Key` header and reuse the same key on every retry. On the first call the server stores the key with its result; when it sees the same key again, it returns the stored result instead of charging again. The header is only an expired IETF draft, so the server implements the store-and-replay itself.

### Why use exponential backoff and jitter together?

Exponential backoff makes each retry wait longer than the last, which gives a struggling server time to recover instead of being hit again immediately. Jitter adds a random delay so that many clients, which all failed at the same moment, do not retry in sync and create a fresh spike. Backoff spaces retries out; jitter breaks their alignment.
