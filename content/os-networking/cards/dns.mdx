## What it is

DNS (the Domain Name System) is the phone book of the internet: it turns a name like `api.shop.example` into an IP address like `203.0.113.10`. A packet can only be sent to an IP address, not to a name (see [IP addresses](card:ip-addressing)), so before your client connects to the payment server, it does a DNS lookup to find that address. DNS is a normal request and response carried over [UDP or TCP](card:tcp-and-udp) on port 53.

## Why it exists

If there were no DNS, you would have to hard-code IP addresses everywhere. That hurts twice: addresses are hard to remember, and the moment a service moves to a new server with a new IP, every client breaks and must be updated. A name adds one layer of indirection: clients remember the name, and you can repoint the name to a new IP whenever you like. DNS also lets one name return different IPs for load spreading and failover.

## How it works

1. The app asks its recursive resolver for the A record of `api.shop.example`. The resolver's job is to return a final answer.
2. If the resolver has the answer cached and the TTL has not expired, it returns it at once, and the walk below is skipped.
3. On a miss, the resolver asks a root server. The root does not know the IP; it refers the resolver to the servers for the `.example` top-level domain (TLD).
4. The resolver asks the `.example` TLD server, which refers it down to the authoritative server for `shop.example`.
5. The authoritative server holds the real record and answers `203.0.113.10` with a TTL. The resolver caches that answer for the TTL and returns it.

So the key is caching at every level: most lookups are answered from a cache and never reach the root.

## Example

Two commands show the answer and the walk. The record types are listed under the [DNS records](card:dns-records) node.

```bash
dig +noall +answer api.shop.example A    # show the final answer and its remaining TTL
dig +trace api.shop.example              # walk root, TLD and authoritative yourself
```

What to notice:

- `+noall +answer` prints only the answer line, including the TTL that is counting down; refresh it and the TTL shrinks, which proves the answer is cached.
- `+trace` skips the resolver's cache and does the recursive walk itself, so you see the root, then the TLD, then the authoritative server referring down, step by step.
- Change `A` to `AAAA` to ask for an IPv6 address, or `MX` for the mail servers of that name.

## Rules and defaults

- **Port and transport:** DNS uses port 53. Queries go over UDP by default; the client switches to TCP when the UDP answer is truncated, and TCP is also used for zone transfers.
- **TTL:** set per record by the zone owner. A low TTL makes changes take effect quickly but causes more lookups; a high TTL caches longer but makes changes slow to spread.
- **CNAME at the apex is not allowed:** a name with a CNAME may hold no other records, but the zone apex (`shop.example`) must hold SOA and NS records, so you cannot put a CNAME there. Use an A or AAAA record.
- **In system design:** one name can map to many IPs, and managed DNS (such as Amazon Route 53) can route by weight, latency, geography or health, which gives failover and load spreading. Kubernetes gives every Service an internal DNS name for discovery.

## Not to be confused with

- **DNS vs the connection itself:** DNS only finds the IP. The actual [TCP connection](card:tcp-and-udp) and the HTTP request happen afterwards, to that IP.
- **TTL in DNS vs TTL in an IP packet:** the DNS TTL is a number of seconds an answer may be cached. The IP packet TTL is a hop count that drops by one at each router. Same word, different meaning.

## Common mistakes

- **"DNS 'propagation' is the network copying my record around."** Nothing is pushed. A change spreads only as old cached answers expire. The slowest users are behind a resolver that cached the old value, and they wait out its TTL.

## Interview Qs

### You changed a DNS record but some users still reach the old IP. Why?

Resolvers cached the old answer and keep returning it until its TTL runs out; nothing clears caches early. The fix is to lower the TTL (for example to 60 seconds) well before a planned change, so caches drop the old value quickly, then move the record.

### Why can a CNAME not sit at the zone apex?

A name that has a CNAME record is allowed to hold no other records. But the zone apex, such as `shop.example`, must hold SOA and NS records to exist as a zone. A CNAME there would conflict with those required records, so you use an A or AAAA record at the apex instead.

### When does DNS use TCP instead of UDP?

When a UDP answer is too big and comes back truncated, the client retries over TCP; for zone transfers between name servers; or when a client simply prefers TCP. Every DNS implementation must support TCP (RFC 7766), so you cannot block TCP port 53 and expect DNS to keep working.
