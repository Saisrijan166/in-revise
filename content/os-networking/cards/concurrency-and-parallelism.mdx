## What it is

Concurrency and parallelism are two ways a program deals with many tasks. Concurrency means many tasks are in progress at the same time and share the CPU by taking turns, so one core is enough. Parallelism means tasks run in the very same instant, each on its own core, so it needs more than one core. A [thread](card:threads) is the unit the CPU runs, and the OS switches between threads through [context switching](card:context-switching), which is what makes concurrency on one core possible.

## Why it exists

A payment server handles many requests, and each one spends most of its time waiting on the database or the network, not using the CPU. If the server served requests strictly one after another, the core would sit idle during every wait and almost no work would get done. Concurrency lets the core switch to another request during that wait, so many requests move forward on the same core. Parallelism goes further and uses extra cores to run CPU-heavy work in the same instant.

## How it works

<Compare id="concurrency-vs-parallelism" />

1. Request A starts, then asks PostgreSQL for a row and must wait for the answer.
2. While A waits, the OS switches the core to request B, which runs its code.
3. When A's row arrives, the OS switches back to A, which continues. This switching is concurrency, and it works on a single core.
4. If the machine has a second core, B can run on it in the very same instant that A runs on the first core. That overlap is parallelism.

So the key is: concurrency is about structure (many tasks in progress), parallelism is about execution (many tasks literally at once).

## Analogy

<Analogy title="One cook, two cooks" limit="A cook chooses when to switch dishes; the OS scheduler switches threads whenever it decides, without asking them.">
One cook moving between three dishes keeps all of them going: that is concurrency on one core. Two cooks, each working a dish at the same moment, is parallelism on two cores.
</Analogy>

## Rules and defaults

- **One core:** can run tasks concurrently but never in parallel; only one task uses it at any instant.
- **True parallelism:** needs at least as many logical CPUs as tasks you want running at the same instant.
- **Shared data:** concurrency lets tasks touch the same data, which creates [race conditions](card:race-conditions) that you must guard.
- **I/O-bound work:** benefits from concurrency even on one core; **CPU-bound work** speeds up only with real parallelism, up to the number of cores.

## Interview Qs

### Can you have concurrency without parallelism?

Yes. On a single core the OS gives each thread a time slice in turn, so many threads make progress, but only one runs at any instant. That is concurrency with no parallelism. Parallelism needs several cores so threads can run in the same moment.

### Do more threads always make a program faster?

No. CPU-bound work speeds up only until every core is busy; beyond that, extra threads take turns and add [context switches](card:context-switching), which cost time. I/O-bound work gains more, because threads spend most time waiting. Sizing is covered in [thread pools](card:thread-pools).
