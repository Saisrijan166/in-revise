## Why it exists

A server handles many requests, and each spends most of its time waiting on the network or a disk. Serving them strictly one by one would leave the CPU idle.

## How it works

<Compare id="concurrency-vs-parallelism" />

- While request A waits for PostgreSQL, the core runs request B: see [blocking I/O](card:blocking-and-non-blocking-io).
- Concurrency brings shared data, and with it [race conditions](card:race-conditions).

## Analogy

<Analogy title="One cook, two cooks" limit="A cook chooses when to switch dishes; the OS scheduler switches threads without asking them.">
One cook moving between three dishes keeps all of them going: concurrency. Two cooks each working on a dish at the same moment: parallelism.
</Analogy>

## Interview Qs

### Can you have concurrency without parallelism?

Yes. On one core the OS gives each thread a time slice in turn, so many threads make progress, but only one runs at any instant.

### Do more threads always make a program faster?

No. CPU-bound work speeds up only until every core is busy. Beyond that, threads just take turns and add [context switches](card:context-switching). Extra threads help only when most of them are waiting on I/O.
