## Why it exists

Clients and servers written by different people need one shared way to ask for a resource, say what happened, and describe the content.

## How it works

| Method | Safe | Idempotent | Cacheable |
|---|---|---|---|
| GET, HEAD | Yes | Yes | Yes |
| OPTIONS | Yes | Yes | No |
| PUT, DELETE | No | Yes | No |
| POST, PATCH | No | No | Rarely |

- Status classes: 2xx success, 3xx redirect, 4xx client mistake, 5xx server failure.
- Know 200, 201, 204, 301, 302, 304, 400, 404, 409 (conflict), 429 (rate limited), 500.
- Retrying a POST safely needs an [idempotency key](card:network-failures).

## Example

```text
GET /orders/42 HTTP/1.1
Host: api.shop.example
Authorization: Bearer eyJhbGciOi...
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60

{"id": 42, "total": "₹1,499", "status": "PAID"}
```

[Cache-Control](card:caching-and-cdn) says who may store the answer, and for how long.

## Interview Qs

### Is PUT idempotent? Is PATCH?

PUT replaces the resource, so sending it twice leaves the same state. PATCH applies changes like "add one item", so a repeat can differ; RFC 5789 calls it not idempotent, though a patch can be written to be.

### 502 vs 503 vs 504?

502: a proxy got an invalid reply from the app. 503: the server is overloaded or in maintenance, maybe with Retry-After. 504: a proxy gave up waiting for the app. See [load balancers](card:load-balancers-and-proxies).

### HTTP is stateless, so how does login work?

After login the server sends a session id in Set-Cookie, or a token. The client sends it on every request (Cookie or Authorization), and the server looks up who it is.
