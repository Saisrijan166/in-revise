## What it is

HTTP is the language a client and a server use to talk over the web. The client sends a request: a method (what to do), a path (which resource), headers (extra details) and sometimes a body (data). The server sends a response: a status code (what happened), headers and sometimes a body. Once [DNS](card:dns) has found the server's IP and a connection is open, every exchange between browser and payment server is one HTTP request and one response.

## Why it exists

Clients and servers are written by different people in different languages, and they still need to understand each other. Without a shared format, every pair of programs would invent its own way to ask for data and report results, and nothing would interoperate. HTTP fixes one simple shape, so any client can call any server: the method says the intent, the status code says the outcome, and headers describe the content. That shared agreement is what makes the web work.

## How it works

The method tells the server your intent, and two properties decide how it may be retried and cached.

| Method | Safe (read-only) | Idempotent (repeat is same) | Usually cacheable |
|---|---|---|---|
| GET, HEAD | Yes | Yes | Yes |
| OPTIONS | Yes | Yes | No |
| PUT, DELETE | No | Yes | No |
| POST, PATCH | No | No | Rarely |

1. The client picks a method for its intent: GET to read, POST to create, PUT to replace, PATCH to change part, DELETE to remove.
2. The server does the work and returns a status code: 2xx success, 3xx redirect, 4xx the client's mistake, 5xx the server's failure.
3. The client reads the status to decide what to do next: 200 use the body, 301 follow the new location, 404 the resource is gone, 429 slow down and retry later.

So the key is that method plus status code carry the meaning; the body is just the data.

## Example

A GET request for one order, and the response. This is the running payment example, over plain HTTP:

```text
GET /orders/42 HTTP/1.1
Host: api.shop.example
Authorization: Bearer eyJhbGciOi...
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60

{"id": 42, "total": "1499.00", "status": "PAID"}
```

What to notice:

- The request's first line is method, path and version; the `Host` header names which site on that IP (one server can host many).
- `Authorization: Bearer ...` carries the token, because HTTP is stateless and the server would otherwise not know who is asking.
- `Cache-Control: private, max-age=60` is the server telling the client it may reuse this answer for 60 seconds; [HTTP caching](card:caching-and-cdn) builds on this header.
- Change the method to DELETE and the same path means "remove order 42"; the path is the resource, the method is the intent.

## Rules and defaults

- **Stateless:** the server keeps no memory of past requests. State is carried by the client on each request, usually a session id in a `Cookie` or a token in `Authorization`.
- **Status classes:** 2xx success, 3xx redirect, 4xx client error, 5xx server error. Worth knowing: 200, 201 (created), 204 (no content), 301/302 (redirect), 304 (not modified), 400, 401, 403, 404, 409 (conflict), 429 (rate limited), 500.
- **Retrying POST is not automatically safe:** POST is not idempotent, so a blind retry can create duplicates. Use an [idempotency key](card:network-failures) when you must retry it.

## Not to be confused with

- **Safe vs idempotent:** safe means the request changes nothing (read-only). Idempotent means repeating it leaves the same state, even if the first call did change something. GET is both; DELETE is idempotent but not safe (it changes state, but deleting twice ends the same).
- **401 vs 403:** 401 is authentication (the server does not know who you are, log in). 403 is authorisation (it knows you and refuses).

## Common mistakes

- **"PUT and PATCH are the same, both update."** PUT replaces the whole resource with the body you send, so a missing field is cleared. PATCH sends only the fields to change. PUT is idempotent; PATCH like "add one item" is not (RFC 5789).

## Interview Qs

### Is PUT idempotent? Is PATCH?

PUT replaces the resource with the body, so sending it twice leaves the same final state: it is idempotent. PATCH sends a change, which can be relative like "add one item", so a repeat can differ. RFC 5789 says PATCH is not idempotent by default, though a specific patch can be written to be.

### What is the difference between 401 and 403?

401 Unauthorized means the request has no valid credentials: the client should authenticate (log in). 403 Forbidden means the server understood and the client is authenticated, but is not permitted to do this, and logging in again will not help. In short: 401 is about who you are, 403 is about what you may do.

### HTTP is stateless, so how does a logged-in session work?

After login the server sends a session id in `Set-Cookie`, or issues a token. The client stores it and sends it back on every request (`Cookie` or `Authorization`). The server looks it up to know who is calling. The protocol stays stateless; the client carries the identity each time.
