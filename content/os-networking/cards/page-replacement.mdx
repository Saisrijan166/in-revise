## What it is

Page replacement is the OS's rule for choosing which page to throw out of RAM when RAM is full and a new page has to come in. The page that is thrown out is the victim. A replacement policy is the strategy that picks the victim, such as "evict the page used longest ago". This builds on [paging](card:paging-and-page-faults): a [major page fault](card:paging-and-page-faults) can only load its page once there is a free frame.

## Why it exists

RAM usually holds only some of the pages that processes are using, because the sum of their address spaces is larger than RAM. When a page that is not in RAM is touched, it needs a frame, and if every frame is taken, one page must leave. The choice matters: evict a page that is needed again immediately and it faults straight back in from disk, so a poor policy turns into a stream of slow disk reads.

## How it works

| Policy | Which page it evicts | In practice |
|---|---|---|
| FIFO | The page loaded earliest | Simple, but ignores how pages are used; can suffer Belady's anomaly |
| LRU | The least recently used page | Good results, but tracking exact use on every access is too costly |
| Optimal | The page used farthest in the future | Needs to know the future, so it is only a benchmark |
| Clock | The first page whose use bit is 0, clearing bits as it scans | A cheap approximation of LRU, used in real systems |

1. A page fault occurs and there is no free frame.
2. The policy selects a victim page using its rule (for example, least recently used).
3. If the victim is dirty (changed since it was loaded), the OS writes it back to disk first; a clean page is simply dropped.
4. The freed frame is given to the new page, which is loaded, and the faulting instruction retries.

So the key is to pick a victim you will not need again soon; LRU approximates this by betting that recently used pages will be used again.

## Example

With three frames and the reference string `7 0 1 2 0 3 0 4 2 3`, the three policies fault a different number of times (F marks a fault).

```text
refs     7 0 1 2 0 3 0 4 2 3
FIFO     F F F F . F F F F F   9 faults
LRU      F F F F . F . F F F   8 faults
Optimal  F F F F . F . F . .   6 faults
```

What to notice:

- All three start the same while frames are still empty; they only differ once a frame must be reused.
- LRU beats FIFO because it keeps recently used pages (like page 0) that are referenced again, instead of evicting by load order.
- Optimal is best because it alone can see the future references; no real OS can do this, so it is used only to judge how good a real policy is.

## Rules and defaults

- **When it runs:** only on a page fault that needs a frame and finds none free.
- **Dirty vs clean:** a dirty victim costs a disk write before eviction; a clean victim is just discarded, so clean pages are cheaper to evict.
- **Real kernels:** Linux does not track exact LRU; it approximates it with active and inactive page lists and reclaims from the inactive list.
- **Belady's anomaly:** with FIFO, adding frames can increase faults. LRU and optimal are "stack" policies and never get worse with more frames.
- **Thrashing:** if the combined working sets exceed RAM, paging dominates and real work stalls; fix it with more RAM, fewer processes, or less memory per process.

## Interview Qs

### What is thrashing, and how do you fix it?

Thrashing is when processes' working sets do not fit in RAM, so the system spends almost all its time paging to and from disk and gets little real work done, with the CPU mostly idle. You fix it by adding RAM, running fewer processes at once, or reducing each process's memory use.

### What is Belady's anomaly?

Belady's anomaly is that with the FIFO policy, giving a process more frames can cause more page faults, not fewer. For the reference string 1 2 3 4 1 2 5 1 2 3 4 5, FIFO faults 9 times with 3 frames but 10 times with 4. LRU and optimal never show this.

### Why not just use the optimal policy?

The optimal policy evicts the page that will be used farthest in the future, which requires knowing future accesses. A real OS cannot see the future, so optimal cannot be implemented. It is kept as the yardstick: real policies like LRU are judged by how close they come to it.
