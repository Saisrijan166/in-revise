## Why it exists

Each [process](card:processes) has its own memory, so one crash cannot corrupt another. To cooperate, the kernel must carry data or share pages between them.

## How it works

| Mechanism | Use when |
|---|---|
| [Pipe](card:pipe) | one-way stream between related processes (shell pipelines) |
| [Named pipe (FIFO)](card:named-pipe) | the same, between unrelated processes on one host |
| [Message queue](card:message-queue-ipc) | separate messages rather than a byte stream |
| [Shared memory](card:shared-memory-ipc) | large data without copying; guard it with a [semaphore](card:semaphores) |
| [Signal](card:unix-signal) | a tiny notice, such as "stop now" |
| [Socket](card:ports-and-sockets) | same host ([Unix domain](card:unix-domain-socket)) or across hosts |

## Example

After `kill -TERM <pid>` the hook prints; after `kill -KILL` it never does.

```java
Runtime.getRuntime().addShutdownHook(new Thread(() ->
        System.out.println("Shutdown hook: finishing in-flight orders")));
System.out.println("Orders API running");
Thread.sleep(60_000);
```

```text output
Orders API running
Shutdown hook: finishing in-flight orders
```

## Defaults

| What | Default | Where |
|---|---|---|
| Graceful shutdown | on (`server.shutdown=graceful`) | Spring Boot 4.1 |
| SIGTERM to SIGKILL grace | 30 s (`terminationGracePeriodSeconds`) | Kubernetes Pods |

## Interview Qs

### Message passing vs shared memory?

With a pipe or queue the kernel copies each message and handles waiting. With shared memory both processes touch the same pages: faster for big data, but they must coordinate with a semaphore or lock.

### How does a Spring Boot service shut down cleanly on Kubernetes?

Kubernetes sends SIGTERM, waits the grace period, then sends SIGKILL. On SIGTERM, Spring Boot refuses new requests and lets in-flight ones finish; keep `spring.lifecycle.timeout-per-shutdown-phase` below the pod's grace period.
