## What it is

The memory hierarchy is the set of places a CPU can keep data, arranged from fastest and smallest to slowest and largest. At the top are registers inside the core, then three levels of CPU cache (L1, L2, L3), then main memory (RAM), then disk (SSD or HDD). A cache is a small, fast store that holds copies of recently used data so the CPU does not have to fetch it from a slower level every time.

## Why it exists

A CPU core can do work far faster than RAM can hand it data: a RAM read takes roughly 100 nanoseconds, while the core finishes many instructions in that time. If every read waited for RAM, the core would sit idle most of the time. Small caches next to the core keep copies of recent data, so the common case is a fast cache hit and the core rarely waits for RAM.

## How it works

1. The core needs a value, so it asks its L1 cache first.
2. If L1 has the value, that is a cache hit and the core gets it almost at once.
3. If L1 misses, the request goes to L2, then L3, then RAM, each slower than the one before.
4. When the value is finally found, the CPU copies its whole 64-byte cache line up, so the neighbours of that value are now cheap to read too.

So the key is to work in a way that turns most reads into L1 or L2 hits, which depends on locality.

## Example

This reads the cache sizes and cache-line size of a Linux machine, so you can see the levels and the 64-byte line in real numbers.

```bash
lscpu | grep -E '^L[123]'
getconf LEVEL1_DCACHE_LINESIZE
```

```text output
L1d cache:                               64 KiB (2 instances)
L1i cache:                               64 KiB (2 instances)
L2 cache:                                512 KiB (2 instances)
L3 cache:                                3 MiB (1 instance)
64
```

What to notice:

- L1 and L2 each have two instances here, one per core, while L3 is a single shared cache. This matches "L1/L2 per core, L3 shared".
- The caches get larger as you go down (64 KiB, 512 KiB, 3 MiB) because larger stores are slower, so only the smallest stay closest to the core.
- `LEVEL1_DCACHE_LINESIZE` is 64: data moves in 64-byte blocks, which is why reading neighbours is nearly free.

## Rules and defaults

- **Cache line size:** 64 bytes on Intel Core and Xeon CPUs. One memory read fills a whole line, not a single byte.
- **Cache levels:** L1 and L2 are usually private to one core; L3 is usually shared across the cores of a chip.
- **Latency order (approximate, from Norvig's table):** L1 about 0.5 ns, L2 about 7 ns, RAM about 100 ns, an HDD seek about 8 ms. These are orders of magnitude, not exact figures.
- **Address translations** have their own cache, the [TLB](card:paging-and-page-faults), and file data read from disk is kept in the [page cache](card:files-and-file-descriptors) in RAM.

## Interview Qs

### What is locality of reference?

Locality is the tendency of programs to reuse data they used recently (temporal locality) and to use data stored near it (spatial locality). Caches, including the TLB, bet on this: they keep recent data and fetch whole lines, so most accesses become hits.

### Why is looping over an array faster than walking a linked list?

Array elements sit next to each other, so one cache line brings several, and the next reads are hits (spatial locality). Linked-list nodes can be anywhere in RAM, so each step may land on a new line and cause a cache miss that waits for memory.

### What is false sharing, and how do you fix it?

Two threads write different variables that happen to share one cache line. Each write invalidates the line in the other core's cache, so the line bounces between cores and throughput drops. The fix is to pad the hot fields into separate cache lines; since Java 8 the JVM can pad marked fields itself (JEP 142, used inside the JDK).
