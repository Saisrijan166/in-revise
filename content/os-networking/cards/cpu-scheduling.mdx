## What it is

**CPU scheduling** is how the kernel decides which ready thread to run next on a free core, and for how long, when more threads are ready than there are cores. The part that decides is the **scheduler**. A **scheduling algorithm** is the rule it uses. Each rule optimises a different goal: some aim for the lowest average wait, some for the fastest first response, some for fairness, and no single rule is best at all three.

## Why it exists

A core runs one thread at a time, but many threads are usually ready at once. Some order has to be chosen, and the order decides real outcomes: how long each user waits for a reply, and whether some jobs ever run at all. A careless rule lets one long job block many short ones, or lets a busy stream of high-priority work freeze a low-priority task forever. A good scheduler balances these so the system feels fast and fair.

## How it works

The common textbook algorithms differ in which job they pick next, whether they can interrupt a running job (preemptive), and what goes wrong with each.

| Algorithm | Runs next | Preemptive | Watch out |
|---|---|---|---|
| FCFS | The earliest to arrive | No | Convoy effect: short jobs stuck behind a long one |
| SJF | The shortest job | No | Needs to know job lengths; long jobs can starve |
| SRTF | The shortest remaining time | Yes | Same, plus more context switches |
| Priority | The highest priority | Either | Starvation; fix with aging |
| Round robin | The next in turn, one time slice each | Yes | The slice size is a trade-off |

1. Jobs become ready and join the scheduler's queue.
2. The scheduler applies its rule to pick one and runs it, either to completion (non-preemptive) or until its slice ends or a better job appears (preemptive).
3. A preempted or finished job leaves the core, and the scheduler picks again.

So the key is that the rule you pick decides who waits and whether anyone starves. Real kernels mix these ideas: an [MLFQ](card:mlfq) moves jobs between priority queues by how they behave, and Linux uses [EEVDF](card:eevdf).

## Example

Three jobs arrive together: one 100 ms report and two 10 ms API calls. A job's waiting time is when it first starts, so the order of execution decides the average.

```text
FCFS  report, api1, api2   waits 0, 100, 110 ms   average 70 ms
SJF   api1, api2, report   waits 0,  10,  20 ms   average 10 ms
```

What to notice:

- FCFS keeps the arrival order, so both quick API calls sit behind the long report and wait about 100 ms each. That is the convoy effect.
- SJF runs the two short jobs first, so they barely wait and the average drops from 70 ms to 10 ms.
- SJF needs to know, or guess, how long each job will take; if it guesses wrong, or a long job keeps getting pushed back by new short ones, that long job can starve.

## Rules and defaults

- **Preemptive is the norm:** general-purpose kernels preempt, so no single thread can hold a core forever; purely non-preemptive scheduling fits only batch jobs or code trusted to yield.
- **Time slice is a trade-off:** a round-robin slice too short wastes the CPU on context switches; too long and response time suffers like FCFS.
- **Aging prevents starvation:** raising a waiting job's priority over time guarantees it eventually runs under priority scheduling.
- **Linux default:** EEVDF since Linux 6.6; of the tasks owed CPU time, it runs the one with the earliest virtual deadline first.

## Interview Qs

### What is the difference between preemptive and non-preemptive scheduling?

Non-preemptive scheduling lets a job keep the CPU until it finishes, blocks or yields on its own. Preemptive scheduling can take the CPU away, for example when a timer interrupt ends the job's time slice or a higher-priority job becomes ready. Servers and desktops use preemptive scheduling so one job cannot freeze the system.

### What are starvation and aging?

Starvation is when a ready job never gets the CPU because others are always chosen first, as a low-priority job can under strict priority scheduling. Aging fixes it: the scheduler raises a job's priority the longer it has been waiting, so its priority eventually rises high enough that it runs.

### What is the convoy effect?

Under FCFS, when one long job arrives first, all the short jobs behind it must wait for it to finish, even though each is quick. This pushes the average waiting time far up. It is the main argument against plain FCFS and for shortest-job-first or round-robin scheduling.
