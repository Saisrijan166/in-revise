## Why it exists

Many threads are ready, but a CPU runs one at a time. The order decides how long users wait and whether some jobs ever run.

## How it works

| Algorithm | Runs next | Preemptive | Watch out |
|---|---|---|---|
| FCFS | Earliest arrival | No | Convoy effect: short jobs stuck behind a long one |
| SJF | Shortest job | No | Needs job lengths; long jobs can starve |
| SRTF | Shortest remaining time | Yes | Same, plus more switches |
| Priority | Highest priority | Either | Starvation; fix with aging |
| Round robin | Next in turn, one time slice each | Yes | Slice size is a trade-off |

- Real schedulers mix ideas: [MLFQ](card:mlfq) moves jobs between priority queues by behaviour; Linux uses [EEVDF](card:eevdf).

## Example

Three jobs arrive together: a 100 ms report and two 10 ms API calls. Waiting time is the start time:

```text
FCFS  report, api1, api2   waits 0, 100, 110 ms   average 70 ms
SJF   api1, api2, report   waits 0, 10, 20 ms     average 10 ms
```

## Interview Qs

### Preemptive vs non-preemptive scheduling?

Non-preemptive lets a job keep the CPU until it finishes, blocks or yields. Preemptive can take it away, for example when a timer interrupt ends its slice. Servers and desktops use preemptive scheduling.

### What are starvation and aging?

Starvation: a ready job never gets the CPU because others always win, as with low priorities under strict priority scheduling. Aging raises a job's priority the longer it waits, so it eventually runs.

### What is the convoy effect?

Under FCFS, short jobs queue behind one long job, so the average wait shoots up.
