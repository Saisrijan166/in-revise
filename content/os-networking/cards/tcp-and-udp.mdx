## Why it exists

Apps need a choice: full reliability built into the transport (TCP), or a thin, quick path that adds little more than ports and a checksum (UDP).

## How it works

<Compare id="tcp-vs-udp" />

- TCP's machinery: the [handshake](card:tcp-handshake), [ACKs and resends](card:tcp-reliability), [flow and congestion control](card:flow-and-congestion-control).
- [DNS](card:dns) uses UDP for most queries, but servers must also support TCP, for large answers and zone transfers (RFC 7766).
- QUIC, the transport under [HTTP/3](card:http-versions), rebuilds reliability and congestion control on top of UDP.

## Example

Two writes on one TCP connection come out as one read (Java, localhost):

```java
try (var server = new ServerSocket(8080);
     var client = new Socket("localhost", 8080);
     var conn = server.accept()) {
    client.getOutputStream().write("order:42;".getBytes());   // send 1
    client.getOutputStream().write("order:43;".getBytes());   // send 2
    Thread.sleep(100);                       // both writes reach the buffer
    byte[] buf = new byte[100];
    int n = conn.getInputStream().read(buf);  // one read
    System.out.println(n + " bytes: " + new String(buf, 0, n));
}
```

```text output
18 bytes: order:42;order:43;
```

The `;` is the framing. Real protocols use a delimiter or a length prefix.

## Interview Qs

### When would you choose UDP over TCP?

When late data is worse than lost data: live voice and video, where waiting for a resend is not an option. Also when the protocol adds its own reliability, as QUIC does.

### Is TCP message-based?

No, it is a byte stream. Two sends can arrive in one read, or one send in two reads. The app must mark where each message ends.

### Why does DNS mostly use UDP?

A small query and answer fit in one datagram, so no handshake is needed. Large answers and zone transfers go over TCP, which every DNS server must support.
