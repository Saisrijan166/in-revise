## What it is

TCP and UDP are the two transport protocols that run on top of [IP](card:tcp-ip-model). Both add [ports](card:ports-and-sockets) so the data reaches the right program on a host. The difference is what else they add. TCP first sets up a connection, then gives a reliable, ordered stream of bytes: everything arrives once, in order, and anything lost is resent automatically. UDP adds almost nothing: it sends each message (a datagram) on its own, with no setup and no promise that it arrives, once, or in order.

## Why it exists

Different applications need different things, and the network can lose, reorder or duplicate packets. A web page or file transfer must be exact, so it wants the transport to hide all of that and hand over clean, ordered data: that is TCP. A live voice call cannot wait for a lost packet to be resent, because by then that moment of audio is already in the past; it would rather drop the gap and move on. So the transport layer offers both: TCP for correctness, UDP for a thin, fast path the application controls itself.

## How it works

<Compare id="tcp-vs-udp" />

1. The application picks a protocol when it opens a [socket](card:ports-and-sockets): a stream socket for TCP, a datagram socket for UDP.
2. For TCP, the two ends run a [handshake](card:tcp-handshake) to agree to talk; UDP skips this and the first `send` goes straight out.
3. On TCP, your writes become one continuous byte stream: the sender may merge or split them, and the receiver reads bytes, not messages. On UDP, each `send` is one datagram and each `receive` returns exactly that datagram.
4. TCP tracks every byte and [resends what is lost](card:tcp-reliability), with [flow and congestion control](card:flow-and-congestion-control) deciding how fast to send. UDP does none of this, so if the app needs it, the app must add it.

So the key is that TCP trades extra work and one round trip of setup for delivery you can trust, while UDP hands you raw datagrams and leaves the guarantees to you.

## Example

On one TCP connection, two separate writes can arrive in a single read, which shows there are no message boundaries.

```java
try (var server = new ServerSocket(8080);
     var client = new Socket("localhost", 8080);
     var conn = server.accept()) {
    client.getOutputStream().write("order:42;".getBytes());   // write 1
    client.getOutputStream().write("order:43;".getBytes());   // write 2
    Thread.sleep(100);                                         // let both reach the buffer
    byte[] buf = new byte[100];
    int n = conn.getInputStream().read(buf);                   // one read
    System.out.println(n + " bytes: " + new String(buf, 0, n));
}
```

```text output
18 bytes: order:42;order:43;
```

What to notice:

- Two `write` calls came back in one `read`: TCP joined them into one stream, so a read is not a message.
- The `;` is doing the framing: the client knows where each order ends only because of that delimiter. Real protocols use a delimiter or a length prefix.
- If this were UDP, the two `send` calls would arrive as two datagrams, each received whole and separately, but either one could also be silently lost.

## Rules and defaults

- **TCP header:** 20 bytes without options; it carries sequence and acknowledgement numbers, the window and flags (RFC 9293).
- **UDP header:** 8 bytes: source port, destination port, length and checksum, and nothing else (RFC 768).
- **DNS:** most queries go over UDP, but every DNS server must also support TCP, for answers too large for one datagram and for zone transfers (RFC 7766).
- **UDP apps should add congestion control:** RFC 8085 tells applications on UDP to limit their own sending rate, because the transport will not.

## Not to be confused with

A byte stream and a datagram are the real split. A byte stream (TCP) is a continuous flow of bytes with no edges, so the receiver must find message boundaries itself. A datagram (UDP) is one self-contained message that arrives whole or not at all. Rule: TCP = one ordered stream you must frame; UDP = separate messages that may go missing.

## Common mistakes

- **"TCP is slow and UDP is fast, full stop."** TCP's cost is the handshake and the resends, which buy you delivery and order. On a clean link TCP is fast too; UDP is only faster because the app is doing less, or doing without.
- **"A TCP read returns one message."** It returns whatever bytes are available, which may be part of a message or several messages joined. TCP is a [byte stream](term:byte-stream), so you must frame messages yourself.

## Interview Qs

### When would you choose UDP over TCP?

When late data is worse than lost data, such as live voice and video, where waiting for a resend would stall the stream. Also when the protocol adds its own reliability on top of UDP, as QUIC does for HTTP/3. For normal request-response APIs, TCP is the default.

### Is TCP message-based?

No. TCP is a byte stream with no message boundaries. Two sends can arrive in one read, or one send can arrive in two reads. The application must mark where each message ends, usually with a delimiter or a length prefix, and reassemble messages itself.

### Why does DNS mostly use UDP?

A small query and its answer each fit in one datagram, so UDP avoids the cost of a handshake for a single quick exchange. Large answers and zone transfers do not fit, so they use TCP, which every DNS server is required to support as well.
