## What it is

A connection pool is a small set of database connections the app opens ahead of time and keeps ready. When a request needs the database it borrows one connection from the pool, runs its queries, and returns the connection; the connection stays open for the next request. The app never opens a connection per request. In a Java app on Spring Boot 4.1 this pool is HikariCP, created for you.

## Why it exists

Opening a new database connection is expensive: it needs a [TCP handshake](card:tcp-handshake), often a [TLS](card:tls-https) handshake, and a login before the first query can run, and each of those is a round trip. If every request opened its own connection, it would pay all that cost before doing any work, and the database would waste effort setting connections up and tearing them down. A pool pays that cost once per connection and then reuses it, so requests go straight to querying. It also caps how many connections the app can open, which protects the database.

## How it works

<Steps label="One request using a pool of 10 connections">
  <Step title="Borrow">The request's thread takes an idle, already-open connection from the pool.</Step>
  <Step title="Use">It runs its SQL on PostgreSQL over that connection.</Step>
  <Step title="Return">It hands the connection back to the pool; the connection stays open.</Step>
  <Step title="Reuse">The next request borrows the same connection and pays no setup cost.</Step>
  <Step title="Pool empty">If all 10 are busy, a new request waits up to connectionTimeout, then gets an error.</Step>
</Steps>

1. At startup the pool opens a few connections and keeps them idle.
2. Each request borrows one, uses it, and returns it, as in the steps above.
3. The pool limits the total to `maximumPoolSize`, so the database never sees more than that from this instance.
4. You size the whole system by a budget: the number of app instances times each pool's size must stay under the database's `max_connections`.

So the key is reuse within a capped, small pool: fast requests and a protected database.

## Example

This is the pool configuration for the payment service. Spring Boot reads these properties and builds the HikariCP pool.

```properties
# application.properties (Spring Boot 4.1, HikariCP)
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.connection-timeout=30000
spring.datasource.hikari.max-lifetime=1800000
```

What to notice:

- `maximum-pool-size=10` caps this instance at 10 connections; ten such instances already reach PostgreSQL's default of about 100, so this is the number to watch when you scale out.
- `connection-timeout=30000` (milliseconds) is how long a request waits for a free connection before failing; a request hanging exactly this long points to pool exhaustion.
- `max-lifetime=1800000` retires a connection after 30 minutes, so stale connections are replaced before the database or a firewall drops them.
- HTTP clients pool connections too: keep-alive reuses the same TCP connection for several requests ([HTTP versions](card:http-versions)).

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Maximum connections in the pool | 10 | HikariCP `maximumPoolSize` |
| Wait time for a free connection | 30 s | HikariCP `connectionTimeout` |
| Total connections the database accepts | about 100 | PostgreSQL 18 `max_connections` |

- **Small pools win:** a pool near the number of queries the database can run in parallel, with extra threads waiting briefly, beats a large pool that overloads the database.
- **Shared budget:** when many instances outgrow `max_connections`, put [PgBouncer](card:pgbouncer) in front to multiplex many app connections onto fewer real ones.

## Common mistakes

- **"Set the pool huge so nothing ever waits."** Beyond what the database can run at once, extra connections only add contention and slow every query. Small and steady is faster.
- **"The pool is the problem, so grow it."** Usually the real cause is slow queries, long transactions or a connection leak holding connections. Fix those first, then size the pool.

## Interview Qs

### Why use a connection pool instead of opening a connection per request?

Opening a connection needs a TCP handshake, often TLS, and a database login, all before the first query. Paying that on every request is slow for the user and heavy for the database. A pool opens connections once and reuses them, so requests go straight to querying. It also caps how many connections the app can open.

### Every request hangs for the full timeout and then fails. What is wrong?

The pool is exhausted: all its connections are held, usually by slow queries, long transactions, or a connection leak. New requests wait up to `connectionTimeout` and then error. Fix the slow work and any leak first; growing the pool just pushes the load onto the database.

### How big should the pool be?

Small. HikariCP's guide starts from roughly (database CPU cores times 2) plus the disk's effective spindles, then load tests from there. Its own example is about 10 connections on a 4-core database serving thousands of users. Crucially, all instances times their pool size must stay under the database's `max_connections`.
