## What it is

HTTP/1.1, HTTP/2 and HTTP/3 are three versions of the same protocol. They carry the same [requests, methods and status codes](card:http-basics); what changes is how the bytes travel over the network. HTTP/1.1 is text and sends one request at a time on a connection. HTTP/2 packs requests into binary streams that share one connection. HTTP/3 keeps those streams but moves them off TCP onto QUIC, a transport that runs over [UDP](card:tcp-and-udp).

## Why it exists

One web page or API screen makes dozens of requests. With HTTP/1.1 each connection handles one request at a time, so the browser either waits in line or opens about six connections per site, which is wasteful and still slow. HTTP/2 lets all those requests share one connection at once, cutting handshakes and sockets. But they still share one TCP stream, so a single lost packet stalls them all; HTTP/3 removes that last bottleneck by giving each stream its own loss recovery.

## How it works

<Compare id="http1-vs-http2-vs-http3" />

1. The client and server agree the version during the TLS handshake using ALPN; the server can advertise HTTP/3 with an [Alt-Svc](card:alt-svc) header so the next connection tries QUIC.
2. HTTP/1.1 reuses one TCP connection but runs requests serially; a slow response blocks the next one (head-of-line blocking at the HTTP level).
3. HTTP/2 splits each request into a binary stream and interleaves many streams on one TCP connection, so none waits for another at the HTTP level. It also shrinks repeated headers with HPACK.
4. HTTP/3 carries streams over QUIC, which recovers lost packets per stream, so a loss stalls only its own stream; QUIC also folds in TLS 1.3, so a fresh connection sets up in one round trip.

So the key is where blocking can still happen: HTTP/1.1 at the request level, HTTP/2 at the TCP level, HTTP/3 only within one stream.

## Rules and defaults

- **Persistent connections:** on by default in HTTP/1.1 (RFC 9112); `Connection: close` opts out. Browsers open about six parallel connections per origin over HTTP/1.1.
- **Multiplexing:** HTTP/2 and HTTP/3 use one connection with many streams, so domain sharding and spriting (HTTP/1.1 workarounds) no longer help.
- **Server push is effectively gone:** HTTP/2 server push was disabled by default in Chrome 106 and other Chromium browsers; use `103 Early Hints` to preload instead.
- **Fallback:** HTTP/3 needs UDP. If a network blocks UDP, clients fall back to HTTP/2 or HTTP/1.1 over TCP, so you keep TCP serving too.

## Not to be confused with

- **HTTP-level vs TCP-level head-of-line blocking:** HTTP/1.1 blocks because responses queue on the connection. HTTP/2 fixes that, but TCP must deliver bytes in order, so one lost packet still blocks all streams at the TCP level. HTTP/3 solves the TCP-level case with QUIC.
- **QUIC vs HTTP/3:** QUIC is the transport (streams, loss recovery, TLS 1.3) over UDP; HTTP/3 is HTTP mapped onto QUIC.

## Interview Qs

### Why does HTTP/3 run over UDP instead of a new transport?

TCP is baked into operating systems and middleboxes and is slow to change. UDP is a thin layer that already passes through existing networks, so QUIC is built on top of it in user space. QUIC then adds streams, per-stream loss recovery, congestion control and TLS 1.3, and can set up a connection in one round trip.

### What does switching to HTTP/2 change in a system design?

Each client uses one long-lived connection instead of about six. That means fewer TCP and TLS handshakes, fewer open sockets on the load balancer, and better use of each connection. Old HTTP/1.1 tricks like domain sharding stop helping and should be removed, since they only add connections and DNS lookups.

### HTTP/2 multiplexes, so why can it still feel slow on a bad network?

Its streams all ride one TCP connection, and TCP delivers bytes strictly in order. If one packet is lost, TCP holds back every stream until the retransmission arrives, so all of them stall together. This is TCP-level head-of-line blocking. HTTP/3 avoids it by recovering loss per QUIC stream.
