## Why it exists

Unix gives every open file, device, pipe or socket a file descriptor, so the same `read()` and `write()` work on all of them.

## How it works

<Mermaid
  alt="An fd points to an open file entry (offset, flags), which points to the inode. Data goes through the page cache in RAM and reaches the SSD or HDD later, or at once on fsync."
  chart={`flowchart LR
  FD["fd table: 0 1 2 3"] --> OF["Open file: offset, flags"]
  OF --> IN["Inode: metadata, blocks"]
  IN --> PC["Page cache (RAM)"]
  PC -- "later, or fsync" --> D[("SSD / HDD")]`}
/>

- The first file a program opens is usually fd 3; `accept()` returns a new fd per client.

## Example

A hard link is a second name for the inode; a symlink holds a path, so it can dangle:

```bash
echo '{"id":42}' > order.json
ln order.json order-hard.json        # hard link
ln -s order.json order-link.json     # symbolic link
stat -c '%i %h %N' order*            # inode, link count, name
rm order.json
cat order-hard.json; cat order-link.json
```

```text output
8046594 2 'order-hard.json'
8046594 2 'order.json'
8046608 1 'order-link.json' -> 'order.json'
{"id":42}
cat: order-link.json: No such file or directory
```

## Interview Qs

### What is a file descriptor, and why does a server care?

An index into the process's open-file table. Sockets are fds too, so each connection uses one; past RLIMIT_NOFILE, accept() fails with EMFILE.

### HDD vs SSD: why does random I/O matter?

An HDD has moving parts, so it manages only a few hundred random I/Os per second: in OSTEP's table, 2 MB/s random vs 223 MB/s sequential. SSDs have no moving parts and do tens to hundreds of MB/s random.
