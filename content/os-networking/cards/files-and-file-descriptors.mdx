## What it is

A file descriptor (fd) is a small non-negative integer that a [process](card:processes) uses to refer to something it has open. The same `read()` and `write()` calls work whether the fd points to a file on disk, a network socket, or a pipe to another process. So, to a program, a socket is just an fd it reads and writes, which is why fds and sockets come up together. Behind a file's fd, the file on disk is described by an inode: its metadata and disk blocks.

## Why it exists

A server needs one uniform way to talk to very different things: log files, client sockets, pipes. Giving each of them an fd and the same `read()`/`write()` interface means your payment server reads a request from a socket and writes to a log file with the same two calls. The cost is that fds are a limited, per-process resource, so a leak or a connection spike runs the server out of them.

## How it works

  chart={`flowchart LR
  FD["fd table: 0 1 2 3 ..."] --> OF["Open file: offset, flags"]

1. The program opens a file or accepts a socket; the kernel returns the lowest free fd number. The first file is usually fd 3, because 0, 1 and 2 are already taken.
2. Each `accept()` on a listening socket returns a new fd for that one client, so each connection consumes an fd.
3. A `write()` copies the bytes into the page cache in RAM and returns; the kernel writes them to the device later, in the background.
4. A `read()` of data already in the page cache is served from RAM, skipping the disk entirely, which is why repeat reads are fast.

So the key is that writes are not on disk when `write()` returns; `fsync()` is what forces them down.

## Example

A hard link is a second name for the same inode; a symbolic link holds a path and can dangle if the target is removed. This was run; inode numbers vary by machine.

```bash
echo '{"id":42}' > order.json
ln order.json order-hard.json        # hard link: another name for the same inode
ln -s order.json order-link.json     # symbolic link: a path pointing at order.json
stat -c '%i %h %N' order*            # inode number, link count, name
rm order.json                        # remove the original name
cat order-hard.json; cat order-link.json
```

```text output
8046594 2 'order-hard.json'
8046594 2 'order.json'
8046608 1 'order-link.json' -> 'order.json'
{"id":42}
cat: order-link.json: No such file or directory
```

What to notice:

- `order.json` and `order-hard.json` share one inode number and show a link count of `2`: they are two names for the same file data, not two copies.
- After `rm order.json`, the data survives because the inode still has one name (`order-hard.json`): the file goes only when its last link is removed.
- The symlink has its own inode and just stores the path `order.json`; once that name is gone, the symlink dangles and `cat` fails.

## Rules and defaults

- **Standard fds:** 0 is stdin, 1 is stdout, 2 is stderr, opened for you at startup.
- **Open-file limit:** each process has a soft cap `RLIMIT_NOFILE` (`ulimit -n`); opening past it fails with `EMFILE`, reported as "Too many open files".
- **Durability:** `write()` only guarantees the page cache; `fsync(fd)` blocks until that file's data is on the device. For a newly created file, also `fsync` its directory so the name itself is persisted.
- **Storage:** HDDs pay a mechanical seek and rotation per random access, so random I/O is far slower than sequential; SSDs have no moving parts and are much faster at random reads.

## Interview Qs

### What is a file descriptor, and why does a server care about them?

It is a small integer that stands for something a process has open, and the same `read()`/`write()` work on it whether it is a file, socket or pipe. Sockets are fds too, so each client connection uses one; once a process hits `RLIMIT_NOFILE`, `accept()` fails with `EMFILE` and the server stops taking clients.

### Why is write() returning not enough for durability, and what fixes it?

`write()` usually only copies the bytes into the page cache in RAM, so a crash or power loss before the kernel flushes them loses the data. Calling `fsync(fd)` blocks until that file's data is on the device; for a new file you also `fsync` its directory so the name survives. Databases rely on this to keep committed data.

### Why does random versus sequential I/O matter on an HDD?

Every random read on an HDD pays a mechanical seek and rotational delay to move the head, which dominates the time. OSTEP's figures show a few MB/s random against hundreds of MB/s sequential. SSDs have no moving parts, so their random reads are far closer to sequential, which changes how databases lay out data on each.
