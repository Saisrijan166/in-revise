## What it is

TCP reliability is the set of mechanisms that let TCP hand the application an exact, in-order copy of the bytes that were sent, even though the [IP](card:tcp-ip-model) layer under it can lose, corrupt, duplicate or reorder packets. It works by numbering every byte with a [sequence number](card:tcp-handshake), having the receiver acknowledge the next byte it still expects, and resending anything that is not acknowledged. These are the guarantees that [TCP has and UDP does not](card:tcp-and-udp).

## Why it exists

The network gives no promises: a packet can vanish, arrive twice, arrive out of order, or arrive with flipped bits. If the application had to cope with all of that itself, every program would reinvent the same fiddly, error-prone logic. TCP does it once, in the transport layer. It detects a missing or corrupted byte range and resends just that range, and it reorders what arrives early, so the program above simply reads a clean stream and never sees the mess underneath.

## How it works

1. The sender labels its data by byte: the first chunk is bytes 1-1000, the next 1001-2000, and so on.
2. The receiver replies with the next byte it wants. After bytes 1-1000 it sends ACK 1001, meaning "I have everything up to 1000".
3. When 1001-2000 is lost but later bytes arrive, the receiver keeps every out-of-order chunk in a buffer and keeps re-sending ACK 1001, because 1001 is still the first byte it is missing.
4. The sender spots the loss one of two ways: the retransmission timer (RTO) runs out with no new ACK, or three duplicate ACKs arrive (fast retransmit). Three duplicates are quicker than waiting for the timer.
5. The sender resends only the missing range, 1001-2000. The receiver now has a complete run and jumps its ACK forward to 5001, since the buffered bytes were waiting for exactly this gap.

So the key is that one cumulative ACK number describes all progress, and only the unacknowledged gap is resent.

## Example

The byte numbering shows up in a packet capture. These are two segments from one connection.

```text
seq=1       len=1000   -> carries bytes 1..1000
(ack 1001 comes back: "give me byte 1001 next")
seq=2001    len=1000   -> carries bytes 2001..3000, arrives before 1001..2000
(ack is still 1001: the 1001..2000 gap is not filled yet)
```

What to notice:

- `seq` is the number of the segment's first byte, so segment lengths tell you the byte ranges; TCP is counting bytes, not packets.
- The second segment arrives before the missing one, yet the ACK stays at 1001: the receiver reports the first gap, not the highest byte it holds.
- If the gap is never filled, the sender's RTO fires and it resends 1001-2000; nothing after it is resent, because the receiver already buffered that.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Initial RTO | 1 s; then smoothed RTT plus four times its variation | RFC 6298 |
| Fast retransmit trigger | 3 duplicate ACKs | RFC 5681 |

- **SACK (selective acknowledgement):** an option where the receiver also reports which out-of-order blocks it holds, so the sender resends only the true gaps rather than everything after the first missing byte (RFC 2018).
- **Head-of-line blocking:** because the stream is in order, one lost segment holds back all the bytes behind it from the application until it is resent; this is what [HTTP/2 over TCP suffers and HTTP/3 avoids](card:http-versions).

## Not to be confused with

Reliability and [flow or congestion control](card:flow-and-congestion-control) are different jobs. Reliability decides what to resend and when, so nothing is lost. Flow and congestion control decide how much to send at a time, so the receiver and the network are not overrun. Rule: retransmission = correctness; windows = pacing.

## Common mistakes

- **"A duplicate ACK means data was duplicated."** It means data arrived after a gap: the receiver re-sends the same "next byte I need" number. Three of them is the signal to fast-retransmit the missing range.
- **"TCP resends from the lost point onward (go-back-N)."** With SACK, the receiver tells the sender exactly which blocks it already has, so only the gaps are resent, not everything after the loss.

## Interview Qs

### How does TCP detect that a segment was lost?

Two ways. The retransmission timer (RTO) runs out with no acknowledgement for the data, or three duplicate ACKs arrive, which means later bytes got through but one range is missing. The duplicate-ACK path (fast retransmit) is quicker, because it does not wait for the timer to expire.

### What do the sequence and acknowledgement numbers mean?

The sequence number is the number of the first data byte in a segment, because TCP numbers every byte. The acknowledgement number is the next byte the receiver expects, so it confirms every byte before it at once. That is why it is called a cumulative acknowledgement.

### What is head-of-line blocking in TCP?

TCP delivers bytes strictly in order, so if one segment is lost, every byte that arrived after it must wait in a buffer until the gap is resent, even though it is already there. This delay is why HTTP/2, which multiplexes streams over one TCP connection, can stall, and why HTTP/3 moved to QUIC over UDP.
