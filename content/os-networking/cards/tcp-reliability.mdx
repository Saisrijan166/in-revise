## Why it exists

Packets can be lost, corrupted or arrive out of order. TCP detects this and hands the app an exact, in-order byte stream.

## How it works

<Mermaid
  alt="Sender sends bytes 1-1000 and gets ACK 1001. Bytes 1001-2000 are lost. Bytes 2001-3000, 3001-4000 and 4001-5000 each arrive and each gets a duplicate ACK 1001. After the third duplicate the sender resends 1001-2000, and the receiver answers ACK 5001."
  chart={`sequenceDiagram
  participant S as Sender
  participant R as Receiver
  S->>R: bytes 1-1000
  R->>S: ACK 1001
  S-xR: bytes 1001-2000 (lost)
  S->>R: bytes 2001-3000, 3001-4000, 4001-5000
  R->>S: ACK 1001, ACK 1001, ACK 1001 (3 duplicates)
  S->>R: resend 1001-2000 (fast retransmit)
  R->>S: ACK 5001 (later bytes were buffered)`}
/>

- **Sliding window:** many bytes can be in flight before an ACK; [flow and congestion control](card:flow-and-congestion-control) set how many.
- **SACK** reports which blocks arrived, so only the gaps are resent.
- One lost segment holds back later bytes from the app: TCP head-of-line blocking, see [HTTP versions](card:http-versions).

## Defaults

| What | Default | Where |
|---|---|---|
| Initial RTO | 1 s; after that, smoothed RTT + 4 × its variation | RFC 6298 |
| Fast retransmit trigger | 3 duplicate ACKs | RFC 5681 |

## Interview Qs

### How does TCP detect a lost segment?

Two ways: the retransmission timer runs out with no ACK, or three duplicate ACKs arrive, meaning later data got through but one piece is missing. The second is faster.

### What do the sequence and acknowledgement numbers mean?

The sequence number is the number of the segment's first byte. The acknowledgement number is the next byte the receiver expects, so it confirms every byte before it.
