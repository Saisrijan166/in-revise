## Why it exists

One CPU runs one thread at a time. To share it among many threads, the kernel must pause one and resume another unnoticed.

## How it works

<Steps label="One context switch">
  <Step title="Trigger">A timer interrupt, a blocking call or a wake-up enters the kernel.</Step>
  <Step title="Save">The kernel stores thread A's registers, program counter and stack pointer.</Step>
  <Step title="Pick">The [scheduler](card:cpu-scheduling) chooses the next ready thread, B.</Step>
  <Step title="Restore">It loads B's saved state; for another process it also switches the page table.</Step>
  <Step title="Resume">Return-from-trap continues B where it stopped.</Step>
</Steps>

- A system call alone is a [mode switch](card:what-is-an-os), not a context switch.
- Thousands of runnable threads mean constant switching; [thread pools](card:thread-pools) bound them.
- Why caches and the TLB matter: [memory hierarchy](card:memory-hierarchy), [paging](card:paging-and-page-faults).

## Example

A sleeper gives up the core; a busy loop gets preempted. A local run:

```bash
sleep 5 & sleep 1; grep ctxt /proc/$!/status
sh -c "while :; do :; done" & sleep 1; grep ctxt /proc/$!/status; kill $!
```

```text output
nonvoluntary_ctxt_switches:	0
voluntary_ctxt_switches:	0

```

## Interview Qs

### What happens during a context switch?

The kernel saves the current thread's registers, program counter and stack pointer, picks the next thread, restores its state and, for another process, switches the page table. The new thread then resumes.

### Why is a thread switch cheaper than a process switch?

Threads of one process share an address space, so the page table and TLB entries stay valid. A process switch changes the page table, which can flush the TLB.

### Why do too many threads slow a server?

A CPU runs one thread at a time. Extra runnable threads add switches, scheduler work and cold caches, and each platform thread holds its own stack. Bounding threads keeps the CPU on real work.
