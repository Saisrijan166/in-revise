## What it is

A **context switch** is the moment the kernel stops running one [thread](card:threads) on a CPU core and starts running another. A core can run only one thread at a time, so to share it the kernel saves the current thread's state (its registers, program counter and stack pointer) and loads the next thread's saved state. The "context" is that saved state. The switch itself is pure overhead: during it the core does the OS's bookkeeping, not the program's work.

## Why it exists

A single core runs one thread at a time, but a machine usually has far more runnable threads than cores. To share the core and keep the system responsive, the kernel must be able to pause one thread and resume another so smoothly that neither notices. Without context switching, a thread would hold its core until it finished, and one long task could freeze everything else. The switch is the mechanism that makes many threads look like they run together.

## How it works

One context switch is a short, fixed sequence inside the kernel.

<Steps label="One context switch">
  <Step title="Trigger">A timer interrupt, a blocking system call or a wake-up enters the kernel and interrupts thread A.</Step>
  <Step title="Save">The kernel stores thread A's registers, program counter and stack pointer into A's record.</Step>
  <Step title="Pick">The scheduler (you will see this in [CPU scheduling](card:cpu-scheduling)) chooses the next ready thread, B.</Step>
  <Step title="Restore">The kernel loads B's saved state; if B is in another process, it also switches the page table.</Step>
  <Step title="Resume">A return-from-trap continues thread B exactly where it last stopped.</Step>
</Steps>

So the key is that every switch spends real time saving and restoring state, and leaves the new thread with caches that belong to the old one.

## Example

A sleeping task gives up the CPU voluntarily; a busy loop is forced off it. These lines read each process's switch counters from `/proc` (counts vary).

```bash
sleep 5 & sleep 1; grep ctxt /proc/$!/status
sh -c "while :; do :; done" & sleep 1; grep ctxt /proc/$!/status; kill $!
```

```text output
voluntary_ctxt_switches:	1
nonvoluntary_ctxt_switches:	0
voluntary_ctxt_switches:	0
nonvoluntary_ctxt_switches:	10
```

What to notice:

- `sleep` has a voluntary switch and no involuntary ones: it blocked itself by sleeping, so it gave up the CPU on its own.
- The busy loop (`while :`) never blocks, so all its switches are involuntary: the kernel kept taking the core away when each time slice ended.
- The counts show the two causes of switching directly: a thread either yields the CPU or has it taken.

## Rules and defaults

- **A system call is not a context switch:** it is a [mode switch](card:what-is-an-os) on the same thread. A switch only happens when the kernel changes which thread runs.
- **Thread switch versus process switch:** switching between threads of one process keeps the page table and TLB valid; switching to another process changes the page table and can flush the TLB, so it is costlier.
- **Only runnable threads cause switching:** a thread blocked on I/O costs memory (its stack) but does not add to the switching load, because it is not asking for the CPU.
- **Bound the count:** thousands of runnable threads mean constant switching, so servers use [thread pools](card:thread-pools) to cap how many run at once.

## Interview Qs

### What exactly happens during a context switch?

The kernel saves the current thread's registers, program counter and stack pointer into that thread's record, asks the scheduler for the next ready thread, and loads its saved state. If the next thread is in a different process, it also switches the page table. A return-from-trap then resumes the chosen thread where it had stopped.

### Why is switching between threads of one process cheaper than switching between processes?

Threads of one process share one address space, so the page table stays the same and the TLB entries remain valid. A process switch changes the page table, which usually flushes the TLB, so the new process starts with slow address translations until the TLB refills.

### Why can too many threads make a server slower, not faster?

A core runs one thread at a time, so extra runnable threads do not add parallelism; they add switching. Each switch costs save and restore time, scheduler work and a cold cache and TLB for the next thread, and each platform thread also holds its own stack. Bounding the number of threads keeps the CPU spending its time on real work.
