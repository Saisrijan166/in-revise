## Why it exists

A [race](card:race-conditions) comes from steps interleaving on shared data. A lock makes those steps run as one unit by letting a single thread in at a time.

## How it works

<Steps label="The lock protocol">
<Step title="Acquire">Thread A takes the free lock. Thread B finds it held and waits, asleep or spinning.</Step>
<Step title="Critical section">A alone reads and writes the shared data.</Step>
<Step title="Release">A unlocks in `finally`; a waiting thread gets the lock next.</Step>
</Steps>

- Java `synchronized` uses the object's [monitor](card:monitor-lock): a lock plus `wait` and `notify`.
- [Priority inversion](card:priority-inversion): a low-priority holder blocks a high-priority waiter; priority inheritance fixes it.

## Example

```java
static final ReentrantLock lock = new ReentrantLock();
static int count = 0;

static void increment() {
    lock.lock();                 // wait here if another thread holds it
    try { count++; }             // critical section
    finally { lock.unlock(); }   // always release, even on an exception
}
// two threads call increment() 100,000 times each, then:
System.out.println(count);
```

```text output
200000
```

## Interview Qs

### When is a spinlock better than a blocking mutex?

When the wait is very short and the holder runs on another core. On one core a spinning thread burns its whole time slice while the holder cannot run, so most code should block instead.

### synchronized or ReentrantLock?

Both are reentrant mutexes with the same basic rules. ReentrantLock adds `tryLock` with a timeout, interruptible waits, fairness and several conditions, but you must unlock it yourself in `finally`.
