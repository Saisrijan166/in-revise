## What it is

A lock is a tool that lets only one thread at a time run a chosen block of code, called the [critical section](card:critical-section). A thread acquires the lock before the block and releases it after; any other thread that reaches an acquired lock waits until it is free. This gives mutual exclusion: the protected steps on shared data run start to finish without another thread slipping in, which is the direct fix for the [race conditions](card:race-conditions) you just saw.

## Why it exists

A race happens because the steps of two threads interleave on shared data. Without a lock, there is no way to say "these three lines must run together, untouched." A lock draws that boundary: while one thread holds it, no other thread can enter the same critical section, so the three lines behave as one indivisible step. The cost is waiting, so you keep the critical section as short as possible to let the other threads back in quickly.

## How it works

<Steps label="The lock protocol">
<Step title="Acquire">Thread A takes the free lock. Thread B reaches it, finds it held, and waits, either asleep or spinning.</Step>
<Step title="Critical section">A alone reads and writes the shared data; B still cannot enter.</Step>
<Step title="Release">A releases the lock in a finally block; the OS then lets one waiting thread, say B, acquire it.</Step>
</Steps>

1. A thread calls `lock()`; if the lock is free it becomes the owner, otherwise it waits.
2. The owner runs the critical section with no other thread inside.
3. The owner calls `unlock()` in `finally`, so the lock is freed even if the body throws.
4. One waiting thread is woken and acquires the lock next.

So the key is: acquire, do the shared work alone, and always release, even on an exception.

## Example

A `ReentrantLock` protects a shared counter so two threads never lose an update.

```java
static final ReentrantLock lock = new ReentrantLock();
static int count = 0;

static void increment() {
    lock.lock();                 // wait here if another thread holds it
    try { count++; }             // critical section: only one thread at a time
    finally { lock.unlock(); }   // always release, even on an exception
}
// two threads call increment() 100,000 times each, then:
System.out.println(count);
```

```text output
200000
```

What to notice:

- `lock.lock()` blocks the second thread until the first releases, so the two `count++` steps never interleave and the total is exactly 200000.
- `unlock()` sits in `finally`, so an exception inside the critical section still frees the lock; without it, every waiting thread would block forever.
- The lock is `static final`, so both threads share the one lock object; two different lock objects would guard nothing in common.

## Rules and defaults

- **Ownership (mutex):** only the thread that acquired a `ReentrantLock` may unlock it; another thread calling `unlock()` throws.
- **Fairness:** `new ReentrantLock()` is non-fair by default (Java 25), so waiting order is not promised; `new ReentrantLock(true)` serves the longest waiter first but is slower.
- **Reentrancy:** `synchronized` and `ReentrantLock` let the owner acquire the same lock again, which is needed when one locked method calls another.
- **Spinlock vs blocking:** a spinlock loops while waiting, so use it only for very short waits on another core; otherwise a blocking lock lets the CPU do other work.
- **Scope:** a Java lock guards one JVM. Across servers, lock the database row with `SELECT ... FOR UPDATE` or use a distributed lock.

## Not to be confused with

A lock (mutex) protects a critical section and has an owner, so threads take turns. A [semaphore](card:semaphores) holds a count of permits and lets up to N threads in at once, with no owner. Rule: a mutex is for "one at a time on this data"; a semaphore is for "at most N users of this resource."

## Interview Qs

### When is a spinlock better than a blocking mutex?

When the wait is expected to be very short and the holder runs on another core, so the waiting thread spins for a few cycles instead of paying the cost of sleeping and waking. On a single core a spinning thread burns its whole time slice while the holder cannot run, so there most code should block instead.

### synchronized or ReentrantLock?

Both are reentrant mutexes with the same basic behaviour. `ReentrantLock` adds `tryLock` with a timeout, interruptible waiting, optional fairness and multiple condition queues, which `synchronized` lacks. The cost is that you must release it yourself in `finally`, whereas `synchronized` releases automatically when the block ends.
