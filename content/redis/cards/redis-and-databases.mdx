## What it is

Redis and a relational database such as PostgreSQL are two different kinds of store, and most backends use both. A relational database keeps rows in tables on disk, checks rules such as "each payment id is unique", and answers SQL queries that join tables. [Redis](card:what-is-redis) keeps values in RAM and finds them only by key. The question is not which one is better, but which data belongs where.

## Why it exists

Redis is so fast that teams ask whether it can replace the database. For payments the answer matters: if a crash loses the last writes, a customer's ₹500 payment could vanish. With its default settings, PostgreSQL confirms a commit only after the change is safely logged to disk, and it rejects data that breaks its rules. Knowing what each store guarantees tells you where each piece of data should live.

## How it works

<Compare id="redis-vs-database" />

1. The payment service writes each payment to PostgreSQL. The commit returns only after the change is logged, so it survives a crash.
2. For data it reads often, such as payment 9001 or the merchant settings, the service keeps a copy in Redis under a key such as `payment:9001`, with a lifetime.
3. Reads check Redis first. On a miss they read PostgreSQL and store a fresh copy; you will see this pattern in [cache-aside](card:cache-aside).
4. Data that is short-lived or shared between servers, such as a request counter or a lock, lives only in Redis, because losing it in a crash does little harm.

So the key is: decide per piece of data, by asking what happens if it is lost.

## Example

Besides the payment row in PostgreSQL, the payment service uses Redis for three helpers.

```bash
redis-cli SET payment:9001 '{"status":"PENDING","amount":500}' EX 300
redis-cli INCR rate:user:7:upi
redis-cli SET lock:payment:9001 worker-1 NX PX 30000
redis-cli SET lock:payment:9001 worker-2 NX PX 30000
```

```text output
OK
(integer) 1
OK
(nil)
```

What to notice:

- `payment:9001` is only a copy of the PostgreSQL row. It expires after 300 seconds and can be rebuilt from the database at any time.
- `rate:user:7:upi` counts the user's UPI requests. If Redis loses it, the user only gets a fresh limit.
- `NX` means "only if the key does not exist", so worker 2 gets `(nil)` and knows worker 1 holds the lock. A lock alone does not prevent a double charge; [distributed locks](card:distributed-locks) explains why.

## Rules and defaults

- **Source of truth:** for each kind of data, choose one store whose copy wins. For payments, orders and accounts, that is the database.
- **Durability is a setting:** how much Redis keeps after a crash depends on its [RDB and AOF](card:persistence-rdb-aof) settings. A successful write is not always on disk yet.
- **Size:** Redis Open Source keeps all data in RAM, so the data set must fit in memory.
- **No rules between keys:** Redis has no foreign keys, no constraints across keys and no joins. The app keeps related keys consistent.

## Common mistakes

- **"Put everything in Redis to make the app fast."** Data you query in many ways, such as payments by date, merchant and status, fits SQL far better. Redis finds values by key unless you add search indexes.

## Interview Qs

### Can Redis be your primary database?

Yes, for data whose possible crash loss is acceptable, such as sessions or leaderboards, with persistence configured to match. For orders and payments, keep a relational database as the source of truth and add Redis beside it for speed.

### When is Redis the wrong choice?

When the data is larger than the RAM you can afford, or when you need ad hoc queries, joins, constraints and durable transactions across related records, such as a payment ledger.

### Redis and the database disagree. Which one is right?

The database, because it is the source of truth. The Redis copy is stale: delete it or refresh it from the database. [Cache invalidation](card:cache-invalidation) shows how to keep the two in step.
