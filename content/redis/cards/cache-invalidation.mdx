## What it is

Cache invalidation means removing a cached copy when the data in the database changes, so readers stop getting the old version. A copy that no longer matches its database row is called stale. With [cache-aside](card:cache-aside), invalidation is a `DEL` on the key right after the database change; the next read misses and loads the fresh row.

## Why it exists

`merchant:42:config` holds a 2% fee, and an admin changes it to 3% in PostgreSQL. Without invalidation, every payment keeps using 2% until the TTL ends, which could be 30 minutes of wrong fees. A very short TTL alone would shrink that window but cause many more misses. Deleting the key right after the change ends the stale window at once, and the TTL stays as a safety net.

## How it works

1. The service updates merchant 42 in PostgreSQL inside a transaction. Until it commits, other readers still see the old row.
2. The transaction commits, and the new fee becomes visible to everyone.
3. The service deletes `merchant:42:config`.
4. The next read misses, loads the committed row and stores it with a TTL.
5. If the delete fails, for example on a network error, the TTL removes the stale copy later, so the damage has a time limit.

So the key is: delete after the commit, and always keep a TTL behind it.

## Example

`changeFee` runs in one database transaction (`@Transactional` commits when the method returns) and registers the delete to run only after a successful commit.

```java
@Transactional
public void changeFee(long merchantId, BigDecimal fee) {
    merchants.updateFee(merchantId, fee);                    // UPDATE, not committed yet
    String key = "merchant:" + merchantId + ":config";
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            redis.delete(key);                               // runs only after a successful commit
        }
    });
}
```

What to notice:

- `afterCommit` runs once the commit has succeeded. On a rollback it never runs, and the cached copy stays, which is correct because the row did not change.
- Calling `redis.delete(key)` directly in the method body would run before the commit. A reader in that gap would reload the old row and cache it for the full TTL.
- With Spring's `@CacheEvict`, which you will see in [Spring Cache](card:spring-cache-abstraction), a transaction-aware cache manager gives the same after-commit timing without this code.

## Rules and defaults

- **Delete rather than update:** a `DEL` can be retried safely, and the next reader loads the truth. Facebook's memcache chose deletes for this reason.
- **After the commit:** delete only once the database change is visible to other readers.
- **TTL backstop:** keep a TTL on every cached copy, so a missed or failed delete is wrong only for a bounded time.
- **Spring Cache timing:** a `RedisCacheManager` is not transaction-aware by default (Spring Data Redis 4.1). `RedisCacheManager.builder(factory).transactionAware()` holds cache puts and evicts until after the commit.
- **Many writers:** if batch jobs or other services change the same table, capture changes from the database log (change data capture) and delete keys from one place. Redis Data Integration (Redis Software and Redis Cloud) can feed changes into Redis this way.
- **Many app instances:** to clear copies that each instance keeps in its own memory, broadcast the change with [Pub/Sub](card:pub-sub), within its delivery limits.

## Not to be confused with

TTL expiry removes a key when its timer runs out, whether the data changed or not. Eviction removes keys when Redis reaches its memory limit. Invalidation removes a key because its data changed. Rule: TTL = time, eviction = memory, invalidation = a data change.

## Common mistakes

- **"Update the database, then delete the key, and the cache can never be stale."** A rare race remains. A reader that loaded the old row just before your update can store it after your delete. Facebook calls this a stale set and fixes it with leases; for most apps the TTL bounds it.

## Interview Qs

### Why delete the cached key instead of writing the new value?

A delete can be retried safely, and the next read loads the truth from the database. With updates, two writers can reach Redis in a different order from the database and leave the older value cached until its TTL runs out.

### Many services write the same table. How do you keep Redis fresh?

Do not rely on every service remembering to delete. Capture committed changes from the database log (change data capture) and delete the matching keys from one place, with TTLs as the backstop.

### What if the delete fails after the commit?

The database is already correct, so do not roll anything back. Retry the delete, because deletes are safe to repeat, and log the failure. If every retry fails, the TTL removes the stale copy later, which is why every cached copy needs one.
