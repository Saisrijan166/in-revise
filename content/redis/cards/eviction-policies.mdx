## What it is

Eviction is Redis deleting keys on its own to stay under a memory limit. You set the limit with `maxmemory`, for example 2 GB. The eviction policy, set with `maxmemory-policy`, decides which keys go when the limit is reached, or tells Redis to refuse new writes instead. LRU means least recently used: the key that nobody has read or written for the longest time.

## Why it exists

[Redis](card:what-is-redis) keeps all its data in RAM, and RAM runs out. Without a limit, a growing cache takes all the machine's memory: the operating system starts moving Redis memory to disk, which makes it slow, or kills the process. With `maxmemory` and a policy, a cache drops its least useful keys and keeps working. A store whose keys must not vanish can instead reject writes with a clear error.

## How it works

  W([Write needs memory]) --> M{Over maxmemory?}

1. A client sends a command that adds data, such as `SET`.
2. Before running it, Redis compares the memory in use with `maxmemory`.
3. Under the limit, the command runs normally.
4. Over the limit with `noeviction`, the default, Redis answers with an OOM (out of memory) error. Commands that only read still work.
5. With any other policy, Redis samples a few keys, evicts the best candidate for that policy, and repeats until it is under the limit. Then it runs the command.

So the key is: eviction happens only when a write needs memory, and the policy alone decides which key goes.

## Example

A test instance runs with `maxmemory 2mb` and the default `noeviction`. It is already full of 1 KB `merchant:*:config` keys.

```bash
redis-cli SET payment:9001 '{"status":"PENDING"}' EX 300
redis-cli EXISTS merchant:1:config
redis-cli CONFIG SET maxmemory-policy allkeys-lru
redis-cli SET payment:9001 '{"status":"PENDING"}' EX 300
redis-cli INFO stats | grep evicted_keys
```

```text output
(error) OOM command not allowed when used memory > 'maxmemory'.
(integer) 1
OK
OK
evicted_keys:37
```

What to notice:

- Under `noeviction` the write is refused, but `EXISTS`, a read, still works.
- After the switch to `allkeys-lru`, the same `SET` succeeds, because Redis evicted old merchant keys to make room.
- `evicted_keys` counts every eviction. If it keeps rising in production, the cache is too small or the policy evicts useful keys.

## Rules and defaults

| Policy | Evicts |
|---|---|
| `noeviction` (default) | Nothing; writes that need memory fail |
| `allkeys-lru` | The least recently used key, among all keys |
| `allkeys-lfu` | The least frequently used key (Redis 4.0+) |
| `allkeys-lrm` | The least recently modified key; reads do not count (Redis 8.6+) |
| `allkeys-random` | A random key |
| `volatile-lru`, `-lfu`, `-lrm`, `-random` | The same rules, only among keys with a TTL |
| `volatile-ttl` | The key with the shortest TTL left |

- **maxmemory:** 0 by default, which means no limit on 64-bit systems (Redis Open Source 8.10).
- **maxmemory-samples:** 5 keys per eviction by default; 10 comes very close to true LRU at some extra CPU.
- **Buffers:** memory for the buffers that feed replicas and the AOF log is not counted against `maxmemory`, so leave some RAM free for them.
- **Big writes:** one command that adds a lot of data can push memory well over the limit for a moment.

## Not to be confused with

LRU evicts the key that has gone unused for the longest time. LFU evicts the key used least often, using a counter that slowly decays so old popularity fades. Rule: LRU when recent means hot; LFU when popular means hot. And a [TTL](card:ttl-and-expiration) removes a key because its own time ran out, while eviction removes keys because the instance is out of memory.

## Common mistakes

- **Cache keys and must-keep keys in one instance with volatile-lru.** A cache key stored without a TTL is never evicted, and memory fills up. The Redis docs suggest two separate instances instead.
- **Leaving maxmemory at 0 on a cache.** Nothing is ever evicted, and Redis grows until the machine runs out of memory.

## Interview Qs

### What happens when Redis runs out of memory?

It depends on maxmemory-policy. With noeviction, the default, writes that need memory get an OOM error while reads still work. With any other policy, Redis evicts keys until it is back under maxmemory, then runs the write.

### Which policy would you choose for a cache?

allkeys-lru when a small set of keys gets most of the reads, the common case. allkeys-lfu when popularity matters more than recency. allkeys-random when all keys are read about equally. volatile-ttl when you mark eviction candidates with short TTLs.

### Is Redis LRU exact?

No. Exact LRU would need extra memory per key. Redis samples a few random keys, plus a pool of good candidates since Redis 3.0, and evicts the oldest. Raising maxmemory-samples to 10 gets very close to true LRU at more CPU cost.
