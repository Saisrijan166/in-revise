## What it is

Persistence means writing Redis's data to disk so that it is still there after a restart or a crash. Redis keeps all data in RAM, as you saw in [What Redis is](card:what-is-redis), and RAM is empty after the process stops. Redis has two ways to persist: an RDB snapshot, which is one file holding all data at one moment, and the AOF (append-only file), which is a log of every write command. You can use one, both or neither.

## Why it exists

Without persistence, a restart of the payment service's Redis wipes every key. For a cached copy such as `payment:9001` that only costs a cache miss, because the database still has the record. But shared login sessions live only in Redis, and losing them logs every user out. Persistence lets Redis reload its data from disk at startup, and you choose how many recent writes you can afford to lose.

## How it works

<Mermaid
  alt="A write changes the data in RAM and Redis replies OK. With AOF on, the command is also appended to the AOF and fsynced to disk once a second. At a save point, Redis forks a child process that writes all data to dump.rdb."
  chart={`flowchart LR
  C["SET payment:9001 PAID"] --> M[("Data in RAM")]
  M -- "AOF on: append command" --> A["AOF buffer"]
  A -- "fsync once a second" --> F[("appendonlydir")]
  M -- "save point reached: fork" --> K["Child process"]
  K -- "writes snapshot" --> R[("dump.rdb")]`}
/>

1. A write such as `SET payment:9001 PAID` changes the data in RAM, and Redis replies OK.
2. If AOF is on, Redis also appends the command to the AOF. With the default `appendfsync everysec`, a background thread calls fsync once a second, which forces the operating system to put the log on the disk.
3. When a save point is reached, for example 100 changes within 300 seconds, Redis forks: it creates a child process that is a copy of itself. The child writes all data to a temporary file and renames it to `dump.rdb` when done, while the parent keeps serving clients.
4. After the fork, parent and child share memory, and a page is copied only when the parent changes it (copy-on-write), so the snapshot costs extra RAM only for pages written meanwhile.
5. The AOF keeps growing, so Redis rewrites it in the background: a child writes the shortest set of commands for today's data, and new writes go to a fresh file.
6. At startup Redis loads the AOF if AOF is on; otherwise it loads `dump.rdb`.

## Example

This test runs a Redis 8 container with AOF on, writes the cached payment, then crashes Redis on purpose to show what AOF keeps.

```bash
docker run -d --name pay-redis -v pay-data:/data redis:8 redis-server --appendonly yes > /dev/null
docker exec pay-redis redis-cli SET payment:9001 PAID
sleep 2                                 # longer than the 1-second fsync interval
docker kill -s KILL pay-redis           # a crash: no clean shutdown, no final save
docker start pay-redis && sleep 1
docker exec pay-redis redis-cli GET payment:9001
```

```text output
OK
pay-redis
pay-redis
PAID
```

What to notice:

- `GET` still returns `PAID` after the kill: Redis replayed the AOF in the `pay-data` volume.
- The `sleep 2` matters. With `everysec`, a write is on disk only after the next fsync, so a crash within about a second of the write can lose it.
- Start the same container with `--save "" --appendonly no` instead, and the last `GET` prints an empty line: the key is gone, because nothing was on disk.

## Rules and defaults

- **Defaults (Redis Open Source 8.10):** RDB save points `3600 1 300 100 60 10000`, meaning a snapshot after 1 change in an hour, 100 in 5 minutes or 10000 in a minute. AOF is off (`appendonly no`); when it is on, `appendfsync` is `everysec`.
- **appendfsync choices:** `always` fsyncs before replying to each batch of writes, which is the safest and very slow. `everysec` can lose about one second. `no` leaves flushing to the operating system, which on Linux usually means every 30 seconds.
- **AOF files (Redis 7.0 and later):** the AOF is a folder, `appendonlydir`, holding a base file, incremental files and a manifest that lists them. The base file uses the RDB format by default (`aof-use-rdb-preamble yes`), so it loads fast.
- **Automatic AOF rewrite:** starts when the AOF has grown by 100% since the last rewrite and is at least 64 MB (`auto-aof-rewrite-percentage 100`, `auto-aof-rewrite-min-size 64mb`).
- **Turning on AOF for existing data:** use `CONFIG SET appendonly yes` on the running server, then put the setting in redis.conf. Turning it on only in the file and restarting starts from an empty AOF.
- **Backups:** an RDB file never changes once written, so copy it while Redis runs: the docs suggest hourly and daily copies, one a day off the machine.

## Not to be confused with

RDB is a periodic photo of all data; AOF is a running diary of every write. Persistence keeps data across a restart of one server, while [replication](card:replication), the next concept, keeps a live copy on another server in case the machine is lost. Rule: persistence survives a restart, a replica survives a lost server, and only a backup lets you go back in time.

## Common mistakes

- **"AOF alone is the safest setup."** The Redis docs discourage AOF alone. Keep RDB snapshots as well, for backups, faster restarts and protection against bugs in the AOF engine.

## Interview Qs

### RDB or AOF for a payment service's Redis?

It depends on what Redis holds. Cached copies of payments can be rebuilt from the database, so they need no persistence. Sessions or counters that exist only in Redis need AOF with everysec, for a loss window of about a second, plus RDB for backups and fast restarts. The payment records themselves belong in the database.

### Why does a large Redis pause during BGSAVE?

Creating the child is not free: fork() runs in the main thread and must copy the process's page tables, which grow with the dataset. On a big dataset or a slow virtual machine this can block all clients for milliseconds, sometimes up to about a second.
