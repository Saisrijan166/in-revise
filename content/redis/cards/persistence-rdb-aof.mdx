## Why it exists

Redis keeps data in RAM, so a crash or restart loses it. Persistence writes it to disk to load back.

## How it works

<Compare id="rdb-vs-aof" />

- Since Redis 7.0 the AOF is a folder: a base file, incremental files and a manifest.
- A background AOF rewrite replaces the log with the shortest set of commands for today's data.
- By default the AOF base file uses RDB format, so it loads fast.

## Example

```text
-- redis.conf: keep merchant:42:config and sessions across restarts
appendonly yes
appendfsync everysec
save 3600 1 300 100 60 10000

-- check at runtime
INFO persistence      -> aof_enabled:1 ... rdb_last_bgsave_status:ok
BGSAVE                -> Background saving started
```

## Defaults

| What | Default | Where |
|---|---|---|
| RDB save points | 3600 s and 1 change, 300 s and 100, 60 s and 10000 | Redis Open Source 8.10 redis.conf |
| appendonly | no (AOF off) | Redis Open Source 8.10 redis.conf |
| appendfsync | everysec | Redis Open Source 8.10 redis.conf |

## Interview Qs

### RDB or AOF for a payment service's Redis?

Both, if Redis holds data you cannot rebuild: AOF everysec for a small loss window, RDB for backups and fast restarts. The payment records themselves stay in [the database](compare:redis-vs-database).

### Why does a large Redis pause during BGSAVE?

fork() runs on the main thread and must copy the process's page tables. With a big dataset or a slow virtual machine this can block clients for milliseconds, sometimes about a second.

### Why not always use appendfsync always?

It fsyncs the log before replying to each batch of writes. That is the safest mode but very slow; parallel writes share one fsync. Most setups keep everysec.
