## What it is

Redis Sentinel is a set of separate processes that watch a Redis primary and its [replicas](card:replication). It runs from the same `redis-server` program in Sentinel mode, usually on port 26379. When the primary stops answering, the Sentinels agree that it is down, promote one replica to primary and repoint the other replicas to it. Applications do not hard-code the primary's address; they ask a Sentinel for it.

## Why it exists

Replication gives you a copy, but when the primary dies at 3 a.m. someone must pick a replica, run `REPLICAOF NO ONE` on it, repoint the other replicas and change every application's configuration. Until then, every write from the payment service fails. Sentinel does these steps automatically, without a person. Because clients ask Sentinel for the address, they find the new primary without a redeploy.

## How it works

1. Each Sentinel checks the primary all the time. If it gets no valid reply for `down-after-milliseconds`, it marks the primary subjectively down (SDOWN): down in its own view only.
2. When at least the quorum of Sentinels report it down, the primary is objectively down (ODOWN).
3. To act, one Sentinel must be elected leader for this failover by a majority of all Sentinels. Without a majority, no failover happens.
4. The leader picks a replica: lowest `replica-priority` first (a number set on each replica, 100 by default), then the one with the most data from the primary, and skips replicas cut off too long. It promotes that replica and repoints the others to it.
5. All Sentinels now report the new address. When the old primary comes back, Sentinel turns it into a replica of the new primary.

## Example

Three Sentinels watch the payment service's primary under the name `payments`. Each one uses this configuration:

```text
port 26379
sentinel monitor payments 172.20.0.2 6379 2
sentinel down-after-milliseconds payments 5000
```

Then the test asks a Sentinel for the primary, freezes the primary and asks again:

```bash
redis-cli -p 26379 SENTINEL GET-MASTER-ADDR-BY-NAME payments
docker pause redis-primary > /dev/null   # the primary stops answering
sleep 20                                 # 5 s to SDOWN, then vote and promote
redis-cli -p 26379 SENTINEL GET-MASTER-ADDR-BY-NAME payments
```

```text output
1) "172.20.0.2"
2) "6379"
1) "172.20.0.4"
2) "6379"
```

What to notice:

- The last number in `sentinel monitor` is the quorum, 2: two Sentinels must agree before the primary counts as down.
- `down-after-milliseconds 5000` makes the test fast. The default is 30 seconds, and a lower value can cause failovers on short network hiccups.
- The second answer is a replica's address: it was promoted. An app that asks Sentinel reconnects to it without any configuration change.

## Rules and defaults

- **Defaults (Redis Open Source 8.10 sentinel.conf):** port 26379, `down-after-milliseconds 30000`, `failover-timeout 180000` (3 minutes), `parallel-syncs 1` (replicas repointed one at a time).
- **Placement:** run at least three Sentinels, on machines or zones that fail independently.
- **Never promote a replica:** set its `replica-priority` to 0. It still follows the new primary.
- **Spring Boot 4.1:** set `spring.data.redis.sentinel.master` to the name, `payments`, and `spring.data.redis.sentinel.nodes` to the Sentinels' `host:port` list. The client asks them for the primary.
- **No write guarantee:** the Redis docs say Sentinel does not keep every acknowledged write during a failure, because replication is asynchronous. A [lock](card:distributed-locks) taken on the old primary can also vanish this way.

## Not to be confused with

Sentinel adds automatic failover to one primary that holds all the data. [Redis Cluster](card:redis-cluster), the next concept, splits the data across several primaries and runs failover itself, with no Sentinel processes. Rule: Sentinel = failover only; Cluster = sharding plus failover.

## Common mistakes

- **"Two Sentinels are enough: one next to the primary, one next to the replica."** If the primary's machine dies, it takes one Sentinel with it. The survivor is one of two, not a majority, so it cannot start a failover.

## Interview Qs

### Why do you need at least three Sentinels?

A failover needs a leader voted by a majority of all Sentinels. With three on independent machines, losing one machine leaves two out of three, which is still a majority. With two, losing one leaves one out of two, so no failover can start.

### Can a Sentinel failover lose data?

Yes. Writes the old primary acknowledged but had not yet sent to the promoted replica are lost. A network split is worse: clients still connected to the old primary keep writing, and those writes vanish when it rejoins. `min-replicas-to-write` limits how long that can go on.

### How does the application find the new primary?

It uses a Sentinel-aware client. The client is given the Sentinels' addresses and the primary's name, asks a Sentinel for the current address, and asks again when the connection fails. In Spring Boot that is the `spring.data.redis.sentinel.*` properties.
