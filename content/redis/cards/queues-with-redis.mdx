## What it is

A job queue is a waiting line of work. One part of the system, the producer, adds jobs; separate worker processes take them off and do them. Redis has no queue type, but a [list](card:lists) works as one, a [sorted set](card:sorted-sets) can hold jobs until a set time, and a [stream](card:streams) adds acknowledgements. This concept shows when to use each.

## Why it exists

When payment 9001 succeeds, the service must email a receipt, which can take seconds. If the API sends the email before replying, the user waits, and a slow mail server makes the payment API slow too. With a queue, the API adds "send receipt for 9001" and replies at once. A worker sends the email later, and a crashed worker can be retried without the user noticing.

## How it works

<Mermaid
  alt="The payment API pushes job 9001 onto the jobs:receipts list. Worker w1 moves it atomically into its own list jobs:processing:w1, sends the receipt, and then removes the job from its processing list."
  chart={`flowchart LR
  API[Payment API] -- "1. LPUSH 9001" --> Q[(jobs:receipts)]
  Q -- "2. BLMOVE" --> P[(jobs:processing:w1)]
  P --> W[Worker w1: 3. send receipt]
  W -- "4. LREM 9001" --> P`}
/>

1. The API adds the job to the left end of the list with `LPUSH jobs:receipts 9001`.
2. A worker waits with `BLMOVE jobs:receipts jobs:processing:w1 RIGHT LEFT 0`. When a job arrives, Redis takes it from the right end and puts it in the worker's processing list in one atomic step.
3. The worker does the job. If it crashes now, the job is still in `jobs:processing:w1`.
4. When done, the worker removes the job with `LREM jobs:processing:w1 1 9001`.
5. A separate watcher puts back on the queue any job that has stayed in a processing list too long.

The simpler `BRPOP` removes the job outright, so a crash between steps 2 and 4 loses it. That is why step 2 uses `BLMOVE`.

## Example

A receipt job goes through the reliable queue, then a status check is scheduled for later in a sorted set.

```bash
redis-cli LPUSH jobs:receipts 9001
redis-cli BLMOVE jobs:receipts jobs:processing:w1 RIGHT LEFT 0
redis-cli LREM jobs:processing:w1 1 9001
# check payment 9001 at 10:05 IST on 20-10-2026 (Unix time 1792470900)
redis-cli ZADD jobs:delayed 1792470900 check:9001
redis-cli ZRANGE jobs:delayed -inf 1792470900 BYSCORE LIMIT 0 10
redis-cli ZREM jobs:delayed check:9001   # worker w1
redis-cli ZREM jobs:delayed check:9001   # worker w2, a moment later
```

```text output
(integer) 1
"9001"
(integer) 1
(integer) 1
1) "check:9001"
(integer) 1
(integer) 0
```

What to notice:

- `BLMOVE` returns the job, `"9001"`, and the job now waits in `jobs:processing:w1` until `LREM` returns 1.
- The delayed job's score is its run time. `ZRANGE ... BYSCORE` up to now lists only jobs that are due.
- Both workers saw the due job, but only w1's `ZREM` returned 1, so only w1 runs it. Skip the `ZREM` check and both would run it.

## Rules and defaults

- **BLMOVE:** Redis 6.2+. It replaces the deprecated `BRPOPLPUSH`; `BLMOVE ... RIGHT LEFT` does the same thing.
- **Timeout 0:** the worker blocks until a job arrives, with no time limit.
- **At least once:** a job that is retried after a crash may run twice, so make each job safe to repeat, for example by checking whether receipt 9001 was already sent.
- **Kafka instead:** when events must stay on disk for a long time and many services replay them. Redis keeps streams in memory.

## Not to be confused with

A list hands each job to one worker and keeps it until taken. A stream keeps every entry, gives each one to one worker per consumer group, and tracks which entries were acknowledged. [Pub/Sub](card:pub-sub) sends each message to whoever is subscribed at that moment and keeps nothing. Rule: list for simple jobs, stream for acks and replay, Pub/Sub only for live notices.

## Interview Qs

### How do you build a job queue with Redis?

Producers `LPUSH` jobs onto a list, and workers block on `BRPOP`. To survive crashes, each worker uses `BLMOVE` to move a job into its own processing list and `LREM`s it when done, while a watcher re-queues jobs stuck there too long.

### How do you run a job later?

Add it to a sorted set with its run time as the score. Workers read due jobs with `ZRANGE ... BYSCORE` up to now and claim each with `ZREM`; only the worker that gets 1 runs it.

### When would you choose Kafka over Redis Streams?

When events must stay on disk for a long time or be replayed by many services. Redis streams live in memory, are usually capped with `MAXLEN`, and replicate asynchronously, so they suit short-lived work queues better than a long event history.
