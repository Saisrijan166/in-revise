## Why it exists

Slow work, such as emailing a payment receipt, should not hold up the API reply. A queue lets the API answer now and a worker do the job later.

## How it works

<Compare id="pub-sub-vs-lists-vs-streams" />

- BRPOP removes the job at once; if the worker then crashes, the job is gone. BLMOVE keeps a copy.
- A watcher re-queues jobs left in a processing list too long.

## Example

```text
-- payment PAY101 succeeded: queue its receipt
LPUSH jobs:receipts PAY101                            -> (integer) 1
-- worker w1 waits for a job and keeps it in its processing list
BLMOVE jobs:receipts jobs:processing:w1 RIGHT LEFT 0  -> "PAY101"
-- ... receipt sent ...
LREM jobs:processing:w1 1 PAY101                      -> (integer) 1
-- delayed: check UPI status at 10:05 IST on 20-10-2026
ZADD jobs:delayed 1792470900 check:PAY101             -> (integer) 1
ZRANGE jobs:delayed -inf 1792470900 BYSCORE LIMIT 0 10
ZREM jobs:delayed check:PAY101                        -> (integer) 1, so w1 runs it
```

## Interview Qs

### How do you build a job queue with Redis?

Producers LPUSH jobs onto a list; workers block on BRPOP. To survive crashes, a worker uses BLMOVE to move each job into its processing list and LREMs it when done.

### How do you run a job later?

Add it to a sorted set with the run time as score. Workers read jobs due up to now with ZRANGE ... BYSCORE and claim each with ZREM: only the worker that gets 1 runs it.

### When would you choose Kafka over Redis Streams?

When events must stay on disk for a long time or be replayed by many services. Redis streams live in memory, are usually capped with MAXLEN, and replicate asynchronously.
