## What it is

A round trip is the time a command takes to travel from your app to Redis plus the time its reply takes to come back. Normally a client sends one command and waits for the reply before it sends the next. Pipelining means the client sends many commands without waiting, and then reads all the replies, in the same order, at the end. It is a way to save network time; it does not make the commands one atomic step.

## Why it exists

Redis runs a GET very quickly, but every reply still has to cross the network. Reading 1,000 payment statuses one by one, 1 ms away from Redis, takes about a second, and nearly all of it is waiting. The Redis docs give an extreme case: with a 250 ms round trip, a client can make only 4 requests a second, however fast the server is. With pipelining the client pays roughly one round trip per batch instead of one per command.

1. The client writes several commands into the connection, one after another, without reading anything.
2. Redis reads them, often many in a single `read()` system call (a request to the operating system), and runs them one by one in the order sent. Commands from other clients may run between them.
3. Redis keeps the replies in memory and sends them back, often many in a single `write()` call.
4. The client reads the replies in the same order as its commands.

So a pipeline saves round trips and system calls, but the commands stay separate.

## Example

The payment service reads the status and the remaining TTL of three payments in one round trip:

```java
List<String> ids = List.of("9001", "9002", "9003");
List<Object> replies = stringRedisTemplate.executePipelined(
    (RedisCallback<Object>) connection -> {
        StringRedisConnection c = new DefaultStringRedisConnection(connection);
        for (String id : ids) {
            c.get("payment:" + id);   // queued on the connection, no waiting
            c.ttl("payment:" + id);
        }
        return null;                  // must be null: the replies come back as the list
    });
System.out.println(replies);
```

```text output
[PAID, -1, PENDING, 600, FAILED, -1]
```

What to notice:

- Inside the callback, `c.get` and `c.ttl` return nothing useful: their replies arrive only in the `replies` list, after the whole batch.
- The list holds one reply per command, in the order sent: a status, then the seconds left before expiry (it counts down), where -1 means the key has no expiry.
- The callback must return `null`; Spring discards it and returns the pipeline's replies instead.
- Six commands cost about one round trip. Without `executePipelined`, the same loop would wait six times.

## Rules and defaults

- **One command first:** if a single command for many keys fits, such as MGET or MSET, use it instead of a pipeline. It is one command and one round trip.
- **Batch size:** Redis holds every reply in memory until it sends it, so send large jobs in batches, such as 10,000 commands, then read and send the next batch.
- **Not atomic:** commands from other clients can run between yours. Put MULTI and EXEC inside the pipeline if you need both speed and isolation.
- **Each command alone:** an error in one pipelined command does not stop the others.
- **Scripts in a pipeline:** a NOSCRIPT error cannot be handled in the middle of a pipeline, so run SCRIPT LOAD first or send EVAL ([Lua scripts](card:lua-and-functions)).

## Not to be confused with

A pipeline is a way for the client to send commands: it saves network time and gives no isolation. A [MULTI/EXEC transaction](card:transactions-multi-exec) is a server guarantee: the queued commands run with no other client in between. The two combine well. Rule: a pipeline saves time; MULTI/EXEC keeps commands together.

## Common mistakes

- **"Pipelining makes a slow command faster."** It removes network waiting only. A command that is slow on the server, such as KEYS on a big database, still blocks every client.

## Interview Qs

### What is pipelining and when would you use it?

The client sends many commands without waiting for each reply, then reads all the replies together. Use it for bulk loads and for many independent reads or writes, when one multi-key command such as MGET cannot do the job.

### Is a pipeline the same as MULTI/EXEC?

No. A pipeline only batches network traffic; other clients' commands can run between yours, and you get no isolation. MULTI/EXEC runs the queued commands with no other client in between. You can send a MULTI/EXEC block inside a pipeline to get both.

### Why does pipelining help even when Redis runs on the same machine?

Each command sent alone costs a `read()` and a `write()` system call, and switching into the operating system is slow compared with running the command. A pipeline lets Redis read many commands in one call and write many replies in one call. The Redis docs show throughput rising up to about ten times.
