## What it is

A distributed lock lets processes on different machines agree that only one of them does a piece of work at a time. A Java `synchronized` block cannot do this, because it only stops threads inside one JVM. With Redis the lock is one key, such as `lock:payment:9001`: the worker that creates the key holds the lock. The key has a TTL, which here is called a lease, so it disappears even if the holder crashes.

## Why it exists

The payment service runs on three app servers, each polling for payments to capture. Without a lock, two servers can pick up payment 9001 at the same moment and both call the bank. With a lock, the first server to create the key does the capture and the others see the key and skip it. The lease matters too: without it, a server that crashed while holding the lock would block payment 9001 forever.

## How it works

1. A worker makes a random token and sends `SET lock:payment:9001 <token> NX PX 30000`. `NX` creates the key only if it does not exist; `PX 30000` gives it a 30-second lease.
2. Redis replies `OK` to exactly one worker. The others get `nil` and skip the job or retry after a short random delay.
3. The holder does the work well inside the lease, then deletes the key only if it still holds its token.
4. If the holder crashes instead, the key expires after 30 seconds and another worker can take the lock.

The diagram shows the weak spot of step 3: a lease can expire while its holder still runs. A fencing token is a number that grows with every grant. The holder sends it with each write, and the database refuses a number older than one it has already seen. Plain `SET NX` gives no such number; Redisson's `RFencedLock` returns one with each grant.

## Example

Worker A locks payment 9001, worker B tries the same lock, and then each tries to release it.

```bash
redis-cli SET lock:payment:9001 7f3a91c2 NX PX 30000   # worker A
redis-cli SET lock:payment:9001 c0d4e815 NX PX 30000   # worker B
redis-cli PTTL lock:payment:9001                        # lease left, in ms
redis-cli DELEX lock:payment:9001 IFEQ c0d4e815         # B tries to release
redis-cli DELEX lock:payment:9001 IFEQ 7f3a91c2         # A releases its own
```

```text output
OK
(nil)
(integer) 29347
(integer) 0
(integer) 1
```

Before Redis 8.4 the release is this Lua script, run with `EVAL` and the lock key in `KEYS[1]` and the token in `ARGV[1]`:

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

What to notice:

- Worker B gets `(nil)`, not an error: the key exists, so `NX` refuses to overwrite it and B must not start the work.
- `DELEX ... IFEQ` with B's token returns 0 and leaves A's lock alone. A plain `DEL` from B would have removed it.
- The script checks and deletes in one atomic step. A `GET` in the app followed by `DEL` leaves a gap in which the lease can expire.
- You will see the same lock in Java in [Redis Code Templates](card:redis-code-templates).

## Rules and defaults

- **Token:** must be unique across all clients and requests; the Redis docs suggest 20 random bytes.
- **Lease length:** longer than the slowest normal run, short enough that a crash does not block work for long. Redis never extends it for you.
- **Extending a lease:** Redisson's `RLock` watchdog renews the lock while its holder lives; unrenewed, it expires after 30 seconds by default (`lockWatchdogTimeout`). It runs only if you lock without a lease time.
- **Failover:** replicas get writes asynchronously, so a primary can crash before the lock key reaches its replica, letting a second worker lock on the new primary. You will see this in [Replication](card:replication).
- **Redlock:** locks the same key on N independent primaries (for example 5) and counts it as held if a majority grant it within the lease. Its safety is debated: Kleppmann says it relies on timing assumptions; antirez disagrees. Redisson deprecated `RedissonRedLock`.

## Not to be confused with

A local lock, such as `ReentrantLock`, works inside one JVM. A distributed lock works across machines and ends by a delete or by expiry. An idempotency key does not prevent a second attempt; it makes the second attempt change nothing. Rule: the lock avoids duplicate work; the idempotency key makes duplicates safe.

## Common mistakes

- **"SET the key, then call EXPIRE."** If the app dies between the two calls, the key never expires and the job is blocked for good. Use `SET ... NX PX` in one command.
- **"A fixed value such as locked is fine."** Then every worker writes the same value, and a release cannot tell who owns the lock. Use a random token per request.

## Interview Qs

### How do you build a distributed lock with Redis?

Send `SET lock:payment:9001 <random token> NX PX 30000`. `OK` means you hold the lock; `nil` means someone else does. Do the work inside the lease, then release by deleting the key only if it still holds your token, with `DELEX ... IFEQ` on Redis 8.4+ or a compare-and-delete Lua script.

### What happens if the work takes longer than the lease?

The key expires, a second worker takes the lock, and both run at once. Keep the work short, extend the lease while working (Redisson's watchdog does this), and pass a fencing token so the database rejects writes from the older holder.

### Does a Redis lock make a payment happen exactly once?

No. Expiry, a long pause or a failover can let two workers in. Give each payment an idempotency key with a unique constraint in the database, and send the same key to the payment provider, so a second attempt changes nothing.
