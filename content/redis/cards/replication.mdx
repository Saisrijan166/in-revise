## What it is

Replication means one Redis server, the primary, keeps one or more other servers, the replicas, as live copies of its data. The primary takes the writes and sends each one to its replicas as a stream of commands. Replicas reject writes by default but can answer reads. The primary does not wait for the replicas before it replies OK; this is called asynchronous replication.

## Why it exists

With one server, a crash means the payment service has no Redis until someone repairs it, and a dead disk leaves only your backups. All reads also share that server's one main thread. A replica keeps an up-to-date copy on another machine, so it can take over, and slow reads can move off the primary. Taking over is not automatic with replication alone: [Sentinel](card:sentinel) or [Cluster](card:redis-cluster), later in this topic, does it.

## How it works

  alt="The app writes to the primary, which streams the write commands to two replicas. The app may also read from replica 1, which can be slightly behind."
  chart={`flowchart LR
  App -- writes --> P[(Primary)]

1. You run `REPLICAOF <primary-host> 6379` on the new server, or put `replicaof` in its redis.conf.
2. The first time, the replica needs everything. The primary makes an [RDB snapshot](card:rdb-snapshot) and sends it, buffering new writes meanwhile; the replica loads it, then applies the buffered writes. This is a full sync.
3. From then on, the primary streams every change to the replica, including the deletes of keys that expired or were evicted. The primary names this history with a replication ID, a random string, and counts the bytes it has sent in its replication offset.
4. If the link breaks for a short time, the replica reconnects with `PSYNC`, sending the primary's replication ID and the offset it reached. If the primary's backlog still holds what was missed, it sends only that part. This is a partial resync.
5. If the backlog no longer holds it, the replica gets a full sync again.

So the replication ID and offset say exactly which version of the data a replica has.

## Example

Here a new replica joins the payment service's primary, and the primary writes a payment and waits for both replicas.

```bash
# on redis-replica-1
redis-cli REPLICAOF redis-primary 6379
sleep 10                                # let the first full sync finish
redis-cli INFO replication | grep -E "^(role|master_link_status)"
# on redis-primary
redis-cli SET payment:9001 PAID
redis-cli WAIT 2 100                    # wait up to 100 ms for 2 replicas
# on redis-replica-1
redis-cli GET payment:9001
redis-cli SET payment:9001 FAILED
```

```text output
OK
role:slave
master_link_status:up
OK
(integer) 2
"PAID"
(error) READONLY You can't write against a read only replica.
```

What to notice:

- `INFO` still uses the old word `slave` for a replica, and `master_link_status:up` means the first full sync has finished.
- `WAIT 2 100` returned 2: both replicas confirmed the write within 100 ms. It only waits and counts; it does not undo the write if fewer confirm.
- The replica refuses `SET` because `replica-read-only` is on by default. All writes must go to the primary.

## Rules and defaults

- **Defaults (Redis Open Source 8.10):** `replica-read-only yes`, `repl-backlog-size 1mb`, `min-replicas-to-write 0` (off).
- **Full sync without disk:** `repl-diskless-sync yes` by default, so the primary streams the snapshot over the network. It waits `repl-diskless-sync-delay`, 5 seconds by default, so more replicas can share one transfer.
- **Expiry:** replicas never expire keys themselves. The primary sends a delete, and meanwhile a replica hides keys that are already past their TTL from reads.
- **Limiting lost writes:** with `min-replicas-to-write N` and `min-replicas-max-lag M`, the primary refuses writes unless at least N replicas confirmed within the last M seconds. It bounds the loss window; it does not guarantee each write.
- **Persistence off on the primary:** do not let such a primary restart automatically, or it comes back empty and empties its replicas too.

## Not to be confused with

Replication copies the whole dataset to other servers; [Cluster](card:redis-cluster) splits the dataset so each primary holds a different part. [Persistence](card:persistence-rdb-aof) protects one server across a restart. Rule: replica = same data elsewhere, shard = different data on each node, backup = an older version you can restore.

## Interview Qs

### Is Redis replication synchronous? What does WAIT do?

No. The primary replies before replicas have the write. `WAIT numreplicas timeout` blocks the client until that many replicas confirm its earlier writes, or the timeout passes, and returns how many did. It makes losing a write much less likely, but the Redis docs say it does not make Redis strongly consistent.

### What is the difference between a full sync and a partial resync?

A full sync sends a complete RDB snapshot and then the live stream; it is used for a new replica or one that is too far behind. A partial resync sends only the missed writes from the primary's backlog, using the replica's replication ID and offset. It is much cheaper.

### Why read from replicas, and what is the risk?

Replicas add read capacity, and slow commands can run there without blocking the primary. The risk is stale data: a replica can be behind, so a read right after a write may return the old value. Read just-changed data from the primary.
