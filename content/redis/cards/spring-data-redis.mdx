## What it is

Spring Data Redis is a Spring library for using Redis from Java. Its main class, the template, has a method for each Redis command: `opsForValue().set(...)` sends SET. A template uses serialisers, converters that turn Java keys and values into the bytes Redis stores. Below the template, a client library holds the network connection and sends the commands; Spring Boot uses Lettuce by default.

## Why it exists

Without it, every service would use a client library directly: open connections, convert each key and value to bytes by hand, and translate errors in every method. Spring Data Redis puts that work in one shared template. Spring Boot adds the setup: when the Redis starter is on the classpath, it creates the connection factory and the templates as beans, the objects Spring creates and injects. A service only asks for a template in its constructor and calls it.

## How it works

1. At startup, Spring Boot reads the `spring.data.redis.*` properties and builds a `RedisConnectionFactory` for Lettuce.
2. Boot creates two template beans on that factory: `StringRedisTemplate` and `RedisTemplate<Object, Object>`.
3. Your service calls a template method, such as `opsForValue().set(key, value, Duration)`.
4. The template's serialisers turn the key and the value into bytes.
5. Lettuce sends the command over its shared connection, and the template turns the reply back into a Java value.

So the key is the serialiser: it decides what Redis really stores, so choose it on purpose.

## Example

The payment service caches the payment record `payment:9001` as JSON, so another service, or a person with redis-cli, can read it.

```java
@Bean
RedisTemplate<String, Payment> paymentTemplate(RedisConnectionFactory factory) {
    var template = new RedisTemplate<String, Payment>();
    template.setConnectionFactory(factory);
    template.setKeySerializer(RedisSerializer.string());
    template.setValueSerializer(new JacksonJsonRedisSerializer<>(Payment.class));
    return template;
}

// In PaymentService: Payment is record Payment(String id, long amount, String status)
paymentTemplate.opsForValue().set("payment:9001", payment, Duration.ofMinutes(5));
```

```bash
redis-cli GET payment:9001
redis-cli TTL payment:9001
```

```text output
"{\"id\":\"9001\",\"amount\":500,\"status\":\"PAID\"}"
(integer) 297
```

What to notice:

- `RedisSerializer.string()` stores the key as plain text, so redis-cli finds `payment:9001`. Remove that line and the key is written as JDK bytes, which is a different key.
- `JacksonJsonRedisSerializer` (Jackson 3, Spring Data Redis 4.0 and later) writes the record as readable JSON and reads it back as a `Payment`.
- Passing a `Duration` sends one `SET payment:9001 ... EX 300`, so the value and its TTL arrive together; the TTL had dropped to 297 when redis-cli ran.
- The bean is named `paymentTemplate`, so Boot's own `redisTemplate` bean still exists beside it.

## Rules and defaults

- **Server:** `localhost:6379` unless you set `spring.data.redis.host` and `port`. If you set `spring.data.redis.url`, Boot ignores host, port, username and password (Spring Boot 4.1).
- **Client:** the starter brings Lettuce. To use Jedis, exclude `lettuce-core` and add the `jedis` dependency.
- **Replacing Boot's beans:** any bean of type `StringRedisTemplate` replaces Boot's. A `RedisTemplate` replaces Boot's only if the bean is named `redisTemplate`.
- **Serialisation:** `RedisTemplate` and Spring's `RedisCache` use JDK serialisation unless you set serialisers. `StringRedisTemplate` uses `StringRedisSerializer`, so keys and values are readable text (Spring Data Redis 4.1).
- **Connections:** Lettuce shares one thread-safe connection for normal commands. Blocking commands such as BLPOP and MULTI/EXEC transactions need a dedicated connection. With `commons-pool2` on the classpath, Boot builds a pooled connection factory.

## Not to be confused with

`StringRedisTemplate` is a ready `RedisTemplate<String, String>` whose serialisers write plain text, so what you store is what redis-cli shows. `RedisTemplate` takes any key and value types, and you choose its serialisers. Rule: text and counters go through `StringRedisTemplate`; objects go through a `RedisTemplate<String, T>` with a JSON value serialiser.

Lettuce and Jedis are the client libraries under the template; the template is the API you call. Rule: keep Lettuce unless your team already runs Jedis.

## Common mistakes

- **"`spring.redis.host` still configures Redis."** Spring Boot 3.0 renamed these properties to `spring.data.redis.*`. Boot 4.1 marks the old names as an error and does not bind them, so the app quietly connects to `localhost:6379`.

## Interview Qs

### Do you need a connection pool with Lettuce?

Usually not. One thread-safe Lettuce connection is shared by all threads for normal commands. Blocking commands such as BLPOP and MULTI/EXEC transactions each need a dedicated connection, so add `commons-pool2` when you use them often; Spring Boot then builds a pooled connection factory.

### How do you store Java objects as JSON in Redis?

Define a `RedisTemplate<String, T>` bean with `RedisSerializer.string()` for keys and `JacksonJsonRedisSerializer` for values. Redis then holds readable JSON that other languages and redis-cli can read, and the template turns it back into your object.

### Why is JDK serialisation a poor choice for Redis values?

The bytes are Java-only, so other services and redis-cli cannot read them. The Spring Data Redis docs also warn that Java deserialisation of untrusted data can let an attacker run code, and recommend a format such as JSON instead.
