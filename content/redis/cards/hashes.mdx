## Why it exists

A payment has several fields that change on their own. Stored as one JSON string, every change means read, edit, write back. A hash lets you change just one field.

## How it works

- Small hashes use a compact encoding: see [memory optimisation](card:memory-optimization).
- Need nested objects or arrays? Use [JSON](card:json-and-query-engine).

## Example

```text
HSET payment:PAY101:details amount 500 currency INR method UPI  -- 3
HGET payment:PAY101:details amount           -- "500"
HINCRBY payment:PAY101:details retries 1     -- 1
HEXPIRE payment:PAY101:details 600 FIELDS 1 method   -- 1) 1
HGETALL payment:PAY101:details               -- all fields and values
```

## Interview Qs

### When is a hash better than a JSON string?

When fields are read or changed one at a time. HSET or HINCRBY touches one field; a string must be read, edited and written back whole.

### How would you keep several counters for one merchant?

One hash per merchant, one field per counter: `HINCRBY merchant:42:stats upi 1`. Each increment is atomic, and HGETALL reads every counter in one call.
