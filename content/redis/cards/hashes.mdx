## What it is

A hash is a key whose value is a small map of fields, each field holding a string value. It looks like one row of a table: the key `payment:9001` has the fields `amount`, `currency`, `method` and `status`. You can read or change one field on its own. A field value is always a string, so a hash cannot hold another hash or a list inside it.

## Why it exists

If the payment record is cached as one JSON [string](card:strings), changing its status means three steps: read the whole text, edit it in the app, and write it back. Two app servers doing this at the same time can each overwrite the other's change. A hash avoids both problems: `HSET payment:9001 status PAID` changes one field in one command, and `HINCRBY` adds to a numeric field in one atomic step, so no other client can slip in between the read and the write.

## How it works

1. `HSET key field value [field value ...]` creates the hash if needed and writes the fields. It returns how many fields were new.
2. `HGET key field` reads one field; `HMGET` reads several; `HGETALL` reads them all.
3. `HINCRBY key field n` reads the field as an integer, adds n and stores it again, in one step. A missing field starts at 0.
4. `HDEL key field` removes a field. When the last field goes, Redis deletes the key itself.

So the key is: one key per object, one field per property.

## Example

The payment service stores payment 9001 as a hash, marks it paid and counts a retry.

```bash
redis-cli HSET payment:9001 amount 500 currency INR method UPI status PENDING
redis-cli HSET payment:9001 status PAID
redis-cli HINCRBY payment:9001 retries 1
redis-cli HGET payment:9001 status
redis-cli HMGET payment:9001 amount currency
redis-cli HEXPIRE payment:9001 600 FIELDS 1 retries
```

```text output
(integer) 4
(integer) 0
(integer) 1
"PAID"
1) "500"
2) "INR"
1) (integer) 1
```

What to notice:

- The second HSET returned 0: `status` already existed, so it was updated, not added. Only that one field changed.
- `HINCRBY` created the missing field `retries` from 0 and returned the new value, 1.
- `amount` came back as `"500"`, a string. Your code converts it to a number.
- `HEXPIRE` returned 1, meaning the expiry was set on `retries` alone; the rest of the hash does not expire. You will learn expiry in [TTL and key expiry](card:ttl-and-expiration).

## Rules and defaults

- **Values are strings:** numbers are stored as text; `HINCRBY` and `HINCRBYFLOAT` read them as numbers.
- **Field expiry:** since Redis 7.4, `HEXPIRE` and `HPEXPIRE` set an expiry on single fields. Redis 8.0 added `HSETEX` and `HGETEX` to set or read fields and their expiry in one command.
- **Size:** the number of fields has no practical limit other than memory. Small hashes use a compact encoding, covered in [Big keys and memory use](card:memory-optimization).
- **Whole-hash commands:** `HGETALL`, `HKEYS` and `HVALS` read every field. On a big hash, walk the fields in pages with `HSCAN`.

## Not to be confused with

A [string](card:strings) holds one whole value, so you rewrite it to change anything. A hash holds flat fields, so you change one at a time. A [JSON document](card:json-and-query-engine) holds nested objects and arrays and can change any part by path. Rule: whole value = string; flat fields = hash; nested = JSON.

## Interview Qs

### When is a hash better than a JSON string?

When fields are read or changed one at a time. HSET or HINCRBY touches one field in one command. A string must be read, edited and written back whole, which costs more and lets two writers overwrite each other's change.

### What happens if you run HINCRBY on a field that holds text?

Redis returns the error "hash value is not an integer" and changes nothing. Field values are plain strings, and HINCRBY works only when the string reads as an integer. So keep counters in their own fields and never mix them with text.

### Can one field of a hash expire on its own?

Yes, since Redis 7.4. HEXPIRE sets an expiry on named fields, and when it runs out Redis removes only those fields. Before 7.4 you could only expire the whole key, so short-lived fields had to go into separate keys.
