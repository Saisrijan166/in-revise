## What it is

These are four ways a cache stops shielding the database. A stampede (also called a thundering herd) happens when a popular key expires and many requests miss and rebuild it at the same moment. Penetration means requests for ids that exist neither in Redis nor in the database, so nothing is ever cached. An avalanche means many keys expire together, or a cache node starts empty. A hot key gets so much traffic that the one Redis node holding it is overloaded.

## Why it exists

A cache protects the database only while requests hit it, and the database is usually sized for that. During a sale, `merchant:42:config` may be read 5,000 times a second. When it expires, all of those requests can reach PostgreSQL in the same second. The database slows down or falls over, and then even the rebuild fails. Naming the case tells you which fix applies.

## How it works

<Compare id="stampede-vs-penetration-vs-avalanche" />

A stampede on `merchant:42:config`, handled with a rebuild lock:

1. Request A misses and runs `SET lock:merchant:42:config req-7 NX EX 10`. Redis replies `OK`, so A is the one that rebuilds.
2. Requests B, C and the rest also miss, but their `SET NX` returns nil because the lock exists. They wait a few milliseconds and read again, or serve a stale copy if the app kept one.
3. A reads PostgreSQL, stores the config with a fresh TTL and removes the lock.
4. The waiting requests now hit.
5. If A crashes, the lock's 10-second TTL frees it, so another request can rebuild.

So the key is one rebuild per key, not one per request. You will see how to release a lock safely in [distributed locks](card:distributed-locks).

## Example

One redis-cli session with the three fixes: the rebuild lock, a cached absence, and a TTL with jitter.

```bash
SET lock:merchant:42:config req-7 NX EX 10
SET lock:merchant:42:config req-8 NX EX 10
GET payment:9999
SET payment:9999 NOT_FOUND EX 60
SET merchant:43:config '{"feePct":3}' EX 3727
```

```text output
OK
(nil)
(nil)
OK
OK
```

What to notice:

- The first `SET NX` returns `OK` and the second returns `(nil)`: only one caller gets the lock. `EX 10` frees it if that caller crashes.
- `GET payment:9999` misses, and the database has no payment 9999 either. Storing the marker `NOT_FOUND` for 60 seconds stops repeats; the app must treat that value as "no such payment".
- Keep that TTL short. If payment 9999 is created later, callers see it within a minute.
- `EX 3727` is 3600 seconds plus a random 127 chosen by the app. Keys loaded together then expire over several minutes, not in one second.

## Rules and defaults

- **Early refresh:** instead of a lock, each reader may recompute a key a little before it expires, with a probability that rises near expiry, so usually one reader refreshes first (XFetch, VLDB 2015).
- **Bloom filter:** keep real payment ids in a [Bloom filter](card:json-and-query-engine). A "not present" answer is certain, so the app skips the database; a "maybe present" still needs the database check.
- **Warm before traffic:** a new or restarted node starts empty, which acts like an avalanche. Run a script that replays common reads before the node takes traffic (AWS guidance).
- **Finding hot keys:** `redis-cli --hotkeys` samples keys and works only when `maxmemory-policy` is an LFU policy. `HOTKEYS` (Redis 8.6+) tracks the top keys by CPU time and network bytes.
- **Spreading a hot key:** let each app instance keep a local copy with Redis client-side caching (Redis 6+), where the server sends an invalidation message when the key changes. Or store copies under several keys on different nodes and read one at random, or read from replicas.

## Not to be confused with

A hot key is a small key that gets a huge share of the requests. A [big key](card:memory-optimization) is one very large value that makes single commands slow. Rule: big key = size, so split it; hot key = traffic, so spread the reads.

## Interview Qs

### How do you prevent a cache stampede on one popular key?

Let one caller rebuild: the first one to miss takes a short lock with `SET NX EX`, reloads the value and stores it, while the others wait briefly or serve a stale copy the app kept. Another option is early refresh, where one reader refreshes the key shortly before it expires.

### A flash sale makes one product key hot. What do you do?

Keep a short-lived copy in each app instance with Redis client-side caching (Redis 6+), so most reads never reach Redis. Or store copies of the key on several nodes and read one at random; replicas can also share the reads.

### Redis restarts empty at peak traffic. What happens?

Every read misses, so it acts like an avalanche on the database. Warm the cache first with a script that replays common reads, and limit how many database calls run at once until hits recover; you will see how in [failure handling](card:redis-failure-handling).
