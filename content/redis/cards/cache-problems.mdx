## Why it exists

A cache shields the database only while requests hit it. Some patterns of misses send a sudden flood to the database instead, often at peak traffic.

## How it works

<Compare id="stampede-vs-penetration-vs-avalanche" />

- The rebuild lock uses the same `SET NX` idea as [distributed locks](card:distributed-locks).
- Early refresh: each reader may recompute a little before expiry, at random, so one usually refreshes first.
- Large values are a different problem: [big keys](card:memory-optimization).

## Example

```text
GET payment:PAY999                        -> (nil)   miss; the DB has no PAY999
SET payment:PAY999 "NOT_FOUND" EX 60      -- cache the absence briefly
SET merchant:42:config "{...}" EX 3727    -- 3600 s plus random jitter
```

## Interview Qs

### A flash sale makes one product key hot. What do you do?

Keep a short-lived copy in each app instance, kept fresh by Redis client-side caching (Redis 6+). Or store copies of the key on several nodes and read one at random; replicas can also share the reads.

### Redis restarts empty at peak traffic. What happens?

Every read misses, so it acts like an avalanche on the database. Warm the cache first with a script that replays common reads, and limit database calls until hits recover: see [failure handling](card:redis-failure-handling).
