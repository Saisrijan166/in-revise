## What it is

A list is a key whose value is a sequence of strings kept in the order you add them. It is not sorted, and the same value may appear more than once. You work on its two ends: the left end is called the head (commands starting with L) and the right end is the tail (commands starting with R). Redis builds lists as linked lists, so adding or removing at an end costs the same however long the list is.

## Why it exists

Two needs come up again and again: "show the latest N payments" and "give the next job to a free worker". Keeping them in one [string](card:strings) means rewriting the whole value on every change, and keeping them in a database table means a worker asks "anything new?" again and again. A list adds an item at one end and removes it at the other in one fast command, and a worker can wait inside Redis until a job arrives.

## How it works

<Mermaid
  alt="A producer pushes new payment ids on the left with LPUSH. The list runs from the newest item at the head to the oldest at the tail. A worker takes the oldest item from the right with BRPOP, so items are handled first in, first out."
  chart={`flowchart LR
  P[Producer] -- LPUSH --> H["head: 9003, 9002, 9001 :tail"]
  H -- BRPOP --> W[Worker]`}
/>

1. A producer calls `LPUSH key item`. If the key does not exist, Redis creates the list first.
2. Each new item goes in at the head, so the oldest item drifts towards the tail.
3. A worker calls `BRPOP key timeout`. If the list has an item, Redis removes the one at the tail and returns it at once.
4. If the list is empty, the worker's connection waits until a producer pushes an item or the timeout runs out.
5. When the last item is popped, Redis deletes the key automatically.

So the key is: push at one end and pop at the other for first in, first out; push and pop at the same end for last in, first out.

## Example

The payment service keeps merchant 42's latest payments and hands one refund job to a worker.

```bash
redis-cli LPUSH recent:merchant:42 payment:9001 payment:9002 payment:9003
redis-cli LTRIM recent:merchant:42 0 99
redis-cli LRANGE recent:merchant:42 0 1
redis-cli RPUSH jobs:refund payment:9001
redis-cli BRPOP jobs:refund 5
redis-cli BRPOP jobs:refund 1
```

```text output
(integer) 3
OK
1) "payment:9003"
2) "payment:9002"
(integer) 1
1) "jobs:refund"
2) "payment:9001"
(nil)
```

What to notice:

- One `LPUSH` with three ids put the last one, 9003, at the head. `LRANGE 0 1` read the two newest.
- `LTRIM 0 99` keeps indexes 0 to 99 and deletes the rest, so the feed never grows past 100 items. Run it after every push.
- `BRPOP` returned two values, the list name and the item, because one call can watch several lists.
- The second `BRPOP` waited 1 second on the now empty list and returned nil. The empty list had already been deleted.

## Rules and defaults

- **Length limit:** a list can hold up to 2^32 - 1 (about 4.29 billion) items.
- **Speed:** commands at the head or tail are O(1), meaning their cost does not grow with the list. Commands that reach into the middle, such as `LINDEX`, are O(n).
- **Blocking timeout:** in seconds, read as a decimal number; 0 waits forever. With several keys, `BRPOP` pops from the first non-empty one in the order you listed them.
- **Missing or empty key:** read commands return an empty reply or nil, not an error; the key is created on the first push and deleted with the last item.

## Not to be confused with

A list is a queue inside Redis: each item is popped by one worker and is then gone. A [stream](card:streams), which you will meet soon, keeps every entry after it is read and tracks which worker has finished it. Rule: list = simple job queue; stream = jobs that must not be lost.

## Common mistakes

- **"BRPOP makes the queue reliable."** BRPOP removes the item as it returns it. If the worker crashes before finishing, the job is lost. `BLMOVE` moves the item to a "processing" list instead; [Queues with Redis](card:queues-with-redis) shows this pattern.

## Interview Qs

### Why are pushes O(1) but LINDEX slow?

Redis lists are linked lists, built for fast work at the head and tail. Reaching an item in the middle means walking the list to it, so the cost grows with its position. For fast access to the middle of a big collection, the Redis docs suggest a sorted set.

### How would you keep only the latest 100 payments for a dashboard?

LPUSH each new payment id, then LTRIM the list to 0 99 right after. The list never holds more than 100 items, and LRANGE 0 9 reads the newest ten.

### What does BRPOP with timeout 0 do?

It waits until an item arrives, with no time limit. With a non-zero timeout it returns nil when the time runs out. If several workers wait on the same list, the one that has waited longest gets the next item.
