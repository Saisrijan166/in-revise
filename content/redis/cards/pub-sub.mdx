## What it is

Pub/Sub (publish/subscribe) is a messaging feature, not a data type. A client subscribes to a channel, a name such as `payment-events`, and keeps its connection open to wait. Another client publishes a message on that channel, and Redis pushes it at once to every subscriber connected at that moment. Channels are not keys: Redis stores no messages, so a subscriber that joins later never sees earlier ones.

## Why it exists

When payment 9001 succeeds, several app servers may need to know at once, for example to push a live update to the customer's screen. With a [list](card:lists), only one worker would get each item. With a [stream](card:streams), each service would need its own consumer group and would store every event. Pub/Sub broadcasts one message to all current listeners in one call, with nothing to store or clean up.

## How it works

1. Each listener runs `SUBSCRIBE payment-events` and waits on its open connection.
2. The payment service runs `PUBLISH payment-events "9001 PAID"`.
3. Redis pushes the message to every client subscribed to that channel, and to every `PSUBSCRIBE` pattern that matches its name.
4. `PUBLISH` returns how many clients received it. Redis keeps nothing, so a client that subscribes afterwards never sees this message.

So the key is: delivery happens only in the moment of PUBLISH.

## Example

Two clients are listening: one ran `SUBSCRIBE payment-events`, the other `PSUBSCRIBE payment-*`. The payment service publishes on two channels.

```bash
redis-cli PUBLISH payment-events "9001 PAID"
redis-cli PUBLISH refund-events "9001 REFUNDED"
```

```text output
(integer) 2
(integer) 0
```

This is what the first subscriber printed:

```bash
redis-cli SUBSCRIBE payment-events
```

```text output
1) "subscribe"
2) "payment-events"
3) (integer) 1
1) "message"
2) "payment-events"
3) "9001 PAID"
```

What to notice:

- The first PUBLISH reached 2 clients: the exact subscriber and the pattern subscriber, because `payment-events` matches `payment-*`.
- The second PUBLISH returned 0. Nobody listens on `refund-events`, so that message is lost; Redis did not store it.
- The subscriber first gets a `subscribe` confirmation, then a `message` with the channel name and the payload. Its connection stays open and blocked, waiting for more.

## Rules and defaults

- **Delivery:** at-most-once. If a subscriber errors or disconnects, the message is lost for it.
- **No keyspace link:** channels ignore database numbers, so a message published while using db 10 reaches a subscriber using db 1. Prefix channel names, for example with the environment, to keep them apart.
- **Subscribed connection:** RESP2 and RESP3 are versions of the protocol clients use to talk to Redis. With RESP2 a subscribed client can only run subscribe-type commands, PING, RESET and QUIT; with RESP3 it can run any command.
- **Redis Cluster:** a normal PUBLISH is forwarded to every node. Sharded Pub/Sub (`SSUBSCRIBE`, `SPUBLISH`, Redis 7.0+) keeps a channel inside one shard, which scales better.
- **Keyspace notifications:** Redis can publish events when keys change or expire. They are off by default (`notify-keyspace-events ""`, Redis Open Source 8.10).

## Not to be confused with

Pub/Sub broadcasts to clients listening now and stores nothing. A [stream](card:streams) stores entries so consumers can read them later and acknowledge them. A [list](card:lists) hands each item to exactly one worker. Rule: live broadcast = Pub/Sub; must not lose = stream; one worker per job = list.

## Interview Qs

### Is Redis Pub/Sub reliable?

No. Delivery is at-most-once: a subscriber that is disconnected, or fails while handling a message, loses it, and Redis keeps no history. Use streams with consumer groups when every message must be processed.

### What are keyspace notifications?

Pub/Sub events that Redis publishes when keys change or expire, for example on the channel `__keyevent@0__:expired`. They are off by default, and like all Pub/Sub they are lost if no client is listening, so they are not a reliable trigger for business logic.

### When is Pub/Sub the right choice?

For live, short-lived signals where a missed message does no harm: pushing a "payment done" update to open browser sessions, or telling app servers to clear a local cache. The next update or a periodic refresh covers anything missed.
