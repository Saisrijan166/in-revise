## What it is

These are three other caching patterns, named by who does the loading and writing. In read-through, a cache layer (a library or product that sits between the app and the database) loads a missing entry itself, so the app only ever asks the cache. In write-through, every write updates the cache and the database before it returns. In write-behind, also called write-back, a write updates the cache at once and the database later, in the background.

## Why it exists

[Cache-aside](card:cache-aside) has two costs. Every service repeats the load-and-store code, and after a write the key is deleted, so the next reads miss or see a briefly stale copy. Read-through puts the loading code in one place. Write-through makes reads right after a write hit the cache with the new value. Write-behind makes writes fast and lets the cache merge many writes into a few database writes, at the price of possible data loss.

## How it works

<Compare id="cache-aside-vs-read-through-vs-write-through-vs-write-behind" />

Follow one read and one write of merchant 42's configuration under each pattern:

1. **Read-through:** the app asks the cache layer for merchant 42. On a miss, the layer runs a loader the app registered, stores the row and returns it.
2. **Write-through:** the app writes the new fee to PostgreSQL and stores the same value in Redis, and reports success only after both.
3. A read right after the write-through finds the new value in Redis: a hit.
4. **Write-behind:** the cache layer stores the new fee and returns success at once, and puts the database write on a queue.
5. A background worker later merges queued writes to the same key and sends them to PostgreSQL in batches. If the cache dies before this step, the queued writes are lost.

So the key is: each pattern moves work from the app into a cache layer, and write-behind also trades safety for speed.

## Example

With plain Redis, write-through is code the app writes itself: write the database, then store the same value instead of deleting it.

```java
void updateConfig(long id, String json) {
    configRepo.save(id, json);                                   // 1. write PostgreSQL
    redis.opsForValue().set("merchant:" + id + ":config", json,
            Duration.ofMinutes(30));                             // 2. write the same value to Redis
}                                                                // 3. only now does the caller get success
```

What to notice:

- The only change from cache-aside is `set` in place of `delete`, so the next read is a hit with the new value instead of a miss.
- The TTL stays. If the `set` fails after the database write, the old copy lives only until it expires.
- Two writers can reach Redis in the opposite order from the database, leaving the older value cached. You will see in [cache invalidation](card:cache-invalidation) why many teams prefer deleting.

## Rules and defaults

- **Redis Open Source loads nothing:** no command makes Redis read your database. Read-through needs a client library or an integration layer. For write-behind, Redis Software has a write-behind integration (in preview), or you write your own worker.
- **Pair write-through with lazy loading:** a new or restarted node has no data until each key is written again, so add cache-aside reads to fill the gaps (AWS ElastiCache guidance).
- **Write-through still needs a TTL:** most written data is never read, so a TTL removes copies nobody uses.
- **Write-behind and payments:** until the worker flushes, the cache holds the only copy of the change. Never use it for payment records or anything you cannot lose.
- **Refresh-ahead:** when an entry is read shortly before it expires, the cache layer reloads it in the background. It helps only if it predicts well which entries will be read again; wrong guesses cost database calls.

## Interview Qs

### Why pair write-through with lazy loading?

Write-through fills the cache only when data is written, so a new or restarted cache node lacks everything until each item is written again. Lazy loading fills those gaps on reads. A TTL then clears copies that nobody reads, which write-through alone would keep.

### When would you choose write-behind?

When writes are heavy, the database is the bottleneck, and losing or reordering the last few writes is acceptable, such as counters or analytics. The database write must also not fail later, because the caller was already told the write succeeded.

### Which strategy would you use for payment records?

Cache-aside, with the database written first and the cached copy deleted after the commit. The payment must be durable before the caller hears success, which rules out write-behind. Write-through is possible but adds a second write that can fail or arrive out of order.
