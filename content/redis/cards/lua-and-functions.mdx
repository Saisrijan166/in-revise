## What it is

A Lua script is a small program in the Lua language that your app sends to Redis to run on the server. Inside it, `redis.call` runs one Redis command and hands its reply back to the script. While the script runs, no other command runs, so the whole script is one atomic step. Unlike [MULTI/EXEC](card:transactions-multi-exec), it can decide its writes from a value it reads. Redis Functions (Redis 7.0+) work the same way, but the code is loaded into Redis once and called by name.

## Why it exists

"Mark payment 9001 PAID only if it is still PENDING, then add its amount to the merchant total" needs a read whose result decides the writes. MULTI/EXEC cannot use a read, and WATCH needs a retry loop, with more retries when many servers touch the same key. A script moves the read, the if and the writes into Redis, so they run in one call and one round trip, with no retries.

## How it works

| | EVAL | EVALSHA | FCALL |
|---|---|---|---|
| You send | the script text | its SHA1 digest | the function name |
| Code lives in | the request | script cache, lost on restart | the database, kept |
| Load it with | nothing | SCRIPT LOAD, or one EVAL | FUNCTION LOAD |
| Since | Redis 2.6 | Redis 2.6 | Redis 7.0 |

1. The app sends EVAL with the script, the number of keys, the key names and then the other arguments. Redis puts the key names in the `KEYS` table and the rest in `ARGV`.
2. Redis compiles the script and stores it in the script cache under its SHA1 digest, a fixed-length fingerprint of the script text.
3. Redis runs the script line by line. Each `redis.call` runs one command, and the next line can use its reply.
4. The script's return value goes back to the app as the reply. No other client's command ran in between.
5. Later calls send EVALSHA with only the digest. If the cache was emptied, Redis replies NOSCRIPT and the app sends EVAL again.

## Example

The payment service marks a payment as paid only while it is PENDING, and adds the amount to merchant 42's total in the same step:

```lua
-- mark_paid.lua: KEYS[1] = payment, KEYS[2] = merchant daily total, ARGV[1] = amount in paise
if redis.call('GET', KEYS[1]) ~= 'PENDING' then
  return 0                                   -- already PAID or FAILED: change nothing
end
redis.call('SET', KEYS[1], 'PAID')
return redis.call('INCRBY', KEYS[2], ARGV[1])
```

From Java, with [Spring Data Redis](card:spring-data-redis):

```java
RedisScript<Long> markPaid = RedisScript.of(new ClassPathResource("mark_paid.lua"), Long.class);
Long total = stringRedisTemplate.execute(markPaid,
        List.of("payment:9001", "merchant:42:paise:2026-10-21"), "50000");
System.out.println(total);
```

```text output
50000
```

What to notice:

- The if uses the reply of the GET to choose the writes. A second call returns 0, because the payment is no longer PENDING.
- Both key names go in the key list, and the amount in `ARGV`. Never build a key name inside the script.
- `execute` sends EVALSHA first and falls back to EVAL when Redis replies NOSCRIPT. Create the `RedisScript` once, as a bean, so its SHA1 is not computed on every call.

## Rules and defaults

- **Keys must be declared:** the script should touch only keys passed in `KEYS`. In [Redis Cluster](card:redis-cluster) they must all be in one hash slot.
- **Busy script:** Redis never stops a running script. After `busy-reply-threshold` (5000 ms by default in Redis 8.10; old name `lua-time-limit`), other clients get BUSY errors. `SCRIPT KILL` stops the script only if it has not written yet; otherwise only `SHUTDOWN NOSAVE` ends it, losing unsaved data.
- **Script cache:** it is not persisted. A restart, a failover to a replica or `SCRIPT FLUSH` empties it, and EVALSHA then replies NOSCRIPT.
- **Errors:** an error from `redis.call` stops the script and goes to the client; `redis.pcall` returns the error to the script to handle.
- **Functions:** they are saved in the AOF file and copied to replicas with the data. In Redis Cluster you must load them on every primary yourself.

## Not to be confused with

An EVAL script belongs to the app: the app keeps the code and sends it, or its digest, and the script cache can lose it at any time. A Redis Function belongs to the database: you load a library once with FUNCTION LOAD, call each function by name with FCALL, and Redis keeps it across restarts and on replicas. Rule: script = code the app sends; function = code Redis keeps.

## Common mistakes

- **"If the script fails halfway, Redis undoes its earlier writes."** It does not. If the script writes a key and the next `redis.call` fails, the first write stays. Check inputs before the first write.

## Interview Qs

### When do you choose a Lua script over MULTI/EXEC?

When a later command depends on an earlier reply, such as "mark PAID only if still PENDING". MULTI/EXEC cannot branch, and WATCH needs a retry loop. A script reads, decides and writes in one atomic step and one round trip.

### EVALSHA returns NOSCRIPT. Why, and what do you do?

The script cache lives in memory only. A restart, a failover or SCRIPT FLUSH empties it, so the digest is unknown. Load the script again with SCRIPT LOAD, or send it with EVAL, and retry. Spring's RedisTemplate falls back to EVAL for you.

### Why must every key name be passed in KEYS?

Redis reads the key arguments to know which keys a script touches. In a cluster, the client uses them to send the call to the node that owns those keys, and Redis rejects declared keys from different slots. A key name built inside the script may belong to another node, and the call then fails.
