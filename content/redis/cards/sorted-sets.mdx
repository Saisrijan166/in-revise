## Why it exists

A leaderboard in SQL means ORDER BY on every read. A sorted set keeps members in score order as they change, so "top 3" and "my rank" are cheap.

## How it works

Merchants ranked by payment volume today (key `rank:merchants:2026-10-20`):

| Member | Score | ZREVRANK (0 = top) |
|---|---|---|
| merchant:42 | 98000 | 0 |
| merchant:8 | 75500 | 1 |
| merchant:17 | 75500 | 2 |

- Equal scores sort by member name as bytes ("merchant:17" before "merchant:8"); REV flips that too.
- Sliding-window limits use a sorted set too: [rate limiting](card:rate-limiting-with-redis); delayed jobs: [queues](card:queues-with-redis).

## Example

```text
ZINCRBY rank:merchants:2026-10-20 500 merchant:42   -- "98500"
ZRANGE rank:merchants:2026-10-20 0 2 REV WITHSCORES -- top 3 with scores
ZREVRANK rank:merchants:2026-10-20 merchant:17      -- 2
ZRANGE rank:merchants:2026-10-20 50000 +inf BYSCORE -- score 50000 and up
```

## Interview Qs

### How would you build a real-time leaderboard?

One sorted set per board. ZINCRBY the member's score on each event; read the top N with ZRANGE ... REV WITHSCORES and a user's place with ZREVRANK. Each update is O(log n).

### Why is a sorted set fast for both updates and ranges?

It keeps a hash table for member-to-score lookups and a skip list kept in score order. An update repositions one member in O(log n); a range read walks the already ordered list.
