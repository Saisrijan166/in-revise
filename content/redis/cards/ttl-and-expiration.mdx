## Why it exists

Cached copies go stale and short-lived state piles up. A TTL lets Redis remove them by itself, with no cleanup job.

## How it works

| Command | Effect on the TTL |
|---|---|
| `SET k v EX 300` / `PX 300000` | Value plus TTL in seconds / ms |
| `EXPIRE k 300` / `PEXPIRE` / `EXPIREAT` | Adds or changes the TTL |
| `PERSIST k` | Removes the TTL |
| `SET k v` (no option) | Drops the old TTL |
| `SET k v KEEPTTL` | Keeps the old TTL (Redis 6.0+) |
| `INCR`, `HSET`, `LPUSH` | Change the value, keep the TTL |

- Keys leave by [lazy expiry](card:ttl-lazy-expiry) or [active expiry](card:ttl-active-expiry); replicas wait for the primary's DEL.
- Pick the TTL per data: minutes for payment status, hours for merchant config.
- Fields inside a hash can have their own TTL: see [hashes](card:hashes).

## Example

```text
SET payment:PAY101 PENDING EX 300    -- status lives 5 minutes
TTL payment:PAY101                   -> 300
SET payment:PAY101 PAID KEEPTTL      -- update, keep the timer
TTL payment:PAY101                   -> 291
SET payment:PAY101 PAID              -- plain SET: timer dropped
TTL payment:PAY101                   -> -1
```

## Interview Qs

### How does Redis remove expired keys?

Lazily: a command that touches an expired key deletes it and gets nothing. Actively: a background cycle samples keys with a TTL and deletes expired ones, so unread keys are freed too.

### I updated a cached value and now it never expires. Why?

A plain SET replaces the key and discards its TTL. Pass EX again or use KEEPTTL. Commands that only change the value, like INCR or HSET, keep the TTL.
