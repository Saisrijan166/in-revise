## What it is

A TTL, short for time to live, is a timer you attach to a key. When the timer runs out, the key expires: Redis treats it as gone and deletes it. A key without a TTL lives until something deletes it. You set the timer with the `EX` option of `SET`, or with `EXPIRE` on a key that already exists.

## Why it exists

Cached copies go stale, and short-lived state, such as a payment status or a login attempt counter, piles up. Without a TTL you would need a cleanup job that finds and deletes old keys, and it would miss some. With a TTL, each key carries its own end time, so old copies disappear by themselves and their memory is freed.

## How it works

<Mermaid
  alt="A key is stored with an expiry time. Before that time, reads return the value. After it, two paths delete the key: a command that touches it deletes it and gets nothing back, and a background cycle that samples keys with a TTL deletes the expired ones it finds."
  chart={`flowchart LR
  S["SET ... EX 300"] --> K[Key + expiry time]
  K -- "read before expiry" --> V([Value returned])
  K -- "read after expiry" --> L[Deleted on access, reply nil]
  K -- "never read again" --> A[Background cycle finds and deletes it]`}
/>

1. `SET payment:9001 ... EX 300` stores the value and an expiry time: now plus 300 seconds, saved as an absolute Unix time.
2. Until then, reads return the value, and `TTL payment:9001` reports the seconds left.
3. After that time, the first command that touches the key sees that it expired, deletes it and answers as if it never existed. This is lazy expiry.
4. Keys that nobody touches are found by active expiry: several times a second, Redis samples some keys that have a TTL and deletes the expired ones.
5. Replicas, the copies of a primary server that you will meet in [replication](card:replication), do not delete expired keys on their own. The primary sends them a `DEL` for each expired key.

So the key is: clients never read an expired key, but the moment it is actually deleted is not fixed.

## Example

The payment service caches the status of payment 9001 for 5 minutes, then updates it twice.

```bash
redis-cli SET payment:9001 '{"status":"PENDING"}' EX 300
redis-cli TTL payment:9001
redis-cli SET payment:9001 '{"status":"PAID"}' KEEPTTL
redis-cli TTL payment:9001
redis-cli SET payment:9001 '{"status":"PAID"}'
redis-cli TTL payment:9001
redis-cli TTL payment:9999
```

```text output
OK
(integer) 300
OK
(integer) 299
OK
(integer) -1
(integer) -2
```

What to notice:

- `TTL` counts down: 300 seconds, then 299 a moment later.
- `KEEPTTL` replaces the value but keeps the running timer.
- The plain `SET` replaced the key and its timer, so `TTL` now returns `-1`: the key will never expire. This is the most common TTL bug.
- `-2` means there is no key `payment:9999` at all.

## Rules and defaults

- **Removes the TTL:** `SET` without `EX`, `PX` or `KEEPTTL`, `GETSET`, `DEL`, the `*STORE` commands, and `PERSIST`.
- **Keeps the TTL:** commands that change the value in place, such as `INCR`, `LPUSH` and `HSET`. `RENAME` moves the TTL to the new name.
- **Conditional EXPIRE (Redis 7.0+):** `NX` sets a TTL only if there is none, `XX` only if there is one, `GT` only if longer, `LT` only if shorter.
- **Zero or negative:** `EXPIRE key 0` deletes the key at once.
- **Accuracy:** an expired key stops being returned within 0 to 1 ms (since Redis 2.6).
- **Clock:** the expiry is an absolute time, so it keeps running while Redis is stopped, and moving the server clock forward expires keys early.
- **Hash fields:** fields inside a hash can have their own TTL; see [hashes](card:hashes).

## Not to be confused with

A TTL is your own timer on one key: the key goes when its time runs out. Eviction is Redis deleting keys because memory reached its limit, whatever their timers say; you will see it in [eviction policies](card:eviction-policies). Rule: TTL is freshness you choose; eviction is a safety net for memory.

## Common mistakes

- **Setting the TTL in a second command.** `SET` followed by `EXPIRE` leaves a key with no TTL if the app crashes in between. Use `SET ... EX` in one command.
- **The same TTL for many keys loaded together.** They all expire at the same moment and send a burst of reads to the database; [cache problems](card:cache-problems) shows the fix.

## Interview Qs

### How does Redis remove expired keys?

In two ways. Lazily: a command that touches an expired key deletes it and gets nothing back. Actively: a background cycle samples keys that have a TTL and deletes the expired ones, so keys that nobody reads are freed too.

### I updated a cached value and now it never expires. Why?

A plain SET replaces the key and discards its TTL, so TTL returns -1. Pass EX again or use KEEPTTL. Commands that only change the value in place, such as INCR or HSET, keep the TTL.

### Do replicas expire keys themselves?

No. To stay consistent, the primary turns each expiry into a DEL and sends it to its replicas and to the append-only file (AOF), its log on disk. Replicas still keep the expiry times, so a replica promoted to primary starts expiring keys on its own.
