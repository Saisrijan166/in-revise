## Why it exists

Counting unique users with a set costs memory for every member. When you only need yes/no per ID, or an approximate count, these tools use a tiny fraction of that.

## How it works

| Tool | Answers | Exact? | Memory |
|---|---|---|---|
| Bitmap | "Was user 7 active today?" "How many were?" | yes | 1 bit per ID up to the highest ID |
| Bitfield | "Retries for slot 3?" (many small counters) | yes | the bits you choose per counter |
| HyperLogLog | "About how many unique payers?" | no | at most 12 KB per counter |

- A Bloom filter answers "seen before?" approximately: [Bloom filter](card:json-and-query-engine).

## Example

```text
SETBIT active:2026-10-20 7 1         -- user 7 was active
GETBIT active:2026-10-20 7           -- 1
BITCOUNT active:2026-10-20           -- users active today
BITFIELD retries:42 INCRBY u8 0 1    -- 8-bit counter at bit 0, now 1
PFADD payers:2026-10-20 user:7 user:9 user:7   -- 1
PFCOUNT payers:2026-10-20            -- 2 (an estimate)
```

## Defaults

| What | Default | Where |
|---|---|---|
| BITFIELD overflow | WRAP (also SAT, FAIL) | Redis Open Source 8.10 |

## Interview Qs

### How do you find users active on each of the last 7 days?

Keep one bitmap per day. BITOP AND the seven keys into a new key, then BITCOUNT it: bit n is 1 only if user n was active on all seven days.

### Why is HyperLogLog so small?

It keeps only a small fixed-size state about what it has seen, never the items. That caps it at 12 KB but makes the count approximate, and you cannot list the members.
