## What it is

These are three space-saving tools built on [strings](card:strings). A bitmap is not a separate type: it is a string that bit commands treat as a long row of bits, where bit number 7 can mean "user 7 was active today". A bitfield packs many small integers, such as 8-bit retry counters, into one string. A HyperLogLog is a probabilistic structure: it estimates how many distinct items you added, using at most 12 KB, without storing the items.

## Why it exists

Counting unique payers with a [set](card:sets) stores every member, so memory grows with every user. Often you need less: one yes/no per user id, or only "about how many?". A bitmap needs one bit per id, so a million ids fit in about 125 KB. A HyperLogLog stays at most 12 KB whether it has seen a thousand items or a billion.

## How it works

| Tool | Answers | Exact? | Memory |
|---|---|---|---|
| Bitmap | "Was user 7 active today?" "How many were?" | yes | 1 bit per id, up to the highest id set |
| Bitfield | "How many retries for slot 3?" | yes | the bits you choose per counter |
| HyperLogLog | "About how many unique payers today?" | no, about 0.81% error | at most 12 KB per counter |

1. A bitmap starts empty. `SETBIT key 7 1` grows the string to cover bit 7 and turns it on.
2. `GETBIT key n` returns that bit; a bit you never set reads as 0. `BITCOUNT key` counts the bits that are 1.
3. A HyperLogLog takes items with `PFADD`. It hashes each item and keeps only a small summary of the hashes, never the item.
4. `PFCOUNT` turns that summary into an estimate of how many distinct items were added. Adding the same item again does not change it.

## Example

The payment service marks users 7 and 9 as active today, counts distinct payers, and counts a retry for merchant 42.

```bash
redis-cli SETBIT active:2026-10-21 7 1
redis-cli SETBIT active:2026-10-21 9 1
redis-cli GETBIT active:2026-10-21 8
redis-cli BITCOUNT active:2026-10-21
redis-cli PFADD payers:2026-10-21 user:7 user:9 user:7
redis-cli PFCOUNT payers:2026-10-21
redis-cli BITFIELD retries:merchant:42 INCRBY u8 0 1
```

```text output
(integer) 0
(integer) 0
(integer) 0
(integer) 2
(integer) 1
(integer) 2
1) (integer) 1
```

What to notice:

- `SETBIT` returns the bit's old value, 0 here. User 8 was never set, so `GETBIT` returns 0.
- `BITCOUNT` returned 2, exact. The whole bitmap is only 2 bytes because the highest bit set is 9.
- `PFADD` returned 1 because the estimate changed; `user:7` twice still counts once, so `PFCOUNT` says 2.
- `BITFIELD ... INCRBY u8 0 1` treats bits 0 to 7 as an unsigned 8-bit counter and adds 1.

## Rules and defaults

- **Bitmap limit:** a string is at most 512 MB, so a bitmap holds up to 2^32 bits. Setting a very high bit allocates memory for every bit below it.
- **Combine days:** `BITOP AND|OR|XOR|NOT` combines bitmaps into a new key, for example users active on every one of 7 days.
- **HyperLogLog:** at most 12 KB, far less while it has seen few items; standard error 0.81%. `PFMERGE` joins several into one. It is stored as a string, so `GET` and `SET` can copy it.
- **BITFIELD overflow:** `WRAP` by default (Redis Open Source 8.10); `SAT` stops at the limit, `FAIL` refuses the change.

## Not to be confused with

A HyperLogLog answers "how many distinct items?". A Bloom filter, part of [JSON, Search and other Redis 8 types](card:json-and-query-engine), answers "have I seen this item?". Both are small and approximate, but neither lists the items. Rule: count = HyperLogLog; membership = Bloom filter; exact members = set.

## Interview Qs

### How do you find users active on each of the last 7 days?

Keep one bitmap per day, with bit n for user n. BITOP AND the seven keys into a new key, then BITCOUNT it. Bit n is 1 only if user n was active on all seven days.

### Why is HyperLogLog so small?

It never stores the items. It hashes each one and keeps a fixed-size summary of patterns in the hashes, which caps it at 12 KB. The price is an approximate count, about 0.81% standard error, and you cannot list the members.

### When is a bitmap a bad idea?

When ids are sparse or huge. A bitmap grows to the highest bit set, so one user with id 4,000,000,000 makes the string about 500 MB even if only two bits are on. Use a set or a HyperLogLog then.
