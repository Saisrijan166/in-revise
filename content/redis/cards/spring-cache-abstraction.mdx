## What it is

Spring's cache abstraction adds [cache-aside](card:cache-aside) to a Java method through annotations instead of hand-written Redis code. You put `@Cacheable` on a method, and Spring wraps the bean in a proxy: an object that sits in front of the bean and receives calls from other beans. The proxy checks the cache before the method runs and stores the result after. When Redis is available and configured, Spring Boot keeps these entries in Redis through a `RedisCacheManager`.

## Why it exists

Hand-written cache-aside repeats the same steps in every service method: build the key, `GET`, check for null, load, `SET` with a TTL, and delete on writes. Each copy is a chance to forget the TTL or build a wrong key. With annotations, the caching rule is one line on the method, and the same code runs against Redis, an in-memory cache, or no cache at all in tests (`spring.cache.type=none`).

## How it works

1. At startup, `@EnableCaching` turns the cache proxies on, and Spring Boot creates a `RedisCacheManager` because Redis is configured.
2. Another bean calls `find("9001")`. The proxy builds the key from the cache name `payments` and the argument, giving the Redis key `payments::9001`.
3. On a hit, the proxy returns the cached value, and the method body does not run.
4. On a miss, the method runs, and the proxy stores its result in Redis with the configured TTL before returning it.
5. When another bean calls `refund("9001")`, marked `@CacheEvict`, the method runs first. Only after it returns normally does the proxy delete `payments::9001`.

So the key is: the proxy does the caching, so only calls that pass through it are cached.

## Example

`PaymentQueryService` caches payment lookups and evicts the entry when a payment is refunded.

```java
@Configuration
@EnableCaching
class CacheConfig { }

@Service
class PaymentQueryService {
    private final PaymentRepository repo;
    PaymentQueryService(PaymentRepository repo) { this.repo = repo; }

    @Cacheable(cacheNames = "payments", key = "#id", unless = "#result == null")
    public PaymentView find(String id) { return repo.load(id); }   // Redis key payments::9001

    @CacheEvict(cacheNames = "payments", key = "#id")
    public void refund(String id) { repo.refund(id); }
}
```

```properties
spring.cache.redis.time-to-live=10m
```

What to notice:

- `key = "#id"` uses the method argument. With exactly one argument, that is also the default key.
- Calling `find("9001")` twice from another bean runs `repo.load` once; the second call is a hit. Removing `@EnableCaching` makes the annotations do nothing, with no error.
- `unless = "#result == null"` skips storing a missing payment. Without it, Boot caches a null marker that never expires unless you set a TTL.
- Boot stores values with Java serialisation by default, so `PaymentView` must implement `Serializable`; otherwise storing it fails.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Entry TTL | never expires | `spring.cache.redis.time-to-live`, Spring Boot 4.1 |
| Cache `null` results | yes | `spring.cache.redis.cache-null-values`, Spring Boot 4.1 |
| Key prefix | the cache name plus `::` | `spring.cache.redis.use-key-prefix`, Spring Boot 4.1 |
| Value format | Java serialisation | Boot's auto-configured cache, Spring Boot 4.1 |
| After-commit evicts | off | `RedisCacheManager` builder, Spring Data Redis 4.1 |

- **Where @EnableCaching goes:** on one of your `@Configuration` classes. The Spring Boot docs advise against the main application class, because that makes caching mandatory, including in every test.
- **Per-cache TTL:** register a `RedisCacheManagerBuilderCustomizer` bean and call `withCacheConfiguration("payments", RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ofMinutes(5)))`.
- **JSON values:** define your own `RedisCacheConfiguration` bean with a JSON serialiser; Boot then uses it instead of its default.
- **sync = true:** the default Redis cache writer takes no lock. The opt-in locking writer (`RedisCacheWriter.lockingRedisCacheWriter`) locks the whole cache, not one entry.
- **Null not allowed:** with `cache-null-values=false`, a method that returns null makes the cache throw an error; add `unless = "#result == null"`.

## Not to be confused with

`@Cacheable` skips the method on a hit and caches the result on a miss. `@CachePut` always runs the method and then overwrites the entry with its result. `@CacheEvict` runs the method and then deletes the entry, or all entries with `allEntries = true`. Rule: `@Cacheable` for reads, `@CachePut` for writes that return the new object, `@CacheEvict` for writes that do not.

## Interview Qs

### How do you give each cache its own TTL?

Register a `RedisCacheManagerBuilderCustomizer` bean and call `withCacheConfiguration` for each cache name, passing a `RedisCacheConfiguration` with its own `entryTtl`. `spring.cache.redis.time-to-live` sets one default TTL for all caches.

### Does @CacheEvict run before or after the method?

After the method completes successfully, so a failed refund keeps the entry. With `beforeInvocation = true` the entry is evicted before the method runs, even if the method then throws. `allEntries = true` clears the whole cache.

### Why does @Cacheable not work when the method is called from the same class?

Caching happens in a proxy that wraps the bean. A call like `this.find(id)` goes straight to the method and skips the proxy, so nothing is checked or stored. Move the cached method to another bean, or call it through the bean from outside.
