## What it is

Redis Cluster is Redis's built-in sharding: the keys are split across several primaries, so each primary holds only part of the data. Every key belongs to one of 16384 hash slots, and each primary owns a range of slots. Each primary can have [replicas](card:replication), and the cluster itself promotes a replica when a primary fails, so no Sentinel is needed.

## Why it exists

With [Sentinel](card:sentinel), every key and every write still live on one primary, so its RAM and its one main thread set the limit. If the merchant data outgrows one server's memory, more replicas do not help, because each replica holds the same full copy. Cluster spreads the slots over several primaries, so adding a primary adds both memory and write capacity.

## How it works

/>

1. The client computes the key's slot: the CRC16 checksum of the key, mod 16384. `payment:9001` is slot 6906, which primary B owns.
2. It sends the command straight to B, using a map of slot owners that it fetched from the cluster.
3. If the map is old and the command reaches the wrong node, that node does not forward it. It replies `MOVED 6906 <host:port>`, and the client updates its map and retries there.
4. While a slot is being moved to another node, called resharding, the old owner may reply `ASK`. The client sends just that command to the new node, after an `ASKING` command, and keeps its map.
5. If the majority of primaries cannot reach B for `cluster-node-timeout`, B's replica is elected and takes over its slots.

So the key rule is that one command, transaction or script may only use keys from one slot.

## Example

This runs on a real three-primary cluster. `-c` tells redis-cli to follow redirects as a cluster client does.

```bash
redis-cli -c CLUSTER KEYSLOT payment:9001
redis-cli -c SET payment:9001 PAID
redis-cli GET payment:9001                 # no -c: redis-cli does not follow redirects
redis-cli -c MSET merchant:42:config A merchant:42:limits B
redis-cli -c MSET {merchant:42}:config A {merchant:42}:limits B
redis-cli -c SELECT 1
```

```text output
(integer) 6906
OK
(error) MOVED 6906 172.20.0.3:6379
(error) CROSSSLOT Keys in request don't hash to the same slot
OK
(error) ERR SELECT is not allowed in cluster mode
```

What to notice:

- `SET` with `-c` printed OK because redis-cli followed the redirect to slot 6906's owner. Without `-c`, the same node only answered `MOVED` with the owner's address.
- The first `MSET` fails because its two keys are in different slots. With the hash tag `{merchant:42}`, only `merchant:42` is hashed, so both keys are in slot 7650.
- `SELECT` fails: Cluster has only database 0.

## Rules and defaults

- **Size:** at least 3 primaries. The docs recommend 6 nodes: 3 primaries and 3 replicas.
- **Ports:** each node needs its data port and a cluster bus port for node-to-node messages, by default the data port + 10000 (16379).
- **Failure timeout (Redis 8.10):** `cluster-node-timeout` is 15000 ms by default.
- **Adding a node:** add it empty, then move some slots to it with `redis-cli --cluster reshard`. The keys move with their slots, and clients keep working.
- **Hash tags:** only the text between the first `{` and the next `}` is hashed, and only if that text is not empty. Tag only keys that must be used together, because every key with one tag lands in one slot, on one node.
- **Spring Boot 4.1:** `spring.data.redis.cluster.nodes` lists a few seed nodes, and the client discovers the rest. `spring.data.redis.cluster.max-redirects` limits how many redirects it follows.

## Not to be confused with

Consistent hashing places keys and nodes on a ring, and a new node takes over part of the ring. Redis Cluster instead has a fixed set of 16384 slots, and a new node is given whole slots. [Sentinel](card:sentinel) only adds failover to one primary that holds all the data. Rule: Sentinel = failover; Cluster = sharding plus failover.

## Common mistakes

- **"MULTI/EXEC or a Lua script can update any keys in Cluster."** They work only if all keys are in one slot; otherwise the cluster rejects them with CROSSSLOT. Give the keys one hash tag, such as `{payment:9001}:status` and `{payment:9001}:events`.

## Interview Qs

### How do you update two keys atomically in Redis Cluster?

Put them in the same slot with a hash tag, for example `{payment:9001}:status` and `{payment:9001}:events`. Both keys hash only `payment:9001`, so they land on one node, and `MULTI`/`EXEC` or a Lua script can use them together. Keys in different slots fail with CROSSSLOT.

### What is the difference between MOVED and ASK?

MOVED means the slot now lives on another node for good: the client updates its slot map and sends future commands there. ASK appears only while a slot is being moved: the client sends just that one command to the named node, after `ASKING`, and keeps its map.

### When do you need Cluster instead of Sentinel?

When one primary can no longer hold all the data in RAM or handle all the writes. Sentinel only adds failover; Cluster also spreads data and writes across primaries. The price is the one-slot rule for multi-key commands and database 0 only.
