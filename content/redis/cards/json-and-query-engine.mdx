## Why it exists

Core Redis finds data only by key. Real apps also ask "all UPI payments between ₹400 and ₹600", and want nested objects. Redis 8 answers these without a second database.

## How it works

<Mermaid
  alt="The app writes payment documents as JSON keys with the prefix payment. FT.CREATE defines an index over that prefix with amount as a numeric field and method as a tag. Redis Search updates the index on every write. FT.SEARCH queries the index by field values and returns matching keys."
  chart={`flowchart LR
  A[App] -- JSON.SET --> D[("payment:* JSON docs")]
  D -- indexed on write --> I["FT.CREATE index"]
  A -- FT.SEARCH --> I
  I -- matching keys --> A`}
/>

- The engine was named Redis Query Engine in the 8.0 release notes; the docs now call it Redis Search.
- Bloom filter as the fix for cache penetration: [cache problems](card:cache-problems).

## Example

```text
JSON.SET payment:PAY101 $ '{"amount":500,"method":"UPI","customer":{"id":7}}'  -- OK
JSON.GET payment:PAY101 $.customer.id       -- "[7]"
JSON.NUMINCRBY payment:PAY101 $.amount 50   -- "[550]"
FT.CREATE idx:pay ON JSON PREFIX 1 payment: SCHEMA $.amount AS amount NUMERIC $.method AS method TAG
FT.SEARCH idx:pay "@method:{UPI} @amount:[400 600]"   -- finds payment:PAY101
```

## Interview Qs

### Can Redis query by a field value, not only by key?

Yes, with Redis Search, built into Redis 8: FT.CREATE indexes hashes or JSON documents under a key prefix, and FT.SEARCH filters by numbers, tags, text, location or vectors. Plain Redis has key access only.

### What does a Bloom filter guarantee?

A "no" is certain: the item was never added. A "yes" may be a false positive. It uses little, fixed memory because it stores hashed bits, not the items.
