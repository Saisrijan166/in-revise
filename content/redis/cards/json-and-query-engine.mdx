## What it is

Redis 8 adds several types beyond the core ones. A JSON document is a key that holds a nested JSON value, and a path such as `$.customer.id` reads or changes one part of it. Redis Search builds a secondary index, a lookup by field value rather than by key name, over hashes or JSON documents. Redis 8 also includes time series and probabilistic types such as the Bloom filter, which uses little memory but may answer "probably yes" wrongly.

## Why it exists

Core Redis finds data only by key: you must already know `payment:9001`. Support staff ask instead "all UPI payments between ₹400 and ₹600", and a [hash](card:hashes) cannot hold the payment's nested customer object. Without these types you would copy the data into a second database just to query it. Since Redis 8.0 they come with Redis Open Source, so the same server stores the documents and answers the query.

## How it works

<Mermaid
  alt="The app writes payment documents as JSON keys with the prefix payment. FT.CREATE defines an index over that prefix with amount as a numeric field and method as a tag. Redis Search updates the index on every write. FT.SEARCH queries the index by field values and returns matching keys."
  chart={`flowchart LR
  A[App] -- JSON.SET --> D[("payment:* JSON docs")]
  D -- indexed on write --> I["FT.CREATE index"]
  A -- FT.SEARCH --> I
  I -- matching keys --> A`}
/>

1. The app writes each payment with `JSON.SET payment:<id> $ '{...}'`.
2. Once, `FT.CREATE` defines an index: which key prefix to watch, and which paths to index as numbers, tags or text.
3. Redis Search indexes the existing keys with that prefix, then updates the index on every later write.
4. `FT.SEARCH` runs a query on the index and returns the matching keys, without scanning the whole keyspace.

## Example

The payment service stores payment 9001 as JSON, queries it by field, and checks a Bloom filter of seen payment ids.

```bash
redis-cli JSON.SET payment:9001 '$' '{"amount":500,"method":"UPI","customer":{"id":7}}'
redis-cli JSON.GET payment:9001 '$.customer.id'
redis-cli JSON.NUMINCRBY payment:9001 '$.amount' 50
redis-cli FT.CREATE idx:payments ON JSON PREFIX 1 payment: SCHEMA '$.amount' AS amount NUMERIC '$.method' AS method TAG
redis-cli FT.SEARCH idx:payments '@method:{UPI} @amount:[400 600]' NOCONTENT
redis-cli BF.ADD seen:payment-ids 9001
redis-cli BF.EXISTS seen:payment-ids 9002
```

```text output
OK
"[7]"
"[550]"
OK
1) (integer) 1
2) "payment:9001"
(integer) 1
(integer) 0
```

What to notice:

- `JSON.GET` with `$.customer.id` read one nested value, and `JSON.NUMINCRBY` changed the amount in place. Results come back as arrays, because a `$` path can match several places.
- `FT.SEARCH` found `payment:9001` (amount 550, method UPI): 1 match. `NOCONTENT` returns only key names, not documents.
- `BF.EXISTS` returned 0 for 9002, which is certain: 9002 was never added. A 1 would only mean "probably".

## Rules and defaults

- **Since Redis 8.0:** Redis Stack and Redis Community Edition were merged into one distribution, Redis Open Source, with JSON, Redis Search, time series and the probabilistic types built in.
- **Probabilistic types:** Bloom filter and Cuckoo filter (membership), Count-min sketch (frequency), Top-K (most frequent items) and t-digest (percentiles).
- **Naming:** the 8.0 release notes call the engine the Redis Query Engine; the docs now call it Redis Search.
- **Vector sets:** added in Redis 8.0, where the release notes marked them as a beta.
- **Arrays (Redis 8.8+, preview):** a sparse sequence of strings addressed by integer index, for ring buffers and event logs. The docs say the type may still change.

## Not to be confused with

A Bloom filter and a [HyperLogLog](card:bitmaps-hyperloglog) are both small and approximate, but they answer different questions; that concept gives the rule. A JSON document is not a [hash](card:hashes): a hash holds flat string fields, while JSON holds nested objects, arrays and numbers. Rule: flat object = hash; nested object = JSON.

## Interview Qs

### Can Redis query by a field value, not only by key?

Yes, with Redis Search, built into Redis 8. FT.CREATE indexes hashes or JSON documents under a key prefix, and FT.SEARCH filters by numbers, tags, text, location or vectors. Without an index, Redis only finds data by key name.

### What does a Bloom filter guarantee?

A "no" is certain: the item was never added. A "yes" may be a false positive. It uses little memory because it keeps hashed bits, not the items, so you cannot list or delete what you added. It is a common guard against lookups for ids that do not exist.

### When would you store an object as JSON instead of a hash?

When it is nested, like a payment with a customer object and a list of attempts, or when you need to change one part by path. A hash is flat and uses less memory, so it fits flat objects.
