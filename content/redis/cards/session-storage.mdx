## Why it exists

A session kept in one server's memory works only on that server. With many servers behind a load balancer, every server must read the same sessions.

## How it works

<Mermaid
  alt="A load balancer sends the user to app server 1 or 2. Both read and write the same session hash in Redis."
  chart={`flowchart LR
  U([User, session cookie]) --> LB[Load balancer]
  LB --> A1[App server 1]
  LB --> A2[App server 2]
  A1 <--> R[(Redis: one hash per session)]
  A2 <--> R`}
/>

- Spring Session stores the hash as spring:session:sessions:id, with fields such as lastAccessedTime and sessionAttr:userId.
- Each save sets the key to expire at last access plus the idle timeout.

## Example

```properties
# dependency: spring-boot-starter-session-data-redis (Spring Boot 4.1)
spring.data.redis.host=redis.internal
spring.session.timeout=15m
spring.session.data.redis.namespace=pay:session
```

## Defaults

| What | Default | Where |
|---|---|---|
| Session idle timeout | 30m, via server.servlet.session.timeout | Spring Boot 4.1 |
| Key namespace | spring:session | Spring Session 4.1 |
| Repository type | default (not indexed) | Spring Boot 4.1, spring.session.data.redis.repository-type |

## Interview Qs

### How do you share sessions across many instances?

Store them outside the app, in Redis. With Spring Boot, add the Spring Session Data Redis starter: HttpSession reads and writes go to Redis, and any instance can serve the user.

### What happens to sessions if Redis goes down?

Session lookups fail, so those requests fail too; if Redis loses its data, every user must sign in again. Run Redis with a replica and failover, and decide the fallback in advance: see [failure handling](card:redis-failure-handling).
