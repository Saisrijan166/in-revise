## What it is

A session is what a server remembers about a user between requests, such as "this browser is signed in as user 7". The browser keeps only the session id, in a cookie; the data stays on the server side. A shared session store keeps that data in Redis instead of in one app server's memory. Each session becomes a [hash](card:hashes) with a [TTL](card:ttl-and-expiration) equal to the idle timeout.

## Why it exists

The payment service runs on two app servers behind a load balancer. If sessions live in each server's memory, a user who signed in on server 1 looks signed out when the next request reaches server 2. A restart or deploy also wipes every session on that server. With sessions in Redis, every server reads the same data, so any server can serve any request and a restart logs no one out.

## How it works

<Mermaid
  alt="A user's browser sends its session cookie to a load balancer, which sends the request to app server 1 or app server 2. Both servers read and write the same session hash in Redis."
  chart={`flowchart LR
  U([Browser, SESSION cookie]) --> LB[Load balancer]
  LB --> A1[App server 1]
  LB --> A2[App server 2]
  A1 <--> R[(Redis: one hash per session)]
  A2 <--> R`}
/>

1. The user signs in, and Spring Session creates a session with a random id and sends it to the browser in a cookie named `SESSION`.
2. It saves the session as a hash at `spring:session:sessions:<id>`, with fields such as `creationTime`, `lastAccessedTime`, `maxInactiveInterval` and one `sessionAttr:<name>` field per attribute.
3. On the next request, whichever server receives it reads the id from the cookie and loads the hash from Redis.
4. When the request ends, Spring Session saves the changes and sets the key to expire at the last access time plus the idle timeout.
5. If no request comes within the idle timeout, Redis expires the key and the session is gone.

Spring Session does this with a servlet filter that wraps each request, so `HttpSession` calls go to Redis while your code stays the same.

## Example

The payment service turns on Redis sessions with one dependency and a few properties; the login code uses a plain `HttpSession`.

```properties
# dependency: spring-boot-starter-session-data-redis (Spring Boot 4.1)
spring.data.redis.host=redis.internal
spring.session.timeout=15m
```

```java
@RestController
public class LoginController {

    @PostMapping("/login")
    public String login(@RequestParam long userId, HttpSession session) {
        // after the password check passes:
        session.setAttribute("userId", userId);   // Spring Session writes it to Redis
        return "logged in";
    }

    @GetMapping("/me")
    public Object me(HttpSession session) {
        return session.getAttribute("userId");    // works on any app server
    }
}
```

What to notice:

- Nothing in the controller mentions Redis. Remove the starter and the same code keeps sessions in server memory again.
- `setAttribute("userId", ...)` becomes the hash field `sessionAttr:userId`.
- With `spring.session.timeout=15m`, a user who sends no request for 15 minutes is signed out. Without it, Boot uses `server.servlet.session.timeout`, which defaults to 30 minutes.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Idle timeout | `server.servlet.session.timeout`, 30m | Spring Boot 4.1 |
| Key namespace | `spring:session` (`spring.session.data.redis.namespace`) | Spring Boot 4.1 |
| Repository type | `default` (`spring.session.data.redis.repository-type`) | Spring Boot 4.1 |
| Cookie name | `SESSION` | Spring Session 4.1 |

- **Indexed repository:** set `repository-type` to `indexed` when you need to find all sessions of one user or listen for session events, such as expiry. The default repository looks a session up only by its id.
- **Several apps on one Redis:** give each its own namespace, so their session keys do not clash.
- **What to store:** small values such as a user id. Keep sensitive data, such as card numbers, out of the session.

## Not to be confused with

Sticky sessions make the load balancer send a user to the same server every time, so the session can stay in that server's memory. A shared session store lets any server handle any request. Rule: sticky sessions hide the problem; a shared store removes it.

## Interview Qs

### How do you share sessions across many instances?

Store them outside the app, in Redis. With Spring Boot, add the Spring Session Data Redis starter: `HttpSession` reads and writes go to Redis, and any instance can serve the user. Each session is one hash, and its TTL is the idle timeout.

### What happens to sessions if Redis goes down?

Requests that need the session fail while Redis is unreachable, and if Redis loses its data, every user must sign in again. Run Redis with a replica and automatic failover, and decide the fallback in advance; you will see how in [When Redis Is Slow or Down](card:redis-failure-handling).

### Why not use sticky sessions?

A user's session then lives on one server. If that server crashes or is redeployed, its users are signed out, and the load balancer cannot move them to a less busy server. A shared store lets you add, remove or restart servers freely.
