## What it is

Memcached is an older in-memory cache that, like [Redis](card:what-is-redis), stores values under keys in RAM. Its values are opaque: plain bytes that Memcached never looks inside, so the app turns each object into bytes itself. Memcached runs several worker threads, and its servers never talk to each other. Redis does the same caching job and adds typed values, saving to disk, copies on other servers and scripts.

## Why it exists

Both tools answer reads from memory, so interviewers ask why you would pick one over the other. The answer is about features and operations, not raw speed. To cache rendered pages or serialised objects that you can always rebuild, Memcached is enough. Once you need lists, sets or rankings, data that survives a restart, or a standby copy for failover, you need Redis.

## How it works

<Compare id="redis-vs-memcached" />

1. With Memcached, the app serialises an object to bytes, hashes the key to pick one server, and stores the bytes there.
2. To change one field, the app reads the whole value, changes it in its own memory and writes the whole value back.
3. If that Memcached server dies, its keys are gone, and the app reloads them from the database.
4. With Redis, the app can store a hash and change one field with one command. Replicas keep a copy, and [Sentinel](card:sentinel) or [Redis Cluster](card:redis-cluster) can promote a replica when a server dies.

So the key is: Memcached only stores and returns blobs; Redis understands the shape of the data.

## Example

The payment service checks four needs against both tools.

| Need | Memcached | Redis |
|---|---|---|
| Cache merchant settings as JSON for 10 minutes | Yes | Yes |
| Count a user's requests | Yes (`incr`) | Yes (`INCR`) |
| Rank merchants by today's payment total | No ordered type | Sorted set |
| Keep sessions after a crash | No | Yes, with persistence on |

The first two rows are plain caching and counting, where both tools work. The last two need a data type or persistence, which only Redis has.

## Rules and defaults

- **Worker threads:** 4 by default (`memcached -t`).
- **Item size:** at most 1 MB per item by default (`memcached -I`). A Redis string can be up to 512 MB.
- **When memory is full:** Memcached drops the least recently used items by default.
- **Restarts:** Memcached 1.5.18 and later can keep data across a clean restart (warm restart), but a crash loses everything.

## Interview Qs

### When would you still choose Memcached?

For a simple cache of serialised objects on large multi-core servers, where losing the data is fine and you need no data types, replication or persistence. Otherwise pick Redis, so that one tool covers caching, counters and locks.

### Does Memcached replicate data?

No. Memcached servers do not know about each other: no replication and no synchronisation. The client decides which server holds each key. If a node dies, its keys are lost and the app reloads them from the database.

### Is Redis faster than Memcached?

Not in general. Both serve simple reads from RAM, and Memcached uses many threads, so it can use more CPU cores on one server. The real difference is features: types, persistence, replication and scripting in Redis.
