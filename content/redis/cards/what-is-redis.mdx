## Why it exists

Reading hot, simple data from a disk database again and again is slow. Redis serves it from memory and adds ready-made structures for counters, queues and rankings.

## How it works

<Mermaid
  alt="Two app servers send commands over TCP to Redis. Optional I/O threads read and write the sockets. One main thread runs the commands one at a time against data held in RAM. Disk is used only for persistence files."
  chart={`flowchart LR
  A[App 1] -- TCP --> IO[Socket I/O]
  B[App 2] -- TCP --> IO
  IO --> M[Main thread: one command at a time]
  M <--> RAM[(Data in RAM)]
  RAM -. copies .-> D[(Disk: RDB / AOF)]`}
/>

- Running one command at a time makes each command atomic: see [single-command atomicity](card:single-command-atomicity).
- Common uses: [caching](card:cache-aside), [sessions](card:session-storage), [rate limits](card:rate-limiting-with-redis), [leaderboards](card:sorted-sets), [locks](card:distributed-locks), [queues](card:queues-with-redis).

## Example

```text
SET merchant:42:config '{"upi":true,"card":true}' EX 600   -- OK
GET merchant:42:config     -- "{\"upi\":true,\"card\":true}"
TYPE merchant:42:config    -- string
```

## Interview Qs

### Redis is single-threaded. Why is it still fast?

Data is in RAM, most commands take constant, tiny time, and the main thread never blocks on disk or sockets. It is "mostly" single-threaded: background threads handle some disk work and deletes, and optional I/O threads handle sockets.

### Is Redis only a cache?

No. It also stores sessions, counters, rate limits, leaderboards, locks and queues. It can persist data to disk, but how much survives a crash depends on its [persistence](card:persistence-rdb-aof) settings.
