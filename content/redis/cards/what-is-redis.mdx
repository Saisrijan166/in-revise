## What it is

Redis is a server that keeps its data in RAM, the computer's working memory, instead of on disk. That is what "in-memory" means. You store each item under a key, a name you choose such as `merchant:42:config`, much like a key in a Java `Map`. The item is the value, and it has a type: a string, a hash, a list, a set and others. Your app talks to Redis over the network with commands, short instructions such as `SET` (store) and `GET` (read).

## Why it exists

The payment service reads the same merchant settings from PostgreSQL on every request. Each read is a full SQL query, and thousands of identical queries a second load the database for no new information. With Redis, the service keeps a copy of those settings in memory and fetches it with one key lookup, which Redis itself usually runs in under a microsecond. Redis also offers ready-made structures for counters, queues and rankings, so you do not build them on top of SQL tables.

## How it works

<Mermaid
  alt="Two app servers send commands over TCP to Redis. Redis reads all connections, and one main thread runs the commands one at a time against data held in RAM. Disk is used only for copies of the data."
  chart={`flowchart LR
  A[App 1] -- TCP --> IO[Read all connections]
  B[App 2] -- TCP --> IO
  IO --> M[Main thread: one command at a time]
  M <--> RAM[(Data in RAM)]
  RAM -. copies .-> D[(Disk files)]`}
/>

1. The app opens a TCP connection to Redis, on port 6379 by default, and keeps it open.
2. It sends a command, for example `GET merchant:42:config`.
3. Redis watches all its connections at once and never waits for one slow client. Commands that are ready go to the main thread.
4. The main thread runs them one at a time. This is what "single-threaded" means: while one command runs, no other command touches the data.
5. The command reads or changes the value in RAM, and the reply goes back on the same connection.

So the key is: each command is small and runs alone, which makes it safe without locks, but one slow command delays everyone.

## Example

The payment service stores the merchant settings, counts today's payments and looks for a payment that is not cached yet.

```bash
redis-cli SET merchant:42:config '{"upi":true,"card":true}' EX 600
redis-cli GET merchant:42:config
redis-cli TYPE merchant:42:config
redis-cli INCR stats:payments:today
redis-cli INCR stats:payments:today
redis-cli GET payment:9001
```

```text output
OK
"{\"upi\":true,\"card\":true}"
string
(integer) 1
(integer) 2
(nil)
```

What to notice:

- `SET` stores the JSON text as a string value. Redis does not read the JSON; it keeps the bytes and returns them unchanged on `GET`.
- `EX 600` gives the key a 600-second lifetime; you will see this in [TTL and key expiry](card:ttl-and-expiration).
- `INCR` adds one to a number and returns the new value. Because commands run one at a time, two services calling it together never lose a count.
- `(nil)` means no such key. In a cache, that is a miss: the app must read PostgreSQL instead.

## Rules and defaults

- **Port:** 6379 by default (Redis Open Source 8.10).
- **Data must fit in RAM:** Redis Open Source keeps the whole data set in memory. You cap its size with `maxmemory`, covered in [eviction policies](card:eviction-policies).
- **I/O threads:** off by default (`io-threads 1`, Redis Open Source 8.10). When you turn them on, extra threads read, parse and write client data, which helps only on busy servers with spare CPU cores.
- **Background threads:** some slow work, such as flushing files to disk and freeing large deleted values, runs off the main thread.

## Not to be confused with

A relational database such as PostgreSQL keeps data on disk and answers SQL queries; Redis keeps data in RAM and answers by key. You will compare them in [Redis vs a relational database](card:redis-and-databases). Memcached is another in-memory cache, but its values are plain bytes and its servers do not copy data to each other. Rule: the database keeps the records; Redis keeps fast copies and shared helpers.

## Interview Qs

### Redis runs commands on one thread. Why is it still fast?

The data is in RAM, and common commands such as GET, SET and INCR take constant time. The main thread never blocks on reading or writing sockets, so it is almost always busy with real work. For a simple command, the network round trip costs far more than the command itself.

### Is Redis really single-threaded?

Mostly. One main thread runs all commands. Background threads handle some disk work and free large deleted values, and optional I/O threads handle socket reads, writes and parsing. So "single-threaded" describes how commands run, not the whole process.

### Is Redis only a cache?

No. It also holds sessions, counters, rate limits, leaderboards, locks and queues. It can save its data to disk, but how much survives a crash depends on its [persistence](card:persistence-rdb-aof) settings, so the payment records themselves stay in the database.
