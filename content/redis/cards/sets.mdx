## What it is

A set is a key whose value is a collection of unique strings, called members, with no order. If you add a member that is already there, nothing changes. Unlike a [list](card:lists), a set does not remember the order you added members in. Redis can also compare sets: which members two sets share, which they have together, and which only one has.

## Why it exists

Many checks are "have I seen this already?" or "who is in both groups?". The payment provider may send the same webhook event twice, and the service must not process it twice. With a list you would scan every item to find a duplicate, which gets slower as it grows. A set answers "is this id here?" in one fast command and keeps the members unique for you.

## How it works

User 7 has paid with `{UPI, card}`; user 9 with `{UPI, wallet}`.

| Command | Result | Meaning |
|---|---|---|
| SINTER user:7:methods user:9:methods | UPI | in both sets |
| SUNION user:7:methods user:9:methods | UPI, card, wallet | in either set |
| SDIFF user:7:methods user:9:methods | card | only in the first set |

1. `SADD key member` adds the member and returns 1, or returns 0 if it was already there.
2. `SISMEMBER key member` returns 1 if the member is in the set, 0 if not.
3. `SCARD key` returns how many members the set has. "Cardinality" is the word for this count.
4. `SINTER`, `SUNION` and `SDIFF` combine sets inside Redis and return the result, so the app does not download every member first.

## Example

The payment service skips a webhook event it has already handled, then compares two users' payment methods.

```bash
redis-cli SADD seen:payment-events evt-501
redis-cli SADD seen:payment-events evt-501
redis-cli SCARD seen:payment-events
redis-cli SADD user:7:methods UPI card
redis-cli SADD user:9:methods UPI wallet
redis-cli SINTER user:7:methods user:9:methods
redis-cli SDIFF user:7:methods user:9:methods
redis-cli SISMEMBER user:9:methods card
```

```text output
(integer) 1
(integer) 0
(integer) 1
(integer) 2
(integer) 2
1) "UPI"
1) "card"
(integer) 0
```

What to notice:

- The first `SADD` returned 1 (new event, so process it). The second returned 0 (already seen, so skip it). `SCARD` confirms one member.
- Check and add happen in one command, so two app servers that get the same event at the same moment cannot both see 1.
- `SDIFF` returned `card` because it keeps members of the first set only. Swap the keys and it returns `wallet`.
- `seen:payment-events` has no expiry here, so it grows with every event. In real use you would give it an expiry, as [TTL and key expiry](card:ttl-and-expiration) shows.

## Rules and defaults

- **Size limit:** a set can hold up to 2^32 - 1 (about 4.29 billion) members.
- **Speed:** adding, removing and checking a member are O(1): the cost does not grow with the set.
- **Whole-set commands:** `SMEMBERS` returns every member in one reply and is O(n). On a big set, walk it in pages with `SSCAN`.
- **Memory:** a huge set uses memory for every member. If an estimate is enough, use a probabilistic type instead: the Redis docs suggest a Bloom filter for "seen before?", and a [HyperLogLog](card:bitmaps-hyperloglog) estimates counts.

## Common mistakes

- **"SMEMBERS on a big set is fine because SADD is fast."** SADD touches one member; SMEMBERS builds a reply with all of them while other clients wait. Use SSCAN or SCARD when you only need a page or the count.

## Interview Qs

### How do you avoid processing the same payment event twice?

SADD the event id to a set of seen ids. A reply of 1 means new, so process it; 0 means already seen, so skip it. Give the key an expiry so the set does not grow forever. For a hard guarantee, the database should also reject duplicates.

### Set or HyperLogLog for counting unique visitors?

A set gives the exact count and lets you list the members, but its memory grows with every visitor. A HyperLogLog uses at most about 12 KB per counter and gives a close estimate, but cannot list who the visitors were.

### How would you find users who paid with both UPI and card?

Keep one set per method, such as method:UPI:users and method:card:users, and run SINTER on the two keys. Redis computes the overlap on the server and returns only the common user ids.
