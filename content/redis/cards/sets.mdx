## Why it exists

Many checks are "have I seen this already?" or "who is in both groups?". A set answers them in one call, and Redis keeps the members unique for you.

## How it works

User 7 paid with `{UPI, card}`; user 9 paid with `{UPI, wallet}`.

| Command | Result | Meaning |
|---|---|---|
| SINTER u7 u9 | UPI | used by both |
| SUNION u7 u9 | UPI, card, wallet | used by either |
| SDIFF u7 u9 | card | only user 7 (order of keys matters) |

- Huge sets cost memory. For an approximate unique count, use [HyperLogLog](card:bitmaps-hyperloglog).

## Example

```text
SADD payment:PAY101:events CREATED       -- 1 (added)
SADD payment:PAY101:events CREATED       -- 0 (already there)
SCARD payment:PAY101:events              -- 1
SISMEMBER payment:PAY101:events CREATED  -- 1 (yes)
```

## Interview Qs

### How do you avoid processing the same payment event twice?

SADD the event ID to a set of seen IDs. A reply of 1 means new, so process it; 0 means it was already seen. Add a TTL to the key if the set must not grow forever.

### Set or HyperLogLog for unique visitors?

A set gives the exact count and the members, but memory grows with every visitor. A [HyperLogLog](card:bitmaps-hyperloglog) uses a small fixed amount of memory and gives a close estimate, without the members.
