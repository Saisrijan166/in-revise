## What it is

Failure handling is the plan for what each Redis use does when Redis is slow or unreachable, for example during a restart, a [failover](card:sentinel) to a replica, or one slow command that holds up every other client. The plan has two parts. First, the app must notice the failure fast, through short timeouts and a circuit breaker. Second, each use has its own fallback: a cache, a rate limiter, a lock and a session each fail in a different way.

## Why it exists

Without a plan, every request waits on Redis. Lettuce's default command timeout is 60 seconds, so each request thread can hang for a minute, and the server soon has no free threads. If the cache then falls back to the database for every request, PostgreSQL gets the full read load that the cache used to absorb, and fails next. A plan made in advance keeps a Redis outage small: some requests get slower, but the service stays up.

## How it works

| Use | When Redis fails | Detail |
|---|---|---|
| Cache | Miss: read the database | Cap the flood: [cache problems](card:cache-problems) |
| Rate limit | Fail open or fail closed | Availability or protection, chosen per endpoint |
| Lock | Not acquired: retry later | Never run guarded work unlocked: [locks](card:distributed-locks) |
| Session | Lookups fail; lost data means signing in again | [Sessions](card:session-storage) |

1. The client sends a command and waits for the reply, at most for the command timeout.
2. If Redis is unreachable, Lettuce keeps the command in a buffer and tries to reconnect. If the timeout ends first, the call fails, and Spring throws a `QueryTimeoutException`.
3. Your code, or Spring's cache error handler, catches the error and runs the fallback for that use, from the table above.
4. After many failures in a row, a circuit breaker opens and skips Redis at once, so no request waits for a timeout.
5. After a pause, the breaker lets a few test calls through, and closes again once they succeed.

So the key is to fail fast first, and then fall back in a way the rest of the system can carry.

## Example

The payment service caches the merchant config with `@Cacheable`. This configuration makes a Redis error behave like a cache miss instead of failing the request.

```java
@Configuration
@EnableCaching
class CacheConfig implements CachingConfigurer {
    @Override
    public CacheErrorHandler errorHandler() {
        return new LoggingCacheErrorHandler();   // log, then run the method as on a miss
    }
}
```

What to notice:

- Without this bean, Spring uses `SimpleCacheErrorHandler`, which rethrows. A Redis outage would then turn every `@Cacheable` call into an error.
- `LoggingCacheErrorHandler` logs a warning and does not rethrow. Spring treats a failed read as a miss, so the method runs and loads the merchant config from PostgreSQL; a failed write is logged too, and the result is returned uncached.
- It does not make the call fast: each failed read still waits for the command timeout. Pair it with a short `spring.data.redis.timeout`.

## Rules and defaults

- **Command timeout:** 60 seconds in Lettuce when `spring.data.redis.timeout` is not set (Spring Boot 4.1, Spring Data Redis 4.1). Set a short value, such as `2s`.
- **Connect timeout:** `spring.data.redis.connect-timeout` limits how long opening a connection may take.
- **Reconnect:** Lettuce reconnects automatically and buffers the commands sent while it is disconnected, then sends them once it is back. The buffer lives in memory, so it is lost if the app restarts.
- **Measured:** with Redis stopped and a 5-second timeout, a GET through `StringRedisTemplate` failed after 5.0 seconds with `QueryTimeoutException` (Lettuce 7.5, Spring Data Redis 4.1.1).
- **Circuit breaker:** it comes from a library such as Resilience4j, wrapped around your Redis calls.

## Not to be confused with

Failing open means that when a check such as a rate limiter cannot run, the request is allowed anyway. Failing closed means the request is denied. Rule: fail open where an outage hurts more than some abuse, such as a product search; fail closed where abuse hurts more, such as login attempts or payment capture.

## Common mistakes

- **"Lettuce reconnects by itself, so there is nothing to do."** Reconnecting does not stop callers from waiting: buffered commands still wait up to the command timeout before they fail.
- **"If the lock service is down, run the job anyway."** Then two workers can capture the same payment. Treat a lock you cannot take as not held, and retry later.

## Interview Qs

### Redis goes down. What happens to your payment app?

Merchant config is read from the database, with the load capped. The login limiter follows its fail-open or fail-closed rule. Workers cannot take `lock:payment:9001`, so they retry later. Payment records are safe, because they live in the database. Short timeouts and a circuit breaker keep requests from hanging.

### Should a rate limiter fail open or fail closed?

It depends on the cost of each mistake. Failing open keeps users served but drops protection while Redis is down. Failing closed keeps login and payment endpoints protected, but takes them down together with Redis. So the choice is made per endpoint, not once for the whole app.

### How do you find what makes Redis slow?

`SLOWLOG GET` lists recent slow commands, `LATENCY DOCTOR` explains latency spikes once the latency monitor is switched on, and `INFO` shows memory, clients and hit counts. Then look for [big keys](card:memory-optimization) and for [KEYS](card:key-design), which walks the whole keyspace.
