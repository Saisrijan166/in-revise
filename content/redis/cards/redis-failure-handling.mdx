## Why it exists

Redis can restart, fail over or stall on a slow command. Without a plan, every request waits on it, then the database drowns.

## How it works

| Use | When Redis fails | Detail |
|---|---|---|
| Cache | Miss: read the database | Cap the flood: [cache problems](card:cache-problems) |
| Rate limit | Fail open or fail closed | Availability vs protection, per endpoint |
| Lock | Not acquired: retry later | Never run guarded work unlocked: [locks](card:distributed-locks) |
| Session | Lookups fail; lost data means sign in again | [Sessions](card:session-storage) |

- Short client timeouts: `spring.data.redis.timeout` (read) and `spring.data.redis.connect-timeout`.
- A circuit breaker, such as Resilience4j, skips Redis at once after repeated failures, then tests it again.

## Example

```java
@Configuration
@EnableCaching
class CacheConfig implements CachingConfigurer {
    @Override
    public CacheErrorHandler errorHandler() {
        return new LoggingCacheErrorHandler();   // log, then run the method as on a miss
    }
}
```

## Interview Qs

### Redis goes down. What happens to your payment app?

Merchant config comes from the database, with capped load. The UPI limiter follows its fail-open or fail-closed rule. Workers cannot take `lock:payment:PAY101`, so they retry later. Payment records stay safe in the database.

### Should a rate limiter fail open or fail closed?

It depends on the cost. Fail open keeps users served but drops protection; fail closed guards login or payment endpoints but takes them down with Redis.

### How do you find what makes Redis slow?

`SLOWLOG GET` lists slow commands, `LATENCY DOCTOR` explains latency spikes once the monitor is on, and `INFO` shows memory, clients and hit counts. Then look for [big keys](card:memory-optimization).
