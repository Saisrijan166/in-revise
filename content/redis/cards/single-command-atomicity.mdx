## Why it exists

Two app servers that read a value, change it and write it back can overwrite each other. Redis offers single commands that do the whole step at once.

## How it works

| Step | Server A | Server B | Count in Redis |
|---|---|---|---|
| 1 | GET → 5 | | 5 |
| 2 | | GET → 5 | 5 |
| 3 | SET 6 | | 6 |
| 4 | | SET 6 | 6: one payment lost |
| Fix | INCR → 6 | INCR → 7 | 7 |

- Redis runs commands one at a time ([why](card:what-is-redis)), so no command sees another half done.
- Several steps as one: [MULTI/EXEC with WATCH](card:transactions-multi-exec) or a [Lua script](card:lua-and-functions).
- SET NX as a lock, with its expiry and safe release: [distributed locks](card:distributed-locks).

## Example

```text
INCR payment:request-count                         -- (integer) 1
INCRBY merchant:42:paise:2026-10-20 50000          -- ₹500 kept as paise
EXPIRE merchant:42:paise:2026-10-20 172800         -- keep two days
HINCRBY merchant:42:methods upi 1                  -- per-method count in a hash
SET payment:PAY101 PAID IFEQ PENDING               -- OK only if still PENDING (8.4+)
```

## Interview Qs

### How do you count payments per merchant per day across many servers?

One key per merchant and day, `INCRBY` on every payment, and a [TTL](card:ttl-and-expiration) so old days vanish. Each `INCRBY` is atomic, so no lock is needed.

### Can you use INCRBYFLOAT for money totals?

Better not. It works on double-precision floats, which round. Store paise as integers and use `INCRBY`; format rupees in the app.
