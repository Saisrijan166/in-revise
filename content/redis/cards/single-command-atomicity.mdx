## What it is

An atomic operation is one that other clients see either fully done or not started, never half done. In Redis every single command is atomic, because the main thread runs one command from start to end before it starts the next one ([why Redis works this way](card:what-is-redis)). Some commands, such as `INCR`, read a value, change it and write it back inside that one command. That makes them safe to call from many app servers at the same time.

## Why it exists

The payment service runs on three app servers, and each one counts the payments of merchant 42. If a server reads the count with GET, adds 1 in Java and writes it back with SET, two servers can read the same old value and both write the same new one. One payment is then lost from the count, which is called a lost update. A lock would prevent it, but it costs extra round trips and failure handling. `INCR` removes the problem: the read, the add and the write happen inside Redis as one command, so nothing can run between them.

## How it works

| Step | Server A | Server B | Count in Redis |
|---|---|---|---|
| 1 | GET → 5 | | 5 |
| 2 | | GET → 5 | 5 |
| 3 | SET 6 | | 6 |
| 4 | | SET 6 | 6: one payment lost |
| Fix | INCR → 6 | INCR → 7 | 7 |

1. Server A sends GET and gets 5.
2. Before A writes, Redis runs Server B's GET, which also returns 5. Each command ran whole, but A's two commands had a gap, and B's command used it.
3. A writes 6, then B writes 6. The count should be 7.
4. With INCR, each server sends one command. Redis runs A's INCR to the end (5 to 6) and only then B's (6 to 7).

So the key is to put the whole read-change-write into one command.

## Example

The payment service records a ₹500 payment for merchant 42 and marks payment 9001 as paid, typed in redis-cli:

```bash
SET payment:9001 PENDING
INCR merchant:42:payments:2026-10-21
INCRBY merchant:42:paise:2026-10-21 50000
EXPIRE merchant:42:paise:2026-10-21 172800
SET payment:9001 PAID IFEQ PENDING
SET payment:9001 PAID IFEQ PENDING
```

```text output
OK
(integer) 1
(integer) 50000
(integer) 1
OK
(nil)
```

What to notice:

- `INCR` on a key that did not exist returns 1: Redis started it at 0. One key per merchant and day keeps each day's count separate.
- The amount is kept as 50000 paise, a whole number, so the total is exact.
- `INCRBY` and `EXPIRE` are two commands. If the app crashes between them, the key never expires. [MULTI/EXEC](card:transactions-multi-exec), which comes next, groups them.
- The first `SET … IFEQ PENDING` writes PAID. The second replies nil, because the value is no longer PENDING. A late duplicate request changes nothing.

## Rules and defaults

- **Missing key:** INCR, INCRBY, DECR and HINCRBY treat a missing key or field as 0 before adding.
- **Integers only:** the value must be a base-10 whole number within the 64-bit signed range. Otherwise INCR replies `ERR value is not an integer or out of range`, and a result past the range is refused with an overflow error.
- **Conditional writes in one command:** `SET NX` writes only if the key is missing. `SET IFEQ` (Redis 8.4+) writes only if the current value equals the one you give and never creates the key. `DELEX` (Redis 8.4+) deletes in the same compare-first way.
- **Counter with expiry (Redis 8.8+):** `INCREX key EX 172800` adds and sets the expiry in one command, which removes the INCR-then-EXPIRE gap.
- **Beyond one command:** when a step needs several commands, use [MULTI/EXEC](card:transactions-multi-exec) or a [Lua script](card:lua-and-functions).

## Common mistakes

- **"INCRBYFLOAT is fine for money totals."** It does binary floating-point maths, where amounts like 0.1 are not stored exactly, and its output keeps at most 17 decimal digits. Store paise as integers and use INCRBY.
- **"SET NX makes a complete lock."** It is only the first step. A safe lock also needs an expiry and a release that checks the owner, which you will see in [distributed locks](card:distributed-locks).

## Interview Qs

### Why is INCR safe across many app servers when GET plus SET is not?

Redis runs every command whole, one at a time. INCR reads, adds and writes inside one command, so no other client can act in between. GET and SET are two commands, and another server's GET can run between them, read the same old value and overwrite your update.

### How do you count payments per merchant per day across many servers?

Use one key per merchant and day, such as `merchant:42:payments:2026-10-21`, and send `INCR` on every payment. Each INCR is atomic, so no lock is needed. Give the key a TTL of a few days so old counters disappear, or use INCREX on Redis 8.8+ to add and set the expiry together.

### Can you use INCRBYFLOAT for money totals?

Better not. It uses binary floating-point numbers, which cannot hold most decimal amounts exactly, so totals can drift by tiny amounts. Store paise as whole numbers, add them with INCRBY, and format rupees in the app.
