## What it is

Rate limiting means allowing each client only so many requests in a period, such as 5 login attempts per user per minute. Requests over the limit get HTTP status 429, Too Many Requests. With Redis, the count for each client is one key, such as `rate:user:7:login`, and the key's TTL ends the period. Redis fits because [one command such as INCR is atomic](card:single-command-atomicity), so many servers can count into one key without losing updates.

## Why it exists

A bot can try thousands of passwords against the login endpoint, or flood the payment API. If each app server counted in its own memory, four servers would allow four times the limit, because the load balancer spreads the requests. Keeping the counter in Redis gives one number that every server reads and updates. Expired keys clean themselves up, so idle users cost nothing.

## How it works

1. A login request for user 7 reaches any app server.
2. The server runs one Lua script in Redis that increments `rate:user:7:login` and, if the count is now 1, sets a 60-second expiry.
3. Redis returns the new count. No other client's command runs while the script runs.
4. If the count is 5 or less, the server checks the password. Above 5, it replies 429 with `Retry-After`.
5. After 60 seconds the key expires, and the next attempt starts a new count at 1.

This is the fixed window rule. A Lua script is needed, not [MULTI/EXEC](card:transactions-multi-exec), because the script must set the expiry only when the count it just read is 1, and MULTI/EXEC cannot branch on a value read inside it.

## Example

The fixed-window login limiter: the script, then six attempts by user 7 within one minute.

```lua
-- KEYS[1] = rate:user:7:login   ARGV[1] = window in seconds
local count = redis.call("INCR", KEYS[1])
if count == 1 then
  redis.call("EXPIRE", KEYS[1], ARGV[1])
end
return count
```

```bash
for i in 1 2 3 4 5 6; do
  redis-cli EVAL "$(cat login-limit.lua)" 1 rate:user:7:login 60
done
redis-cli TTL rate:user:7:login
```

```text output
(integer) 1
(integer) 2
(integer) 3
(integer) 4
(integer) 5
(integer) 6
(integer) 59
```

What to notice:

- The script returns the count, and the app decides: attempts 1 to 5 go on to the password check, and attempt 6 gets 429.
- `TTL` shows 59 seconds left: the expiry was set once, on the first attempt, and later attempts did not push it back.
- Remove the `if count == 1` check and every attempt resets the TTL, so a client that keeps trying is never let back in.
- You will see the Java call for this script in [Redis Code Templates](card:redis-code-templates).

## Rules and defaults

- **INCREX (Redis 8.8+):** `INCREX rate:user:7:login UBOUND 5 EX 60 ENX` does the same in one command. It replies with the new value and the amount added; at the cap it adds nothing and replies `[5, 0]`. `ENX` sets the TTL only when the key has none.
- **Retry-After:** RFC 6585 says a 429 response may include it; use the key's remaining TTL as the value.
- **Key per action:** limit logins and payments with different keys, so a burst on one does not block the other.
- **Redis Cluster:** a script may only touch keys in one hash slot. A limiter that uses two keys, such as the current and previous window of the sliding window counter below, gives both one hash tag, such as `{rate:user:7:login}`. You will see hash slots in [Redis Cluster](card:redis-cluster).

## Not to be confused with

There are three common counting rules. A fixed window keeps one counter per clock window and resets at the edge. A sliding window counts requests in the last N seconds: the log keeps each request time in a [sorted set](card:sorted-sets), and the counter blends the previous window's count with the current one. A token bucket stores tokens that refill at a steady rate; each request spends one. Rule: fixed window for simple limits, sliding window as the general default, token bucket when short bursts are fine.

## Interview Qs

### Design a rate limiter with Redis.

Use one key per user and action, such as `rate:user:7:login`. A Lua script increments it and sets a 60-second TTL on the first hit. Above the limit, return 429 with `Retry-After`. All app servers share the count. For a smoother limit, use a sliding window; for bursty clients, a token bucket.

### Why can a fixed window let through twice the limit?

The count resets at the window edge. A client can send 5 requests at 10:00:59 and 5 more at 10:01:00, which is 10 in two seconds. A sliding window counts the last 60 seconds whatever the clock says, so it refuses the second burst.

### Why a Lua script and not MULTI/EXEC or WATCH?

MULTI/EXEC queues commands before running them, so it cannot act on the count it reads. WATCH works but aborts and retries whenever another request touches the key, which is exactly the busy case. A script reads, decides and writes atomically in one round trip, with no retries.
