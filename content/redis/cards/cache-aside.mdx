## What it is

Cache-aside is the most common way to use Redis as a cache. A cache is a fast copy of data whose real home, the source of truth, is somewhere else: here PostgreSQL. The application keeps the copy itself: it looks in Redis first and, on a miss (the key is not in Redis), reads the database and stores the result in Redis. It is also called lazy loading, because data enters the cache only when someone asks for it.

## Why it exists

The payment service reads merchant 42's configuration (fee, allowed payment methods) from PostgreSQL on every payment request. That is the same row thousands of times a minute, and each read costs a network round trip and database work, so at peak the database becomes the bottleneck. With cache-aside, only the first read after the copy expires goes to PostgreSQL. All the others are memory lookups in Redis.

## How it works

<Mermaid
  alt="Cache-aside. Read path: the app runs GET merchant:42:config. On a hit it returns the value. On a miss it reads PostgreSQL, stores the value in Redis with SET and a 1800-second TTL, then returns it. Write path: the app updates PostgreSQL first, then deletes the key in Redis."
  chart={`flowchart TD
  R([Read merchant 42]) --> C{"GET merchant:42:config"}
  C -- hit --> RET([Return value])
  C -- miss --> DB[(Read PostgreSQL)]
  DB --> SET["SET key value EX 1800"]
  SET --> RET
  W([Update merchant 42]) --> U[(1. Update PostgreSQL)]
  U --> DEL["2. DEL merchant:42:config"]`}
/>

1. The app builds the key `merchant:42:config` and sends `GET`.
2. On a hit, Redis returns the stored JSON and the app uses it. The database is not touched.
3. On a miss (the key was never stored, has expired or was evicted), `GET` returns nil and the app runs its SQL query.
4. The app stores the result with `SET ... EX 1800`, so the copy removes itself after 30 minutes, and returns it.
5. When merchant 42's configuration changes, the app updates PostgreSQL first and then deletes the key. The next read misses and loads the new row.

So the key is: the app owns both paths, and Redis only stores what it is given.

## Example

The payment service reads and updates merchant configuration with a `StringRedisTemplate`, the Spring Data Redis helper for string keys and values.

```java
String merchantConfig(long id) {
    String key = "merchant:" + id + ":config";
    String json = redis.opsForValue().get(key);                     // 1. try Redis
    if (json == null) {                                             // miss: absent, expired or evicted
        json = configRepo.loadJson(id);                             // 2. read PostgreSQL
        redis.opsForValue().set(key, json, Duration.ofMinutes(30)); // 3. store with a 30-minute TTL
    }
    return json;
}

void updateConfig(long id, String json) {
    configRepo.save(id, json);                                      // database first
    redis.delete("merchant:" + id + ":config");                     // then delete the cached copy
}
```

What to notice:

- `get` returns `null` for every kind of miss, so one `if` handles a key that never existed, expired or was evicted.
- `set(key, json, Duration.ofMinutes(30))` sends one `SET` with a TTL. Drop the `Duration` and the copy never expires, so a single forgotten delete leaves wrong data for good.
- `updateConfig` writes the database before deleting. Swap the two lines and a reader that runs in between caches the old row again.
- Two requests that miss at the same moment both read the database. That is harmless for one key; you will see the fix for a very popular key in [cache problems](card:cache-problems).

## Rules and defaults

- **Source of truth:** PostgreSQL keeps the real data. The Redis copy can disappear at any time (expiry, eviction, restart), and the app must still work without it.
- **TTL on every copy:** a key stored with a plain `SET` has no TTL, so it lives until deleted or evicted. Always store cached copies with one.
- **Memory limit:** for a Redis that holds only cache copies, set `maxmemory` with `allkeys-lru` or `allkeys-lfu` (see [eviction policies](card:eviction-policies)).
- **Measuring it:** the hit ratio is `keyspace_hits / (keyspace_hits + keyspace_misses)` from `INFO stats`. It counts every key lookup on the instance, not one cache.
- **Not a good fit:** data where most reads miss (each miss costs three trips), and sensitive data in a cache that many applications share.

## Not to be confused with

In cache-aside the application loads a miss from the database. In read-through, which you will see in [caching strategies](card:caching-strategies), a cache layer loads the miss and the app only ever talks to the cache. Redis Open Source cannot do read-through by itself, so with plain Redis you write cache-aside. Rule: cache-aside = the app loads; read-through = the cache loads.

## Interview Qs

### Two requests miss the same key at once. Is that a problem?

Both read the database and both store the same value, which is harmless for one ordinary key. For a hot key read thousands of times a second, every waiting request reloads it at once and floods the database. That is a cache stampede, and the fix, letting one caller rebuild, comes in [cache problems](card:cache-problems).

### What happens when Redis goes down?

Every read becomes a miss and goes to the database, so the app keeps working, only slower. The danger is that the database now gets all the traffic the cache used to absorb. Limit that flood and treat Redis errors as misses; you will see how in [failure handling](card:redis-failure-handling).

### Which data is worth caching?

Data that is read often and changes rarely, like merchant configuration or a product catalogue. Skip data that most requests read only once, because each miss costs three trips and saves nothing. Keep sensitive data out of a cache that many applications share.
