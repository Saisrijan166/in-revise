## What it is

This concept is about how much memory your keys use, and about big keys. A big key is one key whose value holds very many elements or bytes, such as a [set](card:sets) of a million payment ids. Redis stores small collections in a compact encoding, a dense format that uses far less memory, and switches to a normal one as they grow. `MEMORY USAGE` shows a key's size in bytes, and `OBJECT ENCODING` shows its format.

## Why it exists

Memory is the main cost of Redis, because all data sits in RAM, and [eviction](card:eviction-policies) only helps once memory is already full. A big key also hurts speed: commands run one at a time, so reading all of a million-member set, or deleting it with `DEL`, holds the main thread while every other client waits. Finding big keys early, splitting them and deleting them safely keeps both memory and response times under control.

## How it works

| Problem | Find it | Fix |
|---|---|---|
| Huge hash, list or set | `redis-cli --bigkeys` | Split into smaller keys; read parts, not the whole value |
| Key that uses many bytes | `redis-cli --memkeys` | Smaller values, compact encodings |
| A delete stalls the server | `SLOWLOG GET`, the log of slow commands | `UNLINK` instead of `DEL` |

1. Find the largest keys with `redis-cli --bigkeys` (most elements) or `--memkeys` (most bytes). Both walk the keyspace with [SCAN](card:key-design), so they are safe on a live server.
2. Check one key with `MEMORY USAGE` for its bytes and `OBJECT ENCODING` for its format.
3. Split a big key into smaller ones, for example one set per day instead of one per year. Read parts of a value, such as a few hash fields, instead of all of it.
4. Delete a big key with `UNLINK`. It removes the key at once, and a background thread frees the memory.

## Example

`merchant:42:limits` is a small hash. `payment:ids:2025` is a set that already holds one million payment ids.

```bash
redis-cli HSET merchant:42:limits upi 100000 card 200000 wallet 10000
redis-cli OBJECT ENCODING merchant:42:limits
redis-cli MEMORY USAGE merchant:42:limits
redis-cli SCARD payment:ids:2025
redis-cli OBJECT ENCODING payment:ids:2025
redis-cli MEMORY USAGE payment:ids:2025
redis-cli UNLINK payment:ids:2025
```

```text output
(integer) 3
"listpack"
(integer) 77
(integer) 1000000
"hashtable"
(integer) 32277595
(integer) 1
```

What to notice:

- The 3-field hash uses the compact `listpack` encoding and only 77 bytes.
- The million-member set uses the normal `hashtable` encoding and about 32 MB. That is a big key.
- `UNLINK` returns 1 at once, and the 32 MB are freed in the background. `DEL` would free them on the main thread while other clients wait.

## Rules and defaults

| Collection | Compact encoding | Limit (Redis Open Source 8.10) |
|---|---|---|
| Hash | listpack | up to 512 fields, values up to 64 bytes |
| Set of integers only | intset | up to 512 members |
| Other small set | listpack (Redis 7.2+) | up to 128 members |
| Sorted set | listpack | up to 128 members |

- **Automatic switch:** when a collection passes its limit, Redis converts it to the normal encoding by itself.
- **DEL blocks:** `lazyfree-lazy-user-del` is `no` by default. Setting it to `yes` makes `DEL` behave like `UNLINK`.
- **Throttled scans:** `redis-cli --bigkeys -i 0.1` pauses 0.1 seconds every 100 `SCAN` calls, for very busy servers.
- **Freed memory:** Redis does not always give freed memory back to the operating system, so size the server for peak use.

## Not to be confused with

A big key is large: one value with many elements or bytes, which makes single commands slow. A hot key is popular: a small key that receives a huge share of all requests; you will see it in [cache problems](card:cache-problems). Rule: big key is a size problem, so split it; hot key is a traffic problem, so spread the reads.

## Interview Qs

### What is a big key and why is it a problem?

A value with very many elements or bytes. Redis runs commands one at a time, so a command that reads all of it, or a DEL, blocks every other client. Find it with redis-cli --bigkeys or --memkeys, and split it.

### DEL vs UNLINK?

Both remove the key at once, so readers stop seeing it immediately. DEL also frees the memory on the main thread, which blocks for a big value. UNLINK frees the memory in another thread, so the main thread moves on.

### How would you reduce Redis memory use?

Give cache keys TTLs so old data leaves. Store an object as one small hash instead of many separate keys, because small hashes use the compact encoding. Keep values small, split big keys, and set maxmemory with a policy as the safety net.
