## Why it exists

Redis serves commands one at a time from RAM. One slow command on a huge value delays everyone, and memory is the main cost.

## How it works

| Problem | Find it | Fix |
|---|---|---|
| Huge hash, list or set | `redis-cli --bigkeys` | Split into smaller keys; read parts (HMGET), not HGETALL |
| Key uses lots of memory | `redis-cli --memkeys` | Smaller values |
| Delete stalls the server | Slow log | `UNLINK` instead of `DEL` |

- Small collections stay in listpack (intset for integer sets) until a size limit, then convert automatically.
- Too many reads on one key is a hot key: see [cache problems](card:cache-problems).

## Example

```text
HSET merchant:42:config upi on card on wallet off
OBJECT ENCODING merchant:42:config   -> "listpack"
SCARD payment:history:2025           -> 12000000   -- a big key
UNLINK payment:history:2025          -> 1   -- freed in the background
```

## Defaults

| What | Default | Where |
|---|---|---|
| Hash stays listpack | ≤ 512 fields, values ≤ 64 bytes | Redis Open Source 8.10 redis.conf |
| Set stays intset | ≤ 512 integers | Redis Open Source 8.10 redis.conf |

## Interview Qs

### What is a big key and why is it a problem?

A value with very many elements or bytes. Redis runs commands one at a time, so an O(N) read or a DEL on it blocks every other client. Find it with redis-cli --bigkeys.

### DEL vs UNLINK?

Both remove the key at once. DEL frees the memory in the main thread, which blocks on a big value; UNLINK frees it in another thread.
