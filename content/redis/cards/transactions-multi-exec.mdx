## What it is

A Redis transaction is a group of commands that Redis runs one after another with no other client's command in between. You start it with MULTI. Redis then stores, or queues, each command you send instead of running it, and replies QUEUED. EXEC runs the whole queue and returns all the replies as one list. WATCH, sent before MULTI, makes EXEC conditional: if a watched key has changed since, EXEC runs nothing.

## Why it exists

Marking payment 9001 as PAID and adding its 50000 paise to merchant 42's daily total are two commands. Sent separately, another client can read between them and see a paid payment missing from the total, and an app crash after the first leaves the second undone. With MULTI/EXEC Redis runs both together, and if the app disconnects before EXEC, neither runs. "Only if still PENDING" needs a check too: WATCH spots a change by another client, so you retry instead of overwriting it. This is optimistic locking: you take no lock and detect a conflict at write time.

## How it works

  R-->>A: QUEUED, QUEUED

  else changed after WATCH
    R-->>A: nil (nothing ran)
  end`}
/>

1. The app sends WATCH payment:9001. From now on Redis notes any change to that key: a write by any client, an expiry or an eviction.
2. The app reads the status with GET and decides in Java. It is PENDING, so the app goes on.
3. The app sends MULTI and then the two writes. Each one replies QUEUED; nothing has run yet.
4. The app sends EXEC. If the key is unchanged, Redis runs the queued commands in order, with no other client in between, and returns one reply per command.
5. If the key changed, EXEC replies nil and runs nothing. The app starts again from step 1. Either way, EXEC ends the WATCH.

So MULTI/EXEC keeps the writes together, and WATCH adds the check.

## Example

The payment service marks payment 9001 as paid and adds its amount to the merchant total, in redis-cli:

```bash
WATCH payment:9001
GET payment:9001
MULTI
SET payment:9001 PAID
INCRBY merchant:42:paise:2026-10-21 50000
EXEC
```

```text output
OK
"PENDING"
OK
QUEUED
QUEUED
1) OK
2) (integer) 50000
```

What to notice:

- The GET comes before MULTI. Inside MULTI it would only reply QUEUED, and its value would arrive at EXEC, too late to decide anything.
- EXEC returns one reply per queued command, in the order you sent them.
- If another client had changed payment:9001 between WATCH and EXEC, EXEC would reply `(nil)` and neither write would run.
- Without WATCH both writes still run together, but nothing stops you from marking PAID a payment that another server has just marked FAILED.

## Rules and defaults

- **Run-time error:** a command that fails when EXEC runs it, such as WRONGTYPE, fails alone. The other commands still run, and nothing is rolled back.
- **Queue-time error:** if a command is rejected while queueing, for bad syntax or because Redis is out of memory, EXEC refuses the whole transaction with EXECABORT (Redis 2.6.5+).
- **DISCARD:** drops the queue and ends the transaction; none of the commands runs.
- **WATCH:** expiry and eviction count as changes too (Redis 6.0.9+). EXEC, DISCARD and closing the connection unwatch every key; UNWATCH does it by hand.
- **Redis Cluster:** all keys in one transaction must be in the same hash slot, as you will see in [Redis Cluster](card:redis-cluster).
- **One string key:** `SET … IFEQ PENDING` (Redis 8.4+) does this check in [one command](card:single-command-atomicity), with no WATCH and no retry loop.

## Not to be confused with

A SQL transaction runs your statements one by one, lets you read and decide in the middle, and undoes everything on ROLLBACK or on an error. A Redis transaction queues commands and runs them together at EXEC; you cannot act on a read inside it, and it never undoes a command. Rule: SQL transaction = all or nothing; Redis transaction = all together, no rollback.

## Common mistakes

- **"In Spring I can call multi(), then a few RedisTemplate methods, then exec()."** Each RedisTemplate call may use a different connection, so the commands can miss the transaction. Run them inside a `SessionCallback`, which keeps one connection.

## Interview Qs

### How is a Redis transaction different from a SQL transaction?

Both run as one isolated unit, but Redis never rolls back: if one command fails at run time, the others still apply. You also cannot use a read inside the transaction to decide the next command, because replies arrive only at EXEC. Instead of locking rows, WATCH detects a change and cancels EXEC.

### When does EXEC return nil?

When a key you watched changed between WATCH and EXEC: another client wrote it, or it expired or was evicted. None of the queued commands ran. The app reads the key again and retries, or gives up if the new value means it should not write.

### How do you run MULTI/EXEC from Spring Data Redis?

Inside a `SessionCallback`, passed to `redisTemplate.execute(...)`. Inside it you call `multi()`, the commands and `exec()` on the same operations object, so they all use one connection. Plain RedisTemplate calls may each take a different connection and break the transaction.
