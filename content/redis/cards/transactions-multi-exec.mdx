## Why it exists

Some updates touch several keys, or must check a value first. MULTI/EXEC makes the writes one isolated step; WATCH adds optimistic locking for the check.

## How it works

<Steps label="Optimistic update with WATCH">
  <Step title="WATCH">Mark payment:PAY101; Redis notes any change to it.</Step>
  <Step title="Read and decide">GET the status and check it in the app.</Step>
  <Step title="MULTI">Start the queue; each command replies QUEUED.</Step>
  <Step title="EXEC">Runs all, or returns nil if the key changed (a write, expiry or eviction).</Step>
  <Step title="Retry on nil">Start again from WATCH.</Step>
</Steps>

- DISCARD drops the queue; nothing runs.
- In [Redis Cluster](card:redis-cluster) all keys of one transaction must share a hash slot.
- For one string key, `SET … IFEQ` (Redis 8.4+) does this check in [one command](card:single-command-atomicity).

## Example

```text
WATCH payment:PAY101
GET payment:PAY101                          -- "PENDING": the app may go on
MULTI
SET payment:PAY101 PAID
INCRBY merchant:42:paise:2026-10-20 50000
EXEC                                        -- nil if PAY101 changed since WATCH
```

## Interview Qs

### How is a Redis transaction different from a SQL transaction?

Both run as an isolated unit, but Redis never rolls back: if one command fails at run time, the others still apply. You cannot act on reads inside it, and WATCH detects changes instead of locking rows.

### When does EXEC return nil?

When a key you watched was changed by another client, or expired or was evicted, between WATCH and EXEC. Nothing ran; read again and retry.

### How do you run MULTI/EXEC from Spring Data Redis?

Inside a `SessionCallback`, so every command uses the same connection; plain `RedisTemplate` calls may use different ones.
