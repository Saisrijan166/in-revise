## What it is

A stream is a key that holds an append-only log: new entries are only added at the end, and reading them does not remove them. Each entry has an id made from the time in milliseconds and a sequence number, plus a few field-value pairs, like a small [hash](card:hashes). A consumer group is a named set of workers reading one stream together: Redis gives each entry to one worker of the group and remembers which entries each worker has not yet confirmed.

## Why it exists

A [list](card:lists) works as a job queue, but a popped job is gone: if the worker crashes halfway, the payment event is lost, and no second service can read the same events. A stream keeps every entry, so several services can each read all of them, and a consumer group tracks each delivery until the worker confirms it. A crashed worker's events wait to be retried instead of disappearing.

## How it works

1. The payment service calls `XADD payments * ...`. Redis gives the entry a new, larger id and appends it.
2. `XGROUP CREATE` makes the group `billing` once. The id `$` means "start with entries added from now on"; `0` would mean "from the start".
3. A worker calls `XREADGROUP ... STREAMS payments >`. The `>` asks for entries never given to anyone in the group. Redis hands them over and records them in the group's pending entries list (PEL).
4. The worker processes the event and calls `XACK`. Redis removes the id from the pending list.
5. If a worker never acknowledges, its entries stay pending. Another worker can take them over with `XAUTOCLAIM` once they have been idle long enough.

So the key is: reading hands an entry out, and only XACK marks it done.

## Example

The payment service publishes "payment 9001 paid", and a billing worker reads it.

```bash
redis-cli XGROUP CREATE payments billing '$' MKSTREAM
redis-cli XADD payments MAXLEN '~' 100000 '*' payment 9001
redis-cli XREADGROUP GROUP billing worker-a COUNT 10 STREAMS payments '>'
```

```text output
OK
"1792647617474-0"
1) 1) "payments"
   2) 1) 1) "1792647617474-0"
         2) 1) "payment"
            2) "9001"
```

After processing, the worker acknowledges the entry, and the pending list is empty again.

```bash
redis-cli XACK payments billing 1792647617474-0
redis-cli XPENDING payments billing
```

```text output
(integer) 1
1) (integer) 0
2) (nil)
3) (nil)
4) (nil)
```

What to notice:

- `MKSTREAM` created the empty stream together with the group. Without it, `XGROUP CREATE` fails on a missing key.
- The id `1792647617474-0` is the server time in milliseconds plus sequence 0, so you can also read entries by time range.
- `MAXLEN ~ 100000` keeps the stream near 100,000 entries; `~` lets Redis trim in whole blocks, which is cheaper than an exact cut.
- `XPENDING` reports 0 pending entries because `XACK` removed the id. Without the XACK it would report 1 entry, owned by worker-a.

## Rules and defaults

- **Entry ids:** `<milliseconds>-<sequence>`, always increasing, even if the server clock moves back.
- **`>` versus another id:** `>` returns new entries; any other id, such as `0`, returns the worker's own pending entries, which is how a restarted worker finishes old work.
- **Delivery:** at-least-once with XACK. `NOACK` skips the pending list, so a crash loses the entry.
- **Duplicates from producers:** since Redis 8.6, XADD can use producer and message ids (IDMP) to drop a retried XADD.
- **Cost:** adding an entry is O(1); trimming during XADD costs more.

## Not to be confused with

A consumer group is one reader of the whole stream, usually one per service: it gets every entry. A consumer is one worker inside a group: it gets only its share of that group's entries. Rule: one group per service that needs all events; one consumer per worker that splits the load. How a stream differs from a [list](card:lists) is covered there.

## Interview Qs

### What happens if a consumer crashes before XACK?

The entry stays in the group's pending entries list. When the consumer restarts, it re-reads its pending entries with id 0 and processes them. If it never returns, another consumer takes them with XAUTOCLAIM (Redis 6.2+) after a minimum idle time. The entry may be processed twice, so handlers must be idempotent: running them twice has the same effect as once.

### Why does a stream need trimming, and how do you trim it?

Reading does not remove entries, so a stream grows until you trim it. Add `MAXLEN ~ 100000` or `MINID` (Redis 6.2+) to XADD, or run XTRIM. The `~` lets Redis remove only whole internal nodes, which is much cheaper than an exact cut and keeps at least the number you asked for.

### Redis Streams or Kafka?

Streams fit when you already run Redis and the history fits in memory: groups, acknowledgements and replay. Kafka keeps events on disk for as long as you configure and spreads topics over partitions and brokers, so it suits long retention and very high volumes.
