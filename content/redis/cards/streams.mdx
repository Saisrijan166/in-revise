## Why it exists

Pub/Sub loses messages when a reader is away, and a popped list item is gone. A stream keeps every event, and lets several workers share the load with acknowledgements.

## How it works

<Mermaid
  alt="The payment service appends events to the stream payments with XADD. The consumer group billing reads from it. Worker A and worker B each get different entries with XREADGROUP. Each worker sends XACK after processing; entries not yet acknowledged sit in the group's pending entries list."
  chart={`flowchart LR
  P[Payment service] -- XADD --> S[(stream: payments)]
  S --> G{{group: billing}}
  G -- entry 1 --> A[Worker A]
  G -- entry 2 --> B[Worker B]
  A -- XACK --> G
  B -- XACK --> G`}
/>

- XREADGROUP with ID `>` gives new entries; with `0` it re-reads your own pending ones.
- Since Redis 8.6, XADD can drop duplicate retries from a producer (IDMP).
- Stream, list or Pub/Sub for a queue: [queues](card:queues-with-redis).

## Example

```text
XGROUP CREATE payments billing $ MKSTREAM     -- OK (only new entries)
XADD payments MAXLEN ~ 100000 * order PAY101 status SUCCESS  -- "1792490400000-0"
XREADGROUP GROUP billing worker-a COUNT 10 BLOCK 2000 STREAMS payments >
XACK payments billing 1792490400000-0          -- 1
XPENDING payments billing                      -- what is still unacked
```

## Interview Qs

### What happens if a consumer crashes before XACK?

The entry stays in the group's pending entries list. When it restarts it re-reads with ID 0; if it never returns, another consumer takes the entry with XAUTOCLAIM (Redis 6.2+) after an idle time.

### Redis Streams or Kafka?

Streams fit when you already run Redis and the history fits in memory: groups, acks, replay. Kafka keeps events on disk for as long as you configure and spreads topics over partitions, so it suits long retention and big volumes.
