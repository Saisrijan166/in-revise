## What it is

Key design is how you name your keys and how you find them again. Redis has no tables: all keys of a database sit in one flat keyspace, the set of all its keys, so the name is your only structure. The usual convention is object type, id and an optional field, separated by colons, such as `payment:9001:attempts`. To find keys that match a pattern, you walk the keyspace with `SCAN`, a command that returns a few keys per call.

## Why it exists

If the order service and the payment service both write a key named `9001`, one overwrites the other, because [Redis](card:what-is-redis) does not separate them. Clear names prevent such clashes and tell a reader what each key holds. Finding keys has its own danger: `KEYS payment:*` checks every key inside one command, and since commands run one at a time, millions of keys freeze every other client until it ends.

## How it works

<Mermaid
  alt="SCAN loop. The client calls SCAN 0. Redis checks a small batch of keys and returns the next cursor plus the matching keys. The client calls SCAN again with that cursor. When the returned cursor is 0, the scan is complete."
  chart={`flowchart LR
  S([SCAN 0]) --> B[Redis checks a small batch]
  B --> R[Returns next cursor + matches]
  R --> C{Cursor is 0?}
  C -- no --> N[SCAN with that cursor] --> B
  C -- yes --> D([Done])`}
/>

1. You call `SCAN 0` to start. The 0 is the cursor, a bookmark that tells Redis where to continue.
2. Redis checks a small batch of keys, keeps those that fit `MATCH`, and returns them with the next cursor.
3. You call `SCAN` again with that cursor. Between your calls, other clients' commands run normally.
4. You stop when the returned cursor is 0. Every key that existed for the whole scan was returned at least once.

So the key is: many small steps instead of one giant command.

## Example

The database holds 200 session keys and three payment keys. The payment service looks for the payment keys.

```bash
redis-cli SCAN 0 MATCH 'payment:*'
redis-cli SCAN 24 MATCH 'payment:*'
redis-cli --scan --pattern 'payment:*'
```

```text output
1) "24"
2) 1) "payment:9003"
1) "20"
2) (empty array)
"payment:9003"
"payment:9001"
"payment:9002"
```

What to notice:

- The first call returns cursor 24 and one match. The number is only a bookmark, not a count of keys, and it changes from server to server.
- The second call returns no keys, because `MATCH` filters after Redis picks the batch. An empty batch does not mean the scan is over; only cursor 0 does.
- `redis-cli --scan --pattern` runs the whole loop for you and prints every match. It is the safe way to list keys from a terminal.

## Rules and defaults

- **Naming:** use `type:id:field` with colons. The payment service uses these keys:

| Key | Holds |
|---|---|
| `payment:9001` | the cached payment record |
| `payment:9001:attempts` | its retry counter |
| `merchant:42:config` | the merchant's settings |
| `lock:payment:9001` | the lock token |
| `rate:user:7:upi` | a request counter |

- **Length:** `user:1000:followers` is better than `u1000flw`, but a 1 KB key wastes memory and makes lookups compare more bytes. The maximum key size is 512 MB.
- **Numbered databases:** a standalone server has 16 databases by default, chosen with `SELECT`. Redis Cluster supports only database 0, so a key prefix is the portable way to separate data.
- **SCAN options:** `COUNT` is 10 by default and only a hint; `TYPE hash` returns keys of one type only (Redis 6.0+).
- **KEYS:** for debugging only, never in application code.

## Not to be confused with

`KEYS` returns every matching key in one call and blocks the server while it runs. `SCAN` returns a few keys per call with a cursor, so other commands run in between. Rule: `KEYS` only in a debug session on a tiny database, `SCAN` everywhere else.

## Common mistakes

- **"SCAN returns each key exactly once."** A key can come back twice, so the code must cope with duplicates, for example by collecting the keys in a set.
- **"Scan the keyspace on every request."** If the app often needs "all pending payments", keep their ids in a Redis [set](card:sets) and read that set instead.

## Interview Qs

### KEYS vs SCAN?

KEYS returns all matches in one command, O(N) over every key, and blocks all clients meanwhile. SCAN walks the keyspace in small steps with a cursor, so it is safe in production. The cost: a key may be returned twice, and MATCH filters after each batch, so some calls return nothing.

### How do you name Redis keys?

Use object-type:id:field with colons, such as payment:9001:attempts, plus a service prefix when several services share one Redis. Keep names readable; very long keys cost memory and lookup time.

### How do you delete all keys that match a pattern without hurting production?

Walk the keys with SCAN and MATCH, and delete each batch with UNLINK, which frees memory in the background; you will see it in [big keys and memory use](card:memory-optimization). Never run KEYS first to collect them.
