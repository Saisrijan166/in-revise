## What it is

A geospatial index stores places as points and finds the ones near a location. In Redis it is a [sorted set](card:sorted-sets) underneath: each member is a place name, and its score is a geohash, one number made by interleaving the bits of the longitude and the latitude. Points that are close on the map get scores that are close together, so Redis can search a small range of scores instead of every point.

## Why it exists

"Show payment kiosks near me" needs a distance search. Without a geo index, the app would load every kiosk and compute every distance itself, or run a separate geo database. Redis stores the points in memory and answers "within 5 km, nearest first" in one command.

## How it works

<Mermaid
  alt="GEOADD takes a longitude, a latitude and a member name. Redis interleaves the bits of the two coordinates into a 52-bit geohash and stores it as the member's score in a sorted set. GEOSEARCH then reads nearby score ranges to return members within a radius or box."
  chart={`flowchart LR
  A["GEOADD lon lat member"] --> H[52-bit geohash]
  H --> Z[(sorted set score)]
  Z --> S["GEOSEARCH BYRADIUS 5 km"]`}
/>

1. `GEOADD key longitude latitude member` checks the coordinates are in range and turns them into a 52-bit geohash.
2. Redis stores the member in the sorted set with that geohash as its score.
3. `GEOSEARCH` takes a centre (a longitude and latitude, or an existing member) and a shape: a radius or a box.
4. Redis reads the score ranges that cover the shape, then keeps only the members really inside it and computes their distances.

## Example

The payment service indexes two kiosks in Bengaluru and finds those within 5 km of a user.

```bash
redis-cli GEOADD kiosks 77.5946 12.9716 kiosk:mg-road 77.6408 12.9784 kiosk:indiranagar
redis-cli GEOSEARCH kiosks FROMLONLAT 77.60 12.97 BYRADIUS 5 km ASC WITHDIST
redis-cli GEODIST kiosks kiosk:mg-road kiosk:indiranagar km
redis-cli TYPE kiosks
```

```text output
(integer) 2
1) 1) "kiosk:mg-road"
   2) "0.6119"
2) 1) "kiosk:indiranagar"
   2) "4.5200"
"5.0647"
zset
```

What to notice:

- Each `GEOADD` triple is longitude, latitude, name. 77.59 is Bengaluru's longitude, and it comes first.
- `ASC` sorted the results nearest first, and `WITHDIST` added each distance in kilometres.
- `TYPE` says `zset`: the geo index is a plain sorted set, so `ZREM kiosks kiosk:mg-road` removes a kiosk and `ZCARD` counts them.

## Rules and defaults

- **Valid ranges:** longitude -180 to 180; latitude -85.05112878 to 85.05112878. Points nearer the poles cannot be indexed, and GEOADD returns an error for them.
- **Accuracy:** Redis treats the Earth as a sphere, so a distance can be off by up to 0.5% in the worst case.
- **Commands:** `GEOSEARCH` (Redis 6.2+) replaces the deprecated `GEORADIUS` and `GEORADIUSBYMEMBER`. `GEODIST` gives a distance; `GEOPOS` returns a member's coordinates.
- **Units:** `m`, `km`, `mi` or `ft`.

## Interview Qs

### How would you find the nearest merchants to a user?

GEOADD every merchant once with longitude and latitude. On each request, GEOSEARCH from the user's position BYRADIUS, sorted ASC, with COUNT to limit the results and WITHDIST to show distances. When a merchant moves, GEOADD it again; when it closes, ZREM it.

### What are the limits of Redis geo?

Points beyond about 85.05 degrees latitude cannot be indexed. Distances assume a perfect sphere, so they can be off by up to 0.5%. GEOSEARCH works by radius or box only. For polygons, such as a town boundary, use GEOSHAPE fields in the Redis Query Engine; for routes, use a dedicated geo system.
