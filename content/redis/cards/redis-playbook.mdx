## Why it exists

Most Redis questions are "which tool for this problem?". One table answers them all, so each concept page only explains its own tool.

## How it works

|You need (payments)|Reach for|Concept|
|---|---|---|
|Fast reads of merchant config|String with TTL; hash for field updates|[Cache-aside](card:cache-aside)|
|Payments per merchant today|INCR, HINCRBY|[Atomic commands](card:single-command-atomicity)|
|Top merchants by volume|Sorted set|[Sorted sets](card:sorted-sets)|
|Last 10 payments of a user|List, LPUSH + LTRIM|[Lists](card:lists)|
|Payment ids already seen|Set|[Sets](card:sets)|
|Unique payers, millions|HyperLogLog (approximate)|[HyperLogLog](card:bitmaps-hyperloglog)|
|One worker per payment|SET NX PX with a token|[Locks](card:distributed-locks)|
|UPI attempts per user|Counter with TTL, or Lua bucket|[Rate limits](card:rate-limiting-with-redis)|
|Login shared by all instances|Hash with TTL|[Sessions](card:session-storage)|
|Receipt jobs, payment events|List, or stream with groups|[Queues](card:queues-with-redis)|
|Live alerts to online screens|Pub/Sub, no history|[Pub/Sub](card:pub-sub)|
|Merchants within 5 km|Geo index|[Geospatial](card:geospatial)|
|Search merchants by field|JSON + Query Engine|[JSON](card:json-and-query-engine)|

## Interview Qs

### Which Redis data types have you used, and for what?

Name three with a reason: strings for cached values and counters, sorted sets for a leaderboard, hashes for objects updated field by field. Add one non-obvious pick, such as HyperLogLog for unique visitors.

### Where does Redis fit in a payment service?

Around the database, not instead of it: cached merchant config, attempt limits, a processing lock per payment and short-lived status. The payment record stays in the database.
