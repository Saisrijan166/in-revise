## What it is

The Redis playbook is a fixed order of questions for answering any Redis design question. It ties the earlier concepts together: you first say how the data is read and changed, and that picks the data type. Then you add the key name and its TTL, make updates safe when two servers change the same key, say what happens if data is lost, and plan for Redis being down.

## Why it exists

Most Redis interview questions are "which tool would you use for this?" in disguise. Without a frame, candidates name the type they know best, often a JSON string, and forget the TTL, the race or the outage. A fixed order of questions makes the answer complete, and the picker table below turns each common need into one Redis tool.

## How it works

| You need (payments) | Reach for | Concept |
|---|---|---|
| Fast reads of merchant config | String with a TTL; hash for field updates | [Cache-aside](card:cache-aside) |
| Payments per merchant today | INCR, HINCRBY | [Atomic commands](card:single-command-atomicity) |
| Top merchants by volume | Sorted set | [Sorted sets](card:sorted-sets) |
| Last 10 payments of a user | List, LPUSH + LTRIM | [Lists](card:lists) |
| Payment ids already seen | Set | [Sets](card:sets) |
| Unique payers, millions | HyperLogLog (approximate) | [HyperLogLog](card:bitmaps-hyperloglog) |
| One worker per payment | SET NX with a token and a TTL | [Locks](card:distributed-locks) |
| Login attempts per user | Counter with a TTL, or a Lua bucket | [Rate limits](card:rate-limiting-with-redis) |
| Login shared by all instances | Hash with a TTL | [Sessions](card:session-storage) |
| Receipt jobs, payment events | List, or a stream with consumer groups | [Queues](card:queues-with-redis) |
| Live alerts to open screens | Pub/Sub, no history | [Pub/Sub](card:pub-sub) |
| Merchants within 5 km | Geo index | [Geospatial](card:geospatial) |
| Search merchants by field | JSON with the Query Engine | [JSON](card:json-and-query-engine) |

1. **Shape:** ask how the data is read and changed: as a whole value, one field at a time, by rank, as unique members, or in arrival order. The table turns the answer into a type.
2. **Key and life:** name the key `type:id` (see [key design](card:key-design)), give it a [TTL](card:ttl-and-expiration), and rely on [maxmemory and an eviction policy](card:eviction-policies) when memory fills.
3. **Races:** if two app servers can change the same key, make each read-then-write one command, such as INCR, or one script.
4. **Loss and growth:** say what is lost if Redis restarts, and keep valuable records in the database. Add replicas for reads and failover, and [Cluster](card:redis-cluster) when one node's memory or writes are not enough.
5. **Redis down:** give each use its fallback, as in [When Redis is slow or down](card:redis-failure-handling).

## Example

The frame applied to one payment: a customer pays ₹500 by UPI, and the payment id is 9001.

<Steps label="Customer pays ₹500 for payment 9001 by UPI">
  <Step title="Shape">The app polls the status of payment 9001 every few seconds as a whole value, so it is a string. Every payment reads merchant 42's config: a JSON string, or a hash if its fields change one at a time.</Step>
  <Step title="Key and life">`payment:9001:status` lives 10 minutes. `merchant:42:config` has a TTL, and its key is deleted after each committed update.</Step>
  <Step title="Races">INCR counts login attempts on `rate:user:7:login`. Only the worker holding `lock:payment:9001` captures the payment.</Step>
  <Step title="Loss and growth">The ₹500 payment row lives in PostgreSQL, so losing Redis data costs cache misses and reset counters, not payments. Cluster comes later, if one node is not enough.</Step>
  <Step title="Redis down">Config falls back to the database with capped load, the login limiter fails closed, and workers retry the lock later.</Step>
</Steps>

## Not to be confused with

For one object, a string stores the whole value as one blob, a hash stores flat named fields, and JSON stores a nested document that can be changed by path. Rule: string if you always read and write the whole object, hash if fields change on their own, JSON if it is nested.

For messages, Pub/Sub delivers only to clients listening right now, a list is a queue where each item goes to one worker, and a stream keeps a log that groups read, acknowledge and replay. Rule: Pub/Sub for live alerts, a list for simple jobs, a stream when nothing may be lost.

## Interview Qs

### Which Redis data types have you used, and for what?

Name three with a reason: strings for cached values and counters, sorted sets for a leaderboard, and hashes for objects updated field by field. Add one less obvious choice, such as a HyperLogLog for counting unique visitors in at most 12 KB.

### Where does Redis fit in a payment service?

Beside the database, not instead of it: cached merchant config, login attempt limits, a processing lock per payment and short-lived status. The payment record itself stays in the database, which is the source of truth.

### What would you not keep in Redis?

The only copy of data you cannot lose, such as payment records, because persistence settings decide how much a crash loses. Also data you must query in many ways with joins, and very large values, which block other clients while Redis reads or deletes them.
