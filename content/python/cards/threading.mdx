## What it is

The `threading` module runs several threads inside one process. A [thread](card:concurrency-vs-parallelism) is a unit of execution that shares the process's memory with the other threads. You create one with `threading.Thread(target=...)`, call `start()` to run it, and `join()` to wait for it to finish. Because threads share memory, they can read and write the same variables, which is handy but needs locks to stay correct.

## Why it exists

A program often waits: for a network reply, a file read, a database answer. While one task waits, the CPU sits idle. Threads let other work run during those waits, so a server handling many slow connections stays busy instead of blocking on one at a time. Without threads you would process requests strictly one after another, wasting all the waiting time.

## How it works

<Steps>
  <Step title="Create">Make a Thread with a target function and its arguments.</Step>
  <Step title="Start">Call start(); the thread begins running alongside the main thread.</Step>
  <Step title="Wait on I/O">During a network or file wait, the GIL is released, so another thread runs.</Step>
  <Step title="Join">Call join() to block until the thread finishes.</Step>
</Steps>

## Example

```python
import threading

def fetch(order_id):
    print(f"fetching order {order_id}")

threads = [threading.Thread(target=fetch, args=(i,)) for i in range(3)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("all done")
```

```text output
fetching order 0
fetching order 1
fetching order 2
all done
```

What to notice: three threads run `fetch` concurrently, then `join()` makes the main thread wait for every one before printing "all done". The exact order of the three fetch lines can vary between runs, because the threads are interleaved.

## Rules and defaults

- `start()` runs the thread once; calling it twice raises `RuntimeError`.
- `join()` blocks the caller until the thread ends; without it the program may exit while threads still run (unless they are daemon threads).
- Shared mutable state needs a `threading.Lock`; plain `+=` on a shared value is not atomic.
- Standard CPython: the [GIL](card:gil) allows one thread to run Python bytecode at a time, released during I/O.

## Common mistakes

- Using threads for CPU-bound work and expecting multi-core speed-up (the GIL blocks it).
- Updating shared data without a lock, causing lost updates or corrupt state.
- Forgetting `join()`, so results are read before the threads have finished.

## Interview Qs

### When should you use threads in Python?

For I/O-bound work: network calls, file or database access, where tasks spend most of their time waiting. The GIL is released during those waits, so other threads run. For CPU-bound work, use multiprocessing instead.

### Why do threads not speed up CPU-bound work in CPython?

Standard CPython has a Global Interpreter Lock that lets only one thread execute Python bytecode at a time. CPU-bound threads cannot run bytecode in parallel, so they finish no faster than one thread would.

### What is a race condition and how do you prevent it?

It is when two threads access shared data at the same time and the result depends on timing, causing lost or corrupt updates. Prevent it by guarding the shared data with a `Lock` so only one thread changes it at a time.
