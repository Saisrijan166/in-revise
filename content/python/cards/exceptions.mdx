## What it is

An **exception** is an error raised while the program runs, such as dividing by zero or reading a missing dict key. You handle it with four blocks: `try` holds the risky code, `except` catches a matching exception type and deals with it, `else` runs only when `try` finished without error, and `finally` always runs for cleanup. The `raise` statement lets you throw an exception yourself. Handling an exception stops it from crashing the program.

## Why it exists

Some failures cannot be prevented by checking first: a file may vanish between the check and the read, a network call may time out, user input may be the wrong type. Without handling, any such error ends the whole program. `try`/`except` lets you catch the specific failure, recover or report it clearly, and keep running — while `finally` makes sure resources are released on every path.

## How it works

<Steps>
  <Step title="try">Run the code that might raise.</Step>
  <Step title="except">If a matching exception is raised, run its handler and continue.</Step>
  <Step title="else">If no exception was raised, run the else block.</Step>
  <Step title="finally">Always run, whether there was an error or not — used for cleanup.</Step>
</Steps>

1. Python checks `except` clauses top to bottom and runs the first type that matches.
2. `else` is for code that should run only on success, kept out of `try` so its own errors are not caught by mistake.
3. `finally` runs even if the `try` or `except` block does a `return`, `break` or `raise`.

## Example

```python
def total(order):
    try:
        return 100 / order["qty"]
    except ZeroDivisionError:
        return 0
    finally:
        print("checked order")

print(total({"qty": 0}))
```

```text output
checked order
0
```

What to notice: the division by zero is caught, so the function returns 0 instead of crashing. `finally` prints *before* the value is returned, proving it runs on every path — even when the `try` block already decided to return.

## Rules and defaults

- `except SomeError as e:` binds the exception object to `e` so you can read its message.
- Order `except` clauses from specific to general; a parent class like `Exception` catches its subclasses.
- Common built-ins: `ValueError` (right type, bad value), `TypeError` (wrong type), `KeyError` (missing dict key), `IndexError` (bad list index), `ZeroDivisionError`.
- `finally` always runs; a bare `except:` catches almost everything, including signals you should not swallow.

## Common mistakes

- Using a bare `except:` or `except Exception`, which hides typos and unrelated bugs.
- Catching the wrong type, like `except KeyError` for an out-of-range list index (that is `IndexError`).
- Putting success-only code inside `try`, so its errors get caught by the same `except` by accident — use `else`.

## Interview Qs

### When does else run versus finally?

`else` runs only if the `try` block completed with no exception; it is skipped when an exception is raised. `finally` runs in every case — success, handled error, or unhandled error — and is used for cleanup like closing files.

### Why avoid a bare except?

A bare `except:` catches everything, including `KeyboardInterrupt`, `SystemExit` and programming typos that surface as `NameError` or `AttributeError`. It hides real bugs and makes the program hard to debug. Catch the specific exception you actually expect instead.

### What is the difference between ValueError and TypeError?

`TypeError` means the value is the wrong type for the operation, like `len(5)`. `ValueError` means the type is right but the value is unacceptable, like `int("abc")`. The string is the correct type for `int()`, but its content cannot be converted.
