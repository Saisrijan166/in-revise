## What it is

A **context manager** is an object that defines setup and cleanup for a block of code. The `with` statement uses it: it calls the object's `__enter__` method to acquire a resource, runs the indented body, then calls `__exit__` to release the resource. The key promise is that `__exit__` runs no matter how the body ends — normally or by raising an exception. `open()` returns a context manager, which is why `with open(...)` closes files for you.

## Why it exists

Resources like files, locks and database connections must be released, or they leak. Doing it by hand means a `try`/`finally` around every use, and one forgotten `finally` keeps a file open or a lock held. A context manager moves that cleanup into `__exit__` once, so every `with` block gets guaranteed release for free, even when the body raises partway through.

## How it works

<Steps>
  <Step title="Enter">`with cm as x:` calls `cm.__enter__()`; its return value is bound to `x`.</Step>
  <Step title="Run the body">Your indented code runs using the resource.</Step>
  <Step title="Exit on success">At the end, `cm.__exit__(None, None, None)` runs to release the resource.</Step>
  <Step title="Exit on error">If the body raises, `__exit__` still runs (with the exception details) before the error propagates.</Step>
</Steps>

1. Returning a true value from `__exit__` would suppress the exception; returning false (the default) lets it propagate.
2. `contextlib.contextmanager` turns a generator into a context manager: code before `yield` is setup, code after is teardown.

## Example

```python
from contextlib import contextmanager

@contextmanager
def tag(name):
    print(f"open {name}")
    yield                    # with body runs here
    print(f"close {name}")

with tag("order"):
    print("writing")
```

```text output
open order
writing
close order
```

What to notice: the lines before and after `yield` are the setup and cleanup; the `with` body runs exactly where `yield` sits. In real code the teardown goes in a `finally` so it still runs if the body raises.

## Rules and defaults

- `__enter__` returns the value bound after `as`; many managers (like locks) return `None`.
- `__exit__(exc_type, exc_value, traceback)` receives the exception if one occurred, else three `None`s.
- `__exit__` returning a truthy value swallows the exception; the default falsy return re-raises it.
- `with a, b:` or `with (a, b):` manages several resources in one statement.

## Common mistakes

- Putting cleanup after `yield` without a `try`/`finally` in a `@contextmanager`; if the body raises, the teardown is skipped.
- Accidentally returning `True` from `__exit__` and silently hiding real exceptions.
- Opening a file without `with` and forgetting to `close()` it, especially on an error path.

## Interview Qs

### What problem does a context manager solve?

It guarantees a resource is cleaned up. The `with` statement runs `__enter__` to acquire, the body, then `__exit__` to release — and `__exit__` runs even if the body raises. This removes hand-written `try`/`finally` and prevents leaked files, locks and connections.

### How do __enter__ and __exit__ work?

`__enter__` does setup and returns the object bound after `as`. `__exit__` does teardown and always runs, receiving the exception type, value and traceback if the body raised. Returning a truthy value from `__exit__` suppresses that exception; the default lets it propagate.

### How do you write a context manager without a class?

Use `contextlib.contextmanager` on a generator with exactly one `yield`. Code before `yield` is the setup, the `with` body runs at the `yield`, and code after it (best wrapped in `finally`) is the cleanup.
