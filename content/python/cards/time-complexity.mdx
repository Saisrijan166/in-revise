## What it is

Time complexity describes how an operation's cost grows with the size of the data, written in Big-O. For Python's built-ins it tells you which container fits a job. A [list](card:lists) is a dynamic array, so index and append are cheap but front edits shift everything. A [dict](card:dictionaries) and a `set` are hash-based, so looking up, inserting, and deleting a key take roughly constant time whatever the size. Knowing these numbers is a frequent interview check.

## Why it exists

Picking the wrong container quietly makes code slow. Using a list for membership tests or as a queue works on small inputs but degrades to O(n) per operation as data grows, turning a loop into O(n squared). Understanding the complexities lets you choose a set for lookups and a deque for a queue up front, so the code stays fast at scale instead of needing a rewrite later.

## How it works

| Operation | Complexity |
|---|---|
| list index `a[i]` | O(1) |
| list append | O(1) amortised |
| list search `x in a` | O(n) |
| list insert/pop at front | O(n) |
| list pop at end | O(1) |
| dict / set lookup, insert, delete | O(1) average |
| sorting (`sorted`, `.sort`) | O(n log n) |

1. Lists are arrays: end operations are cheap, front operations shift every element.
2. Dicts and sets hash the key, so lookups do not scan; worst case is O(n) but average is O(1).
3. Sorting uses Timsort, which is O(n log n).

## Example

```python
from collections import deque

ids = [101, 102, 103]
print(102 in ids)        # O(n): scans the list

id_set = set(ids)
print(102 in id_set)     # O(1) average: hashes

queue = deque(ids)
print(queue.popleft())   # O(1) from the front
```

```text output
True
True
101
```

What to notice: both `in` checks print `True`, but the set check is O(1) average while the list check is O(n). For removing from the front, `deque.popleft()` is O(1), whereas `ids.pop(0)` would be O(n) because the rest shifts.

## Rules and defaults

- Use a `set` or `dict` key for membership and lookups: O(1) average, not a list's O(n).
- Use a `list` as a stack (`append`/`pop` at the end are O(1)).
- Use a `deque` as a queue (`popleft` O(1)); avoid `list.pop(0)` (O(n)).
- Averages assume well-behaved hashing; adversarial or pathological keys can degrade dict/set to O(n).

## Common mistakes

- Using `x in list` for repeated membership tests instead of a set.
- Using `list.pop(0)` or `insert(0, x)` for a queue instead of a deque.
- Assuming dict/set lookups are O(1) worst case; they are O(1) on average, O(n) worst case.

## Interview Qs

### What is the time complexity of looking something up in a list versus a set?

`x in list` is O(n): it scans each element. `x in set` (or a dict key) is O(1) on average, because it hashes the value and jumps to it. Use a set or dict for fast membership.

### Why is a deque better than a list for a queue?

A queue removes from the front. `deque.popleft()` is O(1), but `list.pop(0)` is O(n) because every remaining element shifts left. For FIFO work at scale, deque is far faster.

### What is the complexity of appending to a list?

O(1) amortised. Most appends are constant time; occasionally the list resizes its underlying array, but averaged over many appends the cost per append is still constant.
