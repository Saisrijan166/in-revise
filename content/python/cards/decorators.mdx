## What it is

A decorator is a function that takes another function and returns a new function that adds behaviour around it. Writing `@deco` on the line above a definition is shorthand for `f = deco(f)`: after the definition, the name `f` points to the function that `deco` returned, not the original. Decorators build on closures and first-class functions. They are used for cross-cutting jobs like logging, timing, caching and access checks, without editing the wrapped function itself.

## Why it exists

The same extra step, such as logging every call or measuring how long it takes, is often needed on many functions. Copying that code into each one is repetitive and easy to get wrong. A decorator writes the extra behaviour once and applies it with a single `@` line, keeping the wrapped function focused on its own job and the shared behaviour in one place.

## How it works

<Steps>
  <Step title="Define the decorator">A function that takes `func` and defines an inner `wrapper`.</Step>
  <Step title="Wrapper adds behaviour">`wrapper` does extra work, calls `func(*args, **kwargs)`, and returns its result.</Step>
  <Step title="Return the wrapper">The decorator returns `wrapper`.</Step>
  <Step title="Apply with @">`@deco` rebinds the name to `wrapper`, so every call goes through it.</Step>
</Steps>

1. `@deco` above `def f` runs `f = deco(f)` as soon as the definition is read.
2. The wrapper takes `*args` and `**kwargs` so it can pass through any arguments.
3. `@functools.wraps(func)` on the wrapper copies the original name and docstring across.

## Example

```python
import functools

def log(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@log
def pay(amount):
    return amount

print(pay(100))
```

```text output
calling pay
100
```

What to notice: `@log` turns `pay` into `log(pay)`, so calling `pay(100)` runs the wrapper first. It prints the name, then calls the real `pay` and returns its result. `functools.wraps` keeps `pay.__name__` as `"pay"` instead of `"wrapper"`.

## Rules and defaults

| What | Behaviour |
|---|---|
| `@deco` | equals `f = deco(f)`, applied when the `def` is read |
| Wrapper signature | use `*args, **kwargs` to wrap any function |
| `functools.wraps` | copies `__name__`, `__doc__` and more to the wrapper |
| Without `wraps` | the function reports the wrapper's name, confusing debuggers |
| Stacking | multiple decorators apply bottom-up (nearest the `def` first) |

## Common mistakes

- **Forgetting `functools.wraps`.** The decorated function then shows the wrapper's name and loses its docstring, which breaks introspection.
- **A wrapper that does not return.** If `wrapper` forgets `return func(...)`, every decorated call returns `None`.
- **A fixed wrapper signature.** `def wrapper(x)` only wraps one-argument functions; use `*args, **kwargs`.

## Interview Qs

### What is a decorator?

A function that takes another function and returns a new one that adds behaviour around it. `@deco` above a definition is shorthand for `f = deco(f)`, so the name then points to the wrapper. It is used for logging, timing, caching and similar cross-cutting concerns.

### Why use functools.wraps inside a decorator?

The wrapper replaces the original function, so without help the decorated function reports the wrapper's name and loses its docstring. `functools.wraps(func)` copies the original's `__name__`, `__doc__` and other metadata onto the wrapper, keeping introspection and debugging correct.

### Why does the wrapper usually take *args and **kwargs?

So the decorator works for any function regardless of how many arguments it takes. The wrapper collects whatever arguments come in and passes them straight through with `func(*args, **kwargs)`, instead of being limited to one specific signature.
