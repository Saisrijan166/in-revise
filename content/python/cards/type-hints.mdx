## What it is

**Type hints** annotate the expected types of parameters, return values and variables, such as `def add(a: int, b: int) -> int`. They are optional metadata. Python does *not* check them while running — the code runs the same with or without them. Their job is to help tools: a static type checker like **mypy** reads the hints and reports mismatches before you run, and editors use them for autocomplete, navigation and safer refactoring.

## Why it exists

In a dynamically typed language, nothing tells you what a function expects until it fails at runtime. On a large codebase that is costly. Hints document the intended types right in the signature, catch many bugs ahead of time through a checker, and make editors far more helpful. Because they are ignored at runtime, they add this safety with no performance cost and no change to how the program behaves.

## How it works

```python
def total(prices: list[int]) -> int:
    return sum(prices)

def find_order(oid: int) -> str | None:   # may return nothing
    return {1: "book"}.get(oid)

print(total([100, 250]))
print(find_order(9))
```

```text output
350
None
```

What to notice: the hints describe the shapes — a list of ints in, an int out; an int in, a `str` or `None` out — but Python does not verify them. `find_order(9)` legitimately returns `None`, which the `str | None` hint documents for readers and for mypy.

## Rules and defaults

- Hints are stored (in `__annotations__`) but not enforced; the interpreter never raises a type error from them alone.
- `X | None` (PEP 604) is the modern union syntax, available since Python 3.10; the older form is `typing.Optional[X]`.
- Built-in generics like `list[int]`, `dict[str, int]` work directly since Python 3.9.
- Run a checker such as `mypy file.py` to actually validate the hints.

## Common mistakes

- Believing hints block wrong types at runtime — they do not; only a checker flags them.
- Forgetting to run mypy, so the hints document intent but catch nothing.
- Writing overly strict or wrong hints that fight the real code instead of describing it.

## Interview Qs

### Are Python type hints enforced at runtime?

No. The interpreter ignores them; code with wrong types still runs. Hints are checked by external static tools like mypy or pyright before runtime, and used by editors. They are documentation and tooling input, not runtime constraints.

### How do you say a value can be a string or None?

Use `str | None` (PEP 604, Python 3.10+). It means the value is a `str` or `None`. The older equivalent is `typing.Optional[str]`, which still works and means exactly the same thing.

### What is the benefit of type hints if they are not enforced?

They catch type bugs early through static checkers, document a function's contract in its signature, and power editor features like autocomplete, go-to-definition and safe refactoring. On large or shared codebases this prevents many errors without any runtime cost.
