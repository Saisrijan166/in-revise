## What it is

A mutable object can be changed after it is created without making a new object; its identity (`id`) stays the same. `list`, `dict`, `set` and `bytearray` are mutable. An immutable object cannot be changed; any operation that looks like a change actually builds a new object. `int`, `float`, `bool`, `str`, `tuple`, `frozenset` and `bytes` are immutable. Only immutable (hashable) objects can be used as dictionary keys or set members.

## Why it exists

Mutable types are efficient for data that grows or changes, like a list of orders you keep appending to. Immutable types are safe to share and cheap to reason about: once made, nobody can alter them, so they work as reliable dictionary keys, set members and constants. Hashing needs a value that never changes, which is exactly why only immutable objects are hashable.

## How it works

<Compare id="mutable-immutable" />

1. A mutable object (list, dict, set) is edited in place; its `id` does not change.
2. An immutable object (int, str, tuple) is never edited; an "edit" rebinds the name to a new object.
3. Immutability is shallow: an immutable container fixes its slots, but a mutable object stored in a slot can still change.

## Example

```python
items = ["apple"]       # mutable list
items.append("milk")    # changes in place, same object
basket = (items, "cash")   # tuple holding the list
basket[0].append("bread")  # the list inside still changes
print(basket)
```

```text output
(['apple', 'milk', 'bread'], 'cash')
```

What to notice: the `list` changes in place both times. The `tuple` `basket` is immutable, so you cannot reassign `basket[0]`, but the list it holds is mutable and can still be appended to. Immutability protects the tuple's references, not the objects behind them.

## Rules and defaults

- Mutable: `list`, `dict`, `set`, `bytearray`. Immutable: `int`, `float`, `bool`, `str`, `tuple`, `frozenset`, `bytes`.
- Only immutable, hashable objects can be dict keys or set items; a list as a key raises `TypeError`.
- Immutability is shallow: a mutable object inside an immutable container can still be mutated.

## Common mistakes

- **Thinking tuples are deeply frozen.** A mutable item inside a tuple can still change.
- **Using a list as a dict key.** Lists are unhashable; use a tuple instead.
- **Forgetting aliasing.** Two names on one mutable object share every edit; copy when you need independence, see [shallow vs deep copy](card:shallow-vs-deep-copy).

## Interview Qs

### Which built-in types are mutable and which are immutable?

Mutable: `list`, `dict`, `set`, `bytearray`. Immutable: `int`, `float`, `bool`, `str`, `tuple`, `frozenset`, `bytes`. Mutable objects change in place; immutable ones make a new object on any change.

### Why can't a list be a dictionary key?

Dict keys must be hashable, and hashing needs a value that never changes. Lists are mutable, so their hash could change and break lookups. Use an immutable tuple of the same values instead.

### Is a tuple always immutable?

The tuple's own slots are immutable: you cannot reassign or resize it. But if a slot holds a mutable object like a list, that object can still be changed in place. Immutability is shallow.
