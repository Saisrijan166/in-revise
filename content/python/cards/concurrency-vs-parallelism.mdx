## What it is

Concurrency means many tasks make progress in overlapping periods: a task runs, pauses while it waits, and another runs. A single CPU core can do this by switching between tasks. Parallelism means tasks run at the very same instant, which needs multiple cores truly executing side by side. A **process** is a running program with its own private memory; a **thread** is a smaller unit of execution inside a process that shares that process's memory with other threads.

## Why it exists

These two words are mixed up constantly in interviews, and the mix-up leads to wrong choices. If you think more threads always run faster, you reach for threads on CPU-heavy work where, in standard Python, they cannot run at the same instant. Knowing that concurrency only needs overlapping progress, while parallelism needs real cores, tells you which tool fits: overlap waiting I/O, or split heavy compute across cores.

## How it works

<Compare id="concurrency-parallelism" />

1. Concurrency structures work so tasks can pause and resume, interleaving their progress.
2. One core is enough for concurrency, because only the structure overlaps, not the actual execution.
3. Parallelism needs several cores so code genuinely runs at the same instant.
4. Parallelism is one way to achieve concurrency, but concurrency does not require it.

## Analogy

<Analogy title="One chef vs three chefs" limit="Real CPUs do not get tired or chat; switching between tasks has a small but real cost.">
One chef cooking three dishes, stirring each while another simmers, is concurrency: one worker, overlapping progress. Three chefs each cooking a dish at once is parallelism: real workers running together.
</Analogy>

## Rules and defaults

- One core can be concurrent (interleaving) but never parallel.
- In Python, [asyncio](card:asyncio) and [threading](card:threading) give concurrency for I/O-bound waits; [multiprocessing](card:multiprocessing) gives real parallelism across cores.
- Standard CPython's [GIL](card:gil) stops threads from running Python bytecode in parallel, so threads give concurrency, not CPU parallelism.

## Not to be confused with

A **process** has its own private memory and is isolated; a **thread** lives inside a process and shares its memory. Rule: pick processes for isolation and CPU parallelism, threads for lightweight shared-memory work.

## Common mistakes

- Saying "I made it concurrent so it runs in parallel" on one core, where only interleaving happens.
- Assuming threads give parallel CPU speed-up in standard CPython; the GIL prevents that.
- Confusing a process (own memory) with a thread (shared memory).

## Interview Qs

### What is the difference between concurrency and parallelism?

Concurrency is many tasks making progress in overlapping periods, which one core can do by switching between them. Parallelism is tasks running at the very same instant, which needs multiple cores. Parallelism is one way to be concurrent, not a requirement.

### Can you have concurrency without parallelism?

Yes. On a single core, tasks still interleave their progress, so they are concurrent without ever running at the same instant. This is exactly how an event loop behaves.

### What is the difference between a process and a thread?

A process is a running program with its own private memory and is isolated. A thread runs inside a process and shares its memory, so threads are lighter and share data directly, but need locks to stay safe.
