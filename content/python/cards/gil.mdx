## What it is

The Global Interpreter Lock (GIL) is a lock inside standard CPython that lets only one thread run Python bytecode at a time. Even with many [threads](card:threading), their Python code is executed one thread at a time, not in parallel. The GIL is released during I/O waits and by some C extensions, so threads still overlap waiting work. It is a feature of CPython's implementation, not a rule of the Python language.

## Why it exists

CPython manages memory with reference counting, and updating those counts from several threads at once would corrupt them. The GIL makes the interpreter thread-safe cheaply by allowing just one thread to touch Python objects at a time. Without it, every object operation would need its own fine-grained locking, which historically made single-threaded code slower. The trade-off is that CPU-bound threads cannot use multiple cores.

## How it works

<Steps>
  <Step title="Acquire">A thread takes the GIL to run Python bytecode.</Step>
  <Step title="Run">It executes until it hits a switch point or starts waiting on I/O.</Step>
  <Step title="Release">On I/O, sleep, or periodically, it releases the GIL.</Step>
  <Step title="Hand over">Another thread acquires the GIL and runs; only one holds it at once.</Step>
</Steps>

## Example

```python
import time, threading

def wait_then_print(order_id):
    time.sleep(1)          # GIL released during the wait
    print(f"order {order_id} ready")

start = time.time()
ts = [threading.Thread(target=wait_then_print, args=(i,)) for i in range(3)]
for t in ts: t.start()
for t in ts: t.join()
print(f"done in {time.time() - start:.1f}s")
```

```text output
order 0 ready
order 1 ready
order 2 ready
done in 1.0s
```

What to notice: three one-second waits finish in about one second, not three. The GIL is released during `sleep`, so the threads wait at the same time. If the work were CPU-bound bytecode instead of a wait, the GIL would serialise it and the total would be about three seconds.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| GIL present | Yes | Standard CPython build |
| One thread runs bytecode | Always, when GIL present | CPython |
| GIL released on I/O | Automatic | CPython |
| Free-threaded (no-GIL) build | Opt-in, officially supported | CPython 3.14 (PEP 779) |

- Jython and IronPython have no GIL; it is not part of the language.
- For CPU parallelism on a standard build, use [multiprocessing](card:multiprocessing).

## Common mistakes

- Claiming Python cannot run threads in parallel at all; it overlaps I/O-bound threads fine.
- Thinking the GIL is a language rule; it is a CPython implementation detail.
- Assuming the free-threaded build is the default in 3.14; it is an opt-in build.

## Interview Qs

### What is the GIL and why does it exist?

The Global Interpreter Lock lets only one thread run Python bytecode at a time in standard CPython. It exists to make memory management (reference counting) thread-safe cheaply, without locking every object operation individually.

### Does the GIL make threads useless?

No. The GIL is released during I/O waits, so threads overlap I/O-bound work well. It only stops CPU-bound threads from using multiple cores. For CPU-bound parallelism, use multiprocessing.

### Is the GIL part of the Python language?

No. It is a CPython implementation detail. Other implementations like Jython have no GIL, and CPython 3.14 officially supports an opt-in free-threaded build without it (PEP 779).
