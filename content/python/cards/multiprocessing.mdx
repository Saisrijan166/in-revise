## What it is

The `multiprocessing` module runs work in separate [processes](card:concurrency-vs-parallelism) instead of threads. Each process is a full program with its own memory and its own interpreter, so each has its own [GIL](card:gil). This sidesteps the GIL and lets CPU-heavy work run truly in parallel across cores. Because the processes do not share memory, they talk through inter-process communication (IPC): a `Queue`, a `Pipe`, or shared-memory objects.

## Why it exists

Threads cannot speed up CPU-bound work in standard CPython, because the GIL serialises Python bytecode. When you need to actually use all your cores (hashing many files, image processing, heavy maths), you need separate processes, each free of the others' GIL. `multiprocessing` gives that with an API close to `threading`, so you can parallelise compute without dropping to a lower-level tool.

## How it works

<Compare id="threading-vs-multiprocessing" />

1. `Process(target=f)` describes a worker; `start()` launches it as a new OS process.
2. The child gets its own copy of the needed data (pickled across on the spawn start method).
3. Workers compute on their own core, free of the parent's GIL.
4. Results come back through a `Queue` or `Pipe`; `join()` waits for each process to finish.

## Example

```python
from multiprocessing import Process, Queue

def total(order, q):
    q.put(sum(order))

if __name__ == "__main__":
    q = Queue()
    p = Process(target=total, args=([10, 20, 30], q))
    p.start()
    p.join()
    print(q.get())
```

```text output
60
```

What to notice: the worker cannot change the parent's variables, so it sends its result back through the `Queue`. The launch sits inside `if __name__ == "__main__"`, which stops child processes from re-running it and spawning endlessly.

## Rules and defaults

- Each process has its own memory and GIL, so CPU-bound work runs in parallel.
- Arguments and results crossing processes must be picklable; they are copied, not shared.
- The default start method is `spawn` on Windows and macOS, and (as of Python 3.14) `forkserver` on most Linux; all re-import the module, so guard startup with `if __name__ == "__main__"`.
- Use `Queue`, `Pipe`, or `multiprocessing.shared_memory` to communicate; plain globals do not cross.

## Not to be confused with

A **thread** shares the process's memory and is light but limited by the GIL; a **process** has its own memory and GIL and runs CPU work in parallel. Rule: threads for I/O waits, processes for CPU crunching.

## Common mistakes

- Expecting child processes to see changes to the parent's variables (they get copies).
- Leaving the launch code outside `if __name__ == "__main__"`, causing runaway spawning.
- Passing unpicklable objects (like an open file or a lambda) as arguments.

## Interview Qs

### When should you use multiprocessing instead of threading?

For CPU-bound work: heavy computation that should use several cores. Each process has its own GIL, so they run in parallel. Threads cannot, because the GIL serialises bytecode in standard CPython.

### How do processes share data?

They do not share memory directly. You pass data through IPC: a `multiprocessing.Queue` or `Pipe`, or a shared-memory object. The data is usually pickled to cross the process boundary.

### Why do you need `if __name__ == "__main__"` with multiprocessing?

On the spawn and forkserver start methods, each child re-imports the module. Without the guard, the module-level launch code runs again in every child, spawning more processes and often crashing.
