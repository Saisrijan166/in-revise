## What it is

**Dunder methods** (double-underscore, also called magic or special methods) are methods with names like `__str__` and `__len__` that Python calls behind built-in operations. Defining them lets your objects work with normal syntax: `print(obj)` calls `__str__`, `len(obj)` calls `__len__`, `obj1 == obj2` calls `__eq__`. You rarely call them directly; you implement them so the built-ins and operators do the right thing.

## Why it exists

You want your own types to behave like built-in ones, so that `print`, `len`, `==`, sorting and membership "just work" instead of needing special functions. Python exposes these behaviours through dunder methods: implement the hook and the matching syntax uses it. This keeps a consistent interface across all types, and is why Python code reads the same for a list, a string, or your `Order`.

## How it works

1. Python translates syntax to a dunder call: `len(x)` runs `x.__len__()`, `x == y` runs `x.__eq__(y)`.
2. Define the dunder in your class to supply the behaviour.
3. `__str__` is for a readable, user-facing string; `__repr__` is for an unambiguous, developer-facing one.
4. If `__str__` is missing, `str()` and `print()` fall back to `__repr__`.

## Example

```python
class Order:
    def __init__(self, id, items):
        self.id, self.items = id, items
    def __repr__(self):
        return f"Order({self.id!r}, items={len(self.items)})"
    def __len__(self):
        return len(self.items)
    def __eq__(self, other):
        return self.id == other.id
    def __hash__(self):
        return hash(self.id)

o = Order("A1", ["pen", "book"])
print(repr(o), len(o))
```

```text output
Order('A1', items=2) 2
```

What to notice: `__repr__` gives a clear debug string, `__len__` makes `len(o)` work, and `__eq__` with a matching `__hash__` lets orders compare by id and still be used in sets. Equal orders must hash equal, so `__hash__` uses the same `id`.

## Rules and defaults

- `__repr__` should be unambiguous, ideally valid Python that recreates the object; `__str__` should be readable.
- Defining `__eq__` without `__hash__` sets `__hash__` to `None`, making the object unhashable.
- A mutable object used for equality normally should not be hashable (do not define `__hash__`).
- Other common dunders: `__lt__` (and friends) for ordering, `__getitem__` for indexing, `__call__` to make an object callable, `__enter__`/`__exit__` for context managers.

## Common mistakes

- **Defining __eq__ but not __hash__** and then using the object in a set or as a dict key.
- **Making __hash__ inconsistent with __eq__.** Equal objects must have equal hashes.
- **Only defining __str__.** Debuggers and the REPL use `__repr__`, so define that first.

## Interview Qs

### Difference between __str__ and __repr__?

`__str__` returns a readable string for users, used by `str()` and `print()`. `__repr__` returns an unambiguous string for developers, used in the REPL and debuggers. If `__str__` is missing, Python falls back to `__repr__`.

### Why define __eq__ and __hash__ together?

Hashable collections require equal objects to have equal hashes. If you define `__eq__` without `__hash__`, Python sets `__hash__` to `None`, so the object becomes unhashable and cannot go in a set or be a dict key.

### What are dunder methods?

Special methods named with double underscores, like `__init__`, `__str__`, `__len__` and `__eq__`, that Python calls for built-in operations and operators. Implementing them lets your objects support `print`, `len`, `==`, indexing and more.
