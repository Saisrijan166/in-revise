## What it is

A **custom exception** is your own error type, made by subclassing the built-in `Exception`. It lets callers catch exactly your error, like `OutOfStockError`, instead of a generic one. You signal it with `raise`. Separately, `assert` is a debugging statement: `assert cond, msg` raises `AssertionError` when `cond` is false. It looks like validation but is meant only for internal checks, because Python's `-O` (optimise) mode deletes every `assert` from the bytecode.

## Why it exists

Generic exceptions are hard to handle precisely: catching `Exception` around an order flow also traps bugs you did not mean to. A named type like `OutOfStockError` lets a handler respond to that one case and let others propagate. And knowing that `assert` is stripped under `-O` prevents a dangerous mistake — validating real input with `assert` leaves production with no checks at all.

## How it works

```python
class OutOfStockError(Exception):
    pass

def buy(stock, qty):
    if qty > stock:
        raise OutOfStockError(f"only {stock} left")
    return stock - qty

try:
    buy(2, 5)
except OutOfStockError as e:
    print("rejected:", e)
```

```text output
rejected: only 2 left
```

1. The class inherits from `Exception`, so it is catchable by `except OutOfStockError` and by `except Exception`.
2. `raise` creates and throws the exception with a message, which the `as e` handler reads.
3. Real input checks use `if ... raise`, which survives `-O`, unlike `assert`.

What to notice: the error carries a readable message and is caught by its own type, so other failures would not be hidden. Replacing the `if`/`raise` with `assert qty <= stock` would break under `python -O`.

## Rules and defaults

- Inherit from `Exception` (or a subclass), never `BaseException`, which is reserved for system-exiting events.
- The message passed to the exception is available via `str(e)` and `e.args`.
- `assert cond, msg` raises `AssertionError`; `python -O` removes all assertions and sets `__debug__` to `False`.
- Keep custom exceptions small; add attributes only if handlers need structured data.

## Common mistakes

- Using `assert` for validating user input, config or API data — it is silently removed by `-O`.
- Subclassing `BaseException`, so normal `except Exception` handlers miss the error.
- Raising a bare string or generic `Exception("...")` when a specific named type would let callers handle it cleanly.

## Interview Qs

### How do you create a custom exception?

Subclass `Exception`: `class OutOfStockError(Exception): pass`. Raise it with a message, `raise OutOfStockError("no stock")`, and catch it with `except OutOfStockError`. Inheriting from `Exception` (not `BaseException`) keeps it catchable by ordinary handlers.

### What is the difference between raise and assert?

`raise` deliberately throws an exception and is part of normal control flow. `assert` checks a debug assumption and raises `AssertionError` if false. Crucially, `python -O` strips all `assert` statements, so `assert` must never be used for validation that production depends on.

### Why not use assert for input validation?

Because `python -O` removes every `assert`, the validation would simply not run in optimised mode, letting bad data through. Use an explicit `if` with `raise ValueError(...)` so the check always executes.
