## What it is

**Testing** means writing code that checks your code: you call a function and assert the result. **pytest** is the popular third-party test runner (plain `assert`); **unittest** is the built-in one (class-based). **Logging** is the `logging` module, which records messages at a severity level. **pdb** is the built-in debugger that pauses your program so you can inspect it.

## Why it exists

Without tests, every change risks breaking something silently and you only find out in production. Without logging you sprinkle `print()` calls, then delete them, then add them back for the next bug, with no timestamps or way to filter. The `logging` module and a test runner give you a repeatable safety net and diagnostics you can turn up or down without editing the logic.

## How it works

<Steps label="Checking and diagnosing code">
  <Step title="Test">Write a function that asserts the expected result; pytest or unittest collects and runs it.</Step>
  <Step title="Mock">Replace slow or external parts (a network call, the clock) with unittest.mock fakes.</Step>
  <Step title="Log">Emit messages at a level; set the threshold once so only what you want is shown.</Step>
  <Step title="Debug">Drop breakpoint() where it fails and step through with pdb.</Step>
</Steps>

1. A test fails loudly when the output is wrong, pointing at the line.
2. `coverage` reports which lines your tests actually ran.
3. Logging levels run DEBUG (10) < INFO (20) < WARNING (30) < ERROR (40) < CRITICAL (50); the logger shows its level and above.

## Example

```python
def order_total(order):
    return sum(i["price"] * i["qty"] for i in order["items"])

def test_order_total():
    order = {"items": [{"price": 50, "qty": 2}, {"price": 50, "qty": 1}]}
    assert order_total(order) == 150

test_test = test_order_total()  # pytest would run this for you
print("ok")
```

```text output
ok
```

What to notice: the test is just a function with `assert`. pytest discovers any `test_*` function, runs it, and if the sum were wrong it would show the expected and actual values. No test framework boilerplate is needed for a plain check.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Root logger level | WARNING | `logging` (Python 3.14) |
| pytest test discovery | files/functions named `test_*` | pytest |
| Debugger entry | `breakpoint()` calls pdb | built in since Python 3.7 |

You must call `logging.basicConfig(level=...)` to see INFO or DEBUG; by default they are hidden.

## Common mistakes

- **Using print() instead of logging.** You lose levels, timestamps and the ability to silence output later.
- **Expecting INFO logs to show by default.** The root level is WARNING; lower it first.
- **Mocking too much.** If you fake the thing under test, the test passes but proves nothing.

## Interview Qs

### How is pytest different from unittest?

unittest is built in and class-based: you subclass `TestCase` and use methods like `self.assertEqual`. pytest is third-party and uses plain `assert` with readable failure output, plus fixtures for setup. pytest can also run existing unittest tests.

### Why use logging instead of print?

Logging has severity levels, timestamps and named loggers, and you can change what is shown (or send it to a file) without editing the code. print always goes to stdout with no level or easy way to filter.

### What does unittest.mock do?

It replaces a real object or function with a configurable fake, so a test does not hit a network, database or clock. You can set the fake's return value and assert it was called with the expected arguments.
