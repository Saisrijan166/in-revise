## What it is

The habits a Java or Spring developer must unlearn when reading Python. Python uses indentation instead of braces, decides types at runtime, passes `self` explicitly, treats empty values as false, and separates `==` (value) from `is` (identity). It also has the [GIL](card:gil), which changes how threads behave.

## Why it exists

Java and Python look similar enough that a Java developer assumes they work the same, then gets caught: a shared mutable default argument, a thread pool that does not speed up CPU work, or `is` used where `==` was meant. Knowing the differences up front saves debugging time and answers the "how is Python different from Java?" interview question directly.

## How it works

| Topic | Java | Python |
|---|---|---|
| Blocks | Braces `{ }` and semicolons | Indentation; newline ends a statement |
| Types | Declared and checked | Dynamic; hints optional, not enforced |
| Method receiver | Implicit `this` | Explicit `self` first parameter |
| Variadic args | Overloads / varargs | `*args` and `**kwargs` |
| Value equality | `.equals()` | `==` (calls `__eq__`) |
| Identity | `==` | `is` |
| Overloading | Many methods, same name | Not supported; use defaults / *args |
| CPU-bound threads | Scale across cores | Limited by the GIL; use processes |

1. Truthiness: empty containers, `0`, `""` and `None` are falsy, so `if items:` means "not empty".
2. A mutable default argument (`def f(x=[])`) is created once and shared across calls.
3. The GIL is a CPython detail (standard builds), not a language rule; it serialises bytecode execution.

## Example

```python
a = [1, 2]
b = [1, 2]
print(a == b)      # value equality: same contents
print(a is b)      # identity: same object?
print(bool([]))    # empty list is falsy
```

```text output
True
False
False
```

What to notice: `==` is True because the lists hold the same values (like Java `.equals`), but `is` is False because they are two different objects (like Java `==`). An empty list is falsy, so `if a_list:` tests non-emptiness.

## Rules and defaults

| What | Behaviour | Note |
|---|---|---|
| `==` | Calls `__eq__`, compares value | Like Java `.equals()` |
| `is` | Compares identity | Like Java `==` |
| GIL | One thread runs Python bytecode at a time | CPython standard build |
| Free-threaded build | No-GIL, opt-in | Officially supported via PEP 779 in 3.14 |
| Method overloading | Not supported | Last definition wins; use defaults/*args |

## Common mistakes

- **Using `is` to compare values.** `is` checks identity; use `==` for equality. `is` is only for `None` and singletons.
- **Expecting threads to speed up CPU work.** The GIL serialises it; use `multiprocessing` for parallel CPU work.
- **Reusing a mutable default argument.** `def f(x=[])` shares one list across calls; use `None` and create inside.
- **Writing two methods with the same name.** The second replaces the first; Python has no overloading.

## Interview Qs

### How is Python's == different from Java's ==?

In Java `==` compares references and `.equals()` compares values. In Python it is effectively reversed: `==` compares values (it calls `__eq__`, like `.equals`), and `is` compares identity (same object, like Java's `==`).

### Does Python support method overloading?

Not in the Java sense. If you define two methods with the same name, the second replaces the first. You get similar flexibility with default arguments, `*args`/`**kwargs`, or dispatching on argument types inside one method.

### Why do Python threads not scale CPU-bound work like Java's?

Because of the GIL, a CPython detail that lets only one thread run Python bytecode at a time. Threads still help I/O-bound work (they release the GIL while waiting), but for CPU-bound work you use multiprocessing or the opt-in free-threaded build.
