## What it is

Three special methods cover an object's life. `__new__` actually creates the instance and returns it. `__init__` then initialises that instance, setting its attributes; it is the method people loosely call the **constructor**. `__del__` is a **finaliser**: Python may call it when the object is about to be reclaimed, but the timing is not guaranteed.

## Why it exists

Creating an object and setting it up are two separate jobs. `__new__` handles allocation (and is the only hook for building [immutable](term:immutable) types like `int` or `tuple`), while `__init__` handles the everyday work of filling in attributes. `__del__` exists so an object can react when it is collected, but because Python reclaims memory through reference counting plus a garbage collector, you cannot predict when, so it is unfit for important cleanup.

## How it works

<Steps>
  <Step title="__new__ creates">`Order("A1")` first calls `__new__(cls, "A1")`, which builds and returns a blank instance.</Step>
  <Step title="__init__ initialises">Python then calls `__init__(self, "A1")` on that instance to set its attributes.</Step>
  <Step title="Use the object">The fully built object is returned to you.</Step>
  <Step title="__del__ finalises">Much later, when nothing references it, Python may call `__del__` before reclaiming it.</Step>
</Steps>

## Example

```python
class Order:
    def __new__(cls, id):
        print("creating")
        return super().__new__(cls)

    def __init__(self, id):
        print("initialising")
        self.id = id

o = Order("A1")
```

```text output
creating
initialising
```

What to notice: `__new__` runs first and prints "creating", then `__init__` runs and prints "initialising". `__new__` must `return` the instance (via `super().__new__(cls)`); if it does not, `__init__` is skipped. You rarely write `__new__` yourself.

## Rules and defaults

- `__new__` is implicitly a static method and must return an instance; if it returns something that is not an instance of the class, `__init__` does not run.
- `__init__` must return `None`.
- `__del__` is not guaranteed to run for objects still alive at interpreter exit, and `del x` only drops one reference, it does not call `__del__` directly.
- Prefer a context manager (`with`) or `weakref.finalize` for cleanup.

## Common mistakes

- **Using __del__ as a destructor** for files, sockets or locks. Its timing is unreliable.
- **Forgetting to return from __new__**, which silently skips `__init__`.
- **Thinking del x destroys the object.** It removes one reference; the object lives until its reference count hits zero.

## Interview Qs

### Is __init__ a constructor?

Informally yes, but strictly `__init__` is an initialiser: it sets up an instance that `__new__` has already created and returned. `__new__` is the method that truly constructs the object.

### When should you override __new__?

Rarely: when subclassing an immutable type such as `int`, `str` or `tuple`, or to control instance creation (singletons, caching). For normal classes, `__init__` is enough.

### Why avoid __del__ for cleanup?

Its call time is not guaranteed; reference cycles or interpreter exit can delay it or skip it. Use a context manager (`with`) or `weakref.finalize`, which release resources at a known point.
