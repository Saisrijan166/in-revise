## Why it exists

Every request needs the same steps: find the right code, convert the input, call it, write the output, handle errors. Spring MVC does these steps once, in one servlet, so controllers hold only business logic.

## How it works

<Mermaid
  alt="Spring MVC request flow. The HTTP request passes the servlet filters and reaches DispatcherServlet. A HandlerMapping finds the handler and its interceptors. Interceptors run preHandle. The HandlerAdapter binds the arguments and calls the controller method. If the method has @ResponseBody, an HttpMessageConverter writes the return value, such as JSON. Otherwise a ViewResolver finds the view, which renders HTML. If an exception is thrown, a HandlerExceptionResolver turns it into an error response."
  chart={`flowchart TD
  R([HTTP request]) --> F[Servlet filters]
  F --> DS[DispatcherServlet]
  DS --> HM["HandlerMapping: find handler + interceptors"]
  HM --> PH["Interceptors: preHandle"]
  PH --> HA["HandlerAdapter: bind arguments, call controller"]
  HA --> Q{"@ResponseBody?"}
  Q -- yes --> MC["HttpMessageConverter writes JSON"]
  Q -- no --> VR["ViewResolver: view renders HTML"]
  HA -. exception .-> ER["HandlerExceptionResolver: error response"]`}
/>

- Filters run before DispatcherServlet; interceptors run inside it. See [Filters vs Interceptors](card:filters-interceptors).
- With a [@RestController](card:rest-controller), every method takes the converter path; the `Accept` header picks the format.
- The reactive stack has the same design, with `DispatcherHandler` in place of the servlet.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| DispatcherServlet path | `/` (`spring.mvc.servlet.path`) | Spring Boot 4.1 |
| JSON library | Jackson 3 (`tools.jackson` packages) | Spring Boot 4.0+ |
| URL matching | `PathPattern` (`AntPathMatcher` is deprecated) | Spring Framework 7.0 |

## Interview Qs

### What is the front controller pattern in Spring MVC?

One central servlet, DispatcherServlet, receives every request and runs the shared steps: mapping, argument binding, writing the body or rendering a view, and error handling. Delegate beans such as HandlerMapping and HandlerAdapter do the actual work.

### Walk me through a request to a @RestController.

Filters run first. DispatcherServlet asks a HandlerMapping for the handler and its interceptors, and preHandle runs. The HandlerAdapter binds the arguments (a converter reads @RequestBody) and calls the method. A converter writes the return value as JSON. Exceptions go to the exception resolvers.

### HandlerMapping vs HandlerAdapter?

HandlerMapping decides which handler serves the request. HandlerAdapter knows how to call that kind of handler, such as an annotated method, so DispatcherServlet does not depend on any handler type.
