## What it is

DispatcherServlet is the single entry point of a Spring MVC web app. A servlet is a Java class that a web server such as Tomcat calls for each HTTP request. Spring Boot registers one servlet, DispatcherServlet, in the [embedded server](card:embedded-server), and that servlet hands each request to the right controller method. This design is called the front controller pattern.

## Why it exists

Every request needs the same chores: find the code for this URL, turn the JSON body into an object, call the code, turn the result back into JSON, and handle errors. Without a front controller, each endpoint would repeat these chores. DispatcherServlet does them once, for every request, so a controller method holds only the logic for its own endpoint.

Follow one request, `POST /payments` with the body `{"amount": 500.00, "currency": "INR"}`:

1. Tomcat receives the request and passes it through the servlet filters, such as security. You will see filters in [Filters, Interceptors and AOP](card:filters-interceptors).
2. DispatcherServlet asks a HandlerMapping which method handles `POST /payments`. The answer is `PaymentController.create`.
3. A HandlerAdapter prepares the arguments. An HttpMessageConverter (Jackson, for JSON) reads the body into a `PaymentRequest` object. Then the adapter calls the method.
4. The controller calls `PaymentService`, which saves a `Payment` through `PaymentRepository`.
5. The method returns a `PaymentResponse`. The converter writes it as JSON in the response body.
6. If any step throws an exception, HandlerExceptionResolver beans turn it into an error response, as you will see in [Global Exception Handling](card:exception-handling).

So each layer has one job: the controller speaks HTTP, the service holds the business rules, and the repository talks to the database.

## Example

This is the controller method that the request above reaches. Later web concepts build on this same class.

```java
@RestController
@RequestMapping("/payments")
class PaymentController {
    private final PaymentService service;
    PaymentController(PaymentService service) { this.service = service; }

    @PostMapping                                       // HandlerMapping: POST /payments lands here
    PaymentResponse create(@RequestBody PaymentRequest request) {   // converter: JSON -> object
        return service.create(request);                // converter: object -> JSON
    }
}
```

What to notice:

- The method never touches the raw request or response. DispatcherServlet and its helpers do the reading and writing.
- `@PostMapping` plus `@RequestMapping("/payments")` is what the HandlerMapping matches. A `GET /payments` would not reach this method.
- `@RequestBody` tells the HandlerAdapter to use a message converter for this argument. Without it, Spring would not read the JSON body into the object.

## Rules and defaults

- **Registered for you:** Spring Boot's auto-configuration creates DispatcherServlet and maps it to `/`, so it receives every request path (`spring.mvc.servlet.path`, Spring Boot 4.1).
- **Customising MVC:** add a `WebMvcConfigurer` bean for interceptors, CORS or formatters. Boot's defaults stay in place.
- **Not allowed together:** `@EnableWebMvc` and Boot's MVC auto-configuration. With `@EnableWebMvc` you take full control and Boot backs off.

## Interview Qs

### What is the front controller pattern in Spring MVC?

One central servlet, DispatcherServlet, receives every request and runs the shared steps of request handling. It does not do the work itself. It delegates to helper beans: HandlerMapping finds the method, HandlerAdapter calls it, message converters read and write bodies, and exception resolvers handle errors.

### Walk me through what happens when a REST endpoint is called.

The filters run first. DispatcherServlet asks a HandlerMapping for the matching controller method. A HandlerAdapter binds the arguments, reading the JSON body through a message converter, and calls the method. The controller calls the service and the repository. The return value is written as JSON by a message converter.

### Why are HandlerMapping and HandlerAdapter separate?

HandlerMapping decides which handler serves a request. HandlerAdapter knows how to call that kind of handler. Keeping them apart means DispatcherServlet does not depend on any handler type, so annotated controllers and other handler styles can share the same flow.
