## Why it exists

Installing a server and copying files onto it is slow and easy to get wrong. One self-contained file, or one image, runs the same way everywhere.

## How it works

<Compare id="jar-vs-war-vs-native-image" />

- `java -jar app.jar` starts Spring Boot's launcher, which loads the nested jars, then your main class.
- Buildpacks turn the jar into an OCI image; they need a running Docker daemon.

## Example

```bash
./mvnw package                     # target/app.jar
java -jar target/app.jar           # embedded server starts
./mvnw spring-boot:build-image     # OCI image with buildpacks
./mvnw -Pnative native:compile     # GraalVM native executable
```

## Interview Qs

### What is inside a Spring Boot fat jar?

Your classes in `BOOT-INF/classes`, every dependency jar nested unchanged in `BOOT-INF/lib`, and Spring Boot's loader classes, which read those nested jars because plain Java cannot.

### How do you deploy a Spring Boot app as a war?

Set packaging to `war`, extend `SpringBootServletInitializer`, mark `spring-boot-starter-tomcat` as `provided`, and deploy it to a servlet container. WebFlux apps cannot be deployed as a war.

### When would you build a native image?

When fast startup and low memory matter, such as containers and functions (FaaS). The cost is a closed world: reflection needs hints, and the classpath and beans are fixed at build time.
