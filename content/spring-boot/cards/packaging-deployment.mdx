## What it is

Packaging is how you turn the payment service into something a server can run. Spring Boot's default is an **executable jar**: one file holding your classes, every library, and the [embedded web server](card:embedded-server), started with `java -jar`. The other choices are a **war**, a file you deploy into an existing servlet container such as Tomcat, and a **native image**, a machine executable built by GraalVM that needs no JVM.

## Why it exists

The [embedded server](card:embedded-server) showed why one self-contained jar beats a Tomcat installed on every machine. The packaging problem is how to build that jar: plain Java cannot load a jar that sits inside another jar, and merging all libraries into one jar hides which libraries you ship and breaks when two jars hold a file with the same name. Boot's own jar format and loader solve this. The war and the native image cover the two cases the jar does not fit: a shared servlet container, and apps where JVM startup time and memory are the bottleneck.

## How it works

<Compare id="jar-vs-war-vs-native-image" />

1. `mvn package` compiles your code, and the Spring Boot plugin repackages the jar: classes go to `BOOT-INF/classes`, each dependency jar to `BOOT-INF/lib`, and Boot's loader classes to the root.
2. `java -jar app.jar` starts Boot's launcher, `JarLauncher`, which the manifest names as `Main-Class`. It sets up a class loader that can read the nested jars.
3. The launcher then calls the `main` method of your class, which the manifest names as `Start-Class`. That starts Spring and the embedded server.
4. For a container image, buildpacks take that jar and wrap it with a suitable JVM into an OCI image, the standard container image format that Docker runs, with no Dockerfile.

## Example

The payment service built four ways with Maven:

```bash
./mvnw package                     # target/payment-service.jar
java -jar target/payment-service.jar
./mvnw spring-boot:build-image     # OCI image with buildpacks
./mvnw -Pnative native:compile     # GraalVM native executable
```

What to notice:

- The second line starts the app and its Tomcat on port 8080. No server is installed on the machine.
- `build-image` needs a running Docker daemon, because buildpacks build the image inside Docker.
- `native:compile` takes much longer than a normal build, and needs GraalVM 25 or later with Spring Boot 4.

## Rules and defaults

- **War deployment:** set packaging to `war`, make the main class extend `SpringBootServletInitializer`, and mark `spring-boot-starter-tomcat` as `provided`. The war can still run with `java -jar`.
- **WebFlux:** war deployment is not supported, because WebFlux runs on embedded Reactor Netty, not on a servlet container.
- **Native closed world:** the classpath is fixed at build time and code that cannot be reached is left out. Reflection, resources and proxies need hints.
- **Spring AOT:** for a native image, Spring turns bean definitions into generated Java code and hint files at build time, so beans cannot change at run time. `@Profile` and `@ConditionalOnProperty` are therefore limited.

## Common mistakes

- **"A native image is always the better choice."** It builds slowly, and libraries that use reflection may need extra hints. For a long-running service, the normal JVM is usually fine.

## Interview Qs

### What is inside a Spring Boot fat jar?

Your classes in `BOOT-INF/classes`, every dependency jar nested unchanged in `BOOT-INF/lib`, and Spring Boot's loader classes at the root. The manifest points `java -jar` at the loader, which reads the nested jars, because plain Java cannot, and then calls your main class.

### How do you deploy a Spring Boot app as a war?

Set packaging to `war`, extend `SpringBootServletInitializer` and override `configure`, mark `spring-boot-starter-tomcat` as `provided`, and deploy the file to a servlet container. WebFlux applications cannot be deployed this way.

### When would you build a native image?

When fast startup and low memory matter, such as in containers that scale up often and in functions (FaaS). The cost is a slow build and a closed world: reflection needs hints, and the classpath and beans are fixed at build time.
