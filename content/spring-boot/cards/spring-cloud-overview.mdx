## Why it exists

Splitting an app into services adds new problems: where config lives, how services find each other, one entry point, and calls that fail. Spring Cloud answers each with a Boot-style library.

## How it works

| Problem between services | Spring Cloud answer |
| --- | --- |
| Config spread over many apps | [Config Server](card:config-server) |
| Instances come and go | [Eureka](card:service-discovery-eureka), Consul or Kubernetes |
| One door for all clients | [Spring Cloud Gateway](card:spring-cloud-gateway) |
| A called service is failing | [Circuit breaker and retry](card:resilience4j) |
| Events between services | [Kafka](card:spring-kafka), Spring Cloud Stream |

- One release train BOM sets every Spring Cloud version; Boot does not manage it.
- Calling another service by name uses [HTTP clients](card:http-clients) with Spring Cloud LoadBalancer.

## Example

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.cloud</groupId>
      <artifactId>spring-cloud-dependencies</artifactId>
      <version>2025.1.3</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

## Interview Qs

### Spring Boot vs Spring Cloud?

Spring Boot builds one production-ready service. Spring Cloud is a set of projects on top of Boot for the patterns between services: central config, discovery, gateway, load balancing, circuit breakers and messaging.

### What is a release train?

One BOM of Spring Cloud project versions tested together, named by year since 2020.0. Import it and leave versions off the Spring Cloud starters. For Boot 4.1, use 2025.1.x from 2025.1.2.

### What happened to Hystrix, Ribbon and Zuul?

They were removed in Spring Cloud 2020.0. Use Resilience4j for circuit breakers, Spring Cloud LoadBalancer for client-side load balancing and Spring Cloud Gateway for routing. Eureka is still supported.
