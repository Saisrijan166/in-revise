## What it is

Filters, interceptors and AOP are three ways to run the same code around many requests or calls without writing it in each controller. A servlet filter belongs to the Servlet API and wraps the whole HTTP request. A HandlerInterceptor belongs to Spring MVC and wraps the call to the chosen controller method. [AOP](card:spring-aop), which you met earlier, wraps calls to Spring bean methods, such as a service method.

## Why it exists

Some work must happen for many requests: adding a request ID, logging, timing, checking an API key. Copying it into every controller method repeats code and is easy to forget on a new endpoint. These hooks run it once, at a chosen depth. The depth decides what the code can see: raw HTTP for a filter, the chosen handler for an interceptor, the method and its arguments for AOP.

## How it works

<Compare id="filter-vs-interceptor-vs-aop" />

For `GET /payments/42`, the order is:

1. Each filter runs its code and calls `chain.doFilter(...)` to pass the request on. A filter that does not call it stops the request.
2. DispatcherServlet picks the controller method, then calls each interceptor's `preHandle`. If one returns `false`, the controller is never called.
3. The controller runs and calls `PaymentService` through its AOP proxy, so advice such as a transaction wraps the service method.
4. The interceptors' `postHandle` runs, then `afterCompletion` once the request is complete, even after an error, for every interceptor whose `preHandle` returned `true`.
5. Control returns to the filters in reverse order, so each can act after the response, for example to log the time taken.

## Example

A filter that gives every response a request ID, and an interceptor registered only for payment URLs:

```java
@Component                                          // Boot registers it for every URL (/*)
class RequestIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
            FilterChain chain) throws ServletException, IOException {
        res.setHeader("X-Request-Id", UUID.randomUUID().toString());
        chain.doFilter(req, res);                   // pass it on; skip this and nothing else runs
    }
}
```

```java
@Component
class PaymentTimingInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute("start", System.nanoTime());
        return true;                                // false: the controller is never called
    }
}
@Configuration
class WebConfig implements WebMvcConfigurer {
    private final PaymentTimingInterceptor timing;
    WebConfig(PaymentTimingInterceptor timing) { this.timing = timing; }
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(timing).addPathPatterns("/payments/**");
    }
}
```

What to notice:

- The filter is a bean, so Spring Boot registers it with Tomcat on its own. The interceptor is also a bean, but it runs only after you add it in a `WebMvcConfigurer`.
- `OncePerRequestFilter` is Spring's base class for filters: it aims for exactly one run per request dispatch and hands you typed `HttpServletRequest` and `HttpServletResponse` objects.
- The header is set before `chain.doFilter`, while the response is not yet written. Setting it after the chain could be too late.

## Rules and defaults

- **Filter order:** usually safe to leave unordered. If order matters, put `@Order` on the filter class or use a `FilterRegistrationBean`; `@Order` on a `@Bean` method does not work.
- **Interceptor scope:** `addPathPatterns` and `excludePathPatterns` choose the URLs. Interceptors run only for requests that matched a handler.
- **Security:** the Spring docs advise against interceptors as a security layer, because their path matching can differ from the controllers'. Use Spring Security, which is a filter, as you will see in [Spring Security and the Filter Chain](card:security-filter-chain).

## Interview Qs

### Both can intercept requests: why do we need filters and interceptors?

They work at different layers. A filter belongs to the Servlet API and sees every request before Spring MVC, even ones no controller handles. An interceptor belongs to Spring MVC, runs inside DispatcherServlet, and knows which controller method was chosen, so it suits handler-aware logic.

### If AOP can intercept methods, why do we need filters?

AOP wraps calls to Spring bean methods; it does not see the HTTP request as a whole. Filters work on the raw request and response, for example headers, compression or authentication before any controller is chosen. So a filter guards the request and AOP guards the business method.

### Explain preHandle, postHandle and afterCompletion.

preHandle runs before the handler and can stop the request by returning false. postHandle runs after the handler, before a view renders; for JSON responses the body is already written. afterCompletion runs after the complete request, even after an exception, so it suits cleanup and timing.
