## Why it exists

Some logic must run for many requests: logging, request IDs, auth checks, timing. Writing it in every controller repeats code; these three hooks run it once, at three different depths.

## How it works

<Compare id="filter-vs-interceptor-vs-aop" />

- Order: filters, DispatcherServlet, `preHandle`, controller, service (through an AOP proxy), `postHandle`, `afterCompletion`, then filters unwind.
- `preHandle` returning false stops the request; the controller never runs.
- Extend `OncePerRequestFilter` so the filter runs once per request.

## Example

```java
@Component                                         // a filter for every request
class RequestIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
            FilterChain chain) throws ServletException, IOException {
        res.setHeader("X-Request-Id", UUID.randomUUID().toString());
        chain.doFilter(req, res);                  // pass it on, or stop here
    }
}
```

## Interview Qs

### Both can intercept requests: why filters and interceptors?

Different layers. A filter belongs to the Servlet API and sees every request before Spring MVC. An interceptor belongs to Spring MVC, runs inside DispatcherServlet, and knows which controller method was chosen.

### If AOP can intercept methods, why do we need filters?

AOP wraps calls to Spring bean methods; it knows nothing about the HTTP request as a whole. Filters work on the raw request and response, for example headers or compression.

### Explain preHandle, postHandle and afterCompletion.

preHandle runs before the handler; false stops the request. postHandle runs after the handler, before the view renders. afterCompletion runs after the complete request has finished and suits cleanup.
