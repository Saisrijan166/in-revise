## What it is

A JWT (JSON Web Token) is a short string of three parts joined by dots: a header, a payload of claims such as the user id and expiry time, and a signature. The server that issues it signs it, so any change breaks the signature, but anyone can decode and read the payload. An API that accepts such tokens is called an OAuth2 resource server. It reads the token from the `Authorization: Bearer` header, checks it, and treats the request as that user, without a session.

## Why it exists

With [session login](card:authentication-flow), the server remembers every logged-in user. Run three instances behind a load balancer and each needs that session, so you add sticky sessions or a shared session store. Mobile apps and other services also handle cookies poorly. A JWT carries the login itself. Any instance can verify it locally with the issuer's public key, with no shared state and no call to the issuer for each request.

## How it works

1. The client logs in at an authorization server, a separate service such as Keycloak that issues tokens, and receives a signed JWT.
2. It calls the payment API with the header `Authorization: Bearer <token>`.
3. In the filter chain, BearerTokenAuthenticationFilter takes the token and passes it to the AuthenticationManager, where JwtAuthenticationProvider asks a `JwtDecoder` to check it.
4. The decoder verifies the signature with the issuer's public keys, which it finds through `issuer-uri` on the first token request. It then checks the times `exp` (expires at) and `nbf` (not before), and the issuer `iss`.
5. On success, each scope, a permission the token grants, becomes an authority `SCOPE_<scope>`, and the authenticated user goes into the SecurityContextHolder, so the normal [authorization rules](card:authorization-rules) apply. On failure the answer is 401.
6. Nothing is saved, so the next request repeats the check from step 2.

## Example

The payment service accepts JWTs from the company's identity server, and only tokens with the `payments.write` scope may create payments:

```properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://idp.example.com/realms/shop
spring.security.oauth2.resourceserver.jwt.audiences=payment-api
```

```java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.POST, "/payments").hasAuthority("SCOPE_payments.write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
    return http.build();
}
```

What to notice:

- `issuer-uri` is all Spring needs to find the public keys and to check `iss`. Discovery waits for the first token, so startup does not depend on the identity server being up.
- `audiences` makes Spring reject tokens issued for another API. Without it, `aud` is not checked.
- `hasAuthority("SCOPE_payments.write")` uses the exact authority name; `hasRole` would add `ROLE_` and never match (see [authorization rules](card:authorization-rules)).
- `STATELESS` tells Spring not to keep the login in an HTTP session, so each request must bring its token.

## Rules and defaults

- **Starter (Boot 4.0 and later):** `spring-boot-starter-security-oauth2-resource-server`. The older `spring-boot-starter-oauth2-resource-server` name is deprecated.
- **Algorithm (Security 7.1):** only `RS256` is trusted by default; with `issuer-uri`, Spring trusts the algorithms of the keys the issuer publishes.
- **Clock skew:** 60 seconds for `exp` and `nbf`.
- **Scope prefix:** `SCOPE_`, taken from the `scope` or `scp` claim.
- **Never by hand:** do not parse or check JWTs in your own code; a missed check, such as skipping the signature, lets forged tokens in.

## Not to be confused with

OAuth2 is a framework for how a client gets an access token from an authorization server. JWT is one format that token can have. Rule: OAuth2 = how you get the token; JWT = what the token looks like.

## Interview Qs

### If session login works, why use JWT?

A session keeps the login on the server, so every instance needs access to it. A JWT carries the login, so any instance can check it with no shared state, and non-browser clients just send a header. Neither is always better; sessions are simpler for one browser app.

### How do you log out a user with JWTs?

There is no session to end. Keep access tokens short-lived and use refresh tokens for new ones. To cut access at once, keep a deny list of revoked token ids (`jti`), which brings back some server state.

### Is a JWT encrypted?

Usually not. A signed JWT (JWS) is readable by anyone who holds it; only an encrypted JWT (JWE) hides the claims. Never put passwords or secrets in the payload.

### What does Spring check on each JWT?

The signature, using the issuer's public key, then the expiry `exp` and not-before `nbf` times with 60 seconds of skew, and the issuer `iss` when `issuer-uri` is set. The audience `aud` is checked only if you configure `audiences`.
