## Why it exists

Mobile apps, single-page apps and other services call APIs without a browser session. Each request carries a token instead, which the API checks locally without asking the issuer every time.

## How it works

<Mermaid
  alt="JWT flow. 1: the client logs in at the authorization server. 2: it gets a signed JWT. 3: it calls your API with Authorization: Bearer and the JWT. 4: your API fetches the issuer's public keys. Then it checks the signature, exp, nbf and iss. If they pass, the controller runs; if not, the API answers 401."
  chart={`flowchart LR
  C([Client]) -- "1. log in" --> AS[Authorization server]
  AS -- "2. signed JWT" --> C
  C -- "3. Bearer JWT" --> RS["Your API (resource server)"]
  RS -.->|"4. public keys"| AS
  RS --> V{"signature, exp, nbf, iss OK?"}
  V -- yes --> RUN([Controller])
  V -- no --> DENY([401])`}
/>

- Set `audiences` so a token issued for another API is rejected.
- Never parse or check JWTs by hand; let the resource server do it.

## Example

```properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://idp.example.com/realms/shop
spring.security.oauth2.resourceserver.jwt.audiences=orders-api
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Trusted algorithm | RS256 only | Spring Security 7.1 |
| Clock skew for exp, nbf | 60 seconds | Spring Security 7.1 |
| Scope authority prefix | `SCOPE_` | Spring Security 7.1 |

## Interview Qs

### If session login works, why use JWT?

A session keeps the login on the server, so every instance needs it. A JWT carries the login, so any instance can check it with no shared state. Neither is always better.

### How do you log out a user with JWTs?

There is no session to end. Keep access tokens short-lived; to cut access at once, keep a deny list of revoked token ids (`jti`), which brings back some server state.

### Is a JWT encrypted?

Usually not. A signed JWT (JWS) is readable by anyone; only an encrypted JWT (JWE) hides the claims. Never put passwords or secrets in the payload.
