## Why it exists

A failing service holds threads in every caller until they fail too. Guards around each call stop one sick service from taking others down.

## How it works

<Mermaid
  alt="Circuit breaker states. Closed: calls pass and failures are counted. When the failure rate passes the threshold, it moves to Open, where calls fail at once. After a wait it moves to Half-open and lets a few trial calls through. If they succeed it goes back to Closed; if they fail it goes back to Open."
  chart={`stateDiagram-v2
  [*] --> Closed
  Closed --> Open: failure rate over threshold
  Open --> HalfOpen: wait time ends
  HalfOpen --> Closed: trial calls succeed
  HalfOpen --> Open: trial calls fail`}
/>

- Open: calls are rejected at once with `CallNotPermittedException`, and the fallback answers.
- Put `fallbackMethod` on the outer `@Retry`: a fallback on `@CircuitBreaker` hides failures, so Retry never retries.
- Add `resilience4j-spring-boot4` and `spring-boot-starter-aspectj`; tune instances under `resilience4j.*`.

## Example

```java
@CircuitBreaker(name = "inventory")
@Retry(name = "inventory", fallbackMethod = "unknownStock")
public Stock stock(String sku) {
    return inventory.get().uri("/stock/{sku}", sku).retrieve().body(Stock.class);
}

private Stock unknownStock(String sku, Exception cause) {
    return Stock.unknown(sku);   // retries used up, or circuit open
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Breaker opens at | 50% failed calls, over the last 100 calls | Resilience4j 2.4 |
| Stays open | 60 s, then 10 trial calls | Resilience4j 2.4 |
| Retry | 3 attempts in total, 500 ms apart | Resilience4j 2.4 |
| `@Retryable` | 3 retries after the first call, 1 s apart | Spring Framework 7.0 |

## Interview Qs

### Explain the circuit breaker states.

Closed: calls pass and outcomes are recorded. Open: past the failure-rate threshold, calls fail at once. Half-open: after a wait, a few trial calls decide whether it closes again or reopens.

### How does fallbackMethod work?

A method in the same class with the same parameters plus one exception. The best-matching exception type wins, so an open circuit can be handled apart from other errors.

### Why combine retry with a circuit breaker?

Retry rides out blips; the breaker stops calls in an outage. Retry is the outer aspect, so once the breaker is open, each attempt fails fast. Add `CallNotPermittedException` to the retry's `ignoreExceptions` to stop retrying at once.
