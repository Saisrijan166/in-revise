## Why it exists

A slow or failing dependency holds threads in every caller until the callers fail too. Resilience4j puts small, tunable guards around each call, so one sick service does not take the others down.

## How it works

<Mermaid
  alt="Resilience4j decoration order. A caller's request passes through Retry, then CircuitBreaker, RateLimiter, TimeLimiter and Bulkhead before the remote call. When the circuit breaker is open, it throws CallNotPermittedException and the fallback method answers instead."
  chart={`flowchart LR
  C([Caller]) --> R[Retry] --> CB[CircuitBreaker] --> RL[RateLimiter] --> TL[TimeLimiter] --> BH[Bulkhead] --> X[(Remote call)]
  CB -. "open: CallNotPermittedException" .-> FB([fallbackMethod])`}
/>

- Breaker states: closed (calls pass, outcomes counted), open (calls fail at once), half-open (a few trial calls).
- Add `resilience4j-spring-boot4` (2.4.0) and AOP support (`spring-boot-starter-aspectj` in Boot 4); tune each named instance under `resilience4j.*`.
- [Spring Cloud Circuit Breaker](card:spring-cloud-circuit-breaker) gives one `CircuitBreakerFactory` API over Resilience4j and others.

## Example

```java
@Service
public class InventoryService {
    private final RestClient inventory;
    public InventoryService(RestClient inventory) { this.inventory = inventory; }

    @CircuitBreaker(name = "inventory", fallbackMethod = "unknownStock")
    @Retry(name = "inventory")
    public Stock stock(String sku) {
        return inventory.get().uri("/stock/{sku}", sku).retrieve().body(Stock.class);
    }

    private Stock unknownStock(String sku, Exception cause) {
        return Stock.unknown(sku);   // circuit open or call failed
    }
}
```

Tune the `inventory` instances:

```properties
resilience4j.circuitbreaker.instances.inventory.sliding-window-size=20
resilience4j.circuitbreaker.instances.inventory.minimum-number-of-calls=10
resilience4j.circuitbreaker.instances.inventory.wait-duration-in-open-state=30s
resilience4j.retry.instances.inventory.max-attempts=3
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Breaker opens at | 50% failed calls | Resilience4j 2.4 |
| Measured over | Last 100 calls; needs at least 100 | Resilience4j 2.4 |
| Stays open | 60 s, then 10 trial calls in half-open | Resilience4j 2.4 |
| Retry | 3 attempts in total, 500 ms apart | Resilience4j 2.4 |
| Bulkhead | 25 concurrent calls, no waiting | Resilience4j 2.4 |
| Time limiter | 1 s | Resilience4j 2.4 |
| `@Retryable` | 3 retries after the first call, 1 s apart | Spring Framework 7.0 |

## Interview Qs

### Explain the circuit breaker states in Resilience4j.

Closed: calls pass and outcomes are recorded in a sliding window. Open: past the failure-rate threshold (50% by default), calls fail at once with CallNotPermittedException. Half-open: after the wait (60 s), a few trial calls decide whether it closes again.

### How does fallbackMethod work?

Name a method in the same class with the same parameters plus one exception parameter. Resilience4j calls the fallback whose exception type matches best, so an open circuit (CallNotPermittedException) can be handled differently from other errors.

### In which order are the annotations applied?

Retry is outermost, then CircuitBreaker, RateLimiter, TimeLimiter and Bulkhead around the call. So every retry attempt passes through the breaker. The `*AspectOrder` properties change the order.

### Does Spring Framework 7 replace Resilience4j?

Partly. Spring Framework 7 has @Retryable, RetryTemplate and @ConcurrencyLimit built in, enabled with @EnableResilientMethods. It has no circuit breaker or rate limiter, so Resilience4j is still the choice for those.
