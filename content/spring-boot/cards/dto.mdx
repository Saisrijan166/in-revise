## What it is

A DTO (data transfer object) is a small class that carries data in or out of your API and nothing else. Its opposite is the entity: the class mapped to a database table, which you will meet in [JPA Entities](card:jpa-entities). In the payment service, `Payment` is the entity, while `PaymentRequest` (what a client sends) and `PaymentResponse` (what a client gets back) are DTOs. The service converts between them, so the controller only sees DTOs.

## Why it exists

The database model and the API contract change for different reasons. If the controller returns the `Payment` entity, three things go wrong. Internal fields such as a card token or a fraud score appear in the JSON. Every column rename breaks the mobile app. And when JSON is written, a related object that JPA loads only on first use can quietly run extra SQL. A DTO puts a fixed, deliberate contract between the outside world and your tables.

## How it works

<Compare id="entity-vs-dto" />

1. The client sends JSON, and Spring reads it into a request DTO, `PaymentRequest`. Only its fields can be set.
2. The controller passes the DTO to `PaymentService`.
3. The service builds or loads the `Payment` entity, applies the business rules and saves it.
4. The service copies the fields the client may see into a response DTO, `PaymentResponse`.
5. The controller returns that DTO, and Jackson writes it as JSON. The entity never leaves the service.

## Example

The DTOs of the payment service and the mapping step inside `PaymentService`:

```java
record PaymentRequest(BigDecimal amount, String currency) { }        // what a client may send

record PaymentResponse(Long id, BigDecimal amount, PaymentStatus status) {  // what a client sees
    static PaymentResponse from(Payment p) {                         // entity -> DTO
        return new PaymentResponse(p.getId(), p.getAmount(), p.getStatus());
    }
}

// In PaymentService: the entity stays inside, only the DTO goes out
PaymentResponse create(PaymentRequest req) {
    Payment saved = repository.save(new Payment(req.amount(), req.currency()));
    return PaymentResponse.from(saved);
}
```

What to notice:

- `PaymentRequest` has no `id` or `status`. The database creates the id and the service sets the status, so a client cannot fake either.
- The `Payment` entity also holds `cardToken` and `fraudScore`. `PaymentResponse.from` does not copy them, so they can never reach the JSON.
- A record gives you the constructor, accessors such as `amount()`, `equals` and `toString` from one line.

## Rules and defaults

- **Where to map:** in the service layer, so the controller sees only DTOs and every read of the entity happens inside the service.
- **Extra SQL during JSON writing:** returning an entity can run queries while Jackson writes it, because Spring Boot can keep the JPA `EntityManager` open for the whole web request. You will see this setting, open-in-view, and its default in [Lazy Loading and the N+1 Problem](card:lazy-loading-n-plus-one).
- **One DTO per purpose:** a create request, an update request and a response often need different fields. Sharing one class brings back mass assignment.

## Common mistakes

- **"A DTO is extra code for nothing in a small app."** In a tiny prototype the entity and the DTO may look the same. The DTO pays off the first time a column changes or a sensitive field is added, and by then many clients depend on the shape.

## Interview Qs

### If the entity already holds the data, why do we need a DTO?

The entity is shaped by the database; the DTO is the API contract. A response DTO hides fields such as a card token, a request DTO blocks mass assignment, and the tables can change without breaking clients. They change for different reasons, so they should be different classes.

### Why is returning a JPA entity from a controller risky?

Jackson writes every property it can reach. Related objects that JPA loads lazily can then run extra queries during JSON writing, as [Lazy Loading and the N+1 Problem](card:lazy-loading-n-plus-one) shows. Internal fields leak, and the API breaks whenever a table changes.

### Is @JsonIgnore enough to protect sensitive fields?

No. It protects only the fields you remember to mark, and every new field is exposed by default. A response DTO works the other way round: nothing is sent unless you add it. That is what OWASP recommends.
