## Why it exists

The database model and the API contract change for different reasons. Sending entities straight out leaks internal fields, ties clients to your tables, and lets JSON writing trigger database queries.

## How it works

<Compare id="entity-vs-dto" />

- Map entity to DTO in the service layer; the controller only sees DTOs.
- Use separate request and response DTOs: clients must not set `id`, `role` or `status` by sending extra JSON.

## Example

```java
record CreateUserRequest(@NotBlank String name, @Email String email) { }
record UserResponse(Long id, String name, String email) {
    static UserResponse from(User u) {                 // entity -> DTO
        return new UserResponse(u.getId(), u.getName(), u.getEmail());
    }
}
// The User entity also has passwordHash and internalStatus: never sent out.
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `spring.jpa.open-in-view` | `true` (EntityManager open for the whole request) | Spring Boot 4.1 |

## Interview Qs

### If the entity already holds the data, why do we need a DTO?

The entity is shaped by the database; the DTO is the API contract. A DTO hides fields such as passwordHash, blocks mass assignment, and lets you change tables without breaking clients.

### Why is returning a JPA entity from a controller risky?

Jackson writes every property it can reach. Lazy relations then load during JSON writing, running extra queries, because open-in-view keeps the EntityManager open. Internal fields leak, and the API breaks when a table changes.

### Is @JsonIgnore enough to protect sensitive fields?

No. It only hides the fields you remember to mark. Choose the fields to send in a response DTO instead, as OWASP advises.
