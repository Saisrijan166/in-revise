## Why it exists

Two users read the same row, both change it, and the second write silently erases the first: a lost update. Locking detects or prevents that.

## How it works

<Compare id="optimistic-vs-pessimistic-locking" />

- An optimistic conflict marks the transaction for rollback; retry the whole read-change-write.
- Do not hold a pessimistic lock across a user's think time.

## Example

```java
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;
    @Version private Long version;   // checked and bumped on every update
}

public interface AccountRepository extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findForUpdate(@Param("id") Long id);
}
```

## Interview Qs

### What is optimistic locking?

Add a @Version field. Each update checks that the version is unchanged and increments it. If another transaction updated first, the update fails with an optimistic lock exception, and the caller retries or reports a conflict.

### Optimistic or pessimistic?

Optimistic when conflicts are rare and reads dominate: no locks, high throughput. Pessimistic when the same rows are updated often and a retry is costly, such as stock counts; keep those transactions short.
