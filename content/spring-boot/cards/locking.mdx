## What it is

Locking is how you stop two transactions from overwriting each other's change to the same row. **Optimistic locking** takes no lock: each row carries a version number, and an update succeeds only if the version is still the one you read. **Pessimistic locking** asks the database to lock the row when you read it, so other transactions wait until you commit. Both work on [JPA entities](card:jpa-entities) through Hibernate.

## Why it exists

Two refunds for account 7 run at the same moment. Each reads a balance of 1000, subtracts 300 and saves 700. The second save silently replaces the first, so one refund is lost. This is a **lost update**. [@Transactional](card:transactional) does not stop it, and neither does PostgreSQL's default [isolation level](card:acid-isolation), because each transaction only read committed data. Locking either detects the clash (optimistic) or prevents it (pessimistic).

## How it works

<Compare id="optimistic-vs-pessimistic-locking" />

With optimistic locking, the two refunds go like this:

1. Refund A and refund B both load account 7 with `version = 3`.
2. A commits first. Hibernate runs `UPDATE account SET balance = 700, version = 4 WHERE id = 7 AND version = 3`. One row matches, so it succeeds.
3. B commits. Its `UPDATE` also says `WHERE version = 3`, but the row now has version 4, so no row matches.
4. Hibernate sees that zero rows changed and throws `OptimisticLockException`. Spring passes it on as `ObjectOptimisticLockingFailureException`, and B's transaction rolls back.
5. B runs again from the start: it reads balance 700 and version 4, and saves 400.

With pessimistic locking, B's read itself waits until A commits, and then reads 700 directly.

## Example

The entity gets a version field, and the repository gets one locking query for hot rows:

```java
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;
    @Version private Long version;   // checked and increased on every update
}

public interface AccountRepository extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findForUpdate(@Param("id") Long id);
}
```

What to notice:

- You never set `version` yourself. Hibernate adds `version = ?` to every UPDATE and DELETE of the entity and increases it.
- Remove `@Version` and both refunds succeed silently: the last write wins and the first refund is lost.
- `findForUpdate` locks the row until the transaction ends. Call it inside a `@Transactional` method; without a transaction, JPA throws `TransactionRequiredException`.

## Rules and defaults

- **Version types (Jakarta Persistence 3.2):** `int`, `Integer`, `short`, `Short`, `long`, `Long`, `java.sql.Timestamp`, `Instant` or `LocalDateTime`. Use at most one version field per entity.
- **After a conflict:** the transaction is marked for rollback. Retry the whole read, change and write in a new transaction, or report the conflict, for example as HTTP `409 Conflict`.
- **Pessimistic lock modes:** `PESSIMISTIC_WRITE` is an exclusive lock (`select ... for update`). `PESSIMISTIC_READ` is a shared lock that blocks writers but not other readers.
- **@Lock:** Spring Data JPA's way to set the lock mode on a repository query method.
- **Keep locks short:** do not hold a pessimistic lock across a user interaction (Hibernate's advice), and keep slow remote calls out of the locked transaction.

## Not to be confused with

The **isolation level** is a rule the database applies to every transaction about what it may *read*. **Locking** is something you add to particular entities or queries to protect a *read-then-write* against another writer. Rule: isolation decides what you see; locking decides who may overwrite.

## Interview Qs

### What is optimistic locking and how does it work in JPA?

Add a field marked @Version. Every UPDATE then includes the version you read in its WHERE clause and increases it. If another transaction updated the row first, no row matches, Hibernate throws an optimistic lock exception, and the caller retries or reports a conflict.

### When do you choose optimistic and when pessimistic locking?

Optimistic when conflicts are rare, for example users editing their own data: no locks, high throughput, an occasional retry. Pessimistic when the same rows are updated often and a retry is costly, such as a stock count during a sale. Keep those transactions short.

### Can pessimistic locking cause deadlocks?

Yes. If transaction A locks row 1 and then wants row 2, while B holds row 2 and wants row 1, both wait for each other. PostgreSQL, for example, detects this and aborts one of the two. Lock rows in the same order everywhere and keep the locked section short.
