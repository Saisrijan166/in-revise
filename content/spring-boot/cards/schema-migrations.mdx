## What it is

The schema is the structure of the database: its tables, columns and indexes. A schema migration is a small script that changes it by one step, such as adding a column. Flyway and Liquibase are tools that keep these scripts in order, run only the ones a database has not had yet, and record each one in a history table. Spring Boot runs them for you when the app starts.

## Why it exists

The `Payment` [entity](card:jpa-entities) gains a `currency` field, so every database (developer, test, production) needs a new column exactly when the new code arrives. Running SQL by hand on each one is easy to forget or do out of order. Letting Hibernate alter tables with `ddl-auto=update` leaves no record, nothing to review, and it cannot rename a column or move data. Migrations make schema changes part of the code: reviewed, versioned and applied the same way everywhere.

## How it works

<Mermaid
  alt="At startup Flyway reads its history table, which lists V1 and V2 as applied. It checks the checksums of V1 and V2 against the files. It then runs V3, the new script, and records it. After that Hibernate starts and validates the entities against the tables."
  chart={`flowchart LR
  H[("flyway_schema_history: V1, V2")] --> C{Checksums of V1, V2 match?}
  C -- no --> F[Startup fails]
  C -- yes --> R[Run V3, record it]
  R --> V[Hibernate validates the schema]`}
/>

1. You add `V3__add_currency.sql` under `src/main/resources/db/migration` and commit it with the code that needs the column.
2. The app starts. Boot runs Flyway before the beans that use the database, such as JPA.
3. Flyway reads its `flyway_schema_history` table and sees that V1 and V2 are already applied.
4. It recomputes the checksums of V1 and V2 from the files. If one was edited after it ran, startup fails here.
5. It runs V3, then records its version, description and checksum in the history table.
6. Hibernate starts. With `ddl-auto=validate` it checks that the entities match the tables and changes nothing.

So the history table is the key: every database remembers which scripts it has had, and gets only the missing ones.

## Example

The migration adds the column, and the settings let Flyway own the schema:

```sql
-- src/main/resources/db/migration/V3__add_currency.sql
ALTER TABLE payment ADD COLUMN currency VARCHAR(3) NOT NULL DEFAULT 'INR';
```

```properties
spring.jpa.hibernate.ddl-auto=validate
```

What to notice:

- The file name is the contract: `V`, the version, two underscores, a description. Flyway orders scripts by version number.
- The `DEFAULT 'INR'` fills existing rows, so `NOT NULL` does not fail on payments that are already there.
- With `validate`, forgetting this script makes startup fail with a missing-column error, instead of failing later on the first query.

## Rules and defaults

| What | Flyway | Liquibase |
| --- | --- | --- |
| A change is | A SQL file, `V3__add_currency.sql` | A changeset in a changelog |
| Written in | SQL | SQL, XML, YAML or JSON |
| Default location | `classpath:db/migration` | `db/changelog/db.changelog-master.yaml` |
| History table | `flyway_schema_history` | `DATABASECHANGELOG` |

- **Starters (changed in 4.0):** add `spring-boot-starter-flyway` or `spring-boot-starter-liquibase`. For Flyway on PostgreSQL or MySQL, also add the database module, `flyway-database-postgresql` or `flyway-mysql`.
- **ddl-auto default (Spring Boot 4.1):** `create-drop` when the database is embedded and no Flyway or Liquibase is found; `none` in every other case.
- **Checksum check:** `spring.flyway.validate-on-migrate` is `true` by default, so an edited applied script stops startup.
- **One tool only:** do not mix Flyway or Liquibase with `schema.sql` and `data.sql`; Boot plans to remove support for that mix.
- **Test data:** Flyway scripts in `src/test/resources/db/migration` run only in tests and are not packaged in the jar.

## Interview Qs

### Why not use ddl-auto=update in production?

It only adds what is missing and alters wrong column types. It keeps no history, cannot rename a column, and never moves data. Versioned scripts are reviewed in code review and run the same way on every database, so Hibernate should only validate.

### How does Flyway know which scripts to run?

Its flyway_schema_history table lists every applied version with a checksum. At startup Flyway compares that list with the files, checks that applied files are unchanged, and runs the newer versions in order.

### What is the difference between Flyway and Liquibase?

Flyway runs plain SQL files ordered by their version number. Liquibase runs changesets listed in a changelog, written in SQL, XML, YAML or JSON. Both run at Boot startup, run each change once, and keep a history table of what they applied.
