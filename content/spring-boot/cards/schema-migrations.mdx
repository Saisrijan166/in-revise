## Why it exists

Every environment needs the same schema, shipped with the code that needs it. Letting Hibernate alter tables leaves no record of what changed.

## How it works

| | Flyway | Liquibase |
| --- | --- | --- |
| A change is | A SQL file, `V2__add_email.sql` | A changeset in a changelog |
| Written in | SQL files | SQL, XML, YAML or JSON |
| Default location | `classpath:db/migration` | `db/changelog/db.changelog-master.yaml` |
| History table | `flyway_schema_history` | `DATABASECHANGELOG` |

- At startup the tool reads its history table, then runs only the scripts not yet applied, in order.
- Use one tool alone; Boot advises against mixing it with `schema.sql` and `data.sql`.

## Example

```sql
-- src/main/resources/db/migration/V2__add_email.sql
ALTER TABLE customer ADD COLUMN email VARCHAR(255);
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `ddl-auto`, embedded DB, no Flyway or Liquibase | `create-drop` | Spring Boot 4.1 |
| `ddl-auto`, every other case | `none` | Spring Boot 4.1 |
| `schema.sql`, `data.sql` | Embedded in-memory databases only | Spring Boot 4.1 |

## Interview Qs

### Why not ddl-auto=update in production?

It only adds what is missing and alters wrong column types. It keeps no history and moves no data. Versioned scripts are reviewed and repeatable; Hibernate should only validate.

### How does Flyway know what to run?

Its flyway_schema_history table lists each applied version with a checksum. At startup it runs the newer versions in order; the checksum shows if an applied script was edited.

### Flyway vs Liquibase?

Flyway runs plain SQL files ordered by version. Liquibase runs changesets from a changelog in XML, YAML, JSON or SQL. Both run at Boot startup and keep a history table.
