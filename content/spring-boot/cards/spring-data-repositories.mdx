## What it is

A Spring Data repository is an interface you declare for one entity, such as `PaymentRepository extends JpaRepository<Payment, Long>`. The two type arguments are the entity class and the type of its id. At startup Spring Data creates a bean that implements the interface, so you inject it into `PaymentService` like any other bean. You add only the method signatures for the queries you need, and Spring Data writes their bodies.

## Why it exists

Without it, each entity needs a data access class: an `EntityManager` field, a `findById` that calls `find`, a `save` that picks the right JPA call, and paging code with a separate count query. That code is almost the same for every entity, and it is easy to get slightly wrong. Spring Data writes it once, inside the framework. Your interface lists only what is special about this entity.

## How it works

1. At startup, Spring Data finds the interfaces that extend `Repository` and creates one bean for each.
2. When you call an inherited method such as `save` or `findById`, the bean passes it to Spring Data's ready-made implementation, which uses the `EntityManager`.
3. When you call a method that has `@Query`, it runs that query.
4. When you call any other declared method, it uses a query built from the name: `findByStatusAndAmountGreaterThan` becomes "where status = ? and amount > ?".

So an inherited method needs no code, a name builds a simple query, and `@Query` handles the rest.

## Example

The payment service needs a filter, a paged list and a safe lookup by id:

```java
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    List<Payment> findByStatusAndAmountGreaterThan(String status, BigDecimal min);

    @Query("select p from Payment p where p.status = :status")
    Page<Payment> findByStatusPaged(@Param("status") String status, Pageable page);
}

// in PaymentService
Payment p = payments.findById(id)
        .orElseThrow(() -> new PaymentNotFoundException(id));
Page<Payment> firstPage = payments.findByStatusPaged("PAID",
        PageRequest.of(0, 20, Sort.by("amount").descending()));
```

What to notice:

- The first method has no query text. `Status` and `Amount` must be fields of `Payment`, and `GreaterThan` becomes `>`.
- The `@Query` text is JPQL: `Payment` and `p.status` are the entity and its field, not the table and column.
- `orElseThrow` turns a missing row into your own exception, which the [global exception handler](card:exception-handling) can map to 404.
- `PageRequest.of(0, 20, ...)` asks for the first 20 rows, largest first. Because the method returns `Page`, Spring Data also runs a count query.

## Rules and defaults

- **Query lookup (default):** Spring Data first looks for a declared query such as `@Query`, and only builds one from the method name if there is none.
- **Update and delete queries:** an `@Query` that changes data needs `@Modifying`. Afterwards the persistence context can still hold entities with old values; `clearAutomatically = true` clears it so later reads load fresh rows.
- **Transactions:** inherited CRUD methods already run in a transaction, read-only for reads. Methods you declare get none by default, so put `@Transactional` on the service method that calls them.
- **Native SQL:** `@Query(nativeQuery = true)` or `@NativeQuery` runs plain SQL over tables and columns, which ties the query to one database.

## Not to be confused with

`CrudRepository` is the basic interface for any Spring Data store, `PagingAndSortingRepository` adds only sorted and paged `findAll`, and `JpaRepository` combines both and adds JPA extras such as `flush`. Rule: CrudRepository = the minimum; JpaRepository = everything a JPA app usually needs.

## Common mistakes

- **"Calling Optional.get() is fine, because the id comes from a real link."** A wrong or old id still arrives. `get()` then throws `NoSuchElementException`, which becomes a 500 error. Use `orElseThrow` with your own exception.
- **"A derived deleteByStatus runs one DELETE statement."** It first loads the matching entities, then deletes them one by one, so `@PreRemove` callbacks run. For a bulk delete, write a `@Modifying` `@Query`.

## Interview Qs

### If CrudRepository has CRUD, why do we need JpaRepository?

JpaRepository adds JPA extras on top of CRUD: methods that return List instead of Iterable, paging and sorting, flush and saveAndFlush, batch deletes and getReferenceById. Use CrudRepository when you want to expose fewer methods or keep the interface independent of the store.

### JPQL or native SQL in @Query?

JPQL queries entities and their fields, so Hibernate checks it against the mapping and it works on any database. Native SQL, with nativeQuery = true, queries tables and columns directly. Use it for database-specific features that JPQL cannot express, and accept that it ties the query to one database.

### How does Spring Data implement an interface you never implemented?

At startup it creates a proxy bean for each repository interface. Calls to inherited methods go to a ready-made implementation, SimpleJpaRepository for JPA. Calls to declared methods run the @Query text or a query built from the method name. Your code only sees the interface.
