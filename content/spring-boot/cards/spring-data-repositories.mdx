## Why it exists

Every entity needs the same data access code: save, find by id, page through, filter by a few fields. Spring Data lets you declare an interface and generates that code.

## How it works

- A method with `@Query` uses that query; otherwise the query is derived from the name.
- JPQL names entities and fields; native SQL names tables and columns.

## Example

```java
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    List<Payment> findByStatusAndAmountGreaterThan(String status, BigDecimal min);

    @Query("select p from Payment p where p.status = :status")
    Page<Payment> findByStatusPaged(@Param("status") String status, Pageable page);
}
// payments.findByStatusPaged("PAID", PageRequest.of(0, 20, Sort.by("amount").descending()));
// payments.findById(id).orElseThrow(() -> new PaymentNotFound(id));
```

## Interview Qs

### If CrudRepository has CRUD, why JpaRepository?

JpaRepository adds JPA extras: List return types, paging and sorting, flush, saveAndFlush, batch deletes and getReferenceById. Use CrudRepository to expose fewer methods or stay store-neutral.

### JPQL vs native SQL in @Query?

JPQL queries entities and their fields, so it is checked against the mapping and stays database-neutral. Native SQL (nativeQuery = true) queries tables and columns directly; use it for database-specific features.

### Why does findById return Optional?

The row may not exist. Optional makes the caller handle that case, usually with orElseThrow, instead of getting a null or calling get() blindly.
