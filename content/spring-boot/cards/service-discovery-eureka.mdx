## Why it exists

In the cloud, instances start, stop and move, so their addresses keep changing. Hardcoded hosts break; services need a live directory they can register in and look up by name.

## How it works

<Mermaid
  alt="Eureka flow. Two orders instances register with the Eureka server and send a heartbeat every 30 seconds. The checkout service fetches the registry every 30 seconds. When checkout calls http://orders, Spring Cloud LoadBalancer picks orders instance 2."
  chart={`flowchart LR
  O1[orders instance 1] -- "register, heartbeat every 30 s" --> E[(Eureka server)]
  O2[orders instance 2] -- "register, heartbeat every 30 s" --> E
  C[checkout] -- "fetch registry every 30 s" --> E
  C -- "http://orders: LoadBalancer picks one" --> O2`}
/>

- The server drops an instance after 90 s without a heartbeat. On a clean shutdown, the client cancels its lease.
- **Self-preservation:** when renewals fall below the threshold, the server stops evicting, because a network fault looks like many instances dying at once.
- Run two or more Eureka servers that register with each other; they copy registrations between them.

## Example

The Eureka server (`spring-cloud-starter-netflix-eureka-server`, main class with `@EnableEurekaServer`):

```properties
server.port=8761
eureka.client.register-with-eureka=false
eureka.client.fetch-registry=false
```

Each service (`spring-cloud-starter-netflix-eureka-client`):

```properties
spring.application.name=orders
eureka.client.serviceUrl.defaultZone=http://eureka:8761/eureka/
```

A caller uses the service name, not a host:

```java
@Bean
@LoadBalanced
RestClient.Builder restClientBuilder() {
    return RestClient.builder();
}

// elsewhere: "orders" is a service id, resolved through Eureka
Order order = builder.build().get().uri("http://orders/orders/{id}", 42)
        .retrieve().body(Order.class);
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Heartbeat (lease renewal) | Every 30 s | Spring Cloud Netflix 5.0 |
| Instance dropped after | 90 s without a heartbeat | Spring Cloud Netflix 5.0 |
| Client registry fetch | Every 30 s | Spring Cloud Netflix 5.0 |
| Self-preservation | On, renewal threshold 0.85 | Spring Cloud Netflix 5.0 |
| LoadBalancer algorithm | Round robin | Spring Cloud Commons 5.0 |
| LoadBalancer instance cache | 35 s TTL | Spring Cloud Commons 5.0 |

## Interview Qs

### How does Eureka work?

Each instance registers on startup and sends a heartbeat every 30 s. The server drops instances that stay silent for 90 s. Clients fetch and cache the registry every 30 s, and a client-side load balancer picks an instance for each call.

### What is self-preservation mode?

When the server gets far fewer renewals than expected (below 85% by default), it stops evicting instances, so a network fault does not wipe out a healthy registry. The cost: dead instances can stay listed for a while.

### @EnableEurekaServer vs @EnableDiscoveryClient?

@EnableEurekaServer turns an app into the registry. @EnableDiscoveryClient marks a client, but it is no longer required: a DiscoveryClient implementation on the classpath, such as the Eureka client starter, registers the app by itself.

### Do you need Eureka on Kubernetes?

Often not. Kubernetes already tracks the Pods behind a Service and gives it a DNS name, so a call to http://orders reaches one of them. Spring Cloud Kubernetes offers a DiscoveryClient on top if your code needs one.
