## What it is

Service discovery is how one service finds the current address of another by its name. Eureka is Netflix's discovery server, which Spring Cloud Netflix packages for Boot apps. It keeps a **registry**: a list of every running instance of every service, with its host and port. Each service is a **Eureka client**: it registers itself, and it reads the registry to find others.

## Why it exists

You could write `http://10.0.4.17:8080` for the fraud-check service in the payment service's config. But instances start, stop, crash and move, and there may be three of them today and six tomorrow, so a fixed address breaks. Discovery replaces fixed addresses with names: the payment service asks for `fraud-check`, and gets whatever instances are alive right now.

1. Each fraud-check instance starts and registers with Eureka under its `spring.application.name`.
2. Every 30 seconds it sends a heartbeat. If none arrives for 90 seconds, Eureka drops the instance.
3. The payment service fetches the registry and caches it, refreshing it every 30 seconds.
4. When it calls `http://fraud-check/...`, Spring Cloud LoadBalancer replaces the name with one live instance from the cache.
5. The request goes straight to that instance. Eureka never sees it.

So the key idea: Eureka is a phone book, not a switchboard.

## Example

The payment service's `FraudCheckClient`, a [RestClient](card:http-clients), resolves the fraud-check service by name:

```java
@Bean
@LoadBalanced                       // service names in URLs go through LoadBalancer
RestClient.Builder loadBalancedBuilder() {
    return RestClient.builder();
}

// in FraudCheckClient, whose RestClient http is built from that builder:
FraudResult check(PaymentRequest request) {
    return http.post().uri("http://fraud-check/checks")   // a service name, not a host
            .body(request)
            .retrieve().body(FraudResult.class);
}
```

What to notice:

- `fraud-check` is the other service's `spring.application.name`, not a DNS host name.
- `@LoadBalanced` marks the builder, so every client built from it asks LoadBalancer to pick an instance per call.
- Remove `@LoadBalanced` and the call fails, because the client tries to find a real host called `fraud-check`.

## Rules and defaults

- **Registration:** having `spring-cloud-starter-netflix-eureka-client` on the classpath is enough; you only set the server URL in `eureka.client.serviceUrl.defaultZone`.
- **Timing (Spring Cloud Netflix 5.0):** heartbeat every 30 s, instance dropped after 90 s without one, client registry fetch every 30 s.
- **Self-preservation:** on by default. When far fewer heartbeats arrive than expected, the server stops dropping instances, because the cause may be a network fault, not dead services.
- **Health:** by default Eureka shows an instance as UP while heartbeats arrive. `eureka.client.healthcheck.enabled=true` sends its [Actuator](card:actuator) health status instead.
- **Load balancing:** Spring Cloud LoadBalancer uses round robin by default.
- **Kubernetes:** a Kubernetes Service already gives a stable DNS name and tracks its Pods, so many teams use that instead of Eureka.

## Not to be confused with

A **service registry** (Eureka) stores which instances exist. A **load balancer** chooses one instance for each call. Rule: Eureka answers "who is alive?"; LoadBalancer answers "which one now?". Here the load balancer runs inside the caller, which is called client-side load balancing.

## Interview Qs

### How does Eureka work?

Each instance registers on startup and sends a heartbeat every 30 seconds; the server drops it after 90 seconds of silence. Callers fetch and cache the registry, and a client-side load balancer picks an instance for each call. Requests go directly between services.

### What is self-preservation mode?

When far more instances stop renewing than expected, the Eureka server stops evicting them. A network problem between Eureka and the services should not wipe out a registry of healthy instances. The cost is that really dead instances may stay listed for a while, so callers need retries.

### Do you need Eureka on Kubernetes?

Often not. Kubernetes gives each Service a DNS name and keeps the list of healthy Pods behind it, so callers use the Service name directly. Eureka still helps when services run outside Kubernetes, or across several platforms.
