## What it is

Propagation is a setting on [@Transactional](card:transactional) that says what a method does when it is called while a transaction is already running. It can **join** that transaction (share it, so both commit or roll back together), **start its own** (pause the caller's until it finishes; Spring calls this *suspending* it), or refuse to run. The default, `REQUIRED`, joins if there is a transaction and starts one if there is not.

## Why it exists

Service methods call other service methods, and each may be `@Transactional`. Some work must fail together: the payment and its ledger entry. Other work must survive a failure: the record that a payment was attempted. Without a rule per method, Spring could not tell these apart. Propagation lets each method declare which kind it is.

## How it works

| Propagation | A transaction exists | No transaction exists |
| --- | --- | --- |
| `REQUIRED` (default) | Join it | Start one |
| `REQUIRES_NEW` | Pause it, start a new one | Start one |
| `NESTED` | Savepoint inside it | Start one |
| `SUPPORTS` | Join it | Run without one |
| `MANDATORY` | Join it | Throw an exception |
| `NOT_SUPPORTED` | Pause it, run without one | Run without one |
| `NEVER` | Throw an exception | Run without one |

Follow one payment where `pay()` uses `REQUIRED` and `AuditService.record()` uses `REQUIRES_NEW`:

1. The controller calls `pay()`. Its proxy finds no transaction, so it starts transaction T1.
2. `pay()` calls `audit.record()`. That proxy sees T1, pauses it, and starts T2 on a second connection.
3. `record()` saves the audit row. Its proxy commits T2 and resumes T1.
4. `pay()` saves the payment, then the debit throws a `RuntimeException`. The proxy of `pay()` rolls back T1.
5. The payment row is gone, but the audit row stays, because T2 had already committed.

So propagation is decided at each proxy, at the moment the call arrives.

## Example

This is the code for the five steps above:

```java
@Service
public class PaymentService {                            // fields omitted
    @Transactional                                       // REQUIRED
    public void pay(PaymentRequest request) {
        audit.record("attempt " + request.orderId());    // REQUIRES_NEW: commits now
        payments.save(new Payment(request.amount()));
        accounts.debit(request.accountId(), request.amount()); // throws: payment rolls back
    }                                                    // the audit row stays
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String message) { auditLog.save(new AuditEntry(message)); }
}
```

What to notice:

- `record()` lives in a separate bean, so the call goes through its proxy. As a method of `PaymentService`, `this.record()` would skip the proxy and the audit row would roll back with the payment.
- Remove `propagation = REQUIRES_NEW` and `record()` joins T1, so the audit row disappears in the rollback.
- While `record()` runs, the thread holds two connections: one for the paused T1 and one for T2.

## Rules and defaults

- **Default:** `REQUIRED` (Spring Framework 7.0).
- **Joining ignores your settings:** a method that joins uses the caller's isolation, timeout and readOnly, and silently ignores its own. Set `validateExistingTransaction = true` on the transaction manager to reject mismatches instead.
- **REQUIRES_NEW needs a big enough pool:** the connection pool (you will see it in [Connection pooling](card:connection-pool)) must exceed the number of concurrent threads by at least one, or threads can deadlock waiting for their second connection.
- **NESTED with JPA:** it uses JDBC savepoints. `JpaTransactionManager` allows it only after you set `nestedTransactionAllowed = true`, and the savepoint covers plain JDBC work, not the entities Hibernate holds in memory.
- **Rollback-only:** when a rollback exception, such as a `RuntimeException`, leaves a joined method through its proxy, the shared transaction is marked rollback-only. The outer method can no longer commit it.

## Not to be confused with

**Propagation** decides *which* transaction a method runs in. **Isolation**, which you will see in [ACID and isolation levels](card:acid-isolation), decides *how much* that transaction sees of other transactions running at the same time. Rule: propagation is about methods calling methods; isolation is about users running at once.

## Common mistakes

- **"REQUIRES_NEW on a method in the same class gives it its own transaction."** The this-call skips the proxy, so the setting is never read. Move the method to another bean.
- **"NESTED is a lighter REQUIRES_NEW."** NESTED never commits on its own; nothing is saved until the outer transaction commits.

## Interview Qs

### If REQUIRED can start a transaction, why do we need REQUIRES_NEW?

REQUIRED starts one only when none exists; otherwise it joins, so its work rolls back with the caller's. REQUIRES_NEW is for work that must commit on its own whatever the caller does, such as an audit log or a failure record.

### What is UnexpectedRollbackException?

An inner method that joined the transaction threw, so its proxy marked the shared transaction rollback-only. The outer method caught the exception and tried to commit. Spring rolls back instead and throws UnexpectedRollbackException, so the caller knows nothing was saved.

### What is the difference between REQUIRES_NEW and NESTED?

REQUIRES_NEW runs a separate physical transaction with its own connection and its own commit. NESTED stays in the same transaction and sets a savepoint: the inner part can roll back to it alone, but nothing commits until the outer transaction commits.
