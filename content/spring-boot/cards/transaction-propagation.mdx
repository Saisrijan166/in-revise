## Why it exists

Service methods call each other, and each may be @Transactional. Spring must know whether an inner call shares the outer transaction or runs on its own, and how much one transaction sees of others' changes.

## How it works

| Propagation | A transaction exists | No transaction |
| --- | --- | --- |
| `REQUIRED` (default) | Join it | Start one |
| `REQUIRES_NEW` | Suspend it, start a new one | Start one |
| `NESTED` | Savepoint inside it | Start one |
| `SUPPORTS` | Join it | Run without one |
| `MANDATORY` | Join it | Throw an exception |
| `NOT_SUPPORTED` | Suspend it, run without one | Run without one |
| `NEVER` | Throw an exception | Run without one |

| Isolation | [Dirty read](card:dirty-read) | [Non-repeatable read](card:non-repeatable-read) | [Phantom read](card:phantom-read) |
| --- | --- | --- | --- |
| `READ_UNCOMMITTED` | Possible | Possible | Possible |
| `READ_COMMITTED` | Stopped | Possible | Possible |
| `REPEATABLE_READ` | Stopped | Stopped | Possible |
| `SERIALIZABLE` | Stopped | Stopped | Stopped |

- `REQUIRES_NEW` holds two connections at once. Spring warns that a pool not larger than the number of concurrent threads can run dry and deadlock.
- Two users editing one row: use [optimistic locking](card:optimistic-locking) (`@Version`) or [pessimistic locking](card:pessimistic-locking) (`@Lock`).

## Example

```java
@Transactional                                       // REQUIRED: one transaction
public void placeOrder(OrderRequest request) {
    auditService.record("attempt " + request.id());  // REQUIRES_NEW: commits at once
    orderRepository.save(Order.from(request));
    stockService.reserve(request);                   // throws: the order rolls back,
}                                                    // but the audit row stays

// In AuditService, another bean, so the call goes through its proxy
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void record(String message) {
    auditRepository.save(new AuditEntry(message));
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Propagation | `REQUIRED` | Spring Framework 7.0 |
| Isolation | `DEFAULT`: the database's level | Spring Framework 7.0 |
| PostgreSQL level | READ COMMITTED | PostgreSQL 18 |
| MySQL level | REPEATABLE READ | MySQL 8.4, InnoDB |
| `NESTED` support | `DataSourceTransactionManager`; off in `JpaTransactionManager` | Spring Framework 7.0 |

## Interview Qs

### REQUIRED vs REQUIRES_NEW?

REQUIRED joins the caller's transaction, so everything commits or rolls back together. REQUIRES_NEW suspends it and runs its own transaction, on its own connection, which commits or rolls back independently of the caller.

### Which isolation levels exist, and which is the default?

READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ and SERIALIZABLE, each stopping more read problems. Spring's default is DEFAULT: the database's own level, READ COMMITTED in PostgreSQL and REPEATABLE READ in MySQL InnoDB.

### Dirty, non-repeatable and phantom reads?

Dirty: you read another transaction's change before it commits. Non-repeatable: you read a row twice and another transaction changed it in between. Phantom: you run the same query twice and a row another transaction inserted appears.

### Optimistic vs pessimistic locking?

Optimistic: a @Version column is checked on update; if the row changed since you read it, you get OptimisticLockException and the transaction is marked for rollback. Pessimistic: @Lock(PESSIMISTIC_WRITE) takes a database lock, so other updaters wait.
