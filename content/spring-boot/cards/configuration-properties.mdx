## What it is

These are the two main ways to get a value from the [Environment](card:externalized-configuration) into a bean. `@Value("${app.name}")` injects **one** key into one field or constructor parameter. `@ConfigurationProperties("app.payment")` goes on a class or record and fills its fields from **every** key that starts with `app.payment`. That class then becomes a normal bean that you inject wherever the settings are needed, through [dependency injection](card:dependency-injection).

## Why it exists

The payment service has a currency, a timeout and a retry count. With `@Value`, each class that needs them repeats the key as a string, such as `"${app.payment.timeout}"`. A typo or a renamed key is found only at runtime, and nothing checks that the timeout is valid. `@ConfigurationProperties` puts the whole group in one typed class: one place for keys, defaults and checks, and your IDE can complete the keys in `application.properties`.

## How it works

<Compare id="value-vs-configuration-properties-vs-environment" />

1. At startup, `@ConfigurationPropertiesScan` (or `@EnableConfigurationProperties`) finds the class and registers it as a bean.
2. Boot collects every key under the prefix from the Environment, whichever source it came from.
3. It matches each key to a field with relaxed binding, so `max-retries` fills `maxRetries`.
4. It converts the text to the field's type: `30s` becomes a `Duration`, `5` an `int`. A missing key gets the `@DefaultValue`.
5. If the class has `@Validated`, Boot checks its constraints, and a failure stops startup.

## Example

The payment settings, then the record that holds them and a service that uses them:

```properties
app.payment.currency=INR
app.payment.max-retries=5
```

```java
@ConfigurationProperties("app.payment")
@Validated
public record PaymentProperties(
        @NotBlank String currency,
        @DefaultValue("30s") Duration timeout,
        @DefaultValue("3") int maxRetries) { }

@Service
class PaymentService {
    PaymentService(PaymentProperties props,
                   @Value("${app.name:payment-service}") String appName) {
        // props: currency=INR, timeout=PT30S, maxRetries=5
    }
}
```

What to notice:

- `max-retries=5` filled `maxRetries`, and the missing timeout took its default of 30 seconds. The comment shows the values a real run printed.
- Starting with an empty `app.payment.currency` fails startup with "Reason: must not be blank", naming the property and its source.
- `@Value` with `:payment-service` has a fallback. Without it, a missing `app.name` stops startup.
- The main class needs `@ConfigurationPropertiesScan`; without it, `PaymentService` fails because no `PaymentProperties` bean exists.

## Rules and defaults

- **Recommended:** Spring Boot's docs recommend `@ConfigurationProperties` for groups of your own settings.
- **Records and constructor binding:** a class with one constructor, or a record, binds through that constructor. It cannot be a `@Component` or `@Bean`; register it by scanning or `@EnableConfigurationProperties`.
- **JavaBean style:** a class with a no-argument constructor binds through setters, so it needs getters and setters.
- **Library classes:** put `@ConfigurationProperties("prefix")` on a public `@Bean` method to bind settings onto an object you did not write.
- **Units:** a `Duration` with no unit means milliseconds, unless the field has `@DurationUnit`.
- **Validation:** needs a Bean Validation implementation, such as `spring-boot-starter-validation`. Nested objects are checked only if their field has `@Valid` (since Boot 3.4).
- **IDE completion:** add `spring-boot-configuration-processor` as an annotation processor; it writes `spring-configuration-metadata.json` from your classes.

## Not to be confused with

`Environment.getProperty("key")` also reads settings, but in code, at the moment you call it, which suits keys chosen at runtime. `@Value` and `@ConfigurationProperties` inject values once, when the bean is created. Rule: one value = `@Value`; a group = `@ConfigurationProperties`; a key known only at runtime = `Environment`.

## Common mistakes

- **"Adding @Component to the properties record."** A record binds through its constructor, and constructor binding does not work for `@Component` beans. Use `@ConfigurationPropertiesScan` instead.

## Interview Qs

### If @Value can read configuration, why do we need @ConfigurationProperties?

`@Value` suits one or two values. For a group of related settings, `@ConfigurationProperties` gives one typed class with defaults, startup validation, full relaxed binding and IDE completion. The key lives in one place instead of being repeated as strings across classes, and Spring Boot's docs recommend it for your own settings.

### @Value or Environment: when do you use which?

`@Value` is declarative: the value is injected once, when the bean is created. `Environment.getProperty()` reads a key in code whenever you call it, which helps when the key name is known only at runtime. It returns `null`, or the default you pass, when the key is missing.

### How do you validate configuration properties?

Put `@Validated` on the class and Jakarta constraints such as `@NotBlank` or `@Min` on its fields, with a validator such as Hibernate Validator on the classpath. Values are checked while binding at startup, and a failure stops the app. Nested objects need `@Valid` on their field.
