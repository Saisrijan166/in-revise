## Why it exists

Many `@Value("${...}")` strings spread over classes are easy to mistype and hard to validate. Binding a whole prefix to one class gives types, defaults, validation and IDE completion in one place.

## How it works

<Compare id="value-vs-configuration-properties-vs-environment" />

- Register the class with `@ConfigurationPropertiesScan` on the main class, or list it in `@EnableConfigurationProperties`.
- A record cannot be a `@Component`: constructor binding needs one of those two.
- `30s` binds to a `Duration`; a bare number means milliseconds.

## Example

```java
@ConfigurationProperties("app.payment")
@Validated
public record PaymentProperties(
        @NotBlank String currency,
        @DefaultValue("30s") Duration timeout) { }

@Service
class PaymentService {
    PaymentService(PaymentProperties props,
                   @Value("${app.name:shop}") String appName) { }
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `@Value` key missing, no `:default` | start-up fails | Spring Boot 4.1 |
| `Duration` with no unit | milliseconds | Spring Boot 4.1 |
| Nested object validated | only if its field has `@Valid` | Spring Boot 3.4 and later |

## Interview Qs

### If @Value can read configuration, why do we need @ConfigurationProperties?

`@Value` suits one or two values. For a group of related settings, `@ConfigurationProperties` gives one typed class with defaults, start-up validation, full relaxed binding and IDE completion. Spring Boot's docs recommend it for your own settings.

### @Value or Environment: when do you use which?

`@Value` is declarative: the value is injected when the bean is created. `Environment.getProperty()` reads a key in code whenever you call it, which helps when the key name is known only at runtime.

### How do you validate configuration properties?

Add `@Validated` to the class and Jakarta constraints such as `@NotBlank` to its fields. Values are checked at binding, and a failure stops start-up. Nested objects need `@Valid` on the field.
