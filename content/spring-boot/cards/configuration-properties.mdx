## Why it exists

Settings scattered as `@Value("${...}")` strings are untyped, easy to mistype and hard to validate. Binding a whole prefix to one class gives types, defaults, validation and IDE completion in one place.

## How it works

<Compare id="value-vs-configuration-properties" />

- Register the class with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`. Constructor binding (records) does not work for `@Component` or `@Bean` beans.
- `30s` binds to a `Duration` and `10MB` to a `DataSize`; a bare number means milliseconds or bytes.
- Add `spring-boot-configuration-processor` and IDEs autocomplete your keys from the generated [configuration metadata](card:configuration-metadata).

## Example

```java
@ConfigurationProperties("app.mail")
@Validated
public record MailProperties(
        @NotBlank String host,
        @DefaultValue("25") int port,
        @DefaultValue("10s") Duration timeout) {
}

@SpringBootApplication
@ConfigurationPropertiesScan
public class ShopApplication { }
```

```properties
app.mail.host=smtp.example.com
app.mail.timeout=5s
```

Inject `MailProperties` through a constructor like any bean. If `app.mail.host` is missing, `@NotBlank` fails and the app does not start.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `Duration` with no unit | milliseconds (`@DurationUnit` changes it) | Spring Boot 4.1 |
| `DataSize` with no unit | bytes (`@DataSizeUnit` changes it) | Spring Boot 4.1 |
| `@Value` key missing, no `:default` | start-up fails | Spring Boot 4.1 placeholder configurer |
| Nested object validated | only if its field has `@Valid` | Spring Boot 3.4 and later |

## Interview Qs

### @Value or @ConfigurationProperties: when do you use which?

`@Value` for a single value or a SpEL expression. `@ConfigurationProperties` for a group of related settings: you get one typed class with defaults, validation, relaxed binding and IDE completion. Spring Boot's docs recommend it for your own components.

### What is relaxed binding?

Spring Boot matches property names loosely: `first-name`, `firstName`, `first_name` and the env var `..._FIRSTNAME` all bind the same field. Kebab-case is the recommended form in files. `@ConfigurationProperties` gets full relaxed binding; `@Value` only when the key is written in kebab-case.

### How do you validate configuration properties?

Add `@Validated` to the class and Jakarta constraints such as `@NotBlank` or `@Min` to its fields, with a validator on the classpath (`spring-boot-starter-validation`). Values are checked at binding, and a failure stops start-up. Nested objects need `@Valid`.

### How do you make configuration properties immutable?

Use a record, or a class with one constructor and final fields. Spring Boot then uses constructor binding: no setters, and `@DefaultValue` on a parameter supplies its default. Register it with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`, not `@Component`.
