## What it is

Spring Boot's test support lets each test start only as much of the app as it checks. A **unit test** starts no Spring at all: you create one class yourself. A **slice test**, such as `@WebMvcTest`, starts the beans of one layer. `@SpringBootTest` starts the whole [application context](card:ioc-container), the container that holds every bean.

## Why it exists

If every test started the whole payment service, with its database, security and every bean, a test suite of hundreds of tests would take minutes. Most tests check one thing: a calculation, a URL mapping, a query. Slices give each kind of test only the beans it needs, so it starts fast and fails for one clear reason.

## How it works

<Compare id="unit-vs-slice-vs-springboottest" />

1. You pick one test annotation for the class, such as `@WebMvcTest` for a controller.
2. The annotation turns on only the [auto-configuration](card:auto-configuration) for that layer, and scans only that layer's beans.
3. Any bean the tested class needs from outside the slice must be supplied as a mock, or the context fails to start.
4. Spring caches the started context. The next test class with the same configuration reuses it instead of starting again.

So the rule is: load the least that still tests something real.

## Example

This test checks that `GET /payments/1` returns the payment as JSON. The real `PaymentService` is not started; a fake stands in for it.

```java
@WebMvcTest(PaymentController.class)
class PaymentControllerTests {

    @Autowired MockMvcTester mvc;
    @MockitoBean PaymentService payments;   // the web slice does not load @Service beans

    @Test
    void returnsPayment() {
        when(payments.find(1L)).thenReturn(new PaymentResponse(1L, new BigDecimal("500.00"), "PAID"));

        assertThat(mvc.get().uri("/payments/1"))
                .hasStatusOk()
                .bodyJson().extractingPath("$.status").isEqualTo("PAID");
    }
}
```

What to notice:

- `@WebMvcTest(PaymentController.class)` starts only this controller and the web setup: mapping, JSON, validation, `@ControllerAdvice`.
- `MockMvcTester` sends the request through the real [DispatcherServlet](card:dispatcher-servlet) without opening a port.
- `@MockitoBean` puts a fake `PaymentService` in the context; [Mockito](card:mockito) explains how fakes work. Remove that line and the context fails to start, because the controller has nothing to inject.

## Rules and defaults

- **One slice per class:** using two `@…Test` slice annotations together is not supported. Pick one and add the other layer's `@AutoConfigure…` annotations by hand.
- **`@SpringBootTest` web environment:** `MOCK` by default (no server). `RANDOM_PORT` and `DEFINED_PORT` start a real server; `NONE` starts no web layer at all.
- **MockMvc in a full test:** add `@AutoConfigureMockMvc`. Since Spring Boot 4.0, `@SpringBootTest` alone gives no MockMvc.
- **`@DataJpaTest`:** scans `@Entity` classes and repositories, uses an embedded database if one is on the classpath, and logs SQL. Add `@AutoConfigureTestDatabase(replace = Replace.NONE)` to keep your real database.
- **Rollback:** a `@Transactional` test is rolled back after each method, but not the work a real server did on its own thread (`RANDOM_PORT`, `DEFINED_PORT`).
- **Test modules (Boot 4.0+):** test support is split into modules named `spring-boot-<technology>-test`, such as `spring-boot-webmvc-test` for `@WebMvcTest`.

## Not to be confused with

A **unit test** checks one class's logic and starts no Spring. An **integration test** checks that real parts work together, such as beans, configuration and a database. Rule: no Spring context means unit test; any context, a slice or the full one, means integration test.

## Common mistakes

- **"Every test should be a @SpringBootTest, to be realistic."** It is the slowest kind and its failures are hard to place. Keep it for a few end-to-end flows.
- **Giving each test class a different set of mocks or properties.** Each new combination starts a new context, so the cache cannot help and the suite slows down.

## Interview Qs

### If JUnit and Mockito can test a service, why use @SpringBootTest?

They test different things. A unit test checks one class in isolation and runs in milliseconds. `@SpringBootTest` checks that the real beans, configuration, transactions and database work together, which a unit test cannot see. So you write many unit tests and a few full-context tests.

### If @SpringBootTest loads everything, why use @WebMvcTest?

Loading the database and every service is wasted time for a controller test. `@WebMvcTest` starts only the web layer, so it checks mappings, validation, JSON and status codes quickly, and a failure points straight at the controller.

### Is data saved in a RANDOM_PORT test rolled back by @Transactional?

No. The real server handles the request on its own thread, in its own transaction, and that transaction commits. Only the test method's transaction rolls back. Clean up the data yourself, for example in an `@AfterEach` method.

### How do you keep a large Spring test suite fast?

Prefer unit tests and slices, and keep test configuration the same across classes so the context cache is reused. Every different set of `@MockitoBean` fields, properties or profiles starts a new context.
