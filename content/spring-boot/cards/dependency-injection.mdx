## What it is

Dependency injection (DI) is the way the [container](card:ioc-container) connects beans. A dependency is another object a class needs to do its work: `PaymentService` needs a `PaymentRepository` to save payments. With DI the class only declares what it needs, usually as constructor parameters, and the container passes in the matching beans. DI is how Spring puts inversion of control into practice.

## Why it exists

If `PaymentService` creates its own repository with `new`, it is tied to that one class. A unit test cannot hand it a fake repository, and the repository it built is not a bean, so Spring cannot manage it. With DI, `PaymentService` asks for "some `PaymentRepository`" and does not care which class it gets. Spring passes the real one; a test passes a fake.

## How it works

  alt="The container creates PaymentRepository first, because it needs nothing. Then it creates PaymentService and passes the repository into its constructor. Then it creates PaymentController and passes the service into its constructor."
  chart={`flowchart LR
  C[Container] -- "1. creates" --> R[PaymentRepository]

  R -. injected into .-> S

1. Spring reads each bean's constructor to see what it needs. `PaymentController` needs a `PaymentService`, and `PaymentService` needs a `PaymentRepository`.
2. It creates the beans in dependency order, starting with the repository, which needs nothing.
3. It calls `new PaymentService(repository)` with the bean it already has, then `new PaymentController(service)`.
4. It finds each dependency by its type. If no bean of that type exists, or several do and nothing says which one to use, startup fails; [@Primary and @Qualifier](card:bean-selection) shows how to choose.

So you never write the wiring code; you only write constructors.

## Example

`PaymentService` declares its one dependency in the constructor, and a test builds it without Spring.

```java
@Service
public class PaymentService {
    private final PaymentRepository repository;           // final: set once, never null

    public PaymentService(PaymentRepository repository) { // no @Autowired needed
        this.repository = repository;
    }

    public Payment pay(long amount) {
        return repository.save(new Payment(null, amount, "COMPLETED"));
    }
}

// In a unit test, no Spring at all:
var service = new PaymentService(new InMemoryPaymentRepository());
```

What to notice:

- `private final` means the field is set once, in the constructor, and can never be null or replaced later.
- The class has one constructor, so Spring uses it without `@Autowired`. Add a second constructor and you must mark the one Spring should use with `@Autowired`.
- The parameter type is the `PaymentRepository` interface, not a concrete class, so Spring and the test can each pass a different implementation.
- The test line builds the service with `new` and an in-memory fake: no container, no database, a fast test.

## Rules and defaults

- **Single constructor:** Spring always uses it, with or without `@Autowired`.
- **Several constructors:** mark one with `@Autowired`. If none is marked, Spring uses the no-argument constructor when there is one.
- **Optional dependencies:** the Spring docs advise setter injection for dependencies that have a sensible default; `@Autowired(required = false)` or an `Optional<T>` parameter also mark a dependency as optional.

## Not to be confused with

There are three ways to inject. Constructor injection passes dependencies as constructor parameters. Setter injection lets Spring create the object first and then call a setter marked `@Autowired`. Field injection puts `@Autowired` on a field, which Spring fills by reflection, setting it directly after the object exists. Rule: constructor for required dependencies, setter for optional ones, field injection avoided in application code.

## Interview Qs

### What is dependency injection, and how is it related to IoC?

An object receives its dependencies from outside instead of creating them. IoC is the principle that the container controls object creation and wiring; DI is how Spring applies it, through constructor parameters, setters or fields.

### Why is constructor injection preferred over field injection?

Dependencies are visible in the constructor, fields can be `final`, the bean can never exist half-built, and a unit test can call the constructor with fakes. With field injection, `new PaymentService()` in a test leaves the field null, and you need Spring or reflection to fill it. The Spring team recommends constructors for required dependencies.

### Why not create a dependency with new inside a bean?

That object is not a bean: Spring injects nothing into it and does not manage it. Your class is also tied to one implementation, so a test cannot swap in a fake.
