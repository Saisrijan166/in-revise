## Why it exists

A class that builds its own collaborators is tied to them and hard to test. With DI the class only declares what it needs, and the [container](card:ioc-container) supplies it.

## How it works

<Mermaid
  alt="The container creates PaymentRepository first, then creates PaymentService and passes the repository into its constructor, then creates PaymentController and passes the service into its constructor."
  chart={`flowchart LR
  C[Container] -- "1. creates" --> R[PaymentRepository]
  C -- "2. new PaymentService(repo)" --> S[PaymentService]
  C -- "3. new PaymentController(service)" --> W[PaymentController]
  R -. injected into .-> S
  S -. injected into .-> W`}
/>

- Spring builds the dependencies first, then passes them in, matching by type.
- Several constructors: mark the one Spring should use with `@Autowired`.

## Example

```java
@Service
public class PaymentService {
    private final PaymentRepository repository;   // final: set once, never null

    public PaymentService(PaymentRepository repository) {   // no @Autowired needed
        this.repository = repository;
    }
}

// Unit test without Spring
var service = new PaymentService(mock(PaymentRepository.class));
```

## Interview Qs

### What is dependency injection, and how is it related to IoC?

An object receives its dependencies instead of creating them. IoC is the principle that the container controls object creation; DI is how Spring applies it, through constructors, setters or fields.

### Why is constructor injection preferred?

Dependencies are explicit, fields can be final, the bean is never half-built, and a unit test can call the constructor with mocks. The Spring team recommends it for required dependencies.

### Why not create a dependency with new inside a bean?

That object is not a bean: Spring injects nothing into it and does not manage it, and the class is tied to one implementation, so tests cannot swap in a mock.
