## Why it exists

A class that builds its own collaborators is tied to them and hard to test. With DI the class only declares what it needs, and the container supplies it.

## How it works

<Compare id="constructor-vs-setter-vs-field-injection" />

- Spring injects by type. When two beans match, see [choosing a bean](card:bean-selection).
- One constructor: Spring uses it, with no `@Autowired`. Several: mark one with `@Autowired`.
- Optional dependency: take `Optional<T>`, `ObjectProvider<T>` or a `@Nullable` parameter.

## Example

```java
@Service
public class CheckoutService {
    private final CartRepository carts;     // final: set once, never null
    private final PaymentClient payments;

    public CheckoutService(CartRepository carts, PaymentClient payments) {  // no @Autowired
        this.carts = carts;
        this.payments = payments;
    }
}

// Unit test: no Spring at all
var service = new CheckoutService(new InMemoryCarts(), mock(PaymentClient.class));
```

## Interview Qs

### What is dependency injection?

A design where an object receives the objects it needs instead of creating them. In Spring the IoC container injects them through constructors, setters or fields when it creates the bean.

### Constructor, setter or field injection: which do you use?

Constructor injection for required dependencies: final fields, no half-built objects, easy tests. Setter injection for optional ones with a default. Avoid field injection: it hides dependencies and needs reflection in tests.

### Do you need @Autowired on the constructor?

Not if the class has only one constructor; Spring always uses it. With several constructors, mark the one to use with `@Autowired`; otherwise Spring falls back to the no-argument constructor, if there is one.

### Why is field injection discouraged?

Fields cannot be final, a class created with `new` fails later with a NullPointerException, a long list of dependencies stays hidden, and unit tests need reflection, such as Mockito's `@InjectMocks`.
