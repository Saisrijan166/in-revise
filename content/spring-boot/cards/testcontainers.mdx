## Why it exists

An in-memory database or a mock does not behave exactly like production. Testcontainers gives each test run a throwaway real service in Docker.

## How it works

<Steps label="A test with Testcontainers">
  <Step title="Start">Testcontainers starts PostgreSQL in Docker.</Step>
  <Step title="Connect">`@ServiceConnection` hands its address and login to Spring Boot.</Step>
  <Step title="Test">The DataSource, JPA and Flyway use the real database.</Step>
  <Step title="Stop">The container is removed after the tests.</Step>
</Steps>

- Declared as a `@Bean`, a container starts once per cached context and is shared.
- `@DynamicPropertySource` is the manual way: add the container's URL as a property yourself.

## Example

```java
@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfig {
    @Bean
    @ServiceConnection   // no spring.datasource.url needed
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:18");
    }
}
```

## Interview Qs

### Why use Testcontainers instead of H2?

H2 is not your production database; some SQL differs or is missing. A test can pass on H2 and fail in production. Testcontainers runs the real database, so tests check what really runs.

### What does @ServiceConnection do?

It reads the container's address and login and registers `ConnectionDetails` beans. Auto-configuration uses them instead of connection properties, so you write no URLs or ports.
