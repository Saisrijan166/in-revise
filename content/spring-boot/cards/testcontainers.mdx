## Why it exists

Mocks and in-memory databases behave differently from the real PostgreSQL, Kafka or Redis. Testcontainers gives each test run a throwaway real service in Docker.

## How it works

<Mermaid
  alt="Testcontainers flow. The test starts. Testcontainers starts PostgreSQL in Docker. @ServiceConnection creates JdbcConnectionDetails from the container. Spring Boot connects the DataSource, JPA and Flyway to it. The tests run on a real database. The container is stopped afterwards."
  chart={`flowchart LR
  T([Test starts]) --> C[Testcontainers starts PostgreSQL in Docker]
  C --> S["@ServiceConnection creates JdbcConnectionDetails"]
  S --> A[DataSource, JPA and Flyway connect to it]
  A --> R[Tests run on a real database]
  R --> X([Container stopped])`}
/>

- Declare containers as `@Bean`s in a shared `@TestConfiguration`: one container per cached context, reused by many test classes. Static `@Container` fields stop after each test class.
- `@DynamicPropertySource` is the manual, more flexible alternative: you add the container's URL as a property yourself.
- At development time, run the app from a test `main` with the same containers, or let Docker Compose support start `compose.yml`.

## Example

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers-postgresql</artifactId>
    <scope>test</scope>
</dependency>
```

```java
@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfig {

    @Bean
    @ServiceConnection   // no spring.datasource.url needed
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:18");
    }
}

@SpringBootTest
@Import(TestcontainersConfig.class)
class OrderRepositoryTests {
    @Autowired OrderRepository orders;   // talks to the real PostgreSQL
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Container in a static `@Container` field | Stopped after the test class | Testcontainers JUnit extension |
| Container declared as a `@Bean` | Started before all other beans, once per context | Spring Boot 4.1 |
| Docker Compose support in tests | Skipped (`spring.docker.compose.skip.in-tests`) | Spring Boot 4.1 |
| Testcontainers version | 2.0.5 | Managed by Spring Boot 4.1.1 |

## Interview Qs

### Why use Testcontainers instead of H2?

H2 is not your production database. Some SQL, such as PostgreSQL's `ON CONFLICT`, is missing or different, so a test can pass and production fail. Testcontainers runs the real database in Docker, so tests check what really runs.

### What does @ServiceConnection do?

It reads the running container's address and login and registers `ConnectionDetails` beans, such as `JdbcConnectionDetails`. Auto-configuration uses them instead of `spring.datasource.*` properties, so you write no connection properties.

### How do you avoid a new container for every test class?

Declare the container as a `@Bean` in a shared `@TestConfiguration`. Spring starts it once per cached context, so all test classes with the same configuration reuse it. Static `@Container` fields are stopped after each class.

### @ServiceConnection vs @DynamicPropertySource?

`@ServiceConnection` is automatic for supported services. `@DynamicPropertySource` is a static method where you add properties from the running container yourself: more code, but it works for any property.
