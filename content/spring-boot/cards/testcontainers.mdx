## What it is

Testcontainers is a Java library that starts real services, such as PostgreSQL or Kafka, in throwaway Docker containers while your tests run. A container is a small isolated process started from an image, like `postgres:18`. Spring Boot's `@ServiceConnection` then tells [auto-configuration](card:auto-configuration) where that container is, so the app connects to it without any URL in your properties.

## Why it exists

The usual shortcut is an in-memory database such as H2. It is fast, but it is not PostgreSQL: some SQL, types and functions behave differently, so a test can pass and the same query can fail in production. Installing a shared test database instead is slow to set up and tests disturb each other's data. Testcontainers gives each test run a fresh, real database and removes it afterwards.

## How it works

<Steps label="A test with Testcontainers">
  <Step title="Start">Testcontainers pulls the image and starts PostgreSQL in Docker on a free port.</Step>
  <Step title="Connect">`@ServiceConnection` creates connection details from the container: host, port, user, password.</Step>
  <Step title="Test">The DataSource, JPA and Flyway use the real database.</Step>
  <Step title="Stop">The container is removed when the test context closes.</Step>
</Steps>

1. You declare the container as a `@Bean` in a test configuration class.
2. Spring starts container beans before any other bean, so the database is up before the `DataSource` is built.
3. `@ServiceConnection` registers a `ConnectionDetails` bean, an object that holds the address and login. Auto-configuration uses it instead of `spring.datasource.*`.
4. The context, and the container with it, is cached and reused by later test classes with the same configuration.

## Example

This test configuration gives the payment service a real PostgreSQL 18 for its tests.

```java
@TestConfiguration(proxyBeanMethods = false)
class TestcontainersConfig {

    @Bean
    @ServiceConnection   // Boot takes the URL, user and password from the container
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:18");
    }
}
```

What to notice:

- A test uses it with `@Import(TestcontainersConfig.class)`, for example on a `@DataJpaTest` for `PaymentRepository`.
- There is no `spring.datasource.url` anywhere. The container picks a random free port, and `@ServiceConnection` passes it to Boot.
- Remove `@ServiceConnection` and the container still starts, but the app does not know about it and connects to whatever the properties say.

## Rules and defaults

- **Dependency:** service connections need `spring-boot-testcontainers` as a test dependency.
- **Precedence:** connection details from `@ServiceConnection` win over connection properties.
- **Slice tests (Spring Boot 4.1):** `@AutoConfigureTestDatabase` defaults to `NON_TEST`, so a `@DataJpaTest` keeps a DataSource that points at a test container instead of swapping in an embedded database.
- **Manual way:** a static `@DynamicPropertySource` method can add the container's URL as a property yourself. It is longer, but works for any property.
- **Docker:** the machine that runs the tests needs Docker or another Docker-API compatible runtime.

## Common mistakes

- **"A static @Container field per test class is the same as a @Bean."** The JUnit extension stops that container after the class, while Spring may keep the cached context that still points at it. A container `@Bean` lives as long as its context.

## Interview Qs

### Why use Testcontainers instead of H2?

H2 is not your production database. Some SQL, data types and functions differ or are missing, so a test can pass on H2 and fail in production. Testcontainers runs the real database, so the tests check what really runs, at the cost of needing Docker and a slower start.

### What does @ServiceConnection do?

It reads the container's host, port and login and registers a `ConnectionDetails` bean. Auto-configuration uses that bean instead of the connection properties, so you write no URLs or ports, and the random port the container gets is handled for you.

### How do you avoid starting a new container for every test class?

Declare the container as a `@Bean` in one shared `@TestConfiguration`, and keep the test configuration the same across classes. The context is cached, and the container lives with the context, so all those classes share one running database.
