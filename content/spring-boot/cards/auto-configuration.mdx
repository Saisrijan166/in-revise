## What it is

Auto-configuration is Spring Boot creating ready-made [beans](card:ioc-container) for you. A bean is an object that Spring creates and manages. When you add a starter, such as the one for databases, Boot also brings setup code that can build the beans that library needs. That setup code runs only when it makes sense for your app.

## Why it exists

Almost every app needs the same plumbing: a database connection pool, a JSON converter, a web server. In plain Spring you wrote a `@Bean` method for each of them, in every project, with almost the same code. Auto-configuration writes that code once, inside Boot, so a new app works with zero setup. You still keep control, because your own bean always replaces Boot's.

## How it works

1. Spring first registers the beans you wrote yourself.
2. Boot then reads a list of auto-configuration classes that ships inside its jars.
3. Each class has conditions, such as "only if this library is on the classpath" or "only if the app has no bean of this type yet". If they are all true, Boot creates the bean. If one is false, it skips that class.

So the order is the key: your beans come first, and Boot fills only the gaps.

## Example

The payment service needs a `DataSource`, the object that hands out database connections. Boot's own auto-configuration looks roughly like this simplified version:

```java
@AutoConfiguration
@ConditionalOnClass(DataSource.class)     // only if JDBC is on the classpath
public class MyDataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean             // only if the app has no DataSource yet
    DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();
    }
}
```

What to notice:

- `@ConditionalOnClass` keeps this class silent in apps that do not use a database at all.
- `@ConditionalOnMissingBean` is the "back off" rule. If the payment service defines its own `DataSource` bean, this method never runs.
- The bean is built from `spring.datasource.*` properties, so you change the database URL in configuration, not in code.

## Rules and defaults

- **Runs automatically:** `@SpringBootApplication` includes `@EnableAutoConfiguration`, so you do not switch it on yourself.
- **Where the list lives:** each jar lists its classes in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (the only supported place since Spring Boot 3.0).
- **Turning one off:** `@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)`, or the `spring.autoconfigure.exclude` property.
- **`@ConditionalOnProperty`:** by default it matches when the property exists and is not `false`.

## Not to be confused with

A [starter](card:starters) decides **which jars** you get. Auto-configuration decides **which beans** Boot builds from those jars. The starter brings the database library; auto-configuration notices it and creates the `DataSource`.

## Common mistakes

- **"I must exclude Boot's bean before I can define my own."** Not needed. Defining your bean is enough; Boot backs off by itself.
- **Guessing why a bean exists.** Start the app with `--debug` to print the condition evaluation report, which lists every auto-configuration and the conditions that passed or failed.

## Interview Qs

### How does Spring Boot know what to configure?

It reads the auto-configuration classes listed in its jars. Each one has conditions on the classpath, properties, the type of web app and the beans that already exist. Only the classes whose conditions all match add beans.

### How do you disable one auto-configuration?

Use `exclude` on `@SpringBootApplication`, `excludeName` when the class is not on the classpath, or the `spring.autoconfigure.exclude` property.

### Why was a bean (not) auto-configured?

Start the app with `--debug`. It logs the condition evaluation report: each auto-configuration with the conditions that matched or failed. With Actuator, the `/actuator/conditions` endpoint shows the same report.
