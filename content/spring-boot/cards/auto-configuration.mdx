## Why it exists

Most apps need the same infrastructure beans, such as a DataSource or a JSON mapper. Auto-configuration creates them from what is on the classpath, and steps back as soon as you define your own.

## How it works

<Mermaid
  alt="Auto-configuration flow. First your own beans are registered. Then Boot reads the AutoConfiguration.imports file in every jar. For each auto-configuration it checks its conditions, such as a class on the classpath, no bean of yours of that type, and a property that is not false. If they match, Boot creates its bean; if not, it skips it and backs off."
  chart={`flowchart TD
  U[1. Your beans are registered] --> L[2. Boot reads every AutoConfiguration.imports]
  L --> C{3. Conditions match? class present, no bean of yours, property not false}
  C -- yes --> NEW[Create Boot's bean]
  C -- no --> SKIP[Skip: Boot backs off]`}
/>

- With HSQLDB on the classpath and no `DataSource` bean, Boot starts an in-memory database. Declare your own `DataSource` and that support backs away.
- Run with `--debug` to log the condition evaluation report: what was configured, what was not, and why.
- Only an auto-configuration's class name is public API: use it to exclude the class, not to call its methods.

## Example

```java
@AutoConfiguration
@ConditionalOnClass(AcmeClient.class)       // only if the library is present
public class AcmeAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean               // back off if the app has one
    AcmeClient acmeClient() {
        return new AcmeClient();
    }
}
```

```text
# src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.autoconfigure.AcmeAutoConfiguration
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `@ConditionalOnProperty` matches | the property exists and is not `false` | Spring Boot 4.1 |
| `proxyBeanMethods` of `@AutoConfiguration` | always `false` | Spring Boot 4.1 |
| `debug` (conditions report) | `false` | Spring Boot 4.1 |

## Interview Qs

### How does auto-configuration work?

Boot reads the classes listed in each jar's AutoConfiguration.imports file. Each is a configuration class with conditions such as `@ConditionalOnClass` and `@ConditionalOnMissingBean`. Only those whose conditions match add beans, and they run after your own beans are registered.

### How do you disable a specific auto-configuration?

Use `exclude` on `@SpringBootApplication`, or `excludeName` with the full class name when the class is not on the classpath. Or list it in `spring.autoconfigure.exclude`. Both ways can be combined.

### How do you make an auto-configuration back off when a bean exists?

Put `@ConditionalOnMissingBean` on its `@Bean` method. If a bean of that type is already defined, the method is skipped. Use it only in auto-configuration classes, which are processed after the app's own beans.

### How do you find out why a bean was or was not auto-configured?

Start the app with `--debug` to log the condition evaluation report, or call Actuator's `/actuator/conditions` endpoint. Both list each auto-configuration with the conditions that matched or failed.
