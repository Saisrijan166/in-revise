## Why it exists

Real apps often have several beans of one type: two payment gateways, two DataSources. Injection by type alone cannot tell them apart, so Spring needs a rule, or it refuses to guess.

## How it works

<Mermaid
  alt="Choosing a bean for one injection point. If no bean matches the type, startup fails unless the dependency is optional. If exactly one matches, it is injected. If several match: a @Qualifier at the injection point first keeps only the matching beans. Then, if exactly one is @Primary, it is injected. Else, if exactly one bean is not marked @Fallback, it is injected. Else, if a bean is named like the field or parameter, it is injected. Otherwise startup fails with NoUniqueBeanDefinitionException."
  chart={`flowchart TD
  T([Injection point of type T]) --> N{How many beans match?}
  N -- none --> X1[Fails, unless optional]
  N -- one --> OK([Inject it])
  N -- several --> Q["@Qualifier? Keep only matching beans"]
  Q --> P{"Exactly one @Primary?"}
  P -- yes --> OK
  P -- no --> F{"Exactly one not @Fallback?"}
  F -- yes --> OK
  F -- no --> NM{"Bean named like the parameter?"}
  NM -- yes --> OK
  NM -- no --> X2[NoUniqueBeanDefinitionException]`}
/>

- A qualifier is a filter, not an id: many beans may share one, and `@Qualifier` on a `List` injects all of them.
- `@Resource` picks a bean by its unique name instead of its type, but only on fields and setters.
- The name match needs parameter names in the bytecode; Spring Boot's Maven parent compiles with `-parameters`.
- A second DataSource in Spring Boot 4.1: declare it `@Bean(defaultCandidate = false)` with a `@Qualifier`, so the auto-configured one stays the default.

## Example

```java
@Component @Primary
class UpiGateway implements PaymentGateway { }

@Component("cardGateway")
class CardGateway implements PaymentGateway { }

@Service
class CheckoutService {
    CheckoutService(PaymentGateway usual,                           // UpiGateway: @Primary
                    @Qualifier("cardGateway") PaymentGateway card,  // picked by name
                    Map<String, PaymentGateway> all) { }            // both, keyed by bean name
}
```

## Interview Qs

### Two beans implement the same interface. What happens?

Injecting the interface fails at startup with NoUniqueBeanDefinitionException. Fix it with @Primary on the usual bean, @Qualifier at the injection point, @Fallback on the backup, or a parameter name that matches a bean name.

### @Primary vs @Qualifier?

@Primary sits on a bean and sets the default for every injection point. @Qualifier sits at one injection point and picks a bean there. When both apply, @Qualifier wins, because it filters the candidates first.

### How do you inject all implementations of an interface?

Inject `List<PaymentGateway>` to get every bean, sorted by `@Order` if set, or `Map<String, PaymentGateway>` keyed by bean name. This is the usual way to build a strategy lookup.

### What does @Fallback do?

Added in Spring Framework 6.2, it is the opposite of @Primary: you mark the beans that should lose. Spring injects a @Fallback bean only when no regular bean of that type is left.
