## What it is

When a constructor asks for a type, Spring looks for beans of that type. If two beans fit, for example `EmailSender` and `SmsSender` both implement `NotificationSender`, Spring cannot guess and startup fails. `@Primary` goes on one bean and marks it as the default choice. `@Qualifier` goes on an injection point, the parameter or field that receives a bean, and names the exact bean that place wants.

## Why it exists

Real apps often have several implementations of one interface: two notification channels, two payment gateways. [Dependency injection](card:dependency-injection) matches by type, and the type alone does not say which one you mean. Spring refuses to pick one at random, because a silent wrong choice, such as sending an SMS instead of an email, is worse than a clear startup error. `@Primary` and `@Qualifier` let you state the choice in code.

## How it works

1. Spring collects every bean whose type matches the parameter.
2. If the parameter has `@Qualifier("smsSender")`, Spring keeps only the beans with that qualifier. A bean's name always counts as its qualifier. If exactly one bean is left, Spring injects it and stops.
3. If several beans are still left, Spring injects the one marked `@Primary`. Two `@Primary` beans are ambiguous again.
4. With no `@Primary`, Spring injects a bean whose name equals the parameter name, if one exists. This needs the `-parameters` compiler flag, which Spring Boot's parent POM and Gradle plugin set for you.
5. Otherwise startup fails with `NoUniqueBeanDefinitionException`, and Boot prints that the class "required a single bean, but 2 were found".

So the qualifier filters first, and `@Primary` only breaks the tie among what is left.

## Example

Two senders implement one interface. `NotificationService` takes the default, one exact choice, and all of them.

```java
interface NotificationSender { void send(String message); }

@Component @Primary
class EmailSender implements NotificationSender { public void send(String m) { } }

@Component                              // bean name: smsSender
class SmsSender implements NotificationSender { public void send(String m) { } }

@Service
class NotificationService {
    NotificationService(NotificationSender usual,                         // EmailSender
                        @Qualifier("smsSender") NotificationSender sms,  // SmsSender
                        List<NotificationSender> all) { }                // both
}
```

What to notice:

- `usual` has no qualifier, so it gets `EmailSender`, the `@Primary` bean.
- `@Qualifier("smsSender")` overrides `@Primary` for that one parameter. `smsSender` is the default name of `SmsSender`.
- `List<NotificationSender>` receives both beans, useful for sending through every channel. A `Map<String, NotificationSender>` would map `emailSender` and `smsSender` to their beans.
- Remove `@Primary` and the first parameter stops startup: two candidates, and no rule to choose.

## Rules and defaults

- **Order of the rules:** the qualifier filters first, then `@Primary` decides, then the parameter name; if none settles it, startup fails.
- **Default bean names:** a scanned class gets its class name with a lower-case first letter; a `@Bean` method's bean gets the method name.
- **A qualifier is a filter, not an id:** several beans can share one qualifier value.
- **`@Fallback` (Spring Framework 6.2+):** the opposite of `@Primary`; that bean is used only when no other candidate is left.
- **List order:** a `List<T>` follows `@Order` or `Ordered` when set, otherwise the order in which the beans were registered.

## Not to be confused with

`@Primary` sits on the bean and sets one default for every injection point of that type. `@Qualifier` sits at one injection point and chooses for that place only. Rule: `@Primary` is the default choice; `@Qualifier` is the exact choice.

## Interview Qs

### Two beans implement the same interface. What happens?

Injecting the interface fails at startup with `NoUniqueBeanDefinitionException`, unless the parameter name matches one bean's name. Fix it by marking the usual bean `@Primary`, by adding `@Qualifier` at the injection point, or by injecting a `List` of all of them.

### If @Primary already picks a bean, why do we need @Qualifier?

`@Primary` sets one default for the whole app. `@Qualifier` lets one class ask for a different bean, such as an OTP service that must send SMS. When both apply, `@Qualifier` wins, because it filters the candidates before `@Primary` is checked.

### How do you inject all implementations of an interface?

Inject `List<NotificationSender>`, sorted by `@Order` if set, or `Map<String, NotificationSender>` keyed by bean name. This is a common way to build a strategy lookup, for example picking a sender by channel name at runtime.
