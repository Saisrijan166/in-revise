## What it is

Spring Security is the Spring project for login, permission checks and protection against common web attacks. In a Spring MVC app it works as a group of [servlet filters](card:filters-interceptors) that run before [DispatcherServlet](card:dispatcher-servlet). A **SecurityFilterChain** is one ordered list of those filters, plus a rule saying which requests it handles. You describe it in a bean, and Spring Security builds the filters from your description.

## Why it exists

Without it, each controller would read the session or token and check permissions itself. The same check is copied into dozens of places, and one forgotten copy leaves an endpoint open. A filter sees every request before any controller, so one place can protect the whole app. The same filters also add defences you would otherwise write by hand, such as blocking requests forged by other sites ([CSRF](card:csrf-cors), covered later).

1. The servlet container (Tomcat) runs its filters for the request. One of them is DelegatingFilterProxy, which Boot registers for you.
2. DelegatingFilterProxy is a plain servlet filter that passes the request to a Spring bean, FilterChainProxy. The split exists because the container starts its filters before Spring has created its beans.
3. FilterChainProxy finds the first SecurityFilterChain whose matcher fits the request, and runs only that chain.
4. The chain's filters run in a fixed order: CsrfFilter checks for forged requests, the login filters read credentials, ExceptionTranslationFilter turns security errors into responses, and AuthorizationFilter applies the access rules.
5. If every filter lets the request through, it reaches DispatcherServlet and your controller. If one rejects it, the response goes back at once and the controller never runs.

## Example

The payment service keeps its health check public and asks for HTTP Basic login everywhere else:

```java
@Configuration
class SecurityConfig {

    @Bean
    SecurityFilterChain paymentSecurity(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health").permitAll()
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}
```

What to notice:

- Each lambda configures one part of the chain: `authorizeHttpRequests` adds AuthorizationFilter, and `httpBasic` adds the Basic login filter.
- Because this bean exists, Boot's default chain backs off, the same way any [auto-configuration](card:auto-configuration) does.
- Remove `.httpBasic(...)` and the chain has no way to log anyone in, so every request except the health check is rejected.

## Rules and defaults

- **Starter only (Boot 4.1):** every URL is secured, including `/error` and Actuator endpoints. Login is form login or HTTP Basic, depending on the request's `Accept` header.
- **Default user:** the name is `user`, and a random password is printed at WARN level at startup. It is for development only.
- **Your own chain:** a `SecurityFilterChain` bean replaces Boot's rules, but the default user stays until you define a `UserDetailsService`, `AuthenticationProvider` or `AuthenticationManager` bean.
- **Several chains:** only the first match runs, so put specific chains first and the catch-all chain last.
- **Your own filter:** place it with `addFilterBefore`, `addFilterAfter` or `addFilterAt` next to a built-in filter.
- **Changed in 6.0 and 7.0:** `WebSecurityConfigurerAdapter` was removed in 6.0, and `and()` was removed from the DSL in 7.0.
- **Debugging:** the response never says why a request was rejected. Set `logging.level.org.springframework.security=TRACE` to log each filter and the reason.

## Common mistakes

- **"I annotate my security filter with @Component and also add it with addFilterBefore."** Boot registers every `Filter` bean with the container too, so it runs twice, once outside the chain. Do not make it a bean, or disable its `FilterRegistrationBean`.

## Interview Qs

### What happens when you add spring-boot-starter-security?

The whole app, Actuator included, needs login. Boot creates the user `user` with a random password printed in the log, and offers form login or HTTP Basic, depending on the request's `Accept` header. Defining a `SecurityFilterChain` bean replaces these rules.

### What is the difference between DelegatingFilterProxy and FilterChainProxy?

DelegatingFilterProxy is a plain servlet filter registered with the container. It looks up a Spring bean lazily, because the container starts before the beans exist. That bean is FilterChainProxy, which picks the first matching SecurityFilterChain and runs its filters.

### How do you configure security without WebSecurityConfigurerAdapter?

Declare a `SecurityFilterChain` bean that takes `HttpSecurity`, configures it with lambdas and returns `http.build()`. The adapter was deprecated in 5.7 and removed in 6.0.

### Why is Spring Security built on filters and not inside controllers?

Filters run for every request before Spring MVC chooses a controller, so nothing can skip them by accident. They also cover requests that no controller handles, such as static files.
