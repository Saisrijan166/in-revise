## Why it exists

Every request must be checked for who is calling and what they may do before it reaches a controller. Servlet filters run first, so Spring Security puts its checks there.

## How it works

<Mermaid
  alt="Request path through Spring Security. The servlet container calls DelegatingFilterProxy, which calls the FilterChainProxy bean. FilterChainProxy picks the first SecurityFilterChain that matches the request and runs its filters in order: CorsFilter and CsrfFilter, then login filters, then ExceptionTranslationFilter, then AuthorizationFilter. Only then does the request reach the DispatcherServlet and the controller."
  chart={`flowchart TD
  R([Request]) --> D["DelegatingFilterProxy (servlet filter)"]
  D --> F["FilterChainProxy (Spring bean)"]
  F -- "first matching chain" --> C1["CorsFilter, CsrfFilter"]
  C1 --> C2["Login filters: form, bearer token, Basic"]
  C2 --> C3[ExceptionTranslationFilter]
  C3 --> C4[AuthorizationFilter]
  C4 --> S([DispatcherServlet and controller])`}
/>

- **Several chains:** give each a `securityMatcher` and an `@Order`; only the first match runs, so keep a catch-all chain last.
- A filter that is also a `@Component` is registered by Boot with the servlet container too, so it can run twice. Add it with `addFilterBefore` and disable the container registration.
- To debug, set `logging.level.org.springframework.security=TRACE`: it logs each filter a request passes.

## Example

```java
@Configuration
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) {
        http.securityMatcher("/api/**")
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| User name | `user` (`spring.security.user.name`) | Spring Boot 4.1 |
| Password | Random, logged at WARN on startup | Spring Boot 4.1 |
| Default chain | Every request authenticated; form login and HTTP Basic | Spring Boot 4.1 |
| `@EnableWebSecurity` | Added for you when missing | Spring Boot 4.1 |
| Security filter order in the container | -100 (`spring.security.filter.order`) | Spring Boot 4.1 |

## Interview Qs

### What happens when you add spring-boot-starter-security?

Every endpoint needs login, including `/error` and Actuator endpoints. Boot creates the user `user` with a random password printed in the log, and a default chain with form login and HTTP Basic. Your own `SecurityFilterChain` bean replaces that chain.

### DelegatingFilterProxy vs FilterChainProxy?

DelegatingFilterProxy is a plain servlet filter registered with the container; it looks up a Spring bean and delegates to it. That bean is FilterChainProxy, which picks the first matching SecurityFilterChain and runs its security filters.

### How do you configure security now that WebSecurityConfigurerAdapter is gone?

Declare one or more `SecurityFilterChain` beans that configure `HttpSecurity` with the lambda DSL and return `http.build()`. Several chains need `securityMatcher` and `@Order`; the first match handles the request.

### Where do you add a custom filter, such as an API-key check?

Call `addFilterBefore`, `addFilterAfter` or `addFilterAt` with a built-in filter class as the anchor. Spring's rule of thumb: an authentication filter goes after `LogoutFilter`, an authorization filter after `AnonymousAuthenticationFilter`.
