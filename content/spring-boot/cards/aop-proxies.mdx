## Why it exists

Spring adds behaviour such as transactions without changing your class. It does this by handing callers a proxy object that runs the extra code around each call.

## How it works

<Mermaid
  alt="The caller calls placeOrder on a proxy. The proxy runs the advice, then calls the real OrderService. A this.audit call inside it skips the proxy."
  chart={`flowchart LR
  C[Caller] -- "placeOrder()" --> P["Proxy: advice runs"]
  P -- "then calls" --> T[Real OrderService]
  T -- "this.audit(): no proxy" --> T`}
/>

- Fixes for self-invocation, best first: move the method to another bean, inject the bean into itself, or use AspectJ weaving.
- A JDK proxy implements the bean's interfaces; a CGLIB proxy is a generated subclass. See [JDK vs CGLIB](compare:jdk-proxy-vs-cglib).
- Do not rely on proxied annotations inside `@PostConstruct`; the proxy may not be ready yet.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Proxy type | CGLIB (`spring.aop.proxy-target-class=true`); set `false` for JDK proxies | Spring Boot 4.1 |
| Core Spring without Boot | JDK proxy if the bean has an interface, else CGLIB | Spring Framework 7.0 |

## Interview Qs

### Why does @Transactional not work when I call the method from the same class?

The call uses `this`, the real object, so the proxy never sees it. Move the method to another bean, or use AspectJ weaving.

### If @Transactional is just an annotation, who starts the transaction?

A proxy Spring puts around the bean. It reads the annotation, starts the transaction, calls your method, then commits or rolls back.

### JDK dynamic proxy vs CGLIB?

A JDK proxy implements the bean's interfaces, so only interface methods are advised. CGLIB generates a subclass, so no interface is needed, but final and private methods cannot be advised. Spring Boot uses CGLIB by default.
