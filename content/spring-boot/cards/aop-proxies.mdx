## What it is

A proxy is a wrapper object that Spring creates around a bean and hands to everyone who asks for that bean. When a caller calls a method, the proxy first runs the extra code, the [advice](card:spring-aop), and then calls the same method on your real object. Self-invocation is the case where your object calls one of its own methods through `this`: that call never passes the proxy.

## Why it exists

Spring wants to add behaviour like transactions without changing your class or making you call Spring code. A proxy does this from the outside: your `PaymentService` stays plain Java, and the proxy in front of it opens and closes the transaction. The price is the self-invocation rule. Many "my @Transactional or @Async does nothing" bugs come from not knowing it.

## How it works

<Mermaid
  alt="The controller calls payAll on the PaymentService proxy. The proxy runs the advice and then calls payAll on the real PaymentService. Inside, the real object calls this.pay, which goes straight to itself, so the proxy and its advice are skipped."
  chart={`flowchart LR
  C[PaymentController] -- "payAll()" --> P["Proxy: runs the advice"]
  P -- "then calls payAll()" --> T[Real PaymentService]
  T -- "this.pay(): proxy skipped" --> T`}
/>

1. At startup Spring sees that `PaymentService` needs advice, such as a `@Transactional` method or a matching aspect.
2. It creates a proxy for that bean and registers the proxy in the container instead of the plain object.
3. `PaymentController` gets the proxy injected, so each of its calls lands on the proxy first.
4. The proxy runs the advice and then calls the real `PaymentService`.
5. Inside that method, a call such as `pay()` means `this.pay()`. It goes straight to the real object, so no advice runs.

So the key idea is: advice runs only on calls that **arrive from outside** the bean, through the proxy.

## Example

The `LoggingAspect` from [Spring AOP](card:spring-aop) logs every `PaymentService` method. Here `payAll` calls `pay` from inside:

```java
@Service
public class PaymentService {

    public String pay(long amount) {
        return "PAID " + amount;
    }

    public void payAll(List<Long> amounts) {
        amounts.forEach(amount -> pay(amount));   // this.pay(): skips the proxy
    }
}
```

The caller prints the injected object's class and then calls `payAll(List.of(100L, 200L))`:

```text output
PaymentService$$SpringCGLIB$$0
-> payAll
<- payAll returned null
```

What to notice:

- The injected object is not `PaymentService` but a generated subclass of it: the CGLIB proxy.
- Only `payAll` is logged. The two `pay` calls ran, but through `this`, so the aspect never saw them.
- If `pay` were `@Transactional`, the same rule applies: no transaction would start for those two calls.
- The cleanest fix is to move `pay` into another bean, such as a `PaymentProcessor`, and call it through that bean's proxy.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Proxy type | CGLIB subclass (`spring.aop.proxy-target-class=true`); set `false` for JDK proxies | Spring Boot 4.1 |
| Proxy type without Boot | JDK proxy if the bean implements an interface, otherwise CGLIB | Spring Framework 7.0 |

- **Final class:** a CGLIB proxy cannot subclass it, so startup fails with "Could not generate CGLIB subclass".
- **Final or private method:** it cannot be overridden, so the proxy cannot advise it. There is no error; the annotation is ignored.
- **Fixes for self-invocation, best first:** move the method to another bean; inject the bean into itself with `@Lazy` and call through that reference (Spring Boot rejects a plain self-reference as a cycle); or use AspectJ weaving, which has no proxy. `AopContext.currentProxy()` also works, but the docs strongly discourage it.
- **Startup code:** do not rely on proxied behaviour inside `@PostConstruct`; the proxy may not be ready, and the call goes through `this` anyway.

## Not to be confused with

A JDK dynamic proxy implements the same interfaces as your bean, so it can only stand in for that interface. A CGLIB proxy is a generated subclass of your class, so it works without an interface but cannot touch final classes or methods. Rule: JDK = "is the interface"; CGLIB = "is a subclass".

## Interview Qs

### Why does @Transactional not work when I call the method from the same class?

Because the call goes through `this`, the real object, not through the proxy that starts transactions. The annotation is only read by the proxy. Move the method into another bean, inject the bean into itself with `@Lazy`, or switch to AspectJ weaving, which puts the advice inside the class itself.

### If @Transactional is only an annotation, who starts the transaction?

A proxy that Spring puts in front of the bean. When a caller calls the method, the proxy reads the annotation, starts a transaction, calls your method, and then commits, or rolls back if a runtime exception escapes. Your method itself contains no transaction code.

### JDK dynamic proxy or CGLIB?

A JDK proxy implements the bean's interfaces, so only interface methods are advised and you must inject the interface type. CGLIB generates a subclass, so no interface is needed and you can inject the class, but final classes and final or private methods cannot be advised. Spring Boot uses CGLIB by default.
