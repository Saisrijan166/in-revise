## Why it exists

Many users change the same data at once. ACID says what a transaction must guarantee; isolation levels let you choose how strictly transactions are kept apart, because full separation is slow.

## How it works

| Isolation level | Dirty read | Non-repeatable read | Phantom read |
| --- | --- | --- | --- |
| `READ_UNCOMMITTED` | Possible | Possible | Possible |
| `READ_COMMITTED` | Stopped | Possible | Possible |
| `REPEATABLE_READ` | Stopped | Stopped | Possible |
| `SERIALIZABLE` | Stopped | Stopped | Stopped |

- **A**tomicity: all steps or none. **C**onsistency: constraints hold at commit. **I**solation: others do not see uncommitted work. **D**urability: a commit survives a crash.
- Databases may give more than the table: PostgreSQL's REPEATABLE READ also stops phantoms.

## Example

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public Report monthlyReport(YearMonth month) {
    // reading the same row twice gives the same values
    return reports.build(month);
}
```

## Interview Qs

### What do dirty, non-repeatable and phantom reads mean?

Dirty: you read another transaction's uncommitted change. Non-repeatable: you read a row twice and it changed in between. Phantom: the same WHERE query returns new rows the second time.

### Which isolation level does Spring use?

Isolation.DEFAULT, which means the database's own level: READ COMMITTED in PostgreSQL, REPEATABLE READ in MySQL InnoDB.

### Why not always use SERIALIZABLE?

It is the safest but the slowest: transactions wait more, or fail and must be retried, so throughput drops. Use it only where correctness needs it.
