## What it is

A [transaction](card:transactional) makes four promises, called ACID. **Atomicity:** all its steps happen, or none do. **Consistency:** the data's rules, such as constraints, hold when it commits. **Isolation:** transactions running at the same time do not disturb each other beyond an agreed limit. **Durability:** once committed, the data survives a crash. The isolation level is that agreed limit: how much one transaction may see of the work of others.

## Why it exists

Many requests read and write payments at the same moment. If the database ran them strictly one after another, nobody would ever see half-done work, but everyone would wait. If it kept them apart too little, a report could include a payment that is later rolled back. Isolation levels let you choose the trade-off per method: more safety and more waiting, or more speed and some read problems.

## How it works

| Read problem | What the transaction sees | First level that stops it |
| --- | --- | --- |
| Dirty read | A change another transaction has not committed yet | `READ_COMMITTED` |
| Non-repeatable read | The same row read twice gives different values | `REPEATABLE_READ` |
| Phantom read | The same WHERE query returns new rows the second time | `SERIALIZABLE` |

`READ_UNCOMMITTED` stops none of them. Each level up stops one more. Here is a non-repeatable read, step by step:

1. Transaction A, a monthly report, reads payment 42: amount 500.
2. Transaction B changes payment 42 to 700, but has not committed yet. Under `READ_COMMITTED`, A still sees 500, because B's change is uncommitted. Seeing 700 now would be a dirty read.
3. B commits.
4. A reads payment 42 again. Under `READ_COMMITTED` it now sees 700, a non-repeatable read. Under `REPEATABLE_READ` it still sees 500.

So each level is a promise about which of these surprises cannot happen inside your transaction.

## Example

A settlement report runs two queries and needs them to agree with each other:

```java
@Transactional(isolation = Isolation.REPEATABLE_READ, readOnly = true)
public SettlementReport settle(LocalDate day) {
    BigDecimal total = payments.sumCompletedOn(day);      // query 1
    List<Payment> rows = payments.findCompletedOn(day);   // query 2
    return new SettlementReport(total, rows);             // total matches rows
}
```

What to notice:

- With PostgreSQL's default, `READ COMMITTED`, each query sees what was committed before *that query* started. A payment completed between query 1 and query 2 would appear in `rows` but not in `total`.
- `REPEATABLE_READ` makes both queries read the same snapshot, so the two always agree.
- The isolation level is applied only when this method starts the transaction. If it [joins](card:transaction-propagation) a caller's transaction, the caller's level is used.

## Rules and defaults

- **Spring's default is `Isolation.DEFAULT`:** Spring sets nothing, and the database's own level applies.
- **PostgreSQL 18:** `READ COMMITTED` by default. `READ UNCOMMITTED` behaves like `READ COMMITTED`, and its `REPEATABLE READ` also stops phantom reads.
- **MySQL 9.7 InnoDB:** `REPEATABLE READ` by default. Plain reads in one transaction come from the snapshot taken at the first read.
- **Retries:** in PostgreSQL, `REPEATABLE READ` and `SERIALIZABLE` transactions can fail with a serialization failure. The app must be ready to retry the whole transaction.
- **Lost updates:** these levels are about what you *read*. Two transactions that both read and then overwrite the same row need [locking](card:locking), which you will see next.

## Interview Qs

### What do dirty, non-repeatable and phantom reads mean?

A dirty read is seeing another transaction's change before it commits. A non-repeatable read is reading the same row twice and getting different values, because someone committed a change in between. A phantom read is running the same WHERE query twice and getting new rows the second time.

### Which isolation level does Spring use?

Isolation.DEFAULT, which means Spring sets nothing and the database's own level applies: READ COMMITTED in PostgreSQL, REPEATABLE READ in MySQL InnoDB. So the same code can see different results on the two databases.

### Why not always use SERIALIZABLE?

It is the safest level but the slowest. Transactions wait for each other more, or fail with serialization errors and must be retried, so throughput drops. Use it only where correctness really needs it, and keep those transactions short.
