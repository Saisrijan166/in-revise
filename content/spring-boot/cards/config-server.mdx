## What it is

Config Server is a small Spring Boot app, from Spring Cloud Config, that serves configuration to all your other services over HTTP. It reads the files from a Git repository, so config is versioned like code. Each service is a **config client**: at startup it asks the server for its own settings, found by its `spring.application.name`, its active [profile](card:profiles) and a **label**, which is a Git branch, tag or commit.

## Why it exists

You already know [externalized configuration](card:externalized-configuration): properties outside the code. With ten services in three environments, those properties live in thirty places. Changing the fraud limit means editing files on many servers and restarting, with no record of who changed what. Config Server keeps them in one Git repository: a change is a commit, you can see its history and roll it back, and no service needs a rebuild.

## How it works

1. The payment service starts with the `prod` profile and finds `spring.config.import=configserver:...`.
2. It calls the server at `/{application}/{profile}/{label}`, here `/payment-service/prod/main`.
3. The server reads `payment-service-prod.yml` from that branch, plus the `application*` files that are shared by all clients, and returns their properties.
4. The client adds them to its environment before the beans are created, so beans see them like local properties.
5. Later, after a commit, a refresh event makes the client fetch again and update the beans that support it.

## Example

The payment service's own `application.properties` needs only these lines:

```properties
spring.application.name=payment-service
spring.config.import=optional:configserver:http://config:8888
management.endpoints.web.exposure.include=health,refresh
```

What to notice:

- `spring.application.name` decides which files the server returns, so it must match the file names in Git.
- `optional:` lets the service start on local config when the server is down. Remove it to fail fast instead.
- `refresh` is an [Actuator](card:actuator) endpoint and is not exposed by default, so it must be listed before `POST /actuator/refresh` works.

## Rules and defaults

- **Client default:** with no URL in the import, the client looks for the server at `http://localhost:8888`.
- **Server port:** the server uses 8080 like any Boot app unless you set `server.port`; 8888 is the usual choice.
- **Label:** the Git backend uses `main` as the default label.
- **Refresh scope:** a `@RefreshScope` bean is a lazy proxy. A refresh throws away its target, and the next call builds a new one with the new values.
- **Rebinding:** a refresh also rebinds `@ConfigurationProperties` beans, but not constructor-bound ones, such as records.
- **Bus:** Spring Cloud Bus sends the refresh to every instance over a broker, such as RabbitMQ or Kafka, through `/actuator/busrefresh`.

## Common mistakes

- **Reading a value with `@Value` in a normal singleton and expecting it to change.** That bean was built once; mark it `@RefreshScope` or use `@ConfigurationProperties`.
- **Storing passwords in plain text in the Git repository.** Anyone with repository access can read them. Store them as `{cipher}` values, which the server decrypts before sending, or use a secret store such as Vault.

## Interview Qs

### Why use a Config Server?

All services' config lives in one place, under version control, per environment. You change a value with a commit, can see who changed it and roll it back, and need no rebuild. Services fetch their own part by name and profile.

### How does @RefreshScope work?

The bean is a lazy proxy that caches its target object. A refresh event clears that cache. The next method call through the proxy creates a fresh target, built with the new property values.

### What happens if the Config Server is down?

At startup, with `optional:` the app starts on its local config; without it, the app fails to start, which is useful when the remote config is essential. Already running apps keep the values they loaded.
