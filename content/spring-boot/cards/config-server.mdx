## Why it exists

Config packed inside each jar is hard to change and keep in step across many services and environments. Config Server keeps it in one versioned Git repo and serves it to all.

## How it works

<Mermaid
  alt="Config Server flow. The Config Server reads orders-prod.yml from a Git repository. Two orders instances ask it for /orders/prod/main at startup. Later Spring Cloud Bus sends a refresh to both instances."
  chart={`flowchart LR
  G[(Git repo)] -- "orders-prod.yml" --> CS[Config Server]
  CS -- "/orders/prod/main" --> A[orders 1]
  CS -- "/orders/prod/main" --> B[orders 2]
  BUS[[Spring Cloud Bus]] -. "busrefresh" .-> A
  BUS -. "busrefresh" .-> B`}
/>

- Requests are `/{application}/{profile}/{label}`: app name, active profile, Git branch.
- A refresh rebuilds `@RefreshScope` beans and rebinds `@ConfigurationProperties` beans, but not records.

## Example

```properties
spring.application.name=orders
spring.config.import=optional:configserver:http://config:8888
management.endpoints.web.exposure.include=refresh
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Client looks for the server at | `http://localhost:8888` | Spring Cloud Config 5.0 |
| Server port | 8080; 8888 is the usual choice | Spring Cloud Config 5.0 |
| Git label | `main` | Spring Cloud Config 5.0 |

## Interview Qs

### Why use a Config Server?

All services' config lives in one place under version control, per environment. You change a value with a commit, can see who changed it and roll back, and need no rebuild.

### How does @RefreshScope work?

The bean is a lazy proxy that caches its target. A refresh clears that cache, so the next method call builds a new bean with the new values.

### What happens if the Config Server is down?

At startup, with `optional:` the app starts on its local config; without it, the app fails to start. That fail-fast is useful when the remote config is essential.
