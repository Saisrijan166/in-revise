## Why it exists

With many services and environments, config packed inside each jar is hard to change, audit and keep in step. Config Server keeps it in one versioned Git repository and serves it to every service.

## How it works

<Mermaid
  alt="Config Server flow. The Config Server reads orders-prod.yml from a Git repository. Two orders instances request /orders/prod/main from the Config Server at startup. Later, Spring Cloud Bus sends a refresh to both instances."
  chart={`flowchart LR
  G[(Git repo)] -- "orders-prod.yml" --> CS[Config Server]
  CS -- "GET /orders/prod/main" --> A[orders instance 1]
  CS -- "GET /orders/prod/main" --> B[orders instance 2]
  BUS[[Spring Cloud Bus]] -. "busrefresh" .-> A
  BUS -. "busrefresh" .-> B`}
/>

- Requests are `/{application}/{profile}[/{label}]`: app name, active profile, Git label. An `application.yml` in the repo is shared by all apps.
- Clients load config at startup. For live changes, refresh one instance with [/actuator/refresh](card:actuator-refresh), or all of them with [Spring Cloud Bus](card:spring-cloud-bus).
- A refresh rebuilds `@RefreshScope` beans and rebinds `@ConfigurationProperties` beans, except records.

## Example

The server, whose main class has `@EnableConfigServer`:

```properties
server.port=8888
spring.cloud.config.server.git.uri=https://github.com/acme/config-repo
spring.cloud.config.server.git.default-label=main
```

Each client, with `spring-cloud-starter-config`:

```properties
spring.application.name=orders
spring.config.import=optional:configserver:http://config:8888
management.endpoints.web.exposure.include=refresh
```

A bean that gets new values after a refresh:

```java
@RefreshScope
@Component
public class Pricing {
    private final BigDecimal discount;

    public Pricing(@Value("${pricing.discount:0}") BigDecimal discount) {
        this.discount = discount;
    }
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Server port | 8080 like any Boot app; 8888 is the convention | Spring Cloud Config 5.0 |
| Client looks for the server at | `http://localhost:8888` | Spring Cloud Config 5.0 |
| Git label | `main`, then `master` | Spring Cloud Config 5.0 |
| Git fetch | On every request (`refresh-rate` 0) | Spring Cloud Config 5.0 |
| Actuator endpoints over HTTP | Only `health`: expose `refresh` yourself | Spring Boot 4.1 |

## Interview Qs

### Why use a Config Server?

It gives every service's config one home under version control, per environment. You change a value with a commit, can see who changed it and roll back, and need no rebuild. Secrets can be stored encrypted as `{cipher}` values.

### How does @RefreshScope work?

The bean is a lazy proxy. A refresh (POST /actuator/refresh) clears its cached instance, so the next method call builds a new one with the new values. @ConfigurationProperties beans are rebound even without it, except records.

### How do you refresh config on 20 instances at once?

Add Spring Cloud Bus over RabbitMQ or Kafka and POST /actuator/busrefresh to one instance; the event reaches all of them. With spring-cloud-config-monitor, a Git webhook to /monitor starts this on every push.

### What happens if the Config Server is down?

At startup, with optional:configserver: the app starts on its local config; without optional:, it fails to start. A running server that loses Git keeps serving its local copy of the repository.
