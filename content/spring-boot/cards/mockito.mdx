## Why it exists

A service test should not need a real database or remote API. Mockito replaces those dependencies with fakes you control, so the test checks only your logic.

## How it works

<Steps label="A Mockito unit test">
  <Step title="Create">`@Mock` makes fakes; `@InjectMocks` builds the class with them.</Step>
  <Step title="Stub">`when(...).thenReturn(...)` sets what a call returns.</Step>
  <Step title="Act">Call the method under test.</Step>
  <Step title="Check">Assert the result, or `verify(...)` that a call happened.</Step>
</Steps>

- A spy wraps a real object: real methods run unless stubbed.
- Need the mock inside Spring? See [@Mock vs @MockitoBean](compare:mock-vs-mockitobean).

## Example

```java
@ExtendWith(MockitoExtension.class)
class PaymentServiceTests {
    @Mock PaymentRepository repo;
    @InjectMocks PaymentService service;

    @Test
    void savesPayment() {
        when(repo.save(any())).thenAnswer(i -> i.getArgument(0));
        service.pay(100);
        verify(repo).save(any(Payment.class));
    }
}
```

## Interview Qs

### Mock vs stub?

A stub gives canned answers, so you check the result. A mock is used to check the calls themselves, such as "was save() called once?". In Mockito one object can do both.

### If Mockito's @Mock exists, why do we need @MockitoBean?

`@Mock` lives only in the test. When Spring creates the object under test, the mock must be a bean in the context. `@MockitoBean` replaces the real bean there.

### What replaced @MockBean?

Spring Framework's `@MockitoBean` and `@MockitoSpyBean` (since 6.2). Boot's `@MockBean` was deprecated in 3.4 and removed in 4.0.
