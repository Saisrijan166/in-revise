## Why it exists

The same jar must run on a laptop, in test and in production, with different URLs, ports and secrets. Keeping those values outside the code means no rebuild per environment and no passwords in Git, as the Twelve-Factor App asks.

## How it works

| Rank (1 wins) | Source | Example |
| --- | --- | --- |
| 1 | [Command-line arguments](card:command-line-args) | `--server.port=9000` |
| 2 | [SPRING_APPLICATION_JSON](card:spring-application-json) | `{"server":{"port":9000}}` |
| 3 | Java system properties | `-Dserver.port=9000` |
| 4 | [OS environment variables](card:os-environment-variables) | `SERVER_PORT=9000` |
| 5 | [Config files](card:config-data-files) | `application.properties`, `application-prod.yaml` |
| 6 | [`@PropertySource`](card:property-source-annotation) | `@PropertySource("classpath:extra.properties")` |
| 7 | Default properties | `SpringApplication.setDefaultProperties(...)` |

- Among config files, highest first: profile-specific outside the jar, then plain outside, then profile-specific inside, then plain inside.
- The full list has 15 sources. Test annotations such as `@TestPropertySource` and DevTools global settings rank above even the command line; JNDI and servlet init parameters sit between ranks 2 and 3.
- [`spring.config.import`](card:config-import) pulls in more files, a [config tree](card:config-tree) of Kubernetes secrets, or a [Config Server](card:config-server).

## Example

```properties
# src/main/resources/application.properties (inside the jar)
server.port=8080
spring.config.import=optional:file:./secrets.properties
```

```bash
java -jar app.jar                      # port 8080
SERVER_PORT=9090 java -jar app.jar     # env var wins: 9090
java -jar app.jar --server.port=9000   # command line wins: 9000
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Config file name | `application` (`spring.config.name`) | Spring Boot 4.1 |
| Folders searched, later wins | `classpath:/`, `classpath:/config/`, `./`, `./config/`, `./config/*/` | Spring Boot 4.1 |
| `.properties` and `.yaml` in one folder | `.properties` wins | Spring Boot 4.1 |
| Missing location or import | start-up fails, unless prefixed `optional:` | Spring Boot 4.1 |

## Interview Qs

### What are the sources of external configuration in Spring Boot?

Properties and YAML files (inside and outside the jar, plus profile-specific ones), environment variables, Java system properties, command-line arguments and `SPRING_APPLICATION_JSON`. Imports add config trees or a Config Server. All of them end up in one `Environment`.

### Which wins: an environment variable or application.properties?

The environment variable. From the top: command-line arguments, then Java system properties, then environment variables, then config files. Among files, outside the jar beats inside, and profile-specific beats plain.

### How do you check which value was used?

Expose the Actuator `env` endpoint: `/actuator/env` lists the property sources in order of precedence, often with each value's origin. Values are masked by default. Or log `org.springframework.boot.context.config` at `trace` to see which files load.

### Properties or YAML: which is better?

Neither: both load the same keys into the same `Environment`. YAML is shorter for nested and list-heavy settings; properties is flat, and the only one `@PropertySource` can load. If both sit in one folder, `.properties` wins, so pick one format per app.
