## What it is

Externalized configuration means keeping settings, such as the database URL, the port or an API key, outside your Java code. Boot reads them from many **property sources**: config files, environment variables, Java system properties and command-line arguments. It merges them all into one object, the `Environment`, while the app [starts](card:application-startup). When two sources set the same key, the higher-ranked source wins.

## Why it exists

The payment service must run on a laptop, in test and in production, each with its own database URL and secrets. Hardcoding `String password = "secret123"` means a rebuild per environment and a password in Git. With externalized configuration you build one jar, keep safe defaults in `application.properties`, and override only what differs at deploy time. Passwords come from the environment and never enter the code or the repository.

## How it works

| Rank (1 wins) | Source | Example |
| --- | --- | --- |
| 1 | [Command-line arguments](card:command-line-args) | `--server.port=9000` |
| 2 | [Java system properties](card:java-system-properties) | `-Dserver.port=9000` |
| 3 | [OS environment variables](card:os-environment-variables) | `SERVER_PORT=9000` |
| 4 | [Config files](card:config-data-files) | `application.properties` or `application.yml` |

1. At startup, Boot loads `application.properties` (or `.yml`) from inside the jar, then any profile-specific file, then the same files from outside the jar.
2. It adds environment variables, Java system properties and command-line arguments on top.
3. For each key, the source with the highest rank provides the value.
4. `@Value`, `@ConfigurationProperties` and your beans read that merged value, never a single file.

This table is the short version; the full list has 15 sources, and test properties even beat the command line.

## Example

The payment service ships with `server.port=8080` and `app.fraud-check.url=http://localhost:9000` in its `application.properties`. The same jar, started three ways:

```bash
java -jar payment.jar                          # port 8080, from the file
SERVER_PORT=9090 java -jar payment.jar         # port 9090: env var beats the file
java -jar payment.jar --server.port=9000       # port 9000: argument beats both
APP_FRAUDCHECK_URL=https://fraud.example.com java -jar payment.jar   # fraud URL
```

What to notice:

- No rebuild happened between the runs; only the environment changed.
- `APP_FRAUDCHECK_URL` sets `app.fraud-check.url`: each dot became `_`, the dash was dropped, and everything is upper case. Most operating systems do not allow dots in variable names, which is why this form exists.
- Each override touches only its own key; every other value still comes from the file.

## Rules and defaults

- **File name and folders:** Boot looks for `application.*` (change with `spring.config.name`) in `classpath:/`, `classpath:/config/`, `./`, `./config/` and `./config/*/`; later locations win.
- **File order:** inside the jar, then a profile file inside the jar, then outside the jar, then a profile file outside the jar. The last one wins.
- **Placeholders:** `spring.datasource.password=${DB_PASSWORD}` reads the env var; `${DB_PASSWORD:dev}` falls back to `dev` when it is missing.
- **Too late for some keys:** `@PropertySource` files are added during the context refresh, too late for `logging.*` and `spring.main.*`.
- **Mounted secrets:** `spring.config.import=optional:configtree:/etc/config/` reads a folder where each file name is a key and its content the value, as Kubernetes mounts secrets.

## Not to be confused with

The **Environment** is the merged result of all sources. A **config file** such as `application.properties` is only one of those sources, and the lowest common one. Rule: the file gives defaults; the Environment gives the value your code actually sees. The two file formats are compared in [properties vs YAML](compare:properties-vs-yaml).

## Interview Qs

### Where can Spring Boot read configuration from?

From config files inside and outside the jar (plain and profile-specific), environment variables, Java system properties and command-line arguments, among others. All of them are merged into one `Environment`, and for each key a higher-ranked source overrides a lower one.

### An environment variable and application.properties set the same key. Which wins?

The environment variable. From the top, the order is command-line arguments, Java system properties, environment variables, then config files. Among files, a file outside the jar beats one inside, and a profile-specific file beats the plain one.

### How do you keep secrets out of the jar?

Reference them with a placeholder such as `${DB_PASSWORD}` and supply the value at deploy time, as an environment variable or a mounted file read with `configtree:`. Spring Boot has no built-in encryption, so the secret must never be committed; a tool such as Spring Cloud Vault can store it.
