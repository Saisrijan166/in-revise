## What it is

`@Async` and `@Scheduled` are two annotations that run your method on a thread other than the caller's. `@Async` on a method means "when someone calls this, run it in the background and let the caller continue". `@Scheduled` means "nobody calls this; Spring runs it on a timer", such as every 10 minutes or at 09:00 on weekdays. Both hand the work to a thread pool, a set of reusable threads that Spring creates and manages.

## Why it exists

When a payment completes, the customer should not wait while a receipt e-mail is sent. And stale `PENDING` payments must be expired every few minutes, with no user request to trigger it. In plain Java you would create threads by hand, size the pool yourself, and write a `while (true) { work(); sleep(); }` loop. That code is easy to get wrong and hard to stop cleanly at shutdown. With one annotation, Spring runs the method on a configured pool and shuts the pool down with the app.

1. `@EnableAsync` and `@EnableScheduling` tell Spring to look for these annotations on beans.
2. For a bean with an `@Async` method, Spring creates a [proxy](card:aop-proxies). When a caller calls that method, the proxy puts the call on the task executor's queue and returns at once.
3. A free thread from the executor's pool takes the call and runs your method.
4. For every `@Scheduled` method, Spring registers a task with the scheduler at startup. The scheduler's thread runs the method each time its timer fires.

So `@Async` reacts to a call, while `@Scheduled` reacts to the clock, and only `@Async` depends on the call passing through the proxy.

## Example

The payment service sends receipts in the background and expires stale payments every 10 minutes. The app has `@EnableAsync` and `@EnableScheduling`, and `PaymentService` prints its own thread before it calls `sendReceipt(42)`:

```java
@Service
public class NotificationService {
    @Async
    public void sendReceipt(long paymentId) {
        System.out.println("receipt " + paymentId + " on " + Thread.currentThread().getName());
    }
}

@Component
public class PaymentCleanupJob {
    @Scheduled(fixedDelay = 10, timeUnit = TimeUnit.MINUTES)   // 10 min after each run ends
    public void expireStalePayments() {
        System.out.println("cleanup on " + Thread.currentThread().getName());
    }
}
```

```text output
cleanup on scheduling-1
pay() on main
receipt 42 on task-1
```

What to notice:

- The first cleanup runs right after startup, on Boot's single scheduler thread, `scheduling-1`.
- The receipt runs on `task-1`, a thread of Boot's task executor, while the caller ran on `main`. That is the proof that `@Async` worked.
- Remove `@EnableAsync` and the receipt line says `main`: the method still runs, but the caller waits for it.
- `fixedDelay` counts 10 minutes from the end of each run, so two cleanups never overlap. See [fixedRate vs fixedDelay vs cron](compare:fixed-rate-vs-fixed-delay).

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| `@Async` executor | `ThreadPoolTaskExecutor`: 8 core threads, unbounded queue, thread names `task-` | Spring Boot 4.1 |
| Scheduler | `ThreadPoolTaskScheduler` with 1 thread, thread names `scheduling-` | Spring Boot 4.1 |
| With `spring.threads.virtual.enabled=true` | `SimpleAsyncTaskExecutor` and `SimpleAsyncTaskScheduler` on virtual threads | Spring Boot 4.1, Java 21+ |

- **Tuning:** set `spring.task.execution.pool.queue-capacity` and `spring.task.execution.pool.max-size` to bound the queue and let the pool grow, and `spring.task.scheduling.pool.size` for more scheduler threads.
- **Your own executor:** if you define an `Executor` bean, Boot's executor backs off and `@Async` uses yours. `@Async("reportExecutor")` picks an executor by bean name.
- **Return types:** an `@Async` method returns `void`, `Future` or `CompletableFuture`. Exceptions from a `void` method go to an `AsyncUncaughtExceptionHandler`, which only logs them by default.
- **`@Scheduled` methods:** must return `void` and take no arguments; inject what they need instead.
- **Not allowed:** `@Async` on a lifecycle callback such as `@PostConstruct` does not run it in the background.

## Not to be confused with

`fixedRate` counts the time between the **starts** of two runs, `fixedDelay` counts from the **end** of one run to the start of the next, and `cron` fires at **clock times**. Rule: rate = steady beat; delay = rest after each run; cron = calendar.

## Common mistakes

- **"@Scheduled gives me a distributed job."** Each instance schedules its own copy. Use a shared lock such as ShedLock, or a single dedicated instance, for once-only jobs.
- **"The default @Async pool protects me from overload."** Its queue is unbounded, so under load tasks pile up in memory while the pool stays at 8 threads. Set a queue capacity.

## Interview Qs

### Why does my @Async method run on the caller's thread?

The call did not pass through the proxy. Common causes: the method is called from the same class through `this`, `@EnableAsync` is missing, the object was created with `new` instead of being injected, or the method is private or final, so the proxy cannot override it.

### If Java already has threads, why use @Async or @Scheduled?

Java gives you the raw threads and executors. These annotations connect them to Spring: one annotation instead of hand-written pools and `sleep()` loops, pools sized through properties, executors chosen by bean name, and clean shutdown with the application context.

### A @Scheduled job runs twice in production. Why, and how do you fix it?

Production runs two instances, and each has its own scheduler, so each runs the job. Add a shared lock, such as ShedLock with a database table, so only one instance runs it at a time. Also check that the job's class is not registered as a bean twice.
