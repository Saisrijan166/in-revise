## Why it exists

Some work should not make the caller wait, like sending an email; some must run on a timer, like a nightly report.

## How it works

<Mermaid
  alt="The caller calls an @Async method through the proxy, which returns at once and hands the work to the task executor. The scheduler thread triggers @Scheduled methods."
  chart={`flowchart LR
  C[Caller] -- calls --> P[Spring proxy]
  P -- "returns at once" --> C
  P -- "hands off" --> E[Task executor]
  E --> M["@Async method on a pool thread"]
  S[Scheduler thread] -- "fixedRate, fixedDelay, cron" --> J["@Scheduled method"]`}
/>

- `@Async` returns `void` or a `CompletableFuture`; a `void` method's exception never reaches the caller.
- A `@Scheduled` method returns `void` and takes no arguments. See [fixedRate vs fixedDelay vs cron](compare:fixed-rate-vs-fixed-delay).
- The default queue is unbounded, so the pool never grows past 8; set `queue-capacity`.

## Example

```java
@Service
class ReportService {
    @Async
    public CompletableFuture<Report> build(long id) {
        return CompletableFuture.completedFuture(reports.load(id));
    }

    @Scheduled(cron = "0 0 9 * * MON-FRI", zone = "Asia/Kolkata")   // 09:00 on weekdays
    public void sendDailyReport() { mailer.sendDaily(); }
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| `@Async` executor | `ThreadPoolTaskExecutor`: 8 core threads, unbounded queue | Spring Boot 4.1 |
| Scheduler | `ThreadPoolTaskScheduler` with 1 thread | Spring Boot 4.1 |
| `spring.threads.virtual.enabled=true` | `SimpleAsyncTaskExecutor` and `SimpleAsyncTaskScheduler` on virtual threads | Spring Boot 4.1, Java 21+ |

## Interview Qs

### Why does my @Async method run on the caller's thread?

The call skips the proxy: it comes from the same class, `@EnableAsync` is missing, or the object was made with `new`.

### If Java already has threads, why use @Async or @Scheduled?

They hand work to Spring-managed, configurable thread pools with one annotation, instead of hand-written threads and `while (true) { sleep(); }` loops.

### A @Scheduled job runs twice in production. Why?

Each instance has its own scheduler, so two pods run it twice. Add a shared lock such as ShedLock.
