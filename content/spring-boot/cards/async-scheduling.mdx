## Why it exists

Some work should not make the caller wait, such as sending an email, and some must run on a timer, such as a nightly report. Spring runs both on managed thread pools instead of threads you create by hand.

## How it works

<Mermaid
  alt="Async and scheduled flow. A caller calls an @Async method through the Spring proxy. The proxy hands the task to applicationTaskExecutor and returns a CompletableFuture to the caller at once; the method then runs on a pool thread. Separately, the scheduler thread triggers @Scheduled methods by fixedRate, fixedDelay or cron."
  chart={`flowchart LR
  C[Caller] -- "calls" --> P[Spring proxy]
  P -- "returns CompletableFuture at once" --> C
  P -- "hands off" --> E[applicationTaskExecutor]
  E --> M["@Async method runs on a pool thread"]
  S[Scheduler thread] -- "fixedRate, fixedDelay or cron" --> J["@Scheduled method"]`}
/>

- `@Async("mailExecutor")` picks an executor bean by name; an `AsyncConfigurer` sets the default executor and the exception handler.
- A `@Scheduled` method takes no arguments. On several instances, each one runs the job, so add a shared lock such as ShedLock.
- Self-invocation skips the proxy: see [AOP and Spring proxies](card:aop-proxies).

## Example

```java
@Configuration
@EnableAsync
@EnableScheduling
class TaskConfig {}

@Service
class ReportService {
    @Async   // runs on applicationTaskExecutor; the caller gets the future at once
    public CompletableFuture<Report> build(long id) {
        return CompletableFuture.completedFuture(reports.load(id));
    }
    @Scheduled(cron = "0 0 9 * * MON-FRI", zone = "Asia/Kolkata")   // 09:00 on weekdays
    public void sendDailyReport() { mailer.sendDaily(); }
}
```

```properties
spring.task.execution.pool.core-size=16
spring.task.execution.pool.queue-capacity=500
spring.task.execution.pool.max-size=32
spring.task.scheduling.pool.size=4
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Executor for `@Async` | `ThreadPoolTaskExecutor`, bean `applicationTaskExecutor` | Spring Boot 4.1 |
| Executor pool | 8 core threads, unbounded queue, so `max-size` never applies | Spring Boot 4.1 |
| Scheduler pool | 1 thread, names start with `scheduling-` | Spring Boot 4.1 |
| With `spring.threads.virtual.enabled=true` | `SimpleAsyncTaskExecutor` and `SimpleAsyncTaskScheduler` | Spring Boot 4.1, Java 21+ |
| `@Scheduled` time unit | Milliseconds | Spring Framework 7.0 |

## Interview Qs

### Why does my @Async method run synchronously?

The call does not go through the proxy: it comes from the same class (`this.build()`), `@EnableAsync` is missing, or the object was created with `new`, not by Spring. Move the method to another bean and inject that bean.

### fixedRate vs fixedDelay vs cron?

`fixedRate` counts the period between start times; `fixedDelay` waits the delay after each run ends; `cron` runs at clock times, like `0 0 9 * * MON-FRI`. Values are milliseconds unless `timeUnit` says otherwise.

### How do you handle exceptions in @Async methods?

With `CompletableFuture`, the exception completes the future, so the caller sees it on `join()` or `get()`. With `void`, it cannot reach the caller and is only logged; register an `AsyncUncaughtExceptionHandler` through `AsyncConfigurer`.

### A @Scheduled job runs twice in production. Why?

Every running instance has its own scheduler, so two pods run the job twice. Add a shared lock such as ShedLock, so the job runs at most once at a time across instances.
