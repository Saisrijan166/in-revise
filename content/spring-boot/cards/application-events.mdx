## What it is

An application event is an object that one bean publishes to say "this happened", such as `PaymentCompleted`. Other beans that want to react declare a listener method, and Spring calls each matching listener. The publisher does not know who listens. Publishing goes through `ApplicationEventPublisher`, an object the [container](card:ioc-container) can inject into any bean.

## Why it exists

When a payment completes, a receipt must be e-mailed, loyalty points added and an audit row written. If `PaymentService` calls `NotificationService`, `LoyaltyService` and `AuditService` directly, it depends on all three, and every new reaction means editing the payment code. Such direct calls, made in both directions, are also how [circular dependencies](card:circular-dependencies) start. With an event, `PaymentService` only says "payment completed", and each reaction lives in its own listener.

## How it works

1. A bean calls `publishEvent()` with any object as the event.
2. Spring looks for listener methods, marked `@EventListener`, whose parameter type matches that object.
3. It calls them one by one, on the same thread. If the publisher runs inside a transaction (a group of database changes saved together, which you will meet in [@Transactional](card:transactional)), the listeners run inside it too.
4. `publishEvent()` returns, and the publisher continues.

So an event is a decoupled method call, not a background job. To change when a listener runs, you change the listener, not the publisher.

## Example

The receipt must go out only if the payment is really saved. The event is a record, `record PaymentCompleted(long paymentId, long amount) {}`, and a `@TransactionalEventListener` waits for the commit:

```java
@Service
public class PaymentService {
    private final ApplicationEventPublisher events;
    public PaymentService(ApplicationEventPublisher events) { this.events = events; }
    @Transactional
    public void complete(Payment payment) {
        payment.setStatus("PAID");                       // saved when the transaction commits
        events.publishEvent(new PaymentCompleted(payment.getId(), payment.getAmount()));
    }
}
@Component
class ReceiptListener {
    @TransactionalEventListener   // AFTER_COMMIT by default
    void onPaid(PaymentCompleted event) { /* send the receipt e-mail */ }
}
```

What to notice:

- `PaymentCompleted` is a plain record; it does not need to extend any Spring class.
- `PaymentService` knows nothing about `ReceiptListener`. A new loyalty listener needs no change here.
- With a plain `@EventListener`, the e-mail would go out before the commit, even for a payment that later rolls back.
- `onPaid` still runs on the caller's thread, after the commit. Add `@Async` to it if the caller must not wait for the e-mail.

## Rules and defaults

- **Any object can be an event:** since Spring Framework 4.2, events need not extend `ApplicationEvent`.
- **Order:** `@Order` on listener methods sets which runs first. `condition = "..."` (a SpEL expression) filters events.
- **Chaining:** a listener that returns an object publishes it as a new event. This does not work for `@Async` listeners.
- **`@Async` listeners:** their exceptions do not reach the publisher, and they run outside its transaction.
- **Transaction phases:** `BEFORE_COMMIT`, `AFTER_COMMIT` (the default), `AFTER_ROLLBACK` and `AFTER_COMPLETION`. With no transaction running, a `@TransactionalEventListener` is skipped unless `fallbackExecution = true`.
- **Writing data after commit:** the original transaction is already committed, so a listener's own database writes need `@Transactional(propagation = REQUIRES_NEW)`. Since Spring Framework 6.1, Spring rejects `@Transactional` on such a listener unless it uses `REQUIRES_NEW` or `NOT_SUPPORTED`.

## Not to be confused with

A Spring event is delivered in memory, to beans in the same running application, and is gone if the app stops. A message broker such as [Kafka](card:spring-kafka), which you will see later, stores messages and delivers them to other services over the network. Rule: inside one app = event; between services = broker.

## Common mistakes

- **"A listener failure cannot affect the publisher."** A synchronous listener's exception is thrown out of `publishEvent()`, so it can fail, and roll back, the publisher's work.

## Interview Qs

### Are Spring events asynchronous?

No. By default `publishEvent()` blocks until every listener has finished, on the same thread and inside the publisher's transaction. Add `@Async` to a listener, with `@EnableAsync`, to run it on another thread. To make every listener asynchronous, define an `applicationEventMulticaster` bean with a task executor.

### Why use @TransactionalEventListener instead of @EventListener?

A plain listener runs at once, before the commit, so it may e-mail a receipt for a payment that later rolls back. `@TransactionalEventListener` waits for the commit by default, so it reacts only to changes that were really saved. You can also choose `AFTER_ROLLBACK` to react to failures.

### Why use events at all, instead of calling the other beans?

Events remove the publisher's dependency on every reaction. `PaymentService` stays small, new reactions are new listener classes, and it avoids cycles between services. The cost is that the flow is harder to follow, because the call site does not show who reacts.
