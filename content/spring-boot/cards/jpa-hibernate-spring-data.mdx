## Why it exists

Writing JDBC code and mapping rows to objects by hand is slow and repetitive. A standard API, an engine that implements it, and generated repositories split that work into three layers.

## How it works

<Compare id="jpa-vs-hibernate-vs-spring-data-jpa" />

- `spring-boot-starter-data-jpa` brings all three: Hibernate, Spring Data JPA and Spring ORM.
- Your code imports `jakarta.persistence.*`, so it depends on the standard, not on Hibernate classes.
- [Spring Data JDBC](card:spring-data-jdbc) is the lighter choice: no lazy loading, no dirty tracking.

## Analogy

<Analogy title="JDBC and the driver" limit="Spring Data JPA has no match in this picture; it is an extra layer on top.">
JDBC is an API you code against; a PostgreSQL driver implements it. JPA is the API; Hibernate is the implementation you plug in.
</Analogy>

## Interview Qs

### If Hibernate does ORM, why do we need JPA?

JPA is the standard your code is written against. Hibernate is one implementation of it. Coding to JPA keeps entity code portable and shared knowledge standard; Hibernate-only features stay optional.

### If JPA exists, why do we need Spring Data JPA?

JPA still needs you to write DAO classes with EntityManager calls and queries. Spring Data JPA generates that code from an interface: CRUD, paging and queries from method names.

### Spring Data JDBC or Spring Data JPA?

JDBC when you want simple, explicit SQL: loading runs the query, saving writes the row, nothing is tracked. JPA when you want an ORM with lazy loading, dirty checking and rich relationship mapping.
