## What it is

These are three layers that work together when a Spring Boot app stores objects in a database. JPA (Jakarta Persistence) is a standard: annotations and interfaces that describe how a Java class maps to a table, which is called object-relational mapping. Such a mapped class is an entity. Hibernate is a library that implements the standard and writes and runs the SQL. Spring Data JPA sits on top. You declare a repository, an interface with methods such as `findById` for one entity, and it creates the class behind it.

## Why it exists

Without them you write JDBC code: open a connection, write the SQL string, then copy each column of the result into a `Payment` field, for every class and every query. JPA lets you describe the mapping once with annotations, and Hibernate turns calls such as "find payment 42" into SQL. Even with JPA, every entity still needs a small data access class with the same find and save methods. Spring Data JPA generates that class from an interface, so the repetitive code disappears.

## How it works

<Compare id="jpa-vs-hibernate-vs-spring-data-jpa" />

Follow one call through the three layers:

1. `PaymentService` calls `paymentRepository.findById(42L)` on the interface you declared.
2. The class Spring Data JPA generated turns this into a JPA call, `entityManager.find(Payment.class, 42L)`. The `EntityManager` is JPA's main interface for loading and saving entities.
3. Hibernate, as the JPA provider, builds `select ... from payment where id = ?` and runs it through JDBC.
4. Hibernate copies the columns of the row into a new `Payment` object and hands it back up the chain.

So you write code against the top two layers, and Hibernate does its work underneath.

## Analogy

<Analogy title="JDBC and the database driver" limit="Spring Data JPA has no match in this picture; it is an extra layer on top of JPA.">
You code against the JDBC API, and a PostgreSQL driver implements it. In the same way, you code against the JPA API, and Hibernate is the implementation plugged in underneath.
</Analogy>

## Example

The whole data layer of a first payment service can be this small:

```java
import java.math.BigDecimal;
import jakarta.persistence.Entity;          // JPA: the standard
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;
import org.springframework.data.jpa.repository.JpaRepository;  // Spring Data JPA

@Entity
public class Payment {
    @Id @GeneratedValue private Long id;
    private BigDecimal amount;
    private String status;
}

public interface PaymentRepository extends JpaRepository<Payment, Long> {}
```

What to notice:

- Nothing is imported from `org.hibernate`. Hibernate is on the classpath through the starter and does the work at runtime.
- The empty interface already has `save`, `findById`, `findAll` and `deleteById`. There is no class to write.
- Because the code depends only on the standard, another JPA provider could run the same entity without changes.

## Rules and defaults

- **One starter:** `spring-boot-starter-data-jpa` brings Hibernate, Spring Data JPA, Spring ORM and the HikariCP connection pool. You add the JDBC driver for your database yourself.
- **Versions in Boot 4.1:** Boot manages Jakarta Persistence 3.2, Hibernate ORM 7.4 and Spring Data JPA 4.1, so you set no version numbers.
- **No persistence.xml:** Boot finds `@Entity` classes and repository interfaces in the package of your main class and below. `@EntityScan` and `@EnableJpaRepositories` change where it looks.

## Not to be confused with

[Spring Data JDBC](card:spring-data-jdbc) is a different Spring Data module. It also gives you repository interfaces, but it runs plain SQL with no Hibernate underneath: no lazy loading and no tracking of changed objects. Rule: Spring Data JPA = an ORM that tracks your objects; Spring Data JDBC = SQL runs when you load or save, nothing more.

## Common mistakes

- **"Spring Data JPA replaces Hibernate."** It does not. Spring Data JPA calls JPA, and something must implement JPA. In a Boot app that is Hibernate; without a provider, no SQL would run.

## Interview Qs

### If Hibernate does ORM, why do we need JPA?

JPA is the standard your code is written against: the annotations, the EntityManager and JPQL. Hibernate is one implementation of it. Coding to JPA keeps entity code portable and familiar to any Java developer, while Hibernate-only features stay optional.

### If JPA exists, why do we need Spring Data JPA?

Plain JPA still needs a data access class per entity, with EntityManager calls and query code. Spring Data JPA generates that class from an interface: CRUD methods, paging, and queries built from method names such as findByStatus.

### Spring Data JDBC or Spring Data JPA?

Spring Data JDBC when you want simple, explicit behaviour: loading runs the query, saving writes the row, and nothing is tracked. Spring Data JPA when you want an ORM with lazy loading, dirty checking and rich relationship mapping.
