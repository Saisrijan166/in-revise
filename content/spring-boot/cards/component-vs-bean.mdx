## Why it exists

The container must know which objects to manage. For your own class an annotation is enough; for a library class you cannot edit, you write a method that builds it.

## How it works

<Compare id="component-vs-bean-annotation" />

- `@Configuration` is itself a `@Component`. By default (`proxyBeanMethods = true`) a call to another `@Bean` method returns the shared bean, not a new object.
- A `@Bean` method gets its own dependencies as method parameters.

## Example

```java
@Configuration
public class TimeConfig {
    @Bean                                  // JDK class: you cannot annotate it
    Clock clock() {
        return Clock.system(ZoneId.of("Asia/Kolkata"));
    }
}

@Service                                   // your class: scanned, Spring calls the constructor
public class InvoiceService {
    InvoiceService(Clock clock) { }
}
```

## Interview Qs

### If @Component and @Bean both create beans, why do we need both?

@Component goes on a class you own; scanning finds it and Spring calls the constructor. @Bean goes on a method; your code builds the object. Use @Bean for third-party classes or when creation needs logic.

### Why use @Service and @Repository if they are just components?

They name the layer, which helps readers, tooling and aspects. @Repository also enables translation of persistence exceptions into Spring's DataAccessException. @Service behaves like @Component today.

### @Component vs @Configuration?

@Configuration is a @Component meant for @Bean methods. Spring subclasses it so calls between its @Bean methods return the shared singleton instead of creating new objects.
