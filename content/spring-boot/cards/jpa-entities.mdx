## Why it exists

Code works with objects; the database stores rows linked by foreign keys. Entity mappings tell JPA which class is which table and which field is which foreign key.

## How it works

| Annotation | Means | Default fetch |
| --- | --- | --- |
| `@ManyToOne` | Many children point to one parent; holds the foreign key | EAGER |
| `@OneToMany` | The parent's list of children | LAZY |
| `@OneToOne` | One row to one row | EAGER |
| `@ManyToMany` | Linked through a join table | LAZY |

- The [owning side](card:owning-side) decides what is written; `mappedBy` marks the inverse side.
- `@JoinColumn` names the foreign key column on the owning side.
- `orphanRemoval = true` deletes a child removed from the parent's collection, at flush.

## Example

```java
@Entity
public class Customer {
    @Id @GeneratedValue private Long id;
    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();
    public void addOrder(Order o) { orders.add(o); o.setCustomer(this); }
}
@Entity public class Order {
    @Id @GeneratedValue private Long id;
    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "customer_id")
    private Customer customer;   // owning side
}
```

## Interview Qs

### What is the owning side, and what does mappedBy do?

The owning side's field is what JPA writes to the foreign key. In one-to-many it must be the @ManyToOne side. The other side sets mappedBy to the owner's field name; changes made only there are not saved.

### Cascade REMOVE vs orphanRemoval?

CascadeType.REMOVE deletes children when the parent is deleted. orphanRemoval also deletes a child that is just removed from the parent's collection. Use both only for children owned by one parent, like order lines.

### Can a Java record be an entity?

No. The spec forbids records, enums and interfaces as entities, and needs a public or protected no-arg constructor. Records work well as DTOs or query projections.
