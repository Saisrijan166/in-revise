## Why it exists

Opening a new database connection for every request is slow. A pool opens a set of connections once and lends them to threads, which give them back when done.

## How it works

<Mermaid
  alt="Threads 1 to 10 each borrow a connection from a pool of 10 open connections to the database and give it back when done. Thread 11 finds none free and waits up to connectionTimeout, 30 seconds by default, then gets an SQLException."
  chart={`flowchart LR
  T1[Thread 1] -- "borrow, then return" --> P[("Pool: 10 open connections")]
  T10[Thread 10] -- "borrow, then return" --> P
  T11[Thread 11] -. "none free: waits up to 30 s" .-> P
  P --> DB[(Database)]`}
/>

- HikariCP recommends leaving `minimumIdle` unset: the pool then stays at a fixed size, which handles spikes best.
- `leakDetectionThreshold` logs a connection that is out of the pool too long, a sign of code that never returns it.
- Boot picks HikariCP whenever it is present; set `spring.datasource.type` to choose another pool.

## Example

```properties
spring.datasource.url=jdbc:postgresql://db:5432/shop
spring.datasource.username=shop
spring.datasource.password=${DB_PASSWORD}
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.connection-timeout=5000
spring.datasource.hikari.max-lifetime=1500000
spring.datasource.hikari.leak-detection-threshold=20000
```

Sizing, from HikariCP's guide: 4 cores and 1 disk give (4 x 2) + 1 = 9, rounded up to 10.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Pool | HikariCP; else Tomcat JDBC, DBCP2, Oracle UCP | Spring Boot 4.1 |
| `maximumPoolSize` | 10 | HikariCP 7.x |
| `minimumIdle` | Same as `maximumPoolSize` | HikariCP 7.x |
| `connectionTimeout` | 30 s | HikariCP 7.x |
| `idleTimeout` | 10 min (only when `minimumIdle` is lower) | HikariCP 7.x |
| `maxLifetime` | 30 min | HikariCP 7.x |
| `keepaliveTime` | 2 min | HikariCP 7.x |
| `leakDetectionThreshold` | 0 (off) | HikariCP 7.x |

## Interview Qs

### Which connection pool does Spring Boot use?

HikariCP, chosen whenever it is on the classpath; the jdbc and data-jpa starters bring it in. It has been the default since Boot 2.0. Without it, Boot tries Tomcat JDBC, then Commons DBCP2, then Oracle UCP; spring.datasource.type picks one directly.

### How do you size the pool?

Smaller than most people expect. HikariCP's guide starts near cores x 2 plus disks, about 10 for a 4-core server, then measure. If each thread holds one connection while asking for another, use Tn x (Cm - 1) + 1 to avoid a pool deadlock.

### Threads fail waiting for a connection. What do you check?

All connections stayed busy for the whole connectionTimeout. Look for long transactions and leaked connections first; leakDetectionThreshold logs them. Then check whether the pool size fits the load.
