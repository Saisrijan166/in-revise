## What it is

A database connection is an open network session between your app and the database, already logged in and ready for SQL. A connection pool opens a set of these connections once and keeps them. A request **borrows** one, uses it, and **returns** it, instead of opening and closing its own. Spring Boot uses the HikariCP pool by default.

## Why it exists

Every request to the payment service needs the database. Opening a new connection each time means a network handshake and a login before any SQL runs, and a traffic spike can open hundreds of connections that overload the database. A pool pays the opening cost once and caps the number of connections, so the database gets steady, limited load.

## How it works

<Mermaid
  alt="Threads 1 to 10 each borrow a connection from a pool of 10 open connections and give it back when done. Thread 11 finds none free and waits up to 30 seconds, then gets an SQLException."
  chart={`flowchart LR
  T1[Thread 1] -- "borrow, return" --> P[("Pool: 10 open connections")]
  T10[Thread 10] -- "borrow, return" --> P
  T11[Thread 11] -. "none free: waits up to 30 s" .-> P
  P --> DB[(Database)]`}
/>

1. When the app first uses the database, usually during startup, HikariCP opens connections and keeps them ready.
2. A request enters a [@Transactional](card:transactional) method, and the transaction manager borrows a connection from the pool.
3. The thread keeps that connection until the transaction commits or rolls back. Then the connection goes back to the pool; it is not closed.
4. If all 10 are busy, the next thread waits. If none comes back within 30 seconds, it gets an `SQLException`.
5. HikariCP retires each connection after its maximum lifetime, 30 minutes by default, and opens a fresh one.

So the length of your transactions decides how many connections you need: a connection is busy for the whole transaction.

## Example

The payment service's pool settings, set to fail fast and to report leaks:

```properties
spring.datasource.url=jdbc:postgresql://db:5432/payments
spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.connection-timeout=5000
spring.datasource.hikari.leak-detection-threshold=20000
```

What to notice:

- `connection-timeout=5000` makes a waiting request fail after 5 seconds instead of 30, so a stuck database shows up quickly.
- `leak-detection-threshold=20000` logs a message about a possible leak when a connection stays out for more than 20 seconds. It is off by default.
- Boot binds these kebab-case names to HikariCP's own settings, such as `maximumPoolSize`.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| `maximumPoolSize` | 10 | HikariCP 7.0 |
| `minimumIdle` | Same as `maximumPoolSize` (a fixed-size pool) | HikariCP 7.0 |
| `connectionTimeout` | 30 s | HikariCP 7.0 |
| `idleTimeout` | 10 min, used only when `minimumIdle` is below the maximum | HikariCP 7.0 |
| `maxLifetime` | 30 min | HikariCP 7.0 |

- **Which pool:** Boot always picks HikariCP when it is present. Without it, Boot tries Tomcat JDBC, then Commons DBCP2, then Oracle UCP. `spring.datasource.type` picks one directly.
- **maxLifetime:** set it a few seconds shorter than any time limit the database or the network puts on connections.
- **Sizing:** HikariCP's guide starts at (CPU cores x 2) + number of disks on the database server, then load-test.
- **REQUIRES_NEW:** each such call holds a second connection, so the pool must exceed the number of concurrent threads, as in [propagation](card:transaction-propagation).

## Not to be confused with

The **connection pool** limits how many database connections exist. The **web server's thread pool** limits how many requests run at once: embedded Tomcat allows 200 worker threads by default in Spring Boot 4.1 (the limit does not apply with virtual threads). Rule: threads carry requests; connections carry SQL. 200 threads can share 10 connections, because most of a request's time is not spent in the database.

## Common mistakes

- **"A slow HTTP call inside a transaction only slows that request."** The thread keeps its connection for the whole transaction, so the call also blocks one of the 10 connections. Make remote calls, such as the fraud check, before or after the transaction.

## Interview Qs

### Which connection pool does Spring Boot use?

HikariCP, chosen whenever it is on the classpath; the jdbc and data-jpa starters bring it in. Without it, Boot tries Tomcat JDBC, then DBCP2, then Oracle UCP. You can force one with spring.datasource.type.

### How do you size the connection pool?

Smaller than most people expect. HikariCP's guide starts at CPU cores times two plus disks on the database server, (4 x 2) + 1 = 9 for a 4-core server with one disk. Then load-test and adjust, and keep transactions short.

### Threads fail waiting for a connection. What do you check?

All connections stayed busy for the whole timeout. First look for long transactions, slow calls inside transactions and leaked connections, using leak-detection-threshold. Then check whether the pool size fits the real load.
