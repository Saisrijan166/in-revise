## Why it exists

A JVM app loads classes, scans and wires beans, and warms up at every start. For functions and containers that start often, startup time and memory per instance matter most.

## How it works

<Mermaid
  alt="Native image build. Your code and Spring go through Spring AOT processing, which writes generated bean code and hint files. GraalVM then runs a static analysis from the main method. Reachable code goes into the native executable; unreachable code is dropped."
  chart={`flowchart LR
  S[Your code + Spring] --> A[Spring AOT: generated bean code and hints]
  A --> G[GraalVM: static analysis from main]
  G --> X([Native executable: reachable code only])
  G -. "unreachable code" .-> D[Dropped]`}
/>

- Spring writes most hints itself; third-party libraries get theirs from the GraalVM Reachability Metadata repository.
- Build with `mvn -Pnative spring-boot:build-image` (a container image) or `mvn -Pnative native:compile` (a local executable).
- Test the AOT code on a normal JVM with `-Dspring.aot.enabled=true`, or record missing hints with the tracing agent.

## Example

```java
@Configuration
@ImportRuntimeHints(ReportHints.class)
class NativeConfig {
}

class ReportHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("templates/report.txt"); // read at run time
        hints.proxies().registerJdkProxy(PriceClient.class);        // a JDK proxy
    }
}
```

```bash
./mvnw -Pnative native:compile   # needs GraalVM 25+ installed
./target/myapp                   # starts without a JVM
```

## Interview Qs

### What is a GraalVM native image, and why use one with Spring Boot?

A platform-specific executable compiled ahead of time, so no JVM is needed to run it. It starts much faster and uses less memory, which suits containers, scale-to-zero and functions as a service.

### What does Spring AOT processing do?

At build time it evaluates the configuration, writes the bean definitions as Java source, generates the proxy classes and writes hint files for reflection, resources and proxies, so GraalVM can see everything the app needs.

### What are the limitations of native images?

A closed world: the classpath and beans are fixed at build time, so `@Profile` and `@ConditionalOnProperty` cannot switch beans later. Reflection, resources and proxies need hints. Builds are slow and heavy, with fewer optimisations than a warmed-up JVM.

### Native image or JVM with an AOT cache?

Both cut startup time. An AOT cache keeps the normal JVM and full Java behaviour; it needs Java 25+ and a training run. A native image drops the JVM for much faster startup and less memory, but brings closed-world limits and long builds.
