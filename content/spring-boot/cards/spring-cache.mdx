## Why it exists

Some reads are slow and return the same result many times, such as a product lookup. Caching by hand fills every method with "get it, else load it and store it" code.

## How it works

<Compare id="cacheable-vs-cacheput-vs-cacheevict" />

- Spring's cache is an abstraction; the provider stores the data and owns expiry and size limits.
- Boot checks providers in order (JCache, Hazelcast, Redis, Caffeine and others) and falls back to a simple map.
- The default key is the single argument, or a `SimpleKey` of all arguments.

## Example

```java
@Configuration
@EnableCaching
class CacheConfig { }

@Service
public class ProductService {   // repository injected through the constructor
    @Cacheable(cacheNames = "products", key = "#id")
    public Product find(long id) { return repository.findById(id).orElseThrow(); }

    @CacheEvict(cacheNames = "products", key = "#id")
    public void delete(long id) { repository.deleteById(id); }
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Provider | First found; else Simple (`ConcurrentHashMap`) | Spring Boot 4.1 |
| Expiry with Simple | None | Spring Framework 7.0 |
| `@CacheEvict` timing | After the method succeeds | Spring Framework 7.0 |

## Interview Qs

### If the database stores the data, why add a cache?

The database is the durable source of truth; the cache is a fast copy. It cuts response time and database load for data read often and changed rarely.

### Why is my @Cacheable not working?

Check @EnableCaching first. Then the call must pass through the proxy: no self-invocation, a public method, a bean from Spring. Also check that the key really repeats.

### How do you set a TTL?

Not on the annotation; the abstraction leaves expiry to the provider. Use spring.cache.redis.time-to-live for Redis, or a Caffeine spec such as expireAfterAccess=600s.
