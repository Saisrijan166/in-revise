## What it is

A cache is a fast store that keeps copies of results you have already fetched, so the next request gets them without asking the database. Spring Cache adds caching to a method with an annotation: `@Cacheable` to read, `@CachePut` to write, `@CacheEvict` to delete. Spring decides *when* to use the cache; a **provider** stores the data. Caffeine keeps it in memory inside your app; Redis keeps it on a separate server that all instances share.

## Why it exists

A front end polls `GET /payments/42` every few seconds to show the status. Each call runs the same SQL query and returns the same answer. Caching by hand means writing "look in the map, else load it and put it" in every such method, plus the code to remove old entries, all mixed with business logic. Spring Cache moves that into one annotation per method, and the same code works with any provider.

## How it works

1. The controller calls `paymentQueries.find(42)`. Like `@Transactional`, this goes through a [proxy](card:aop-proxies).
2. The proxy builds a key from the arguments, here `42`, and looks in the cache named `payments`.
3. On a hit, it returns the stored value. Your method does not run, so no SQL is sent.
4. On a miss, it runs your method, stores the result under key `42`, and returns it.
5. Later, a method with `@CachePut` replaces that entry with its new result, and a method with `@CacheEvict` removes it, so the next read loads fresh data.

So reads fill the cache, and only the write methods you annotate keep it correct.

## Example

The payment service caches the response for a payment and keeps it fresh on change:

```java
@Service
public class PaymentQueryService {     // repository injected through the constructor
    @Cacheable(cacheNames = "payments", key = "#id")
    public PaymentResponse find(long id) {
        return PaymentResponse.from(payments.findById(id).orElseThrow());
    }

    @CachePut(cacheNames = "payments", key = "#id")
    public PaymentResponse complete(long id) {
        return PaymentResponse.from(payments.markCompleted(id));
    }

    @CacheEvict(cacheNames = "payments", key = "#id")
    public void cancel(long id) { payments.deleteById(id); }
}
```

What to notice:

- The second `find(42)` returns the stored `PaymentResponse` and runs no SQL.
- `complete(42)` always runs and replaces the entry, so the next `find(42)` shows the new status.
- Remove `@CacheEvict` from `cancel()` and `find(42)` keeps returning the cancelled payment. With the fallback provider, which never expires entries, that lasts until a restart.
- This caches a DTO, not the entity. The persistence context does not track cached copies, so changing one would never reach the database.

## Rules and defaults

- **Switch it on:** add `spring-boot-starter-cache` and put `@EnableCaching` on a `@Configuration` class. Boot advises against putting it on the main application class, because caching then runs in every test too.
- **Provider choice (Spring Boot 4.1):** if you define no `CacheManager`, Boot uses the first provider it finds, in this order: Generic, JCache, Hazelcast, Infinispan, Couchbase, Redis, Caffeine, Cache2k, Simple. Simple is a `ConcurrentHashMap` with no expiry. `spring.cache.type=none` turns caching off.
- **Expiry:** the annotations have no TTL. Set it on the provider: `spring.cache.redis.time-to-live=10m` (Redis entries never expire by default) or `spring.cache.caffeine.spec=maximumSize=500,expireAfterAccess=600s`.
- **Default key:** no arguments gives `SimpleKey.EMPTY`, one argument is the key itself, several arguments give a `SimpleKey` of all of them.
- **Public methods only:** with proxies, cache annotations on protected, package-private or private methods are silently ignored.
- **Useful attributes:** `unless = "#result == null"` skips storing a result; `sync = true` lets only one thread load a missing entry while the others wait; `@CacheEvict(allEntries = true)` clears the whole cache. Eviction runs after the method succeeds unless `beforeInvocation = true`.

## Not to be confused with

**Spring Cache** stores method results at the service layer, under keys you choose. Hibernate's **second-level cache**, from the [persistence context](card:persistence-context) concept, stores entities by id inside JPA. Rule: Spring Cache caches what your methods return; the second-level cache caches what Hibernate loads.

## Interview Qs

### If the database already stores the data, why add a cache?

They do different jobs. The database is the durable source of truth; the cache is a fast, temporary copy. For data read often and changed rarely, the cache cuts response time and takes load off the database. Every change must still go to the database first.

### Why is my @Cacheable not working?

Check @EnableCaching first. Then the call must pass through the proxy: no this-call from the same class, a public method, a bean created by Spring. Finally, check that the key really repeats between calls; an argument with no proper equals() gives a new key every time.

### How do you set a TTL on a Spring cache?

Not on the annotation; the abstraction leaves expiry to the provider. With Redis, set spring.cache.redis.time-to-live. With Caffeine, set spring.cache.caffeine.spec, for example expireAfterAccess=600s, or build your own CacheManager bean.

### Caffeine or Redis?

Caffeine lives inside each instance: very fast, but every instance has its own copy, so an eviction on one does not reach the others. Redis is one shared cache over the network: a bit slower, but all instances see the same entries. With several instances and data that changes, choose Redis.
