## Why it exists

Without a central place for errors, every controller repeats try/catch blocks, and clients get a different error shape from each endpoint. One advice class gives every error the right status and the same body.

## How it works

<Mermaid
  alt="How Spring MVC resolves an exception, in order. First, an @ExceptionHandler in the same controller; if there is none, one in a @ControllerAdvice. Next, @ResponseStatus on the exception class or a ResponseStatusException sets the status. Next, built-in Spring MVC exceptions are mapped to codes such as 405 or 415. If nothing resolves it, the servlet container forwards to Spring Boot's /error, which answers with JSON or the whitelabel page."
  chart={`flowchart TD
  E([Exception from a controller]) --> L{"@ExceptionHandler in that controller?"}
  L -- no --> G{"@ExceptionHandler in a @ControllerAdvice?"}
  G -- no --> S{"@ResponseStatus or ResponseStatusException?"}
  S -- no --> D{"Built-in Spring MVC exception?"}
  D -- no --> X["Container forwards to Boot's /error"]
  L -- yes --> H[Handler builds the response]
  G -- yes --> H
  S -- yes --> C[That status]
  D -- yes --> M["Mapped code, e.g. 405, 415"]`}
/>

- The closest exception type wins; a match on the thrown exception beats a match on its cause.
- With `spring.mvc.problemdetails.enabled=true`, Boot adds a `ResponseEntityExceptionHandler` (order 0) that renders built-in errors as `application/problem+json`.
- Extra ProblemDetail properties appear as top-level JSON fields.

## Example

```java
@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Order not found");
        pd.setProperty("orderId", ex.orderId());          // extra JSON field
        return pd;
    }
}

// A one-off case needs no custom exception class:
throw new ResponseStatusException(HttpStatus.CONFLICT, "Email already registered");
```

The client receives `application/problem+json`:

```json
{ "title": "Order not found", "status": 404, "detail": "No order 42",
  "instance": "/orders/42", "orderId": 42 }
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| ProblemDetail for built-in errors | Off: `spring.mvc.problemdetails.enabled=false` | Spring Boot 4.1 |
| Fallback for unhandled errors | `/error` (BasicErrorController) | Spring Boot 4.1 |
| Fields in the `/error` JSON | timestamp, status, error, path | Spring Boot 4.1 |
| Exception message, stack trace | Never included (`spring.web.error.include-message`, `include-stacktrace`) | Spring Boot 4.1 (`server.error.*` in 3.x) |

## Interview Qs

### How do you handle exceptions globally in Spring Boot?

Create a @RestControllerAdvice class with @ExceptionHandler methods, one per exception type, each returning a ProblemDetail or ResponseEntity with the right status. It applies to all controllers; a handler inside a controller still takes priority for that controller.

### @ControllerAdvice vs @RestControllerAdvice?

@RestControllerAdvice is @ControllerAdvice plus @ResponseBody, so handler return values are written to the body, usually as JSON. Both apply to all controllers unless narrowed by package, annotation or type.

### What is ProblemDetail?

Spring's class for RFC 9457 problem details: a standard JSON error body with type, title, status, detail and instance, sent as application/problem+json. Return it from an @ExceptionHandler, or set spring.mvc.problemdetails.enabled=true for the built-in errors.

### What happens to an exception nobody handles?

It reaches the servlet container, which forwards to Boot's /error. BasicErrorController answers API clients with JSON (timestamp, status, error, path) and browsers with the whitelabel page. The message and stack trace are hidden by default.
