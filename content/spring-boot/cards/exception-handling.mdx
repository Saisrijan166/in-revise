## What it is

Global exception handling means one class decides how every exception becomes an HTTP error response. You write methods marked `@ExceptionHandler(SomeException.class)`, each returning the response for that exception type. You put them in a class marked `@RestControllerAdvice`, and Spring applies them to all controllers. In the [request flow](card:dispatcher-servlet), this is the step where an exception is turned into an error response.

## Why it exists

Without a central place, each controller wraps its code in try/catch, and each endpoint invents its own error JSON: one says `"error"`, another `"message"`, a third leaks a stack trace. Clients cannot handle errors in one way. With one advice class, the service just throws `PaymentNotFoundException`, and the same handler gives every endpoint the right status and the same body.

1. `PaymentService.find(42)` finds nothing and throws `PaymentNotFoundException`. The exception travels up out of the controller method.
2. DispatcherServlet hands it to its exception resolvers. The first one looks for an `@ExceptionHandler` for this type in the same controller.
3. If there is none, it looks in the advice classes. Among the matching handlers, the one whose type is closest to the thrown exception wins.
4. The handler returns a `ProblemDetail`, Spring's class for a standard JSON error body (RFC 9457), and Spring writes it with that status.
5. If no handler matches, the exception reaches the server, and Spring Boot's `/error` endpoint writes a generic error.

## Example

A custom exception for the payment service and the advice class that maps it to 404:

```java
class PaymentNotFoundException extends RuntimeException {
    PaymentNotFoundException(long id) { super("No payment with id " + id); }
}

@RestControllerAdvice                              // applies to every controller
class ApiErrors {
    @ExceptionHandler(PaymentNotFoundException.class)
    ProblemDetail notFound(PaymentNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Payment not found");
        return pd;                                 // 404, application/problem+json
    }
}
```

What to notice:

- The service and the controller have no try/catch. They throw, and the advice decides the response.
- `ProblemDetail` sets the status to 404. Spring fills in `instance` with the request path, for example `/payments/42`, and sends the content type `application/problem+json`.
- Delete this handler and the same request answers 500 from `/error`, which tells the client nothing useful.

## Rules and defaults

- **Local first:** a handler inside a controller runs before a global one in an advice class.
- **Spring MVC's own errors:** they already have statuses, such as 400 for a failed `@Valid`. To give them a ProblemDetail body too, set `spring.mvc.problemdetails.enabled=true` (off by default in Spring Boot 4.1), or extend `ResponseEntityExceptionHandler` in your advice.
- **Fallback:** unhandled errors go to `/error` (`spring.web.error.path`). Its JSON holds `timestamp`, `status`, `error` and `path`; the message and stack trace are `never` included by default.
- **Changed in 4.0:** these properties moved from `server.error.*` to `spring.web.error.*`.
- **Not covered:** an exception thrown in a servlet filter happens before DispatcherServlet, so advice classes never see it.

## Not to be confused with

`@ExceptionHandler` is the handling method itself. `@ControllerAdvice` is the global place to put such methods. `@RestControllerAdvice` is `@ControllerAdvice` plus `@ResponseBody`, so its handlers write the return value as the body. Rule: `@ExceptionHandler` = how, advice = where.

## Interview Qs

### How do you handle exceptions globally in Spring Boot?

Create a @RestControllerAdvice class with one @ExceptionHandler method per exception type. Each returns a ProblemDetail or a ResponseEntity with the right status. It applies to every controller, so services just throw meaningful exceptions and the API keeps one error shape.

### If @ExceptionHandler handles exceptions, why do we need @ControllerAdvice?

@ExceptionHandler is the mechanism, but declared in a controller it covers only that controller. @ControllerAdvice is the global location, so one set of handlers serves every controller instead of being copied into each.

### What is ProblemDetail?

Spring's class for RFC 9457 "problem details": a standard JSON error body with the fields type, title, status, detail and instance, sent as application/problem+json. Using a standard shape means clients and tools can read your errors without custom code.
