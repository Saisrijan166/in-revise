## What it is

Authorization rules decide whether an [authenticated](card:authentication-flow) caller may do something. Spring Security has two places for them. URL rules, written with `authorizeHttpRequests`, are checked by AuthorizationFilter before the controller runs. Method rules, written with `@PreAuthorize` on a bean method, are checked when that method is called. Both compare the caller's authorities, such as `ROLE_ADMIN`, with what the rule asks for. A method rule can also use SpEL (Spring Expression Language) to read the method's arguments.

## Why it exists

Login alone lets every customer call every endpoint, including refunds and other customers' payments. Writing `if` checks in each controller spreads access logic everywhere, and one missed check is a hole. URL rules put the coarse decisions in one list. Method rules sit on the service, so it stays protected whichever controller, scheduled job or message listener calls it.

## How it works

1. AuthorizationFilter, the last filter in the chain, compares the request's path and HTTP method with the URL rules in the order you wrote them. The first rule that matches decides.
2. That rule checks the current `Authentication`: `permitAll()`, `authenticated()`, `hasRole(...)` or `denyAll()`.
3. If the rule denies, ExceptionTranslationFilter answers. A caller who is not logged in is asked to log in (401 or a redirect to the login page). A logged-in caller gets 403.
4. If it allows, the controller calls the service. With `@EnableMethodSecurity`, that service bean is a [proxy](card:aop-proxies), and the proxy evaluates the `@PreAuthorize` expression first.
5. If the expression is false, the proxy throws `AccessDeniedException`, which becomes 403. If true, the method body runs.

## Example

The payment service lets only admins refund, and lets customers read only their own payments:

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/actuator/health").permitAll()
    .requestMatchers(HttpMethod.POST, "/payments/*/refund").hasRole("ADMIN")
    .requestMatchers("/payments/**").authenticated()
    .anyRequest().denyAll());                   // allow-list: the rest is blocked

@Service
class PaymentService {
    @PreAuthorize("hasRole('ADMIN') or #email == authentication.name")
    public List<PaymentResponse> findFor(String email) { /* ... */ }
}
```

What to notice:

- The refund rule comes before `/payments/**`. Swap them and any logged-in customer can refund.
- `denyAll()` at the end makes the list an allow-list: a new endpoint nobody added a rule for is blocked, not open.
- `#email` is the method argument and `authentication.name` is the logged-in user, so a customer can read only their own payments. A URL rule cannot see that argument.
- Without `@EnableMethodSecurity` on a `@Configuration` class, the `@PreAuthorize` line is silently ignored.

## Rules and defaults

- **First match:** URL rules are checked in the order declared; only the first match applies.
- **Method security (Boot 4.1):** off until you add `@EnableMethodSecurity`. It turns on `@PreAuthorize`, `@PostAuthorize`, `@PreFilter` and `@PostFilter`; it replaces the deprecated `@EnableGlobalMethodSecurity`.
- **Other annotations:** `@Secured` needs `securedEnabled = true`, and JSR-250 annotations such as `@RolesAllowed` need `jsr250Enabled = true`.
- **Argument names:** `#email` needs parameter names at runtime. Boot's Maven parent compiles with `-parameters`, so it works out of the box there.
- **`@PostAuthorize`:** runs after the method, so do not use it on methods that write to the database.
- **Changed in 7.0:** the old `authorizeRequests` was removed; use `authorizeHttpRequests`.

## Not to be confused with

`hasRole("ADMIN")` adds the `ROLE_` prefix and checks `ROLE_ADMIN`. `hasAuthority("ADMIN")` checks the exact string `ADMIN`. Rule: role = prefix added for you; authority = the exact string.

## Interview Qs

### Does the order of requestMatchers matter?

Yes. AuthorizationFilter applies only the first rule that matches, so put specific paths before broad ones and end with `anyRequest()`. Ending with `denyAll()` turns the rules into an allow-list, so a forgotten endpoint is blocked.

### What is the difference between @PreAuthorize and @Secured?

`@Secured` only lists authorities, such as `ROLE_ADMIN`, and must be switched on with `securedEnabled = true`. `@PreAuthorize` is on with `@EnableMethodSecurity` and takes a SpEL expression, so it can also check arguments and the current user.

### Should you use URL security or method security?

Both. URL rules are a coarse first gate for every request. Method rules guard the service layer whichever caller uses it, and can check data, such as whether a payment belongs to the user. Unannotated methods are not protected, so keep a URL catch-all.

### Your @PreAuthorize has no effect. What do you check?

First, that `@EnableMethodSecurity` is present. Second, that the method is called from another bean through the proxy, not from the same class. Third, that the object is a Spring bean and not created with `new`, because only beans get the proxy.
