## Why it exists

Being logged in is not enough: an ordinary user must not reach admin pages. Rules decide that per URL and, for finer checks, per method call.

## How it works

| | URL rules | Method rules |
| --- | --- | --- |
| Where | `authorizeHttpRequests` in the SecurityFilterChain | `@PreAuthorize` on bean methods |
| Can check | Path, HTTP method, authorities | Arguments, the user, any SpEL expression |
| Switched on | When you write rules | `@EnableMethodSecurity` |
| On denial | Not logged in: asked to log in; else 403 | AccessDeniedException, a 403 on the web |

- `@Secured` lists role names only and needs `securedEnabled = true`; prefer `@PreAuthorize`.
- Method checks run in a [proxy](card:aop-proxies): calls from inside the same class skip them.

## Example

```java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers(HttpMethod.GET, "/products/**").permitAll()
    .anyRequest().authenticated());           // catch-all, last

@PreAuthorize("hasRole('ADMIN')")             // on a service method
public void deleteUser(long id) { /* ... */ }
```

## Interview Qs

### Does the order of requestMatchers matter?

Yes. AuthorizationFilter applies only the first rule that matches, so put specific paths before broad ones and end with `anyRequest()`. Ending with `denyAll()` turns the rules into an allow-list.

### @PreAuthorize vs @Secured?

`@Secured` only lists roles and must be switched on with `securedEnabled = true`. `@PreAuthorize` is on with `@EnableMethodSecurity` and takes SpEL, so it can check arguments and the current user.

### URL security or method security?

Both. URL rules are a coarse first gate. Method rules guard the service layer whichever controller calls it, and can check data, such as whether the record belongs to the user.
