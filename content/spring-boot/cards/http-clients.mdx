## What it is

An HTTP client is the code your service uses to call another service's API, the way a browser calls a website. Spring offers two clients today. RestClient makes a call and waits for the answer, which fits a normal Spring MVC app. WebClient starts the call and returns at once with a promise of the answer, which fits reactive apps, as you will see in [Spring MVC vs WebFlux](card:mvc-vs-webflux). Both turn your Java objects into JSON requests and JSON answers back into objects.

## Why it exists

The payment service must ask a fraud service "is this payment safe?" before it saves anything. With a raw HTTP library you would build the URL, write the JSON, send it, check the status, read the bytes and parse them, every time. A client does these steps for you, reuses the same [message converters](card:dispatcher-servlet) as your controllers, and turns error statuses into exceptions.

## How it works

<Compare id="restclient-vs-webclient-vs-resttemplate" />

1. Spring Boot creates a `RestClient.Builder` with its defaults, such as the JSON converters and the timeout properties. It is a prototype bean, so each injection gets a fresh builder.
2. Your class injects the builder, sets a base URL and builds one `RestClient`, which it keeps.
3. Each call names the method and the path, adds a body if needed, and calls `retrieve()`.
4. The client sends the request. A 4xx or 5xx answer throws an exception; a 2xx answer is read into the type you ask for.

## Example

A `FraudCheckClient` that the payment service calls before saving a payment:

```java
@Service
class FraudCheckClient {
    private final RestClient http;
    FraudCheckClient(RestClient.Builder builder) {              // Boot's pre-configured builder
        this.http = builder.baseUrl("https://fraud.internal.example").build();
    }
    FraudResult check(PaymentRequest request) {
        return http.post().uri("/checks")
                .body(request)                                  // written as JSON
                .retrieve()                                     // a 4xx or 5xx reply throws
                .body(FraudResult.class);                       // JSON read into a record
    }
}
```

The same call as an HTTP service interface, with its settings in properties:

```java
interface FraudCheckApi {                             // Spring generates the implementation
    @PostExchange("/checks")
    FraudResult check(@RequestBody PaymentRequest request);
}
```

```properties
spring.http.clients.connect-timeout=1s
spring.http.clients.read-timeout=2s
spring.http.serviceclient.fraud.base-url=https://fraud.internal.example
```

What to notice:

- Injecting the builder, not calling `RestClient.create()`, keeps Boot's converters and timeout settings.
- With the interface, you write no request code at all; you register it with `@ImportHttpServices(group = "fraud", types = FraudCheckApi.class)`, usually on the main application class, and inject `FraudCheckApi` like any bean.
- `read-timeout=2s` means a fraud service that does not answer within 2 seconds causes an exception instead of a thread that waits forever.

## Rules and defaults

- **Starter (Spring Boot 4):** `spring-boot-starter-restclient` brings the blocking clients (RestClient, RestTemplate and HTTP service clients); `spring-boot-starter-webclient` brings the reactive one.
- **No RestTemplate bean:** Boot offers a `RestTemplateBuilder` but no ready `RestTemplate`, because each one usually needs its own settings.
- **Errors by default:** a 4xx or 5xx answer throws a `RestClientException` subclass. Use `onStatus(...)` to handle it your way.
- **OpenFeign:** Spring Cloud OpenFeign still works but is feature-complete; its docs point to Spring's HTTP service clients.

## Interview Qs

### What is the difference between RestTemplate, RestClient and WebClient?

RestTemplate is the classic blocking client with methods like getForObject; Spring Framework 7.0 deprecates it, with removal planned for 8.0. RestClient is also blocking but has a fluent API. WebClient is non-blocking and reactive. New blocking code should use RestClient.

### If RestClient can call APIs, why do we need WebClient?

They follow different execution models. RestClient blocks the calling thread until the answer arrives. WebClient returns a Mono or Flux at once and does not hold a thread while waiting, and it supports streaming. That fits WebFlux apps, where threads must never block.

### What is an HTTP service client?

A Java interface whose methods carry @GetExchange, @PostExchange and similar annotations. Spring generates a proxy that makes the calls through RestClient or WebClient. You declare the remote API once, as a typed interface, instead of building each request by hand.
