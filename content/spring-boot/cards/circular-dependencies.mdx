## What it is

A circular dependency is a loop between beans: `PaymentService` needs `NotificationService`, and `NotificationService` needs `PaymentService`. The loop can also be longer, such as A needs B, B needs C and C needs A. With [dependency injection](card:dependency-injection), Spring must build a bean's dependencies before it can finish that bean, so in a loop there is no bean it can finish first.

## Why it exists

You never add a cycle on purpose. It grows when one class reaches back into another for a small piece of data, for example to read a payment's status. If Spring quietly patched every loop, two classes would stay tangled and harder to test and change. So Spring Boot fails at startup and prints the loop, and you fix the design while the change is still small.

## How it works

1. Spring starts to build `PaymentService` and sees that its constructor needs a `NotificationService`.
2. It marks `PaymentService` as "currently in creation" and starts to build `NotificationService`.
3. The `NotificationService` constructor needs a `PaymentService`, but that bean is still unfinished.
4. Spring throws `BeanCurrentlyInCreationException`. Spring Boot's failure report draws the loop and stops the app.

The fix on the right works because `NotificationService` only needed to read a payment, and `PaymentRepository` can do that. Each bean now depends on something below it, never back up.

## Example

This is the cycle from the diagram, with [constructor injection](card:dependency-injection):

```java
@Service
public class PaymentService {
    private final NotificationService notifications;
    public PaymentService(NotificationService notifications) { this.notifications = notifications; }
}

@Service
public class NotificationService {
    private final PaymentService payments;   // only used to read a payment's status
    public NotificationService(PaymentService payments) { this.payments = payments; }
}
```

What to notice:

- Neither constructor can run without the other object already built, so this fails at startup in any Spring app.
- The comment shows the real problem: `NotificationService` uses `PaymentService` for a read that `PaymentRepository` can do. Change that one field and the cycle is gone.
- Writing `@Lazy PaymentService payments` in the second constructor would also let the app start, but the two classes would stay tangled.

## Rules and defaults

- **Spring Boot default:** `spring.main.allow-circular-references` is `false` (since Spring Boot 2.6, still so in 4.1). Any cycle fails with "The dependencies of some of the beans in the application context form a cycle".
- **Plain Spring Framework:** without Boot, field and setter cycles between singletons are resolved; only constructor cycles fail.
- **Allowing cycles:** setting the property to `true` lets Spring resolve field and setter cycles again. Constructor cycles still fail. Boot's own message calls this a last resort.
- **`@Lazy` on a parameter:** Spring injects a lazy-resolution proxy, a stand-in that looks up the real bean on the first method call. `ObjectProvider<NotificationService>` gives a similar delayed lookup.

## Not to be confused with

`@Lazy` on a class, from [bean lifecycle](card:bean-lifecycle), delays **creating** that bean until something first needs it. `@Lazy` on a constructor parameter delays **looking up** the dependency, by injecting a stand-in. Only the second one gets a constructor cycle past startup. Rule: on the class = create later; on the parameter = fetch later.

## Interview Qs

### How do you fix a circular dependency?

First redesign: move the shared logic into a third bean, or make one bean depend on a lower-level bean such as a repository. As a quick stopgap, put `@Lazy` on one constructor parameter. Setting `spring.main.allow-circular-references=true` is a last resort, and it never fixes a constructor cycle.

### Why does constructor injection expose cycles so early?

Spring must call a constructor with all its arguments ready. In a loop, neither argument can exist first, so startup fails with `BeanCurrentlyInCreationException`. That is useful: you see the design problem on the first run, not later as a half-built bean.

### What happens if you set spring.main.allow-circular-references=true?

Spring goes back to resolving field and setter cycles, by handing one bean an early reference to the other before it is fully initialised. Constructor cycles still fail. The tangled design stays, so treat it as a temporary switch while you remove the cycle.
