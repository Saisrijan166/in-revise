## Why it exists

Two beans that need each other cannot both be built first. The loop usually means they share a job that belongs in a third class, so Spring Boot makes it fail early.

## How it works

<Mermaid
  alt="Before: OrderService needs InvoiceService and InvoiceService needs OrderService, a cycle that fails at startup. After: the shared logic moves to a new TaxCalculator bean; OrderService and InvoiceService both use TaxCalculator, and neither needs the other."
  chart={`flowchart LR
  subgraph BAD [Cycle: fails at startup]
    A[OrderService] -- needs --> B[InvoiceService]
    B -- needs --> A
  end
  subgraph GOOD [Fixed: shared logic in a third bean]
    A2[OrderService] --> T[TaxCalculator]
    B2[InvoiceService] --> T
  end`}
/>

- With constructor injection neither bean can be built first, so even plain Spring fails with `BeanCurrentlyInCreationException`.
- When cycles are allowed, plain Spring breaks setter and field cycles by injecting an early reference to a bean that is not fully initialised yet.
- Boot's startup failure report lists the beans in the cycle and names the property only as a last resort.

## Example

```java
@Service
class OrderService {
    private final InvoiceService invoices;

    OrderService(@Lazy InvoiceService invoices) {   // a proxy, resolved on first call
        this.invoices = invoices;
    }
}

@Service
class InvoiceService {
    InvoiceService(OrderService orders) { }
}
```

```properties
# Last resort: restores the pre-2.6 behaviour; constructor cycles still fail
spring.main.allow-circular-references=true
```

## Interview Qs

### How does Spring resolve circular dependencies?

For singletons wired through setters or fields, plain Spring creates A, exposes an early reference to it, builds B with that reference, then finishes A. Constructor cycles cannot be resolved. Spring Boot switches this off by default since 2.6.

### How do you fix a circular dependency?

Best: redesign. Move the shared logic into a third bean, or let one side publish an event the other listens to. Quick fix: `@Lazy` on one dependency. Last resort: `spring.main.allow-circular-references=true`.

### Why does constructor injection expose cycles?

Spring cannot call either constructor without the other object, so the app fails at startup with BeanCurrentlyInCreationException. That is useful: the cycle is a design smell, and you find it on day one instead of later.

### What changed in Spring Boot 2.6?

Circular references between beans became prohibited by default, so a cycle fails at startup even with setter injection. Setting `spring.main.allow-circular-references=true` restores the old behaviour, which tries to break the cycle automatically.
