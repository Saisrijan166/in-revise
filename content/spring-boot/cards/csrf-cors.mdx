## What it is

These are two browser topics with similar names. CSRF (cross-site request forgery) is an attack: a page on another site makes the user's browser send a request to your app, and the browser attaches your app's cookies, so the request looks logged in. CORS (cross-origin resource sharing) is a permission system: browsers stop a page from reading responses from another origin (scheme, host and port), and from sending some requests at all, unless that server's headers allow it.

## Why it exists

Browsers send a site's cookies with every request to it, whoever started the request. Without CSRF protection, evil.example could submit a hidden form to `/payments` with your user's [session cookie](card:authentication-flow), and the payment would go through. Separately, the browser's same-origin rule blocks your own front end at `app.example.com` from calling `api.example.com`. CORS lets you allow exactly that origin, without turning the rule off for everyone.

## How it works

<Compare id="csrf-vs-cors" />

1. **CSRF:** Spring Security creates a random CSRF token for the user's session and puts it into your pages, as a hidden `_csrf` form field or a value JavaScript can read.
2. **CSRF:** on every unsafe request (POST, PUT, PATCH, DELETE), CsrfFilter compares the token sent in the `X-CSRF-TOKEN` header or `_csrf` field with the stored one.
3. **CSRF:** a forged request from another site carries the cookie but not the token, because that site cannot read your pages. CsrfFilter rejects it with 403.
4. **CORS:** before a non-simple cross-origin call, such as a JSON POST, the browser sends an OPTIONS preflight with the page's `Origin`. It carries no cookies.
5. **CORS:** with `http.cors()`, Spring Security answers the preflight from your CORS settings before any login check, and adds `Access-Control-Allow-Origin` when the origin is allowed.
6. **CORS:** if the headers allow the origin, the browser sends the real request and lets the page read the answer. If not, the page only sees an error.

## Example

The payment front end at `app.example.com` calls the API with its session cookie:

```java
@Bean
UrlBasedCorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST"));
    config.setAllowedHeaders(List.of("Content-Type", "X-XSRF-TOKEN"));
    config.setAllowCredentials(true);               // the page sends its session cookie
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/payments/**", config);
    return source;
}
// In the SecurityFilterChain bean:
http.cors(Customizer.withDefaults())                // answer preflights before login checks
    .csrf(csrf -> csrf.spa());                      // token in the XSRF-TOKEN cookie
```

What to notice:

- The origin is exact. With `setAllowCredentials(true)`, Spring rejects `"*"` in allowed origins, because browsers refuse it with cookies. Use `allowedOriginPatterns` if you need a wildcard.
- `http.cors(...)` puts CORS handling in front of the login checks. If Spring Security does not handle CORS, the preflight, which has no cookies, looks like an unknown caller and is rejected.
- `csrf.spa()` (added in Spring Security 7.0) stores the token in an `XSRF-TOKEN` cookie that JavaScript can read; the app sends it back in the `X-XSRF-TOKEN` header. Another site cannot read your cookies, so it cannot copy the token.

## Rules and defaults

- **CSRF on (Security 7.1):** checked for unsafe methods. GET, HEAD, OPTIONS and TRACE are not checked, so a GET must never change data.
- **Token storage:** in the HTTP session by default, read from the `X-CSRF-TOKEN` header or the `_csrf` parameter.
- **Logout:** with CSRF on, logout works only as a POST, so another site cannot log your users out.
- **Bearer tokens:** with `oauth2ResourceServer`, requests that carry a bearer token skip the CSRF check, because no browser adds that header by itself.
- **Disabling CSRF:** fine for an API that no browser calls with cookies or HTTP Basic. Prefer ignoring only specific endpoints over turning it off everywhere.
- **CORS:** off until you call `http.cors()` or define one `UrlBasedCorsConfigurationSource` bean. With no source, `cors()` reuses Spring MVC's settings, such as `@CrossOrigin`. With two or more source beans, Spring Security cannot choose one and configures none, so pass one with `cors.configurationSource(...)`.

## Common mistakes

- **"My API returns JSON, so CSRF does not apply."** What matters is how credentials travel. If a browser sends a cookie automatically, the endpoint needs CSRF protection.
- **"CORS keeps other programs away from my API."** Only browsers enforce CORS; curl and other servers ignore it. Authentication protects the API.

## Interview Qs

### Both are browser security problems. Why do we need both?

They solve different problems. CORS decides which other origins may call your API from a browser and read the answer. CSRF protection stops another site from tricking the browser into sending a request with your user's cookies. One allows chosen callers; the other blocks forged requests.

### When can you disable CSRF?

When no browser sends credentials automatically: an API used only by other services, or one that takes bearer tokens in a header. Cookie sessions and HTTP Basic used from a browser still need it.

### CORS still fails after adding @CrossOrigin. Why?

The preflight carries no cookies, so Spring Security rejects it before it reaches Spring MVC. Enable `http.cors()` so CORS is handled first; with no other source, it reuses the `@CrossOrigin` settings.
