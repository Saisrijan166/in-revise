## Why it exists

Browsers send a site's cookies with every request to it, even one started by another site: that makes CSRF possible. Browsers also block cross-origin calls unless the server agrees: CORS is how it agrees.

## How it works

<Compare id="csrf-vs-cors" />

- Turn on CORS in Spring Security with `http.cors(...)`, so preflights are answered before login checks.
- Disabling CORS does not open your API: the browser still blocks other origins.

## Example

```java
@Bean
UrlBasedCorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
```

## Interview Qs

### Both are browser security problems. Why do we need both?

They solve different problems. CORS decides which other origins may call your API from a browser. CSRF protection stops another site from tricking the browser into sending a request with your user's cookies.

### When can you disable CSRF?

When no browser sends credentials automatically: an API used only by other services, or one that takes bearer tokens in a header. Cookie sessions and HTTP Basic used from a browser still need it.

### CORS still fails after adding @CrossOrigin. Why?

The preflight carries no cookies, so Spring Security rejects it before it reaches Spring MVC. Enable `http.cors()` so CORS runs first; with no other source it reuses Spring MVC's CORS settings.
