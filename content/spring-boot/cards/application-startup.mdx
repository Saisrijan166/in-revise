## Why it exists

`main` only calls `SpringApplication.run`, yet the app ends up with a configured context, a running server and your startup code done. Knowing the order tells you where to put startup work and why startup fails.

## How it works

<Steps label="SpringApplication.run(App.class, args)">
<Step title="Pick the context type">
Servlet if Spring MVC is on the classpath, reactive if only WebFlux is, otherwise a plain context.
</Step>
<Step title="Prepare the Environment">
Command-line arguments, properties and profiles are loaded. Event: ApplicationEnvironmentPreparedEvent.
</Step>
<Step title="Create the context">
Your main class is loaded as the primary source. Event: ApplicationPreparedEvent.
</Step>
<Step title="Refresh">
Scanned components, then auto-configurations, become bean definitions. Every singleton is created and a web app starts its server. Event: ApplicationStartedEvent.
</Step>
<Step title="Call runners, then ready">
CommandLineRunner and ApplicationRunner beans run. Event: ApplicationReadyEvent; the app now takes traffic.
</Step>
</Steps>

- If startup fails, a [failure analyser](card:failure-analyzer) prints the problem and a fix. Event: ApplicationFailedEvent.
- Early events fire before the context exists, so listen to them with `SpringApplication.addListeners(...)`, not a `@Bean`.

## Example

```java
@Component
class SeedData implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        // java -jar shop.jar --seed=demo
        if (args.containsOption("seed")) {
            List<String> sets = args.getOptionValues("seed");   // [demo]
            // load the demo rows
        }
    }
}
```

## Interview Qs

### How does a Spring Boot application start?

`main` calls `SpringApplication.run`. It picks the context type from the classpath, prepares the Environment, creates the context and refreshes it (components and auto-configurations become beans, the server starts), calls the runners and publishes ApplicationReadyEvent.

### CommandLineRunner vs ApplicationRunner?

Both run once, after the context is refreshed and before the app takes traffic. CommandLineRunner gets the raw `String...` arguments; ApplicationRunner gets `ApplicationArguments` with parsed `--name=value` options. Order several with `@Order`.

### Can you build a non-web Spring Boot application?

Yes. Leave web dependencies off the classpath, or set `spring.main.web-application-type=none`. Put the work in a CommandLineRunner bean.

### Startup is slow. What can you do?

Measure first: record startup steps with `BufferingApplicationStartup` and read `/actuator/startup`. Then remove what you do not need (`--debug` shows what was auto-configured), or enable lazy initialisation, which moves bean creation, and its errors, to first use.
