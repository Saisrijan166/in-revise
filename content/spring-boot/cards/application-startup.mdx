## Why it exists

`main` only calls `SpringApplication.run`, yet you end up with a running app. Knowing the order tells you where to put startup work and why startup fails.

## How it works

<Steps label="SpringApplication.run(App.class, args)">
<Step title="Pick the context type">
From the classpath: servlet, reactive or plain.
</Step>
<Step title="Prepare the Environment">
Arguments, properties and profiles are loaded.
</Step>
<Step title="Refresh the context">
Scanning and auto-configuration give bean definitions; singletons are created; the web server starts.
</Step>
<Step title="Call the runners">
Every CommandLineRunner and ApplicationRunner bean runs once.
</Step>
<Step title="Ready">
ApplicationReadyEvent is published; the app takes traffic.
</Step>
</Steps>

- This is the interview-level order; the real code has more events in between.
- Order several runners with `@Order`.

## Example

```java
@Component
class SeedData implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {
        // java -jar shop.jar --seed=demo
        if (args.containsOption("seed")) {
            // load the demo rows
        }
    }
}
```

## Interview Qs

### How does a Spring Boot application start?

`main` calls `SpringApplication.run`. It picks the context type, prepares the Environment, refreshes the context (beans are created, the server starts), calls the runners, then publishes ApplicationReadyEvent.

### CommandLineRunner vs ApplicationRunner?

Same timing: once, after the context is refreshed. CommandLineRunner gets raw `String...` arguments; ApplicationRunner gets `ApplicationArguments` with `--name=value` options parsed.

### How do you run code once the app is fully started?

Implement a runner, or listen for `ApplicationReadyEvent`, which comes after all runners.
