## What it is

The startup flow is what happens inside `SpringApplication.run(...)`, the one line in `main()`. In that call Boot reads your settings, builds all the [beans](card:ioc-container), starts the web server and finally reports that the app is ready. A **runner** is a bean that implements `CommandLineRunner` or `ApplicationRunner`; Boot calls its `run` method once, near the end of startup, so you can do app-wide work at a safe moment.

## Why it exists

`main()` has one line, yet you end up with a running server. When startup fails, or when you must do something "at startup", you need to know what is ready at each moment. Without that, people put startup work in `@PostConstruct`, where other parts of the app may not be set up yet. Runners give one clear hook: every bean exists, and the app does not yet report that it takes traffic.

## How it works

<Steps label="SpringApplication.run(PaymentApplication.class, args)">
<Step title="1. Pick the app type">
Spring MVC on the classpath: servlet app. Only WebFlux: reactive app. Neither: no web server.
</Step>
<Step title="2. Prepare the Environment">
Command-line arguments, environment variables, config files and active profiles are read.
</Step>
<Step title="3. Refresh the context">
Scanning and auto-configuration register beans; singletons are created and injected; the web server starts.
</Step>
<Step title="4. Call the runners">
Every CommandLineRunner and ApplicationRunner bean runs once, in @Order order.
</Step>
<Step title="5. Ready">
ApplicationReadyEvent is published, and the app reports that it accepts traffic.
</Step>
</Steps>

1. Boot looks at the classpath and decides which kind of application context to create.
2. It builds the Environment, the merged set of all settings, which you will see in [externalized configuration](card:externalized-configuration).
3. It refreshes the context: beans are created, `@PostConstruct` methods run bean by bean, and a web app starts its embedded server. Boot logs "Started PaymentApplication in … seconds".
4. It calls the runners on the main thread, one after another.
5. It publishes `ApplicationReadyEvent`. If anything failed on the way, it publishes `ApplicationFailedEvent` instead and a failure analyser prints the cause.

This is the interview-level order; the real code publishes a few more events in between.

## Example

One bean in the payment service shows all three moments. The app was started with `--seed=demo report.txt`:

```java
@Component
class DemoDataLoader implements ApplicationRunner {
    @PostConstruct
    void init() { System.out.println("1. @PostConstruct: this one bean is ready"); }

    @Override
    public void run(ApplicationArguments args) {
        System.out.println("2. Runner: seed = " + args.getOptionValues("seed"));
        System.out.println("   non-option args = " + args.getNonOptionArgs());
    }

    @EventListener(ApplicationReadyEvent.class)
    void ready() { System.out.println("3. ApplicationReadyEvent: open for traffic"); }
}
```

```text output
1. @PostConstruct: this one bean is ready
2. Runner: seed = [demo]
   non-option args = [report.txt]
3. ApplicationReadyEvent: open for traffic
```

What to notice:

- `@PostConstruct` printed first, while the context was still being built. In the full log, Boot's "Started PaymentApplication" line appears between lines 1 and 2.
- `ApplicationArguments` already split the arguments: `--seed=demo` is an option, `report.txt` is a non-option argument.
- If `run` threw an exception, startup would fail with "Application run failed" and line 3 would never print.

## Rules and defaults

- **When runners run:** once, just before `SpringApplication.run(...)` returns. Order several with `@Order` or the `Ordered` interface.
- **Readiness:** while runners run, the app's readiness state still refuses traffic; it switches to accepting traffic after `ApplicationReadyEvent`.
- **Same thread:** runners and event listeners run on the main thread by default. Keep them short, or hand long work to another thread.
- **Context type:** if both Spring MVC and WebFlux are on the classpath, Boot picks the servlet (MVC) app. `spring.main.web-application-type` overrides it.

## Not to be confused with

`@PostConstruct` sets up **one bean** right after its dependencies are injected. A runner does **app-wide** work after all beans exist. An `ApplicationReadyEvent` listener runs after the runners, when the app already counts as ready. Rule: one bean = `@PostConstruct`; before traffic = runner; after ready = `ApplicationReadyEvent`.

## Interview Qs

### What happens when a Spring Boot application starts?

`main` calls `SpringApplication.run`. Boot picks the app type from the classpath, prepares the Environment, then refreshes the context: beans are created and the embedded server starts. Next it calls the runners, and finally publishes `ApplicationReadyEvent`, after which the app accepts traffic.

### How do you run code once the application has started?

Implement `ApplicationRunner` or `CommandLineRunner` for work that must finish before traffic arrives. For work after the app is ready, listen for `ApplicationReadyEvent`. Avoid `@PostConstruct` for app-wide work, because other beans and the server may not be ready yet.

### Why might a Spring Boot app fail to start, and how do you find out?

Common causes are a port already in use, a missing bean, or a wrong property. Boot's failure analysers print a description and an action, such as "Port 8080 was already in use". If that is not enough, start with `--debug` to see the condition evaluation report.
