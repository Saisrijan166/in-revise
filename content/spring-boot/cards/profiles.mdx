## What it is

A profile is a name, such as `dev`, `test` or `prod`, that you switch on when the app starts. It changes two things. Settings: `application-prod.properties` is loaded on top of `application.properties`. [Beans](card:component-vs-bean): a class or `@Bean` method marked `@Profile("prod")` is created only when `prod` is on. Profiles build on [externalized configuration](card:externalized-configuration): they decide which extra files and beans join the app.

## Why it exists

The payment service talks to a real fraud-check API in production, but on a laptop there is no API to call, and the database URL differs too. Without profiles you would keep separate copies of the config, or write `if (env.equals("prod"))` in the code. Profiles keep every environment's setup in one codebase, side by side, and the right set is chosen at startup by one setting.

## How it works

1. At startup, Boot reads `spring.profiles.active` from the Environment, wherever it was set.
2. It loads `application.properties`, then the file of each active profile, such as `application-prod.properties`. Where both set a key, the profile file wins.
3. While registering beans, it checks every `@Profile`. A bean whose condition does not match is skipped; a bean with no `@Profile` is always created.
4. If no profile was set, the `default` profile is on, and Boot logs `No active profile set, falling back to 1 default profile: "default"`.

## Example

The payment service calls a fraud-check API. On a laptop it uses a fake that approves every payment:

```properties
# application-prod.properties: loaded only when prod is on
app.fraud-check.url=https://fraud.example.com
spring.datasource.url=jdbc:postgresql://prod-db:5432/payments
```

```java
@Configuration
public class FraudCheckConfig {

    @Bean
    @Profile("dev")
    FraudCheckClient fakeFraudCheck() { return payment -> true; }

    @Bean
    @Profile("!dev")
    FraudCheckClient httpFraudCheck(@Value("${app.fraud-check.url}") String url) {
        return new HttpFraudCheckClient(url);
    }
}
```

What to notice:

- With `dev` on, only `fakeFraudCheck` exists; with any other profile, or none, only `httpFraudCheck` exists. Exactly one `FraudCheckClient` bean is created either way.
- The production URL lives only in `application-prod.properties`. Start without `prod` and `${app.fraud-check.url}` must come from somewhere else, or startup fails.
- No code changes between environments: `SPRING_PROFILES_ACTIVE=prod java -jar payment.jar` picks the production set.

## Rules and defaults

- **No profile set:** the `default` profile is on, so `application-default.properties` and `@Profile("default")` beans apply. Rename it with `spring.profiles.default`.
- **Several profiles:** `spring.profiles.active=prod,live` turns on both; for the same key, the profile listed last wins.
- **Adding instead of replacing:** `spring.profiles.include` always adds its profiles.
- **Groups:** `spring.profiles.group.production=proddb,prodmq` turns on three profiles with one name, see [profile groups](card:profile-groups).
- **Not allowed:** `spring.profiles.active`, `include` and `group` inside a profile-specific file such as `application-prod.properties`; Boot refuses them.
- **Expressions:** `@Profile` accepts `!`, `&` and `|`, such as `@Profile("prod & eu")`.

## Interview Qs

### Why do we need profiles?

Environments need different settings and sometimes different beans, such as a fake fraud check on a laptop and the real API in production. Profiles keep every environment's setup in one codebase and choose the right set at startup, so the same build moves from test to production unchanged.

### How do you activate a profile?

Set `spring.profiles.active=prod` in a file, `SPRING_PROFILES_ACTIVE=prod` as an environment variable, or `--spring.profiles.active=prod` on the command line. A higher source replaces the list from a lower one; `spring.profiles.include` adds profiles instead.

### What happens if no profile is active?

The `default` profile is on. `application-default.properties` and `@Profile("default")` beans are used, and Boot logs that it fell back to the default profile. As soon as any profile is active, `default` no longer applies.
