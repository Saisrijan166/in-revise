## Why it exists

Dev, test and prod need different settings and sometimes different beans, such as a fake payment gateway in dev. Profiles keep all of them in one codebase and pick the right set at start-up.

## How it works

<Mermaid
  alt="Profile activation. Setting SPRING_PROFILES_ACTIVE to prod does two things. Files: application.properties loads, then application-prod.properties, whose values win. Beans: beans with @Profile prod or with no @Profile are created; beans with @Profile dev are skipped."
  chart={`flowchart LR
  A(["SPRING_PROFILES_ACTIVE=prod"]) --> F1["application.properties"]
  F1 --> F2["application-prod.properties: its values win"]
  A --> B1["@Profile('prod') and plain beans: created"]
  A --> B2["@Profile('dev') beans: skipped"]`}
/>

- No profile active: the `default` profile is on, so `application-default.properties` applies.
- `spring.profiles.active`, `include` and `group` are refused inside profile-specific files.
- A [profile group](card:profile-groups) turns on several profiles with one name.

## Example

```java
@Configuration
public class PaymentConfig {

    @Bean
    @Profile("dev")
    PaymentGateway fakeGateway() { return new FakeGateway(); }

    @Bean
    @Profile("!dev")
    PaymentGateway realGateway() { return new CardGateway(); }
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Active profiles | none | Spring Boot 4.1 |
| Fallback when none is active | `default` (rename with `spring.profiles.default`) | Spring Boot 4.1 |
| Two active profiles set one key | the last one listed wins | Spring Boot 4.1 |

## Interview Qs

### Why do we need profiles?

Environments need different settings and sometimes different beans. Profiles keep dev, test and prod setup in one codebase and choose the right set at start-up, so the same build moves from test to production unchanged.

### How do you activate a profile?

`spring.profiles.active=prod` in a file, `SPRING_PROFILES_ACTIVE=prod` as an env var, or `--spring.profiles.active=prod` on the command line. A higher source replaces a lower one; `spring.profiles.include` adds instead.

### What happens if no profile is active?

The `default` profile is on, so `application-default.properties` and `@Profile("default")` beans load. Once any profile is active, `default` no longer applies.
