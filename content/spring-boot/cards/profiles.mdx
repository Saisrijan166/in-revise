## Why it exists

Dev, test and prod need different settings and sometimes different beans, such as a local file store in dev and a cloud store in prod. Profiles keep all of them in one codebase and pick the right set at start-up.

## How it works

<Mermaid
  alt="Profile activation flow. Setting SPRING_PROFILES_ACTIVE to prod does two things. Files: application.properties loads, then application-prod.properties, whose values win. Beans: beans with @Profile prod or with no @Profile are registered, and beans with @Profile dev are skipped."
  chart={`flowchart LR
  A(["SPRING_PROFILES_ACTIVE=prod"]) --> F1["application.properties"]
  F1 --> F2["application-prod.properties: its values win"]
  A --> B1["@Profile('prod') and plain beans: registered"]
  A --> B2["@Profile('dev') beans: skipped"]`}
/>

- No profile active: the `default` profile is on, so `application-default.properties` and `@Profile("default")` beans apply.
- One file can hold all of them: split it with `#---` (or `---` in YAML) and mark a part with [`spring.config.activate.on-profile`](card:activate-on-profile).
- [Profile groups](card:profile-groups) turn on several profiles with one name; see [active vs include vs group](compare:profiles-active-include-group).

## Example

```java
@Configuration
public class StorageConfig {

    @Bean
    @Profile("dev")
    FileStore localStore() { return new LocalFileStore(); }

    @Bean
    @Profile("!dev")
    FileStore cloudStore() { return new S3FileStore(); }
}
```

```properties
app.store.bucket=demo
#---
spring.config.activate.on-profile=prod
app.store.bucket=orders-prod
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Active profiles | none | Spring Boot 4.1 |
| Fallback when none is active | `default` (rename with `spring.profiles.default`) | Spring Boot 4.1, Spring Framework 7.0 |
| Two active profiles set one key | the last one listed wins | Spring Boot 4.1 |

## Interview Qs

### Why do we need profiles?

Environments need different settings and sometimes different beans. Profiles keep dev, test and prod setup in one codebase and choose the right set at start-up, so the same build is promoted from test to production without changes.

### How do you activate a profile?

`spring.profiles.active=prod` in a file, `-Dspring.profiles.active=prod`, `SPRING_PROFILES_ACTIVE=prod`, or `--spring.profiles.active=prod`. A higher source replaces a lower one. In a test, use `@ActiveProfiles("test")`; in code, `SpringApplication.setAdditionalProfiles(...)` before the app runs.

### What happens if no profile is active?

The `default` profile is on, so `application-default.properties` and beans marked `@Profile("default")` load. As soon as any profile is active, `default` no longer applies. `spring.profiles.default` changes its name.

### Two active profiles set the same key. Which wins?

The last one listed. With `spring.profiles.active=prod,live`, values in `application-live.properties` override those in `application-prod.properties`. Both override plain `application.properties`.
