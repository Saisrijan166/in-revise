## Why it exists

A thread waiting on a database or remote call does nothing but still costs memory. With thousands of slow requests, thread-per-request servers run out. WebFlux avoids waiting threads; MVC keeps code simple.

## How it works

<Compare id="mvc-vs-webflux-vs-virtual-threads" />

- Never block inside WebFlux; if you must, move the call to another thread with the `publishOn` operator, or choose MVC.
- WebFlux supports annotated controllers, like MVC, and functional endpoints.

## Example

```java
@RestController
class QuoteController {
    private final WebClient web;
    QuoteController(WebClient.Builder b) { web = b.baseUrl("https://quotes.example.com").build(); }

    @GetMapping("/quotes/{id}")
    Mono<Quote> one(@PathVariable String id) {              // 0..1 value; no thread waits
        return web.get().uri("/{id}", id).retrieve().bodyToMono(Quote.class);
    }
}
```

## Interview Qs

### If Spring MVC already handles HTTP, why do we need WebFlux?

It is a different execution model: non-blocking, on a small fixed set of threads, with back pressure. It helps with streaming and many slow I/O calls. A working MVC app has no need to switch.

### What are Mono and Flux?

Reactor's publisher types. Mono emits zero or one value, like a single response; Flux emits zero to many, like a list or a stream. Both come from Project Reactor, the library WebFlux is built on.

### Does using WebFlux make everything non-blocking?

No. A blocking JDBC or HTTP call on the reactive path still blocks a thread, and that thread serves many requests. Use non-blocking drivers end to end, or stay with MVC.
