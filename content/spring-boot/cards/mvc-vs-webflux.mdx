## Why it exists

A thread that waits for a database or a remote call does nothing but still costs memory. With thousands of slow requests, a thread-per-request server runs out of threads. WebFlux avoids waiting threads; MVC keeps simple code.

## How it works

<Compare id="mvc-vs-virtual-threads-vs-webflux" />

- WebFlux offers two styles: annotated controllers, like MVC, and functional endpoints (router functions).
- Never block an event-loop thread. If you must call a blocking API, wrap it: `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`.
- Boot runs WebFlux on Reactor Netty by default; Tomcat or Jetty also work.

## Example

```java
@RestController
class QuoteController {
    private final WebClient web;
    QuoteController(WebClient.Builder builder) { web = builder.baseUrl("https://quotes.example.com").build(); }

    @GetMapping("/quotes/{id}")
    Mono<Quote> one(@PathVariable String id) {                 // 0..1 value; no thread waits
        return web.get().uri("/{id}", id).retrieve().bodyToMono(Quote.class);
    }

    @GetMapping(path = "/quotes", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<Quote> stream() {                                      // 0..N values, streamed
        return web.get().uri("/stream").retrieve().bodyToFlux(Quote.class);
    }
}
```

| What | Default | Where |

| MVC server and worker threads | Tomcat 11, at most 200 | Spring Boot 4.1 (`server.tomcat.threads.max`) |
| WebFlux server | Reactor Netty 1.3 | Spring Boot 4.1 |
| Both web starters on the classpath | Spring MVC is configured | Spring Boot 4.1 |

## Interview Qs

### Spring MVC vs WebFlux: when do you choose which?

MVC for most apps, especially with blocking libraries such as JPA or JDBC: simple code and easy debugging. WebFlux when you need streaming, back pressure, or very many slow concurrent connections with a non-blocking stack end to end.

### What are Mono and Flux?

Reactor's publisher types. Mono emits zero or one value, like a single response; Flux emits zero to many, like a list or a stream. Nothing runs until something subscribes, and in WebFlux the framework subscribes for you.

### What happens if you call a blocking API inside WebFlux?

It holds one of the few event-loop threads, so other requests on that thread stall. Avoid it, or move the call to another thread with subscribeOn(Schedulers.boundedElastic()). If most calls block, use MVC instead.
