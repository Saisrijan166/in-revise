## What it is

Spring has two web stacks. Spring MVC, which every earlier concept used, runs on the Servlet API: each request gets one thread, and the code may block, which means the thread waits while the database or another service answers. WebFlux is the reactive stack: a few threads serve all requests, and code must never block. Instead, a method returns a `Mono` or `Flux`, a promise of a result that arrives later.

## Why it exists

A thread that waits for a database or a remote call does nothing, but it still holds memory. Tomcat's pool has 200 request threads by default, so 200 slow calls at once fill it, and request 201 queues. WebFlux avoids waiting threads altogether: while a call is in flight, the thread serves other requests. The price is a different, harder style of code. Virtual threads, from Java 21, are a third answer: MVC code on threads so cheap that waiting no longer matters.

## How it works

<Compare id="mvc-vs-webflux-vs-virtual-threads" />

Follow one call to the fraud service, which takes 300 ms:

1. **Spring MVC:** a pool thread runs the controller, calls the fraud service and waits 300 ms, doing nothing else. Then it writes the response and returns to the pool.
2. **WebFlux:** an event-loop thread starts the call and immediately moves on to other requests. When the answer arrives, a thread picks the work up again and writes the response.
3. **MVC on virtual threads:** the code is the same as in step 1, but the waiting thread is a virtual thread. While it waits, the JVM frees the real operating-system thread underneath for other work.

So the choice is about waiting: MVC waits on a thread, WebFlux never waits, and virtual threads make waiting cheap.

## Example

The fraud check again, now in a WebFlux controller with WebClient:

```java
@RestController
class FraudStatusController {
    private final WebClient web;
    FraudStatusController(WebClient.Builder builder) {
        this.web = builder.baseUrl("https://fraud.internal.example").build();
    }
    @GetMapping("/fraud-checks/{id}")
    Mono<FraudResult> one(@PathVariable String id) {   // returns at once; the value comes later
        return web.get().uri("/checks/{id}", id)
                .retrieve().bodyToMono(FraudResult.class);
    }
}
```

What to notice:

- The annotations are the same as in Spring MVC. Only the return type changes, to `Mono<FraudResult>`.
- The method returns before the fraud service answers. WebFlux subscribes to the `Mono` and writes the JSON when the value arrives.
- Add a blocking call inside, such as a JPA query, and an event-loop thread stops for its whole duration, slowing every request that shares it.

## Rules and defaults

- **Default server:** `spring-boot-starter-webflux` uses Reactor Netty; `spring-boot-starter-webmvc` uses Tomcat.
- **Both on the classpath:** Spring Boot configures Spring MVC. That lets an MVC app use WebClient without becoming a WebFlux app.
- **Virtual threads:** `spring.threads.virtual.enabled=true` needs Java 21 or later. Then `server.tomcat.threads.max` has no effect.
- **Blocking in WebFlux:** if you must call a blocking library, move it to another thread with Reactor's `publishOn` operator, or choose MVC.

## Interview Qs

### If Spring MVC already handles HTTP, why do we need WebFlux?

It is a different execution model: non-blocking, on a small fixed set of threads, with back pressure, which lets a slow consumer tell a fast producer to slow down. It helps with streaming and very many slow I/O calls. The Spring docs say a working MVC app has no need to switch.

### What are Mono and Flux?

They are Project Reactor's publisher types, the building blocks of WebFlux. A Mono emits zero or one value, like a single response. A Flux emits zero to many values, like a list or a live stream. Nothing runs until something subscribes to them.

### Does using WebFlux make the whole app non-blocking?

No. A blocking JDBC or HTTP call on the reactive path still blocks a thread, and in WebFlux that thread serves many requests. You need non-blocking drivers end to end, such as R2DBC for databases, or you should stay with Spring MVC.
