## What it is

The bean lifecycle is the fixed series of steps the [container](card:ioc-container) takes with each bean: create the object, inject its dependencies, run its setup method, hand it out, and finally run its cleanup method. You hook into it with two annotations: `@PostConstruct` marks the setup method and `@PreDestroy` marks the cleanup method. Lazy initialisation changes only when the first step happens: on first use instead of at startup.

## Why it exists

Some beans must do work once they are complete, such as opening a connection to the fraud-check service, and must undo it before the app stops, such as closing that connection. The constructor is too early when setter or field dependencies are still missing, and plain Java has no reliable "the app is stopping" method on your object. Lifecycle callbacks give fixed places for both.

## How it works

  chart={`flowchart LR

  B --> C["3. @PostConstruct"]
  C --> D[4. In use]
  D -- context closes --> E["5. @PreDestroy"]`}
/>

1. **Create:** Spring calls the constructor and passes the constructor dependencies.
2. **Inject:** it sets any setter or field dependencies.
3. **Initialise:** it runs the `@PostConstruct` method. After this step Spring may also wrap the bean in a proxy, a wrapper object that adds behaviour, which is how features like `@Transactional` work; you will see this in [Proxies and Self-Invocation](card:aop-proxies).
4. **In use:** the bean serves calls until the app stops.
5. **Destroy:** when the context closes, Spring runs the `@PreDestroy` method. Spring Boot registers a JVM shutdown hook, so a normal shutdown closes the context for you.

So `@PostConstruct` runs once, after every dependency is set, and `@PreDestroy` runs once, when the container closes.

## Example

`FraudCheckClient` opens its connection after creation and closes it on shutdown.

```java
@Component
class FraudCheckClient {
    FraudCheckClient() { System.out.println("1. constructor"); }
    @PostConstruct void connect() { System.out.println("2. @PostConstruct: open the connection"); }
    @PreDestroy void disconnect() { System.out.println("4. @PreDestroy: close the connection"); }
}

public class Main {
    public static void main(String[] args) {
        var context = new AnnotationConfigApplicationContext(FraudCheckClient.class);
        System.out.println("3. app is running");
        context.close();
    }
}
```

```text output
1. constructor
2. @PostConstruct: open the connection
3. app is running
4. @PreDestroy: close the connection
```

What to notice:

- `@PostConstruct` runs during startup, before "app is running". A slow method here makes the whole startup slow.
- `context.close()` triggers `@PreDestroy`. In a Boot app the shutdown hook makes this call for you on a normal stop.
- The annotations come from `jakarta.annotation`. Spring Framework 7.0 (Boot 4.0) ignores the old `javax.annotation` ones.
- Make `FraudCheckClient` a prototype and `@PreDestroy` would never run.

## Rules and defaults

- **Eager by default:** singletons are created at startup, so a wiring mistake stops startup at once.
- **`@Lazy`:** on a bean, or on a `@Configuration` class for all its beans, it delays creation to first use. A lazy bean that an eager bean needs is still created at startup.
- **Global switch:** `spring.main.lazy-initialization=true` makes every bean lazy; it is false by default (Spring Boot 4.1). `@Lazy(false)` keeps one bean eager.
- **Other init and destroy hooks:** if a bean uses several, the order is `@PostConstruct`, then `InitializingBean.afterPropertiesSet()`, then a `@Bean(initMethod = ...)`. Destroy follows the same pattern: `@PreDestroy`, `DisposableBean.destroy()`, then `destroyMethod`.
- **`@Bean` objects with `close()`:** a public `close` or `shutdown` method on an object from a `@Bean` method is called at shutdown automatically.

## Common mistakes

- **"Making every bean lazy is a free speed-up."** Startup gets faster, but a broken bean now fails on its first use, perhaps hours later in production, instead of at startup.
- **"I can use the constructor for everything."** Setter and field dependencies are still null inside the constructor. Setup that needs them belongs in `@PostConstruct`.

## Interview Qs

### Explain the Spring bean lifecycle.

Spring instantiates the bean, injects its dependencies, runs init callbacks such as `@PostConstruct`, and may wrap it in a proxy. The bean is then used. When the context closes, Spring runs destroy callbacks such as `@PreDestroy`.

### Eager or lazy: which is the default, and why?

Eager: the `ApplicationContext` creates all singletons at startup, so configuration mistakes fail early, not on a user's request. `@Lazy` or `spring.main.lazy-initialization` delays creation to first use, which speeds up startup but finds errors later.

### Why is my @PreDestroy method not called?

Either the bean is a prototype, whose destroy callbacks Spring never calls, or the context was never closed, for example because the process was killed with `kill -9`. With Boot 4, also check that you import `jakarta.annotation.PreDestroy`, not the old `javax` one.
