## Why it exists

Some beans need setup after their dependencies arrive, such as opening a pool, and cleanup before the app stops. Lifecycle callbacks give fixed places for both, and let Spring add proxies.

## How it works

<Mermaid

- Prefer `@PostConstruct` and `@PreDestroy`; the Spring interfaces tie your class to Spring.
- Keep init callbacks small. For heavy start-up work, listen for `ContextRefreshedEvent` or use `SmartInitializingSingleton`.
- A `BeanFactoryPostProcessor` runs earlier still: it edits bean definitions before any regular bean exists.

## Example

```java
import jakarta.annotation.PostConstruct;      // jakarta, not javax
import jakarta.annotation.PreDestroy;

@Component
public class FileArchiver {
    private final ArchiveProperties props;
    private ExecutorService pool;

    FileArchiver(ArchiveProperties props) { this.props = props; }

    @PostConstruct                            // dependencies are ready here
    void start() { pool = Executors.newFixedThreadPool(props.threads()); }
    @PreDestroy                               // runs when the context closes
    void stop() { pool.shutdown(); }
}
```

## Interview Qs

### Explain the Spring bean lifecycle.

Instantiate, inject dependencies, call Aware methods, run BeanPostProcessors before init, run the init callbacks, run BeanPostProcessors after init, where AOP proxies are made, use the bean, then run the destroy callbacks when the context closes.

### BeanPostProcessor vs BeanFactoryPostProcessor?

A BeanFactoryPostProcessor changes bean definitions before any regular bean is created, for example filling `${...}` placeholders. A BeanPostProcessor works on each bean instance around its init callbacks, for example to inject @Autowired fields or wrap the bean in a proxy.

### Why is @PreDestroy not called on my bean?

Either the bean is a prototype, whose destroy callbacks Spring never calls, or the context was not closed. Spring Boot registers a JVM shutdown hook by default, so a normal shutdown closes the context.

### Which init callback should you use?

@PostConstruct, with @PreDestroy for cleanup; the Spring docs call them best practice. InitializingBean and DisposableBean work but tie the class to Spring. initMethod and destroyMethod on @Bean suit library classes you cannot annotate.
