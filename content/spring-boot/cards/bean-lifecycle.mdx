## Why it exists

Some beans need setup after their dependencies arrive, such as starting a thread pool, and cleanup before the app stops. Lifecycle callbacks give fixed places for both.

## How it works

<Steps label="One singleton bean">
<Step title="Instantiate">
The constructor runs; constructor dependencies are passed in.
</Step>
<Step title="Inject">
Setter and field dependencies are set.
</Step>
<Step title="Initialise">
`@PostConstruct` runs. AOP proxies are added around here.
</Step>
<Step title="In use">
The bean serves calls until the app stops.
</Step>
<Step title="Destroy">
The context closes and `@PreDestroy` runs. Spring Boot closes it on JVM shutdown.
</Step>
</Steps>

- Making every bean lazy speeds up startup but finds wiring errors only on first use.

## Example

```java
@Component
public class FileArchiver {
    private final ExecutorService pool = Executors.newFixedThreadPool(2);

    @PostConstruct   // jakarta.annotation.PostConstruct
    void start() { pool.submit(this::warmUp); }

    @PreDestroy      // runs when the context closes
    void stop() { pool.shutdown(); }

    void warmUp() { }
}
```

## Interview Qs

### Explain the Spring bean lifecycle.

Spring instantiates the bean, injects its dependencies, runs init callbacks such as @PostConstruct, then hands it out. When the context closes, it runs destroy callbacks such as @PreDestroy.

### Eager or lazy: which is the default, and why?

Eager: the ApplicationContext creates all singletons at startup, so configuration mistakes fail early. @Lazy or spring.main.lazy-initialization delays creation to first use, at the cost of finding errors later.

### Why is my @PreDestroy method not called?

Either the bean is a prototype, whose destroy callbacks Spring never calls, or the context was not closed, for example the process was killed.
