## Why it exists

Collections load lazily to save work. But reading a lazy association for each item in a list quietly runs one extra query per item.

## How it works

- Returning an entity from a controller lets the JSON serialiser touch lazy fields; return a DTO instead.
- With `spring.jpa.open-in-view=false`, lazy access outside the service fails fast with LazyInitializationException.

## Example

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    @Query("select o from Order o join fetch o.customer")
    List<Order> findAllWithCustomer();               // 1 query

    @EntityGraph(attributePaths = "customer")
    List<Order> findByStatus(String status);         // 1 query
}
```

```properties
spring.jpa.open-in-view=false
spring.jpa.properties.hibernate.default_batch_fetch_size=16
```

## Interview Qs

### What is the N+1 problem, and how do you fix it?

One query loads N parents, then a lazy association runs one query per parent. Fetch per use case with JOIN FETCH or @EntityGraph; batch fetching only reduces the count.

### If EAGER loads the data, why use LAZY?

EAGER loads the association whenever the entity loads, even unused, and JPQL queries still add a select per row. LAZY loads only on use; you then fetch eagerly per query where needed.

### Why do you get LazyInitializationException?

A lazy association is read after its persistence context closed, often by a controller or the JSON serialiser. Load the data inside the transactional service, or return a DTO.
