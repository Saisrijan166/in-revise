## What it is

Lazy loading means a linked entity, such as a payment's customer, is not read when the payment loads. Hibernate puts a stand-in object, called a proxy, in the `customer` field and runs a query the first time you use it. The N+1 problem is the cost of this in a loop: 1 query loads N payments, then the first use of each payment's customer runs 1 more query, N more in total.

## Why it exists

If every link loaded at once, one payment would pull in its customer, the customer's other payments, and so on, even for a screen that shows only amounts. Lazy loading avoids that by loading on demand. The price is hidden queries. A page that lists 100 payments with customer names can quietly run 101 queries: fast on a laptop with 10 rows, slow in production. Knowing the pattern lets you load exactly what each screen needs in one query.

## How it works

1. `findByStatus("PAID")` runs one SELECT on the payment table. Each `customer` field holds a proxy whose data is not loaded yet.
2. The loop calls `getCustomer().getName()`. The proxy has no name yet, so Hibernate runs a SELECT for that customer.
3. This repeats for every payment. A customer already loaded in this persistence context is reused, so the extra queries are one per distinct customer.
4. The fix is to tell JPA up front. `JOIN FETCH` in JPQL, or `@EntityGraph` on the repository method, makes the first SELECT join the customer table, and the loop runs no more queries.
5. If a proxy is first used after the persistence context closed, Hibernate cannot query any more and throws `LazyInitializationException`.

## Example

This service method looks harmless, but it runs 1 + N queries:

```java
@Transactional(readOnly = true)
public List<String> customerNames() {
    List<Payment> paid = payments.findByStatus("PAID");       // 1 query: N payments
    return paid.stream()
            .map(p -> p.getCustomer().getName())            // 1 more query per customer
            .toList();
}
```

The fix is in the repository, chosen per query:

```java
public interface PaymentRepository extends JpaRepository<Payment, Long> {
    @EntityGraph(attributePaths = "customer")
    List<Payment> findByStatus(String status);                 // payments and customers: 1 query

    @Query("select p from Payment p join fetch p.customer where p.amount > :min")
    List<Payment> findLargeWithCustomer(@Param("min") BigDecimal min);
}
```

What to notice:

- `@EntityGraph` keeps the derived query and adds a join for `customer`. `JOIN FETCH` does the same inside your own JPQL.
- The mapping stays `LAZY`, so other screens that never show customers stay cheap.
- With `@EntityGraph` added, `customerNames()` runs one query with the same code, because every customer is already loaded.

## Rules and defaults

- **open-in-view (Boot 4.1):** `spring.jpa.open-in-view` is on by default in web apps, and Boot logs a warning at startup until you set it. It keeps the `EntityManager` open for the whole request, so lazy loads work in controllers and during JSON writing, out of sight of your service.
- **Turning it off:** with `spring.jpa.open-in-view=false`, lazy access outside the transaction fails at once with `LazyInitializationException`, which shows you where data is missing.
- **Batch fetching:** `spring.jpa.properties.hibernate.default_batch_fetch_size=16` loads up to 16 waiting proxies with one query (an IN list, or an array on PostgreSQL). It cuts 100 extra queries to about 7, not to zero.

## Not to be confused with

The fetch type, LAZY or EAGER, is set on the mapping and decides when a link loads in every query. `JOIN FETCH` and `@EntityGraph` are set on one query and load the link for that query only. Rule: mapping = the default for all queries; fetch join = what this use case needs.

## Common mistakes

- **"Turn on open-in-view to fix LazyInitializationException."** It hides the error by keeping the `EntityManager` open, but the lazy queries still run, now while the JSON is written, often as N+1. Load what you need in the service and return a [DTO](card:dto).

## Interview Qs

### What is the N+1 problem, and how do you fix it?

One query loads N parents, then reading a lazy association runs one query per parent. Fix it per use case: JOIN FETCH in JPQL or @EntityGraph on the repository method loads parents and children in one query. Batch fetching only reduces the number of queries.

### If EAGER loads the data, why use LAZY?

EAGER loads the association every time the entity loads, even when nobody uses it, and in JPQL queries it still adds a select per row. LAZY loads only on use. You then load eagerly per query, with JOIN FETCH or @EntityGraph, where a use case needs the data.

### Why do you get LazyInitializationException?

A lazy association is read after its persistence context closed, often in a controller or while Jackson writes the JSON. Load the data inside the transactional service method, with a fetch join if needed, and return a DTO instead of the entity.
