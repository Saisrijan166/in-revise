## What it is

An API gateway is the single entry point that sits in front of all your services. Clients call only the gateway, and it forwards each request to the right service. Spring Cloud Gateway is Spring's gateway, built on Spring Boot. You describe **routes** in configuration: each route says which requests it accepts (its **predicates**), what to change on the way (its **filters**) and where to send them (its URI).

## Why it exists

Without a gateway, the mobile app must know the address of the payment service, the order service and every other one, and each service repeats the same work: checking tokens, limiting request rates, adding headers. Changing a service's address breaks clients. A gateway hides the services behind one address and does the shared work once, at the edge. It also finds instances through [service discovery](card:service-discovery-eureka).

1. A request arrives. The gateway checks each route's predicates; the first route whose predicates all match is chosen.
2. The route's filters run their "pre" part: for example, rate limiting and rewriting the path.
3. The gateway forwards the request to the route's URI. With `lb://`, Spring Cloud LoadBalancer first picks a live instance from the discovery registry.
4. When the response comes back, the filters run their "post" part, such as adding a header.
5. The gateway returns the response to the client.

## Example

The gateway's `application.yml` sends `/api/payments/**` to the payment service:

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: payments
              uri: lb://payment-service
              predicates:
                - Path=/api/payments/**
              filters:
                - StripPrefix=1
```

What to notice:

- The predicate `Path=/api/payments/**` is the "if": only matching requests use this route.
- `StripPrefix=1` removes the first path part, so `/api/payments/42` reaches the service as `/payments/42`.
- `lb://payment-service` is a service name, resolved by LoadBalancer. With `http://host:port` instead, every request would go to one fixed address.

## Rules and defaults

- **Two variants:** Gateway Server WebFlux runs on Netty and cannot run in a servlet container or as a war. Gateway Server Web MVC runs on the servlet stack.
- **Property prefix (Gateway 5.0):** WebFlux routes live under `spring.cloud.gateway.server.webflux.routes`.
- **Route vs global filters:** a route filter applies to one route; a global filter applies to every route.
- **No instance for `lb://`:** the gateway answers 503 by default.
- **Rate limiting:** `RequestRateLimiter` with the Redis rate limiter keeps a token bucket per key, by default the user's principal name. Over the limit it returns 429; a request with no key is denied.

## Not to be confused with

A **predicate** is a yes or no question about the request: does the path, header or method match? A **filter** is an action on the request or response. Rule: predicates choose the route; filters change the traffic.

## Interview Qs

### What does an API gateway do?

It is the single entry point for clients. It routes each request to the right service, often found through discovery, and does shared work once, such as authentication checks, rate limiting, circuit breaking and adding headers. Clients see one address, and services can move behind it.

### Predicates vs filters?

A predicate is a condition on the request, such as `Path=/payments/**` or a header check; a route is chosen when all its predicates are true. A filter changes the request before it is forwarded, or the response after, for example removing a path prefix or adding a header.

### How do you rate limit in Spring Cloud Gateway?

Add the `RequestRateLimiter` filter with the Redis rate limiter. It keeps a token bucket per key, such as each user: `replenishRate` is the steady rate per second and `burstCapacity` the bucket size. Requests over the limit get 429 Too Many Requests.
