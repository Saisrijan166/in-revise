## What it is

Request mapping is how you tell Spring MVC which controller method handles which request. You put annotations such as `@GetMapping("/{id}")` on a method, and the HandlerMapping from the [request flow](card:dispatcher-servlet) matches incoming requests against them. Binding is the second half: annotations on the method's parameters tell Spring where in the request each value comes from, and Spring converts it to the Java type you declared.

## Why it exists

A request spreads its data over several places: the HTTP method, the path, the query string after `?`, the headers and the body. Without mapping you would read the raw request and parse each piece yourself, in every endpoint. With these annotations you declare what you need, and Spring finds the method, extracts each value, converts `"42"` to a `long`, and rejects bad input before your code runs.

1. At startup, Spring reads the mapping annotations of every controller and builds a table of method plus path.
2. A request arrives. The HandlerMapping finds the entry whose HTTP method and path pattern match, for example `POST /payments/{id}/refunds`.
3. For each parameter, Spring reads the value from the place its annotation names: the path, the query string, a header or the body.
4. It converts the value to the parameter's type. Path and query values are converted from text; a body is read by a message converter.
5. If a required value is missing or cannot be converted, Spring answers 400 and the method is not called.

## Example

The `PaymentController` with a filtered list and a refund endpoint:

```java
@RestController
@RequestMapping("/payments")                                   // shared prefix
class PaymentController {
    private final PaymentService service;
    PaymentController(PaymentService service) { this.service = service; }

    @GetMapping                                                 // GET /payments?status=PAID
    List<PaymentResponse> list(@RequestParam(defaultValue = "PENDING") PaymentStatus status) {
        return service.findByStatus(status);
    }
    @PostMapping("/{id}/refunds")                               // POST /payments/42/refunds
    PaymentResponse refund(@PathVariable long id, @RequestBody RefundRequest body) {
        return service.refund(id, body.amount());
    }
}
```

What to notice:

- `@RequestMapping("/payments")` on the class is added in front of every method's path, so the refund URL is `/payments/{id}/refunds`.
- `status` is an enum. Spring converts the text `PAID` for you; `?status=paid` or `?status=XYZ` gives 400 because no enum constant has that exact name.
- `defaultValue = "PENDING"` makes the parameter optional. Remove it and `GET /payments` with no `status` fails with 400.
- `@PathVariable long id` matches `{id}` by the parameter name. That works because Spring Boot's build setup compiles with the `-parameters` flag.

## Rules and defaults

- **Required by default:** `@RequestParam`, `@PathVariable` and `@RequestBody` are all required. Setting `defaultValue` on `@RequestParam` makes it optional.
- **Status codes Spring MVC sends for you:** wrong HTTP method gives 405, missing or unconvertible values and unreadable JSON give 400, and a body type the method does not accept (see `consumes`) gives 415.
- **Narrowing a mapping:** `consumes = "application/json"` matches only requests with that `Content-Type`; `produces` matches what the client accepts.
- **API versioning (new in Spring Framework 7 / Boot 4):** `@GetMapping(path = "/{id}", version = "2")` maps one path to several versions. You must also say where the version comes from, for example `spring.mvc.apiversion.use.header=X-Version`.

## Not to be confused with

`@PathVariable` reads a piece of the path and says which resource you mean. `@RequestParam` reads the query string and carries options such as filters and paging. `@RequestBody` reads the whole body and carries the data you send. Rule: path = which one, query = how to filter, body = the data.

## Interview Qs

### If @RequestMapping can map requests, why do we need @GetMapping?

@GetMapping is @RequestMapping fixed to GET, and the same holds for the other shortcuts. On a method, plain @RequestMapping without a method attribute matches every HTTP method, which is rarely what you want. So the shortcuts go on methods and @RequestMapping stays on the class for the shared path.

### Both read values from the URL: why have @PathVariable and @RequestParam?

They mean different things. A path variable identifies the resource, as in /payments/42. A request parameter changes how you read it: filtering, sorting or paging, as in /payments?status=PAID&page=2. Keeping them separate gives clean, predictable URLs.

### What happens if the JSON body is malformed?

The message converter cannot read it, so Spring raises HttpMessageNotReadableException and answers 400 Bad Request. Your controller method never runs. To change the error body, handle it in a global exception handler.
