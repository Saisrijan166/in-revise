## What it is

A transaction is a group of database steps that the database treats as one unit: either all of them are saved (commit) or none of them are (rollback). `@Transactional` is the annotation that tells Spring "run this method as one transaction". You write no begin or commit code. A [proxy](card:aop-proxies) around your bean starts the transaction before the method and ends it after.

## Why it exists

`PaymentService.pay()` saves a payment and then debits the customer's account. If the debit fails after the save, you are left with a payment but no money moved. By hand you would take a connection, switch off auto-commit, and write try, commit, catch, rollback and finally blocks in every such method. `@Transactional` moves that code into one place, the proxy, and your method keeps only the business steps.

## How it works

1. `PaymentController` calls `paymentService.pay()`. What it holds is the proxy, not your object.
2. The proxy reads the annotation's settings and asks the transaction manager to begin. With Spring Data JPA this is Boot's `JpaTransactionManager`, which takes a database connection from the pool of open connections Boot keeps ready.
3. The proxy calls your real method. Every repository call inside it uses that same connection and transaction.
4. If the method returns normally, the proxy commits. Hibernate first flushes your entity changes as SQL.
5. If the method throws a `RuntimeException` or an `Error`, the proxy rolls back and passes the exception on to the caller.

So the proxy decides only by what leaves your method: a normal return or a checked exception means commit, an unchecked exception means roll back.

## Example

The payment service debits an account that may throw a checked exception. This shows how to make that exception roll back too:

```java
@Service
public class PaymentService {
    private final PaymentRepository payments;
    private final AccountService accounts;      // constructor omitted

    @Transactional(rollbackFor = InsufficientFundsException.class)
    public PaymentResponse pay(PaymentRequest request) throws InsufficientFundsException {
        Payment payment = payments.save(new Payment(request.amount()));
        accounts.debit(request.accountId(), request.amount()); // may throw
        payment.setStatus(PaymentStatus.COMPLETED);   // no save() needed
        return PaymentResponse.from(payment);
    }
}
```

What to notice:

- Without `rollbackFor`, an `InsufficientFundsException` would commit the payment row, because it is a checked exception.
- A `RuntimeException` from `debit()` rolls back the save even without `rollbackFor`.
- `setStatus()` is written at commit by [dirty checking](card:persistence-context), because the entity is managed inside the transaction.
- If another method of `PaymentService` called `this.pay()`, the proxy would be skipped and no transaction would start.

## Rules and defaults

- **Switched on by Boot:** when a transaction manager bean exists, Spring Boot enables `@Transactional` support itself. With `spring-boot-starter-data-jpa` it registers a `JpaTransactionManager`. You do not add `@EnableTransactionManagement`.
- **Defaults (Spring Framework 7.0):** propagation `REQUIRED`, isolation `DEFAULT` (the database's own level), read-write, the timeout of the underlying system, and rollback on `RuntimeException` and `Error` only.
- **Changing rollback:** use `rollbackFor` and `noRollbackFor` per method. Since Spring Framework 6.2, `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)` changes it for the whole app.
- **Method visibility:** public methods work. Since Spring Framework 6.0, protected and package-private methods also work with class-based proxies, which Boot uses. Private methods never get a transaction.
- **readOnly = true:** a hint to the JDBC driver. With Hibernate, Spring sets the flush mode to `MANUAL`, so dirty checking is skipped. Spring Data's built-in read methods already run read-only, as [repositories](card:spring-data-repositories) showed.
- **Where to put it:** on methods of concrete classes, not on interfaces (the Spring team's advice). On a class, it applies to every method of that class.

## Not to be confused with

The **database transaction** is the real thing: the database keeps the steps together and undoes them on rollback. **`@Transactional`** only tells Spring where to begin and end that transaction. Rule: the database does the work; the annotation marks the boundary. What happens when one `@Transactional` method calls another is a separate setting, [propagation](card:transaction-propagation), which you will see next.

## Common mistakes

- **"Catching and logging the exception is harmless."** The proxy then sees a normal return and commits the half-done work. Rethrow the exception, or call `setRollbackOnly()` on the current transaction status.
- **"readOnly = true makes the database refuse writes."** It is a hint. Some databases reject writes in a read-only transaction, but Spring does not guarantee it.

## Interview Qs

### How does @Transactional work if it is only an annotation?

Spring wraps the bean in a proxy. When a caller calls the method, the proxy reads the annotation, asks the transaction manager to begin a transaction, calls your method, then commits on a normal return or rolls back on a RuntimeException or Error.

### Why does @Transactional sometimes not work?

The call skipped the proxy: a this-call inside the same bean, a private method, or an object created with new. Or the exception was checked or was caught inside the method, so the proxy saw nothing to roll back and committed.

### Why put @Transactional on the service layer, not on the controller or repository?

One business action, such as a payment, may call several repositories. A transaction started on the service method makes all of them commit or roll back together. On a repository, each call would commit on its own; on a controller, the transaction would also cover web work that does not need it.

### What does readOnly = true really do?

It marks the transaction as read-only. Spring passes it to the JDBC driver as a hint and, with Hibernate, sets the flush mode to MANUAL, so Hibernate skips dirty checking and saves time on large reads. It is not a guarantee that writes fail.
