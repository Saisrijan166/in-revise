## Why it exists

One business action often makes several database writes that must all succeed or all fail. Writing begin, commit and rollback by hand in every method is repetitive and easy to get wrong.

## How it works

<Mermaid
  alt="A caller calls the proxy, which begins a transaction and calls your method. If the method returns normally, or throws a checked exception, the proxy commits. If it throws a RuntimeException or an Error, the proxy rolls back. A call from inside the method to another method of the same object goes straight to the object and skips the proxy."
  chart={`flowchart LR
  C[Caller] --> P["Proxy: begin"]
  P --> M[Your method]
  M -- "returns, or checked exception" --> CM[Commit]
  M -- "RuntimeException or Error" --> RB[Roll back]
  M -. "this.other(): skips the proxy" .-> O[Other method]`}
/>

- Boot turns transaction management on for you and uses class-based (CGLIB) proxies by default. See [AOP and Spring proxies](card:aop-proxies) for why self-invocation is missed.
- An exception you catch never reaches the proxy, so the transaction commits. Rethrow it, or call `setRollbackOnly()`.
- Spring recommends annotating concrete classes, not interfaces.

## Example

```java
@Service
public class TransferService {

    private final AccountRepository accounts;

    public TransferService(AccountRepository accounts) {
        this.accounts = accounts;
    }

    @Transactional(rollbackFor = InsufficientFundsException.class)
    public void transfer(long from, long to, BigDecimal amount) throws InsufficientFundsException {
        accounts.findById(from).orElseThrow().withdraw(amount);  // saved by dirty checking
        accounts.findById(to).orElseThrow().deposit(amount);
    }                                                              // commit here
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Propagation | `REQUIRED` | Spring Framework 7.0 |
| Isolation | `DEFAULT`: the database's own level | Spring Framework 7.0 |
| readOnly | `false` (read-write) | Spring Framework 7.0 |
| Timeout | The transaction system's default, or none | Spring Framework 7.0 |
| Rolls back on | `RuntimeException` and `Error` | Spring Framework 7.0 |
| Proxy type | Class-based (CGLIB), `spring.aop.proxy-target-class=true` | Spring Boot 4.1 |

## Interview Qs

### Why does @Transactional sometimes not work?

The call did not pass through the proxy: self-invocation, a private or final method, or an object made with new. Or the exception was checked, or caught inside the method, so the proxy committed.

### Does @Transactional roll back on checked exceptions?

No. By default only RuntimeException and Error cause a rollback. Add rollbackFor = Exception.class, or a specific exception type, to roll back on checked ones too.

### Where should @Transactional go?

On service methods that form one unit of work, on the concrete class. Repository CRUD methods have their own @Transactional, and with the default REQUIRED they join the service's transaction.

### What does readOnly = true do?

It marks the transaction read-only. Spring passes this to the JDBC driver as a hint, and Hibernate sets flush mode MANUAL, which skips dirty checks. It is not a guard you can rely on: some databases reject writes, others do not.
