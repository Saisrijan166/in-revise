## What it is

The persistence context is the set of entity objects that JPA is tracking right now, usually for one transaction. A transaction is a group of database changes that are kept together at commit or undone together at rollback. Each `EntityManager` has one persistence context. An entity inside it is called managed: JPA keeps exactly one object per id and remembers the values it had when it was loaded.

## Why it exists

With plain JDBC, changing a payment's status means writing an UPDATE and remembering to run it. Loading the same row twice also gives two objects that can disagree. The persistence context fixes both. It hands back the same object for the same id, and before commit it compares each managed entity with its loaded values and writes an UPDATE only for what changed. This comparison is called dirty checking. Service code just changes fields.

## How it works

A new object is transient until you save it. Follow a loaded payment through one transaction:

1. The transaction starts, and the `EntityManager` has an empty persistence context.
2. `findById(42L)` runs a SELECT and puts the `Payment` into the context as managed. A second `findById(42L)` in the same transaction returns the same object without SQL.
3. Your code calls `setStatus("PAID")`. No SQL is sent yet.
4. Before commit, JPA flushes: it dirty-checks every managed entity and sends an UPDATE for each changed one.
5. The transaction commits and the context closes. The `Payment` is now detached: it keeps its data, but later changes are not saved.

So flush sends the SQL, and commit makes it permanent.

## Example

`PaymentService` marks a payment as paid. The method runs in one transaction, which you will set up properly in [@Transactional](card:transactional):

```java
@Transactional
public void markPaid(Long id) {
    Payment payment = payments.findById(id).orElseThrow();   // SELECT: now managed
    payment.setStatus("PAID");                              // no save() call
}   // commit: flush sends UPDATE payment set status = 'PAID' ... where id = ?
```

What to notice:

- There is no `save()` call. The payment is managed, so dirty checking finds the change at flush.
- Without `@Transactional`, no transaction ends with this method, so nothing flushes the change and the new status is not saved here.
- The UPDATE runs at the end of the method, so a database error, such as a broken constraint, appears there and not at the `setStatus` line. `saveAndFlush()` would make it appear at once.

## Rules and defaults

- **Lifetime:** in Spring, a persistence context lasts for one transaction by default. With open-in-view, which is on by default in Boot web apps (see [lazy loading](card:lazy-loading-n-plus-one)), the `EntityManager` stays open for the whole web request.
- **Flush mode (JPA 3.2):** `AUTO` by default, which flushes before a query that could see the pending changes, and at commit. `COMMIT` flushes only at commit.
- **How save() decides:** Spring Data JPA treats an entity as new if its non-primitive `@Version` field is null, or, with no version field, if its id is null. New entities get `persist()`, others get `merge()`. An entity can implement `Persistable` to decide itself.
- **Assigned ids:** if you set the id yourself and have no `@Version` field, the id is never null, so `save()` always uses `merge()`.
- **Second-level cache:** an optional Hibernate cache shared by all persistence contexts. It is off until you configure a cache provider.

## Not to be confused with

- **First-level cache:** the persistence context itself, one per transaction. It is always on.
- **Second-level cache:** shared across transactions, optional and off by default.
- **[Spring Cache](card:spring-cache):** caches the results of your own methods marked `@Cacheable`, not entities. You will see it later in this topic.

Rule: first level = inside one transaction; second level = across transactions; Spring Cache = method results.

## Common mistakes

- **"After save(payment), my payment variable is the managed object."** For an entity that is not new, `save()` uses `merge()`, which returns a different, managed copy. Keep using the returned object: `payment = payments.save(payment)`.

## Interview Qs

### What are the entity states?

Transient: a new object JPA does not track yet. Managed: inside a persistence context, so its changes are saved at flush. Detached: it has an id, but its persistence context has closed, so changes are no longer saved. Removed: marked for deletion, and the DELETE runs at flush.

### Does save() always run an INSERT?

No. Spring Data JPA checks whether the entity is new: first a null non-primitive version field, otherwise a null id. A new entity is persisted, which inserts a row. Any other entity is merged: its state is copied onto a managed copy, and the row is updated at flush.

### save() vs saveAndFlush()?

save() can leave the SQL waiting in the persistence context until the next flush. saveAndFlush() flushes at once, which helps when you need the SQL to run now, for example to catch a constraint error at that line. Neither one commits: the transaction can still roll back.
