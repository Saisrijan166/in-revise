## Why it exists

Without tracking, you would write an UPDATE for every field you change. The persistence context remembers what was loaded and works out the SQL for you.

## How it works

<Mermaid
  alt="Entity states. Transient: persist() makes it Managed. Managed: remove() makes it Removed; the row is deleted at flush. When the context closes, or on detach(), a Managed entity becomes Detached. merge() copies a Detached entity back onto a Managed one."
  chart={`flowchart LR
  T([Transient]) -- "persist()" --> M([Managed])
  M -- "remove()" --> R([Removed])
  M -- "context closes, detach()" --> D([Detached])
  D -- "merge()" --> M`}
/>

- Without open-in-view, the context lives for one transaction; then its entities become detached.
- `saveAndFlush()` flushes at once, so constraint errors appear at that line, not at commit.

## Example

```java
@Transactional
public void markPaid(Long id) {
    Payment p = payments.findById(id).orElseThrow();  // managed
    p.setStatus("PAID");                              // no save() needed
}   // commit: flush runs UPDATE payment set status = 'PAID' ...
```

## Interview Qs

### What are the entity states?

Transient: new, not tracked. Managed: in a persistence context; changes are saved at flush. Detached: has an id but is no longer tracked. Removed: marked for deletion at flush.

### Does save() always insert?

No. Spring Data JPA checks whether the entity is new: a null version, or else a null id. New entities are persisted; others are merged, which updates the row.

### save() vs saveAndFlush()?

save() may leave the SQL pending until the next flush. saveAndFlush() flushes immediately, which helps when you need the SQL to run now. Neither commits: the transaction can still roll back.
