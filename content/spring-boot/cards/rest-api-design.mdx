## Why it exists

Clients, proxies and caches all read the HTTP method and status code. Using them as the standard defines lets everyone know what is safe to retry or cache, and what went wrong.

## How it works

| Action | Request | Success | Idempotent? |
| --- | --- | --- | --- |
| Create | `POST /payments` | 201 + `Location` | No |
| Read | `GET /payments/42` | 200 | Yes (also safe) |
| Replace | `PUT /payments/42` | 200 or 204 | Yes |
| Change part | `PATCH /payments/42` | 200 or 204 | Not by default |
| Remove | `DELETE /payments/42` | 204 | Yes |

- Errors: 400 bad input, 401 [not authenticated](card:authentication-flow), 403 not allowed, 404 not found, 409 conflict, 422 valid syntax but cannot process.
- 5xx means the server failed: 500 bug, 502 bad gateway, 503 unavailable.

## Example

```text
POST /payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
{"amount": 1000, "currency": "INR"}

-> 201 Created, Location: /payments/42
(network drops; client retries with the same key)
-> the server returns the stored result: no second payment
```

## Interview Qs

### Which HTTP methods are idempotent?

GET, HEAD, OPTIONS, TRACE, PUT and DELETE. POST is not, and PATCH is not by default. Idempotent means repeating the same request leaves the server in the same state.

### How do you stop a retried payment request from charging twice?

Have the client send an Idempotency-Key header. The server stores the key with the first result and returns that result for a repeat. The header is an IETF draft; Stripe and Adyen use it.

### PUT vs PATCH?

PUT replaces the whole resource with the state you send, so repeating it changes nothing more. PATCH sends a set of changes to apply, so it is not idempotent unless you design it to be.
