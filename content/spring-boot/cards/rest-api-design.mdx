## What it is

REST API design here means using HTTP the way its standard, RFC 9110, defines it. The path names a thing, such as `/payments/42`. The HTTP method says what to do with it: create, read, replace, change or remove. The status code in the answer says how it went. Two properties of methods matter most: safe (the method only reads) and idempotent (sending it twice has the same effect as sending it once).

## Why it exists

Your controller is not the only program reading these requests. Browsers, proxies, caches, API gateways and client libraries all look at the method and the status code. If GET changes data, a cache or a prefetch can trigger the change. If errors come back as 200 with an error message inside, monitoring sees no failures. Following the standard tells every program in between what is safe to retry, what can be cached, and what went wrong.

## How it works

| Action | Request | Success | Idempotent? |
| --- | --- | --- | --- |
| Create | `POST /payments` | 201 + `Location` | No |
| Read | `GET /payments/42` | 200 | Yes (also safe) |
| Replace | `PUT /payments/42` | 200 or 204 | Yes |
| Change part | `PATCH /payments/42` | 200 or 204 | Not by default |
| Remove | `DELETE /payments/42` | 204 | Yes |

1. Choose the path as a noun for the resource, plural for the collection: `/payments`, then `/payments/42` for one payment.
2. Choose the method by its meaning, using the table above. The verb is never in the path, so not `/createPayment`.
3. Answer with a status from the right class: 2xx success, 4xx the client's fault, 5xx the server's fault.
4. For a method that is not idempotent and moves money, such as POST, make retries safe yourself with an idempotency key.

## Example

A retried payment request that is made safe with an `Idempotency-Key` header:

```text
POST /payments
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
{"amount": 1000, "currency": "INR"}

-> 201 Created, Location: /payments/42
(the network drops; the client retries with the same key)
-> the server finds the key and returns the stored 201 result: no second payment
```

What to notice:

- The client creates the key, a random UUID, once per payment attempt and reuses it for every retry of that attempt.
- The server stores the key together with the first result. A repeat with the same key gets the stored answer and does not run the payment again.
- Without the key, the server cannot tell a retry from a new payment of the same amount, so it would charge twice.

## Rules and defaults

- **Common success codes:** 200 OK with a body, 201 Created after a create, 204 No Content when there is nothing to return.
- **Common client errors:** 400 bad input, 401 not authenticated, 403 authenticated but not allowed (you will see both in [Authentication vs Authorization](card:authentication-flow)), 404 not found, 409 conflict with the current state, 422 valid syntax but content that cannot be processed.
- **Common server errors:** 500 an unexpected failure, 502 a bad answer from a server behind this one, 503 temporarily unavailable.
- **PUT can create:** if the client chooses the id and the resource does not exist yet, PUT may create it and answer 201.
- **Idempotency-Key status:** it is an IETF draft, not an RFC, and the draft has expired. Payment providers such as Stripe use the same idea.

## Interview Qs

### Which HTTP methods are idempotent?

GET, HEAD, OPTIONS, TRACE, PUT and DELETE. POST is not, and PATCH is not by default. Idempotent means that repeating the same request leaves the server in the same state as sending it once, which is why clients may retry these methods safely after a timeout.

### What is the difference between PUT and PATCH?

PUT replaces the whole resource with the representation you send, so repeating it changes nothing more. PATCH sends a set of changes to apply, so whether a repeat is harmless depends on the change. "Set status to PAID" is harmless to repeat; "add 100 to the amount" is not.

### How do you stop a retried payment request from charging twice?

Ask the client to send an Idempotency-Key header with each payment attempt. The server stores the key with the first result, for example in a table with a unique constraint, and returns that stored result for any repeat. A new attempt gets a new key.
