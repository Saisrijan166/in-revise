## What it is

Authentication is checking who is calling, for example by a username and password. Authorization is deciding whether that known caller may do a given action, such as refunding a payment. In the [filter chain](card:security-filter-chain), the login filters do authentication. Their result is an `Authentication` object: the user (called the principal) and their authorities, the permission strings such as `ROLE_ADMIN`. Authorization reads those authorities later; the rules are in [Authorization Rules](card:authorization-rules).

## Why it exists

The two checks answer different questions and fail differently. An unknown caller should be asked to log in (401). A known caller without permission should be refused (403), because logging in again will not help. Keeping them apart also lets you change how people log in, from form login to tokens, without touching who may do what.

## How it works

1. A login filter, such as the HTTP Basic filter, reads the username and password from the request.
2. It passes them to the AuthenticationManager. Its usual implementation, ProviderManager, asks each AuthenticationProvider in turn until one supports that kind of credential.
3. For passwords, DaoAuthenticationProvider loads the user through your UserDetailsService, and checks the typed password against the stored hash with the PasswordEncoder ([Password Hashing](card:password-encoding) explains the hash).
4. On success, the filter stores the authenticated `Authentication` in the SecurityContextHolder. ProviderManager has already erased the password from it. On failure nothing is stored: HTTP Basic answers 401, and form login redirects back to the login page.
5. AuthorizationFilter, `@PreAuthorize` and your controller then read the current user from there. FilterChainProxy clears it when the request ends.

## Example

The payment service loads users from its own table, and a controller reads the logged-in user:

```java
@Bean
UserDetailsService userDetailsService(AppUserRepository users) {
    return email -> users.findByEmail(email)
        .map(u -> User.withUsername(u.getEmail())
            .password(u.getPasswordHash())   // "{bcrypt}$2a$10$..."
            .roles(u.getRole())              // "ADMIN" is stored as ROLE_ADMIN
            .build())
        .orElseThrow(() -> new UsernameNotFoundException(email));
}

@GetMapping("/payments/mine")
List<PaymentResponse> mine(Authentication auth) {   // the logged-in user
    return paymentService.findFor(auth.getName());
}
```

What to notice:

- Spring calls the lambda in step 3 with the username the caller typed. The lambda only loads the user; Spring compares the password itself.
- `roles("ADMIN")` stores the authority `ROLE_ADMIN`, which authorization rules check later.
- Because this bean exists, Boot no longer creates its default `user` with a generated password.
- Spring MVC fills the `Authentication auth` parameter from the SecurityContextHolder, so the controller never parses credentials.

## Rules and defaults

- **One user per thread:** the SecurityContextHolder uses a `ThreadLocal` by default, so a thread you start yourself does not see the user.
- **Session login (Security 7.1):** after a form login, the SecurityContext is saved in the HTTP session, and the session cookie finds it on the next request. A stateless chain saves nothing, so each request must authenticate again.
- **Session fixation:** at login Spring changes the session id by default (`changeSessionId`), so an id an attacker planted before login stops working.
- **No matching provider:** if no AuthenticationProvider supports the credential type, login fails with `ProviderNotFoundException`.

## Interview Qs

### Authentication checks the user. Why do we also need authorization?

They answer different questions. A logged-in customer is known, but must still not open admin pages or another customer's payments. Authorization checks that, using the authorities found at login.

### How do AuthenticationManager and AuthenticationProvider fit together?

Login filters call the AuthenticationManager, usually a ProviderManager. It asks each AuthenticationProvider in turn; each handles one credential type, such as DaoAuthenticationProvider for passwords or JwtAuthenticationProvider for JWTs. If none succeeds, login fails.

### How do you get the current user in Spring?

In a controller, add an `Authentication` or `@AuthenticationPrincipal` parameter. Elsewhere, call `SecurityContextHolder.getContext().getAuthentication()`. It holds the principal, credentials and authorities, and is cleared after each request.
