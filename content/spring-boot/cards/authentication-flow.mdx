## Why it exists

Knowing who is calling and deciding what they may do are two separate checks. Spring Security keeps them apart so each can change on its own.

## How it works

<Compare id="authentication-vs-authorization" />

- **Password login:** DaoAuthenticationProvider loads the user through UserDetailsService and checks the password with the PasswordEncoder.
- **Between requests:** the login is kept in the HTTP session by default, unless the chain is stateless.

## Example

```java
@Bean
UserDetailsService users(UserRepository repo) {
    return username -> repo.findByEmail(username)
        .map(u -> User.withUsername(u.email())
            .password(u.passwordHash())   // e.g. {bcrypt}$2a$10$...
            .roles(u.role())
            .build())
        .orElseThrow(() -> new UsernameNotFoundException(username));
}
```

## Interview Qs

### Authentication checks the user. Why do we also need authorization?

They answer different questions. A logged-in customer is known, but must still not open admin pages or another customer's orders. Authorization checks that, using the authorities found at login.

### How do AuthenticationManager and AuthenticationProvider fit together?

Login filters call the AuthenticationManager, usually a ProviderManager. It asks each AuthenticationProvider in turn; each handles one credential type, such as DaoAuthenticationProvider for passwords or JwtAuthenticationProvider for JWTs.

### What is the SecurityContextHolder?

It holds the SecurityContext, which holds the current Authentication: principal, credentials and authorities. By default it is a ThreadLocal, cleared by FilterChainProxy after each request.
