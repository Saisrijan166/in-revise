## Why it exists

Form login, HTTP Basic and JWTs read credentials in different ways, but the check and the result should be the same. Spring Security splits the work: read the credentials, check them, then store who the user is.

## How it works

<Steps label="Username and password login">
<Step title="Filter">
UsernamePasswordAuthenticationFilter builds an unauthenticated UsernamePasswordAuthenticationToken from the request.
</Step>
<Step title="Manager">
The AuthenticationManager, a ProviderManager, asks each AuthenticationProvider until one supports the token.
</Step>
<Step title="Provider">
DaoAuthenticationProvider loads the UserDetails through the UserDetailsService and checks the password with the PasswordEncoder.
</Step>
<Step title="Store">
The authenticated token goes into the SecurityContextHolder and is saved in the HTTP session for later requests.
</Step>
</Steps>

- **On failure** the SecurityContextHolder is cleared and a failure handler runs. A request with no login at all goes to the AuthenticationEntryPoint: a redirect to the login page, or a 401.
- Read the current user with `@AuthenticationPrincipal` in a controller, or `SecurityContextHolder.getContext().getAuthentication()`.

## Example

```java
@Bean
UserDetailsService userDetailsService(UserRepository users) {
    return username -> users.findByEmail(username)
        .map(u -> User.withUsername(u.email())
            .password(u.passwordHash())   // e.g. {bcrypt}$2a$10$...
            .roles(u.role())              // stored as ROLE_<role>
            .build())
        .orElseThrow(() -> new UsernameNotFoundException(username));
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| SecurityContextHolder strategy | `MODE_THREADLOCAL` | Spring Security 7.1 |
| Where the login is kept | HTTP session (`HttpSessionSecurityContextRepository`) | Spring Security 7.1 |
| Credentials after a successful login | Erased by ProviderManager | Spring Security 7.1 |
| Session fixation protection | `changeSessionId`: new session id on login | Spring Security 7.1, Servlet 3.1+ |

## Interview Qs

### How do AuthenticationManager, ProviderManager and AuthenticationProvider fit together?

AuthenticationManager is the interface the login filters call. ProviderManager is its usual implementation and holds a list of AuthenticationProviders. Each provider handles one credential type, such as DaoAuthenticationProvider for passwords; if none can, a ProviderNotFoundException is thrown.

### What is the SecurityContextHolder?

It holds the SecurityContext, which holds the current user's Authentication: principal, credentials and authorities. By default it is a ThreadLocal, and FilterChainProxy clears it after each request.

### How do you log users in from your own database?

Expose a `UserDetailsService` bean whose `loadUserByUsername` returns UserDetails with the password hash and authorities, or throws UsernameNotFoundException. Boot then drops its default user, and DaoAuthenticationProvider does the password check.

### What is a principal in Spring Security?

The identity of the logged-in user, held inside the Authentication next to the credentials and authorities. With a password login it is usually the UserDetails object; in a controller you can inject it with `@AuthenticationPrincipal`.
