## Why it exists

A direct HTTP call makes a service wait for, and fail with, the service it calls. Publishing events to Kafka decouples them: the producer does not wait, and many consumers can share the work.

- Same key, same partition, so one order's events stay in order. In a group, each partition has one consumer; extra consumers sit idle.
- Spring commits offsets after processing (AckMode `BATCH`, auto-commit off), so a crash can redeliver records.
- JSON: `JacksonJsonSerializer` and `JacksonJsonDeserializer` (Jackson 3, Spring Kafka 4.0+); list trusted packages for the deserializer.

## Example

The producer:

```java
@Service
public class OrderEvents {
    private final KafkaTemplate<String, OrderPlaced> kafka;

    public OrderEvents(KafkaTemplate<String, OrderPlaced> kafka) {
        this.kafka = kafka;
    }

    public void publish(OrderPlaced event) {
        kafka.send("orders", event.orderId(), event);   // key: orderId
    }
}
```

The consumer, with a dead-letter topic after 3 attempts (Boot attaches the handler bean):

```java
@KafkaListener(topics = "orders", groupId = "billing")
public void onOrder(OrderPlaced event) {
    billing.chargeOnce(event);   // idempotent: safe if redelivered
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<?, ?> template) {
    var toDlt = new DeadLetterPublishingRecoverer(template);   // orders-dlt
    return new DefaultErrorHandler(toDlt, new FixedBackOff(1000L, 2));
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Offset commit | AckMode `BATCH`; `enable.auto.commit` false | Spring Kafka 4.1 |
| Error handler | 10 attempts, no delay, then the record is logged | Spring Kafka 4.1 |
| Never retried | `DeserializationException`, `ClassCastException` and other fatal errors | Spring Kafka 4.1 |
| Dead-letter topic | `<topic>-dlt`, same partition | Spring Kafka 4.1 |
| Delivery | At least once | Apache Kafka 4.2 |
| Versions | spring-kafka 4.1.1, kafka-clients 4.2.1 | Spring Boot 4.1.1 |

## Interview Qs

### What is a consumer group?

Consumers that share a group id split a topic's partitions: each partition goes to exactly one of them, so they share the load. Every group gets all the messages. Consumers beyond the partition count sit idle.

### How do you keep messages in order?

Kafka keeps order only within a partition. Send related events with the same key, such as the order id, so they land in one partition and are read in the order they were written.

### What happens when a listener keeps failing on a record?

DefaultErrorHandler retries it (10 attempts with no delay by default), then logs it. With a DeadLetterPublishingRecoverer it goes to `<topic>-dlt` instead, so the partition moves on and the record is kept. Deserialisation errors are not retried.

### At-least-once or exactly-once?

At least once by default: offsets are committed after processing, so a crash can redeliver and listeners must be idempotent. Exactly-once needs Kafka transactions and covers read-process-write within Kafka, not your database writes.
