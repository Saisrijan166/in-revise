## What it is

Apache Kafka is a message broker: services write **events** (records) to named **topics**, and other services read them later. A topic is split into **partitions** so that many consumers can read it in parallel. Spring for Apache Kafka gives you `KafkaTemplate` to send records and `@KafkaListener` to receive them, and Spring Boot configures both from `spring.kafka.*` properties. [Application events](card:application-events) stay inside one app; Kafka events travel between services.

## Why it exists

When a payment completes, the notification service must send a receipt. If the payment service calls it over HTTP, the payment waits for the email, and fails when the notification service is down. With Kafka, the payment service writes a `PaymentCompleted` event and moves on. The notification service reads it when it can; if it is down, the event waits in the topic. Neither service needs the other to be running.

## How it works

1. The payment service calls `send("payments", key, event)`. Kafka hashes the key to pick a partition, so one payment's events always land in the same partition, in order.
2. All listeners with group id `notifications` share the topic: Kafka gives each partition to exactly one of them.
3. Each listener reads records in order from its partitions and runs your method for each.
4. After the records are processed, Spring commits the **offset**: the position the group has reached in that partition.
5. If the app crashes before that commit, the records are delivered again after restart. This is **at-least-once** delivery.

## Example

The notification service listens for completed payments and moves a record that keeps failing to a dead-letter topic.

```java
@KafkaListener(topics = "payments", groupId = "notifications")
public void onPaymentCompleted(PaymentCompleted event) {
    receipts.sendOnce(event);   // idempotent: skips payments already handled
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<?, ?> template) {
    var toDlt = new DeadLetterPublishingRecoverer(template);   // sends to payments-dlt
    return new DefaultErrorHandler(toDlt, new FixedBackOff(1000L, 2));
}
```

What to notice:

- `sendOnce` must be safe to call twice for the same payment, because at-least-once delivery allows repeats.
- `FixedBackOff(1000L, 2)` means 2 retries, 1 second apart: 3 tries in total, then the record goes to `payments-dlt`.
- Boot attaches this error handler bean to the listener container factory it auto-configures. Without it, a failing record is tried 10 times and only logged.

## Rules and defaults

- **Offset commit (Spring Kafka 4.1):** `AckMode.BATCH` by default: offsets are committed after all records from one poll, the batch a consumer fetches at a time, are processed.
- **Partitions and consumers:** a group can use at most one consumer per partition; extra consumers stay idle.
- **Order:** Kafka keeps order only within one partition, never across a whole topic.
- **Dead-letter topic:** by default `<topic>-dlt`, same partition as the original record, so it needs at least as many partitions.
- **Exactly once:** needs Kafka transactions, and even then only for Kafka reads and writes, not for an email or a database outside Kafka.

## Not to be confused with

A **topic** is a named stream of events. A **consumer group** is a set of listeners that share the work of reading it. Rule: every group gets every event once; inside a group, each event is handled by one member. Two different services use two different group ids, so both get all events.

## Common mistakes

- **"Send the event inside the database transaction."** If the commit then fails, consumers get an event for a payment that was never saved. Send after commit, or use the [outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html): save the event in the same transaction, and publish it from there.

## Interview Qs

### What is a consumer group?

A set of consumers that share one group id. They split a topic's partitions between them, one consumer per partition, so each record is processed once per group. Every group receives all records, so two services with different group ids both see every event. Consumers beyond the partition count sit idle.

### How do you keep messages in order?

Kafka keeps order only within a partition. Give related events the same key, such as the payment id, so they land in one partition and are read in the order they were written.

### What happens when a listener keeps failing on a record?

The `DefaultErrorHandler` retries it, by default 10 times with no wait, then logs it and moves on. With a `DeadLetterPublishingRecoverer` it is published to `<topic>-dlt` instead, so the record is kept for later inspection or replay, not only written to the log.
