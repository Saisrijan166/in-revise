## Why it exists

In production you cannot attach a debugger. Metrics show that something is slow or failing, traces show where across services, and trace IDs in the logs lead to the details.

## How it works

<Mermaid
  alt="One observation, such as an HTTP request, goes to two handlers. The meter handler records a timer in the MeterRegistry, which Prometheus scrapes from /actuator/prometheus. The tracing handler records a span with a trace ID, which is exported over OTLP or to Zipkin. The trace ID and span ID are also added to log lines."
  chart={`flowchart LR
  O["Observation: HTTP request"] --> MH[Meter handler]
  O --> TH[Tracing handler]
  MH --> REG[(MeterRegistry)]
  REG -- "scraped at /actuator/prometheus" --> PR[Prometheus]
  TH --> SP[Span with traceId]
  SP -- "OTLP or Zipkin" --> TB[Trace backend]
  SP -. "traceId, spanId" .-> LOG[Log lines]`}
/>

- Low-cardinality key values go to metrics and traces; high-cardinality ones, such as a user ID, go to traces only.
- Trace headers go out only on clients built from the auto-configured `RestClient.Builder`, `WebClient.Builder` or `RestTemplateBuilder`.
- `@Observed`, `@Timed` and `@Counted` need `management.observations.annotations.enabled=true` and `spring-boot-starter-aspectj`.

## Example

```java
@Service
class CheckoutService {
    private final ObservationRegistry registry;

    CheckoutService(ObservationRegistry registry) {
        this.registry = registry;
    }

    void checkout(Cart cart) {
        Observation.createNotStarted("checkout", registry)
            .lowCardinalityKeyValue("payment", cart.paymentType()) // metrics + traces
            .highCardinalityKeyValue("cartId", cart.id())          // traces only
            .observe(() -> process(cart));
    }
}
```

```properties
management.endpoints.web.exposure.include=health,prometheus
# keep every trace while developing (default 0.1)
management.tracing.sampling.probability=1.0
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Metrics backend when none is added | In-memory simple registry | Spring Boot 4.1, Micrometer 1.17 |
| `/actuator/prometheus` | Not exposed until you include it | Spring Boot 4.1 |
| HTTP server metric name | `http.server.requests` | Spring Boot 4.1 |
| Trace sampling | 10% (`0.1`) | Spring Boot 4.1 |
| Trace IDs in logs | On when Micrometer Tracing is present | Spring Boot 4.1 |
| `@Observed`, `@Timed`, `@Counted` | Off | Spring Boot 4.1 |

## Interview Qs

### What is Micrometer?

A vendor-neutral facade for metrics and observations: SLF4J for observability. You record counters, gauges and timers once; the registry you add, such as `micrometer-registry-prometheus`, decides where they go.

### Metrics vs traces vs logs?

Metrics are cheap numbers over time, for dashboards and alerts. A trace follows one request across services as a tree of timed spans. Logs are detailed events; with a trace ID in each line, you find the logs of one slow request.

### How do you trace a request across microservices?

Add Micrometer Tracing with OpenTelemetry (`spring-boot-starter-opentelemetry`) or Brave with Zipkin. Calls made with the auto-configured `RestClient` or `WebClient` builders pass the trace headers on, so every service shares one trace ID.
