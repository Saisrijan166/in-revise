## Why it exists

In production you cannot attach a debugger. Logs, metrics and traces let you see what a running system is doing, and why it is slow or failing.

## How it works

| Signal | Answers | In Spring Boot |
| --- | --- | --- |
| Metrics | Is something wrong? (numbers over time) | Micrometer `MeterRegistry`, e.g. Prometheus |
| Traces | Where is it slow? (one request across services) | Micrometer Tracing, OpenTelemetry or Brave |
| Logs | Why did it fail? (detailed events) | SLF4J and Logback, with traceId and spanId |

- One `Observation` (an HTTP request, say) produces both a timer metric and a span.
- Low-cardinality tags go to metrics and traces; high-cardinality ones go to traces only.

## Example

```properties
management.endpoints.web.exposure.include=health,prometheus
# trace every request while developing (default 0.1)
management.tracing.sampling.probability=1.0
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Trace sampling | 10% (`0.1`) | Spring Boot 4.1 |
| `/actuator/prometheus` | Not exposed until you include it | Spring Boot 4.1 |
| HTTP server metric | `http.server.requests` | Spring Boot 4.1 |

## Interview Qs

### Metrics vs traces vs logs?

Metrics are cheap numbers over time, for dashboards and alerts. A trace follows one request across services as timed spans. Logs are detailed events; the trace ID in each line links them to the request.

### How do you trace a request across microservices?

Add Micrometer Tracing with OpenTelemetry (`spring-boot-starter-opentelemetry`). Calls made with the auto-configured `RestClient` or `WebClient` builders pass the trace headers on, so every service shares one trace ID.
