## What it is

Observability is being able to tell what a running system is doing from what it reports, without attaching a debugger. It rests on three signals. **Metrics** are numbers over time, such as error rate. A **trace** follows one request through every service as a chain of timed steps called **spans**. **Logs** are the detailed text events you already write with [SLF4J](card:logging). Spring Boot records metrics and traces with Micrometer, a vendor-neutral library.

## Why it exists

In production the payment service runs as many instances behind a gateway, and a request may pass through three services. When customers say "checkout is slow", logs alone do not say which service or which call. Metrics raise the alert, a trace shows the slow span, and the trace ID in the log lines finds the exact error. Without them you guess and add logging after the incident.

## How it works

| Signal | Answers | In Spring Boot |
| --- | --- | --- |
| Metrics | Is something wrong? | Micrometer `MeterRegistry`; Prometheus scrapes `/actuator/prometheus` |
| Traces | Where is it slow? | Micrometer Tracing with OpenTelemetry or Brave |
| Logs | Why did it fail? | SLF4J and Logback, with `traceId` and `spanId` in each line |

1. A request arrives, and Boot starts an **observation** for it: a timed piece of work with a name and tags.
2. When the observation ends, Micrometer turns it into a timer metric, such as `http.server.requests`, and into a span of the trace.
3. While it runs, the trace ID sits in the logging context, so every log line written during the request carries it.
4. When the service calls another one through an [auto-configured client builder](card:http-clients), the trace ID travels in the request headers, and the next service adds its spans to the same trace.

## Example

The payment service wraps its own work in an observation, so it gets a metric and a span with no extra code for each.

```java
PaymentResponse pay(PaymentRequest request) {
    return Observation.createNotStarted("payment.process", observations)
            .lowCardinalityKeyValue("method", request.method())          // card or upi
            .highCardinalityKeyValue("customerId", request.customerId()) // traces only
            .observe(() -> process(request));
}
```

What to notice:

- `observations` is the `ObservationRegistry` bean that Boot creates and you inject.
- The low-cardinality value `method` has only a few possible values, so it goes on both the metric and the span.
- The high-cardinality value `customerId` goes only on the span. As a metric tag it would create one time series per customer.

## Rules and defaults

- **Sampling:** `management.tracing.sampling.probability` is `0.1` (10%) by default. Set `1.0` while developing to trace every request.
- **Tracer:** add `spring-boot-starter-opentelemetry` for OpenTelemetry, which sends traces over OTLP (OpenTelemetry's own protocol), or `spring-boot-starter-zipkin` for Brave with Zipkin.
- **Prometheus:** the `/actuator/prometheus` endpoint needs `micrometer-registry-prometheus` and must be listed in `management.endpoints.web.exposure.include`.
- **Propagation:** only clients built from the auto-configured `RestClient.Builder`, `WebClient.Builder` or `RestTemplateBuilder` pass the trace on.
- **Log correlation:** with Micrometer Tracing, Boot adds the trace and span IDs to log lines by default; `logging.pattern.correlation` changes the format.

## Not to be confused with

[Actuator](card:actuator) is the set of endpoints that **expose** data, such as `/actuator/prometheus`. Micrometer is the library that **records** metrics and spans inside the app. Rule: Micrometer measures; Actuator shows the measurements to the outside.

## Interview Qs

### Metrics vs traces vs logs?

Metrics are cheap numbers over time, good for dashboards and alerts. A trace follows one request across services as timed spans and shows where time was spent. Logs are detailed events that explain what happened; the trace ID in each line links them to the request that wrote them.

### How do you trace a request across microservices?

Add Micrometer Tracing with OpenTelemetry through `spring-boot-starter-opentelemetry`. Build HTTP clients from the auto-configured builders, so every outgoing call carries the trace headers. Every service then adds its spans to one trace, which the tracing backend shows as one timeline.

### Why not trace 100% of requests in production?

Sending every trace can overwhelm the trace backend, so Spring Boot samples 10% by default. That share is usually enough to see where time goes. Raise it while debugging, or for low-traffic services, and keep it lower for busy ones.
