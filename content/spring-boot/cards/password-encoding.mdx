## Why it exists

Databases leak. Plain text or a fast hash is cracked at once; a slow, salted one-way hash makes every single guess expensive.

## How it works

| Stored value | Checked by | Note |
| --- | --- | --- |
| `{bcrypt}$2a$10$...` | BCryptPasswordEncoder | Default for new hashes; `10` is the strength |
| `{argon2}...` | Argon2PasswordEncoder | Needs a lot of memory per check |
| `{pbkdf2}...` | Pbkdf2PasswordEncoder | A good choice when FIPS is required |
| `{noop}secret` | NoOpPasswordEncoder | Plain text: never in production |
| `$2a$10$...` (no prefix) | none | `matches()` throws IllegalArgumentException |

- Strength is an exponent: each +1 doubles the work. Spring suggests tuning to about one second per check.

## Example

```java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

String hash = encoder.encode(rawPassword);        // sign-up: "{bcrypt}$2a$10$..."
boolean ok = encoder.matches(rawPassword, hash);  // login
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Encoder | DelegatingPasswordEncoder | Spring Security 7.1 |
| Id for new hashes | `bcrypt` | Spring Security 7.1 |
| BCrypt strength | 10 (allowed 4 to 31) | Spring Security 7.1 |

## Interview Qs

### Why hash and not encrypt passwords?

Encryption can be reversed by anyone who gets the key. A hash is one-way: the server only needs to check that a login attempt gives the same hash, never to read the password back.

### What is a salt?

Random bytes mixed into each password before hashing, so equal passwords get different hashes and precomputed tables stop working. The salt is not secret; bcrypt creates it and stores it in the hash.

### How do you move old hashes to bcrypt?

Prefix each old hash with its `{id}` so DelegatingPasswordEncoder knows how to check it. New and changed passwords are then written as bcrypt automatically.
