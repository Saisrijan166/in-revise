## What it is

Password hashing turns a password into a fixed string with a one-way function: you can compute the hash from the password, but not the password from the hash. In Spring Security this is the `PasswordEncoder` interface, with `encode()` at sign-up and `matches()` at login. A good password hash is slow on purpose, and mixes in a salt, random bytes chosen per password. In the [login flow](card:authentication-flow), DaoAuthenticationProvider calls `matches()` for you.

## Why it exists

Databases leak. If passwords are stored as plain text, every account is exposed at once, and people reuse passwords on other sites. Encryption does not fix this, because whoever steals the key can decrypt them all. A fast hash such as MD5 or SHA-256 lets an attacker test a huge number of guesses cheaply on GPUs. A slow, salted hash makes each guess expensive and forces the attacker to crack each password separately.

## How it works

1. At sign-up, you call `encoder.encode(rawPassword)` on Spring's default encoder, DelegatingPasswordEncoder, which hands the work to one algorithm. It picks bcrypt, generates a random salt and runs bcrypt.
2. It returns one string: the `{bcrypt}` prefix, then the bcrypt version, the strength, the salt and the hash. You store this string and never the raw password.
3. At login, DaoAuthenticationProvider loads that string through your UserDetailsService and calls `matches(typedPassword, storedString)`.
4. DelegatingPasswordEncoder reads the `{bcrypt}` prefix and hands the check to the bcrypt encoder.
5. That encoder takes the salt from the stored string, hashes the typed password the same way and compares the two results. Equal means the password is right.

## Example

This runnable snippet shows what is stored and how checking works:

```java
PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
String hash1 = encoder.encode("s3cret-Pass");
String hash2 = encoder.encode("s3cret-Pass");
System.out.println(hash1.substring(0, 15));                // what is stored
System.out.println(hash1.equals(hash2));                    // same password
System.out.println(encoder.matches("s3cret-Pass", hash1));  // login, right password
System.out.println(encoder.matches("s3cret-pass", hash1));  // login, wrong case
try {
    encoder.matches("s3cret-Pass", hash1.substring(8));     // hash without {bcrypt}
} catch (IllegalArgumentException e) {
    System.out.println(e.getClass().getSimpleName());
}
```

```text output
{bcrypt}$2a$10$
false
true
false
IllegalArgumentException
```

What to notice:

- `$2a$10$` means bcrypt version 2a with strength 10. The salt follows inside the same string, so there is nothing else to store.
- The two hashes of one password differ because each has its own salt. So you can never compare hashes with `equals` or a SQL `WHERE`; always call `matches()`.
- A stored value without its `{id}` prefix makes `matches()` throw, which is the usual error after importing old users.

## Rules and defaults

- **Encoder (Security 7.1):** Spring uses DelegatingPasswordEncoder unless you define a `PasswordEncoder` bean. In Boot you usually expose `PasswordEncoderFactories.createDelegatingPasswordEncoder()` as that bean.
- **New hashes:** written with bcrypt. Stored hashes keep their own prefix, such as `{argon2}`, `{pbkdf2}` or `{noop}`.
- **BCrypt strength:** 10 by default, allowed 4 to 31. Each +1 doubles the work; Spring advises tuning it to about one second per check on your servers.
- **`{noop}`:** plain text, for demos only. `User.withDefaultPasswordEncoder()` is also not safe for production.

## Not to be confused with

Encoding, such as Base64, changes the format and anyone can reverse it. Encryption can be reversed by whoever has the key. Hashing cannot be reversed at all. Rule: passwords are hashed, secrets you must read back are encrypted, and encoding is never protection.

## Interview Qs

### Why hash passwords and not encrypt them?

Encryption can be reversed by anyone who gets the key, and the key often leaks with the database. A hash is one-way: the server only needs to check that a login attempt gives the same hash, never to read the password back.

### What is a salt, and is it secret?

Random bytes mixed into each password before hashing, so equal passwords get different hashes and precomputed tables of common hashes stop working. The salt is not secret; bcrypt creates it and stores it inside the hash string.

### Why bcrypt and not SHA-256?

SHA-256 is designed to be fast, which helps an attacker testing guesses. Bcrypt, Argon2 and PBKDF2 are slow on purpose and have a work factor you can raise as hardware gets faster.

### How do you move old hashes to bcrypt?

Prefix each old hash with its `{id}`, such as `{MD5}`, so DelegatingPasswordEncoder knows how to check it. New and changed passwords are then written as bcrypt automatically.
