## Why it exists

Databases leak. If passwords are stored as plain text or a fast hash, an attacker reads or cracks them at once. A slow, salted one-way hash makes every single guess expensive.

## How it works

| Stored value | `matches()` uses | Note |
| --- | --- | --- |
| `{bcrypt}$2a$10$...` | BCryptPasswordEncoder | The default for new hashes; `10` is the strength |
| `{argon2}...` | Argon2PasswordEncoder | Needs a lot of memory per check |
| `{pbkdf2}...` | Pbkdf2PasswordEncoder | Pick it when FIPS is required |
| `{noop}secret` | NoOpPasswordEncoder | Plain text: demos only |
| `$2a$10$...` (no prefix) | none | IllegalArgumentException |

- `encode()` always uses the current default, so the algorithm or strength can change later without breaking old users.
- Strength is an exponent: 10 means 2^10 rounds, so each +1 doubles the work. Check a password once, then use a session or token for later requests.

## Example

```java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

// at sign-up: store only the hash
String hash = passwordEncoder.encode(rawPassword);   // "{bcrypt}$2a$10$..."

// at login (DaoAuthenticationProvider does this for you)
boolean ok = passwordEncoder.matches(rawPassword, hash);
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Encoder when you define none | DelegatingPasswordEncoder | Spring Security 7.1 |
| Id for new hashes | `bcrypt` | Spring Security 7.1 (`PasswordEncoderFactories`) |
| BCrypt strength | 10 (allowed 4 to 31) | Spring Security 7.1 |
| CompromisedPasswordChecker | None | Spring Security 7.1 (available since 6.3) |

## Interview Qs

### What is PasswordEncoder, and what is the default?

The interface for one-way password hashing: `encode()` at sign-up, `matches()` at login. The default is DelegatingPasswordEncoder: it writes `{bcrypt}` hashes and can verify any hash whose `{id}` it knows.

### Why not SHA-256 or MD5?

They are fast: modern hardware computes billions of them per second, so a leaked table is cracked quickly. Adaptive functions such as bcrypt, scrypt, Argon2 or PBKDF2 have a work factor you raise as hardware gets faster.

### What is a salt?

Random bytes mixed into each password before hashing, so equal passwords get different hashes and precomputed rainbow tables stop working. The salt is not secret; bcrypt generates and keeps it for you.

### How do you support old hashes while moving to bcrypt?

Keep the old hashes and add the right `{id}` prefix to each, so DelegatingPasswordEncoder knows how to verify it. New and changed passwords are then written with bcrypt automatically.
