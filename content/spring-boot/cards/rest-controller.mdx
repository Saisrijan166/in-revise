## Why it exists

A web app either renders pages on the server or sends data to a browser app, a phone or another service. Spring uses one controller model for both; the annotation decides whether a return value is a view name or the response data.

## How it works

<Compare id="controller-vs-restcontroller" />

- `ResponseEntity` sets the status and headers per call; `@ResponseStatus(HttpStatus.CREATED)` sets one fixed status.
- Content negotiation checks only the `Accept` header by default; `produces` on a mapping narrows it.

## Example

```java
@RestController
@RequestMapping("/users")
class UserController {
    private final UserService users;
    UserController(UserService users) { this.users = users; }

    @GetMapping("/{id}")
    ResponseEntity<User> get(@PathVariable long id) {
        return ResponseEntity.of(users.find(id));   // Optional: 200 with body, or 404
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)             // 201 instead of 200
    User create(@RequestBody User user) { return users.save(user); }
}
```

## Interview Qs

### @Controller vs @RestController?

@RestController is @Controller plus @ResponseBody, so every method's return value is written to the body by a message converter, usually as JSON. With plain @Controller, a returned String is a view name that a ViewResolver renders as a page.

### When do you return ResponseEntity?

When the status or headers depend on the outcome: 201 with a Location header after a create, 404 when nothing is found, or an ETag. For a fixed status, @ResponseStatus on the method is enough.

### How does Spring decide to send JSON or XML?

Content negotiation. By default it reads the Accept header, then picks a message converter that can write the return type in that media type. If none can, the client gets 406 Not Acceptable.
