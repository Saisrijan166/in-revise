## Why it exists

A platform thread maps to an OS thread, so a server can afford only a few hundred, and each one sits idle while it waits for I/O. Virtual threads are cheap enough to give every request its own, without rewriting the code to be reactive.

## How it works

<Steps label="One request on a virtual thread">
<Step title="Start">
Tomcat starts a new virtual thread for the request; virtual threads are never pooled.
</Step>
<Step title="Mount">
The JVM mounts it on a carrier, a platform thread, and your controller code runs.
</Step>
<Step title="Block">
A blocking call such as JDBC or RestClient unmounts it; the carrier runs other virtual threads meanwhile.
</Step>
<Step title="Resume">
When the data is ready, it is mounted again, possibly on another carrier, and continues.
</Step>
</Steps>

- To limit concurrent work, use a `Semaphore`, not a small thread pool.
- Up to JDK 23, blocking inside `synchronized` pinned the carrier; JEP 491 fixed this in JDK 24. Class initialisers and native callbacks can still pin.
- JDK Flight Recorder reports pinning as the `jdk.VirtualThreadPinned` event.

## Example

```properties
spring.threads.virtual.enabled=true
# virtual threads are daemon threads: keep the JVM up, e.g. in a @Scheduled-only app
spring.main.keep-alive=true
```

Check which kind of thread serves a request:

```java
@GetMapping("/thread")
String thread() {
    return Thread.currentThread().isVirtual() ? "virtual" : "platform";
}
```

## Defaults

| What | Default | Where |

| `spring.threads.virtual.enabled` | `false` | Spring Boot 4.1 |
| Java needed | 21 or later; 24 or later strongly recommended | Spring Boot 4.1 |
| `spring.main.keep-alive` | `false` | Spring Boot 4.1 |
| Tomcat worker threads when off | max 200, min 10 | Spring Boot 4.1 (`server.tomcat.threads.max`, `min-spare`) |

## Interview Qs

### How do you enable virtual threads in Spring Boot, and what changes?

Set spring.threads.virtual.enabled=true on Java 21 or later. Tomcat and Jetty then handle each request on a virtual thread, and the auto-configured executor and scheduler behind @Async and @Scheduled use virtual threads too. Thread-pool properties stop having an effect.

### Virtual threads vs WebFlux?

Both let a few OS threads serve many waiting requests. Virtual threads keep plain blocking code and libraries like JDBC. WebFlux needs non-blocking code end to end, but adds back pressure and streaming.

### What is pinning?

A pinned virtual thread cannot unmount while it blocks, so it holds its carrier platform thread. Up to JDK 23 this happened inside synchronized blocks; JEP 491 fixed that in JDK 24. Blocking in a class initialiser, or native code calling back into Java, can still pin.
