## Why it exists

One server has fixed limits: CPU, memory, disk, and network. As users grow, requests slow down and then fail. Scalability is a system's ability to change its capacity to match demand.

## How it works

- **Vertical scaling (scale up):** give one machine more CPU, memory, or disk.
- **Horizontal scaling (scale out):** add more machines and share the work between them.
- Scaling up is simple but has a ceiling, and resizing often needs a restart.
- Scaling out has a much higher ceiling and survives one machine failing. It needs a [load balancer](card:load-balancer) in front and stateless servers behind it.

## Analogy

<Analogy title="A bigger truck vs more trucks" limit="More trucks only help if the warehouse can load them. If the database is the bottleneck, more web servers will not help. Also, a parcel must not be locked inside one truck: keep session data in a shared store.">
Your delivery company is overloaded. **Scale up:** buy a bigger truck. It is easy, but there is a biggest truck, and if it breaks down nothing gets delivered. **Scale out:** buy more trucks. There is no size limit and one breakdown is fine, but now you need a dispatcher to share the parcels.
</Analogy>

## Example

Traffic doubles for a sale.

- **Scale up:** move the app from a 4-core to an 8-core machine. One restart, no code change.
- **Scale out:** run 4 copies of the app behind a load balancer. First move user sessions out of server memory into Redis, so any copy can serve any user.

## Rules & defaults

- Vertical scaling often means downtime: an Azure VM restarts when it is resized, and an EC2 instance must be stopped to change its instance type.
- Horizontal scaling needs stateless servers: keep session data in a shared store (a database or distributed cache), not in one server's memory.
- Every resource has an upper limit, even in the cloud.
- Scale each tier on its own. Web servers scale out easily; databases are harder (see [Sharding vs Replication](card:sharding-and-replication)).

## Can / Cannot

### Can

- Scale out to survive one machine failing.
- Combine both: grow one machine until it hits a limit, then add machines (Azure calls this diagonal scaling).

### Cannot

- Scale up forever: the biggest machine is the ceiling.
- Fix a database bottleneck by adding more web servers.

## Interview Qs

### What is the difference between vertical and horizontal scaling?

Vertical adds power to one machine; horizontal adds more machines. Vertical is simpler but has a ceiling, stays a single point of failure, and often needs a restart to resize. Horizontal scales further and tolerates failures, but needs a load balancer and stateless servers.

### How do you make the web tier scale out?

Make the servers stateless: move sessions to a shared store such as Redis or a database. Then put a load balancer in front. Now any server can handle any request, and you can add or remove servers freely.

### When would you scale up instead?

When the workload is hard to split, like a single relational database, or when you need a quick fix. A common path is to scale up first while designing the system so it can scale out later.

## Mistake alert

"Just add more servers." Scaling out the web tier does nothing if the database is the bottleneck, and it breaks login sessions if they live in one server's memory.

## Say it like this

"Vertical scaling makes one machine bigger; horizontal scaling adds machines. I keep app servers stateless behind a load balancer so they scale out, and I treat the database separately, because it is usually the harder part to scale."
