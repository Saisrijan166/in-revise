## Why it exists

One server has fixed limits: CPU, memory, disk and network. When users grow past them, requests slow down and then fail.

## How it works

<Compare id="vertical-vs-horizontal-scaling" />

- Scaling out needs a [load balancer](card:load-balancer) in front and stateless servers behind it, so any server can handle any request.

## Analogy

<Analogy title="A bigger truck vs more trucks" limit="More trucks only help if the warehouse can load them. If the database is slow, more web servers will not help.">
Scale up is a bigger truck: easy, but there is a biggest truck, and if it breaks, nothing moves. Scale out is more trucks: no size limit and one breakdown is fine, but now you need a dispatcher (the load balancer).
</Analogy>

## Example

Traffic doubles for a sale.

- **Scale up:** move the app from 4 to 8 CPU cores. One restart, no code change.
- **Scale out:** run 4 copies behind a load balancer, after moving user sessions from server memory to Redis.

## Interview Qs

### Vertical vs horizontal scaling?

Vertical adds power to one machine: simple, but it has a ceiling, often needs a restart, and stays a single point of failure. Horizontal adds machines: it goes further and survives failures, but needs a load balancer and stateless servers.

### How do you make the web tier scale out?

Make servers stateless: keep sessions in Redis or a database, not in server memory. Put a load balancer in front. Now you can add or remove servers freely.

### When would you scale up instead?

When the part is hard to split, like a single relational database, or when you need a quick fix. Scale up first, but design so you can scale out later.

### Performance vs scalability?

A performance problem means the system is slow even for one user. A scalability problem means it is fast for one user but slow under heavy load. A scalable service handles more work in proportion to the resources you add.
