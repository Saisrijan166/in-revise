## Why it exists

With [cache-aside](card:cache-aside), the cache changes only on reads, so a read right after a write can miss or see old data. Write-through keeps the cache current on every write; write-behind also makes writes fast.

## How it works

<Mermaid
  alt="Two write paths. Write-through: the app writes to the cache, the same write goes on to the database, and only then is the write confirmed. Write-behind: the app writes to the cache and is confirmed at once; later the cache writes the changes to the database in batches."

  subgraph WT["Write-through"]

  end
  subgraph WB["Write-behind"]

- **Write-through** can run inside the cache product, or in the app: write the database, then set the key (the AWS example).
- **Write-behind** (write-back) queues changes; several changes to one key in the delay become one database write.
- Two read-side helpers go with these: **read-through** (the cache loads misses itself) and **refresh-ahead** (a key read close to expiry is reloaded in the background).

## Example

A view counter changes 500 times in 10 seconds.

- **Write-through:** 500 cache writes and 500 database writes. Every read is fresh.
- **Write-behind**, flushing every 10 seconds: 500 cache writes, 1 database write. A cache crash before the flush loses those 500 views.

## Interview Qs

### Write-through vs write-behind?

Write-through confirms a write only after the cache and the database both have it: fresh reads, slower writes. Write-behind confirms after the cache write and flushes later: fast writes and fewer database writes, but data is lost if the cache fails before the flush.

### When would you use write-behind?

For write-heavy data where losing the last few seconds is acceptable, such as view counts, likes or metrics. Not for payments or orders, where the database must hold the write before you confirm it.

### What is read-through, and how is it different from cache-aside?

Both load from the database on a miss. In cache-aside the app does it; in read-through the cache does it through a loader, so the app talks only to the cache.

### What problems does write-through bring?

Every write pays for two writes, and most written data is never read, so the cache fills with cold data; add a TTL. A new cache node also starts empty until data is written again, so pair it with lazy loading.
