## What it is

Write-through and write-behind are two write strategies: they decide what happens to the cache and the database when the app writes data. With **write-through**, a write goes to the cache and the database together, and is confirmed only when both have it. With **write-behind** (also called write-back), a write goes to the cache and is confirmed at once, and the database is updated a little later. Both keep the cache updated on writes, unlike [cache-aside](card:cache-aside), which deletes the key instead.

## Why it exists

With cache-aside, the cache changes only on reads, so a read right after a write can miss or see the old value until the key is reloaded. For data where a read must immediately see the latest write, that is not good enough. Write-through fixes it by updating the cache on every write, so the latest value is always there to read. Write-behind goes further for write-heavy data: it makes the write return fast and batches many changes into far fewer database writes, at the cost of durability.

1. In write-through, the app issues one write. The cache is updated, the same change is written to the database, and only when both succeed is the write confirmed.
2. A later read of that key is a hit with the fresh value, because the cache was updated as part of the write.
3. In write-behind, the app writes to the cache and the write is confirmed straight away, before the database is touched.
4. The cache flushes the changes to the database later, often batching several changes to one key into a single database write.

So write-through trades write speed for fresh reads, while write-behind trades durability for write speed.

## Example

A view counter changes 500 times in 10 seconds.

- **Write-through:** 500 cache writes and 500 database writes. Every read is fresh, but the database takes every write.
- **Write-behind**, flushing every 10 seconds: 500 cache writes but 1 database write, because the changes collapse. If the cache crashes before the flush, those 500 views are lost.

What to notice:

- Write-through does one database write per change, so a write-heavy counter floods the database; write-behind collapses them into one.
- The saving of write-behind comes from batching repeated changes to the same key within the delay window.
- The risk of write-behind is the gap before the flush, when the cache holds the only copy. For a view count that is fine; for a payment it is not.

## Rules and defaults

- **Write-through durability:** the write is durable when confirmed, because the database already has it.
- **Write-behind durability:** the write is not durable until the flush; size the flush interval by how much loss you can accept.
- **Cold data:** write-through caches everything written, much of it never read, so set a TTL to drop cold entries.
- **Empty cache node:** write-through only fills keys that are written after the node starts, so pair it with lazy loading to serve keys written before.

## Interview Qs

### Write-through vs write-behind?

Write-through confirms a write only after the cache and the database both have it: fresh reads, but slower writes. Write-behind confirms after the cache write and flushes to the database later in batches: fast writes and far fewer database writes, but data is lost if the cache fails before the flush.

### When would you use write-behind?

For write-heavy data where losing the last few seconds is acceptable, such as view counts, likes or metrics. The batching turns many writes into one and keeps the write path fast. Not for payments or orders, where the database must hold the write before you confirm it to the user.

### What problems does write-through bring?

Every write pays for two writes, cache and database, so it is slower. It also caches everything written, most of which is never read, so the cache fills with cold data; a TTL drops it. And a new cache node starts empty for keys written earlier, so you pair write-through with lazy loading.
