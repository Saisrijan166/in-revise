## What it is

Publish-subscribe (pub/sub) is a way to send one event to many services at once. Publishers send a message to a named channel called a **topic**, not to any particular service. Services that want those events **subscribe** to the topic, and the broker delivers a copy to each of them. The publisher never learns who the subscribers are, so they are fully decoupled. Sending one message to many destinations this way is called **fan-out**.

## Why it exists

When one event, like a payment being captured, matters to several services, the payment service could call billing, then analytics, then email directly. But now it knows about all three, must handle each one being slow or down, and must be changed every time a new consumer appears. With pub/sub it instead announces the event once to a topic and moves on. Each interested service subscribes on its own, so adding or removing a consumer never touches the publisher.

## How it works

1. A publisher sends an event to the topic and returns; it does not wait for any subscriber.
2. The broker copies the event once into every subscription attached to the topic.
3. Each subscriber reads from its own copy at its own pace, so a slow subscriber does not hold up the others.
4. If several workers share one subscription, they split that subscription's messages between them, exactly like a queue.
5. To add a new reaction, a new service just subscribes; the publisher is unchanged.

## Example

A common real setup is an SNS topic with one SQS queue per service, so each service reads durably at its own pace.

- The payment service publishes `PaymentCaptured` once to the `payments` topic.
- Ledger, analytics and email each own an SQS queue subscribed to the topic, so each gets its own copy.
- Later, a new fraud service subscribes a fourth queue. The payment service is not changed at all.
- If email is down for an hour, its queue holds the messages (SQS keeps them for 4 days by default), so nothing is lost.

What to notice:

- The fan-out is one copy **per subscription**, not one shared pool, so every service sees every payment.
- Giving each subscriber its own SQS queue is what makes the subscription **durable**; a down subscriber catches up later.
- A filter policy on a subscription can drop messages it does not care about, so a service receives only the events it wants.

## Rules and defaults

- **Every subscription gets every message:** unless the subscription sets a filter policy to narrow it (Amazon SNS).
- **Delivery and order:** Google Cloud Pub/Sub is at-least-once and does not keep order unless you set ordering keys. Make subscribers idempotent, or use FIFO topics with FIFO queues for strict order.
- **Ack deadline:** Google Cloud Pub/Sub hides a delivered message for 10 s by default (up to 600 s); if the subscriber does not acknowledge in time, it is delivered again.
- **Durable vs fire-and-forget:** a durable subscription (SNS+SQS, Google Pub/Sub) keeps messages for an offline subscriber; [Redis Pub/Sub](card:fire-and-forget-pubsub) is at-most-once, so an offline subscriber simply misses them.

## Not to be confused with

In a [message queue](card:message-queue), each message goes to one consumer and workers share the load. In pub/sub, each subscription gets its own copy, so many services react to one event. Rule: a queue divides work among workers; pub/sub broadcasts an event to many services. Many systems combine both: a topic fans out into one queue per service.

## Common mistakes

- **"A new subscriber will see the events from before it joined."** Usually not. A plain subscription receives only messages published after it subscribed; to replay older events you need a kept log, which is what an [event stream](card:event-streaming) gives you.

## Interview Qs

### How is pub/sub different from a message queue?

In a queue each message goes to one consumer, so workers share the load. In pub/sub every subscription gets its own copy, so many services react to the same event. Many systems combine them: a topic fans out into one queue per service, giving both broadcast and per-service load sharing.

### How do you stop a subscriber that is down from losing events?

Give it a durable subscription: an SQS queue behind an SNS topic, or a Google Pub/Sub subscription, which keeps unacknowledged messages (Google Pub/Sub for 7 days by default). The messages wait until the subscriber returns. Fire-and-forget pub/sub, like Redis Pub/Sub, drops messages for offline subscribers.

### Does pub/sub keep order and deliver each message once?

Not by default. Google Pub/Sub is at-least-once and unordered unless you set ordering keys. For strict order use ordering keys, or SNS FIFO topics with SQS FIFO queues. Either way make subscribers idempotent, because at-least-once delivery can repeat a message.
