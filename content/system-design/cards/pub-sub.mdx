## Why it exists

When one event, like an order placed, matters to many services, calling each one directly ties the sender to all of them. Pub/sub lets the sender announce the event once and not care who listens.

## How it works

<Mermaid
  alt="Pub/sub fan-out. The order service publishes one OrderPlaced message to the orders topic. The topic copies it into three queues: billing, stock and email. Each queue feeds its own service: billing, inventory and email."
  chart={`flowchart TD
  P[Order service] -- "publish OrderPlaced" --> T{{"Topic: orders"}}
  T -- copy --> S1[(Billing queue)]
  T -- copy --> S2[(Stock queue)]
  T -- copy --> S3[(Email queue)]
  S1 --> B[Billing]
  S2 --> I[Inventory]
  S3 --> E[Email]`}
/>

- Each [subscription](card:subscription) gets every message. Workers that share one subscription split its messages, like a queue.
- A common setup: the topic feeds [one queue per service](card:topic-to-queues) (SNS + SQS), so each service reads at its own pace.
- Durable subscriptions keep messages for a subscriber that is down. [Redis Pub/Sub](card:fire-and-forget-pubsub) does not: an offline subscriber misses them.

## Analogy

<Analogy title="A newspaper subscription" limit="Live pub/sub such as Redis Pub/Sub is more like radio: if you are not listening, you miss it.">
The paper is printed once, and every subscriber gets a copy at their own door. The newsroom does not know who reads it, and a new reader just signs up.
</Analogy>

## Example

The fan-out from the Amazon SNS docs, with one SQS queue per service:

- The order service publishes `OrderPlaced` once to the `orders` topic.
- Billing, inventory and email each own a queue subscribed to it: three copies.
- Later, analytics subscribes a fourth queue. The order service does not change.
- Email is down for an hour? Its queue keeps the messages (SQS: 4 days by default).

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Who gets a message | Every subscriber, unless it sets a filter policy | Amazon SNS |
| Ack deadline | 10 s (up to 600 s) | Google Cloud Pub/Sub |
| How long unacked messages are kept | 7 days (10 minutes to 31 days) | Google Cloud Pub/Sub |
| Delivery and order | At-least-once; no ordering unless you set ordering keys | Google Cloud Pub/Sub |
| Delivery attempts before dead-lettering | 5 (5 to 100), when a dead-letter topic is set | Google Cloud Pub/Sub |
| Delivery | At-most-once: an offline subscriber misses the message | Redis Pub/Sub |

## Interview Qs

### How is pub/sub different from a message queue?

In a queue, each message goes to one consumer: workers share the load. In pub/sub, every subscription gets its own copy: many services react to one event. Many systems combine them: a topic fans out into one queue per service.

### How do you make sure a subscriber that is down does not lose events?

Give it a durable subscription: an SQS queue behind an SNS topic, or a Google Pub/Sub subscription, which keeps unacked messages for 7 days by default. Fire-and-forget pub/sub, like Redis Pub/Sub, drops messages for offline subscribers.

### Does pub/sub keep order and deliver each message once?

Not by default. Google Pub/Sub is at-least-once and unordered unless you set ordering keys. For strict order, use ordering keys, or SNS FIFO topics with SQS FIFO queues. Either way, make subscribers idempotent.
