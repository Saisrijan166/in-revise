## Why it exists

After a timeout, the client cannot tell whether the server did the work. The only way forward is to retry, and without idempotency a retry can charge a card or create an order twice.

## How it works

<Mermaid
  alt="Idempotency key flow. A POST to /payments arrives with an Idempotency-Key header K. If K is new, the server claims K atomically, charges the card once, saves K with the response, and returns it. If K was seen and the first request finished, the server returns the saved response. If K was seen and the first request is still running, the server answers 409 Conflict and the client retries later."
  chart={`flowchart TD
  R(["POST /payments with Idempotency-Key K"]) --> S{Seen key K?}
  S -- new --> CL[Claim K atomically]
  CL --> PAY[Charge the card once]
  PAY --> SAVE[Save K with the response]
  SAVE --> OUT([Return the response])
  S -- finished --> REP([Return the saved response])
  S -- running --> BUSY(["409 Conflict: retry later"])`}
/>

- **Some writes are idempotent already:** `PUT /users/42` sets a value, so repeats are harmless. `balance += 100` is not.
- **POST is not,** but an idempotency key makes a POST endpoint safe to retry. The `Idempotency-Key` header is an IETF draft, not yet an RFC; Stripe and Adyen already use it.

## Example

```java
Response pay(String key, PaymentRequest req) {
    String hash = req.fingerprint();
    // atomic: only one request can claim a new key (unique insert or SET NX)
    Saved old = store.putIfAbsent(key, Saved.running(hash));
    if (old != null) {
        if (!old.hash().equals(hash)) return Response.status(422); // key reused
        if (old.running()) return Response.status(409);             // still running
        return old.response();                                      // replay result
    }
    Response res = payments.charge(req);                            // once per key
    store.put(key, Saved.done(hash, res), Duration.ofHours(24));
    return res;
}
```

```python
def pay(key, req):
    fp = req.fingerprint()
    # atomic: only one request can claim a new key (unique insert or SET NX)
    old = store.put_if_absent(key, {"hash": fp, "state": "running"})
    if old is not None:
        if old["hash"] != fp:
            return Response(status=422)       # key reused with a new body
        if old["state"] == "running":
            return Response(status=409)       # first try still running
        return old["response"]                # replay the saved result
    res = payments.charge(req)                # runs once per key
    store.set(key, {"hash": fp, "state": "done", "response": res}, ttl=24 * 3600)
    return res
```

## Defaults

| What | Value | Where |
| --- | --- | --- |
| Idempotent methods | GET, HEAD, OPTIONS, TRACE, PUT, DELETE | RFC 9110 |
| Not idempotent | POST (RFC 9110), PATCH (RFC 5789) | HTTP |
| Key length | Up to 255 characters | Stripe API v1 |
| How long a key is kept | May be pruned once at least 24 hours old | Stripe API v1 |
| What is replayed | Status and body of the first run, even a 500 | Stripe API v1 |
| Same key, different body | 422 Unprocessable Content | IETF draft |
| Retry while the first still runs | 409 Conflict | IETF draft |

## Interview Qs

### Which HTTP methods are idempotent?

GET, HEAD, OPTIONS and TRACE (the safe, read-only ones), plus PUT and DELETE. POST is not, and PATCH is not by default. Idempotent means repeats have the same effect on the server, not that every response is identical.

### How do you stop a retried payment from charging twice?

The client creates a UUID idempotency key per payment and sends it on every retry. The server claims the key atomically, charges once, stores the response with the key, and returns that saved response for any retry.

### Two requests with the same key arrive at once. What happens?

With check-then-insert, both can pass the check and both charge. Claim the key atomically, with a unique insert or Redis `SET NX`, so only one wins. The other gets 409 Conflict and retries later.

### Is idempotency the same as exactly-once delivery?

No. Retries and redelivery mean a message can arrive more than once (at-least-once). An idempotent receiver makes the repeats harmless, so the effect happens once.
