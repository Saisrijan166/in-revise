## What it is

An operation is **idempotent** when running it twice leaves the server in the same state as running it once. `GET /users/42` is idempotent: reading twice changes nothing. `PUT /users/42` that sets a value is too: setting the same value again is a no-op. But `POST /payments` that charges a card is not, because a second POST charges again. Idempotency is the property that lets a client retry a request without doing harm.

## Why it exists

When a request times out, the client cannot tell whether the server finished the work or never got it. A failed response does not mean the operation failed: a payment may have succeeded even though the reply timed out. The only safe recovery is to retry, and without idempotency a retry can charge a card or create an order twice. Making a write idempotent removes that risk, so retrying after a timeout, the normal way to recover, becomes safe.

## How it works

A naturally idempotent write, like `PUT`, needs nothing. To make a `POST` safe, you add an **idempotency key**: a unique ID the client picks for the operation and sends on every attempt, including retries.

1. The client generates a unique key (such as a UUID) for this payment and sends it in the `Idempotency-Key` header.
2. The server tries to claim the key atomically. If it is new, the server charges the card once and saves the key together with the response.
3. A retry carries the same key. The server finds it already stored and returns the saved response, so the card is not charged again.

## Example

A tiny payment handler stores each key with its result and replays it on a retry. The real output below is from running both versions.

```java
static Map<String,String> store = new HashMap<>();
static int charges = 0;

static String pay(String key) {
    String saved = store.get(key);
    if (saved != null) return saved;   // replay: no second charge
    String result = charge();          // runs once per key
    store.put(key, result);
    return result;
}
// pay("order-123"); pay("order-123");  // first charges, retry replays
```

```python
store, charges = {}, 0

def pay(key):
    saved = store.get(key)
    if saved is not None:
        return saved          # replay: no second charge
    result = charge()         # runs once per key
    store[key] = result
    return result
# pay("order-123"); pay("order-123")  # first charges, retry replays
```

```text output
{status=200, paymentId=pay_1}
{status=200, paymentId=pay_1}
total charges: 1
```

What to notice:

- The second `pay("order-123")` returns `pay_1` again and `charges` stays 1: the retry replayed the stored result instead of charging.
- The whole guarantee rests on `charge()` running only when the key is new. If you removed the `store.get` check, each call would charge and `charges` would be 2.
- This map is single-threaded. A real server needs the claim to be atomic (a unique DB insert or Redis `SET NX`), or two concurrent retries could both pass the check and both charge.

## Rules and defaults

- **Idempotent HTTP methods:** GET, HEAD, OPTIONS, TRACE, PUT and DELETE are defined idempotent by RFC 9110; POST (RFC 9110) and PATCH (RFC 5789) are not.
- **Safe is not the same as idempotent:** safe means read-only (GET); PUT and DELETE change data yet repeat safely, so they are idempotent but not safe.
- **A key alone is not enough:** the server must claim it atomically, persist the outcome, and define how long keys are kept, or concurrent duplicates still slip through.
- **Stripe's key rules (as a concrete example):** a key is up to 255 characters, the first response (even a 500) is replayed for later retries, and a key may be pruned once it is at least 24 hours old.

## Interview Qs

### Which HTTP methods are idempotent, and what does that actually guarantee?

GET, HEAD, OPTIONS and TRACE (the safe, read-only ones), plus PUT and DELETE. POST is not, and PATCH is not by default. Idempotent guarantees that repeats have the same effect on server state, not that every response is byte-for-byte identical: a second DELETE may return 404.

### How do you stop a retried payment from charging twice?

The client creates a unique idempotency key per payment and sends it on every attempt. The server claims the key atomically, charges once, stores the response with the key, and returns that stored response for any retry carrying the same key. So the charge happens exactly once however many times the client retries.

### Two requests with the same key arrive at the same instant. What happens?

With a plain check-then-insert, both can read "key not seen", both pass, and both charge. You must claim the key atomically: a unique database insert or Redis `SET NX`, so only one request creates the key. The other gets a 409 Conflict and retries, by which time the first result is stored.

### Is idempotency the same as exactly-once delivery?

No. Retries and message redelivery mean a request can arrive more than once (at-least-once). You rarely get true exactly-once delivery over a network. An idempotent receiver makes the duplicates harmless, so the effect happens once even though the message may arrive several times.
