## What it is

These are four ways to get updates from a server to a browser. Plain HTTP is request-and-response: the client asks and the server answers, then the exchange ends, so the server cannot speak on its own. Short polling and long polling work within that rule by having the client keep asking. [SSE](term:sse) and [WebSockets](term:websockets) instead keep a connection open: SSE streams events one way over a normal HTTP response; WebSockets open a two-way channel over one TCP connection, where either side can send at any time.

## Why it exists

Chat messages, notifications and live scores happen on the server's schedule, not the client's. With plain HTTP the only way to show them is to poll: ask every few seconds and hope something is new. That wastes requests and still shows updates late, by up to one poll interval. These techniques let the server deliver data the moment it has it.

## How it works

<Compare id="realtime-options" />

1. **Short polling:** the client asks on a fixed timer; the server answers at once, usually "nothing new", so most requests are wasted.
2. **Long polling:** the client asks once; the server holds the request open until it has news or a timeout, then answers, and the client asks again.
3. **SSE:** the client opens one GET and the server keeps the response open, writing event after event; on a drop the browser reconnects with `Last-Event-ID`.
4. **WebSockets:** the client sends `Upgrade: websocket`; the server replies `101 Switching Protocols`, and that TCP connection then carries two-way messages.

So the key is whether only the server sends (SSE) or both sides do (WebSockets).

## Analogy

<Analogy title="A long car trip" limit="A car has one child asking; a server holds thousands of open connections at once, and each one uses memory and a socket.">
Short polling is a child asking "are we there yet?" every minute. Long polling is asking once and getting an answer only on arrival. SSE is the driver announcing each town as you pass it. WebSockets is a real conversation: both sides talk whenever they like.
</Analogy>

## Example

An SSE stream is just a long HTTP response made of text events, each ending with a blank line:

```text
retry: 5000
id: 42
event: score
data: {"home": 2, "away": 1}

: a comment line every 15 s or so keeps quiet streams open
```

What to notice:

- `retry: 5000` tells the browser to wait 5 seconds before reconnecting if the stream drops; `id: 42` is the last event ID the browser resends on reconnect so the server can resume.
- The blank line ends one event; without it the browser keeps buffering and never fires the event.
- This is one open response, not a new request per event, which is what makes it cheaper than polling.

Behind nginx, a WebSocket needs the upgrade headers forwarded, or the handshake fails:

```nginx
location /ws/ {
    proxy_pass http://chat_servers;
    proxy_http_version 1.1;                  # Upgrade needs HTTP/1.1
    proxy_set_header Upgrade $http_upgrade;  # hop-by-hop: nginx drops it unless you pass it
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 1h;                   # default 60s would close a quiet socket
}
```

What to notice:

- `Upgrade` and `Connection` are hop-by-hop headers that nginx does not forward by default, so without these two lines the `101 Switching Protocols` handshake never completes.
- `proxy_read_timeout 1h` stops nginx closing a quiet chat connection; the 60 s default is the usual cause of a socket dropping after about a minute.

## Rules and defaults

- **Idle timeout:** AWS ALB and nginx both close a connection after 60 s with no data; raise the timeout or send periodic pings.
- **SSE connection limit:** HTTP/1.1 allows about 6 connections per domain, so many SSE streams can exhaust them; HTTP/2 multiplexes them over one connection (nginx caps streams at 128 by default).
- **SSE reconnect:** the browser reconnects automatically; the delay is browser-defined ("a few seconds") unless a `retry:` field sets it.
- **WebSocket ports:** `ws://` uses port 80 and `wss://` uses port 443, the same ports as HTTP and HTTPS (RFC 6455).
- **Scaling:** an open connection is bound to one server, so to broadcast across servers you must publish events to a shared pub/sub such as Redis.

## Not to be confused with

SSE and WebSockets both keep a connection open, but SSE is one-way (server to client) over a plain HTTP response, while a WebSocket is two-way over a single TCP connection after an Upgrade handshake. Rule: polling re-asks, SSE streams one way, WebSockets talk both ways.

## Interview Qs

### Long polling versus SSE versus WebSockets?

Long polling: the server holds a normal request open until there is news, then the client asks again. SSE: one open HTTP response, server to client only, with automatic reconnect. WebSockets: one two-way connection for frequent messages in both directions, such as chat. Pick SSE for server-only pushes and WebSockets when the client also sends often.

### How do you scale WebSockets across many servers?

Put the servers behind a load balancer; each holds a share of the connections. Because a connection lives on one server, publish every event to a pub/sub such as Redis, so the server holding a user's connection delivers it. Send pings to keep quiet connections alive, and have clients reconnect with backoff.

### Why does a WebSocket drop after about a minute?

A proxy or load balancer closed it as idle: nginx and AWS ALB both default to 60 seconds with no data. Fix it by sending ping frames more often than the timeout, or by raising `proxy_read_timeout` or the ALB idle timeout. nginx also needs the `Upgrade` and `Connection` headers forwarded.

### Why not use WebSockets for everything?

Each connection is stateful and pinned to one server, so deploys, load balancing and scaling get harder, and proxies need extra setup. For server-only updates, SSE or long polling over plain HTTP is simpler and reconnects for free. Use WebSockets when clients also send often.
