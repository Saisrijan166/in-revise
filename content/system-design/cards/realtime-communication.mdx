## Why it exists

HTTP is request and response: the server can only answer when the client asks. Chat, notifications and live scores need the server to send data the moment something happens.

## How it works

<Compare id="realtime-options" />

- **Long polling** works even where proxies or firewalls block WebSockets, but every message pays for a full set of HTTP headers.
- **SSE** is one HTTP response that never ends. If it drops, the browser reconnects and sends `Last-Event-ID`, so the server can resume.
- **Many servers:** a user's connection sits on one server. Publish events to pub/sub, such as Redis, so whichever server holds it can push.

## Analogy

<Analogy title="A long car trip" limit="A car has one passenger asking; a server holds thousands of open connections at once, and each one uses server resources.">
Short polling is a child asking "are we there yet?" every minute. Long polling is asking once and getting the answer only on arrival. SSE is the driver announcing each town as you pass. WebSockets is a real conversation: both sides talk whenever they like.
</Analogy>

## Example

An SSE stream is plain text. Each event ends with a blank line:

```text
retry: 5000
id: 42
event: score
data: {"home": 2, "away": 1}

: a comment line every 15 s or so keeps quiet streams open
```

Behind nginx, a WebSocket needs the upgrade headers passed on:

```nginx
location /ws/ {
    proxy_pass http://chat_servers;
    proxy_http_version 1.1;                  # the default only from nginx 1.29.7
    proxy_set_header Upgrade $http_upgrade;  # hop-by-hop: not forwarded by itself
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 1h;                   # default 60s closes quiet sockets
}
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Idle connection closed after | 60 s (can be 1 to 4,000 s) | AWS Application Load Balancer |
| Quiet upstream closed after | 60 s | nginx `proxy_read_timeout` |
| SSE connections per browser, per domain | 6 on HTTP/1.1; HTTP/2 negotiates streams (default 100) | Browsers (MDN) |
| SSE reconnect delay | Browser-defined, "a few seconds"; `retry:` changes it | HTML Standard |
| WebSocket ports | 80 for `ws://`, 443 for `wss://` | RFC 6455 |

## Interview Qs

### Long polling vs SSE vs WebSockets?

Long polling: the server holds a normal request until there is news, then the client asks again. SSE: one open HTTP response, server to client only, with automatic reconnect. WebSockets: one two-way connection for frequent messages both ways, such as chat.

### How do you scale WebSockets across many servers?

Put servers behind a load balancer; each holds a share of the connections. Publish every event to pub/sub, such as Redis, so the server holding the user's connection delivers it. Send pings to keep quiet connections alive, and let clients reconnect with backoff.

### Why does a WebSocket drop after about a minute?

A proxy or load balancer closed it as idle: nginx and AWS ALB both default to 60 seconds without data. Send ping frames more often, or raise `proxy_read_timeout` or the ALB idle timeout. nginx also needs the Upgrade and Connection headers set.

### Why not use WebSockets for everything?

Each connection is stateful and pinned to one server, so deploys, load balancing and scaling get harder, and proxies need extra setup. For one-way updates, SSE or long polling over plain HTTP is simpler. Use WebSockets when clients also send often.
