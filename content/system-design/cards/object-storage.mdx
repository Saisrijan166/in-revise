## Why it exists

Photos, videos and backups are too big for database rows and too many for one server's disk. Object storage keeps any number of files durably behind a simple HTTP API.

## How it works

<Mermaid
  alt="Direct upload with a presigned URL. 1: the client asks the app server to upload. 2: the app returns a presigned PUT URL. 3: the client PUTs the file straight into the bucket. 4: the client tells the app it is done. 5: the app saves the key and metadata in the database. 6: viewers download through a CDN, which fetches from the bucket on a cache miss."
  chart={`flowchart TD
  C[Client] -- "1. ask to upload" --> A[App server]
  A -- "2. presigned PUT URL" --> C
  C -- "3. PUT the file" --> S[(Bucket)]
  C -- "4. done" --> A
  A -- "5. save key and metadata" --> DB[(Database)]
  V[Viewer] -- "6. GET" --> CDN[CDN]
  CDN -- "cache miss" --> S`}

- **Big files:** multipart upload sends parts in parallel; only a failed part is resent.
- **Cost:** lifecycle rules move old objects to cheaper storage classes, or delete them.
- **No shared transaction** between the bucket and the database: clean up orphaned objects if a step fails.

## Example

Give the client a URL that can PUT one file for 10 minutes:

```java
String uploadUrl(S3Presigner presigner, String key) {
    PutObjectRequest put = PutObjectRequest.builder()
            .bucket("media").key(key).contentType("image/jpeg").build();
    PutObjectPresignRequest req = PutObjectPresignRequest.builder()
            .signatureDuration(Duration.ofMinutes(10))
            .putObjectRequest(put).build();
    return presigner.presignPutObject(req).url().toString();
}
```

```python
def upload_url(s3, key):  # s3 = boto3.client("s3")
    return s3.generate_presigned_url(
        "put_object",
        Params={"Bucket": "media", "Key": key, "ContentType": "image/jpeg"},
        ExpiresIn=600,  # seconds
    )
```

The client must send the same `Content-Type` with its `PUT`, or the signature check fails.

## Defaults

| What | Default or limit | Where |
| --- | --- | --- |
| New bucket access | Private; Block Public Access on | Amazon S3 |
| Storage class on upload | S3 Standard | Amazon S3 |
| One PUT | Up to 5 GB | Amazon S3 |
| Multipart parts | 5 MiB to 5 GiB each, up to 10,000 | Amazon S3 |
| Largest object | 48.8 TiB (10,000 parts of 5 GiB) | Amazon S3 |
| Presigned URL lifetime | Up to 7 days (SDK, CLI); 12 hours (console) | Amazon S3, Signature Version 4 |

## Interview Qs

### Why not store images in the database?

Large files bloat the database, its backups and its memory, and every byte flows through your servers. Object storage holds any number of objects, is built for very high durability and works with a CDN. Keep only the key and metadata in the database.

### How does a user upload a 2 GB video?

The app hands out presigned URLs, and the client uploads straight to the bucket with multipart upload: parts in parallel, resending only failed parts. Then the app marks the file ready, on the client's call or a bucket event. A lifecycle rule removes uploads that never finish.

### Is S3 eventually consistent?

Not since December 2020. After a successful PUT or DELETE, every read and list sees the change. Bucket settings are still eventually consistent, and two writes to the same key at once end with the latest one winning.

### Object, block or file storage?

Block: a disk volume a server mounts, like Amazon EBS, for databases and virtual machines. File: shared folders many machines use at once, like Amazon EFS. Object: whole files by key over HTTP, like S3, for large amounts of unstructured data such as media and backups.
