## Why it exists

Remote calls sometimes hang or fail for a moment. Without a timeout, a hung call holds a thread forever; with careless retries, many clients can flatten a service that was about to recover.

## How it works

<Mermaid
  alt="Retry loop. Make the call with a timeout. On success, return the result. On failure, check three things: is the error transient, is the call safe to retry, and are attempts left? If not, fail and return the error. If yes, wait a random time between 0 and the backoff, double the backoff, and call again."
  chart={`flowchart TD
  C[Call with a timeout] --> S{Success?}
  S -- yes --> R([Return result])
  S -- no --> T{"Transient error, safe to retry, attempts left?"}
  T -- no --> F([Return the error])
  T -- yes --> W["Wait random(0, backoff), then double the backoff"]
  W --> C`}
/>

- **Timeout** frees the thread so you can decide: retry, fall back, or fail. Set a connect timeout and a request timeout.
- **Backoff** gives the service time to recover. **Jitter** spreads out clients that failed at the same moment.
- **Limit** retries: a few attempts, at one layer only, inside a retry budget. Google's SRE book keeps each client's retries under 10% of its requests.
- **Deadline propagation:** pass the time left to each downstream call, so no service keeps working after the caller gave up.

## Example

Capped exponential backoff with full jitter:

```java
<T> T callWithRetry(Supplier<T> call) throws InterruptedException {
    long baseMs = 100, capMs = 5_000;
    int maxAttempts = 3;                               // 1 call + 2 retries
    for (int attempt = 0; ; attempt++) {
        try {
            return call.get();                         // the call has its own timeout
        } catch (TransientException e) {               // never retry a 400 or 404
            if (attempt + 1 >= maxAttempts) throw e;
            long backoff = Math.min(capMs, baseMs << attempt);         // 100, 200, 400...
            Thread.sleep(ThreadLocalRandom.current().nextLong(backoff + 1)); // full jitter
        }
    }
}
```

```python
import random
import time

def call_with_retry(call, max_attempts=3, base=0.1, cap=5.0):
    for attempt in range(max_attempts):          # 1 call + 2 retries
        try:
            return call()                        # the call has its own timeout
        except TransientError:                   # never retry a 400 or 404
            if attempt + 1 == max_attempts:
                raise
            backoff = min(cap, base * 2 ** attempt)   # 0.1, 0.2, 0.4 s...
            time.sleep(random.uniform(0, backoff))    # full jitter
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Request timeout | None: waits forever | Java 21 `HttpRequest` without `timeout(...)` |
| Request timeout | None: waits forever | Python `requests` without `timeout=` |
| Call deadline | None: can wait forever | gRPC |
| Retry attempts | 3 in total, fixed 500 ms wait | Resilience4j 2.x Retry |
| Which errors are retried | Every exception, unless you configure it | Resilience4j 2.x Retry |

## Interview Qs

### How do you choose a timeout?

Measure the dependency's latency and pick a high percentile, such as p99.9, so only about 0.1% of healthy calls time out. Too high wastes threads while waiting; too low causes false failures and extra retries.

### Why add jitter to exponential backoff?

Clients that failed at the same moment also back off by the same amounts, so they retry together in spikes. Jitter randomises each wait, so retries arrive as a smooth trickle. In AWS's simulation it more than halved the total number of calls.

### Which errors should you retry?

Transient ones: timeouts, connection resets, 502, 503 and 504, and 429 after its Retry-After delay. Not 400, 401, 403 or 404: the same request will fail again. And only when the call is idempotent.

### What is a retry storm, and how do you stop it?

Many clients retry at once and keep a struggling service overloaded. Cap the attempts, use backoff with jitter, retry at one layer only, add a retry budget, and put a circuit breaker in front so calls stop while the service is down.
