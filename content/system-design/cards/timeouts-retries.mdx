## What it is

A timeout is a limit on how long one call may wait for a reply; when the limit passes, the caller gives up on that call instead of waiting on. A retry is a fresh attempt after a failed call. Backoff means waiting longer before each retry, and jitter means adding a little randomness to that wait. Together they decide what the payment service does when a call to the card gateway hangs or fails for a moment.

## Why it exists

Remote calls sometimes hang or fail briefly. Without a timeout, a hung call holds its thread and connection forever, and enough hung calls use up every thread until the caller itself stops responding. Retries recover from a short blip, but careless retries do the opposite harm: many clients retrying at once can flatten a service that was just about to recover. Backoff and jitter make retries gentle enough to help rather than hurt.

## How it works

1. Make the call with both a connect timeout and a request timeout set.
2. If it succeeds, return the result.
3. If it fails, retry only when the error is transient (a timeout or a 503, not a 404), the call is idempotent, and attempts remain.
4. Before each retry, sleep a random time between 0 and the current backoff, then double the backoff up to a cap.

So the key is to retry at one layer only, inside a [retry budget](term:retry-budget): the Google SRE book keeps each client's retries under 10% of its requests.

## Example

Capped exponential backoff with full jitter, around a call that already has its own timeout:

```java
<T> T callWithRetry(Supplier<T> call) throws InterruptedException {
    long baseMs = 100, capMs = 5_000;
    int maxAttempts = 3;                               // 1 call + 2 retries
    for (int attempt = 0; ; attempt++) {
        try {
            return call.get();                         // the call has its own timeout
        } catch (TransientException e) {               // never retry a 400 or 404
            if (attempt + 1 >= maxAttempts) throw e;
            long backoff = Math.min(capMs, baseMs << attempt);        // 100, 200, 400...
            Thread.sleep(ThreadLocalRandom.current().nextLong(backoff + 1)); // full jitter
        }
    }
}
```

```python
import random, time

def call_with_retry(call, max_attempts=3, base=0.1, cap=5.0):
    for attempt in range(max_attempts):          # 1 call + 2 retries
        try:
            return call()                        # the call has its own timeout
        except TransientError:                   # never retry a 400 or 404
            if attempt + 1 == max_attempts:
                raise
            backoff = min(cap, base * 2 ** attempt)   # 0.1, 0.2, 0.4 s...
            time.sleep(random.uniform(0, backoff))    # full jitter
```

What to notice:

- `baseMs << attempt` doubles the backoff each attempt (100, 200, 400ms), and `Math.min(capMs, ...)` stops it growing without bound.
- The sleep is a random value between 0 and the backoff (full jitter), so two clients that failed together do not retry at the same instant.
- Only `TransientException` is caught and retried; a 400 or 404 is rethrown at once, because repeating it would fail the same way.
- Remove the jitter and keep a fixed wait, and all clients retry in a synchronised spike that can re-overload the service.

## Rules and defaults

- **Java 21 `HttpRequest`:** no request timeout unless you call `timeout(...)`; without it the call can wait forever.
- **Python `requests`:** no timeout unless you pass `timeout=`; without it the call can wait forever.
- **Resilience4j 2.x Retry:** 3 attempts in total with a fixed 500ms wait, and it retries every exception unless you configure which ones.
- **Deadline propagation:** pass the time remaining to each downstream call, so no service keeps working on a request after the original caller has already given up.

## Common mistakes

- **"Retry every error."** A 400, 401, 403 or 404 will fail the same way on every attempt, so retrying only wastes work. Retry only transient errors: timeouts, connection resets, 502, 503, 504, and 429 after its `Retry-After` delay.
- **"More retries means more reliable."** Stacking retries at several nested layers multiplies the load (4x4x4 = 64 calls on the bottom service) and can cause a retry storm. Retry at one layer, cap the attempts, and put a [circuit breaker](card:circuit-breaker) in front.

## Interview Qs

### How do you choose a timeout value?

Measure the dependency's latency and pick a high percentile, such as p99.9, so only about 0.1% of healthy calls time out. Too high wastes threads waiting on stuck calls; too low turns slightly slow but healthy calls into false failures and extra retries.

### Why add jitter to exponential backoff?

Clients that failed at the same moment also back off by the same amount, so they retry together in sharp spikes that can re-overload the service. Jitter randomises each wait, so retries arrive as a smooth trickle instead. In AWS's simulation, adding jitter more than halved the total number of calls.

### What is a retry storm, and how do you stop it?

Many clients retry at once and keep a struggling service overloaded, so it never recovers. Cap the attempts, use backoff with jitter, retry at one layer only, add a retry budget that limits retries to a small fraction of requests, and put a circuit breaker in front so calls stop while the service is down.
