## Why it exists

Rows, orders and messages need an ID the moment they are created. With one database, a counter is enough; with many servers and shards, each server must make IDs on its own without ever repeating one.

## How it works

<Compare id="id-generation-options" />

- **UUID v7** (RFC 9562, 2024) starts with a 48-bit Unix time in milliseconds, then random bits, so IDs sort by creation time, to the millisecond.
- **Snowflake:** each generator packs time, its machine id and a sequence into 64 bits, and makes up to 4,096 IDs per millisecond.
- **Counters across servers:** Flickr ran two ticket servers, one handing out odd IDs and one even (step 2, offsets 1 and 2).

## Example

Pack a Snowflake ID, and make UUIDs:

```java
static final long EPOCH = 1288834974657L;     // Twitter's custom epoch (Nov 2010), ms

long snowflake(long nowMs, long machineId, long sequence) {
    return ((nowMs - EPOCH) << 22)   // 41 bits: ms since EPOCH
         | (machineId << 12)         // 10 bits: 0 to 1023
         | sequence;                 // 12 bits: 0 to 4095 in the same ms
}

UUID random = UUID.randomUUID();                              // v4
UUID timed = UUID.ofEpochMillis(System.currentTimeMillis());  // v7, Java 26+
```

```python
import uuid

EPOCH = 1288834974657  # Twitter's custom epoch (Nov 2010), ms

def snowflake(now_ms: int, machine_id: int, sequence: int) -> int:
    return ((now_ms - EPOCH) << 22) | (machine_id << 12) | sequence

random_id = uuid.uuid4()  # v4
timed_id = uuid.uuid7()   # v7, Python 3.14+
```

Read the time back with `(id >> 22) + EPOCH`. 41 bits of milliseconds last about 69 years.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Counter step (`auto_increment_increment`) | 1 | MySQL 8.4 |
| Counter start (`auto_increment_offset`) | 1; set to the server ID in multi-primary Group Replication | MySQL 8.4 |
| `gen_random_uuid()` | Version 4 (random); `uuidv7()` added for version 7 | PostgreSQL 18 |

## Interview Qs

### Design a unique ID generator for a distributed system.

Use Snowflake-style 64-bit IDs: 41 bits of milliseconds since a custom epoch, 10 bits of machine id, 12 bits of sequence. Each server makes IDs locally, up to 4,096 per millisecond, with no coordination, and IDs sort roughly by time.

### UUID or auto-increment for a primary key?

Auto-increment is small and ordered, but needs one central counter and reveals how many rows exist. UUIDs can be made anywhere. If you pick UUIDs, prefer v7: time-ordered keys keep index inserts close together; random v4 keys do not.

### What if the server clock moves backwards?

The generator could repeat or reorder IDs. Twitter's Snowflake refuses to make IDs until the clock passes the last timestamp it used. Run NTP in a mode that never steps the clock backwards.

### Can a UUID be a secret token?

No. RFC 9562 says UUIDs must not be used as security capabilities. Random IDs make guessing harder, but you must still check permissions on every request.
