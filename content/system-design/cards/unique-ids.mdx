## What it is

Unique ID generation is how a system gives each new row, order or message an identifier that no other one shares. With a single database, a built-in counter does this easily. The hard case is a system split across many servers and [shards](card:sharding-and-replication): each server must create IDs on its own, without asking a central counter every time, and still never produce the same ID twice. The common choices are a database counter, a random UUID, and a time-ordered ID such as UUID v7 or Snowflake.

## Why it exists

A row needs an ID the instant it is created, before it is saved. With one database you let the database assign the next number, and that is simple and compact. But once writes are spread across many servers or shards, a single shared counter becomes a bottleneck and a single point of failure: every insert would have to wait on it. So you need IDs that each server can mint locally, that never clash, and ideally that still sort by time so they do not scatter writes across the whole index.

## How it works

<Compare id="id-generation-options" />

1. **Auto-increment** asks one database for the next number: compact and ordered, but central.
2. **UUID v4** fills 122 bits with randomness, so any server makes one alone, but the IDs have no order.
3. **UUID v7** (RFC 9562, 2024) puts a 48-bit Unix millisecond time first, then random bits, so IDs sort by creation time to the millisecond.
4. **Snowflake** packs 41 bits of time, a 10-bit machine id and a 12-bit per-millisecond sequence into 64 bits, letting each generator make up to 4,096 IDs per millisecond with no coordination.

So the key is: go local to avoid the central counter, and keep a timestamp first so IDs stay roughly ordered.

## Example

A Snowflake ID packs three fields into one 64-bit number, and you can read the fields back out.

```java
static final long EPOCH = 1288834974657L;     // Twitter's custom epoch (Nov 2010), ms

long snowflake(long nowMs, long machineId, long sequence) {
    return ((nowMs - EPOCH) << 22)   // 41 bits: ms since EPOCH
         | (machineId << 12)         // 10 bits: 0 to 1023
         | sequence;                 // 12 bits: 0 to 4095 within the same ms
}

UUID random = UUID.randomUUID();                              // v4, no order
UUID timed = UUID.ofEpochMillis(System.currentTimeMillis());  // v7, Java 26+
```

```python
import uuid

EPOCH = 1288834974657  # Twitter's custom epoch (Nov 2010), ms

def snowflake(now_ms: int, machine_id: int, sequence: int) -> int:
    return ((now_ms - EPOCH) << 22) | (machine_id << 12) | sequence

random_id = uuid.uuid4()  # v4, no order
timed_id = uuid.uuid7()   # v7, Python 3.14+
```

```text output
1724551110456266752
1724551110456266753
machine id back: 5
ms back: 1700000000000
```

What to notice:

- The two Snowflake IDs in the output differ only by their sequence (0 then 1) in the same millisecond, so they are unique and adjacent.
- `(id >> 12) & 0x3FF` reads the machine id back (5), and `(id >> 22) + EPOCH` reads the timestamp back; the fields are just bit ranges.
- 41 bits of milliseconds lasts about 69 years from the epoch, which is why Snowflake uses a recent custom epoch rather than 1970.

## Rules and defaults

- **MySQL 8.4 counter:** `auto_increment_increment` defaults to 1 and `auto_increment_offset` to 1; in multi-primary Group Replication you set the offset per server so counters do not collide.
- **PostgreSQL 18:** `gen_random_uuid()` returns a version 4 (random) UUID; `uuidv7()` was added for time-ordered version 7.
- **Built-in v7:** Python 3.14 added `uuid.uuid7()`, and Java 26 added `UUID.ofEpochMillis`.
- **Clock safety:** if the server clock steps backwards, a time-based generator could repeat or reorder IDs. Twitter's Snowflake refuses to issue IDs until the clock passes the last timestamp used, so run NTP in a mode that never steps the clock backwards.

## Not to be confused with

A unique ID guarantees that two IDs do not clash. An [idempotency](card:idempotency) key guarantees that retrying the same request has the same effect as sending it once. They are different jobs: an idempotency key is supplied by the client for one specific operation, while a unique ID is minted for each new entity. Rule: unique ID = this row is distinct; idempotency key = this request is the same one as before.

## Interview Qs

### Design a unique ID generator for a distributed system.

Use Snowflake-style 64-bit IDs: 41 bits of milliseconds since a custom epoch, 10 bits of machine id, 12 bits of sequence. Each server makes IDs locally, up to 4,096 per millisecond, with no coordination, and the IDs sort roughly by time, which keeps index inserts close together.

### UUID or auto-increment for a primary key?

Auto-increment is small and ordered but needs one central counter and reveals how many rows exist. UUIDs can be made anywhere with no coordination. If you choose UUIDs, prefer v7: time-ordered keys keep index inserts near each other, while random v4 keys scatter them across the index.

### What if the server clock moves backwards?

A time-based generator could then repeat or reorder IDs. Twitter's Snowflake refuses to issue IDs until the clock passes the last timestamp it used. Run NTP in a mode that slews the clock gradually and never steps it backwards.

### Can a UUID be used as a secret access token?

No. RFC 9562 states that UUIDs must not be used as security capabilities. Random IDs make guessing harder, but you must still check permissions on every request rather than trusting that the ID is unguessable.
