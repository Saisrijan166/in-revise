## Why it exists

Different data has different shapes. Orders and payments need strict rules and transactions; sessions and feeds need fast, simple lookups at huge scale.

## How it works

## Example

The same user with orders. SQL keeps two tables and joins them when reading:

```sql
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 1;
```

A document store can keep the orders inside the user, so one read returns everything:

```json
{ "_id": 1, "name": "Asha",
  "orders": [ { "id": 101, "total": 499 },
              { "id": 102, "total": 1299 } ] }
```

Embedding works when the data is read together and the list stays small.

## Interview Qs

### SQL or NoSQL for this design?

Start from the data and how it is read. SQL for related data, joins and multi-row transactions, like orders and payments. NoSQL for simple key or document lookups at very large scale, like sessions and feeds.

### Can NoSQL databases do ACID transactions?

Many can. In MongoDB a single-document write is atomic, and multi-document transactions work since 4.0 (4.2 for sharded clusters), at a performance cost.

### How do you scale a SQL database?

Scale up, then add caching and read replicas for reads. When writes or data outgrow one machine, shard by a key, or use a distributed database with SQL such as Google Spanner.
