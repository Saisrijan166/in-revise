## Why it exists

Different data has different shapes. Orders and payments need strict rules, joins, and transactions. Sessions, feeds, and events need fast, simple lookups at huge scale. Picking the right store early saves a painful migration later.

## How it works

| | SQL (relational) | NoSQL (non-relational) |
| --- | --- | --- |
| Data model | Tables of rows and columns, linked by keys | Document, key-value, wide-column, or graph |
| Schema | Fixed, checked when you write | Flexible, often interpreted when you read |
| Queries | SQL, with joins across tables | Mostly by key or one access pattern; few or no joins |
| Transactions | ACID across many rows and tables | Atomic per item by default; some support multi-item transactions |
| Scaling | Usually scale up, plus read replicas; sharding takes work | Built to spread data across many nodes |
| Examples | PostgreSQL, MySQL | DynamoDB (key-value), MongoDB (document), Cassandra (wide-column), Neptune (graph) |

## Example

The same "user with orders", two shapes. SQL keeps two tables and joins them at read time:

```sql
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 1;
```

A document store can embed the orders inside the user, so one read returns everything:

```json
{ "_id": 1, "name": "Asha",
  "orders": [ { "id": 101, "total": 499 },
              { "id": 102, "total": 1299 } ] }
```

Embedding works when data is read together and the list stays small.

## Rules & defaults

- **MongoDB:** a write to a single document is always atomic. Multi-document transactions arrived in 4.0 (replica sets) and 4.2 (sharded clusters), and they cost more than single-document writes.
- **MongoDB schemas** are flexible by default, but schema validation can reject inserts and updates that break your rules.
- **PostgreSQL stores JSON too:** prefer `jsonb` (binary, faster to query, indexable with GIN) over `json` (PostgreSQL 18 docs).
- **The four NoSQL families:** key-value, document, wide-column, graph.

## Can / Cannot

### Can

- Scale SQL a long way: read replicas, sharding extensions such as Citus for PostgreSQL, or a distributed database with SQL such as Google Spanner.
- Use ACID transactions across documents and shards in MongoDB.

### Cannot

- Expect rich joins from most NoSQL stores. Model the data around your queries instead.
- Change several items atomically by default. In key-value and document stores, atomicity covers one key or one document unless you use a transaction.

## Interview Qs

### SQL or NoSQL for this design?

Start from the data and the access patterns. Choose SQL for related data, joins, and multi-row transactions, such as orders and payments. Choose NoSQL for simple key or document lookups at very large scale or with a changing shape, such as sessions, feeds, and events. A relational database is a safe default.

### Can NoSQL databases do ACID transactions?

Many can. In MongoDB, a single-document write is atomic, and multi-document transactions are supported since 4.0 (4.2 for sharded clusters), though they cost more than single-document writes.

### How do you scale a SQL database?

Scale up first, then add caching and read replicas for reads. When writes or data size outgrow one machine, shard by a key. Distributed databases with SQL, such as Google Spanner, split rows by key range and spread them across servers for you.

## Mistake alert

"NoSQL means no schema and no transactions, and SQL cannot scale." All three are outdated. NoSQL schemas are flexible and can be validated, MongoDB has multi-document transactions, and SQL scales with replicas, sharding, or distributed SQL.

## Say it like this

"I choose by access pattern. Orders and payments want a relational database for joins and ACID transactions. High-volume, simple lookups such as sessions or activity feeds fit a key-value or document store that scales out."
