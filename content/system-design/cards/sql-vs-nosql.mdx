## What it is

A database is the store your service keeps its data in. The two broad families are SQL and NoSQL. A **SQL** (relational) database keeps data in tables of rows and columns with a schema, meaning the columns and their types are fixed up front; it links tables by keys and reads them back with joins. **NoSQL** is a group of databases, each shaped for one way of reading: key-value (look up by a key), document (a JSON-like record), wide-column, or graph.

## Why it exists

Different data has a different natural shape, and no single store is best for all of it. If you force a shopping cart that is one JSON blob into many relational tables, every read becomes a join; if you force payments, which need strict rules and multi-row transactions, into a bare key-value store, you lose those guarantees. Having both families lets you match the store to how the data is shaped and read, instead of bending the data to one tool.

## How it works

1. Start from the data: is it a set of related things you query many ways (SQL), or one record you almost always fetch by its key (NoSQL)?
2. Check the transactions you need: multi-row, all-or-nothing writes point to SQL, though some NoSQL stores now offer them too.
3. Check scale last. SQL scales with read replicas and sharding; NoSQL is built to spread across machines from the start, which matters only at very large volume.

So the key is to choose by data shape and read pattern first, and treat "it must scale" as a reason to design well, not a reason to pick NoSQL.

## Example

The same user with orders, in each model. SQL keeps two tables and joins them when reading:

```sql
SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 1;
```

A document store can keep the orders inside the user, so one read returns everything:

```json
{ "_id": 1, "name": "Asha",
  "orders": [ { "id": 101, "total": 499 },
              { "id": 102, "total": 1299 } ] }
```

What to notice:

- In SQL the order rows live in their own table; the join stitches them to the user at read time, which is flexible but is a second step.
- In the document the orders sit inside the user, so one read by `_id` returns the whole thing with no join.
- Embedding works only while the order list stays small and bounded. If a user can have unlimited orders, a document store would reference them in a separate collection instead, much like SQL.

## Rules and defaults

- **SQL schema:** columns and types are fixed and checked on every write; changing them is a migration.
- **NoSQL schema:** flexible by default, but optional validation exists, for example MongoDB schema validation.
- **MongoDB transactions:** a single-document write is always atomic; multi-document transactions exist since 4.0, and since 4.2 on sharded clusters.
- **SQL and JSON:** PostgreSQL stores JSON in a `jsonb` column, so "I need flexible fields" is not by itself a reason to leave SQL.
- **Scaling SQL:** read replicas spread reads; sharding (for example with the Citus extension) spreads writes and data across nodes.

## Not to be confused with

- **SQL the query language vs SQL the database family:** people say "SQL database" to mean relational. NoSQL databases also have query interfaces; they just are not the SQL standard.
- **NoSQL vs "no transactions":** NoSQL means "not only relational", not "no guarantees". Rule: relational = tables, joins, ACID across rows; NoSQL = one access pattern, scale-out, per-item atomicity with optional multi-item transactions.

## Interview Qs

### SQL or NoSQL for this design, and how do you decide?

Start from the data and how it is read. SQL for related data, joins and multi-row transactions, like orders and payments. NoSQL for simple key or document lookups at very large scale, like sessions and feeds. Do not pick NoSQL only because the system must scale; SQL scales too.

### Can NoSQL databases do ACID transactions?

Many can. In MongoDB a single-document write is atomic, and multi-document transactions work since 4.0 (4.2 for sharded clusters), at some performance cost. The old belief that NoSQL has no transactions is out of date.

### How do you scale a SQL database?

Scale up the machine first, then add caching and read replicas to spread reads. When writes or the data size outgrow one machine, shard by a key, or use a distributed SQL database. Scale is a design problem, not a reason to abandon SQL.
