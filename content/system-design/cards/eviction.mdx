## What it is

Eviction is a cache dropping a key to free memory. A cache holds far less than the database it fronts, so it cannot keep everything. When it reaches its memory limit, it throws out some keys to make room for new ones, even keys that are still valid. The rule that chooses which key to drop is the **eviction policy**. The two most common are LRU, which drops the key not used for the longest time, and LFU, which drops the key used the fewest times.

## Why it exists

A cache is meant to hold the hot, frequently read data in fast memory, but memory is limited while the database is not. Without eviction, the cache would fill up and then either refuse new writes or crash the machine. Eviction lets the cache keep running by making room automatically, and a good policy makes room by dropping the data least likely to be read again, so the keys people still want stay in the cache.

## How it works

| Policy | Drops first | Good when |
| --- | --- | --- |
| **LRU** | The key not used for the longest time | A few keys get most reads (most apps) |
| **LFU** | The key used the fewest times | Some keys stay popular for a long time |
| **Random** | Any key | All keys are read about equally |
| **Shortest TTL** | The key closest to expiring | Your code gives short TTLs to keys it can afford to lose |

1. On a write, the cache checks whether it is at its memory limit. If there is room, it just stores the key.
2. If it is full, it applies the policy to pick a victim and removes it, then stores the new key.
3. Real caches approximate the policy rather than tracking every key exactly: Redis samples a few keys (`maxmemory-samples`, 5 by default) and drops the oldest of the sample, which is close to true LRU but cheaper.
4. A one-off scan can still flush hot keys out of plain LRU, so Memcached uses a segmented LRU (HOT, WARM, COLD queues) that shields busy keys from such scans.

So eviction is driven by memory pressure, and the policy decides whose turn it is to go.

## Example

A tiny LRU cache in each language: it drops the least recently used entry once it holds more than its capacity.

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);                  // true = keep access order
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;                // drop the least recent
    }
}
```

```python
from collections import OrderedDict
class LruCache:
    def __init__(self, capacity):
        self.capacity, self.data = capacity, OrderedDict()

    def get(self, key):
        if key in self.data:
            self.data.move_to_end(key)           # now the most recent
        return self.data.get(key)

    def put(self, key, value):
        self.data[key] = value
        self.data.move_to_end(key)
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)        # drop the least recent
```

With capacity 2, after `put a`, `put b`, `get a`, `put c`, both versions print:

```text output
a:1 b:null c:3
```

What to notice:

- The sequence touches `a` just before inserting `c`, so `b` is the least recently used and is the one evicted; `a` and `c` survive.
- In Java, `LinkedHashMap(16, 0.75f, true)` keeps entries in access order, and `removeEldestEntry` returning true drops the oldest. Pass `false` and it keeps insertion order, so `a` would be evicted instead.
- In Python, `move_to_end` on every get and put marks a key as most recent, and `popitem(last=False)` removes the least recent. Both give an O(1) LRU.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Memory limit (`maxmemory`) | 0, meaning no limit on 64-bit; 3 GB on 32-bit | Redis Open Source |
| Policy when full (`maxmemory-policy`) | `noeviction`: commands that add data fail; reads work | Redis Open Source |
| Policy when full | `volatile-lru`: only keys with a TTL can be evicted | Azure Managed Redis |
| Keys sampled per eviction | 5 (`maxmemory-samples`) | Redis Open Source |
| Memory limit (`-m`) | 64 MB; when full it evicts (`-M` returns errors instead) | Memcached 1.6 |
| Function cache size (`maxsize`) | 128 entries, LRU | Python `functools.lru_cache` |

- `allkeys-*` policies may drop any key; `volatile-*` only keys that have a TTL, and behave like `noeviction` when no key has one.

## Interview Qs

### What is the difference between LRU and LFU?

LRU drops the key not used for the longest time; LFU drops the key used the fewest times. LFU keeps steady favourites but must forget old popularity, so Redis decays its LFU counters over time (`lfu-decay-time`, one minute by default), or a key that was once popular would never be evicted.

### How would you build an LRU cache with O(1) get and put?

Use a hash map for lookups plus a doubly linked list in use order. On each get or put, move the entry to the front; when the cache is full, remove the entry at the back. Java's `LinkedHashMap` in access order does exactly this, which is why the example subclasses it.

### Which Redis eviction policy would you pick for a cache, and what else must you set?

`allkeys-lru` when unsure: Redis recommends it for the common case where a few keys get most reads. You must also set `maxmemory`, because Redis Open Source has no limit on 64-bit and defaults to `noeviction`, which makes writes fail once the machine fills up.

### What happens when Redis is full and the policy is noeviction?

Commands that add data return an error, while reads keep working. A `volatile-*` policy behaves the same way when no key has a TTL, because there is then nothing it is allowed to evict.
