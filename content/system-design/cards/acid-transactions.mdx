## Why it exists

Money and stock counts must never end up half-changed, and many users change the same rows at once. Transactions make each change all or nothing; isolation levels decide how much concurrent transactions can see of each other.

## How it works

<Compare id="isolation-levels" />

- **Anomalies:** a dirty read sees uncommitted data, a non-repeatable read sees a row change between two reads, and a phantom read sees the set of matching rows change.
- **PostgreSQL Serializable** uses SSI: no extra blocking, but a conflicting transaction fails with SQLSTATE `40001` and must be retried.

## Example

A lost update under Read Committed:

```text
stock = 10
T1: SELECT stock        -> 10
T2: SELECT stock        -> 10
T2: UPDATE stock = 9; COMMIT
T1: UPDATE stock = 9; COMMIT    -- two sales, but stock is 9
```

Do the check and the write in one statement. PostgreSQL makes the second one wait, then re-checks `WHERE` on the new row:

```sql
UPDATE items SET stock = stock - 1
WHERE id = 7 AND stock > 0;   -- 0 rows updated means sold out
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Isolation level | Read Committed | PostgreSQL 18 |
| Isolation level | Repeatable Read | MySQL 8.4 (InnoDB) |
| Read Uncommitted | Runs as Read Committed | PostgreSQL 18 |
| Serialization failure | Error SQLSTATE 40001: retry the whole transaction | PostgreSQL 18 |

## Interview Qs

### What does ACID mean?

Atomicity: all of a transaction's changes commit, or none do. Consistency: constraints hold after every commit. Isolation: others do not see its changes before it commits. Durability: once committed, data survives a crash, because the change is in the write-ahead log first.

### Dirty read, non-repeatable read, phantom read?

Dirty: you read a change another transaction has not committed. Non-repeatable: you read a row twice and a commit in between changed it. Phantom: you rerun a query and other commits added or removed matching rows.

### Which isolation level would you use for payments?

Keep transactions short at Read Committed and make each critical step safe: an atomic conditional UPDATE, or SELECT ... FOR UPDATE on the rows you change. If a rule spans many rows, use Serializable and retry on serialization failures.

### What is write skew?

Two transactions read the same rows, check a rule, then each updates a different row. Neither overwrites the other, yet the rule breaks: two on-call doctors each see the other on call, and both go off call. Snapshot isolation allows it; Serializable stops it.
