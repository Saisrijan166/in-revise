## What it is

The CAP theorem is a rule about systems that keep copies of the same data on several machines. It names three properties: consistency, availability and partition tolerance. A partition is a network failure where messages between some nodes are lost, so the nodes cannot talk. The theorem says that while a partition is happening, a system cannot keep both full consistency and full availability, so it has to favour one.

## Why it exists

Once your data lives on more than one machine, as it does after you add [replication](card:sharding-and-replication), the network between those machines can fail at any time. When it does, a node that is cut off from the others faces a question with no free answer: should it serve a request using its own copy, which might be out of date, or should it refuse until it can check with the others? CAP names this exact trade-off so you decide it on purpose instead of being surprised by it in production.

## How it works

| Letter | What it means | What it does NOT mean |
| --- | --- | --- |
| **C**onsistency | Every read returns the latest completed write, as if one single copy existed. | The C in ACID, which means the data follows its rules. |
| **A**vailability | Every request to a working node gets a real response, not an error. | An uptime number like 99.99%. |
| **P**artition tolerance | The system keeps running when messages between nodes are lost. | A feature you can turn on or off. |

1. In normal times the network works, nodes stay in sync, and you get both C and A.
2. A partition starts: some nodes can no longer reach the others.
3. A cut-off node now has a choice for each request. It can answer from its own copy, which may be stale, and stay available (A).
4. Or it can refuse the request until it can confirm with the other side, and stay consistent (C).

So the key is that CAP is a choice you make only during a partition, and only between C and A.

## Example

A payment service runs in two regions, and the link between them breaks.

- **Recording a charge picks C:** a cut-off region refuses charges it cannot confirm, so the same card is not charged twice from two sides.
- **Showing the account's past payments picks A:** it serves the last known list. A slightly old list does no harm.

## Rules and defaults

- **P is not optional:** on a real network, messages get lost, so every distributed system must tolerate partitions. The practical choice is between C and A.
- **A true CA system:** only a single node that never partitions, which is not a distributed system.
- **Tunable per request:** many stores let you choose. Cassandra sets a consistency level per query; MongoDB uses read and write concerns; DynamoDB has a `ConsistentRead` flag.
- **PACELC extends CAP:** if there is a **P**artition, trade **A** against **C**; **E**lse, even with no partition, trade **L**atency against **C**.

## Common mistakes

- **"We built a CA system."** On a real network you cannot, because partitions will occur; you only chose how the system behaves when one does.
- **Labelling a whole database CP or AP.** The behaviour depends on its settings and on the operation. Say what a given operation does during a partition instead.

## Interview Qs

### Explain the CAP theorem in one sentence.

During a network partition, a replicated system must choose between consistency (every read sees the latest write) and availability (every working node still answers). When the network is healthy, it can have both.

### Can you build a CA system?

Not as a distributed system on a real network. Partitions will happen, so partition tolerance is not optional. Only a single node that never talks over a network avoids the choice.

### Is MongoDB CP and Cassandra AP?

That is too simple. Both are tunable: Cassandra sets consistency per query, MongoDB uses read and write concerns. Describe what your chosen settings do during a partition instead of giving the whole database one label.

### What is PACELC?

Daniel Abadi's extension of CAP: if there is a Partition, trade Availability against Consistency; Else, when the network is fine, trade Latency against Consistency. It reminds you that strong consistency costs latency even with no partition.
