## Why it exists

Once data is copied to several machines, the network between them can fail. CAP says what is still possible during that failure. It helps you decide, feature by feature, what to give up.

## How it works

The three letters, following the 2002 proof by Gilbert and Lynch:

| Letter | What it means | What it does NOT mean |
| --- | --- | --- |
| **C**onsistency | Every read sees the latest write, as if there were only one copy (linearizability). | The C in ACID (data follows the rules). |
| **A**vailability | Every request to a working node gets a response (not an error). No time limit is set. | An uptime target like 99.99%. |
| **P**artition tolerance | The system keeps running even if the network drops messages between nodes. | A feature you can switch off on a real network. |

During a network partition, a node that cannot reach the others must either:

- **Choose C:** refuse or wait, so no one reads stale data. Some users see errors.
- **Choose A:** answer from its own copy, which may be stale. Everyone gets an answer.

When there is no partition, you can have both C and A.

## Example

A ticket site runs in two regions, and the link between them breaks.

- **Seat booking chooses C:** the cut-off region refuses bookings, so no seat is sold twice.
- **The event page chooses A:** it shows the last known description. Slightly old text is fine.

One system can make different choices for different features.

## Rules & defaults

- Partitions will happen in any distributed system, so the real choice is C or A, and only while a partition lasts.
- Brewer himself wrote in 2012 that the "2 of 3" framing was always misleading.
- Many databases let you tune the choice: Cassandra sets a consistency level per query (such as `ONE`, `QUORUM`, `ALL`); MongoDB uses read and write concerns.
- PACELC (Abadi, 2012) adds the normal case: if Partition, choose Availability or Consistency; Else, choose Latency or Consistency.

## Interview Qs

### Explain the CAP theorem.

In a distributed system with copies of data, during a network partition you must choose between consistency (every read sees the latest write) and availability (every working node answers). When there is no partition, you can have both.

### Can you build a CA system?

Not as a distributed system on a real network. Partitions will happen, so you cannot opt out of P. Only a single-node system avoids the question, because there is no network between copies.

### Is MongoDB CP and Cassandra AP?

Those labels are too simple. Both are tunable: Cassandra sets consistency per query, and MongoDB uses read and write concerns. Kleppmann points out that many real systems are neither CP nor AP under the theorem's strict definitions. Describe what your chosen settings do during a partition instead.

### What is PACELC?

An extension by Daniel Abadi. If there is a Partition, trade Availability against Consistency; Else, in normal operation, trade Latency against Consistency. It explains why systems relax consistency even when the network is fine.

## Mistake alert

"CAP means pick any two of three." No. P is a fact of life in distributed systems, so you only choose between C and A while a partition lasts. Also, the C in CAP is linearizability, not the C in ACID.

## Say it like this

"CAP says that during a network partition, a replicated system must give up either consistency or availability. I would choose consistency for payments and bookings, choose availability for feeds and profiles, and set this per operation where the database allows it."
