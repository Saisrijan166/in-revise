## Why it exists

Once data is copied to several machines, the network between them can fail. CAP tells you what you must give up while that failure lasts.

## How it works

| Letter | What it means | What it does NOT mean |
| --- | --- | --- |
| **C**onsistency | Every read sees the latest write, as if there were one copy. | The C in ACID (data follows the rules). |
| **A**vailability | Every request to a working node gets a response, not an error. | An uptime target like 99.99%. |
| **P**artition tolerance | The system keeps running when messages between nodes are lost. | A feature you can switch off. |

- During a network partition, a cut-off node must refuse (**C**) or answer from its own, maybe stale, copy (**A**).
- With no partition, you can have both.

## Example

A ticket site runs in two regions, and the link between them breaks.

- **Seat booking picks C:** the cut-off region refuses bookings, so no seat is sold twice.
- **The event page picks A:** it shows the last known text. Slightly old is fine.

## Interview Qs

### Explain the CAP theorem.

In a replicated system, during a network partition you must choose consistency (every read sees the latest write) or availability (every working node answers). With no partition, you can have both.

### Can you build a CA system?

Not as a distributed system on a real network: partitions will happen, so P is not optional. Only a single-node system avoids the question.

### Is MongoDB CP and Cassandra AP?

Too simple. Both are tunable: Cassandra sets consistency per query, MongoDB uses read and write concerns. Say what your settings do during a partition instead.

### What is PACELC?

Daniel Abadi's extension: if there is a Partition, trade Availability against Consistency; Else, trade Latency against Consistency.
