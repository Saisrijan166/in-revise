## What it is

Load shedding means that when a server has more work than it can handle, it deliberately refuses some requests straight away, so the requests it does accept still finish quickly. Graceful degradation is the related idea of doing less rather than failing: if a part is missing, serve a simpler, cached or partial result instead of an error. Both choose "a worse answer now" over "a good answer too late, or none".

## Why it exists

A server that accepts every request when overloaded just gets slower and slower. Soon most answers arrive after the client has already given up, so the work is wasted: its [goodput](term:goodput), the useful answers delivered in time, drops toward zero. Worse, its backlog and slowness spread to the servers calling it, and they fall over too. Shedding the excess early keeps the server fast for the requests it accepts, and stops the overload from cascading.

## How it works

<Steps label="What an overloaded server does">
<Step title="Watch its own load">
Track a cheap signal of load on each server: requests in flight, CPU use, or queue length.
</Step>
<Step title="Reject early and cheaply">
Past the limit, return 503 at once, before doing any real work. Rejecting must cost almost nothing, or shedding adds load instead of removing it.
</Step>
<Step title="Shed low priority first">
Drop batch jobs and crawler traffic before real users. Keep health checks answering, so the load balancer does not think the server is dead.
</Step>
<Step title="Skip dead work">
Drop a queued request whose caller has already timed out: its answer can no longer be used, so producing it only steals capacity.
</Step>
<Step title="Degrade, do not fail">
If a dependency is down or slow, do less: cached, partial or simpler results, instead of failing the whole response.
</Step>
</Steps>

So the key is that rejecting must be far cheaper than serving, so the server can shed a flood without the shedding itself becoming the bottleneck.

## Example

Shedding by capping the number of requests in flight with a semaphore:

```java
private final Semaphore inFlight = new Semaphore(100);   // at most 100 at once

Response handle(Request req) {
    if (!inFlight.tryAcquire()) {                        // full: shed immediately
        return Response.status(503).header("Retry-After", "1").build();
    }
    try {
        return process(req);
    } finally {
        inFlight.release();
    }
}
```

```python
import threading

in_flight = threading.BoundedSemaphore(100)      # at most 100 at once

def handle(request):
    if not in_flight.acquire(blocking=False):    # full: shed immediately
        return Response(status=503, headers={"Retry-After": "1"})
    try:
        return process(request)
    finally:
        in_flight.release()
```

What to notice:

- `tryAcquire` (and `acquire(blocking=False)`) never waits: if all 100 permits are taken, the request is shed in one cheap check, with no queueing.
- The 503 carries `Retry-After`, telling a well-behaved client to wait a second before trying again, which spreads the load out.
- The permit is released in a `finally` block, so a failing request still frees its slot. Drop the `finally` and a few errors would leak permits until the server sheds everything.

## Rules and defaults

- **Server overloaded, shedding:** return 503 Service Unavailable, optionally with a `Retry-After` header (RFC 9110).
- **One client over its rate limit:** return 429 Too Many Requests, optionally with `Retry-After` (RFC 6585). This is a different concern from shedding.
- **Keep queues short and bounded:** a long queue only adds waiting time; by the time a deep-queued request runs, its caller has often timed out.
- **Readiness vs liveness (Kubernetes):** a failing readiness probe stops new traffic to a busy instance (a form of shedding), while a failing liveness probe restarts it. Do not fail liveness just because a downstream dependency is briefly unavailable, or you restart healthy instances.

## Not to be confused with

Load shedding protects one server from its total incoming load, whoever is sending it, and uses 503. Rate limiting caps each individual client for fairness and abuse control, and uses 429. A [circuit breaker](card:circuit-breaker) is the outbound side: it stops a client from calling a failing dependency. Rule: rate limit per client, shed by total load, break per failing dependency.

## Common mistakes

- **"Just queue everything and serve it eventually."** A long queue turns overload into high latency. The request is served only after its caller has timed out, so the work is wasted. Keep queues short and shed the overflow.
- **"We built a degraded mode, so we are covered."** A degraded path that is never exercised quietly breaks, and then fails on the day it is finally needed. Test degraded and fallback modes regularly, for example with periodic game-day drills.

## Interview Qs

### What is load shedding, and why not just queue the extra requests?

Load shedding rejects excess requests early so accepted ones stay fast. A long queue only adds waiting: by the time a deeply queued request is served, its caller has often timed out, so the work is wasted and the server is busy producing answers nobody can use. Keep queues short and bounded, and shed the overflow with a cheap 503.

### Load shedding versus rate limiting: how are they different?

Rate limiting caps each client, for fairness and abuse control, usually returning 429. Load shedding protects the server from its total load, whoever sends it, usually returning 503, and it fires even when every client is within its own limit. Use both: rate limits at the gateway, shedding on every server.

### What is a cascading failure, and how do you prevent it?

One part fails or slows, its load or its callers' retries pile onto the others, and they fail too, until the whole system is down. Prevent it with load shedding, timeouts, limited retries with backoff and jitter, circuit breakers, bulkheads, and enough spare capacity to absorb a lost peer.
