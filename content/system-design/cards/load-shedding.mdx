## Why it exists

An overloaded server that accepts everything gets slower until most answers arrive after the client gave up. It works hard and helps no one, and its load then moves to other servers, which fall over too.

## How it works

<Steps label="What an overloaded server does">
<Step title="Watch its own load">
Count requests in flight, CPU or queue length on each server.
</Step>
<Step title="Reject early">
Past the limit, return 503 at once, before any real work. Rejecting must cost almost nothing.
</Step>
<Step title="Shed low priority first">
Batch jobs and crawlers go first. Health checks stay, or the load balancer pulls healthy servers out.
</Step>
<Step title="Skip dead work">
Drop queued requests whose caller already timed out. Keep queues short.
</Step>
<Step title="Degrade, do not fail">
If a dependency is down or slow, do less: cached, partial or simpler results.
</Step>
</Steps>

- **Graceful degradation example:** recommendations are down, so the product page shows without them. Under heavy load, search can query a smaller cached index.

## Example

Shed by counting requests in flight:

```java
private final Semaphore inFlight = new Semaphore(100);   // max requests at once

Response handle(Request req) {
    if (!inFlight.tryAcquire()) {                        // full: shed at once
        return Response.status(503).header("Retry-After", "1").build();
    }
    try {
        return process(req);
    } finally {
        inFlight.release();
    }
}
```

```python
import threading

in_flight = threading.BoundedSemaphore(100)      # max requests at once

def handle(request):
    if not in_flight.acquire(blocking=False):    # full: shed at once
        return Response(status=503, headers={"Retry-After": "1"})
    try:
        return process(request)
    finally:
        in_flight.release()
```

Illustration: a server can answer 1,000 requests a second within the 1 s client timeout, and 1,500 arrive. Without shedding, queues grow and most answers come too late. With shedding, about 1,000 get fast answers and 500 get a quick 503.

## Defaults

| Situation | Status code | Spec |
| --- | --- | --- |
| Server overloaded, shedding load | 503 Service Unavailable, optional `Retry-After` | RFC 9110 |
| One client over its rate limit | 429 Too Many Requests, optional `Retry-After` | RFC 6585 |

## Interview Qs

### What is load shedding, and why not just queue everything?

Rejecting excess requests early so accepted ones stay fast. A long queue only adds waiting: by the time a request is served, its caller may have timed out, so the work is wasted. Keep queues short and bounded.

### Load shedding vs rate limiting?

Rate limiting caps each client, for fairness and abuse control, usually with 429. Load shedding protects the server from total load, whoever sends it, usually with 503. Use both: rate limits at the gateway, shedding on every server.

### What is graceful degradation? Give an example.

Keeping the core feature working during a failure by doing less. If recommendations are down, show the product page without them. Under heavy load, search a smaller cached index. Test these modes often, or they break when needed.

### What is a cascading failure, and how do you prevent it?

One part fails or slows down, its load moves to the others, and they fail too. Prevent it with load shedding, timeouts, limited retries with backoff and jitter, circuit breakers, and spare capacity.
