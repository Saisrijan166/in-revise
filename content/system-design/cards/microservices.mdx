## What it is

This is a choice about how to split an application into deployable units. A **monolith** is one app: all the code is built, shipped and run together, usually against one shared database. **Microservices** break that app into small services, each around one business capability (orders, payments, search), each with its own process and database, each deployed on its own. A **modular monolith** sits in between: one deployable app, but with strict internal module boundaries. The split is about deployment and ownership, not about writing better code.

## Why it exists

As one codebase grows, every small change needs a full rebuild and redeploy, many teams step on each other in one release, and you must scale the whole app just to scale one busy part. Microservices remove these pains: each service deploys and rolls back alone, one team owns each end to end, and you add instances only where the load is. The cost is that calls between services now cross the network, so you take on timeouts, retries, tracing and a database per service.

## How it works

<Compare id="monolith-vs-microservices" />

1. **Split by business capability.** Each service owns one area (orders, payments, search) and one team owns it. Conway's law: systems end up shaped like the teams that build them, so team and service boundaries should match.
2. **Give each service its own database.** A service's tables are private; others read its data only through its API or events, never by querying its tables.
3. **Handle changes that span services with a [saga](card:saga)**, not one ACID transaction: a chain of local transactions, each with a compensating action if a later step fails.
4. **Migrate gradually with the strangler fig pattern:** put a facade in front and move one capability at a time to a new service, until the old app can retire.

## Example

A shop has orders, payments and search. Today one copy of each part is enough. On sale day, search traffic grows 10 times while the rest stays flat.

- **Monolith:** to handle the search load you run 10 copies of the whole app, carrying the payments and orders code along for no reason.
- **Microservices:** you run 10 search instances and keep one of everything else. But checkout now calls payments over the network, so that call needs a timeout, a retry policy and tracing to debug.

What to notice:

- The win is targeted scaling: only search scales, so you spend on the part that is actually busy.
- The cost appears at once: an in-process call that could never fail is now a network call that can time out, so the simple checkout path grows reliability code it did not need before.

## Rules and defaults

- **Data stays private per service:** no shared tables; cross-service reads call each API (API composition), cross-service writes use sagas.
- **No ACID across services:** a transaction cannot span two service databases, so a multi-service change is eventually consistent, not atomic.
- **Start simple:** Fowler's guidance is monolith-first; a well-modularised monolith is faster for a new product or small team, split later when a boundary is clear.
- **The microservice premium:** microservices add CI/CD per service, orchestration, monitoring and tracing; take it on only when independent deploy, scaling or ownership justifies it.

## Not to be confused with

A modular monolith is not the same as microservices. A modular monolith has strict module boundaries but is still one deployable unit with one database, so modules call each other in-process. Microservices turn those boundaries into separate deployables with separate databases, reached over the network. Rule: modular monolith = clean boundaries, one deploy; microservices = clean boundaries, many deploys and the network between them.

## Common mistakes

- **"Microservices are automatically faster or more scalable."** They are not. A network call is slower than an in-process call; the gain is independent scaling of one part, not raw speed. Badly split services can be slower and harder to run.

## Interview Qs

### When would you choose microservices over a monolith?

When many teams must ship independently, different parts have very different scaling needs, and the domain boundaries are clear enough to split cleanly. For a new product or small team, a well-modularised monolith ships faster and is easier to run; split out services later, once a real need and a clear boundary appear.

### How do microservices share data if they can't share tables?

They do not share tables. Each service owns its database and exposes data only through its API or events. A cross-service read calls each API and joins in code (API composition) or reads a prepared view (CQRS). A cross-service write uses a saga: local transactions plus compensating actions.

### What are the main costs of microservices?

Network latency and partial failure instead of reliable in-process calls, no ACID transaction across services, harder testing and debugging, and heavy operations: CI/CD per service, orchestration, monitoring and distributed tracing. Fowler calls this the microservice premium, a cost you take on only when the benefits clearly outweigh it.

### How do you move an existing monolith to microservices?

Use the strangler fig pattern. Put a facade in front, move one capability at a time into a new service, route its traffic there, then delete the old code. Clients keep calling the same interface, so the migration is gradual rather than one risky rewrite.
