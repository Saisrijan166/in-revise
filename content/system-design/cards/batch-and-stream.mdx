## Why it exists

Some answers can wait for all the data, like a monthly bill. Others must come while events are still arriving, like a fraud alert. Each needs a different kind of job.

## How it works

<Compare id="batch-vs-stream" />

- **Batch:** [MapReduce](card:mapreduce) splits one job across many machines: *map* turns each record into key/value pairs, *reduce* merges all values for a key. Spark runs batch and streaming with the same DataFrame API.
- **Stream:** an endless stream has no end to wait for, so you group events into **windows** and use **event time** with **watermarks** to decide when a window is complete.
- Events behind the watermark are late. Flink drops them by default; you can allow some lateness or send them to a side output.

## Example

Clicks at 12:01, 12:03, 12:04, 12:09 and 12:11. Count them per window:

| Window | Groups | Counts |
| --- | --- | --- |
| Tumbling, 5 min | 12:00–12:05, 12:05–12:10, 12:10–12:15 | 3, 1, 1 |
| Sliding, 10 min, every 5 min | 12:00–12:10, 12:05–12:15 (and more) | 4, 2 |
| Session, 3 min gap | clicks 12:01, 12:03, 12:04; then 12:09, 12:11 | 3, 2 |

A nightly batch job gives one number, 5, the next morning.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Allowed lateness | 0: events behind the watermark are dropped | Apache Flink 2.3 |
| Checkpointing | Off until you enable it | Apache Flink 2.3 |
| Structured Streaming mode | Micro-batch, latency from about 100 ms | Apache Spark 4.2 |
| Continuous processing | About 1 ms, but only at-least-once | Apache Spark 4.2 |

## Interview Qs

### Batch or stream: how do you choose?

Ask how fresh the result must be. Daily reports, billing and model training fit batch. Fraud checks, alerts and live counts fit stream. Many systems use both.

### What are tumbling, sliding and session windows?

Tumbling: fixed size, no overlap, so each event is in one window. Sliding: fixed size, but a new window starts every slide, so windows overlap. Session: keeps growing while events arrive and closes after a gap with no events.

### How do you handle late or out-of-order events?

Window by event time, not arrival time. A watermark says no events older than t are expected, so windows up to t can close. Events after that are late: allow some lateness, send them to a side output, or drop them (Flink's default).

### Lambda vs Kappa architecture?

Lambda runs a batch system and a stream system side by side and merges their results, so the same logic lives in two codebases. Kappa (Jay Kreps, 2014) keeps only the stream job and reprocesses by replaying the retained log, for example in Kafka.
