## What it is

Batch and stream are two ways to process a lot of data. **Batch processing** takes a fixed, bounded dataset, such as yesterday's payments, and processes it in one run on a schedule, then stops. **Stream processing** runs all the time over an endless flow of events, handling each one soon after it arrives. The split comes from the data: batch data has an end to wait for, while a stream never ends.

## Why it exists

Some answers can wait until all the data is in, like a monthly bill or a nightly settlement total. Others must be ready while events are still arriving, like a fraud alert that is useless an hour later. A batch job cannot give a second-fresh answer, because it runs only on its schedule; a stream job gives that freshness but costs more to build and run. Having both lets you match the tool to how fresh each answer must be.

## How it works

<Compare id="batch-vs-stream" />

1. A **batch** job reads a bounded input, processes it (often split across many machines, as in [MapReduce](card:mapreduce)), writes the result, and exits. On failure you rerun it on the same input.
2. A **stream** job never ends, so it cannot wait for "all the data"; instead it groups events into **windows** (fixed slices, overlapping slices, or bursts of activity).
3. It groups by **event time**, when the event happened, not when it arrived, so a delayed event still lands in the right window.
4. A **watermark** tells the job that no events older than time T are still expected, so it can close windows up to T and emit their results.
5. Events that arrive after the watermark are **late**; Flink drops them by default, or you allow some lateness or send them to a side output.

## Example

Five clicks arrive at 12:01, 12:03, 12:04, 12:09 and 12:11. Different window types group them differently:

| Window | Groups | Counts |
| --- | --- | --- |
| Tumbling, 5 min | 12:00-12:05, 12:05-12:10, 12:10-12:15 | 3, 1, 1 |
| Sliding, 10 min, every 5 min | 12:00-12:10, 12:05-12:15 | 4, 2 |
| Session, 3 min gap | 12:01, 12:03, 12:04; then 12:09, 12:11 | 3, 2 |

What to notice:

- **Tumbling** windows do not overlap, so each click is counted once; totals across windows add up to all five clicks.
- **Sliding** windows overlap, so a click can be counted in two windows (the 12:04 and later clicks appear twice here).
- **Session** windows have no fixed size: they grow while clicks keep coming and close after a 3-minute gap, so the gap after 12:04 splits the data into two sessions.
- A nightly **batch** job over the same clicks would give one number, 5, the next morning instead of these live per-window counts.

## Rules and defaults

- **Allowed lateness:** 0 by default in Apache Flink 2.3, so events behind the watermark are dropped unless you configure lateness or a side output.
- **Checkpointing:** off until you enable it in Flink; without it a failed stream job cannot restore its state.
- **Spark Structured Streaming:** micro-batch by default, latency from about 100 ms; continuous processing reaches about 1 ms but only at-least-once.
- **Reprocessing:** a batch job reruns on the same input; a stream job replays the retained log (for example a Kafka topic) through the fixed code.

## Not to be confused with

**Event time** is when the event happened; **processing time** is when the job handled it. Windowing by event time keeps results correct even when events arrive out of order, whereas windowing by processing time is simpler but wrong for delayed events. Rule: for correct counts under delay and retries, window by event time and use watermarks.

## Common mistakes

- **"Streaming replaces batch."** Many systems keep both, and batch is still simpler for large, non-urgent jobs like nightly reports.
- **"Window by when the event arrived."** Arrival time drifts with network delay and retries, so counts jump around. Window by event time, with a watermark to decide when a window is complete.

## Interview Qs

### Batch or stream: how do you choose?

Ask how fresh the result must be. Daily reports, billing and model training fit batch, which is simpler and cheaper and reruns on failure. Fraud checks, alerts and live counts fit stream, which processes events within seconds but adds state and checkpoints. Many systems use both.

### What are tumbling, sliding and session windows?

Tumbling windows are fixed size with no overlap, so each event is in one window. Sliding windows are fixed size but start every slide interval, so they overlap. Session windows grow while events arrive and close after a gap with no events.

### How do you handle late or out-of-order events?

Window by event time, not arrival time, so a delayed event still lands in the right window. A watermark says no events older than T are expected, so windows up to T can close. Later events are late: allow lateness, use a side output, or drop them (Flink's default).

### What is the difference between Lambda and Kappa architecture?

Lambda runs a batch system and a stream system side by side and merges their results, so the same logic lives in two codebases. Kappa (Jay Kreps, 2014) keeps only the stream job and reprocesses by replaying the retained log, so there is one codebase.
