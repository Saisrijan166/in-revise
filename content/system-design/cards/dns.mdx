## What it is

DNS, the Domain Name System, is the service that turns a name like `example.com` into an IP address so your machine can connect to it. Computers route traffic using IP addresses (numbers like `192.0.2.10`), but people use and share names. DNS is the lookup that sits in between. It also lets you change the IP address behind a name without telling any user, because they only ever know the name.

## Why it exists

Without DNS, every client would have to hard-code the IP address of every server it talks to. When you moved a service to a new machine, every user would have a stale, wrong address, and there would be no way to send users to a nearby or healthy server. DNS gives each service a stable name and keeps the changing address in one place, so you repoint the name instead of chasing every client.

## How it works

The browser does not know the IP, so it asks a recursive resolver to find it, and the resolver walks down a chain of servers.

<Steps label="Looking up www.example.com">
<Step title="Ask the resolver">
The browser and the operating system first check their own caches. On a miss they ask a recursive resolver, usually run by the ISP or the company network, to do the work.
</Step>
<Step title="Root, then TLD">
The resolver asks a root server, which points it to the servers for .com. Those point it to example.com's own authoritative servers, the ones that hold the real records.
</Step>
<Step title="Get the record">
The authoritative server returns the record, for example `A 192.0.2.10` with a TTL of 300 seconds.
</Step>
<Step title="Cache and connect">
The resolver caches the answer for the TTL and hands the IP back, and the browser connects to it.
</Step>
</Steps>

So the key is caching: a cached answer at any step skips the rest of the walk, which is why most lookups are fast and why changes take time to spread.

## Example

A small zone file for example.com. Each line is a name, its TTL in seconds, the record type, and the value.

```text
example.com.      3600  NS     ns1.example.net.
example.com.      300   A      192.0.2.10
example.com.      300   AAAA   2001:db8::10
www.example.com.  300   CNAME  example.com.
example.com.      3600  MX     10 mail.example.com.
```

What to notice:

- The `A` record for `example.com` has a 300-second TTL, so a resolver may reuse that IP for five minutes before asking again. Lowering this number makes a planned IP change spread faster.
- `www.example.com` is a `CNAME` to `example.com`, so both names resolve to the same IP; you only maintain the address in one place.
- `NS` and `MX` carry a 3600-second TTL because the name servers and mail server rarely change, so there is no need to look them up often.

## Rules and defaults

- **A vs CNAME:** an `A`/`AAAA` record points a name at an IP; a `CNAME` points a name at another name.
- **CNAME limits:** a `CNAME` cannot sit at the zone apex (the bare `example.com`) or alongside other records for the same name. Managed DNS offers alias-style records to work around this at the apex.
- **TTL guidance:** managed DNS treats 60 to 120 seconds as a common TTL for records you may fail over, and an hour to a day for `NS` and `MX` records that rarely change.
- **Root servers:** there are 13 named root server identities (a through m), served from many locations worldwide.

## Not to be confused with

DNS can *roughly* balance load by returning several IPs, but it is not a [load balancer](card:load-balancer). DNS hands out an address and then steps aside; it never sees the actual requests, and caches delay any change. A load balancer sits in the request path, checks server health per request, and reacts in seconds. In practice you point a DNS name at a load balancer.

## Common mistakes

- **"A low TTL is always better."** A very low TTL means resolvers ask again constantly, which adds lookups and load. Keep TTLs moderate normally, and lower them only before a planned change.
- **"DNS changes failover instantly."** Even with health checks, clients and resolvers that cached the old answer keep using it until the TTL expires, so DNS failover is measured in the TTL, not in milliseconds.

## Interview Qs

### What happens when you type a URL into the browser?

The browser resolves the name: it checks its own cache, then the OS cache, then a recursive resolver that walks the root, the TLD and the authoritative servers. With the returned IP, it opens a TCP connection, does the TLS handshake for HTTPS, and sends the HTTP request.

### What is a DNS TTL, and how do you pick it?

A TTL is how many seconds resolvers may cache a record. Short TTLs let changes spread fast but cause more lookups; long TTLs are cheaper and faster but slow to change. Keep TTLs moderate, and lower them before a planned change or failover.

### Can DNS do load balancing?

Roughly. It can return several IPs, or use weighted, geo or latency routing with health checks. But caches delay changes and DNS cannot see each request, so a failed server may still get traffic until its answer expires. Put a real load balancer behind the DNS name.
