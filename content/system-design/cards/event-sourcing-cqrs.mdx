## Why it exists

A normal table keeps only the latest value, so the history of how it got there is lost. One data model also struggles to serve strict writes and many fast, differently shaped reads.

## How it works

<Mermaid
  alt="Event sourcing with CQRS. A command such as PlaceOrder goes to the write model, which checks the rules and appends events to the event store. A projector reads new events and updates a read database. A query such as my orders reads only from the read database."
  chart={`flowchart TD
  C(["Command: PlaceOrder"]) --> W[Write model checks the rules]
  W -- append event --> ES[(Event store)]
  ES -- new events --> P[Projector]
  P --> RD[(Read database)]
  Q(["Query: my orders"]) --> RD`}
/>

- **Event sourcing:** each change is an immutable event, like `OrderPlaced`, appended to that entity's stream. Current state = replay its events; a [snapshot](card:event-snapshot) every N events keeps replay short.
- **CQRS:** commands go to the write model; queries read a separate model shaped for screens. With separate stores, events update the read side a little later.
- Each works alone: CQRS can use one database, and event sourcing can answer reads by replaying.

## Analogy

<Analogy title="A ledger, not a whiteboard" limit="A ledger is small and read by people. A real event store also needs versioned event formats, snapshots and projections.">
A whiteboard shows only today's balance; rub it out and the past is gone. An accountant's ledger lists every entry, and the balance is their sum. A mistake is fixed by adding a reversing entry, never by erasing a line.
</Analogy>

## Example

One bank account's event stream:

| # | Event | Balance after replay |
| --- | --- | --- |
| 1 | `AccountOpened` | 0 |
| 2 | `Deposited 500` | 500 |
| 3 | `Withdrew 200` (a wrong charge) | 300 |
| 4 | `WithdrawalReversed 200` | 500 |

Event 4 is a compensating event: event 3 stays in history. A projection keeps `balance = 500` in the read database, so reads skip the replay.

## Interview Qs

### What is event sourcing?

Instead of overwriting the current state, store each change as an immutable event in an append-only log. State is rebuilt by replaying an entity's events, with snapshots to keep it fast. You get a full audit trail and the state at any past time.

### What is CQRS, and does it need event sourcing?

CQRS uses separate models for writes (commands) and reads (queries), sometimes in separate databases kept in sync by events. It does not need event sourcing, but they pair well: the events can feed the read model.

### When would you not use them?

For simple CRUD domains, short-lived MVPs, and screens that must show a write immediately. They add event versioning, projections, replays and a lagging read side. Fowler warns that for most systems CQRS adds risky complexity.

### How do you fix a wrong event or change an event's format?

Never edit stored events. Append a compensating event that reverses the effect. For a new format, add a version to each event and upcast old versions to the new shape when reading them.
