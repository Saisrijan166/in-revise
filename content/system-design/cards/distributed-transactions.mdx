## What it is

A distributed transaction is one logical action that must change data in more than one database or service and stay all-or-nothing across them. A normal [ACID transaction](card:acid-transactions) covers only a single database, so it cannot do this. There are two common approaches. Two-phase commit (2PC) makes several databases commit together as one atomic step. A saga gives up that single atomic step and instead runs a chain of local commits, undoing any failure with compensating actions.

## Why it exists

One business action, such as placing an order, can touch several stores: reserve stock in one, charge the card in another, create the order in a third. If you just run three separate local transactions, a failure in the third leaves the first two committed, so stock is held and the card charged for an order that does not exist. You need a way to keep the whole action consistent when one step fails, either by committing all of them atomically (2PC) or by cleanly undoing the committed steps (saga).

## How it works

<Compare id="two-phase-commit-vs-saga" />

1. **2PC, phase 1 (prepare):** a coordinator asks each participant to do its work, save it to disk and lock it, then vote yes or no.
2. **2PC, phase 2 (commit):** if every vote is yes, the coordinator tells all to commit; if any vote is no, it tells all to roll back. Locks are held the whole time.
3. **Saga:** each service runs its own local transaction and commits, then triggers the next step.
4. **Saga recovery:** if a later step fails, the saga runs the compensating action of each already-committed step, usually in reverse order, to undo its effect.

So the key is atomic-but-blocking (2PC) versus committed-step-by-step-and-undoable (saga).

## Example

An order saga runs across three services. Step 3 fails, so the saga refunds the card and cancels the order.

| Step | Local transaction | Compensation |
| --- | --- | --- |
| 1. Order service | Create order as PENDING | Mark order CANCELLED |
| 2. Payment service | Charge the card | Refund the card |
| 3. Stock service | Reserve items: fails, out of stock | Nothing to undo |

The same idea with 2PC on PostgreSQL, driven by a transaction manager:

```sql
-- On each participant (needs max_prepared_transactions > 0)
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
PREPARE TRANSACTION 'tx-42';  -- phase 1: work saved to disk, locks still held

-- Once every participant has prepared:
COMMIT PREPARED 'tx-42';      -- phase 2 (or ROLLBACK PREPARED 'tx-42')
```

What to notice:

- In the saga, step 2 already committed the charge, so recovery is a refund, a new action, not an automatic rollback.
- In the 2PC block, `PREPARE TRANSACTION` ends phase 1 but keeps the locks; the row stays locked until `COMMIT PREPARED` or `ROLLBACK PREPARED`.
- If the coordinator crashes between the two statements, that prepared transaction sits locked until it recovers, which is the blocking problem.

## Rules and defaults

- **PostgreSQL 18:** `max_prepared_transactions` defaults to 0, so `PREPARE TRANSACTION` is disabled until you set it higher and restart.
- **MySQL 8.4:** the InnoDB engine supports XA (2PC) transactions for use with an external transaction manager.
- **Saga steps must be idempotent:** a retry after a timeout must not charge or refund twice, so each step and each compensation keys off a request id.
- **Outbox for events:** write each step's event to an outbox table inside the same local transaction, then a relay publishes it, so an event is never lost if the service crashes after committing.

## Interview Qs

### How do you keep data consistent across microservices?

Not with one ACID transaction, because each service owns its own database. Use a saga: local transactions, each with a compensating action, plus idempotent steps and a transactional outbox so events are not lost. Accept that the data is eventually consistent across services.

### Why avoid two-phase commit across services?

It blocks: if the coordinator fails after participants prepare, they wait with locks held until it recovers. Every participant must support prepare, which some databases and message brokers do not, and the extra round trips add latency and reduce throughput.

### Choreography or orchestration for a saga?

Choreography: each service reacts to the previous service's event, with no extra component, but the flow gets hard to follow as steps grow. Orchestration: one orchestrator sends each command and runs compensations, which is clearer for complex flows but adds a component that can itself fail.

### A compensation fails. What now?

Retry it, which is why compensations must be idempotent, and the saga saves its progress so it can resume from the failed step. If retries keep failing, raise an alert for a person to resolve it manually.
