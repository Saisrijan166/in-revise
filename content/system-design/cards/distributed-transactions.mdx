## Why it exists

One business action, like placing an order, can change data in several databases or services. A local ACID transaction cannot cover them all, so you need another way to stay consistent when one step fails.

## How it works

<Compare id="two-phase-commit-vs-saga" />

- **2PC in practice:** databases expose it to a transaction manager, as XA in MySQL or `PREPARE TRANSACTION` in PostgreSQL.
- **Saga recovery:** after a failure, run the compensations of the steps that already committed, often in reverse order.
- **Outbox:** each step writes its event to an outbox table in the same local transaction; a relay publishes it, so no event is lost.

## Example

An order saga across three services. Step 3 fails, so the saga refunds the card, then cancels the order.

| Step | Local transaction | Compensation |
| --- | --- | --- |
| 1. Order service | Create order as PENDING | Mark order CANCELLED |
| 2. Payment service | Charge the card | Refund the card |
| 3. Stock service | Reserve items: fails, out of stock | Nothing to undo |

The same idea with 2PC on PostgreSQL, run by a transaction manager:

```sql
-- On each participant (needs max_prepared_transactions > 0)
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
PREPARE TRANSACTION 'tx-42';  -- phase 1: saved to disk, locks still held

-- When every participant has prepared:
COMMIT PREPARED 'tx-42';      -- phase 2 (or ROLLBACK PREPARED 'tx-42')
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Prepared transactions (`max_prepared_transactions`) | 0: `PREPARE TRANSACTION` is disabled | PostgreSQL 18 |
| XA (2PC) transactions | Supported by the InnoDB engine | MySQL 8.4 |

## Interview Qs

### How do you keep data consistent across microservices?

Not with one ACID transaction, because each service owns its database. Use a saga: local transactions, each with a compensating action, plus idempotent steps and a transactional outbox so events are not lost. Accept that data is eventually consistent.

### Why avoid two-phase commit across services?

It blocks: if the coordinator fails after participants prepare, they wait with locks held until it recovers. Every participant must support prepare, which some databases and message brokers do not, and the extra round trips add latency.

### Choreography or orchestration?

Choreography: each service reacts to the previous event; no extra component, but the flow gets hard to follow as steps grow. Orchestration: one orchestrator sends each command and runs compensations; clearer for complex flows, but it is one more part that can fail.

### A compensation fails. What now?

Retry it: compensations must be idempotent, and the saga saves its progress so it can resume from the failed step. If retries keep failing, raise an alert for a person to fix it.
