## What it is

An event stream is an append-only **log** of events. A producer adds events to the end, and each one stays in the log; reading an event does not remove it. This is the big difference from a [queue](card:message-queue), where a message is deleted once handled. Each reader keeps an **offset**, saying how far it has read. Because events are kept, many readers read them at their own speed, and a reader can move its offset back to re-read old events. Apache Kafka is the best-known example.

## Why it exists

A queue deletes a message once it is handled, so a new reader, or a bug fix, cannot go back to the events it missed. If three teams each need every payment event, you would copy the data three times. A log keeps the events for days, so many systems read the same stream independently at their own pace, and a team can replay history to rebuild a view or fix a bug, without the producer sending anything again.

## How it works

1. A producer appends each record to one **partition** of the topic, chosen by the record's key; records with the same key always land in the same partition.
2. Inside the partition every record gets a number, its **offset**, and the records stay in that order.
3. A **consumer group** reads the topic; within one group each partition is read by only one consumer, so the group's parallelism is capped by the partition count.
4. A different consumer group reads the same records on its own, with its own offsets, so adding a group adds no copies of the data.
5. Records leave the log only when **retention** (age or size) expires, never because someone read them. To replay, a group moves its offset back.

## Example

The topic is `payments` with 3 partitions, keyed by `paymentId`. The `billing` group's committed offset on partition 0 is 1,000 while the partition's end is 1,050, so its **lag** is 50. A bug corrupted billing from 09:00, so you stop the group and rewind its offset:

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group billing --topic payments --execute \
  --reset-offsets --to-datetime 2026-10-27T09:00:00.000
```

What to notice:

- The reset changes only the `billing` group's offset; on restart it re-reads from 09:00 and reprocesses those events, because the log still holds them.
- Other groups keep their own offsets, so they do not notice the rewind at all.
- This replay is possible only within retention: once events older than 7 days are removed, you cannot rewind past that point.

## Rules and defaults

- **Order:** guaranteed within a partition only. Key related events the same (for example by `paymentId`) so they share a partition and stay ordered.
- **Parallelism:** one consumer per partition in a group, so the partition count caps how many consumers in a group do work. Plan partitions ahead.
- **Retention (`log.retention.hours`):** 168 hours (7 days) by default in Apache Kafka 4.3; `log.retention.bytes` is -1 (no size limit) by default.
- **Where a new group starts (`auto.offset.reset`):** `latest` by default, so a brand-new group reads only events written from now on, not the whole history.
- **Replication:** `default.replication.factor` is 1 by default; production usually sets 3 so a broker can fail without data loss.

## Not to be confused with

A [queue](card:message-queue) deletes a message once it is acknowledged and gives it to one worker. An event stream keeps the record and lets many groups read it. A [topic](card:pub-sub) in pub/sub fans out live copies but usually does not keep a replayable history. Rule: use a stream when readers need an ordered log they can replay, not just a one-time delivery.

## Common mistakes

- **"More consumers in a group always means more throughput."** Only up to the partition count. With 4 partitions a 5th consumer sits idle, so you scale by adding partitions, not just consumers.
- **"Kafka stores events forever."** By default they are deleted after 7 days, so replay works only inside the retention window unless you raise retention or use compaction.

## Interview Qs

### Kafka vs a queue like RabbitMQ or SQS?

Kafka is a log: it keeps records after they are read, many consumer groups read the same data, and order holds per partition. RabbitMQ and SQS delete a message once it is acknowledged, and workers share the messages. Use Kafka for event streams and replay, a queue to hand out jobs.

### How does Kafka keep events in order?

Only within a partition. Records with the same key go to the same partition, so you key by the entity, like `paymentId`, to keep that entity's events ordered. Strict order across a whole topic needs a single partition, which limits you to one working consumer per group.

### How do you scale consumers, and what limits it?

Add consumers to the group and Kafka spreads the partitions among them, one consumer per partition. With 4 partitions a 5th consumer gets nothing, so plan partitions ahead. Adding partitions later changes how keys map to partitions, so a key's new records can move to another partition and break per-key order.

### A consumer crashes. What happens to its work?

The group rebalances: its partitions move to the other consumers, which resume from the last committed offset. Records processed after that commit are read again, so delivery is at-least-once and processing must be idempotent.
