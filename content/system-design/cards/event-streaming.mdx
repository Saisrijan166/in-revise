## Why it exists

A queue deletes a message once it is handled, so a new reader, or a bug fix, cannot go back to old events. A log keeps events for days, so many systems read the same data at their own pace and can replay it.

## How it works

<Mermaid
  alt="Event streaming. Producers append records to a topic with two partitions; the record key decides the partition. Partition 0 holds offsets 0 to 4 and partition 1 holds offsets 0 to 3. In consumer group A, consumer 1 reads partition 0 and consumer 2 reads partition 1. Consumer group B has one consumer that reads both partitions on its own."
  chart={`flowchart TD
  PR[Producers] -- "key picks the partition" --> P0["Partition 0: offsets 0 1 2 3 4"]
  PR --> P1["Partition 1: offsets 0 1 2 3"]
  P0 --> A1["Group A: consumer 1"]
  P1 --> A2["Group A: consumer 2"]
  P0 --> B1["Group B: one consumer"]
  P1 --> B1`}
/>

- A producer appends each record to one partition, chosen by its key if it has one. In a partition, each record has a number: its offset.
- Inside a consumer group, each partition is read by one consumer. Other groups read the same records on their own.
- Records leave by retention (time or size), never because someone read them.

## Example

Topic `orders`, 3 partitions, key `orderId`. Partition 0 ends at offset 1,050; the `billing` group's committed offset is 1,000, so its lag is 50. A bug corrupted billing since 09:00? Fix it, stop the group's consumers, and rewind:

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group billing --topic orders --execute \
  --reset-offsets --to-datetime 2026-10-16T09:00:00.000
```

On restart, billing reads from 09:00 again. Other groups do not notice.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| How long records are kept (`log.retention.hours`) | 168 h (7 days) | Apache Kafka 4.3 broker |
| Size limit (`log.retention.bytes`) | -1: no size limit | Apache Kafka 4.3 broker |
| Partitions for a new topic (`num.partitions`) | 1 | Apache Kafka 4.3 broker |
| Copies of each partition (`default.replication.factor`) | 1 (3 is common in production) | Apache Kafka 4.3 broker |
| Where a new group starts (`auto.offset.reset`) | `latest`: only records written from now on | Apache Kafka 4.3 consumer |
| Offset commits (`enable.auto.commit`) | On, every 5 s | Apache Kafka 4.3 consumer |
| How long records are kept | 24 h (up to 365 days) | Amazon Kinesis Data Streams |

## Interview Qs

### Kafka vs RabbitMQ or SQS?

Kafka is a log: it keeps records after they are read, many consumer groups read the same data, and order holds per partition. RabbitMQ and SQS queues delete a message once it is acked, and workers share the messages. Use Kafka for event streams and replay, a queue for jobs.

### How does Kafka keep events in order?

Only within a partition. Records with the same key go to the same partition, so key by the entity, like `orderId`. Strict order for a whole topic needs one partition, which means one active consumer per group.

### How do you scale consumers, and what limits it?

Add consumers to the group; Kafka spreads the partitions among them, one consumer per partition. With 4 partitions, a 5th consumer gets nothing, so plan partitions ahead. Adding partitions later changes `hash(key) % N`, so a key's new records can land in another partition.

### A consumer crashes. What happens?

The group rebalances: its partitions move to other consumers, which resume from the last committed offset. Records processed after that commit are read again, so delivery is at-least-once and processing must be idempotent.
