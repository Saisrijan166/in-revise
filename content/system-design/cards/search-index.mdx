## What it is

A search index answers "which documents contain these words?" quickly. Its core is an **inverted index**: for each term it keeps the list of documents that contain that term, the reverse of a document listing its own words. Before words go in, text is run through **analysis**: it is split into terms and normalised, for example lowercased and stemmed, so "Running" and "runs" both become "run". You saw ordinary [indexes](card:indexing) on column values; a search index is built for matching and ranking free text.

## Why it exists

People search text by the words in it, in any form and order, and expect the best matches first. A plain `WHERE description LIKE '%phone%'` reads every row (a leading wildcard cannot use a B-tree index), so it is slow on a large table. Worse, it matches only an exact substring: it will not connect "phones" to "phone", and it cannot rank results by how well they match. An inverted index solves both: it looks up a few short term lists instead of scanning, and it scores the matches.

1. Each document is analysed into normalised terms, and every term records which documents contain it.
2. The query goes through the same analysis, so "Shoes" in the query matches "shoes" in the index.
3. The engine looks up each query term's list and combines them, never touching documents that contain none of the terms.
4. It ranks the matches by a relevance score (BM25), so the document with both words comes first.

So the key is: analyse once on write and once on query, match on term lists, and rank the results.

## Example

PostgreSQL 18 can do full-text search with no extra system, using a `tsvector` column and a GIN (inverted) index:

```sql
-- A stored tsvector column, plus a GIN (inverted) index on it
ALTER TABLE products ADD COLUMN search tsvector
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(name, ''))) STORED;
CREATE INDEX products_search_idx ON products USING GIN (search);

-- The 'english' config stems words, so "Running Shoes" matches "run & shoe"
SELECT id, name, ts_rank(search, q) AS rank
FROM products, to_tsquery('english', 'run & shoe') AS q
WHERE search @@ q
ORDER BY rank DESC LIMIT 10;
```

What to notice:

- `to_tsvector('english', ...)` is the analysis step: it splits and stems the name into terms and stores them in the `search` column.
- The GIN index is the inverted index; without it, `@@` would still work but would scan every row.
- `to_tsquery('english', 'run & shoe')` analyses the query the same way, which is why "Running Shoes" in the data matches, and `ts_rank` orders the results by relevance.

## Rules and defaults

- **Relevance score:** Elasticsearch 9.x ranks with BM25 by default (parameters k1 = 1.2, b = 0.75).
- **Default analyzer:** the Elasticsearch `standard` analyzer splits on word boundaries and lowercases; it keeps stop words unless you configure otherwise.
- **Near real-time:** a new document becomes searchable after a refresh, about every 1 second, for indices that were searched in the last 30 seconds.
- **Scale-out:** Elasticsearch splits each index into shards spread across nodes, so search scales horizontally.
- **PostgreSQL index choice:** GIN is the preferred index for full-text search; GiST also works. For substring `LIKE '%term%'`, the `pg_trgm` extension can index it.
- **Source of truth:** the database holds the truth; the search index is a copy, kept in sync asynchronously (for example by change data capture), so expect a short lag.

## Interview Qs

### What is an inverted index?

A map from each term to the documents that contain it: the reverse of a document listing its words. A search looks up each query term, combines the lists, and never scans documents that contain none of the terms. It is the structure behind Lucene, Elasticsearch and PostgreSQL full-text search.

### Why not LIKE '%term%'?

A B-tree serves only patterns anchored at the start, like `LIKE 'term%'`. A leading wildcard reads every row, and `LIKE` has no stemming or ranking, so "phones" will not match "phone". If you only need substring matching, PostgreSQL's `pg_trgm` extension can index `LIKE '%term%'`.

### How do you keep a search engine in sync with the database?

Keep the database as the source of truth. Capture its changes with change data capture, for example Debezium reading the write-ahead log or binlog into Kafka, and index them asynchronously. Expect a short lag, and rebuild the index from the database if it ever drifts.

### How are results ranked?

By a relevance score. Elasticsearch uses BM25 by default: a term counts more when it is rare across all documents and frequent in this one, repeats give diminishing returns, and matches in shorter fields count more. This puts the most relevant documents at the top.
