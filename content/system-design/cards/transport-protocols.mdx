## What it is

TCP and UDP are the two common transport protocols: the layer that actually carries your data between two machines, on top of IP. IP alone can lose, delay, reorder or duplicate packets. TCP adds the work to hide all of that, so your app sees a clean, in-order stream of bytes. UDP adds almost nothing, so your app sees the raw packets and must handle any loss itself.

## Why it exists

Different data has different needs. A payment or a database write must arrive complete and in order, or the result is wrong; here you want TCP to do the resending and ordering for you. A live video frame is useless once it is late; waiting for a resend only freezes the picture, so here you want UDP, which hands you each packet as it comes and lets you skip the ones that are lost. One protocol cannot serve both needs, so the network offers both.

## How it works

The difference is the handshake and what happens to a lost packet.

<Compare id="tcp-vs-udp" />

1. **TCP** first does a three-way handshake (SYN, SYN-ACK, ACK) to open a connection.
2. It numbers every byte, and the receiver acknowledges what it got. Anything not acknowledged is resent, so data arrives complete and in order.
3. Because ordering is strict, a lost packet holds up all the bytes behind it until the resend arrives. This wait is called head-of-line blocking.
4. **UDP** skips all of that: the first datagram already carries your data, and nothing is acknowledged or resent.
5. **QUIC** gets the best of both: it runs over UDP but adds reliable, encrypted streams, and a loss in one stream does not block the others. HTTP/3 is built on it.

## Analogy

<Analogy title="A phone call vs postcards" limit="A real call holds a line open just for you, but TCP still shares the network with everyone; and apps can add their own checks on top of UDP, which postcards cannot.">
TCP is a phone call: you connect first, and if a word is lost you say "pardon?" and hear it again. UDP is a stack of postcards: each one travels alone, some get lost, and they may arrive in any order.
</Analogy>

## Example

This is the setup cost before the first request can even be sent, when one round trip to the server takes 100 ms. Fewer round trips means the user waits less.

| Setup | Round trips before the first request | Wait |
| --- | --- | --- |
| TCP + TLS 1.3 | 2: the TCP handshake, then the TLS handshake | about 200 ms |
| QUIC (HTTP/3) | 1: it merges both handshakes into one | about 100 ms |
| QUIC, repeat visit (0-RTT) | 0: the request rides in the first flight | about 0 ms |
| UDP, such as a DNS lookup | 0: the first datagram is already the question | about 0 ms |

What to notice:

- TCP needs two separate handshakes for an HTTPS request, which is why a far-away server feels slow on the first connection.
- QUIC folds the connection and encryption setup together, so HTTP/3 starts one round trip sooner than HTTP/2 over TCP.
- Plain UDP has no setup at all, which is why a small DNS lookup can be one packet out and one packet back.

## Rules and defaults

- **TCP header:** 20 bytes without options; **UDP header:** 8 bytes. UDP's smaller header is part of why it is lighter per packet.
- **Ordering:** TCP guarantees in-order delivery to the app; UDP gives you packets in whatever order they arrive, if they arrive.
- **Pacing:** TCP has built-in flow control and congestion control; UDP has none, so a UDP app must pace itself or it can flood the network.
- **DNS:** uses UDP by default; it retries over TCP when a reply is truncated, and zone transfers (AXFR) always use TCP.

## Not to be confused with

TCP and UDP are **transport** protocols; HTTP is an **application** protocol that runs on top of them. HTTP/1.1 and HTTP/2 run over TCP; HTTP/3 runs over QUIC, which runs over UDP. So "HTTP vs TCP" is not a choice: HTTP always needs a transport underneath.

## Common mistakes

- **"UDP has no error checking at all."** It has an optional checksum that detects a corrupted packet, but it still does not resend or reorder; it just drops the bad one.
- **"A load balancer only works with TCP."** Layer 4 load balancers can balance UDP too (for example DNS or QUIC traffic); you will see this with the [load balancer](card:load-balancer).

## Interview Qs

### TCP or UDP: when do you use each?

TCP when every byte must arrive in order: web APIs, payments, file transfers, database connections. UDP when fresh data matters more than complete data: live voice and video, online games, and most DNS lookups. In a design interview, treat TCP as the default and say why if you pick UDP.

### Why do video calls and games prefer UDP?

With TCP, one lost packet holds up all the newer data behind it until it is resent, which freezes live media. An old video frame is useless anyway, so it is better to skip it and show the next one. UDP hands each packet to the app and lets it make that choice.

### What is QUIC, and why does HTTP/3 use it?

QUIC is a transport built on UDP that adds reliable, encrypted streams. It merges the connection and TLS handshakes, so setup takes one round trip instead of two, and a lost packet stalls only its own stream, not the whole connection. HTTP/3 is HTTP carried over QUIC.
