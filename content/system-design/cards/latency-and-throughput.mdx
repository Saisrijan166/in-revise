## What it is

These are the two numbers that describe how a system performs under load. Latency is how long one request takes, from sending it to getting the reply, measured in milliseconds. Throughput is how many requests the system finishes per second. They are different: a system can be fast for one request yet handle few per second, or handle a huge number per second while each one waits. A design needs both numbers to be judged.

## Why it exists

"Fast" is not one thing. The payment service might answer a single checkout in 40 ms when idle, but during a sale it must also handle thousands of checkouts per second. If you only track one number, you miss the other problem: low latency but low throughput means long queues under load, and high throughput with high latency means every user waits. Separating the two lets you set a clear target, such as "p99 under 200 ms at 5000 requests per second".

## How it works

| What | Latency | Throughput |
| --- | --- | --- |
| Question it answers | How long does one request take? | How many requests finish per second? |
| Unit | milliseconds, reported as p50, p95, p99 | requests/s or MB/s |
| How to improve it | do less work, do it in parallel, do it closer to the user (cache, CDN) | add servers, remove the bottleneck |
| What to watch | the slow tail, made worse by fan-out | near full load, queues grow and latency rises |

1. A request arrives. If the server is busy, it waits in a queue first, then gets processed, then the reply is sent. Latency is the whole of that time.
2. Throughput is how many such requests complete each second across all servers.
3. As load nears capacity, the queue in step 1 grows, so latency climbs while throughput stays flat. This is why the two trade off.
4. Report latency as percentiles: p50 is the typical request; p99 is the time within which 99% finish, so it shows what the slowest 1% feel.

So the key is to aim for the most throughput you can get while keeping p99 latency within an acceptable limit.

## Analogy

<Analogy title="A highway" limit="Cars do not time out, retry, or split one trip into 100 parallel trips that all must finish; requests do.">
Latency is how long one car takes to cross the bridge. Throughput is how many cars cross per hour. Adding a lane carries more cars per hour, but no single car drives any faster. At rush hour, cars queue at the merge, so every trip takes longer, even though more cars pass in total.

## Example

One server replies in 10 ms, except 1 reply in 100 takes 1 second. Look at what the average hides.

```text
Average:   (99 × 10 ms + 1 × 1000 ms) / 100 ≈ 20 ms
           but no single request actually took 20 ms.

p99:        about 1000 ms. The slowest 1% feel a full second.

Fan-out:   if a page calls 100 such servers and needs all replies,
           it is fast only if all 100 are fast: 0.99^100 ≈ 0.37.
           So about 63% of pages take over 1 second.
```

What to notice:

- The average of 20 ms describes no real request: it sits between the fast 10 ms and the rare 1000 ms, fooling you into thinking users are fine.
- p99 exposes the slow tail: 1% of single requests already wait a full second.
- Fan-out makes a rare tail common. Calling 100 servers turns a 1% chance of slowness into a 63% chance per page (Dean and Barroso, 2013). The fix is timeouts, [hedged requests](term:hedged-requests), or fewer calls per page.

## Rules and defaults

- **Report percentiles, not averages:** the Google SRE book recommends p50, p95 and p99 because the mean hides the slow tail.
- **p99 meaning:** p99 = 800 ms means 99% of requests finished within 800 ms and the slowest 1% took at least that long.
- **Little's law:** requests in flight = throughput × latency. At 2000 requests/s and 50 ms each, about 100 requests are in flight; use this to size thread and connection pools.
- **Units:** throughput is per second (requests/s or MB/s); latency is per request (ms). Do not mix them up.

## Interview Qs

### Latency vs throughput?

Latency is how long one request takes; throughput is how many requests finish per unit of time. They are linked: as load nears capacity, queues build and latency rises while throughput flattens. The goal is the most throughput you can get while keeping latency within an acceptable limit, usually stated as a p99 target.

### Why use p99 instead of the average?

The average mixes many fast requests with a few very slow ones, so it can describe no real request and hide a painful tail. p99 shows the time within which 99% of requests finish, so you see what the slowest 1% actually experience. For this reason latency targets (SLOs) are set on percentiles, not the mean.

### Every server is fast, so why is the page slow?

The page probably fans out to many servers and waits for the slowest reply. If each server is slow 1% of the time, a page calling 100 of them is slow about 63% of the time, because it needs all of them to be fast at once. Fix it with timeouts, hedged requests, or by making fewer calls per page.

### Which latency numbers should you know?

Orders of magnitude from Jeff Dean's 2009 list: a memory read is about 100 ns, a round trip inside one datacentre about 0.5 ms, a spinning-disk seek about 10 ms, and California to the Netherlands and back about 150 ms. Hardware has improved since, so remember the relative order, not the exact values.
