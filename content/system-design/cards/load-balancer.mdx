## What it is

A load balancer is a single network address that sits in front of a group of servers and hands each incoming request to one of them. Clients only ever talk to the load balancer; they do not know how many servers there are behind it, or which one served them. It also watches the servers with health checks, so it can stop sending requests to any server that is down.

## Why it exists

Once you [scale out](card:scalability) to many servers, two problems appear. First, clients need one stable address to call, not a list of server IPs that keeps changing as you add or remove machines. Second, something must pick a server for each request and avoid the ones that have failed. Without a load balancer you would hard-code server addresses into clients and keep sending traffic to dead machines. The load balancer solves both: one address in, healthy servers chosen automatically.

## How it works

Each request flows through the load balancer, which filters out unhealthy servers and then picks one.

<Steps label="One request through a load balancer">
<Step title="Client calls one address">
The client knows only the load balancer's address, usually found through [DNS](card:dns), and sends its request there.
</Step>
<Step title="Skip unhealthy servers">
The load balancer ignores any server that is currently failing its health check, so those get no traffic until they pass again.
</Step>
<Step title="Pick a server">
It chooses one healthy server using its method, such as round robin or least connections.
</Step>
<Step title="Forward and reply">
It forwards the request to that server, and the response comes back to the client through the load balancer.
</Step>
</Steps>

A Layer 4 load balancer does this by IP and port without reading the request; a Layer 7 one reads the HTTP request, so `/api` and `/images` can go to different servers.

## Example

This is round robin, the default method, in a few lines: it keeps a counter and sends each new request to the next server in turn.

```java
String[] servers = {"app1", "app2", "app3"};
int i = 0;
String next() { return servers[i++ % servers.length]; }
// 5 requests:
// -> app1, app2, app3, app1, app2
```

```python
servers = ["app1", "app2", "app3"]
i = 0
def next_server():
    global i
    s = servers[i % len(servers)]
    i += 1
    return s
# 5 requests -> app1, app2, app3, app1, app2
```

```text output
[app1, app2, app3, app1, app2]
```

What to notice:

- The counter wraps with `% servers.length`, so after the last server it starts again at the first; each server gets an equal share of requests.
- It balances the **count** of requests, not their cost. If one request is far heavier, this even split still overloads whichever server happened to get it, which is why least connections exists.
- A real load balancer also removes a failed server from this list first, so the counter only ever lands on healthy servers.

## Rules and defaults

A tiny nginx upstream shows the same idea in config, with weights and a backup server:

```nginx
upstream backend {
    server app1.example.com weight=2;  # gets twice the requests of app2
    server app2.example.com;
    server app3.example.com backup;    # used only if the others are down
}
server {
    listen 80;
    location / { proxy_pass http://backend; }
}
```

| What | Default | Where |
| --- | --- | --- |
| How a server is picked | Round robin (weighted) | nginx, AWS ALB |
| When nginx skips a server | 1 failed request within 10 s, then skipped for 10 s | nginx `max_fails`, `fail_timeout` |
| Health check timing | Every 30 s; unhealthy after 2 fails; healthy after 5 passes | AWS ALB |
| Active health checks | Paid NGINX Plus only | nginx |

## Not to be confused with

A load balancer spreads requests across **identical copies** of one service. A [reverse proxy](card:reverse-proxy) is one front door that adds TLS, caching or compression in front of servers, and an [API gateway](card:api-gateway) routes and secures **many different** APIs. One product (like nginx) can play all three roles, but the jobs are distinct: balance load, front servers, or manage APIs.

## Common mistakes

- **"Add a load balancer and sessions just work."** If a server stores session state in memory, a later request routed to a different server loses it. Keep servers stateless (store sessions in a shared cache), or use sticky sessions.
- **"The load balancer removes the single point of failure."** It removes it for the servers, but the single load balancer becomes the new one. Run it redundantly or use a managed, multi-zone load balancer.

## Interview Qs

### What does a load balancer do?

It gives clients one stable address, spreads requests across several servers, and stops sending traffic to servers that fail their health checks. That is what makes scaling out usable: you can add or remove servers behind it without clients noticing.

### Layer 4 vs Layer 7?

Layer 4 routes by IP and port without reading the request, so it is fast and works for any TCP or UDP traffic. Layer 7 reads the HTTP request, so it can route by path, host, header or cookie, and terminate TLS. Web apps usually want Layer 7; non-HTTP traffic needs Layer 4.

### Which algorithm would you pick?

Round robin when requests and servers are similar. Least connections when request times vary, so busy servers get fewer new requests. A hash of the client IP or a key when the same client must keep reaching the same server.

### Isn't the load balancer a single point of failure?

Yes, if there is only one. Run a redundant pair (active-passive or active-active), or use a managed load balancer that runs across several availability zones, so one instance or zone failing does not take the whole system down.
