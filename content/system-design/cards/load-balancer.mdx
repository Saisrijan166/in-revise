## Why it exists

Once you scale out, clients need one address to call, and something must decide which server gets each request. A load balancer does both, and it stops sending traffic to servers that are down.

## How it works

<Steps label="One request through a load balancer">
<Step title="Client calls one address">
The client only knows the load balancer's address (often through DNS), never the servers behind it.
</Step>
<Step title="Skip unhealthy servers">
Health checks probe every server. Servers that fail stop getting traffic until they pass again.
</Step>
<Step title="Pick a server">
An algorithm picks one healthy server, for example round robin or least connections.
</Step>
<Step title="Forward and reply">
The load balancer forwards the request and passes the server's response back to the client.
</Step>
</Steps>

- **Layer 4** load balancers route by IP address and port. They do not read the request, so they are fast and work for any TCP or UDP traffic. Example: AWS Network Load Balancer.
- **Layer 7** load balancers read HTTP, so they can route by path, host, or header, like `/api` to one group and `/images` to another. Example: AWS Application Load Balancer.

## Example

A tiny nginx setup:

```nginx
upstream backend {
    # no method line = weighted round robin (the default)
    server app1.example.com weight=2;  # gets 2x the requests of app2
    server app2.example.com;           # weight=1 by default
    server app3.example.com backup;    # used only if the others are down
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
    }
}
```

## Rules & defaults

- **nginx (open source):** default method is weighted round robin. Others: `least_conn`, `ip_hash`, `hash`, `random`, and `least_time` (open source since mainline 1.31.0; before that, NGINX Plus only).
- **nginx health checks are passive:** a server is skipped after `max_fails` failures (default 1) within `fail_timeout` (default 10s). Active probes (`health_check`) need NGINX Plus.
- **AWS Application Load Balancer:** round robin by default; least outstanding requests and weighted random are options. Default health check: every 30s, unhealthy after 2 failures, healthy after 5 successes.
- **HAProxy:** the default `balance` method changed from `roundrobin` to `random` in version 3.3.

## Can / Cannot

### Can

- Take a failed server out of rotation automatically, and bring it back when it recovers.
- Route by URL path, host, or header (Layer 7 only).
- Keep a user on one server with sticky sessions (on AWS ALB, through a cookie).

### Cannot

- Remove every single point of failure: one load balancer is itself one. Run a redundant pair or a managed, multi-zone service.
- See the request path or headers at Layer 4.
- Make uneven work even with plain round robin. It counts requests, not how heavy they are.

## Interview Qs

### What does a load balancer do?

It gives clients one address, spreads requests across servers, and stops sending traffic to servers that fail health checks. This is what makes horizontal scaling work.

### Layer 4 vs Layer 7 load balancing?

Layer 4 routes by IP and port without reading the request, so it is fast and works for any TCP or UDP traffic. Layer 7 reads HTTP, so it can route by path, host, header, or cookie, at a higher cost per request.

### Which algorithm would you choose?

Round robin when requests and servers are similar. Least connections, or least outstanding requests on AWS ALB, when request times vary. A hash of the client IP or a key when the same client should keep reaching the same server.

### Isn't the load balancer a single point of failure?

Yes, if there is only one. Run two in active-passive or active-active mode, or use a managed load balancer that runs in several availability zones behind DNS.

## Mistake alert

"Round robin spreads the load evenly." It spreads requests evenly, not work. If some requests take ten times longer, one server can still be overloaded. Use least connections when request times vary.

## Say it like this

"I put a Layer 7 load balancer in front of stateless app servers, with health checks so failed servers drop out, and least connections if request times vary. To avoid a single point of failure, I use a managed multi-zone load balancer or a redundant pair."
