## Why it exists

Networks drop messages and consumers crash mid-work. Every queue or stream must pick what happens then: lose the message, or deliver it again.

## How it works

<Compare id="delivery-semantics" />

- The difference is **when the consumer acknowledges** (commits its offset or deletes the message): before the work, or after it.
- Duplicates come from retries: a producer with no reply resends, and a consumer that crashes before its ack gets the message again.
- **Exactly-once** is really *effectively once*. Kafka's idempotent producer and transactions cover writes inside Kafka; anything outside needs an [idempotent consumer](card:idempotent-consumer).

## Example

An idempotent consumer: the message ID and the change commit together.

```java
void handle(Message msg) {
    db.inTransaction(tx -> {
        // unique key on message_id: a repeat cannot insert it again
        boolean isNew = tx.insertIfAbsent("processed_messages", msg.id());
        if (isNew) {
            tx.addToBalance(msg.accountId(), msg.amount());
        }
    });
    msg.ack();   // only after the commit; a repeat is acked and skipped
}
```

```python
def handle(msg):
    with db.transaction() as tx:
        # unique key on message_id: a repeat cannot insert it again
        is_new = tx.insert_if_absent("processed_messages", msg.id)
        if is_new:
            tx.add_to_balance(msg.account_id, msg.amount)
    msg.ack()    # only after the commit; a repeat is acked and skipped
```

If two copies arrive at once, the unique key lets only one insert win.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Delivery guarantee | At-least-once | Kafka |
| `enable.idempotence` (producer) | `true`, unless other settings conflict | Kafka 4.3 |
| `isolation.level` (consumer) | `read_uncommitted`: also sees aborted transactional writes | Kafka 4.3 |
| `processing.guarantee` | `at_least_once`; `exactly_once_v2` needs brokers 2.5+ | Kafka Streams 4.3 |
| Standard queue | At-least-once: a copy can arrive again | Amazon SQS |
| FIFO deduplication interval | 5 minutes | Amazon SQS |
| Visibility timeout | 30 s; not deleted in time, it is delivered again | Amazon SQS |

## Interview Qs

### Explain at-most-once, at-least-once and exactly-once.

At-most-once: zero or one delivery, so a message may be lost. At-least-once: one or more, so nothing is lost but repeats happen. Exactly-once: the effect happens once, built from at-least-once plus deduplication or transactions.

### Is exactly-once delivery really possible?

Not end to end across a network: an acknowledgement can be lost, so someone must resend or give up. What systems offer is exactly-once processing: Kafka within Kafka, or at-least-once plus an idempotent consumer everywhere else.

### How do you make a consumer idempotent?

Give each message a stable ID. In one transaction, insert the ID into a processed-messages table with a unique key and apply the change; a repeat fails the insert and is skipped. Or use naturally idempotent writes, like an upsert that sets an absolute value.

### How does Kafka provide exactly-once?

The idempotent producer adds a producer ID and sequence numbers, so the broker drops resent copies. Transactions write to many partitions and commit the consumer offset atomically. Consumers set to `read_committed` see only committed data.
