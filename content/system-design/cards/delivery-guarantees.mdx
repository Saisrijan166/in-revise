## What it is

A delivery guarantee describes what a messaging system promises when things go wrong. There are three levels. **At-most-once**: a message arrives zero or one time, so it may be lost but never repeated. **At-least-once**: it arrives one or more times, so it is never lost but may repeat. **Exactly-once**: the final effect happens once, built by combining at-least-once delivery with a way to detect and skip repeats. Which one you get depends on **when the consumer acknowledges** a message.

## Why it exists

Networks drop packets and consumers crash mid-work, and when an acknowledgement is lost the sender cannot tell whether the message was lost or just slow. Each choice is wrong some of the time: give up, and sometimes lose a real message; or resend, and sometimes deliver a duplicate. Every queue and stream picks one of these, so you need to know which one you have and design the consumer to match.

## How it works

<Compare id="delivery-semantics" />

1. The only real difference is **when the consumer acknowledges** (commits its offset or deletes the message): before doing the work, or after it.
2. Acknowledge first (at-most-once): a crash before the work loses the message, because the broker already thinks it is done.
3. Acknowledge after (at-least-once): a crash before the ack re-delivers the message, because the broker never heard it was done.
4. Duplicates always come from retries: a producer with no reply resends, and a consumer that crashes before acknowledging is sent the message again.
5. To reach an **exactly-once effect**, keep at-least-once delivery and add deduplication, so a repeat is recognised and skipped.

## Example

An idempotent consumer makes at-least-once safe by recording the message ID and the change together in one transaction.

```java
void handle(Message msg) {
    db.inTransaction(tx -> {
        // unique key on message_id: a repeat cannot insert the same id twice
        boolean isNew = tx.insertIfAbsent("processed_messages", msg.id());
        if (isNew) {
            tx.addToBalance(msg.accountId(), msg.amount());
        }
    });
    msg.ack();   // only after the commit; a repeat is acked and skipped
}
```

```python
def handle(msg):
    with db.transaction() as tx:
        # unique key on message_id: a repeat cannot insert the same id twice
        is_new = tx.insert_if_absent("processed_messages", msg.id)
        if is_new:
            tx.add_to_balance(msg.account_id, msg.amount)
    msg.ack()    # only after the commit; a repeat is acked and skipped
```

What to notice:

- The ID insert and the balance change are in **one** transaction, so either both happen or neither does; a crash cannot record the ID without applying the change.
- The unique key on `message_id` blocks a duplicate: the second delivery fails the insert, so `isNew` is false and the balance is left alone.
- `msg.ack()` runs only after the commit, so a crash before it just re-delivers the message and the dedupe handles it.

## Rules and defaults

- **Kafka delivery:** at-least-once by default; the idempotent producer is on by default (`enable.idempotence=true`), so the broker drops producer resends inside Kafka.
- **Kafka consumer isolation:** `isolation.level` is `read_uncommitted` by default, so a consumer sees writes from a transaction that later aborts unless you set `read_committed`.
- **Kafka Streams:** `processing.guarantee` is `at_least_once` by default; `exactly_once_v2` still covers only Kafka-internal reads and writes.
- **SQS:** standard queues are at-least-once; FIFO queues deduplicate a resend with the same deduplication ID within a 5-minute window.
- **Outside systems:** a broker cannot undo an email, a charge or your database write, so deduplicate before the side effect.

## Not to be confused with

**Delivery** is how many times the message reaches the consumer; **processing** is how many times its effect is applied. Kafka's exactly-once makes a chain of Kafka reads and writes atomic, not delivery over the network. Rule: across a network you get at-least-once; exactly-once is an effect you build with idempotency, not a delivery the broker promises end to end.

## Common mistakes

- **"Publish the event right after the database write, in the code."** If the write commits but the publish fails (or the reverse), the two disagree. The **transactional outbox** pattern fixes this: write the change and an outbox row in one transaction, and a relay publishes outbox rows later, so the event is never lost though it may be published more than once.
- **"An idempotent producer makes my consumer idempotent."** No. It only stops duplicate writes inside Kafka; a consumer that applies the same message twice to your database still needs its own dedupe.

## Interview Qs

### Explain at-most-once, at-least-once and exactly-once.

At-most-once: zero or one delivery, so a message can be lost but never repeated. At-least-once: one or more, so nothing is lost but repeats happen. Exactly-once: the effect happens once, built from at-least-once plus deduplication. The level depends on whether the consumer acknowledges before or after the work.

### Is exactly-once delivery really possible?

Not end to end across a network. An acknowledgement can be lost, so someone must resend or give up, forcing either a possible duplicate or a possible loss. What systems actually offer is exactly-once **processing**: Kafka within Kafka, or at-least-once plus an idempotent consumer everywhere else.

### How do you make a consumer idempotent?

Give each message a stable ID. In one transaction, insert the ID into a processed-messages table with a unique key and apply the change; a repeat fails the insert and is skipped. Alternatively use naturally idempotent writes, like an upsert that sets an absolute value.

### What is the transactional outbox pattern?

It solves the risk that a service commits a database change but then fails to publish the matching event. You write the change and an outbox row in the same transaction, and a separate relay reads the outbox and publishes the event. The relay may publish more than once, so consumers must be idempotent.
