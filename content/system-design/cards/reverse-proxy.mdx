## What it is

A reverse proxy is a server that stands in front of your app servers and takes every client request first. The client connects only to the proxy; the proxy then forwards the request to one of the real app servers, which live on a private network and have no public address. Those servers answer the proxy, and the proxy answers the client. Because every request passes through it, the proxy is a natural place to do shared jobs once: ending HTTPS, caching, compression and serving static files.

## Why it exists

If every app server faces the internet directly, each one must hold a TLS certificate, decrypt HTTPS, fend off attacks, and publish its own address, and clients must know all of those addresses. That repeats work and exposes every machine. A reverse proxy does the shared, edge-facing jobs in one place and hides the app servers behind it, so the servers only handle application logic on a trusted private network.

## How it works

1. The client opens an HTTPS connection to the proxy's public address, believing it is the application.
2. The proxy decrypts the request ([TLS termination](term:tls-termination)), so the app servers never handle encryption.
3. The proxy reads the HTTP request and decides what to do: serve a cached reply or a static file itself, or forward the request onward.
4. For forwarded requests it opens a connection to a private app server, adds the real client IP in an [X-Forwarded-For](term:x-forwarded-for) header, and passes the request on.
5. The app server replies to the proxy, which may compress or cache the reply, then sends it back to the client.

So the key is that one machine faces the internet and the rest stay hidden.

## Example

A small nginx reverse proxy that ends TLS, serves static files, and forwards the rest:

```nginx
server {
    listen 443 ssl;                              # TLS ends here
    ssl_certificate     /etc/nginx/site.crt;
    ssl_certificate_key /etc/nginx/site.key;
    gzip on;                                     # off by default
    gzip_types text/css application/javascript;  # text/html is always included
    location /static/ { root /var/www; }         # nginx serves these itself
    location / {
        proxy_pass http://app:8080;              # plain HTTP to the private app
        proxy_set_header Host $host;             # pass the client's host name
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

What to notice:

- `listen 443 ssl` with the two certificate lines is where HTTPS is decrypted; the app server behind it speaks plain HTTP and never sees a certificate.
- `location /static/` is served straight from disk by nginx, so those requests never reach the app server at all.
- `proxy_pass http://app:8080` forwards everything else to the private app; `app` resolves on the internal network, not from the internet.
- Without the `X-Forwarded-For` line, the app would log the proxy's IP for every request instead of the real client's.

## Rules and defaults

- **Compression:** off by default (`gzip off`); once on, nginx compresses only `text/html` until you list more types.
- **Response cache:** off by default (`proxy_cache off`); you must configure a cache zone to use it.
- **Upstream timeouts:** 60 s each for connect, send and read in nginx; a slow app server past these gets a 504 returned to the client.
- **Client IP:** the app server sees the proxy's IP unless the proxy adds `X-Forwarded-For` and the app is configured to trust it (only from your own proxy, since clients can forge it).
- **Single point of failure:** one proxy means one thing whose failure takes down everything, so run at least two.

## Not to be confused with

A forward proxy sits in front of clients and sends their outbound requests to the internet, hiding the clients (a company or VPN proxy). A reverse proxy sits in front of servers and receives inbound requests for them, hiding the servers. A [load balancer](card:load-balancer) spreads requests across many identical servers; a reverse proxy adds edge features and is useful even with one server. Rule: forward proxy hides clients, reverse proxy hides servers, load balancer spreads load. Tools like nginx and HAProxy can act as all three at once.

## Interview Qs

### Reverse proxy versus load balancer?

A load balancer spreads requests across many servers doing the same job, so it needs several servers to be useful. A reverse proxy is one front door that adds TLS termination, caching, compression and security, and helps even with a single app server. Tools such as nginx and HAProxy do both roles together.

### What is TLS termination and why do it at the proxy?

The proxy holds the certificate and decrypts HTTPS, so the app servers skip that work and certificates live in one place. Traffic from the proxy to the app is plain HTTP on a private network; if that network is not trusted, the proxy re-encrypts before forwarding.

### Behind a proxy, how does the app see the client's real IP?

The proxy adds the client's address to the `X-Forwarded-For` header; AWS ALB does this automatically, nginx with `proxy_set_header`. The app reads the client IP from that header, but trusts it only when the request came from your own proxy, since a client can put anything in it.
