## What it is

Concurrency control is how a database stops two users who change the same row at once from clobbering each other. It uses one of two strategies. **Pessimistic locking** assumes clashes are likely, so it locks the row before changing it; anyone else waits. **Optimistic locking** assumes clashes are rare, so it takes no lock: it reads a version number with the row and, at write time, retries unless the version is unchanged. You saw in [ACID](card:acid-transactions) that the default level can lose an update; this stops that.

## Why it exists

Two users read the same row, both change it in memory, and both write it back. Without any control, the second write silently overwrites the first: a seat is sold twice, or a stock count is wrong. This is a lost update. You could force every writer to wait in line with a lock, but locking is expensive when clashes are actually rare, and dangerous if a lock is held while a human thinks. Having both strategies lets you lock only when contention is real, and otherwise check-and-retry, which costs nothing when nothing clashes.

## How it works

The comparison shows the two flows side by side; read it, then the notes.

<Compare id="optimistic-vs-pessimistic-locking" />

1. Optimistic: read the row and its `version`. Later, run `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`. If 1 row changes you won; if 0 rows change, someone else wrote first, so reload and retry.
2. Pessimistic: run `SELECT ... FOR UPDATE` to lock the row, make your change, then commit, which releases the lock. Other writers wait at the `SELECT`.
3. Often the simplest option is neither explicit lock: one atomic conditional update, such as `UPDATE seats SET holder = 42 WHERE id = 7 AND holder IS NULL`, where the check and the write happen together.
4. Across separate services, a [distributed lock](card:distributed-lock) such as Redis `SET key value NX PX 30000` expires on its own if its holder dies.

So the key is: lock only hot rows in short transactions; everywhere else, check a version or use one atomic update.

## Example

Optimistic save of a page, with a `version` column, in application code:

```java
boolean savePage(Connection db, long id, String body, int readVersion)
        throws SQLException {
    String sql = "UPDATE pages SET body = ?, version = version + 1"
               + " WHERE id = ? AND version = ?";
    try (PreparedStatement ps = db.prepareStatement(sql)) {
        ps.setString(1, body);
        ps.setLong(2, id);
        ps.setInt(3, readVersion);
        return ps.executeUpdate() == 1;  // 0 rows: conflict, reload and retry
    }
}
```

```python
def save_page(conn, page_id, body, read_version):
    with conn.cursor() as cur:
        cur.execute(
            "UPDATE pages SET body = %s, version = version + 1"
            " WHERE id = %s AND version = %s",
            (body, page_id, read_version),
        )
        conn.commit()
        return cur.rowcount == 1  # 0 rows: conflict, reload and retry
```

What to notice:

- `read_version` is the version the user had when they loaded the page. The `WHERE version = ?` is the whole safety check: it passes only if nobody wrote in between.
- The row count is the signal: `1` means saved, `0` means a conflict. There is no lock, so no other writer was blocked.
- Remove `AND version = ?` and the last writer always wins silently, which is the lost update this prevents.
- Pessimistic locking instead would be `SELECT ... FOR UPDATE` first, which makes other writers wait rather than retry.

## Rules and defaults

- **Lock wait timeout:** MySQL 8.4 InnoDB waits `innodb_lock_wait_timeout` (50 s by default), then errors 1205 and rolls back only that statement. PostgreSQL waits indefinitely unless you set `lock_timeout` (0, off, by default).
- **Deadlock handling:** PostgreSQL checks for a deadlock after `deadlock_timeout` (1 s) of waiting; InnoDB detects them and rolls back the smaller transaction. The aborted one must be retried.
- **Avoid deadlocks:** lock rows in the same order everywhere, and keep transactions short.
- **JPA `@Version`:** adds the version column and the version-check UPDATE for you (Jakarta Persistence 3.2).
- **Last safety net:** a unique constraint, for example on (show, seat), rejects a double booking even if the application logic has a gap.

## Not to be confused with

- **Optimistic vs pessimistic:** optimistic acts at write time and retries on a clash; pessimistic acts first and makes others wait.
- **A row lock vs an atomic update:** `SELECT ... FOR UPDATE` then update is two steps holding a lock; one conditional `UPDATE` does the check and write together. Rule: prefer the single atomic update when the logic fits in one statement.

## Common mistakes

- **"Optimistic locking is always better because it never blocks."** Under heavy contention its retries pile up and waste work; for hot rows, pessimistic locking or a queue is faster.

## Interview Qs

### Optimistic or pessimistic locking: when do you use each?

Optimistic when conflicts are rare or edits are long, like forms: no waiting, just retry on a version mismatch. Pessimistic when many writers fight over the same rows and retries would pile up: lock with SELECT ... FOR UPDATE in a short transaction. Never hold a lock across user think time.

### How does optimistic locking work?

Each row carries a version. Read it with the data. Write with `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`. If 0 rows change, someone else won: reload, then retry or show a conflict. JPA's `@Version` does this for you.

### How do you stop two users booking the same seat?

Make the claim one atomic step: update the seat only WHERE it is still free and check that 1 row changed, or lock it with SELECT ... FOR UPDATE in a short transaction. Add a unique constraint on (show, seat) as the last safety net against a double booking.

### What is a deadlock, and how do you avoid it?

Two transactions each hold a lock the other needs, so neither can proceed. PostgreSQL and InnoDB detect this and abort one of them. Avoid it by locking rows in the same order everywhere, keeping transactions short, and retrying the aborted transaction.
