## Why it exists

Two users read the same row and both write it back. Without control, the last write silently wins: a seat is sold twice, or stock goes wrong.

## How it works

<Compare id="optimistic-vs-pessimistic-locking" />

- **Often simplest:** one atomic conditional update, such as `UPDATE seats SET holder = 42 WHERE id = 7 AND holder IS NULL`. The check and the write happen together.
- **MVCC** in PostgreSQL: plain reads never block writers, and row locks block only other writers and lockers.
- **Across services**, a [distributed lock](card:distributed-lock) such as Redis `SET key value NX PX 30000` expires by itself if its holder dies.

## Example

Optimistic save of a page, with a `version` column:

```java
boolean savePage(Connection db, long id, String body, int readVersion)
        throws SQLException {
    String sql = "UPDATE pages SET body = ?, version = version + 1"
               + " WHERE id = ? AND version = ?";
    try (PreparedStatement ps = db.prepareStatement(sql)) {
        ps.setString(1, body);
        ps.setLong(2, id);
        ps.setInt(3, readVersion);
        return ps.executeUpdate() == 1;  // 0 rows: conflict, reload and retry
    }
}
```

```python
def save_page(conn, page_id, body, read_version):
    with conn.cursor() as cur:
        cur.execute(
            "UPDATE pages SET body = %s, version = version + 1"
            " WHERE id = %s AND version = %s",
            (body, page_id, read_version),
        )
        conn.commit()
        return cur.rowcount == 1  # 0 rows: conflict, reload and retry
```

Pessimistic: lock first, and others wait.

```sql
BEGIN;
SELECT stock FROM items WHERE id = 7 FOR UPDATE;  -- other writers wait here
UPDATE items SET stock = stock - 1 WHERE id = 7;
COMMIT;                                           -- lock released
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Wait for a row lock | 50 s, then error 1205; only that statement rolls back | MySQL 8.4 InnoDB (`innodb_lock_wait_timeout`) |
| Wait for a lock | No limit (`lock_timeout` = 0 turns it off) | PostgreSQL 18 |
| Deadlock check | After 1 s of waiting (`deadlock_timeout`) | PostgreSQL 18 |
| Deadlock detection | On: InnoDB rolls back a small transaction | MySQL 8.4 InnoDB |

## Interview Qs

### Optimistic or pessimistic locking: when do you use each?

Optimistic when conflicts are rare or edits are long, like forms: no waiting, just retry on a version mismatch. Pessimistic when many writers fight over the same rows and retries would pile up: lock with SELECT ... FOR UPDATE in a short transaction.

### How does optimistic locking work?

Each row carries a version. Read it with the data. Write with `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`. If 0 rows change, someone else won: reload, then retry or show a conflict. JPA's `@Version` does this for you.

### How do you stop two users booking the same seat?

Make the claim one atomic step: update the seat only WHERE it is still free and check that 1 row changed, or lock it with SELECT ... FOR UPDATE. Add a unique constraint on (show, seat) as the last safety net.

### What is a deadlock, and how do you avoid it?

Two transactions each hold a lock the other needs. PostgreSQL and InnoDB detect this and abort one. Avoid it by locking rows in the same order everywhere, keeping transactions short, and retrying the aborted one.
