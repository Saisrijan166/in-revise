## Why it exists

Replicas receive each write at slightly different moments. A consistency model says what a read may return in that gap, so you can trade fresh data against speed and availability.

## How it works

<Compare id="strong-vs-eventual-consistency" />

- In between sit per-client guarantees: **read-your-writes** (you see your own changes) and **monotonic reads** (your reads never go back in time).
- **Causal consistency** keeps cause before effect: nobody sees a reply before the message it answers. Unrelated writes may show in different orders.
- You can often choose per request: DynamoDB's `ConsistentRead`, [Cassandra's consistency levels](card:tunable-consistency), MongoDB's read concerns.

## Example

A balance check must not read an old value; a product page can. A DynamoDB strong read:

```java
GetItemRequest req = GetItemRequest.builder()
    .tableName("Accounts")
    .key(Map.of("id", AttributeValue.builder().s("acc-42").build()))
    .consistentRead(true)   // strong; leave it out for eventual (half the cost)
    .build();
Map<String, AttributeValue> account = dynamo.getItem(req).item();
```

```python
resp = table.get_item(
    Key={"id": "acc-42"},
    ConsistentRead=True,   # strong; leave it out for eventual (half the cost)
)
account = resp.get("Item")
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Read consistency | Eventual; set `ConsistentRead` for strong (tables and local secondary indexes only) | Amazon DynamoDB |
| Read cost per 4 KB | Strong: 1 read unit; eventual: 0.5 | Amazon DynamoDB |
| Reads | Linearizable; opt-in `serializable` reads are faster but may be stale | etcd v3.6 |

## Interview Qs

### Strong vs eventual consistency?

Strong: every read returns the latest completed write, as if there were one copy. Eventual: replicas may return old values for a while, but agree once writes stop. Strong costs latency and availability; eventual is faster and keeps answering.

### When is eventual consistency acceptable?

When a slightly old value does no harm: like counts, feeds, view counts, DNS. Not for balances, stock or seat bookings, where acting on an old value sells the same thing twice.

### What is read-your-writes, and how do you get it?

After you write, your own reads show it, even if others still see the old value. Send that user's reads to the primary, or use session guarantees such as MongoDB causally consistent sessions or Cosmos DB session tokens.

### Why not make everything strongly consistent?

Each write must reach other replicas before it is confirmed, which adds latency, and when they cannot be reached the request fails. Azure Cosmos DB even blocks strong consistency by default for regions more than 8,000 km apart.
