## What it is

A consistency model is the exact promise a replicated store makes about what a read may return. When data is copied to several machines, each copy gets a write at a slightly different moment. The model tells you whether a read is guaranteed to return the newest value, or may return an older one for a while. Picking a model lets you trade fresh data against speed and availability, the choice that [CAP](card:cap-theorem) describes during a partition.

## Why it exists

Say your payment service keeps a copy of each account balance on two replicas for faster reads. A write updates one replica first; the other lags by a few milliseconds, sometimes more under load. Without a stated model you cannot reason about what a read sees in that gap, so one operation might act on an old balance by accident. A consistency model removes the guessing: it names what a read may return, so you can demand strong reads where staleness is dangerous and allow stale reads where it is harmless.

## How it works

<Compare id="strong-vs-eventual-consistency" />

1. **Strong (linearizable)** behaves as if there were one copy: once a write completes, every later read anywhere returns that value or a newer one.
2. **Eventual** lets reads return an older value for a while; if writes stop, all replicas end up equal.
3. Between them sit per-client promises: **read-your-writes** (you always see your own latest write) and **monotonic reads** (your reads never go backwards to an older value).
4. **Causal consistency** keeps cause before effect: no one sees a reply before the message it answers, though unrelated writes may appear in different orders on different nodes.

So the key is a ladder from strong to eventual, and you climb only as high as each operation needs.

## Example

A balance check must not read an old value; a list of past payments can. DynamoDB chooses per read with one flag.

```java
GetItemRequest req = GetItemRequest.builder()
    .tableName("Accounts")
    .key(Map.of("id", AttributeValue.builder().s("acc-42").build()))
    .consistentRead(true)   // strong read; omit it for an eventual read at half the cost
    .build();
Map<String, AttributeValue> account = dynamo.getItem(req).item();
```

```python
resp = table.get_item(
    Key={"id": "acc-42"},
    ConsistentRead=True,   # strong read; omit it for an eventual read at half the cost
)
account = resp.get("Item")
```

What to notice:

- `ConsistentRead=True` asks for a strong read, so the balance is the latest committed value, never a stale replica.
- Removing that line gives an eventual read: faster and half the read cost, but it may return an older balance.
- The choice is per call, so the same table serves strong reads for money and eventual reads for low-risk data.

## Rules and defaults

- **DynamoDB read default:** eventually consistent. Pass `ConsistentRead` for a strong read on a table or local secondary index; global secondary indexes support only eventual reads.
- **DynamoDB read cost:** a strong read uses 1 read unit per 4 KB; an eventual read uses 0.5.
- **etcd read default:** linearizable; an opt-in `serializable` read is faster but may be stale.
- **Strong is not free:** a strong write waits for other replicas, so it adds latency and fails when they are unreachable. Cosmos DB even blocks strong consistency by default across regions more than 8,000 km apart.

## Not to be confused with

Consistency models describe **what a read may return** over time. The C in [CAP](card:cap-theorem) is one specific model, linearizability, named during a partition. Isolation levels (in [ACID](card:acid-transactions)) describe how concurrent transactions on one database interleave, which is a different question. Rule: consistency models = which value a read sees across replicas; isolation levels = how transactions overlap on one node.

## Interview Qs

### What is the difference between strong and eventual consistency?

Strong: every read returns the latest completed write, as if there were one copy. Eventual: replicas may return old values for a while but agree once writes stop. Strong costs latency and availability; eventual is faster and keeps answering.

### When is eventual consistency acceptable?

When a slightly old value does no harm: like counts, feeds, view counts, DNS records. Not for balances, stock levels or seat bookings, where acting on an old value can sell the same thing twice or overdraw an account.

### What is read-your-writes, and how do you get it?

After you write, your own reads show your change even if other users still see the old value. Route that user's reads to the primary for a short time, or use session guarantees such as MongoDB causally consistent sessions or Cosmos DB session tokens.

### Why not make everything strongly consistent?

Each write must reach other replicas before it is confirmed, which adds latency, and when those replicas cannot be reached the write fails. For data that can safely lag, that is a cost with no benefit, so you reserve strong reads for operations where staleness is harmful.
