## What it is

Cache invalidation is keeping the cache in step with the database by removing or replacing a cached copy once the data has changed. A cache holds copies, and a copy is correct only until the original changes; after that it is stale. Invalidation gets rid of the stale copy, so a later read does not keep serving the old value. The hard part is that removing a popular key can send all its readers to the database at once.

## Why it exists

A cache speeds reads by serving a saved copy, but that copy does not know when the database behind it changes. Without invalidation, a price change or profile edit would never reach readers: they would keep seeing the old value until the key happened to be dropped. Invalidation makes the change visible, on a schedule you choose, from "within the TTL" to "on the next read". It is tricky because you must also avoid the flood of traffic that removing a hot key causes.

## How it works

| Way | What happens | Stale for |
| --- | --- | --- |
| **TTL** | The key deletes itself after a set time | Up to the TTL |
| **Delete on write** | After the database write, the app deletes the key | Until the delete lands |
| **Update on write** | The write also sets the new value ([write-through](card:write-through)) | Until both writes finish |
| **Versioned key** | Keys carry a version, like `user:42:v7`; a change bumps it | Old keys are never read again |
| **Change events** | A process reads the database's change log and deletes keys | Until the event is applied |

1. Give every key a TTL, so even if nothing else fires, a stale key clears itself within that time.
2. On a write, update the database and then delete (or update) the key, so the next read sees the change, not the TTL wait.
3. For many caches at once, drive deletes from the database's change log, so every cache, even in another region, drops the key.
4. Guard against the herd: when a hot key is removed, use a lock or lease so one request reloads it while others wait.

So a TTL is the floor of freshness, and write-time deletes or change events raise it.

## Example

A hot key expires. A simple lease with Redis `SET ... NX EX` lets one caller reload it; the others wait 50 ms and retry.

```java
String get(String key) throws InterruptedException {
    while (true) {
        String value = cache.get(key);
        if (value != null) return value;                     // hit
        // Miss: only the caller that wins this 10 s lock reloads.
        if (cache.setIfAbsent("lock:" + key, "1", Duration.ofSeconds(10))) {
            value = db.load(key);
            cache.set(key, value, Duration.ofMinutes(5));
            cache.delete("lock:" + key);
            return value;
        }
        Thread.sleep(50);                                    // others wait, then retry
    }
}
```

```python
def get(key):
    while True:
        value = cache.get(key)
        if value is not None:
            return value                                     # hit
        # Miss: only the caller that wins this 10 s lock reloads.
        if cache.set(f"lock:{key}", 1, nx=True, ex=10):
            value = db.load(key)
            cache.set(key, value, ex=300)
            cache.delete(f"lock:{key}")
            return value
        time.sleep(0.05)                                     # others wait, then retry
```

What to notice:

- `SET ... NX` sets the lock only if it does not exist, so exactly one caller wins and reloads; the rest see the lock and wait.
- The `EX 10` on the lock is a safety net: if the winner crashes before releasing it, the lock expires and another caller takes over.
- At Facebook, memcache leases cut the peak database load for one hot key from 17,000 to 1,300 queries per second.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Request coalescing (`proxy_cache_lock`) | Off; when on, a waiter goes to the backend itself after 5 s | nginx |
| Serve stale while refreshing (`proxy_cache_use_stale updating`) | Off | nginx |
| Lease tokens per key | At most one every 10 s | Facebook memcache (NSDI 2013) |

- **Keep a TTL even with delete-on-write:** if a delete is ever lost, the key still expires on its own.
- **Spread the TTLs:** add a small random jitter to each TTL so many keys do not all expire at once and cause an avalanche.
- **Cache misses too (negative caching):** when the database returns nothing, cache a short-lived "not found" marker, or repeated lookups for a missing key hit the database every time.

## Common mistakes

- **"Update the cached value on a write."** Two racing updates can land out of order, leaving the older value. Deleting the key is idempotent and avoids this, which is why Facebook deletes rather than updates.
- **"A missing row is nothing to cache."** Without negative caching, requests for data that does not exist (cache penetration) skip the cache and pound the database. Cache the "not found" result with a short TTL.

## Interview Qs

### How do you keep a cache consistent with the database?

Choose by how fresh the data must be. A TTL alone allows staleness up to the TTL. Delete the key after each database write for near-fresh reads, or write through when a read must see the write at once. Keep a TTL as a safety net; drive deletes from the change log when many caches must agree.

### Why delete the cached value on a write instead of updating it?

Deletes are idempotent, so a retried or reordered delete does no harm. Two racing updates, by contrast, can leave the older value in the cache. Facebook's memcache deletes on writes for this reason, and lets the next read reload the fresh value.

### What is a cache stampede, and how do you prevent it?

A hot key expires and many requests miss at once, all hitting the database together. Let one request reload it ([request coalescing](card:request-coalescing), a lock or a [lease](card:cache-lease)), [serve the old value](card:serve-stale) while it reloads, or [refresh hot keys early](card:early-expiration).

### How do you invalidate caches across many servers or regions?

Drive deletes from the database itself: a process reads committed changes and sends deletes to every cache. Facebook runs such a daemon, mcsqueal, on every database and batches its deletes, so caches in every region drop the stale key.
