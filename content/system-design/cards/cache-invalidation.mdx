## Why it exists

A cache holds copies. When the database changes, each copy is wrong until something removes or replaces it, and removing a hot key can flood the database.

## How it works

| Way | What happens | Stale for |
| --- | --- | --- |
| **TTL** | The key deletes itself after a set time | Up to the TTL |
| **Delete on write** | After the database write, the app deletes the key | Until the delete lands |
| **Update on write** | The write also sets the new value ([write-through](card:write-through)) | Until both writes finish |
| **Versioned key** | Keys carry a version, like `user:42:v7`; a change bumps it | Old keys are never read again |
| **Change events** | A process reads the database's change log and deletes keys | Until the event is applied |

- Keep a TTL even with the others: if a delete is lost, the key still expires.
- **Thundering herd:** when a hot key expires or is deleted, many requests miss at once. Fix it with [request coalescing](card:request-coalescing) or [leases](card:cache-lease) (one request reloads, the others wait), by [serving the stale copy](card:serve-stale) during the reload, or by [refreshing early](card:early-expiration).

## Example

A hot key expires. A simple lease with Redis `SET ... NX EX` lets one caller reload it; the others wait 50 ms and try again.

```java
String get(String key) throws InterruptedException {
    while (true) {
        String value = cache.get(key);
        if (value != null) return value;                     // hit
        // Miss: only the caller that wins this 10 s lock reloads.
        if (cache.setIfAbsent("lock:" + key, "1", Duration.ofSeconds(10))) {
            value = db.load(key);
            cache.set(key, value, Duration.ofMinutes(5));
            cache.delete("lock:" + key);
            return value;
        }
        Thread.sleep(50);                                    // others wait, then retry
    }
}
```

```python
def get(key):
    while True:
        value = cache.get(key)
        if value is not None:
            return value                                     # hit
        # Miss: only the caller that wins this 10 s lock reloads.
        if cache.set(f"lock:{key}", 1, nx=True, ex=10):
            value = db.load(key)
            cache.set(key, value, ex=300)
            cache.delete(f"lock:{key}")
            return value
        time.sleep(0.05)                                     # others wait, then retry
```

At Facebook, memcache leases cut the peak database load for hot keys from 17,000 to 1,300 queries per second.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Request coalescing (`proxy_cache_lock`) | Off; when on, a waiter goes to the backend itself after 5 s | nginx |
| Serve stale while refreshing (`proxy_cache_use_stale updating`) | Off | nginx |
| Lease tokens per key | At most one every 10 s | Facebook memcache (NSDI 2013) |

## Interview Qs

### How do you keep a cache consistent with the database?

Choose by how fresh the data must be. A TTL alone allows staleness up to the TTL. Delete the key after each database write for near-fresh reads, or write through when a read must see the write at once. Keep a TTL as a safety net.

### Why delete the cached value on a write instead of updating it?

Deletes are idempotent, so a retried or reordered delete does no harm. Two racing updates, by contrast, can leave the older value in the cache. Facebook's memcache deletes on writes for this reason.

### What is a cache stampede, and how do you prevent it?

A hot key expires and many requests miss at once, all hitting the database. Let only one request reload it (request coalescing, a lock or a lease), serve the old value meanwhile, or refresh hot keys a little before they expire.

### How do you invalidate caches across many servers or regions?

Drive deletes from the database itself: a process reads committed changes and sends deletes to every cache. Facebook runs such a daemon, mcsqueal, on every database and batches its deletes.
