## Why it exists

In a system of many services, a user's slow or failed request can break anywhere. You need data from the running system to notice the problem, find where it is, and see what went wrong.

## How it works

| Signal | Answers | Example |
| --- | --- | --- |
| **Metrics** | Is something wrong, and how much? | Checkout errors jump from 0.1% to 5% |
| **Traces** | Where did this request spend its time? | 1.8 s of a 2 s request was in the payment service |
| **Logs** | What exactly happened? | `card gateway timeout after 1.5 s` |

- **Join them:** each service passes the trace context to the next in a request header and writes the trace ID into every log line.
- **What to measure:** if you can track only four things, track latency, traffic, errors and saturation. Use percentiles such as p99, because averages hide the slow tail.
- **What to alert on:** only urgent, actionable problems that users feel or soon will.

## Example

Every hop sends this W3C Trace Context header, the OpenTelemetry default:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  00                                 version
  4bf92f3577b34da6a3ce929d0e0e4736   trace ID: 16 bytes, same in every service
  00f067aa0ba902b7                   parent span ID: 8 bytes, the calling span
  01                                 flags: sampled
```

The payment service writes a structured log line that carries the same trace ID:

```json
{"time": "2026-10-16T10:15:02Z", "level": "error", "service": "payment",
 "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736", "msg": "card gateway timeout"}
```

Search the logs for that trace ID, and every service's lines for this one request appear together.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| How trace context is sent | W3C Trace Context (`traceparent` header) and W3C Baggage | OpenTelemetry SDKs (`OTEL_PROPAGATORS`) |
| Which traces are recorded | Every new trace; child spans follow the parent's choice | OpenTelemetry SDKs (`parentbased_always_on`) |
| How often metrics are pulled | Every 1 minute, with a 10 s timeout | Prometheus 3.15 (`scrape_interval`, `scrape_timeout`) |

## Interview Qs

### Logs vs metrics vs traces?

Metrics are numbers over time, cheap to keep, and drive dashboards and alerts. Traces follow one request across services as timed spans. Logs are detailed records of single events. Metrics show something is wrong, traces show where, logs show what happened.

### What would you monitor for this service?

The four golden signals: latency (successes and failures apart), traffic, errors, and saturation of the tightest resource, such as a connection pool. Track latency as percentiles like p99, not averages.

### A request is slow in a microservices system. How do you find out why?

Use distributed tracing. Each service passes the trace context in headers and records spans, so the trace shows which span took the time. Then search the logs by that trace ID to see what happened inside it.

### What should wake someone up at night?

Only urgent, actionable, user-visible problems, such as the error budget burning fast. Causes like high CPU or one failed request go to dashboards or tickets, not pages.
