## What it is

Observability is being able to understand what a running system is doing from the data it emits, without attaching a debugger to it. That data comes in three kinds, called signals. Metrics are numbers tracked over time. Traces follow a single request as it moves across services. Logs are detailed records of individual events. You need all three because each answers a different question.

## Why it exists

In a single program you can read the code and attach a debugger. In a [microservices](card:microservices) system, one user's slow or failed request passes through many services, and the fault can be in any of them. You cannot pause production to look. Instead the running system must continuously emit metrics, traces and logs, so that when something breaks you can notice it, find which service is responsible, and see what went wrong, all from the data already flowing out.

## How it works

| Signal | Answers | Example |
| --- | --- | --- |
| **Metrics** | Is something wrong, and how much? | Checkout errors jump from 0.1% to 5% |
| **Traces** | Where did this request spend its time? | 1.8s of a 2s request was in the payment service |
| **Logs** | What exactly happened there? | `card gateway timeout after 1.5 s` |

1. Each service passes a shared trace context to the next one in a request header, and writes the same trace ID into every log line.
2. Metrics raise the alarm when a signal such as error rate or latency crosses a threshold.
3. A trace for one slow request shows which span, and so which service, took the time.
4. Logs filtered by that trace ID show the detailed events inside that span.

So the key is the shared trace ID: it is what lets you jump from a metric, to the slow span, to the exact log lines for that one request.

## Example

Every hop sends this W3C Trace Context header, the OpenTelemetry default:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
  00                                 version
  4bf92f3577b34da6a3ce929d0e0e4736   trace ID: same in every service for this request
  00f067aa0ba902b7                   parent span ID: the calling span
  01                                 flags: this trace is sampled (recorded)
```

The payment service then writes a structured log line carrying that same trace ID:

```json
{"time": "2026-10-16T10:15:02Z", "level": "error", "service": "payment",
 "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736", "msg": "card gateway timeout"}
```

What to notice:

- The `trace_id` in the header and in the log line is identical, so searching logs for that ID gathers every service's lines for this one request in one place.
- The log is JSON with named fields (`level`, `service`, `trace_id`), so you can filter by any of them; a plain-text log line could not be filtered this cleanly.
- The `01` flag marks the trace as sampled; an unsampled trace is still propagated but not recorded, which keeps tracing affordable at high traffic.

## Rules and defaults

- **Trace context format:** OpenTelemetry SDKs send W3C Trace Context (the `traceparent` header) and W3C Baggage by default (`OTEL_PROPAGATORS`).
- **Which traces are recorded:** the default sampler records every new trace, and child spans follow the parent's sampled decision (`parentbased_always_on`). High-traffic systems lower this.
- **Metric scrape interval:** Prometheus 3.15 pulls metrics every 1 minute by default, with a 10-second timeout (`scrape_interval`, `scrape_timeout`).
- **Use percentiles for latency:** report p99, not the average, because an average hides a slow tail that a few users feel badly.

## Common mistakes

- **"Log everything as free text."** Unstructured logs are hard to search and correlate. Use structured (JSON) logs with a trace ID field, so you can filter by request, service and level.
- **"Alert on every cause."** Alerting on CPU, memory and single errors creates noise that hides real problems. Alert on user-visible symptoms and SLO burn rate; send causes to dashboards and tickets.

## Interview Qs

### Logs versus metrics versus traces: when do you use each?

Metrics are numbers over time, cheap to keep, and drive dashboards and alerts: they tell you something is wrong. Traces follow one request across services as timed spans: they tell you where the time went. Logs are detailed records of single events: they tell you what happened. You use all three together, narrowing from the metric to the slow span to the exact log lines.

### A request is slow in a microservices system. How do you find out why?

Use distributed tracing. Each service passes the trace context in a header and records a span, so the trace for that request shows which span, and so which service, took the time. Then filter the logs by that request's trace ID to read what happened inside that span. Metrics tell you it is slow; the trace tells you where.

### What should wake someone at night, and what should not?

Only urgent, actionable, user-visible problems, such as the error budget burning fast or checkout failing. Causes like high CPU, high memory or a single failed request are not symptoms users feel directly, so they belong on dashboards or in tickets, not on a pager that wakes a tired engineer for nothing.
