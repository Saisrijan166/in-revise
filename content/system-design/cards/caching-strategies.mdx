## What it is

A caching strategy is the rule that decides how a cache is kept in step with its [source of truth](card:caching-layers), the database. It has two separate parts. The **read** part decides who loads data into the cache when a read is not found there: the app, or the cache itself. The **write** part decides what happens to the cache when data is written: is the cache updated together with the database, later than it, or skipped. You choose one of each and combine them.

## Why it exists

A cache holds a copy of the data, and a copy can go out of step with the original. If you never thought about it, the cache could serve data that was changed long ago, or a write could leave a stale copy behind. Naming the strategies turns a vague worry into a clear choice: you decide, per kind of data, how fresh reads must be and how fast writes must be, and pick the read and write rule that match. That trade-off, fresh reads against fast writes, is the heart of caching.

## How it works

| Part | Strategy | What happens | Watch out |
| --- | --- | --- | --- |
| Read | [Cache-aside](card:cache-aside) | The app checks the cache; on a miss it reads the database and fills the cache | The first read of each key is slow |
| Read | Read-through | The cache loads a miss from the database through a loader | The cache must know how to load |
| Read | Refresh-ahead | A key read close to its expiry is reloaded in the background | Wasted loads if the guess is wrong |
| Write | [Write-through](card:write-through) | The cache and the database are both updated, then the write is confirmed | Every write is slower |
| Write | Write-behind | Confirmed after the cache write; the database is updated later, in batches | A crash before the flush loses writes |
| Write | Write-around | Only the database is written; the cache fills on a later read miss | The next read of that key misses |

1. For reads, pick who fills the cache: the app (cache-aside), the cache through a loader (read-through), or a background reload before expiry (refresh-ahead).
2. For writes, pick when the cache changes: with the database (write-through), after it (write-behind), or not at all on the write (write-around).
3. Combine the two. A common pair is cache-aside with write-around: the cache holds only read data, and writes skip it.

So the name of each strategy tells you the path the data takes.

## Example

Think of the growing payment service. Its product catalogue and its payment records need different strategies.

- **Product catalogue:** read constantly, changed rarely. Use cache-aside: the cache fills from reads and stays small. On the rare update, delete the key so the next read reloads it.
- **Payment write-counts shown on a dashboard:** written very often, read occasionally, and a few seconds of loss is acceptable. Use write-behind: confirm fast and flush to the database in batches.

What to notice:

- The same system uses different strategies for different data; there is no single right answer for the whole service.
- Refresh-ahead only helps when the cache can guess which keys will be read again; each wrong guess costs a database read for nothing.
- Write-around keeps data that is written but rarely read from pushing hot keys out of the cache.

## Not to be confused with

Cache-aside and read-through both load the database on a read miss, but differ in who does the loading. In cache-aside the application code checks the cache, loads the database on a miss and fills the cache. In read-through the cache does this itself through a loader, so the application only ever talks to the cache. Rule: cache-aside puts the logic in your app; read-through hides it inside the cache.

## Interview Qs

### What caching strategies do you know?

For reads: cache-aside, where the app loads misses, and read-through, where the cache loads them; refresh-ahead reloads hot keys in the background before they expire. For writes: write-through, which updates cache and database together, write-behind, which updates the database later in batches, and write-around, which writes only the database.

### Why would you use write-around?

When data is written often but read rarely or much later, such as audit logs. Writing it straight to the database keeps it from filling the cache and pushing out hot keys. The first read after a write misses, so write-around is paired with cache-aside, which reloads the key on that miss.

### What is refresh-ahead, and when does it hurt?

The cache reloads a key that is read close to its expiry, in the background, so a reader never waits for the reload. It hurts when the guess is wrong: keys that nobody reads again are reloaded anyway, each reload costing a database read for a value no one uses.
