## Why it exists

A cache holds a copy of the database. Every design must decide how the copy gets filled and how writes keep it close to the database, trading fresh reads against fast writes.

## How it works

| Strategy | Path | What happens | Watch out |
| --- | --- | --- | --- |
| [Cache-aside](card:cache-aside) | Read | The app checks the cache; on a miss it reads the database and fills the cache | The first read of each key is slow |
| Read-through | Read | The cache loads a miss from the database through a loader | The cache must know how to load |
| Refresh-ahead | Read | A key read close to its expiry is reloaded in the background | Wasted loads if the guess is wrong |
| [Write-through](card:write-through) | Write | The cache and the database are both updated, then the write is confirmed | Every write is slower |
| Write-behind | Write | Confirmed after the cache write; the database is updated later, in batches | A crash before the flush loses writes |
| Write-around | Write | Only the database is written; the cache fills on a later read miss | The next read of that key misses |

- Refresh-ahead only helps when the cache can guess which keys will be read again; each wrong guess costs a database read.
- Write-around keeps data that is written but rarely read from pushing hot keys out of the cache.

## Interview Qs

### What caching strategies do you know?

For reads: cache-aside (the app loads misses) and read-through (the cache loads them); refresh-ahead reloads hot keys before they expire. For writes: write-through (cache and database together), write-behind (database later, in batches) and write-around (database only).

### Cache-aside vs read-through?

Both load from the database on a miss. In cache-aside the app does it; in read-through the cache does it through a loader, so the app talks only to the cache.

### When would you use write-around?

When data is written often but read rarely or much later, such as audit logs, so it does not push hot keys out of the cache. The first read after a write misses, so pair it with cache-aside.

### What is refresh-ahead, and when does it hurt?

The cache reloads a key that is read close to its expiry, in the background, so readers do not wait. It hurts when it guesses wrong: keys nobody reads again still cost a database load each time.
