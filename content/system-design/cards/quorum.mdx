## What it is

A quorum is a rule for how many replicas a read and a write must involve so that a read is sure to see the latest write, without contacting every copy. You keep N copies of each piece of data. A write is confirmed once W replicas have stored it. A read asks R replicas and keeps the newest value it gets back. The rule R + W > N guarantees that the set of replicas a read touches and the set a write touched always overlap in at least one replica.

## Why it exists

With [replication](card:sharding-and-replication) you could make writes wait for all N copies, so every read is fresh, but then one slow or dead replica blocks every write. The other extreme, write to one and read from one, is fast but a read can hit a replica that never got the write and return a stale value. Quorums give you a dial between these. By choosing W and R so that R + W > N, you get fresh reads while still tolerating some replicas being down, which is the balance a busy payment store needs.

## How it works

1. A write is sent to all N replicas but is confirmed to the client once W of them acknowledge it.
2. The remaining replicas may still hold the old value for a short time.
3. A read asks R replicas and collects their versions.
4. Because R + W > N, the R replicas a read asks must include at least one of the W replicas that took the write, so the read sees the newest version.
5. Stale replicas are repaired in the background, for example by read repair.

So the key is the overlap: R + W > N means a read can never completely miss a confirmed write.

## Example

With N = 3, a majority is floor(3 / 2) + 1 = 2. Cassandra sets R and W per query through consistency levels such as ONE, QUORUM and ALL.

```java
SimpleStatement write = SimpleStatement
    .newInstance("UPDATE payments SET status = ? WHERE id = ?", "SETTLED", 42)
    .setConsistencyLevel(DefaultConsistencyLevel.QUORUM);   // W = 2 of 3
session.execute(write);

SimpleStatement read = SimpleStatement
    .newInstance("SELECT status FROM payments WHERE id = ?", 42)
    .setConsistencyLevel(DefaultConsistencyLevel.QUORUM);   // R = 2 of 3
Row row = session.execute(read).one();
```

```python
from cassandra import ConsistencyLevel
from cassandra.query import SimpleStatement

write = SimpleStatement("UPDATE payments SET status = %s WHERE id = %s",
                        consistency_level=ConsistencyLevel.QUORUM)  # W = 2 of 3
session.execute(write, ("SETTLED", 42))

read = SimpleStatement("SELECT status FROM payments WHERE id = %s",
                       consistency_level=ConsistencyLevel.QUORUM)   # R = 2 of 3
row = session.execute(read, (42,)).one()
```

What to notice:

- Both the write and the read use QUORUM, so W = 2 and R = 2, and 2 + 2 > 3 guarantees the read sees the latest write.
- One replica can be down and both calls still succeed, because each needs only 2 of 3.
- Dropping the read to ONE (R = 1) breaks the overlap: the read might hit the one replica that missed the write and return a stale status.

## Rules and defaults

- **Common setting:** the Dynamo paper used N = 3, R = 2, W = 2, which tolerates one replica being down while keeping fresh reads.
- **Cassandra QUORUM:** a majority of the replicas, floor(N / 2) + 1, so 2 of 3 (Apache Cassandra 5.0).
- **Driver default when you set none:** LOCAL_ONE, one replica in the local data centre, in the Cassandra Java driver 4.x and the DataStax Python driver 3.0 and later. That is R = W = 1, so set QUORUM when you need the overlap.
- **Overlap is not full linearizability:** sloppy quorums and concurrent writes can still produce stale reads, so use consensus for compare-and-set.

## Interview Qs

### What does R + W > N mean?

N is the number of copies, W how many must confirm a write, and R how many a read asks. If R + W is greater than N, the replicas a read asks always include at least one that holds the latest confirmed write, so the read is not stale in the simple case.

### With N = 3, which R and W would you choose?

W = 2 and R = 2 is the usual choice: reads see the latest write, and one replica can be down without blocking. For read-heavy data you can use R = 1 and W = 3 for the fastest reads, but then any replica being down blocks every write.

### What happens when fewer than W replicas are up?

With a strict quorum the write fails: the system gives up availability to stay consistent. Dynamo uses a sloppy quorum instead: it writes to the next healthy nodes, which hand the data back when the real owner returns, called hinted handoff.

### Does a quorum make reads linearizable?

Not on its own. Sloppy quorums, concurrent writes and partly failed writes can still return stale values, and Kleppmann warns against relying on the overlap for strong guarantees. For compare-and-set, use consensus, such as Cassandra's Paxos-based `IF NOT EXISTS`.
