## Why it exists

Copies of the same data can disagree for a while. A quorum rule makes every read set overlap every write set, so a read reaches an up-to-date copy without waiting for all of them.

## How it works

<Mermaid
  alt="N = 3 replicas. A write of x = 7 with W = 2 reaches replicas A and B; replica C is behind and still has x = 5. A read with R = 2 asks replicas B and C. B has x = 7, so the read returns the newer value. The write set and the read set overlap at B."
  chart={`flowchart LR
  W(["Write x = 7, W = 2"]) --> A[("Replica A: x = 7")]
  W --> B[("Replica B: x = 7")]
  C[("Replica C: x = 5, behind")]
  R(["Read, R = 2"]) --> B
  R --> C`}
/>

- Any R replicas include at least one that took the write. The read keeps the newest version; stale copies are fixed later, for example by read repair.
- Cassandra sets R and W per query with [consistency levels](card:tunable-consistency) such as ONE, QUORUM and ALL.

## Example

N = 3, so a majority is 3 / 2 + 1 = 2 (integer division).

- **W = 2, R = 2:** 2 + 2 = 4 > 3. Reads always overlap the write, and one replica can be down.
- **W = 1, R = 1:** 1 + 1 = 2 ≤ 3. Fast, but a read can hit the one replica that missed the write.

```java
SimpleStatement write = SimpleStatement
    .newInstance("UPDATE users SET name = ? WHERE id = ?", "Asha", 42)
    .setConsistencyLevel(DefaultConsistencyLevel.QUORUM);   // W = 2 of 3
session.execute(write);

SimpleStatement read = SimpleStatement
    .newInstance("SELECT name FROM users WHERE id = ?", 42)
    .setConsistencyLevel(DefaultConsistencyLevel.QUORUM);   // R = 2 of 3
Row row = session.execute(read).one();
```

```python
from cassandra import ConsistencyLevel
from cassandra.query import SimpleStatement

write = SimpleStatement("UPDATE users SET name = %s WHERE id = %s",
                        consistency_level=ConsistencyLevel.QUORUM)  # W = 2 of 3
session.execute(write, ("Asha", 42))

read = SimpleStatement("SELECT name FROM users WHERE id = %s",
                       consistency_level=ConsistencyLevel.QUORUM)   # R = 2 of 3
row = session.execute(read, (42,)).one()
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Common (N, R, W) | (3, 2, 2) | Amazon Dynamo paper, 2007 |
| QUORUM level | A majority of replicas, n / 2 + 1: 2 of 3 | Apache Cassandra 5.0 |
| Consistency level when you set none | LOCAL_ONE: one replica in the local data centre | Cassandra Java driver 4.x; DataStax Python driver 3.0 and later |

## Interview Qs

### What does R + W > N mean?

N is the number of copies, W how many must confirm a write, and R how many a read asks. If R + W > N, the replicas a read asks always include one that has the latest confirmed write.

### N = 3. Which R and W would you choose?

W = 2 and R = 2 is the usual choice: reads see the latest write, and one replica can be down. For read-heavy data, R = 1 and W = 3 gives the fastest reads, but any replica that is down blocks writes.

### What happens when fewer than W replicas are up?

With a strict quorum the write fails: the system gives up availability to stay consistent. Dynamo uses a sloppy quorum instead: it writes to the next healthy nodes, which hand the data back when the owner returns (hinted handoff).

### Does a quorum make reads linearizable?

Not by itself. Sloppy quorums, concurrent writes and partly failed writes can still give stale reads, and Kleppmann warns against relying on it. For compare-and-set, use consensus, such as Cassandra's Paxos-based `IF NOT EXISTS`.
