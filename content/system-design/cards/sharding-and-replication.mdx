## Why it exists

One database server eventually runs out of room for reads, writes or data, and if it dies, everything stops. Replication and sharding solve different parts of that.

## How it works

<Mermaid
  alt="Two diagrams. Replication: a primary database copies every write to replica 1 and replica 2, so all three hold the same data. Sharding: a router sends users A to M to shard 1 and users N to Z to shard 2, so each shard holds different data."
  chart={`flowchart TD
  subgraph REP [Replication: same data, many copies]
    P[(Primary)] -- copies writes --> R1[(Replica 1)]
    P -- copies writes --> R2[(Replica 2)]
  end
  subgraph SHD [Sharding: different data on each node]
    RT[Router] -- users A to M --> S1[(Shard 1)]
    RT -- users N to Z --> S2[(Shard 2)]
  end`}
/>

- **Replication:** full copies. In leader-based setups all writes go to the primary; replicas serve reads and can take over.
- **Sharding:** each shard holds a slice of the rows, picked by a shard key such as `user_id`.
- **Together:** real systems replicate each shard. In MongoDB, every shard must be a replica set.

## Example

Pick a shard from a key with a stable hash:

```java
int shardFor(String userId, int shards) {
    // hashCode() is stable across runs; floorMod keeps the result >= 0
    return Math.floorMod(userId.hashCode(), shards);
}
```

```python
import zlib

def shard_for(user_id: str, shards: int) -> int:
    # crc32: stable across runs (str hash() is not); fine for a demo
    return zlib.crc32(user_id.encode()) % shards
```

With hash 1337: `1337 % 4 = 1` (shard 1), but `1337 % 5 = 2`. Add one shard and most keys move; [consistent hashing](card:consistent-hashing) moves only about 1 in 5.

## Interview Qs

### Sharding vs replication?

Replication keeps copies of the same data on several nodes, for availability and reads. Sharding splits different data across nodes, to scale writes and storage. Large systems do both: each shard is replicated.

### How do you choose a shard key?

One that never changes, has many distinct values, spreads load evenly, and appears in most queries. Avoid ever-increasing keys like timestamps: all new writes would hit one shard.

### Range or hash sharding?

Range keeps nearby keys on one shard, so range queries are fast, but ever-increasing keys pile onto the last shard. Hash spreads writes evenly, but a range query usually has to ask every shard.

### A user updates their profile but sees the old one. Why?

The read hit an asynchronous replica that has not caught up (replication lag). Read your own writes from the primary for a short time, or use stronger read settings.
