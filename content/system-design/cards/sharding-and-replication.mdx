## What it is

Replication and sharding are two ways to spread a database across more than one machine, and they solve different problems. Replication means every node keeps a full copy of the same data. Sharding means each node keeps a different slice of the data: one node holds some rows, another node holds the rest. A large system usually does both, because each fixes a different limit.

## Why it exists

One database server has a fixed amount of CPU, memory, disk and network. As the payment service grows, that one server runs out of room: too many reads, too many writes, or too much data to store. And if it dies, everything stops because there is only one copy. Replication removes the single copy and spreads read load; sharding spreads writes and storage across many servers so no single one is the limit.

## How it works

<Compare id="sharding-vs-replication" />

1. With replication, every write goes to one node called the primary. The primary copies each change to its replicas, so they slowly become full copies of the same data.
2. Reads can go to any replica, which multiplies read capacity. If the primary fails, a replica is promoted to take its place, called failover.
3. With sharding, a router looks at the shard key of each row (such as `merchant_id`) and sends the row to the shard that owns that key's range or hash.
4. A query that knows the shard key goes straight to one shard; a query without it must ask every shard and combine the results.

So replication answers "how do I survive failure and serve more reads", and sharding answers "how do I handle more writes and more data than one node holds".

## Example

In the payment service, you pick which shard a merchant's payments live on from the shard key, using a stable hash so the same merchant always maps to the same shard.

```java
int shardFor(String merchantId, int shards) {
    // hashCode() is stable across runs; floorMod keeps the result >= 0
    return Math.floorMod(merchantId.hashCode(), shards);
}
```

```python
import zlib

def shard_for(merchant_id: str, shards: int) -> int:
    # crc32 is stable across runs (str hash() is not); fine for a demo
    return zlib.crc32(merchant_id.encode()) % shards
```

What to notice:

- The shard key is hashed, not used raw, so merchants spread evenly instead of clustering by name.
- `floorMod` (Java) and `%` (Python) map the hash into `0..shards-1`, one slot per shard.
- The weakness: with `% shards`, adding one shard changes the result for most keys, so almost all data must move. [Consistent hashing](card:consistent-hashing) fixes this by moving only a small fraction.
- A plain `str` `hash()` in Python is randomised per run, so it would send the same merchant to different shards on restart; `crc32` is stable.

## Rules and defaults

- **Writes go to the primary:** in leader-based replication, only the primary accepts writes; replicas are read-only copies.
- **Replicas are asynchronous by default:** PostgreSQL 18 and Amazon RDS replicas apply changes after the write commits, so they can briefly lag behind and return stale data. Synchronous replication removes the lag but makes writes wait.
- **Shard key cannot change easily:** moving a row to another shard means deleting and re-inserting it, so pick a key that rarely changes.
- **Replication is not a backup:** a bad `DELETE` is copied to every replica. Keep separate point-in-time backups ([see Backups and Disaster Recovery](card:disaster-recovery)).

## Common mistakes

- **"Sharding and replication are alternatives; I pick one."** They are not. Real systems replicate each shard: sharding spreads the data, replication protects each slice. In MongoDB every shard must be a replica set.
- **"I should shard from day one for scale."** Sharding adds cross-shard queries, resharding pain and a harder operational story. Add an index, a cache and read replicas first; shard only when one primary truly cannot keep up.

## Interview Qs

### What is the difference between sharding and replication?

Replication keeps copies of the same data on several nodes, for availability and read capacity. Sharding splits different data across nodes, to scale writes and total storage. Large systems do both: each shard is also replicated.

### How do you choose a shard key?

Pick a field that rarely changes, has many distinct values, spreads load evenly, and appears in most queries, such as `merchant_id`. Avoid ever-increasing keys like timestamps or auto-increment ids, because all new writes would pile onto one shard and make it hot.

### A user updates their profile but then sees the old value. Why?

The read hit an asynchronous replica that has not yet applied the latest write, called replication lag. Fix it by reading your own recent writes from the primary for a short window, or by using a replica with stronger read guarantees.
