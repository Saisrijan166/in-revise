## Why it exists

Some work is slow, like sending email or encoding video, or it arrives in bursts. Doing it inside the request makes users wait and can overload the service; a queue holds the work until a worker is free.

## How it works

<Mermaid
  alt="Message queue flow. A producer sends a message to the queue. A worker receives it, and the message is hidden from other workers. When the job is done, the worker deletes or acks it, and it is removed from the queue. If the worker crashes or runs past the timeout, the message becomes visible in the queue again. A message that fails too many times moves to a dead-letter queue."
  chart={`flowchart TD
  P[Producer] -- send --> Q[(Queue)]
  Q -- "receive: now hidden" --> W[Worker]
  W -- "done: delete or ack" --> X([Removed from queue])
  W -. "crash or timeout: visible again" .-> Q
  Q -- "failed too many times" --> DLQ[(Dead-letter queue)]`}
/>

- A received message stays in the queue until the worker acks it. Amazon SQS hides it for the visibility timeout; if it is not deleted by then, it shows again.
- **Back pressure:** when workers fall behind, cap the queue and reject new work (for example HTTP 503) so clients retry later.
- A task queue, such as Celery or a RabbitMQ work queue, is the same idea for background jobs.

## Example

The API enqueues a resize job and replies at once; many workers share the queue.

```java
int upload(long imageId) {
    queue.send(new ResizeJob(imageId));   // enqueue the job
    return 202;                           // Accepted: done later
}

void workOnce() {                         // each worker calls this in a loop
    Message msg = queue.receive();        // waits; now hidden from others
    try {
        resize(msg.body());
        queue.delete(msg);                // ack only after success
    } catch (Exception e) {
        log.warn("will retry", e);        // no delete: it comes back later
    }
}
```

```python
def upload(image_id):
    queue.send({"image_id": image_id})    # enqueue the job
    return 202                            # Accepted: done later

def work_once():                          # each worker calls this in a loop
    msg = queue.receive()                 # waits; now hidden from others
    try:
        resize(msg.body)
        queue.delete(msg)                 # ack only after success
    except Exception:
        log.warning("will retry")         # no delete: it comes back later
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Visibility timeout | 30 s (0 s to 12 h) | Amazon SQS |
| How long a message is kept | 4 days (1 minute to 14 days) | Amazon SQS |
| Largest message | 1 MiB | Amazon SQS |
| Receive wait | 0 s, short polling (long polling waits up to 20 s) | Amazon SQS |
| Deliveries before drop or dead-letter | 20 | RabbitMQ 4.0+ quorum queues |
| Time to ack a delivery | 30 minutes, then the channel is closed | RabbitMQ (quorum queues only from 4.3) |

## Interview Qs

### Why put a queue between two services?

The caller does not wait for slow work, bursts wait in the queue instead of overloading the worker, and nothing is lost while a worker is down. You can also scale workers on their own. The cost: one more system to run, and results arrive later.

### A worker crashes halfway through a job. What happens?

It never deleted or acked the message, so the broker delivers it again: SQS after the visibility timeout, RabbitMQ when the connection closes. Another worker runs the job, so the job must be idempotent.

### What is a dead-letter queue?

A side queue for messages that keep failing. SQS moves a message there after `maxReceiveCount` receives; RabbitMQ 4.0+ quorum queues dead-letter (or drop) it after 20 deliveries by default. Alert on it, fix the bug, then redrive the messages.

### The queue keeps growing. What do you do?

Producers are faster than workers. Add workers and scale them on queue depth, then set a limit: when the queue is full, reject new work with HTTP 503 so clients retry later with backoff. Watch the age of the oldest message.
