## What it is

A message queue is a line of jobs that sits between the code that creates work and the code that does it. The code that adds a job is the **producer**; the processes that take jobs off the queue and run them are the **workers** (also called consumers). The producer adds a job and moves on at once; it does not wait for the work to finish. This is how you do work **asynchronously**: the result is ready a moment later, not inside the request.

## Why it exists

Some work is slow, like sending a receipt email or encoding a video, or it arrives in sudden bursts. If you do it inside the request, the user waits for the whole thing, and a flood of requests can overload the service until it falls over. With a queue, the request just adds a job and returns; a fixed set of workers drains the queue at a steady pace, so slow work and bursts no longer hurt the user-facing service.

## How it works

1. The producer sends a job to the queue and returns immediately, without waiting for it to run.
2. A free worker receives the message. The broker hides it from other workers so two do not run the same job.
3. The worker does the job, then acknowledges it: it tells the broker "done", and the message is deleted.
4. If the worker crashes or takes too long, it never acknowledges, so the broker makes the message visible again and another worker picks it up. That is why a job can run more than once and must be idempotent.
5. A message that keeps failing is moved to a **dead-letter queue** after a set number of tries, so one bad message does not block the rest.

## Example

The checkout API puts a receipt-email job on the queue and returns at once; a pool of workers shares the queue.

```java
int checkout(long paymentId) {
    queue.send(new ReceiptJob(paymentId));   // add the job, do not wait
    return 202;                               // Accepted: the email is sent later
}

void workOnce() {                             // each worker loops over this
    Message msg = queue.receive();            // blocks; now hidden from others
    try {
        sendReceipt(msg.body());
        queue.delete(msg);                    // acknowledge only after success
    } catch (Exception e) {
        log.warn("will retry", e);            // no delete: it reappears later
    }
}
```

```python
def checkout(payment_id):
    queue.send({"payment_id": payment_id})    # add the job, do not wait
    return 202                                # Accepted: the email is sent later

def work_once():                              # each worker loops over this
    msg = queue.receive()                     # blocks; now hidden from others
    try:
        send_receipt(msg.body)
        queue.delete(msg)                     # acknowledge only after success
    except Exception:
        log.warning("will retry")             # no delete: it reappears later
```

What to notice:

- `checkout` returns `202 Accepted`, not `200 OK`: the work is accepted, not finished. The caller must not assume the email is sent yet.
- `queue.delete` runs only after `sendReceipt` succeeds. Move the delete before the send and a crash in between would lose the receipt instead of retrying it.
- Nothing in the code limits how fast producers add jobs. If they outrun the workers, the queue grows; you cap it and add workers separately.

## Rules and defaults

- **Delivery is at-least-once:** a message reappears after a crash, so the same job can run more than once. Make jobs idempotent (see [idempotency](card:idempotency)).
- **Visibility timeout:** in Amazon SQS a received message is hidden for 30 seconds by default (0 s to 12 h). Set it longer than your slowest job, or the job reappears and runs twice while still in progress.
- **Retention:** SQS keeps a message for 4 days by default (1 minute to 14 days); after that it is dropped.
- **Dead-letter queue:** configure it so a poison message is set aside after N tries instead of looping forever.
- **Back pressure:** a queue does not make workers faster. When workers fall behind, cap the queue and reject new work (HTTP 503) so clients retry later.

## Not to be confused with

A message queue gives each job to **one** worker, so workers share the load. [Publish-subscribe](card:pub-sub) gives **every** subscriber its own copy of each message. An [event stream](card:event-streaming) keeps messages in a log after they are read, so many readers can replay them. Rule: queue to share work, pub/sub to notify many services, stream to keep and replay an ordered log.

## Common mistakes

- **"If the API returned 202, the work is done."** No. `202 Accepted` means only that the job was queued. The worker may still fail, so the user needs a way to see the final result or error.
- **"Retry every failure forever."** A poison message would loop forever and waste workers. Cap retries and send it to a dead-letter queue instead.

## Interview Qs

### Why put a queue between two services?

The caller does not wait for slow work, a burst waits in the queue instead of overloading the worker, and nothing is lost while a worker is down. You can also scale workers on their own. The cost is one more system to run and results that arrive later.

### A worker crashes halfway through a job. What happens?

It never acknowledged the message, so the broker delivers it again: SQS after the visibility timeout, RabbitMQ when the connection drops. Another worker runs the same job, so the job must be idempotent or the user gets a duplicate effect, like two receipts.

### What is a dead-letter queue, and why use one?

A side queue for messages that keep failing. After a set number of tries, the broker moves the message there instead of retrying forever. This stops one poison message from blocking the queue, and lets you alert on it, fix the bug, then re-process the held messages.

### The queue keeps growing. What do you do?

Producers are faster than workers. Add workers and scale them on queue depth. Then set a limit: when the queue is full, reject new work with HTTP 503 so clients retry with backoff. Watch the age of the oldest message.
