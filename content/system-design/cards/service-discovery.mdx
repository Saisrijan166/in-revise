## What it is

Service discovery is how a caller finds a live network address for a service it wants to call, using the service's name rather than a fixed IP. In a [microservices](card:microservices) system, instances come and go constantly, so there is a **registry**: a live list that maps each service name to the addresses of its running, healthy instances. Instances add themselves on start, and the registry removes them when they stop or fail a health check. A caller then asks "where is `orders`?" and gets back addresses it can actually reach.

## Why it exists

Instances get a new IP address whenever they autoscale, crash and restart, or redeploy. If a caller hardcodes an instance's address, that address breaks the moment the instance goes away, and the caller cannot see new instances that appeared. You would be editing config every time the fleet changes. Service discovery removes this: instances keep the registry up to date automatically, and callers always look up the current, healthy set by name, so the system heals itself as instances move.

## How it works

1. An instance starts and registers its address with the registry (Consul, etcd, Eureka or the Kubernetes API).
2. The registry health-checks each instance and drops any that fail, so the list holds only reachable instances.
3. A caller looks up the service by name and receives the current healthy addresses.
4. The caller sends the request: in **client-side discovery** it picks an instance and load-balances itself; in **server-side discovery** it calls a router or load balancer that does the lookup and forwarding.

## Example

In Kubernetes you rarely run a registry by hand: a Service does discovery for you. This Service named `orders` groups the ready Pods behind one stable name.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: orders
  namespace: shop
spec:
  selector:
    app: orders        # groups Pods with this label; only ready ones get traffic
  ports:
    - port: 80
      targetPort: 8080
```

What to notice:

- Callers use the DNS name `http://orders.shop.svc.cluster.local`, or just `http://orders` from the same namespace, and never touch a Pod IP.
- `selector: app: orders` picks the Pods; a Pod that fails its readiness probe is dropped from the Service until it passes, so traffic only goes to healthy Pods.
- Scaling the Pods up or down changes nothing for the caller: the name stays the same and the Service tracks which Pods are ready.

## Rules and defaults

- **Default Service type is ClusterIP:** reachable only inside the cluster; the Service gets a stable virtual IP and DNS name.
- **Service DNS name:** `<service>.<namespace>.svc.<cluster-domain>`, where the cluster domain defaults to `cluster.local` (kubeadm `dnsDomain`).
- **Registries hold only live instances:** etcd deletes a key when its lease is not renewed; ZooKeeper deletes an ephemeral node when the session ends; Consul leaves unhealthy instances out of DNS answers.
- **The registry must be highly available:** run 3 or 5 servers that agree via Raft (etcd, Consul), because if the registry is down, new lookups fail.

## Not to be confused with

Service discovery is not the same as load balancing, though they work together. Service discovery answers "which instances exist and are healthy right now?" A load balancer answers "which one of those should get this request?" In client-side discovery the caller does both; in server-side discovery and Kubernetes a load balancer or kube-proxy does the balancing over the instances discovery found. Rule: discovery finds the list, load balancing picks from it.

## Interview Qs

### How do services find each other in a microservices system?

Through service discovery. Instances register with a registry such as Consul, etcd, Eureka or the Kubernetes API, and health checks remove the dead ones. A caller looks up a service by name and gets the current healthy addresses, then calls one directly (client-side) or through a load balancer (server-side).

### Client-side versus server-side discovery: what's the trade-off?

Client-side: the caller queries the registry and load-balances itself, so there are fewer network hops, but every language needs the discovery library (Netflix Eureka). Server-side: the caller hits a router or load balancer that does the lookup and forwards (AWS ELB, Kubernetes), so clients stay simple at the cost of one extra hop.

### How does Kubernetes do service discovery?

A Service selects Pods by label and gets a stable virtual IP and DNS name like `orders.shop.svc.cluster.local`. kube-proxy on each node forwards traffic to one of the ready Pods. Pods that fail their readiness probe are dropped, so callers use one name and never deal with changing Pod IPs.

### What happens if the registry goes down?

Callers can keep using addresses they already cached, but those entries go stale as instances move, and any new lookup fails. So the registry must be highly available: run 3 or 5 Consul or etcd servers that use Raft to stay in agreement, so losing one server does not lose discovery.
