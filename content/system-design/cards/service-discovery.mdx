## Why it exists

Instances get new IP addresses whenever they autoscale, crash or redeploy. A hardcoded address breaks the moment that instance goes away.

## How it works

<Mermaid
  alt="Service discovery flow. A new instance of the orders service registers its address with the service registry, and the registry health-checks it. A caller asks the registry where orders is, gets back the healthy addresses, and calls one of them."
  chart={`flowchart TD
  I[New orders instance] -->|"1. register address"| REG[(Service registry)]
  REG -.->|"health checks"| I
  C[Caller] -->|"2. where is orders?"| REG
  REG -->|"3. healthy addresses"| C
  C -->|"4. call one"| I`}
/>

- **Client-side discovery:** the caller queries the registry and picks an instance (Netflix Eureka). Fewer hops, but every language needs the discovery code.
- **Server-side discovery:** the caller hits a router or load balancer that queries the registry (AWS ELB, Kubernetes). Simpler clients, one more hop.
- Registries keep only live instances: etcd deletes keys when a lease is not renewed; ZooKeeper deletes ephemeral nodes when the session ends.

## Example

A Kubernetes Service named `orders` in the `shop` namespace:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: orders
  namespace: shop
spec:
  selector:
    app: orders        # Pods with this label; only ready ones get traffic
  ports:
    - port: 80
      targetPort: 8080
```

Callers use `http://orders.shop.svc.cluster.local`, or just `http://orders` from the same namespace. A Pod that fails its readiness probe is removed from the Service until it passes.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Service type | ClusterIP: reachable only inside the cluster | Kubernetes |
| `targetPort` | Same as `port` | Kubernetes |
| Service DNS name | `<service>.<namespace>.svc.<cluster domain>` | Kubernetes |
| Cluster domain | `cluster.local` | kubeadm `dnsDomain` |
| DNS lookup name | `<service>.service.consul` | Consul |
| Unhealthy instances | Left out of DNS answers | Consul |

## Interview Qs

### How do services find each other in a microservices system?

Through service discovery. Instances register with a registry such as Consul, etcd, Eureka or the Kubernetes API, and health checks remove dead ones. Callers look up a name and get healthy addresses, either directly or through a load balancer.

### Client-side vs server-side discovery?

Client-side: the caller queries the registry and load-balances itself, with fewer hops but a library per language (Eureka). Server-side: the caller hits a router that looks up and forwards (AWS ELB, Kubernetes), with simpler clients but one more hop.

### How does Kubernetes do service discovery?

A Service selects Pods by label and gets a stable virtual IP and DNS name, like `orders.shop.svc.cluster.local`. kube-proxy on each node forwards traffic to one of the ready Pods.

### What happens if the registry goes down?

Callers can keep using addresses they cached, but those go stale and new lookups fail. So the registry must be highly available: run 3 or 5 Consul or etcd servers, which use Raft to stay in agreement.
