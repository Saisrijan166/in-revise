## Why it exists

Every trip to the database costs time, and most apps fetch the same data again and again. A copy kept closer to the user saves that trip; the design question is where to keep it.

## How it works

<Mermaid
  alt="A request passes caches in order. The user's browser cache comes first. On a miss the request goes to a CDN edge cache, then to a reverse-proxy cache, then to the app server and its in-process cache, then to a shared cache such as Redis, and finally to the database, which keeps its own buffer cache. A hit at any stop returns the answer without going further."
  chart={`flowchart TD
  U([User]) --> B[Browser cache]
  B -->|miss| CDN[CDN edge cache]
  CDN -->|miss| RP[Reverse-proxy cache]
  RP -->|miss| APP["App server, in-process cache"]
  APP -->|miss| R[("Shared cache, e.g. Redis")]
  R -->|miss| DB[("Database, buffer cache")]`}
/>

- **Shared HTTP caches** ([CDN](card:cdn), [reverse proxy](card:reverse-proxy)) keep one response for many users. Personal pages must say `private`, so only the browser keeps them.
- **In-process vs distributed:** a local copy is fastest but differs per server; Redis or Memcached gives every server the same copy for one network hop. Many systems check local first, then shared.
- Watch the **hit ratio**: hits ÷ (hits + misses). If most requests miss, checking the cache costs more than it saves.

## Example

Two `Cache-Control` headers, as MDN recommends:

```text
# app.3f9a1c.js: the file name changes with every release
Cache-Control: public, max-age=31536000, immutable

# The HTML page: personal, so browser only; check before reuse
Cache-Control: private, no-cache
```

- The script is cached for a year (31,536,000 seconds); a new release gets a new name, so users still get it.
- The HTML is checked every time; if it has not changed, the server answers `304 Not Modified` with no body.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| No `Cache-Control` or `Expires` | Caches may guess a lifetime, typically 10% of the time since `Last-Modified` | HTTP caching (RFC 9111) |
| Reverse-proxy caching | Off; entries unused for 10 minutes are removed (`inactive`) | nginx `proxy_cache`, `proxy_cache_path` |
| Database buffer cache | 128 MB (`shared_buffers`) | PostgreSQL 18 |

## Interview Qs

### Where can you add a cache in a web system?

At every hop: the browser, a CDN, a reverse proxy, the app's own memory, a shared cache such as Redis, and the database's buffer cache. Caches closer to the user save more trips, but you control their freshness less.

### In-process cache or distributed cache?

In-process is fastest, but each server keeps its own copy: values drift between servers and new servers start empty. A distributed cache like Redis gives one shared copy for one network hop. Default to shared; add a small local layer for very hot keys.

### How do you know a cache is working?

Measure the hit ratio: hits divided by hits plus misses. Redis reports `keyspace_hits` and `keyspace_misses` in `INFO stats`. If the ratio is low, check whether keys are evicted too early or TTLs are too short.

### How do you cache static files but still ship updates?

Put a version or hash in the file name and cache it for a year with `immutable`. A release changes the name, so browsers fetch the new file. Keep the HTML on `no-cache` so it always points to the latest names.
