## What it is

A cache is a copy of data kept somewhere faster to reach than its original source, so the same data does not have to be fetched or computed again. A **hit** means the data was found in the cache; a **miss** means it was not there and has to be fetched from the source. In a web system there is not one cache but many, sitting at different stops along a request's path, from the user's browser down to the database.

## Why it exists

Every trip to the database costs time, and most apps read the same data again and again. Without caches, a popular product page would hit the database on every view, and the database would become the bottleneck as traffic grows. A copy kept closer to the user answers the common reads in a fraction of the time and takes that load off the database. The design question is not whether to cache, but where.

## How it works

1. The request first checks the user's own browser cache. A hit here needs no network at all.
2. On a miss it reaches a shared HTTP cache, a [CDN](card:cdn) edge near the user and then a [reverse proxy](card:reverse-proxy) in front of the app. These keep one stored copy that serves many users, so a page marked `private` is never kept here.
3. Still a miss, so the request reaches an app server, which may keep a small in-process cache in its own memory: fastest to read, but each server has a separate copy that can drift.
4. The app then checks a distributed cache such as Redis, one shared copy every server reads over the network, and only on a miss there does it read the database, which keeps its own buffer cache of recent pages.

So caches closer to the user save more trips, but you control their freshness less.

## Example

Two `Cache-Control` headers, as MDN recommends, for a static script and for an HTML page.

```text
# app.3f9a1c.js: the file name changes with every release
Cache-Control: public, max-age=31536000, immutable

# The HTML page: personal, so browser only; recheck before reuse
Cache-Control: private, no-cache
```

What to notice:

- `public, max-age=31536000` lets shared caches keep the script for a year (31,536,000 seconds); `immutable` tells the browser never to recheck it.
- A new release gives the file a new hashed name, so users fetch the new file instead of a stale cached one. This is why a version in the name is safe to cache for so long.
- `private` on the HTML keeps it out of shared CDN and proxy caches, so one user's page is never served to another.
- `no-cache` stores the page but rechecks it every time; if it has not changed, the server answers `304 Not Modified` with no body, saving the download.

## Rules and defaults

- **No freshness header:** with no `Cache-Control` or `Expires`, a cache may guess a lifetime, commonly 10% of the time since `Last-Modified` (RFC 9111 heuristic freshness).
- **Reverse-proxy cache:** off by default in nginx; once enabled, entries unused for 10 minutes are removed (`proxy_cache_path inactive`).
- **Database buffer cache:** PostgreSQL 18 keeps recent pages in `shared_buffers`, 128 MB by default, so repeated reads of the same rows avoid the disk.
- **Hit ratio:** measure hits ÷ (hits + misses). Redis reports `keyspace_hits` and `keyspace_misses` in `INFO stats`. A low ratio means the cache is paying its cost without saving trips.

## Not to be confused with

An in-process cache and a distributed cache both store hot data, but differ in reach. An in-process cache lives inside one app server's memory: no network hop, so the fastest, but every server has its own copy that can drift. A distributed cache like Redis is one shared store that all servers read over the network: one network hop, but one copy everyone agrees on. Rule: shared cache for correctness across servers, in-process only for very hot keys that tolerate drift.

## Interview Qs

### Where can you add a cache in a web system?

At every hop: the browser, a CDN, a reverse proxy, the app's own memory, a shared cache such as Redis, and the database's buffer cache. Caches closer to the user save more trips, but you control their freshness less, so personal data must stay in private caches.

### In-process cache or distributed cache?

In-process is fastest because there is no network hop, but each server keeps its own copy, so values drift between servers and a new server starts empty. A distributed cache like Redis gives one shared copy for one network hop. Default to a shared cache; add a small in-process layer only for very hot keys.

### How do you know a cache is actually helping?

Measure the hit ratio, hits divided by hits plus misses. Redis reports `keyspace_hits` and `keyspace_misses` in `INFO stats`. If the ratio is low, keys may be evicted too early or TTLs may be too short, and the cache is adding a lookup without saving a database trip.

### How do you cache static files but still ship updates?

Put a version or hash in the file name and cache it for a year with `immutable`. A new release changes the name, so browsers fetch the new file. Keep the HTML on `no-cache` so it always points to the latest file names.
