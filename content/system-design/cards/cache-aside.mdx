## Why it exists

Reading from a database is slow compared with memory, and most apps read the same data again and again. A cache such as Redis or Memcached keeps hot data in memory; with cache-aside, the app decides what goes in.

## How it works

<Mermaid
  alt="Cache-aside flow. Read path: the app checks the cache. On a hit it returns the value. On a miss it reads the database, stores the value in the cache with a TTL, then returns it. Write path: the app updates the database first, then deletes the key from the cache."
  chart={`flowchart TD
  R([Read key]) --> C{In cache?}
  C -- hit --> RET([Return value])
  C -- miss --> DB[(Read database)]
  DB --> SET[Store in cache with TTL]
  SET --> RET
  W([Write key]) --> U[(1. Update database)]
  U --> DEL[2. Delete key from cache]`}
/>

- AWS calls this **lazy loading**: data is cached only when someone reads it.

## Example

```java
User getUser(long id) {
    String key = "user:" + id;
    User user = cache.get(key);
    if (user == null) {                          // miss
        user = db.findUser(id);
        cache.set(key, user, Duration.ofMinutes(5));
    }
    return user;
}

void updateUser(long id, User data) {
    db.updateUser(id, data);                     // 1. database first
    cache.delete("user:" + id);                  // 2. then invalidate
}
```

```python
def get_user(user_id):
    key = f"user:{user_id}"
    user = cache.get(key)
    if user is None:                         # miss
        user = db.find_user(user_id)
        cache.set(key, user, ttl=300)        # 5 minutes
    return user

def update_user(user_id, data):
    db.update_user(user_id, data)            # 1. database first
    cache.delete(f"user:{user_id}")          # 2. then invalidate
```

## Interview Qs

### Walk me through cache-aside.

Read: check the cache; on a miss, load from the database, store it with a TTL, and return it. Write: update the database, then delete the key so the next read reloads it.

### Why delete the key after the database write, not before?

If you delete first, a reader can miss, read the old row, and put it back before your write lands. The cache then stays stale until the TTL runs out.

### Cache-aside vs write-through?

Cache-aside fills the cache on reads: a small cache, but slow misses and possibly stale data. Write-through updates the cache on every write: fresher data, but slower writes and a cache full of data nobody reads.

### A hot key expires and the database is flooded. What do you do?

That is a thundering herd. Let one request rebuild the value while the others wait (request coalescing, or leases as Facebook does), or refresh very hot keys before they expire.
