## What it is

Cache-aside, also called lazy loading, is a read strategy where the application itself manages the cache. The cache sits "aside" the database: it is not in the write path, and it does not know how to load data on its own. The app checks the cache, and when the data is not there, it reads the database, puts a copy in the cache, and returns it. This is the most common caching pattern, and the one most interviews expect you to describe.

## Why it exists

Reading from a database is slow compared with reading from memory, and most apps read the same few rows again and again. You want those hot rows in a fast cache like Redis, but you do not want to cache every row, most of which are never read. Cache-aside solves this by filling the cache only when something is actually read, so the cache stays small and holds exactly the data people use. It also keeps working when the cache is down, because every path still ends at the database.

## How it works

1. On a read, the app asks the cache for the key. If it is a hit, the value is returned straight away.
2. On a miss, the app reads the row from the database.
3. The app stores that value in the cache with a TTL, so future reads of the same key are hits, then returns it.
4. On a write, the app updates the database first, then deletes the key from the cache. The next read of that key misses and reloads the new value.

So the app, not the cache, does all the loading, and a write clears the stale copy rather than trying to update it.

## Example

The payment service caches a user record. On a read it loads lazily; on a write it invalidates the key.

```java
User getUser(long id) {
    String key = "user:" + id;
    User user = cache.get(key);
    if (user == null) {                          // miss
        user = db.findUser(id);
        cache.set(key, user, Duration.ofMinutes(5));
    }
    return user;
}

void updateUser(long id, User data) {
    db.updateUser(id, data);                     // 1. database first
    cache.delete("user:" + id);                  // 2. then invalidate
}
```

```python
def get_user(user_id):
    key = f"user:{user_id}"
    user = cache.get(key)
    if user is None:                         # miss
        user = db.find_user(user_id)
        cache.set(key, user, ttl=300)        # 5 minutes
    return user

def update_user(user_id, data):
    db.update_user(user_id, data)            # 1. database first
    cache.delete(f"user:{user_id}")          # 2. then invalidate
```

What to notice:

- On a miss the value is stored with a 5-minute TTL, so a stale copy can live at most 5 minutes even if an invalidation is missed.
- The write updates the database first, then deletes the key. Swap the two lines and a concurrent reader can refill the cache with the old row after your write, leaving it stale until the TTL.
- The write deletes the key rather than setting the new value; deleting is simpler and avoids two racing writes leaving the wrong value behind.

## Rules and defaults

- **Write order:** database first, then delete the key. This is the safe order against concurrent reads.
- **Always set a TTL:** it is the safety net. If an invalidation is ever lost, the stale key still expires on its own.
- **Not fully race-free:** a read miss that overlaps a write can still repopulate an old value; the TTL bounds how long that lasts. Stronger freshness needs [write-through](card:write-through) or change-event invalidation.
- **Empty cache node:** a fresh or restarted cache simply misses and refills from the database, so cache-aside survives restarts without special handling.

## Not to be confused with

Cache-aside and read-through both load the database on a miss, but the loader differs. In cache-aside your application code does the loading and talks to both the cache and the database. In read-through the cache does the loading through a built-in loader, and the app talks only to the cache. Rule: cache-aside keeps the load logic in your code; read-through hides it in the cache.

## Common mistakes

- **"A TTL keeps the cache fresh."** A TTL only caps how long a stale copy survives. For near-fresh reads you still invalidate on each write.
- **"Update the cache on a write instead of deleting it."** Two concurrent updates can write their values to the cache out of order, leaving the older one. Deleting is idempotent and avoids this.

## Interview Qs

### Walk me through cache-aside.

On a read, check the cache; on a miss, load the row from the database, store it with a TTL, and return it. On a write, update the database first, then delete the key so the next read reloads the new value. The application does all the loading; the cache sits aside the database.

### Why delete the key after the database write, not before?

If you delete first, a concurrent reader can miss, read the old row, and write it back into the cache before your database write lands. The cache then holds the stale value until the TTL expires. Updating the database first and deleting after closes most of that window.

### A hot key expires and the database is suddenly flooded. What is happening?

That is a cache stampede, or thundering herd: when the hot key expires, many requests miss at the same moment and all hit the database together. You let one request rebuild the value while the others wait or get the old copy, or you refresh very hot keys a little before they expire.
