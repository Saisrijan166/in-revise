## What it is

An API style is the agreed way a client and a service exchange data and actions over the network. The three common styles are REST, gRPC and GraphQL. REST acts on **resources**, things like a user or an order, each at its own URL. gRPC calls a named **method** on a remote service, as if it were a local function. GraphQL gives one endpoint and lets the client write a **query** naming the exact fields it wants. All three run over HTTP, so the choice is about shape and speed.

## Why it exists

Every client and service must agree on how to ask for data, or nothing can talk to anything. One style does not fit every case. A public API has unknown clients and benefits from REST's standard methods and cacheable responses. Two internal services you own want speed and a strict contract, which gRPC gives. Many screens needing different fields from the same data over-fetch with REST, which GraphQL solves. Each style trades something, so you pick per situation.

## How it works

<Compare id="rest-vs-grpc-vs-graphql" />

1. With **REST**, the client picks a resource URL and an HTTP method: `GET /users/42` to read, `POST /users` to create. The server returns the resource, usually as JSON, and marks whether the response may be cached.
2. With **gRPC**, both sides share a `.proto` file that lists the service's methods and message types. A build step turns it into client and server code, so a remote call looks like calling a normal method.
3. With **GraphQL**, the client sends a query naming the fields it wants to one endpoint, usually `/graphql`. The server checks the query against a typed schema, then returns only those fields.

So the key is: REST exposes data, gRPC exposes methods, and GraphQL lets the client shape the reply.

## Example

The same screen needs a user's name and their order totals, shown three ways.

REST uses two round trips, and each returns the whole object:

```text
GET /users/42
GET /users/42/orders
```

GraphQL uses one request to one URL, and only the asked-for fields come back:

```text
POST /graphql
{ "query": "{ user(id: 42) { name orders { total } } }" }
```

gRPC uses typed methods declared in a shared contract (`stream` means many replies):

```proto
service UserService {
  rpc GetUser (UserId) returns (User);
  rpc WatchOrders (UserId) returns (stream Order);
}
```

What to notice:

- REST makes two calls because each resource has its own URL; the client cannot ask for a mix in one call.
- The GraphQL query returns `name` and each order's `total` and nothing else, so a mobile screen is not forced to download fields it will not show.
- In the `.proto`, `GetUser` returns one `User` and `WatchOrders` returns a `stream Order`; the generated code gives the caller a typed method, not a URL to format by hand.

## Rules and defaults

- **REST caching:** a `GET` response can be cached by browsers and CDNs (RFC 9110); `POST` responses are not cached by default, which is why read-heavy public APIs lean on REST.
- **gRPC transport:** gRPC runs over HTTP/2 and sends binary Protocol Buffers by default, which is smaller and faster to parse than text JSON.
- **gRPC in the browser:** a browser cannot speak raw gRPC; you must use gRPC-Web through a proxy such as Envoy, and today it supports unary and server-streaming calls only.
- **GraphQL over HTTP:** queries usually go by `POST`, so most HTTP caches skip them; you cache with `GET` queries or persisted queries instead.

## Not to be confused with

REST and RPC sound similar but differ in what you name. REST names a resource (a noun, `GET /users/42`) and uses standard HTTP methods on it. [RPC](term:rpc), the family gRPC belongs to, names an operation (a verb, `getUser(42)`) and calls it like a function. Rule: REST acts on resources with HTTP verbs; RPC calls named methods.

## Common mistakes

- **"GraphQL replaces REST everywhere."** GraphQL shines when clients need varied field sets, but it loses easy HTTP caching and adds query-depth and N+1 risks. Many systems keep REST for simple public endpoints and use GraphQL only where it pays off.
- **"gRPC is just REST with Protobuf."** gRPC is method calls over HTTP/2 with streaming and a strict generated contract, not resources at URLs. The models are different, not a format swap.

## Interview Qs

### REST, gRPC or GraphQL: how do you choose?

REST for public APIs and simple CRUD: every client speaks HTTP and GETs can be cached. gRPC for internal calls that need speed, a strict contract or streaming, where you control both ends. GraphQL when web and mobile clients need different fields from the same data and REST would over-fetch or need many endpoints.

### Why can't a browser call gRPC directly?

A browser gives JavaScript no low-level control over HTTP/2 frames, and raw gRPC needs that control. So you put a proxy such as Envoy in front and use gRPC-Web from the browser. gRPC-Web supports unary and server-streaming calls, not client or bidirectional streaming.

### What is the N+1 problem in GraphQL, and how do you fix it?

Asking for 10 users and their orders can run 1 query for the users, then 1 query per user for orders: 11 calls. The fix is batching: a DataLoader collects all the order keys from one request and loads them in a single query, turning N+1 into 2.
