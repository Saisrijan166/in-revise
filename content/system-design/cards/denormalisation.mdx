## What it is

Normalisation is organising tables so each fact is stored in exactly one place; when you need facts together, you join the tables. The normal forms (1NF, 2NF, 3NF) are rules that remove duplicate data step by step, and most designs stop at 3NF. Denormalisation is the opposite move, done on purpose: you copy a fact to where it is read, or keep a precomputed value, so a read can avoid a join. You met the SQL model in [SQL vs NoSQL](card:sql-vs-nosql).

## Why it exists

If the same fact sits in many rows, one update can miss some of them and the rows start to disagree. This is called an update anomaly: a warehouse ends up with two different addresses because one row was changed and the rest were not. Normalising removes the duplicate so there is nothing to keep in sync. But fully normalised data can need many joins to read, and on a hot, read-heavy path those joins can be slow. Denormalisation adds a few copies back, by choice, to make that one path fast.

## How it works

The comparison shows the trade-off; read it, then the two rules below.

<Compare id="normalisation-vs-denormalisation" />

1. Design normalised first: give each fact one home, so writes touch one row and nothing can drift.
2. Measure your real read paths. Most joins on indexed keys are fast and need no change.
3. If one hot read is genuinely slow because of joins, copy a few fields that rarely change onto the table that is read, or keep a precomputed count or a materialized view.
4. From then on, every write to the original fact must also update the copy.

So the key is that normalisation protects writes, denormalisation speeds one read, and you pay for the copy on every write.

## Example

This table's key is (part, warehouse), but the address depends on the warehouse alone, so it repeats for every part. That breaks 2NF:

| part | warehouse | qty | warehouse_address |
| --- | --- | --- | --- |
| P1 | W1 | 10 | 5 MG Road |
| P2 | W1 | 4 | 5 MG Road |

Change the address in one row only, and W1 now has two addresses: an update anomaly. Normalise by moving the address into a `warehouses` table. Denormalise the other way only when a read is hot:

```sql
-- the order list shows the customer's name on every row: copy it to skip a join
ALTER TABLE orders ADD COLUMN customer_name TEXT;
-- the price: renaming a customer must now also update all their orders
```

What to notice:

- In the first table the address is duplicated by accident, which is the bug; normalising removes it.
- The `ALTER TABLE` duplicates `customer_name` on purpose, to serve a hot read without a join.
- The comment is the whole cost: the name now lives in two places, so a rename must update every order row or they disagree. Copy only fields, like a name, that change rarely.

## Rules and defaults

- **Normal forms:** 1NF = one value per cell; 2NF = every non-key column depends on the whole key; 3NF = non-key columns depend only on the key. Most schemas stop at 3NF.
- **When to denormalise:** only a read path measured to be too slow, copying fields that change rarely.
- **Document stores:** embed data that is read together and stays small; reference data that grows without limit or changes often.
- **MongoDB document limit:** a single document can be at most 16 MiB, so an ever-growing embedded array eventually will not fit.
- **Precomputed values:** a PostgreSQL materialized view is a stored, denormalised query result you refresh on a schedule.

## Not to be confused with

- **Normalisation vs denormalisation:** normalisation removes copies to protect writes; denormalisation adds copies back to speed one read.
- **An accidental duplicate vs a deliberate copy:** the repeated address above is a design mistake; a copied `customer_name` is a measured choice. Rule: remove duplicates you did not plan, add only the ones you did.

## Interview Qs

### What is normalisation? Explain 1NF, 2NF and 3NF.

Organising tables so each fact is stored once. 1NF: one value per cell, no repeating groups. 2NF: every non-key column depends on the whole primary key, not part of it. 3NF: non-key columns depend only on the key, not on each other. The goal is to stop the same fact from drifting apart across rows.

### When would you denormalise, and what does it cost?

When a read-heavy path needs many joins and you have measured it to be too slow. Copy a few fields that rarely change, or keep a precomputed value. The cost is that every write must now update every copy, so avoid it for data that changes often.

### Embed or reference in a document database?

Embed when data is read together, is one-to-few and stays bounded, so one read returns it. Reference when it grows without limit, is shared by many documents or changes often. In MongoDB a document can be at most 16 MiB, so unbounded arrays must be referenced.
