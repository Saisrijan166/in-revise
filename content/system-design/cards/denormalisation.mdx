## Why it exists

When the same fact sits in many rows, an update can miss some of them and the data stops agreeing. Normalising removes the copies; denormalising adds a few back when joins make hot reads too slow.

## How it works

<Compare id="normalisation-vs-denormalisation" />

- **Normal forms** are rules that remove duplicates step by step. Most designs stop at [3NF](card:third-normal-form).
- **Document stores:** embed data that is read together and stays small; reference data that grows without limit or changes often.

## Example

The key is (part, warehouse), but the address depends on the warehouse alone, so it repeats for every part (this breaks 2NF):

| part | warehouse | qty | warehouse_address |
| --- | --- | --- | --- |
| P1 | W1 | 10 | 5 MG Road |
| P2 | W1 | 4 | 5 MG Road |

Change the address in one row only, and W1 now has two addresses: an update anomaly. Normalise by moving the address into a `warehouses` table.

Denormalise the other way when a read is hot:

```sql
-- the order list shows the customer's name: copy it to skip a join
ALTER TABLE orders ADD COLUMN customer_name TEXT;
-- now renaming a customer must also update all their orders
```

## Interview Qs

### What is normalisation? Explain 1NF, 2NF and 3NF.

Organising tables so each fact is stored once. 1NF: one value per cell, no repeating groups. 2NF: every non-key column depends on the whole primary key. 3NF: non-key columns depend only on the key, not on other non-key columns.

### When would you denormalise?

When a read-heavy path needs many joins and you have measured it to be too slow. Copy a few fields that rarely change, or keep a precomputed value. Avoid it for data that changes often: every write must update every copy.

### Embed or reference in a document database?

Embed when data is read together, is one-to-few and stays bounded. Reference when it grows without limit, is shared by many documents or changes often. In MongoDB a document can be at most 16 MiB.
