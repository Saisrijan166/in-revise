## Why it exists

One buggy script or attacker can send thousands of requests and slow the service for everyone. Limits keep usage fair, slow down brute-force logins and protect the servers behind the API.

## How it works

<Mermaid
  alt="Token bucket rate limiter. A request arrives and the limiter finds its key: API key, user or IP. If that key's bucket has a token left, it takes one and forwards the request to the service. If the bucket is empty, it replies 429 Too Many Requests with a Retry-After header. Separately, tokens refill at a steady rate r, up to the bucket size N."
  chart={`flowchart TD
  R([Request]) --> K["Find the key: API key, user or IP"]
  K --> B{"Token left in this key's bucket?"}
  B -- yes --> T[Take one token]
  T --> S([Forward to the service])
  B -- no --> E(["Reply 429 + Retry-After"])
  F["Refill r tokens per second, up to N"] -.-> B`}
/>

- **Bucket size N** is the biggest burst; **refill rate r** is the average limit. AWS API Gateway and Stripe both use a token bucket.
- Other algorithms trade accuracy for memory: see [leaky bucket and the window counters](compare:rate-limit-algorithms).
- **Many servers:** keep counters in one store such as Redis and change them in one atomic step (a Lua script). With a separate read and write, two servers can both spend the last token.

## Example

A bucket of 10 tokens refilled at 5 per second: a client can send 10 requests at once, then about 5 per second.

```java
class TokenBucket {
    private final double capacity, perSecond;
    private double tokens;
    private long last = System.nanoTime();
    TokenBucket(double capacity, double perSecond) {
        this.capacity = capacity; this.perSecond = perSecond; this.tokens = capacity;
    }
    synchronized boolean allow() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) / 1e9 * perSecond);  // refill
        last = now;
        if (tokens < 1) return false;            // empty: reply 429
        tokens -= 1; return true;                // spend one token
    }
}
```

```python
import time

class TokenBucket:
    def __init__(self, capacity, per_second):
        self.capacity, self.per_second = capacity, per_second
        self.tokens, self.last = capacity, time.monotonic()

    def allow(self):
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.per_second)
        self.last = now
        if self.tokens < 1:
            return False                         # empty: reply 429
        self.tokens -= 1                         # spend one token
        return True
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Algorithm | Leaky bucket | nginx `limit_req` |
| Burst allowed | 0: at `rate=10r/s`, one request per 100 ms | nginx `limit_req` |
| Status when rejected | 503; set `limit_req_status 429` | nginx (directive since 1.3.15) |
| Account limit, per Region | 10,000 requests/s, burst 5,000 (token bucket) | AWS API Gateway (some Regions: 2,500 and 1,250) |
| Status when blocked | 429; counters kept per data centre | Cloudflare rate limiting rules |

## Interview Qs

### How would you design a rate limiter for an API?

Put it at the API gateway and key it by API key or user. Keep a token bucket per key in Redis, updated atomically with a Lua script. Reject extra calls with 429 and Retry-After. If Redis is down, fail open so the API keeps working.

### Token bucket vs leaky bucket?

A token bucket lets a client burst up to the bucket size, then holds it to the refill rate. A leaky bucket queues requests and lets them out at a fixed rate, so bursts wait or are dropped. AWS API Gateway uses a token bucket; nginx uses a leaky bucket.

### Fixed window vs sliding window?

A fixed window resets a counter on the clock: one number per key, but bursts on both sides of a reset can pass twice the limit. A sliding window counts the last N seconds: the log is exact but stores every timestamp; the counter estimates it from two numbers.

### What should a limited client receive?

HTTP 429 Too Many Requests, a short message, and Retry-After with the seconds to wait. Many APIs, such as GitHub's, also send headers with the limit, the requests left and the reset time, so clients can slow down before they hit it.
