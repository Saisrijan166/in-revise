## What it is

Rate limiting counts how many requests a client makes over a time window and turns away the ones above an allowed number. The "client" is picked out by a key, usually an API key, user ID or IP address, so each client has its own count. When a client goes over its limit, the service replies with 429 Too Many Requests instead of processing the request. Limits usually live at the [API gateway](card:api-gateway), so every service behind it is protected.

## Why it exists

Without limits, one buggy script, a retry storm, or an attacker can send thousands of requests and use up the servers' capacity, so ordinary users get slow or failed responses. On your payment service, an attacker could also hammer the login endpoint to guess passwords, or run up your cloud bill. A rate limit caps how fast any one client can call, which keeps capacity fair, slows brute-force attempts, and protects the services behind the API.

## How it works

This shows the token-bucket method, the most common one.

1. A request arrives and the limiter works out its key, such as the API key.
2. It looks up that key's bucket, which holds up to N tokens and refills at r tokens per second.
3. If the bucket has at least one token, it takes one and forwards the request.
4. If the bucket is empty, it rejects the request with 429 and a [Retry-After](term:retry-after) header.
5. Across many servers, the bucket lives in a shared store such as Redis, and step 3 is done as one atomic update so two servers cannot both spend the last token.

So the key is that the bucket size sets the biggest burst and the refill rate sets the long-run average.

## Example

A bucket of 10 tokens that refills at 5 per second starts full. We fire 13 requests instantly and count how many pass before the refill can help.

```java
double capacity = 10, perSecond = 5, tokens = 10;
long last = System.nanoTime();
int allowed = 0, rejected = 0;
for (int i = 0; i < 13; i++) {
    long now = System.nanoTime();
    tokens = Math.min(capacity, tokens + (now - last) / 1e9 * perSecond);  // refill
    last = now;
    if (tokens >= 1) { tokens -= 1; allowed++; }   // spend a token
    else rejected++;                               // empty: would reply 429
}
System.out.println("burst of 13: allowed=" + allowed + " rejected=" + rejected);
```

```python
import time
capacity, per_second, tokens = 10, 5, 10
last = time.monotonic()
allowed = rejected = 0
for _ in range(13):
    now = time.monotonic()
    tokens = min(capacity, tokens + (now - last) * per_second)  # refill
    last = now
    if tokens >= 1:
        tokens -= 1; allowed += 1                  # spend a token
    else:
        rejected += 1                              # empty: would reply 429
print(f"burst of 13: allowed={allowed} rejected={rejected}")
```

```text output
burst of 13: allowed=10 rejected=3
```

What to notice:

- 10 pass and 3 are rejected: the burst arrives far faster than 5 tokens per second refill, so only the starting 10 tokens are available.
- Wait about 0.6 s and 3 tokens refill, so 3 more requests would pass; the bucket size caps the burst, the refill rate caps the average.
- `tokens -= 1` and the empty check must happen as one step. On a shared Redis counter across servers, split them and two servers can both see the last token and both spend it.

## Rules and defaults

- **Status code:** the standard reply when limited is `429 Too Many Requests` (RFC 6585), ideally with a `Retry-After` header.
- **nginx limit_req:** rejects with `503` by default; set `limit_req_status 429` to return 429 instead.
- **AWS API Gateway:** a token bucket defaulting to 10,000 requests/s with a burst of 5,000, per account per Region (some Regions 2,500 and 1,250).
- **Cloudflare:** rejects with 429; its counters are kept per data centre, so a global limit is approximate.
- **Shared counters:** across many servers the count must live in one store and be updated atomically (for example a Redis Lua script), or concurrent requests undercount.

## Not to be confused with

Rate limiting and load shedding both reject requests, but for different reasons: a rate limit rejects a client who has exceeded its own quota, while load shedding (which you will see later) drops low-priority work only when the whole system is overloaded, regardless of who sent it. The different algorithms (token bucket, leaky bucket, fixed and sliding windows) are compared below. Rule: rate limiting is per-client and always on; load shedding is system-wide and kicks in only under stress.

## Interview Qs

### How would you design a rate limiter for an API?

Put it at the API gateway and key it by API key or user. Keep a token bucket per key in Redis, updated atomically with a Lua script so servers do not race. Reject extra calls with 429 and Retry-After. If Redis is down, fail open so the API keeps serving while you lose protection briefly.

### Token bucket versus leaky bucket?

A token bucket lets a client burst up to the bucket size, then holds it to the refill rate, so short spikes pass. A leaky bucket queues requests and releases them at a fixed rate, so bursts wait or are dropped and the output is smooth. AWS API Gateway uses a token bucket; nginx `limit_req` uses a leaky bucket.

### Fixed window versus sliding window?

A fixed window keeps one counter per key and resets it on the clock; it is cheap but bursts on both sides of a reset can pass up to twice the limit. A sliding window counts the last rolling N seconds: a log of timestamps is exact but heavy, while a counter estimates it from the current and previous windows with little memory.

### What should a rate-limited client receive back?

HTTP 429 Too Many Requests, a short message, and a `Retry-After` header with the seconds to wait. Many APIs, such as GitHub's, also return headers with the limit, the number of requests left and the reset time, so a well-behaved client can slow down before it is blocked.
