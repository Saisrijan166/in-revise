## Why it exists

With `hash(key) % N`, changing N sends most keys to a different server, so adding one cache or database node moves most of the data. Consistent hashing moves only the keys the new node takes over.

## How it works

<Mermaid
  alt="A hash ring from 0 to 99 with three servers: A at 10, B at 40 and C at 75, linked clockwise, and C links back to A past 99. A key with hash 52 goes to C, the next server clockwise. A key with hash 90 wraps around to A."
  chart={`flowchart LR
  A(("A at 10")) -- clockwise --> B(("B at 40"))
  B -- clockwise --> C(("C at 75"))
  C -- "wraps past 99" --> A
  K1["key hash 52"] -.-> C
  K2["key hash 90"] -.-> A`}
/>

- **Owner:** from the key's hash, walk clockwise; the first server point owns it. So C owns 41 to 75.
- **Change:** add D at 60, and only keys 41 to 60 move, from C to D. Remove C, and its keys go to A, the next point.
- **Virtual nodes:** each server gets many points, like `A#0` to `A#99`. Arcs even out, and a failed server's keys spread over all the others.

## Example

A tiny ring with virtual nodes. CRC32 is a stable hash, fine for a demo; Cassandra uses Murmur3.

```java
TreeMap<Long, String> ring = new TreeMap<>();   // ring position -> server

long hash(String s) {
    CRC32 crc = new CRC32();
    crc.update(s.getBytes(StandardCharsets.UTF_8));
    return crc.getValue();                       // 0 .. 2^32 - 1
}
void addServer(String server, int vnodes) {      // vnodes points per server
    for (int i = 0; i < vnodes; i++) ring.put(hash(server + "#" + i), server);
}
String serverFor(String key) {
    var e = ring.ceilingEntry(hash(key));        // first point clockwise
    return (e != null ? e : ring.firstEntry()).getValue();  // wrap around
}
```

```python
import bisect, zlib

ring = []  # sorted list of (position, server)

def add_server(server: str, vnodes: int) -> None:
    for i in range(vnodes):                  # vnodes points per server
        bisect.insort(ring, (zlib.crc32(f"{server}#{i}".encode()), server))

def server_for(key: str) -> str:
    pos = zlib.crc32(key.encode())           # 0 .. 2**32 - 1
    i = bisect.bisect_left(ring, (pos, ""))  # first point clockwise
    return ring[i % len(ring)][1]            # wrap around
```

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Virtual nodes per node (`num_tokens`) | 16 (was 256 in 3.11) | Apache Cassandra 4.0 and later |
| Hash used to place rows (`partitioner`) | Murmur3Partitioner | Apache Cassandra 5.0 |
| `hash $key` without `consistent` | Adding or removing a server can remap most keys | nginx 1.7.2 and later |
| `hash $key consistent` | Ketama ring: only a few keys remap | nginx 1.7.2 and later |

## Interview Qs

### Why not just use hash(key) % N?

Changing N changes the result for most keys, so adding or removing a server reshuffles most of the data or cache. A ring moves only the keys in the arcs next to the change, about 1/(N+1) of them when you add one server.

### What are virtual nodes, and why use them?

Each physical server gets many points on the ring. Data and load spread more evenly, a failed server's keys go to many servers instead of one, and a bigger server can take more points.

### How do you replicate data on a ring?

Store each key on its owner and on the next N-1 servers clockwise. Dynamo calls this the preference list, and it skips extra points of the same server so the copies land on distinct machines.

### Does Redis Cluster use consistent hashing?

No. Every key maps to one of 16,384 hash slots, `CRC16(key) mod 16384`, and each primary owns some slots. To add a node, you move some slots to it, with no downtime.
