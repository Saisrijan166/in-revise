## What it is

Consistent hashing is a way to decide which server holds each key so that adding or removing a server moves as few keys as possible. You hash every server and every key onto the same circle, called a ring. A key belongs to the first server you meet going clockwise from the key's position. It is the standard answer to the problem that plain `hash(key) % N` has when N changes, which you met when sharding the payment service.

## Why it exists

The simple rule `hash(key) % N` picks a server from the key and the server count N. But if you add or remove one server, N changes, and `hash(key) % N` changes for almost every key. For a cache that means nearly every key suddenly maps to a different server and misses; for a sharded database it means moving almost all the data. Consistent hashing changes the rule so that one extra server only takes over the keys next to it, and the rest stay put.

## How it works

<Mermaid
  alt="A hash ring from 0 to 99 with three servers: A at 10, B at 40 and C at 75, linked clockwise, and C links back to A past 99. A key with hash 52 goes to C, the next server clockwise. A key with hash 90 wraps around to A."
  chart={`flowchart LR
  A(("A at 10")) -- clockwise --> B(("B at 40"))
  B -- clockwise --> C(("C at 75"))
  C -- "wraps past 99" --> A
  K1["key hash 52"] -.-> C
  K2["key hash 90"] -.-> A`}
/>

1. Hash each server to a position on the ring. Here A is at 10, B at 40 and C at 75.
2. To place a key, hash it, then walk clockwise to the first server point. So C owns every key from 41 up to 75.
3. A key whose hash is past the last point, such as 90, wraps around and belongs to A, the first point.
4. Add server D at 60: only keys from 41 to 60 move, from C to D. Everything else stays. Remove C and its keys go to the next point clockwise, A.

So the key is that a change touches only the arc next to it, not the whole ring.

## Analogy

<Analogy title="Seats around a round table" limit="Real servers are placed by a hash, not by hand, so without virtual nodes the gaps between them are uneven.">
Guests (keys) each sit at the next named chair (server) going clockwise. Add one more chair and only the guests between it and the previous chair move seats; everyone else stays where they are.
</Analogy>

## Example

A tiny ring with virtual nodes. CRC32 is a stable hash, fine for a demo; Cassandra uses Murmur3.

```java
TreeMap<Long, String> ring = new TreeMap<>();   // ring position -> server

long hash(String s) {
    CRC32 crc = new CRC32();
    crc.update(s.getBytes(StandardCharsets.UTF_8));
    return crc.getValue();                       // 0 .. 2^32 - 1
}
void addServer(String server, int vnodes) {      // vnodes points per server
    for (int i = 0; i < vnodes; i++) ring.put(hash(server + "#" + i), server);
}
String serverFor(String key) {
    var e = ring.ceilingEntry(hash(key));        // first point clockwise
    return (e != null ? e : ring.firstEntry()).getValue();  // wrap around
}
```

```python
import bisect, zlib

ring = []  # sorted list of (position, server)

def add_server(server: str, vnodes: int) -> None:
    for i in range(vnodes):                  # vnodes points per server
        bisect.insort(ring, (zlib.crc32(f"{server}#{i}".encode()), server))

def server_for(key: str) -> str:
    pos = zlib.crc32(key.encode())           # 0 .. 2**32 - 1
    i = bisect.bisect_left(ring, (pos, ""))  # first point clockwise
    return ring[i % len(ring)][1]            # wrap around
```

What to notice:

- `ceilingEntry` (Java) and `bisect_left` (Python) both find the first ring point at or after the key's hash; that is "walk clockwise".
- When the key is past the last point, the code wraps to the first entry, which is the ring closing the circle.
- `vnodes` adds many points per server. With three servers at 100 points each, adding a fourth moved about a third of 10,000 keys in a test run, close to the 1/4 you would expect; one point each would be far more uneven.

## Rules and defaults

- **Virtual nodes are needed for balance:** one random point per server leaves uneven arcs, so give each server many points.
- **Cassandra `num_tokens`:** 16 virtual nodes per server by default since 4.0 (it was 256 in 3.11).
- **Cassandra `partitioner`:** `Murmur3Partitioner` is the default hash that places rows (Cassandra 5.0).
- **nginx `hash $key`:** remaps most keys when a server changes; add the `consistent` flag (`hash $key consistent`) to get a ketama ring where only a few keys move. Both available since nginx 1.7.2.
- **Redis Cluster is different:** it does not use a ring; each key maps to one of 16,384 fixed hash slots via `CRC16(key) mod 16384`, and primaries own slot ranges.

## Interview Qs

### Why not just use hash(key) % N?

Changing N changes the result for almost every key, so adding or removing one server reshuffles almost all of the cache or data. A ring moves only the keys in the arc next to the change, about 1/(N+1) of them when you add one server, and leaves the rest where they are.

### What are virtual nodes, and why use them?

Each physical server gets many points on the ring instead of one. The load spreads more evenly because no server gets one huge arc, a failed server's keys go to many servers rather than piling on one neighbour, and a bigger server can be given more points to take a larger share.

### How do you keep replicas with consistent hashing?

Store each key on its owner and the next N-1 distinct servers clockwise. Dynamo calls this the preference list and skips extra virtual points of a server already chosen, so the copies land on different physical machines, not the same one twice.

### Does Redis Cluster use consistent hashing?

No. Every key maps to one of 16,384 fixed hash slots, `CRC16(key) mod 16384`, and each primary owns a set of slots. To add a node you move some slots to it, with no downtime; it is slot-based, not a clockwise ring.
