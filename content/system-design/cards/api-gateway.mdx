## What it is

An API gateway is a single entry point that sits in front of many backend services. Clients send every request to the gateway instead of to the services directly. For each request the gateway does the shared edge jobs, checking the caller's identity, applying rate limits and logging, then reads the request and routes it to the service that owns it. It is a [reverse proxy](card:reverse-proxy) with API-aware features, so it builds on the same "one front door" idea but adds per-API routing, authentication and quotas.

## Why it exists

In a system of many services, without a gateway each client must know the address of every service, and every service must repeat authentication, TLS and rate limiting. That duplicates the same edge code everywhere and makes clients fragile, because any change to the service layout breaks them. A gateway gives clients one stable endpoint and does those shared jobs once, so services can be added, split or moved without the clients noticing.

1. A client sends its request to the gateway's single endpoint.
2. The gateway validates the caller, usually by checking a token, and rejects anyone unauthenticated.
3. It applies rate limits and logs the call, so every service gets this protection for free.
4. It reads the path, host or header and routes the request to the owning service: `/users` to the users service, `/orders` to the orders service.
5. For a screen that needs several services, it can call an aggregator that fans out to them and returns one combined reply.

So the key is that clients see one endpoint while the services behind it can change freely.

## Example

A mobile home screen needs the user's profile, recent orders and current offers, each from a different service.

- **No gateway:** the phone makes 3 separate calls over a slow mobile network, and each one can fail or time out on its own.
- **With gateway aggregation:** the phone makes 1 call. The gateway calls the 3 services over the fast internal network and returns one combined reply.

What to notice:

- The slow, unreliable hop is the mobile network, so cutting 3 mobile round trips to 1 is the real win.
- The 3 internal calls still happen, but on a fast, reliable network where a retry is cheap.
- Azure suggests putting aggregation in a separate service behind the gateway, so heavy fan-out does not slow down plain routing.

## Rules and defaults

- **Throttle limit:** AWS API Gateway defaults to 10,000 requests/s with a burst of 5,000, per account per Region (some Regions start lower, such as 2,500 with a burst of 1,250).
- **Over the limit:** AWS API Gateway returns `429 Too Many Requests`.
- **Backend timeout:** on AWS API Gateway REST APIs the integration timeout ranges from 50 ms to 29 s; Regional and private APIs can request more than 29 s.
- **Largest payload:** 10 MB on AWS API Gateway REST APIs.
- **Run several instances:** the gateway is on the path of every request, so run several instances behind a load balancer or it is a single point of failure.

## Not to be confused with

A [load balancer](card:load-balancer) spreads traffic across identical copies of one service and does not understand your APIs. A [reverse proxy](card:reverse-proxy) is one front door that adds TLS, caching and compression. An API gateway adds API-level features on top: routing to different services, authentication, quotas and request transformation. Rule: load balancer spreads load, reverse proxy adds edge features, gateway manages APIs. They often stack, with a load balancer in front of several gateway instances.

## Interview Qs

### Why use an API gateway if we already have a load balancer?

A load balancer only spreads traffic across copies of one service; it does not know your APIs. A gateway adds API-level work: routing to different services by path, authenticating callers, enforcing quotas and transforming requests. They are complementary, and a common setup puts a load balancer in front of several gateway instances.

### What are the downsides of an API gateway?

It adds a hop on every request, so it costs latency, and it can become a bottleneck and a single point of failure. It is also one more thing to run. Mitigate by running several instances, load-testing it, and keeping business logic out so it does not grow into a shared monolith.

### Where should authentication happen, at the gateway or in each service?

Validate the token once at the gateway so unauthenticated callers never reach a service. Each service still decides what that caller may do, using the trusted identity the gateway passes, never an unverified header. Make services reachable only through the gateway so nobody can bypass its checks.

### What is the Backend for Frontend (BFF) pattern?

A separate gateway or backend per client type, such as one for mobile and one for web, each shaped to that client's needs so a screen gets exactly the data it wants. It suits clients with very different needs; the cost is more services to run and some duplicated code between them.
