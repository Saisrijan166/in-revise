## What it is

A Bloom filter is a small, memory-only structure that answers one question: have I seen this item before? Its answer is either "definitely not" or "maybe". It never says "definitely yes". It works on a bit array (an array of 0s and 1s) and a few hash functions, which you met when [indexing](card:indexing) turned keys into positions. In exchange for the occasional wrong "maybe", it uses far less memory than storing every item.

## Why it exists

Some lookups are slow, like reading from disk or calling another service, and most of them find nothing. Checking a real set of all known items would be exact, but that set can be too large to keep in memory. A Bloom filter stores a tiny fingerprint of the set instead, so it can answer "definitely not here" from memory in a few bit reads, letting you skip the slow lookup for the common case where the item is absent.

1. Start with a bit array of all 0s and pick k hash functions.
2. To add an item, run it through all k hash functions to get k positions, and set those bits to 1.
3. To check an item, compute the same k positions and read those bits.
4. If any of them is 0, the item was never added, because adding it would have set that bit. If all are 1, answer "maybe": those bits could have been set by other items.

So the key is that a real member always has all its bits set, which is why a "no" is certain and only a "yes" can be wrong.

## Example

A tiny filter with `m` bits and `k` hash functions, run on 100 items.

```java
BitSet bits = new BitSet(m);                   // m bits, all 0

int spot(String item, int i) {                 // double hashing: h1 + i * h2
    int h1 = item.hashCode() * 0x9E3779B9, h2 = (h1 >>> 16) | 1;
    return Math.floorMod(h1 + i * h2, m);
}
void add(String item) {
    for (int i = 0; i < k; i++) bits.set(spot(item, i));
}
boolean mightContain(String item) {
    for (int i = 0; i < k; i++) if (!bits.get(spot(item, i))) return false;
    return true;                               // maybe: could be a false positive
}
```

```python
import hashlib
class BloomFilter:
    def __init__(self, m: int, k: int):
        self.m, self.k, self.bits = m, k, bytearray(m)   # 1 byte per bit, for clarity

    def _spots(self, item: str):                         # k independent hashes
        for i in range(self.k):
            yield int(hashlib.sha256(f"{i}:{item}".encode()).hexdigest(), 16) % self.m

    def add(self, item: str):
        for p in self._spots(item):
            self.bits[p] = 1

    def might_contain(self, item: str) -> bool:
        return all(self.bits[p] for p in self._spots(item))   # True means maybe
```

```text output
all added report present: True
false positive rate: 0.92%
```

What to notice:

- The output ran the Python version with `m = 1000`, `k = 7` and 100 items, then tested 10,000 non-members.
- Every added item reports present: there are no false negatives, as promised.
- About 0.92% of non-members wrongly report "maybe", close to the ~0.8% the formula predicts for this size; this is the false-positive rate.
- In production use a tested library (Guava `BloomFilter`, or Redis `BF.ADD` and `BF.EXISTS`) rather than a hand-rolled one.

## Rules and defaults

| What | Default | Where |
| --- | --- | --- |
| Filter created by `BF.ADD` | 1% error rate, room for 100 items, next sub-filter 2x bigger | Redis 8 |
| `bloom_filter_fp_chance` | 0.01 (0.1 with LeveledCompactionStrategy) | Cassandra 5.0 |
| `BloomFilter.create(funnel, n)` | 3% false positives | Guava 33.7 |

- **Sizing rule:** for n items at error rate p, use about `m = -n * ln(p) / (ln 2)^2` bits and `k = (m/n) * ln 2` hashes. For 1% that is roughly 9.6 bits per item and 7 hashes.

## Common mistakes

- **"I can remove an item by clearing its bits."** A basic Bloom filter has no delete: a bit may be shared with another item, so clearing it would make that item wrongly report absent (a false negative). Use a counting Bloom filter, a cuckoo filter (Redis `CF.DEL`), or rebuild from the data.
- **"A bigger filter is always better."** Past a point the memory is wasted. Size it from your real item count and the error rate you can tolerate; oversizing costs memory, undersizing makes "maybe" wrong too often.

## Interview Qs

### What is a Bloom filter, and when would you use one?

A compact bit array that tests set membership and answers "definitely not" or "maybe". Use it in front of a slow lookup that usually finds nothing: an LSM store skipping files for a key, a crawler skipping already-seen URLs, or a quick "this username may be taken" check before hitting the database.

### Why false positives but never false negatives?

Adding an item sets all of its k bits, and bits are never cleared, so a real member always finds every one of its bits set and reports "maybe". An item that was never added can still find all k of its bits already set by other items, which is a false positive.

### How big should it be?

Choose n, the expected number of items, and p, the error rate you can accept. Then `m ≈ -n·ln(p)/(ln2)²` bits and `k ≈ (m/n)·ln2` hashes; for 1% that is about 9.6 bits per item and 7 hashes. If you later add many more items than n, the false-positive rate rises.
