## Why it exists

Some lookups are slow, like a disk read or a network call, and usually find nothing. A Bloom filter answers "definitely not here" from memory, so most of those lookups are skipped.

## How it works

- More bits per item means fewer false positives. The best number of hash functions is about (bits ÷ items) × ln 2.
- Bits are never cleared, so a fuller filter says "maybe" more often. Redis 8 adds a bigger sub-filter when one is full.
- Burton Bloom described it in 1970, to keep most word lookups for a hyphenation program off a slow disk.

## Example

A tiny filter: `m` bits and `k` hash functions.

```java
BitSet bits = new BitSet(m);                   // m bits, all 0

int spot(String item, int i) {                 // double hashing: h1 + i * h2
    int h1 = item.hashCode() * 0x9E3779B9, h2 = (h1 >>> 16) | 1;
    return Math.floorMod(h1 + i * h2, m);
}

void add(String item) {
    for (int i = 0; i < k; i++) bits.set(spot(item, i));
}

boolean mightContain(String item) {
    for (int i = 0; i < k; i++) if (!bits.get(spot(item, i))) return false;
    return true;                               // maybe: could be a false positive
}
```

```python
import hashlib
class BloomFilter:
    def __init__(self, m: int, k: int):
        self.m, self.k, self.bits = m, k, bytearray(m)   # 1 byte per bit, for clarity

    def _spots(self, item: str):                         # k independent hashes
        for i in range(self.k):
            yield int(hashlib.sha256(f"{i}:{item}".encode()).hexdigest(), 16) % self.m

    def add(self, item: str):
        for p in self._spots(item):
            self.bits[p] = 1

    def might_contain(self, item: str) -> bool:
        return all(self.bits[p] for p in self._spots(item))   # True means maybe
```

With m = 1,000, k = 7 and 100 items, theory gives about 0.8% false positives; both demos measure close to 1%. In production, use Guava's `BloomFilter` or Redis `BF.ADD` and `BF.EXISTS`.

## Interview Qs

### What is a Bloom filter, and when would you use one?

A compact bit array that tests set membership and answers "definitely not" or "maybe". Use it in front of a slow lookup that usually finds nothing: an LSM store skipping files, a crawler skipping seen URLs, a quick "username may be taken" check.

### Why false positives, but never false negatives?

Adding an item sets all of its k bits, and bits are never cleared, so a real member always finds its bits set. An item never added can still find all its bits set by other items.

### How big should it be?

Pick n, the expected items, and p, the error rate. Bits m ≈ −n × ln(p) ÷ (ln 2)², and hashes k ≈ (m ÷ n) × ln 2. For 1%, that is about 9.6 bits per item and 7 hashes. Add more items than planned and false positives rise.

### Can you delete from a Bloom filter?

Not from a basic one: a bit may be shared with other items, so clearing it causes false negatives. Use a counting Bloom filter (small counters instead of bits), a cuckoo filter (Redis `CF.DEL`), or rebuild the filter from the data.
