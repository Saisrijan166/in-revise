## What it is

A geospatial index is a special [index](card:indexing) for locations on a map, so you can ask "what is near this point" quickly. A location has two values at once, latitude and longitude, and a normal index sorts by one value at a time, so it cannot handle "near" well. Geospatial indexes solve this two ways: encode each point as a single key that keeps nearby points together (geohash, H3), or store points in a tree of boxes that shrink where points are dense (quadtree, R-tree).

## Why it exists

A query like "find drivers within 3 km" is about closeness in two dimensions. If you put a normal index on `(lat, lng)`, it can narrow to the right band of latitude, but within that band it still scans every longitude, so it reads a thin strip wrapping the whole globe. That is slow and reads far too many rows. A geospatial index keeps points that are near on the map near in the index, so a nearby search touches only a small region.

## How it works

<Steps label="Nearby search with a geohash">
<Step title="Encode">
Store each place's geohash. Central Bengaluru is `tdr1v9q`; its first 6 characters name a cell of about 1.2 km by 0.6 km.
</Step>
<Step title="Add the neighbours">
Take the user's cell and the 8 cells around it, so places just across an edge are not missed.
</Step>
<Step title="Range-scan the index">
Fetch places whose geohash starts with one of those 9 prefixes, from a B-tree or a Redis sorted set.
</Step>
<Step title="Filter exactly">
Compute the real distance for each candidate, drop those outside the radius, and sort by distance.
</Step>
</Steps>

<Compare id="geohash-vs-quadtree" />

- **Shapes** such as delivery zones need an R-tree of bounding boxes. PostGIS builds it on GiST: `USING GIST (geom)`.
- **Uber's H3** uses hexagons, so a cell's centre is the same distance from all six of its neighbours.

## Example

Redis GEO stores points and searches a radius for you (`GEOSEARCH` needs Redis 6.2+). Longitude comes first.

```text
GEOADD drivers 77.5946 12.9716 driver:17
GEOADD drivers 77.6100 12.9800 driver:8
GEOADD drivers 77.6245 12.9352 driver:42
GEOSEARCH drivers FROMLONLAT 77.6000 12.9700 BYRADIUS 3 km ASC
1) "driver:17"     # about 0.6 km away
2) "driver:8"      # about 1.6 km away; driver:42 (4.7 km) is outside
```

What to notice:

- `GEOADD` takes longitude before latitude; swapping them silently stores the wrong place.
- `GEOSEARCH ... BYRADIUS 3 km ASC` returns only points within 3 km, nearest first, so Redis does the encode-and-filter work for you.
- `driver:42` is 4.7 km away and is correctly left out, showing the radius filter at work.
- Each driver update is one `GEOADD` that overwrites the old position, which is why Redis GEO suits points that move every few seconds.

## Rules and defaults

| What | Default or limit | Where |
| --- | --- | --- |
| Argument order | Longitude, then latitude | Redis `GEOADD` |

| Distance error | Up to 0.5%: Earth is treated as a sphere | Redis GEO |

## Interview Qs

### Why can't a normal index find nearby places?

A B-tree sorts by one value at a time. With an index on `(lat, lng)`, the latitude range limits the scan, but longitude is only checked inside that range, so you still read a strip wrapping the globe. A geospatial index keeps points that are near on the map next to each other, so a nearby search stays local.

### Geohash or quadtree?

Geohash is a fixed grid stored as plain string keys in any database or Redis, with a cheap one-key update when a point moves. Quadtree adapts to density by splitting busy areas into smaller cells, but it is usually held in memory and changes shape as points are added or removed.

### How do you find nearby drivers when locations change every few seconds?

Keep current locations in memory, for example in Redis GEO. Each update is a single `GEOADD` that overwrites the driver's old position, and `GEOSEARCH` returns the drivers within a radius, nearest first, so both the write and the query stay fast under constant movement.
