## What it is

An index is a separate, sorted data structure the database keeps alongside a table. It maps the values of one or more columns to the rows that hold them, like a book index maps words to page numbers. The usual kind is a **B-tree**: a shallow tree you walk from a root page down to a leaf in a few steps. With an index a lookup reads a handful of pages; without one, the database does a **full table scan**, reading every row to find the few that match.

## Why it exists

Without an index, `WHERE user_id = 42` makes the database read every row in the table, because it has no way to know where the matching rows are. On a small table that is fine, but as the table grows to millions of rows, every such query reads all of them and gets slower and slower. An index gives the database a sorted map, so it jumps to the matching rows directly. The cost is real but bounded: the index must be kept up to date on every write.

1. The query starts at the root page, which narrows the range in one comparison.
2. It follows pointers down through internal pages, each step narrowing further, to the right leaf.
3. The leaf holds the key and a pointer to the row, so a few page reads replace reading the whole table.
4. Because keys stay sorted, the same index serves `=`, ranges, `ORDER BY` and `LIKE 'abc%'`; a leading wildcard like `LIKE '%abc'` cannot use it.

So the key is: an index trades a little write cost for turning full scans into a few page reads. Write-heavy stores such as Cassandra use an LSM tree instead of a B-tree:

## Example

A covering composite index on PostgreSQL 18, and three queries against it:

```sql
-- Equality column first, then the range/sort column; INCLUDE makes it covering
CREATE INDEX orders_user_time ON orders (user_id, created_at) INCLUDE (total);

-- Starts from the leftmost column: can be an index-only scan
SELECT created_at, total FROM orders
WHERE user_id = 42 AND created_at >= '2026-10-01'
ORDER BY created_at DESC LIMIT 20;

-- Skips user_id: with many users, expect a full table scan
SELECT * FROM orders WHERE created_at >= '2026-10-01';
```

What to notice:

- The column order `(user_id, created_at)` matches the query: equality on `user_id`, then a range and sort on `created_at`, so the index does the filtering and the ordering.
- `INCLUDE (total)` puts `total` in the index, so the second query reads only the index, never the table: an index-only scan.
- The third query starts from `created_at`, skipping `user_id`, so it cannot use this index and falls back to a full scan. Run `EXPLAIN` to see the plan the database actually picks.

## Rules and defaults

- **Default index type:** `CREATE INDEX` builds a B-tree in PostgreSQL 18.
- **Automatic indexes:** PostgreSQL creates one for every `PRIMARY KEY` and `UNIQUE` constraint.
- **Foreign keys:** PostgreSQL does not index foreign-key columns automatically; add it yourself. MySQL 8.4 does create one if it is missing.
- **MySQL InnoDB storage:** table rows live inside the primary-key B-tree (a clustered index), and every other index stores the primary key to find the row.
- **The planner decides:** an index is not guaranteed to be used; the query planner may choose a full scan when most rows match. Confirm with `EXPLAIN`.
- **Building an index:** in PostgreSQL a plain `CREATE INDEX` blocks writes until done; `CREATE INDEX CONCURRENTLY` does not.

## Not to be confused with

- **Primary key vs index:** a primary key is a uniqueness-and-identity constraint; it happens to be backed by an index. An index can also be non-unique and on any columns.
- **B-tree vs LSM tree:** both are index structures, but a B-tree changes pages in place (read-friendly) while an LSM tree buffers writes and merges files (write-friendly). Rule: default to a B-tree; choose an LSM tree when writes far outnumber reads.

## Interview Qs

### Why not index every column?

Every insert, update and delete must also change each index, and each index takes disk and memory. An unused index is pure cost with no benefit. Index what frequent queries filter, join or sort on, and drop indexes that `EXPLAIN` and usage stats show nobody uses.

### How do you order columns in a composite index?

Equality columns first, then the range or sort column, as in `(user_id, created_at)`. It serves queries on `user_id`, or on both columns, but usually not on `created_at` alone. PostgreSQL 18 can skip-scan, but generally only when the first column has few distinct values.

### A query on an indexed column is still slow. Why?

Run `EXPLAIN`. Common causes: a function on the column, like `lower(email)`, without a matching expression index; a leading wildcard, `LIKE '%x'`; a query that skips the leftmost column of a composite index; or so many matching rows that a full scan is actually cheaper.

### B-tree or LSM tree?

B-tree for reads and range scans: a few page reads per lookup, used by PostgreSQL and MySQL. LSM tree for heavy writes: writes go to memory and are flushed as sorted files, merged later. Reads may check several files, so Bloom filters help. Cassandra and RocksDB use LSM trees.
