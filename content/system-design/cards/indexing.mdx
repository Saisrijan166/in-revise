## Why it exists

Without an index, the database reads every row to find the few that match (a full table scan). That gets slower as the table grows.

## How it works

<Mermaid
  alt="A B-tree lookup for user_id 42. The query starts at the root page, which sends keys under 50 to the left. An internal page says keys 40 to 49 are in leaf 7. Leaf 7 holds key 42 and a pointer to its row. Three page reads find the row instead of reading the whole table."
  chart={`flowchart TD
  Q(["WHERE user_id = 42"]) --> R["Root page: under 50, go left"]
  R --> I["Internal page: 40 to 49 are in leaf 7"]
  I --> L["Leaf 7: key 42 + row pointer"]
  L --> T[("Row for user 42")]`}
/>

- Keys stay sorted, so `=`, ranges, `ORDER BY` and `LIKE 'abc%'` can use a B-tree; `LIKE '%abc'` cannot.
- A composite index on `(a, b)` is sorted by `a`, then by `b`, so a query must start from `a`: the leftmost-prefix rule.
- Write-heavy stores such as Cassandra use an LSM tree instead:

## Example

PostgreSQL 18, an `orders` table:

```sql
-- Equality column first, then the range/sort column; INCLUDE makes it covering
CREATE INDEX orders_user_time ON orders (user_id, created_at) INCLUDE (total);

-- Starts from the leftmost column: can be an index-only scan
SELECT created_at, total FROM orders
WHERE user_id = 42 AND created_at >= '2026-10-01'
ORDER BY created_at DESC LIMIT 20;

-- Skips user_id: with many users, expect a full table scan
SELECT * FROM orders WHERE created_at >= '2026-10-01';
```

Run `EXPLAIN` to see the plan the database picks.

## Defaults

| What | Default | Where |
| --- | --- | --- |
| Index type of `CREATE INDEX` | B-tree | PostgreSQL 18 |
| Index for `PRIMARY KEY` and `UNIQUE` | Created automatically | PostgreSQL 18 |
| Index on foreign-key columns | Not created: add it yourself | PostgreSQL 18 |
| Index on foreign-key columns | Created automatically if missing | MySQL 8.4 |
| Where table rows are stored | Inside the primary-key B-tree (clustered index) | MySQL 8.4 InnoDB |
| Building an index | Blocks writes until done; `CREATE INDEX CONCURRENTLY` does not | PostgreSQL 18 |

## Interview Qs

### Why not index every column?

Every insert, update and delete must also change each index, and each index takes disk and memory. An unused index is pure cost. Index what frequent queries filter, join or sort on, and drop indexes nobody uses.

### How do you order columns in a composite index?

Equality columns first, then the range or sort column, as in `(user_id, created_at)`. It serves queries on `user_id`, or on both, but usually not on `created_at` alone. PostgreSQL 18 can skip-scan, but generally only when the first column has few distinct values.

### A query on an indexed column is still slow. Why?

Run `EXPLAIN`. Common causes: a function on the column, like `lower(email)`, without an expression index; a leading wildcard, `LIKE '%x'`; a query that skips the leftmost column; or so many matching rows that a full scan is cheaper.

### B-tree or LSM tree?

B-tree for reads and range scans: a few page reads per lookup, used by PostgreSQL and MySQL. LSM tree for heavy writes: writes go to memory and are flushed as sorted files, merged later. Reads may check several files, so Bloom filters help. Cassandra and RocksDB use LSM trees.
