## What it is

A circuit breaker is a wrapper around a remote call that watches how often the call fails. While failures are rare it stays out of the way. Once failures become common it trips open, like an electrical breaker, and makes every call fail instantly for a while instead of actually trying. This builds on [timeouts and retries](card:timeouts-retries): retry handles a short blip, and the breaker steps in when the trouble lasts longer.

## Why it exists

When a dependency is down or very slow, every caller waits for its timeout, holding a thread and a connection the whole time. These pile up until the caller runs out of threads and fails too, and the failure spreads from service to service: a [cascading failure](term:cascading-failure). A breaker cuts this off by failing fast the moment a dependency looks unhealthy, so the caller stays alive and the sick dependency gets quiet time to recover.

## How it works

1. In the **closed** state, calls pass through normally and the breaker counts failures in a recent window.
2. When the failure rate crosses the threshold, the breaker moves to **open** and makes every call fail instantly, with no remote call, until a wait timer ends.
3. When the timer ends, it moves to **half-open** and lets only a few trial calls through.
4. If the trials succeed it returns to closed; if one fails it goes back to open and waits again.

So the key is that a slow service must trip it too: count timeouts as failures, or a hanging dependency never crosses the threshold.

## Example

A breaker around the payment service's call to the card gateway, returning cached data when open:

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)                          // open at 50% failures...
    .slidingWindowSize(20).minimumNumberOfCalls(10)    // ...in the last 20 calls
    .waitDurationInOpenState(Duration.ofSeconds(30))   // then go half-open
    .permittedNumberOfCallsInHalfOpenState(3)          // 3 trial calls
    .build();
CircuitBreaker breaker = CircuitBreaker.of("card-gateway", config);

Price getPrice(String id) {
    try {
        return breaker.executeSupplier(() -> gateway.fetch(id));
    } catch (CallNotPermittedException e) {            // open: fail fast
        return cache.getPrice(id);                     // fallback
    }
}
```

```python
import pybreaker

# Opens after 5 failures in a row; after 30 s, one trial call is let through
breaker = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)

def get_price(item_id):
    try:
        return breaker.call(gateway.fetch, item_id)
    except pybreaker.CircuitBreakerError:      # open: fail fast
        return cache.get_price(item_id)        # fallback
```

What to notice:

- While the breaker is open, `executeSupplier` does not call the gateway at all; it throws `CallNotPermittedException` immediately, so the caller returns a fallback in microseconds instead of waiting a whole timeout.
- The fallback (`cache.getPrice`) is what the user sees during the outage, so it must be simple and tested; a fallback path that rarely runs often fails exactly when it is finally needed.
- Resilience4j counts a failure rate over a window; pybreaker counts consecutive failures. Both let you choose which exceptions count.

## Rules and defaults

| Setting | Resilience4j 2.x | pybreaker 1.4 |
| --- | --- | --- |
| Opens when | 50% of calls fail | 5 failures in a row |
| Measured over | Last 100 calls (min 100 recorded) | Consecutive failures |
| Wait before half-open | 60 seconds | 60 seconds |
| Trial calls in half-open | 10 | 1 |
| Counts as a failure | Every exception, unless configured | Every exception, unless excluded |

- **One breaker per dependency** (or per shard). A single shared breaker would block calls to the healthy dependencies too when one goes bad.

## Not to be confused with

A [retry](card:timeouts-retries) assumes the fault is brief and tries the call again. A circuit breaker assumes the fault is lasting and stops calling for a while. A [bulkhead](term:bulkhead) is different again: it caps how many calls or threads one dependency may use, so a slow dependency cannot starve the rest. Rule: retry = try again; breaker = stop trying for now; bulkhead = limit the blast radius.

## Common mistakes

- **"One breaker can guard all my downstream calls."** Share a breaker across dependencies and a single bad one trips it, cutting off the healthy ones too. Use one breaker per dependency.
- **"A circuit breaker repairs the failing service."** It only stops calling it; it does nothing to fix the dependency. It buys the dependency quiet time and keeps the caller alive, but recovery still depends on the dependency itself.

## Interview Qs

### Explain the three states of a circuit breaker.

Closed: calls go through and failures are counted. Open: calls fail at once without touching the service, until a wait timer ends. Half-open: a few trial calls go through; if they all succeed the breaker closes, and if one fails it opens again and waits.

### Circuit breaker versus retry: how do they differ, and do you use both?

Retry assumes the fault is short and tries again; a breaker assumes it is lasting and stops calling. Use both together: retry inside the breaker for brief blips, and let the breaker stop the retries once it opens, so you do not keep hammering a service that is clearly down.

### What does the user see when the circuit is open, and why test it?

A fallback: cached or default data, a page without that one feature, or a clear "try again later". Test it because this path runs only during outages, so a bug in it stays hidden until the worst moment, when it is the only thing standing between the user and a hard error.
