## Why it exists

When a dependency is down or very slow, every caller waits for its timeout and holds threads and connections meanwhile. They pile up until the caller fails too, and the failure spreads.

## How it works

<Mermaid
  alt="Circuit breaker states. Closed: calls go through. When failures pass the threshold, it moves to Open. Open: calls fail at once. When the wait time ends, it moves to Half-open. Half-open: if the trial calls succeed, it moves back to Closed; if a trial call fails, it goes back to Open."
  chart={`flowchart LR
  C([Closed]) -- "failures pass threshold" --> O([Open])
  O -- "wait time ends" --> H([Half-open])
  H -- "trial calls succeed" --> C
  H -- "a trial call fails" --> O`}
/>

- Count **timeouts** as failures too, so a slow service trips the breaker, not only a dead one.
- Half-open lets only a few calls through, because a recovering service can fall over again under full traffic.
- Use one breaker per dependency, or per shard: one shared breaker would block the healthy ones too.
- When open, return a **fallback**: cached data, a default, or a clear "try later". Keep it simple and test it.
- Popularised by Michael Nygard's book *Release It!*. Netflix Hystrix is in maintenance mode; Netflix points new projects to Resilience4j.

## Example

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)                          // open at 50% failures...
    .slidingWindowSize(20).minimumNumberOfCalls(10)    // ...in the last 20 calls
    .waitDurationInOpenState(Duration.ofSeconds(30))   // then go half-open
    .permittedNumberOfCallsInHalfOpenState(3)          // 3 trial calls
    .build();
CircuitBreaker breaker = CircuitBreaker.of("prices", config);

Price getPrice(String id) {
    try {
        return breaker.executeSupplier(() -> priceClient.fetch(id));
    } catch (CallNotPermittedException e) {            // open: fail fast
        return cache.getPrice(id);                     // fallback
    }
}
```

```python
import pybreaker

# Opens after 5 failures in a row; after 30 s, one trial call goes through
breaker = pybreaker.CircuitBreaker(fail_max=5, reset_timeout=30)

def get_price(item_id):
    try:
        return breaker.call(price_client.fetch, item_id)
    except pybreaker.CircuitBreakerError:      # open: fail fast
        return cache.get_price(item_id)        # fallback
```

## Defaults

| Setting | Resilience4j 2.x | pybreaker 1.4 |
| --- | --- | --- |
| Opens when | 50% of calls fail | 5 failures in a row |
| Measured over | Last 100 calls (at least 100 recorded) | Consecutive failures |
| Wait before half-open | 60 s | 60 s |
| Trial calls in half-open | 10 | 1 |
| Counts as failure | Every exception, unless configured | Every exception, unless excluded |

## Interview Qs

### Explain the three states.

Closed: calls go through and failures are counted. Open: calls fail at once without touching the service, until a timer ends. Half-open: a few trial calls go through; if they succeed it closes, and if one fails it opens again.

### Circuit breaker vs retry?

Retry assumes the fault is short and tries again. A circuit breaker assumes it is not, and stops calling. Use both: retry inside the breaker, and stop retrying when the breaker is open.

### What does the user see when the circuit is open?

A fallback: cached or default data, a page without that feature, or a clear "try again later". Keep the fallback simple and test it, because a path that rarely runs can fail exactly when you need it.

### Where do you put circuit breakers?

In the caller, around each remote dependency: other services, databases and third-party APIs. A service mesh sidecar can add them without changing application code.
