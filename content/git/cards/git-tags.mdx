## What it is

A tag is a name that points to one specific [commit](card:git-commit). Teams use it to mark a release, like `v1.0` or `v2.3.1`, so that version is easy to find later. Unlike a [branch](card:git-branches), a tag does not move when you add new commits; it stays on the commit you put it on. Git has two kinds: a lightweight tag (just a name) and an annotated tag (a full object that also stores who tagged it, when, and a message).

## Why it exists

After you ship version 1.0, work continues and main moves far ahead. Months later you need the exact code that shipped, to reproduce a bug or build a patch. Searching the history by date is slow and error-prone. A tag pins that commit with a human name, so `git checkout v1.0` takes you straight to it. Annotated tags also record who made the release and why, which matters for an audit or a signed, trusted build.

## How it works

  <Step title="Create">`git tag v1.0` makes a lightweight tag; `git tag -a v1.0 -m "First release"` makes an annotated one.</Step>
  <Step title="List and inspect">`git tag` lists tags; `git show v1.0` shows the tagged commit, plus the message and tagger for an annotated tag.</Step>
  <Step title="Push">Tags are not sent by a normal push. Run `git push origin v1.0`, or `git push origin --tags` for all.</Step>
</Steps>

## Example

Create an annotated release tag and push it:

```bash
git tag -a v1.0 -m "First release"
git tag
git push origin v1.0
```

```text output
v1.0
 * [new tag]         v1.0 -> v1.0
```

What to notice:

- `git tag -a ... -m` makes an annotated tag, so the message, tagger and date are stored in a tag object.
- `git tag` with no arguments just lists the tag names.
- The push had to name the tag. A plain `git push` would not have sent `v1.0` at all.

## Rules and defaults

| What | Default | Note |
|---|---|---|
| Kind created | Lightweight | `git tag <name>`; `-a` makes it annotated |
| Moves with commits | No | A tag is fixed to one commit |
| Sent by `git push` | No | Push by name, or `--tags` for all |
| Delete | Local only | `git tag -d v1.0`; push a delete with `git push origin --delete v1.0` |

- Annotated tags are recommended for anything you release or share; lightweight tags are fine only as temporary private marks.

## Common mistakes

- **"My tag pushed with my branch."** A normal push does not send tags. Push them by name or with `--tags`.
- **"A tag moves like a branch."** It does not. It stays on the commit you tagged, which is the point of a release marker.
- **"Deleting a tag locally removes it from the remote."** No. You must also run `git push origin --delete <tag>`.

## Interview Qs

### What is a Git tag and when do you use one?

A tag is a fixed name for one commit, used to mark a release such as `v1.0`. Unlike a branch it does not move as new commits arrive, so it always points to exactly the code you shipped. GitHub and GitLab build releases from tags.

### Difference between a lightweight and an annotated tag?

A lightweight tag is just a name pointing at a commit, with no extra data. An annotated tag is a full object storing the tagger, date and message, and it can be GPG-signed. Use annotated tags for releases; lightweight ones only as throwaway private marks.

### How do you push a tag to a remote?

A normal `git push` does not include tags. Push one with `git push origin v1.0`, or push all tags with `git push origin --tags`. To remove a remote tag, run `git push origin --delete v1.0`.
