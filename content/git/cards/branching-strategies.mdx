## What it is

A branching strategy is the team's agreed rule for how [branches](card:git-branches) are created, reviewed and merged. It decides how often code reaches the main line and how releases are cut. Three strategies dominate interviews: trunk-based development, GitHub Flow, and Git Flow. They trade off simplicity against structure.

## Why it exists

With no agreed rule, branches live for weeks, drift far from main, and merge in painful conflicts, while nobody is sure which branch is production. A shared strategy sets how small and short-lived branches should be and where releases come from, so integration stays cheap and everyone knows which line is safe to deploy.

## How it works

| Strategy | Branches | Flow | Fits |
|---|---|---|---|
| Trunk-based | `main` only; tiny short-lived branches | commit small changes to main daily, hide unfinished work behind feature flags | teams that deploy many times a day with strong CI |
| GitHub Flow | `main` plus one branch per change | branch → pull request → review → merge to main → deploy | web apps and open source with continuous deployment |
| Git Flow | long-lived `main` and `develop`, plus feature, release, hotfix | features off develop; release branch stabilises; hotfix off main | versioned software supported in several live versions |

1. **Trunk-based:** branches last a day or two; a feature flag keeps incomplete code switched off so main is always releasable.
2. **GitHub Flow:** each change is a branch with a pull request; after review it merges to main, which is then deployed.
3. **Git Flow:** `develop` integrates the next release; a release branch allows only fixes before merging to `main` (tagged); a hotfix branch off the production tag patches live bugs.

## Not to be confused with

GitHub Flow keeps a short-lived branch per change and reviews it in a pull request before merging to main. Trunk-based pushes even smaller changes into main itself as often as possible, using feature flags instead of long reviews. Rule: GitHub Flow is "branch then merge"; trunk-based is "integrate into main constantly".

## Common mistakes

- **Treating Git Flow as the default for every project.** Its own author now recommends a simpler flow for teams doing continuous delivery; Git Flow earns its extra branches only for explicitly versioned, multi-release software.
- **Calling any use of feature branches "Git Flow".** Git Flow specifically means the long-lived `develop` plus release and hotfix branches, not just having branches.

## Interview Qs

### What is trunk-based development?

Everyone integrates into one main branch (the trunk) through very short-lived branches, often several times a day. Unfinished work is hidden behind feature flags so main stays releasable, and continuous integration checks every push. It suits teams that deploy frequently.

### How does GitHub Flow differ from Git Flow?

GitHub Flow is lightweight: one branch per change, a pull request, review, merge to main, deploy. Git Flow is heavier: long-lived `develop` and `main` plus feature, release and hotfix branches. GitHub Flow suits continuous deployment; Git Flow suits versioned releases.

### Is Git Flow still recommended?

Not as a default. Its author added a 2020 note suggesting a simpler workflow like GitHub Flow for continuous delivery, and keeping Git Flow only for software with explicit versions that must be supported in several live versions at once.
