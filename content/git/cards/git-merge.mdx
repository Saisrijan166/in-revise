## What it is

Merge combines another [branch](card:git-branches) into the branch you are on. Git has two ways to do it. If your branch has no commits of its own since the two split, Git does a fast-forward: it just moves your branch pointer up to the other branch's tip. If both branches have new commits, Git does a three-way merge, using the common ancestor of the two branches to build one new merge commit that has two parents.

## Why it exists

People work on separate branches at the same time. At some point their work has to come together in one branch. Without merge you would copy changes by hand and lose the record of where each change came from. Merge joins the two lines of work in one step and, when they diverged, keeps both histories visible through a merge commit, so you can always see what came from which branch.

## How it works

<Compare id="fast-forward-vs-merge-commit" />

1. Git finds the common ancestor: the last commit both branches share.
2. If your branch's tip is that ancestor (your side added nothing), it fast-forwards: the pointer slides to the other tip, no commit is made.
3. If both sides added commits, Git replays the other branch's changes on top of yours.
4. Git records the result as a merge commit with two parents: your old tip and the other branch's tip.
5. If the same lines changed on both sides, Git stops with a [conflict](card:merge-conflicts) for you to resolve.

## Example

A feature branch, then a fast-forward because main did not move:

```bash
git switch main
git merge feature-login
```

```text output
Updating 3a4b5c6..9f8e7d6
Fast-forward
 login.java | 14 ++++++++++++++
 1 file changed, 14 insertions(+)
```

What to notice: Git prints "Fast-forward" and no merge commit is created; it simply moved main from `3a4b5c6` to `9f8e7d6`. If main had its own new commits, you would instead see "Merge made by the 'ort' strategy" and a merge commit. Use `git merge --no-ff feature-login` to force a merge commit even here, which keeps the feature grouped in history.

## Rules and defaults

| What | Behaviour | Notes |
|---|---|---|
| Default | `--ff`: fast-forward if possible, else merge commit | `merge.ff` config can change it |
| `--no-ff` | Always make a merge commit | Keeps the feature visible as a group |
| `--ff-only` | Fast-forward or fail | Refuses to create a merge commit |

- A three-way merge commit always has two parents; a fast-forward adds none.
- Before a true merge Git sets `ORIG_HEAD` to the old tip, so you can undo with `git reset --hard ORIG_HEAD`.

## Common mistakes

- **"A fast-forward merge loses the feature branch's commits."** It keeps every commit; it only skips making a merge commit. The branch label is what moves.
- **"--no-ff and a normal merge are the same."** `--no-ff` forces a merge commit even when Git could have fast-forwarded.

## Interview Qs

### What is the difference between a fast-forward and a three-way merge?

A fast-forward happens when your branch has no new commits since the split: Git just moves the pointer to the other tip, no merge commit. A three-way merge happens when both branches diverged: Git uses the common ancestor to build a merge commit with two parents.

### When does Git create a merge commit?

Only in a three-way merge, when both branches have new commits since they split. It then combines them into one commit with two parents. A fast-forward merge creates no commit. You can force a merge commit with `git merge --no-ff`.

### How do you force a merge commit even when a fast-forward is possible?

Use `git merge --no-ff <branch>`. It always records a merge commit, which keeps the feature's commits grouped and makes it clear where the branch was merged. Setting `merge.ff` to `false` makes this the default.
