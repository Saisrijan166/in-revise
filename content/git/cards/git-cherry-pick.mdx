## What it is

Cherry-pick takes the change made by one specific commit and applies it onto the branch you are currently on, recording it as a new commit. The original commit stays where it is on its own branch. It is the tool for moving a single commit across branches, unlike a [merge](card:git-merge), which brings over a whole branch's history.

## Why it exists

Sometimes you need exactly one commit from another branch, not everything on it. A bug is fixed on the development branch, but that branch also has half-finished features you cannot ship yet. Merging would drag all of it into your release branch. Cherry-pick lets you take just that one fix. Without it, you would have to re-type the change by hand or merge far more than you want.

## How it works

<Steps label="Cherry-picking one commit">
  <Step title="Find the commit">Get the commit's hash from `git log` on the branch that has it.</Step>
  <Step title="Go to the target">`git switch` to the branch that should receive the change. Your working tree must be clean.</Step>
  <Step title="Cherry-pick">Run `git cherry-pick <hash>`. Git re-applies that commit's change and records a new commit.</Step>
  <Step title="Resolve if needed">On an overlap you get conflict markers. Fix them, `git add`, then `git cherry-pick --continue` (or `--abort` to cancel).</Step>
</Steps>

The new commit carries the same change but a new id, because its parent is different.

## Example

Landing a single fix from develop onto a release branch:

```bash
git switch release
git cherry-pick a1b2c3d
```

```text output
[release 7f2e9a1] Fix null pointer on empty cart
 Date: Mon Nov 2 10:14:22 2026 +0530
 1 file changed, 2 insertions(+), 1 deletion(-)
```

What to notice: the new commit on `release` is `7f2e9a1`, not the original `a1b2c3d`. It has the same change and message but a new id, because it sits on a new parent. The original `a1b2c3d` is still on `develop`, untouched. Nothing else from `develop` came along.

## Rules and defaults

- Cherry-pick always creates a new commit with a new id; the source commit is unchanged.
- The working tree must be clean before you start.
- `-x` adds a "(cherry picked from commit …)" line, useful when backporting between public branches.
- `-n` applies the change without committing, so you can combine several picks into one commit.

## Common mistakes

- **Expecting the same commit id.** The picked commit always gets a new id on the target branch; only the change is copied.
- **Cherry-picking a long chain instead of merging.** For many commits, a merge or rebase is cleaner; cherry-pick is for one or a few specific commits.
- **Picking the same fix that later gets merged.** You can end up with the change twice. Prefer one path for a given commit.

## Interview Qs

### What is git cherry-pick used for?

To apply one specific commit's change onto your current branch as a new commit, without merging the whole branch it came from. A common case is taking a single hotfix from development onto a release branch while leaving its unfinished work behind.

### Does cherry-pick move the commit or copy it?

It copies the change. Git re-applies the commit on your current branch as a new commit with a new id; the original stays untouched on its branch. The id differs because the new commit has a different parent.

### How is cherry-pick different from merge?

Merge brings an entire branch's history into yours, often with a merge commit. Cherry-pick takes just one chosen commit and re-applies it as a new commit. Use merge to integrate a branch, cherry-pick to grab a single change.
