## What it is

`git blame` annotates each line in a file with information from the commit that last modified that line: the abbreviated commit hash, the author, the date, and the line number. It answers "who last touched this line, and in which commit?" so you can then read that commit to learn why the line is there.

## Why it exists

When you hit a line you do not understand, or one that looks wrong, you need its backstory: which change introduced it and why. Searching the whole [log](card:git-log) by hand is slow. Blame maps each current line straight to its last commit, giving you a starting point in one command. From there `git show` reveals the full reason.

## How it works

<Steps label="Tracing a line">
<Step title="Blame the file">Run git blame on the file (or a line range) to see each line's last-changing commit.</Step>
<Step title="Read the hash">Note the commit hash next to the line you care about.</Step>
<Step title="Show the commit">Run git show on that hash to read the full diff and the commit message.</Step>
<Step title="Look further if needed">If that commit only reformatted the line, blame its parent to find the real change.</Step>
</Steps>

- Default output per line: short commit hash, author and date, line number, then the line.
- `-L <start>,<end>` limits blame to a line range, which is much faster on big files.
- Blame only explains lines that are present now; it says nothing about deleted or replaced lines (use `git log -S` for those).

## Example

```bash
git blame -L 12,13 src/payment/Charge.java
```

```text output
a1b2c3d4 (Ravi Menon 2026-09-14 12) if (amount <= 0)
e5f6a7b8 (Priya Shah 2026-10-02 13)     throw new IllegalArgumentException("amount");
```

What to notice:

- Each line shows the commit hash, author and date that last changed it. Line 12 and line 13 came from different commits.
- To learn why line 13 throws, run `git show e5f6a7b8`: that commit's message and full diff explain the change. The hash is the handle that links blame to the rest of the history.

## Common mistakes

- **Treating the last author as the culprit.** Blame shows the last change, which may be a rename or reformat. The cause can be an earlier commit; blame the parent to see past cosmetic changes.
- **Expecting it to explain deleted lines.** Blame only annotates lines that still exist. Use `git log -S<string>` (the pickaxe) to find when a line was removed.

## Interview Qs

### What does git blame do?

It shows, for each line of a file, the commit, author and date that last modified that line. You use it to trace why a line exists: find the commit from blame, then `git show` that commit for the full change.

### How do you blame only part of a large file?

Use `-L`, for example `git blame -L 40,60 file`, to annotate only lines 40 to 60. You can also give a regex or `+count`, and repeat `-L` for several ranges. This is much faster than blaming the whole file.

### Does git blame tell you who caused a bug?

Not reliably. It names whoever last changed the line, which might just be a reformat or rename. The real cause can be an earlier commit, so follow the trail back by blaming the parent commit rather than stopping at the latest author.
