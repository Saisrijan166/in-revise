## What it is

A `.gitignore` file lists patterns for files Git should not track, such as build output, dependency folders, logs and secrets. You commit `.gitignore` itself so the whole team shares the same rules. Each line is a glob pattern; a trailing slash means a directory, and a leading `!` re-includes a file an earlier line excluded. One key rule: it only affects files Git is not already tracking.

## Why it exists

Not everything in a project folder belongs in Git. Build output (`target/`, `build/`), installed dependencies (`node_modules/`), editor files and secret files (`.env`) are generated or private, and committing them bloats the repository and leaks secrets. Without `.gitignore`, [git status](card:git-status) would flag all of them as untracked and you would risk committing them by accident. The file tells Git to stay quiet about them so you see only the changes that matter.

## How it works

```text
# build output
target/
build/

# logs, except one we keep
*.log
!important.log

# secrets
.env
```

1. Git reads `.gitignore` and skips matching files when it decides what is untracked, so they no longer appear in `git status`.
2. A trailing slash (`target/`) matches only a directory of that name; without it, the pattern matches files and directories.
3. `*` matches anything except a slash, so `*.log` matches log files at that level and below.
4. A `!` line re-includes a file an earlier line ignored, if its parent directory is not itself ignored.

What to notice: these rules decide which *new* files Git ignores. A file that is already committed is not affected at all.

## Rules and defaults

| Pattern | Matches |
|---|---|
| `*.log` | Any file ending in `.log` |
| `build/` | A directory named `build` (not a file) |
| `!keep.log` | Re-includes `keep.log` that an earlier line ignored |
| `# text` | A comment; the line is skipped |

- **Already-tracked files are not affected.** Adding a pattern for a committed file does nothing; Git keeps tracking it and showing its changes.
- **To untrack it:** run `git rm --cached <file>`, which removes it from Git but leaves it on disk, then keep the `.gitignore` line and commit.

## Common mistakes

- **Ignoring a file that is already committed and expecting it to disappear.** It stays tracked. Use `git rm --cached` first.
- **Forgetting the trailing slash.** `build` matches a file or directory; `build/` matches only the directory.
- **Putting `!important.log` before `*.log`.** The negation must come after the line that excluded the file, or it has no effect.

## Interview Qs

### Does adding a file to .gitignore stop Git from tracking it?

Only if Git was not already tracking it. A file that is already committed is not affected by `.gitignore`. To untrack it, run `git rm --cached <file>` and keep the pattern; the file stays on disk but Git stops tracking it.

### How do you stop tracking a file you already committed, like a secret?

Run `git rm --cached config/.env`, which removes it from Git's index while leaving it on disk, add the file to `.gitignore`, then commit. New copies of the file will stay ignored. The already-leaked history still contains it, though.

### What does a trailing slash mean in a gitignore pattern?

It restricts the pattern to directories. `logs/` matches only a directory named `logs`; `logs` without the slash matches a file or a directory with that name. A leading `!` re-includes a file that an earlier pattern ignored.
