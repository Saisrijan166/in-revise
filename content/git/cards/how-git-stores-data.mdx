## What it is

When you commit, Git saves a [snapshot](term:snapshot): a record of what every tracked file looks like at that moment. It does not store a list of edits. A file that did not change since the last commit is not copied again; Git just links to the copy it already has. Every piece Git stores (a file's content, a folder, a commit) is an object named by a hash of its content, so the same content always gets the same name.

## Why it exists

If Git stored each version as a diff on top of the one before, reading an old version would mean replaying a long chain of patches, and a single corrupted patch would break everything after it. By storing whole snapshots that reuse unchanged files, Git can jump to any version instantly and stays small. Naming every object by its content [hash](term:sha-1) makes the history tamper-evident: change one byte and the id changes, so Git notices corruption and no two different contents collide under one name.

1. Each file's content is stored as a **blob** object, named by the hash of that content.
2. A **tree** object lists the files and sub-folders in one directory, pointing to their blobs and sub-trees.
3. A **commit** object points to the root tree (the full snapshot), plus its parent commit, author and message.
4. On the next commit, unchanged blobs and trees are reused by their hash; only changed objects are new.

See [git objects](card:git-objects) for the four object types in detail.

## Rules and defaults

| What | Value | Note |
|---|---|---|
| Storage model | Snapshots | A commit points to a full tree, not a diff |
| Object name | Hash of content | Same content gives the same id |
| Default hash | SHA-1 | 40-hex-character id; a hardened SHA-1 since Git 2.13 |
| SHA-256 | Supported, opt-in | Set at `git init --object-format=sha256`; not usable by old Git, limited server support |

- `git diff` still shows line-by-line differences, but Git computes them on the fly from two snapshots; it does not store them.

## Common mistakes

- **"Git stores diffs between commits."** It stores snapshots and reuses unchanged files; diffs are computed when you ask for them.
- **"A new commit copies every file again."** Only changed files become new blobs. Unchanged files are linked by their existing hash.
- **"Git has moved to SHA-256 by default."** SHA-1 is still the default object format; SHA-256 is an opt-in repository format.

## Interview Qs

### Does Git store snapshots or diffs?

Snapshots. Each commit points to a tree that captures the whole project at that moment. Unchanged files are reused by reference, so snapshots are cheap. Git computes diffs on demand; it does not store them.

### How does Git name its objects?

By the hash of their content (content addressing). The same content always produces the same id, and changing one byte changes the id, which makes the history tamper-evident and lets identical files share one blob.

### Which hash does Git use?

SHA-1 is still the default object format, producing a 40-character hex id; Git has used a hardened SHA-1 since 2.13. SHA-256 repositories are supported as an opt-in format but are not readable by older Git and have limited protocol support.
