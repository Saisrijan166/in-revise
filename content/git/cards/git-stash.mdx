## What it is

Git stash takes the changes you have not committed and saves them aside, then returns your working tree to the last commit ([HEAD](term:head)). The changes are not lost; they sit in a stash entry you can bring back later. By default it saves your tracked changes, both [staged](term:staging-area) and unstaged. New untracked files are left where they are unless you ask for them.

## Why it exists

You are halfway through a feature when a manager asks for an urgent fix on another branch. Your work is not ready to commit, and Git will not let you [switch branches](card:switching-branches) if the switch would overwrite your changes. Without stash you would make a throwaway commit just to park the work. Stash gives you a clean tree in one command, lets you do the urgent fix, and then restores exactly where you were.

## How it works

<Steps label="Park work and bring it back">
  <Step title="Save">`git stash` records your tracked changes and reverts the working tree to HEAD. Add `-u` to also stash untracked files.</Step>
  <Step title="Switch and work">Move to another branch, fix the urgent thing, and commit it there.</Step>
  <Step title="Come back">Return to your branch. The stash is still in the list, newest at `stash@{0}`.</Step>
  <Step title="Restore">`git stash pop` reapplies the changes and removes the entry; `git stash apply` reapplies but keeps it.</Step>
</Steps>

## Example

A quick shelf-and-restore while handling an urgent branch:

```bash
git stash
git stash list
git switch hotfix
git switch -
git stash pop
```

```text output
Saved working directory and index state WIP on feature-login: 9a1c2e4 Add form
stash@{0}: WIP on feature-login: 9a1c2e4 Add form
Switched to branch 'hotfix'
Switched to branch 'feature-login'
Dropped refs/stash@{0} (f30ab2c...)
```

What to notice:

- `git stash` reported a clean save and named the entry `stash@{0}`.
- `git switch -` jumps back to the previous branch.
- `git stash pop` reapplied the changes and then dropped the entry, so the list is now empty. If the reapply had hit a conflict, Git would keep the entry so nothing is lost.

## Rules and defaults

| What | Default | Note |
|---|---|---|
| Saved content | Tracked changes | Modified and staged tracked files |
| Untracked files | Not stashed | Add `-u` / `--include-untracked` |
| Ignored files | Not stashed | Add `-a` / `--all` |
| Storage | A list | `stash@{0}` newest; `drop` one, `clear` all |

- A stash is not tied to a branch, so you can apply it on any branch.
- `git stash clear` discards all entries and they are hard to recover; use it with care.

## Common mistakes

- **"Stash saved my new files too."** Untracked files are skipped by default. Use `git stash -u`.
- **"pop and apply are the same."** `pop` removes the entry after a successful reapply; `apply` always keeps it. On a conflict, `pop` also keeps it.
- **"Stash belongs to this branch."** It does not. You can apply the same stash on a different branch.

## Interview Qs

### What does git stash do?

It saves your uncommitted tracked changes to a separate entry and resets the working tree to HEAD, giving you a clean tree. You bring the changes back later with `git stash apply` or `git stash pop`. It is useful when you must switch tasks mid-work.

### Does git stash include untracked files?

No, not by default. It saves only tracked changes, staged and unstaged. Pass `-u` (or `--include-untracked`) to add untracked files, and `-a` (or `--all`) to also include ignored files.

### Difference between git stash apply and git stash pop?

Both reapply the stashed changes to the working tree. `apply` leaves the stash in the list so you can reuse it; `pop` removes it after a successful reapply. If the reapply conflicts, `pop` keeps the stash so you do not lose it.
