## What it is

`git diff` shows the exact lines that changed between two versions of your files. Which two versions depends on how you call it. Plain `git diff` compares your working directory with the [staging area](term:staging-area), so it shows changes you have not staged yet. `git diff --staged` compares the staging area with the last commit, so it shows what your next commit will save. You can also diff any two commits or branches.

## Why it exists

Before you stage or commit, you want to read exactly what you are about to save, line by line, not just a list of file names. [git status](card:git-status) tells you which files changed; `git diff` tells you how. Because staging splits your work into "staged" and "not staged", one diff view is not enough: you need to see the unstaged part and the staged part separately so you commit the right lines and catch mistakes like a stray debug print.

## How it works

| Command | Compares | Shows |
|---|---|---|
| `git diff` | Working directory vs staging area | Changes not staged yet |
| `git diff --staged` | Staging area vs last commit | What the next commit will save |
| `git diff HEAD` | Working directory vs last commit | All changes, staged and not |
| `git diff A B` | Commit/branch A vs B | What differs between the two |

1. A change starts in the working directory, where plain `git diff` shows it.
2. After `git add`, that change moves to the staging area: it leaves plain `git diff` and appears in `git diff --staged`.
3. `--cached` is an exact alias of `--staged`.
4. Give two commits or branch names to compare any two points in history.

## Example

```bash
git add app.java
git diff
git diff --staged
```

```text output
(git diff prints nothing)

diff --git a/app.java b/app.java
-  int timeout = 30;
+  int timeout = 60;
```

What to notice: after `git add`, plain `git diff` is empty because there are no unstaged changes left. The staged edit still exists and shows under `git diff --staged`, which is the precise preview of your next commit.

## Common mistakes

- **Thinking an empty git diff means no changes.** It may just mean everything is staged. Check `git diff --staged` too, or `git diff HEAD` to see both at once.
- **Confusing --staged with the working directory.** `--staged` never looks at unstaged edits; it compares the staging area with the last commit only.

## Interview Qs

### What is the difference between git diff and git diff --staged?

`git diff` compares the working directory with the staging area, showing unstaged changes. `git diff --staged` (alias `--cached`) compares the staging area with the last commit, showing exactly what the next commit will save.

### You staged a change and git diff shows nothing. Why?

Because plain `git diff` only shows unstaged changes, and staging moved your change out of that view. It is now in `git diff --staged`. Use `git diff HEAD` to see staged and unstaged changes together.

### How do you see what changed between two branches?

Run `git diff branch1 branch2`, which shows the line-level differences between the tips of the two branches. The same form works with two commit hashes, for example `git diff HEAD~1 HEAD`.
