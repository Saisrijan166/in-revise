## What it is

A good commit records one logical change and explains it in a clear message. The message has a short subject line in the imperative mood ("Add retry to webhook"), a blank line, then a body saying why. [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) is a popular format that prefixes the subject with a type, such as `feat:` or `fix:`, to make history machine-readable.

## Why it exists

History is only useful if you can read it. When commits lump many unrelated changes under a vague message like "updates", you cannot tell what each commit did, you cannot revert just one change, and tools like [git bisect](card:git-bisect) point you at a huge commit that touched everything. Small, well-described commits keep each change findable and reversible on its own.

## How it works

| Part | Rule | Example |
|---|---|---|
| Scope | one logical change per commit | the feature, or the fix, not both |
| Subject | imperative, about 50 chars | `Add rate limit to login` |
| Body | wrap text; say *why*, not *what* | "Prevents brute-force attempts" |
| Type (optional) | Conventional Commits prefix | `feat:`, `fix:`, `docs:` |

1. Make one logical change and stage exactly that change.
2. Write the subject as a command: "Fix", "Add", "Remove", not "Fixed" or "Fixes".
3. In Conventional Commits, start with a type: `feat:` for a new feature (a MINOR version), `fix:` for a bug fix (a PATCH version); a `!` or `BREAKING CHANGE:` footer marks a MAJOR change.
4. Keep committing small, so each commit builds and passes tests on its own.

## Example

```bash
git add src/auth/reset.js
git commit -m "feat(auth): add password reset via email token"
```

```text output
[main 4a2f9c1] feat(auth): add password reset via email token
 1 file changed, 24 insertions(+)
```

What to notice:

- The subject names one change in imperative mood, with a `feat(auth):` type and scope. A reader scanning `git log --oneline` learns exactly what this commit did.
- Only the one file for this change is staged, so the commit is atomic and can be reverted on its own.

## Common mistakes

- **Vague messages** like "updates", "fix stuff" or "wip". They make the log useless and hide what actually changed.
- **Mixing changes.** Reformatting, a bug fix and a new feature in one commit cannot be reviewed or reverted separately.
- **Past-tense subjects** ("Added login"). The convention is imperative, matching Git's own generated messages ("Merge branch...").

## Interview Qs

### What makes a commit "atomic"?

It contains exactly one logical change and nothing else, and it builds and passes tests on its own. That lets you review, revert or cherry-pick that single change without dragging in unrelated work.

### What is Conventional Commits?

A message convention of `type(scope): description`, such as `feat(auth): add reset`. `feat` marks a new feature (MINOR), `fix` a bug fix (PATCH), and a `!` or `BREAKING CHANGE:` footer a MAJOR change. Tools can then generate changelogs and version numbers automatically.

### Why write small commits instead of one big one?

Small commits are easier to review, and when a bug appears `git bisect` lands on a tiny commit whose few lines reveal the cause. One large commit forces reviewers and bisect to sort through many unrelated changes.
