## What it is

git pull is [fetch plus integrate](card:fetch-pull-push). When your branch and the remote branch have both gained new commits (they diverged), Git must decide how to combine them. The three choices are: merge (make a merge commit), rebase (replay your commits on top of the remote's), and fast-forward only (do it only if no new commit is needed, else refuse). Since Git 2.27, a diverged pull with no strategy set stops and asks you to pick one; the unset default is fast-forward only, which fails.

## Why it exists

If only one side moved, pull can just fast-forward and there is no decision. But when both sides committed, the histories have genuinely split, and Git cannot guess whether you want a merge commit or a linear rebase. Picking silently surprised people, so Git now requires an explicit choice. Teams also want one house style for everyone, which the config options provide.

## How it works

| Strategy | Command | Result when diverged |
|---|---|---|
| Merge | `git pull --no-rebase` | Merge commit joining both lines |
| Rebase | `git pull --rebase` | Your commits replayed on top; linear history |
| Fast-forward only | `git pull --ff-only` | Refuses unless no merge is needed |

1. pull fetches the remote commits first.
2. If your branch can simply move forward, it fast-forwards under any strategy.
3. If histories diverged, the chosen strategy decides: merge adds a commit, rebase rewrites your local commits, ff-only stops and does nothing.

## Example

Set a default once, then pull without flags:

```bash
git config pull.rebase true
git pull
```

```text output
Successfully rebased and updated refs/heads/main.
```

What to notice:

- `pull.rebase true` makes every later `git pull` rebase your commits onto origin, so no merge commits appear from pulling.
- Per-pull, `git pull --rebase` or `git pull --no-rebase` overrides the config for one command.
- `git config pull.ff only` makes pull refuse a diverged update instead, so you integrate deliberately.

## Rules and defaults

| What | Default | Where |
|---|---|---|
| Integration method once you choose | merge (pull.rebase is false) | git config |
| Unconfigured diverged pull | stops and makes you choose (unset default --ff-only, which fails) | since Git 2.27 |

- **Per command:** `--rebase`, `--no-rebase`, `--ff-only`.
- **Persisted:** `pull.rebase true/false` and `pull.ff` (`true`, `false`, or `only`); `--global` applies to all repos.
- Rebasing rewrites your local commits, so avoid it on commits you have already shared (same caution as [git rebase](card:git-rebase)).

## Common mistakes

- **"pull never changes history."** With --rebase (or pull.rebase true), pull rewrites your local commits onto the remote base; they get new commit IDs.
- **"A merge commit from pull is a bug."** It is what merge does on a diverged pull (pull.rebase false). Use --rebase or --ff-only if you do not want it.

## Interview Qs

### What does git pull do when the branches have diverged?

Since Git 2.27, with no strategy set it stops and asks you to choose (the unset default is --ff-only, which fails). Choosing merge creates a merge commit, --rebase replays your commits on top for a linear history, and --ff-only refuses unless it can fast-forward.

### Why does Git 2.27+ ask you to choose a pull strategy?

Because a diverged pull can merge or rebase, and silently picking one surprised people. Git now stops and asks you to set pull.rebase (true or false) or use --ff-only, so the behaviour is explicit and consistent.

### How do you make pull always rebase?

Set it in config: git config --global pull.rebase true. Then every git pull rebases your local commits onto the remote instead of creating a merge commit. Use pull.ff only to make pull refuse a diverged update instead.
