## What it is

`git commit` saves a snapshot of the [staging area](term:staging-area) into your repository's history, with a short message describing the change and your name and email as the author. It records only what is staged, so the commit is exactly the set of changes you prepared with [git add](card:staging-and-add). The snapshot is saved on your own machine; sharing it is a separate step, [git push](card:git-push).

## Why it exists

As you work you need fixed points you can return to, compare against, and explain to teammates. A commit is that point: a labelled snapshot of the project at one moment. Without commits you would have only the current files, with no history of what changed, when, or why. Because a commit saves only staged changes, you decide exactly what each one contains, so the history reads as a clear list of steps rather than one big blob.

## How it works

<Steps>
<Step title="Stage">Run git add so the staging area holds exactly the changes you want to save.</Step>
<Step title="Commit">Run git commit -m "message". Git snapshots the staged changes and records the message, author and time.</Step>
<Step title="Confirm">git log now shows the new commit at the top. It is saved locally only.</Step>
</Steps>

1. Git takes the content currently in the staging area, not the working directory, and writes it as a new commit.
2. It attaches your message, your configured author name and email, the time, and a link to the previous commit.
3. The new commit is stored locally. `git push` later sends it to the remote.

## Example

```bash
git config user.name "Asha Rao"
git config user.email "asha@example.com"
git add refund.java
git commit -m "Add refund endpoint"
```

```text output
[main 9f2a1c4] Add refund endpoint
 1 file changed, 12 insertions(+)
```

What to notice: only `refund.java` was staged, so only it is in the commit. The author `Asha Rao` comes from `git config`, not from the login name. `git commit -am "..."` would have staged tracked edits automatically, but a brand-new file still needs `git add` first.

## Not to be confused with

Staging, committing and pushing are three steps on the way to your team ([git add](card:staging-and-add) → git commit → [git push](card:git-push)). `git add` prepares what to save. `git commit` saves it to your local history. `git push` uploads your local commits to the remote so others can see them. See [add vs commit vs push](compare:add-vs-commit-vs-push). Rule: a commit is local until you push.

## Common mistakes

- **Expecting unstaged edits in the commit.** Only staged changes are saved. Edits made after `git add`, and untracked files, are left out.
- **Using -am for a new file.** `-a` stages tracked edits and deletes only, never new files. Add new files explicitly first.
- **Thinking commit shares the work.** It is local. Teammates see it only after `git push`.

## Interview Qs

### What exactly does a commit save?

A snapshot of the staging area, not the whole working directory. It records only staged changes, plus a message, the author's name and email from `git config`, the time, and a link to the parent commit.

### What is the difference between git commit -m and git commit -am?

`-m` sets the message inline and commits whatever is already staged. `-am` first stages edits and deletes of tracked files, then commits. `-am` does not stage new untracked files, so those still need an explicit `git add`.

### Where does the commit author come from?

From `git config user.name` and `user.email`. You usually set them once with `git config --global`. They are not taken from your system login name, which is why committing with the wrong config shows the wrong author.
