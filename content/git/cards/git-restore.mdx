## What it is

`git restore` is the command for fixing files and the [staging area](term:staging-area) without touching the branch. Plain `git restore <file>` discards edits you have not staged yet. With `--staged` it does the opposite job: it unstages a file (removes it from the next commit) but leaves your edits in place. With `--source=<commit>` it brings a file back as it was in an older commit.

## Why it exists

You often need to undo one file, not the whole branch. Before Git 2.23 you used [git checkout](card:switching-branches) to discard file edits and `git reset` to unstage, two commands that also did bigger, unrelated jobs, which was confusing and easy to get wrong. `git restore` was added so file-level undo has its own clear command that can never accidentally move the branch or change history.

## How it works

<Steps label="What restore does to one file">
  <Step title="git restore <file>">Copies the file from the staging area back into your working copy, discarding unstaged edits.</Step>
  <Step title="git restore --staged <file>">Copies the file from HEAD into the staging area, so it is unstaged. The working copy and its edits are untouched.</Step>
  <Step title="git restore --source=<commit> <file>">Copies the file from that commit into your working copy, bringing back an old version.</Step>
</Steps>

- The default source is the staging area; with `--staged` the default source is [HEAD](term:head).
- It changes files and the index only. The branch pointer and commit history never move.

## Example

```bash
git add app.js config.yaml          # staged both by mistake
git restore --staged config.yaml    # unstage one; edits kept
git restore app.js                  # discard unstaged edits in app.js
git status -s
```

```text output
 M config.yaml
```

What to notice: after `git restore --staged`, `config.yaml` shows as modified but unstaged, so its edits survived. `app.js` is gone from the list because its unstaged edits were discarded and it now matches the staged version. Nothing here moved the branch.

## Not to be confused with

`git restore` works on file contents and staging; [git reset](card:git-reset) moves the branch to another commit and can also change staging and files. For dropping edits in one file, reach for restore; for undoing a whole commit, reach for reset. See [restore vs reset](compare:restore-vs-reset).

## Common mistakes

- **Expecting --staged to delete edits.** It only unstages; the edits stay. The destructive form is plain `git restore <file>`.
- **Thinking restore can undo a commit.** It cannot move the branch, so it never removes a commit. That is a job for `git reset` or `git revert`.

## Interview Qs

### How do you unstage a file without losing your changes?

Run `git restore --staged <file>`. It copies the file from HEAD into the staging area so it is no longer staged, while leaving your edits in the working copy untouched.

### How do you throw away unstaged changes in one file?

`git restore <file>` copies the file back from the staging area (or HEAD), discarding unstaged edits. The edits are not committed anywhere, so this cannot be undone.

### Why was git restore added when checkout already existed?

`git checkout` did too many jobs: switching branches and changing files. Git 2.23 split it into `git switch` for branches and `git restore` for files, so each command is clearer and safer.
