## What it is

A merge conflict happens when a [merge](card:git-merge) cannot combine two branches on its own, because both branches changed the same lines of the same file. Git stops partway, keeps `HEAD` where it was, and writes conflict markers into the file so you can see both versions. You then decide what the final text should be, remove the markers, and finish the merge yourself.

## Why it exists

If both sides edited the same line differently, there is no safe automatic answer: picking one would silently drop the other person's work. Git refuses to guess. Instead it stops and hands the decision to you, marking exactly where the two versions disagree. Without this, a merge could quietly throw away code. The cost is that you must resolve the spot by hand before the merge can complete.

## How it works

<Steps label="Resolving a conflict">
  <Step title="Git stops and marks">Git reports each conflicted file and writes markers: your version, a `=======` divider, then their version.</Step>
  <Step title="See what is conflicted">Run `git status` to list every file needing resolution.</Step>
  <Step title="Edit the file">Keep the correct code (yours, theirs, or a blend) and delete the `<<<<<<<`, `=======` and `>>>>>>>` lines.</Step>
  <Step title="Stage it">Run `git add <file>` to mark it resolved; repeat for each conflicted file.</Step>
  <Step title="Finish">Run `git commit` (or `git merge --continue`) to record the merge, or `git merge --abort` to cancel.</Step>
</Steps>

Changes on different lines merge cleanly on their own; only real overlaps stop the merge.

## Example

A file in conflict looks like this. Everything between the markers is for you to resolve:

```text
<<<<<<< HEAD
int timeout = 30;
=======
int timeout = 60;
>>>>>>> feature-login
```

What to notice: the lines above `=======` are your branch's version (`HEAD`), the lines below are the incoming branch's version. You replace the whole block with the single final line you want, for example `int timeout = 60;`, then delete the three marker lines. After saving, `git add` the file and commit. Leaving even one marker line in the file is a common cause of broken builds.

## Rules and defaults

- During a conflict `HEAD` stays put and `MERGE_HEAD` points at the branch being merged; the index holds three versions of each conflicted file (ancestor, yours, theirs), which `git ls-files -u` shows.
- A merge commit is only created after every conflict is staged.
- `git merge --abort` requires that you have not already committed the merge.

## Common mistakes

- **Committing with markers still in the file.** The `<<<<<<<` lines become real code and break the build. Search for them before committing.
- **Running git add before actually resolving.** `git add` just marks a file as resolved; if you have not fixed the overlap, you commit broken code.
- **Forgetting other conflicted files.** `git status` lists them all; resolve every one before committing.

## Interview Qs

### Why do merge conflicts happen?

Because both branches changed the same lines of the same file, so Git has no safe way to combine them automatically. It stops, marks the spot in the file, and asks you to choose. Changes on different lines merge without a conflict.

### How do you resolve a merge conflict?

Open each conflicted file, keep the correct code, and delete the `<<<<<<<`, `=======` and `>>>>>>>` markers. Then `git add` each resolved file and run `git commit` (or `git merge --continue`). Use `git status` to find all conflicted files.

### How do you cancel a merge that went wrong?

Run `git merge --abort`. It stops the in-progress merge and resets your branch and working tree to the state just before the merge, as long as the merge has not been committed yet.
