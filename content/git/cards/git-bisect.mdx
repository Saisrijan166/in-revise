## What it is

`git bisect` finds the exact commit that introduced a bug by running a binary search over your history. You tell Git one commit where the bug is present ("bad") and one older commit where it is absent ("good"). Git repeatedly checks out a commit halfway between them and asks you to test it, narrowing the range by half each time until only the first bad commit is left.

## Why it exists

A bug that was not there a few hundred commits ago is somewhere in between, but testing every commit back in time could mean hundreds of builds. Binary search turns that into roughly log2(N) tests: about 10 for 1000 commits. Bisect automates the bookkeeping of which commits are still suspects, so you only have to answer "good or bad?".

## How it works

<Steps label="Bisecting a bug">
<Step title="Start">Run git bisect start.</Step>
<Step title="Mark the ends">git bisect bad on a commit with the bug, git bisect good on an older commit without it.</Step>
<Step title="Test the middle">Git checks out a commit halfway between. Build and test it.</Step>
<Step title="Mark the result">git bisect good or git bisect bad. Git halves the range and checks out a new middle commit.</Step>
<Step title="Repeat until found">Keep testing and marking until Git names the first bad commit.</Step>
<Step title="Reset">git bisect reset returns you to your original HEAD.</Step>
</Steps>

- Each answer halves the remaining suspects, so the number of tests grows logarithmically with history length.
- `git bisect run <cmd>` automates it: your script's exit code decides each step, so Git finds the commit with no manual testing.

## Example

Automate the search with a test script that exits non-zero when the bug is present:

```bash
git bisect start HEAD v2.4.0   # HEAD is bad, v2.4.0 is good
git bisect run ./check_bug.sh
git bisect reset
```

```text output
Bisecting: 255 revisions left to test after this (roughly 8 steps)
...
d4e5f6a7 is the first bad commit
    feat: switch payment client to new timeout
```

What to notice:

- `git bisect run` ran the script on each middle commit, using exit 0 as good and 1-127 (except 125) as bad, so no manual testing was needed.
- It found the first bad commit in about 8 steps out of 256 revisions. `git bisect reset` then restored the branch you started on. Exit code 125 would have skipped a commit that cannot be built or tested.

## Common mistakes

- **Forgetting git bisect reset.** Until you reset, you are left on a detached middle commit, not your branch.
- **Scripting exit codes wrong.** For `git bisect run`, the test must exit 0 for good and 1-127 (not 125) for bad; 125 means "untestable, skip". A build failure that returns 126 or 127 is treated as bad.

## Interview Qs

### What problem does git bisect solve?

It finds the commit that introduced a bug using binary search. You mark a good and a bad commit; Git checks out the middle one each step and you mark it good or bad, halving the range until the first bad commit is identified, in about log2(N) tests.

### How do you automate a bisect?

Write a script that tests the code and returns an exit code: 0 for good, 1-127 (except 125) for bad, 125 for untestable. Run `git bisect start`, mark the bad and good ends, then `git bisect run ./script`. Git tests each middle commit by itself.

### How do you end a bisect session?

Run `git bisect reset`. It cleans up the bisection state and returns you to the commit you had checked out before starting. Without it you stay on the detached commit Git checked out during the search.
