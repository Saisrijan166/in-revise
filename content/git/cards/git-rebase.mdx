## What it is

Rebase takes the commits on your branch and replays them, one by one, on top of a different base commit, usually the latest tip of another branch. The result is a straight-line history with no [merge](card:git-merge) commit. Because each replayed commit gets a new parent, Git rewrites it, so it receives a new commit id even though the change inside it is the same.

## Why it exists

When your feature branch falls behind main, you want main's newer work without a merge commit cluttering the history. Rebase moves your commits on top of the latest main, so the branch reads as if you started from today. A merge would instead record an extra merge commit and keep the history branching. Rebase keeps it linear, which many teams prefer for a clean, readable log. The cost is that it rewrites commits, so it is unsafe on shared history.

1. Git finds where your branch split from the new base (the common ancestor).
2. It sets the commits you made after that point aside.
3. It moves your branch to the new base's tip.
4. It replays each saved commit on top, in order; any overlap stops as a conflict to resolve, then `git rebase --continue`.
5. Each replayed commit is a new object with a new id. See the [reflog](card:git-reflog) if you need to recover the originals.

## Example

Interactive rebase to tidy the last three commits before sharing:

```bash
git switch feature-login
git rebase -i HEAD~3
```

```text output
pick a1b2c3d Add login form
squash e4f5g6h Fix typo
reword i7j8k9l Handle empty password
```

What to notice: in the editor you change the word in front of each commit. `pick` keeps it, `squash` folds it into the commit above, `reword` keeps it but lets you rewrite its message, and `drop` deletes it. Here two commits become one and the last gets a better message. After saving, every rebased commit has a new id, so if the branch was pushed you run `git push --force-with-lease`.

## Rules and defaults

| Interactive command | What it does |
|---|---|
| `pick` | Keep the commit as is |
| `reword` | Keep it, edit its message |
| `squash` | Merge it into the previous commit |
| `drop` | Remove the commit |

- Rebased commits always get new ids, because their parent changed.
- The golden rule: do not rebase commits that others have already pulled.
- After rebasing a pushed branch, use `git push --force-with-lease`; it refuses if the remote moved since you last fetched, protecting a teammate's push. Plain `--force` has no such check.

## Common mistakes

- **Rebasing a shared branch like main.** It rewrites history everyone has, causing divergence and duplicate commits. Merge shared branches instead.
- **Using plain --force after a rebase.** It can silently overwrite a teammate's new commits; `--force-with-lease` checks first and refuses if the remote changed.
- **Thinking rebase and the original commits coexist.** The originals are replaced on your branch; only the [reflog](card:git-reflog) still holds them for a while.

## Interview Qs

### What does git rebase do, and how does it differ from merge?

Rebase replays your commits on top of another branch's tip, giving a linear history with no merge commit. Merge instead records a merge commit that joins both histories. Rebase rewrites commits (new ids); merge keeps the original commits.

### What is the golden rule of rebasing?

Never rebase commits that others have already pulled. Rebasing rewrites those commits with new ids, so everyone else's branch still points at the old ones. Their next pull diverges and may duplicate commits. Rebase only local, unshared commits.

### Why do you need --force-with-lease after a rebase?

Rebase rewrites commit ids, so the remote branch and your local branch diverge and a normal push is rejected. `--force-with-lease` overwrites the remote only if it has not changed since you last fetched, so it will not silently erase a teammate's push.
