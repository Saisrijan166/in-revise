## What it is

Squash merge combines every commit on a feature branch into a single new commit on the target branch. You can do it with `git merge --squash`, or with the "Squash and merge" button on a GitHub or GitLab pull request. The target branch ends up with one commit for the whole feature, instead of all the small commits that were made along the way.

## Why it exists

Feature branches often fill up with messy commits: "wip", "fix typo", "try again". You do not want all of that noise on main. Squash merge lets the branch stay messy while main gets one clean, meaningful commit per feature. This keeps the main history easy to read and easy to revert: one commit undoes the whole feature. The cost is that the branch's individual commits, and the detail in their messages, do not reach main.

## How it works

<Steps label="Squash merging with the CLI">
  <Step title="Switch to the target">`git switch main` (or whichever branch should receive the feature).</Step>
  <Step title="Squash">Run `git merge --squash feature`. Git applies the branch's combined change to your working tree and index but does not commit.</Step>
  <Step title="Commit once">Run `git commit`. Write one message describing the whole feature. This single commit is all that lands on main.</Step>
</Steps>

Unlike a normal [merge](card:git-merge), `--squash` makes no merge commit and records no second parent, so Git does not mark the feature branch as merged.

## Example

Folding a noisy feature branch into one commit on main:

```bash
git switch main
git merge --squash feature-login
git commit -m "Add login feature"
```

```text output
Squash commit -- not updating HEAD
Automatic merge went well; stopped before committing as requested
[main 9d1c2b3] Add login feature
 2 files changed, 48 insertions(+)
```

What to notice: the squash step says it "stopped before committing as requested", so no commit exists yet; `git commit` then makes the one combined commit `9d1c2b3`. All of `feature-login`'s small commits are rolled into it. Because there is no merge commit, `git branch --merged` will not list `feature-login`.

## Rules and defaults

- `git merge --squash` stages the change but never commits; you commit yourself. It cannot be combined with `--commit`.
- It records no merge commit and no second parent, so the branch is not seen as merged (deleting it may need `git branch -D`).
- GitHub's "Squash and merge" produces the same single-commit result on the base branch; the PR is still marked merged on the platform.

## Common mistakes

- **Expecting --squash to commit by itself.** It stops before committing on purpose; you must run `git commit`.
- **Thinking the feature's commits are preserved on main.** They are folded into one; the individual commits and messages are not on main.
- **Deleting the branch with -d after a squash.** Git does not see it as merged, so `-d` may refuse; use `-D` once you are sure.

## Interview Qs

### What is a squash merge?

It combines all of a branch's commits into one commit on the target branch. `git merge --squash` stages the combined change and you commit once; GitHub's "Squash and merge" does the same for a pull request. Main stays clean with one commit per feature.

### What is the trade-off of squashing?

You lose the branch's individual commits and their messages on the target branch, so the step-by-step history of the feature is gone. In return, main is tidy and each feature is one revertable commit. Keep the branch if you need the detailed history.

### Why does git merge --squash not create a commit?

By design: it applies the combined change to your working tree and index, then stops so you can write one message for the whole feature and commit yourself. It also records no merge commit, so Git does not mark the branch as merged.
