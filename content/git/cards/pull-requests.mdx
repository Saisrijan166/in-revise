## What it is

A pull request (PR), called a merge request on GitLab, is a request to review the commits on one [branch](card:git-branches) and merge them into another, usually a feature branch into main. It is a feature of the hosting platform, not a Git command. The PR page shows the diff, lets teammates comment and approve, runs automated checks, and gives a button to merge when everyone is satisfied.

## Why it exists

On a team you do not want everyone pushing straight to main: a bad commit would break the shared branch for all. A PR adds a gate. The change is visible, discussed and tested before it lands, so problems are caught early and there is a record of who approved what. Without PRs, review would be ad hoc and main could receive unreviewed or untested code at any time.

## How it works

<Steps>
  <Step title="Branch">Create a feature branch from the latest main and commit your work there.</Step>
  <Step title="Push">Push the branch to the remote with `git push -u origin <branch>`.</Step>
  <Step title="Open PR">On the platform, open a pull request from your branch into main.</Step>
  <Step title="Review">Teammates read the diff, comment and approve; you push fixes, which update the same PR.</Step>
  <Step title="Checks">Automated checks (CI) run; protected main can require them to pass.</Step>
  <Step title="Merge">Once approved and green, merge, choosing a merge commit, squash, or rebase.</Step>
</Steps>

1. The PR tracks a branch, so new pushes to that branch update the PR automatically.
2. A [protected branch](term:protected-branch) can block the merge until approvals and checks are satisfied.
3. Merging can create a merge commit, [squash into one commit](card:squash-merge), or rebase the commits onto main.

## Rules and defaults

- **Not a Git command:** you push with Git, but the PR is created and merged on the platform.
- **Protected branches:** rules on main can require a number of approvals, passing status checks, and an up-to-date branch before merge.
- **Merge methods:** merge commit keeps all commits plus a merge node; squash combines them into one; rebase replays them onto main without a merge commit.
- Pushing more commits to the branch updates the open PR; you do not open a new one.

## Common mistakes

- **"A PR merges code by itself."** It only proposes the merge. A person (or an automation rule) still has to approve and click merge.
- **"PRs are part of Git."** Git has branches, commits and pushes; PRs are added by GitHub, GitLab and similar platforms.

## Interview Qs

### What is a pull request?

A request on a hosting platform to review the commits on one branch and merge them into another, usually a feature branch into main. It shows the diff, collects reviews and comments, runs checks, and offers a button to merge when approved.

### What is a protected branch?

A branch, often main, with rules that must be met before anyone can merge or push: for example required approvals, passing status checks, or an up-to-date branch. It stops unreviewed or broken code from reaching the shared branch.

### What merge options does a PR offer?

A merge commit keeps every commit plus a merge node; squash and merge combines them into a single commit on the target branch; rebase and merge replays the commits onto the target without a merge commit. Squash is popular for a tidy history.
