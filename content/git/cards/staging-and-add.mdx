## What it is

`git add` copies changes from your working directory into the [staging area](term:staging-area), the list of exactly what your next commit will save. Staging is a separate step so you can group related edits into one clean commit and leave the rest for later. Nothing is saved to history by `git add`; it only prepares the next commit. You confirm what is staged with [git status](card:git-status).

## Why it exists

You often change several things at once: a bug fix, a stray debug line, an unrelated rename. If every edit went straight into a commit, your history would be a jumble and reviewers could not follow it. The staging area lets you pick which changes belong together and commit just those, so each commit tells one story. It also lets you split one messy file across two commits with `git add -p`.

## How it works

```bash
git add app.java          # stage one file
git add .                 # current folder and below
git add -A                # the whole repository
git add -p                # choose chunks interactively
```

1. `git add <file>` stages that file. `git add .` stages every add, edit and delete under the folder you are standing in.
2. `git add -A` stages every add, edit and delete across the whole repository, no matter where you run it.
3. `git add -u` stages edits and deletes of already-tracked files, but adds no new files.
4. `git add -p` walks through each changed chunk (a "hunk") and asks whether to stage it, so one file's changes can go into different commits.

What to notice: `.` is a folder; `-A` is the whole tree. Since Git 2.0 both also stage deletions, which older Git did not do.

## Rules and defaults

| Command | New files | Edits | Deletes | Scope |
|---|---|---|---|---|
| `git add .` | Yes | Yes | Yes | Current folder and below |
| `git add -A` | Yes | Yes | Yes | Whole repository |
| `git add -u` | No | Yes | Yes | Tracked files only |
| `git add -p` | As chosen | As chosen | As chosen | Chunks you pick |

- Staging copies the file's content as it is now. If you edit the file again after staging, the new edit is not staged until you `git add` again.
- `git add` never writes to history; only `git commit` does.

## Common mistakes

- **Editing after staging and expecting the new edit.** Staging is a snapshot of that moment. Change the file again and you must re-stage it.
- **Using git add . from a subfolder and missing changes elsewhere.** It only covers the current folder and below; use `git add -A` for the whole repo.
- **Thinking git add saves your work.** It does not. Until you commit, a staged change is not in history.

## Interview Qs

### What is the staging area and why does Git have it?

It is the list of changes your next commit will save. Git has it so you can choose exactly what goes into each commit, grouping related edits and leaving others out, which keeps history clean and reviewable.

### What is the difference between git add . and git add -A?

Both stage new, modified and deleted files. `git add .` is limited to the folder you run it from and below; `git add -A` stages across the whole repository regardless of where you stand. Since Git 2.0 both include deletions.

### How do you commit only part of a file's changes?

Use `git add -p`. Git shows each chunk of the file and asks whether to stage it. Stage the chunks you want, leave the rest, then commit. This splits one file's changes across separate commits.
