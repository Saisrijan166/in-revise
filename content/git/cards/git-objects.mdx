## What it is

Everything in Git's database is one of four object types. A **blob** holds the content of a file. A **tree** holds one directory: a list of names, each pointing to a blob or a sub-tree. A **commit** points to one root tree (the whole snapshot) plus its parent and metadata. A **tag object** is an annotated [tag](card:git-tags), pointing to a commit with its own message. Every object is named by a hash of its content, so the same content gets the same name.

## Why it exists

Git needs a storage model that is small, fast and safe to copy. Splitting files into content (blobs) and names (trees) means two identical files are stored once, and renaming a file does not copy its content. Naming every object by its content hash means a repository can be verified: if one byte changes, the hash changes, so corruption and tampering are caught. These four simple object types are enough to represent any version of any project.

## How it works

1. Git stores each file's bytes as a **blob**. The blob has no name of its own.
2. A **tree** lists one folder's entries: a name and mode for each, pointing to a blob (a file) or a sub-tree (a folder).
3. A **commit** points to the root tree, so it captures the full project, and links to its parent(s), author, committer and message.
4. An **annotated tag** becomes a **tag object** that points to the tagged commit and stores the tagger, date and message.

## Example

Look at the type of any object by its hash:

```bash
git cat-file -t HEAD
git cat-file -p HEAD
```

```text output
commit
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 9a1c2e4f...
author Asha <asha@example.com> 1730520000 +0530
committer Asha <asha@example.com> 1730520000 +0530

Add payment form
```

What to notice:

- `git cat-file -t` prints the object's type; here `HEAD` resolves to a `commit`.
- `-p` pretty-prints it: the commit points to one `tree`, lists its `parent`, and carries the author, committer and message.
- The tree line is itself a hash; running `git cat-file -p` on it would list the blobs and sub-trees.

## Rules and defaults

| Object | Holds | Points to |
|---|---|---|
| Blob | File content bytes | Nothing |
| Tree | Names and modes for one directory | Blobs and sub-trees |
| Commit | Author, committer, message | One root tree, parent commit(s) |
| Tag object | Tagger, date, message | The tagged commit (usually) |

- The name and path of a file are never in its blob; they are in the tree that references it.

## Common mistakes

- **"A blob knows its file name."** It does not. The name lives in the tree. This is why identical content is stored as one blob.
- **"A commit stores the whole file list itself."** The commit points to a tree, and the tree holds the listing. The commit mainly adds parent links and metadata.
- **"Every tag is a tag object."** Only annotated tags are objects. A lightweight tag is just a reference pointing at a commit, with no object of its own.

## Interview Qs

### What are the four Git object types?

Blob, tree, commit and tag object. A blob is a file's content, a tree is a directory listing names that point to blobs and sub-trees, a commit points to a root tree plus parents and metadata, and a tag object is an annotated tag. Each is named by its content hash.

### Where is a file's name stored, in the blob or the tree?

In the tree. A blob stores only the file's content bytes, with no name or path. The tree object that references the blob supplies the name and mode. This lets two identical files share one blob.

### What does a commit object point to?

One root tree, which captures the full snapshot of the project, and its parent commit (two or more parents for a merge). It also stores the author, the committer and the commit message. It does not store diffs.
