## What it is

These three commands move commits between your repository and a [remote](card:git-remotes). fetch pulls commits down from the remote into remote-tracking branches like origin/main, without changing the branch you are on. pull does a fetch and then integrates those commits into your current branch by merging or rebasing. push sends your commits up to the remote so others can see them.

## Why it exists

Work happens in parallel: you commit locally while teammates commit to the shared repo. You need a way to bring their commits down and send yours up. fetch lets you download and review before changing anything. pull saves a step when you just want to catch up. push shares your finished work. Without these, every copy of the repo would drift apart with no way to reconcile.

## How it works

<Compare id="fetch-vs-pull-vs-push" />

1. `git fetch` downloads commits and updates origin/* tracking branches; your branch and files are untouched.
2. `git pull` runs that fetch, then merges (or rebases) `origin/<branch>` into your current branch.
3. `git push` uploads your new commits to the matching remote branch; it is rejected if the remote has commits you do not have.

## Example

Catch up on the remote, then share a commit:

```bash
git fetch origin
git log --oneline main..origin/main
git pull
git commit -am "Add retry to payment client"
git push
```

```text output
a1b2c3d Fix timeout in payment client
Updating 9f8e7d6..a1b2c3d
Fast-forward
```

What to notice:

- `git fetch` let us see the remote's new commit (`main..origin/main`) before touching our branch.
- `git pull` then fast-forwarded our main to include it.
- After committing, `git push` uploaded our work. It would have been rejected if someone had pushed again in the meantime.

## Rules and defaults

- **fetch is safe:** it never changes your working branch or files; it only updates remote-tracking branches.
- **pull integrates:** it merges by default or rebases with --rebase; since Git 2.27 a diverged pull with no strategy set makes you choose (see [pull strategies](card:pull-strategies)).
- **push needs you to be up to date:** if the remote branch has moved ahead, push is rejected to avoid losing commits; fetch or pull first.
- A plain `git pull` and `git push` use the branch's upstream (see [tracking branches](card:tracking-branches)).

## Common mistakes

- **"fetch and pull are the same."** fetch only downloads; pull downloads and then changes your branch. Prefer fetch when you want to review first.
- **"Force-push to get past a rejected push."** A rejection usually means a teammate pushed; force-pushing overwrites their commits. Pull and integrate instead.

## Interview Qs

### What is the difference between git fetch and git pull?

fetch downloads remote commits into remote-tracking branches like origin/main and leaves your branch unchanged. pull does the same fetch and then merges or rebases those commits into your current branch. fetch is review-first; pull updates you in one step.

### Why might git push be rejected?

Because the remote branch has commits you do not have locally. Pushing would discard them, so Git refuses. You fetch or pull to integrate the remote commits first, resolve any conflict, then push again.

### What does git fetch change on your side?

Only the remote-tracking branches, such as origin/main, and the objects they point to. Your local branches, working files and staging area are untouched until you merge or rebase.
