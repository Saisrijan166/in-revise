## What it is

A fork is a copy of someone else's repository, made under your own account on the hosting platform. It is a GitHub or GitLab feature, not a Git command. You use it when you want to contribute to a project you do not have permission to push to: you own your fork fully, so you can push there and then propose your changes back to the original repository through a [pull request](card:pull-requests).

## Why it exists

Open-source projects let anyone read and [clone](card:init-and-clone) them, but only trusted maintainers can push. Without a fork, an outside contributor would have nowhere to push their work and no way to offer it. A fork gives every contributor a writable copy of the project, so they can build their change in the open and send it back for review. The original repository stays protected from direct, unreviewed pushes.

## How it works

<Steps>
  <Step title="Fork">On the platform, fork the repo; a copy appears under your account.</Step>
  <Step title="Clone the fork">git clone your fork to your machine; origin now points at the fork.</Step>
  <Step title="Add upstream">`git remote add upstream <original-url>` so you can pull the project's new changes.</Step>
  <Step title="Branch and push">Commit on a branch and push it to your fork (origin).</Step>
  <Step title="Open a PR">Open a pull request from your fork's branch to the original repository.</Step>
</Steps>

<Compare id="clone-vs-fork" />

1. You push to the fork (origin), never to the original, which you cannot write to.
2. `upstream` is the original repo; fetch it to keep your fork current.
3. The maintainers review your pull request and merge it into the original.

## Example

Set up remotes after cloning your fork, then sync with the original:

```bash
git clone https://github.com/you/pay.git
cd pay
git remote add upstream https://github.com/acme/pay.git
git remote -v
```

```text output
origin	https://github.com/you/pay.git (fetch)
origin	https://github.com/you/pay.git (push)
upstream	https://github.com/acme/pay.git (fetch)
upstream	https://github.com/acme/pay.git (push)
```

What to notice:

- `origin` is your fork, which you can push to; `upstream` is the original, which you fetch from.
- To update your fork, `git fetch upstream` then merge or rebase `upstream/main`.
- You push your branch to `origin`, then open the pull request to `acme/pay`.

## Rules and defaults

- **Fork gives write access to your copy only:** you own the fork; you still cannot push to the original.
- **Two remotes:** `origin` = your fork, `upstream` = the original, by convention.
- **Syncing:** fetch upstream and integrate regularly, so your branch does not drift far from the project.
- A fork is a platform feature; cloning is the Git command that copies it to your machine.

## Common mistakes

- **"Clone and fork are the same."** Clone copies a repo to your machine; a fork copies it under your account on the server. See [clone vs fork](compare:clone-vs-fork).
- **"Push my fix straight to the original."** You cannot, without write access. Push to your fork and open a pull request instead.

## Interview Qs

### What is a fork and when do you use one?

A fork is a copy of a repository under your own account on the hosting platform. You use it to contribute to a project you cannot push to: you fork it, clone your fork, push your work there, and open a pull request to the original.

### What is the difference between clone and fork?

Clone is a Git command that copies a repo to your machine and sets origin. A fork is a platform feature that makes a copy under your account on the server. You fork when you lack push access, then clone your fork.

### How do you keep a fork up to date with the original?

Add the original repository as a remote named upstream. Run git fetch upstream, then merge or rebase upstream/main into your branch, and push to your fork. This brings the project's new commits into your copy before you continue.
